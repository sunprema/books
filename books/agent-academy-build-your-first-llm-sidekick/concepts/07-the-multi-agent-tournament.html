Tournament Arc · When One Isn't Enough

The Multi-Agent Tournament

Every tournament arc has the same beat: the hero meets someone who fights completely differently, and discovers that raw power was never the only axis. This chapter is that beat — and it opens with a warning, because multi-agent architectures are the single most over-reached-for technique in this whole book.

The rule: do not add a second agent until the first one is instrumented. If you cannot see which tool call went wrong in a single-agent run, you will not be able to tell a coordination bug from a tool bug in a multi-agent one — and they look identical from the outside.

The wall: one context, one job

Kohai is doing fine on a forty-commit release. Now point it at a quarter's worth of work across four repositories, with a security-review pass, a migration-notes pass, and a customer-facing summary in a different voice. Watch what breaks.

It is not that the model gets confused, exactly. It is that one conversation accumulates every commit, every tool result, and every intermediate judgment, and by the time it is writing the customer summary it is reasoning through a haystack of build-log fragments it needed forty turns ago. One agent has one context and one set of instructions, and both are being asked to be four things at once.

Techniques you already have, free

Before building a coordinator, notice that three forms of division-of-labour are already available without one. Reach for these first.

The server-side loop

A server-executed tool already runs its own loop: the model searches, reads results, decides whether to search again, and iterates until it has what it needs — without your application participating. That is delegation with zero code. If a subtask is "go research this," a server tool may already be the sub-agent you were about to write.

Tool search

A common reason people split agents is that one agent has too many tools. But the tool_search tool exists specifically for working with large tool libraries, by discovering and loading tools on demand rather than holding every schema in context. If your motivation for a second agent is "the tool list got long," solve the tool list problem directly.

The advisor tool

The advisor tool pairs a faster executor model with a higher-intelligence advisor model consulted mid-generation. That is a two-model division of labour — cheap model does the volume, expensive model does the strategy — with no coordinator to write, no message passing to debug, and no shared-state problem.

When you genuinely need specialists

Sometimes none of those fit and the work really is several jobs. The shape that survives contact with reality is a coordinator and a small number of specialists, where each specialist is an ordinary chapter-2 loop with its own system prompt and its own narrow tool list.

There is nothing exotic in that picture. A specialist is a function that runs a loop and returns a string. The coordinator is a chapter-2 loop whose tools are those functions — which means everything you already know applies unchanged: schemas describe them, descriptions trigger them, errors come back as results.

def historian(question: str) -> str:
    """A full chapter-2 loop with its own prompt and its own two tools."""
    return run_agent(
        model="claude-haiku-4-5",          # cheap: this is retrieval, not judgment
        system="You answer questions about commit history. Cite hashes.",
        tools=[list_commits_tool, show_commit_tool],
        prompt=question,
    )

COORDINATOR_TOOLS = [{
    "name": "ask_historian",
    "description": (
        "Ask a specialist that can read the repository's commit history. "
        "Call this when you need facts about what changed. Give it one "
        "self-contained question — it cannot see this conversation."
    ),
    "input_schema": {
        "type": "object",
        "properties": {"question": {"type": "string"}},
        "required": ["question"],
        "additionalProperties": False,
    },
    "strict": True,
}]
It cannot see this conversation

That clause in the description is doing real work. Sub-agents do not share context — each one starts from whatever its caller put in its messages, and nothing else. The single most common multi-agent bug is a coordinator delegating "now do the same for the other repo," where "the same" and "the other" mean nothing to a fresh context. Brief precisely, every time. If a specialist needs shared state, write it somewhere both can read.

The economics of delegation

Model choice is a real lever here, and the spread is wide: Haiku 4.5 costs $1 per million input tokens and $5 per million output against Opus 5's $5 and $25. A cheap specialist and an expensive coordinator differ fivefold per token. Retrieval and extraction go to the cheap model; the judgment calls stay with the expensive one.

But count honestly, because delegation is not free. Each sub-agent re-establishes its own context, does its own exploration, and reports back — and then the coordinator reads that report as input tokens. A three-specialist fan-out can easily cost more than one well-scoped agent, and it always costs more latency. The win is not efficiency. The win is that each context stays small enough to reason well in, and each prompt gets to be about one thing.

Delegate when…Stay single when…
The subtasks are genuinely independent and can run in parallel The steps are sequential and each needs the last one's context
A subtask needs a very different system prompt or voice One prompt can honestly describe the whole job
A subtask should run on a cheaper model The saving is smaller than the extra round trips
A subtask should have narrower tool access than the whole run You are only splitting because the tool list got long — use tool search

The boundary question, again

Chapter 3 taught you that tools sort into three execution buckets — user-defined client tools, provider-schema client tools, and server-executed tools — and that the bucket determines what your application is responsible for. A multi-agent design has to answer that same question for every specialist: whose process does this run in, and therefore whose guardrails apply?

This matters more than it sounds. If your Reviewer specialist runs in your process with your handler, chapter 5's boundary holds. If you delegate it to something outside that boundary, you have widened the trust surface, and the fact that the caller was another agent rather than a user changes nothing about it.

Named technique: the fresh-context verifier

If you take one multi-agent pattern from this chapter, take this one. Ask a second agent, with a clean context and no memory of how the work was done, to check the output against the source.

For Kohai: after the draft is written, hand a verifier the draft and the list_commits tool, with one instruction — every hash cited in this draft must appear in the commit list; report any that do not. It is cheap, it runs on the small model, and it catches the exact failure from chapter 1 that started this whole book. A self-check inside the same conversation is weaker: the context that produced the mistake is the context being asked to find it.

What you can do now that you couldn't before

You can tell the difference between needing specialists and needing a longer tool list — and you know the three ways to get division of labour without writing a coordinator at all. You can build a coordinator when you actually need one, brief its specialists so a fresh context can act on the brief, and pick models per role instead of per project. And you have the verifier pattern, which is the cheapest reliability win in this book.

One arc left, and it is the one that decides whether any of this survives contact with a Monday morning.
