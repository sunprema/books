Final Battle · Monday Morning

Final Boss: Real-World Reliability

The final boss is not a harder version of anything you have fought. It is Monday. Your agent has been running unattended over the weekend, the person who wrote it is on holiday, and something is quietly wrong in a way nobody will notice until Thursday.

Everything in this chapter exists to make that Thursday impossible.

Technique one: exhaust the stop reasons

Chapter 2 told you the loop exits on "end_turn", "max_tokens", "stop_sequence" or "refusal", and chapter 3 added "pause_turn". Here is the reveal I promised: those five are not variations of "done." They are five different outcomes and exactly one of them is success.

stop_reasonMeansCorrect response
tool_useIt wants a tool runExecute, return results, continue
end_turnFinished naturallyTake the answer
pause_turnThe server-side loop hit its iteration capRe-send the conversation including the paused response
max_tokensOutput ran out of room — the answer is truncatedRaise max_tokens or narrow the task. Never ship it
stop_sequenceHit a sequence you configuredHandle per your own design
refusalThe model declinedSurface it; do not blindly re-send

A paused turn is not a failure. It means the work is not finished. Re-send the conversation, including the paused response, to let the model continue where it left off.

Treating pause_turn as an error is the classic way to throw away a research turn that was halfway through its own loop. Treating max_tokens as success is how a truncated draft gets published. Here is the exhaustive version:

for _ in range(MAX_ITERATIONS):
    response = client.messages.create(...)

    if response.stop_reason == "tool_use":
        # ... execute, append results ...
        continue

    if response.stop_reason == "pause_turn":
        # Not an error: the server-side loop hit its cap. Re-send.
        messages.append({"role": "assistant", "content": response.content})
        continue

    if response.stop_reason == "max_tokens":
        raise Truncated(response)

    if response.stop_reason == "refusal":
        return handle_refusal(response)

    return response          # end_turn: the only success

raise IterationLimit()   # the loop must be bounded

Note the for rather than a while. An unbounded loop around a paid API call is a bill with no upper limit, and it only takes one tool that keeps returning something the model wants to investigate.

Technique two: verify what can be verified

"Hallucination" is a big scary word for something usually quite tractable. In an agent, most invented facts are invented in a place where a cheap check would have caught them — because the whole reason you built an agent was that the ground truth was reachable.

Kohai cites commit hashes. A hash either appears in git log or it does not. That is not a judgment call, it is a set membership test, and it costs microseconds:

import re

def verify_hashes(draft: str, since: str) -> list[str]:
    real = {line.split("\t")[0] for line in list_commits(since).splitlines() if line}
    cited = set(re.findall(r"\b[0-9a-f]{7,40}\b", draft))
    return sorted(cited - real)   # empty list = nothing invented

if bad := verify_hashes(draft, "v2.2.1"):
    raise Unverified(f"draft cites commits that do not exist: {bad}")

Ten lines, and they turn "the agent sometimes makes things up" into a hard failure you find immediately rather than a soft one you find in a customer's inbox. Ask of every agent output: what claim here is mechanically checkable? Check that, and stop worrying about the rest until you have.

Yes, that's a regex

Chapter 1 told you that parsing model output with a regex means the structure belonged in a schema. This one is different, and the difference is worth naming: that regex extracted a decision the pipeline would act on. This one audits a claim in prose meant for humans. The first is control flow and belongs in a tool call. The second is verification of the deliverable itself, and there is nothing else it could be.

Technique three: retry the transient, escalate the rest

Errors sort into three bins and each gets a different response.

KindExampleResponse
Model-recoverableBad ref, missing file, malformed argument Return as a tool result with is_error true — the model retries itself
TransientRate limit, 5xx, connection reset Retry with backoff, outside the agent loop
TerminalBad credentials, missing permission, iteration limit Stop and escalate to a human

The first row is the one people miss, and it is the one that makes agents feel robust. Errors returned as tool results with is_error true are what let the model adapt rather than fail blindly. The other two rows are ordinary distributed-systems hygiene; the SDKs already retry rate limits and server errors for you, so do not build a second retry layer on top without checking.

Technique four: log the trace, not the answer

When a run goes wrong you will not ask "what did it say." You will ask "what did it do, and why did it think that was reasonable." So log the trace: for every turn, the stop reason, every tool name and its arguments, every result including errors, and the token usage.

Cost is observable per request — the response reports input and output token counts in its usage metrics. And remember tool use adds tokens on top of a normal request from three places: the tools parameter itself, the tool_use and tool_result blocks, and an automatically included tool-use system prompt. Server tools can add usage-based charges beyond tokens as well — web search, for instance, charges per search performed. An agent that is 30% more expensive this week is telling you something about its behaviour, and you will only hear it if you were writing the numbers down.

log.info(
    "agent.turn",
    extra={
        "run_id": run_id,
        "turn": turn,
        "stop_reason": response.stop_reason,
        "tools": [b.name for b in response.content if b.type == "tool_use"],
        "in_tokens": response.usage.input_tokens,
        "out_tokens": response.usage.output_tokens,
    },
)

Technique five: ask, don't hardcode

Every model constant in chapter 6 will eventually be wrong. Model capabilities and token limits can be queried programmatically through the Models API, whose response includes max_input_tokens, max_tokens, and a capabilities object for every available model. A harness that checks limits at runtime does not silently break the week a constant changes.

The same caution applies to what the model can know unaided. Reliable knowledge cutoffs are published per model — May 2026 for Claude Opus 5, January 2026 for Claude Sonnet 5 — and that bounds what an agent can answer without a retrieval tool. When your agent confidently discusses a library version released after its cutoff, that is not a mystery. That is a missing tool.

Technique six: an eval set beats an opinion

"It seems better" is not a measurement, and you will change your prompt many times. Build a small fixed set of cases — for Kohai, ten tag ranges from real history with a human-approved answer for each — and run it before every prompt change. Twenty cases is enough to catch a regression. Zero cases means every change is a coin flip you cannot see the result of.

Score what you can score automatically: hash validity, whether known-important commits appear, whether chores were excluded. Save the human judgment for the cases the automatic scores pass and you still dislike.

Technique seven: the discipline of "done"

One rule from the multisession pattern deserves its own section, because it is the difference between a progress log you can trust and one that lies: mark a feature complete only after end-to-end verification confirms it works, not when the code is written.

Apply it to the agent and to yourself. An agent that records "release notes drafted" before the hashes were verified will resume tomorrow from a state that never existed. A developer who ships an agent because the happy path ran once is making the same mistake with a longer feedback loop.

The deployment checklist

  • Every stop_reason has an explicit branch — including pause_turn.
  • The loop is bounded by iteration count.
  • Tool failures return as is_error results, not exceptions.
  • Every irreversible tool is gated or absent.
  • Every path and identifier is validated against an allowlist, resolved first.
  • Mechanically checkable claims in the output are checked.
  • Every turn is logged: stop reason, tools, arguments, results, tokens.
  • An eval set exists and runs before prompt changes.
  • Model IDs and limits come from configuration or the API, not from a literal in the loop.
  • A human can see what the agent did without reading the code.

Graduation

Look back at where this started: a chatbot inventing commits, because it had no way to look. You now know why that happened, and you have built the thing that fixes it — a loop, a menu of tools, memory that survives the process, a boundary in code, and a checklist that catches the ways it can quietly go wrong.

Here is your honest final power-level check, because I promised those. Everything in this book is the basic form. Real systems add evaluation harnesses, tracing infrastructure, cost controls, permission models, and a great deal of unglamorous operational work. But the mechanism does not get more exotic than what you have. Bigger agents are the same loop with better instrumentation and harder-won judgment about what to put on the menu.

You have the anatomy. Go build something that actually needs it — and give your sidekick a better name than Kohai.
