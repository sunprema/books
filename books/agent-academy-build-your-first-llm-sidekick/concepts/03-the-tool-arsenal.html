Tool Arc · The Weapons

The Tool Arsenal

A tool is three fields. That is the whole definition, and the fact that it is so small is exactly why beginners underestimate it and then spend two days wondering why the model never calls their tool.

tools = [
    {
        "name": "get_weather",
        "description": "Get the current weather for a given location.",
        "input_schema": {
            "type": "object",
            "properties": {
                "location": {
                    "type": "string",
                    "description": "City and state, e.g. San Francisco, CA",
                }
            },
            "required": ["location"],
        },
    }
]

Name, description, JSON Schema. Notice what is not there: any code. The schema describes a shape, not an implementation. Your run_tool function from chapter 2 is what actually does the work, and the model never sees it.

The description is the trigger, not the label

Here is where most first agents lose. With the default tool_choice of {"type": "auto"}, the model decides on each turn whether to call a tool or respond directly. It calls a tool when the request maps to that tool's described capability and the answer is not already in context. So the description is not documentation for humans who will read your code later. It is the matching surface. A tool described as "Repo utility" will be ignored forever, because nothing a user says maps to that.

Write the description as a trigger condition, not a summary. Not "reads commits" — "Call this when the user asks what changed in the repository, or names a version tag or commit range."

The system prompt is the second lever, and it is documented as genuinely steerable. A light instruction such as "Use the tools to investigate before responding." increases tool use. A stronger form such as "Always call a tool first before responding." pushes further. In the other direction, "Use your judgment about whether to call a tool or respond directly." keeps triggering conservative. If your agent is under-calling, try the prompt before you redesign the schema.

Three kinds of weapon

Tools differ primarily by where the code executes, and that one axis determines what your application is responsible for. There are exactly three buckets.

BucketWho runs itYou return a tool_result?
User-defined client tools
Your business logic, your APIs		 YouYes
Anthropic-schema client tools
memory, bash, text_editor, computer		 YouYes
Server-executed tools
web_search, web_fetch, code_execution, tool_search		 The providerNo — never

The middle row deserves more respect than beginners give it. Anthropic-schema client tools have the same execution model as your own — the model asks, your code runs it, you return a result — but the schemas are trained-in. The model has been optimised on thousands of successful trajectories that use those exact tool signatures, so it calls them more reliably and recovers from errors more gracefully than it would with a custom tool that does the same thing. If you are about to write your own edit_file tool, use text_editor instead. You are not being clever by reinventing it; you are opting out of training.

Later reveal, early warning

Server tools run their own loop inside the provider's infrastructure: the model searches, reads results, decides whether to search again, and iterates until it has what it needs — all without your application participating. That internal loop has an iteration limit. If the model is still going when it hits the cap, you get stop_reason: "pause_turn" instead of "end_turn". That is not an error. It means the work is not finished, and you should re-send the conversation including the paused response so it can continue. Chapter 8 shows the handler.

Arming Kohai

Kohai needs two tools to do its job. Watch the descriptions — each one states when to call it, not just what it does.

KOHAI_TOOLS = [
    {
        "name": "list_commits",
        "description": (
            "List commits in the repository between two refs, newest first. "
            "Call this when the user asks what changed, names a version tag, "
            "or asks for release notes. Returns hash, author, date and subject."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "since": {"type": "string",
                          "description": "Starting ref, e.g. v2.3.0"},
                "until": {"type": "string",
                          "description": "Ending ref. Defaults to HEAD."},
            },
            "required": ["since"],
            "additionalProperties": False,
        },
        "strict": True,
    },
    {
        "name": "show_commit",
        "description": (
            "Show the full message and changed-file list for one commit. "
            "Call this when a commit subject is too terse to classify."
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "sha": {"type": "string", "description": "Full or short commit hash"},
            },
            "required": ["sha"],
            "additionalProperties": False,
        },
        "strict": True,
    },
]

Two tools, not twelve. Resist the urge to hand your agent a giant arsenal on day one — a focused set is easier to debug, and every tool you add costs tokens on every single request.

Named technique: strict schemas

Notice "strict": True above. Adding it to a custom tool definition guarantees that the model's tool calls match the declared schema exactly. This is the honest answer to the regex tell from chapter 1: instead of hoping the output parses, you make malformed output impossible. It requires additionalProperties: false and a required list, which is a small price.

Parallel calls, and turning them off

By default a single assistant message may contain several tool_use blocks — the model asks for three commit details at once because it can. Your loop from chapter 2 already handles this correctly: it iterates every tool_use block and returns all the results in one user message. Splitting them across several messages is a real bug, not a style choice.

While you are learning, it is reasonable to turn parallelism off so traces are easier to read. Set disable_parallel_tool_use inside tool_choice:

tool_choice={"type": "auto", "disable_parallel_tool_use": True}

The full set of tool_choice values is worth knowing now, because chapter 5 uses two of them as safety controls:

ValueBehaviour
{"type": "auto"}The model decides (default)
{"type": "any"}It must use at least one tool
{"type": "tool", "name": "..."}It must use that specific tool
{"type": "none"}It cannot use tools at all

The failed call — and how the agent recovers

Your list_commits tool will be called with a tag that does not exist. Not might be — will be. The instinct is to raise an exception and let the program die. Do not. A tool failure is reported back as an ordinary tool result with is_error set to true and the message in content:

{
    "type": "tool_result",
    "tool_use_id": tool_use.id,
    "content": "Error: unknown ref 'v2.3.0'. Known tags: v2.2.0, v2.2.1, v3.0.0",
    "is_error": True,
}

That is the whole recovery mechanism, and it is beautiful in its plainness. The model reads the error like any other result, sees the list of real tags, and calls list_commits again with v2.2.1. An exception would have ended the run; an informative error turned a dead end into one extra turn. Put the useful detail in the message — what was wrong and what would be valid — because that string is the entire briefing the model gets.

Honest accounting

Tools are not free. Using them adds input tokens from three places: the tools parameter itself (names, descriptions, schemas), the tool_use and tool_result blocks in the transcript, and an automatically included tool-use system prompt — 286 tokens on Claude Opus 5 for tool_choice of auto or none. That last one is fixed overhead you pay on every tool-enabled request.

This is the real argument for a small arsenal. Ten tools with paragraph-long descriptions is a standing tax on every turn of every conversation.

What you can do now that you couldn't before

You can define a tool the model will actually reach for, because you write the description as a trigger rather than a label. You know the three execution buckets and why you should prefer a trained-in schema over your own. You can make malformed calls impossible with strict, and — the one that separates a demo from a system — you can turn a tool failure into a recovery instead of a crash.

Kohai can now read your repository. But it forgets everything the moment the conversation ends. Next arc: memory.
