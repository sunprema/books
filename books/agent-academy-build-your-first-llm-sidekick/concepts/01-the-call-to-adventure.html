Training Arc · Round One

The Call to Adventure

Here is your opponent. Not a boss yet — a sparring partner, the one who shows you exactly how far your current skills go. Open a chat window and type this:

"Write the release notes for my repository since v2.3.0."

You will get release notes. They will be beautifully formatted. They will have section headings, a nice summary line, maybe an emoji. And they will be about commits that do not exist, because the model has never seen your repository and cannot see it now. It answered the shape of your question rather than the substance, because the shape was all it had.

This is not a failure of intelligence. Ask that same model to explain a subtle concurrency bug and it will out-reason most humans. The problem is narrower and more mechanical than "it isn't smart enough," and once you see it clearly the rest of this book is just consequences.

Name the rival: the model cannot reach

A language model never executes anything on its own. It emits a structured request; your application — or the provider's servers — runs the operation and returns the result into the conversation.

Read that twice, because beginners get it backwards constantly. When a model "calls a tool," it does not call anything. It writes down, in a format your code can parse, that it would like read_commits(since="v2.3.0") to happen. Then it stops and waits. If nobody on your side runs that function, nothing happens. The model is a very good typist with no hands.

So the chatbot did not lie to you out of malice or carelessness. You asked a question whose honest answer required reaching into a system it has no connection to, and it had no mechanism to say let me go look. Give it that mechanism and the same model that invented your commits will read them instead.

Meet your sidekick

You are going to build one thing across this whole book, and you are going to keep building it until it is genuinely useful. Its name is Kohai — the junior student — and its job is release notes.

Kohai's mission

Given a git repository and a starting tag, read the commits since that tag, decide which ones a human reader actually cares about, group them, and draft release notes that cite real commit hashes.

That mission is deliberately unglamorous, and deliberately chosen. It needs fresh data the model cannot have (your commits), it needs judgment a script cannot have (which changes matter to a reader), and it has a verifiable output (every hash it cites either exists or does not). Most real agent work looks like this. Very little of it looks like a robot butler.

When this is the right weapon

Before you learn a technique, learn what it beats — otherwise you will use it on everything and lose. Tool use fits when the task requires something the model cannot do from text alone:

  • Actions with side effects. Sending an email, writing a file, updating a record. The model can describe these; only a tool can perform them.
  • Fresh or external data. Current prices, today's weather, the contents of a database. Anything outside the training data or specific to your system needs a tool to fetch it.
  • Structured, guaranteed-shape outputs. When you need a JSON object with specific fields rather than prose that happens to contain the information.
  • Calling into existing systems. Databases, internal APIs, filesystems — the bridge between a natural-language request and the systems that fulfil it.

And it does not fit when the model can answer from training alone, when the interaction is one-shot question-and-answer with no side effects, or when tool-calling latency would dominate a trivial response. Every tool call is at least one extra round trip. For a lightweight task the overhead can exceed the work.

Power level check

An agent is slower and more expensive than a single model call, and it has more ways to fail. If your task is "summarise this paragraph," an agent is not a power-up, it is a handicap. The reason to build one is that the task genuinely cannot be done without reaching outside the conversation. Reach for it when that is true and not before.

The tell you will learn to recognise

There is one diagnostic worth memorising now, because it will save you weeks later. Here it is, quoted almost exactly from the documentation, and it is sharper than it looks:

If you are writing a regex to extract a decision from model output, that decision should have been a tool call. Parsing free-form text to recover structured intent is a sign the structure belongs in the schema.

Every beginner writes the regex version first. You ask the model to reply with DECISION: ship or DECISION: hold, then you grep for it, and it works until the day the model writes Decision — ship and your pipeline silently takes the wrong branch. The fix is not a better regex. The fix is to stop asking for a decision in prose and start asking for it in a shape the model is constrained to produce. You will build exactly that in chapter 3.

What you can do now that you couldn't before

You can tell, before you write a line of code, whether a task needs an agent or just needs a prompt. You know that the model never executes anything — that every action in every agent you will ever build is a request your own code chose to honour. And you can spot the regex tell in your own work, which is the single most common way a would-be agent gets built backwards.
