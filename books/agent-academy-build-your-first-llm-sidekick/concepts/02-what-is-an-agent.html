Training Arc · The Basic Form

What Is an Agent?

Every martial art has a stance you drill until it is boring, and then you spend the rest of your life discovering it was never boring. This is that stance. It is a while loop. Learn it exactly and the rest of this book is decoration.

The contract

Start with the relationship, not the code. Tool use is a contract between your application and the model: you specify what operations are available and what shape their inputs and outputs take; the model determines when and how to call them.

That is a clean split of responsibility and it is worth internalising. You own the menu. The model owns the ordering. You never have to predict which tool it will pick, and it never gets to invent a tool you did not put on the menu. Engineers with ordinary API experience can integrate this the same way they would any typed interface: define the schema, handle the callback, return a result. The only novelty is that the caller on the other end is a language model choosing based on the conversation.

The technique: the agentic loop

Here is the canonical shape, a loop keyed on stop_reason:

  1. Send a request with your tools array and the user message.
  2. The model responds with stop_reason: "tool_use" and one or more tool_use blocks.
  3. Execute each tool. Format the outputs as tool_result blocks.
  4. Send a new request containing the original messages, the assistant's response, and a user message with the tool_result blocks.
  5. Repeat from step 2 while stop_reason is "tool_use".

In one sentence: while stop_reason is tool_use, execute the tools and continue the conversation. That is the whole engine. Everything else in this book — memory, guardrails, multiple agents — hangs off those five lines.

The loop in code

while True:
    response = client.messages.create(
        model="claude-opus-5",
        max_tokens=16000,
        tools=tools,
        messages=messages,
    )
    if response.stop_reason != "tool_use":
        break

    # Append the WHOLE response, not just its text: the tool_use
    # blocks live in here and the next request needs them.
    messages.append({"role": "assistant", "content": response.content})

    results = [
        {
            "type": "tool_result",
            "tool_use_id": b.id,
            "content": run_tool(b.name, b.input),
        }
        for b in response.content
        if b.type == "tool_use"
    ]
    messages.append({"role": "user", "content": results})

Nineteen lines. That is an agent. Not a toy version of one — that is the mechanism production systems run, with more error handling wrapped around it.

Three details that bite everyone

The API is stateless. Every request must carry the full prior conversation: the original messages, the assistant's response including its tool_use blocks, and the user message containing the tool_result blocks. The model has no memory of the previous call. You are re-narrating the whole story every time.

Append response.content, not response.content[0].text. This is the single most common beginner bug. You reach for the text because that is what you want to print, you append that instead, and the tool_use blocks vanish. The next request then contains a tool_result that answers nothing, and the API rejects it.

Every tool_result must carry the tool_use_id of the block it answers. That id is how the model matches your answer to its question. When the model asks three things at once — and it will — the ids are the only thing keeping the answers from being scrambled.

Don't fake the win

It is tempting to write while response.stop_reason == "tool_use" and call it done. But the loop exits on any other stop reason — "end_turn", "max_tokens", "stop_sequence", or "refusal" — and those mean very different things. end_turn is success. max_tokens is a truncated answer that looks complete. refusal means the model declined. Treating all four as "done" is how an agent silently ships half a result. Chapter 8 makes you handle each one; for now, just know they exist.

Observe, think, act — where the folklore fits

You will hear agents described as an observe, think, act cycle. That framing is fine as intuition, but map it onto the real mechanism so you are never confused about which part is yours:

FolkloreWhat actually happensWhose code
ObserveTool results arrive in the message listYours
ThinkThe model generates its next turnThe provider's
ActA tool_use block is emitted, then you run itBoth
RepeatThe while loopYours

Notice that three of the four rows are yours. An agent is mostly ordinary software. The model is one function call inside it — the interesting one, but one.

What you can do now that you couldn't before

You can write the loop from memory, and you know the three things that break it: dropping the full response, losing the tool_use_id, and pretending only one exit condition exists. You also know exactly which parts of an agent you are responsible for, which matters a great deal in chapter 5 when we ask who is responsible for safety.

What you cannot do yet is give Kohai anything to call. The loop is the skeleton; next you forge the weapons.
