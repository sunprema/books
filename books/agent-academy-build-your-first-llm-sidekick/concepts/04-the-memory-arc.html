Memory Arc · Allies Remembered

The Memory Arc

Kohai finishes a run and you close the terminal. Tomorrow you run it again. It has no idea it has ever met your repository. It re-reads every commit, re-derives that your team writes chore(deps): for dependency bumps and does not want those in release notes, and re-makes the same three mistakes you corrected yesterday.

This is the wall of the memory arc, and beating it requires first being precise about a word that gets used for two completely different things.

Two things called memory

Chapter 2's loop already gave you the left column: every turn re-sends the whole transcript, so within one run the agent remembers everything. That is short-term memory, and it is free in effort and expensive in tokens. The right column is what survives the terminal closing.

The technique: the memory tool

The memory tool lets the model store and retrieve information across conversations in a directory of files that persist between sessions, building up knowledge over time without keeping everything in the context window.

The pattern it enables has a name worth learning: just-in-time context retrieval. Rather than loading all relevant information up front, the agent records what it learns in memory files and reads them back on demand. That keeps the active context focused on the current task — which matters enormously for long-running sessions that would otherwise overwhelm the context window.

The memory tool operates client-side. The model only requests file operations; your application executes each request against storage you control and returns the result in a tool_result block. Memory lives entirely in your application.

Same contract as chapter 3, then. But the declaration is startlingly small, because this is an Anthropic-schema tool: the schema is trained in, so you do not write one.

tools = [{"type": "memory_20250818", "name": "memory"}]

That is the entire configuration. The name must be memory, you do not define an input_schema for a provider-supplied tool, and no beta header is required. Everything else is your handler.

Six commands to implement

CommandDoes
viewShow directory contents, or file contents with an optional view_range
createWrite a new file from file_text
str_replaceReplace one occurrence of old_str with new_str
insertInsert text after line insert_line (0 = start of file)
deleteDelete a file or directory
renameMove old_path to new_path

The model addresses everything under /memories. That path is a prefix your handler maps onto real storage — a per-user directory, keys in a database, an encrypted blob store. It is not required to be a real directory on your disk, and in a multi-user system it had better not be a single shared one.

The protocol you get for free

When the memory tool is present in your request's tools, the API automatically adds a memory-protocol instruction to the system prompt. You do not send it yourself. In substance it tells the model to view its memory directory before doing anything else, to record status and progress as it works, and — the line that shapes everything — to assume interruption: its context window might be reset at any moment, so it risks losing any progress not recorded in memory.

That last instruction is why a memory-enabled agent behaves differently from one you bolted a database onto. It is not just permitted to write notes; it is told to expect to be cut off mid-task. Design your memory files as if the process will die, because that is the assumption the model is already operating under.

The trap: path traversal

This one is real

A malicious path such as /memories/../../secrets.env can reach files outside the memory directory. Your implementation must validate every path in every command. Your application executes whatever the model requests — and the model can be steered by text it reads from a repository, a web page, or a ticket. This is not a hypothetical.

The documented safeguards are specific, so implement them specifically: validate that all paths start with /memories; resolve paths to canonical form and verify they remain within the memory directory; reject sequences such as ../ and ..\\; watch for URL-encoded traversal like %2e%2e%2f; and use your language's built-in path utilities rather than string surgery.

from pathlib import Path

ROOT = Path("./memories").resolve()

def safe_path(requested: str) -> Path:
    if not requested.startswith("/memories"):
        raise ValueError("path must start with /memories")
    candidate = (ROOT / requested.removeprefix("/memories").lstrip("/")).resolve()
    if not candidate.is_relative_to(ROOT):
        raise ValueError("path escapes the memory root")
    return candidate

Three lines of check. Call it at the top of every command handler, without exception. The resolve() is the part that matters: it collapses .. and follows symlinks, so the containment test is done against what the filesystem will actually open, not against the string the model sent.

Hygiene: memory that does not rot

Memory grows, and unbounded growth turns an asset into a tax. The documented recommendations are worth adopting from day one: track file sizes and cap how large a file can grow; cap how many characters view returns and let the model page through the rest with view_range; and periodically delete files that have not been accessed in a long time.

There is also a rule about what not to store. The model usually refuses to write sensitive information to memory files, but the recommendation for a stronger guarantee is validation in your handler that strips sensitive data before the file is written. "Usually refuses" is a model behaviour; your validator is a boundary. Chapter 5 is about exactly that distinction.

Named technique: the multisession pattern

For work spanning multiple sessions, do not let memory files accrete ad hoc. The documented pattern sets them up deliberately, and it turns memory into a recovery mechanism:

  1. Initializer session. Before any substantive work, create the memory files: a progress log tracking what is done and what comes next, a feature checklist defining scope, and a reference to any startup script the project needs.
  2. Subsequent sessions. Each one opens by reading those files, restoring project state without re-exploring the code base or retracing earlier decisions.
  3. End-of-session update. Before a session ends, update the progress log with what was completed and what remains.

And the key principle: work on one feature at a time, and mark it complete only after end-to-end verification confirms it works — not when the code is written.

That last sentence is the difference between a progress log you can trust and one that lies to the next session. An agent that marks things done on writing them will confidently resume from a state that never existed.

Memory's two siblings

Memory is one of three tools for the same underlying problem — a conversation that outgrows its context window — and they are complements, not alternatives. Context editing clears specific tool results on the client. Compaction automatically summarises the whole conversation server-side as it approaches the context window limit. For long-running agents, consider both: compaction keeps the active context small without client-side bookkeeping, and memory preserves the information that must survive summarisation.

Read that division of labour carefully, because it tells you what to write to memory. Anything a summariser might reasonably drop, but you would be sad to lose, belongs in a file. Everything else can be allowed to fade.

What you can do now that you couldn't before

You can tell conversation history from persistent memory and reach for the right one. You can wire up the memory tool with a one-line declaration and a six-command handler, and you can write that handler without opening a path-traversal hole. You know the multisession pattern, including the discipline that makes its progress log honest.

Kohai now remembers that your team hides dependency bumps. It also now has write access to a filesystem — which is a very good moment to talk about what it is allowed to do.
