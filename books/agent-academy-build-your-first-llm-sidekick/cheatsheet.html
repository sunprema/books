The 30-second summary

The model never executes anything. It emits a tool_use block; your code runs it and returns a tool_result; you loop while stop_reason == "tool_use". Tools are a name, a description, and a JSON Schema. Memory is files you own. Guardrails live in your handler, never in the prompt.

The loop

for _ in range(MAX_ITERATIONS):
    r = client.messages.create(model=MODEL, max_tokens=16000,
                                 tools=TOOLS, messages=messages)
    if r.stop_reason != "tool_use":
        return finish(r)
    messages.append({"role": "assistant", "content": r.content})   # FULL content
    messages.append({"role": "user", "content": [
        {"type": "tool_result", "tool_use_id": b.id,
         "content": run(b.name, b.input)}
        for b in r.content if b.type == "tool_use"
    ]})                                    # ALL results, ONE message

Stop reasons

ValueDo
tool_useRun the tools, continue
end_turnSuccess — take the answer
pause_turnServer loop hit its cap. Re-send with the paused response
max_tokensTruncated. Raise the cap or narrow the task
stop_sequenceYour configured sequence fired
refusalThe model declined. Surface it; don't blind-retry

Tool definition

{
  "name": "list_commits",
  "description": "... Call this when the user asks what changed.",
  "input_schema": {
    "type": "object",
    "properties": {"since": {"type": "string", "description": "e.g. v2.3.0"}},
    "required": ["since"],
    "additionalProperties": False
  },
  "strict": True
}

Write the description as a trigger, not a label. strict requires additionalProperties: false plus required, and guarantees the call matches the schema exactly.

tool_choice

ValueEffect
{"type": "auto"}Model decides (default)
{"type": "any"}Must use at least one tool
{"type": "tool", "name": "x"}Must use tool x
{"type": "none"}Cannot use tools

Add "disable_parallel_tool_use": true to any of them for at most one call per turn.

Tool error

{"type": "tool_result", "tool_use_id": id,
 "content": "Error: unknown ref 'v9'. Known tags: v2.2.1, v3.0.0",
 "is_error": True}

Say what was wrong and what would be valid. This is the recovery mechanism — never raise where you could return.

Memory

tools = [{"type": "memory_20250818", "name": "memory"}]
# commands to implement: view create str_replace insert delete rename
# all paths under /memories — validate every one

The API adds the memory protocol to the system prompt for you. Guard against traversal: prefix check, resolve(), containment check, and reject ../ and %2e%2e%2f.

Gotchas, ranked by how often they bite

  1. Appending response.content[0].text instead of response.content — the tool_use blocks vanish.
  2. Splitting parallel tool_results across several user messages instead of one.
  3. Breaking only on end_turn, so truncation and refusal read as success.
  4. An unbounded while loop around a paid call.
  5. A vague tool description, so the tool is never called.
  6. Raising on tool failure instead of returning is_error.
  7. Treating pause_turn as an error.
  8. Trusting the system prompt as a security boundary.
  9. Opening a memory path without resolving and containing it first.
  10. Forgetting the API is stateless — every request carries the whole conversation.

Pre-deploy checklist

  • Every stop reason branches explicitly
  • Iteration bound in place
  • Tool failures return, never raise
  • Irreversible tools gated or absent
  • Paths and identifiers allowlisted, resolved first
  • Checkable claims in the output are checked
  • Every turn logged with tokens
  • An eval set runs before prompt changes
  • Model IDs and limits from config or the API
