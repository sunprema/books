Chapter 02 · Part I — Orientation

APFS Clones, and Calling clonefile from Rust

Everything in the previous chapter rested on a claim I have not yet justified: that you can have two independent files that occupy the space of one. That sounds like it should be impossible. A file is its bytes; two files, two sets of bytes. So before we write a line of Rust, let's ask the filesystem what it actually offers — and then look at the twenty-nine lines that reach it.

Four ways to have the same data twice

Unix has offered three of them for decades, and macOS added a fourth.

A copy is the obvious one: new inode, new blocks, double the space. Perfectly independent, perfectly expensive. A hard link is the opposite trade: two directory entries pointing at the same inode. One set of blocks, no extra space — but also one file wearing two names. Change it through either name and both “files” change, because there was only ever one. A symlink sidesteps the question: it is a tiny file containing a path, and anything that reads it is really reading the target. Delete the target and the link dangles.

The fourth is the APFS clone, and it is the one that makes this application possible. A clone is a genuinely new inode — its own metadata, its own permissions, its own timestamps — whose file structure initially points at the same physical extents as the original. No bytes are copied. And the moment either file is written to, the filesystem quietly gives that file private storage for the blocks that changed. That last property is copy-on-write, and it is what buys back the independence a hard link throws away.

The system call

macOS exposes cloning through clonefile(2). Four facts from its manual page matter to us, and each one turns into code later:

  1. It shares extents, not bytes. The call creates a new inode that shares the source's data extents; nothing is copied up front, and the two diverge lazily as either is written.
  2. The destination must not exist. If it does, the call fails with EEXIST. There is no “overwrite” mode.
  3. Same filesystem only. Source and destination on different filesystems is EXDEV.
  4. The clone inherits the source's attributes. The new file gets its own copy of the source's attributes and extended attributes — with ownership downgraded if you lack privilege, and setuid/setgid cleared.
Remember fact 4 A fresh clone arrives wearing the source's clothes: its permissions, its Finder tags, its resource fork. When we use a clone to replace a different file, that is precisely wrong — and fixing it is the entire subject of chapter 11.

Fact 2 looks like an obstacle. It is the opposite: it is a safety property the transaction engine leans on. Because clonefile physically cannot land on an existing path, there is no code path anywhere in this program that could clone directly over a user's file, even by mistake. Chapter 10's design — clone to a hidden temp sibling, then swap by renaming — is not paranoia layered on top of the syscall; it is the only thing the syscall permits.

Twenty-nine lines of Rust

Here is the entire macOS implementation. Read it once for shape, then we will take it apart line by line.

src/apfs/clone.rsthe complete macOS implementation, verbatim

/// Clone `source` to `destination` via `clonefile(2)`: an APFS
/// copy-on-write clone sharing data blocks until either file is written.
///
/// `destination` must not exist (`clonefile` fails with EEXIST — the
/// transaction engine relies on this: it never clones onto a live target,
/// only onto a fresh temp path). Symlinks are not followed.
#[cfg(target_os = "macos")]
pub fn clone_file(source: &Path, destination: &Path) -> io::Result<()> {
    use std::ffi::CString;
    use std::os::unix::ffi::OsStrExt;

    // From <sys/clonefile.h>; not bound by the libc crate.
    const CLONE_NOFOLLOW: u32 = 0x0001;

    let src = CString::new(source.as_os_str().as_bytes())
        .map_err(|_| io::Error::new(io::ErrorKind::InvalidInput, "source path contains NUL"))?;
    let dst = CString::new(destination.as_os_str().as_bytes())
        .map_err(|_| io::Error::new(io::ErrorKind::InvalidInput, "destination path contains NUL"))?;

    let result = unsafe { libc::clonefile(src.as_ptr(), dst.as_ptr(), CLONE_NOFOLLOW) };
    if result == 0 {
        Ok(())
    } else {
        Err(io::Error::last_os_error())
    }
}

The signature

fn clone_file(source: &Path, destination: &Path) -> io::Result<()>. It borrows both paths — it has no reason to own them — and returns io::Result<()>, which is just Result<(), std::io::Error>. The success value is the unit type: there is nothing to hand back, only the fact that it worked. This is the ordinary Rust idiom for “a side effect that can fail,” and it means callers can write adapter.clone_file(a, b)?; and move on.

Turning a path into something C can read

C strings are NUL-terminated byte sequences. Rust's Path is neither NUL-terminated nor guaranteed to be UTF-8 — on Unix it is an arbitrary byte string. The bridge is two steps: as_os_str().as_bytes() exposes the raw bytes (that as_bytes comes from the std::os::unix::ffi::OsStrExt extension trait, which is why the use sits inside the function), and CString::new copies them into a NUL-terminated buffer.

CString::new can fail, for exactly one reason: the bytes already contain an interior NUL, which would silently truncate the path. The code maps that to a clear InvalidInput error rather than unwrapping. It is a case that will essentially never fire, and handling it costs two lines — that ratio is what makes a systems program trustworthy.

Why the CStrings must be bound to variables

Key idea — the FFI ownership trap src.as_ptr() returns a pointer into the buffer that src owns. If the CString were a temporary — say, if the code had written CString::new(…)?.as_ptr() inline — it would be dropped at the end of that statement and the pointer would dangle before clonefile ever saw it. Binding src and dst to locals keeps the buffers alive for the whole call. This is the single most common FFI bug in Rust, and the fix is exactly the boring thing this code does.

The flag the libc crate does not have

The libc crate binds the clonefile function but not the constants from <sys/clonefile.h>, so the code declares the one it needs and says so in a comment. CLONE_NOFOLLOW means: if the source is a symlink, do not follow it. That is the same “never resolve a link on our behalf” discipline you will see in the walker (follow_links(false)), in the preflight checks (symlink_metadata), and in every extended-attribute call (XATTR_NOFOLLOW). A tool that replaces files must always operate on the thing it named, never on something the thing points to.

Declaring a C constant yourself is a small, honest piece of unsafety debt: you are asserting that 0x0001 is what the header says. When you do this, cite the header in a comment, exactly as this code does — the comment is the audit trail.

The unsafe block, and what it is claiming

One expression is unsafe: libc::clonefile(src.as_ptr(), dst.as_ptr(), CLONE_NOFOLLOW). Calling any foreign function is unsafe in Rust, because the compiler cannot see across the boundary; it cannot know whether the callee will honour the pointers' lifetimes, or write where it should not. Writing unsafe here is a promise from the programmer to the compiler: I have checked the things you cannot. In this case the checks are the ones we just walked through — both pointers are valid, NUL-terminated, alive for the duration of the call, and the flag is a value the syscall accepts.

Notice how small the block is. Not the whole function, not the error handling — one expression. That is deliberate style: an unsafe block is a claim you have to defend, so make it cover as little ground as possible.

Errors, the Unix way

C reports failure by returning -1 and setting the thread-local errno. Rust's io::Error::last_os_error() reads that errno and wraps it in a proper io::Error — one that will print “File exists (os error 17)” and whose raw_os_error() the tests can match on exactly. The pattern “zero is success, anything else means go ask errno” recurs in every FFI call in this codebase; once you have read it here you have read it in volume.rs, forks.rs and metadata.rs too.

Compiling on a machine that has no APFS

Both blocks in clone.rs carry a #[cfg(…)] attribute, which decides at compile time whether the item exists at all. The macOS version is the real one; here is its counterpart:

src/apfs/clone.rsthe non-macOS stub, verbatim

#[cfg(not(target_os = "macos"))]
pub fn clone_file(_source: &Path, _destination: &Path) -> io::Result<()> {
    Err(io::Error::new(
        io::ErrorKind::Unsupported,
        "APFS cloning requires macOS",
    ))
}

The payoff is that cargo check, cargo clippy and the platform-neutral half of the test suite all run on Linux or in CI, while the parts that genuinely need a Mac are the parts that are honestly marked as needing one. (The integration tests take the other half of the deal: they open with #![cfg(target_os = "macos")], so the whole file compiles away elsewhere.) Underscored parameter names are how you tell the compiler — and the reader — that ignoring an argument is intended, not forgotten.

Proving it is a clone and not a hard link

All of the above is a claim about behaviour. The repository turns it into a test that runs against a real APFS volume — macOS temp directories are on one — and the assertions are exactly the distinctions from our comparison table.

tests/apfs_integration.rsverbatim

#[test]
fn clone_shares_content_but_diverges_on_write() {
    let dir = tempfile::tempdir().unwrap();
    let source = dir.path().join("source.bin");
    let cloned = dir.path().join("cloned.bin");
    let data = vec![0x5au8; 256 * 1024];
    fs::write(&source, &data).unwrap();

    clone::clone_file(&source, &cloned).unwrap();

    // Same content, different inode: a real clone, not a hardlink.
    assert_eq!(fs::read(&cloned).unwrap(), data);
    let src_meta = fs::metadata(&source).unwrap();
    let clone_meta = fs::metadata(&cloned).unwrap();
    assert_ne!(src_meta.ino(), clone_meta.ino());
    assert_eq!(clone_meta.len(), data.len() as u64);

    // Copy-on-write isolation: writing the clone leaves the source alone.
    fs::write(&cloned, b"diverged").unwrap();
    assert_eq!(fs::read(&source).unwrap(), data);
}

Three assertions, three properties: same bytes, assert_ne! on the inode numbers (so it is not a hard link), and the source surviving a write to the clone unchanged (so copy-on-write really is isolating them). If you ever need to explain APFS clones to someone, this test is a better explanation than a paragraph.

And the EEXIST behaviour the transaction engine depends on is pinned down too, right down to the destination's contents being untouched:

tests/apfs_integration.rsverbatim

#[test]
fn clone_refuses_existing_destination() {
    let dir = tempfile::tempdir().unwrap();
    let source = dir.path().join("source.bin");
    let dest = dir.path().join("existing.bin");
    fs::write(&source, b"source").unwrap();
    fs::write(&dest, b"already here").unwrap();

    let err = clone::clone_file(&source, &dest).unwrap_err();
    assert_eq!(err.raw_os_error(), Some(libc::EEXIST));
    assert_eq!(fs::read(&dest).unwrap(), b"already here");
}

“Same volume”, in code

Cloning is a same-volume feature, so the program has to answer two questions before it can plan anything: are these two paths on the same filesystem, and is that filesystem APFS at all. Both live in src/apfs/volume.rs, and the first is almost embarrassingly small — two paths are on the same filesystem when their st_dev matches.

src/apfs/volume.rsverbatim

/// Device id (`st_dev`) of the filesystem holding `path`.
/// Never follows a symlink at the final component.
pub fn device_of(path: &Path) -> io::Result<u64> {
    use std::os::unix::fs::MetadataExt;
    Ok(std::fs::symlink_metadata(path)?.dev())
}

/// True when both paths live on the same filesystem. A prerequisite for
/// cloning, checked at preflight time — volumes can unmount and remount
/// between scan and reclaim.
pub fn same_volume(a: &Path, b: &Path) -> io::Result<bool> {
    Ok(device_of(a)? == device_of(b)?)
}

The second needs the C library again, because Rust's standard library has no notion of “what kind of filesystem is this.” The answer comes from statfs, whose f_fstypename field is a C string we compare against b"apfs":

src/apfs/volume.rsverbatim

/// True when the filesystem holding `path` is APFS. Cloning is an
/// APFS-only feature; HFS+, network mounts, etc. must be rejected.
#[cfg(target_os = "macos")]
pub fn is_apfs(path: &Path) -> io::Result<bool> {
    use std::ffi::{CStr, CString};
    use std::os::unix::ffi::OsStrExt;

    let c_path = CString::new(path.as_os_str().as_bytes())
        .map_err(|_| io::Error::new(io::ErrorKind::InvalidInput, "path contains NUL"))?;
    let mut sfs: libc::statfs = unsafe { std::mem::zeroed() };
    let rc = unsafe { libc::statfs(c_path.as_ptr(), &mut sfs) };
    if rc != 0 {
        return Err(io::Error::last_os_error());
    }
    let fstype = unsafe { CStr::from_ptr(sfs.f_fstypename.as_ptr()) };
    Ok(fstype.to_bytes() == b"apfs")
}

Three unsafe operations, each a different flavour. std::mem::zeroed() conjures an all-zero statfs for the kernel to fill in — safe here because a C struct of integers and byte arrays has no invalid zero state, which is exactly the kind of reasoning an unsafe block is a receipt for. The call itself is unsafe like any FFI call. And CStr::from_ptr is unsafe because it trusts that the bytes it is handed really are NUL-terminated — which the kernel guarantees for this field.

A timing decision Both of these are called at preflight time, immediately before a replacement — not at scan time. The doc comment says why: volumes can unmount and remount between runs. Anything the program believes about the filesystem has a shelf life, and this codebase is consistently suspicious about how short it is.

Why du will lie to you afterwards

Here is the fact that generates every support question a tool like this will ever receive. After reclaiming, du and Finder's “size” column still show each file at its full size. Nothing has shrunk. Did it work?

It did. Those tools report a file's logical length — how many bytes you would read out of it — and that has not changed, because both files really do still contain all their bytes. What changed is how many physical blocks the volume has committed, and the place that shows up is the volume's free space. The README is blunt about it:

README.md Reported savings are estimates. APFS free-space accounting, local snapshots (including Time Machine's), sparse files, and pre-existing clones all make the observed free-space change differ from the naïve sum. du will still show each clone at full size; the volume's free space is what improves.

This honesty is not just documentation — it is in the type system, in a small way. Chapter 3 will show you a method called estimated_reclaimable_bytes, and the word estimated is in the name on purpose.

So what did we actually gain?

A primitive, and three constraints that will shape everything after it. The primitive: one syscall that makes a second, fully independent file for free. The constraints: it refuses an existing destination (so we must stage and swap), it refuses a different volume (so grouping must be per-device), and it gives the new file the source's metadata (so a replacement must restore the target's).

Every one of those constraints reappears as a line of code in the second half of this book. The program is, in a real sense, the shape this syscall pressed into it.
