Chapter 12 · Part IV — Replacing a File Safely

Crash Recovery, and What We Gained

Chapter 10 handled every way the transaction can fail. This chapter handles the one thing it cannot: not failing, but simply stopping. A power cut. A kill -9. A kernel panic between two renames. No error is returned, no rollback runs, no line of our code executes at all — and somewhere on the disk is a directory containing a hidden backup, a hidden temp clone, and possibly no file where the user's file used to be.

What is actually on the disk

Imagine finding that directory with no other information. There is notes.md, a .filecleaner.3f9a….tmp and a .filecleaner.3f9a….backup. What do you do?

You cannot tell. Is the temp file a half-verified clone that must be discarded, or a fully verified one that was about to become the answer? Is the backup the user's current file, or a stale copy of a file that has already been correctly replaced? The bytes are identical either way — that is the entire premise of the tool. The filesystem alone cannot distinguish “before the swap” from “after the swap.”

Which is why every step of chapter 10 wrote its intention down first.

Five states, and what each one licenses

src/txn/journal.rsverbatim

/// Transaction states, journaled durably *before* the filesystem step each
/// one precedes. After a crash, the journal plus what is actually on disk
/// determines recovery:
///
/// - `Prepared`     → nothing user-visible has changed; roll back.
/// - `BackupCreated`→ target may have been renamed to the backup; roll back.
/// - `Swapped`      → the clone was fully verified; roll forward.
/// - terminal states record the outcome.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum TxnState {
    /// Intent recorded; covers temp-clone creation and verification.
    Prepared,
    /// Written before `rename(target, backup)`.
    BackupCreated,
    /// Written before `rename(temp, target)`.
    Swapped,
    /// Final validation passed and the backup was removed.
    Committed,
    /// The transaction was undone; the target is untouched.
    RolledBack,
}

Look at what each state is defined by. Not “we are cloning” or “we are verifying” — each state names the filesystem operation it precedes. backup-created does not mean the backup exists; it means we are about to create it. That is a subtle and important difference: the journal records intentions, and an intention written before an act is the only thing that survives an interruption of the act.

And notice how few states there are. There is no state for “temp cloned” or “metadata restored,” even though those are real steps. prepared covers all of them — because the recovery action is identical for every one of them: nothing the user can see has changed, so delete any debris and roll back. States exist to distinguish different repairs, not to log progress. Adding a state that does not change the repair would be pure cost.

The state machine, enforced twice

The legal transitions are one matches!:

src/txn/journal.rsverbatim

    /// Legal state-machine transitions. Forward progress is strictly
    /// ordered; any non-terminal state may roll back; `Swapped` may commit
    /// directly (recovery rolls forward from there).
    pub fn can_transition(self, next: TxnState) -> bool {
        use TxnState::*;
        matches!(
            (self, next),
            (Prepared, BackupCreated)
                | (BackupCreated, Swapped)
                | (Swapped, Committed)
                | (Prepared, RolledBack)
                | (BackupCreated, RolledBack)
                | (Swapped, RolledBack)
        )
    }

Matching on the tuple (self, next) against a list of allowed pairs is a lovely way to write a transition table: the whole legal graph is six lines, and anything not listed is illegal by construction. Terminal states appear on no left-hand side, so they have no outgoing edges at all.

And this is not advisory. The database layer refuses to perform an illegal transition:

src/index/db.rsinside journal_set_state, verbatim

        let current = TxnState::parse(&current)
            .ok_or_else(|| anyhow::anyhow!("journal row {id} has unknown state {current:?}"))?;
        if !current.can_transition(next) {
            anyhow::bail!(
                "illegal journal transition for row {id}: {} -> {}",
                current.as_str(),
                next.as_str()
            );
        }

It reads the row's current state, parses it, and rejects the write if the edge is not on the list. So a bug in the executor — jumping straight from prepared to committed, say — fails loudly at the moment it is attempted, instead of writing a state that makes the journal's story untrue. The doc comment on that method is explicit about why: an illegal transition is a bug and must fail loudly rather than corrupt the recovery invariants.

The unit tests for the machine are worth their four lines each. They assert the round trip through the string form, the strict forward order (including that Prepared cannot reach Swapped), that every non-terminal state can roll back, and that terminal states can go nowhere at all.

Finding the wreckage

src/index/db.rsverbatim

    /// All journal rows in a non-terminal state — interrupted transactions
    /// that recovery must repair.
    pub fn journal_incomplete(&self) -> Result<Vec<JournalEntry>> {
        let mut stmt = self.conn.prepare(
            "SELECT id, group_id, source, target, temp, backup, size, state, error
             FROM txn_journal
             WHERE state IN ('prepared', 'backup-created', 'swapped')
             ORDER BY id",
        )?;

Three states, one index scan, ordered by id so repairs happen in the order the transactions started. This is the query that idx_journal_state in chapter 5 exists for, and it is why the journal table has no foreign keys — these rows must be findable even if the scan that produced them was deleted and the groups rebuilt.

Then, for each one:

src/txn/recovery.rsverbatim

/// Repair every interrupted transaction found in the journal. Returns a
/// human-readable description of each repair. Safe to run on every launch;
/// an empty journal is a no-op.
pub fn recover_all(db: &mut Db) -> Result<Vec<String>> {
    let mut actions = Vec::new();
    for entry in db.journal_incomplete()? {
        let action = recover_one(db, &entry)?;
        actions.push(format!(
            "txn #{} ({}): {}",
            entry.id,
            entry.target.display(),
            action
        ));
    }
    Ok(actions)
}

Rolling back: the two states before the point of no return

src/txn/recovery.rsverbatim

        TxnState::Prepared => {
            remove_if_exists(&entry.temp)?;
            db.journal_set_state(
                entry.id,
                TxnState::RolledBack,
                Some("interrupted before swap; target untouched"),
            )?;
            Ok("rolled back (target was never touched)".into())
        }
        TxnState::BackupCreated => {
            let mut note = "rolled back";
            if !entry.target.exists() && entry.backup.exists() {
                fs::rename(&entry.backup, &entry.target)?;
                note = "rolled back (target restored from backup)";
            }
            remove_if_exists(&entry.temp)?;
            db.journal_set_state(
                entry.id,
                TxnState::RolledBack,
                Some("interrupted during swap; target restored"),
            )?;
            Ok(note.into())
        }

prepared is the easy one. Whatever we were doing — cloning, restoring metadata, verifying — none of it touched the user's file. There may be a temp clone; delete it if so. Done.

backup-created is the interesting one, because we genuinely do not know whether the crash landed before or after rename(target, backup). So the code asks the filesystem the one question that settles it: is the target missing while the backup exists? If yes, the rename happened and we put it back. If no, it did not, and there is nothing to restore. Either way the temp is removed and the row is closed.

Key idea Recovery uses both sources of truth. The journal says which repair to perform; the filesystem says which parts of it are still needed. Neither alone is enough — the journal cannot know how far a half-executed rename got, and the filesystem cannot tell a pre-swap backup from a post-swap one.

Note the condition is !target.exists() && backup.exists(), not just one of them. If both exist, something outside this transaction's story has happened and the safe move is to leave the target alone. Recovery never overwrites a file that is already sitting where it belongs.

Rolling forward: the state where undoing would be the mistake

Here is the arm that makes this design interesting, and it is worth reading in full:

src/txn/recovery.rsverbatim

        TxnState::Swapped => {
            // The temp clone passed full verification before `swapped` was
            // journaled, so completing the swap is the safe direction.
            if !entry.target.exists() && entry.temp.exists() {
                fs::rename(&entry.temp, &entry.target)?;
                if let Some(dir) = entry.target.parent() {
                    let _ = fsync_dir(dir);
                }
            }
            if entry.target.exists() {
                remove_if_exists(&entry.backup)?;
                db.journal_set_state(entry.id, TxnState::Committed, None)?;
                Ok("rolled forward (swap completed, backup removed)".into())
            } else if entry.backup.exists() {
                // Clone lost mid-crash; fall back to the original.
                fs::rename(&entry.backup, &entry.target)?;
                remove_if_exists(&entry.temp)?;
                db.journal_set_state(
                    entry.id,
                    TxnState::RolledBack,
                    Some("clone lost during interruption; target restored from backup"),
                )?;
                Ok("rolled back (clone was lost; target restored from backup)".into())
            } else {
                db.journal_set_state(
                    entry.id,
                    TxnState::RolledBack,
                    Some("neither target, temp, nor backup found; manual attention required"),
                )?;
                Ok("UNRESOLVED: neither target, temp, nor backup exists".into())
            }
        }

Why forward and not back? Because of what swapped means. Chapter 10 wrote that state only after the temp clone had passed every verification — type, size, mode against the target's snapshot, bytes against the source, resource fork against the source — and after the post-rename stat proved the original had not changed during the transaction. That clone is known-good. The original is sitting safely at the backup path. Finishing the rename is a single atomic operation with a known-correct input; rolling back would discard verified work for no gain.

Then three cases, in order of preference:

On diskRepairOutcome
target exists (or the rename completes it)remove the backup, mark committedcommitted — the reclaim succeeded
no target, no temp, but a backuprename backup back, remove temprolled-back — the user's file is back
none of the threeclose the row with a warningUNRESOLVED — say so plainly

That middle case — “clone lost mid-crash” — is defensive to the point of paranoia, and it is right to be. If the temp file vanished (a filesystem-level cleanup, a user tidying hidden files, a truly unlucky crash) but the backup is still there, the original is recoverable, and recovering it beats leaving the path empty.

And the third case is the honest one. If none of the three paths exist, there is genuinely nothing this program can do. It does not pretend: the journal error says manual attention required, and the line printed to the user starts with UNRESOLVED. A tool that admits its limits is more trustworthy than one that always claims success.

When recovery runs, and why that is the whole point

Not on a flag. Not on a repair subcommand. Before every command, every time:

src/lib.rsverbatim

/// Repair any transactions interrupted by a crash or kill. Run on every
/// launch; returns a description of each repair performed.
pub fn recover(db_path: &Path) -> Result<Vec<String>> {
    if !db_path.exists() {
        return Ok(Vec::new());
    }
    let mut db = Db::open(db_path)?;
    recovery::recover_all(&mut db)
}

The early return matters: on a machine that has never run a scan there is no database, and opening one would create an empty file for nothing. Otherwise, repair, and hand back a description of what was done — which main prints before it does anything else:

filecleaner groups, after a power cut
$ filecleaner groups
recovered: txn #7 (/Users/you/Downloads/golang.pdf): rolled forward (swap completed, backup removed)
Scan #1: 2 duplicate groups
  logical duplicates: 26.2 KiB   est. reclaimable: 26.2 KiB
…

One line, and then the command the user asked for. They never learn that a repair was pending; they just learn that one happened. The user guide's promise is exactly this: if your Mac loses power mid-reclaim, no cleanup is needed from you.

There is a second, quieter reason recovery runs first. A leftover .filecleaner.* temp file is byte-identical to a real file by construction. If a scan ran before recovery cleaned it up, the walker's own-artifact filter from chapter 4 would skip it — but a stale backup at the target path would confuse the index. Repairing first means every later stage sees a filesystem in a consistent state.

Testing a crash you cannot cause

You cannot reliably kill a process between two specific renames in a unit test. So the tests do the next best thing: they construct the wreckage by hand — write a journal row in a chosen state, arrange the files on disk exactly as a kill at that moment would have left them — and then run recovery against it. There is one test per state:

TestReconstructed stateAsserted repair
recovery_from_prepared_removes_temp_and_rolls_backjournal prepared, a temp file existstemp gone, target's original content intact, row rolled-back
recovery_from_backup_created_restores_targetjournal backup-created, target renamed awaytarget restored, temp and backup gone, row rolled-back
recovery_from_swapped_rolls_forwardjournal swapped, clone staged, target missingtarget has the clone's content, backup removed, row committed
recovery_from_swapped_with_lost_clone_falls_back_to_backupjournal swapped, no temp, backup presenttarget restored from backup, row rolled-back
recovery_is_idempotent_and_ignores_terminal_rowsa repairable row plus a terminal onefirst run repairs one, second run repairs nothing

The idempotence test is the one I would keep closest:

tests/txn_integration.rsabridged &mdash; setup elided

    assert_eq!(recover(&f.db_path).unwrap().len(), 1);
    assert_eq!(recover(&f.db_path).unwrap().len(), 0, "nothing left to do");

Because recovery runs on every launch, it must be a no-op the second time. If it were not — if it kept trying to repair a row it had already closed — every subsequent command would try to undo a completed reclaim. Two lines, and they pin down the one property that makes “run it always” a safe policy.

Notice too what makes the “roll forward” test convincing: the reconstructed temp file contains different bytes from the original (b"clon" versus b"orig"), so afterwards you can tell from the content alone which way recovery went. Testing a swap between two identical files would prove nothing.

What we gained — the whole book, in one page

We began with three copies of a video and a refusal to delete any of them. Twelve chapters later, here is what the program does, end to end, and what each piece cost:

StepWhat it buysLines
Walk and filter (ch. 4)Candidates, with an audit trail of every refusal, reading no file contents~260
Index (ch. 5)Resumability, and a durable claim about the past to check against later~640
Funnel (ch. 6)200,000 files narrowed to a handful of pairs~270
Preflight (ch. 9)A dry run that means something, and a cheap “probably”~150
Transaction (ch. 10)A replacement with only two possible outcomes~330
Metadata (ch. 11)A replacement macOS cannot tell from the original~470
Recovery (ch. 12)Crash safety that needs nothing from the user~110

And the Rust that carried it, none of it exotic: ownership decided who owned a path and when a buffer died; Result and ? carried failures without obscuring the happy path; two error crates split “something to decide” from “something to read”; iterators and closures expressed the eligibility policy in nine lines; one trait turned an untestable platform boundary into a fault-injection rig; enums with exhaustive match made “did you handle every state?” a compile error; and unsafe was confined to one module, in blocks one expression wide, each with a comment saying what was being promised.

And the honest caveats This is not a backup tool: after reclaiming, the copies share physical blocks on one volume, and if those blocks die they all die together. The savings are estimates — snapshots, sparse files and pre-existing clones make the observed free space differ, and du will keep reporting each file at full size. And a replaced file has a new inode, so sync services will see it as changed and may re-upload it. The README says all three plainly, which is itself part of the design.

So what did we actually gain?

A working answer to a question that sounds impossible: how do you modify someone's files while they are using the computer, and be certain you can never make things worse?

The answer turned out not to be cleverness. It was a sequence of ordinary decisions, each one paid for by the last. Narrow aggressively, so the authoritative check is affordable. Check at the last possible instant, not the most convenient one. Stage beside the thing you are replacing, so the commit is a rename. Write down what you are about to do, before you do it. Track how far you got, so undo is a lookup. And after the point of no return, stop trying to undo.

Those ideas are not about APFS, or macOS, or even about files. They are what any program looks like when it takes seriously that it might be interrupted, and that the data does not belong to it. The best way to keep reading is to clone the repository, run cargo test, and then break something on purpose — comment out the post-rename stat check and watch which test fails first. That test will tell you, better than this book can, what that line was for.

Final challenges
  1. Add a TempVerified state between prepared and backup-created. Write the recovery arm for it — and then argue whether it earns its place.
  2. Recovery never re-verifies content: rolling forward from swapped trusts a verification that happened before the crash. Construct the scenario where that trust is misplaced, and say what it would cost to close.
  3. The journal keeps committed and rolled-back rows forever. Design a retention policy, and say exactly which recovery guarantee constrains how aggressive it can be.
  4. Take the pattern — journal intent, stage beside, verify, atomic swap, repair on launch — and apply it to something that is not a file. A configuration record? A database row? What plays the part of rename?
