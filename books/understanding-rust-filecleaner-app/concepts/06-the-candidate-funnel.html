Chapter 06 · Part II — Finding the Duplicates

The Candidate Funnel

Here is the problem in one sentence: you have 200,000 files totalling 400 GB, and you need to know which of them have identical contents. The naïve answer — hash everything, compare the hashes — is correct, obvious, and reads 400 GB off the disk. On a laptop that is tens of minutes of grinding for an answer that, nine times out of ten, is “there were eleven duplicates.” The funnel is how this program gets the same answer while opening almost nothing.

The argument, before the code

The insight is that duplicate detection is a series of ever-more-expensive questions, and each one only has to be asked of whatever survived the last. Two files with different sizes cannot possibly be identical — and their sizes are already in the database, so that question costs no disk reads at all. Two files with the same size probably still differ, and looking at a few kilobytes from each will usually prove it. Only the files that survive both deserve to be read in full.

Stage 1: the cheapest question is a SQL query

The first stage does not open a single file. It asks the index which files even could have a partner:

src/index/db.rsverbatim

    /// Files that still need a partial fingerprint: members of a
    /// (volume, size, resource-fork length) bucket containing at least two
    /// distinct inodes. Everything else can never be a duplicate candidate.
    pub fn fingerprint_candidates(&self, scan_id: i64) -> Result<Vec<HashCandidate>> {
        self.candidates(
            scan_id,
            "SELECT f.id, f.path, f.size, f.mtime_sec, f.mtime_nsec
             FROM files f
             JOIN (SELECT dev, size, rsrc_len
                   FROM files WHERE scan_id = ?1
                   GROUP BY dev, size, rsrc_len
                   HAVING COUNT(DISTINCT ino) >= 2) b
               ON f.dev = b.dev AND f.size = b.size AND f.rsrc_len = b.rsrc_len
             WHERE f.scan_id = ?1 AND f.fingerprint IS NULL",
        )
    }

Every clause is a decision from an earlier chapter, cashed in:

  • GROUP BY dev — because clones are same-volume only (chapter 2). A duplicate on an external drive can never be reclaimed against one on the internal disk, so it is not even a candidate.
  • size — the obvious one. Different lengths, different files.
  • rsrc_len — because on macOS identical data forks with different resource forks are different files (chapter 4). Putting it in the bucket key means such files never meet.
  • HAVING COUNT(DISTINCT ino) >= 2 — the sharp one. Not COUNT(*): distinct inodes. Ten hard links to one file are ten rows and one inode, and there is nothing to reclaim among them. This single word is how the hardlink rule from chapter 3 reaches all the way down into stage one.
  • AND f.fingerprint IS NULL — the resumability clause. Already fingerprinted? Not a candidate for fingerprinting.

The second stage's query is the same shape with the fingerprint added to the bucket key and f.sha256 IS NULL as the filter. Both funnel through one private helper, candidates, which is where the row-decoding loop lives — two public methods, one implementation, no duplicated decode.

Stage 2: a fingerprint is three peeks

Now we open files, but only barely.

src/index/fingerprint.rsverbatim

/// Bytes hashed per sampled range.
pub const RANGE_LEN: u64 = 64 * 1024;

/// Cheap partial fingerprint: BLAKE3 over the first, middle, and last
/// 64 KiB. Splits most same-sized files without reading full contents.
/// Files small enough that the ranges would overlap are hashed whole.
pub fn compute(
    path: &Path,
    size: u64,
    mtime_sec: i64,
    mtime_nsec: i64,
) -> Result<[u8; 32], HashError> {
    verify_unchanged(path, size, mtime_sec, mtime_nsec)?;

    let mut file = File::open(path)?;
    let mut hasher = blake3::Hasher::new();

    if size <= 3 * RANGE_LEN {
        let mut buf = Vec::with_capacity(size as usize);
        file.read_to_end(&mut buf)?;
        hasher.update(&buf);
    } else {
        let offsets = [0, size / 2 - RANGE_LEN / 2, size - RANGE_LEN];
        let mut buf = vec![0u8; RANGE_LEN as usize];
        for offset in offsets {
            file.seek(SeekFrom::Start(offset))?;
            file.read_exact(&mut buf)?;
            hasher.update(&buf);
        }
    }
    Ok(*hasher.finalize().as_bytes())
}

Read a 4 GB video with this and you touch 192 KiB — about 0.005% of it. Three seeks and three reads, regardless of size.

Why first, middle and last? Because file formats cluster their differences. Two exports of the same video share a container header; two versions of a document share a preamble; two disk images differ deep inside. Sampling only the head would call thousands of distinct files identical and push them all to the expensive stage. Three points from opposite ends of the file catch the overwhelming majority of near-misses cheaply.

Why the small-file branch? Look at the offsets for a 100 KiB file: 0, 18 KiB, 36 KiB — three overlapping 64 KiB windows that between them run off the end of the file, so read_exact would fail. Below 3 × RANGE_LEN (192 KiB) the file is simply hashed whole, which is both correct and, at that size, cheaper than seeking around.

Why BLAKE3 here and SHA-256 later? This stage is a filter, not a record. Nothing is stored under this hash forever; it exists to split a bucket, so raw speed is the only thing that matters and BLAKE3 is very fast. The next stage produces the value the database keeps, and there a widely-recognised cryptographic standard is the better citizen. Two hashes with two jobs.

read_exact rather than read is a small correctness point worth noticing: a plain read is allowed to return fewer bytes than you asked for, and hashing a partially-filled buffer would produce a fingerprint that depends on how the kernel felt that morning. read_exact loops until the buffer is full or the file ends.

The check that runs before every read

Both hashing functions open with the same line: verify_unchanged(path, size, mtime_sec, mtime_nsec)?;. It is fifteen lines and it is the spine of this program's honesty.

src/index/hasher.rsverbatim

/// Confirm `path` is still the regular file the scan recorded: same size,
/// same mtime. Called before any read so we never hash — and later never
/// reclaim — a file that moved on.
pub fn verify_unchanged(
    path: &Path,
    size: u64,
    mtime_sec: i64,
    mtime_nsec: i64,
) -> Result<(), HashError> {
    use std::os::unix::fs::MetadataExt;

    let meta = std::fs::symlink_metadata(path).map_err(|_| HashError::Stale)?;
    if !meta.is_file()
        || meta.len() != size
        || meta.mtime() != mtime_sec
        || meta.mtime_nsec() != mtime_nsec
    {
        return Err(HashError::Stale);
    }
    Ok(())
}

The scan happened at some point in the past. Between then and now, the user may have edited the file, replaced it, deleted it, or swapped it for a directory. So before trusting anything the index says about a file, the code re-stats it and compares against what was recorded — size, modification time to the nanosecond, and still-a-regular-file.

Notice the error handling on the very first line: .map_err(|_| HashError::Stale). If the stat fails at all — the file is gone, the directory became unreadable — the answer is not “an I/O error occurred,” it is “this candidate is stale.” That is the right framing, because the caller's response is identical in both cases: drop it and move on.

Key idea Stale is a value, not a failure. The funnel counts it separately from I/O errors and keeps going. A tool that aborted a 200,000-file scan because one file was saved mid-run would be unusable — and a tool that hashed the new contents and stored them under the old identity would be dangerous.

Stage 3: the stored identity

src/index/hasher.rsverbatim

/// Stream the whole data fork and return its SHA-256 — the stored content
/// identity. (Byte comparison, not this hash, is the final authority before
/// a destructive replacement.)
pub fn full_sha256(
    path: &Path,
    size: u64,
    mtime_sec: i64,
    mtime_nsec: i64,
) -> Result<[u8; 32], HashError> {
    verify_unchanged(path, size, mtime_sec, mtime_nsec)?;

    let mut file = File::open(path)?;
    let mut hasher = Sha256::new();
    let mut buf = vec![0u8; 1024 * 1024];
    loop {
        let n = file.read(&mut buf)?;
        if n == 0 {
            break;
        }
        hasher.update(&buf[..n]);
    }
    Ok(hasher.finalize().into())
}

A 1 MiB buffer, reused for the whole file, with hasher.update(&buf[..n]) feeding only the bytes actually read. Memory use is constant whether the file is 2 MB or 200 GB — the streaming shape that everything touching large files should have. And unlike the fingerprint, here a short read is fine and expected: the loop simply hashes what it got and asks again, stopping at n == 0 (end of file).

The unit test is a nice touch of paranoia — it hashes b"abc" and compares against the published SHA-256 test vector, byte by byte. That is not testing SHA-256 (the sha2 crate can do that); it is testing that this code feeds it correctly.

Read the doc comment again “Byte comparison, not this hash, is the final authority before a destructive replacement.” The program computes a cryptographic hash of the entire file — and then still refuses to act on it. Chapter 10 re-reads both files in full and compares them byte for byte inside the transaction. Why? Two reasons, and the second is the real one. A hash collision is astronomically unlikely; but a stale hash is not. The SHA-256 in the database was true at scan time, and the file may have changed since. The byte comparison happens milliseconds before the swap, in the same transaction — and that closeness in time, more than the strength of the hash, is what makes it authoritative.

The driver: one function, four lines of meaning

src/index/funnel.rsverbatim

/// Run the duplicate-detection funnel over a scan: partial fingerprints for
/// size-bucket survivors, full SHA-256 for fingerprint survivors, then
/// rebuild the confirmed duplicate groups.
pub fn run(db: &mut Db, scan_id: i64) -> Result<FunnelReport> {
    let mut report = FunnelReport::default();

    let candidates = db.fingerprint_candidates(scan_id)?;
    let fingerprints = hash_stage(&candidates, &mut report, |c| {
        fingerprint::compute(&c.path, c.size, c.mtime_sec, c.mtime_nsec)
    });
    report.fingerprinted = fingerprints.len() as u64;
    db.set_fingerprints(&fingerprints)?;

    let candidates = db.full_hash_candidates(scan_id)?;
    let hashes = hash_stage(&candidates, &mut report, |c| {
        hasher::full_sha256(&c.path, c.size, c.mtime_sec, c.mtime_nsec)
    });
    report.fully_hashed = hashes.len() as u64;
    db.set_sha256s(&hashes)?;

    report.groups = db.rebuild_groups(scan_id)?;
    Ok(report)
}

Ask the database what needs doing, do it, write the results back. Twice. Then rebuild the groups. The two stages are visibly the same shape because they are the same shape — which is what makes the shared helper below possible.

And because every result is persisted before the next stage begins, the whole function is restartable. Kill it during the SHA-256 stage and re-run: stage one finds no candidates (every fingerprint is already stored), stage two picks up the files whose sha256 is still NULL. The FunnelReport says as much in its own doc comment — a re-run over an unchanged index reports zeros, because there was nothing left to do.

Parallelism in five lines, without a single lock

src/index/funnel.rsverbatim

fn hash_stage(
    candidates: &[HashCandidate],
    report: &mut FunnelReport,
    hash: impl Fn(&HashCandidate) -> Result<[u8; 32], HashError> + Sync,
) -> Vec<(i64, [u8; 32])> {
    let results: Vec<(i64, Result<[u8; 32], HashError>)> = candidates
        .par_iter()
        .map(|c| (c.id, hash(c)))
        .collect();

    let mut ok = Vec::with_capacity(results.len());
    for (id, result) in results {
        match result {
            Ok(digest) => ok.push((id, digest)),
            Err(HashError::Stale) => report.stale += 1,
            Err(HashError::Io(_)) => report.errors += 1,
        }
    }
    ok
}

The parameter that makes one function serve two stages

hash: impl Fn(&HashCandidate) -> Result<[u8; 32], HashError> + Sync. In English: “any callable that turns a candidate into a 32-byte digest or a hash error, and that is safe to call from several threads at once.” The impl Trait position means the compiler generates a specialised copy for each call site — no dynamic dispatch, no allocation — and the two closures in run slot straight in.

The + Sync is not decoration. It is what par_iter() demands, and demanding it is how Rust knows this parallelism is sound. Try to pass a closure capturing something thread-unsafe and this line is where it fails to compile.

par_iter(): change one word, get every core

Rayon's parallel iterators are drop-in replacements for the standard ones: .iter() becomes .par_iter(), and the work is distributed across a thread pool sized to the machine. That is the entire change. The .map(…).collect() after it is ordinary iterator code.

This is I/O-bound work, and the bound is the point — a pool of a few threads keeps the disk busy while one thread waits on a read, without spawning 200,000 tasks that would thrash it. PLAN.md's design note is one line: “No Tokio: rayon with a bounded pool fits this batch, disk-bound workload.” An async runtime would have brought a scheduler, a colour to every function signature, and no benefit for work that is a fixed batch of blocking reads.

Collect first, then count

Key idea The obvious way to write this is to increment report.stale from inside the parallel map — and that needs a Mutex, or an atomic, and it makes the ordering of results non-deterministic. This code sidesteps the whole problem: the parallel phase produces a Vec of (id, Result) and touches nothing shared; the sequential phase walks that Vec and does the counting. No locks, no atomics, no contention — and the counters are exact.

The match in that second phase is where the two variants of HashError finally earn their existence. A stale file and an unreadable file are both “no digest,” but the user needs to be told different things — and the CLI prints them separately: dropped: 2 changed since scan, 1 unreadable. That is the payoff for a typed error enum, and it is the subject of the next chapter.

Grouping: from hashes to reviewable groups

The last call in the funnel rebuilds the groups from scratch. Its core is one more GROUP BY, now with the full hash in the key:

src/index/db.rsinside rebuild_groups, verbatim

                "SELECT dev, size, rsrc_len, sha256
                 FROM files
                 WHERE scan_id = ?1 AND sha256 IS NOT NULL
                 GROUP BY dev, size, rsrc_len, sha256
                 HAVING COUNT(DISTINCT ino) >= 2",

For each surviving key it loads the members, calls policy::choose_source from chapter 3, and writes one groups row plus a group_id on every member. One ordering detail is worth stealing:

src/index/db.rsinside rebuild_groups, verbatim

        // Clear membership before deleting groups so the files → groups
        // foreign key never dangles.
        tx.execute(
            "UPDATE files SET group_id = NULL WHERE scan_id = ?1",
            params![scan_id],
        )?;
        tx.execute("DELETE FROM groups WHERE scan_id = ?1", params![scan_id])?;

Detach the children, then delete the parents — and do both inside one transaction, so no other reader ever sees the half-way state. The comment explains the order so that the next person does not “tidy” it into a constraint violation.

What the tests insist on

The funnel's integration tests are worth listing, because together they are a specification of everything above:

TestThe claim it defends
Identical large files share a fingerprintSampling is deterministic and position-based.
A one-byte middle difference changes itSame size, same head, same tail — and still split, cheaply.
Small files are hashed wholeThe ≤192 KiB branch is correct, not just non-crashing.
A stale candidate is rejectedverify_unchanged fires before any read.
Hardlinks collapse to one entityCOUNT(DISTINCT ino) does what the comment says.
Resource-fork differences split groupsrsrc_len in the bucket key is load-bearing.
A re-run rehashes nothingThe IS NULL clauses really do make it resumable.

The second row is the one I would put on the wall. Two 400 KiB files, identical except for one flipped byte in the middle, same size, same mtime. A head-only fingerprint would call them candidates and send both to a full hash. This one does not — and the test exists specifically to keep it that way.

So what did we actually gain?

Enormously less I/O, and — less obviously — permission to be paranoid later. Because the funnel narrows 200,000 files down to a handful of genuine candidate pairs, the program can afford to re-read both files in full immediately before touching anything. If detection had to be the authority, we would be forced to trust a hash computed minutes or days ago. Because detection is only a nomination, we get to check the answer at the last possible instant.

That is a design lesson well beyond this program: making the cheap path cheap is often how you buy the right to make the critical path expensive.

Challenges
  1. Compute the total bytes read by the fingerprint stage for 10,000 files of 1 GB each that all share a size, and compare it to the full-hash stage. Then decide how much of that ratio survives if the files are all 100 KiB instead.
  2. hash_stage collects every result before counting. What is the peak memory cost for a million candidates — and would you accept a lock to avoid it?
  3. The fingerprint's middle offset is size / 2 - RANGE_LEN / 2. Construct two files of equal size that this fingerprint cannot distinguish, then say why the funnel is still correct.
