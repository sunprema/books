Chapter 03 · Part II — Finding the Duplicates

The Domain, Written as Types

Before a program can do anything interesting it has to decide what words it uses. Not variable names — words: the handful of nouns that the rest of the code will spend its life passing around. In this application there are five, they all live in src/model.rs, and the whole file is 124 lines. It is the cheapest chapter in the book and, I would argue, the highest-leverage one.

Two names for two numbers

The file opens with a pair of one-line types:

src/model.rsverbatim

/// Identifies a mounted volume (`st_dev`). APFS cloning only works when
/// source and target share a `VolumeId`, and the check must be repeated at
/// preflight time because volumes can unmount and remount between runs.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct VolumeId(pub u64);

/// Stored content identity: SHA-256 of the data fork. Hashes nominate
/// duplicate candidates; a byte-for-byte comparison is the final authority
/// before any replacement.
#[derive(Debug, Clone, PartialEq, Eq, Hash)]
pub struct ContentId(pub [u8; 32]);

These are newtypes: tuple structs that wrap exactly one value and add nothing but a name. VolumeId(pub u64) is a u64 at runtime — same size, same speed, no allocation, no indirection — but a different type at compile time. Hand a function a VolumeId where it wanted a file size and the program does not compile.

Look at the derive lists, because they are a design statement. VolumeId is Copy: it is one machine word, so passing it around should be as cheap as passing an integer. ContentId is not Copy, because it is 32 bytes and the author would rather you noticed when you duplicated one. Both are Hash and Eq, which is the license to use them as keys in a HashMap — the natural thing to want to do with an identity.

An honest note about this codebase These two types are declared and documented, and FileEntry::volume() constructs a VolumeId — but nothing else in the program currently uses either one. The index stores a device as a plain u64 and a hash as a plain [u8; 32], and grouping compares those primitives directly. So the newtypes here document an intention that the code has not yet been wired to enforce. That is worth seeing plainly, because it is the most common half-life of a good idea in a real codebase: the type exists, the discipline hasn't reached the SQL boundary yet.

Why does the discipline stall at that boundary? Because rusqlite hands you back an i64, and every row constructor would need one more conversion. That is a small cost, but it is a cost paid on every read, and this is what makes newtype adoption an all-or-nothing decision in practice. We will meet the exact spot in the next chapter but one.

FileEntry: what one scan observation is

Here is the record the scanner produces, one per eligible file:

src/model.rsverbatim

/// One eligible regular file recorded during enumeration.
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct FileEntry {
    pub path: PathBuf,
    pub dev: u64,
    pub ino: u64,
    pub nlink: u64,
    pub size: u64,
    pub mtime_sec: i64,
    pub mtime_nsec: i64,
    /// Resource-fork length (`com.apple.ResourceFork` xattr), 0 if absent.
    /// Part of the grouping key: files whose forks differ are not
    /// macOS-identical even when their data forks match.
    pub rsrc_len: u64,
}

Every field here is load-bearing, and it is worth asking of each one “what decision does this enable?”

FieldThe decision it enables
pathThe only field the user ever sees. Owned (PathBuf, not &Path) because the entry outlives the walk.
devWhich volume. Clones are same-volume only, so this is part of every grouping key.
inoWhich file, as opposed to which name. Two paths with one inode are one file.
nlinkHow many names this file has. More than one and we refuse to touch it.
sizeThe first, cheapest duplicate filter — and part of the “has it changed?” check.
mtime_sec / mtime_nsecChange detection at nanosecond resolution, and the tiebreaker for choosing a source.
rsrc_lenmacOS-specific: the resource fork's size. Two files with identical data forks and different forks are different files.

Note what is absent: no hash. A FileEntry is what the walker could learn without opening the file. Hashes arrive later, in the database, as nullable columns — and that separation is the funnel's whole economy.

Note also the timestamp types: i64, not u64. Unix timestamps can be negative, and a file dated before 1970 is unusual but not impossible. Choosing the signed type costs nothing and removes a class of bug.

DuplicateGroup: a set of files that claim to be the same

Once the funnel has run, files that share a volume, a size, a resource-fork length and a full SHA-256 are collected into a group. One member is marked the source.

src/model.rsverbatim

/// A confirmed duplicate group: files on one volume sharing size, resource
/// fork length, and full-content SHA-256. Byte comparison still happens at
/// reclaim time; this grouping only nominates candidates.
#[derive(Debug, Clone)]
pub struct DuplicateGroup {
    pub id: i64,
    pub dev: u64,
    pub size: u64,
    pub rsrc_len: u64,
    pub sha256: [u8; 32],
    pub members: Vec<GroupMember>,
}

#[derive(Debug, Clone)]
pub struct GroupMember {
    pub file_id: i64,
    pub path: PathBuf,
    pub ino: u64,
    pub nlink: u64,
    pub mtime_sec: i64,
    pub mtime_nsec: i64,
    pub is_source: bool,
}

Read that doc comment once more — “this grouping only nominates candidates.” The type is called DuplicateGroup, it is keyed by a cryptographic hash, and the author still refuses to let it mean “these files are identical.” It means “these files are worth comparing.” Chapter 10 does the comparing.

A modelling choice worth arguing with

The source is marked by a bool on each member rather than, say, storing the source as its own field of the group. That makes an invalid state representable: zero sources, or three. The code closes the gap with an assertion instead of a type:

src/model.rsverbatim

    pub fn source(&self) -> &GroupMember {
        self.members
            .iter()
            .find(|m| m.is_source)
            .expect("every group has a source")
    }

Is that a flaw? Defensibly not, and it is worth understanding why, because the reasoning shows up constantly in real systems code. The invariant is enforced one layer down: the groups table has a source_file_id INTEGER NOT NULL column, and the loader marks exactly the member whose id matches. There is precisely one function that can construct a group, and it cannot construct a sourceless one. The expect is documentation of that invariant, positioned so that if someone ever builds a group by hand and gets it wrong, the program dies immediately and loudly at the exact spot rather than doing something subtle and destructive later. “Crash on a broken invariant” is the right behaviour for a tool that is about to replace your files.

The safety policy is three methods long

Here is my favourite passage in the codebase, because it is where a paragraph of policy becomes a line of code:

src/model.rsverbatim

    /// Targets that can actually be reclaimed: a different inode than the
    /// source (hardlinks of the source already share storage) and no other
    /// hardlinks (replacing one path of a multi-link inode would silently
    /// break the link relationship for paths outside our view).
    pub fn eligible_targets(&self) -> impl Iterator<Item = &GroupMember> {
        let source_ino = self.source().ino;
        self.members
            .iter()
            .filter(move |m| m.ino != source_ino && m.nlink == 1)
    }

    /// Bytes stored beyond one copy: size × (distinct inodes − 1).
    pub fn logical_duplicate_bytes(&self) -> u64 {
        self.size * (self.distinct_inodes() - 1)
    }

    /// Estimate only: APFS free-space accounting, snapshots, and prior
    /// clones can make the observed change differ.
    pub fn estimated_reclaimable_bytes(&self) -> u64 {
        self.size * self.eligible_targets().count() as u64
    }

The two conditions

m.ino != source_ino excludes hard links of the source. There is nothing to gain: they are already the same inode, already sharing every block. Replacing one would be work that frees zero bytes and breaks a link the user created on purpose.

m.nlink == 1 is the sharper rule. If a file has two names and we replace it, the path we replaced now points at a brand-new inode — and the other name, which we may never have seen, still points at the old one. We would have silently severed a relationship the user relies on, in a directory we might not even have scanned. The tool refuses. a file with more than one link is never reclaimed

A closure that has to own its capture

One Rust detail in eligible_targets is worth slowing down for, because it is a rite of passage. The closure is written .filter(move |m| …). Without move, the closure would borrow the local source_ino — and the function returns the iterator, which would then outlive the local it borrowed. The compiler rejects it. With move, the closure takes source_ino by value (it is a u64, so this is a copy of eight bytes) and the iterator is free to travel.

The return type is worth noticing too: impl Iterator<Item = &GroupMember>. The caller learns “this is some iterator of member references” and nothing about the three layers of Filter<Iter<…>> underneath, which means the implementation can change without touching a signature. And because the items are references, no member is cloned to iterate the group.

Counters that serialize

The last type in the file is a plain bag of counters, and its derive list is the interesting part:

src/model.rsverbatim

/// Counters accumulated during a scan, reported to the user afterwards.
#[derive(Debug, Default, Clone, PartialEq, Eq, serde::Serialize)]
pub struct ScanStats {
    pub eligible: u64,
    pub eligible_bytes: u64,
    pub directories: u64,
    pub symlinks: u64,
    pub zero_byte: u64,
    pub special: u64,
    pub packages_skipped: u64,
    pub own_artifacts: u64,
    pub hardlinked: u64,
    pub errors: u64,
}

Default is why the walker can begin with ScanStats::default() and get ten zeroes without writing them out. serde::Serialize is why filecleaner scan --json can emit these counters to a GUI without a second, hand-maintained JSON shape. One struct, two audiences: the human-readable printer in main.rs reads the fields, and serde writes them. When the SwiftUI app wants a new counter, adding a field here is the whole change.

Choosing the source: a whole policy in one comparison

Which copy survives as the one whose blocks everyone shares? It matters less than you would think — after cloning, no copy is more authoritative than any other — but it must be decided the same way every time, or two runs would disagree about which file to leave alone. src/policy.rs is 67 lines including its tests, and this is the whole of the logic:

src/policy.rsverbatim

/// Default source selection: oldest modification time wins, ties broken by
/// lexicographically smallest path. Deterministic so repeated runs pick the
/// same source. The source is only ever read, never written, during a
/// reclamation transaction.
pub fn choose_source(members: &[FileEntry]) -> usize {
    assert!(!members.is_empty(), "cannot choose a source from no members");
    let mut best = 0;
    for (i, candidate) in members.iter().enumerate().skip(1) {
        let b = &members[best];
        let candidate_key = (candidate.mtime_sec, candidate.mtime_nsec, &candidate.path);
        let best_key = (b.mtime_sec, b.mtime_nsec, &b.path);
        if candidate_key < best_key {
            best = i;
        }
    }
    best
}

The trick is the tuple. In Rust, tuples compare lexicographically: compare the first elements, and only if they are equal move on to the second, then the third. So (mtime_sec, mtime_nsec, &path) expresses “oldest second wins; if the seconds tie, oldest nanosecond; if those tie too, the alphabetically first path” in a single <. Writing that policy as nested ifs would take a dozen lines and hide the intent.

Two more details. The function returns an index, not a reference — which sidesteps the borrow that returning &FileEntry would create, and lets the caller in db.rs use it to look up a database row id instead. And &candidate.path compares a &PathBuf without cloning anything: the comparison borrows, does its work, and ends.

The three unit tests below it read like a specification, which is the point of them:

src/policy.rsone of three unit tests, verbatim

    #[test]
    fn nanoseconds_break_second_ties() {
        let mut older = entry("/z/file.txt", 1000);
        older.mtime_nsec = 100;
        let mut newer = entry("/a/file.txt", 1000);
        newer.mtime_nsec = 200;
        assert_eq!(choose_source(&[newer, older]), 1);
    }

Note the adversarial construction: the newer file is also the alphabetically-first one, so a policy that accidentally sorted by path alone would return 0 and fail. A test that can only pass for the right reason is worth three that pass for any reason.

Key idea The doc comment slips in a promise that the whole second half of the book has to keep: the source is only ever read, never written. Chapter 10 will show you that the executor opens the source exactly twice, both times for reading, and never names it in a rename or a remove_file.

So what did we actually gain?

A vocabulary, and — more importantly — a place where the safety rules live as code rather than as prose. eligible_targets is the answer to “which files may we touch?”, and it is nine lines long, in one file, with its reasoning in a doc comment directly above it. When chapter 9's preflight re-checks the same conditions against the live filesystem, it is not duplicating this logic; it is confirming that the world still matches what this decided.

We also gained a small, honest lesson: two newtypes that document an intention the code hasn't finished adopting. Real codebases are full of these, and reading one accurately means noticing them rather than assuming every declared type is load-bearing.

Challenges
  1. Make VolumeId load-bearing: change FileEntry.dev and DuplicateGroup.dev to VolumeId. How many call sites change, and how many of them are inside db.rs?
  2. logical_duplicate_bytes multiplies before subtracting. Construct a group where size * (distinct_inodes() - 1) overflows a u64, and say whether you consider it a real bug.
  3. source() panics on a sourceless group. Rewrite it to return Option<&GroupMember> and follow the change outward — what happens to eligible_targets, which calls it unconditionally?
