Chapter 07 · Part III — Rust Craft in the Middle

Errors: anyhow at the Edges, thiserror in the Core

We are about to enter the half of this program that changes your files, and almost everything in it can fail. So it is worth stopping for one short chapter on how this codebase says “no.” It uses two error crates — which sounds like indecision, and is in fact the single most useful convention in the Rust ecosystem.

One question decides which crate you want

Does the caller need to do something different depending on which failure happened?

If yes, the caller must be able to match, which means the error needs a type with named variants. That is thiserror: a derive macro that writes the boilerplate for a custom error enum. If no — if the error is going to be printed, logged, and turned into a non-zero exit code — then a type is overhead and what you want is a good message with context attached. That is anyhow.

The usual formulation is “thiserror for libraries, anyhow for applications.” This project is both at once — a library crate and a binary that consumes it — so it draws the line inside itself, and drawing it is the interesting part.

The smallest typed error in the program

We met this one in the last chapter. Two variants, and both of them exist because the funnel counts them into different columns:

src/index/hasher.rsverbatim

/// Why a funnel stage could not hash a candidate.
#[derive(Debug, thiserror::Error)]
pub enum HashError {
    /// The file changed (or vanished, or stopped being a regular file)
    /// since it was scanned. The filesystem is mutable; stale candidates
    /// simply drop out of the funnel.
    #[error("file changed since scan")]
    Stale,
    #[error(transparent)]
    Io(#[from] std::io::Error),
}

Four pieces of machinery in nine lines. Let's name each one.

#[derive(thiserror::Error)]

Generates the std::error::Error implementation — the trait that makes a type a first-class error: printable, chainable, usable with ? and with anyhow. Written by hand this is twenty lines of impl Display and impl Error. Note also that Debug is still derived normally — thiserror does not do that one for you, and the trait requires it.

#[error("…")]

The Display text for that variant. This is the string a user will read, so it is written for a user: “file changed since scan”, not “StaleCandidateError”. The format string may interpolate the variant's fields — {0} for a tuple field, {name} for a named one — which we will see used in a moment.

#[from]

Generates impl From<std::io::Error> for HashError. That single line is what makes let mut file = File::open(path)?; work inside a function returning Result<_, HashError>. The ? operator is not magic: on the error path it calls From::from to convert whatever it caught into the function's declared error type. #[from] supplies that conversion.

#[error(transparent)]

“Do not add a message of my own; forward Display and source straight through to the wrapped error.” So an underlying “Permission denied (os error 13)” prints exactly that, rather than “hash error: Permission denied (os error 13)”. Use it whenever your variant is pure pass-through; use a message when your variant genuinely adds information.

Both patterns are visible in the same enum here, which makes it a good nine lines to keep bookmarked.

Eleven variants that are really a safety policy

Now the big one. Read this as a list of the reasons this program will refuse to touch your file — because that is exactly what it is:

src/txn/planner.rsverbatim

#[derive(Debug, thiserror::Error)]
pub enum PreflightError {
    #[error("target is not a regular file")]
    TargetNotRegular,
    #[error("source is not a regular file")]
    SourceNotRegular,
    #[error("target changed since scan (size, mtime, or inode differs)")]
    TargetChanged,
    #[error("target has additional hardlinks; replacing it would break them")]
    TargetHardlinked,
    #[error("source and target are the same inode")]
    SameInode,
    #[error("source and target are on different volumes; APFS clones are same-volume only")]
    DifferentVolume,
    #[error("target volume is not APFS")]
    NotApfs,
    #[error("target is immutable (uchg/schg flag set)")]
    TargetImmutable,
    #[error("source is not readable: {0}")]
    SourceUnreadable(String),
    #[error("target directory is not writable")]
    DirNotWritable,
    #[error(transparent)]
    Io(#[from] std::io::Error),
}

Ten named refusals and one pass-through. Every message is a complete sentence aimed at a person, and several of them explain why rather than only what: “replacing it would break them,” “APFS clones are same-volume only.”

Here is why that matters. The CLI does not translate these into user-facing copy. It prints them:

Key idea The error type and the user-facing text are the same string, written once. There is no mapping table in main.rs from variant to message that could drift out of sync with the enum, and adding a twelfth refusal automatically means the CLI can explain it. That is Display earning its keep.

Note the one variant carrying data: SourceUnreadable(String), whose message interpolates it with {0}. “Not readable” is not actionable on its own — the user needs to know whether it was permissions or a vanished file — so the underlying reason is carried along. Compare that to DirNotWritable, where there is nothing to add: the check that produced it was a boolean.

Composing one typed error out of another

src/txn/executor.rsverbatim

#[derive(Debug, thiserror::Error)]
pub enum TxnError {
    #[error("preflight failed: {0}")]
    Preflight(#[from] PreflightError),
    #[error("identity verification failed: {0}")]
    Identity(String),
    #[error("temp clone verification failed: {0}")]
    TempVerify(String),
    #[error("final validation failed: {0}")]
    FinalValidation(String),
    #[error(transparent)]
    Io(#[from] io::Error),
    #[error("database error: {0}")]
    Db(String),
}

The first variant is the interesting one. Preflight(#[from] PreflightError) means a PreflightError converts automatically into a TxnError — which is precisely why the executor can open with a single line:

    planner::preflight(plan, adapter)?;

No map_err, no match. And unlike the Io variant, this one keeps a prefix — "preflight failed: {0}" — because knowing that a transaction died during preflight rather than mid-swap is information the reader wants. Compare with #[error(transparent)] on the line below: same mechanism, opposite decision, and both are right.

Three variants carry a String rather than a structured cause: Identity, TempVerify, FinalValidation. These are the “we checked and it did not match” failures, where the interesting detail is a human explanation like “source and target resource forks differ”, and no caller is going to branch on which mismatch. It is a pragmatic middle ground: typed enough to distinguish the stage, loose enough not to invent a taxonomy nobody will match on.

Db(String) is the same pragmatism from the other direction. The database returns an anyhow::Error, which cannot be a source for a thiserror variant, so it is flattened to its message. That is a real seam between the two crates, and this is how it is paid for.

Above the line: context, not types

Now the other half. At the engine's edges, failures are for reading, and anyhow's job is to make sure that by the time one reaches a human it says which thing failed:

src/lib.rsinside run_scan, verbatim

        let canonical = root
            .canonicalize()
            .with_context(|| format!("cannot access scan root {}", root.display()))?;

Without that line the user sees “No such file or directory (os error 2)” and has no idea which of the four paths they typed was wrong. With it they see the context and the cause, chained. And with_context takes a closure, so the format! only runs on the error path — free when things go well.

The same trick works on Option, and this is my favourite instance of it in the codebase:

src/lib.rsinside list_groups, verbatim

    let scan_id = match scan_id {
        Some(id) => id,
        None => db
            .latest_scan_id()?
            .context("no completed scans in the index; run `filecleaner scan` first")?,
    };

Remember chapter 5, where latest_scan_id carefully converted “no rows” into Ok(None)? This is the payoff. The None becomes an error whose message tells the user exactly what to do next. A tool that says “here is what to type” instead of “none” is a tool people can use without reading the manual.

And because main itself returns anyhow::Result<()>, no error handling is needed at the top at all — a ? anywhere in main prints the message, prints its chain of causes, and exits non-zero:

Two type aliases that keep signatures honest

One last touch. The engine returns per-target outcomes, and the raw types are a mouthful, so lib.rs names them:

src/lib.rsverbatim

/// Per-target outcome of a dry run: the plan plus its preflight verdict.
pub type DryRunResult = (TxnPlan, Result<(), PreflightError>);
/// Per-target outcome of an executed reclaim.
pub type ReclaimResult = (TxnPlan, Result<TxnReport, TxnError>);

Notice the shape: a Vec of these, not a Result<Vec<…>>. Reclaiming a group of five files is five independent operations, and the third one failing must not discard the results of the first two. So the outcome is “here is what happened to each target,” and every entry carries both the plan (so the caller can name the file) and its verdict.

The Vec<Result> versus Result<Vec> choice is one of those small decisions that determines whether a tool feels solid. Here it is what allows the CLI to end a run with “Reclaimed (estimate): 1.2 GiB; 1 target(s) failed and were rolled back” instead of a single sentence about the first thing that went wrong.

So what did we actually gain?

A rule you can apply tomorrow, in your own code. Ask of every failure: does someone branch on this? If a caller counts it, retries it, rolls back because of it, or prints a specific sentence for it — give it a variant. If it is going to be shown to a human and nothing else — give it context and move on.

In this program the answer split cleanly at the library boundary, and the payoff is concrete: the funnel can count stale files separately from unreadable ones, the CLI can tell you exactly why each target was skipped, and the executor can decide how far to roll back — all without a single if err.to_string().contains(…) anywhere in the codebase.

Challenges
  1. TxnError::Db(String) flattens an anyhow::Error into text, losing its chain. Change db.rs to return a typed error and follow the change outward — is the result better, or just longer?
  2. PreflightError::Io is transparent while TxnError::Preflight has a prefix. Write out the exact message a user sees when an I/O error happens during preflight inside a transaction, following both attributes.
  3. Find a failure in this codebase that is currently a String and that you think a caller should branch on. Propose the variant, and name the caller.
