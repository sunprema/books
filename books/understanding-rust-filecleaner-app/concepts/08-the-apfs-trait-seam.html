Chapter 08 · Part III — Rust Craft in the Middle

A Seam for Failure: the ApfsAdapter Trait

Here is a test I would like to write. “Start replacing a file; when the clone is half-created, fill up the disk; assert that the user's original file is exactly as it was, that no debris is left behind, and that the journal says rolled back.” Now: how do you fill up a disk on demand, in a unit test, reliably, on someone else's laptop? You don't. You arrange for the program to be told the disk is full — and the arrangement is one trait.

The comment that defines the architecture

src/apfs/mod.rs opens with a module doc comment. It is four lines and it is the load-bearing sentence of this codebase:

src/apfs/mod.rsthe module doc comment, verbatim

//! All Darwin-specific and `unsafe` code lives in this module. Everything
//! above it (scanner, index, policy, transactions) stays platform-neutral
//! and depends on the [`ApfsAdapter`] trait, so tests can inject failures
//! at any step without touching a real filesystem.

Read the causal chain in it: because the platform code is confined, the layers above can depend on an interface instead of on macOS — and therefore the tests can substitute a different implementation. Testability is not a bonus here; it is the reason the boundary exists.

A trait, in Rust, is a set of method signatures a type can promise to provide. If you come from an object-oriented language, it will look like an interface, and for this purpose it behaves like one. The differences that matter here are two: a trait can be implemented for a type you did not write, and calls through a trait can be resolved either at compile time (static dispatch, zero cost) or at run time (dynamic dispatch, one pointer indirection). This code uses the latter, and we will see why.

Seven methods, chosen carefully

src/apfs/mod.rsverbatim

/// The platform operations a reclamation transaction needs.
pub trait ApfsAdapter: Send + Sync {
    /// APFS copy-on-write clone. `destination` must not exist.
    fn clone_file(&self, source: &Path, destination: &Path) -> io::Result<()>;

    /// Device id of the filesystem holding `path`.
    fn device_of(&self, path: &Path) -> io::Result<u64>;

    /// Whether `path` lives on an APFS filesystem.
    fn is_apfs(&self, path: &Path) -> io::Result<bool>;

    /// Capture a target's restorable metadata.
    fn snapshot_metadata(&self, path: &Path) -> io::Result<MetadataSnapshot>;

    /// Reapply a snapshot to a fresh clone.
    fn restore_metadata(&self, path: &Path, snap: &MetadataSnapshot)
    -> io::Result<RestoreOutcome>;

    /// Full resource-fork contents; empty when absent.
    fn read_resource_fork(&self, path: &Path) -> io::Result<Vec<u8>>;

    /// BSD flags (`st_flags`) of `path`; 0 on platforms without them.
    /// Preflight uses this to reject immutable targets.
    fn bsd_flags(&self, path: &Path) -> io::Result<u32>;
}

The doc comment is doing precise work: the platform operations a reclamation transaction needs. Not “filesystem operations.” Not an abstraction over files in general. Seven methods, each one a thing the transaction engine actually calls.

That narrowness is the whole trick. A general FileSystem trait with thirty methods would need a thirty-method test double, and nobody writes those — so in practice such projects test the happy path against the real disk and hope. Because this trait is seven methods, a complete, hostile, scriptable implementation fits in about eighty lines. Testability is a function of surface area.

Notice what is not in the trait, either. The executor opens files, compares bytes, and calls fs::rename directly through std. Those operations are portable, so they do not need a seam — and leaving them out means the fault-injection tests exercise real renames on a real filesystem, with only the platform-specific parts scripted. The double is a scalpel, not a simulator.

: Send + Sync

The supertrait bound says any implementation must be safe to send between threads and to share between them. Nothing in the current engine reclaims in parallel — but declaring the bound now costs nothing, and it constrains implementations (including test doubles) to be thread-safe from the start. It is also the reason the fault-injection adapter cannot reach for a plain Cell like the walker did.

Everything takes &self

Every method borrows immutably, even the ones that mutate the filesystem. That is honest: the adapter holds no state, so cloning a file changes nothing about the adapter. The consequence lands in the test double, which needs to count calls and therefore has to find mutability elsewhere — we will get there in a minute.

The real implementation is a unit struct

src/apfs/mod.rsabridged &mdash; five delegating bodies elided

/// The real implementation used in production.
pub struct RealApfs;

impl ApfsAdapter for RealApfs {
    fn clone_file(&self, source: &Path, destination: &Path) -> io::Result<()> {
        clone::clone_file(source, destination)
    }

    // …device_of, is_apfs, snapshot_metadata, restore_metadata and
    //   read_resource_fork delegate to their modules the same way…

    #[cfg(target_os = "macos")]
    fn bsd_flags(&self, path: &Path) -> io::Result<u32> {
        use std::os::macos::fs::MetadataExt;
        Ok(std::fs::symlink_metadata(path)?.st_flags())
    }

    #[cfg(not(target_os = "macos"))]
    fn bsd_flags(&self, _path: &Path) -> io::Result<u32> {
        Ok(0)
    }
}

pub struct RealApfs; — no fields, no body, no semicolon-less braces. A unit struct occupies zero bytes; it exists purely to have a type that can implement the trait. Constructing one, as lib.rs does with let adapter = RealApfs;, compiles to nothing at all.

Six of the seven methods are one-line delegations to the free functions in clone.rs, volume.rs, metadata.rs and forks.rs. The seventh, bsd_flags, is the one place a cfg split lives inside the impl rather than in a module: on macOS it reads st_flags through the std::os::macos extension trait, and elsewhere it returns Ok(0). Zero means “no flags set,” so preflight's immutability check on a non-Mac simply never fires — a safe default.

How the engine holds it: &dyn ApfsAdapter

Both the planner and the executor take the adapter the same way:

pub fn preflight(plan: &TxnPlan, adapter: &dyn ApfsAdapter) -> Result<(), PreflightError>

pub fn execute(
    db: &mut Db,
    adapter: &dyn ApfsAdapter,
    plan: &TxnPlan,
) -> Result<TxnReport, TxnError>

&dyn ApfsAdapter is a trait object: a fat pointer carrying the data pointer and a pointer to the method table. The alternative would be a generic, fn execute<A: ApfsAdapter>(…, adapter: &A, …), which compiles a separate copy of the function per adapter type — faster calls, more code.

Dynamic dispatch is the right call here for a reason that has nothing to do with performance: it means there is exactly one compiled execute in the binary, and the fault-injection tests exercise the very same machine code that runs against your files. With a generic, the test would exercise execute::<FaultyAdapter> — a different instantiation of the same source. In practice monomorphised copies behave identically, but for the single most safety-critical function in the program, “the tests run the same code” is a property worth one pointer indirection. The call happens a handful of times per file replacement, next to operations measured in milliseconds; the cost is not measurable.

The adapter that fails on cue

Now the payoff. tests/fault_injection.rs defines an adapter that wraps the real one and misbehaves at exactly one chosen point. The catalogue of misbehaviour is an enum, and its doc comments tell you what each fault is for:

tests/fault_injection.rsverbatim

#[derive(Clone, Copy, PartialEq)]
enum Fault {
    /// `snapshot_metadata` fails with EIO before anything is mutated.
    Snapshot,
    /// `clonefile` fails with ENOSPC — the disk-full case.
    CloneEnospc,
    /// `restore_metadata` fails with EPERM — the permission case.
    RestorePerm,
    /// Reading the temp clone's resource fork (3rd fork read) fails.
    TempForkRead,
    /// Not a failure: rewrite the target (same size, different bytes)
    /// during `snapshot_metadata` — before the in-txn byte compare.
    MutateEarly,
    /// Rewrite the target during `restore_metadata` — *after* the byte
    /// compare, in the verify-to-swap window.
    MutateLate,
}

Four of these are failures at four different points in the transaction. The other two are not failures at all — they are a user, editing the file you are in the middle of replacing, at two different instants. We will come back to those.

The adapter itself holds the real implementation, the fault to inject, the target's path, and a counter:

tests/fault_injection.rsverbatim

struct FaultyAdapter {
    real: RealApfs,
    fault: Fault,
    target: PathBuf,
    fork_calls: AtomicU32,
}

And each method is a one-line decision: is this my fault? Then fail. Otherwise, do the real thing.

tests/fault_injection.rsverbatim

    fn clone_file(&self, source: &Path, destination: &Path) -> io::Result<()> {
        if self.fault == Fault::CloneEnospc {
            return Err(io::Error::from_raw_os_error(libc::ENOSPC));
        }
        self.real.clone_file(source, destination)
    }

io::Error::from_raw_os_error(libc::ENOSPC) constructs the exact error a genuinely full disk produces — the same errno, the same ErrorKind, the same message. The executor cannot tell the difference, which is precisely the point. No disk was filled; no VM was spun up; the test runs in milliseconds.

Counting calls when all you have is &self

One fault needs to fire on the third call to a method — and the method signature gives out only a shared reference. Chapter 4 hit this exact wall in the walker and reached for a Cell. Here the Send + Sync bound rules that out, so the answer is its thread-safe cousin:

tests/fault_injection.rsverbatim

    fn read_resource_fork(&self, path: &Path) -> io::Result<Vec<u8>> {
        // Executor call order: source (1), target (2), temp (3).
        let call = self.fork_calls.fetch_add(1, Ordering::SeqCst) + 1;
        if self.fault == Fault::TempForkRead && call == 3 {
            return Err(io::Error::from_raw_os_error(libc::EIO));
        }
        self.real.read_resource_fork(path)
    }

AtomicU32::fetch_add increments and returns the previous value, atomically, through a shared reference. The comment above it is the test's real documentation: it encodes knowledge of the executor's call order, so that call == 3 unambiguously means “while verifying the temp clone.” That is a slightly brittle coupling — reorder the executor's fork reads and this test targets a different step — and it is a fair price for reaching a failure point that has no other name.

Ordering::SeqCst is the strongest memory ordering and the right default when you are not doing lock-free algorithm design: correct first, and here there is no contention to optimise away.

One assertion, six faults

Every fault case ends by calling the same function. This is the safety property of the entire program, written down once:

tests/fault_injection.rsverbatim

/// Every failed transaction must leave: the expected target content at the
/// target path (same inode — never swapped), no artifacts, a terminal
/// `rolled-back` journal row, and an untouched source.
fn assert_fully_rolled_back(rig: &Rig, expected_content: &[u8]) {
    assert_eq!(fs::read(&rig.plan.target).unwrap(), expected_content);
    assert_eq!(
        fs::metadata(&rig.plan.target).unwrap().ino(),
        rig.target_ino,
        "target inode must be the original — the swap must not have happened"
    );
    assert!(!rig.plan.temp.exists(), "temp not cleaned up");
    assert!(!rig.plan.backup.exists(), "backup not cleaned up");
    assert_eq!(fs::read(&rig.plan.source).unwrap(), rig.original);

    let entry = rig.db.journal_entry(1).unwrap();
    assert_eq!(entry.state, TxnState::RolledBack);
    assert!(entry.error.is_some(), "rollback must record its cause");
    assert!(rig.db.journal_incomplete().unwrap().is_empty());
}

Seven assertions, and each one closes a different way a “safe” tool could still ruin your day:

AssertionThe disaster it rules out
content equals expectedYour file's bytes changed.
inode is the originalThe bytes match but the file was silently replaced — which would break hard links, file descriptors, and sync services.
no temp fileHidden debris accumulating in your folders.
no backup fileSame, plus confusion for a later recovery pass.
source unchangedThe promise that the source is only ever read.
journal is rolled-backA crash-recovery pass later “finishing” a transaction that already failed.
error recorded, nothing incompleteA silent failure — and a row that recovery would keep trying to repair forever.

The inode check is the one I would single out. A less careful test would compare contents and stop — but the whole hazard of this program is that it swaps one file for another with identical bytes. Only the inode number can tell you whether the swap happened.

The two faults that are really a user

Back to MutateEarly and MutateLate. Neither returns an error; each rewrites the target file with different bytes of the same length, and then lets the real operation proceed:

tests/fault_injection.rsverbatim

    fn mutate_target(&self) {
        let len = fs::metadata(&self.target).unwrap().len() as usize;
        fs::write(&self.target, vec![0xEEu8; len]).unwrap(); // same size, new bytes
    }

This is you, saving a file, while the tool is mid-transaction. The two variants place that save on either side of the executor's byte comparison — and the assertions demand that each window has its own defence:

tests/fault_injection.rsverbatim

#[test]
fn target_mutated_before_byte_compare_is_caught_by_it() {
    let (rig, err) = run_fault(Fault::MutateEarly);
    assert!(
        matches!(&err, TxnError::Identity(msg) if msg.contains("data forks differ")),
        "got: {err}"
    );
    // The user's mutation survives; nothing was replaced.
    let mutated = vec![0xEEu8; rig.original.len()];
    assert_fully_rolled_back(&rig, &mutated);
}

#[test]
fn target_mutated_after_byte_compare_is_caught_before_swap() {
    let (rig, err) = run_fault(Fault::MutateLate);
    assert!(
        matches!(&err, TxnError::Identity(msg) if msg.contains("changed during the transaction")),
        "got: {err}"
    );
    let mutated = vec![0xEEu8; rig.original.len()];
    assert_fully_rolled_back(&rig, &mutated);
}
Key idea Look at what is passed to the assertion: &mutated, not &rig.original. The test does not demand that the tool undo the user's edit — it demands that the user's edit is what survives. Two different mechanisms catch the two windows (the byte comparison catches the first, a post-rename stat check catches the second), and both tests end at the same place: your bytes, your inode, nothing touched. Chapter 10 shows both mechanisms in the executor.

Also worth noticing: matches!(&err, TxnError::Identity(msg) if msg.contains(…)). The test asserts on the error's variant and then on a substring of its detail — exactly the granularity chapter 7's design provides. The variant is the contract; the message is a hint.

One more test in the same file skips the adapter entirely and uses the real filesystem, because the failure it wants is one std::fs can produce directly: it sets a directory to mode 0o555, runs preflight, restores the mode for cleanup, and asserts PreflightError::DirNotWritable. Use the seam where you need it; use the real thing where you can.

A second double, with a different job

The planner's own unit tests need something else again: a real filesystem for the stat checks, but scripted answers for the questions about volumes. So they define a second, smaller double — and its unimplemented methods are the interesting part:

src/txn/planner.rsabridged &mdash; the scripted methods are elided

    /// Adapter whose volume answers are scripted; everything else is real.
    struct FakeVolumes {
        source_dev: u64,
        target_dev: u64,
        apfs: bool,
        flags: u32,
    }

    impl ApfsAdapter for FakeVolumes {
        fn clone_file(&self, _s: &Path, _d: &Path) -> io::Result<()> {
            unreachable!("preflight never clones")
        }
        // …device_of, is_apfs and bsd_flags return the scripted fields…
        fn snapshot_metadata(&self, _path: &Path) -> io::Result<MetadataSnapshot> {
            unreachable!("preflight never snapshots")
        }
        fn read_resource_fork(&self, _path: &Path) -> io::Result<Vec<u8>> {
            unreachable!("preflight never reads forks")
        }
    }

Those unreachable! messages are executable documentation. “Preflight never clones” is a claim about the design — the dry run must be read-only — and it is enforced here: if anyone ever adds a clone to the preflight path, these tests panic with a sentence explaining what rule was broken. A comment would have gone stale; this cannot.

Two doubles, two shapes, one trait. That is what a well-sized seam buys you: each test writes only the fiction it needs, and everything else stays real.

So what did we actually gain?

The ability to ask “what if?” about the moments that matter and get an answer in milliseconds. What if the disk fills mid-clone? What if we lack permission to restore ownership? What if the user saves the file after we verified it but before we swap it? Each of those is one line in an enum and one test, and each ends at the same assertion: your file, your inode, no debris, a journal row that says what happened.

The design lesson generalises past macOS. Put the code you cannot control behind an interface sized to what you actually call — not to the platform — and the failures you could never reproduce become the failures you test on every commit.

Challenges
  1. Add a fault that makes bsd_flags report UF_IMMUTABLE. Which test file should it live in — and does the transaction even get far enough to need it?
  2. TempForkRead fires on the third call because of a comment about call order. Design a way to name the step directly rather than counting, and weigh it against the simplicity of a counter.
  3. fs::rename is not behind the trait. Write the test you would most want if it were — then decide whether it justifies widening the seam.
