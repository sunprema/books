Chapter 04 · Part II — Finding the Duplicates

Walking the Disk

The scan is where the program meets the real world, and the real world is hostile in dull ways. Directories you cannot read. Symlinks that loop. Bundles that look like folders but behave like documents. Files that vanish between the moment you list them and the moment you stat them. The walker's job is not to be clever — it is to be unsurprisable, and to come back with a tidy list and an honest census of everything it refused.

The shape of the answer

The whole module returns one struct, and the pairing tells you the design:

src/scanner/walker.rsverbatim

pub struct WalkOutcome {
    pub files: Vec<FileEntry>,
    pub stats: ScanStats,
}

What we kept, and what we didn't — in the same value. A walker that returned only files would leave the user unable to answer “why did it only find 38 things in a folder with 200?” The counters are not diagnostics bolted on; they are half the result.

Errors are counted, never propagated

Notice what the signature is not. It is not Result<WalkOutcome>. A permission-denied directory in the middle of ~/Documents must not abort a scan of forty thousand files — it should increment stats.errors and be skipped. This is a genuine judgement call, and it is the right one for a tool that runs over other people's home directories: partial results with an accurate count of what was missed beat an error message and nothing.

Setting up the traversal

Here is the top of walk_roots, and it packs three decisions into ten lines:

src/scanner/walker.rsverbatim

/// Enumerate eligible regular files under `roots`.
///
/// Symlinks are never followed. Package directories are skipped unless
/// `include_packages` is set — except when a root itself is a package, which
/// counts as the user explicitly choosing to traverse it.
pub fn walk_roots(roots: &[PathBuf], include_packages: bool) -> WalkOutcome {
    let mut files = Vec::new();
    let mut stats = ScanStats::default();
    let mut seen_paths = std::collections::HashSet::new();

    for root in roots {
        let packages_skipped = Cell::new(0u64);
        let walk = WalkDir::new(root)
            .follow_links(false)
            .into_iter()
            .filter_entry(|entry| {
                if !include_packages
                    && entry.depth() > 0
                    && entry.file_type().is_dir()
                    && filter::is_package_dir(entry.path())
                {
                    packages_skipped.set(packages_skipped.get() + 1);
                    return false;
                }
                true
            });

follow_links(false)

The same rule as CLONE_NOFOLLOW in the last chapter. A tool that replaces files must never be redirected by a link into somewhere the user did not name. It also happens to make infinite loops impossible: a symlink pointing at its own ancestor is just an entry to count and skip.

filter_entry prunes; a filter would not

This is the most consequential line in the function. walkdir's filter_entry is not Iterator::filter. When the closure returns false for a directory, walkdir does not descend into it at all — the entire subtree is pruned. Filtering afterwards would visit every file inside a .photoslibrary containing forty thousand images and then throw them away.

Why prune packages at all? Because on macOS a .app or .photoslibrary is a directory that the system and its applications treat as a single document. filter.rs says it plainly:

src/scanner/filter.rsverbatim

/// Directory extensions that macOS treats as packages (documents that are
/// really directories). Skipped by default: replacing files inside a package
/// can corrupt it as a unit, so traversal must be an explicit user choice.
const PACKAGE_EXTENSIONS: &[&str] = &[
    "app",
    "appex",
    "band",
    "bundle",
    "docset",
    "fcpbundle",
    "framework",
    "imovielibrary",
    "kext",
    "lproj",
    "mpkg",
    "photoslibrary",
    "pkg",
    "playground",
    "plugin",
    "prefpane",
    "qlgenerator",
    "scptd",
    "tvlibrary",
    "xcodeproj",
    "xcworkspace",
    "xpc",
];

And the test for one is an extension lookup, lowercased so Upper.APP is caught too:

src/scanner/filter.rsverbatim

/// True if `path` looks like a macOS package root, judged by extension.
pub fn is_package_dir(path: &Path) -> bool {
    path.extension()
        .and_then(|e| e.to_str())
        .is_some_and(|ext| {
            let ext = ext.to_ascii_lowercase();
            PACKAGE_EXTENSIONS.contains(&ext.as_str())
        })
}

That chain is idiomatic Rust worth reading slowly. path.extension() gives Option<&OsStr> — a path may have no extension. .and_then(|e| e.to_str()) keeps it an Option while attempting UTF-8 conversion, which can also fail. Then .is_some_and(…) collapses the whole thing to a bool: “there is a value, and it satisfies this predicate.” No unwrap, no nesting, and every failure mode answers “not a package.”

entry.depth() > 0: consent, encoded

Key idea The package rule is suspended at depth zero. If you type filecleaner scan ~/Pictures/Photos Library.photoslibrary, you have named the package yourself — that is the explicit choice the doc comment asks for, so the walk proceeds. One comparison against zero turns a blanket refusal into a policy about consent, and there is a test for each half of it.

Why the counter is a Cell

Here is a puzzle the compiler sets you. filter_entry requires a closure that implements Fn — callable through a shared reference, potentially many times — not FnMut. So the obvious let mut packages_skipped = 0u64; followed by packages_skipped += 1 inside the closure will not compile: incrementing requires mutable access to a captured variable, and an Fn closure does not get it.

The answer is Cell<u64>, which offers interior mutability: you may replace the value through a shared reference, because Cell guarantees nobody can be holding a reference to the inside. So packages_skipped.set(packages_skipped.get() + 1) mutates through a &, the closure stays an Fn, and after the walk the count is folded back into the stats:

src/scanner/walker.rsthe end of the per-root loop, verbatim

        stats.packages_skipped += packages_skipped.get();

Cell is not a lock and costs nothing at runtime; it is single-threaded interior mutability, which is exactly what a walk on one thread needs. Its multi-threaded cousins — Mutex, AtomicU32 — show up later in the book, in chapter 8, for exactly this same “I only have a shared reference and I need to count” problem.

The classification ladder

Inside the loop, every entry runs a gauntlet. Each rung either counts the entry as excluded and continues, or lets it through. Read it top to bottom and you have read the eligibility policy:

src/scanner/walker.rsverbatim &mdash; rungs 1&ndash;4

        for result in walk {
            let entry = match result {
                Ok(entry) => entry,
                Err(_) => {
                    stats.errors += 1;
                    continue;
                }
            };

            let file_type = entry.file_type();
            if file_type.is_dir() {
                stats.directories += 1;
                continue;
            }
            if file_type.is_symlink() {
                stats.symlinks += 1;
                continue;
            }
            if !file_type.is_file() {
                stats.special += 1;
                continue;
            }

src/scanner/walker.rsverbatim &mdash; rungs 5&ndash;7, continuing the same loop

            let name = entry.file_name().to_string_lossy();
            if filter::is_own_artifact(&name) {
                stats.own_artifacts += 1;
                continue;
            }

            let meta = match entry.metadata() {
                Ok(meta) => meta,
                Err(_) => {
                    stats.errors += 1;
                    continue;
                }
            };

            if meta.len() == 0 {
                stats.zero_byte += 1;
                continue;
            }

The self-reference trap The .filecleaner.* rung deserves a moment. During a reclaim, the tool creates a hidden clone next to the target — a file whose content is, by construction, byte-identical to another file it is about to index. Without this rung, a scan that overlapped a reclaim (or ran after an interrupted one) would happily nominate the tool's own scratch files as duplicates, and the transaction engine would start operating on its own machinery. Two lines in filter.rs close that off:

src/scanner/filter.rsverbatim

/// Prefix for temp/backup files created by our own reclamation transactions.
/// They must never be scanned as duplicate candidates.
pub const OWN_ARTIFACT_PREFIX: &str = ".filecleaner.";

/// True if `file_name` is a temp/backup file created by this tool.
pub fn is_own_artifact(file_name: &str) -> bool {
    file_name.starts_with(OWN_ARTIFACT_PREFIX)
}

The constant is pub so the planner can build names from the same string it is filtered by — one source of truth for what “our files” look like.

Recording a survivor

What is left is a real, non-empty, non-linked regular file we can read. Three more things happen before it becomes a FileEntry:

src/scanner/walker.rsverbatim

            // Overlapping roots may reach the same path twice.
            if !seen_paths.insert(entry.path().to_path_buf()) {
                continue;
            }

            if meta.nlink() > 1 {
                stats.hardlinked += 1;
            }

            stats.eligible += 1;
            stats.eligible_bytes += meta.len();
            let rsrc_len = forks::resource_fork_len(entry.path());
            files.push(FileEntry {
                path: entry.into_path(),
                dev: meta.dev(),
                ino: meta.ino(),
                nlink: meta.nlink(),
                size: meta.len(),
                mtime_sec: meta.mtime(),
                mtime_nsec: meta.mtime_nsec(),
                rsrc_len,
            });

Deduplicating overlapping roots

HashSet::insert returns true if the value was new. So if !seen_paths.insert(…) reads as “if we had already seen this, skip.” It matters because filecleaner scan ~/Documents ~/Documents/Invoices is a perfectly reasonable thing to type, and without this the same file would be indexed twice and could end up appearing to be a duplicate of itself.

Hard links are recorded, not rejected — yet

A file with nlink > 1 is counted but still indexed. That is deliberate: chapter 3's eligible_targets needs to see those members in order to report them to the user as “(hardlinked ×2 — skipped)” rather than silently omitting them. Exclusion happens where the decision is made, not where the data is gathered.

Unix metadata needs an extension trait

meta.len() is portable std. meta.dev(), meta.ino(), meta.nlink() and meta.mtime_nsec() are not — they only exist because the file begins with use std::os::unix::fs::MetadataExt;. This is Rust's extension trait pattern: the platform-specific API is a trait that adds methods to a portable type, so the portable type stays portable and the extra power is something you opt into by name. Delete that use and the file stops compiling with “no method named ino” — which is exactly the reminder you want that you have left portable ground.

entry.into_path(): a move, not a copy

Every other field is read through &meta, but the path is taken with entry.into_path(), which consumes the DirEntry and hands over the PathBuf it owned. No allocation, no copy of the bytes — the buffer simply changes owner. This is why into_path() is the last thing the loop does with entry: after a move, the original is gone, and the compiler enforces that you do not reach for it again.

Small, but the habit is the point. In a walk over a hundred thousand files, “take ownership instead of cloning” is a hundred thousand avoided allocations, and it costs one word of API knowledge.

One xattr call per file

forks::resource_fork_len is the walker's only trip into the apfs module, and it is a cheap one — a getxattr asking for a size, not for content:

src/apfs/forks.rsverbatim

/// Length of the resource fork at `path`, 0 if absent or unreadable.
/// Never follows symlinks.
#[cfg(target_os = "macos")]
pub fn resource_fork_len(path: &Path) -> u64 {
    use std::ffi::CString;
    use std::os::unix::ffi::OsStrExt;

    let Ok(c_path) = CString::new(path.as_os_str().as_bytes()) else {
        return 0;
    };
    let len = unsafe {
        libc::getxattr(
            c_path.as_ptr(),
            c"com.apple.ResourceFork".as_ptr(),
            std::ptr::null_mut(),
            0,
            0,
            libc::XATTR_NOFOLLOW,
        )
    };
    if len < 0 { 0 } else { len as u64 }
}

Three things to collect here. The let … else form binds c_path when the conversion succeeds and otherwise runs a block that must diverge — here, return 0. It is the tidiest way to say “handle the failure and get out” without an if let pyramid. The c"com.apple.ResourceFork" literal is a C string literal, NUL-terminated at compile time with no allocation at all. And passing a null buffer with length 0 is the standard xattr idiom for “don't give me the value, just tell me how big it is.”

Why record it at all? Because on macOS a file's content can live in two places: the ordinary data fork and a resource fork carried as an extended attribute (old fonts, custom icons, some legacy documents). Two files with identical data and different resource forks are not the same file, and the fork length is a nearly-free way to keep them in separate buckets from the very first stage of the funnel.

One test that pins the whole policy

The walker's unit test builds a small tree containing one of everything the ladder rejects, then asserts on every counter at once:

src/scanner/walker.rsunit test, abridged &mdash; the file-name assertions are elided

    #[test]
    fn walks_and_filters() {
        let dir = tempfile::tempdir().unwrap();
        let root = dir.path();

        write(&root.join("a.txt"), b"hello world");
        write(&root.join("sub/b.txt"), b"hello world");
        write(&root.join("empty.txt"), b"");
        write(&root.join("Fake.app/Contents/inside.txt"), b"packaged");
        write(&root.join(".filecleaner.x.tmp"), b"leftover");
        symlink(root.join("a.txt"), root.join("link.txt")).unwrap();
        fs::hard_link(root.join("a.txt"), root.join("hard.txt")).unwrap();

        let outcome = walk_roots(&[root.to_path_buf()], false);

        // …assertions that a.txt, b.txt and hard.txt are the three survivors…

        assert_eq!(outcome.stats.eligible, 3);
        assert_eq!(outcome.stats.zero_byte, 1);
        assert_eq!(outcome.stats.symlinks, 1);
        assert_eq!(outcome.stats.packages_skipped, 1);
        assert_eq!(outcome.stats.own_artifacts, 1);
        // a.txt and hard.txt share an inode; both count as hardlinked.
        assert_eq!(outcome.stats.hardlinked, 2);
    }

Seven files in, three out, and every excluded file accounted for by name in a counter. The last assertion is the subtle one: a.txt and hard.txt are one inode with two names, so both paths carry nlink == 2 and both are counted. That number is a count of paths, not of files — and the comment says so, which is the only reason the reader is not left guessing.

Two more tests take the consent rule apart from both ends: a package passed explicitly as a root is traversed and reports packages_skipped: 0, and include_packages: true traverses a nested one. A fourth confirms the overlapping-roots dedupe. Four tests, and the entire policy in this chapter is nailed down.

So what did we actually gain?

A list of candidates, and an audit trail for everything we refused. The walker reads no file contents at all — not one byte — and yet it has already thrown away symlinks, packages, empties, specials and our own leftovers. Everything that survives is a real file we can open, on a known device, with a known size and a known modification time.

That last sentence is the setup for the next two chapters. Size and mtime are what the index stores, and they are what lets the funnel decide which of these files is even worth opening. Out of 38 files in the earlier example, six.

Challenges
  1. Replace the Cell<u64> with a plain mut counter and read the compiler's error carefully. What exactly does it say about Fn versus FnMut?
  2. seen_paths holds a PathBuf per eligible file for the whole walk. Estimate the memory cost for a million-file scan, and propose a cheaper key that preserves the property being defended.
  3. The ladder counts a vanished file as stats.errors. Should “the file disappeared while we were looking at it” be its own counter? Argue it as a user-facing decision, not a code one.
