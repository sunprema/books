Chapter 10 · Part IV — Replacing a File Safely

The Journaled Transaction

This is the chapter the other eleven exist for. We have a source, a target we believe is identical, a plan, and a preflight that says “probably.” Now we have to replace a real file on a real disk, in a way that survives being wrong, being interrupted, and being raced by the user — and that leaves, in every one of those cases, either the old file or the new one. Never neither. Never something in between.

The sequence, in one breath

The executor's doc comment is the specification, and it is worth reading before any code:

src/txn/executor.rsthe doc comment on execute(), verbatim

/// Execute one reclamation transaction:
///
/// preflight → journal `prepared` → snapshot target metadata → byte-compare
/// both forks (final authority) → clone source to temp → restore target
/// metadata onto temp → verify temp → journal `backup-created` →
/// rename(target, backup) → journal `swapped` → rename(temp, target) →
/// fsync dir → final validation → remove backup → journal `committed`.
///
/// On any failure the filesystem is rolled back to the pre-transaction
/// state and the journal records `rolled-back` with the error. The source
/// is never opened for writing at any point.

Everything in this chapter is an elaboration of that picture. Note in particular that the journal state is always written before the step it names — we will come back to why that direction is the only one that works.

The outer shell: commit or undo

src/txn/executor.rsverbatim &mdash; the opening

pub fn execute(
    db: &mut Db,
    adapter: &dyn ApfsAdapter,
    plan: &TxnPlan,
) -> Result<TxnReport, TxnError> {
    planner::preflight(plan, adapter)?;

    let journal_id = db
        .journal_insert(plan)
        .map_err(|e| TxnError::Db(e.to_string()))?;

src/txn/executor.rsverbatim &mdash; the two arms that follow

    match run(db, adapter, plan, journal_id) {
        Ok(mut warnings) => {
            // Past this point the swap is validated: never roll back.
            if let Err(err) = fs::remove_file(&plan.backup) {
                warnings.push(format!(
                    "backup not removed ({}): {err}; recovery will clean it up",
                    plan.backup.display()
                ));
            }
            if let Err(err) = db.journal_set_state(journal_id, TxnState::Committed, None) {
                warnings.push(format!(
                    "journal not marked committed: {err}; recovery will complete it"
                ));
            }
            Ok(TxnReport {
                journal_id,
                bytes: plan.size,
                warnings,
            })
        }
        Err((progress, err)) => {
            let message = match rollback(plan, progress) {
                Ok(()) => err.to_string(),
                Err(rb_err) => format!("{err}; ROLLBACK INCOMPLETE: {rb_err}"),
            };
            let _ = db.journal_set_state(journal_id, TxnState::RolledBack, Some(&message));
            Err(err)
        }
    }
}

The structure is a fork with a moral. All the dangerous work is in run, whose error type is not a bare TxnError but a pair: (Progress, TxnError). The second element says what went wrong; the first says how far we got, which is the only thing that determines how to undo it.

After success, nothing is allowed to fail hard

Look at the Ok arm. Two things still have to happen — delete the backup, mark the journal committed — and neither is allowed to turn this into a failure. Both are caught and turned into warnings that say who will clean up. The comment states the rule: past this point the swap is validated: never roll back.

Key idea Once the new file is in place and has passed final validation, the user's data is correct. Undoing it because a bookkeeping step failed would take a correct outcome and destroy it. A leftover hidden backup file is untidy; recovery will remove it on the next run. Losing the reclamation because unlink returned EBUSY would be absurd. Know which of your steps are the point and which are the paperwork.

A failed rollback is shouted, not swallowed

In the Err arm, if the rollback itself fails, the journal message becomes "{err}; ROLLBACK INCOMPLETE: {rb_err}" — capitals and all. That is the one situation this program cannot fully handle on its own, and it makes sure the record says so in words a human will notice while scanning a log.

Notice too let _ = db.journal_set_state(…) on the failure path: we are already returning an error, and if even the journal write fails there is nothing further to do about it. The deliberate let _ says “ignored, on purpose” — unlike a silently dropped Result, which the compiler would warn about.

Progress: knowing how far you got

src/txn/executor.rsverbatim

/// How far the filesystem was mutated, for rollback.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
enum Progress {
    Clean,
    TempCreated,
    BackupRenamed,
    TargetSwapped,
}

Four states, one per mutation the transaction can have performed. It is private to the module — no pub — because it is an implementation detail of undoing, not part of anyone's API. And it is Copy, because it is a one-byte value that gets threaded through every error path:

    let mut progress = Progress::Clean;
    let fail = |p: Progress, e: TxnError| (p, e);
    // …
        .map_err(|e| fail(progress, e.into()))?;

That tiny fail closure is just a tidier way of writing (progress, e.into()) at twenty call sites. Because Progress is Copy, capturing it costs nothing and the closure sees whatever the variable held when the failure occurred.

This is a small but genuinely important design idea: rollback is driven by a recorded fact, not by inspecting the filesystem. An undo routine that asked “does the temp file exist? does the backup exist?” would be guessing, and would guess wrong the moment another process or an interrupted earlier run left similar debris around. The transaction knows what it did.

Step 2: the final authority

Before anything is created, the executor compares the two files — for real, byte by byte, both forks:

src/txn/executor.rsinside run(), verbatim

    // 2. Identity: the byte comparison is the final authority, run inside
    //    the transaction so nothing can change between check and swap
    //    without being caught by the rename of that exact inode.
    let identical = data_forks_identical(&plan.source, &plan.target)
        .map_err(|e| fail(progress, e.into()))?;
    if !identical {
        return Err(fail(
            progress,
            TxnError::Identity("source and target data forks differ".into()),
        ));
    }
    let source_fork = adapter
        .read_resource_fork(&plan.source)
        .map_err(|e| fail(progress, e.into()))?;
    let target_fork = adapter
        .read_resource_fork(&plan.target)
        .map_err(|e| fail(progress, e.into()))?;
    if source_fork != target_fork {
        return Err(fail(
            progress,
            TxnError::Identity("source and target resource forks differ".into()),
        ));
    }

Both forks, because on macOS a file is not only its data. Two documents with identical data and different custom icons are different documents, and the funnel's grouping key only compared fork lengths. Here the contents are compared.

The comparison itself is worth reading, because it is the kind of routine people get subtly wrong:

src/txn/executor.rsverbatim

/// Streaming byte-for-byte comparison of two data forks.
pub fn data_forks_identical(a: &Path, b: &Path) -> io::Result<bool> {
    let mut fa = fs::File::open(a)?;
    let mut fb = fs::File::open(b)?;
    if fa.metadata()?.len() != fb.metadata()?.len() {
        return Ok(false);
    }
    let mut buf_a = vec![0u8; 1024 * 1024];
    let mut buf_b = vec![0u8; 1024 * 1024];
    loop {
        let n = read_full(&mut fa, &mut buf_a)?;
        let m = read_full(&mut fb, &mut buf_b)?;
        if n != m || buf_a[..n] != buf_b[..m] {
            return Ok(false);
        }
        if n == 0 {
            return Ok(true);
        }
    }
}

/// Read until the buffer is full or EOF.
fn read_full(file: &mut fs::File, buf: &mut [u8]) -> io::Result<usize> {
    let mut filled = 0;
    while filled < buf.len() {
        let n = file.read(&mut buf[filled..])?;
        if n == 0 {
            break;
        }
        filled += n;
    }
    Ok(filled)
}

Three details do the work. Length first: cheapest possible disqualifier, and it means the loop never has to reason about one file ending early. Constant memory: two 1 MiB buffers regardless of file size. read_full: this is the subtle one. A plain read may return fewer bytes than asked for at any time, for reasons that have nothing to do with the file's contents — so comparing two raw read results could report a difference between two identical files simply because the kernel filled the buffers differently. Looping until full or EOF removes that entirely.

Its own unit test builds a 3 MiB pattern (so the loop runs several times), then a copy differing only in the last byte, and a copy one byte shorter — catching both the “difference in the final buffer” and the “length mismatch” cases.

And notice: the source is opened with fs::File::open — read-only. Grep the whole executor for the source path and you find two read opens and nothing else. That is the “never written” promise from chapter 3, kept.

Steps 3–5: build the replacement and audit it

Only now does anything get created:

src/txn/executor.rsinside run(), verbatim

    // 3. Clone to the hidden temp path in the target's directory.
    adapter
        .clone_file(&plan.source, &plan.temp)
        .map_err(|e| fail(progress, e.into()))?;
    progress = Progress::TempCreated;

    // 4. Make the clone metadata-identical to the target.
    let restore = adapter
        .restore_metadata(&plan.temp, &snapshot)
        .map_err(|e| fail(progress, e.into()))?;
    let warnings = restore.warnings;

progress is advanced immediately after the operation that made it true — so if the very next line fails, rollback knows a temp file exists. The metadata restore is chapter 11's subject; for now, note only that it returns warnings rather than failing when it cannot restore ownership or an ACL, and that those warnings ride all the way out to the user in the TxnReport.

Then the clone is put on trial. Four independent checks, and the file is not permitted to replace anything until it passes all of them:

src/txn/executor.rsinside run(), verbatim

    // 5. Verify the temp clone before it can replace anything.
    let temp_meta = fs::symlink_metadata(&plan.temp).map_err(|e| fail(progress, e.into()))?;
    if !temp_meta.is_file() || temp_meta.len() != plan.size {
        return Err(fail(
            progress,
            TxnError::TempVerify("temp clone has wrong type or size".into()),
        ));
    }
    if temp_meta.mode() & 0o7777 != snapshot.mode {
        return Err(fail(
            progress,
            TxnError::TempVerify("temp clone mode does not match target".into()),
        ));
    }
    let temp_identical =
        data_forks_identical(&plan.temp, &plan.source).map_err(|e| fail(progress, e.into()))?;
    if !temp_identical {
        return Err(fail(
            progress,
            TxnError::TempVerify("temp clone content does not match source".into()),
        ));
    }
    let temp_fork = adapter
        .read_resource_fork(&plan.temp)
        .map_err(|e| fail(progress, e.into()))?;
    if temp_fork != source_fork {
        return Err(fail(
            progress,
            TxnError::TempVerify("temp clone resource fork does not match".into()),
        ));
    }

Type and size, permission bits against the snapshot we took of the target, contents against the source, resource fork against the source. You could argue every one of these is redundant — clonefile just made this file, of course it matches. The counter-argument is the one this whole codebase runs on: the cost is one stat and one read of a file we just wrote (still warm in the page cache), and the thing being protected is a user's data. verify the thing you built before you let it replace something

mode & 0o7777 masks off the file type bits and keeps the permission bits — including setuid, setgid and sticky, which live in the fourth octal digit and which a careless & 0o777 would silently drop.

Step 6: the swap, and the race it closes

Here is the heart of the whole program:

src/txn/executor.rsinside run(), verbatim

    // 6. Swap, journaling each rename before it happens.
    db.journal_set_state(journal_id, TxnState::BackupCreated, None)
        .map_err(|e| fail(progress, TxnError::Db(e.to_string())))?;
    fs::rename(&plan.target, &plan.backup).map_err(|e| fail(progress, e.into()))?;
    progress = Progress::BackupRenamed;

    // Close the verify-to-swap race: rename preserves the inode, so the
    // renamed backup must still match what the scan recorded. A target
    // mutated at any point since preflight shows up here (mtime/size) and
    // rolls back — the user's edit wins, not the clone.
    let backup_meta = fs::symlink_metadata(&plan.backup).map_err(|e| fail(progress, e.into()))?;
    if backup_meta.ino() != plan.expected.ino
        || backup_meta.len() != plan.expected.size
        || backup_meta.mtime() != plan.expected.mtime_sec
        || backup_meta.mtime_nsec() != plan.expected.mtime_nsec
    {
        return Err(fail(
            progress,
            TxnError::Identity("target changed during the transaction".into()),
        ));
    }

    db.journal_set_state(journal_id, TxnState::Swapped, None)
        .map_err(|e| fail(progress, TxnError::Db(e.to_string())))?;
    fs::rename(&plan.temp, &plan.target).map_err(|e| fail(progress, e.into()))?;
    progress = Progress::TargetSwapped;

Journal first, then act

Both renames are preceded by a journal write, and the ordering is the entire recovery story. Suppose we crash between them. The journal says backup-created, and the recovery pass in chapter 12 knows: the target may or may not have been renamed away, but the clone was definitely not put in its place, so restore the backup if the target is missing. If the journal had been written after the rename, a crash in the gap would leave a filesystem that had moved on and a journal that had not — and recovery would have to guess.

Note also that a journal write failure is a transaction failure. It is not optional bookkeeping; a step whose intent could not be recorded must not happen.

The check I would frame and hang on a wall

Between the two renames sits a stat of the backup path, compared against what the scan recorded. Why there, of all places?

Consider the window this closes. The byte comparison happened in step 2. Steps 3, 4 and 5 — cloning a possibly-large file, restoring metadata, verifying — take real time. During all of it, the user can save the target. Nothing so far would notice: the clone was made from the source, and the verification compared it to the source.

The insight is that rename preserves the inode. After rename(target, backup), the backup path names exactly the same file object that the target path named a moment ago — including any changes made to it since. So re-statting it and comparing against plan.expected asks: is this still the file we scanned? A save during the window bumps the mtime (and usually the size), and this check catches it. And because the rename has already happened, there is no gap left between the check and the swap in which a further change could sneak in unnoticed — anything that happens now happens to the backup, which is about to be discarded or restored, not to the file we are replacing.

Key idea The user's edit always wins. Not “usually”, not “unless you were unlucky”. Two mechanisms cover two windows — the byte comparison for everything before step 2, this stat for everything after — and chapter 8's MutateEarly/MutateLate faults exist precisely to prove that each window has its own guard.

PLAN.md records this check as a hardening item added in milestone M5, with the reasoning attached: rename preserves the inode so the check is sound. It is a good example of a safety property that was not obvious in the first design and became obvious once somebody asked “what happens if the user saves right here?”

Step 7: durability and the last audit

src/txn/executor.rsinside run(), verbatim

    if let Some(dir) = plan.target.parent() {
        // Durability of the renames; best-effort.
        let _ = fsync_dir(dir);
    }

    // 7. Final validation before the backup may be deleted.
    let final_meta = fs::symlink_metadata(&plan.target).map_err(|e| fail(progress, e.into()))?;
    if !final_meta.is_file() || final_meta.len() != plan.size {
        return Err(fail(
            progress,
            TxnError::FinalValidation("replaced target has wrong type or size".into()),
        ));
    }
    let final_identical =
        data_forks_identical(&plan.target, &plan.source).map_err(|e| fail(progress, e.into()))?;
    if !final_identical {
        return Err(fail(
            progress,
            TxnError::FinalValidation("replaced target content does not match source".into()),
        ));
    }

    Ok(warnings)
}

fsync_dir is three lines — fs::File::open(dir)?.sync_all() — and it exists because renaming a file changes a directory, and directory changes are cached like any other. Without the fsync, a power cut moments after a successful reclaim could leave the directory entry not yet on stable storage. It is best-effort (let _ =) because some filesystems refuse to fsync a directory handle, and failing a validated swap over that would be the wrong trade.

Then the final validation reads the file at the target path — the new one — and compares it to the source all over again. This is the third full comparison in one transaction. If it fails, Progress::TargetSwapped tells rollback to discard the clone and rename the backup back. Only after this passes does the outer shell delete the backup, which is the moment the operation becomes irreversible.

Undo, one case per mutation

src/txn/executor.rsverbatim

/// Undo according to how far the transaction got. The target ends up back
/// in place in every case.
fn rollback(plan: &TxnPlan, progress: Progress) -> io::Result<()> {
    match progress {
        Progress::Clean => Ok(()),
        Progress::TempCreated => remove_if_exists(&plan.temp),
        Progress::BackupRenamed => {
            remove_if_exists(&plan.temp)?;
            if !plan.target.exists() && plan.backup.exists() {
                fs::rename(&plan.backup, &plan.target)?;
            }
            Ok(())
        }
        Progress::TargetSwapped => {
            // The clone sits at the target path but failed validation:
            // discard it and restore the original from backup.
            if plan.backup.exists() {
                remove_if_exists(&plan.target)?;
                fs::rename(&plan.backup, &plan.target)?;
            }
            remove_if_exists(&plan.temp)
        }
    }
}

A match with one arm per state, and the compiler guarantees the arms are exhaustive: add a fifth Progress variant and this function stops compiling until you say what undoing it means. That is a real safety property — the kind of thing that is a code-review checklist item in other languages and a compile error here.

Two touches of care. The BackupRenamed arm restores only if the target is missing and the backup is present — so a rollback that runs when the world is already in the right shape does nothing rather than clobbering. And remove_if_exists treats NotFound as success:

src/txn/executor.rsverbatim

fn remove_if_exists(path: &Path) -> io::Result<()> {
    match fs::remove_file(path) {
        Ok(()) => Ok(()),
        Err(err) if err.kind() == io::ErrorKind::NotFound => Ok(()),
        Err(err) => Err(err),
    }
}

“Make sure this file is gone” succeeds when the file was never there. That is what makes rollback — and, in chapter 12, recovery — idempotent: safe to run twice, or ten times, or after a crash that happened during a previous rollback.

What the tests demand

The happy-path integration test asserts more than “it worked” — it asserts the shape of having worked:

AssertionWhat it proves
content unchangedThe replacement is byte-identical.
assert_ne! on the target's inodeIt really was replaced — a no-op would also have passed the content check.
mode is still 0o600, mtime is still 1 400 000 000The target's metadata survived, not the source's.
source inode and bytes unchangedThe source was never written.
no .filecleaner.* leftTemp and backup both cleaned up.
journal row is committedRecovery will not touch it later.

And then there is the test that justifies the entire byte-comparison design. It writes a target with the same length as the source but different bytes, and then restores the original mtime so that every cheap check agrees:

tests/txn_integration.rsthe adversarial test, abridged &mdash; fixture setup elided

        // Adversarial mutation: same size, same restored mtime — only the
        // bytes differ. Stat-based preflight passes; the byte comparison
        // inside the transaction must catch it.
        let mut tweaked = data.clone();
        tweaked[100] ^= 0xff;
        fs::write(&target, &tweaked).unwrap();
        set_mtime(&target, 1_400_000_000);

        let (_, results) = reclaim_group(&f.db_path, group_id).unwrap();
        let (_, result) = &results[0];
        let err = result.as_ref().expect_err("mismatch must fail");
        assert!(err.to_string().contains("identity"), "got: {err}");

        assert_eq!(fs::read(&target).unwrap(), tweaked, "target untouched");
        no_artifacts_left(&f.root);

Size: identical. Modification time: identical. Inode: identical. Preflight passes every one of its ten checks. And the transaction still refuses, because it read both files. PLAN.md names this test for what it is: proof that stat checks alone would have been wrong.

So what did we actually gain?

A replacement operation with no bad outcomes. Trace any failure through the code and it lands in one of two places: the original file, untouched, with a rolled-back journal row explaining why — or the new clone, fully verified, with a committed one. There is no third branch where a file is half-written, or missing, or silently the wrong bytes.

The techniques are transferable and none of them are exotic: stage the new thing beside the old one; verify it before it can do harm; record your intent before each irreversible step; make the commit point a rename; track how far you got so undo is a lookup rather than a guess; and after the commit point, refuse to undo. Any one of those alone is worth having. Together they are what lets a program modify your files while you keep working.

What we have not handled is the case where the process simply stops — no error, no rollback, no chance to run any of this code. That is what the journal states have been for all along, and it is the last chapter.

Challenges
  1. The final validation compares the new target against the source. Why not against the snapshot of the old target instead — and what would that catch that this does not?
  2. Trace what happens if rename(temp, target) fails after swapped is journaled. Which Progress arm runs, and what does the next recovery pass see?
  3. The transaction performs three full byte comparisons of the same content. Design a version with two, say exactly which guarantee you gave up, and decide whether you would ship it.
