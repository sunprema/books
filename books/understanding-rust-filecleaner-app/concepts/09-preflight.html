Chapter 09 · Part IV — Replacing a File Safely

Preflight: Earning the Right to Touch a File

Everything so far has been reconnaissance. We know which files look identical, we know which of them we are allowed to consider, and we have a syscall that can make a clone. Now we are going to modify somebody's disk — and before the first byte moves, this chapter's job is to answer one question about each target as cheaply as possible: is it still true?

First, write down exactly what we intend to do

The unit of work is one target file, and it gets a plan:

src/txn/planner.rsverbatim

/// A fully specified reclamation: replace `target` with a clone of
/// `source`, staged at `temp`, keeping `backup` until final validation.
/// Temp and backup live in the target's directory so both renames are
/// same-directory and atomic.
#[derive(Debug, Clone)]
pub struct TxnPlan {
    pub group_id: i64,
    pub source: PathBuf,
    pub target: PathBuf,
    pub temp: PathBuf,
    pub backup: PathBuf,
    pub size: u64,
    pub expected: ExpectedTarget,
}

/// What the scan recorded about the target; preflight re-checks the live
/// file against this so a target that changed since scanning is never
/// touched.
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct ExpectedTarget {
    pub ino: u64,
    pub size: u64,
    pub mtime_sec: i64,
    pub mtime_nsec: i64,
}

Four paths, a size, and a small record of expectations. That last field is the important one, and it is worth naming what it is: a claim about the past. It says “when we scanned, this path was inode 42, 1.2 MB, last modified at this nanosecond.” Every safety check from here to the end of the book is some form of comparing the live filesystem against this struct.

Notice that the plan is a plain data structure with no methods and no behaviour. It can be built, printed, cloned, stored in the journal and handed to a test — which is exactly what happens. Separating what we are going to do from doing it is why the dry run costs almost no extra code.

Where the temp and backup files go

src/txn/planner.rsverbatim

/// Build the transaction plan for one eligible target of a group.
pub fn make_plan(group: &DuplicateGroup, target: &GroupMember) -> TxnPlan {
    let dir = target.path.parent().unwrap_or(Path::new("."));
    let token = format!("{:016x}", rand::random::<u64>());
    TxnPlan {
        group_id: group.id,
        source: group.source().path.clone(),
        target: target.path.clone(),
        temp: dir.join(format!(".filecleaner.{token}.tmp")),
        backup: dir.join(format!(".filecleaner.{token}.backup")),
        size: group.size,
        expected: ExpectedTarget {
            ino: target.ino,
            size: group.size,
            mtime_sec: target.mtime_sec,
            mtime_nsec: target.mtime_nsec,
        },
    }
}

Three decisions live in those four lines of path construction.

1. In the target's own directory — not /tmp

This is not a stylistic preference; it is forced twice over. First, clonefile fails with EXDEV across filesystems, so a clone staged in /tmp could not be made from a source on your data volume. Second — and this is the one that would bite you even if cloning were unrestricted — rename(2) is only atomic within a filesystem. A cross-device “move” is a copy followed by a delete, with a window in the middle where the file exists twice, half-written, or not at all. The entire crash-safety argument of the next three chapters rests on two renames being indivisible, so both staging paths must be siblings of the target.

2. A dotted prefix, so the mess is invisible and recognisable

The names begin with .filecleaner. — the same OWN_ARTIFACT_PREFIX constant the walker filters on in chapter 4. The leading dot hides them from Finder and from an ordinary ls; the prefix makes them unmistakably ours, so a later scan skips them and a later recovery pass recognises them. The user guide even tells users what they are and asks them not to delete them by hand, because recovery uses them.

3. One random token, shared by both names

format!("{:016x}", rand::random::<u64>()) produces sixteen hex digits — 64 bits of randomness — and both the temp and the backup path use the same one. Two consequences: two concurrent transactions in the same directory cannot collide, and a human (or a recovery pass) looking at a directory containing .filecleaner.3f9a….tmp and .filecleaner.3f9a….backup can see at a glance that they belong to the same operation.

A collision would need two transactions to draw the same 64-bit number in the same directory at the same moment. And even if it happened, the failure is safe rather than destructive: clonefile refuses an existing destination with EEXIST, and that target simply rolls back.

There is a unit test for exactly this, and its assertions are the three decisions above:

The target in that fixture is in a nested subdirectory while the source is in the parent — so a naive implementation that staged next to the source would pass a sloppier test and fail this one.

Ten questions, asked in order

Now the check itself. Read the doc comment first, because it tells you both what the function is for and — unusually — what it deliberately does not do:

src/txn/planner.rsverbatim &mdash; the first half

/// Cheap safety checks, run immediately before a transaction (and for dry
/// runs). Reads only — never mutates the filesystem. Content identity is
/// deliberately NOT checked here; the executor byte-compares both forks
/// inside the journaled transaction.
pub fn preflight(plan: &TxnPlan, adapter: &dyn ApfsAdapter) -> Result<(), PreflightError> {
    use std::os::unix::fs::MetadataExt;

    let target_meta = std::fs::symlink_metadata(&plan.target).map_err(|err| {
        if err.kind() == std::io::ErrorKind::NotFound {
            PreflightError::TargetChanged
        } else {
            PreflightError::Io(err)
        }
    })?;
    if !target_meta.is_file() {
        return Err(PreflightError::TargetNotRegular);
    }
    if target_meta.ino() != plan.expected.ino
        || target_meta.len() != plan.expected.size
        || target_meta.mtime() != plan.expected.mtime_sec
        || target_meta.mtime_nsec() != plan.expected.mtime_nsec
    {
        return Err(PreflightError::TargetChanged);
    }
    if target_meta.nlink() > 1 {
        return Err(PreflightError::TargetHardlinked);
    }

    let source_meta = std::fs::symlink_metadata(&plan.source)?;
    if !source_meta.is_file() {
        return Err(PreflightError::SourceNotRegular);
    }
    if source_meta.ino() == target_meta.ino() && source_meta.dev() == target_meta.dev() {
        return Err(PreflightError::SameInode);
    }

symlink_metadata, not metadata

The difference is one word and it is the difference between checking the file you named and checking whatever it points at. fs::metadata follows symlinks; fs::symlink_metadata does not. If the target path is a symlink, this returns the link's metadata, is_file() is false, and preflight refuses with TargetNotRegular. Use the following variant and a symlink would quietly pass every check — and we would replace the link with a regular file, destroying the link and leaving its target orphaned. Same rule as CLONE_NOFOLLOW, follow_links(false), XATTR_NOFOLLOW. The program is relentless about this.

“Not found” is not an I/O error, it is a change

That first map_err reclassifies NotFound as TargetChanged while leaving every other failure an Io. From the user's point of view a file that was deleted since the scan is a file that changed, and the message they get — “target changed since scan” — leads them to the right action (re-scan) instead of to a puzzling ENOENT.

The three-part identity check

Inode, size, and mtime to the nanosecond, all compared against the plan's expected. Each catches something the others miss: a different inode means the path now names a different file entirely (an editor that saves by write-and-rename does exactly this); a different size means it was appended to or truncated; a different mtime catches a same-size edit. Together they are cheap and they catch the overwhelming majority of real changes.

But not all of them A determined adversary — or an unlucky program — can write different bytes of the same length and then restore the original mtime, and every check above passes. The repository has a test that does precisely that. Which is why preflight is explicitly not the authority, and why the doc comment says content identity is checked elsewhere. Cheap checks first, expensive truth last.

Hard links, again — and why the check is repeated

Chapter 3's eligible_targets already excluded members with nlink > 1. So why check again? Because that filter ran against the index, which describes the world as it was at scan time. Somebody could have run ln five minutes ago. The index says what we believed; preflight asks the filesystem. That distinction — belief versus observation — is the organising idea of this entire chapter.

Then the platform half, which is where the adapter from chapter 8 finally gets used:

src/txn/planner.rsverbatim &mdash; the second half

    if adapter.device_of(&plan.source)? != adapter.device_of(&plan.target)? {
        return Err(PreflightError::DifferentVolume);
    }
    if !adapter.is_apfs(&plan.target)? {
        return Err(PreflightError::NotApfs);
    }

    let flags = adapter.bsd_flags(&plan.target)?;
    if flags & (UF_IMMUTABLE | SF_IMMUTABLE) != 0 {
        return Err(PreflightError::TargetImmutable);
    }

    std::fs::File::open(&plan.source)
        .map_err(|err| PreflightError::SourceUnreadable(err.to_string()))?;

    let dir = plan.target.parent().unwrap_or(Path::new("."));
    if !dir_writable(dir) {
        return Err(PreflightError::DirNotWritable);
    }

    Ok(())
}

Two constants and a bitmask

The immutability check reads flags & (UF_IMMUTABLE | SF_IMMUTABLE) != 0 — the classic C idiom for “is either of these bits set,” written in Rust with the same operators. The constants are declared in the file, as clone.rs declared CLONE_NOFOLLOW:

src/txn/planner.rsverbatim

const UF_IMMUTABLE: u32 = 0x0000_0002;
const SF_IMMUTABLE: u32 = 0x0002_0000;

UF_ is the user-settable “locked” flag — the checkbox in Finder's Get Info panel. SF_ is the system flag, which not even root can clear without dropping the system's security level. Either one means somebody deliberately said “do not modify this,” and the tool takes that at face value. Note also the digit separators in the literals (0x0002_0000) — free readability for a bit pattern.

The one check that is a syscall in disguise

src/txn/planner.rsverbatim

/// `access(2)` check: can this process create and rename entries in `dir`?
/// Read-only, so it is safe during dry runs.
fn dir_writable(dir: &Path) -> bool {
    use std::ffi::CString;
    use std::os::unix::ffi::OsStrExt;

    let Ok(c_dir) = CString::new(dir.as_os_str().as_bytes()) else {
        return false;
    };
    unsafe { libc::access(c_dir.as_ptr(), libc::W_OK | libc::X_OK) == 0 }
}

Why access(2) rather than the more obvious “try to create a file and see”? Because a dry run must not create anything, ever. access asks the kernel “would I be permitted?” without doing it. Both bits are needed: W_OK to create and remove entries, X_OK to traverse the directory to reach them.

This is also a textbook TOCTOU — time-of-check-to-time-of-use — pattern, and it is worth being honest about that. Permissions could change between this check and the rename. The mitigation is not to make the check airtight, which is impossible; it is that the actual operation is also checked, and its failure rolls back cleanly. Preflight exists to give the user a good report during a dry run, not to make the transaction safe. The transaction makes itself safe.

The dry run is preflight, and nothing else

Here is the entire dry-run path in the engine:

src/lib.rsverbatim

/// Plan every eligible target of a group and run read-only preflight on
/// each. Mutates nothing — this is the `--dry-run` path.
pub fn dry_run_group(
    db_path: &Path,
    group_id: i64,
) -> Result<(DuplicateGroup, Vec<DryRunResult>)> {
    let group = get_group(db_path, group_id)?;
    let adapter = RealApfs;
    let results = group
        .eligible_targets()
        .map(|target| {
            let plan = planner::make_plan(&group, target);
            let verdict = planner::preflight(&plan, &adapter);
            (plan, verdict)
        })
        .collect();
    Ok((group, results))
}

And the real path, for comparison — the same iteration, with executor::execute where the verdict was:

src/lib.rsverbatim

/// Execute the reclamation transaction for every eligible target of a
/// group. Each target is an independent journaled transaction; one failure
/// rolls back that target only and the rest proceed.
pub fn reclaim_group(
    db_path: &Path,
    group_id: i64,
) -> Result<(DuplicateGroup, Vec<ReclaimResult>)> {
    let group = get_group(db_path, group_id)?;
    let mut db = Db::open(db_path)?;
    let adapter = RealApfs;
    let mut results = Vec::new();
    for target in group.eligible_targets() {
        let plan = planner::make_plan(&group, target);
        let result = executor::execute(&mut db, &adapter, &plan);
        results.push((plan, result));
    }
    Ok((group, results))
}
Key idea The dry run is not a simulation of the real path — it is the real path's first step, stopped early. Same eligible_targets, same make_plan, same preflight, same adapter. There is no second implementation to drift out of sync, and that is the only reason a dry run's verdict is worth anything.

Two smaller things worth noticing in the pair. The dry run never opens the database for writing — it does not even bind a mutable Db — so “mutates nothing” extends to the index as well as the disk. And the reclaim loop is a plain for pushing into a Vec, deliberately: each transaction is independent, failures are per-target, and there is no ? that could abandon the remaining files.

One integration test guards the purity claim directly. It runs the dry run against a healthy group, asserts the verdict is Ok, then asserts that the target's inode is unchanged, that no .filecleaner.* artifacts exist in the directory, and that the journal contains no incomplete rows — because a dry run should not have written a journal row at all.

The refusals, tested one at a time

Every branch above has a test, and they are pleasingly literal:

src/txn/planner.rstwo of the unit tests, verbatim

    #[test]
    fn changed_target_is_rejected() {
        let (_dir, plan) = fixture();
        fs::write(&plan.target, b"identical!").unwrap(); // size changed
        assert!(matches!(
            preflight(&plan, &ok_adapter()),
            Err(PreflightError::TargetChanged)
        ));
    }

    #[test]
    fn symlink_target_is_rejected() {
        let (dir, mut plan) = fixture();
        let link = dir.path().join("link.bin");
        std::os::unix::fs::symlink(&plan.target, &link).unwrap();
        plan.target = link;
        assert!(matches!(
            preflight(&plan, &ok_adapter()),
            Err(PreflightError::TargetNotRegular)
        ));
    }

And one test earns special mention for its honesty about overlapping defences:

src/txn/planner.rsunit test, verbatim

    #[test]
    fn hardlink_of_source_is_rejected_as_same_inode() {
        let dir = tempfile::tempdir().unwrap();
        let source = dir.path().join("src.bin");
        fs::write(&source, b"identical").unwrap();
        let target = dir.path().join("target.bin");
        fs::hard_link(&source, &target).unwrap();
        let plan = plan_for(dir.path(), &source, &target);
        // nlink == 2 trips first; both rejections protect the same invariant.
        assert!(matches!(
            preflight(&plan, &ok_adapter()),
            Err(PreflightError::TargetHardlinked | PreflightError::SameInode)
        ));
    }

The test accepts either variant, and the comment explains why: two independent checks defend the same invariant, and which one fires first is an implementation detail. A test that demanded one specific variant would break the day someone reordered two if statements — without anything actually being less safe. Writing the assertion at the granularity of the guarantee, not the code path, is a small skill worth practising.

So what did we actually gain?

A cheap, honest “probably yes” — and a dry run that means something. Ten stat-and-syscall checks cost microseconds and eliminate every target that is obviously ineligible, so the user gets a report they can trust before they type --confirm, and the expensive machinery of the next chapter only ever runs on plausible work.

What we did not gain is certainty. Preflight cannot prove the two files are identical, and it cannot prove nothing will change in the next millisecond — and the code says so out loud in its doc comment rather than implying otherwise. That candour is the handoff to chapter 10, which closes both gaps in the only way they can be closed: inside the transaction, at the last possible instant.

Challenges
  1. Preflight checks the source is readable by opening it and dropping the handle immediately. Why not hold the handle open through the transaction — what would that buy, and what would it cost?
  2. The expected record has no hash. Adding one would let preflight detect same-size, same-mtime edits. Say what it would cost per target, and why the design puts that check in the executor instead.
  3. Find an eleventh check you would add. Now justify it against the criterion the existing ten meet: cheap, read-only, and actionable by the user.
