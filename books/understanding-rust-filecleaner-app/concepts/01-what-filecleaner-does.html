Chapter 01 · Part I — Orientation

A Tool That Deletes Nothing

Here is a small, familiar disaster. Somewhere on your Mac there are three copies of the same 240 MB video: one in ~/Downloads, one in a project folder, one in a directory called final-FINAL. You know they are the same. You would like the disk space back. And yet you do not delete any of them, because you cannot remember which one some script, some export, some half-finished edit is pointing at — and being wrong costs you the file.

Every deduplication tool you have ever seen resolves that tension by asking you to accept the risk: pick a survivor, delete the rest, hope. The application we are going to read for the next twelve chapters resolves it a different way. It never deletes anything. All three copies stay exactly where they are, with their own names, their own permissions, their own Finder tags, their own last-modified dates — and afterwards they occupy the space of one.

The promise, stated precisely

The project is sunprema/file_cleaner, and its README states the whole idea in two sentences:

README.md A duplicate-file space reclaimer for macOS/APFS. It finds files with byte-identical content and — instead of deleting anything — replaces each duplicate with an APFS clone of a chosen source file. Every file keeps its path, its metadata, and its independence; the data blocks are shared on disk (copy-on-write) until a file is modified.

Read that again slowly, because the whole program falls out of it. Three words are doing the work. Byte-identical means we will need a way to be certain two files are the same — not probably, certainly — without reading every byte of every file on the disk. Clone means we will need a specific macOS system call, and we will need to reach it from Rust. Independence means the replacement has to be so faithful that nothing downstream — not Finder, not a backup tool, not a shell script — can tell a swap happened.

That is the book. Chapters 2 through 6 build the machinery for the first word, chapter 2 explains the second, and chapters 9 through 12 earn the third.

Meeting the tool as a user first

Before we open a single .rs file, let's use the thing. There are four commands, and the workflow is deliberately a staircase: nothing on your disk changes until the last step, and the last step needs a flag you have to type on purpose.

README.mdthe whole workflow

filecleaner scan ~/Downloads ~/Documents   # index files, find duplicate groups
filecleaner groups                         # review groups and estimated savings
filecleaner reclaim --group 3              # dry run: show what would happen
filecleaner reclaim --group 3 --confirm    # perform the replacement

A scan prints a census of what it saw and what it decided to ignore. This is the real output shape, from the project's own user guide:

filecleaner scan ~/Downloads
$ filecleaner scan ~/Downloads
Scan #1 complete
  index:              /Users/you/.filecleaner/index.db
  eligible files:     38 (12.2 MiB)
  directories:        2
  skipped:            1 zero-byte, 0 symlinks, 0 special, 0 packages
Duplicate detection:
  fingerprinted:      6   fully hashed: 6
  duplicate groups:   3

Two lines there are worth pinning to the wall, because they are the shape of chapters 4 and 6. skipped: is the eligibility policy — the tool refuses to consider several categories of file, each for a reason we will meet. And fingerprinted: 6 fully hashed: 6 is the candidate funnel: out of 38 files, only six were interesting enough to hash at all.

Reviewing a group shows you the decision the tool would make, with the chosen source and the target that would be replaced:

filecleaner groups
$ filecleaner groups
Scan #1: 3 duplicate groups
  logical duplicates: 267.8 KiB   est. reclaimable: 267.8 KiB

Group 3  [2 files × 241.6 KiB, sha256 860ae0e3]
  logical duplicates: 241.6 KiB   est. reclaimable: 241.6 KiB
  source  /Users/you/Downloads/golang copy.pdf
  target  /Users/you/Downloads/golang.pdf
Key idea reclaim --group 3 with no other flag is a dry run. The destructive path is spelled --confirm. That is not politeness; it is encoded in the argument parser, and we will see the exact declaration in a moment.

One repository, two crates

Now open Cargo.toml. It is short, and almost every line of it is a decision we will spend a chapter on.

The first thing to notice is the [[bin]] and [lib] pair. This one package produces two artifacts: a library crate called file_cleaner and a binary called filecleaner. The binary is a thin front end; all the actual capability lives in the library, and src/main.rs has to use file_cleaner::… like any other consumer would.

That split is not decoration. It is what makes the integration tests in tests/ possible — they link the library, not the binary — and it is what lets the SwiftUI app in FileCleanerApp/ drive the same engine through the CLI's --json mode without a second implementation of anything. (The Swift app is outside this book's scope; it is worth knowing only that it exists and that it adds no logic of its own.)

The second thing is edition = "2024". Editions are Rust's way of making small, opt-in language changes without breaking old code. We will see one concrete consequence in chapter 5, where the database code uses a let chain — if let Some(x) = … && condition — which was stabilized in Rust 1.88 and is available only in this edition.

The module map

The entire public shape of the library is six lines:

src/lib.rslines 1&ndash;6, verbatim

pub mod apfs;
pub mod index;
pub mod model;
pub mod policy;
pub mod scanner;
pub mod txn;

Six modules, and they are stacked. Reading them bottom-up is reading the program's trust gradient: the further down you go, the more dangerous the code and the smaller it is.

That last point is worth stating as a rule, because it explains design decisions we will meet six chapters from now. every unsafe block in the program is inside src/apfs/ The scanner does not know it is on a Mac. The transaction engine does not call clonefile; it calls a method on a trait. That single constraint is what makes chapter 8's fault-injection tests possible, and it is the difference between “we tested the happy path” and “we tested a disk that fills up exactly between the clone and the rename.”

The engine, in eight functions

Under those module declarations, lib.rs is almost entirely a set of free functions that the CLI calls in order. Here are two of them, and they show the house style you will see everywhere: take paths, do one thing, return a report.

src/lib.rsverbatim

/// Walk `roots`, filter eligible regular files, and persist them into the
/// SQLite index at `db_path` as a new scan session.
pub fn run_scan(db_path: &Path, roots: &[PathBuf], include_packages: bool) -> Result<ScanReport> {
    let mut canonical_roots = Vec::with_capacity(roots.len());
    for root in roots {
        let canonical = root
            .canonicalize()
            .with_context(|| format!("cannot access scan root {}", root.display()))?;
        canonical_roots.push(canonical);
    }

    let mut db = Db::open(db_path)?;
    let scan_id = db.begin_scan(&canonical_roots)?;

    let outcome = walker::walk_roots(&canonical_roots, include_packages);

    db.insert_files(scan_id, &outcome.files)?;
    db.finish_scan(scan_id)?;

    Ok(ScanReport {
        scan_id,
        stats: outcome.stats,
    })
}

Nine lines of logic and one thing to note early: the roots are canonicalize()d before anything else happens. Symlinked and relative paths are resolved once, at the door, so every path recorded in the index is absolute and real. When we get to the transaction engine and start comparing a live file against what the scan recorded, that decision quietly pays for itself.

The CLI as a data structure

One reason this program is pleasant to read is that its command-line interface is not parsing code at all. With clap's derive feature, the commands are an enum and the flags are fields; the parser is generated from the types. Here is the whole surface:

src/main.rsverbatim

#[derive(Subcommand)]
enum Command {
    /// Scan directories, then find duplicate groups among the results.
    Scan {
        /// Directories to scan.
        #[arg(required = true)]
        paths: Vec<PathBuf>,

        /// Traverse macOS packages (.app bundles, libraries, etc.).
        #[arg(long)]
        include_packages: bool,
    },
    /// List scan sessions in the index.
    Scans,
    /// List duplicate groups found by the most recent scan.
    Groups {
        /// Show groups for a specific scan instead of the latest.
        #[arg(long)]
        scan: Option<i64>,
    },
    /// Replace a group's duplicate targets with APFS clones of the source.
    /// Without --confirm this is a dry run and modifies nothing.
    Reclaim {
        /// The duplicate group to reclaim (see `filecleaner groups`).
        #[arg(long)]
        group: i64,

        /// Show what would happen without touching anything (default).
        #[arg(long, conflicts_with = "confirm")]
        dry_run: bool,

        /// Actually perform the replacements.
        #[arg(long)]
        confirm: bool,
    },
}

Three details reward a second look. The doc comments are not comments to the compiler's eye alone — clap turns each one into the help text for that command or flag, so filecleaner reclaim --help prints the sentences you just read. conflicts_with = "confirm" makes --dry-run --confirm a parse error rather than a runtime coin flip. And Option<i64> for --scan is how “the user did not say” is represented: not a sentinel like -1, but the absence the type system already has a word for.

The dispatch that follows is exactly as boring as it should be, and it contains the one thing that surprised me most on a first read of this codebase:

src/main.rsinside main(), verbatim

    // Repair any transaction a previous run left interrupted, before
    // touching anything else.
    let recovered = recover(&db_path)?;
    if !json {
        for action in &recovered {
            println!("recovered: {action}");
        }
    }

Before scan, before groups, before anything: repair. Not on a flag, not on a subcommand, not “if the user reports a problem.” If a previous run was killed halfway through replacing a file, the very next invocation of any command puts things right and tells you what it did. We will build the machinery that makes that safe in chapters 10 and 12; for now, just note that the program was designed on the assumption that it will be interrupted.

Say it early This tool is not a backup tool and does not create redundancy. After reclaiming, the copies share the same physical blocks on the same volume; if those blocks are lost, every copy is lost together. The README says this in its own section, and it is the honest counterweight to the word “clone.”

So what did we actually gain?

A shape to hang the next eleven chapters on. The program is a pipeline with a conscience: walk the disk cheaply, index what you saw, narrow to real duplicates, then replace one file at a time under a transaction that can be interrupted at any instant. Every module you will read exists to serve one of those four verbs, and the one module that touches macOS directly is quarantined at the bottom so the other five can be tested on any machine.

Next chapter we go straight to the bottom of that stack — to the twenty-nine lines that make the whole idea possible.

Challenges
  1. The binary is named filecleaner and the library file_cleaner. Why can't they be spelled identically? (Hint: what characters may appear in a Rust crate path?)
  2. run_scan canonicalizes its roots but the walker records entry.into_path() as it goes. What would break if the roots were left relative and the user changed directory between scan and reclaim?
  3. --dry-run is declared but the dispatch matches on confirm alone, binding the other field as dry_run: _. Is the flag therefore useless? Argue both sides.
