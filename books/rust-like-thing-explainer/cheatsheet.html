Quick reference

The Whole Book, On One Page

Fourteen chapters, boiled down. Every table here uses a plain word first and the real Rust name in small type right after it — the same deal the chapters made with you. Keep this page open while you write.

The 30-second summary

Every value has exactly one owner. You can borrow it — look at it without taking it — but at any moment it's either many people looking or one person changing it, never both. The compiler checks all of this before your program ever runs, not while it's running. Enums make every state a value can be into a named, closed list, and match forces you to handle all of them. Failure that's expected comes back as a value (Result) you check; failure that means something is truly broken stops the program (panic!). Traits are a list of things a type can do, not a family tree. When one owner genuinely isn't enough, reach on purpose for a shared box (Rc/Arc) or a watched box (Cell/RefCell/Mutex) — never as a reflex.

Who gets to keep the toy

Rust calls this: ownership
RuleLooks like
One owner at a time.let s2 = s1; — s1 is no longer usable
Handing a String/Vec/etc. to a new name is a "move," not a copy.let s2 = s1; // s1 moved
Plain numbers, bools, chars copy instead of moving — they're small and simple, so Rust calls them "Copy" types.let y = x; // x still fine
Want a real, separate second copy on purpose? Ask for it out loud.let s2 = s1.clone();
When an owner's scope ends, its value is cleaned up automatically, in reverse order of arrival.the "Drop" trait's drop() runs for you

A type can't be both Copy and have custom Drop cleanup — a silent duplicate plus two cleanups is exactly the double-free ownership exists to rule out.

How long a borrowed thing can stick around

Rust calls this: lifetimes

A lifetime tag ('a) never makes anything live longer. It only names a relationship so the strict friend can check a look never outlives what it's looking at. Most functions never write one at all — the compiler fills it in for you using three rules, in order, before it ever asks you to write anything:

Elision ruleMeaning
1Every reference coming in gets its own separate tag.
2Exactly one reference coming in? Its tag becomes the tag of whatever comes back out.
3A method with &self/&mut self? self's tag becomes the tag of what comes back out.

fn longest<'a>(x: &'a str, y: &'a str) -> &'a str — needed only once rule 1 leaves more than one possible source and there's no self for rule 3 to prefer. 'static means "for the whole run of the program" — every string literal is &'static str. It's a narrow, strong claim, not a fix for a lifetime error.

Only one hand on the marker at a time

A guard releases its hold when it's dropped. A panic while holding a Mutex/RwLock write guard "poisons" it — later locks return an Err by default (still recoverable with into_inner()).

A box that can only hold one kind of thing at a time

Rust calls this: enums, Option, Result
ShapeDefinition
Maybe nothing, maybe a valueenum Option<T> { None, Some(T) }
Worked, or a reason it didn'tenum Result<T, E> { Ok(T), Err(E) }

A variant can carry its own data, of its own shape — no data, named fields, or unnamed fields, mixed freely in one enum. Only one variant is ever "live" at a time, so an enum's size is roughly its biggest variant plus a small hidden tag (and sometimes not even that — Option<&T> is the exact same size as &T).

A guard (Some(x) if x > 5) is invisible to the exhaustiveness check — the plain patterns still have to cover everything, guard or no guard. A library can mark an enum #[non_exhaustive] so outside code must always add a catch-all, leaving room to add variants later.

Bad news you can hold in your hand

Rust calls this: Result and the ? operator
ToolDoes
.unwrap()Ok value, or panic with the Err's debug text
.expect("msg")same, but you pick the panic message
?on Err, returns it from the whole function right there (converted via From); on Ok, unwraps and keeps going
fn main() -> Result<(), E>lets ? work directly in main
Box<dyn Error>"any error type" — quick, but callers can't match on which one

A custom error only truly needs Debug + Display. Use Result when the caller could reasonably handle it (bad input, a timeout). Use panic! when a promise the code depends on is broken — that's a bug, not bad input.

A list of things something must know how to do

Default: a bounded generic. Reach for dyn only when a collection genuinely needs to mix concrete types, or binary size matters more than the small per-call cost. A trait with a generic method, or one returning bare Self, generally can't become dyn Trait.

Passing one toy between many friends, safely

Rust calls this: Box, Rc, Arc, Weak
BoxOwnersThreadsFor
Box<T>one—put a value on the heap; fixes a recursive type's infinite size
Rc<T>manyone onlyshared ownership; clone just bumps a counter
Arc<T>manymanysame as Rc, atomic counter, costs a bit more
Weak<T>refers, doesn't ownmatches its Rc/Arcbreaks reference cycles; .upgrade() → Option<Rc<T>>

Write Rc::clone(&a), not a.clone() — it's cheap and the call site should show that. A parent → child link is usually the strong (Rc) direction; a child's link back up to its parent should usually be Weak, or neither is ever dropped.

Teaching the rulebook to watch many hands at once

Rust calls this: Send, Sync, threads, channels
MarkerMeans
Sendsafe to move this value to another thread
Syncsafe for more than one thread to hold &T at once

Rc<T> is neither — plain arithmetic counters aren't safe to touch from two threads. Cell/RefCell are Send but never Sync — no locking, so a shared &T across threads could race. thread::spawn(move || ...) needs a move closure. mpsc::channel() gives a cloneable Sender and one Receiver — sending moves the value across, so nothing is ever touched by two threads at once.

Waiting without standing still

Rust calls this: Future, async/await
PieceMeans
Calling an async fndoes nothing yet — returns a lazy Future
.awaitpolls it; on "not yet," hands control back instead of blocking the thread
Runtimestd ships none — real programs add one, usually tokio

Never call a blocking function (std::thread::sleep, a blocking read) inside async code — it silently starves every other task sharing that thread, with no compiler warning. Use the runtime's async version instead. Pinning is handled for you in ordinary .await code — you'll essentially never write it by hand.

The locked door marked "you are on your own"

Rust calls this: unsafe

unsafe unlocks exactly five things, nothing else — every other rule (types, ownership, borrowing) still applies word for word inside the block:

  1. dereference a raw pointer
  2. call an unsafe function
  3. touch a mutable static
  4. implement an unsafe trait
  5. read a union field

Making a raw pointer is safe; only dereferencing one needs unsafe. Every unsafe block should carry a // SAFETY: comment saying exactly why it's sound. Wrap it in a safe function whenever you can, so nobody calling your code needs to write unsafe themselves — that's how Vec, String, and Mutex are built.

Hearing what the rulebook is really telling you

Rust calls this: reading the borrow checker
How long, by how many hands?Reach for
Just a quick look, right nowborrow — &value
Must outlive the thing that gave it to youan owned copy — move or .clone()
Many keepers, long-term, maybe changinga shared box — Rc/Arc + the Cell family

Every borrow error names two spots: where the conflicting look began, and where it's still needed — read both before touching anything. Ask why before pressing .clone(); a copy is a real decision, not a reflex. "Newtype" (struct UserId(u32)) stops two things that share a shape from being swapped by accident. "Make illegal states unrepresentable" — build the box so the wrong combination has nowhere to live, instead of catching it after the fact.

Common red messages, decoded

E0106 — missing lifetime specifier
A returned look doesn't say which input it's a look at. Say which one, or hand back an owned value instead.
E0499 — cannot borrow as mutable more than once at a time
Two read-write looks on the same value, live at once. Let the first one finish before starting the second.
E0502 — also borrowed as immutable / as mutable
A read-write look and a read-only look on the same value, both still needed. Move the read to before the change, or the change to after the read's last use.
E0004 — non-exhaustive patterns
Your match is missing a case the compiler names for you. Add it, or a trailing _ if you truly mean "anything else."

None of this is meant to be memorized. Fighting the strict friend gets old fast; reading what it's actually pointing at doesn't — that's the whole difference, and now you have it on one page.
