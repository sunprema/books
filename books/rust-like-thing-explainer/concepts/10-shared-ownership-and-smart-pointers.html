Passing One Toy Between Many Friends, Safely

Rust calls this: Box, Rc, Arc, and Weak — "smart pointers"

Every value you've met so far had exactly one owner. That was the whole rule, all the way back to the second chapter: one owner, and when that owner is done, the value goes away. Most of the time that rule is exactly right. This chapter is about the handful of times it genuinely isn't — when a thing really does need to belong to more than one place at once — and about the small, careful boxes Rust hands you for exactly that job, and only that job.

Here's the problem

Picture a club with three friends in it, and one photo of the whole club that all three of them genuinely care about. Nobody in that club is "the" owner of the photo. It isn't fair to say the photo belongs to whichever friend happened to pick it up first — and it would be strange for that one friend to be the one who decides, alone, when the photo gets thrown away. All three care about it. All three should get a say in whether it still exists.

But "one owner, and it's gone when they're done" is exactly the rule this whole book has been teaching. If you tried to hand the same photo to all three friends the ordinary way, Rust would stop you — the moment the first friend takes it, that's the owner, and the other two are left holding nothing at all. You need a genuinely different kind of box for a genuinely different kind of situation: one thing, more than one honest owner, all at once.

First, a smaller problem: a box that keeps holding another box

Before we get to sharing, there's a simpler trick worth meeting on its own, because the other three all lean on it: a plain box called "Box." A Box does one thing — it takes a value that would normally sit right where it's made, and moves it somewhere else instead, a separate storage room Rust calls the "heap." What you're left holding is a small note with that room's address written on it. Still one owner, still dropped the moment that owner goes out of scope — a Box doesn't bend a single one of the ownership rules. All it changes is where the actual thing is kept.

Here's why that small trick matters. Say you want to build a chain — a box, holding the next box, holding the next box, and so on, however long the chain turns out to be. Rust needs to know, before your program even runs, exactly how big every value is. But "a box holding another box holding another box, forever" has no fixed size at all — it's a chain with no bottom, and Rust can't build storage for something whose size it can never pin down.

A Box fixes this because a note with an address on it is always exactly the same size, no matter what room it points to — one small room, one enormous room, doesn't matter, the note itself never grows. So instead of a box directly holding the next box, it holds a note pointing at the next box. Now Rust only ever needs to know the size of one note, and the chain can go on as long as it needs to.

rust — a chain that could never be sized, until one link becomes a note

enum Chain {
    Link(i32, Box<Chain>),   // holds a NOTE to the next link, not the link itself
    End,
}

use Chain::{Link, End};

let chain = Link(1, Box::new(Link(2, Box::new(Link(3, Box::new(End))))));

Back to the club: a box that counts its own owners

Now for the actual photo problem. Rust has a box built for exactly that situation, called "Rc" — short for "reference counted." An Rc holds one photo, but it hands out as many tickets to it as you like. Every ticket is a fully real, fully equal owner. And the box itself keeps a small, honest tally taped to the back: how many tickets are out there right now. The photo only gets thrown away once that tally reaches zero — once every single ticket-holder has let go.

Handing out a new ticket is called "cloning" the Rc — written Rc::clone(&a) rather than the ordinary a.clone(), on purpose, so it's obvious to anyone reading the code that this isn't a slow, expensive copy of the whole photo. It's just one more ticket to the very same photo, and Rust only has to bump the tally by one.

rust — three tickets, one photo, one honest tally

use std::rc::Rc;

let photo = Rc::new(String::from("club photo"));
println!("tickets out: {}", Rc::strong_count(&photo)); // 1

let jos_ticket = Rc::clone(&photo);
let maxs_ticket = Rc::clone(&photo);
println!("tickets out: {}", Rc::strong_count(&photo)); // 3

drop(jos_ticket);
println!("tickets out: {}", Rc::strong_count(&photo)); // 2 — thrown away only once this hits 0

The whole idea

Box answers "where does this thing live?" Rc answers a different question: "who's allowed to say this thing still exists?" With Rc, the honest answer becomes: everyone holding a ticket, together, and not one of them alone.

One thing an Rc ticket will not let you do: change the photo. Every ticket only ever gives you a look, never the one marker from a few chapters back — and that's on purpose, since Rust has no way to check, across every ticket everyone's holding, that only one of them is changing it at a time. If you genuinely need to both share and change something, you reach for last chapter's trapdoor from inside the ticket itself — an Rc<RefCell<T>> pairs the two ideas cleanly: Rc hands out the tickets, RefCell keeps its own sign-in sheet for whoever's currently allowed to change what's inside.

The tally that works across rooms too

There's one thing an ordinary Rc tally can't survive: more than one room working at once. A plain tally — just a number going up and down — is exactly the same whiteboard-collision problem from two chapters ago, if two rooms ever bump it at the exact same instant. So Rust simply refuses, before your program even runs, to let a plain Rc ticket cross into a second room at all.

For that job, Rust hands you Rc's sturdier twin, called "Arc" — short for "atomically reference counted." This is the pairing this book promised, back in the mutation chapter, that we'd properly meet: everything about Arc works exactly like Rc — same tickets, same tally, same "thrown away once it hits zero" — except its tally is bumped with a special kind of counting move that can never be caught halfway, even if two rooms bump it at the exact same instant. Think of an ordinary tally as pencil marks on a shared sheet, and Arc's tally as a mechanical click-counter: two hands can slam the button at once and it still ends up exactly right, every single time.

That certainty isn't free — an Arc's special counting move costs a little more than an ordinary Rc's plain one. So the working rule is simple: reach for Rc when everything sharing the photo lives in one room, and reach for Arc only once the photo genuinely needs to cross into a second room. And remember: Arc alone still only ever hands out a look, the same as Rc — pair it with last chapter's Mutex when more than one room also needs to change what's shared, not just look at it.

rust — one shared list, three rooms, one tally that can't be fooled

use std::sync::Arc;
use std::thread;

let photo = Arc::new(String::from("club photo"));
let mut rooms = Vec::new();

for name in ["jo", "max", "sam"] {
    let photo = Arc::clone(&photo);   // a new ticket, safe to carry into a new room
    rooms.push(thread::spawn(move || {
        println!("{name} is looking at {photo}");
    }));
}

for room in rooms { room.join().unwrap(); }

The one trap tickets can hide from you

Here's the honest, genuinely annoying part. A tally that only ever goes up and down sounds foolproof — but there's exactly one way to trick it, and Rust's rules don't catch this one, not even at compile time. Picture two friends who each end up holding a ticket to the other friend's thing. Jo's box has a ticket to Max's, and Max's box has a ticket right back to Jo's. Neither tally can ever reach zero — Jo is keeping Max's tally above zero, and Max is keeping Jo's tally above zero, forever, even if every other friend in the club has long since walked away.

Nothing crashes. Nothing refuses to compile. As far as Rust's ownership rules can see, every single ticket that got handed out was completely, individually valid. What you actually get is a quiet, permanent leak — two things sitting there forever, unreachable by anyone who'd actually use them, never thrown away, because each one is honestly still "owned."

A ticket that doesn't count

Rust's fix isn't a rule the compiler enforces for you — it's a second, quieter kind of ticket you get to choose, called "Weak." A Weak ticket points at the exact same thing an Rc ticket does, but it doesn't touch the real tally at all. It's kept on a separate little list, off to the side, that has no say in whether the thing gets thrown away.

Because a Weak ticket doesn't count, whatever it points at might genuinely already be gone by the time you go to use it — so you can never look through one directly. Instead, you .upgrade() it, which hands you back an honest Option: Some, with a real, full ticket in hand, if the thing is still there — or None, plainly, if it isn't. The very check-every-case habit this book already taught you, showing up right here to save you.

rust — a ticket back to the parent that never keeps it alive

use std::cell::RefCell;
use std::rc::{Rc, Weak};

struct Friend {
    name: String,
    club: RefCell<Weak<Club>>,      // a look back up — doesn't own the club
}

struct Club {
    members: RefCell<Vec<Rc<Friend>>>,  // a real ticket down to each member
}

let jo = Rc::new(Friend { name: String::from("jo"), club: RefCell::new(Weak::new()) });
let club = Rc::new(Club { members: RefCell::new(vec![Rc::clone(&jo)]) });
*jo.club.borrow_mut() = Rc::downgrade(&club);   // a ticket that doesn't count

match jo.club.borrow().upgrade() {
    Some(c) => println!("jo's club has {} member(s)", c.members.borrow().len()),
    None => println!("jo's club is gone"),
}

The pattern behind that code is worth remembering on its own, far more than the exact syntax: whichever direction is real ownership — the club owning its members, a parent owning its children — stays a real, counted Rc ticket. The direction that's just a look back — a member remembering which club it's in — becomes a Weak ticket instead. You decide which direction is which. Rust will happily let you get it wrong; it just won't warn you when you do.

Here's the part that is genuinely a trap

There's no automatic check for this the way there is for almost everything else in this book. Two real tickets pointing at each other compiles cleanly, runs cleanly, and simply never gets cleaned up. The only real defense is the habit itself: the moment two things are about to hold tickets back to each other, stop and ask which direction is genuinely "owns" — and make the other direction Weak, on purpose, every time.

Why this is worth it

Be honest about the cost first: every one of these boxes is more typing, and a little more thinking, than a plain owned value. A tally to maintain. A choice, every time, of which direction owns and which one merely looks. That's real, ongoing work, and this book won't pretend it isn't.

What you get back is a rule that stayed honest the whole time. "One owner" was never really the deepest truth this book was teaching — the deepest truth was "ownership should always be clear, on purpose, never by accident." A single owner is the plain, easy way to keep that promise. Rc, Arc, and Weak are how you keep the very same promise on the rarer day a single owner genuinely isn't the honest answer — by writing the sharing down, in the open, instead of quietly hoping nobody notices you snuck around the rule.

Box<T>
Moves a value to a separate storage room (the "heap") and hands back a small, fixed-size note pointing at it. Still exactly one owner — only where the value lives changes.
Rc<T>
A box that hands out many equal, real "tickets" (owners) to one shared value, and keeps an honest tally. Thrown away only once every ticket has let go. Look-only — pair with RefCell to also allow changes.
Arc<T>
Rc's twin for more than one room (thread) at once — the same tally, kept with a counting move that can never be caught halfway. Costs a little more; only reach for it once sharing crosses into a second room.
Reference cycle
Two boxes each holding a real ticket to the other. Neither tally ever reaches zero — a quiet, permanent leak that compiles and runs cleanly, with nothing warning you it happened.
Weak<T>
A ticket that doesn't count toward the tally. Since what it points at might already be gone, you never look through it directly — only through .upgrade(), which hands back Some ticket or plainly, honestly, None.

Because Rust makes you write shared ownership down, on purpose, in plain sight — a real ticket here, a non-counting one there — you get to share a thing between as many friends as it genuinely needs, without ever quietly losing track of who's actually still holding it.
