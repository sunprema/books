Bad News You Can Hold in Your Hand

Rust calls this: Result and the ? mark — plus panic!, for the news nobody can fix

A couple of chapters back you met the two-sided box: Ok on one side, Err on the other, and a promise that it gets a whole chapter of its own. This is that chapter. Not what the box is — you already know that — but what you actually do with a piece of bad news once it lands in your hand: carry it, pass it along, translate it, and every so often, decide there's nothing left to do but stop.

Here's the problem

In plenty of other languages, a function that goes wrong doesn't hand you anything. It rings an alarm — often called an "exception" — that goes flying straight out of the function, right past whoever called it, right past whoever called them, up and up, looking for anyone who thought to listen for it. Most of the time, nobody did. So the alarm keeps flying, past function after function that had no idea it was even possible, until it either finds someone waiting for it or reaches the very top and takes the whole program down with it.

Here's the part that should bother you: you cannot tell, just by reading a function's own name and its list of things it takes in and gives back, whether it's the kind of function that might set off one of these alarms. It looks exactly like every safe, ordinary function next to it. The failure is invisible right up until the one day it isn't.

The fix: bad news is a real thing you're handed

Rust has no alarm system like that at all. When a function might fail, it says so, right in its own signature — and instead of ringing a bell and running off, it hands you something back: the two-sided box, Result<T, E>. Either it's Ok, holding whatever you actually asked for, or it's Err, holding an honest note about what went wrong. Either way, you get something solid, in your hand, that you can look at, pass to someone else, or set down for a moment — never a shout that flew past you before you even knew it happened.

rust — a register that might genuinely jam

enum RegisterError {
    Jammed,
    OutOfPaper,
}

fn open_register() -> Result<(), RegisterError> {
    Err(RegisterError::Jammed)
}

Nothing about calling open_register() can catch you off guard, because its own signature already told you the truth: "this might not work, and here's exactly the shape the bad news will take if it doesn't." Reading that box back is nothing new — it's the same match from last chapter, with both sides written out, Ok and Err, no shape left unaccounted for.

The whole idea

An exception is bad news that goes looking for someone to catch it. A Result is bad news that stays exactly where you put it, in a box, until someone deliberately picks it up and looks. One of those you can lose track of. The other, you genuinely cannot.

Passing bad news up without opening it: the ? mark

Most of the time, a function in the middle of the chain — like the shift manager, ringing up a sale — doesn't actually want to handle a jammed register itself. It just wants to pass that bad news straight up to whoever's in charge, unopened, the moment it shows up. Written out by hand with match, that's a lot of the same three lines, over and over, every single place it happens:

rust — passing bad news up, the long way

fn ring_up_sale() -> Result<(), RegisterError> {
    match open_register() {
        Ok(()) => {}
        Err(e) => return Err(e),
    }
    println!("sale complete");
    Ok(())
}

Rust has a shortcut for exactly that pattern — "if it's bad news, hand it straight up and stop here; otherwise, keep going" — written as one small mark, ?, stuck right onto the end of the call:

rust — the same thing, with the ? mark

fn ring_up_sale() -> Result<(), RegisterError> {
    open_register()?;   // bad news leaves right here, if there is any
    println!("sale complete");
    Ok(())
}

That one character does exactly what the longer version did, no more and no less: if the box is Ok, it quietly hands you what's inside and your code keeps going, right there on the same line. If the box is Err, your whole function stops on the spot and hands that same Err straight up to whoever called it — no shouting, no flying off to parts unknown, just the note, passed one level up, still sealed.

When the note needs translating along the way

Making your own kind of note — like RegisterError — turns out to need almost nothing extra. Rust calls the whole family of "real error notes" "Error," and to join that family, a note only has to know how to do two small things: describe itself to a person, in plain words (Display), and describe itself for debugging (Debug, which you usually get for free just by asking, with #[derive(Debug)]). That's the whole requirement.

rust — the whole cost of making your own error note

use std::fmt;

#[derive(Debug)]
enum RegisterError {
    Jammed,
    OutOfPaper,
}

impl fmt::Display for RegisterError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            RegisterError::Jammed => write!(f, "the drawer is jammed"),
            RegisterError::OutOfPaper => write!(f, "out of receipt paper"),
        }
    }
}

impl std::error::Error for RegisterError {}

A note can also remember what caused it. That's a small, optional extra called source() — a pointer back to the earlier note, if there was one. It's how a store owner reading just the top-level note can still trace the whole trail back to the exact register that jammed, without anyone hand-writing a breadcrumb trail themselves.

And when different rooms hand you notes in genuinely different shapes — a register problem, a shipment problem, a lock problem — you don't have to make every function agree on one note type up front. A function can say "I might hand back any real error note," written Box<dyn Error>, and the ? mark will still translate whatever specific note arrives into that shape automatically, as it passes through. It's a fine way to get started — the trade is that whoever catches a Box<dyn Error> can read it and print it, but can no longer ask "which exact kind of trouble was this," the way they still could with your own RegisterError box.

rust — main itself is allowed to hand back a Result too

use std::error::Error;

fn main() -> Result<(), Box<dyn Error>> {
    ring_up_sale()?;
    Ok(())
}

When there's no note left to hand: panic!

A jammed register is bad news you can work around — reset it, try another till, tell the customer to hang on a second. Now picture something else entirely: the floor under the register cracks. That's not a note you politely hand up the chain and keep ringing up sales while someone reads it. You stop. Everyone stops. You don't trust anything that happens on that floor again until it's actually fixed.

That's what "panic!" is for. It's not a bigger, angrier Err — it's a completely different move. A Result is a value your code chooses to look at and react to. A panic! doesn't hand anything back at all; it stops your program's normal path right there, on the spot.

rust — a broken promise, not bad luck

fn charge_cents(cents: u32) {
    if cents == 0 {
        panic!("charge_cents called with 0 — that's a bug in the caller");
    }
    // ...
}

By default, a panic! prints what went wrong, then walks back out through every function it's currently inside of, closing things up properly as it goes — the same tidy cleanup you met a few chapters ago, just running all at once, in a hurry, on the way out. Only then does the program actually stop. (You can ask Rust to skip that walk-back entirely and just stop immediately — a setting called panic = "abort" — trading the tidy cleanup for a smaller, faster-quitting program. Most programs never need to touch that setting.)

There's a fast, blunt way to turn any ordinary Result into a panic, on purpose, and you've probably already guessed its name: .unwrap(). Call it on an Ok, and you get what's inside. Call it on an Err, and your program panics right then, using whatever the note said as the message. .expect("...") does the exact same thing, except you get to write the message — which matters more than it sounds like, the day you're staring at a panic from three floors deep and trying to work out which one actually caused it.

rust — a message you'll thank yourself for later

let cash = open_register()
    .expect("could not open the register");

The trap

.unwrap() is tempting because it makes an Err disappear with almost no typing. But every .unwrap() you leave in real, running code is a promise that this particular bad news is never actually going to happen — and a jammed register genuinely can happen. Reach for it while you're still figuring the code out, then go back and turn it into a real, handled Err before anyone depends on this code for real.

When panic really is the right call

The honest rule: reach for Result whenever the failure is something the code calling you could reasonably be expected to do something about — a jammed register, a customer's card getting declined, a file that isn't there yet. Reach for panic! when what actually broke is a promise, not an input — when some rule your code was relying on turned out to be false, and there's no sensible way for the calling code to keep going as if nothing happened, because at that point the real problem is a bug, not bad luck.

A few situations are worth calling out by name, because they look like they should be handled "properly" and mostly aren't. Quick examples and early drafts of code — reaching for .unwrap() there is fine; working out real error handling before you even know if the idea works is effort spent in the wrong place. Tests — a test is supposed to stop loudly the moment something's wrong, so a panic there is doing its job. And anytime you genuinely know something the compiler can't prove — say, you're parsing a piece of text that's hard-coded right there in your own program, and you know, by construction, that it's always valid — an Err in that one spot could only ever mean you made a mistake writing the code itself, never that the real world handed you something odd.

Why this is worth it

Be honest about the cost first: writing Result and ? and a real error type takes more typing than letting a failure just fly off and hoping someone, somewhere, catches it. The first time you write out a whole Display implementation just to say "the drawer is jammed," it can feel like a lot of ceremony for one short sentence.

What you get back is bigger than the typing. No bad news in a Rust program ever flies out of a function silently — every function that can fail says so, right in its own signature, where you can't miss it reading the code or calling it. And when something truly can't be recovered from, Rust doesn't quietly keep running on a cracked floor, hoping nobody notices — it stops, loudly, at the exact moment the promise broke, instead of limping on and failing somewhere else entirely, in a way that's much harder to trace back to the real cause.

Result<T, E>
Bad news as a real thing you're handed — Ok or Err — instead of an alarm that flies past you unannounced.
? mark
Passes an Err straight up to whoever called you, one level at a time, sealed and unopened, without writing the same match by hand at every stop.
Custom error / Error trait
Your own note type. It only needs to say how to describe itself (Display) and how to show up in debugging (Debug) to count as a real Rust error.
Box<dyn Error>
"Any real error note, I don't need to know which kind." Handy early on; trades away being able to ask which exact note arrived.
panic!
Not a bigger Err — a different move entirely. Stops the program on the spot, for a broken promise nobody can recover from, instead of handing back a value at all.
.unwrap() / .expect()
Turns an Err into a panic on purpose. Fine while you're still figuring things out; a trap if it's still there once real, unpredictable bad news can actually reach it.

Once every function that can fail has to say so out loud, and every piece of bad news is something you can actually hold, check, and pass along on purpose, you stop hoping nothing slips through — because nothing invisible was ever allowed to fly past you in the first place.
