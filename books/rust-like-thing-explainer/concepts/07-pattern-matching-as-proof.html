Checking Every Single Box Before You Move On

Rust calls this: pattern matching — and the promise that it never lets a box go unchecked is called exhaustiveness

Last chapter you met the sign frame — a box that's honestly only ever one shape at a time. That's only half the story. A sign frame nobody ever reads back is useless. This chapter is about the reading part: how you open the frame, see which sign is really there, and why Rust won't let you walk away having checked only some of the signs.

Here's the problem

Picture a checklist taped to a clipboard, one for closing up the shop each night: lock the register, turn off the lights, lock the front door. A tired employee glances at it, ticks off "lock the register" and "turn off the lights," and heads home. The front door is still unlocked. Nobody meant for that to happen — the checklist had three items, the employee only looked hard enough to remember two, and nothing on the clipboard forced a look at the third.

Code has the exact same problem, and it's worse, because the missed item doesn't sit there quietly like an unlocked door — it hides. Say you're reading back the shop sign from last chapter, and you write code that only checks for Open and Closed, and quietly forgets BackAt. The program compiles. It runs. It works, every single day, right up until the one morning the sign really does say BackAt(15) — and now your code has no idea what to do, because nobody ever told it. The missing case wasn't found by testing. It was found by a customer.

The fix: a checklist that won't let you skip a box

Remember "match," the tool from last chapter that reads a sign back out of its frame? Here's the part that only shows its full weight once you try to cheat it: a match is not a clipboard you glance at. It is a clipboard that physically will not let you set it down until every box on it has been checked. Rust calls this promise "exhaustiveness," and it's checked by the compiler — the strict friend — before your program is ever allowed to run, not by a test you have to remember to write.

rust — a checklist with one box left unchecked

enum ShopSign {
    Open,
    Closed,
    BackAt(u8),
}

fn greet(sign: ShopSign) -> &'static str {
    match sign {
        ShopSign::Open => "come on in!",
        ShopSign::Closed => "sorry, we're closed.",
        // BackAt is never mentioned
    }
}

That code does not compile. Not "compiles with a warning" — refuses, flat out, with an error that names the exact box you left unchecked: ShopSign::BackAt. Rust looked at the whole short list of signs the frame is allowed to hold, looked at your checklist, and found one sign with nobody assigned to it. It won't guess what you meant. It won't quietly do nothing and hope for the best. It stops you, right there, on your own screen, on a day nothing bad has happened yet — instead of leaving that gap for a customer to find.

The whole idea

Exhaustiveness isn't the compiler being fussy. It's the compiler turning a promise you'd otherwise have to keep by memory — "I checked every sign, I'm sure of it" — into a promise it keeps for you, every single time, whether you remembered to think about it or not.

Reaching into the box while you check it

A checklist box isn't just a check mark — sometimes the box has something written inside it you need to read. Rust's match does both jobs in one motion: it figures out which sign is really there, and it pulls out whatever that sign is carrying, handing it to you by name, right in the same line. This is called "destructuring," a fancy word for "pulling the pieces of a box apart while you're already looking at it."

rust — pulling the number out of BackAt while checking which sign it is

fn greet(sign: ShopSign) -> String {
    match sign {
        ShopSign::Open => "come on in!".to_string(),
        ShopSign::Closed => "sorry, we're closed.".to_string(),
        ShopSign::BackAt(minutes) => {
            format!("back in {} minutes.", minutes)
        }
    }
}

Look at that third arm. minutes didn't exist a moment ago — it's a brand-new name, born right there in the pattern, holding whatever number the real sign is actually carrying. You never wrote a separate line to "reach in and grab it." Checking which sign it is and unpacking what's inside it happen in the exact same breath. This works just as well on bigger boxes — a struct's named fields, a tuple's slots, a sign carrying another sign inside it — you can pull apart as many layers as you need, all inside one pattern.

A few more ways to write a box on the checklist

Three small tools make checklists like this pleasant to write instead of tedious. First, "or," written |, lets one box on the checklist stand for several signs at once, when they all get the same answer:

rust — three numbers, one box, plus a range of numbers as one box

match roll {
    1 | 2 | 3 => "low",
    4..=6 => "high",
    n @ 7..=9 => {
        println!("pretty high: {n}");
        "very high"
    }
    _ => "off the board",
}

4..=6 is one box standing for a whole run of numbers at once, instead of writing 4 | 5 | 6 by hand. And n @ 7..=9 does two things at once — it checks the number falls between 7 and 9, and it hands you that number under the name n, so the box both tests and grabs a value in the same breath. Rust calls that little @ the "at" operator — read it as "call this n, while also checking it's in this range."

Last, the plain underscore _ is a box that catches absolutely anything and doesn't bother naming what it caught — it's how you write "and everything else" as your very last box on the checklist. Don't confuse it with the two dots .., which is a smaller, different tool: inside a single box, .. means "and skip naming the rest of this sign's fields," not "and skip the rest of the checklist."

rust — .. skips naming the rest of one sign's fields, not the rest of the checklist

struct Ticket { id: u32, priority: u8, label: String }

let Ticket { id, priority, .. } = ticket;   // label is skipped, ticket is still fully matched
println!("#{id} at priority {priority}");

The trap: a box that only looks checked

Sometimes you want a box on the checklist to depend on more than just the sign — you want an extra "and only if" condition. Rust lets you tack one on with if, called a "match guard." Here's the honest, worth knowing trap: a guard is a promise you make out loud, not one Rust checks for you.

rust — two boxes that LOOK like they cover every case, but don't compile

let n = 4;
match n {
    x if x < 5 => println!("small"),
    x if x >= 5 => println!("big"),
    // error: still "non-exhaustive patterns" — even though every real
    // number is either < 5 or >= 5
}

To you, that clearly covers every number there is. To the strict friend checking your checklist, it doesn't — because the strict friend never looks at what's written after the if. It only checks the shape of each box, and every one of these boxes has the same plain shape: "any number, x." As far as the checklist is concerned, both boxes might silently say "no, not this one" at run time, and then there'd be nowhere left for the number to go. So it insists on one more, unconditional box, just in case:

rust — fixed: an unguarded box closes the checklist for real

match n {
    x if x < 5 => println!("small"),
    _ => println!("big"),
}

This can feel picky the first time you meet it — of course x >= 5 catches whatever x < 5 didn't. But the strict friend isn't reading your math homework; it's checking that a box exists for every shape of value, full stop, without needing to trust that any particular if will fire the way you expect. That's a smaller, safer promise to check — and it's exactly why it can check it perfectly, every single time.

What happens when the list of signs grows

Here's where "checking every box" earns its keep for real. Say six months from now, someone adds a fourth sign to the shop door — Renovating. Every single match anywhere in the whole program that reads a ShopSign and does not already have a catch-all box now stops compiling. Not one of them. Every one, at once, the moment that new sign is added.

Read that again, because it's the opposite of how most bugs get found. Nobody has to remember to go hunting through the codebase for every place a sign gets read back. Nobody has to write a test for "did we forget Renovating somewhere." The compiler already knows every single spot, because it's the same compiler that checked every one of those matches was exhaustive in the first place — and now the ground truth changed under them. It simply refuses to build until each one is updated to say what Renovating means there.

That's the "proof" in this chapter's Rust name for the idea. A match that compiles isn't a match that was probably tested for every case — it's a match that's provably handling every case that exists right now, checked by a machine that never gets tired near the end of a long checklist the way a person can.

A box that's allowed to grow later, on purpose

Sometimes that strictness is exactly what a library author does not want to hand a customer. Picture a company that sells those same sign frames wholesale, to other shops. If a customer shop writes code that checks every sign the frame can hold today, and then the sign company adds a brand-new sign next year, every one of those customer shops' programs would suddenly stop compiling — a change the sign company made, breaking code it doesn't even own.

Rust lets a sign-frame maker opt out of that, on purpose, by marking the enum "non_exhaustive." It's a small tag that only matters once the frame crosses into someone else's code: inside the company that makes the frame, nothing changes — a match there can still list every sign with no catch-all. But any other shop's code that reads the frame is now required to add a catch-all box of its own, up front, whether it needs one today or not — a standing promise to handle "some sign I haven't heard of yet."

rust — a frame maker that reserves the right to add new signs later

// inside the sign-frame company's own code:
#[non_exhaustive]
pub enum ApiError {
    NotFound,
    Timeout,
}

// inside a shop that just buys frames from them:
match err {
    ApiError::NotFound => { /* ... */ }
    ApiError::Timeout => { /* ... */ }
    _ => { /* required, even though every sign is already listed above */ }
}

It's a trade, made in the open. The sign company gives up nothing — it can grow its list of signs freely. Every shop that buys from it gives up a small amount of proof — "I've handled every sign that exists," becomes "I've handled every sign I know about, plus whatever comes next" — in exchange for their own code not breaking out from under them on someone else's release day.

Why this is worth it

Be honest about the annoyance first: writing out every box, every time, is more typing than a quick guess would be. And the guard trap from a few pages back really does trip people up the first time they hit it — staring at two conditions that obviously cover every number there is, and being told they don't. That frustration is real, and it doesn't fully go away just because it's for a good reason.

What you get in return is bigger than the typing costs. Remember the closing checklist with the unlocked front door — the box nobody noticed was empty, until the one night it mattered? A Rust match makes that specific failure impossible to compile. Not harder to hit. Not caught later by a good test suite, if someone happened to write one for that exact case. Impossible — the program does not exist, on your machine, on the day you wrote it, until every box has something in it. You find out you missed a sign while you're sitting at your own desk, not months later when a customer walks into a shop that says three contradictory things at once.

Match / exhaustiveness
A checklist the compiler won't let you walk away from until every possible sign has a box. Miss one, and the program refuses to build — it doesn't wait to fail until the sign actually shows up.
Destructuring
Pulling the pieces out of a sign — its fields, its carried value — while you're already checking which sign it is, in the very same pattern.
| , ..= , @ , _ , ..
Small tools for writing one box that covers several signs (|), a whole range of numbers (..=), a name plus a check at once (@), "anything else" (_), or "skip the rest of this sign's own fields" (..).
Match guard
An extra if condition tacked onto one box. It runs at the very last moment, after the checklist is already proven complete — the checklist itself never trusts what a guard says.
non_exhaustive
A tag a library author puts on an enum to keep the right to add new signs later, at the cost of requiring every outside shop's checklist to always carry a catch-all box.

Once every box on the checklist has to have something in it before your program is even allowed to run, "I think I covered every case" stops being a hope you carry around in your head and becomes something the strict friend already checked for you, for good.
