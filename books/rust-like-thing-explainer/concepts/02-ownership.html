Who Gets to Keep the Toy

Rust calls this: ownership

Every value your program makes belongs to somebody. Rust cares, a lot, about exactly who — because knowing who's holding a thing is how it knows when that thing can safely go away.

Here's the problem

Picture a toy truck. One kid, Sam, is holding it. Sam writes "Sam's truck" on a sticky note and puts it in his pocket, so he remembers it's his.

Now say Sam hands the truck to his friend Jo. If Sam's sticky note still says the truck is his — if both Sam and Jo think they're the one holding it — trouble is coming. Maybe Sam walks off and tosses the truck in the donation bin, not knowing Jo is still pushing it around the room. Now Jo is holding a truck that, as far as anyone's notes say, doesn't exist anymore. That's not a toy problem. In a computer program, it's called using memory after it's already been thrown away — and it's one of the oldest, nastiest bugs there is.

One truck, one name on the sticky note

Rust's fix is almost stubbornly simple. At any moment, exactly one sticky note is allowed to say "this is mine" for any one value. Rust has a small word for whoever's sticky note is currently true: the "owner." The rule, in full, is just three sentences:

The whole rule

Every value has exactly one owner. There is never more than one owner at the same time. And when the owner's turn is over — when it leaves the room, so to speak — the value is cleaned up right then, automatically.

That's it. That one rule is most of what makes Rust programs safe without needing a helper watching the whole party, the way we talked about in the last chapter.

What actually happens when you hand something over

Here's where it gets interesting. In Rust, handing a value to someone else — even just writing let jo = sam; — doesn't make a second truck. There is still only one truck. What happens is the sticky note itself gets torn off Sam and stuck onto Jo. Sam's old note is gone. From that moment on, if Sam's code tries to use the truck again, the compiler — that strict friend from the last chapter — stops it, before your program ever runs.

Rust has a name for this kind of handoff: a "move." The word is well chosen. It isn't a copy. The thing actually moved, and only one name is valid for it afterward.

rust — handing a truck to a friend

let sam = String::from("truck");
let jo = sam;                 // the sticky note moves from sam to jo

println!("{}", jo);      // fine — jo is holding it now
println!("{}", sam);     // error: sam's value was moved to jo

That second println! line won't even compile. And that's exactly the point. Rust would rather stop you with a clear note on your screen today than let you and a friend both think you're holding the same truck and find out the hard way, later, that one of you is wrong.

Not everything is worth fighting over

Here's a fair question: does handing someone a single coin really need all this fuss? If Sam gives Jo the number 5, does Sam really lose the number 5?

No — and Rust agrees with you. Small, simple things, like plain numbers, true-or-false answers, and single letters, are so cheap to duplicate that Rust just duplicates them instead of moving them. It's like handing someone a photocopy of a coin instead of the coin itself — there's plenty more where that came from, so nobody has to give anything up. Rust marks these types with a small label, "Copy," and you'll mostly notice it by what doesn't happen: no error, no crossed-out sticky note.

rust — a number doesn't need to move

let x = 5;
let y = x;                    // x is Copy: this just duplicates it

println!("{} {}", x, y);       // fine — both still work

A toy truck is different. It's a real, one-of-a-kind thing — under the hood, Rust says it "owns" a chunk of space set aside to hold it, the way a real truck takes up real space in a real toy box. Duplicating that isn't free, so Rust won't do it silently. If you truly want two separate trucks — an actual second one, not just a second name for the same truck — you have to ask for it out loud, by calling .clone():

rust — asking, out loud, for a real second truck

let sam = String::from("truck");
let jo = sam.clone();       // a whole separate truck, made on purpose

println!("{} {}", sam, jo);      // fine — two real trucks, two owners

That one word, spelled out in the code, is the whole idea: quietly duplicating something big is a cost you should always be able to see, not one hidden inside a plain equals sign.

When the room empties out

There's still the third sentence of the rule to explain: when the owner's turn is over, the value is cleaned up right then. What does "turn is over" actually mean?

It means the little stretch of code — the room, if we're keeping the picture — that the owner was born in has come to an end. Rust calls that stretch of code a "scope." Most of the time it's just whatever's between one pair of curly braces { } and the matching one. The instant the closing brace is reached, if nobody moved the value out to somewhere else first, Rust puts it away — automatically, and always at that exact same spot.

rust — the truck gets put away when the room empties

fn play_with_truck() {
    let truck = String::from("truck");  // truck's room starts
    println!("{}", truck);
}   // the closing brace: truck's room ends, truck is put away right here

Rust has a name for the moment something gets put away: "drop." You never have to write the put-away step yourself, the way you'd have to remember to call free() in some older languages. It just happens, exactly once, exactly when the owner's room ends — whether the room is a block of code, the body of a function, or one trip through a loop.

One extra, tidy detail

If more than one thing was born in the same room, Rust puts them away in the opposite order they arrived — like stacking chairs, the last one down comes off first. And if a value is really a small box holding several other things inside it, each of those inner things gets put away too, in the order they were packed. You never have to ask for this. It just happens, every time, the same way.

Handing a truck through a doorway

One more shape this takes, worth seeing once: passing a value into a function is a move too, exactly like handing it to a friend. The function's body is its own little room. If you pass your truck in and the function doesn't hand it back out, your truck's room ends the moment the function finishes — and it gets dropped there, not back where you called it from.

rust — passing a truck through a doorway

fn put_away(t: String) {
    println!("putting away {}", t);
}   // t's room ends here — t is dropped, inside put_away

fn main() {
    let truck = String::from("truck");
    put_away(truck);         // truck moves into put_away
    println!("{}", truck);  // error: truck was moved
}

This is exactly why the very next chapter matters so much: most of the time, you don't actually want to give your truck away just to let a friend look at it for a second. You want to let them use it without taking it home. Rust has a whole separate way to do that — it's called borrowing, and it's next.

Why one owner is worth it

Here's the part that is famously annoying

Nearly every Rust beginner, at some point, tries to use a value after it's already moved — and gets stopped cold by the compiler, usually while just trying to print something twice. It feels like being told you can't hold your own truck. That's a real, common frustration, and it doesn't go away in a week. It fades once "who owns this right now?" becomes a question you start asking automatically.

Here's why it's worth the friction. Because exactly one owner is ever responsible for a value, Rust always knows, without guessing and without watching your program while it runs, precisely where that value gets put away. No two pieces of code can ever both think they're in charge of throwing it out. Nothing can ever get thrown away twice. And nothing can ever get used after it's already gone — because the compiler catches that this morning, at your desk, instead of your program catching it at 3 a.m., in front of someone else.

Owner
Whoever's sticky note currently says "this is mine." Only one, ever, for a given value.
Move
Handing a value to someone else. The sticky note travels; the old name stops working.
Copy
What happens instead of a move, for small simple things like numbers — duplicating is so cheap Rust just does it, no note needed.
Drop
The automatic put-away that happens the instant the owner's room — its "scope" — closes.

Because exactly one name is ever true for a value at a time, your program can never fight itself over who's holding it — or forget to put it away at all.
