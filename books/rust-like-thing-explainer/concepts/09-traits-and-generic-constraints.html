A List of Things Something Must Know How to Do

Rust calls this: traits, trait bounds, and the choice between static and dynamic dispatch

Every value you've met so far had one fixed, exact type — a String, a RegisterError, an i32. Now you're going to write code that doesn't care about the exact type at all. It only cares whether that type can do one particular job. This chapter is about how Rust writes down "I don't need to know what you are — I only need to know what you can do."

Here's the problem

Say you want one function that can announce anything, as long as it knows how to describe itself in one line: a tweet, a news article, a weather report. Written the ordinary way, you'd need a separate function for each one — announce_tweet, announce_article, announce_report — even though every single one of those functions would do the exact same thing: ask the thing for its one-line description, then print it.

The three functions aren't actually different. Only the type of thing being announced is different. You want to write the "ask for a description, then print it" part exactly once — but Rust won't let a function take "literally anything" and just hope a .describe() method happens to exist on it. It needs actual proof, before your code even runs, that whatever shows up really can do that job.

The fix: write down the job, not the type

Rust lets you name a job — a short list of things a type must know how to do — completely separately from any one type. That named list is called a "trait." A trait doesn't hold any data of its own. It's not a bigger box a type gets built inside of. It's closer to a checklist pinned to a door: any type that can honestly check off every item on the list is allowed through, no matter what that type actually is underneath.

rust — the checklist, and one type checking off every item

trait Summary {
    fn summarize(&self) -> String;
}

struct Tweet {
    text: String,
}

impl Summary for Tweet {
    fn summarize(&self) -> String {
        format!("tweet: {}", self.text)
    }
}

Notice what's missing: no shared parent, no "Tweet is a kind of Summary." A Tweet is just a Tweet. It happens to also, separately, know how to summarize itself, because somebody wrote a second block — impl Summary for Tweet — that says so. An Article, a WeatherReport, or anything else can check off the exact same list in its own, completely unrelated way, with its own impl block. And the reverse works too: one type is free to check off several completely different lists at once, if it can honestly do all of those jobs.

The whole idea

A class hierarchy asks "what kind of thing is this, deep down?" A trait only ever asks "can this thing do the job?" It doesn't care what a type is. It only cares what a type can do — and it wants proof, checked before your program ever runs, not a promise you typed in good faith.

A trait can even hand you a job already half-done. Write a body right inside the trait itself, and any type that doesn't want to bother writing its own version can accept that one as-is, with an empty impl block:

rust — a default answer, free for the taking

trait Summary {
    fn summarize(&self) -> String {
        String::from("(Read more...)")
    }
}

struct Article {
    headline: String,
}

impl Summary for Article {}   // takes the default, exactly as written

Telling a generic function what it's allowed to assume

Now the actual function — the one written once, for anything that can summarize. You write it with a placeholder letter standing in for "some type, to be decided later," usually T. This is called a "generic." But a bare T, with nothing else said about it, is almost useless — Rust has no idea what a totally unknown type is allowed to do, so by default it assumes almost nothing. It'll let you move a T around and hand it off. It will not let you call .summarize() on it, print it, or compare it to another one — not unless you say, right there in the function's own definition, exactly which jobs a T is guaranteed to be able to do.

That's what a "trait bound" is: a promise attached to the placeholder letter, saying "whatever type actually shows up here, it's guaranteed to check off this list." Once that promise is written down, the compiler will let your function body call every method on that list, and it will refuse — before your program ever runs — to compile a call to this function with any type that can't actually back the promise up.

rust — one function, proof required at the door

fn notify(item: &impl Summary) {
    println!("Breaking news! {}", item.summarize());
}

// the exact same function, spelled the longer, more explicit way
fn notify<T: Summary>(item: &T) {
    println!("Breaking news! {}", item.summarize());
}

Both of those are the same function to Rust — &impl Summary is just a shorter way to write "some type, and I'm promising up front it can summarize itself." Either way, call notify(&my_tweet) or notify(&my_article) and it works, no copy-pasting required. Call it with something that never checked off that list, and your program doesn't compile at all — the mistake is caught the moment you write it, not the first time a user happens to trigger that code path.

Need more than one job proven at once? Chain the promises together with a plus sign. And once a function starts asking for several promises on several placeholder letters, the list can get long and hard to read sitting right there in the angle brackets — so Rust lets you move the whole list down to its own line, called a where clause. It changes nothing about what's required. It's purely there so a human can still read the function's name before running out of room.

rust — two promises, moved out of the way

fn describe<T>(item: &T) -> String
where
    T: Summary + std::fmt::Display,
{
    format!("{} -- {}", item, item.summarize())
}

One promise, kept before the race even starts

Here's what actually happens when your program gets built. Rust doesn't leave notify as one blurry function that figures out, while running, what kind of thing it was handed. Instead, for every different type you actually call notify with in your whole program, the compiler quietly writes out a fresh, separate, fully specific copy of notify — one exactly for Tweet, one exactly for Article, each with the placeholder letter swapped out for the real type. It's exactly as if you'd hand-written every one of those copies yourself, back when this chapter started with "three functions instead of one" — except now the compiler does the copying, and you only ever wrote the idea down once.

Because of that, calling notify costs nothing extra at runtime compared to calling a plain, ordinary, non-generic function — which exact copy to run was already decided back when the program was built, the same way a bricklayer already knows which brick goes where before laying the first one. Rust calls this deciding-ahead-of-time approach "static dispatch." The one real cost, and it's worth saying plainly, is that every extra type you use with the same generic function means one more full copy of its compiled code sitting in your finished program — more different types, a bigger program, and a bit more time spent building it.

When you genuinely don't know the type until later

Static dispatch has one real limit: the placeholder letter T is still exactly one specific type, decided per call. Sometimes that's not what you want at all — say, a list of things to announce today, and that list is genuinely a mix: a couple of tweets, an article, a weather report, all sitting in the very same collection. No single T can be "Tweet and Article and WeatherReport" all at once.

For exactly that case, Rust has a second way to use a trait, written dyn Summary — almost always tucked behind a Box, like Box<dyn Summary>. Instead of handing the compiler one exact type to build a specific copy for, you hand it a box holding some value plus a small attached card listing exactly where to find that value's own summarize method. Rust calls that little card a "vtable" — short for "virtual table," a plain lookup card of "where each job on the list actually lives, for this one value." Calling .summarize() on it means checking that card first, then jumping to whatever it points at — one small extra step, paid at the moment you actually call it, instead of a decision made once, ahead of time.

rust — one box, genuinely different things inside it

let items: Vec<Box<dyn Summary>> = vec![
    Box::new(Tweet { text: String::from("hi") }),
    Box::new(Article { headline: String::from("News") }),
];

for item in &items {
    println!("{}", item.summarize()); // checks each one's own card
}

Rust calls this "dynamic dispatch" — which exact summarize to run is settled while the program is actually running, one card-check at a time, not fixed ahead of time the way a generic's copies are. In exchange, only one single copy of the announcing code exists anywhere in your program, no matter how many different kinds of things ever flow through it — genuinely useful the day binary size, not raw speed, is what you're watching.

Not every checklist can become a card

A trait can only be used as dyn Trait if every job on its list can be written down on one fixed-size lookup card ahead of time. Rust calls a trait that manages this "dyn compatible." Two things break it in practice: a method that's itself generic — an unlimited family of possible versions can't fit on one fixed card — and a method that hands back a bare Self, since by the time you're holding a dyn Trait, the box has already forgotten the real type's exact size, and can't say how big a fresh one would be. Hit this, and Rust simply refuses to build the card at all, right there at compile time.

Which one to reach for

Default to the plain generic with a trait bound. It costs nothing at runtime, and the compiler gets to look at each specific, fully-known copy and squeeze it as tight as it possibly can. Reach for dyn Trait specifically the moment you actually need one variable, one field, or one list to genuinely hold more than one kind of thing at once — or the day your compiled program has gotten large enough that trading one small per-call card-check for far fewer duplicated copies is worth it. Most code, most of the time, never needs to ask that second question at all.

Why this is worth it

Be honest about the cost first: naming a trait, then writing an impl block for every type that uses it, is more typing than just calling .summarize() and hoping it happens to exist. Some languages let you skip straight to hoping. Rust asks you to say the promise out loud first.

What you get back is bigger than the typing. One idea, written once, genuinely works for anything honest enough to prove it belongs — no copy-pasted near-duplicate functions to keep in sync by hand, and no chance of calling .summarize() on something that was never actually promised to have one, because that mistake simply can't compile. And you still get to choose, deliberately, whether that proof gets checked once, ahead of time, or once per call, while your program is already running — instead of the choice quietly being made for you.

trait
A named checklist of jobs a type can do — no data of its own, and no class hierarchy underneath it.
impl Trait for Type
One type, checking off one checklist, in its own way. Any number of types can check off the same list; any type can check off any number of lists.
trait bound (T: SomeTrait)
A promise attached to a generic placeholder: whatever type shows up here is guaranteed to check off this list, so the function body is allowed to rely on it.
impl Trait (argument position)
Shorthand for a generic parameter with a bound — the same function, spelled shorter.
static dispatch
A separate, specialized copy of a generic function built for each type it's actually called with; which copy runs is decided before the program starts.
dyn Trait / dynamic dispatch
A box holding a value plus a lookup card (a "vtable") to its own methods; which method runs is decided while the program runs. Lets one collection hold genuinely different types at once.
dyn compatible
A trait whose whole checklist can fit on one fixed-size lookup card — no generic methods, no bare Self returns.

Once you can write "anything that can do this job," instead of "this exact type and no other," the same honest idea gets to work for whatever shows up next — today's types, and the ones you haven't written yet.
