Case Study: A QA Agent Over Knowledge Graphs

You have a Neo4j database full of interconnected entities—people, companies, products, transactions—and a user who wants to ask questions in plain English. The gap between “Who are the top suppliers linked to delayed shipments in Q3?” and the Cypher query that answers it is surprisingly wide. This chapter builds the bridge: a complete, production-shaped QA agent that turns natural language into graph queries, executes them, and returns human-readable answers. Along the way you’ll see every LangGraph pattern from the previous chapters come together in a single, testable pipeline.

The Problem: Natural Language Over a Knowledge Graph

Knowledge graphs excel at representing relationships. A relational database can tell you that order 4417 shipped late; a knowledge graph can tell you why—because the supplier shares a warehouse with another supplier whose port is under congestion. But writing Cypher (Neo4j’s query language) requires expertise that most end users don’t have. The question is not whether an LLM can generate Cypher—it can, with varying reliability—but how to wrap the generation in a pipeline that handles ambiguity, retries on failure, and presents results transparently.

Our requirements are concrete: accept a natural language question, decide whether it needs a graph query at all, extract the relevant schema elements, generate Cypher, execute it against Neo4j, and summarize the raw results into a conversational answer. If the generated Cypher fails, the pipeline should retry with the error message as context. And the whole thing should be accessible through a Streamlit chat interface where the user can see exactly which Cypher was generated and what data came back.

Pipeline Architecture

Before touching code, let’s map out the full pipeline as a LangGraph state graph. There are six nodes, one conditional edge for the error-retry loop, and a clear entry and exit.

The diagram shows the happy path running top-to-bottom on the right side: Intent Classifier → Schema Extractor → Cypher Generator → Query Executor → Summarizer → END. Two branches deviate from that path. First, the Intent Classifier can short-circuit to END when the question doesn’t need a graph query (e.g., “Hello” or “What is Cypher?”). Second, if the Query Executor encounters a Cypher syntax error or a constraint violation, control flows to the Error Handler, which annotates the state with the error message and loops back to the Cypher Generator for another attempt.

Pipeline Stages at a Glance

Each node’s role, input, and output within the pipeline
Stage Node Name Responsibility Key State Update
1 classify_intent Decide whether the question requires a graph query or can be answered directly intent — "graph_query" or "direct_answer"
2 extract_schema Identify the node labels, relationship types, and properties relevant to the question schema_elements — list of entities and relations
3 generate_cypher Produce a read-only Cypher query using the extracted schema and, on retries, the previous error cypher_query, cypher_explanation
4 execute_query Run the Cypher against Neo4j and capture the result set or error query_results or query_error
5 summarize_results Convert raw query results into a natural language answer answer
6 handle_error Package the error context and increment the retry counter retry_count, error_context

Defining the Pipeline State

Everything flows through one TypedDict. Each node reads what it needs, writes what it produces, and leaves the rest untouched. Notice that we include both a query_results field and a query_error field—only one is populated after the executor runs, and the conditional edge checks which.

Pipeline state definition

from typing import TypedDict, Optional, Annotated
from langgraph.graph import add_messages
from langchain_core.messages import BaseMessage


class SchemaElement(TypedDict):
    """A node label, relationship type, or property from the graph schema."""
    element_type: str   # "node", "relationship", or "property"
    name: str
    description: str


class QAState(TypedDict):
    # Conversation history (uses add_messages reducer)
    messages: Annotated[list[BaseMessage], add_messages]

    # Intent classification
    question: str
    intent: Optional[str]            # "graph_query" | "direct_answer"
    direct_answer: Optional[str]

    # Schema extraction
    schema_elements: Optional[list[SchemaElement]]

    # Cypher generation
    cypher_query: Optional[str]
    cypher_explanation: Optional[str]

    # Execution
    query_results: Optional[list[dict]]
    query_error: Optional[str]

    # Summarization
    answer: Optional[str]

    # Error handling
    retry_count: int
    error_context: Optional[str]
    max_retries: int

A few things to notice. The messages field uses the add_messages reducer so that each node can append messages without overwriting the conversation history. The retry_count and max_retries fields control how many times the error loop can cycle before giving up. And the error_context field accumulates information from failed attempts so the Cypher generator can learn from its mistakes.

Structured Output with Pydantic

Several nodes need the LLM to return structured data—not free-form text. We use Pydantic models and LangChain’s with_structured_output to enforce the shape of the LLM’s response at each stage.

Pydantic models for structured LLM outputs

from pydantic import BaseModel, Field


class IntentClassification(BaseModel):
    """Whether the question needs a graph query."""
    intent: str = Field(
        description="Either 'graph_query' or 'direct_answer'"
    )
    reasoning: str = Field(
        description="Brief explanation of why this intent was chosen"
    )
    direct_answer: str | None = Field(
        default=None,
        description="Answer if intent is direct_answer, else None"
    )


class ExtractedSchema(BaseModel):
    """Relevant schema elements for the user's question."""
    entities: list[str] = Field(
        description="Node labels relevant to this question"
    )
    relationships: list[str] = Field(
        description="Relationship types relevant to this question"
    )
    properties: list[str] = Field(
        description="Property names to use in the query"
    )


class CypherOutput(BaseModel):
    """A generated Cypher query with explanation."""
    query: str = Field(
        description="The Cypher query to execute"
    )
    explanation: str = Field(
        description="What this query does in plain English"
    )

By asking for a reasoning field on the intent classifier, we get chain-of-thought baked into the structured output. The model must articulate why it chose a particular intent before committing, which improves accuracy—especially on borderline questions like “What types of products do you have?” which could be answered from schema metadata alone or from an actual query.

Node 1: The Intent Classifier

The first node is a gatekeeper. Not every user message requires a graph query. Greetings, follow-up clarifications, or questions about the system itself should be handled without touching Neo4j. The intent classifier makes this call.

Intent classifier node

from langchain_anthropic import ChatAnthropic

llm = ChatAnthropic(model="claude-sonnet-4-20250514")

INTENT_PROMPT = """You are a question classifier for a knowledge graph QA system.
The knowledge graph contains information about companies, people,
products, and their relationships.

Given the user's question, determine:
1. Does this question require querying the knowledge graph? (graph_query)
2. Can it be answered directly without a query? (direct_answer)

Questions about greetings, system capabilities, or general knowledge
should be classified as direct_answer.

Questions about specific entities, relationships, counts, or patterns
in the data should be classified as graph_query.

User question: {question}"""


def classify_intent(state: QAState) -> dict:
    """Classify whether the question needs a graph query."""
    question = state["question"]

    classifier = llm.with_structured_output(IntentClassification)
    result = classifier.invoke(
        INTENT_PROMPT.format(question=question)
    )

    update = {
        "intent": result.intent,
    }

    if result.intent == "direct_answer":
        update["direct_answer"] = result.direct_answer
        update["answer"] = result.direct_answer

    return update

The conditional edge after this node is straightforward: check state["intent"] and route accordingly.

Conditional routing after intent classification

def route_after_intent(state: QAState) -> str:
    """Route to schema extraction or directly to END."""
    if state["intent"] == "graph_query":
        return "extract_schema"
    return "__end__"

Node 2: The Schema Extractor

Rather than dumping the entire graph schema into the Cypher generation prompt (which can be enormous in production databases), we first extract only the relevant portions. This node takes the user’s question and a cached copy of the full schema, then identifies which node labels, relationship types, and properties matter.

Schema extractor with caching

from functools import lru_cache
from neo4j import GraphDatabase

driver = GraphDatabase.driver(
    "bolt://localhost:7687",
    auth=("neo4j", "password")
)


@lru_cache(maxsize=1)
def get_full_schema() -> str:
    """Fetch and cache the graph schema. Called once per process."""
    with driver.session() as session:
        # Get node labels and their properties
        labels = session.run(
            "CALL db.schema.nodeTypeProperties()"
        ).data()
        # Get relationship types
        rels = session.run(
            "CALL db.schema.relTypeProperties()"
        ).data()
    return format_schema(labels, rels)


SCHEMA_PROMPT = """Given the user's question and the full graph schema below,
identify ONLY the node labels, relationship types, and properties
that are relevant to answering this question.

Full schema:
{schema}

User question: {question}"""


def extract_schema(state: QAState) -> dict:
    """Extract relevant schema elements for the question."""
    full_schema = get_full_schema()

    extractor = llm.with_structured_output(ExtractedSchema)
    result = extractor.invoke(
        SCHEMA_PROMPT.format(
            schema=full_schema,
            question=state["question"]
        )
    )

    return {
        "schema_elements": [
            {"element_type": "node", "name": e, "description": ""}
            for e in result.entities
        ] + [
            {"element_type": "relationship", "name": r, "description": ""}
            for r in result.relationships
        ]
    }
Schema Caching

The @lru_cache decorator means the schema is fetched from Neo4j exactly once per process. In a production deployment, you’d want a TTL-based cache (e.g., using cachetools.TTLCache) so that schema changes are picked up within minutes rather than requiring a restart. You might also store the formatted schema string in Redis so that multiple worker processes share it.

Node 3: The Cypher Generator

This is the most critical node. It takes the user’s question, the extracted schema, and (on retries) the previous error, then generates a Cypher query. The prompt engineering here matters more than anywhere else in the pipeline.

Cypher generator node

CYPHER_PROMPT = """You are a Cypher query expert. Generate a Neo4j Cypher query
to answer the user's question using ONLY the schema elements provided.

RULES:
1. Use ONLY read operations (MATCH, RETURN, WITH, WHERE, ORDER BY, LIMIT).
2. NEVER use write operations (CREATE, MERGE, SET, DELETE, REMOVE, DROP).
3. Always include a LIMIT clause (max 25 rows).
4. Use parameterized values where possible.
5. Prefer explicit relationship directions over undirected patterns.

Relevant schema:
{schema}

User question: {question}
{error_context}"""


def generate_cypher(state: QAState) -> dict:
    """Generate a Cypher query from the question and schema."""
    error_ctx = ""
    if state.get("error_context"):
        error_ctx = (
            f"\nPrevious attempt failed with error:\n"
            f"{state['error_context']}\n"
            f"Please fix the query to avoid this error."
        )

    schema_text = format_schema_elements(
        state["schema_elements"]
    )

    generator = llm.with_structured_output(CypherOutput)
    result = generator.invoke(
        CYPHER_PROMPT.format(
            schema=schema_text,
            question=state["question"],
            error_context=error_ctx
        )
    )

    return {
        "cypher_query": result.query,
        "cypher_explanation": result.explanation,
        "query_error": None,  # Clear previous error
    }


def format_schema_elements(elements: list[dict]) -> str:
    """Format schema elements into a readable string."""
    nodes = [e["name"] for e in elements if e["element_type"] == "node"]
    rels = [e["name"] for e in elements if e["element_type"] == "relationship"]
    return (
        f"Node labels: {', '.join(nodes)}\n"
        f"Relationship types: {', '.join(rels)}"
    )

The prompt rules are deliberate guardrails. Rule 1 and 2 prevent the LLM from generating mutation queries—a critical safety requirement. Rule 3 ensures the result set stays manageable. Rule 5 improves query performance by avoiding undirected pattern matching, which is expensive in large graphs. On retries, the error context gives the model specific information about what went wrong, which typically produces a corrected query on the second attempt.

Cypher Injection Safety

Even with prompt-level guardrails, never trust LLM-generated Cypher without server-side protection. Configure your Neo4j user with read-only access at the database level. Use a dedicated user account with only MATCH and RETURN privileges. Additionally, validate the generated Cypher before execution: parse it to confirm it contains no write keywords, or run it in a read-only transaction (session.read_transaction). Prompt injection attacks can cause the LLM to ignore your rules and generate destructive queries—database-level permissions are your last line of defense, not the prompt.

Node 4: The Query Executor

With a Cypher query in hand, the executor runs it against Neo4j. This node is primarily about error handling: catching exceptions, formatting them for the retry loop, and ensuring the connection is properly managed.

Query executor with error capture

from neo4j.exceptions import CypherSyntaxError, ClientError


def execute_query(state: QAState) -> dict:
    """Execute the Cypher query against Neo4j."""
    cypher = state["cypher_query"]

    try:
        with driver.session() as session:
            # Use read_transaction for safety
            result = session.read_transaction(
                lambda tx: tx.run(cypher).data()
            )
        return {
            "query_results": result,
            "query_error": None,
        }
    except (CypherSyntaxError, ClientError) as e:
        return {
            "query_results": None,
            "query_error": str(e),
        }
    except Exception as e:
        # Unexpected errors should not retry
        return {
            "query_results": None,
            "query_error": f"Unexpected error: {e}",
        }

Notice that we use read_transaction rather than a general session.run. This is the database-level enforcement complementing our prompt-level guardrails: even if the LLM produces a CREATE statement despite instructions, the read transaction will reject it.

Node 5: The Error Handler and Retry Loop

When Cypher execution fails, the error handler packages up the failure context and increments the retry counter. The conditional edge after the executor decides whether to enter this loop.

Error handler and routing logic

def handle_error(state: QAState) -> dict:
    """Package error context for the retry loop."""
    return {
        "error_context": (
            f"Query: {state['cypher_query']}\n"
            f"Error: {state['query_error']}"
        ),
        "retry_count": state.get("retry_count", 0) + 1,
    }


def route_after_execution(state: QAState) -> str:
    """Route based on query success or failure."""
    if state.get("query_error"):
        retry_count = state.get("retry_count", 0)
        max_retries = state.get("max_retries", 2)
        if retry_count < max_retries:
            return "handle_error"
        # Max retries exceeded; summarize the failure
        return "summarize_results"
    return "summarize_results"

The routing function checks two conditions: did the query fail, and have we exhausted our retries? If the query failed but retries remain, we go to the error handler which loops back to the Cypher generator. If retries are exhausted or the query succeeded, we proceed to the summarizer—which handles both success and graceful failure messaging.

Node 6: The Summarizer

The final node converts raw Neo4j query results (or a failure message) into a natural language answer. It also appends the answer to the conversation history for continuity.

Summarizer node

SUMMARIZE_PROMPT = """You are a helpful assistant that explains query results
in clear, natural language. Given the user's original question and
the query results from a knowledge graph, provide a concise answer.

If the results are empty, say so clearly and suggest how to refine
the question. If there was an error, explain what went wrong without
exposing technical details.

User question: {question}
Query results: {results}
Query used: {cypher}"""


def summarize_results(state: QAState) -> dict:
    """Summarize query results into a natural language answer."""
    results = state.get("query_results")
    error = state.get("query_error")

    if error and not results:
        results_text = f"Query failed after retries: {error}"
    elif not results:
        results_text = "No results found."
    else:
        results_text = str(results[:25])  # Cap display

    response = llm.invoke(
        SUMMARIZE_PROMPT.format(
            question=state["question"],
            results=results_text,
            cypher=state.get("cypher_query", "N/A")
        )
    )

    return {
        "answer": response.content,
        "messages": [response],
    }

Assembling the Graph

With all nodes and routing functions defined, we wire them together into a LangGraph StateGraph. This is the moment where the architecture diagram from earlier becomes executable code.

Full graph assembly with MemorySaver

from langgraph.graph import StateGraph, END
from langgraph.checkpoint.memory import MemorySaver

# Build the graph
builder = StateGraph(QAState)

# Add nodes
builder.add_node("classify_intent", classify_intent)
builder.add_node("extract_schema", extract_schema)
builder.add_node("generate_cypher", generate_cypher)
builder.add_node("execute_query", execute_query)
builder.add_node("summarize_results", summarize_results)
builder.add_node("handle_error", handle_error)

# Set entry point
builder.set_entry_point("classify_intent")

# Add edges
builder.add_conditional_edges(
    "classify_intent",
    route_after_intent,
    {
        "extract_schema": "extract_schema",
        "__end__": END,
    }
)

builder.add_edge("extract_schema", "generate_cypher")
builder.add_edge("generate_cypher", "execute_query")

builder.add_conditional_edges(
    "execute_query",
    route_after_execution,
    {
        "handle_error": "handle_error",
        "summarize_results": "summarize_results",
    }
)

# Error handler loops back to Cypher generation
builder.add_edge("handle_error", "generate_cypher")

# Summarizer goes to END
builder.add_edge("summarize_results", END)

# Compile with memory for conversation continuity
memory = MemorySaver()
graph = builder.compile(checkpointer=memory)

The MemorySaver checkpointer gives us conversation continuity across invocations. When a user asks a follow-up question, the graph can access the previous state—including past queries and answers—through the thread’s checkpoint. This is essential for the Streamlit integration, where users expect a conversational experience.

Why MemorySaver Here?

For a local prototype, MemorySaver (an in-memory checkpointer) is fine. In production, you’d swap it for SqliteSaver or a PostgreSQL-backed checkpointer so that conversation state persists across deployments. The graph code itself doesn’t change—only the checkpointer argument to compile().

Running the Pipeline

result = graph.invoke(

A typical run produces output like this: the generated Cypher (e.g., MATCH (s:Supplier)-[:SHIPPED]->(o:Order) WHERE o.status = ’delayed’ WITH s, count(o) AS delays WHERE delays > 3 RETURN s.name, delays ORDER BY delays DESC LIMIT 25) and a natural language answer summarizing the results. The transparency of showing the Cypher is valuable for debugging and for users who want to verify the query logic.

Integrating Streamlit for the Frontend

A command-line interface is fine for development, but end users need something more approachable. Streamlit gives us a chat interface with minimal code. The key features: streaming responses, displaying the generated Cypher for transparency, and showing the raw query results alongside the natural language answer.

Streamlit chat application

import streamlit as st
from langchain_core.messages import HumanMessage

# Import the compiled graph from our pipeline module
from pipeline import graph

st.set_page_config(
    page_title="Knowledge Graph QA",
    page_icon="🔍",
    layout="wide",
)

st.title("Knowledge Graph QA Agent")
st.caption("Ask questions about your data in natural language")

# Initialize session state
if "thread_id" not in st.session_state:
    st.session_state.thread_id = "streamlit-" + str(hash(id(st)))
if "chat_history" not in st.session_state:
    st.session_state.chat_history = []

# Display chat history
for msg in st.session_state.chat_history:
    with st.chat_message(msg["role"]):
        st.markdown(msg["content"])
        if "cypher" in msg:
            with st.expander("View Cypher Query"):
                st.code(msg["cypher"], language="cypher")
        if "results" in msg:
            with st.expander("View Raw Results"):
                st.json(msg["results"])

# Handle new input
if prompt := st.chat_input("Ask a question about the knowledge graph"):
    # Display user message
    with st.chat_message("user"):
        st.markdown(prompt)

    st.session_state.chat_history.append(
        {"role": "user", "content": prompt}
    )

    # Run the pipeline
    config = {
        "configurable": {
            "thread_id": st.session_state.thread_id
        }
    }

    with st.chat_message("assistant"):
        with st.spinner("Thinking..."):
            result = graph.invoke(
                {
                    "question": prompt,
                    "messages": [HumanMessage(content=prompt)],
                    "retry_count": 0,
                    "max_retries": 2,
                },
                config=config,
            )

        # Display the answer
        st.markdown(result["answer"])

        # Show Cypher query if one was generated
        if result.get("cypher_query"):
            with st.expander("View Cypher Query"):
                st.code(result["cypher_query"], language="cypher")

        # Show raw results if available
        if result.get("query_results"):
            with st.expander("View Raw Results"):
                st.json(result["query_results"])

    # Save to chat history
    history_entry = {
        "role": "assistant",
        "content": result["answer"],
    }
    if result.get("cypher_query"):
        history_entry["cypher"] = result["cypher_query"]
    if result.get("query_results"):
        history_entry["results"] = result["query_results"]

Let’s walk through what this gives the user. They type a question into the chat input. A spinner appears while the pipeline runs. When done, the natural language answer appears in the chat, and two expandable sections offer transparency: “View Cypher Query” shows exactly what was executed against Neo4j, and “View Raw Results” shows the data that came back. The chat history persists across interactions using Streamlit’s session state, and the LangGraph checkpointer ensures the graph’s internal state persists too.

For a more responsive experience, you can replace the invoke call with stream and use Streamlit’s st.write_stream. This lets the user see the answer being generated token by token, which is especially helpful for longer answers.

Streaming variant

# Replace the invoke block with streaming
with st.chat_message("assistant"):
    response_container = st.empty()
    full_response = ""

    for event in graph.stream(
        {
            "question": prompt,
            "messages": [HumanMessage(content=prompt)],
            "retry_count": 0,
            "max_retries": 2,
        },
        config=config,
        stream_mode="updates",
    ):
        # Each event is a dict of {node_name: state_update}
        for node_name, update in event.items():
            if node_name == "summarize_results":
                full_response = update.get("answer", "")
                response_container.markdown(full_response)
            elif node_name == "generate_cypher":
                with st.expander("Generated Cypher"):
                    st.code(
                        update.get("cypher_query", ""),
                        language="cypher"
                    )

With stream_mode="updates", you receive each node’s state update as it completes. This lets you show intermediate results—the generated Cypher appears as soon as the Cypher Generator node finishes, even while the Query Executor and Summarizer are still running.

Handling Ambiguous Queries

Real users ask imprecise questions. “Show me the top customers” doesn’t specify what “top” means—by revenue, by order count, by recency? There are three strategies for handling this, and a production system typically uses all three.

  1. Clarification routing. Add a conditional edge after the intent classifier that detects ambiguity and asks the user for clarification before proceeding. This requires an “ambiguous” intent and a node that generates a clarification question.
  2. Default assumptions with disclosure. The Cypher generator makes a reasonable assumption (e.g., “top by revenue”) and the summarizer discloses it: “Here are the top customers by revenue. If you meant something else, please specify.”
  3. Multi-query expansion. Generate multiple Cypher queries for different interpretations, execute them in parallel, and let the summarizer present all perspectives. This is more expensive but more thorough.

For most applications, strategy 2 strikes the right balance. It’s fast, doesn’t block the user, and maintains transparency about what assumptions were made. You can implement it by adding an assumptions field to the CypherOutput model and including it in the summarization prompt.

Guardrails on Generated Cypher

We’ve already discussed read-only database access. But there are additional guardrails worth applying before the query reaches Neo4j.

Cypher validation before execution

import re

FORBIDDEN_KEYWORDS = [
    "CREATE", "MERGE", "SET", "DELETE",
    "REMOVE", "DROP", "DETACH",
    "CALL.*dbms", "LOAD CSV",
]


def validate_cypher(query: str) -> tuple[bool, str]:
    """Validate that Cypher is read-only and bounded."""
    upper = query.upper()

    # Check for write operations
    for keyword in FORBIDDEN_KEYWORDS:
        if re.search(keyword, upper):
            return False, f"Forbidden keyword: {keyword}"

    # Ensure LIMIT clause exists
    if "LIMIT" not in upper:
        return False, "Query must include a LIMIT clause"

    # Check LIMIT value is reasonable
    limit_match = re.search(r"LIMIT\s+(\d+)", upper)
    if limit_match:
        limit_val = int(limit_match.group(1))
        if limit_val > 100:
            return False, f"LIMIT {limit_val} exceeds maximum of 100"

    return True, "OK"

You’d call validate_cypher inside the execute_query node, before running the query. If validation fails, set query_error to the validation message—the same retry loop handles it just like a Neo4j error. The LLM will then regenerate the query, this time knowing that it needs a LIMIT clause or that MERGE is forbidden.

Defense in Depth

Think of Cypher safety as three layers: (1) prompt instructions tell the LLM to generate read-only queries, (2) regex validation catches obvious violations before they reach the database, and (3) the read-only database user rejects anything that slips through. No single layer is sufficient. Prompt instructions can be bypassed through injection. Regex validation can miss creative evasion. Only the database-level permission is airtight—but the other layers reduce unnecessary error-retry cycles and make the system respond faster.

Schema Caching in Practice

The schema extraction node we wrote earlier fetches the full schema once via @lru_cache. In a real deployment, there are two additional optimizations worth considering.

Embedding-based schema matching. If your graph has hundreds of node labels and relationship types, the full schema string might exceed what you want to put in a prompt. Instead of sending the full schema to the LLM for extraction, embed each schema element (label name + description) and use vector similarity to retrieve only the top-k most relevant elements for a given question. This turns the schema extractor from an LLM node into a retrieval node—faster and cheaper.

TTL-based invalidation. Graph schemas change when new node types or relationship types are added. A stale schema cache means the LLM doesn’t know about new entities. Use a time-to-live cache (e.g., 15 minutes) and log a warning when the schema changes between cache refreshes. This way you catch schema drift early without hammering the database on every request.

TTL-based schema cache

from cachetools import TTLCache, cached

schema_cache = TTLCache(maxsize=1, ttl=900)  # 15 minutes


@cached(cache=schema_cache)
def get_full_schema_ttl() -> str:
    """Fetch graph schema with 15-minute TTL cache."""
    with driver.session() as session:
        labels = session.run(
            "CALL db.schema.nodeTypeProperties()"
        ).data()
        rels = session.run(
            "CALL db.schema.relTypeProperties()"
        ).data()
    return format_schema(labels, rels)

Testing the Pipeline

Testing a multi-step LLM pipeline requires a different approach than testing deterministic code. You can’t assert exact outputs because the LLM’s responses vary. Instead, test the structure and the edges.

Unit-test individual nodes by mocking the LLM and Neo4j driver. Verify that each node reads the correct state keys and writes the correct updates. Test the routing logic with hand-crafted state dictionaries—these are pure functions and fully deterministic. Integration-test the full pipeline with a small Neo4j test database (a Docker container with known data). Assert that the answer mentions expected entities or values, not that it matches an exact string.

These tests are fast, deterministic, and catch real bugs—like accidentally swapping the retry condition or misspelling a node name in a route return value. The routing logic is where most pipeline bugs hide, and it’s the easiest part to test thoroughly.

Production Considerations

Moving this pipeline from a prototype to a production system involves several additional concerns beyond the code we’ve written. Here are the most important ones.

Observability

Instrument each node with logging and tracing. LangSmith integrates naturally with LangGraph and gives you visibility into every LLM call, including the prompts, responses, and latencies. At minimum, log the generated Cypher and whether execution succeeded—this gives you a dataset of query patterns you can use to improve prompts and detect regressions.

Latency

The pipeline makes three sequential LLM calls on the happy path (intent, schema extraction, and Cypher generation) plus one more for summarization. Each adds 1–3 seconds. Consider whether the intent classifier and schema extractor can be combined into a single LLM call that returns both the intent and the relevant schema elements. This trades prompt complexity for a full round-trip savings.

Concurrent Users

The MemorySaver checkpointer is not suitable for multi-user deployments—it stores state in process memory and loses it on restart. Use a persistent checkpointer (PostgreSQL or Redis) and ensure each user gets a unique thread_id. The Neo4j driver’s connection pool handles concurrent queries natively, but you should set pool size limits in the driver configuration.

Cost Control

Each pipeline run uses 3–4 LLM calls. In a high-traffic application, this adds up. Consider caching common question-to-Cypher mappings, using a smaller model for intent classification (which doesn’t require the same reasoning capability as Cypher generation), and setting strict retry limits. Two retries is usually sufficient—if the LLM can’t fix the Cypher in two attempts, a third is unlikely to help.

What We Built

This chapter took every pattern from the book—state management, conditional edges, error-retry loops, streaming, checkpointing—and combined them into a single application. The QA agent is not a toy: it handles intent routing, schema-aware query generation, execution with retry, and transparent presentation through a Streamlit frontend. The key architectural insight is that each node has a single responsibility and communicates through a shared, typed state. This makes the pipeline debuggable (you can inspect state between any two nodes), testable (routing logic is pure functions), and extensible (add a new node without rewriting existing ones).

Let’s be honest about the limits. LLM-generated Cypher is not as reliable as hand-written queries. Ambiguous questions will sometimes produce wrong or irrelevant answers. The retry loop helps, but it’s not magic—if the LLM fundamentally misunderstands the schema, a retry with the error message may not fix the underlying confusion. For production use, invest in prompt engineering with real user questions, build a test suite of known-good query patterns, and monitor the retry rate as a health metric.
