04 Persistence across turns

State and Memory

A chatbot that forgets every message the moment it replies is not a conversation partner—it’s a vending machine. You feed it a coin, you get a response, the transaction is over. Real conversations carry context: the customer’s name, the last three things they asked, the decision that was deferred two turns ago. In LangGraph, the mechanism that carries that context is state, and the mechanism that preserves it across invocations is memory. This chapter shows you how both work, from the shape of a single state object through checkpointing, cross-thread stores, and strategies for keeping memory from outgrowing the context window.

Defining State Schemas

Every LangGraph graph operates on a state object. When a node runs, it receives the current state, does its work, and returns a dictionary of updates. The graph merges those updates back into state before handing it to the next node. The question is: what shape should that state take?

The simplest approach uses Python’s TypedDict. You declare a class whose fields name every piece of data the graph needs to carry, and you annotate each field with its type. LangGraph reads those annotations at compile time to understand what the state contains.

A minimal state schema with TypedDict

from typing import TypedDict, Annotated
from langgraph.graph import MessagesState
import operator

class ChatState(TypedDict):
    messages: Annotated[list, operator.add]
    user_name: str
    turn_count: int

Notice three things. First, messages is annotated with Annotated[list, operator.add]. That second element—operator.add—is a reducer, and we’ll spend the next section on those. Second, user_name and turn_count have no reducer, which means new values simply overwrite old ones. Third, this is an ordinary Python class; there is no magic base class to inherit from (though LangGraph does provide MessagesState as a convenient shortcut when all you need is a message list).

If you prefer runtime validation—ensuring that turn_count is actually an integer, for instance—you can define your state with a Pydantic BaseModel instead. LangGraph supports both approaches interchangeably.

State schema with Pydantic validation

from pydantic import BaseModel, Field
from typing import Annotated
import operator

class ValidatedChatState(BaseModel):
    messages: Annotated[list, operator.add] = Field(default_factory=list)
    user_name: str = ""
    turn_count: int = 0
    sentiment: str = "neutral"

With Pydantic you gain defaults, validators, and serialization for free. The cost is a small amount of extra overhead on each state transition. For most applications, either approach works. Pick the one that matches the rest of your codebase.

Reducers in Depth

When two nodes both return a value for the same state field, what should happen? Should the second value replace the first? Should both values be combined? This is the problem reducers solve.

A reducer is a function that takes the current field value and the update value, then returns the merged result. LangGraph calls it every time a node returns an update for that field. If no reducer is specified, the default behavior is simple overwrite: the new value replaces the old.

Default Overwrite Behavior

Fields without an Annotated wrapper use overwrite semantics. If a node returns {"user_name": "Alice"} and a later node returns {"user_name": "Bob"}, the final state will contain "Bob". This is the right choice for fields that represent a single current value: a user’s name, a classification label, a boolean flag.

The operator.add Reducer

The most common reducer is operator.add, which concatenates lists. When a node returns {"messages": [new_msg]}, the reducer appends new_msg to the existing message list rather than replacing it. This is essential for chat-style applications where every node might add a message.

Be precise about what you return. If the field is a list with an operator.add reducer, your node must return a list, not a bare item. Returning a string where a list is expected will cause operator.add to concatenate characters in unpleasant ways.

Custom Reducer Functions

You can write your own reducer for more nuanced merging logic. A reducer is any callable that takes two arguments—the existing value and the incoming update—and returns the merged result.

Custom state with multiple reducers

from typing import TypedDict, Annotated
import operator

def keep_max(current: int, update: int) -> int:
    """Always keep the larger value."""
    return max(current, update)

def deduplicated_add(current: list, update: list) -> list:
    """Append items, but skip duplicates."""
    seen = set(current)
    return current + [item for item in update if item not in seen]

def merge_dicts(current: dict, update: dict) -> dict:
    """Shallow-merge two dictionaries."""
    return {**current, **update}

class ResearchState(TypedDict):
    # Messages accumulate in order
    messages: Annotated[list, operator.add]
    # Sources are deduplicated as they arrive
    sources: Annotated[list, deduplicated_add]
    # Confidence tracks the highest score seen
    confidence: Annotated[int, keep_max]
    # Metadata merges across nodes
    metadata: Annotated[dict, merge_dicts]
    # Summary overwrites (no reducer)
    summary: str

In this schema, five fields use three different merge strategies. The sources list grows but never contains duplicates. The confidence score only ever goes up. The metadata dictionary accumulates keys from different nodes without clobbering earlier entries. Meanwhile, summary simply overwrites because the latest summary is the only one that matters.

Reducer Rule of Thumb

If a field accumulates data over the life of the graph (messages, tools called, sources found), it needs a reducer. If a field represents a single current value (the current step, a classification, a flag), let it overwrite. Getting this wrong is a common source of bugs: forgetting a reducer on a message list means every node’s messages replace the previous node’s messages instead of appending.

Short-Term Memory: Checkpointing

State carries data within a single invocation of the graph. But what about between invocations? If a user sends “My name is Alice” in one call to graph.invoke() and “What’s my name?” in a second call, state is rebuilt from scratch each time unless you add a checkpointer.

A checkpointer serializes the entire state at every super-step of the graph’s execution and stores it. When you invoke the graph again with the same thread_id, the checkpointer reloads the last saved state, and the conversation continues seamlessly.

MemorySaver: The In-Memory Checkpointer

For development and prototyping, LangGraph provides MemorySaver, an in-memory checkpointer that stores state in a Python dictionary. It is fast and requires no external dependencies, but it vanishes when the process exits.

MemorySaver checkpointing with thread_id

from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.checkpoint.memory import MemorySaver
from langchain_openai import ChatOpenAI

model = ChatOpenAI(model="gpt-4o-mini")

def chatbot(state: MessagesState):
    response = model.invoke(state["messages"])
    return {"messages": [response]}

# Build the graph
builder = StateGraph(MessagesState)
builder.add_node("chatbot", chatbot)
builder.add_edge(START, "chatbot")
builder.add_edge("chatbot", END)

# Compile with a checkpointer
checkpointer = MemorySaver()
graph = builder.compile(checkpointer=checkpointer)

# First invocation: introduce yourself
config = {"configurable": {"thread_id": "user-alice-001"}}
result = graph.invoke(
    {"messages": [{"role": "user", "content": "Hi, I'm Alice."}]},
    config=config,
)
print(result["messages"][-1].content)
# "Hello Alice! Nice to meet you."

# Second invocation: same thread_id, memory persists
result = graph.invoke(
    {"messages": [{"role": "user", "content": "What's my name?"}]},
    config=config,
)
print(result["messages"][-1].content)
# "Your name is Alice!"

# Different thread_id: a separate conversation
config_b = {"configurable": {"thread_id": "user-bob-002"}}
result = graph.invoke(
    {"messages": [{"role": "user", "content": "What's my name?"}]},
    config=config_b,
)
print(result["messages"][-1].content)
# "I don't know your name yet. What should I call you?"

The critical detail is thread_id. It acts as a namespace for checkpoints. Two calls with the same thread_id share state; two calls with different thread_id values are completely isolated. Think of each thread as a separate filing cabinet drawer: the checkpointer stores the graph’s full state in that drawer after each super-step, and pulls it back out at the start of the next invocation.

How Checkpoints Accumulate

Checkpoints are not just the “latest state.” The checkpointer stores a snapshot after every super-step within every invocation. This means you can rewind a conversation to any prior point—a feature called time travel that we’ll explore in a later chapter. For now, the important thing to understand is that checkpoints form a timeline.

Each checkpoint captures the complete state at that moment. When a new invocation arrives with the same thread_id, the checkpointer loads Checkpoint 4 (the most recent), merges in the new input using the state’s reducers, and the graph continues from there. The older checkpoints remain available for replay or debugging.

Production Checkpointers

MemorySaver is strictly for development. In production, you need checkpoints that survive process restarts. LangGraph offers several options:

  • SqliteSaver — stores checkpoints in a SQLite database file. Good for single-server deployments and local testing with persistence.
  • PostgresSaver — stores checkpoints in PostgreSQL. The right choice for multi-server deployments where multiple graph instances need to share checkpoint data.
  • Custom checkpointers — you can implement the BaseCheckpointSaver interface to store checkpoints in Redis, DynamoDB, or any other backend your infrastructure demands.

Swapping checkpointers is a one-line change. The graph doesn’t know or care where its state is stored:

Switching from MemorySaver to PostgresSaver

# Development
from langgraph.checkpoint.memory import MemorySaver
checkpointer = MemorySaver()

# Production
from langgraph.checkpoint.postgres import PostgresSaver
checkpointer = PostgresSaver.from_conn_string(
    "postgresql://user:pass@localhost:5432/langgraph"
)

# Either way, compile identically
graph = builder.compile(checkpointer=checkpointer)

Long-Term Memory: The Store

Checkpoints are scoped to a thread_id. If Alice chats in thread "alice-001" and then starts a new thread "alice-002", the second thread knows nothing about the first. This is by design—each thread is an independent conversation. But sometimes you need information that persists across threads: Alice’s preferred language, her account tier, the topics she frequently asks about. This is long-term memory, and LangGraph implements it through the Store.

State vs. Store: Know the Difference

State is per-thread. It lives inside checkpoints, is scoped to a single thread_id, and carries the data a conversation needs right now: the message history, the current step, intermediate results. Store is cross-thread. It lives outside any single conversation and holds data that should be available everywhere: user profiles, learned preferences, organizational knowledge. State is the notebook you bring to a meeting; Store is the filing cabinet back at the office.

Store Basics: Namespaces, Keys, Values

A Store is a key-value system organized by namespaces. A namespace is a tuple of strings that creates a hierarchy, similar to a file path. Within a namespace, you store items by key, and each item is a dictionary of arbitrary data.

Using a Store for cross-thread user profiles

from langgraph.store.memory import InMemoryStore

store = InMemoryStore()

# Save a user profile (accessible from any thread)
store.put(
    namespace=("users", "alice"),
    key="profile",
    value={
        "name": "Alice Chen",
        "preferred_language": "English",
        "account_tier": "premium",
    },
)

# Save learned preferences
store.put(
    namespace=("users", "alice", "preferences"),
    key="communication",
    value={
        "style": "concise",
        "likes_examples": True,
        "timezone": "US/Pacific",
    },
)

# Retrieve from any thread
profile = store.get(("users", "alice"), "profile")
print(profile.value["name"])  # "Alice Chen"

# List all items in a namespace
prefs = store.search(("users", "alice", "preferences"))
for item in prefs:
    print(item.key, item.value)

To use a Store inside a graph, pass it at compile time and access it from within your nodes. The store is available through the node’s config parameter or can be injected directly.

Accessing the Store from within graph nodes

from langgraph.store.memory import InMemoryStore
from langgraph.graph import StateGraph, MessagesState, START, END
from langgraph.checkpoint.memory import MemorySaver

store = InMemoryStore()
checkpointer = MemorySaver()

def chatbot(state: MessagesState, config: dict, *, store: InMemoryStore):
    user_id = config["configurable"]["user_id"]

    # Load user profile from the store
    profile = store.get(("users", user_id), "profile")
    context = ""
    if profile:
        context = f"User preferences: {profile.value}"

    # Use profile in the prompt
    messages = state["messages"]
    if context:
        messages = [{"role": "system", "content": context}] + messages

    response = model.invoke(messages)
    return {"messages": [response]}

builder = StateGraph(MessagesState)
builder.add_node("chatbot", chatbot)
builder.add_edge(START, "chatbot")
builder.add_edge("chatbot", END)

graph = builder.compile(checkpointer=checkpointer, store=store)

# Invoke with both thread_id and user_id
config = {"configurable": {
    "thread_id": "thread-789",
    "user_id": "alice",
}}
result = graph.invoke(
    {"messages": [{"role": "user", "content": "Hello!"}]},
    config=config,
)

This pattern separates concerns cleanly. The checkpointer handles the conversation’s message history (short-term, per-thread). The store handles the user’s identity and preferences (long-term, cross-thread). A node can read both, using the thread’s state for conversational context and the store for persistent knowledge about who it’s talking to.

Comparing Memory Types

The distinction between short-term and long-term memory matters for architecture decisions. Here is a side-by-side comparison.

Short-term vs. long-term memory in LangGraph
Aspect Short-Term (Checkpointer) Long-Term (Store)
Scope Per-thread (one conversation) Cross-thread (all conversations)
Keyed by thread_id Namespace tuple + key
Typical content Message history, intermediate results, current step User profiles, preferences, learned facts
Lifetime Lives as long as the thread is active Lives until explicitly deleted
Access pattern Automatic—loaded/saved by the checkpointer Explicit—nodes call store.get() / store.put()
Implementations MemorySaver, SqliteSaver, PostgresSaver InMemoryStore, custom Store backends
Metaphor Notepad on your desk during a meeting Filing cabinet in the office

Managing the Context Window with Summarization

There is a practical problem with accumulating messages forever: the context window is finite. A model with a 128K context window sounds generous, but a busy support conversation can reach that limit in a few hundred turns. Before that happens, you need a strategy for compressing older messages without losing the information they carry.

The most common approach is rolling summarization. When the message list grows past a threshold, you summarize the older messages into a compact paragraph, keep the most recent messages verbatim, and store the summary alongside the live messages in state.

Summarization pattern for long conversations

from typing import TypedDict, Annotated
import operator
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import MemorySaver
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage, SystemMessage

model = ChatOpenAI(model="gpt-4o-mini")
SUMMARY_THRESHOLD = 10  # Summarize when message count exceeds this
KEEP_RECENT = 4          # Always keep the N most recent messages

class ConversationState(TypedDict):
    messages: Annotated[list, operator.add]
    summary: str  # Rolling summary of older messages


def chatbot(state: ConversationState):
    """Generate a response, including the summary as context."""
    messages = state["messages"]
    summary = state.get("summary", "")

    # Prepend summary as a system message if one exists
    prompt_messages = []
    if summary:
        prompt_messages.append(
            SystemMessage(content=
                f"Summary of earlier conversation:\n{summary}"
            )
        )
    prompt_messages.extend(messages)

    response = model.invoke(prompt_messages)
    return {"messages": [response]}


def maybe_summarize(state: ConversationState):
    """If the message list is too long, summarize older messages."""
    messages = state["messages"]

    if len(messages) <= SUMMARY_THRESHOLD:
        return {}  # No changes needed

    # Split: older messages to summarize, recent to keep
    older = messages[:-KEEP_RECENT]
    recent = messages[-KEEP_RECENT:]

    # Build a summarization prompt
    existing_summary = state.get("summary", "")
    summary_prompt = "Summarize the following conversation."
    if existing_summary:
        summary_prompt += (
            f"\n\nPrevious summary:\n{existing_summary}"
            "\n\nExtend the summary with these new messages:"
        )

    summarize_messages = [
        HumanMessage(content=summary_prompt),
        *older,
        HumanMessage(content="Provide a concise summary."),
    ]
    summary_response = model.invoke(summarize_messages)

    # Return the trimmed messages and updated summary
    # We delete the old messages by returning only recent ones
    return {
        "summary": summary_response.content,
        "messages": recent,  # This overwrites via a special "delete + add" pattern
    }


def should_summarize(state: ConversationState):
    """Route to summarization if messages are getting long."""
    if len(state["messages"]) > SUMMARY_THRESHOLD:
        return "summarize"
    return "end"


# Build the graph
builder = StateGraph(ConversationState)
builder.add_node("chatbot", chatbot)
builder.add_node("summarize", maybe_summarize)
builder.add_edge(START, "chatbot")
builder.add_conditional_edges(
    "chatbot",
    should_summarize,
    {"summarize": "summarize", "end": END},
)
builder.add_edge("summarize", END)

checkpointer = MemorySaver()
graph = builder.compile(checkpointer=checkpointer)

Study the flow. After the chatbot generates its response, a conditional edge checks whether the message list has grown past the threshold. If it has, the maybe_summarize node takes the older messages, asks the model to summarize them, and returns only the recent messages plus the updated summary. On the next turn, the chatbot will see the summary as a system message followed by the recent messages—a much smaller payload that still captures the essential context.

Summarization Tradeoffs

Summarization introduces a small cost: an extra LLM call per summarization step, and the inherent lossy nature of compression. Specific details (exact numbers, verbatim quotes) may not survive summarization. Tune the threshold and the summarization prompt to balance cost against fidelity for your use case. Some applications keep a separate “key facts” list alongside the summary to preserve critical details that the summary might gloss over.

Alternative Trimming Strategies

Summarization is the most sophisticated approach, but simpler strategies sometimes suffice:

  • Truncation — simply drop messages beyond a fixed window. Fast and predictable, but loses all context from older messages. Works for stateless Q&A where earlier exchanges are rarely relevant.
  • Token-based trimming — count tokens instead of messages and trim from the front when the count exceeds a threshold. More precise than message-count trimming because a single message might be very long.
  • Hybrid — summarize messages older than N turns, but also drop messages older than M turns entirely. This caps both the summary’s staleness and the total token budget.

External Memory: Vector Stores and Databases

State and Store handle conversational memory—what happened in this or previous chats. But many applications need access to knowledge that didn’t originate in a conversation: product catalogs, documentation, policy documents, historical records. This is where external memory comes in.

The pattern is straightforward. A node in your graph queries an external system—a vector store, a SQL database, an API—and places the results into state for downstream nodes to use. This is the “retrieval” in Retrieval-Augmented Generation (RAG), and LangGraph makes it a first-class node in the graph rather than an implicit preprocessing step.

Connecting a vector store as external memory

from typing import TypedDict, Annotated
import operator
from langchain_openai import OpenAIEmbeddings
from langchain_chroma import Chroma
from langgraph.graph import StateGraph, START, END

# Initialize the vector store
embeddings = OpenAIEmbeddings()
vectorstore = Chroma(
    collection_name="product_docs",
    embedding_function=embeddings,
)
retriever = vectorstore.as_retriever(search_kwargs={"k": 3})

class RAGState(TypedDict):
    messages: Annotated[list, operator.add]
    retrieved_docs: list  # Overwrites each turn
    answer: str

def retrieve(state: RAGState):
    """Fetch relevant documents based on the latest user query."""
    last_message = state["messages"][-1]
    docs = retriever.invoke(last_message.content)
    return {"retrieved_docs": docs}

def generate(state: RAGState):
    """Generate a response using retrieved documents as context."""
    docs = state["retrieved_docs"]
    context = "\n\n".join(doc.page_content for doc in docs)
    messages = state["messages"]

    prompt = [
        {"role": "system", "content": f"Use this context:\n{context}"},
        *messages,
    ]
    response = model.invoke(prompt)
    return {"messages": [response], "answer": response.content}

builder = StateGraph(RAGState)
builder.add_node("retrieve", retrieve)
builder.add_node("generate", generate)
builder.add_edge(START, "retrieve")
builder.add_edge("retrieve", "generate")
builder.add_edge("generate", END)

graph = builder.compile()

Notice that retrieved_docs uses overwrite semantics (no reducer). Each turn replaces the previous set of documents with freshly retrieved ones. The message list, on the other hand, accumulates via operator.add. This is a typical pattern: ephemeral retrieval results overwrite, while the conversation history appends.

SQL Databases and APIs

The same pattern applies to any external data source. A node can query a SQL database, call a REST API, or read from a cache. The key insight is that the node’s job is to fetch data and place it into state; downstream nodes then use that data without knowing where it came from. This separation makes it easy to swap data sources without rewiring your graph.

A database-backed retrieval node

import sqlite3

def lookup_order(state: dict):
    """Fetch order details from a database."""
    order_id = state.get("order_id")
    if not order_id:
        return {"order_details": None}

    conn = sqlite3.connect("orders.db")
    cursor = conn.execute(
        "SELECT * FROM orders WHERE id = ?",
        (order_id,),
    )
    row = cursor.fetchone()
    conn.close()

    return {"order_details": dict(row) if row else None}
External Memory Is Not Checkpointed

Data fetched from external sources and placed into state is captured in checkpoints. But the external source itself is not managed by LangGraph. If the underlying database changes between invocations, the checkpointed state and the live database may disagree. Design your nodes to re-fetch when freshness matters, and rely on checkpointed data only when you need historical consistency.

Putting It All Together: A Memory Architecture

A production chatbot typically uses all three layers of memory simultaneously. Here is how they fit together:

  1. State (with reducers) carries the live data within each graph invocation: the current message list, tool call results, intermediate computations. Reducers control how node outputs merge.
  2. Checkpointer persists state between invocations for the same thread. Swap MemorySaver for PostgresSaver when you go to production.
  3. Store holds cross-thread knowledge: user profiles, preferences, organizational facts. Nodes explicitly read from and write to the store.
  4. External memory (vector stores, databases, APIs) provides domain knowledge that didn’t originate in conversations. Nodes fetch this data on demand and place it into state.
  5. Summarization keeps the message list from growing unbounded. Older messages are compressed into a summary that preserves essential context without consuming the entire context window.

Each layer operates at a different scope and timescale. State is per-invocation. Checkpoints span invocations within a thread. The store spans threads. External memory spans the entire application. The summarization pattern bridges between state and the context window, ensuring that long-running conversations remain practical.

Design Principle: Start Simple

You do not need all five layers from day one. Start with state and a checkpointer. Add a store when you have a clear cross-thread use case (like user profiles). Add external memory when you need RAG. Add summarization when conversations actually grow long enough to hit context limits. Each layer is independent and can be added without restructuring the others.

Advanced Patterns

Separate Input and Output Schemas

Sometimes you want to expose a clean API: the caller sends in a specific shape, and the graph returns a different shape, while internally the state carries additional fields that neither the caller nor the consumer should see. LangGraph supports this with separate input and output schemas.

Input, output, and internal state schemas

class InputState(TypedDict):
    question: str

class OutputState(TypedDict):
    answer: str
    sources: list[str]

class InternalState(InputState, OutputState):
    # Fields only used inside the graph
    retrieved_docs: list
    search_queries: Annotated[list, operator.add]
    confidence: float

builder = StateGraph(
    InternalState,
    input=InputState,
    output=OutputState,
)

The caller sends {"question": "..."}. The graph returns {"answer": "...", "sources": [...]}. Internally, the graph can use retrieved_docs, search_queries, and confidence freely. This is especially useful when your graph is deployed as a service and you want a stable API that doesn’t leak implementation details.

Private State Between Nodes

A related pattern uses typed node inputs to pass data directly between two nodes without it appearing in the global state. This is useful when an intermediate value is needed by exactly one downstream node and cluttering global state with it would be confusing. Consult the LangGraph documentation for the Command pattern, which enables this kind of targeted state passing.

Token-Aware Message Trimming

LangChain provides a trim_messages utility that can be used inside a node to cap the token count before calling the model. This is lighter-weight than full summarization and can be combined with it: trim to stay within the context window, but also summarize periodically so that the trimmed messages don’t lose too much context.

Token-aware trimming before model calls

from langchain_core.messages import trim_messages

def chatbot(state: ConversationState):
    messages = state["messages"]

    # Trim to fit within the model's context window
    trimmed = trim_messages(
        messages,
        max_tokens=4000,
        strategy="last",  # Keep the most recent messages
        token_counter=model,
    )

    response = model.invoke(trimmed)
    return {"messages": [response]}

Common Mistakes and How to Avoid Them

Memory in LangGraph is conceptually simple but has a few sharp edges that are worth calling out explicitly.

  • Forgetting the reducer on a message list. Without Annotated[list, operator.add], each node’s messages replace the previous node’s messages. You end up with only the last node’s output. Always annotate accumulating fields.
  • Reusing thread IDs across unrelated conversations. If two different users share a thread_id, they share a conversation. Generate unique thread IDs per conversation, typically by combining a user identifier with a session or conversation identifier.
  • Using MemorySaver in production. It lives in-process memory. A server restart, a deployment, or a worker crash wipes all checkpoints. Switch to SqliteSaver or PostgresSaver before deploying.
  • Storing large objects in state. Everything in state gets serialized into checkpoints. Storing entire documents or large binary data in state inflates checkpoint size and slows down serialization. Keep state lean; store bulky data externally and reference it by ID.
  • Confusing state and store. State is for this conversation. Store is for cross-conversation facts. Putting user preferences in state means they’re lost when the thread ends. Putting conversation-specific data in the store means it leaks into other threads.

What We Built

This chapter covered the entire memory stack in LangGraph. You learned to define state schemas with TypedDict or Pydantic, control how fields merge with reducers, persist conversations across invocations using checkpointers, share knowledge across threads with the Store, manage growing context windows through summarization, and connect external data sources as graph nodes. The central insight is that memory in LangGraph is not a single mechanism but a set of complementary layers, each operating at a different scope. State carries data through the current invocation. Checkpoints carry it across invocations. The Store carries it across threads. External memory reaches beyond conversations entirely.

With state and memory in place, your graphs can hold real conversations and remember what matters. In the next chapter, we turn to control flow patterns—conditional edges, branching, parallel execution, and the routing logic that lets a graph make decisions about what to do next.
