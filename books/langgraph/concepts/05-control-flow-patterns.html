05 Branching, looping, and pausing

Control Flow Patterns

A straight pipeline gets you surprisingly far—until the first time your agent needs to choose between two paths, retry a failed API call, or wait for a human to say “go ahead.” At that point you need real control flow: branches that pick a direction at runtime, loops that circle back to fix mistakes, and pauses that hold the graph mid-stride until someone reviews the work. This chapter hands you those tools one at a time, with code you can run after each section.

Conditional Routing and Branching

When a node finishes its work, the default behaviour is to follow its single outgoing edge to the next node. But many workflows need a fork in the road. A customer message might be a complaint, a billing question, or a feature request—and each one should flow to a different handler. LangGraph solves this with conditional edges: edges whose destination is decided at runtime by a plain Python function you write.

The add_conditional_edges API

The method signature looks like this: you give it a source node name, a path function that inspects the current state and returns a string key, and (optionally) a dictionary that maps those keys to node names. If you omit the dictionary, LangGraph assumes the returned string is the node name itself.

Signature of add_conditional_edges

# source:   the node whose output triggers the decision
# path_fn:  a callable (state) -> str
# path_map: optional dict mapping return values to node names

graph.add_conditional_edges(
    "classify",        # source node
    route_by_category,   # path function
    {                    # path map
        "billing":   "handle_billing",
        "complaint": "handle_complaint",
        "general":   "handle_general",
    }
)

The path function receives the full state dictionary (or your typed state object) and must return one of the keys in the path map. If it returns something not in the map, LangGraph raises an error at runtime—loud and early, which is what you want. Notice that the path function is a pure function of state. It doesn’t call an LLM or do I/O; it simply reads fields that an upstream node has already set.

Code Example: Routing by Classification

Let’s build a small support-ticket router. A classify node calls an LLM to label the ticket, then a conditional edge sends it to the right handler.

Conditional routing based on ticket classification

from typing import TypedDict, Literal
from langgraph.graph import StateGraph, END
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini")

class TicketState(TypedDict):
    message: str
    category: str
    response: str

def classify(state: TicketState) -> dict:
    """Ask the LLM to label the ticket."""
    result = llm.invoke(
        f"Classify this support ticket into exactly one word — "
        f"billing, complaint, or general:\n\n{state['message']}"
    )
    return {"category": result.content.strip().lower()}

def handle_billing(state: TicketState) -> dict:
    return {"response": "Routing to billing team..."}

def handle_complaint(state: TicketState) -> dict:
    return {"response": "Escalating complaint to supervisor..."}

def handle_general(state: TicketState) -> dict:
    return {"response": "Sending to FAQ bot..."}

# --- Build the graph ---
builder = StateGraph(TicketState)

builder.add_node("classify", classify)
builder.add_node("handle_billing", handle_billing)
builder.add_node("handle_complaint", handle_complaint)
builder.add_node("handle_general", handle_general)

builder.set_entry_point("classify")

# The path function reads state["category"]
def route_ticket(state: TicketState) -> str:
    return state["category"]

builder.add_conditional_edges(
    "classify",
    route_ticket,
    {
        "billing":   "handle_billing",
        "complaint": "handle_complaint",
        "general":   "handle_general",
    }
)

# Every handler leads to END
builder.add_edge("handle_billing", END)
builder.add_edge("handle_complaint", END)
builder.add_edge("handle_general", END)

graph = builder.compile()

# Run it
result = graph.invoke({"message": "I was double-charged last month"})
print(result["category"])   # "billing"
print(result["response"])  # "Routing to billing team..."

Notice the pattern: the classify node writes a category field into state, and the path function simply reads it back. The LLM call and the routing decision live in separate functions. This keeps each piece testable—you can unit-test route_ticket without calling any model.

Multiple Conditional Branches (Fan-Out)

Sometimes you want a single node to dispatch work to several nodes in parallel. LangGraph supports this: if your path function returns a list of strings instead of a single string, the graph will fan out to all of them simultaneously. Each target node receives the same state snapshot, runs independently, and their state updates are merged when they all finish.

Fan-out to multiple nodes

def route_multi(state):
    """Send to multiple handlers at once."""
    targets = []
    if state["needs_summary"]:
        targets.append("summarize")
    if state["needs_translation"]:
        targets.append("translate")
    return targets  # list triggers parallel execution

builder.add_conditional_edges("triage", route_multi)

Fan-out is powerful but requires care: if two parallel branches update the same state key, the last write wins (or you’ll need a reducer, as discussed in Chapter 4). Plan your state schema so parallel branches write to different fields whenever possible.

Loops and Retries

Graphs are not trees. LangGraph lets you create cycles—node A can route back to node B, which routes back to node A. This is essential for agents that check their own work and try again when the result isn’t good enough. The key safety rule: every loop must have an exit condition, or you’ll spin forever.

Creating Cycles in the Graph

A cycle is just an edge that points “backwards” relative to entry. You build it the same way you build any edge—the only difference is that you pair it with a conditional edge that eventually breaks out of the loop.

Basic cycle pattern

# generate produces a draft, evaluate scores it
builder.add_edge("generate", "evaluate")

# evaluate either accepts (goes to END) or loops back
builder.add_conditional_edges(
    "evaluate",
    lambda s: "accept" if s["score"] >= 0.8 else "retry",
    {"accept": END, "retry": "generate"}
)

This will loop as long as the score stays below 0.8. But what if the model never produces a good enough draft? You need a counter.

Code Example: Retry Loop with Max Attempts

The pattern below shows a self-correcting loop with a hard limit. The attempts counter lives in state, increments on each pass, and the conditional edge checks it before routing back.

Retry loop with max attempts

from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, END
import operator

class CodeState(TypedDict):
    task: str
    code: str
    errors: str
    attempts: int
    passed: bool

MAX_RETRIES = 3

def write_code(state: CodeState) -> dict:
    """Generate or revise code based on task and any prior errors."""
    if state.get("errors"):
        prompt = (
            f"Fix this code:\n{state['code']}\n\n"
            f"Errors:\n{state['errors']}"
        )
    else:
        prompt = f"Write Python code for: {state['task']}"
    code = llm.invoke(prompt).content
    return {
        "code": code,
        "attempts": state.get("attempts", 0) + 1,
    }

def run_tests(state: CodeState) -> dict:
    """Execute the code and capture errors (simplified)."""
    try:
        exec(state["code"])
        return {"passed": True, "errors": ""}
    except Exception as e:
        return {"passed": False, "errors": str(e)}

def decide_next(state: CodeState) -> str:
    """Pass if tests pass or we've exhausted retries."""
    if state["passed"]:
        return "done"
    if state["attempts"] >= MAX_RETRIES:
        return "give_up"
    return "retry"

# Build
builder = StateGraph(CodeState)
builder.add_node("write_code", write_code)
builder.add_node("run_tests", run_tests)
builder.set_entry_point("write_code")

builder.add_edge("write_code", "run_tests")
builder.add_conditional_edges(
    "run_tests",
    decide_next,
    {
        "done":    END,
        "give_up": END,
        "retry":   "write_code",  # <-- the cycle
    }
)

graph = builder.compile()
result = graph.invoke({"task": "Write a function that reverses a string"})
print(f"Passed: {result['passed']}, Attempts: {result['attempts']}")

Three things to notice. First, the attempts counter is part of state—it survives across loop iterations because every checkpoint preserves it. Second, the decide_next function has three exits: success, failure after exhausting retries, and retry. Third, the cycle goes from run_tests back to write_code, not to itself. This gives the code-writing node a chance to read the errors and try a different approach each time.

Recursion limit

LangGraph enforces a default recursion limit of 25 steps per invocation. If your graph needs more loop iterations, pass {"recursion_limit": 50} (or whatever bound makes sense) as part of the config when you call graph.invoke(). This safety net catches infinite loops during development—always set it intentionally rather than removing it.

Human-in-the-Loop

Agents are useful precisely because they can act autonomously. But autonomy without oversight is risky. Sending an email, executing a trade, deleting a database record—these are actions where you probably want a human to glance at the plan before the graph carries it out. LangGraph gives you three mechanisms for pausing execution and handing control to a person: interrupt_before, interrupt_after, and the interrupt() function.

Compile-Time Interrupts: interrupt_before and interrupt_after

When you compile the graph, you can pass lists of node names where execution should pause. interrupt_before pauses before the named node runs—you get to inspect the state that would flow in. interrupt_after pauses after the node has run, so you can see what it produced before the graph moves on.

Compiling with interrupts

from langgraph.checkpoint.memory import MemorySaver

checkpointer = MemorySaver()

graph = builder.compile(
    checkpointer=checkpointer,
    interrupt_before=["send_email"],    # pause before sending
    interrupt_after=["draft_email"],     # pause after drafting
)

A checkpointer is required for interrupts. When the graph pauses, the entire state is saved to the checkpoint store. When the human approves, the graph resumes from that checkpoint. Without a checkpointer, there would be nothing to resume from. We covered checkpointers in Chapter 4; here we use the in-memory MemorySaver for simplicity.

Code Example: Human Approval Flow

Here’s a complete example: an agent drafts an email, pauses for human review, and then either sends or revises it.

Human-in-the-loop approval flow

from typing import TypedDict
from langgraph.graph import StateGraph, END
from langgraph.checkpoint.memory import MemorySaver

class EmailState(TypedDict):
    request: str
    draft: str
    approved: bool
    sent: bool

def draft_email(state: EmailState) -> dict:
    # In production, call an LLM here
    return {"draft": f"Dear customer, regarding: {state['request']}..."}

def send_email(state: EmailState) -> dict:
    # Actually send the email
    print(f"SENT: {state['draft']}")
    return {"sent": True}

builder = StateGraph(EmailState)
builder.add_node("draft_email", draft_email)
builder.add_node("send_email", send_email)
builder.set_entry_point("draft_email")
builder.add_edge("draft_email", "send_email")
builder.add_edge("send_email", END)

checkpointer = MemorySaver()
graph = builder.compile(
    checkpointer=checkpointer,
    interrupt_before=["send_email"],  # pause before sending
)

# --- First run: drafts email, then pauses ---
config = {"configurable": {"thread_id": "email-1"}}
result = graph.invoke({"request": "refund for order #42"}, config)

# At this point the graph is paused.
# Inspect what the draft node produced:
state = graph.get_state(config)
print("Draft:", state.values["draft"])
print("Next node:", state.next)  # ("send_email",)

# --- Human reviews and approves ---
# Option A: resume as-is (approve the draft)
result = graph.invoke(None, config)
print("Sent:", result["sent"])  # True

# Option B: modify the draft before resuming
# graph.update_state(config, {"draft": "Revised email body..."})
# result = graph.invoke(None, config)

The critical moments: after the first invoke, the graph has stopped just before send_email. The state includes the draft. We call get_state to read it and state.next to see where the graph will resume. When we’re satisfied, calling invoke(None, config) with the same config resumes from the checkpoint. Passing None as input means “continue with existing state”—but we could also call update_state first to change the draft before resuming.

The interrupt() Function for Dynamic Interrupts

Compile-time interrupts are declared once when you build the graph. But sometimes you only need to pause under certain conditions—say, when the amount exceeds a threshold. The interrupt() function lets you pause from inside a node, at runtime.

Using interrupt() inside a node

from langgraph.types import interrupt

def process_payment(state):
    amount = state["amount"]

    if amount > 1000:
        # Pause and send the amount to the client for approval.
        # When the client resumes, `response` holds their answer.
        response = interrupt({
            "question": f"Approve payment of ${amount}?",
            "amount": amount,
        })

        if response != "approved":
            return {"status": "rejected"}

    # proceed with payment
    return {"status": "completed"}

When interrupt() is called, the graph saves its state and returns the value you pass (the dictionary with the question and amount) to the client. The client—your application code, a web UI, a Slack bot—receives this value, presents it to the human, and then resumes the graph with the human’s answer. That answer becomes the return value of interrupt() inside the node, and execution continues from that exact point.

interrupt() vs interrupt_before / interrupt_after

Use interrupt_before and interrupt_after when you know at compile time that a specific node always needs human oversight. They are declared once and apply every time the graph runs. Use the interrupt() function when the decision to pause depends on runtime data—the node itself decides whether to stop. The interrupt() function also lets you send a structured value to the client and receive a response back, making it a two-way communication channel. Compile-time interrupts simply pause; to communicate, you read and modify state externally.

Breakpoints and State Editing

Human-in-the-loop is one use of pausing. But LangGraph’s checkpoint system enables something broader: the ability to inspect, modify, and even rewind state at any point in the graph’s execution. Think of it as a debugger for your agent’s thought process.

Inspecting State at Any Checkpoint

Every time a node completes, the checkpointer saves the full state. You can retrieve the current state—or any past state—using the graph API.

Reading current and historical state

config = {"configurable": {"thread_id": "debug-session-1"}}

# Get the latest state
current = graph.get_state(config)
print("Values:", current.values)
print("Next:", current.next)          # which node runs next
print("Config:", current.config)        # includes checkpoint_id

# List all checkpoints (most recent first)
for snapshot in graph.get_state_history(config):
    print(
        snapshot.config["configurable"]["checkpoint_id"],
        snapshot.next,
        snapshot.values.get("attempts", 0),
    )

The get_state_history method returns a generator of StateSnapshot objects, one per checkpoint, newest first. Each snapshot includes the state values at that point, the next node(s) that would run, and the checkpoint’s unique ID. This gives you a complete audit trail of the graph’s execution.

Modifying State Before Resuming

When the graph is paused—whether by an interrupt or because you’re debugging—you can change the state before letting it continue. The update_state method writes new values into the current checkpoint.

Editing state with update_state

# The graph paused before "send_email" and the draft has a typo.
# Fix it before resuming.
graph.update_state(
    config,
    {"draft": "Dear customer, we have processed your refund for order #42."}
)

# Resume from the corrected state
result = graph.invoke(None, config)

An important subtlety: update_state creates a new checkpoint with your modifications. It doesn’t overwrite the old one. This means you can always go back to the pre-modification state if needed. The values you pass are merged into the existing state using the same reducers defined in your state schema.

You can also pass an as_node parameter to update_state. This tells LangGraph to treat the update as if a specific node produced it, which matters for determining which node runs next.

Updating state as a specific node

# Pretend the "draft_email" node produced this revised draft
graph.update_state(
    config,
    {"draft": "Revised draft..."},
    as_node="draft_email",
)

# Now the graph thinks draft_email just ran,
# so "send_email" is next.

Time-Travel Debugging

Because every step is checkpointed, you can rewind to any previous point and replay from there—potentially with modified state. This is “time travel” debugging, and it is remarkably useful when an agent goes off the rails three steps into a long chain.

Rewinding and replaying from an earlier checkpoint

# Find the checkpoint where things went wrong
for snapshot in graph.get_state_history(config):
    if snapshot.values.get("attempts") == 1:
        # This is the state after the first attempt
        old_config = snapshot.config
        break

# Option 1: Resume from that exact checkpoint
result = graph.invoke(None, old_config)

# Option 2: Modify state, then resume
graph.update_state(
    old_config,
    {"code": "def reverse(s): return s[::-1]"},  # inject a fix
)
result = graph.invoke(None, old_config)

The workflow for time-travel debugging is straightforward: list checkpoints with get_state_history, find the one you want, and either resume from it directly or modify it first with update_state. Each replay forks the checkpoint history—it doesn’t overwrite the original timeline. You can try multiple fixes from the same starting point without losing any history.

Checkpointer in production

MemorySaver is fine for development and tests. In production, use a persistent checkpointer like SqliteSaver or PostgresSaver from the langgraph-checkpoint-sqlite or langgraph-checkpoint-postgres packages. Without persistence, all checkpoints vanish when the process restarts—and with them, any paused human-in-the-loop flows.

Control Flow Patterns at a Glance

The table below collects the patterns from this chapter into a quick reference. Each row tells you what problem the pattern solves and points to the API you’d reach for.

Control flow patterns and when to use each
Pattern Key API When to Use Example
Conditional routing add_conditional_edges(src, fn, map) A node’s output determines which node runs next Classify a ticket, then route to the right handler
Fan-out (parallel branches) add_conditional_edges with path function returning a list A single decision dispatches work to multiple nodes in parallel Run summarization and translation simultaneously
Retry loop Conditional edge back to an earlier node An agent needs to check its work and try again on failure Generate code, run tests, loop back if tests fail
Compile-time interrupt compile(interrupt_before=[...], interrupt_after=[...]) A node always needs human approval before or after running Pause before sending an email every time
Dynamic interrupt interrupt(value) inside a node Pausing depends on runtime conditions; you need two-way communication Ask for approval only when payment exceeds $1,000
State editing graph.update_state(config, values) Correct or override agent state before resuming Fix a typo in a draft during a human review pause
Time-travel replay graph.get_state_history(config) + replay from checkpoint Debug a past decision or try a different path from an earlier state Rewind to attempt #1 and inject a correct answer

Composing Patterns Together

In practice, you rarely use just one of these patterns. A production agent might branch based on a classifier, loop within one branch to refine its output, and pause for human approval before taking an irreversible action. The beauty of LangGraph’s approach is that these patterns compose cleanly: conditional edges, cycles, and interrupts are all just graph primitives. You mix them by adding the right edges and passing the right compile options.

Consider the complaint branch from our earlier diagram. In a real system, you’d want the agent to draft a response, review it for quality (looping if it’s poor), and then pause for a human supervisor to approve the final version before sending it. That’s a conditional branch into a retry loop into a human-in-the-loop interrupt—three patterns stacked together, each doing its job.

Three patterns composed: branch, loop, and interrupt

# After classification routes to "handle_complaint"...

def draft_response(state):
    # LLM drafts a response to the complaint
    draft = llm.invoke(f"Write an empathetic response: {state['message']}")
    return {
        "draft": draft.content,
        "draft_attempts": state.get("draft_attempts", 0) + 1,
    }

def check_quality(state):
    # LLM scores the draft
    score = llm.invoke(f"Rate 0-10: {state['draft']}")
    return {"quality_score": int(score.content.strip())}

def quality_gate(state):
    if state["quality_score"] >= 7:
        return "approve"
    if state["draft_attempts"] >= 3:
        return "approve"   # best effort after 3 tries
    return "retry"

def send_response(state):
    # Actually send the response
    return {"sent": True}

# Wire it up
builder.add_node("draft_response", draft_response)
builder.add_node("check_quality", check_quality)
builder.add_node("send_response", send_response)

builder.add_edge("handle_complaint", "draft_response")
builder.add_edge("draft_response", "check_quality")
builder.add_conditional_edges(
    "check_quality",
    quality_gate,
    {"approve": "send_response", "retry": "draft_response"}
)
builder.add_edge("send_response", END)

# Compile with interrupt before the risky action
graph = builder.compile(
    checkpointer=checkpointer,
    interrupt_before=["send_response"],
)

The flow: classify routes the complaint to handle_complaint, which hands off to draft_response. The draft is scored by check_quality, and if the score is below 7, the graph loops back for another attempt (up to three times). Once the draft passes or retries are exhausted, the graph moves to send_response—but because we compiled with interrupt_before=["send_response"], it pauses there. A human reviewer inspects the draft, optionally edits it with update_state, and then resumes.

Practical Tips

Cover Every Path

If your path function can return a value that isn’t in the path map, LangGraph will raise a ValueError at runtime. This is good—it fails fast. But you should still add a fallback or default path. A common pattern is to include a "__default__" key or catch-all node that handles unexpected classifications gracefully.

Always Use Loop Counters

Even if you believe your exit condition will eventually trigger, add a counter and a maximum. LLMs are stochastic—what works 99% of the time will fail on the 100th run. A counter in state plus a check in your conditional edge is cheap insurance.

Design the Interrupt Experience

When using interrupt(), think about what you send to the client. The value you pass becomes what the human sees. Make it actionable: include the draft text, the proposed action, the amount, the risk level. The more context you provide, the faster the human can decide. Similarly, define clearly what the expected response format is—a boolean, a string like "approved", or a freeform edit.

Save Checkpoint IDs for Critical Points

If you know you might need to rewind to a specific moment—say, right after initial classification—save that checkpoint’s ID. You can extract it from graph.get_state(config).config["configurable"]["checkpoint_id"]. Having it on hand lets you rewind directly instead of scanning through history.

Streaming and interrupts

When using graph.stream() instead of invoke(), an interrupt causes the stream to end. You still resume the same way: call stream(None, config) or invoke(None, config). The checkpoint doesn’t care whether the original run used streaming or not.

What You’ve Learned

Control flow is what turns a static pipeline into an adaptive agent. You now have four tools in your belt: conditional edges that pick a path at runtime, cycles that let agents retry and self-correct, interrupts that pause for human judgement, and state editing that lets you rewrite history and replay from any point. These patterns compose freely—a single graph can branch, loop, pause, and resume as the situation demands.

With control flow handled, you’re ready to scale up. In the next chapter, we move from single graphs to multi-agent systems—graphs that contain other graphs, agents that delegate to specialists, and patterns for coordinating teams of autonomous workers.
