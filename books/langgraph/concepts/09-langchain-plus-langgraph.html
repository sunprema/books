Appendix: LangChain + LangGraph Together

You’ve spent this entire book learning how to think in graphs—nodes, edges, state, cycles. Along the way, you may have noticed LangChain lurking quietly inside many of our examples: a chat model here, a tool binding there. That wasn’t an accident. LangGraph was born from the LangChain ecosystem, and the two frameworks were designed to work together. The question isn’t whether to use one or the other. It’s where each one belongs in the stack.

Think of it this way. If you’re building a workshop, LangChain is the set of precision tools on your bench—the drill, the saw, the measuring tape. LangGraph is the blueprint that tells you the order of operations, what happens when a measurement is off, and how to loop back and try again. Neither replaces the other. This appendix shows you exactly how they fit together, with real code you can adapt for production.

LangChain Loaders with LangGraph Orchestration

One of LangChain’s greatest strengths is its library of document loaders. There are loaders for PDFs, web pages, databases, CSV files, Notion exports, Google Drive, and dozens more. Each one knows how to fetch raw content from a specific source and normalize it into a Document object with page_content and metadata. That’s a genuinely useful abstraction.

The pain shows up when you need to orchestrate multiple loaders, handle failures gracefully, or route documents through different processing paths based on their content. A linear chain can’t express “if the PDF fails to load, try the cached version; if neither works, flag for human review.” A graph can.

Document Loaders Feeding into Graph Nodes

The pattern is simple: wrap a LangChain loader inside a LangGraph node function. The node receives state, calls the loader, and writes the results back into state. The graph handles the flow.

A graph node that loads web pages using LangChain’s WebBaseLoader:

from langchain_community.document_loaders import WebBaseLoader
from langgraph.graph import StateGraph
from typing import TypedDict, Annotated
import operator

class IngestState(TypedDict):
    urls: list[str]
    documents: Annotated[list, operator.add]
    errors: Annotated[list[str], operator.add]

def load_web_documents(state: IngestState) -> dict:
    """Load documents from URLs using LangChain's WebBaseLoader."""
    docs = []
    errors = []
    for url in state["urls"]:
        try:
            loader = WebBaseLoader(url)
            docs.extend(loader.load())
        except Exception as e:
            errors.append(f"Failed to load {url}: {e}")
    return {"documents": docs, "errors": errors}

Notice what happened. The LangChain loader does the I/O—it knows how to fetch and parse a web page. The LangGraph node handles the error collection and state management. Each framework does what it’s best at.

Text Splitters for Chunking Within a Pipeline

Raw documents are rarely ready for an LLM. They need to be split into chunks that fit within context windows and that carry enough meaning to be useful in retrieval. LangChain’s text splitters handle this with battle-tested logic for overlap, separator detection, and size constraints.

Adding a chunking node that uses LangChain’s RecursiveCharacterTextSplitter:

from langchain_text_splitters import RecursiveCharacterTextSplitter

def chunk_documents(state: IngestState) -> dict:
    """Split documents into retrieval-sized chunks."""
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=1000,
        chunk_overlap=200,
        separators=["\n\n", "\n", ". ", " "]
    )
    chunks = splitter.split_documents(state["documents"])
    return {"documents": chunks}

# Wire it into the graph
graph = StateGraph(IngestState)
graph.add_node("load", load_web_documents)
graph.add_node("chunk", chunk_documents)
graph.add_edge("load", "chunk")
graph.set_entry_point("load")
graph.set_finish_point("chunk")

pipeline = graph.compile()

By placing the splitter in its own node, you gain visibility. LangGraph’s tracing shows you how many chunks were produced, how long the splitting took, and what the state looked like before and after. If you later want to swap in a different splitting strategy—say, semantic chunking—you replace one node without touching the rest of the graph.

Vector Stores in LangGraph Workflows

Retrieval-Augmented Generation—RAG—is the most common pattern for grounding LLM responses in real data. The basic idea is straightforward: before the model answers a question, you search a vector store for relevant documents and include them in the prompt. But the “basic idea” gets complicated fast. What if the retrieved documents aren’t relevant enough? What if the answer requires multiple rounds of retrieval? What if you need to combine retrieval with tool calls? These are graph problems.

Retrieval Nodes That Query Vector Stores

A LangChain vector store exposes a .as_retriever() method that returns a Runnable—an object with an .invoke() method that takes a query string and returns documents. This interface maps cleanly onto a LangGraph node.

A retrieval node using FAISS:

from langchain_community.vectorstores import FAISS
from langchain_openai import OpenAIEmbeddings

# Build the vector store (typically done once during ingestion)
embeddings = OpenAIEmbeddings()
vectorstore = FAISS.from_documents(chunks, embeddings)
retriever = vectorstore.as_retriever(search_kwargs={"k": 4})

def retrieve(state: dict) -> dict:
    """Fetch relevant documents from the vector store."""
    question = state["question"]
    docs = retriever.invoke(question)
    return {"context": docs}

The retriever is a LangChain component. It knows how to embed a query, search the vector index, and return ranked documents. The graph node is a thin wrapper that pulls the question from state and pushes the results back. Clean separation.

RAG as a Graph Pattern

Here’s where LangGraph truly earns its place. A production RAG system isn’t a single retrieve-then-generate step. It’s a decision graph: retrieve documents, check relevance, maybe reformulate the query and retrieve again, generate an answer, check whether the answer is grounded in the sources, and either return it or loop back. Let’s build this.

Complete RAG pipeline as a LangGraph graph using LangChain retrievers:

from langchain_openai import ChatOpenAI
from langchain_community.vectorstores import FAISS
from langchain_openai import OpenAIEmbeddings
from langgraph.graph import StateGraph, END
from typing import TypedDict
from langchain_core.documents import Document

class RAGState(TypedDict):
    question: str
    context: list[Document]
    answer: str
    relevance_ok: bool
    retries: int

# LangChain components
embeddings = OpenAIEmbeddings()
vectorstore = FAISS.from_documents(documents, embeddings)
retriever = vectorstore.as_retriever(search_kwargs={"k": 4})
llm = ChatOpenAI(model="gpt-4o", temperature=0)

# Node: retrieve documents
def retrieve_docs(state: RAGState) -> dict:
    docs = retriever.invoke(state["question"])
    return {"context": docs}

# Node: check if retrieved docs are relevant
def check_relevance(state: RAGState) -> dict:
    docs_text = "\n".join(d.page_content for d in state["context"])
    prompt = (
        f"Question: {state['question']}\n\n"
        f"Documents:\n{docs_text}\n\n"
        "Are these documents relevant to the question? "
        "Answer only 'yes' or 'no'."
    )
    result = llm.invoke(prompt)
    is_relevant = "yes" in result.content.lower()
    return {"relevance_ok": is_relevant}

# Node: generate answer from context
def generate_answer(state: RAGState) -> dict:
    docs_text = "\n\n".join(d.page_content for d in state["context"])
    prompt = (
        "Answer the question based only on the context below.\n\n"
        f"Context:\n{docs_text}\n\n"
        f"Question: {state['question']}"
    )
    result = llm.invoke(prompt)
    return {"answer": result.content}

# Node: reformulate question for re-retrieval
def reformulate(state: RAGState) -> dict:
    prompt = (
        f"The original question was: {state['question']}\n"
        "The retrieved documents were not relevant. "
        "Rephrase the question to improve retrieval."
    )
    result = llm.invoke(prompt)
    return {"question": result.content, "retries": state["retries"] + 1}

# Router: check relevance or give up
def route_on_relevance(state: RAGState) -> str:
    if state["relevance_ok"]:
        return "generate"
    if state["retries"] >= 2:
        return "generate"  # give up and answer anyway
    return "reformulate"

# Build the graph
graph = StateGraph(RAGState)
graph.add_node("retrieve", retrieve_docs)
graph.add_node("check", check_relevance)
graph.add_node("generate", generate_answer)
graph.add_node("reformulate", reformulate)

graph.set_entry_point("retrieve")
graph.add_edge("retrieve", "check")
graph.add_conditional_edges("check", route_on_relevance, {
    "generate": "generate",
    "reformulate": "reformulate",
})
graph.add_edge("reformulate", "retrieve")  # cycle back
graph.add_edge("generate", END)

rag_app = graph.compile()

# Run it
result = rag_app.invoke({
    "question": "How does FAISS handle high-dimensional vectors?",
    "context": [],
    "answer": "",
    "relevance_ok": False,
    "retries": 0,
})
print(result["answer"])

Study this graph. It has a cycle—reformulate loops back to retrieve. It has a conditional exit—after two failed retrievals, it gives up and generates anyway. It has clear separation of concerns—each node does one thing. This is the kind of control flow that a simple chain cannot express but that a graph handles naturally.

Combining Retrieval with Tool Calling

In more advanced architectures, retrieval is just one of several tools available to an agent. The LLM decides when to search the vector store, when to call an API, and when to answer directly. LangChain’s tool-binding interface makes this clean.

Making a retriever available as a tool:

from langchain_core.tools import tool

@tool
def search_knowledge_base(query: str) -> str:
    """Search the internal knowledge base for relevant information."""
    docs = retriever.invoke(query)
    return "\n\n".join(d.page_content for d in docs)

# Now use it in a ReAct agent
from langgraph.prebuilt import create_react_agent

agent = create_react_agent(
    model=ChatOpenAI(model="gpt-4o"),
    tools=[search_knowledge_base],
)

The @tool decorator is LangChain. The create_react_agent function is LangGraph. The retriever inside the tool is LangChain. The agent loop that decides when to call the tool is LangGraph. Each layer does its job.

LangChain Model Interfaces

One of LangChain’s most practical contributions is its unified interface for LLM providers. Whether you’re calling OpenAI, Anthropic, a local Ollama model, or a dozen other providers, the interface is the same: instantiate the model, call .invoke() with messages, get a response. This consistency is especially valuable in LangGraph, where you might want to swap providers without changing your graph logic.

Interchangeable LLM Providers

Each provider has its own package, but they all conform to the same BaseChatModel interface. This means you can pass any of them into the same graph node.

Using different LLM providers interchangeably in graph nodes:

from langchain_openai import ChatOpenAI
from langchain_anthropic import ChatAnthropic
from langchain_ollama import ChatOllama
from langgraph.graph import StateGraph, END
from typing import TypedDict
from langchain_core.messages import HumanMessage

# Three different providers, same interface
models = {
    "openai": ChatOpenAI(model="gpt-4o", temperature=0),
    "anthropic": ChatAnthropic(model="claude-sonnet-4-20250514", temperature=0),
    "local": ChatOllama(model="llama3", temperature=0),
}

class MultiModelState(TypedDict):
    query: str
    provider: str
    response: str

def call_llm(state: MultiModelState) -> dict:
    """Call whichever LLM provider the state specifies."""
    model = models[state["provider"]]
    messages = [HumanMessage(content=state["query"])]
    result = model.invoke(messages)
    return {"response": result.content}

# Build a simple graph
graph = StateGraph(MultiModelState)
graph.add_node("llm", call_llm)
graph.set_entry_point("llm")
graph.add_edge("llm", END)
app = graph.compile()

# Same graph, different providers
r1 = app.invoke({"query": "Explain RAG briefly.", "provider": "openai", "response": ""})
r2 = app.invoke({"query": "Explain RAG briefly.", "provider": "anthropic", "response": ""})
r3 = app.invoke({"query": "Explain RAG briefly.", "provider": "local", "response": ""})

The graph definition doesn’t change at all. The call_llm node picks the right model from a dictionary based on state. This is the kind of flexibility that comes from LangChain’s consistent interface, deployed within LangGraph’s state management.

Using bind_tools() for Tool Calling

When you call model.bind_tools(tools), LangChain attaches tool schemas to the model so the LLM knows what tools are available. The model can then return tool_calls in its response, which your graph can route and execute. This is the bridge between LangChain’s tool definitions and LangGraph’s execution loop.

Binding tools to a model for use in a graph:

from langchain_core.tools import tool
from langchain_openai import ChatOpenAI

@tool
def get_weather(city: str) -> str:
    """Get current weather for a city."""
    # In production, call a real weather API
    return f"Weather in {city}: 72°F, partly cloudy"

@tool
def search_docs(query: str) -> str:
    """Search internal documentation."""
    return f"Found 3 results for: {query}"

# Bind tools to the model
llm = ChatOpenAI(model="gpt-4o")
llm_with_tools = llm.bind_tools([get_weather, search_docs])

# Now llm_with_tools can return tool_calls in its responses
# LangGraph's ToolNode or create_react_agent handles execution

The key insight: bind_tools() doesn’t execute anything. It just tells the model what tools exist. LangGraph’s tool execution node (or the create_react_agent wrapper) handles actually calling the tools and feeding results back. LangChain defines. LangGraph executes.

Structured Output with .with_structured_output()

Sometimes you need the LLM to return data in a specific shape—not free-form text, but a Python object with typed fields. LangChain’s .with_structured_output() method handles the prompt engineering and parsing to make this reliable.

Using structured output in a graph node:

from pydantic import BaseModel, Field
from langchain_openai import ChatOpenAI

class Classification(BaseModel):
    """Classify user intent."""
    category: str = Field(description="One of: question, complaint, praise, request")
    urgency: int = Field(description="1-5, where 5 is most urgent")
    summary: str = Field(description="One-sentence summary")

llm = ChatOpenAI(model="gpt-4o")
classifier = llm.with_structured_output(Classification)

def classify_input(state: dict) -> dict:
    """Classify user input into structured categories."""
    result = classifier.invoke(state["user_message"])
    return {
        "category": result.category,
        "urgency": result.urgency,
        "summary": result.summary,
    }

This is powerful in a graph context. The structured output becomes part of the state, and conditional edges can route based on the classification—urgent complaints go to one path, casual questions go to another. LangChain guarantees the shape of the data. LangGraph uses that shape for routing decisions.

When to Combine Both in Production

If you’ve read this far, the pattern is probably becoming clear. But let’s make it explicit, because getting this wrong leads to either over-engineered pipelines or under-powered agents.

LangChain for Components

LangChain excels as a component library. It gives you battle-tested implementations of common building blocks: model interfaces, embedding functions, vector store connectors, document loaders, text splitters, output parsers, and tool definitions. These components have been used in thousands of production systems. Their edge cases are well-mapped. Their APIs are stable.

Reach for LangChain when you need:

  • A chat model with a standard interface (ChatOpenAI, ChatAnthropic, ChatOllama)
  • Embedding functions for vector similarity
  • Vector store connectors (FAISS, Chroma, Pinecone, Weaviate)
  • Document loaders for specific data sources
  • Text splitters with configurable chunking strategies
  • Tool definitions with the @tool decorator
  • Output parsers and structured output helpers

LangGraph for Orchestration

LangGraph excels at flow control. It gives you the ability to define how components interact: what runs first, what runs next, what happens when something fails, and when to loop back. It manages state across steps, supports human-in-the-loop patterns, and provides streaming, persistence, and observability out of the box.

Reach for LangGraph when you need:

  • Conditional branching based on LLM output
  • Cycles and retry loops
  • State management across multiple steps
  • Human-in-the-loop approval gates
  • Parallel execution of independent tasks
  • Streaming intermediate results
  • Persistence and resumption of long-running workflows
  • Step-level observability and debugging

The Recommended Architecture

The recommended architecture is simple: LangGraph at the top, LangChain components inside nodes. The graph defines the workflow. The nodes contain LangChain components that do the actual work. This gives you the best of both worlds—reliable components with flexible orchestration.

Key Insight

LangChain builds the parts. LangGraph wires the machine.

This is like how a factory works. The machines on the assembly line (LangChain components) are specialized—one drills, one welds, one paints. The conveyor system (LangGraph) decides which machine runs next, handles exceptions, and routes products through quality checks. You wouldn’t use the conveyor system to drill holes. You wouldn’t use the drill to route products.

What Stays in LangChain vs. What Moves to LangGraph

If you’re already using LangChain and considering a move to LangGraph, the transition doesn’t have to be all-or-nothing. Here’s a practical guide for what stays and what moves.

What Stays in LangChain

Keep using LangChain for individual components that do one thing well:

  • Model instantiation. ChatOpenAI(model="gpt-4o") is concise, well-tested, and handles authentication, retries, and rate limiting. No reason to rewrite it.
  • Tool definitions. The @tool decorator with docstring-based schema generation is genuinely useful. Keep it.
  • Retrievers and vector stores. LangChain’s retriever interface abstracts over many different vector store backends. This is a good abstraction.
  • Document loaders and splitters. These are utility components. They load data and chunk it. LangChain’s implementations are mature.
  • Embedding models. Same story—a clean interface over multiple providers.
  • Structured output. .with_structured_output() handles the messiness of coercing LLM output into typed objects.

What Moves to LangGraph

Move orchestration logic out of LangChain chains and into LangGraph graphs:

  • Sequential chains. If you’re using SequentialChain or the pipe operator (|) to string together multiple steps, consider whether you need conditional logic, error handling, or cycles. If you do, use a graph.
  • Agent loops. LangChain’s legacy AgentExecutor is superseded by LangGraph’s create_react_agent. The graph-based version gives you more control over the loop, better streaming, and persistence.
  • Routing logic. If your chain has RunnableBranch or complex conditional logic, a graph with conditional edges is more readable and debuggable.
  • Multi-step state. If you’re passing state through multiple chain steps using RunnablePassthrough or custom dictionaries, LangGraph’s typed state is cleaner.
  • Human-in-the-loop. LangGraph has built-in interrupt() support. Building this in plain LangChain requires manual checkpointing.
  • Error recovery. If a step fails and you need to retry with different parameters or fall back to a different strategy, that’s a graph pattern.
Migration Note

You don’t need to migrate all at once. Start by wrapping your existing LangChain chains in LangGraph nodes. Each node can contain a full LCEL chain internally. Over time, as you need more control, you can break the chain apart into separate nodes with edges between them. The graph grows organically from your needs, not from a rewrite mandate.

create_react_agent: Where Both Meet

If you’ve used create_react_agent from LangGraph’s prebuilt module, you’ve already been using both frameworks together without thinking about it. Let’s look under the hood.

What create_react_agent does internally:

from langgraph.prebuilt import create_react_agent
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool

@tool
def multiply(a: int, b: int) -> int:
    """Multiply two numbers."""
    return a * b

# This one line combines both frameworks:
# - ChatOpenAI (LangChain) provides the model interface
# - @tool (LangChain) defines the tool schema
# - create_react_agent (LangGraph) builds the graph:
#   - An "agent" node that calls the model
#   - A "tools" node that executes tool calls
#   - Conditional edges that loop until no more tools are needed
#   - State management for messages
agent = create_react_agent(
    model=ChatOpenAI(model="gpt-4o"),
    tools=[multiply],
)

Under the hood, create_react_agent calls model.bind_tools(tools)—a LangChain operation—and builds a StateGraph with two nodes and a conditional edge—a LangGraph operation. The Runnable interface that LangChain’s chat models implement is directly compatible with LangGraph’s node functions. There’s no adapter layer, no translation step. They were designed to fit together.

Production Patterns

Let’s close with some patterns you’ll encounter in real systems. These are common architectures that use both frameworks effectively.

Pattern 1: RAG Agent with Fallback

An agent that tries retrieval first, falls back to web search if the knowledge base doesn’t have the answer, and uses structured output for quality checks.

RAG agent with fallback search:

from langchain_openai import ChatOpenAI
from langchain_core.tools import tool
from langgraph.prebuilt import create_react_agent

@tool
def search_knowledge_base(query: str) -> str:
    """Search the internal knowledge base. Use this first."""
    docs = retriever.invoke(query)
    if not docs:
        return "No relevant documents found in knowledge base."
    return "\n\n".join(d.page_content for d in docs)

@tool
def web_search(query: str) -> str:
    """Search the web. Use when knowledge base has no answer."""
    # In production, call a search API
    return f"Web results for: {query}"

agent = create_react_agent(
    model=ChatOpenAI(model="gpt-4o"),
    tools=[search_knowledge_base, web_search],
    prompt="You are a research assistant. Always try the knowledge "
           "base first. Only use web search if the knowledge base "
           "does not have relevant information.",
)

Pattern 2: Multi-Model Pipeline

Different steps in a workflow might benefit from different models. Use a cheap, fast model for classification and a powerful model for generation.

Using different models for different stages:

from langchain_openai import ChatOpenAI
from langchain_anthropic import ChatAnthropic
from langgraph.graph import StateGraph, END
from pydantic import BaseModel, Field

# Fast model for triage
triage_model = ChatOpenAI(model="gpt-4o-mini", temperature=0)

# Powerful model for generation
writer_model = ChatAnthropic(
    model="claude-sonnet-4-20250514", temperature=0.7
)

class Triage(BaseModel):
    complexity: str = Field(description="simple or complex")

triage_classifier = triage_model.with_structured_output(Triage)

def triage_node(state: dict) -> dict:
    result = triage_classifier.invoke(state["question"])
    return {"complexity": result.complexity}

def simple_answer(state: dict) -> dict:
    result = triage_model.invoke(state["question"])
    return {"answer": result.content}

def complex_answer(state: dict) -> dict:
    result = writer_model.invoke(state["question"])
    return {"answer": result.content}

def route_by_complexity(state: dict) -> str:
    return "simple" if state["complexity"] == "simple" else "complex"

graph = StateGraph(dict)
graph.add_node("triage", triage_node)
graph.add_node("simple", simple_answer)
graph.add_node("complex", complex_answer)
graph.set_entry_point("triage")
graph.add_conditional_edges("triage", route_by_complexity, {
    "simple": "simple",
    "complex": "complex",
})
graph.add_edge("simple", END)
graph.add_edge("complex", END)

pipeline = graph.compile()

This is cost optimization through architecture. Simple questions get a fast, cheap answer. Complex questions get a thorough, expensive one. LangChain provides both model interfaces with the same API. LangGraph routes between them based on the triage result. The graph makes the cost tradeoff visible and configurable.

Pattern 3: Document Ingestion Pipeline

A full ingestion pipeline loads documents from multiple sources, chunks them, generates embeddings, and stores them in a vector database. Error handling at each stage is critical in production.

Ingestion pipeline with error handling:

from langchain_community.document_loaders import WebBaseLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_community.vectorstores import FAISS
from langchain_openai import OpenAIEmbeddings
from langgraph.graph import StateGraph, END

def load_documents(state: dict) -> dict:
    loader = WebBaseLoader(state["urls"])
    try:
        docs = loader.load()
        return {"documents": docs, "load_error": None}
    except Exception as e:
        return {"documents": [], "load_error": str(e)}

def chunk_documents(state: dict) -> dict:
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=1000, chunk_overlap=200
    )
    chunks = splitter.split_documents(state["documents"])
    return {"chunks": chunks}

def embed_and_store(state: dict) -> dict:
    embeddings = OpenAIEmbeddings()
    vectorstore = FAISS.from_documents(state["chunks"], embeddings)
    vectorstore.save_local("./faiss_index")
    return {"status": "stored", "chunk_count": len(state["chunks"])}

def check_load_result(state: dict) -> str:
    return "error" if state.get("load_error") else "chunk"

def handle_error(state: dict) -> dict:
    return {"status": f"Failed: {state['load_error']}"}

graph = StateGraph(dict)
graph.add_node("load", load_documents)
graph.add_node("chunk", chunk_documents)
graph.add_node("store", embed_and_store)
graph.add_node("error", handle_error)
graph.set_entry_point("load")
graph.add_conditional_edges("load", check_load_result, {
    "chunk": "chunk",
    "error": "error",
})
graph.add_edge("chunk", "store")
graph.add_edge("store", END)
graph.add_edge("error", END)

ingest = graph.compile()

Every component inside these nodes—the loader, the splitter, the embeddings, the vector store—is LangChain. The error handling, the routing, the step-by-step progression—that’s LangGraph. The separation means you can swap FAISS for Pinecone by changing one node. You can add a metadata enrichment step by adding one node and one edge. The pipeline grows without becoming fragile.

Common Pitfalls

A few mistakes come up often enough to be worth naming:

  1. Over-graphing. Not every LLM call needs a graph. If your workflow is truly linear—load, split, embed, store—with no branching or error recovery, a simple script or LCEL chain is fine. Add a graph when you need the control flow it provides.
  2. Under-graphing. The opposite mistake: building complex logic inside a single node when it should be multiple nodes with edges. If a node has three if statements and two try/except blocks, consider splitting it up. The graph should reflect the actual decision structure.
  3. Version mismatches. LangChain and LangGraph release independently. Check compatibility. The langchain-core package is the shared foundation—make sure all your langchain-* packages use the same version of it.
  4. State bloat. Don’t store full document objects in state if you only need their text. State is serialized for persistence and checkpointing. Keep it lean.
  5. Mixing old and new. LangChain’s legacy AgentExecutor and LangGraph’s create_react_agent are not meant to be used together. Pick one. The LangGraph version is the recommended path forward.
Watch Out

If you find yourself importing from langchain.agents (the old agent module) and langgraph.prebuilt in the same file, stop and pick one. The old agent framework and the new graph-based framework solve the same problem in different ways. Mixing them creates confusion, not capability.

Wrapping Up

Throughout this book, we’ve built agents from first principles. We started with the core graph abstraction—nodes, edges, state. We added conditional routing, cycles, tool use, memory, persistence, human-in-the-loop patterns, and streaming. We built a complete Q&A agent as a case study. And now, in this appendix, we’ve seen how the LangChain ecosystem provides the components that make LangGraph nodes powerful.

The principle is worth restating one more time: LangGraph controls the flow. LangChain provides the parts. Use LangGraph to define what happens when, in what order, under what conditions. Use LangChain to instantiate models, define tools, connect to vector stores, load documents, and parse outputs. The boundary between them is the node function’s signature—state in, state out.

This is not the only way to build AI applications. But it is a principled way—one that separates concerns, makes logic visible, and scales from a single LLM call to a multi-agent system with persistence and human oversight. You now have the tools and the patterns. Go build something that works.
