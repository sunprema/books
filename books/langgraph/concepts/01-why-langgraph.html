02 Nodes, edges, and state

Core Concepts

Before you can build anything useful with LangGraph, you need a shared vocabulary—a small set of interlocking parts whose behavior you can predict. This chapter hands you that vocabulary. By the end you’ll know exactly what a node does, how edges decide where execution goes next, why state travels through the graph instead of living inside any single node, and how reducers give you fine-grained control over how state updates merge together. Everything that follows in this book rests on these ideas, so we’ll take the time to get them right.

The Mental Model: A Workshop Assembly Line

Imagine a workshop where a single workpiece—a block of wood, say—moves along a series of stations. At each station, a craftsperson inspects the workpiece, performs one specific operation (cutting, sanding, staining), and sends it onward. The workpiece carries the accumulated results of every previous station. No craftsperson needs to know what happened upstream; they only need to look at the workpiece, do their job, and pass it along.

A LangGraph graph works the same way. The workpiece is state—a typed dictionary that flows through the graph. Each station is a node—a Python function that reads state, does work, and returns updates. The conveyor belts between stations are edges—some fixed, some switching dynamically based on what the workpiece looks like at that moment. That’s really all there is. Let’s look at each piece.

State: The Shared Workpiece

State is the single most important concept in LangGraph. It is the data structure that every node reads from and writes to. There is exactly one state object per graph execution, and it lives for the duration of that execution. You define its shape before you build the graph, typically using Python’s TypedDict or Pydantic’s BaseModel.

Defining state with TypedDict:

from typing import TypedDict

class AgentState(TypedDict):
    # The user’s original question
    query: str
    # The LLM’s generated response
    response: str
    # Whether the response passed a quality check
    approved: bool

Notice what’s happening here. We’re declaring three fields with explicit types. Every node in the graph will receive an instance of this AgentState and can read any field. When a node finishes its work, it returns a plain dictionary containing only the fields it wants to update—not the entire state. LangGraph merges that partial dictionary back into the full state automatically.

Key insight

Every node sees the full state, returns only what changed. A node that sets response doesn’t need to echo back query or approved. This keeps nodes focused: each one is responsible for exactly the fields it owns.

You can also define state with Pydantic if you want runtime validation:

Defining state with Pydantic BaseModel:

from pydantic import BaseModel

class AgentState(BaseModel):
    query: str = ""
    response: str = ""
    approved: bool = False

The Pydantic approach gives you default values and automatic type coercion. Use whichever feels right for your project; the graph doesn’t care which you choose. Throughout this book, we’ll mostly use TypedDict because it’s lighter and appears more frequently in the LangGraph documentation.

Nodes: The Workers

A node is a Python function. That’s it. No special base class, no decorator magic, no framework superstructure. A node takes the current state as its argument and returns a dictionary of updates. It can be synchronous or asynchronous—LangGraph handles both transparently.

A synchronous node function:

def generate_response(state: AgentState) -> dict:
    # Call an LLM (simplified for illustration)
    result = llm.invoke(state["query"])
    return {"response": result.content}

Look at what this function does. It reads state["query"] to get the input, calls an LLM, and returns a dictionary with a single key: "response". It doesn’t touch approved. It doesn’t return the full state. It returns only the delta—the part that changed.

An asynchronous node function:

async def check_quality(state: AgentState) -> dict:
    # Run a quality check on the response
    is_good = await quality_checker.acheck(
        query=state["query"],
        response=state["response"]
    )
    return {"approved": is_good}

This second node reads two fields (query and response) and writes one (approved). It doesn’t need to know which node set response—it just trusts that the field will be there by the time this node runs. The graph’s edges guarantee ordering.

Nodes can do anything a normal Python function can: call APIs, query databases, run sub-chains, perform computations, even invoke other LangGraph graphs. The only contract is the signature: take state in, return a dictionary out.

Node naming

When you register a node with add_node("generate", generate_response), the first argument is the node’s name in the graph. This name appears in logs, traces, and streaming output. Choose descriptive names—you’ll thank yourself when debugging at 2 a.m.

Edges: The Routing

Edges connect nodes. They answer the question: “After this node finishes, where does execution go next?” LangGraph provides two kinds of edges, and understanding the difference is crucial.

Normal Edges (Fixed Routing)

A normal edge is unconditional. After node A finishes, execution always goes to node B. No questions asked.

Adding a fixed edge:

graph.add_edge("generate", "check_quality")

This says: “When generate finishes, run check_quality.” Always. Every time. It’s the conveyor belt bolted to the floor.

Conditional Edges (Dynamic Routing)

This is where LangGraph gets interesting. A conditional edge inspects the current state and decides where to go based on what it finds. You provide a routing function that reads the state and returns a string indicating which node should run next.

Adding a conditional edge:

def route_after_check(state: AgentState) -> str:
    # If the quality check passed, we’re done
    if state["approved"]:
        return "end"
    # Otherwise, regenerate
    return "regenerate"

graph.add_conditional_edges(
    "check_quality",       # source node
    route_after_check,        # routing function
    {                         # path map: return value → node name
        "end": END,
        "regenerate": "generate",
    }
)

The add_conditional_edges method takes three arguments. First, the source node—the node whose output triggers the routing decision. Second, a function that examines state and returns a string. Third, a path map that translates those return strings into actual node names (or the special END constant).

This is how you build loops, retries, branching logic, and agent decision-making. The routing function is just Python, so you can use any logic you want: check a boolean, count iterations, compare scores, parse structured output from an LLM. The graph doesn’t prescribe what your decision logic looks like.

Watch out

The path map must cover every possible return value from your routing function. If route_after_check returns "regenerate" but the path map doesn’t include that key, LangGraph will raise an error at runtime. Be exhaustive.

START and END: Entry and Exit

Every graph needs to know where to begin and where to stop. LangGraph provides two special constants for this: START and END.

Importing the constants:

from langgraph.graph import StateGraph, START, END

START is a virtual node that represents the entry point of your graph. You connect it to your first real node with a normal edge: 

graph.add_edge(START, "generate")

END is a virtual node that signals completion. When execution reaches END, the graph stops and returns the final state. You can route to END from any edge: 

graph.add_edge("check_quality", END)
# or via a conditional edge as shown above

Think of START and END as the doors of the workshop. Work enters through START, passes through your nodes, and exits through END. A graph without an edge from START will never execute. A graph that never reaches END will run forever (or until your patience runs out).

Seeing the Whole Picture

Let’s put these pieces together visually. Here’s what a simple generate-and-check graph looks like, with state flowing through it:

Study this diagram. You can trace the flow: execution starts at START, moves to generate (which sets response), continues to check_quality (which sets approved), hits the conditional check, and either exits through END or loops back to generate for another attempt. The state object carries all accumulated values throughout.

StateGraph: The Builder

Now that you understand the individual pieces, let’s see how they come together. The StateGraph class is your builder. You create one, pass it your state type, add nodes and edges, then compile it into an executable graph.

A complete StateGraph definition:

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

# 1. Define state
class AgentState(TypedDict):
    query: str
    response: str
    approved: bool
    attempt_count: int

# 2. Define nodes
def generate(state: AgentState) -> dict:
    result = llm.invoke(state["query"])
    count = state.get("attempt_count", 0)
    return {
        "response": result.content,
        "attempt_count": count + 1,
    }

def check_quality(state: AgentState) -> dict:
    is_good = quality_checker.check(
        query=state["query"],
        response=state["response"],
    )
    return {"approved": is_good}

# 3. Define routing logic
def should_retry(state: AgentState) -> str:
    if state["approved"]:
        return "done"
    if state["attempt_count"] >= 3:
        return "done"  # give up after 3 tries
    return "retry"

# 4. Build the graph
graph = StateGraph(AgentState)

graph.add_node("generate", generate)
graph.add_node("check_quality", check_quality)

graph.add_edge(START, "generate")
graph.add_edge("generate", "check_quality")

graph.add_conditional_edges(
    "check_quality",
    should_retry,
    {"done": END, "retry": "generate"},
)

# 5. Compile
app = graph.compile()

Let’s walk through this step by step. First, we define the state shape with four fields. Second, we write two node functions—each takes AgentState and returns a partial dictionary. Third, we write a routing function that returns one of two strings. Fourth, we create a StateGraph instance, register our nodes and edges, and add a conditional edge with a path map. Fifth, we call compile() to produce the final executable.

The builder pattern—add_node, add_edge, add_conditional_edges, compile—is the API you’ll use every time you build a LangGraph application. It might feel ceremonial at first, but the explicitness pays off: you can look at any graph definition and understand the entire flow without running it.

Graph Compilation: From Blueprint to Machine

The .compile() call is where LangGraph validates your graph and transforms it into a CompiledStateGraph—an object that implements LangChain’s Runnable interface. This means you get a standard set of methods for execution:

  • invoke(input) — Run the graph synchronously, return the final state
  • ainvoke(input) — Run the graph asynchronously
  • stream(input) — Yield state updates as each node completes
  • astream(input) — Async streaming

Running a compiled graph:

# Synchronous execution
result = app.invoke({"query": "What is LangGraph?"})
print(result["response"])

# Streaming execution
for event in app.stream({"query": "What is LangGraph?"}):
    print(event)

During compilation, LangGraph checks that your graph is well-formed: every node referenced by an edge actually exists, there’s a path from START to at least one node, and all conditional edge path maps have valid targets. If anything is wrong, you get a clear error at compile time rather than a mysterious failure at runtime.

When does compilation happen?

Compilation is a one-time step. You build and compile the graph once, then call invoke() or stream() as many times as you want. Each invocation gets a fresh state object. The compiled graph itself is stateless and thread-safe.

Reducers: Controlling How State Merges

So far, every state update has been a simple replacement: if node A sets response to "Hello" and node B later sets response to "Goodbye", the final value is "Goodbye". The new value replaces the old one. This is the default behavior, and it works well for most fields.

But what about fields where you want to accumulate values? Imagine a list of messages in a conversation, or a list of tool calls, or a running log of decisions. You don’t want each node to replace the entire list—you want each node to append to it. That’s what reducers are for.

A reducer is a function that takes the current value of a field and a new value, and combines them. You declare reducers using Python’s Annotated type:

Defining state with reducers using Annotated:

import operator
from typing import Annotated, TypedDict

class ChatState(TypedDict):
    # Messages accumulate — each node appends, never replaces
    messages: Annotated[list[str], operator.add]
    # Summary is replaced — default behavior, no reducer needed
    summary: str
    # Tool calls accumulate too
    tool_calls: Annotated[list[dict], operator.add]
    # Turn counter uses a custom reducer
    turn_count: Annotated[int, lambda current, new: current + new]

The syntax Annotated[list[str], operator.add] says: “This field is a list of strings, and when a node returns an update for this field, concatenate the new list onto the existing one.” So if the current value is ["Hello"] and a node returns {"messages": ["How are you?"]}, the result is ["Hello", "How are you?"].

Nodes using accumulating state:

def user_input(state: ChatState) -> dict:
    # Append one message to the list
    return {"messages": ["User: What is the weather?"]}

def assistant_response(state: ChatState) -> dict:
    # Append another message — the existing ones are preserved
    return {
        "messages": ["Assistant: It’s sunny today!"],
        "turn_count": 1,  # adds 1 to existing count
    }

Without the reducer annotation, the second node’s return would replace the messages list entirely, wiping out the user’s input. With the reducer, each node contributes items to a growing list. This is the pattern that makes multi-turn chat, tool-calling agents, and ReAct loops possible in LangGraph.

Reducer behavior comparison
Field declaration Merge behavior Example
response: str Replace (default) Old: "A" → Update: "B" → Result: "B"
Annotated[list, operator.add] Concatenate lists Old: ["A"] → Update: ["B"] → Result: ["A", "B"]
Annotated[int, lambda a, b: a + b] Sum integers Old: 3 → Update: 1 → Result: 4
Annotated[set, lambda a, b: a | b] Union of sets Old: {"x"} → Update: {"y"} → Result: {"x", "y"}
Annotated[T, custom_fn] Your function decides Any logic: pick max, merge dicts, deduplicate, etc.

The key takeaway: without a reducer, the last write wins. With a reducer, you control exactly how concurrent or sequential updates combine. Choose the right reducer for each field, and your state management becomes trivially correct.

The messages pattern

The most common reducer in LangGraph applications is Annotated[list[BaseMessage], operator.add] for the messages field. LangGraph even provides a pre-built MessagesState class that includes this pattern. You’ll see it extensively starting in Chapter 3.

Channels: The Machinery Under the Hood

You may encounter the term “channels” in LangGraph documentation or error messages. Channels are the internal mechanism that manages state updates. Each field in your state type gets its own channel, and each channel knows its reducer (if any).

When a node returns {"response": "Hello"}, LangGraph doesn’t just do a dictionary merge. It routes the update to the response channel, which applies the appropriate reducer (default replace, or your custom function), validates the type, and stores the result. The next node that runs will see the updated value when it accesses state["response"].

You rarely interact with channels directly. They’re an implementation detail that you can safely ignore until you need to debug a tricky state update or build something unusual like a custom channel type. For now, just know they exist and that they’re the reason state updates are reliable and predictable.

Channels in practice

If you see an error message mentioning “channel” or “InvalidUpdateError,” it usually means a node returned a value for a state field with an incompatible type—for example, returning a string for a field that expects a list. The channel caught the mismatch before it could cause subtle bugs downstream.

The Builder API at a Glance

Let’s consolidate everything into a reference of the StateGraph methods you’ll use most often:

StateGraph builder methods
Method Signature Purpose
StateGraph(state_type) StateGraph(AgentState) Create a new graph builder with the given state schema
add_node (name: str, fn: Callable) Register a named node with its function
add_edge (from: str, to: str) Add a fixed (unconditional) edge between nodes
add_conditional_edges (source: str, path: Callable, path_map: dict) Add a dynamic routing edge with a path function and map
compile (**kwargs) -> CompiledStateGraph Validate and produce an executable graph

The compile method also accepts optional keyword arguments for advanced features like checkpointing (for persistence and time-travel) and interrupts (for human-in-the-loop workflows). We’ll cover these in later chapters. For now, a bare .compile() is all you need.

Putting It All Together

Let’s build one more example that uses everything from this chapter—state with reducers, multiple nodes, both edge types, and compilation:

A research assistant graph with accumulating results:

import operator
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph, START, END

class ResearchState(TypedDict):
    topic: str
    # Each source node appends its findings
    findings: Annotated[list[str], operator.add]
    # Final synthesized answer (replaced, not accumulated)
    answer: str
    # Count of sources consulted
    sources_checked: Annotated[int, lambda a, b: a + b]

def search_web(state: ResearchState) -> dict:
    # Simulate a web search
    return {
        "findings": [f"Web result for {state['topic']}"],
        "sources_checked": 1,
    }

def search_docs(state: ResearchState) -> dict:
    # Simulate searching internal documents
    return {
        "findings": [f"Doc result for {state['topic']}"],
        "sources_checked": 1,
    }

def synthesize(state: ResearchState) -> dict:
    all_findings = "\n".join(state["findings"])
    return {"answer": f"Based on {state['sources_checked']} sources: {all_findings}"}

# Build the graph
graph = StateGraph(ResearchState)

graph.add_node("search_web", search_web)
graph.add_node("search_docs", search_docs)
graph.add_node("synthesize", synthesize)

# Fan out from START to both search nodes
graph.add_edge(START, "search_web")
graph.add_edge(START, "search_docs")

# Both feed into synthesize
graph.add_edge("search_web", "synthesize")
graph.add_edge("search_docs", "synthesize")

# Synthesize leads to END
graph.add_edge("synthesize", END)

app = graph.compile()

# Run it
result = app.invoke({"topic": "quantum computing"})
print(result["answer"])
# sources_checked will be 2 (1 + 1 via the reducer)
# findings will have 2 items (concatenated via operator.add)

This example shows something new: fan-out. Both search_web and search_docs have edges from START, so LangGraph runs them in parallel. Both nodes append to the findings list and add 1 to sources_checked. The synthesize node waits until both search nodes finish, then sees the combined state. The reducers make this work without either search node needing to know about the other.

Parallelism through structure

When multiple nodes share the same upstream edge, LangGraph runs them concurrently. You don’t write threading code or manage async coordination—the graph structure implies the parallelism, and reducers handle the merging. This is one of LangGraph’s most powerful patterns.

How State Actually Flows

Let’s trace through a single invocation to make the state lifecycle concrete. When you call app.invoke({"topic": "quantum computing"}), here’s what happens internally:

  1. Initialization. LangGraph creates a state object from your input: {"topic": "quantum computing", "findings": [], "answer": "", "sources_checked": 0}. Fields you didn’t provide get default values based on their type.
  2. START resolves. The graph looks at edges from START, finds two targets (search_web and search_docs), and schedules both.
  3. Parallel execution. Both search nodes run concurrently. Each receives the same state snapshot. Each returns a partial update.
  4. Reducer merge. LangGraph applies both updates through the channels. findings gets both items concatenated (via operator.add). sources_checked gets 0 + 1 + 1 = 2 (via the lambda reducer). These merges are deterministic and conflict-free because the reducers define exactly how to combine concurrent writes.
  5. Downstream node. synthesize receives the merged state, reads all findings, produces the answer.
  6. END. Execution reaches END. The final state is returned to the caller.

This lifecycle is the same whether you have three nodes or thirty. State in, partial updates out, reducers merge, next node runs. The pattern scales because each node is self-contained.

Common Mistakes (and How to Avoid Them)

As you start building graphs, you’ll likely hit a few of these. Here’s what to watch for:

  1. Returning full state from a node. Don’t return every field—return only what changed. Returning unchanged fields triggers unnecessary reducer calls and can cause subtle bugs with accumulating fields. If a node doesn’t modify messages, don’t include messages in the return dictionary.
  2. Forgetting to wrap list returns for reducer fields. If findings uses operator.add, returning {"findings": "a single string"} will fail. You need {"findings": ["a single string"]}—always a list, even for one item.
  3. Missing edges from START. If no edge connects START to any node, the graph compiles but immediately returns the initial state without executing anything.
  4. Incomplete path maps. Every return value from a conditional edge’s routing function must appear as a key in the path map. Missing keys cause runtime errors.
  5. Infinite loops. If your conditional edge can loop back to a previous node, make sure there’s always a termination condition. Add a counter or a max-retries check.
Guardrails for loops

LangGraph provides a recursion_limit parameter on compiled graphs: app.invoke(inputs, {"recursion_limit": 25}). If your graph exceeds this many node executions in a single invocation, it raises a GraphRecursionError. Set this whenever you have conditional edges that loop.

Design Principles Behind These Concepts

The choices LangGraph makes are intentional. Understanding the “why” helps you use the framework with the grain rather than against it.

Explicit over implicit. Every connection between nodes is an edge you added. There’s no hidden control flow, no event bus, no implicit ordering. You can read a graph definition top to bottom and know exactly what will execute and in what order.

State over message passing. Nodes don’t send messages to each other. They read from and write to shared state. This eliminates an entire category of bugs around message ordering, missed messages, and coupling between producers and consumers.

Partial updates over full state returns. By asking nodes to return only what changed, LangGraph keeps nodes decoupled. A node that computes a summary doesn’t need to know about the 15 other fields in the state. If you add a new field to the state later, existing nodes continue to work unchanged.

Reducers over coordination. When parallel nodes need to combine their results, reducers handle it declaratively. You say how values combine (append, sum, union) and the framework takes care of when. This is simpler and safer than manual lock management or merge logic scattered across nodes.

What You Now Know

This chapter gave you the vocabulary for everything that follows. You now know that a LangGraph application is a directed graph of nodes (plain Python functions) connected by edges (fixed or conditional), all operating on shared state (a typed dictionary with optional reducers). You know that START and END mark entry and exit, that StateGraph is the builder, and that .compile() turns your blueprint into a runnable machine. You understand that reducers give you precise control over how state fields merge, and that channels are the invisible plumbing underneath.

These aren’t abstract concepts—they’re the tools you’ll use in every graph you build. In the next chapter, we’ll take them off the workbench and build your first complete graph from scratch, step by step, with real LLM calls and real output.
