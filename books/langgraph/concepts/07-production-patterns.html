06 Collaboration at scale

Multi-Agent Systems

A single agent can only carry so much weight. Ask one LLM to research a topic, draft an article, and then critique its own writing, and you will watch it lose the thread—context bloats, instructions blur, quality drops. The solution is the same one that works in any workshop: give each person a defined job and a clear way to hand work to the next station. In LangGraph that means composing multiple agents—each with its own graph, state, and tools—into a coordinated system. This chapter shows you how to nest graphs inside graphs, wire agents together with well-known collaboration patterns, fan work out in parallel, and bring it all together in a practical research-assistant that researches, writes, and reviews.

Subgraphs: Nesting Graphs Inside Graphs

You already know how to build a StateGraph, compile it, and invoke it. A subgraph is nothing more than taking one of those compiled graphs and using it as a node inside a larger graph. The outer graph treats the subgraph the same way it treats any function node—it passes state in and gets state back—but inside, the subgraph runs its own full cycle of nodes and edges, oblivious to the world outside.

Why bother? Three reasons come up over and over. First, encapsulation: the subgraph owns its own state schema, so you can develop and test it independently. Second, reuse: the same subgraph can appear in multiple parent graphs without duplication. Third, clarity: a node named research_agent is easier to reason about than twenty nodes inlined into the parent.

Compiled Graphs as Nodes

The mechanics are straightforward. You compile a StateGraph into a CompiledGraph, then call add_node on the parent graph with that compiled object. LangGraph handles invocation, state marshalling, and error propagation automatically.

A subgraph as a node in a parent graph

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

# ── Child graph: a small summariser ──

class SummaryState(TypedDict):
    text: str
    summary: str

def summarise(state: SummaryState) -> dict:
    # In practice, call an LLM here
    return {"summary": state["text"][:80] + "..."}

summary_graph = StateGraph(SummaryState)
summary_graph.add_node("summarise", summarise)
summary_graph.add_edge(START, "summarise")
summary_graph.add_edge("summarise", END)
compiled_summary = summary_graph.compile()

# ── Parent graph ──

class ParentState(TypedDict):
    text: str
    summary: str
    final_output: str

def format_output(state: ParentState) -> dict:
    return {"final_output": f"Summary: {state['summary']}"}

parent_graph = StateGraph(ParentState)
parent_graph.add_node("summariser", compiled_summary)  # compiled graph as a node
parent_graph.add_node("formatter", format_output)
parent_graph.add_edge(START, "summariser")
parent_graph.add_edge("summariser", "formatter")
parent_graph.add_edge("formatter", END)

app = parent_graph.compile()

result = app.invoke({"text": "LangGraph lets you build stateful agents..."})
print(result["final_output"])

Notice two things. The parent graph and the child graph share some field names (text and summary), which lets LangGraph automatically map state between them. And the compiled graph is passed directly to add_node—no wrapper function needed.

State Mapping Between Parent and Child

When the parent and child state schemas share field names, LangGraph passes matching fields into the subgraph and merges results back automatically. But what if the schemas diverge? You have two options. You can write a thin wrapper function that transforms the parent’s state into the shape the child expects, invokes the compiled subgraph manually, and maps the result back. Or you can align your schemas deliberately—which is almost always the better choice, because explicit shared contracts make your system easier to debug.

When LangGraph invokes a subgraph node, it extracts the fields from the parent state that match the child’s schema by name and type. After the subgraph finishes, any fields in its output that also exist in the parent schema are written back. Fields that exist only in the child stay private—the parent never sees them.

State isolation in subgraphs

Each subgraph has its own state schema, and fields that do not appear in the parent’s schema are invisible to the parent. This is not a bug—it is the mechanism that gives you encapsulation. A research agent can track its own search_queries list internally without polluting the parent’s state. If you ever find yourself dumping every field into a giant shared schema, step back: you are losing the benefit of subgraphs. Keep shared state narrow and intentional.

Agent Collaboration Patterns

Once you can nest agents as subgraphs, the question becomes: how should they talk to each other? Three patterns appear repeatedly in production systems, and each makes a different trade-off between control and flexibility.

Supervisor Pattern

The supervisor pattern is the most common starting point. One agent—the supervisor—receives the user’s request and decides which specialist agent should handle it. The supervisor does not do the work itself; it routes. Think of a project manager who assigns tasks to the team and checks the results.

In LangGraph the supervisor is typically an LLM node that uses tool calling to delegate. Each specialist is exposed as a “tool” the supervisor can invoke. When the supervisor calls the research tool, the graph routes to the research subgraph. When it calls the write tool, the graph routes to the writer subgraph. The supervisor inspects the returned state and decides whether to delegate again or finish.

Supervisor pattern with tool-based delegation

from typing import TypedDict, Annotated, Literal
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.prebuilt import create_react_agent
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool
from langchain_core.messages import HumanMessage

llm = ChatOpenAI("gpt-4o-mini")

# ── Specialist tools ──

@tool
def web_search(query: str) -> str:
    """Search the web for information."""
    return f"Results for: {query}..."

@tool
def write_section(topic: str, notes: str) -> str:
    """Write a section given a topic and research notes."""
    return f"Draft section on {topic}..."

# ── Build specialist agents as compiled subgraphs ──

researcher = create_react_agent(llm, tools=[web_search])
writer = create_react_agent(llm, tools=[write_section])

# ── Supervisor state ──

class SupervisorState(TypedDict):
    messages: Annotated[list, add_messages]
    next_agent: str

# ── Supervisor node: decides who works next ──

def supervisor(state: SupervisorState) -> dict:
    system_prompt = (
        "You are a supervisor. Given the conversation, decide "
        "which agent should act next: 'researcher', 'writer', "
        "or 'FINISH' if the task is complete."
    )
    response = llm.invoke([
        {"role": "system", "content": system_prompt},
        *state["messages"]
    ])
    # Parse the decision from the LLM's response
    content = response.content.strip().lower()
    if "researcher" in content:
        return {"next_agent": "researcher"}
    elif "writer" in content:
        return {"next_agent": "writer"}
    else:
        return {"next_agent": "FINISH"}

# ── Routing function ──

def route_next(state: SupervisorState) -> Literal["researcher", "writer", "__end__"]:
    if state["next_agent"] == "FINISH":
        return "__end__"
    return state["next_agent"]

# ── Assemble the graph ──

graph = StateGraph(SupervisorState)
graph.add_node("supervisor", supervisor)
graph.add_node("researcher", researcher)
graph.add_node("writer", writer)

graph.add_edge(START, "supervisor")
graph.add_conditional_edges("supervisor", route_next)
graph.add_edge("researcher", "supervisor")  # report back
graph.add_edge("writer", "supervisor")      # report back

app = graph.compile()

Walk through the flow. The user sends a message; the supervisor node reads it and decides "researcher" should go first. The conditional edge routes to the researcher subgraph, which runs its own ReAct loop—calling web_search as needed. When the researcher finishes, the edge leads back to the supervisor. The supervisor sees the research results in the message history and now routes to the writer. The writer drafts content, returns to the supervisor, and this time the supervisor decides "FINISH". The conditional edge maps that to END, and the graph completes.

Peer-to-Peer Pattern

In the peer-to-peer pattern there is no central coordinator. Agents communicate through shared state—one agent writes its output into a field that the next agent reads. This works well when you have a fixed pipeline: agent A always passes to agent B, who passes to agent C.

You implement this with straightforward edges. Each agent node reads from and writes to the shared state. There is no routing logic because the sequence is predetermined. The advantage is simplicity; the disadvantage is rigidity. If agent B discovers that agent A’s output is insufficient, it has no mechanism to ask for a redo unless you build one.

Use peer-to-peer when your workflow is a conveyor belt: each station does its job and passes the workpiece forward. Use the supervisor pattern when decisions about routing need to happen at runtime.

Hierarchical Pattern

The hierarchical pattern extends the supervisor idea to multiple levels. A top-level supervisor delegates to mid-level supervisors, each of whom manages their own specialists. Think of a large organisation: the CEO assigns a project to a department head, who assigns sub-tasks to individual contributors.

In LangGraph this is straightforward because subgraphs nest. A mid-level supervisor is itself a compiled graph that contains specialist nodes. The top-level supervisor adds these mid-level graphs as nodes. Each level makes routing decisions independently and maintains its own state.

The trade-off is latency and token cost. Every supervisory decision is an LLM call. Two layers of supervision means at least two extra LLM invocations per task. Use hierarchical patterns when your problem genuinely has that many dimensions—for example, a system that handles both customer support and internal operations, where each domain has its own set of specialists.

Comparing the Patterns

Multi-agent architecture comparison
Dimension Supervisor Peer-to-Peer Hierarchical
Routing Central LLM decides at each step Fixed edges, no runtime routing Multi-level LLM decisions
Flexibility High—agents invoked on demand Low—pipeline is static Very high—nested delegation
Complexity Moderate Low High
Latency overhead One supervisor call per routing step No overhead Multiple supervisor calls per level

Map-Reduce and Parallelisation

So far every pattern has been sequential: one agent works, then the next. But many real tasks are embarrassingly parallel. If you need to research five sub-topics, there is no reason to research them one at a time. LangGraph gives you the Send() API for exactly this: dynamic fan-out to parallel node executions, followed by aggregation.

The Send() API

Send lives in langgraph.types. You use it inside a conditional-edge function: instead of returning a string (the name of the next node), you return a list of Send objects. Each Send specifies a target node and a state update to pass to that node. LangGraph launches all of them in parallel, waits for every branch to complete, and then merges the results back into the parent state.

The signature is simple: Send(node_name, state_update). The node_name is a string naming a node in your graph. The state_update is a dictionary of values that will be the input state for that particular branch. Each branch gets its own copy of the state, so branches do not interfere with each other.

Using Send() for parallel fan-out

from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.types import Send
import operator

# ── State: topics to research and collected results ──

class ResearchState(TypedDict):
    topics: list[str]
    results: Annotated[list[str], operator.add]  # merge via concatenation

# ── Node: research a single topic ──

def research_topic(state: ResearchState) -> dict:
    topic = state["topics"][0]  # each branch gets exactly one topic
    # In practice, call an LLM or search API here
    finding = f"Findings on {topic}: ..."
    return {"results": [finding]}

# ── Node: aggregate all results ──

def aggregate(state: ResearchState) -> dict:
    combined = "\n\n".join(state["results"])
    return {"results": [f"=== Aggregated Report ===\n{combined}"]}

# ── Fan-out function: returns a list of Send() objects ──

def fan_out(state: ResearchState) -> list[Send]:
    return [
        Send("research_topic", {"topics": [topic], "results": []})
        for topic in state["topics"]
    ]

# ── Build the graph ──

graph = StateGraph(ResearchState)
graph.add_node("research_topic", research_topic)
graph.add_node("aggregate", aggregate)

graph.add_conditional_edges(START, fan_out)     # dynamic fan-out
graph.add_edge("research_topic", "aggregate")   # all branches converge
graph.add_edge("aggregate", END)

app = graph.compile()

result = app.invoke({
    "topics": ["quantum computing", "gene editing", "fusion energy"],
    "results": []
})
print(result["results"])

Here is what happens when you invoke the graph. The fan_out function inspects the list of topics and creates one Send per topic. LangGraph launches three parallel instances of research_topic, each with its own single-element topics list. When all three finish, their results are merged using operator.add (list concatenation) into the parent state. The aggregate node then sees all three findings and combines them into a final report.

The Map-Reduce Pattern

The code above is a textbook map-reduce. The “map” phase fans out to parallel workers. The “reduce” phase aggregates their results. You can chain multiple map-reduce stages: the output of one aggregation becomes the input for the next fan-out.

A few practical tips. First, keep the state passed to each branch small—you are serialising it for every branch, and large states multiply memory usage. Second, use Annotated with a reducer function (like operator.add) on any field that multiple branches will write to; without a reducer, branches will overwrite each other. Third, think about error handling: if one branch fails, the default behaviour is to fail the entire graph. In production you may want to catch exceptions inside the node and return a sentinel value instead.

Send() is dynamic

Unlike static edges, Send() determines the number of parallel branches at runtime based on the current state. If the user provides ten topics, ten branches launch. If they provide one, only one runs. This makes it ideal for workloads where the fan-out factor is not known at graph-definition time.

Building a Research Assistant Agent

Let us bring everything together. We will build a research assistant that takes a question, researches it, writes a structured answer, and reviews the answer for quality. Three specialist agents, one supervisor to coordinate them, and a fan-out step for parallel research.

Architecture Overview

The system has four logical components:

  1. Supervisor — receives the user’s question, decomposes it into sub-questions, routes to specialists, and decides when the output is good enough.
  2. Researcher — takes a list of sub-questions, fans out in parallel to gather information on each, and aggregates the findings.
  3. Writer — takes the research findings and produces a structured, readable answer.
  4. Reviewer — reads the draft, scores it on completeness and accuracy, and either approves or sends feedback that triggers another revision cycle.

Defining the State

We need a state schema that every component can work with. We will keep it lean: the original question, a list of sub-questions, research findings, the current draft, and a review verdict.

State schema for the research assistant

from typing import TypedDict, Annotated, Literal
import operator

class ResearchAssistantState(TypedDict):
    question: str                                      # original user question
    sub_questions: list[str]                             # decomposed sub-questions
    findings: Annotated[list[str], operator.add]       # parallel-merge field
    draft: str                                          # current written draft
    review: str                                         # reviewer feedback
    status: str                                         # "research" | "write" | "review" | "done"
    revision_count: int                                  # how many times we have revised

Notice that findings uses an operator.add reducer. When the researcher fans out to parallel sub-question nodes, each branch appends its findings to the list. Without the reducer, the last branch to finish would overwrite results from earlier branches.

Building the Specialist Agents

The researcher agent receives a single sub-question and returns findings. In production you would wire this to a search API, a retrieval-augmented generation pipeline, or a database query tool. Here we use a simplified version that shows the structure.

Researcher node with parallel fan-out

from langgraph.types import Send
from langchain_openai import ChatOpenAI

llm = ChatOpenAI("gpt-4o-mini")

def decompose(state: ResearchAssistantState) -> dict:
    """Supervisor decomposes the question into sub-questions."""
    response = llm.invoke([
        {"role": "system", "content": "Break this question into 2-4 sub-questions. Return one per line."},
        {"role": "user", "content": state["question"]}
    ])
    subs = [q.strip() for q in response.content.split("\n") if q.strip()]
    return {"sub_questions": subs, "status": "research"}

def fan_out_research(state: ResearchAssistantState) -> list[Send]:
    """Create one parallel branch per sub-question."""
    return [
        Send("research_one", {**state, "sub_questions": [sq], "findings": []})
        for sq in state["sub_questions"]
    ]

def research_one(state: ResearchAssistantState) -> dict:
    """Research a single sub-question."""
    sq = state["sub_questions"][0]
    response = llm.invoke([
        {"role": "system", "content": "You are a research assistant. Provide key facts."},
        {"role": "user", "content": sq}
    ])
    return {"findings": [f"[{sq}]: {response.content}"]}

The writer agent receives the accumulated findings and produces a coherent draft.

Writer node

def write_draft(state: ResearchAssistantState) -> dict:
    """Write a structured answer from research findings."""
    findings_text = "\n".join(state["findings"])
    response = llm.invoke([
        {"role": "system",
         "content": "Write a clear, structured answer using these research findings. "
                    "Use sections with headings. Be thorough but concise."},
        {"role": "user",
         "content": f"Question: {state['question']}\n\nFindings:\n{findings_text}"}
    ])
    return {"draft": response.content, "status": "review"}

The reviewer reads the draft and either approves or returns feedback. We cap revisions at two to prevent infinite loops.

Reviewer node

def review_draft(state: ResearchAssistantState) -> dict:
    """Review the draft for completeness and accuracy."""
    response = llm.invoke([
        {"role": "system",
         "content": "Review this draft. If it is good, respond with 'APPROVED'. "
                    "Otherwise, provide specific feedback for improvement."},
        {"role": "user",
         "content": f"Question: {state['question']}\n\nDraft:\n{state['draft']}"}
    ])
    content = response.content
    new_count = state.get("revision_count", 0) + 1

    if "APPROVED" in content or new_count >= 2:
        return {"review": content, "status": "done", "revision_count": new_count}
    else:
        return {"review": content, "status": "write", "revision_count": new_count}

Assembling the Full Graph

Now we wire everything together. The supervisor logic lives in the routing function, which inspects status to decide where to go next.

Full research assistant graph assembly

from langgraph.graph import StateGraph, START, END
from langgraph.types import Send

def route_after_review(state: ResearchAssistantState) -> str:
    """Route based on review status."""
    if state["status"] == "done":
        return "__end__"
    return "write_draft"  # revise

graph = StateGraph(ResearchAssistantState)

# Add nodes
graph.add_node("decompose", decompose)
graph.add_node("research_one", research_one)
graph.add_node("write_draft", write_draft)
graph.add_node("review_draft", review_draft)

# Edges
graph.add_edge(START, "decompose")
graph.add_conditional_edges("decompose", fan_out_research)  # parallel
graph.add_edge("research_one", "write_draft")                # converge
graph.add_edge("write_draft", "review_draft")
graph.add_conditional_edges("review_draft", route_after_review)

app = graph.compile()

# ── Run it ──

result = app.invoke({
    "question": "What are the main approaches to carbon capture?",
    "sub_questions": [],
    "findings": [],
    "draft": "",
    "review": "",
    "status": "",
    "revision_count": 0
})

print(result["draft"])

Trace the execution. The user’s question enters at START and flows to decompose, which breaks it into sub-questions like “What is direct air capture?” and “What are ocean-based approaches?” The conditional edge from decompose calls fan_out_research, which creates a Send for each sub-question. These run in parallel through research_one, and their findings merge via the operator.add reducer. Once all branches complete, execution flows to write_draft, which synthesises the findings. The draft moves to review_draft. If the reviewer approves (or the revision cap is reached), we go to END. Otherwise, we loop back to write_draft for another revision attempt.

Guard against infinite loops

Any cycle in your graph—like the write-review-revise loop above—can potentially run forever. Always include an escape hatch: a revision counter, a maximum iteration count, or a recursion_limit parameter when compiling the graph (graph.compile(recursion_limit=25)). In production, combine both: a soft limit in your logic and a hard limit in the graph configuration. When the limit triggers, make sure you return whatever partial result you have, not an empty response.

Design Decisions for Multi-Agent Systems

Building multi-agent systems raises questions that single-agent graphs do not. Let us address the most common ones.

When to Use Multiple Agents

A single agent with many tools is simpler and often sufficient. Reach for multi-agent architectures when you see one of these signals: the context window is getting crowded (each agent can operate with a focused system prompt); different parts of the task need different models (a cheap model for classification, a strong model for writing); or the task naturally decomposes into independent sub-problems that benefit from parallel execution.

If your task is a linear pipeline with clear stages, peer-to-peer nodes may be enough—you do not always need the overhead of a supervisor. If the task requires real-time dynamic routing, the supervisor pattern is your friend. And if you find yourself building supervisors for your supervisors, pause and ask whether the problem really demands that complexity, or whether you are over-engineering.

State Schema Design

In multi-agent systems, state design is critical. Keep the shared state schema minimal—include only what agents genuinely need to communicate. Use subgraph-private state for internal bookkeeping. If two agents both write to the same field, you must define a reducer (via Annotated) or you will get unpredictable overwrites.

A common pattern is to use a messages field with the add_messages reducer as the primary communication channel. This works well for conversational agents but can become unwieldy for data-processing pipelines. For the latter, typed fields like findings, draft, and review give you more control and make the state self-documenting.

Error Handling in Multi-Agent Systems

When one agent fails in a multi-agent system, the default behaviour is for the entire graph to fail. For production systems, consider these strategies. First, catch exceptions inside node functions and write error information into the state so the supervisor can decide what to do. Second, use retry_policy on nodes that call external APIs to handle transient failures. Third, design your supervisor to be resilient: if the researcher fails, can the writer still produce a useful (if less informed) draft?

create_react_agent for quick specialists

When you need a specialist agent quickly, create_react_agent from langgraph.prebuilt gives you a fully functional ReAct agent in one call. Pass it an LLM and a list of tools, and it returns a compiled graph that you can drop straight into a parent graph as a node. This is often the fastest way to prototype a multi-agent system—build each specialist with create_react_agent, wire them together with a supervisor, and iterate from there.

Debugging Multi-Agent Graphs

Multi-agent systems are harder to debug than single-agent graphs because the execution path is determined at runtime. Here are the techniques that help most.

Tracing. Use LangSmith or another tracing tool to visualise the full execution graph, including which agents ran, in what order, and what they returned. LangGraph integrates with LangSmith natively—every node invocation appears as a span in the trace.

State inspection. After each node runs, print or log the full state. In development, you can use the stream method to watch state changes in real time:

Streaming state updates for debugging

for event in app.stream(initial_state):
    for node_name, state_update in event.items():
        print(f"--- {node_name} ---")
        print(state_update)
        print()

Isolation testing. Because each subgraph is independently compiled, you can test it in isolation. Invoke the researcher subgraph directly with test inputs. Verify it returns the expected state shape. Only after each specialist works in isolation do you wire them together.

Recursion limits. If your graph seems to hang, it is probably stuck in a cycle. Set a low recursion_limit during development (e.g., 10) so failures surface quickly. Raise it once you have confirmed the graph terminates correctly.

Patterns at a Glance

Let us condense the chapter into a decision framework.

  • Subgraphs give you encapsulation and reuse. Use them whenever a group of nodes logically belongs together and has its own internal state.
  • Supervisor pattern gives you runtime flexibility. Use it when the task requires dynamic routing based on intermediate results.
  • Peer-to-peer gives you simplicity. Use it for fixed-sequence pipelines where every input follows the same path.
  • Hierarchical gives you scale. Use it for complex domains where sub-domains each need their own routing logic.
  • Map-reduce gives you parallelism. Use it whenever you can decompose work into independent units and aggregate the results.

These patterns compose. The research assistant combined supervisor routing with map-reduce parallelism and subgraph encapsulation. That is typical of real systems: you pick the patterns that fit your problem and layer them together.

Honest Limits

Multi-agent systems are powerful, but they come with real costs. Every agent invocation burns tokens. Every supervisor decision adds latency. Every state merge is a potential source of bugs. The more agents you add, the harder the system is to reason about.

Start with the simplest architecture that solves your problem. A single agent with good tools handles a surprising range of tasks. Add a second agent only when you can articulate why the first cannot do the job alone. Add a supervisor only when you need runtime routing. Add parallelism only when sequential execution is genuinely too slow. Each layer of complexity should earn its place.

You now know how to compose agents into systems—nesting graphs as subgraphs, routing with supervisors, and fanning out work in parallel. The core insight is that LangGraph treats multi-agent coordination as a graph-design problem: the same nodes-and-edges abstraction that structures a single agent also structures teams of agents. In the next chapter, we turn to production concerns: persistence, deployment, monitoring, and the patterns that keep multi-agent systems reliable in the real world.
