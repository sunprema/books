03 From zero to chatbot

Building Your First Graph

You have the concepts—nodes, edges, state, reducers. Now you want something that actually runs. In this chapter we go from a blank file to a working chatbot, then extend it with tool calling so the bot can reach out into the world and loop back with results. By the end you will have built, compiled, and invoked two graphs, and you will understand the concrete mechanics behind every piece of theory from Chapter 2.

Setting Up Your Environment

Before you write a single line of graph code, you need three things: Python 3.10 or later, the LangGraph package, and an API key for the language model you want to call. Let’s get them all in place.

Install the core packages

# For OpenAI models
pip install langgraph langchain-openai

# — or, for Anthropic models —
pip install langgraph langchain-anthropic

The langgraph package pulls in langchain-core automatically. You only need one model provider package—pick whichever you already have an API key for. Every example in this chapter works with either provider; the only difference is the import name and the environment variable.

Set your API key (choose one)

# In your shell, or in a .env file
export OPENAI_API_KEY="sk-..."

# — or —
export ANTHROPIC_API_KEY="sk-ant-..."
Keep keys out of code

Never paste an API key directly into a Python file. Use environment variables or a secrets manager. If you accidentally commit a key, revoke it immediately in the provider’s dashboard.

A quick sanity check: open a Python REPL and run import langgraph; print(langgraph.__version__). If you see a version number (0.2 or higher), you’re ready.

A Bare-Bones Chatbot

The simplest useful graph has one node—call the language model—and two edges—START to that node and that node to END. That’s it. Three moving parts. Let’s build it piece by piece, then look at the complete listing.

Step 1 — Define the State

Every graph needs a state schema. For a chatbot, the state is straightforward: a list of messages. LangGraph ships a ready-made schema called MessagesState that does exactly this. It defines a single key—messages—with a reducer that appends new messages instead of overwriting the list.

Import MessagesState

from langgraph.graph import StateGraph, START, END, MessagesState

MessagesState is a TypedDict with one key. Behind the scenes it looks roughly like this:

What MessagesState provides (you don’t need to write this)

from typing import Annotated
from langgraph.graph.message import add_messages

class MessagesState(TypedDict):
    messages: Annotated[list, add_messages]
MessagesState — your go-to for chat applications

Whenever you’re building a conversational agent, reach for MessagesState first. It pre-configures the add_messages reducer, which handles appending, deduplication by message ID, and proper ordering. You can always extend it later by subclassing, but for most chatbots it’s all you need.

Step 2 — Create the Chatbot Node

A node is a plain Python function that receives the current state and returns a partial update. Our chatbot node takes the messages so far, passes them to the language model, and returns the model’s response. The reducer takes care of appending it.

Define the chatbot node

from langchain_openai import ChatOpenAI

# Or: from langchain_anthropic import ChatAnthropic

llm = ChatOpenAI(model="gpt-4o-mini")
# Or: llm = ChatAnthropic(model="claude-sonnet-4-20250514")

def chatbot(state: MessagesState):
    """Call the LLM with the full message history."""
    response = llm.invoke(state["messages"])
    return {"messages": [response]}

Notice three things. First, the function signature: it takes a MessagesState dict and returns a dict with the same shape. Second, we wrap the response in a list because the add_messages reducer expects an iterable. Third, we don’t manage conversation history ourselves—state carries it forward turn after turn.

Step 3 — Wire Up the Graph

Now we build the graph structure: add the node, connect START to it, and connect it to END.

Build and compile the graph

# Create a graph builder with our state schema
graph_builder = StateGraph(MessagesState)

# Add the chatbot node
graph_builder.add_node("chatbot", chatbot)

# Wire edges: START -> chatbot -> END
graph_builder.add_edge(START, "chatbot")
graph_builder.add_edge("chatbot", END)

# Compile into a runnable graph
graph = graph_builder.compile()

The call to compile() freezes the graph’s structure and returns a CompiledGraph object. This object is a LangChain Runnable, which means you can call .invoke(), .stream(), or .batch() on it.

Step 4 — Invoke the Graph

You invoke the graph by passing in an initial state. For a chatbot, that means a dict with a messages key containing the user’s input.

Send a message and print the response

from langchain_core.messages import HumanMessage

result = graph.invoke({
    "messages": [HumanMessage(content="What is LangGraph?")]
})

# The result is the full state after execution
for msg in result["messages"]:
    print(f"{msg.type}: {msg.content}")

Expected output

human: What is LangGraph?
ai: LangGraph is a framework for building stateful, multi-step
    applications with language models, using a graph-based
    architecture where nodes represent computation steps and
    edges define the flow between them.

That’s a working chatbot. The data flows in a straight line: START hands the initial state to the chatbot node, which calls the LLM and returns an AI message, and then execution reaches END. The full state—both the human message and the AI response—comes back as the result.

Complete Listing: Basic Chatbot

Here is the entire program in one place. Copy it into a file, set your API key, and run it.

basic_chatbot.py — a minimal LangGraph chatbot

from langgraph.graph import StateGraph, START, END, MessagesState
from langchain_openai import ChatOpenAI
from langchain_core.messages import HumanMessage

# 1. Set up the LLM
llm = ChatOpenAI(model="gpt-4o-mini")

# 2. Define the chatbot node
def chatbot(state: MessagesState):
    response = llm.invoke(state["messages"])
    return {"messages": [response]}

# 3. Build the graph
graph_builder = StateGraph(MessagesState)
graph_builder.add_node("chatbot", chatbot)
graph_builder.add_edge(START, "chatbot")
graph_builder.add_edge("chatbot", END)

# 4. Compile
graph = graph_builder.compile()

# 5. Run
result = graph.invoke({
    "messages": [HumanMessage(content="What is LangGraph?")]
})

for msg in result["messages"]:
    print(f"{msg.type}: {msg.content}")

Seventeen lines of meaningful code. That’s the minimum viable graph. But a chatbot that can only generate text is limited—it can’t check the weather, query a database, or do arithmetic reliably. For that, we need tools.

Adding Tool Calling

Tool calling is where graph-based architecture starts to pay for itself. When a language model decides it needs to call a tool, the response doesn’t go straight to the user. Instead, execution routes to a tool node that runs the tool, then loops back to the chatbot so the model can incorporate the tool’s output. This is the cycle we talked about in Chapter 2—and now you’ll build one yourself.

The plan is straightforward. We will:

  1. Define one or more tools as Python functions.
  2. Bind those tools to the LLM so it knows they exist.
  3. Add a ToolNode that executes tool calls automatically.
  4. Add a conditional edge that routes based on whether the model wants to call a tool or is ready to respond.
  5. Wire the tool node back to the chatbot—creating the cycle.

Step 1 — Define Tools

A tool is a regular Python function decorated with @tool from LangChain. The decorator reads the function’s name, docstring, and type hints to generate a schema that the LLM can understand.

Two simple tools

from langchain_core.tools import tool

@tool
def multiply(a: float, b: float) -> float:
    """Multiply two numbers together."""
    return a * b

@tool
def get_weather(city: str) -> str:
    """Get the current weather for a city."""
    # In a real app, call a weather API here
    return f"It's 72°F and sunny in {city}."

tools = [multiply, get_weather]

The docstring matters. The LLM reads it to decide when to use the tool, so write something clear and accurate.

Step 2 — Bind Tools to the LLM

Before the LLM can call tools, it needs to know about them. The bind_tools method attaches the tool schemas to every request the model makes.

Create a tool-aware LLM

llm = ChatOpenAI(model="gpt-4o-mini")
llm_with_tools = llm.bind_tools(tools)

Now when we call llm_with_tools.invoke(messages), the model might return an AIMessage with a tool_calls field instead of plain text content. That’s the signal our graph will act on.

Step 3 — Update the Chatbot Node

The chatbot node changes by exactly one word: we call llm_with_tools instead of llm.

Updated chatbot node

def chatbot(state: MessagesState):
    response = llm_with_tools.invoke(state["messages"])
    return {"messages": [response]}

Step 4 — Add the Tool Node

LangGraph provides ToolNode in its prebuilt module. You pass it a list of tools and it handles the rest—looking at the latest AIMessage, extracting any tool_calls, invoking the right function, and returning the results as ToolMessage objects.

Import and create the ToolNode

from langgraph.prebuilt import ToolNode

tool_node = ToolNode(tools=tools)

ToolNode is just a node—a callable that takes state and returns a state update. You could write it by hand, but the prebuilt version handles edge cases like parallel tool calls, error messages, and proper message formatting.

Step 5 — Add the Conditional Edge

Here is the decision point. After the chatbot node runs, we need to ask: did the model request any tool calls? If yes, route to the tool node. If no, the model produced a final answer, so route to END.

LangGraph provides tools_condition for exactly this check. It looks at the last message in state. If the message has a non-empty tool_calls field, it returns "tools". Otherwise it returns END.

Import the routing function

from langgraph.prebuilt import tools_condition

Step 6 — Wire It All Together

Now we assemble the graph. The key difference from the basic chatbot is the conditional edge after the chatbot node and the edge from the tool node back to the chatbot. That backward edge is what creates the cycle.

Build the graph with tool-calling loop

graph_builder = StateGraph(MessagesState)

# Add nodes
graph_builder.add_node("chatbot", chatbot)
graph_builder.add_node("tools", tool_node)

# Entry edge
graph_builder.add_edge(START, "chatbot")

# Conditional edge: chatbot decides what happens next
graph_builder.add_conditional_edges(
    "chatbot",
    tools_condition,  # Returns "tools" or END
)

# After tools run, always go back to chatbot
graph_builder.add_edge("tools", "chatbot")

# Compile
graph = graph_builder.compile()

Look at the flow: START → chatbot → (conditional) → tools → chatbot → (conditional) → END. The chatbot and tools nodes can bounce back and forth as many times as needed. Each pass through the chatbot node gives the model a chance to either call another tool or produce a final answer.

Won’t the cycle run forever?

In theory, yes—a buggy tool or a confused model could loop indefinitely. In practice, LangGraph has a default recursion limit (typically 25 steps). If the graph hits this limit, it raises a GraphRecursionError. You can adjust this with the recursion_limit config parameter when invoking the graph. We’ll cover error handling in more detail in Chapter 6.

Visualizing the Tool-Calling Loop

Let’s see the graph we just built. The diagram below shows the two nodes, the conditional routing from the chatbot, and the backward edge that creates the cycle.

Read the diagram from top to bottom. Every user message enters at START and arrives at the chatbot node. The chatbot calls the LLM. If the LLM’s response contains tool calls, the conditional edge routes to the tools node. The tools node executes the requested functions and returns the results as messages. Then the cycle edge sends execution back to the chatbot, where the LLM sees the tool results and decides what to do next—call more tools or produce a final answer. When there are no tool calls, the dashed edge leads to END.

Complete Listing: Chatbot with Tools

Here is the full program for the tool-calling chatbot. It combines every piece from the previous sections into one runnable file.

tool_chatbot.py — a chatbot that can call tools

from langgraph.graph import StateGraph, START, END, MessagesState
from langgraph.prebuilt import ToolNode, tools_condition
from langchain_openai import ChatOpenAI
from langchain_core.tools import tool
from langchain_core.messages import HumanMessage

# ── Tools ──────────────────────────────────────────────

@tool
def multiply(a: float, b: float) -> float:
    """Multiply two numbers together."""
    return a * b

@tool
def get_weather(city: str) -> str:
    """Get the current weather for a city."""
    return f"It's 72°F and sunny in {city}."

tools = [multiply, get_weather]

# ── LLM with tools bound ──────────────────────────────

llm = ChatOpenAI(model="gpt-4o-mini")
llm_with_tools = llm.bind_tools(tools)

# ── Nodes ─────────────────────────────────────────────

def chatbot(state: MessagesState):
    response = llm_with_tools.invoke(state["messages"])
    return {"messages": [response]}

tool_node = ToolNode(tools=tools)

# ── Graph ─────────────────────────────────────────────

graph_builder = StateGraph(MessagesState)

graph_builder.add_node("chatbot", chatbot)
graph_builder.add_node("tools", tool_node)

graph_builder.add_edge(START, "chatbot")
graph_builder.add_conditional_edges("chatbot", tools_condition)
graph_builder.add_edge("tools", "chatbot")

graph = graph_builder.compile()

# ── Run ───────────────────────────────────────────────

result = graph.invoke({
    "messages": [
        HumanMessage(content="What's 17 times 24?")
    ]
})

for msg in result["messages"]:
    print(f"{msg.type}: {msg.content}")

Expected output

human: What's 17 times 24?
ai:
tool: 408.0
ai: 17 times 24 is 408.

Let’s walk through what happened. The user asked “What’s 17 times 24?” The chatbot node called the LLM, which recognized the multiply tool and returned an AIMessage with an empty content string and a tool_calls list containing multiply(a=17, b=24). The conditional edge saw the tool call and routed to the tools node. The tools node executed multiply(17, 24) and returned a ToolMessage with content 408.0. The cycle edge sent control back to the chatbot. The LLM saw the tool result, recognized the computation was complete, and produced the final response: “17 times 24 is 408.” The conditional edge saw no tool calls and routed to END.

Try a multi-tool query: “What’s the weather in Paris, and what’s 6 times 7?” The model will issue both tool calls, the tools node will execute them, and the chatbot will synthesize both results into a single answer. The graph handles multiple tool calls in one pass without any extra code from you.

Following the Execution Trace

To make the internal mechanics concrete, here is exactly what happens at each step when you run the tool-calling chatbot with the multiply question.

Execution trace for “What’s 17 times 24?”
Step Node Action Messages after
1 START Pass initial state to first node HumanMessage(“What’s 17 times 24?”)
2 chatbot LLM returns AIMessage with tool_calls=[multiply(17, 24)] HumanMessage, AIMessage(tool_calls)
3 condition tool_calls is non-empty → route to “tools” —
4 tools Execute multiply(17, 24) → 408.0 HumanMessage, AIMessage, ToolMessage(408.0)
5 chatbot LLM sees tool result, produces final answer HumanMessage, AIMessage, ToolMessage, AIMessage(“408”)
6 condition No tool_calls → route to END —
7 END Return final state All four messages

Notice that the chatbot node ran twice and the conditional check ran twice. The graph managed all of this automatically—you didn’t write a while loop or an if-else chain. The structure of the graph is the control flow.

Streaming Responses

For real applications you rarely want to wait for the entire graph to finish before showing anything to the user. LangGraph supports streaming at two levels: node-level streaming (getting updates as each node completes) and token-level streaming (getting individual tokens as the LLM generates them).

Node-level streaming with .stream()

for event in graph.stream({
    "messages": [HumanMessage(content="What's the weather in Tokyo?")]
}):
    # Each event is a dict: {node_name: state_update}
    for node_name, update in event.items():
        print(f"── {node_name} ──")
        if "messages" in update:
            for msg in update["messages"]:
                print(f"  {msg.type}: {msg.content[:80]}")

With .stream(), you get a state update dictionary every time a node finishes executing. This lets you show progress in a UI—for example, displaying “Calling tool...” while the tools node runs, then showing the final response when the chatbot node runs the second time.

Token-level streaming

For streaming individual tokens as the LLM generates them (the “typing” effect), use graph.astream_events() with the async API. We’ll cover this in detail in Chapter 7 when we discuss production deployment patterns.

Extending MessagesState

MessagesState is sufficient for many chatbots, but sometimes you need additional fields in your state—a user’s name, a session ID, a running summary. You can subclass MessagesState and add whatever you need.

Custom state that extends MessagesState

class ChatState(MessagesState):
    # Inherits "messages" with add_messages reducer
    user_name: str
    turn_count: int

The messages key keeps its reducer behavior. The new fields (user_name and turn_count) use the default last-write-wins semantics. Your nodes can read and write these additional fields just like they read and write messages.

Start with MessagesState and extend only when you have a clear reason. Extra state means extra surface area for bugs. We’ll explore more sophisticated state patterns in the next chapter.

Anatomy of the Pattern

Before moving on, let’s name the pattern you just built. The tool-calling chatbot follows what we can call the ReAct loop—the model reasons about what to do, acts by calling a tool, observes the result, and reasons again. This loop is one of the most common agent patterns, and you’ve implemented it in about 30 lines of code.

Components of the tool-calling chatbot
Component Role Source
MessagesState State schema with message accumulation langgraph.graph
StateGraph Graph builder langgraph.graph
START, END Special nodes marking entry and exit langgraph.graph
ToolNode Executes tool calls from AIMessage langgraph.prebuilt
tools_condition Routes based on presence of tool_calls langgraph.prebuilt
bind_tools Attaches tool schemas to LLM requests LangChain chat model

Every one of these components is swappable. You can replace ToolNode with a custom node that adds logging or retry logic. You can replace tools_condition with a function that considers other factors beyond tool calls. You can even replace the LLM with a different model mid-conversation. That’s the advantage of building with a graph: each piece has a clear boundary and a well-defined contract.

Common Mistakes and How to Avoid Them

When you’re first building graphs, a few mistakes come up repeatedly. Here are the ones I see most often, along with their fixes.

Forgetting to bind tools

If you add a ToolNode and a conditional edge but forget to call llm.bind_tools(tools), the LLM will never generate tool calls. The conditional edge will always route to END, and the tools node will never execute. The graph won’t error—it will just act like a basic chatbot. Always verify that you’re invoking the tool-bound LLM inside your chatbot node.

Missing the return edge from tools to chatbot

If you forget graph_builder.add_edge("tools", "chatbot"), the graph has no path forward after executing tools. Compilation may succeed, but invocation will fail or produce incomplete results. The tool results need to flow back to the chatbot so the LLM can interpret them.

Returning a message instead of a list

The add_messages reducer expects an iterable of messages. If your node returns {"messages": response} instead of {"messages": [response]}, you may get unexpected behavior because the reducer will try to iterate over the message object itself. Always wrap single messages in a list.

Forgetting to compile

The StateGraph object is a builder—it doesn’t have .invoke() or .stream() methods. You must call .compile() to get a runnable graph. If you see an AttributeError when trying to invoke, check that you’re calling methods on the compiled graph, not the builder.

Try It Yourself

The best way to internalize these patterns is to modify them. Here are a few exercises, roughly in order of difficulty.

  1. Add a third tool. Write a divide tool and add it to the tools list. Ask the chatbot a question that requires division. Watch the trace to confirm the tool was called.
  2. Switch providers. If you used OpenAI, swap in ChatAnthropic. If you used Anthropic, swap in ChatOpenAI. Notice how little changes—the graph structure is model-agnostic.
  3. Add a system message. Modify the chatbot node to prepend a SystemMessage that gives the bot a personality. For example: “You are a pirate who always responds in pirate speak.”
  4. Build a multi-turn conversation. Write a loop that accepts user input from the terminal, invokes the graph, and prints the response. You’ll need to accumulate messages across turns—hint: pass the full message list from the previous result as input to the next invocation.
  5. Visualize both graphs. Generate Mermaid diagrams for both the basic chatbot and the tool-calling chatbot. Compare the two structures side by side.

What You Built

In this chapter you went from zero to two working chatbots. The first was a straight line—START, chatbot, END. The second introduced the cycle that makes tool calling possible: chatbot to tools and back again, with a conditional edge controlling the exit. You saw that the graph structure is the program’s control flow, and that LangGraph’s prebuilt components (ToolNode, tools_condition, MessagesState) handle the common patterns so you can focus on your application’s unique logic.

But these chatbots forget everything between invocations. Ask a question, get an answer, and the slate is wiped clean. In the next chapter—State and Memory—we’ll add persistence so your graph can remember past conversations, checkpoint mid-execution, and resume exactly where it left off.
