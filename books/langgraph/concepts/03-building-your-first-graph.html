01 Beyond linear chains

Why LangGraph?

You have built a chain. Prompt goes in, response comes out. Maybe you strung a few steps together—retrieve some documents, stuff them into context, ask the model, parse the answer. It works. Then a stakeholder asks: “Can it retry when the output is bad?” You hack in a while loop. “Can it ask a human for approval before acting?” You add a flag and a callback. “Can two agents collaborate on this?” You stare at the ceiling. The linear chain that served you so well has become a straitjacket, and you are looking for a way out.

The Linear Chain Problem

Think of a linear chain as an assembly line in a factory. A workpiece moves from Station A to Station B to Station C, and at the end you get a finished product. Assembly lines are brilliant when every product follows the same path. But what happens when a quality inspector at Station C discovers a defect? The workpiece needs to go back to Station A. An assembly line can’t do that—not without stopping the belt, reversing the motor, and confusing every other workpiece on the line.

The earliest LLM applications followed exactly this pattern. You sent a prompt to a model, got a completion back, maybe post-processed it, and returned it to the user. Frameworks like LangChain made this composable: you could snap together a PromptTemplate, an LLM, and an OutputParser into a chain that flowed in one direction. The LCEL (LangChain Expression Language) syntax made it elegant—pipe operators, streaming out of the box, batch support. For retrieval-augmented generation, summarisation, or single-shot classification, sequential chains remain the right tool.

But real-world AI applications are rarely single-shot. Consider what happens when you need any of the following:

  • Retry on failure. The model produces malformed JSON. You want to feed the error message back and ask it to try again—up to three times. That’s a loop, not a line.
  • Conditional branching that reconverges. Based on a classification step, you route to one of four specialist prompts, then merge the results. A linear chain can branch, but merging cleanly is awkward.
  • Human-in-the-loop. Before the agent executes a tool call, a human must approve it. The system needs to pause, persist its state, wait (possibly for hours), then resume exactly where it left off.
  • Multi-agent collaboration. A “researcher” agent gathers information, passes it to a “writer” agent, whose draft goes to a “critic” agent, whose feedback loops back to the writer. This is cyclic by nature.
  • Long-running state. A customer-support bot needs to remember what happened three turns ago, track which tools it has already called, and know which sub-tasks are complete. That state must survive across multiple LLM invocations and possibly across process restarts.

None of these are exotic requirements. They are the bread and butter of production AI systems. The issue is not that LangChain is flawed—it is that sequential chains are the wrong abstraction for problems that are inherently cyclic and stateful. You need a different shape.

The Shape of Real AI Work

If you have worked with data pipelines, you have likely encountered DAGs—directed acyclic graphs. Tools like Apache Airflow let you express complex dependencies: task C waits for both task A and task B to finish. But notice the word acyclic. A DAG cannot contain loops. An edge can never point backward. For data pipelines that run once per schedule, this is fine. For an AI agent that needs to iterate, reflect, and retry, it is a fundamental limitation.

What you need is a directed graph that allows cycles. In such a graph, a node can send control back to a node that already ran. A “reflect” node can route back to a “generate” node. A “validate” node can loop back to “fix” until the output passes. The graph terminates not because it ran out of edges, but because a node explicitly says “we’re done”—or because a configurable recursion limit prevents infinite loops.

Cycles alone are not enough. Each time control passes through a node, the system’s state may change: a new message has been appended, a tool result has been recorded, a counter has been incremented. You need a shared, mutable state object that every node can read and write, and that persists across the entire execution—including across cycles. This is the core insight that separates LangGraph from its predecessors.

Key Insight

Graphs are control flow for AI. Just as if, while, and for give you control flow in a programming language, a graph with conditional edges and cycles gives you control flow for multi-step AI systems. Nodes are the operations. Edges are the decisions. State is the memory. LangGraph makes this pattern a first-class abstraction rather than something you hack together with ad-hoc Python loops and global variables.

Enter LangGraph

LangGraph is a low-level orchestration framework built by LangChain Inc. It is open-source under the MIT license, currently at version 1.2.x, and considered production-stable. You install it with a single command:

Installing LangGraph

# Requires Python >= 3.10
pip install langgraph

Despite sharing the “Lang” prefix, LangGraph is a standalone package. You do not need LangChain to use it. Your nodes can be plain Python functions that accept and return dictionaries. That said, LangGraph integrates seamlessly with LangChain components—chat models, tools, retrievers, output parsers—when you want them. Think of LangGraph as the control plane and LangChain as one possible component library you can plug into it.

LangGraph’s value proposition rests on three pillars:

  1. Stateful execution. A TypedDict (or Pydantic model) defines the shape of your state. Every node receives the current state and returns updates to it. The framework merges those updates for you, using reducers you can customise (append to a list, overwrite a value, increment a counter).
  2. Cyclic graphs. Edges can point backward, creating loops. Conditional edges let you route dynamically based on the current state. A built-in recursion limit (default 25) prevents runaway loops, and you can tune it per invocation.
  3. Multi-actor orchestration. Each node is an independent actor. Nodes can represent different agents, tools, human checkpoints, or sub-graphs. You compose them into a single graph that the framework executes, handling the state passing and edge routing for you.

When to Choose LangGraph

Not every project needs a graph. If your workflow is “prompt in, response out,” a LangChain chain or even a raw API call is simpler and easier to reason about. Reach for LangGraph when you recognise one or more of these signals:

  • You need loops. Retry logic, iterative refinement, reflection patterns—any time the output of a step feeds back into an earlier step.
  • You need persistent state. The system must remember what has happened across multiple LLM calls, and that state must survive process restarts or long pauses (e.g., waiting for a human).
  • You have multiple agents. A supervisor delegates to specialists, or peers collaborate in a round-robin. Each agent is a subgraph or a node, and the framework manages the hand-offs.
  • You need human checkpoints. A person must review, approve, edit, or inject data at certain points in the workflow. The system pauses, persists, and resumes without losing context.
  • You have complex conditional routing. Based on the current state—not just the last step’s output—different paths should be taken, and those paths may reconverge or loop.

If none of those apply, you probably don’t need LangGraph yet. And that’s fine. The best tool is the simplest one that solves your problem. We’ll be honest throughout this book about when a graph adds value and when it adds only ceremony.

A Concrete Example: The Retry Loop

Let’s make this concrete. Suppose you ask an LLM to produce a JSON object with specific fields. Sometimes the model gets it right; sometimes it doesn’t. You want to validate the output, and if it fails validation, feed the error back and ask the model to try again—up to three attempts.

In a plain LangChain chain, there is no built-in way to express “go back to step 1.” You would need to wrap the chain in a Python for loop, manage a counter yourself, catch exceptions, and re-invoke the chain from scratch. The chain itself has no memory of previous attempts; you would need to manually accumulate the conversation history.

In LangGraph, this is a natural graph shape. Here is a minimal implementation:

A retry loop in LangGraph

from typing import TypedDict, Annotated
import json
from langgraph.graph import StateGraph, START, END

# 1. Define the state shape
class RetryState(TypedDict):
    prompt: str
    raw_output: str
    parsed: dict | None
    error: str | None
    attempts: int

# 2. Define the nodes (plain functions)
def generate(state: RetryState) -> dict:
    # In a real app, call your LLM here.
    # For this example, we simulate a response.
    if state["attempts"] < 2:
        raw = '{"name": "Alice", missing_quote}'  # bad JSON
    else:
        raw = '{"name": "Alice", "age": 30}'     # valid JSON
    return {"raw_output": raw, "attempts": state["attempts"] + 1}

def validate(state: RetryState) -> dict:
    try:
        parsed = json.loads(state["raw_output"])
        return {"parsed": parsed, "error": None}
    except json.JSONDecodeError as e:
        return {"parsed": None, "error": str(e)}

# 3. Define the conditional edge
def should_retry(state: RetryState) -> str:
    if state["error"] is None:
        return "done"
    if state["attempts"] >= 3:
        return "done"       # give up after 3 tries
    return "retry"

# 4. Build the graph
builder = StateGraph(RetryState)
builder.add_node("generate", generate)
builder.add_node("validate", validate)

builder.add_edge(START, "generate")
builder.add_edge("generate", "validate")
builder.add_conditional_edges(
    "validate",
    should_retry,
    {"retry": "generate", "done": END},
)

# 5. Compile and run
graph = builder.compile()
result = graph.invoke({
    "prompt": "Generate a JSON person object",
    "raw_output": "",
    "parsed": None,
    "error": None,
    "attempts": 0,
})

print(result["parsed"])    # {"name": "Alice", "age": 30}
print(result["attempts"])  # 3

Notice a few things about this code:

  1. State is explicit. RetryState is a TypedDict. Every field is declared up front. There are no hidden globals, no closures capturing mutable variables.
  2. Nodes are plain functions. generate and validate each take the current state and return a dictionary of updates. They do not need to know about the graph structure.
  3. Edges define control flow. The add_conditional_edges call is where the retry logic lives. The function should_retry inspects the state and returns a string that maps to the next node.
  4. The cycle is explicit. The mapping {"retry": "generate", "done": END} creates a backward edge from validate to generate. LangGraph knows about this cycle and will enforce the recursion limit.
  5. Compile, then invoke. The compile() step validates the graph structure (no orphan nodes, all edges resolve) and returns a runnable object. You invoke it like any other LangChain runnable.
Note

The compiled graph is a CompiledStateGraph object that implements the LangChain Runnable interface. This means you get .invoke(), .stream(), .batch(), and async variants for free. If you are already using LCEL, the compiled graph can be composed into larger chains.

What the Same Loop Looks Like Without LangGraph

To appreciate what LangGraph gives you, consider how you would implement the same retry loop using only LangChain and plain Python. This is not a contrived strawman—it is what many teams actually write before they discover LangGraph:

A retry loop without LangGraph

import json
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="gpt-4o-mini")
prompt = "Generate a JSON object with name and age fields."

max_attempts = 3
parsed = None
last_error = None

for attempt in range(max_attempts):
    if last_error:
        full_prompt = (
            f"{prompt}\n\nYour previous attempt failed: "
            f"{last_error}. Try again."
        )
    else:
        full_prompt = prompt

    response = llm.invoke(full_prompt)
    try:
        parsed = json.loads(response.content)
        break  # success
    except json.JSONDecodeError as e:
        last_error = str(e)

print(parsed)

This works for a simple case. But look at what you lose:

  • No persistence. If the process crashes on attempt 2, you start over from scratch. There is no checkpoint to resume from.
  • No visibility. You cannot inspect the state between attempts without adding print statements. There is no structured trace of which attempts failed and why.
  • No composability. If you later want to add a “human review” step before accepting the output, you are back to restructuring the loop. The control flow is tangled with the business logic.
  • Harder testing. Testing the retry logic means running the entire loop. With LangGraph, you can test each node in isolation and verify edge conditions with unit tests on the routing function.

The LangGraph version separates concerns cleanly. The what (generate, validate) lives in nodes. The when (retry or stop) lives in edges. The memory (attempts, errors, parsed output) lives in state. Each piece can be understood, tested, and modified independently.

The Pregel Heritage

LangGraph’s internal execution model draws inspiration from two systems in distributed computing: Google’s Pregel paper (2010) and Apache Beam. Understanding this lineage is not required to use LangGraph, but it explains certain design choices that might otherwise seem surprising.

Pregel was designed for processing large-scale graphs—think billions of web pages linked by hyperlinks. Its model is simple: computation proceeds in a series of “supersteps.” In each superstep, every vertex in the graph runs a user-defined function, reads messages sent to it in the previous superstep, and can send messages to other vertices for the next superstep. Vertices can also vote to halt. When all vertices have halted and no messages are in transit, the computation terminates.

LangGraph borrows several ideas from this model:

  • Superstep-like execution. LangGraph executes one node (or a set of parallel nodes) per step. After each step, state updates are merged, and the next node is determined by evaluating edges. This sequential-step model makes debugging straightforward: you can inspect the state after every single step.
  • State as shared messages. Instead of vertices sending messages to each other, nodes in LangGraph read from and write to a shared state object. The effect is similar—nodes communicate through data—but the single shared state is simpler for most AI orchestration use cases.
  • Explicit termination. A LangGraph execution ends when a node routes to the special END node, analogous to all Pregel vertices voting to halt. The recursion limit acts as a safety net to prevent infinite loops.

From Apache Beam, LangGraph takes the idea of reducers—functions that define how multiple updates to the same state key should be combined. For instance, a list of messages might use an “append” reducer (new messages are added to the end) rather than an “overwrite” reducer (the last value wins). We’ll explore reducers in depth in Chapter 2.

Don’t Over-Analogise

Pregel was built for massive distributed graph processing—PageRank over billions of nodes, shortest paths across the entire web. LangGraph solves a very different problem: orchestrating a handful of AI steps with rich state. The inspirations are real, but LangGraph is not a distributed computing framework. It runs in a single process (or via a deployment server), and its graphs typically have five to fifty nodes, not five billion.

Where LangGraph Fits in the Ecosystem

The LangChain ecosystem has grown into a family of complementary packages. Understanding where each piece fits will save you from importing the wrong thing or reinventing functionality that already exists.

  • langchain-core. The foundational abstractions: Runnable, BaseMessage, BaseTool, ChatPromptTemplate. This is the thin layer that defines interfaces. LangGraph uses some of these types (especially messages) but does not depend on the full langchain package.
  • langchain. The high-level framework with chains, agents, and retrieval helpers. Built on langchain-core. Great for linear workflows, RAG pipelines, and quick prototypes.
  • langgraph. The orchestration framework you are learning in this book. It provides the StateGraph class, conditional edges, checkpointing, and multi-agent primitives. It depends on langchain-core for shared types but not on langchain itself.
  • LangSmith. The observability platform. It traces LLM calls, chain executions, and—crucially—LangGraph steps. Each node invocation, state snapshot, and edge decision is logged as a trace span. Not required, but highly recommended for debugging and evaluation.
  • LangGraph Platform. A deployment solution that lets you deploy your compiled graph as a production API with built-in persistence, streaming, cron-triggered runs, and a task queue. Available as a cloud-hosted or self-hosted service.

The key takeaway: LangGraph is not a replacement for LangChain. It is a sibling that addresses a different class of problems. You can use LangGraph without ever importing langchain. You can also use both together, with LangChain components as the building blocks inside LangGraph nodes. Building Your Mental Model

Before we move on, let’s crystallise the mental model you’ll carry through the rest of this book. A LangGraph application has four fundamental ingredients:

  1. State. A typed dictionary (or Pydantic model) that represents everything the system knows at any point in time. Messages, intermediate results, counters, flags—they all live here.
  2. Nodes. Functions that do work. Each node receives the current state and returns a partial update. A node might call an LLM, run a tool, query a database, or simply compute a value. Nodes are deliberately simple—the complexity lives in the graph structure, not in any single node.
  3. Edges. Connections between nodes that define the flow. An edge can be unconditional (“after A, always go to B”) or conditional (“after A, go to B if the state says X, go to C if the state says Y”). Conditional edges are where your control logic lives.
  4. The Graph. The container that holds nodes and edges, compiles them into an executable, and manages the execution loop. After compilation, the graph is a Runnable that you invoke, stream, or batch—just like any other component in the LangChain ecosystem.

If you can hold these four concepts in your head, you have the foundation for everything that follows. Chapters 2 and 3 will go deep on each one. For now, the important thing is the shape: state flows through a graph of nodes connected by edges, and that graph can loop.

What LangGraph Is Not

It helps to be clear about boundaries. LangGraph is not:

  • A model. LangGraph does not contain or wrap an LLM. It orchestrates calls to models—any model, from any provider—but the model itself is always an external dependency.
  • A no-code builder. LangGraph is a Python (and JavaScript/TypeScript) library. You write code. LangGraph Studio provides a visual debugger, but you still define graphs in code.
  • An “AutoGPT” framework. LangGraph does not try to be an autonomous agent that figures out its own workflow. You define the graph; the framework executes it. The AI decides what to do within each node, but the overall flow is your design.
  • A distributed computing framework. Despite its Pregel inspiration, LangGraph runs in a single process. The LangGraph Platform can scale deployments, but the graph execution model is single-threaded (with support for parallel node execution within a single superstep).

These boundaries are features, not limitations. By staying focused on orchestration, LangGraph avoids the complexity bloat that plagues more ambitious frameworks. It does one thing well: it gives you control flow for multi-step AI systems, with state management built in.

Getting Ready

For the rest of this book, you will need:

  • Python 3.10 or later. LangGraph uses modern Python features including TypedDict, Annotated types, and the X | Y union syntax introduced in 3.10.
  • LangGraph installed. pip install langgraph. We’ll add complementary packages (like langchain-openai or langchain-anthropic) as needed in specific chapters.
  • An LLM API key. Most examples use a chat model. Any provider works—OpenAI, Anthropic, Google, or a local model via Ollama. We’ll show setup instructions when we first use each provider.
  • A code editor and terminal. Nothing fancy. The examples are designed to run as standalone scripts or in Jupyter notebooks.

import langgraph

Looking Ahead

In this chapter, we established why LangGraph exists: linear chains break down when your AI workflow needs cycles, persistent state, human checkpoints, or multi-agent collaboration. We saw the core abstraction—a stateful, cyclic graph where nodes are functions, edges are control flow, and a shared TypedDict carries everything the system knows. We built a concrete retry loop that would be awkward in a sequential chain but falls naturally out of LangGraph’s graph model.
