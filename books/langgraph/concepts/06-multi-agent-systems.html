07 Ship it, watch it, fix it

Production Patterns

You have a graph that works on your laptop. It handles branching, loops, human-in-the-loop pauses, and multi-agent coordination. Now a harder question arrives: what happens when a user is staring at a blank screen for twelve seconds while your LLM thinks? What happens when the API returns a 503 at 2 a.m.? What happens when a container restarts mid-run? This chapter is about the gap between “it works” and “it works in production.” We will walk through four areas—streaming, observability, deployment, and error handling—that turn a prototype into something you can ship with confidence.

Streaming: Show Progress as It Happens

The single most impactful change you can make for user experience is to stop waiting until the entire graph finishes before showing output. LangGraph’s streaming interface lets you push partial results to your client as soon as each node completes—or even as individual tokens arrive from an LLM call. The mechanism is straightforward: instead of calling graph.invoke(), you call graph.stream() and iterate over chunks.

Stream Modes

The stream_mode parameter controls what each chunk contains. LangGraph supports five modes, and choosing the right one depends on what your consumer needs.

Streaming modes and their use cases
Mode Each chunk yields Best for
"values" Full state after each node runs Debugging, UI that re-renders whole state
"updates" Only the keys a node changed Efficient frontends, incremental UI updates
"messages" LLM message objects as they arrive Chat interfaces showing token-by-token output
"events" Fine-grained lifecycle events Custom dashboards, logging pipelines
"custom" Whatever your node emits explicitly Progress bars, intermediate artifacts

The default mode is "values". In most production apps, you will want "updates" for efficiency or "messages" for chat-style token streaming. You can also pass a list of modes to receive multiple streams interleaved.

Streaming in Practice

Here is a concrete example. We have a simple two-node graph—one that retrieves documents, one that generates an answer—and we stream updates to see each node’s output the moment it finishes.

Streaming with “updates” mode

from langgraph.graph import StateGraph, START, END
from langchain_openai import ChatOpenAI
from typing import TypedDict, Annotated
import operator

class State(TypedDict):
    question: str
    documents: Annotated[list, operator.add]
    answer: str

def retrieve(state: State) -> dict:
    # Simulate retrieval
    docs = ["Doc A: LangGraph supports streaming.",
            "Doc B: Use stream_mode for control."]
    return {"documents": docs}

def generate(state: State) -> dict:
    llm = ChatOpenAI(model="gpt-4o-mini")
    context = "\n".join(state["documents"])
    prompt = f"Answer based on:\n{context}\n\nQuestion: {state['question']}"
    response = llm.invoke(prompt)
    return {"answer": response.content}

graph = StateGraph(State)
graph.add_node("retrieve", retrieve)
graph.add_node("generate", generate)
graph.add_edge(START, "retrieve")
graph.add_edge("retrieve", "generate")
graph.add_edge("generate", END)

app = graph.compile()

# Stream updates as each node completes
for chunk in app.stream(
    {"question": "How does LangGraph handle streaming?"},
    stream_mode="updates"
):
    # chunk is a dict: {"node_name": {changed_keys}}
    for node_name, updates in chunk.items():
        print(f"Node '{node_name}' updated: {list(updates.keys())}")

When you run this, you see Node ’retrieve’ updated: [’documents’] appear immediately after retrieval finishes, without waiting for the generate step. The user knows something is happening.

Streaming Tokens from LLM Calls

Node-level streaming is good, but for chat applications you want tokens as they emerge from the language model. The "messages" stream mode does exactly this. Each chunk contains an AIMessageChunk with partial content as it arrives from the provider.

Token-level streaming with “messages” mode

# Stream individual tokens from LLM calls
for chunk in app.stream(
    {"question": "Explain streaming in LangGraph."},
    stream_mode="messages"
):
    msg, metadata = chunk
    # msg is an AIMessageChunk during generation
    if msg.content:
        print(msg.content, end="", flush=True)

The tuple returned by each chunk includes the message object and metadata telling you which node produced it. This lets you build a typewriter effect in a chat UI while still distinguishing output from different nodes if your graph has multiple LLM calls.

Fine-Grained Events with astream_events

For maximum control, the async method astream_events emits structured events for every significant moment in the graph’s lifecycle: node starts, node ends, LLM token emissions, tool calls, retries, and more. Each event carries a name, a run ID, and data that you can filter, route, or log however you need.

Using astream_events for detailed tracing

async for event in app.astream_events(
    {"question": "What is LangGraph?"},
    version="v2"
):
    kind = event["event"]
    if kind == "on_chat_model_stream":
        token = event["data"]["chunk"].content
        if token:
            print(token, end="", flush=True)
    elif kind == "on_chain_start":
        print(f"\n--- Node started: {event['name']} ---")

The version="v2" parameter selects the current event schema. Use astream_events when you need to build custom monitoring dashboards, pipe events to external systems, or implement sophisticated progress indicators that go beyond what the simpler stream modes offer.

Custom Stream Emissions

Sometimes you want to emit something that is neither state nor LLM tokens—a progress percentage, an intermediate image URL, or a status message. Inside any node function, you can use the writer callback from the RunnableConfig to push custom data to clients streaming with stream_mode="custom".

Emitting custom stream data from a node

from langgraph.config import get_stream_writer

def process_documents(state: State) -> dict:
    writer = get_stream_writer()
    docs = state["documents"]
    for i, doc in enumerate(docs):
        # ... process document ...
        writer({"progress": (i + 1) / len(docs), "current_doc": doc.id})
    return {"processed": True}

On the client side, chunks from stream_mode="custom" will contain exactly the dictionaries you passed to the writer. This is how you build rich progress indicators without polluting your graph state.

Observability with LangSmith

Streaming tells your users what’s happening. Observability tells you what’s happening. When a graph produces an unexpected answer, you need to trace the execution path: which nodes ran, what state they saw, what the LLM received and returned, and where things diverged from your expectations. LangSmith provides this tracing layer.

Setting Up LangSmith Integration

Integration requires setting environment variables before your graph runs. LangSmith is opt-in—your code does not change, and you do not import anything new.

Environment variables for LangSmith tracing

# Enable tracing
export LANGSMITH_TRACING="true"
export LANGSMITH_API_KEY="lsv2_pt_..."
export LANGSMITH_PROJECT="my-production-graph"

Once these are set, every graph.invoke() or graph.stream() call is automatically traced. Each trace appears in the LangSmith dashboard as a hierarchical tree of runs—the graph execution at the top, each node as a child, and each LLM call or tool invocation nested under its node.

Tracing Execution Through the Graph

A LangSmith trace for a LangGraph execution shows you several things that are difficult to reconstruct from logs alone:

  • Execution order—which nodes ran and in what sequence, including parallel branches
  • State snapshots—the full state before and after each node, so you can see exactly how data transformed
  • LLM inputs and outputs—the exact prompts sent to the model and the responses returned
  • Latency breakdown—how long each node took, making bottlenecks visible
  • Token counts and costs—per-call and aggregate token usage across the entire graph run
  • Error details—full stack traces when nodes fail, with the state that caused the failure

Debugging Failed Runs

When a production run fails, LangSmith lets you filter by error status, locate the failing node, inspect the state it received, and see the full exception. Because LangGraph checkpoints state at each step, you can even reproduce the failure by replaying from the checkpoint just before the error—no need to reconstruct the user’s entire input sequence.

You can also add custom metadata to make traces easier to find. Pass a config dictionary with tags or metadata to any invocation.

Adding metadata to a traced run

result = app.invoke(
    {"question": "What is streaming?"},
    config={
        "tags": ["production", "v2.1"],
        "metadata": {
            "user_id": "usr_abc123",
            "session_id": "sess_xyz789"
        }
    }
)

Now in LangSmith you can search for all runs tagged "production", filter by user ID, or find every run in a particular session. This is essential for customer support scenarios where you need to understand what the system did for a specific user.

Tracing overhead

LangSmith tracing adds minimal latency because traces are sent asynchronously in a background thread. The overhead is typically under 1 millisecond per traced call. In high-throughput scenarios, you can reduce volume by sampling: set LANGSMITH_TRACING_SAMPLE_RATE to a value between 0 and 1 to trace only a fraction of runs.

Deployment Considerations

A graph running in a Jupyter notebook or a CLI script is not the same as a graph running behind an API that serves thousands of concurrent requests. Deployment adds requirements around packaging, serving, scaling, and lifecycle management. LangGraph provides several paths depending on your constraints.

LangGraph Platform

LangGraph Platform is the managed infrastructure layer purpose-built for deploying LangGraph applications. It provides a standardized API server that wraps your graph in REST endpoints, handles persistence with built-in checkpointing, manages background runs, and supports streaming out of the box. The platform comes in two flavors: a fully managed cloud offering and a self-hosted option where you run the same infrastructure on your own machines.

The langgraph.json Configuration File

At the heart of any LangGraph deployment is a langgraph.json file that declares your graphs, dependencies, and environment configuration.

A langgraph.json configuration file

{
    "dependencies": ["."],
    "graphs": {
        "qa_agent": "./src/agent.py:graph"
    },
    "env": ".env",
    "python_version": "3.11"
}

The "graphs" field maps a name to a Python module path and variable. LangGraph Platform uses this to locate your compiled graph object. The "dependencies" field points to directories or requirements files. The "env" field tells the platform where to find your environment variables.

Local Development with LangGraph CLI

Before deploying to the cloud, you can run the same platform API server locally using the LangGraph CLI.

Starting a local development server

# Install the CLI
pip install langgraph-cli

# Start the local dev server
langgraph dev

This spins up a local API server (by default on port 8123) that mirrors the production LangGraph Platform API. You get the same REST endpoints, the same streaming behavior, and the same checkpointing—all running on your machine. It hot-reloads when you change your graph code, making the development loop fast.

REST API Endpoints

Whether running locally or in the cloud, LangGraph Platform exposes a consistent set of REST endpoints for interacting with your deployed graph. The most important ones are:

  • POST /threads/{thread_id}/runs—start a new graph run
  • POST /threads/{thread_id}/runs/stream—start a run and stream results via server-sent events
  • GET /threads/{thread_id}/state—retrieve the current state of a thread
  • GET /threads/{thread_id}/history—fetch the state history for checkpointing and replay
  • POST /threads—create a new thread (conversation)

The thread-based API is a natural fit for conversational applications. Each thread maintains its own checkpoint history, so separate conversations are isolated. You can also use the Python or JavaScript SDK to interact with these endpoints without constructing HTTP requests manually.

Using the LangGraph SDK to interact with a deployed graph

from langgraph_sdk import get_client

client = get_client(url="http://localhost:8123")

# Create a thread
thread = await client.threads.create()

# Stream a run
async for chunk in client.runs.stream(
    thread["thread_id"],
    "qa_agent",  # graph name from langgraph.json
    input={"question": "What is LangGraph?"},
    stream_mode="updates"
):
    print(chunk)

Comparing Deployment Options

Your choice depends on your operational maturity, compliance requirements, and budget. Here is how the options compare:

LangGraph deployment options comparison
Option Hosting Operational effort Scaling Best for
LangGraph Cloud Fully managed by LangChain Minimal—deploy via GitHub Automatic Teams wanting fast iteration, no infra management
Self-Hosted Platform Your infrastructure (K8s, Docker) Moderate—you manage containers You configure Compliance-sensitive orgs, data residency requirements
Bring Your Own Server Any Python hosting (EC2, Cloud Run, etc.) Higher—you handle everything You manage Existing infra, maximum control, simple graphs
Local Dev Server Your laptop via langgraph dev None N/A Development, testing, prototyping
Cloud vs. self-hosted

LangGraph Cloud and the self-hosted platform run the same API server and support the same features—streaming, checkpointing, cron jobs, background runs, and double-texting handling. The difference is purely operational: who manages the infrastructure. If you start with Cloud, migrating to self-hosted later is straightforward because the API surface is identical.

Error Handling and Durable Execution

LLM applications fail in ways that traditional software does not. API rate limits, transient network errors, model timeouts, and content filter rejections are all routine in production. LangGraph provides structured mechanisms for handling these failures without littering your node functions with try/except blocks.

RetryPolicy for Transient Failures

The most common production failure is a transient API error—a 429 rate limit, a 503 service unavailable, or a network timeout. These resolve on their own if you wait and try again. LangGraph’s RetryPolicy automates this pattern with configurable backoff.

Configuring RetryPolicy on a node

from langgraph.pregel import RetryPolicy

# Define a retry policy with exponential backoff
retry = RetryPolicy(
    max_attempts=3,            # Try up to 3 times total
    initial_interval=1.0,      # Wait 1 second before first retry
    backoff_factor=2.0,        # Double the wait each time: 1s, 2s
    max_interval=10.0,         # Never wait more than 10 seconds
    retry_on=lambda exc: isinstance(exc, (TimeoutError, ConnectionError))
)

graph = StateGraph(State)
graph.add_node(
    "call_llm",
    call_llm_function,
    retry=retry  # Attach the retry policy to this node
)
graph.add_node(
    "search_web",
    search_function,
    retry=RetryPolicy(max_attempts=5)  # More retries for flaky APIs
)

Notice the retry_on parameter. By default, RetryPolicy retries on any exception. In practice, you want to be more selective: retry on network errors and rate limits, but not on ValueError from your own code (that indicates a bug, not a transient failure). The retry_on callable receives the exception and returns True if a retry should be attempted.

When a retry is triggered, LangGraph does not re-execute the entire graph—it only retries the specific node that failed. The rest of the graph’s state remains intact thanks to checkpointing. If all retry attempts are exhausted, the exception propagates to the caller.

Error Handlers on Nodes

Sometimes retrying is not the right response. If an LLM call fails because the input is too long, retrying will fail every time. Instead, you want to catch the error and take an alternative path—maybe truncate the input, use a smaller model, or return a fallback response. LangGraph lets you attach error handlers at the node level.

Error handler that provides a fallback response

from langgraph.graph import StateGraph, START, END

def generate_answer(state: State) -> dict:
    # This might fail: context too long, model overloaded, etc.
    llm = ChatOpenAI(model="gpt-4o")
    response = llm.invoke(state["prompt"])
    return {"answer": response.content}

def handle_generation_error(state: State, error: Exception, config) -> dict:
    # Fallback: use a shorter prompt with a cheaper model
    print(f"Primary generation failed: {error}")
    llm = ChatOpenAI(model="gpt-4o-mini")
    short_prompt = state["prompt"][:2000]  # Truncate aggressively
    response = llm.invoke(short_prompt)
    return {
        "answer": response.content,
        "used_fallback": True
    }

graph = StateGraph(State)
graph.add_node(
    "generate",
    generate_answer,
    error_handler=handle_generation_error
)
graph.add_edge(START, "generate")
graph.add_edge("generate", END)
app = graph.compile()

The error handler receives the same state the original node received, plus the exception that was raised and the config. It returns a state update just like a normal node function. From the graph’s perspective, the node succeeded—the handler’s return value replaces the failed node’s output. This lets the rest of the graph continue executing normally.

Error handlers and retry policies work together. If a node has both, retries are attempted first. Only after all retry attempts are exhausted does the error handler fire. This gives you a layered strategy: retry transient failures, then fall back gracefully for persistent ones.

Timeout Policies

LLM calls can hang indefinitely if the provider has issues. A timeout prevents a single slow node from blocking your entire graph. You can set timeouts at the node level.

Setting a timeout on a node

graph.add_node(
    "slow_analysis",
    analyze_documents,
    retry=RetryPolicy(max_attempts=2),
    # If the node doesn't complete within 30 seconds, it raises a TimeoutError
    metadata={"timeout": 30}
)

When a timeout fires, the node raises a TimeoutError. If the node has a retry policy that covers TimeoutError, it will retry. If it has an error handler, the handler will fire after retries are exhausted. This creates a robust execution chain: try the node, time out if it hangs, retry a few times, fall back if it still fails.

Durable Execution

Here is a scenario that keeps production engineers up at night: a multi-step agent is ten minutes into a complex task. It has called six tools, accumulated context, and is about to deliver the final answer. Then the container restarts. Without durable execution, the entire run is lost. The user has to start over.

LangGraph solves this through its checkpointing system, which you met in the chapter on persistence. In a production deployment, checkpointing is not just about human-in-the-loop workflows—it is the foundation of durable execution. After each node completes, the graph’s full state is persisted to a checkpoint store (Postgres in production, SQLite for local development). If the process dies, the graph can resume from the last checkpoint rather than restarting from scratch.

Durable execution guarantees

Durable execution means your graph survives process restarts. LangGraph achieves this by checkpointing state after each node execution. When the graph resumes, it replays from the last successful checkpoint—nodes that already completed are skipped, and execution picks up exactly where it left off. This is critical for long-running agents that might take minutes or hours to complete. It also means that deploying new code does not kill in-flight runs: they continue from their last checkpoint on the new version of the container.

Durable execution requires no special configuration beyond having a persistent checkpointer. On LangGraph Platform, this is set up automatically with a PostgreSQL-backed store. For self-hosted deployments, you configure the checkpointer in your graph compilation.

Compiling a graph with a persistent checkpointer

from langgraph.checkpoint.postgres import PostgresSaver

# Connect to your Postgres database
checkpointer = PostgresSaver.from_conn_string(
    "postgresql://user:pass@localhost:5432/langgraph"
)

# Compile with the persistent checkpointer
app = graph.compile(checkpointer=checkpointer)

# Now every run is durable:
# - State is saved after each node
# - Runs survive process restarts
# - You can resume from any checkpoint
config = {"configurable": {"thread_id": "user-123-session-1"}}
result = app.invoke(input_data, config=config)

If the process crashes mid-run, you resume by invoking the same thread ID with None as input. The graph reads the last checkpoint, determines which node was executing, and resumes from there.

Resuming a graph after a process restart

# After process restart, resume with the same thread_id
config = {"configurable": {"thread_id": "user-123-session-1"}}

# Pass None to resume from the last checkpoint
result = app.invoke(None, config=config)

Putting It All Together

In a production graph, you combine all of these patterns. Each node gets a retry policy tuned to its specific failure modes, error handlers provide fallback behavior, timeouts prevent hangs, and the whole system is durably checkpointed so nothing is lost to infrastructure failures.

A production-ready graph with full error handling

from langgraph.graph import StateGraph, START, END
from langgraph.pregel import RetryPolicy
from langgraph.checkpoint.postgres import PostgresSaver

# Different retry policies for different failure profiles
llm_retry = RetryPolicy(
    max_attempts=3,
    initial_interval=1.0,
    backoff_factor=2.0,
    max_interval=10.0
)

api_retry = RetryPolicy(
    max_attempts=5,
    initial_interval=0.5,
    backoff_factor=1.5,
    max_interval=30.0
)

graph = StateGraph(State)

graph.add_node("retrieve", retrieve_docs, retry=api_retry)
graph.add_node(
    "generate",
    generate_answer,
    retry=llm_retry,
    error_handler=fallback_generate
)
graph.add_node("validate", validate_output)

graph.add_edge(START, "retrieve")
graph.add_edge("retrieve", "generate")
graph.add_edge("generate", "validate")
graph.add_edge("validate", END)

# Durable checkpointing
checkpointer = PostgresSaver.from_conn_string(DB_URL)
app = graph.compile(checkpointer=checkpointer)

A Production Readiness Checklist

Before you ship, walk through this list. Each item maps back to a pattern we covered in this chapter:

  1. Streaming enabled—your API or UI uses stream() rather than invoke() for any user-facing interaction, so users see progress immediately
  2. Tracing configured—LangSmith environment variables are set, and you have tagged your runs with version and user metadata for searchability
  3. Retry policies on external calls—every node that calls an LLM or external API has a RetryPolicy with appropriate backoff and exception filtering
  4. Error handlers for critical nodes—nodes where failure would break the user experience have fallback logic via error handlers
  5. Timeouts on slow nodes—nodes that call external services have timeouts to prevent indefinite hangs
  6. Persistent checkpointing—a PostgreSQL or equivalent checkpointer is configured so runs survive process restarts
  7. langgraph.json defined—your deployment configuration file exists and correctly references your graph
  8. Local dev server tested—you have run langgraph dev and verified the REST API behaves as expected before deploying
Side effects and retries

When you add retry policies, make sure your node functions are safe to call multiple times. If a node sends an email, charges a credit card, or writes to a database, a retry could duplicate that side effect. Either make these operations idempotent (using idempotency keys) or move side-effect-producing logic after the retry boundary. This is not a LangGraph-specific concern—it is the oldest lesson in distributed systems—but it catches people off guard when they first add retries to an LLM pipeline.

What You Have Learned

Production is not a single feature—it is a layer of patterns applied consistently. Streaming transforms user experience by showing work in progress rather than hiding behind a spinner. Observability with LangSmith gives you the ability to trace, debug, and understand what your graph does in the real world. Deployment options range from fully managed cloud to self-hosted infrastructure, all sharing the same API surface. And error handling—retry policies, error handlers, timeouts, and durable execution—ensures your graph keeps running even when the external services it depends on do not.
