Chapter four

The Discovery Engine

Stage two is where the grounded brief from chapter 3 turns into an actual solution — code that runs, produces a score, and either works or doesn't. The paper's summaries describe this component, the Discovery Engine, as running a parallel explore-exploit search tree over candidate solutions. Let's take that apart term by term, because each half of the name is doing real work.

Explore, exploit, and why you need both

"Explore-exploit" is an old idea from decision theory, and the tension it names is simple: do you try something new that might be better, or do you keep refining the best thing you've already found? Pure exploration wanders forever without committing to anything good. Pure exploitation gets stuck polishing the first mediocre idea it tried. A search that's any good at finding solutions to hard problems has to do both, and has to decide, continuously, which one to do next.

"Parallel" is the second half of the description, and it's what makes this tractable at the scale a real research task demands: rather than trying one candidate solution at a time, the Discovery Engine runs multiple branches of the tree at once — some still exploring fresh approaches, others exploiting a branch that already scored well — and the tree's shape (which branches get more budget, which get abandoned) is what the search is actually optimizing.

What discovery contributes to the evidence chain

Recall from chapter 2's evidence-card examples: a numerical claim has to trace back to a recorded run output. This is the stage where that recorded output gets made. Every branch of the search tree that actually runs — explored or exploited, kept or dropped — produces a real execution record. When the paper's results table later reports a score, that number isn't typed in from memory of how the run "should" have gone; it's read off one specific, identifiable branch of this tree.

"our solution scores 1.0600 on Parameter Golf, state of the art"

A concrete case: Parameter Golf

One of the generalization tasks the paper evaluates on is Parameter Golf, a task with strict submission constraints — among them, an artifact size limit of 16MB. This is exactly the kind of constraint an explore-exploit search has to respect as it searches, not discover after the fact: a candidate solution that scores brilliantly but produces a 20MB artifact isn't a valid submission at all.

The results bear this out in a way that's almost a controlled experiment on its own. One of the baseline systems evaluated on Parameter Golf failed to produce a valid submission at all — its output exceeded the 16MB limit. ScientistOne, by contrast, adhered to the declared constraint and reached a state-of-the-art score of 1.0600. Same task, same rules, and one system's search simply didn't treat the constraint as binding until it was too late to matter.

Why this belongs in a book about evidence

It's tempting to read the Parameter Golf result as purely an optimization story — one search found a better solution than another. But look again: the failing baseline's problem wasn't a worse score, it was a submission that couldn't be verified against the task's own rules at all. A search that respects task constraints as it explores is a search whose eventual claim ("state of the art") actually has something to trace to. A search that ignores them produces nothing to check in the first place.

So what did we actually gain?

A concrete sense of how discovery works — parallel branches trading off exploring new ideas against exploiting good ones — and why that stage matters to the evidence chain specifically: every numerical claim later in the paper traces back to one identifiable, constraint-respecting run this stage actually performed.
