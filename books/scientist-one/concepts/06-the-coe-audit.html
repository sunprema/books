Chapter six

The CoE Audit

Everything so far has been about ScientistOne checking itself as it works — the Problem Investigator grounding its brief, the Discovery Engine producing real run records, the Claim Verifier gating what ships. That's all self-reported discipline. For it to mean anything to a skeptical reader, you need a check that doesn't trust the system being checked — one that works identically whether it's pointed at ScientistOne or at a baseline that never heard of Chain-of-Evidence. That's the CoE Audit.

Post-hoc, and uniform

Two words in the paper's description do most of the work here. Post-hoc means the audit runs on a finished paper and its submitted code — it doesn't need access to the system's internal evidence records, its search tree, or any cooperation from the system that produced the output at all. Uniform means the same four checks apply to every system in the comparison, baseline or not, with no special-casing. That combination is what makes the audit's numbers comparable across systems that were never designed with CoE in mind.

Why this design choice matters

A verification method that only works on systems built to cooperate with it can't tell you anything about the systems that aren't. The CoE Audit's whole evidentiary value in this paper comes from being able to point the same four checks at ScientistOne and at four baseline systems that have no CoE machinery at all, and get numbers that mean the same thing on both sides.

The four checks

The audit is organized as four integrity checks, each targeting a different way a paper can fail to be what it claims. It's worth resisting the urge to collapse these into a single "quality score" — each one catches something the others structurally cannot.

  1. I1 — Score verificationextract the reported score, compare it to an independent re-run of the submitted code
  2. I2 — Specification violationinspect the solution code to confirm it solves the task honestly, not by exploiting the evaluator metric or reading ground-truth answer files
  3. I3 — Reference verificationcross-check every bibliography entry against real sources to catch hallucinated references
  4. I4 — Method-code alignmentverify the paper's method description actually matches the submitted implementation

Look at what each one would catch that the others would miss. A system could pass I1 — its reported score really does reproduce — while failing I2, because the code that produces that reproducible score is quietly reading the answer key instead of solving the problem. A system could pass I3, with every reference real, while failing I4, because the method section describes an algorithm the code doesn't actually run. Each check is a different lie detector, aimed at a different place a paper can lie.

I2 deserves a second look

Specification violation is the subtlest of the four, so it's worth dwelling on. This check isn't asking "does the code run and produce a number" — that's I1's job. It's asking whether the number the code produces was earned honestly against the task's actual rules. A solution that peeks at held-out answers, or that special-cases the exact metric function instead of solving the underlying problem, can produce a perfect, perfectly reproducible score while having done none of the work the task was designed to measure. I1 alone would wave that straight through; I2 exists specifically to catch it.

Specification violation (I2) ⚠ what it's designed to catch

A solution that reads a held-out ground-truth file directly, or hard-codes a shortcut against the evaluator's own scoring function, rather than solving the stated task.

code inspection against the task's declared rules — not the score the code happens to output

Reading a pass rate correctly

Because each check is binary per paper — a given paper's score either reproduces under I1 or it doesn't — the audit can report results as simple pass-rate fractions across a paper set, like "12 of 12" or "14 of 15." That format is deliberately legible: no averaging, no hidden weighting between checks, just a count of papers that cleared a specific, named bar. We'll read the actual fractions — for ScientistOne and for the baselines it's compared against — in the next chapter.

Four checks, aimed at four different lies a paper can tell, applied the same way to every system in the room.

So what did we actually gain?

A verification method that doesn't have to trust the system it's checking — post-hoc, uniform, and split into four independent checks so a pass on one doesn't paper over a failure on another. This is the instrument the paper's headline numbers were measured with, which makes it the right thing to understand before reading those numbers in chapter 7.
