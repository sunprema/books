Chapter eight

Traits and Generics

Rust has no inheritance, so this is where abstraction lives. A trait says what a type can do; a generic writes code once for every type that can do it. Together they are the reason the standard library is as small as it is.

Generics

fn largest<T: PartialOrd>(items: &[T]) -> &T {
    let mut best = &items[0];
    for it in items {
        if it > best { best = it; }
    }
    best
}

struct Pair<T> { a: T, b: T }

T: PartialOrd is a trait bound. It is not documentation — without it, it > best does not compile, because nothing yet says a T can be compared. Rust generics are checked once, at the definition, rather than at each instantiation; there is no C++-template surprise where the error appears four layers into someone else's header.

At compile time the generic is monomorphised: a specialised copy is emitted per concrete type used. A generic call is therefore exactly as fast as a hand-written one. You pay in binary size and compile time, which is the trade the whole language keeps making.

Traits

trait Drawable {
    fn draw(&self) -> String;         // required
    fn label(&self) -> &str { "shape" }  // default method
}

struct Circle { r: f64 }
struct Square { s: f64 }

impl Drawable for Circle {
    fn draw(&self) -> String { format!("circle r={}", self.r) }
    fn label(&self) -> &str { "circle" }
}

impl Drawable for Square {
    fn draw(&self) -> String { format!("square s={}", self.s) }
}

A trait can be implemented for any type, including types you didn't write — with one restriction. The orphan rule says either the trait or the type must be local to your crate. Otherwise two crates could each add a different Display for Vec<u8> and linking them would be undecidable. The escape hatch is the newtype from chapter 5.

Writing bounds

// all four of these say the same thing
fn show<T: Drawable>(x: &T) { }
fn show(x: &impl Drawable) { }
fn show<T>(x: &T) where T: Drawable { }
fn show<T: Drawable + Clone>(x: &T) { }   // (plus one more bound)

Use impl Trait in argument position for the short cases and a where clause once the signature grows past a line. In return position, impl Trait means something different: "one specific type that I'm not naming". That is how you return a closure or an iterator without writing out its unspeakable type. 

fn evens(limit: u32) -> impl Iterator<Item = u32> {
    (0..limit).filter(|n| n % 2 == 0)
}

Edition 2024 changed one rule here

A return-position impl Trait now implicitly captures all in-scope generic parameters, including lifetimes, unless you say otherwise with a use<…> bound. In practice this removes a class of "hidden type captures lifetime" errors that used to need a workaround; if you read older Rust advice about Captures<'a> helper traits, that is what it was for.

Static or dynamic dispatch

Generics give you one function per concrete type, chosen at compile time. Sometimes you need the opposite: a single collection holding circles and squares. That needs a trait object. 

let shapes: Vec<Box<dyn Drawable>> = vec![
    Box::new(Circle { r: 1.0 }),
    Box::new(Square { s: 2.0 }),
];
for s in &shapes { println!("{}", s.draw()); }

Implement From, never Into — a blanket impl in the standard library gives you Into for free the moment you write From. That blanket impl is itself a nice demonstration of the system: impl<T, U: From<T>> Into<U> for T, written once, applying forever.

Before you continue

Define a small trait — Drawable, Serializable, whatever fits your chapter 5 domain — with one required method and one default method. Implement it for two types. Then write the same function twice: once generic over T: YourTrait, once taking &[Box<dyn YourTrait>], and note which one you could not have written the other way.
