Chapter nine

Closures, Iterators, and Functional Style

Rust is not a functional language, but its iterators are the best argument for functional style you will find in a systems language: expressive to write, and compiled down to the loop you would have written by hand.

Closures

let add = |a: i32, b: i32| a + b;
let add = |a, b| a + b;              // types inferred from use

let threshold = 10;
let over = |n: &i32| *n > threshold;   // captures `threshold`

let data = vec![1, 2, 3];
let owns = move || data.len();          // `move`: takes data by value

A closure captures whatever its body needs, and captures it as weakly as it can get away with — by shared reference if it only reads, by mutable reference if it mutates, by value if it must. move forces the last of those, which is what you need when the closure outlives the scope (a thread, an async task, a returned callback).

Fn
only reads its captures; callable many times, even shared.
FnMut
mutates its captures; callable many times, exclusively.
FnOnce
consumes its captures; callable once. Every closure is at least this.

You do not choose which one a closure is — the compiler works it out from the body. You only care when writing a function that takes a closure, where the bound you ask for decides what your callers may pass. Ask for the weakest one that works, which is usually FnMut for a callback and FnOnce for something you'll run once.

Iterators are lazy

This is the point everything else hangs off. map does not map. It builds an object that will map, when something asks it for values. 

let it = readings.iter().map(|r| r.value);   // nothing has happened
let v: Vec<f64> = it.collect();               // now it runs, once

Laziness is why a chain of ten adaptors makes exactly one pass over the data and allocates nothing in between. It is also why a chain you never consume does nothing at all — the compiler warns, because Iterator is marked #[must_use].

Those are the three for loops from chapter 6, named. When a closure in a chain gets a &&T and the compiler complains about comparing references, you almost always wanted .copied(), .cloned(), or a *.

The adaptors worth knowing

let total: u32 = readings
    .iter()
    .filter(|r| r.valid)
    .map(|r| r.value)
    .sum();

let names: Vec<&str> = people
    .iter()
    .filter_map(|p| p.nickname.as_deref())   // filter + map in one
    .take(5)
    .collect();

let longest = words.iter().max_by_key(|w| w.len());  // Option<&&str>
let any_bad = rows.iter().any(|r| r.is_err());
let folded = nums.iter().fold(String::new(), |mut acc, n| {
    acc.push_str(&n.to_string());
    acc
});

Roughly: map transforms, filter selects, filter_map does both and drops the Nones, enumerate pairs with an index, zip pairs two iterators, chain concatenates, rev reverses, take/skip slice the stream, and flat_map flattens. The consumers are collect, sum, count, fold, find, any/all, min/max, and for.

collect is stranger than it looks

collect is generic over what it builds, so the annotation is what decides the result. The same chain can produce four different things: 

let v: Vec<i32>                = xs.iter().copied().collect();
let s: String                  = chars.iter().collect();
let m: HashMap<_, _>           = pairs.into_iter().collect();
let r: Result<Vec<i32>, _>    = lines.iter().map(|l| l.parse()).collect();

That last one is a small piece of magic worth internalising. Collecting an iterator of Results into a Result<Vec<_>, _> short-circuits: it stops at the first Err and returns it. Collect into Vec<Result<_, _>> instead and you keep every outcome. Two annotations, two entirely different error policies, no control flow written.

When a chain won't compile, the type annotation is usually the fix, not the chain.

Iterators or indexing?

Prefer iterators. They read as what you meant rather than how you got there, they cannot go out of bounds, and they compile to the same machine code — iterators are the standard demonstration of Rust's "zero-cost abstraction" claim, and the claim holds.

Index when the arithmetic is the algorithm — sliding windows you can't express with windows(), in-place partitioning, matrix strides. And break the chain when it gets long: three or four adaptors read well, nine do not. A for loop with a clear body is not a failure of style.

Before you continue

Take a Vec of strings and, in one chain, parse each to a number, drop the failures, keep the even ones, and sum them. Then write the version that fails on the first bad parse by collecting into Result<Vec<i32>, _>. The difference between those two is one type annotation, and that is the point.
