Chapter thirteen

A Small Project

Let's build one thing end to end: logstat, a command-line tool that reads a log file and reports how many lines hit each status code. Small enough to hold in your head, big enough to use structs, enums, traits, iterators, errors, modules and tests — which is to say, the whole book.

Project structure

logstat/
  Cargo.toml
  src/
    main.rs        # argument handling and printing. Thin.
    lib.rs         # the public API: run(), Report
    parse.rs       # one line -> one Entry
    error.rs       # LogError
  tests/
    end_to_end.rs  # uses only the public API

The split is the point. Logic in the library, process concerns in the binary. It costs one extra file and it is what makes the thing testable — an integration test can call logstat::run without spawning a process or capturing stdout.

Core types

// src/lib.rs
pub mod error;
mod parse;

pub use error::LogError;

use std::collections::BTreeMap;

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Class { Ok, Redirect, ClientError, ServerError }

impl Class {
    fn of(status: u16) -> Option<Self> {
        match status {
            200..=299 => Some(Class::Ok),
            300..=399 => Some(Class::Redirect),
            400..=499 => Some(Class::ClientError),
            500..=599 => Some(Class::ServerError),
            _ => None,
        }
    }
}

#[derive(Debug, Default)]
pub struct Report {
    pub counts: BTreeMap<u16, usize>,
    pub skipped: usize,
}

Class::of returns Option rather than a Class::Unknown variant — an unrecognised status isn't a class, it's the absence of one, and the type should say so. BTreeMap rather than HashMap because the report should come out in a stable order.

The error type

// src/error.rs
use std::fmt;

#[derive(Debug)]
pub enum LogError {
    Io { path: String, source: std::io::Error },
    Empty(String),
}

impl fmt::Display for LogError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            LogError::Io { path, source } => write!(f, "{path}: {source}"),
            LogError::Empty(path) => write!(f, "{path}: no parsable lines"),
        }
    }
}

impl std::error::Error for LogError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self {
            LogError::Io { source, .. } => Some(source),
            LogError::Empty(_) => None,
        }
    }
}

Note the path field. A bare io::Error says "No such file or directory" and leaves the user guessing which file. An error type is a place to keep context, and adding it is usually the difference between a usable CLI and an annoying one.

Parsing and IO

// src/parse.rs
pub fn status_of(line: &str) -> Option<u16> {
    // …a common-log-format line: the status is the 9th field
    line.split_whitespace().nth(8)?.parse().ok()
}

// src/lib.rs
use std::fs::File;
use std::io::{BufRead, BufReader};

pub fn run(path: &str) -> Result<Report, LogError> {
    let file = File::open(path)
        .map_err(|source| LogError::Io { path: path.into(), source })?;

    let mut report = Report::default();

    for line in BufReader::new(file).lines() {
        let line = line
            .map_err(|source| LogError::Io { path: path.into(), source })?;
        match parse::status_of(&line).filter(|s| Class::of(*s).is_some()) {
            Some(s) => *report.counts.entry(s).or_insert(0) += 1,
            None => report.skipped += 1,
        }
    }

    if report.counts.is_empty() {
        return Err(LogError::Empty(path.into()));
    }
    Ok(report)
}

BufReader::new(file).lines() streams: memory stays flat whether the log is a kilobyte or forty gigabytes. Compare fs::read_to_string, which is perfect for a config file and catastrophic here. Each line is itself a Result, because a read can fail halfway through.

The binary

// src/main.rs
use std::process::ExitCode;

fn main() -> ExitCode {
    let Some(path) = std::env::args().nth(1) else {
        eprintln!("usage: logstat <file>");
        return ExitCode::from(2);
    };

    match logstat::run(&path) {
        Ok(report) => {
            for (status, n) in &report.counts {
                println!("{status:>5}  {n}");
            }
            eprintln!("({} lines skipped)", report.skipped);
            ExitCode::SUCCESS
        }
        Err(e) => {
            eprintln!("logstat: {e}");
            ExitCode::FAILURE
        }
    }
}

Results to stdout, diagnostics to stderr, non-zero exit on failure — that's what makes a tool composable in a pipeline. main can also return Result<(), E> directly, which is shorter but prints the Debug form and always exits 1; ExitCode is what you want once the exit status matters.

Tests

// tests/end_to_end.rs — sees only the public API
use std::io::Write;

#[test]
fn counts_by_status() {
    let mut f = tempfile::NamedTempFile::new().unwrap();
    writeln!(f, r#"h - - [d] "GET / HTTP/1.1" 200 12"#).unwrap();
    writeln!(f, r#"h - - [d] "GET /x HTTP/1.1" 404 0"#).unwrap();

    let r = logstat::run(f.path().to_str().unwrap()).unwrap();
    assert_eq!(r.counts[&200], 1);
    assert_eq!(r.counts[&404], 1);
}

#[test]
fn missing_file_is_an_error() {
    assert!(logstat::run("/nope").is_err());
}

Add tempfile = "3" under [dev-dependencies] and it never ships in the binary. Notice the second test: the error path deserves a test as much as the happy one, and in Rust it is one line because errors are ordinary values.

Shipping

cargo build --release        # target/release/logstat
cargo install --path .       # into ~/.cargo/bin
cargo publish                # crates.io — needs description + license in Cargo.toml

Before you continue

Build it, or build your own version of it — a file organiser, a todo manager, whatever you'd actually use. The requirements are the same: library plus thin binary, one real error type with context, streaming IO, an integration test for the happy path and one for a failure. Then run cargo clippy and fix what it finds.
