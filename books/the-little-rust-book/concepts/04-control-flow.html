Chapter three

Control Flow

Three quarters of this chapter you can guess. The quarter you can't — match — is the one Rust programmers use most, and the one that quietly makes refactoring safe.

if, and only bool

if n > 0 {
    println!("positive");
} else if n < 0 {
    println!("negative");
} else {
    println!("zero");
}

// if n { … }        // error: expected `bool`, found integer

No truthiness. An integer is not a condition, a pointer is not a condition, an empty string is not a condition. If you want the test, write it: if !v.is_empty().

And since if is an expression, both arms must have the same type — which is the compiler catching a class of bug that ternaries in other languages let through.

Three loops

loop {                      // forever, until you break
    if done() { break; }
}

while attempts < 3 {         // conditional
    attempts += 1;
}

for i in 0..5 { }             // 0,1,2,3,4
for i in 0..=5 { }            // 0,1,2,3,4,5 — inclusive
for item in &items { }        // borrow each element
for (i, item) in items.iter().enumerate() { }

loop is an expression too, and break can carry a value out of it. That makes "retry until it works, then keep the result" a single expression instead of a mutable variable declared above the loop: 

let reading = loop {
    if let Some(v) = sensor.try_read() {
        break v;                  // the loop's value
    }
};

Nested loops can be labelled, which beats a found flag: 'outer: for … { break 'outer; }.

match: the one that matters

match compares a value against patterns, top to bottom, and it is exhaustive: if you have not covered every possibility, the program does not compile. 

let size = match n {
    0 => "zero",
    1..=9 => "small",
    x if x % 2 == 0 => "big and even",   // a guard
    _ => "big",                          // the catch-all
};

Exhaustiveness is worth more than it looks. Add a variant to an enum six months from now and the compiler walks you to every place that has to decide something new. This is the single most valuable refactoring property Rust has, and it costs you the discipline of not reaching for _ when you could enumerate.

if let and let-else

When only one arm is interesting, match is noise. if let is the shorthand: 

if let Some(name) = maybe_name {
    println!("hello, {name}");
} else {
    println!("anonymous");
}

And when the uninteresting case means "give up", let … else keeps the happy path flat. The else block must diverge — return, break, continue, or panic: 

let Some(name) = maybe_name else {
    return Err("no name".into());
};
// `name` is in scope, unindented, for the rest of the function

An edition 2024 nicety

In edition 2024, a temporary created by an if let scrutinee is dropped before the else block runs, rather than living to the end of the whole statement. If you have hit a surprising "still borrowed" error in an if let … else on an older edition, this is the fix.

A first look at ?

Rust has no exceptions. A function that can fail returns Result<T, E>, and the caller deals with it. Written out, that gets tedious fast — so there is an operator. 

// the long way
let text = match std::fs::read_to_string(path) {
    Ok(t) => t,
    Err(e) => return Err(e),
};

// the same thing
let text = std::fs::read_to_string(path)?;

? means: if this is Ok, unwrap it and carry on; if it is Err, convert the error and return it from this function immediately. It works in any function returning Result (or Option), which includes main. Chapter 6 does errors properly; for now, recognise the question mark as "and if that failed, we're done here".

Before you continue

Implement a tiny text menu or number guesser using match and a loop. Read a line with std::io::stdin().read_line(&mut buf), match on buf.trim(), and let the loop break with the chosen value. Try leaving out the _ arm to see exhaustiveness complain.
