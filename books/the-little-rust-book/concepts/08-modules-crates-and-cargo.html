Chapter seven

Modules, Crates, and Cargo

Everything so far fits in one file. This chapter is about the second file, and the fifth, and the dependency you didn't write. Rust's module system is famously the part people bounce off — mostly because of one misunderstanding we'll clear up immediately.

Four words, in order

Module
A namespace inside a crate. Introduced by mod, nested arbitrarily, private by default.
Crate
The unit of compilation. Either a binary crate (rooted at src/main.rs, produces an executable) or a library crate (rooted at src/lib.rs).
Package
What cargo new makes: a Cargo.toml plus one or more crates. At most one library, any number of binaries.
Workspace
Several packages sharing one lockfile and one target/. Not needed until it is.

mod is not an import

The one misunderstanding

mod foo; does not "import" anything. It declares that a module called foo is part of this crate, and tells the compiler to find its body in foo.rs or foo/mod.rs. You write it once, in the parent. use is the separate, purely cosmetic thing that shortens a path. 

// src/lib.rs — the crate root
pub mod parser;      // loads src/parser.rs, and exposes it
mod internal;        // loads src/internal.rs, crate-private

pub use parser::Config;   // re-export: callers write mycrate::Config
// src/parser.rs
use crate::internal::normalise;   // absolute, from the crate root
use std::collections::HashMap;

#[derive(Debug, Default)]
pub struct Config {
    pub values: HashMap<String, String>,   // fields are private too
}

pub fn parse(text: &str) -> Config { /* … */ }

Everything is private to its module unless marked pub, and that includes struct fields. Privacy is per-module, not per-type: a child module can see its ancestors' private items, but not the other way round. When pub is too wide there are narrower forms — pub(crate) is the one you will use.

use, as, and re-exports

use std::collections::{HashMap, HashSet};
use std::io::Result as IoResult;   // rename a clashing name
use super::Shape;                    // relative: the parent module
use self::helpers::tidy;             // relative: this module

pub use is the interesting one. It re-exports a name, which lets you organise a crate into deep private modules while presenting a flat public surface. Most well-shaped crates you use do this: the file layout is for the maintainer, and the pub use block at the top of lib.rs is for you.

Cargo, dependencies, profiles

# Cargo.toml
[dependencies]
serde = { version = "1", features = ["derive"] }
rand = "0.9"

[dev-dependencies]
tempfile = "3"          # tests and examples only

[profile.release]
lto = true

cargo add serde --features derive writes that line for you. Version strings are caret requirements by default: "1" means "any 1.x that is at least 1.0". The exact resolved versions live in Cargo.lock — commit it for a binary, and by convention leave it uncommitted for a library.

Two build profiles matter. dev is the default: fast to compile, unoptimised, debug assertions on, integer overflow panics. release (--release) optimises hard, takes noticeably longer, and turns those assertions off. Benchmark only in release; a debug build can be an order of magnitude slower and tells you nothing.

Tests come with the language

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn parses_a_pair() {
        let cfg = parse("a=1");
        assert_eq!(cfg.values.get("a").map(|s| s.as_str()), Some("1"));
    }

    #[test]
    fn rejects_garbage() {
        assert!(parse_strict("nonsense").is_err());
    }
}

Unit tests live beside the code in a #[cfg(test)] module, so they can reach private items and are compiled out of the real build. Integration tests live in tests/, are separate crates, and see only your public API — which is exactly the pressure that keeps that API honest.

Documentation that can't rot

/// Parses `key=value` lines into a [`Config`].
///
/// # Examples
///
/// ```
/// let cfg = mycrate::parse("host=localhost");
/// assert_eq!(cfg.values["host"], "localhost");
/// ```
pub fn parse(text: &str) -> Config { /* … */ }

cargo doc --open renders that to the same HTML you have been reading on docs.rs all along. The part that matters: cargo test compiles and runs the example. An out-of-date example in your documentation is a failing test, not a disappointment for a stranger.

Before you continue

Split your chapter 6 parser into a library: move the logic to src/lib.rs plus a src/parser.rs, leave src/main.rs as a thin caller, add one dependency with cargo add, and write one #[test]. Run cargo test and cargo doc --open.
