Chapter six

Collections, Strings, and Error Handling

Three things you need before you can write a real program: somewhere to put data, a way to hold text, and a story for what happens when it all goes wrong. Rust's answers are Vec, String, and a return value.

String and &str

The two-string-types thing confuses everyone once. It is the ownership rules applied to text, and nothing more.

The distinction

Both are guaranteed UTF-8. That guarantee is what forbids the operation everyone reaches for first: 

let s = String::from("héllo");
// let c = s[0];       // error: `String` cannot be indexed by `{integer}`

for c in s.chars() { }      // by Unicode scalar value
for b in s.bytes() { }      // by byte
let head = &s[..1];        // byte slice — panics off a char boundary

s[0] would have to mean a byte or a character, and those are different things in UTF-8. Rather than pick the wrong one silently, Rust makes you say which you meant. Useful methods: len() (bytes!), is_empty(), trim(), split_whitespace(), splitn(), replace(), starts_with(), parse::<T>(), push_str().

Vec<T>

let mut v: Vec<i32> = Vec::new();
v.push(1);
v.push(2);

let mut v = vec![1, 2, 3];       // the macro is shorter

let a = v[0];                  // panics if out of range
let b = v.get(10);             // Option<&i32> — None, no panic
let last = v.pop();            // Option<i32>

for x in &v { }                 // borrow
for x in &mut v { *x *= 2; }   // borrow mutably
for x in v { }                  // consume: v is gone afterwards

Those three for forms are the whole ownership model showing through a loop header. It is worth staring at them for a moment: the third one moves the vector into the loop, which is why it isn't there after.

HashMap and HashSet

use std::collections::HashMap;

let mut counts: HashMap<String, u32> = HashMap::new();

for word in text.split_whitespace() {
    *counts.entry(word.to_string()).or_insert(0) += 1;
}

if let Some(n) = counts.get("rust") { println!("{n}"); }
for (k, v) in &counts { println!("{k}: {v}"); }

The entry API is the idiom worth memorising: entry(k).or_insert(v) hands you a &mut to the existing value or to the one it just inserted, in one hash lookup. Also useful: or_insert_with(Vec::new) for a map of lists, and or_default().

Keys must be Eq + Hash, which is what #[derive(PartialEq, Eq, Hash)] was for. Iteration order is unspecified and deliberately randomised per process — if you need order, use BTreeMap. HashSet<T> is the same thing with no values.

Errors are values

Rust splits failure in two. Something is either recoverable — the file is missing, the input is malformed, the socket closed — and that is a Result<T, E> the caller must handle. Or it is a bug — an index out of range, an invariant broken — and that is panic!, which unwinds and aborts the thread.

A library that panics has decided, on your behalf, that your program should stop. Return the Result and let the caller be wrong on purpose. 
fn load(path: &str) -> Result<Config, ConfigError> {
    let text = std::fs::read_to_string(path)?;   // io::Error → ConfigError
    let cfg = parse(&text)?;
    Ok(cfg)
}

Each ? is "if this failed, convert the error and return it". The conversion goes through the From trait, which is what lets one function propagate three different error types into its own.

A custom error type

The whole of a hand-written error type is a data-carrying enum, a Display impl, and one empty line: 

use std::fmt;

#[derive(Debug)]
enum ConfigError {
    Io(std::io::Error),
    Missing(String),
    BadNumber { key: String, value: String },
}

impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            ConfigError::Io(e) => write!(f, "reading config: {e}"),
            ConfigError::Missing(k) => write!(f, "missing key: {k}"),
            ConfigError::BadNumber { key, value } =>
                write!(f, "key {key} is not a number: {value:?}"),
        }
    }
}

impl std::error::Error for ConfigError {}

// this impl is what makes `?` on an io::Error work above
impl From<std::io::Error> for ConfigError {
    fn from(e: std::io::Error) -> Self { ConfigError::Io(e) }
}

Debug is for you, Display is for the user, and implementing std::error::Error — which needs no methods once you have the other two — is what makes your type interoperate with every other error in the ecosystem.

When you get tired of writing that

Two crates are the community default, and they split by audience. thiserror derives exactly the code above from attributes — use it in libraries, where callers need to match on what failed. anyhow gives you one boxed anyhow::Error that anything converts into — use it in applications, where the error is going to be printed and the process is going to exit. Many projects use both, in exactly those places.

Before you continue

Parse some input into a HashMap: take a string of key=value lines, split each on the first =, and return Result<HashMap<String, String>, ConfigError>. Make a second function that reads a numeric key, propagating with ?. Feed it a malformed line and read your own Display output.
