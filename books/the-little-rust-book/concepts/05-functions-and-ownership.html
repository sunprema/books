Chapter four

Functions and Ownership

Here is the chapter. Everything before it was preparation and everything after it assumes this. The good news: it is three rules and one idea. The honest news: the first afternoon is frustrating, and then it isn't.

Functions, briefly

fn area(w: f64, h: f64) -> f64 {
    w * h                 // last expression, no semicolon, no `return`
}

fn log(msg: &str) {      // no `->` means it returns ()
    eprintln!("[log] {msg}");
}

Parameter types and the return type are always written; nothing is inferred across a function boundary. That is deliberate — a signature is a contract, and reading one should not require reading the body.

return exists for early exits. For the final value, leave the semicolon off. Adding one turns the body's last expression into a statement and you get "expected f64, found ()" — probably your second-most-common early error.

The three rules

Ownership

1. Each value has one variable that is its owner.
2. There can be only one owner at a time.
3. When the owner goes out of scope, the value is dropped.

Rule 3 is where the garbage collector went. There is no collector because there is no question: the compiler knows, statically, where each value's owner ends, and inserts the cleanup there.

Move semantics

Assigning a value that owns a heap allocation does not copy the heap data, and does not make a second owner. It moves ownership, and invalidates the old binding at compile time. 

let s1 = String::from("hi");
let s2 = s1;              // s1 is moved into s2

// println!("{s1}");     // error[E0382]: borrow of moved value: `s1`
println!("{s2}");         // fine

Simple stack types don't move, they copy — because copying them is trivial and there is nothing to free. Integers, floats, bool, char, and tuples of those implement the Copy trait, so let b = a; leaves a usable.

Passing a value to a function moves it too. Which is why, most of the time, you don't pass values — you lend them.

Borrowing

fn length(s: &String) -> usize {   // borrows; caller keeps ownership
    s.len()
}

fn shout(s: &mut String) {           // borrows mutably
    s.push_str("!");
}

let mut msg = String::from("hey");
println!("{}", length(&msg));         // msg still ours
shout(&mut msg);
println!("{msg}");                    // "hey!"

The borrowing rules

At any given point you may have either one mutable reference or any number of immutable references — never both. And every reference must be valid for as long as it is used.

That single restriction is what buys data-race freedom in chapter 11 for free. It is also the rule you will trip over. When you do, the fix is almost never .clone(); it is usually to shorten a borrow by ending it earlier, or to restructure so the two things you are borrowing are separate fields rather than the whole struct. 

let mut v = vec![1, 2, 3];
let first = &v[0];        // immutable borrow starts
// v.push(4);           // error[E0502]: cannot borrow `v` as mutable
println!("{first}");     // …because `first` is still live here
v.push(4);              // fine — the borrow ended above

That error is not pedantry. push may reallocate the vector's buffer, which would leave first pointing at freed memory — the exact bug that makes iterator invalidation a C++ interview question.

Slices

A slice is a borrowed view of a contiguous run: a pointer and a length, owning nothing. &str is a slice of a string; &[T] is a slice of an array or vector. 

fn first_word(s: &str) -> &str {
    match s.find(' ') {
        Some(i) => &s[..i],
        None => s,
    }
}

let owned = String::from("hello world");
first_word(&owned);          // &String coerces to &str
first_word("hello world");   // a literal is already &str

Take &str, not &String, in your function signatures. It accepts both, borrows rather than allocates, and is the single most common piece of Rust style advice for a reason.

Lifetimes, lightly

Look again at first_word: it returns a reference. Into what? Into the caller's string — so that string must outlive the result. The compiler tracks that relationship, and its name for it is a lifetime.

Most of the time you never write one, because the elision rules fill them in: one input reference means the output borrows from it. You start writing them when there is genuine ambiguity: 

// which input does the result borrow from? you have to say.
fn longer<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() >= b.len() { a } else { b }
}

Read 'a as "some region of the program". The signature says: the result is valid for whatever region both inputs are valid for. Lifetimes are not runtime objects and they do not change how the code runs; they are how you tell the compiler a relationship it can't infer.

A lifetime annotation never makes anything live longer. It only describes what already has to be true.

Before you continue

Write two functions: one taking &str that returns the last word, one taking &mut String that appends to it. Call both on the same String. Then deliberately hold the result of the first across the call to the second, read the E0502 error, and fix it by moving the println!.
