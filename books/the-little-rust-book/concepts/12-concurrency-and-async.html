Chapter eleven

Concurrency and Async

This is where the last seven chapters get paid back. Rust's concurrency story is not a new set of rules — it is the ownership rules, applied across threads, which turns the entire category of data races into compile errors.

Threads

use std::thread;

let handle = thread::spawn(|| {
    expensive_work()
});

do_something_else();

let result = handle.join().unwrap();   // waits; Err if it panicked

spawn takes a closure and returns a JoinHandle<T>. join() blocks until the thread finishes and gives you its return value, wrapped in a Result because the thread might have panicked. These are real OS threads, one to one.

A spawned thread may outlive the scope that created it, so its closure almost always needs move — the compiler will insist, and its suggestion is right.

Send and Sync do the work

Two marker traits, no methods

Send — this type can be moved to another thread.
Sync — &T can be shared with another thread.

Almost everything is both, automatically, because the compiler derives them structurally. The interesting cases are the exceptions: Rc is neither (its counter isn't atomic), and RefCell is Send but not Sync (its borrow flag isn't either). So the moment you try to share an Rc across a thread::spawn, the program stops compiling — and the reason it stops is a data race you would otherwise have shipped.

"Fearless concurrency" is marketing for something specific: you cannot compile a data race. Deadlocks are still yours to earn.

Channels: don't share, send

use std::sync::mpsc;
use std::thread;

let (tx, rx) = mpsc::channel();

for id in 0..4 {
    let tx = tx.clone();          // multi-producer
    thread::spawn(move || {
        tx.send(format!("worker {id} done")).unwrap();
    });
}
drop(tx);                        // drop the original, or rx never ends

for msg in rx {                   // single-consumer; ends when all senders are gone
    println!("{msg}");
}

mpsc is multi-producer, single-consumer. The receiver is an iterator that finishes when every sender has been dropped — which is why the drop(tx) line is not optional. Forgetting it is the classic first channel bug: the loop simply never returns.

Sending a value moves it, so ownership crosses the thread boundary and no sharing is involved at all. Where you can express a problem this way, do.

Shared state: Arc + Mutex

use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));
let mut handles = vec![];

for _ in 0..8 {
    let counter = Arc::clone(&counter);
    handles.push(thread::spawn(move || {
        let mut n = counter.lock().unwrap();
        *n += 1;
    }));   // guard drops here — the lock releases
}

for h in handles { h.join().unwrap(); }
println!("{}", *counter.lock().unwrap());   // 8

Arc gives many owners; Mutex gives one writer at a time. lock() returns a guard, and the guard's Drop releases the lock — so there is no unlock to forget, and no path out of the block that skips it. The Result from lock() reports a poisoned mutex: another thread panicked while holding it, and the data may be inconsistent.

Keep the guard's scope small

A MutexGuard lives until the end of its statement or block. Holding one across a long call — and especially across an .await — is how you turn a lock into a bottleneck or a deadlock. Take what you need, drop the guard, then do the slow thing.

Async, in one page

Threads are the right tool when the work is CPU-bound or the count is small. When you have ten thousand connections mostly waiting on a socket, ten thousand OS threads is the wrong shape. That is what async is for. 

async fn fetch(url: &str) -> Result<String, reqwest::Error> {
    let body = reqwest::get(url).await?.text().await?;
    Ok(body)
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let (a, b) = tokio::join!(
        fetch("https://example.com"),
        fetch("https://example.org"),
    );
    println!("{} / {}", a?.len(), b?.len());
    Ok(())
}

Rust ships the syntax, not the runtime

An async fn returns a Future, and a Future does nothing until something polls it. The standard library defines Future and the language provides async/.await — the scheduler, the timers and the IO come from a crate. In practice that crate is Tokio: add tokio = { version = "1", features = ["full"] } and put #[tokio::main] on an async main.

Async in Rust is genuinely more advanced than the rest of the language — pinning, cancellation, "function colouring", runtime-specific traits. This chapter is deliberately the first mile only. Write the threaded version first; move to async when the shape of the problem asks for it.

Before you continue

Write a tiny program that spawns four threads, each sending a result over an mpsc channel, and prints them as they arrive. Remember the drop(tx). Then, for contrast, try sharing an Rc into one of those threads and read the error the compiler gives you — that error is the whole chapter in one message.
