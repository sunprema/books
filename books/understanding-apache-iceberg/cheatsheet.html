The 30-second summary

Iceberg is a table format: a set of notes that turns a pile of files in cheap storage into one dependable table. It is not a database, not an engine, not storage. Every change makes a new snapshot (a saved version), so readers never see half-done work and you can go back in time. A catalog points to the newest version and makes commits all-or-nothing. Many engines can share one copy of the data. You still own the chores: compaction, snapshot expiry, cleanup. Choose the catalog first; it is the part that is hard to swap.

A. Glossary

TermIn plain words
Table formatRules and notes that say which files make up a table, and what its columns are.
Open table formatA table format with a public spec, so many tools can use the same table.
LakehouseCheap open storage plus warehouse-style reliability and governance.
Data fileA file holding rows, usually Parquet, in object storage.
Metadata fileThe top note: schema, partition spec, list of snapshots, which one is current.
SnapshotThe whole table as it was after one commit. Never changed afterward.
Manifest listOne per snapshot: lists the manifests that belong to it.
ManifestA list of data files, with counts and min/max values used to skip files.
TermIn plain words
CatalogThe address book: maps a table name to its current metadata file; makes commits atomic.
REST catalogA shared way for engines to talk to any catalog. A protocol, not a product.
Partition specThe recipe that groups rows into files, e.g. by day of a timestamp.
Hidden partitioningIceberg derives the partition value itself, so queries filter on the real column.
Schema evolutionAdd, rename, drop or reorder columns without rewriting old files (columns tracked by ID).
Time travelRead the table as it was at an earlier snapshot or time.
RollbackPoint the table back at an earlier snapshot after a bad run.
Branch / tagA named moving line of snapshots / a named fixed snapshot. Tags protect a version from expiry.
TermIn plain words
COW (copy-on-write)A change rewrites the affected data files. Slower writes, simple fast reads.
MOR (merge-on-read)A change writes a small “ignore these rows” file; readers merge. Fast writes, slower reads until compaction.
Delete fileMOR note naming rows to ignore, by position or by matching values.
Deletion vectorVersion 3 way to mark deleted rows in a compact bitmap per data file.
CompactionRewriting many small files into fewer big ones.
Expire snapshotsDropping old versions and their files. Permanent: no time travel to them after.
WAP (write-audit-publish)Write to a branch, check the data, then publish. Bad data never reaches readers.
CDC (change data capture)A feed of inserts, updates and deletes from a source database, applied to a table.

Choosing a query engine

JobLean towardCheck
Big batch ETL and maintenanceSparkNeeds a cluster to run
Streaming writesFlink, or Kafka Connect sinkCommit interval vs. small files

Rule for all four: “supports Iceberg” is not enough. Ask which format version, which catalogs, read or write, and delete files.

D. Questions to ask vendors and platform teams

Catalog support
  • Does it speak the Iceberg REST protocol, and which version?
  • Can other engines write through it, or only read?
  • Can we export tables and permissions if we leave?
Governance
  • Who sets access rules: catalog, engine, or both? Do they hold for every engine?
  • Is direct bucket access locked down so policies cannot be bypassed?
  • Can we prove a deletion, including old snapshots and delete files?
  • Is there an audit log of who read and changed what?
Maintenance and operations
  • Who runs compaction, snapshot expiry and orphan cleanup? How often?
  • What is the retention default, and can it be set per table?
  • How do we see table health: file counts, snapshot counts, failed commits?
  • What happens when two writers collide?
Cost model
  • What do we pay for: storage, requests, compute for upkeep, metadata calls?
  • Does automatic upkeep bill separately?
  • What does it cost to leave: data copy, egress, rewrite?
Interoperability
  • Which Iceberg format versions are supported today, and when is v3?
  • Are row-level deletes and delete files handled by every engine we use?
  • Is Iceberg native here, or translated from another format?
  • Will an upgrade cut off any reader we have?

Gotchas

  • Never delete or move files in the bucket by hand. The metadata still points at them. Use table maintenance.
  • Snapshots are not backups. They live beside the data, and expiring them is permanent.
  • DELETE is not erasure. Rows stay readable in old snapshots until expiry and file rewrite.
  • Iceberg tracks small files; it does not stop them. Frequent commits need regular compaction.
  • Nothing maintains itself. Compaction, expiry and orphan cleanup need an owner.
  • ACID is per table. No cross-table transactions in core Iceberg.
  • Bare INSERT OVERWRITE can replace the whole table. Use dynamic partition overwrite.
  • MERGE fails if one target row matches many source rows. De-duplicate the source first.
  • Pin a tag, not a bare snapshot ID, for anything that must be reproduced later.
  • Orphan cleanup with a short window can delete files of in-flight writes. Keep the safe default age.
  • A v3 upgrade is one-way and cuts off v2-only readers.
  • Locked-down storage is what makes catalog policy real. Direct bucket credentials bypass it.
