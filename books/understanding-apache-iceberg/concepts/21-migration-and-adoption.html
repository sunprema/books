Part V · Making Good Decisions

Moving House Without Moving the Books

The data world calls this: migration and adoption

Here’s the problem

Picture a big old library that wants a better way to find its books. One plan is to leave every book on its shelf and just write a new card catalog. Nothing heavy gets carried, and readers barely notice. The other plan is to build a new library next door, carry the books over, and move readers across one branch at a time while the old reading room stays open.

Both plans are fine. The trouble comes when you pick one without knowing why, or when you shut the old room before anyone has checked that the new one has every book.

The idea: two ways to move, and one slow part

Moving to Iceberg comes in two kinds. In-place migration writes Iceberg’s notes (its metadata, the table’s own list of what files it holds) on top of data files that already exist. The files are not moved or rewritten. That is the card catalog plan. Shadow migration (also called full-data migration) builds a brand-new Iceberg table and copies the data into it, using a CTAS (a query that makes a new table from an old one’s rows) or a second pipeline running next to the first. That is the new library plan. It is slower and costs more. But you can change how the data is laid out on the way in, and the old table stays untouched if you need to go back.

The slow part is not the data. Guidance keeps saying the same thing: the hard parts are getting every reader to switch, and changing how people work. Who owns each table, who governs the catalog, and who knows the new engine all need answers.

How it works: the tools for each source

For old Hive tables, Iceberg’s Spark procedures do the card-catalog work. snapshot makes a test copy under a new name that points at the source’s files. The source stays the real one and keeps taking writes, so this is how you try out engines and pipelines safely. migrate converts the table in place and keeps its name, so existing queries keep working. It needs every writer stopped first, it adopts only Parquet, Avro or ORC files as they are, and it keeps the original as a renamed backup. add_files adds existing files into a table that already exists, as one new version, without rewriting them. It is the building block for custom and step-by-step moves.

-- Test first: Iceberg view of a Hive table, source untouched
CALL spark_catalog.system.snapshot('db.sales', 'db.sales_iceberg_test');
-- Then convert in place (stop all writers first)
CALL spark_catalog.system.migrate('db.sales');

-- Build-your-own: register existing files as a new version
CALL spark_catalog.system.add_files(
  table => 'db.sales_iceberg',
  source_table => 'db.sales_staging');

One catch with add_files: files that came from Hive need a name mapping (a note that tells Iceberg which file column is which) on the table. Snapshot and migrate set it for you.

Delta Lake has its own road. A module called iceberg-delta-lake, shipped apart from the Spark and Flink runtimes, has an action named snapshotDeltaLakeTable. It replays the Delta log into the new table as ordered commits, so the history comes along, and it reuses the same Parquet files. Hudi has no official Iceberg procedure. The usual path is Apache XTable (still incubating), which translates metadata among Hudi, Delta and Iceberg in either direction without rewriting data, in full or step-by-step sync modes.

You may also put the move off. Delta Lake UniForm writes Iceberg metadata after each Delta commit, so Iceberg readers can read a Delta table today. Teams can adopt Iceberg-reading engines first and decide about converting later. The limit is that it is read-only from the Iceberg side.

Proving it matches. Equal row counts prove little. Soft deletes, computed columns and type changes can all hide drift. Practitioners run the old and new pipelines side by side, compare daily with checksums or business-level totals, and move readers only after a long enough clean run. One written rule of thumb is seven matching days in a row. Give that dual-running phase a named owner and a deadline, or the “temporary” phase becomes permanent.

A phased road. The plan that keeps showing up: start with new tables or one low-risk area. Prove the upkeep and rules there (the last chapter’s rota, plus catalog governance). Move reads before writes. Keep the old path as your way back until parity holds. Then retire it.

Design principle

Move the metadata first and the people second, and never close the old door until the new one has proved itself. A migration is finished when the last reader has switched, not when the last byte has moved.

Use case: the Hive warehouse that cannot stop

A team has a large Hive sales table that dashboards hit all day. They run snapshot to make a test copy and point a new engine at it, while the real table carries on. Once the tests pass, they pick a quiet hour, stop the writers, and run migrate. The original lives on as a renamed backup. A second table with a bad layout takes the other road: a shadow copy with new partitioning, checked daily against the old one until it has matched for a full week. Then its readers switch, one team at a time.

Watch out for

  • Running migrate without the snapshot dry run, or without freezing writers, is the classic migration incident.
  • A snapshot table shares real files with its source. Running remove_orphan_files or expiring hard on it can delete files the original still needs.
  • Translated tables (UniForm, XTable) are for reading. If both sides write, one side’s cleanup can destroy the other’s table.
  • Skipping the people work. Table owners, catalog rules and new engine skills decide whether the move sticks.

Sources: AWS prescriptive guidance on Iceberg migration; Apache Iceberg docs on Hive and Delta Lake migration and Spark procedures; Cloudera on Hive migration; Apache XTable; Delta Lake UniForm docs; practitioner guidance on shadow migration.

Because you can move the notes before the data and keep the old path open until the new one matches, you can adopt Iceberg step by step, without a weekend of risk or a day when everything stops.
