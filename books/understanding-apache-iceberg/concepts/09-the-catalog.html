Part III · Architecture and Design Principles

The Address Book Every Table Starts From

The data world calls this: the catalog

Here’s the problem

Picture a huge library. Nobody walks the shelves hunting for a book. You go to the front desk and ask the card index, “Where is the latest edition of this one?” The index gives you a shelf. When a new edition arrives or an old one is returned, that is written down at the same desk, one at a time.

Now take the desk away. Everyone wanders the stacks. Two people each put a “newest edition” on the shelf at the same moment, and nobody can say which one is newest. A table made of files in cheap storage is that library. Something has to be the desk.

The idea: one desk that knows the current page

The catalog (a service that keeps a list of table names and, for each one, the place of its current description file) is that desk. You ask for a table by name, such as sales.orders, and it hands back a pointer to the table’s newest metadata file. Every program that wants the table starts there. So the pointer, not a folder in storage, decides what the table is right now.

This is a break from the old habit of treating a folder as the table. Drop files into the table’s folder without a proper commit and they add nothing to the table. Delete files from it by hand and you may break the table. The folder holds the pages; the desk says which ones count.

How it works: swap the pointer, but only if nobody beat you

A writer never edits the table in place. It writes a complete new metadata file, then asks the catalog to move the pointer from the old file to the new one. The move is a compare-and-swap (an update that works only if the pointer still holds the value you started from). If another writer got in first, the swap is refused, and the second writer must look at the new state and try again. Nobody silently overwrites anybody.

Different catalogs do this in different ways. Hive Metastore makes a conditional update to a location property. AWS Glue checks a version number. Nessie checks a commit hash. The engine sees the same promise every time: one winner per swap.

Since every engine has to pass the desk to find a table or save a change, the desk is also the natural place to ask the other hard questions: who is allowed in, who changed what, and who gets a short-lived key to the storage. That is why the catalog became the place to compete, more than the file format ever was.

The REST catalog (an open, shared description of how to talk to a catalog over the web) is the common language. It covers table and folder management, a commit that needs no locks, views, and handing out storage keys. By now the major engines and managed catalogs speak it. Note that it names a protocol, not a product. Two catalogs can both speak it and still differ in sign-in, rules, upkeep and price.

The choices, in plain words

  • Cloud-run catalogs. AWS Glue, Amazon S3 Tables (a storage type with a built-in catalog that also tidies files for you), Databricks Unity Catalog (a REST doorway to its Iceberg tables, still in public preview) and Snowflake Open Catalog. Quickest to start; they tie you to one cloud’s way of doing rules.
  • Apache Polaris. An open-source REST catalog that began at Snowflake, was given to the Apache foundation in 2024, and reached version 1.0 in 2025. It adds role-based access and short-lived storage keys. Snowflake Open Catalog is a run-for-you version.
  • Project Nessie. A catalog with Git-like habits: branches, tags and commits that can cover many tables. Try a set of changes on a branch, then merge them all at once, which comes close to the multi-table transactions Iceberg itself lacks.
Design principle

The catalog is strategic infrastructure, not a setting. Your data files can move, but your grants, folders, audit history and upkeep rules live in the catalog and do not move on their own. Choosing one means choosing where rules live, who hands out storage keys, and how hard it is to leave.

Use case: three engines, one table

A company streams orders in with one engine, runs reports with a second, and lets data scientists explore with a third. All three ask the same catalog for sales.orders, so all three see the same current table, and the catalog’s sign-in and rules apply to every one of them. If a team wants to rehearse a risky fix first, a branch-style catalog lets them try it apart from the main table and merge when happy.

Deciding: how to think about the choice

SituationReach forTrade-off
One cloud, small team, want to start fastThe cloud’s own catalogEasy now; rules and state are tied to that cloud
Many engines, and you want to stay free to moveAn open REST catalog such as PolarisMore portable protocol; you pick sign-in and upkeep yourself, or buy a run-for-you version
Changes spanning many tables must land togetherA branching catalog such as NessieStrong team workflow; one more thing to learn and run
Already deep in one vendor’s platformThat vendor’s catalog, with REST accessFewer moving parts; check how much rule state you could take with you

Watch out for

  • Treating the catalog as a setting. Swapping it later is a real migration, because grants, folders and audit history do not travel by themselves.
  • Assuming “REST catalog” is a product. It is a protocol, and the products behind it differ a lot.
  • Registering one table location in two catalogs. Only one desk can own the pointer, so two of them split the table’s history or damage it.
  • Carrying the old folder habit forward. The folder no longer defines the table; the pointer does.

Sources: Apache Iceberg Table Spec; Iceberg REST Catalog specification; Dremio on the life of a write; Apache Polaris docs; Project Nessie and Iceberg Nessie docs; AWS, Databricks and Snowflake catalog docs; the 2026 state-of-catalogs survey.

Because one desk decides what the table is right now, every engine you use sees the same table, and no two writers can quietly undo each other.
