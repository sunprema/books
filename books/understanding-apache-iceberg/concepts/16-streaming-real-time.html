Part IV · Use Cases and Patterns

Data That Never Stops Arriving

The data world calls this: streaming and real-time data

Here’s the problem

A shop’s website records every click: who looked at which shoe, who added what to a cart. The clicks never stop, day or night. The team wants the table of clicks to stay fresh, so they save a new version of it every minute. That is 1,440 versions a day.

Think of a flipbook. Each page is one complete, consistent picture of the business at that minute. Anyone can open the table and land on a whole page, never on a half-drawn one. The catch: a flipbook with 1,440 new pages a day gets heavy fast. Teams that run this at big scale, Netflix among them, pair it with automatic tidying and with alarms that shout when a page is late.

The idea: a conveyor belt that saves in small steps

Events flow in from apps, sensors, or databases. A streaming job collects them for a short while and then saves them to the table in one commit, a single all-or-nothing save. People call this micro-batch commits (a steady stream chopped into small, regular saves). Each save becomes one snapshot of the table.

So “real time” here means minutes fresh, not instant. The official guidance suggests saving no more often than once a minute. Iceberg is great for dashboards, monitoring, and analysis. It is not the tool for answers within a split second.

How it works: save only when it is safe

No double counting on a crash. Flink, a popular streaming engine, saves to Iceberg only after its own safety checkpoint succeeds. If the job dies and restarts, it picks up from the last saved version, which remembers its checkpoint number. The result is exactly-once delivery (every event lands one time, even when machines fail). If you would rather not write code, the Iceberg Kafka Connect sink does the same job with settings alone, with a default save every 5 minutes, and can fan one topic out into several tables.

Copying a live database. A shop’s orders database changes all day. CDC (change data capture: a feed of every insert, update, and delete from the source database) lets Iceberg mirror it. Flink’s upsert mode applies those changes. It needs a format-v2 table with key columns named, and partitioned tables must include their partition columns in that key.

-- Flink SQL: continuous CDC upsert into an Iceberg v2 table
INSERT INTO iceberg_catalog.db.customers /*+ OPTIONS('upsert-enabled'='true') */
SELECT id, name, email, updated_at FROM kafka_cdc_source;

A hidden bill. To keep writing fast, streaming jobs record deletes as notes (equality deletes: a note saying “any row with this key is gone”) rather than hunting down the old row. The work of applying those notes moves to whoever reads the table. Until compaction rewrites the files, reading gets slower. Format v3 can turn such notes into the cheaper deletion vectors.

Late, repeated, and out-of-order events. The exactly-once promise covers duplicates your own crashes cause. It does not cover duplicates sent by the source, such as a producer that sends twice or a replayed change feed. Those need a key: upsert in the sink, or a de-duplicating MERGE afterwards.

The table can be a stream too. Spark can read an Iceberg table as a stream starting from a chosen time, taking only appended snapshots, with limits on files or rows per batch. The changelog view (a listing of what changed between versions, including before and after pictures of updated rows) lets downstream jobs follow along without rereading everything.

The chores that come with it

A one-minute rhythm is 1,440 commits a day, each leaving small files and metadata behind. Streaming writes are quick appends that skip tidying the metadata, so the table needs regular chores: rewrite_data_files to merge small files, rewrite_manifests to tidy the file lists, and expire_snapshots to retire old versions.

Design principle

Freshness is bought with commits, and every commit leaves clutter. Pick the slowest rhythm your users can live with, and budget for the cleaning that rhythm creates.

Use case: clickstream, sensors, and mirrors

Web clicks, device telemetry, and sensor readings all land through a one-minute stream, so analysts can ask what is happening this hour. Operations teams watch the same tables for trouble. A customers table mirrored from the live database through CDC stays a few minutes behind, and any past minute can be revisited through its snapshot. One caution for jobs that never rest: watch the time since the last successful commit. Commits can fail even while the job’s checkpoints look healthy.

Deciding: should this be a stream?

SituationChoiceTrade-off
Dashboards fine with data a few minutes oldStream into IcebergMore chores: compaction and expiry
Mirror an operational databaseCDC with upsert modeReads slow down until compaction runs
Move a topic into tables with no codeKafka Connect sinkFewer knobs than writing your own job
Source may send duplicatesKey-based upsert or MERGENeeds a trustworthy key
Answers needed in millisecondsNot IcebergCommit interval sets the floor on latency

Watch out for

  • Chasing freshness by committing faster. Snapshots and small files multiply, and the cleaning bill grows faster than the speed gain.
  • Expiring snapshots or deleting stray files too eagerly. A running Flink job needs the last snapshot it committed, found through its job id in the snapshot summary, to recover.
  • Watching only checkpoints. Monitor commit lag on its own.
  • Skipping scheduled compaction on an upsert table. It gets slower every day, quietly.

Sources: Apache Iceberg docs on Flink Writes, Spark Structured Streaming, Spark Procedures, and the Kafka Connect sink; Dremio, “Approaches to Streaming Data into Apache Iceberg Tables”; RisingWave on CDC upsert and delete semantics; Data Engineer Things, “How Netflix operates Apache Iceberg at scale”.

Because every minute’s save is a whole, checked page of the flipbook, you get fresh numbers without ever reading half-written data, and you pick for yourself how fresh is fresh enough.
