Change the Columns Without Touching the Old Files

The data world calls this: schema evolution

Here’s the problem

Think of a company’s staff records. People change their names, their job titles and their desks all the time. Yet payroll never gets confused, because it does not look people up by name. It looks them up by badge number. A new hire never gets a departed worker’s badge, so nobody’s pay is ever paid to the wrong person.

Now picture a table of data that works the other way. It finds each column by its name, or by its place in the row. Someone renames a column from cust_id to customer_id. To the old way of working, that looks like one column vanishing and a new, empty one appearing. Someone drops a column and later adds a new one with the same name, and the old column’s values quietly show up under it. Nothing crashes. The numbers are just wrong.

Iceberg gives every column a badge number and always looks columns up by that.

The idea: a column is its badge, not its name

Business changes, so tables must change. A schema (the list of columns in a table and the kind of value each one holds) is never finished. Iceberg lets you add, drop, rename and reorder columns, including columns nested inside other columns. It also lets you widen a type, for example from a small whole number to a bigger one.

These changes only touch the table’s records. They do not rewrite the data files that already exist. A table with a billion old rows takes the same moment to change as an empty one.

How it works: field IDs

The trick is the field ID (a unique number given to every column, even nested ones, on the day it is created, and never reused). Data files remember their columns by these numbers. When a reader opens an old file, it asks the table’s current schema which column each number means today, and reads the right values from the file.

Because of the badge idea, the official docs promise a handful of plain things. A new column never picks up an old column’s values. Dropping a column does not shift any other column’s values. A rename keeps every value attached to its column. And if you add a column with the name of one you dropped, it gets a fresh number, so the old data cannot come back under it.

This is why the logical schema (what people see when they query) and the physical layout (what is really stored in the files) can differ without harm. Old files simply lack the new column, and readers fill in empty values for them. In the newer table format, version 3, a new column can have a default value (a stand-in shown for rows that were written before the column existed), so even the old rows look filled in, still without rewriting a file.

ALTER TABLE prod.db.orders ADD COLUMN discount_pct decimal(9,2);
ALTER TABLE prod.db.orders RENAME COLUMN cust_id TO customer_id;
ALTER TABLE prod.db.orders ALTER COLUMN qty TYPE bigint;
ALTER TABLE prod.db.orders DROP COLUMN legacy_flag;
Design principle

Treat the schema as a governed, versioned contract, not an afterthought. Every change is saved as a new numbered version of the schema, and every snapshot knows which version it was written under, so the history of your columns can be checked just like the history of your data.

Use case: the new rule from the business

The sales team asks for a discount percentage on every order. At the same time, a naming clean-up says cust_id must become customer_id, and an old flag nobody uses is to go. On a table kept the old way, this could be a weekend of copying files and rebuilding. With Iceberg, an engineer runs the four statements above. They finish in moments. Old reports on last year’s data still read correctly, and new orders carry the new column from the start.

Because the schema is itself versioned, you can also look back at an older snapshot and see the columns it had at the time. That makes an argument about “what did this column mean in March?” easy to settle.

Deciding: how far you can lean on it

ChangeSafe for the data?Trade-off
Add a columnYesOld rows read empty, unless you give a default (version 3)
Rename a columnYesEvery query and dashboard using the old name breaks
Reorder columnsYesAnything reading by position, outside Iceberg, may be surprised
Widen a type (int to long)YesOnly widening is allowed; narrowing is not
Drop a columnYesThe values stay inside old files and old snapshots
Change meaning, keep the nameNoThe format cannot know; add a new column instead

Watch out for

  • The table format protects the data, not the SQL. A rename is safe in storage but loud downstream, so tell everyone who reads the table.
  • Dropping a column does not free space or scrub values. If it held sensitive data, the bytes remain until files are rewritten and old history is expired.
  • Types only widen. Picking an oversize type early is cheaper than being stuck with a too-small one.
  • Reading the raw files with a tool that does not know Iceberg skips the badge lookup, so it will see old names and dropped columns.

Sources: Apache Iceberg docs, Evolution and Spark DDL; Apache Iceberg Table Spec; Google Open Source Blog and AWS Prescriptive Guidance on Iceberg v3.

Because every column keeps its badge number, you can let your tables change with the business without rewriting history or wondering whose numbers are whose.
