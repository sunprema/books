A City Plan for Your Data

The data world calls this: designing an Iceberg lakehouse

Here’s the problem

Imagine a town where every builder puts up houses wherever they like. No streets are named, no districts are marked, and nobody keeps a list of addresses. The water crew, the power crew and the mail carrier each wander around hunting for the right door. Every house works fine alone. The town does not.

Many data teams build this town by accident. Tables pile up, each engine finds them its own way, and no one can say who owns what. The fix is not a better house. It is a plan for the whole town, drawn before the digging starts.

The idea: land, buildings, districts, and one address book

Think of the lakehouse as a city. Cheap object storage (big shared disk space in the cloud) is the land. Tables are the buildings. Namespaces (named groups of tables) are zoned districts, one for each area of the business. The catalog (the official address book for tables) is the registry that every service must check before it touches a single building. The engines are the utilities, and they plug into any building.

A common plan has six layers. Storage holds the data and the table notes. The catalog lets you find a table and makes each change happen all at once or not at all. Ingestion brings data in: batch loads, streams, change feeds and dropped files. Transformation engines reshape it. Consumption is where people and programs read it: dashboards, SQL, machine learning. Governance, meaning who may see and change what, runs through all of them.

How it works: one registry, many engines

Tables are named in three parts: catalog.namespace.table. The middle part does a lot of work. Give each business area its own namespace, and often each quality stage too. A popular stage plan is the medallion layout (three tiers of cleanliness): bronze keeps raw data exactly as it arrived, silver holds cleaned and matched data, and gold holds the neat summaries people read. A namespace is also the natural line for owners and access rules.

Pick engines by job, not by brand. Because the table format and the catalog are shared, one table can be read and written by many engines. Spark-class engines suit big batch jobs and upkeep. Flink-class engines suit streaming in. Trino and BigQuery-class engines suit fast interactive SQL with many users. DuckDB-class tools suit small, local analysis. You choose per workload, and no one is locked to a single platform.

Choose the catalog first. Catalogs that speak the open Iceberg REST catalog standard stay portable across engines and vendors. Modern ones can also link out to other catalogs, such as Unity Catalog or AWS Glue, so you are not forced into one company’s control room.

-- Namespaces as domain + layer boundaries
CREATE NAMESPACE lake.sales_silver;
CREATE TABLE lake.sales_silver.orders (
  order_id BIGINT, customer_id BIGINT,
  order_ts TIMESTAMP, amount DECIMAL(12,2))
USING iceberg
PARTITIONED BY (days(order_ts));

Shape each table on purpose. Its partition plan, sort order, update style (copy-on-write or merge-on-read) and target file size should come from how that table is read and written. These choices set your query cost and your upkeep later. And every production table needs an owner and a plan for compaction, old-version cleanup and stray-file cleanup. You can run these yourself or hand them to managed services such as Amazon S3 Tables or Glue optimization.

Design principle

Settle the shared things first — the address book, the districts and the owners — and leave the engines free. The parts that everyone depends on should be the parts that are hardest to lock in.

Use case: a growing company draws its map

A retailer starts with sales and customers. It makes one namespace per area and layer: raw feeds in bronze, cleaned orders in silver, daily summaries in gold. Streaming lands in bronze, a nightly batch job tidies silver, and analysts query gold through a fast SQL engine. Each namespace has a named owner who also holds the upkeep plan. When marketing arrives next year, it gets a new district, not a new town.

Deciding: an architect’s checklist

Ask firstLean towardTrade-off
1. What jobs and delays matter?List workloads before toolsSkipping this means buying for the wrong job
2. Which engine for each job?Several engines, one set of tablesMore engines means more skills to keep
3. Where is the single source of truth?One catalog with the open REST standardA proprietary catalog can lock in everything
4. How are districts and owners laid out?Namespace per domain and layerMore namespaces, more rules to manage
5. Partitioning and updates, per table?Decide from real queries and writesDate-by-habit pruning is hard to fix for old data
6. Who runs upkeep?A named owner, or a managed serviceManaged is easier but ties you to its rules
7. Who may see what?Access rules at the catalog and namespaceFiner rules cost more to maintain
8. What does it cost?Count storage, compute and storage requestsTiny files raise request bills quietly

Watch out for

  • Copying an old warehouse layout one-to-one, with no domains or owners, leaves nothing to govern later.
  • Choosing engines first and the catalog last. The dependency runs the other way.
  • Partitioning every big table by date out of habit. Changing the plan later helps only future data.
  • Designing only how data gets in. A table with no upkeep owner decays quietly until queries slow and bills jump.

Sources: Google Cloud Lakehouse docs on key concepts; “Medallion architecture with Apache Iceberg”; “The State of Apache Iceberg Catalogs (2026)”; Apache Iceberg docs on Maintenance and Spark Procedures; Dremio on small files and storage costs; AWS on S3 Tables compaction.

Because you draw the map before you build, new teams, tools and tables slot into place instead of piling up, and you keep the freedom to swap any engine later.
