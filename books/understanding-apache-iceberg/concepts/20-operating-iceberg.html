Keeping the Kitchen Clean

The data world calls this: operating Iceberg tables (table maintenance)

Here’s the problem

Picture a shared office kitchen. Every lunch rush leaves a few dishes in the sink. The fridge slowly fills with dated leftovers. Unlabeled boxes pile up on the shelf, and nobody will say whose they are. No single person did anything wrong. But after a month, nobody can find a clean fork.

A data table works the same way. Every job that writes to it leaves dishes behind. The fix in a good kitchen is boring: a rota on the wall, in the right order, with a name next to each job. Tables need the same.

The idea: four chores, each for a different mess

Iceberg gives you the tools to clean up, but nothing runs them for you. “Maintaining a table” means four chores that come around again and again. Compaction (rewrite_data_files) glues many tiny files into a few right-sized ones. Snapshot expiry (expire_snapshots) throws away old versions of the table, and the files only they used. Manifest rewriting (rewrite_manifests) tidies the table’s own notes so a query can plan faster. Orphan cleanup (remove_orphan_files) deletes files that no version points to, usually left behind by jobs that failed halfway.

Why so many? Because a table grows in more than one way. Streaming jobs that commit every minute can make tens of thousands of small files in a day, since each task writes its own file for each commit. Every commit also adds a new version, called a snapshot (a saved picture of the table at one moment). Each one is a little more clutter.

How it works: the rota, in order

The order on the rota matters: compact first, expire old versions second, remove stray files last. The picture below shows it. The red step is the one you cannot take back.

Small files cost money, not just time. In one worked example, a table of 100,000 small files needed about 200,000 read requests for a full scan and 15 to 30 seconds just to plan the query. After compacting to about 2,000 right-sized files, planning took under a second and request costs fell by around 93%. Object stores bill per request, so a pile of tiny files shows up on the invoice.

Tiny commits cost too. Every commit writes a new list of files and a new table-notes file, however little data it carries, and that notes file is rewritten whole. So batching your writes matters as much as compacting afterwards. Rewriting manifests helps in the same way: cut a table from 500 manifests to 20 and every query skips 480 separate reads.

-- Keep the 10 newest versions; drop older than a cutoff
CALL catalog.system.expire_snapshots(
  table => 'db.sales',
  older_than => TIMESTAMP '2026-10-07 00:00:00',
  retain_last => 10);

-- Compact only the recent partitions
CALL catalog.system.rewrite_data_files(
  table => 'db.sales',
  strategy => 'binpack',
  where => 'order_ts >= DATE \'2026-10-01\'');

Watch health with plain SQL. Iceberg shows its own insides as small tables (metadata tables, such as snapshots, files, partitions and manifests). Ask them for the average file size per partition, the file count per partition, and how fast the snapshot count grows. When average size drops below your line, compact. Since version 1.2, REST and JDBC catalogs can also push health numbers out to your monitoring.

Or hire it out. Amazon S3 Tables does compaction, snapshot cleanup and stray-file removal for you. Its defaults are a 512 MB target file size, at least one snapshot kept, and a 120-hour limit on snapshot age. AWS Glue also offers managed compaction for Parquet Iceberg tables that does not block queries running at the same time.

Design principle

A lakehouse is a product, not a pile of files. A product needs owners, promises about how fast and fresh it will be, and a plan for its whole life, including how old things leave.

Use case: the streaming table that got slow

A team streams orders into a table, committing every minute. For weeks it is fine. Then dashboards crawl and the storage bill shows a jump in requests. A look at the file metadata table shows thousands of tiny files per day. The team sets a rota: compact recent partitions nightly, expire versions after the agreed history window, remove stray files weekly, and name one owner. They also batch the stream into fewer commits. Planning time drops, and the bill follows.

Watch out for

  • Expiring snapshots is permanent. Set the history window from audit and recovery needs, not from the storage bill alone.
  • Running orphan cleanup with a very short age window can delete files from jobs still writing, and corrupt the table. The default is 3 days, and a dry run comes first for a reason.
  • Storage grows right after compaction. The old files stay until the versions that use them expire, so cleanup takes two steps.
  • Assuming the format cleans itself. Iceberg ships the chores, but nothing schedules them, so an unowned table slowly decays until queries and bills show it.

Because someone owns a short, ordered rota, your tables stay fast and cheap to read, and you find out about trouble from a dashboard instead of from the bill.
