Teaching a Computer the Same Lesson Twice

The data world calls this: machine learning and AI workloads

Here’s the problem

Six months ago a team taught a computer to guess which customers were about to leave. Now the model is under review, and someone asks a simple question: “What exactly did it learn from?” The team looks at the table. It has changed every day since. Rows were fixed, rows were added, some were removed. The lesson book the computer studied is gone.

Now picture a table that remembers. One query, pointed at the label the team stuck on the table the day they trained, brings back the exact rows the model studied. It works like checking out the same Git commit a program was built from, only for data.

The idea: the lesson book keeps every edition

Every save to an Iceberg table makes a new, unchangeable snapshot with an ID and a time. So the exact state of a training table, months ago, can be asked for later without keeping a second copy. Versioning the data is a property of the table itself, not a separate system to run.

For learning from data, that means reproducible training (you can rebuild the same model from the same rows on demand). Teams write the snapshot ID next to the model, in a tracking tool such as MLflow, and read it back later with VERSION AS OF. The same trick, time travel (asking a table what it looked like at an earlier moment), also gives point-in-time correctness (a training row may only use facts known at that moment). Without it, tomorrow’s news leaks into yesterday’s lesson, and teams hand-build tangled joins to stop that.

How it works: pin the data like you pin the code

Tags beat bare IDs. A raw snapshot ID can be swept away when old versions are retired. A tag (a named label on a snapshot) is kept under its own retention rule, so it survives that cleanup for as long as you say.

-- Freeze the training set at model-build time
ALTER TABLE ml.churn_training CREATE TAG `churn-model-v12`;

-- Months later: reproduce the exact training data
SELECT * FROM ml.churn_training VERSION AS OF 'churn-model-v12';

Fixes and retraining. Row-level updates fix mislabeled records, and deletes honor requests to erase a person. Each change makes a new auditable snapshot. The changelog view (a list of exactly which rows changed between two versions) shows what is different between two training runs.

Try ideas on a side road. A branch (a separate line of table history) lets a team build and check a candidate training or test set without touching the main one, then merge it forward or throw it away. It is the same move used for data quality gates.

Python can walk right in. PyIceberg reads tables from plain Python, with no JVM, into Arrow, pandas, or DuckDB. That puts lakehouse tables within reach of notebooks, Ray, and PyTorch data loaders.

Design principle

A model is only as repeatable as its data. Pin the data the way you pin the code, with a named label that is kept on purpose.

Use case: churn guesses, recommendations, and test sets

The churn story above is the plain version. A bigger one is Netflix’s Axion, the fact store behind its personalization models. It keeps logged raw facts in Iceberg tables, paired with a fast cache for quick lookups, and rebuilds features from those facts on demand. That cut the data prep for an experiment from weeks of waiting on new feature logging to hours. The same habit suits testing language models: freeze an evaluation set with a tag, and every model version gets graded on the same questions.

Deciding: when to lean on the table

SituationChoiceTrade-off
Must rebuild a model’s exact training dataTag a snapshot, record the tag with the runTags keep old files around, so storage grows
Compare two training runsChangelog view between snapshotsOnly shows data; not code or settings
Build a candidate evaluation setUse a branch, then merge or discardBranch reads use the table’s current columns
Notebook or Python training jobPyIceberg into Arrow or pandasFine for scans; not a live lookup service
Answers needed in milliseconds at serving timeNot Iceberg alone; add a fast cacheNetflix pairs its tables with one

Watch out for

  • Pinning a bare snapshot ID. Cleanup can remove it and quietly break reproducibility. Tag anything a model depends on.
  • Thinking the snapshot is the whole recipe. It pins only the data. Version the feature code, settings, and environment too.
  • Tags and branches read differently: a branch read uses the table’s current columns, while a tag or snapshot read uses the columns as they were. That can change a feature pipeline’s column list.
  • Erasure beats perfect memory. After a privacy delete, the “exact” old training set legally must change. Write that difference down rather than pretending the snapshot is untouched.

Sources: Dremio, “Apache Iceberg + Machine Learning: Solving Data Versioning for AI”; Apache Iceberg docs on Branching and Tagging, Spark Queries, and Spark Procedures; ZenML and IEEE summaries of Netflix Axion; DZone on PyIceberg; InfoQ, “Reproducible ML with Apache Iceberg”.

Because the table remembers every edition of the lesson book, you can answer “what did it learn from?” with one query instead of a shrug.
