Part III · Architecture and Design Principles

The Warehouse and Its Ledger

The data world calls this: storage, files, and metadata

Here’s the problem

Picture a warehouse full of sealed crates. A worker has an order: “bring me every crate with an amount over 500, from this month.” With no paperwork, the worker opens every crate in every aisle to peek inside. That takes all day, and most crates were never going to match.

Now give the front office an inventory ledger. For each sealed crate it records what is inside, the range printed on its label (smallest and biggest amount), and the aisle it sits in. The picker plans the whole route at the front office and walks straight to the few crates that matter, without opening a single one. An Iceberg table is that warehouse plus that ledger.

The idea: plain files on cheap shelves, plus a careful ledger

The warehouse is object storage (cheap, huge, shared file storage in the cloud, such as Amazon S3, Azure’s ADLS or Google Cloud Storage, or look-alikes you run yourself). An Iceberg table lives there as ordinary files. Iceberg needs no storage service of its own. It only adds a convention for tracking which files make up the table.

That convention was built around what shelves like these are bad at. Asking them to list a folder is slow, and renaming a file is not safe to count on. So Iceberg never uses listings or renames to say what the table is. It writes new files that are never edited afterward, then moves one pointer at the catalog in a single step. Older Hive-style tables leaned on folder listings and suffered on S3 for it.

The crates are data files, usually in Parquet (a column-by-column file layout, so a question about two columns reads only those two). Avro and ORC are allowed too. Column layout compresses well, and each chunk of a file carries its own small and big values, so even inside a file a reader can skip chunks.

How it works: a tree of notes that never change

The ledger is a tree with four layers. The catalog points to one table metadata file (a small JSON note with the table’s shape history, its partition rules and a log of snapshots). Each snapshot has a manifest list (an Avro file naming the manifests, with a summary of the partitions each covers). Each manifest (an Avro file) lists data files, along with their partition values and per-column smallest, biggest and empty counts. Every layer is immutable. A new snapshot simply reuses the manifests that did not change.

catalog entry: db.orders -> s3://lake/orders/metadata/00012-abc.metadata.json
  00012-abc.metadata.json   (schemas, partition specs, snapshot log)
    └─ snap-9871.avro              manifest list for current snapshot
        ├─ manifest-a1.avro        -> 140 data files (2026-09, col min/max)
        └─ manifest-b2.avro        -> 6 data files + 2 delete files (2026-10)
            └─ data/.../file-0001.parquet

This is why planning is fast. An engine prunes in stages, without touching the data. First, partition summaries in the manifest list let it skip whole manifests. Then the smallest and biggest values in each manifest let it skip single files: a filter of amount over 500 skips any file whose biggest amount is 400. Last, the chunk statistics inside Parquet files trim what remains. Cost grows with the size of the ledger, never with a folder listing.

The ledger also grows. Every commit adds a snapshot, a manifest list and usually new manifests. Frequent tiny commits, the habit of streaming jobs, pile up small data files and a heavy ledger, and planning slows as manifests multiply. Iceberg tracks small files efficiently, but it does not stop them from appearing.

Design principle

Optimize for the whole lifecycle: write, query, evolve and maintain. A table that is quick to write but never tidied gets slow to read. Compacting small files toward a target size (commonly 128–512 MB), expiring old snapshots, removing orphan files and rewriting manifests are part of the design, not chores for later.

Upkeep is increasingly done for you. Amazon S3 Tables runs compaction, snapshot expiry and orphan cleanup in the background. AWS Glue’s table optimizer compacts when a partition passes a file-count limit, and Databricks Unity Catalog’s predictive optimization handles compaction and snapshot expiry for its managed Iceberg tables.

One change at the file layer is worth knowing. Format version 3 replaces position-delete files with deletion vectors (tiny bitmaps attached to a data file that mark which rows are gone) and gives each row a steady ID with a last-changed number. Version 3 readers can read version 2 tables, but not the other way round.

Use case: a stream that must stay fast

A team feeds orders in all day, committing every minute. By week two the dashboards crawl, because thousands of tiny files and manifests are in the way. They schedule compaction toward large files, expire snapshots older than their retention window, and let the manifests be rewritten. The same queries drop back to reading a handful of well-sized files.

Deciding: how much care the shelves need

SituationApproachTrade-off
Big tables, mostly read in slicesRely on the ledger; sort or group data on the columns people filter byPruning only works if file ranges don’t overlap
Streaming or frequent small commitsPlan compaction and snapshot expiry from day oneUpkeep costs compute, but skipping it costs more at read time
You don’t want to run upkeepA managed service that tidies in the backgroundLess control, more tie-in to that service
Tiny tables, or very frequent single-row changesThink twice; a database may fit betterFiles plus a ledger have overhead that small data never repays

Watch out for

  • Thinking Iceberg “solves” small files. It tracks them well; it doesn’t prevent them.
  • Deleting or moving files by hand in the bucket. Anything a live snapshot points to may only be removed through the table’s own upkeep steps.
  • Expecting label ranges to help on randomly scattered values. If every file’s range overlaps your filter, nothing is skipped and nobody tells you.
  • Forgetting that the ledger is files too. Lose the current metadata file, or set the wrong permissions on its folder, and the table breaks even if every crate is fine.

Sources: Apache Iceberg Table Spec; Iceberg docs on reliability; Dremio on metadata performance and manifest files; Amazon S3 Tables; AWS Glue compaction; Databricks Unity Catalog managed tables; AWS and Databricks on Iceberg v3; best practices for snapshot expiration.

Because a careful ledger tells every engine exactly which few files matter, your queries stay fast and cheap on plain storage, as long as you keep the ledger tidy.
