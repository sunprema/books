Part III · Architecture and Design Principles

Proofread Before You Print

The data world calls this: reliability, write-audit-publish and data contracts

Here’s the problem

Picture a newspaper. Reporters file their stories onto the proof pages. Editors read those proofs and check the facts, while yesterday’s paper is still on the newsstand for anyone to buy. Only when the editors say “good” does the new edition get printed, all at once.

Now imagine a paper with no proof stage. Stories go straight onto the newsstand page by page, and readers pick up a front page with half its words missing. That is how old-style data tables behaved. This chapter is about how to run your tables like the good newspaper.

The idea: a change is all in, or not there at all

In older folder-style tables, what the table “was” depended on which files you saw when you listed a folder. So a reader could see a half-finished load, renaming folders on cloud storage was not one single step, and nothing could change several partitions as one act. Iceberg removes that whole kind of “half-loaded table” accident by design.

Here is why. The only way an Iceberg table changes is one swap: the catalog’s pointer moves from the old metadata note to the new one. That is the atomic commit (a change that either lands in full or is not there at all). There is no in-between state for a reader to bump into. The guarantees apply to one table at a time, the same family of promises databases call ACID (safe, all-or-nothing changes).

Readers get a calm view too. A query picks one frozen snapshot (the table as it stood at one moment) and sticks with it until it finishes, however many writers commit meanwhile. This is called snapshot isolation.

How it works: two writers, no locks, and a proof stage

Writers do not queue up behind a lock. Each one prepares its new files, assuming nothing has changed, then tries the swap. This is optimistic concurrency (go ahead, and check at the end). If another writer got there first, the loser looks at the fresh table, checks its work still makes sense, and tries again.

Two kinds of failure hide here. Losing the race for the pointer is harmless, and retries fix it automatically. But if two writers changed the same rows or files, the check fails, and no number of retries helps. The cure is to design writers that touch different partitions or rows. Plain appends never clash this way. For row changes, you pick how strict to be: the strict level fails if any concurrent commit added files that might hold matching rows, and the looser level is more forgiving.

Atomic commits stop broken tables. They do not stop wrong data. For that there is write-audit-publish (stage the data, check it, then show it to readers). The pipeline writes to a named branch (a side copy of the table’s history). Checks run on the branch while the main table is untouched. When the checks pass, main is moved up to the branch in one step, called a fast-forward. Branch-based write-audit-publish has been the recommended pattern since Iceberg 1.2.

ALTER TABLE lake.db.events SET TBLPROPERTIES ('write.wap.enabled'='true');
-- each run writes to its own branch (Spark session: SET spark.wap.branch = etl_run_42)
INSERT INTO lake.db.events SELECT ...;            -- lands on branch, invisible on main
SELECT count(*) FROM lake.db.events.branch_etl_run_42
WHERE event_time IS NULL;                          -- audit the staged data
CALL lake.system.fast_forward('db.events', 'main', 'etl_run_42');  -- publish atomically

Those are the three steps in Spark SQL: write to the branch, audit the branch, fast-forward main. And if a bad batch slips through anyway, old snapshots are still kept until you expire them. So you can roll the table back to an earlier snapshot in seconds, instead of re-running pipelines or digging up backups.

The table’s promise to its readers

An Iceberg schema works like a data contract (a written promise about what a table looks like). The schema is versioned in the table’s metadata, each column has a stable ID, and engines check every write against it. The shape changes only through deliberate schema changes, never because of whatever files happened to land in the folder.

Design principle

Make bad data visible before it reaches consumers. Stage every change where nobody is reading, check it there, and publish it in one step. Then a mistake is a failed check on a side branch, not a wrong number in someone’s report.

Use case: the nightly orders load

A team loads orders every night. Each run writes to its own branch and counts rows with missing timestamps. If the count is zero, the run fast-forwards main, and the morning dashboards show the new day all at once. If not, the run stops, the branch is thrown away, and yesterday’s numbers stay in place while someone looks into it.

Deciding: how much checking do you need?

SituationApproachTrade-off
Reports or models depend on the tableWrite-audit-publish with a branch per runAn extra step and extra storage per run
Many writers on one tableKeep writers on different partitions or rows; batch the commitsVery frequent commits cause retry storms that burn compute
Several tables must change togetherOrchestrate carefully, or use catalog-level branchingCore Iceberg promises are per table, not across tables
Scratch data, low stakesPlain atomic commits are enoughNo staging, so bad data is only caught after the fact

Watch out for

  • Believing the guarantee covers more than one table. It does not.
  • Fast-forward fails if main moved on after the branch began. Several pipelines publishing to one table need a rebase or cherry-pick plan, not just this pattern.
  • Forgotten branches. A stale branch quietly keeps every file it points to, which blocks cleanup and grows your bill. Give audit branches an expiry.

Sources: Apache Iceberg Table Spec; Apache Iceberg docs on reliability and branching; Dremio and lakeFS write-audit-publish guides; AWS Glue Iceberg commit-conflict documentation; Cloudera snapshot-expiry documentation.

Because changes land whole and get checked before anyone sees them, you can trust the number on the screen and fix a bad night by simply not publishing it.
