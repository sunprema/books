Part I · The Problem Iceberg Solves

The Box, Not the Ship

The data world calls this: Iceberg is a table format, not a database or an engine

Here’s the problem

Picture a busy harbor. Goods arrive in standard steel boxes. Every box has a paper list on it that says exactly what is inside. A port office keeps a register that points to the newest list for each box. And any crane, from any port, can lift any box, because the boxes all have the same shape.

Now someone asks, “So is the box the ship? Does the box replace the crane?” Of course not. The box is only an agreement about how goods are packed. It moves nothing by itself.

People ask the same thing about Iceberg all the time: “Is it a database? Does it replace Spark?” Iceberg is the box.

The idea: a rulebook, not a running machine

The project describes itself as a high-performance format for huge analytic tables. It brings the reliability and simplicity of SQL tables to big data, so that engines such as Spark, Trino, Flink, Presto, Hive and Impala can safely work with the same tables at the same time.

Look at the word “format.” Iceberg is a written specification (a public rulebook that says how a table must be stored) plus code libraries that follow it. There is no Iceberg server humming away somewhere. A table is just data files and record files sitting in storage, plus one pointer that says which record file is the current one. The libraries live inside whatever engine is reading or writing.

So you cannot “install Iceberg” like a program. Using it means choosing a place for the pointer, at least one engine, and a person who owns upkeep. The format is the agreement between those pieces.

How it works: four parts that cooperate

Think of a table as four cooperating parts. Data files hold the rows, in formats like Parquet, ORC or Avro. Metadata files (snapshots, manifest lists and manifests) record exactly which files make up each version of the table. A catalog (the register that maps a table name to its current metadata file) holds the pointer. And any number of engines (programs that actually run queries, like Spark, Trino or Flink) read and write through that metadata.

# the chain every read follows
ENGINES   Spark | Trino | Flink | DuckDB | Snowflake
             |
CATALOG   db.sales -> s3://lake/sales/metadata/v412.metadata.json
             |
METADATA  metadata.json -> manifest list -> manifests (file stats)
             |
DATA      s3://lake/sales/data/*.parquet

What does this middle band give you? Real table behavior: a schema whose columns have stable ID numbers, and partitioning kept as a table setting instead of folder layout. All-or-nothing commits with serializable snapshot isolation (readers and writers do not trip over each other). Saved versions called snapshots, so you can look back in time or undo a bad change. Safe changes to schema and partitions. And column statistics, so a query can skip files it does not need.

What does it leave out? It does not run queries, it is not the storage, it does not load or schedule your data jobs, and it does not draw dashboards. Its speed comes from planning, not scanning. The records let an engine plan a read in a fixed number of remote calls and skip files using partition values and min/max numbers. But the engine still reads the Parquet files that remain. Iceberg helps engines waste less work; it does not do the work.

Design principle

Standardize the table, not the machine. When the shape of the box is a public agreement, the cranes can compete, change and multiply, and the goods never have to be repacked.

Two things people get wrong

“Iceberg replaces Spark.” That mixes up two different jobs. Spark runs queries. Iceberg says what the table is. They work together, and Spark is still one of the main engines that reads and writes Iceberg tables.

“Iceberg is a database.” Close, but wrong in a useful way. It has no computing, no sessions and no query planner of its own. The closer picture: the table layer of a database, pulled out of the engine and shared, so many engines can treat the same files as one steady table. It also aims at big analytic tables with changes made a commit at a time. Row-level updates and deletes exist to serve corrections, change feeds and compliance deletions, not thousands of tiny single-row transactions.

Use case: one table, three crane operators

A company keeps its orders as one Iceberg table in cloud storage. A streaming job adds new orders all day. Analysts query the table with a SQL engine. The data science team reads the same table from a notebook. Nobody copies anything, and a reader never sees half of a write. Each team chose the engine it likes, and the table did not care. That only works because the table is defined by the format and not by any one tool.

Deciding: what to expect from it

You need…Iceberg?Who really provides it
Reliable big analytic tables, versions, safe schema changesYesThe format and its metadata
Many engines sharing one tableYesThe format, plus a shared catalog
Running queries fastNoYour engine
A place to keep bytesNoObject storage

Watch out for

  • Iceberg does not look after itself. Compaction, expiring old snapshots and cleaning stray files are jobs some engine must run, or tables get slower and costlier.
  • Do not read the Parquet files directly and skip the metadata. Deleted rows come back, and half-written files get counted, because only snapshots decide what belongs to the table.
  • A table is only as all-or-nothing as its catalog. The commit is the catalog’s pointer swap, so a weak or bypassed catalog gives up the safety.

Sources: Apache Iceberg Table Spec; Apache Iceberg project site; Databricks, Iceberg v3 (2025).

Once you see Iceberg as the box and not the ship, you stop asking it to do the crane’s job, and you can swap engines without ever repacking your data.
