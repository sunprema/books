Sort the Files So Questions Skip Most of Them

The data world calls this: hidden partitioning

Here’s the problem

Picture a mailroom where every sender must hand-write a routing code on the envelope, and every carrier must memorize the plan of the shelves. If one sender writes the code wrong, the letter lands on the wrong shelf and nobody notices. If a carrier does not know the plan, they walk every shelf looking for one letter.

Now picture a post office that works the way a real one does. Senders write only the address. The office works out the routing itself. And when the office decides to rearrange its shelves, it does not ask anyone to mail their old letters again.

Big tables are the first mailroom. Iceberg is the post office.

The idea: group rows so a question can skip the rest

Partitioning (grouping rows into files by a shared value, such as the day they happened) lets a question that asks about one day ignore every file from other days. On a very large table, this is the biggest single lever for how much data a question has to touch.

The old way, called Hive-style, makes each group a real folder keyed by an extra column. If your rows have an event_time, someone must add a second column, say event_date, as text, and fill it in correctly on every write. Then every question must filter on event_date by name. Forget, and the question quietly reads everything.

The official docs spell out the costs. The engine cannot turn a filter on event_time into a filter on event_date by itself. People who do not know the folder layout get slow questions. A wrongly written event_date gives wrong answers with no error. And because every question names the folder column, the layout can never change without breaking them all.

How it works: the table does the sorting

Iceberg’s answer is hidden partitioning (the table is told a rule, such as “group by the day of event_time”, and applies it itself, so nobody sees or fills in a helper column). The rule is called a transform (a small, fixed recipe that turns a real column into a group label). The format defines a short list: use the value as is, take the year, month, day or hour of a time, hash a value into N buckets (good for things like user ids with huge numbers of values), or cut a value down to its first W characters.

Writers hand over raw values. Iceberg applies the transform and records each file’s group label in its metadata. That removes a whole family of bugs where the sender’s idea of the label and the table’s idea disagree. Readers just ask about event_time. Iceberg knows the transform, so it turns that question into a question about day labels and skips every file whose label cannot match.

The groups live in the metadata, not in folder names. File paths do not matter for correctness, which is why one table can hold several layouts across its life.

CREATE TABLE prod.db.events (
  id bigint, event_time timestamp, device string)
USING iceberg
PARTITIONED BY (days(event_time), bucket(16, id));

Changing your mind later

Data grows and questions change. A table that was fine with one group per day may later want one per hour. In Iceberg this is a change to the table’s records only. The new rule gets a new number, new files follow it, and old files keep the layout they were written with. The planner checks each file against the rule it was written under. Nothing is rewritten, nothing goes offline, and no question breaks.

-- Partition evolution: metadata-only, old files untouched
ALTER TABLE prod.db.events ADD PARTITION FIELD hours(event_time);
ALTER TABLE prod.db.events DROP PARTITION FIELD bucket(16, id);
Design principle

Partition for your questions, not for convenience or habit. Look at what people actually filter on, group by that, and keep the rule out of their sight. When the questions change, change the rule.

Use case: the events table that outgrew its shelves

A product team stores every click in one table. At first it grows slowly and a group per day is plenty. A year on, volume has jumped and most questions look at the last few hours. On a Hive-style table, changing from days to hours means a new helper column, a rewrite of the whole history, and a message to every analyst to change their questions. In Iceberg, an engineer adds an hourly rule. From that moment, new data is grouped by hour. Old data stays grouped by day. Analysts keep filtering on event_time and never notice.

Deciding: how to choose the rule

SituationReach forTrade-off
Questions filter on a time rangeDay, or hour for very busy tablesFiner groups skip more but make more, smaller files
Lookups on a key with millions of valuesBucket into N groupsSpreads load evenly; does not help range questions
Questions on a short category or prefixUse as is, or cut to a prefixFine only if the number of values stays small
Small table, or no common filterNo partitioning at allSimpler; the file statistics still help
Questions have shifted over timeEvolve the ruleOld files keep the old layout until you choose to rewrite them

Watch out for

  • Do not carry Hive habits over. Adding a text event_date column just to partition by it brings back the duplicate column and the wrong-value bugs that hidden partitioning removes.
  • Too many groups, such as a raw high-value column or too fine a time slice, makes a swarm of tiny files and slows both writing and planning.
  • Evolution does not rewrite history. A question that spans the change prunes the old data less well until you choose to rewrite it.
  • Filter on the real column. Wrapping event_time in a formatting function can hide it from the table, so pruning may not happen.

Sources: Apache Iceberg docs, Partitioning, Evolution and Spark DDL; Apache Iceberg Table Spec; RisingWave on hidden partitioning.

Because the table sorts the files for you, your questions stay fast and honest, and you can reshuffle the shelves later without asking anyone to mail their letters again.
