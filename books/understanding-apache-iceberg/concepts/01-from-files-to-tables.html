Part I · The Problem Iceberg Solves

A Folder of Files Is Not a Table

The data world calls this: moving from files to a managed table format

Here’s the problem

Two jobs write into the same folder of data files. At midnight, one of them dies halfway through. It leaves a few half-finished files behind.

In the morning, every dashboard that looks inside that folder counts those leftover files as real data. The numbers are too big. Nobody gets an error. Nobody knows why the totals look wrong.

That is what happens when a table (a named, trusted set of rows) is really just whatever files happen to sit in a folder right now.

The idea: a table is a list, not a place

Data lakes keep information in cheap storage as files. A popular file type is Parquet (a way to lay out the bytes of one file so columns are quick to read). But Parquet only says how the bytes inside one file are arranged. It says nothing about which files, taken together, make up a table.

The older answer, the Hive way, called a folder a table. A small side-database, the metastore (a notebook of folder names), remembered the folders. But the files inside each folder were found by listing the storage at read time. So the table was whatever was in the folders at that moment.

Iceberg changes one thing. The table becomes an explicit written list of files, kept in its own records. A file is in the table only if the list says so.

What people expect from a table

Anyone who has used a database expects a lot from the word “table”:

  • A defined shape — named columns that can change safely.
  • Consistent reads — you never see a half-done change.
  • All-or-nothing writes — a change fully lands or does not land at all.
  • Row-level fixes — update or delete single records.
  • History — ask what the table looked like before.
  • Fast planning — find the right files without opening everything.
  • A name to guard — something that access rules and governance can attach to.

A bare folder of Parquet files gives you none of these.

How it works

Think about why the folder way breaks. The table’s facts live in two places: the notebook (folders) and the storage (files). No one can change both in a single step. So a job that rewrites several folders can be seen half-done by someone reading at the same time. A job that crashes leaves half-written files that readers count as data.

Cloud object storage makes it worse. Netflix kept its data on S3, not on a classic cluster file system. Listing folders there was slow and, back then, could show stale answers. Renaming a file was really copy-then-delete, which is not one step. And the work of planning a query grew with every folder and file. These troubles pushed Netflix to design Iceberg.

In Iceberg, a snapshot (the full set of data files that make up the table at one moment) is recorded through a chain of small records, a manifest list and manifest files. Data files are written in place first. They join the table only when a commit (one all-or-nothing step) writes a new metadata file and swaps the table’s “current” pointer in a catalog (the table’s address book).

# What storage sees              # What the table knows
s3://lake/sales/dt=2026-10-13/   metadata/v412.metadata.json  <- current pointer
  part-0001.parquet  (job A)       snapshot 9812: [files...]
  part-0002.parquet  (job A)       snapshot 9813: [files...]
  part-0003.parquet  (crashed B!)  # never committed -> invisible to readers

Writers are polite: if two try to commit at once, one retries on top of the other’s result when the rules allow. Readers keep using the snapshot they first loaded, so they never see a partial write. And since the list also carries each file’s partition values and column statistics, planning a query takes a fixed few calls, and files can be skipped without opening them.

Back to the midnight crash: in Iceberg the dead job leaves only unreferenced files. Those sit in storage, but no snapshot points to them, so no dashboard counts them.

Design principle

Define the table by an explicit, versioned list of files, not by what a folder contains. Then “what is in the table” is a decision someone made, not an accident of storage.

Use case: the shared sales table

Picture a sales table that a nightly job loads, a streaming job tops up, and five teams query. With folders, every team has a story about double counts or a report that changed while it ran. At industry scale this is the same pattern the researchers behind the lakehouse idea describe: lakes caused reliability and stale-data troubles, so companies copied lake data again and again into a separate warehouse. With a managed table, one copy serves everyone, and a failed load simply never happened.

Deciding: when it is worth it

SituationFolder of filesManaged table
One-off export, one readerFine and simpleOverkill
Many writers or readers at onceHalf-done reads, double countsClean all-or-nothing commits
Need history or fixes to single rowsRewrite folders by handBuilt in
Huge tables on cloud storageSlow listing, slow planningPlan from metadata
Cost to adoptNoneNeeds a catalog, upkeep, and tools that understand the format

Watch out for

  • Object stores are not file systems. Renames are copies, listings are billed requests, and no multi-file step is all-or-nothing.
  • Adding a Hive metastore does not fix this. It tracks folders, not files.
  • Even with Iceberg, a file in the bucket is not automatically in the table. A tool that scans the bucket directly will still see uncommitted and orphaned files.

Sources: Apache Iceberg Table Spec; Iceberg docs, Reliability; Armbrust et al., Lakehouse (CIDR 2021); Ryan Blue, Iceberg: a fast table format for S3 (Strata NY 2018).

When your table is a list you can trust, a crashed job stops being tomorrow’s mystery and becomes a non-event.
