The Table That Answers the Auditor

The data world calls this: compliance, audit, and data products

Here’s the problem

A rule-checker from the government writes to you: “What did your risk table say on March 31?” The old way is a long scramble. Someone finds a backup, sets up a scratch machine, loads the backup, and hopes it matches what was really on screen that day.

Now picture a team that tagged the table the night the quarter closed. They type one question, pointed at that tag, and the exact table comes back. The trail of proof was the table all along.

The idea: the table is its own record book

Every change to an Iceberg table makes a new saved version. So time travel (asking a table what it looked like at an earlier moment) turns audits into questions you can type: TIMESTAMP AS OF or VERSION AS OF brings back the table as the checker would have seen it. The history and snapshots lists record every version, what kind of change it was, and which program wrote it.

Two more tools finish the picture. A tag (a named label on one saved version) can be kept for as long as you choose; the official docs suggest an end-of-year tag kept forever, or an end-of-week tag kept seven days. A branch (a separate line of table history) gives new data a waiting room, so nobody reads it until it has been checked.

How it works: forgetting takes two steps

Remembering everything is the easy half. The hard half is a person asking you to erase their data. A DELETE on an Iceberg table is only a note that says “hide this row.” The bytes still sit in the data files, and in every older version. They truly go away only after old versions are retired and the affected files are rewritten.

-- Preserve the audited quarter-close state indefinitely
ALTER TABLE prod.finance.risk_positions CREATE TAG `Q1-2026-close` AS OF VERSION 365;

-- Answer the auditor from the preserved state
SELECT * FROM prod.finance.risk_positions VERSION AS OF 'Q1-2026-close';

-- Erasure: logical delete, then make it physical
DELETE FROM prod.crm.customers WHERE customer_id = 42;
CALL catalog.system.expire_snapshots(table => 'prod.crm.customers');
CALL catalog.system.rewrite_data_files(table => 'prod.crm.customers');

Memory has a length. Retiring old versions also retires your power to look back. Common settings keep only about five days of history, so how far an auditor can travel is a rule you set for each table, not a free gift.

Check before you publish. With the audit-branch pattern, new data is written to a waiting branch, checked, and only then moved onto the main line. Bad data is never seen by readers. Netflix uses this pattern across thousands of production tables. If a mistake gets out anyway, rollback_to_snapshot undoes it, and cherrypick_snapshot lets you promote one checked change by its ID. It is release management, but for data.

From tables to products. A data product (a table other teams can trust, with an owner and clear rules) needs more than snapshots. LinkedIn’s OpenHouse wraps Iceberg tables in a control layer for upkeep, retention and sharing rules. At open-sourcing in 2024 it managed over 3,500 production tables for more than 550 daily users.

Design principle

Put the proof inside the thing you are proving. When history, labels, and checked publishing live in the table itself, trust is built in rather than rebuilt for each audit.

Use case: regulated reports and customer data

A bank tags its risk table at every quarter close and answers each inquiry with one query on the tag. Its customer table is run on another rule: short history, regular rewrites, so an erasure request is truly honored within a set time. Same tool, two different retention settings, each picked on purpose.

Deciding: when to lean on it

SituationChoiceTrade-off
Auditor asks about a past dateTag at close, query with AS OFA tag keeps every file it points at, so storage grows
Person asks to be erasedDelete, expire, then rewrite filesCosts compute, and backups need their own plan
Unchecked data must not reach readersWrite to a branch, check, then publishAn extra step before data is visible
Wrong data already publishedRoll back to the earlier snapshotReaders see the older table until fixed
Who may read which column?Not snapshots; use the catalog and governance layerHistory shows what changed, not who may see it

Watch out for

  • Treating DELETE as erasure. The data lives on in older versions, in unrewritten files, and in backups and storage version history.
  • Long memory for audits and short memory for privacy pull opposite ways. Set retention per table, or one rule will quietly break the other.
  • A forever tag on a table with personal data can keep rows alive long after they were “deleted.”
  • History is not access control or lineage by itself.

Sources: Apache Iceberg docs on Spark Queries, Spark Procedures, Branching and Tagging, and Spark Structured Streaming; Dremio, “Apache Iceberg and the Right to Be Forgotten”; Data Lakehouse Hub on GDPR hard deletes; Netflix write-audit-publish summary (VuTR); LinkedIn Engineering and InfoWorld on OpenHouse.

Because the table keeps its own proof and forgets only when you tell it how, you can answer an auditor in one query and honor a privacy request without guessing.
