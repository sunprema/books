Fixing One Row Without Redoing the Whole Table

The data world calls this: updates, deletes, copy-on-write and merge-on-read

Here’s the problem

A printer finds one wrong word on page 212 of a thick book. There are two ways to fix it. He can reprint the page, so every future reader gets a clean book. Or he can ship the book as it is, with a slip of paper that says “page 212, line 4: read this instead.” Every reader must then check the slip as they go.

Either way the word gets fixed. The only question is who pays: the printer, once, at the press, or every reader, every time they read. Later, when enough slips pile up, the printer makes a new printing that folds them all in.

Tables full of data face the same choice every time someone says, “change this row” or “forget this person.”

The idea: rows must be able to change

It is tempting to believe that data for reports only ever grows. In real life it does not. People ask you to erase their data to follow privacy laws such as GDPR and CCPA. A source system sends bad numbers that must be corrected. A customer moves, and the old address must be replaced while the history is kept (the data world calls these slowly changing dimensions, tables where a few facts about a thing change now and then). And a live shop database sends a stream of its changes to the report tables, a trick called CDC (change data capture, copying every insert, edit and delete from one database to another).

Before Iceberg, lakes of files handled all of this the blunt way: find the groups of files that held the row and rewrite those whole groups. Iceberg’s version 2 format made row-level delete, update and merge a normal part of the table. Each one is a single all-or-nothing step, so a reader sees the table before the change or after it, never half.

How it works: pay at press time or at reading time

Iceberg offers two ways to carry out a change. In copy-on-write (rewrite every file that holds an affected row, and write it out clean), reading stays simple and fast, because the files are always clean. But the cost follows the number of files touched, not the number of rows changed. Fix one row in a gigabyte file and you write a gigabyte.

In merge-on-read (leave the data files alone and write a small side file listing the rows that no longer count), the change is quick and cheap to write. The bill moves to the reader, who must lay the slip over the page on every scan. The more unmerged slips there are, the more each read costs.

The slips come in two kinds. A position delete (a note naming the exact file and row number) is precise and easy for readers, but the writer must first find the rows. An equality delete (a note saying “any row with this value is gone”) needs no looking up before writing, which streaming writers like, but it is the costliest for readers, who must compare values on every scan.

Version 3 of the format swaps position slips for deletion vectors (one compact tick-list per data file, kept in a Puffin file), which cuts the extra reading work. Streaming jobs that write equality deletes usually convert them to vectors during upkeep. Version 3 is real today: Iceberg 1.10.0 made it generally available, 1.11.0 (May 2026) is current, and AWS, Snowflake and Google support it. Version 3 readers can read version 2 tables, but upgrading a table is one-way.

The choice is not for the whole table. Table properties set it for each kind of action (write.delete.mode, write.update.mode, write.merge.mode), and each defaults to copy-on-write. One table can use merge-on-read for streaming deletes and copy-on-write for nightly merges.

MERGE INTO prod.db.customers t
USING staged_changes s ON t.customer_id = s.customer_id
WHEN MATCHED AND s.op = 'D' THEN DELETE
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;
ALTER TABLE prod.db.customers SET TBLPROPERTIES (
  'write.delete.mode' = 'merge-on-read',
  'write.update.mode' = 'copy-on-write');
Design principle

Choose the update strategy from your workload, not from fashion. Count how often you read and how often you change, then pay at the place that happens less. Merge-on-read is only half a plan: it needs compaction (regularly rewriting files with their slips folded in) to pay down the reading debt.

Use case: a customer table fed by a live shop

A company copies its shop database into a customer table all day long. Each batch has new customers, changed addresses and closed accounts, and the one MERGE above applies all of it as a single step. If the table is read by a handful of dashboards and changed once a night, copy-on-write keeps those dashboards fast. If changes arrive every minute, merge-on-read keeps the writers keeping up, and a scheduled compaction job keeps the readers from slowing down.

Deciding: which way to pay

SituationReach forTrade-off
Read-heavy table, changed rarely in batchesCopy-on-writeFast, simple reads; each change rewrites whole files
Frequent or streaming changesMerge-on-read plus scheduled compactionCheap writes; reads slow down until compaction runs
Streaming writer that cannot look rows up firstEquality deletes, converted laterNo read before write; costliest for readers
Mixed jobs on one tableChoose per action with table propertiesMore settings to keep track of
Table never changes after loadNeither; just appendSimplest of all, until the first privacy request

Watch out for

  • A DELETE does not erase bytes. The rows stay readable in older snapshots by time travel, and under merge-on-read they still sit inside current files, hidden by a slip. Real erasure is a pipeline: delete, compact, expire old snapshots, remove orphan files.
  • Equality delete files can hold the very values they were written to remove, such as an email address. Column minimum and maximum bounds in the metadata can keep values too.
  • Merge-on-read without scheduled compaction slows down quietly. Every unmerged slip adds read work until queries crawl.
  • Picking by fashion pays the wrong cost every time: merge-on-read on a read-heavy report table, or copy-on-write on a busy change feed. Measure your read and write mix first.

Because you can pick who pays for each change, you can fix one wrong row or honor one deletion request without reprinting the whole book.
