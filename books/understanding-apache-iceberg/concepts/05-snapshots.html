Every Change Saves a Whole New Picture of the Table

The data world calls this: snapshots

Here’s the problem

Picture a team that saves its work in Git. Every save is a commit. A commit never changes after it is made. It points to a complete copy of the project, yet it shares every unchanged file with the commit before it. The “current version” is just whichever commit a label points at. If you break something, you move the label back. If you want to remember a good moment, you stick a tag on it.

Now picture a table of data with none of that. Last night’s job wrote a bad batch. Someone is running a report right now, and files are changing under it. Nobody can say what the table looked like yesterday at noon. Undoing the mess means hunting through folders by hand.

Iceberg gives a table the same habit that Git gives a project: save a whole new picture on every change, and never rub out the old ones.

The idea: a table is a list of pictures

A snapshot (the complete state of a table at one moment, meaning the full set of data files and delete files that made up the table at that commit) is how Iceberg remembers a version. Every change makes a new one: adding rows, overwriting, deleting rows, even tidying small files into bigger ones. Nothing is edited in place. The table keeps an ordered snapshot log (the list of past snapshots, oldest to newest) and one label saying which snapshot is current.

You might fear this means copying the whole table every time. It does not. Neighbouring snapshots share the record files and data files that did not change, so a new snapshot costs only the small records for what changed.

How it works: a chain, a label, and shared files

Each snapshot also writes a short note about itself: what kind of change it was (append, overwrite, delete or replace) and how many files and rows were added or removed. That makes the table’s history double as an audit trail.

Readers and writers stay out of each other’s way. A query picks the snapshot that is current when it starts and keeps seeing exactly that, even if a writer commits halfway through. This is called snapshot isolation (every reader sees one steady picture, never a half-finished change). Writers never block readers, and readers never block writers.

Old pictures can be read. Time travel (asking a question of the table as it was earlier) works by choosing an older snapshot, either by its ID or by a time. A time is turned into whichever snapshot was current at that moment.

Undo is a label move. A rollback (pointing the table back at an earlier snapshot) touches no data files, so it is instant. The bad snapshots stay readable until you clean them up.

Names for the special ones. A tag is a fixed label on a snapshot you want to remember, such as the books at month end. A branch is its own line of commits, handy for trying a change and checking it before it goes live. Each can have its own retention rule.

-- Time travel (Spark SQL; FOR keyword optional)
SELECT * FROM prod.db.events TIMESTAMP AS OF '2026-10-01 00:00:00';
SELECT * FROM prod.db.events VERSION AS OF 10963874102873;

-- Undo a bad load, then trim history
CALL prod.system.rollback_to_snapshot('db.events', 10963874102873);
CALL prod.system.expire_snapshots(table => 'db.events',
  older_than => TIMESTAMP '2026-10-07 00:00:00', retain_last => 10);

Keeping history without keeping everything

Pictures pile up, and so do the files behind them. Retention (a rule for how much history to keep) is something you operate on purpose. Expiring snapshots removes the ones older than a cutoff. By default that means older than five days, always keeping at least the latest one. Only files that belonged to no surviving snapshot are physically deleted. A file that any kept snapshot still uses is left alone.

Design principle

Never change a thing; add a new version and move one label. Safe reads, cheap undo and a free history all come from that single habit.

Use case: the bad nightly load

At 2 a.m. a job loads a batch with the wrong currency. By 8 a.m. the finance dashboard looks odd. You look at the snapshot list, find the last one from before the job, and roll back to it. Dashboards are right again in seconds. Meanwhile the bad snapshot is still there, so the data team can read it, work out what went wrong, and fix the job. Later, retention clears it away.

Deciding: what to keep, and when it is not enough

SituationUse snapshots?Trade-off
Undo a bad pipeline runYesWorks only while the old snapshot has not been expired
Rerun a report or model on past dataYesPin the snapshot ID; a timestamp may land on a different one
Audit who changed what, and whenYesLonger history costs more storage
Test a change before readers see itYes, with a branchSomeone has to check and then publish it
Disaster recovery or a true backupNoSnapshots live beside the data; copy it elsewhere too
Keep every version foreverNoOld files are kept, so storage and records grow without limit

Watch out for

  • A snapshot is not a backup. Once history is expired, or files are deleted under the table, it is gone.
  • Never expiring anything means every replaced file is kept forever. Treat retention as a job someone owns.
  • “As of this time” picks whatever was current then, which may not be what a given job actually read. Pin IDs when you need the same answer twice.
  • Rolling back moves the label but does not erase the bad snapshots, and new commits after a rollback start a branching history.
