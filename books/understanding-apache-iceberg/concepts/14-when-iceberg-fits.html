The Right Tool for the Size

The data world calls this: choosing Iceberg — when it fits

Here’s the problem

An online shop grew very fast. Soon it had many teams, and each team kept its data in its own kind of table, readable only by its own tools. Nobody could ask one question across all of it. The silos had grown without anyone planning them.

That is close to what happened at Shopify. The team put all of its lake data into one table format, Iceberg, and let a query engine called Trino read it. The walls came down, and some questions that took hours now took seconds. One table format, many engines.

The idea: match the tool to the size of the job

A freight train is a wonderful way to move a mountain of grain. It is a silly way to bring home a loaf of bread. Iceberg is a freight train. It was built at Netflix to keep petabyte-scale tables (so much data it fills thousands of disks) reliable on cheap object storage, and it was given to the Apache foundation in 2018. Its habits — files that never change, a written history of every version, and planning a query without walking through folders — all aim at big, analysis-heavy data.

So the honest question is not “Is Iceberg good?” It is “Is my job the kind this train was built for?” Six kinds of jobs say yes loudly.

  • Huge piles of data to analyze. This is the home ground.
  • Many teams, many engines. By 2025 the big platforms could all read and write Iceberg, including Snowflake, Databricks, BigQuery and AWS. One table can serve all of them.
  • Batch and streaming into the same table. Spark jobs, Flink streams, and a Kafka sink can all feed one governed table.
  • Long-lived data whose shape keeps changing. Tables can grow new columns without being rebuilt.
  • Data you must prove. Every version is kept, so an auditor can see the past.
  • Data for machine learning. You can pin the exact training set you used.

How it works: a lot of readers, one table

Why can the middle box be shared so freely? Writers add data by committing a new snapshot (a saved view of the table at one moment). Flink commits when it takes its checkpoints. Readers always see a whole snapshot, never a half-finished one. That same history also gives you tags (a name stuck on an important version, which the docs suggest for audits and privacy-law retention) and branches (a private side copy for experiments). Teams use the same tools to freeze a training set for a model.

The proof is not small. Netflix checks data quality across thousands of Iceberg tables before it shows them to readers. LinkedIn’s tool for running tables handled more than 3,500 of them with 550 daily users when it was shared with the world. Shopify moved its central lakehouse onto Iceberg.

Design principle

Choose a tool for the problems you have, not the ones you might have. Iceberg pays you back when data is big, shared and long-lived. When none of those is true, its extra layers are a cost with no return.

Use case: the table many people trust

Picture a table of customer orders. The finance team reads it in one engine, the data scientists in another, and a stream of new orders flows in all day. Last quarter’s numbers must be reproducible next year, and the order shape changes as the shop adds new things to sell. This is a table with many hands on it and a long life. Every part of Iceberg earns its place here.

Deciding: fits, or does not fit?

Your situationVerdictTrade-off
Large analytic tables, several teams or enginesGood fitYou take on upkeep, but share one copy
Batch and streaming into one datasetGood fitFresh in minutes, not in milliseconds
Must audit or reproduce past results, or version ML dataGood fitOld snapshots cost storage until expired
Your biggest table fits on a laptopLikely overkillExtra layers add delay and chores, not speed
Orders, accounts, many single-row writes per secondWrong toolUse a database such as PostgreSQL or MySQL
Readers need data within a second, or instant lookupsWrong toolCommits come in batches, not one row at a time
One engine, one team, no second one in sightMaybe not yetA managed warehouse may be simpler

Watch out for

  • Hoping Iceberg will make small data fast. At laptop size, its extra layers only add waiting.
  • Treating its row-level updates as permission to run a shop’s live orders on it. Frequent single-row writes belong in a database.
  • Adopting the format but letting each engine keep its own catalog. The silos then come back one level up.
  • Forgetting the chores. Merging small files, expiring old snapshots and sweeping up stray files must happen on schedule, so every table needs an owner.

Because you know which jobs Iceberg is built for, you can say yes with confidence where it saves you from silos and copies, and say no where a simpler tool will serve you better.
