A Table Is a Short Chain From a Name to Some Files

The data world calls this: the three-layer architecture — catalog, metadata, data

Here’s the problem

Think of how a publisher gets you the right edition of a book. There is a front desk with a register that says which edition is the current one. That edition has a table of contents. The table of contents points to chapter lists. Each chapter list points to page indexes with short summaries. And only at the very end do you reach the pages themselves.

Nobody wanders the shelves opening every book to see what is inside. You follow the chain, and the summaries tell you which chapters and pages you can skip.

A pile of data files has no front desk. To find what belongs to a table, an engine has to walk the whole storage shelf and list every file. That is slow, and it can even show you half-finished work. Iceberg builds the front desk.

The idea: three layers, one pointer

An Iceberg table has three layers. At the top sits the catalog (a register that maps a table name to the place of its current record file). In the middle sits the metadata layer (a tree of small record files that say which data files make up the table). At the bottom sits the data layer (the real rows, in files that never change once written, usually Parquet). Everything except the catalog is just plain files in object storage.

One rule holds the whole thing together. The catalog’s pointer to the current metadata file is the single source of truth. Whatever that pointer names is, by definition, the table. A file sitting in the same folder that the pointer does not lead to is not part of the table, even if it looks like it should be.

How it works: down the chain, and back up

The middle layer has three kinds of file. The metadata.json (the table’s main record) holds the schemas, how the table is split up, its settings, the current snapshot, and a log of older snapshots. Each snapshot points to exactly one manifest list (a chapter list for that version, with summaries such as the range of values in each part). The manifest list points to manifests (page indexes that list data files, with each file’s place, row count, and the smallest and biggest value of each column).

The read path goes top-down. The engine asks the catalog for the table, opens the current metadata.json, and picks a snapshot. The newest one is the usual choice; an older one is what time travel means. It opens that snapshot’s manifest list and drops any manifest the summaries rule out. It opens the manifests that are left and drops any file whose numbers cannot match. Only then does it read the files that survive. So the skipping happens in two steps before a single row is touched, and the engine never has to list a storage folder.

The write path goes bottom-up. A writer first writes new data files. Then it writes new manifests, a new manifest list, and a new metadata.json. Last of all it asks the catalog to swap its pointer to the new metadata file. Until that swap succeeds, no reader can see any of it. Old files are never changed, which is why an update is just a new version that shares most of its files with the old one, and history stays put.

Because the table is described by files, you can even ask it about itself:

-- Look at the middle layer as ordinary tables (Spark)
SELECT * FROM prod.db.events.snapshots;
SELECT * FROM prod.db.events.manifests;
SELECT file_path, record_count FROM prod.db.events.files;
Design principle

Make all the coordination one tiny atomic step. Everything else is built off to the side from files that never change, and only a single pointer swap makes it real.

Why many engines can share one table

Two writers can try to commit at once. The swap is a “compare-and-swap”: it only works if the table is still the one the writer started from. The loser re-reads the new state, checks that the two changes do not clash, rewrites only the small metadata files, and tries again. No one holds a lock while the big data files are written.

Since all agreement comes down to that one swap, Spark, Trino, Flink, DuckDB and others can read and write the same table without ever talking to each other. They only have to follow the same rulebook.

Use case: fixing last Tuesday’s bad load

A nightly job writes a bad batch, and by morning dashboards look wrong. With plain files you would hunt for the bad ones and delete them by hand, hoping a reader is not mid-query. With the three layers, the bad batch was just one commit. The table’s earlier snapshot is still there, with all its files, so you point the table back to it. Readers see the old state or the new state, never a mix.

Deciding: what this design costs and gives

Design choiceWhat you getWhat you pay
Planning by metadata, not by listing foldersPlanning grows with metadata size, not file countA reader must open a few small files first
Files never change; every write adds a versionSafe reads, history, time travelOld files pile up until someone cleans them
One pointer swap as the commitAll-or-nothing changes across enginesYou depend on a catalog that can swap atomically
Retry instead of lockWriters do not block each otherBusy writers on the same data may need retries

Watch out for

  • Do not treat the storage folder as the table. It can hold files from old snapshots, failed writes and abandoned jobs. Only the metadata tree says what belongs.
  • Never delete or move files directly in storage. The metadata still points to them, and the table breaks. Remove files only through table operations such as expiring snapshots or removing orphans.
  • Do not treat the catalog as a small setting. Without a catalog that can swap atomically, there is no safe table.
  • Very frequent tiny commits swell the metadata layer and the snapshot history unless upkeep runs.

Sources: Apache Iceberg Table Spec; Apache Iceberg docs, Reliability; Dremio, The Life of a Write Query; Alex Merced, metadata.json and commits explainers.

Once you see a table as a short chain ending in one pointer, you can let any engine read it, let any writer change it, and still trust that you will never open it to find a half-finished mess.
