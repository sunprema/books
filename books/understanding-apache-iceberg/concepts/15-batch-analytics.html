The Nightly Numbers You Can Trust

The data world calls this: batch analytics and reporting

Here’s the problem

It is the last day of the month, and a finance team is closing the books. The month’s numbers are poured into a side copy of the table, where nobody else can see them. Checks run against that copy: do the totals match the bank? Are any orders missing? Only when every check passes does the team flip one switch and make the new numbers the official ones.

Then they stick a label on that exact version, say “EOY-2023”, and keep it forever. Daily loads carry on as usual, but the audited numbers never move. Without this, the same team would be copying files, crossing fingers and hoping nobody opened the report halfway through.

The idea: a loading dock with an inspector

A typical report is built like a kitchen. Raw ingredients arrive at the back door: raw tables that hold data just as it came in. A cook cleans and combines them into curated tables, the tidy ones with the answers. Finally the dining room, the dashboards and spreadsheets, consumes them. Data engineers call the whole thing a batch pipeline (a job that runs on a schedule, such as every night, and handles a big chunk of data at once).

Iceberg helps with one big worry: the person eating must never get a half-cooked dish. Every write to an Iceberg table is a single snapshot commit (one all-or-nothing step that swaps in the new version). So a dashboard open during a long job sees the old complete table, then the new complete table, and nothing in between.

How it works: three safe habits

Habit one: reruns that do no harm. Nightly jobs fail and get retried. If the retry adds the same rows again, your revenue doubles. The fix is a dynamic partition overwrite (a write that replaces exactly the slices of the table, such as days, that the job produced and leaves every other slice alone). Run it twice and you get the same answer twice. This is a choice you make in the job; Iceberg does not do it for you.

Habit two: fold in the late news. A refund shows up three days late. A wrong price is corrected. For this, use MERGE INTO (one command that says: where a row matches, update it; where it is new, add it). Iceberg rewrites only the data files the change touches, and the official docs prefer it over overwrite for row-level fixes.

-- Late-arriving corrections folded into a curated sales table
MERGE INTO prod.sales.daily_revenue t
USING updates_batch s
ON t.order_id = s.order_id
WHEN MATCHED THEN UPDATE SET t.amount = s.amount, t.updated_at = s.updated_at
WHEN NOT MATCHED THEN INSERT *;

Habit three: write, audit, publish. Netflix made this pattern famous in 2017, and calls it write-audit-publish (write new data where readers cannot see it, check it, then reveal it all at once). Iceberg supports it with branches (named side copies of a table that cost almost nothing, because no data is copied):

ALTER TABLE db.table SET TBLPROPERTIES ('write.wap.enabled'='true');
ALTER TABLE db.table CREATE BRANCH `audit-branch` RETAIN 7 DAYS;
-- jobs write with spark.wap.branch = audit-branch; checks run on the branch
CALL catalog.system.fast_forward('db.table', 'main', 'audit-branch');

Netflix runs this across thousands of tables. An auditing tool checks the hidden version, and only a passing grade exposes it. Nothing is copied during the check.

When a bad run slips through

Suppose it happens anyway. You do not need a backup. The rollback_to_snapshot command points the table back at an earlier saved version. And when someone asks, “Why did the numbers change overnight?”, the history and snapshots tables list every version, what kind of change made it, and which job wrote it. That is a small query, not a hunt through log files.

Design principle

Make publishing a single step, separate from loading. When loading is slow and messy but publishing is instant and whole, readers only ever see finished, checked work.

Use case: the monthly sales report

A shop loads orders every night into raw tables. A job tidies them into a curated daily revenue table. Each night it overwrites just that night’s slice, so a retry is harmless. Refunds that arrive late are merged in. Before the new slice goes live, the checks compare order counts and totals. Managers open the same dashboard every morning and the number matches the one from yesterday’s meeting, unless a documented correction changed it.

Deciding: how to load

SituationUseTrade-off
Reload whole days or months on a scheduleDynamic partition overwriteSimple and safe to retry; replaces whole slices
Late or corrected individual rowsMERGE INTOPrecise, but costs more work per run
Reports others rely on, such as finance closeWrite-audit-publish with a branchAn extra step and a retention period to manage
Answers needed within seconds of an eventNot this patternBatch means waiting for the next scheduled run

Watch out for

  • Overwriting with no slice named. Spark’s default mode can replace the whole table; the docs recommend the dynamic mode for Iceberg.
  • Merging a batch that has two rows for the same key. The merge stops with an error, so remove duplicates first.
  • Retrying a job that only adds rows. It silently doubles your data. Safe reruns are a design choice, not a default.
  • Forgetting the chores. Frequent loads pile up small files and old snapshots, so merging files and expiring snapshots belong in the pipeline’s routine.

Sources: Apache Iceberg docs on Spark Writes, Spark Procedures, Spark Queries, and Branching and Tagging; lakeFS, “Data Engineering Patterns: Write-Audit-Publish”; Netflix write-audit-publish write-up (vutr.substack.com); Dremio on streaming into Iceberg.

Because every load is checked before anyone sees it, and every mistake can be undone in one step, you can trust the number on tomorrow’s dashboard and sleep through tonight’s retry.
