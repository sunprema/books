Part III · Architecture and Design Principles

One Box, Every Port

The data world calls this: interoperability and openness

Here’s the problem

Before the standard shipping container, goods were packed and unpacked again at every border. A crate left the factory, was unloaded at the dock, re-stacked for the train, and unloaded again for the truck. Each hand-off cost time, money and broken items.

Then everyone agreed on one box size. Ships, trains and cranes did not become the same machine. A ship is still a ship. But any port could now handle any container, and goods stopped being repacked at every border. Data has the same problem: every tool wants its own copy, in its own shape. An Iceberg table is the standard box.

The idea: many tools, one table

A table’s state lives in open files plus an open way of talking to the catalog (the front desk that says which note is current). So several tools can read and write the very same table at once. Their safety does not come from any one tool’s lock. It comes from the format’s own optimistic commit rule: each writer tries to move the pointer, and if someone else moved it first, the loser looks again and retries.

The list of ports is long and growing. Spark has the fullest support: table setup, row changes, upkeep procedures and streaming. Flink reads and writes, in streaming or batch. Trino’s connector does full read and write SQL. Dremio reads, writes and tidies tables. Snowflake works with tables it manages and with tables managed elsewhere. BigQuery has its own managed Iceberg tables and can also read outside ones.

Even small tools join in. DuckDB’s Iceberg add-on gained writing in version 1.4 (September 2025): create a table and insert rows through a connected catalog, with updates and deletes arriving in later 1.4 releases. Reading by pointing straight at a metadata path stays read-only. So a process on a laptop can now safely commit to the same table a big Spark cluster looks after.

How it works: one front desk, many doors

What makes this practical is the REST catalog protocol (one shared set of requests for finding a table, committing a change and getting access keys). Without it, every engine needs its own plug-in for every catalog. With it, the same table served by Polaris, S3 Tables, Unity Catalog or Nessie can be reached from Spark, Trino, Flink, DuckDB, Snowflake or Dremio by changing settings, not code.

The format is also governed in the open, by Apache, with numbered format versions. In real life, the catch is that every tool involved must understand the table’s version and features. Version 3 readers can read version 2 tables. But an engine that only knows version 2 cannot read a version 3 table that uses deletion vectors or row lineage.

Standards also bend formats toward each other. Apache XTable (incubating since February 2024) translates table metadata between Iceberg, Delta Lake and Hudi without rewriting the data files. Its 0.4.0 release added Paimon and plain Parquet as sources. One set of files can wear several labels.

Design principle

Separate where data lives from how it is processed. Keep the data in open files in storage you control, behind an open front desk, and treat each engine as a replaceable visitor. Then you can change tools as your needs change, without moving the goods.

Use case: the same table, three teams

A data platform team keeps orders in one table on cloud storage. Pipelines write to it with Spark and Flink. Analysts query it from Trino and Snowflake. A data scientist opens the same table in DuckDB on a laptop. Nobody exports a copy, and when the company later evaluates a new engine, it points the engine at the same catalog and tries it on real data.

Deciding: how open do you need to be?

SituationApproachTrade-off
Several engines, several teams, a horizon of yearsOpen tables behind a REST catalogYou own more of the upkeep and the testing
Streaming writers plus batch readersShare one table, and plan maintenance away from busy write windowsCorrectness is safe, but jobs can force each other into retries
Small team, one engine, no other tools plannedA managed platform may cost less to runOpenness pays off with the number of engines, teams and years; you may never get there
A vendor says “supports Iceberg”Ask which direction: read, write, which catalogs, which versionsCheckbox answers hide very different freedoms

Watch out for

  • Believing “supports Iceberg” means full freedom. It is often read-only, or limited to certain catalogs, versions or delete handling. Check the write path.
  • Lopsided openness. For example, one major platform’s REST endpoint gives outside engines read and write on its own Iceberg tables, but read-only on its Delta tables, and Iceberg tables from foreign catalogs are read-only inside it.
  • Thinking an open format ends lock-in. It moves up a layer: storage and table format are now common goods, so stickiness gathers in the catalog, the grants and the managed upkeep.
  • Trusting that reading tells you everything. Nearly every engine reads Iceberg well. Trouble shows up when each one writes: delete strategies, partition rules and format versions.

Sources: Apache Iceberg Table Spec; Iceberg REST catalog specification; Apache Polaris REST API; Apache Flink, Trino, Snowflake and BigQuery Iceberg documentation; DuckDB Iceberg extension; Apache XTable; Databricks on Iceberg v3 and on Unity Catalog; catalog landscape and governance guides.

Because any tool can open the same standard box, you can pick the right engine for each job and change your mind later, without ever copying your data.
