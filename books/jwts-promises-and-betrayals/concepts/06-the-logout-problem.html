Chapter Six The problem cryptography cannot solve
06

The logout problem

Everything so far has been about tokens that should not have been accepted. This chapter is about a token that was issued correctly, verifies perfectly, and must nevertheless stop working — right now.

A session identifier is a pointer. The server holds the session; deleting it ends the session everywhere, instantly. That is not a feature anyone designed — it falls out of the fact that the credential means nothing on its own.

A JWT is the opposite by design. It is self-contained: valid because its signature and claims check out, not because a server says so. That is exactly why it scales, and exactly why you cannot take it back. There is nothing to delete.

"Stateless authentication" is not a claim that no state exists. It is a decision about where the state lives — and revocation is the bill that arrives for it.

How I would approach this

The attack — outliving my welcome

I have your token: from an XSS, a stolen laptop, a leaked log, a shared machine in a library. You notice. You lock the account, reset the password, revoke my device, and email the user that everything is secure.

None of that touches me. Your API does not consult a session store on each request — that was the point. It verifies my token, finds a valid signature and an exp in the future, and serves me. I keep working until that timestamp, and the only question that matters is how far away you set it.

Twenty-four hours is common. Thirty days is not rare. I have seen tokens with no exp at all.

Three answers, in increasing order of honesty

1. Short lifetimes

Make the window small enough that it stops mattering. Five to fifteen minutes is the range most systems settle on. This costs you nothing architecturally and bounds every other failure in this book: a leaked token, a stolen token, a token in an old log entry — all of them expire on their own. If you do one thing from this chapter, do this one.

2. A denylist keyed on jti

Chapter four introduced jti as a unique identifier for a specific token. That is what makes selective revocation possible: on logout, record the jti; on each request, reject tokens whose jti appears in the list.

Be honest about the trade — you have reintroduced a lookup on the hot path, which is the thing you adopted JWTs to avoid. Two details keep it cheap. Entries only need to live until the token's own exp, so a store with TTL support expires them for you and the list stays bounded. And the lookup is a small key-value read, not a session load.

# On logout: remember only until the token would have died anyway.
SETEX "revoked:"$jti  $(exp - now)  1

# On each request, after signature + claim checks:
EXISTS "revoked:"$jti   # 1 -> reject

3. Split the credential in two

The design most production systems converge on, and the one the OAuth security BCP assumes: a short-lived, stateless access token that services verify locally, plus a long-lived, stateful refresh token that only the issuer sees and can revoke centrally.

The refresh token is where revocation lives, and it is consulted every few minutes rather than every request. Logout deletes the refresh record; the access token dies of old age shortly after. You get local verification on the hot path and a real off switch, and you pay for it with one round trip per token refresh.

The defense — RFC 9700 on refresh tokens

A long-lived refresh token is a high-value target, so the OAuth 2.0 Security BCP does not leave it unprotected. Section 2.2.2 requires that refresh tokens for public clients be sender-constrained or use refresh token rotation; section 4.14 details both.

Rotation means each use issues a new refresh token and invalidates the old one. Its real value is detection: if an old token is ever replayed, either I stole it or the legitimate client did — and the issuer cannot tell which, so it revokes the whole chain and forces a fresh login. Theft becomes visible instead of silent.

Trust boundaries

Trusted
That a verified, unexpired token was validly issued at some point in the past.
Never trusted
That a valid token reflects the account's current state — permissions, password, employment, or consent.
Revocable only through
A short exp, a jti denylist, or a stateful refresh step. Nothing else can withdraw a token.
Check
Time it: from clicking "log out everywhere", how long does a captured token keep working? That number is your real answer, whatever the UI said.
