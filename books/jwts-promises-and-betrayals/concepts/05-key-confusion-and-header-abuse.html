Chapter Five When the token picks the key
05

Key confusion and header abuse

The JOSE header carries parameters that tell a verifier which key to use and where to find it. Every one of them is written by whoever sent the token. This chapter is about what happens when a server takes that advice.

Chapter three ended on a sentence worth repeating: a public key is safe to publish, which is why asymmetric verification scales. Now watch that property turn into a weapon.

Algorithm confusion: your public key as my password

Your issuer signs with an RSA private key. Your services verify with the matching public key, which — being public — I can fetch from your JWKS endpoint, your documentation, or your TLS certificate chain. I now hold a value your servers treat as a verification key and I treat as a string I know.

So I change one field. alg becomes HS256. I write whatever claims I want, and I compute an HMAC over the signing input using your public key as the shared secret. A server that reads alg from the token and dispatches on it will now run HMAC verification with the same public key — and the two computations match, because we both did the same arithmetic with the same value.

The attack — CVE-2015-9235, CVSS 9.8

This is not hypothetical. Node's jsonwebtoken, one of the most downloaded JWT packages ever published, did exactly this before version 4.2.2: verify() took the algorithm from the token header by default. Any application using it with an asymmetric key could be handed a forged HS256 token signed with the public key, and would accept it.

The fix was not a cryptographic change. It was an API change: an explicit algorithms option, so the caller states what they expect.

The defense — the algorithm is a server decision

Pin the allow-list, as in chapter three. If a service verifies with a public key, then algorithms contains only asymmetric algorithms, and an HS256 token is rejected before its signature is ever computed. Say it as a rule: never pass a value derived from the token into the parameters of the call that verifies the token.

The kid parameter is user input

RFC 7515 section 4.1.4 describes kid as "a hint indicating which key was used to secure the JWS", with an unspecified structure and only one requirement: it is a case-sensitive string. Unspecified structure means implementations invent one — and what they invent is usually a filename or a database row.

// Both degrees of freedom now belong to whoever sent the token.
const h = parseHeader(token)
jwt.verify(token, fs.readFileSync(`/keys/${h.kid}`), { algorithms: [h.alg] })
The attack — traversal and injection through a hint

If kid becomes a path, I set it to something like ../../../../dev/null. The "key" your server loads is empty, and an empty key is one I can also use — I sign my forgery with the same nothing and the HMAC matches. PortSwigger documents this exact technique.

If kid becomes part of a SQL query, it is SQL injection with extra steps, and I can return a key of my choosing from your own database. RFC 8725 section 3.10 exists precisely because both of these keep happening.

The defense — lookup, never construction

kid selects from a finite set you already loaded. It never becomes a path, a URL, or a query fragment. A miss is a rejection, not a fallback.

// KEYRING: Map<kid, key>, built at startup from your own configuration.
const key = KEYRING.get(header.kid)
if (!key) throw new Error('unknown kid')
jwt.verify(token, key, { algorithms: ['RS256'] })

…and jku, jwk, x5u

The remaining header parameters are more direct about it. jwk embeds a public key in the token. jku and x5u give a URL to fetch keys from. A server that honours them without an allow-list is asking the attacker to supply the verification key, which reduces the entire scheme to "I verified that this token was signed by whoever signed this token".

The attack — bring your own key, plus a bonus

With jwk: I generate a keypair, sign my forgery, embed my public key in the header. With jku: I host a JWK Set on my own server and point your verifier at it. Your service fetches it and verifies my token perfectly.

The jku variant comes with a second prize. A server-side fetch of a URL I control is an SSRF primitive — I can aim it at your metadata service or your internal network and learn things that have nothing to do with tokens.

The defense — a strict allow-list, or nothing at all

PortSwigger's guidance is a limited allow-list of acceptable public keys for jwk, and a strict allow-list of permitted hosts for jku; RFC 8725 section 3.10 requires whitelisting jku and x5u URLs. RFC 7515 additionally requires those resources to be fetched over TLS with a validated server identity.

The stronger position, and the one I would take in most systems: reject tokens carrying these headers entirely. Almost no application needs per-token key discovery. Fetch your issuer's JWKS on your own schedule, from a URL in your own configuration, and let the token do nothing but identify which of those keys it used.

Every one of these attacks is the same mistake wearing different clothes: the token was allowed to influence how it would be checked.

Trust boundaries

Trusted
Keys loaded from your configuration or fetched from a JWKS URL you hardcoded, on your schedule.
Never trusted
alg as a dispatch value; kid as a path or query; jku/x5u as a fetch target; jwk as a key.
Trusted as a hint only
kid, used solely as a lookup into a set you already trust — a miss must reject.
Check
Grep for anything that reads the token header before verification. Every hit is either safe by construction or one of the attacks above.
