Anatomy of a JWT

Three base64url strings and two dots. Before we can ask how it breaks, we have to be precise about what it claims to do — because the gap between that claim and what people believe is where most of this book lives.

Here is a token. It is not encrypted, it is not obfuscated, and it is not doing anything clever. It is RFC 7519's JWS Compact Serialization: three parts, base64url-encoded, joined by periods.

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjMiLCJleHAiOjE3NjkzODAwMDB9.4Xy0mQd7pV1sJ2Rk9tLbN3wG8cA6eZfH

Decode the first two and you get JSON. The JOSE header says how the token was secured; the claims set says what the issuer is asserting. The third part is the signature.

// part 1 — the JOSE header
{ "alg": "HS256", "typ": "JWT" }

// part 2 — the claims set
{ "sub": "123", "exp": 1769380000 }

What the signature actually covers

This is the detail everything else depends on, so let us be exact. Per RFC 7515, the bytes that get signed are not the JSON. They are the encoded header and payload, with the dot between them:

signing input = ASCII( BASE64URL(header) || "." || BASE64URL(payload) )

Two consequences follow immediately. First, changing a single character of either part invalidates the signature. Second — and this is the one people miss — the algorithm declaration is covered by the signature, but covered is not the same as trusted. You still have to decide which algorithm you were willing to accept before you check anything. Chapter three is entirely about that gap.

Everything in a JWT is attacker-supplied until the signature verifies. The token is a claim about itself, and it is making that claim to you.

How I would approach this

Put yourself on the other side for a moment. You hand me a token. I cannot forge a signature without your key — fine. But nothing stops me from editing the token and sending it back, and nothing stops me from hoping you look at it before you check it. That hope is not idle. It has a name in every JWT library's API:

The attack — read-before-verify

Almost every library ships two functions that both return your claims. One verifies the signature. One just base64-decodes. They have friendly, similar names — decode() and verify() — and the wrong one never throws, never warns, and works perfectly in every test you write with your own valid tokens.

PortSwigger lists this as its first JWT attack class for a reason: the developer confuses the two, and the application makes authorization decisions on unverified claims. I do not need to break your cryptography if you never ran it.

// Reads the claims. Verifies nothing. Returns happily for a token I wrote.
const claims = jwt.decode(token)
if (claims.role === 'admin') grantEverything()   // I am admin now
The defense — one door in

Verification and parsing must be the same operation in your codebase. Wrap the library once, return claims only from a function that verified them, and make the raw decoder unreachable from application code. If a developer has to reach past a lint rule to get unverified claims, the mistake stops being accidental.

// The only way to get claims in this codebase.
export function claimsFrom(token) {
  return jwt.verify(token, key, { algorithms: ['RS256'] })
}

The order the spec insists on

RFC 7519 section 7.2 spells out validation as ten steps, and the sequence is the point: confirm the structure, decode and parse the header, confirm you understand every parameter in it, determine whether you are holding a JWS or a JWE, verify accordingly, recurse if the payload is a nested JWT, and only then parse and evaluate the claims. Claims are the last thing you look at, not the first.

One more trap in the header while we are here. typ looks like a type check. It is not. RFC 7515 says plainly that the parameter "is ignored by JWS implementations; any processing of this parameter is performed by the JWS application" — meaning: by you, if you bother. Chapter four shows what goes wrong when nobody bothers.

Trust boundaries

Trusted
The verification key you loaded from your own configuration. Nothing else, yet.
Trusted only after the signature verifies
The claims set, and the header's alg as a description of what was done.
Never trusted
Any byte of the token before verification — including the header that tells you how to verify it.
Check
Search your codebase for decode. Every call site is a question you must be able to answer.
