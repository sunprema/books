Chapter Four From valid signature to valid decision
04

Validation done right

The signature verified. That tells you the token is genuine. It does not tell you the token is genuine for you, right now, or for this purpose — three separate questions, three separate ways to be robbed.

Start with the fact that surprises people: every registered claim in RFC 7519 is optional. The specification defines what exp and aud mean; it does not require any of them to be present. A token with no expiry and no audience is a perfectly valid JWT. Whether it is acceptable is entirely your decision to make and enforce.

Time: exp, nbf, and the skew you allow

exp is a NumericDate after which the token MUST NOT be accepted; nbf is one before which it must not be accepted. The spec permits "some small leeway" for clock skew, and that word small is doing real work.

The attack — living in the leeway

Whatever skew you allow, I get for free. A five-minute tolerance on a fifteen-minute token extends every stolen token's useful life by a third. I have seen an hour configured, by someone who was tired of debugging a clock problem and never came back to it. That is a one-hour window during which a token you expired is still money in my pocket.

The defense — fix clocks, not tolerances

Run NTP and set skew in seconds — thirty is generous. Clock drift is an infrastructure problem; widening the acceptance window is not a fix for it, it is a permanent concession purchased to avoid a one-time repair.

Audience: the question almost nobody asks

Here is the scenario RFC 8725 calls a substitution attack (sections 2.7 and 3.8–3.9), and it is the most common serious JWT flaw I find in systems that otherwise did everything right.

RFC 8725 section 3.9 requires the relying party to validate aud whenever multiple parties share an issuer — which, in any organization with more than one service, is always. RFC 9700 section 2.3 says the same thing from the OAuth side: access tokens SHOULD be audience-restricted to a specific resource server, or to a small set of them.

There is a companion check that is subtler. RFC 8725 section 3.8 requires you to verify that the key you used actually belongs to the claimed issuer. Verifying a signature with the wrong issuer's key produces a valid signature and an invalid decision: if your key resolution is keyed on something the token controls, an attacker picks the issuer whose key they can influence, and iss becomes decorative. Bind key to issuer in your configuration, then check that the token's iss matches the one whose key verified it.

A signature proves who wrote the token. Only the claims can tell you whether they were writing to you.

Cross-JWT confusion

Modern systems mint several kinds of token from the same issuer: ID tokens, access tokens, refresh tokens, password-reset tokens, email confirmation tokens. They are all JWTs. They are all signed with the same key. RFC 8725 sections 2.8 and 3.11–3.12 name the resulting hazard cross-JWT confusion: a token of one kind presented where another kind was expected.

The attack — the wrong token, honestly obtained

I request a password-reset token for my own account through your entirely legitimate flow. It is signed by your key, unexpired, and about me. Then I present it as an API access token. If your API checks the signature, the issuer, the expiry, and the subject — all of which pass — the only thing left to notice is that this token was never meant to be a credential. Nothing in the signature says so.

The defense — explicit typing

RFC 8725 section 3.11 prescribes explicit typing: set the typ header to a media type that names the kind of token, in the form application/example+jwt, and give each kind mutually exclusive validation rules. Remember from chapter one that the JWS layer ignores typ entirely — this check exists only if your application performs it.

// Everything the server decided in advance, in one call.
jwt.verify(token, keyForIssuer(EXPECTED_ISS), {
  algorithms: ['RS256'],                        // ch.3 — no vote for the token
  issuer:     'https://issuer.example.com',    // bound to the key above
  audience:   'https://api.example.com/payments', // this service, not a sibling
  clockTolerance: 30                          // seconds — not minutes
})
// then, separately, because no library does it for you:
if (header.typ !== 'application/at+jwt') throw new Error('wrong token kind')

Two more the BCP insists on

RFC 8725 section 3.3 requires that all cryptographic operations in the token be validated, including those inside nested JWTs — an inner token that nobody verified is an unverified token no matter how good the outer signature was. And sections 2.6 and 3.7 require JSON to be UTF-8 and other Unicode encodings to be rejected, so that you and your attacker cannot be reading the same bytes as two different documents.

Trust boundaries

Trusted
Claims that survived signature verification and your own checks on iss, aud, exp, and token kind.
Never trusted
A claim's presence. Absent claims are not failures in the JWT format — enforcing them is your job alone.
Trusted only for this service
An audience-restricted token. Passing it onward to another service hands that service a credential it cannot safely accept.
Check
Take a valid token from your least-privileged service and present it to your most-privileged one. If it works, you have found your aud gap.
