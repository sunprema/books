The algorithm zoo

A signature is only meaningful if both sides already agree on how it was made. The JOSE specifications let the token state that agreement — which was a design decision with consequences we are still paying for.

RFC 7518 defines the algorithms a JWS may use. The list is short, and the implementation requirements tell you what the working group actually expected you to use.

algFamilyKey modelRFC 7518 s.3.1
HS256HMAC-SHA256Symmetric — one shared secretRequired
RS256RSASSA-PKCS1-v1_5Asymmetric — private signs, public verifiesRecommended

PS256RSASSA-PSSAsymmetricOptional
none—No key. No protection.Optional

The split that matters is the third column. Symmetric means the same secret both signs and verifies: anyone who can check a token can also mint one. Asymmetric means verifiers hold only a public key, which is safe to publish — that is why a fleet of services can verify tokens from one issuer without any of them being able to forge one.

Hold that sentence. In chapter five it becomes an attack.

Keys that are not keys

The specifications set floors, and they are not suggestions. RFC 7518 requires an HMAC key at least as large as the hash output — 256 bits for HS256 — and RSA keys of 2048 bits or larger. RFC 7515 asks for a minimum of 128 bits of entropy in any key. RFC 8725 adds the human dimension: passwords people can remember must not be used directly as MAC keys.

The attack — offline brute force

Give me one valid HS256 token and I need nothing else from you. The signature is a deterministic function of a string I already have and a secret I do not, so I can try candidate secrets locally, at whatever rate my hardware allows, with no requests to your server and nothing in your logs. Wordlists of leaked and default JWT secrets are published and maintained.

If your secret is secret, changeme, your company name, or the placeholder from the tutorial you started from, this takes seconds. Then I sign whatever claims I like, and every check you perform downstream passes honestly.

The defense — generated, not chosen

HMAC secrets come from a CSPRNG, at full length, and live in a secrets manager — never in source, never in a config template, never typed by a human. If a person could invent it or remember it, it is not a key.

# A 256-bit HS256 secret. Nobody types this; nobody memorises it.
openssl rand -base64 32

The none algorithm

RFC 7518 section 3.6 defines an Unsecured JWS: alg is "none", the third part is empty, and there is no integrity protection whatsoever. It exists for cases where the token is already protected by some other means. The same section says implementations MUST NOT accept Unsecured JWSs by default, and RFC 8725 adds that libraries should not generate them without an explicit request.

eyJhbGciOiJub25lIn0.eyJzdWIiOiIxIiwicm9sZSI6ImFkbWluIn0.

That is a complete, well-formed token asserting that I am an administrator. It ends in a dot with nothing after it. The only thing standing between it and your application is whether your verifier was told, in advance, which algorithms it is willing to accept.

The attack — and the bypass of the obvious fix

The naive fix is a check for the string "none". PortSwigger documents the bypass: "None", "NONE", "nOnE". The alg value is case-sensitive per RFC 7515, but a library that lowercases before dispatch and a filter that compares exact case will happily disagree with each other, and I only need the two of them to disagree once.

The lesson generalizes past this one string: a denylist of bad values is a losing position. You cannot enumerate everything you do not want.

The defense — an allow-list, decided by the server

Name the algorithms you accept before you look at the token. Everything else — including anything spelled like none, including a perfectly good algorithm you simply were not expecting — is rejected without further thought.

// The server decides. The token gets no vote.
jwt.verify(token, key, { algorithms: ['RS256'] })

When the algorithm is fine and the implementation is not

Two more items from the BCP, both easy to miss because they live below the level most applications think about. RFC 8725 section 3.2 recommends deterministic ECDSA (RFC 6979), because ECDSA leaks its private key if the same nonce is ever reused — a class of failure that has burned real systems. The same section advises against RSA PKCS#1 v1.5 encryption padding in favour of RSAES-OAEP.

And a reminder that the verifier itself is code that can be wrong. CVE-2022-21449 — "Psychic Signatures" — made Java 15 through 18 accept an ECDSA signature whose r and s values were both zero. The verification equation multiplied through by those zeros and cheerfully concluded that 0 = 0. An all-zero signature verified against any public key, on any ES256 token, until the April 2022 patch.

You are not trusting a mathematical guarantee. You are trusting a specific implementation of it, in a specific version, on a specific runtime.

Which is why "we use a well-known library" is a statement about likelihood, not a proof. Patch it, pin the versions, and subscribe to its advisories — the next chapter's failures all assume the cryptography worked perfectly.

Trust boundaries

Trusted
The algorithm allow-list in your own code, and a key generated by a CSPRNG at the RFC 7518 minimum size.
Never trusted
The alg value in the token, as an instruction about what to do next.
Trusted only while patched
Your JOSE library and language runtime — CVE-2015-9235 and CVE-2022-21449 both broke verification itself.
Check
Can your service verify a token you signed with alg: none? Test it. The answer should be an exception, not a user.
