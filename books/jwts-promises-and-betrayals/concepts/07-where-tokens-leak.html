Where tokens leak

A bearer token is a password with an expiry date. Anyone holding it is you. So the question is not whether your cryptography is sound — it is how many copies exist, and who can reach them.

"Bearer" is not marketing language. It is the security model: the token authenticates whoever presents it, with no further proof of identity. Everything in this chapter follows from that one property.

Leak one: tokens in URLs

Putting a token in a query string or fragment feels harmless — it is over HTTPS, after all. But a URL is the most-copied string in computing.

  • Browser history, on a machine that may be shared.
  • The Referer header, which hands your token to every third-party resource the page loads.
  • Server and proxy access logs, which are retained, shipped to a logging vendor, and readable by far more people than your database.
  • Anything a user pastes into a ticket, a chat, or a screen share.

This is not a new observation. RFC 9700 section 2.1.2 discourages the OAuth implicit grant precisely because it delivers access tokens through the browser front channel, and recommends the authorization code flow instead — which keeps the token out of URLs, history, and logs.

The attack — reading, not breaking

I do not need a vulnerability in your application. I need read access to one log aggregation index, or one support ticket with a pasted link, or one analytics vendor that captures full page URLs. Every one of those is a system your security team probably classifies as low-sensitivity, because it holds "just URLs".

Leak two: where the browser keeps it

This is the argument that never ends, so let us make the trade-off explicit rather than picking a side.

StorageReadable by JS?Sent automatically?Main exposure
localStorageYesNoAny XSS is total token theft
JS variable (in memory)Yes, while runningNoXSS during the session; lost on reload
HttpOnly cookieNoYesCSRF; needs SameSite and friends

OWASP's long-standing guidance is not to keep session identifiers in local storage, for the simple reason that the data is always accessible to JavaScript. That is the whole argument: localStorage has no access control, so any script on your origin — yours, your analytics vendor's, a compromised npm dependency's — can read it.

The attack — one XSS, one line

With a token in localStorage, my injected script is a one-liner: read it, send it to my server. I now have a valid credential that works from my machine, on my schedule, with no browser of yours involved. Your XSS has been upgraded from "runs script in a user's page" to "full account takeover, offline, until exp".

With an HttpOnly cookie, that line returns nothing. I can still act as the user while my script runs in their page — an important thing to be clear about — but I cannot take the credential home with me. That is a genuine reduction in blast radius, not a fix for XSS.

The defense — pick your attack, then defend it

The mainstream answer: refresh token in an HttpOnly, Secure, SameSite cookie; access token held in memory only, never persisted. Cookies mean CSRF is now your problem, so pair them with SameSite plus a custom header or double-submit token.

Neither option survives XSS intact. Treat "we store tokens in JavaScript" as a reason to raise the severity of every XSS finding, not as a settled architecture.

Set-Cookie: refresh=<token>; HttpOnly; Secure; SameSite=Lax; Path=/auth

Leak three: your own logs

The most common leak I find is not clever. It is a request logger, added during an incident, that serializes headers at debug level — and Authorization: Bearer … is a header. From there the token flows to wherever logs go: a vendor, a bucket, a laptop, a retention period measured in years.

The defense — redact at the boundary

Redact Authorization, Cookie, and any field matching a JWT shape in the logging layer itself, not at each call site — one place that cannot be forgotten under pressure. Then go and grep your log store for eyJ, the base64url prefix of every {"-opening JOSE header. Do it before reading further; it takes a minute and it is routinely a bad minute.

While you are treating token contents as data rather than truth: RFC 8725 sections 2.9 and 3.10 warn against blindly trusting claims used in lookups. A sub or kid that reaches a query, a filename, or an outbound request is untrusted input — chapter five showed what that costs.

You cannot stop a token from being copied. You can make each copy short-lived, narrow in scope, and useless somewhere else.

Which is the last connection worth drawing. RFC 9700 sections 2.3 and 4.10.2 recommend audience-restricting access tokens so a token stolen from one resource server cannot be replayed at another. Combine that with chapter six's short lifetimes and a leak stops being an emergency and becomes an incident with a known, bounded blast radius: one service, for a few minutes.

Trust boundaries

Trusted
The token in transit under TLS, and in server memory during a request.
Never trusted
Any place a token is written down: URLs, localStorage, logs, analytics payloads, error reports, screenshots.
Reduced, not eliminated, by
HttpOnly cookies (blocks theft, not abuse), short lifetimes, and audience restriction.
Check
Search your log store for eyJ. Then search your front-end for localStorage. Both searches should come back empty.
