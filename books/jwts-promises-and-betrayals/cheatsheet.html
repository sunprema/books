Every line below corresponds to a published, exploited failure from the preceding chapters. Read it as a diff against your own verification path, not as advice.

The verification checklist

  1. 1Pin the algorithms. A server-side allow-list. Never algorithms: [header.alg]. ch.3, ch.5
  2. 2Resolve the key yourself. kid is a lookup into a known set — never a path, URL, or query. Reject jwk/jku/x5u. ch.5
  3. 3Verify the signature before reading any claim. One wrapper; no raw decode() in application code. ch.1
  4. 4Check exp and nbf with skew in seconds, not minutes. ch.4
  5. 5Require iss, and confirm the verifying key is bound to that issuer. ch.4
  6. 6Require aud and match it to this service. ch.4
  7. 7Check the token kind via explicit typ — the JWS layer ignores it. ch.4
  8. 8Have a revocation path before you need one: short exp, jti denylist, or a stateful refresh. ch.6

Claims — require, do not hope

ClaimRequire?Check
issAlwaysExact match; key bound to it
audAlwaysContains this service's identifier
expAlwaysFuture, small skew
subAlwaysResolves to a real principal
nbfIf issuedPast, small skew
jtiIf revokingNot on the denylist
iatUsefulSane age for this token kind

All are optional in RFC 7519. The spec defines their meaning; requiring them is entirely your application's job.

Crypto minimums (RFC 7518 / 7515)

  • HMAC key ≥ hash output — 256 bits for HS256.
  • RSA key ≥ 2048 bits.
  • Any key ≥ 128 bits of entropy (RFC 7515 s.10.1).
  • Implementation requirement (RFC 7518 s.3.1 — what a library must support): HS256 Required · RS256 Recommended · ES256 Recommended+ · none Optional.
  • Acceptance (a separate question — what your service allows): implementations MUST NOT accept Unsecured JWSs (none) by default. A library may support it; you should still never accept it.
  • Prefer deterministic ECDSA (RFC 6979); prefer RSAES-OAEP over PKCS#1 v1.5 for encryption.
  • Never compress before encrypting.

The 30-second version

A JWT proves who wrote these exact bytes and nothing else. It does not hide them, does not say who they were for, does not say they are still valid, and cannot be taken back. Pin the algorithm, resolve the key yourself, verify before you read, then demand iss, aud, exp, and the token's kind — and keep the lifetime short enough that the copy you did not know about stops working on its own.

Code smells worth grepping for

  • decode( — anywhere in application code.
  • algorithms: [ built from a variable.
  • kid concatenated into a path or query.
  • localStorage.setItem near anything token-shaped.
  • eyJ in your log store.
  • An exp measured in days.
