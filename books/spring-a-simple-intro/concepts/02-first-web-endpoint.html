Chapter Two

Your First Web Endpoint

The server runs but knows no URLs. Let's find out what happens between main and a response — then add one.

How the app actually starts

When SpringApplication.run executes, roughly this happens:

  1. Spring creates an application context — the container that will hold your objects.
  2. Component scanning walks the packages below your main class, looking for annotated classes.
  3. Auto-configuration inspects the classpath. It sees Spring MVC, so it configures a DispatcherServlet and an embedded Tomcat.
  4. Every discovered component is instantiated and wired together.
  5. Tomcat binds port 8080.

The DispatcherServlet is the piece worth remembering. Every request arrives there first, and its job is to find the method that should handle it. That lookup table is built from your annotations at startup.

Adding a controller

Create HelloController.java beside your main class: 

java@RestController
class HelloController {

  @GetMapping("/hello")
  String hello() {
    return "Task Tracker is up";
  }
}

Restart and call it: 

bash$ curl localhost:8080/hello
Task Tracker is up

Two annotations did that, and both are worth understanding rather than copying.

@RestController

This is @Controller and @ResponseBody combined. @Controller makes the class a component that handles requests. @ResponseBody is the important half: it says the return value is the response body.

Without it, Spring treats a returned String as the name of a view template to render — so returning "Task Tracker is up" would send Spring hunting for a template by that name and fail with a 404. That mismatch is the classic first-day confusion, and it's why you want @RestController for an API.

Rule of thumb

Building an API that returns data? @RestController. Rendering HTML pages server-side? @Controller. This book only ever uses the first.

@GetMapping

This maps an HTTP GET at a path to this method. There is one of these per HTTP method — @PostMapping, @PutMapping, @DeleteMapping, and @PatchMapping — and we'll use all of them in chapter 3.

Returning JSON

Returning a String gives you a plain-text body. Return an object and Spring serializes it to JSON instead: 

java@RestController
class HelloController {

  @GetMapping("/hello")
  String hello() {
    return "Task Tracker is up";
  }

  @GetMapping("/hello/json")
  Greeting helloJson() {
    return new Greeting("Task Tracker is up");
  }
}

record Greeting(String message) {}
bash$ curl localhost:8080/hello/json
{"message":"Task Tracker is up"}

Nobody wrote serialization code. Spring Boot auto-configured a JSON converter, saw that the return type isn't a String, and used it. A Java record works perfectly here — its components become the JSON fields.

Which JSON library

Spring Boot 4 uses Jackson 3 by default. Its group id moved from com.fasterxml.jackson to tools.jackson, and Jackson 2 support ships deprecated. You won't touch either directly in this book, but you will see the new group id if you ever pin a Jackson version by hand.

When the route doesn't work

A 404 on a route you just added is almost always one of three things:

SymptomUsual cause
404, and the startup log never mentions your classThe controller sits outside the main class's package tree, so scanning never found it
404, but the class is foundPath typo, or a missing leading /
500, or an odd view-resolution error@Controller where you meant @RestController

So what did we actually gain?

A URL that returns text and a URL that returns JSON, in about ten lines, with no servlet registration, no routing file, and no serializer. What we don't have is a resource — something with an identity you can create, read, update and delete. That's next.
