Chapter Three

Building a Small REST API

Now the real project starts. A task has an identity, so it can be created, fetched, changed and deleted — and each of those has a correct HTTP shape.

Designing the resource

A REST resource is a noun with a URL. Ours is a task: a title, an optional description, and whether it's done. The URL layout follows directly:

MethodPathMeansSuccess
GET/api/taskslist tasks200
GET/api/tasks/{id}one task200
POST/api/taskscreate a task201
PUT/api/tasks/{id}replace a task200
DELETE/api/tasks/{id}remove a task204

Note the shape: the path names the thing, the method names the action. There is no /api/createTask. That is the whole convention.

Two types, not one

Before the controller, a decision that pays off repeatedly: the object a client sends is not the object we store. 

java// what a client sends — no id, the client doesn't choose it
record NewTask(String title, String description) {}

// what we return
record Task(Long id, String title, String description, boolean done) {}
Why bother

If the client posts the same type you store, the client can set the id — and later, once there's a database, any field you add internally is instantly part of your public API. Two small records keep that boundary honest for free.

A temporary store

Chapter 6 brings a real database. For now, an in-memory map keeps the chapter about HTTP: 

javaprivate final Map<Long, Task> tasks = new ConcurrentHashMap<>();
private final AtomicLong nextId = new AtomicLong(1);

Reading: path variables and query parameters

java@RestController
@RequestMapping("/api/tasks")
class TaskController {

  @GetMapping
  List<Task> list(@RequestParam(defaultValue = "false") boolean doneOnly) {
    return tasks.values().stream()
        .filter(t -> !doneOnly || t.done())
        .toList();
  }

  @GetMapping("/{id}")
  Task byId(@PathVariable Long id) {
    Task found = tasks.get(id);
    if (found == null) throw new TaskNotFoundException(id);
    return found;
  }
}

@RequestMapping on the class sets the shared prefix, so each method declares only what's left. Two ways of taking input appear here, and the difference is not cosmetic:

  • @PathVariable binds a URL segment — /api/tasks/7. Use it for identity: which task.
  • @RequestParam binds a query parameter — ?doneOnly=true. Use it for modifiers: filtering, sorting, paging. defaultValue makes it optional.

Writing: request bodies and status codes

java@PostMapping
ResponseEntity<Task> create(@RequestBody NewTask body) {
  long id = nextId.getAndIncrement();
  Task saved = new Task(id, body.title(), body.description(), false);
  tasks.put(id, saved);

  return ResponseEntity
      .created(URI.create("/api/tasks/" + id))  // 201 + Location
      .body(saved);
}

@PutMapping("/{id}")
Task replace(@PathVariable Long id, @RequestBody NewTask body) {
  if (!tasks.containsKey(id)) throw new TaskNotFoundException(id);
  Task updated = new Task(id, body.title(), body.description(), false);
  tasks.put(id, updated);
  return updated;
}

@DeleteMapping("/{id}")
ResponseEntity<Void> delete(@PathVariable Long id) {
  if (tasks.remove(id) == null) throw new TaskNotFoundException(id);
  return ResponseEntity.noContent().build();  // 204
}

@RequestBody is the mirror of @ResponseBody: it deserializes the incoming JSON into the parameter type.

Getting the status code right

Return a plain object and you get 200 OK. That's right for a read and wrong for almost everything else, so ResponseEntity lets you say what you mean:

CodeUse it when
200 OKA read succeeded, or an update returns the new state
201 CreatedSomething was created — include a Location header pointing at it
204 No ContentIt worked and there is deliberately nothing to return (a delete)
400 Bad RequestThe client's input was malformed — chapter 5
404 Not FoundThat id doesn't exist
The two most common mistakes

Returning 200 from a create instead of 201 with a Location header — the client then has no idea what URL the new thing lives at. And returning 200 with an empty body for a missing id, which tells the client "fine, nothing there" instead of "that doesn't exist".

The exception

We've thrown TaskNotFoundException three times without defining it. It's small: 

javaclass TaskNotFoundException extends RuntimeException {
  TaskNotFoundException(Long id) {
    super("No task with id " + id);
  }
}

Right now that produces a generic 500. Turning it into a proper 404 is chapter 5's job — and doing it in one place, for every controller.

So what did we actually gain?

A complete CRUD resource with correct HTTP semantics. What we also gained, less happily, is a controller that stores data, generates ids and holds business rules. That works at this size and stops working shortly after. Chapter 4 splits it up.
