Chapter One

Getting Started with Spring Boot

Before we write a line of application code, let's be clear about what Spring actually is — and what Boot adds on top of it.

Spring, and then Spring Boot

Spring is the framework underneath: dependency injection, the web layer (Spring MVC), data access, transactions, security. It is old, large, and very well tested. Its historical problem was setup — a Spring application used to need a great deal of XML and boilerplate before it did anything at all.

Spring Boot is the layer that fixed that. It does three things worth naming:

  • Auto-configuration. It looks at what's on your classpath and configures sensible defaults. Put a web library on the path and you get a configured web stack.
  • Starters. One dependency pulls in a coherent set of libraries that are known to work together at matching versions.
  • An embedded server. Your application is a normal Java program with a main method. It contains its own web server, so there is nothing to deploy into.
The key idea

Boot doesn't replace Spring or hide it. It picks defaults for you and gets out of the way. Every default can be overridden, and by chapter 7 you'll be overriding several.

Versions, briefly

This book targets Spring Boot 4.1, published on 10 June 2026. Spring Boot 4 requires Java 17 or later. New minor versions ship about every six months and each carries roughly twelve months of open-source support, so for a new project the right move is simply to take the newest minor.

This will bite you

Spring Boot 4 renamed the web starter. What older tutorials call spring-boot-starter-web is now spring-boot-starter-webmvc; the old name is deprecated in favour of it. Most tutorials you'll find were written for Boot 3 and don't say so. When something doesn't resolve, check the starter name first.

What to install

Three things, and only the first is strictly required.

That third row is not a dodge. Spring Initializr generates a wrapper script — mvnw for Maven, gradlew for Gradle — which downloads the correct build-tool version on first use. You do not install Maven or Gradle yourself, and everyone building the project gets the identical version.

What the build file says

Open pom.xml. Past the boilerplate, two parts matter: 

pom.xml<!-- inherits dependency versions that are tested together -->
<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>4.1.0</version>
</parent>

<dependencies>
  <!-- note: -webmvc, not -web -->
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-webmvc</artifactId>
  </dependency>
</dependencies>

The parent is where version management lives. Because your project inherits from it, you declare dependencies without version numbers and get versions Spring has tested together. The one version you control is the parent's — that is what "upgrading Spring Boot" means in practice.

The main class

java@SpringBootApplication
public class TasksApplication {

  public static void main(String[] args) {
    SpringApplication.run(TasksApplication.class, args);
  }
}

That is the whole bootstrap. @SpringBootApplication is three annotations in one: it marks the class as configuration, switches on auto-configuration, and starts component scanning from this class's package downward. SpringApplication.run builds the application context and starts the embedded server.

Remember where this class lives

Component scanning starts at this class's package and searches below it. A class placed in a sibling package is invisible to Spring — it will simply never be found, with no error. That is the single most common "why isn't my controller working" in a first Spring project.

Running it

bash./mvnw spring-boot:run

The first run downloads dependencies, so give it a minute. Then you'll see the Spring banner and a line ending roughly like this: 

outputTomcat started on port 8080 (http)
Started TasksApplication in 1.4 seconds

Visit http://localhost:8080 and you'll get a 404 error page. That is the correct result: the server is running and routing, and we haven't told it about a single URL yet. Stop it with Ctrl-C.

So what did we gain?

A running HTTP server, a managed dependency set, and a reproducible build — for one dependency and eight lines of Java. Nothing is deployed anywhere; the application is an ordinary program that happens to listen on a port. In the next chapter we give it something to say.
