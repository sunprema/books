Chapter Six

Saving Data with a Database

The map disappears on restart. Let's replace it with a real database — and find out how little code that takes.

Relational databases and JPA

A relational database stores rows in tables. Java has objects. Something has to translate, and writing that translation by hand — SQL strings, ResultSet loops, mapping columns to fields — is tedious and easy to get subtly wrong.

JPA (Jakarta Persistence API) is the specification for doing it declaratively: annotate a class to say which table and columns it maps to, and the implementation generates the SQL. Hibernate is the implementation Spring Boot uses by default.

Spring Data JPA then sits on top of Hibernate and removes the last layer of boilerplate — as we'll see, by letting you not write the repository at all.

The dependencies

pom.xml<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>

<dependency>
  <groupId>com.h2database</groupId>
  <artifactId>h2</artifactId>
  <scope>runtime</scope>
</dependency>

H2 is an in-memory database — nothing to install, and it vanishes on shutdown. That is ideal for development and for chapter 8's tests. Moving to PostgreSQL later is a dependency swap and a few properties, not a code change.

The entity

java@Entity
class Task {

  @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
  private Long id;

  @Column(nullable = false, length = 120)
  private String title;

  private String description;
  private boolean done;

  protected Task() { }            // JPA requires a no-arg constructor

  Task(String title, String description) {
    this.title = title;
    this.description = description;
  }

  // getters and setters
}
Why this isn't a record

JPA needs a no-arg constructor and mutable fields — it constructs entities reflectively and fills them in. Records are final and have neither, so an entity cannot be a record. This is exactly why chapter 3 split NewTask from Task: the wire types stay records, and only the stored type carries JPA's constraints.

@Id marks the primary key. @GeneratedValue(IDENTITY) lets the database assign it — you never set an id yourself. @Column is optional; without it the field maps to a same-named column with default settings, and the constraints here mirror chapter 5's validation at the storage layer.

The repository you don't write

javainterface TaskRepository extends JpaRepository<Task, Long> {
}

That's the whole file. No implementation class exists anywhere — Spring Data generates a proxy at startup. The two type parameters are the entity and its id type, and from them you get:

MethodDoes
save(task)Inserts, or updates if the id is set
findById(id)Returns an Optional<Task>
findAll()Every row
deleteById(id)Removes one
count()How many
existsById(id)Cheaper than fetching to check

Queries from method names

The part that feels like a trick: declare a method following Spring Data's naming grammar and it is implemented for you. 

javainterface TaskRepository extends JpaRepository<Task, Long> {

  List<Task> findByDoneTrue();

  List<Task> findByTitleContainingIgnoreCase(String fragment);

  long countByDoneFalse();
}

The name is parsed at startup into a query. findByTitleContainingIgnoreCase becomes a case-insensitive LIKE. Get the grammar wrong — misspell a field — and the application fails to start with a clear message, which is much better than failing at 3am on the one code path that uses it.

The service barely changes

java@Service
class TaskService {

  private final TaskRepository repository;

  TaskService(TaskRepository repository) {
    this.repository = repository;
  }

  Task create(NewTask body) {
    return repository.save(new Task(body.title(), body.description()));
  }

  Task complete(Long id) {
    Task task = repository.findById(id)
        .orElseThrow(() -> new TaskNotFoundException(id));
    task.setDone(true);
    return repository.save(task);
  }

  void delete(Long id) {
    if (!repository.existsById(id)) throw new TaskNotFoundException(id);
    repository.deleteById(id);
  }
}
This is chapter 4 paying out

We replaced a HashMap with a relational database and the controller didn't change at all. The service changed only where it touched storage. That boundary is the entire reason the layers exist.

Pointing at a database

application.ymlspring:
  datasource:
    url: jdbc:h2:mem:tasks
  jpa:
    hibernate:
      ddl-auto: update
    show-sql: true

ddl-auto: update tells Hibernate to create and alter tables to match your entities. That is convenient in development and dangerous in production, where a schema change should be a reviewed migration, not a side effect of a deploy. Chapter 7 shows how to set it differently per environment.

show-sql: true logs the generated SQL. Turn it on once and read it — it is the fastest way to develop an instinct for what JPA is actually doing on your behalf.

Keep returning records

One temptation to resist: returning the Task entity straight from the controller. It works, and it welds your JSON contract to your table — add an internal column and it silently appears in your public API. Map to a record on the way out: 

javarecord TaskView(Long id, String title, String description, boolean done) {

  static TaskView of(Task t) {
    return new TaskView(t.getId(), t.getTitle(),
                        t.getDescription(), t.isDone());
  }
}

Two Boot 4.1 notes

Spring Boot 4.1 added spring.datasource.connection-fetch=lazy, which defers acquiring a connection until one is genuinely needed — useful for request paths that turn out not to touch the database. Separately, Apache Derby support is now deprecated following Derby's retirement; if you meet it in an old tutorial, reach for H2 instead.

So what did we actually gain?

Persistence, for one interface with no body and six lines of configuration. Tasks now survive a restart. What's hardcoded is the configuration itself — the database URL is in a file we ship. Next.
