Chapter Nine

Basic Security

Our API will delete anyone's task for anyone who asks. Let's put a login in front of it — the simplest one that is honestly a login.

Two different questions

Security answers two questions, and confusing them causes most of the trouble:

  • Authentication — who are you? Verified by credentials.
  • Authorization — are you allowed to do this? Decided from who you are.

Spring Security handles both, in that order, in a chain of servlet filters that runs before your controller.

Adding the starter

pom.xml<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-security</artifactId>
</dependency>

Restart, and every endpoint is locked immediately: 

bash$ curl -i localhost:8080/api/tasks
HTTP/1.1 401

# and in the startup log:
Using generated security password: 8f4a1c2e-...
Secure by default

Just adding the dependency locks everything down. That default is deliberate: you open specific doors on purpose, rather than discovering later which ones you forgot to close. The generated password is for the first five minutes only.

The SecurityFilterChain

Security is configured by declaring a SecurityFilterChain bean — the recommended style since Spring Security 5.4, and the only one in 7: 

java@Configuration
@EnableWebSecurity
class SecurityConfig {

  @Bean
  SecurityFilterChain api(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/hello").permitAll()
            .anyRequest().authenticated())
        .httpBasic(Customizer.withDefaults())
        .csrf(csrf -> csrf.disable())      // stateless API, no browser session
        .build();
  }
}

Read the rules top to bottom — first match wins. So /hello stays open, and anyRequest().authenticated() catches everything else. Putting anyRequest() first would shadow every rule below it.

Spring Security 7 broke old examples

Boot 4.0 ships Spring Security 7.0 and Boot 4.1 ships 7.1. Two changes mean most configuration you'll find online will not compile:

  • authorizeRequests() was removed. Use authorizeHttpRequests().
  • The chained style using .and() was removed. The Lambda DSL is now required.

If a snippet has .and() in it, it predates Spring Security 6 and needs translating, not copying.

That's what the lambdas are doing above. Customizer.withDefaults() turns a feature on with Spring Security's defaults — it is shorthand for the empty lambda it -> {}.

Real users and hashed passwords

java@Bean
PasswordEncoder passwordEncoder() {
  return new BCryptPasswordEncoder();
}

@Bean
UserDetailsService users(PasswordEncoder encoder) {
  UserDetails user = User.withUsername("amara")
      .password(encoder.encode("change-me"))
      .roles("USER")
      .build();

  return new InMemoryUserDetailsManager(user);
}

InMemoryUserDetailsManager holds demo users without a database — fine for learning, and not for anything real. The PasswordEncoder is not optional: passwords are stored as hashes, and BCrypt is deliberately slow so that guessing at scale is expensive.

Two ways to get this wrong

Storing a plaintext password — Spring Security will refuse to match it and you'll get a confusing failure rather than a helpful one. And calling encode() on a value that is already encoded, which silently produces a password nobody can ever log in with. 

bash$ curl -u amara:change-me localhost:8080/api/tasks
[{"id":1,"title":"Write chapter 9",...}]

$ curl -u amara:wrong localhost:8080/api/tasks
HTTP/1.1 401

About HTTP Basic

HTTP Basic sends the username and password, base64-encoded, on every single request. Base64 is encoding, not encryption — anyone who can see the traffic can read the password. So:

  • Over HTTPS it is acceptable for internal tools and first examples.
  • Over plain HTTP it is equivalent to no security at all.
  • For a public API you want tokens — which is the next book, deliberately.

The CSRF line deserves a sentence

CSRF protection defends flows where a browser holds a session cookie and can be tricked into sending it. A stateless API authenticated per-request has no such cookie, so disabling CSRF is a reasonable trade-off — but it is a decision, not a line to paste past. If you later add form login and browser sessions, that same line becomes a real vulnerability.

One Security 7 surprise

The new authorization model also checks dispatch types, including error dispatches. A consequence worth knowing: an unauthenticated render of /error can now return 401 where it previously returned the error page. If your error responses start coming back as 401 after upgrading, that's why — permit /error explicitly.

Roles, briefly

java.authorizeHttpRequests(auth -> auth
    .requestMatchers("/hello").permitAll()
    .requestMatchers(HttpMethod.DELETE, "/api/tasks/**").hasRole("ADMIN")
    .anyRequest().authenticated())

Now anyone signed in can read and create tasks, but only an ADMIN can delete one. That is authorization: same identity, different permissions.

So what did we actually gain?

A closed door with a named key, hashed passwords, and per-route rules — in one configuration class. The application is now feature-complete. All that's left is getting it out of the IDE.
