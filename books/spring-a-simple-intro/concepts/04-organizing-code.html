Chapter Four

Organizing Application Code

Our controller does everything. Let's give each job its own home — and see why dependency injection is what makes that cheap.

What's wrong with one class

Chapter 3's TaskController parses HTTP, owns the storage map, generates ids, and decides what "not found" means. Nothing is broken yet. But two costs are already locked in:

  • Swapping the map for a database means editing the class that handles HTTP.
  • Testing the rule "you can't complete a task that doesn't exist" means making an HTTP request, because that rule doesn't exist anywhere else.

Three layers

The conventional split gives each layer exactly one concern:

LayerOwnsMust not know about
ControllerPaths, status codes, request/response shapesBusiness rules, storage
ServiceBusiness rules, orchestration, transactionsHTTP, SQL
RepositoryReading and writing dataHTTP, business rules

Dependency injection, concretely

The controller needs a service; the service needs a repository. Nobody constructs their own collaborator — they ask for it, and Spring supplies it. That's dependency injection, and in Spring it's mostly one rule: take what you need in the constructor. 

java@Service
class TaskService {

  private final TaskRepository repository;

  TaskService(TaskRepository repository) {   // no @Autowired needed
    this.repository = repository;
  }

  Task complete(Long id) {
    Task task = repository.findById(id)
        .orElseThrow(() -> new TaskNotFoundException(id));
    task.setDone(true);
    return repository.save(task);
  }
}

That comment matters: a class with a single constructor needs no @Autowired. Spring uses that constructor automatically. You'll see @Autowired in older code; on a single constructor it's noise.

Why constructors, not fields

You can inject into a field instead: 

java// don't do this
@Autowired private TaskRepository repository;

It's shorter and worse, for three reasons. The field can't be final. The dependency is invisible from outside the class, so a growing list of them doesn't feel like anything. And you cannot construct the class in a plain unit test — there's no constructor to pass a stub to, so every test needs Spring to start. Constructor injection costs three lines and buys back chapter 8.

The payoff, stated plainly

new TaskService(fakeRepository) is a valid line of Java. That single fact is why chapter 8's service tests run in milliseconds with no Spring context at all.

The stereotype annotations

For Spring to inject something, it has to know about it. Component scanning finds classes carrying a stereotype:

AnnotationPut it onExtra behavior
@ComponentAnything managedThe generic base
@ServiceBusiness logicNone — it documents intent
@RepositoryData accessTranslates persistence exceptions into Spring's DataAccessException hierarchy
@RestControllerWeb handlersResponse bodies, as in chapter 2

All of them are @Component underneath. Only @Repository does anything mechanically different — and in chapter 6 Spring Data supplies the repository, so you won't even write that one.

The controller gets smaller

java@RestController
@RequestMapping("/api/tasks")
class TaskController {

  private final TaskService service;

  TaskController(TaskService service) {
    this.service = service;
  }

  @GetMapping("/{id}")
  Task byId(@PathVariable Long id) {
    return service.byId(id);
  }

  @PostMapping("/{id}/complete")
  Task complete(@PathVariable Long id) {
    return service.complete(id);
  }
}

Each method is now one line: translate the request, call the service, return. If a controller method grows an if about business rules, that if belongs one layer down.

A package layout that scales

Two conventions exist. By layer puts all controllers together; by feature puts everything about tasks together. For anything that might grow past one resource, prefer by feature: 

textcom.example.tasktracker
├── TasksApplication.java
├── task
│   ├── TaskController.java
│   ├── TaskService.java
│   ├── TaskRepository.java
│   ├── Task.java
│   └── TaskNotFoundException.java
└── config
    └── SecurityConfig.java

Everything about tasks is in one folder, so a change stays in one folder. Adding users later means adding a user package, not touching four existing ones.

Keep it under the main class

Every package here sits below TasksApplication's package. That's what keeps component scanning finding them — the rule from chapter 1, now load-bearing.

An aside on Boot 4's modularization

Spring Boot 4 split the formerly monolithic spring-boot-autoconfigure jar into many fine-grained modules. Auto-configuration now arrives with the specific starter that needs it rather than one catch-all jar. You'll notice this only when upgrading an older project and finding that some auto-configuration went missing along with a starter you dropped.

So what did we actually gain?

Three small classes instead of one medium one, and a rule about which knows what. The visible payoff arrives twice: in chapter 6, where swapping storage touches only the repository, and in chapter 8, where the rules can be tested without HTTP. First, though, our API still accepts a task with a blank title.
