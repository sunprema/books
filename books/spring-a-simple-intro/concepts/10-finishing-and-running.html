Chapter Ten

Finishing and Running the Project

The application works on your machine, which is the easy half. Let's make it observable, package it, and run it somewhere else.

Logging

Spring Boot uses SLF4J as the API with Logback behind it, already configured. You need one line per class: 

javaprivate static final Logger log =
    LoggerFactory.getLogger(TaskService.class);

log.info("Completed task {}", id);   // placeholder, not concatenation
Use the placeholder

log.debug("Loaded " + task) builds that string every time the line runs, even when debug logging is switched off. log.debug("Loaded {}", task) only formats if the level is enabled. On a hot path the difference is measurable, and the habit costs nothing.

LevelUse for
ERRORSomething failed and someone should look
WARNSuspicious, but handled
INFOSignificant events — startup, a task created
DEBUGDetail for diagnosing a problem
TRACEEverything, briefly, under duress
 
application.ymllogging:
  level:
    root: INFO
    com.example.tasktracker: DEBUG
    org.hibernate.SQL: DEBUG        # see the generated SQL

Levels are per-package, so you can turn your own code up to DEBUG without drowning in framework noise. If you use Log4j instead of Logback, Spring Boot 4.1 added file rotation with four strategies: size, time, size-and-time, and cron.

Building the JAR

bash./mvnw package
# → target/task-tracker-0.0.1-SNAPSHOT.jar

This runs the tests, compiles, and produces an executable JAR — your code, every dependency, and the embedded Tomcat, in one file. It is often called a fat JAR, and it is the entire deployable unit. No application server, nothing to install alongside it. 

bashjava -jar target/task-tracker-0.0.1-SNAPSHOT.jar

# with production configuration from chapter 7
SPRING_PROFILES_ACTIVE=prod \
SPRING_DATASOURCE_URL=jdbc:postgresql://db:5432/tasks \
SPRING_DATASOURCE_PASSWORD="$DB_PASSWORD" \
java -jar target/task-tracker-0.0.1-SNAPSHOT.jar
"no main manifest attribute"

If you see this, you're running the wrong JAR. Maven builds a plain one first, then Spring Boot's plugin repackages it into the executable one. Both can sit in target/; the executable one is larger and is the one without an .original suffix.

A container, without a Dockerfile

You can write a Dockerfile. You mostly don't need to — the Maven and Gradle plugins build an OCI image directly, using Cloud Native Buildpacks: 

bash./mvnw spring-boot:build-image

docker run -p 8080:8080 \
  -e SPRING_PROFILES_ACTIVE=prod \
  task-tracker:0.0.1-SNAPSHOT

The buildpack picks a JDK, layers the image so dependencies cache separately from your code, and applies sensible container defaults. You need Docker running locally; you don't need to know how to write a good Java Dockerfile, which is a genuinely fiddly thing to get right.

If you meet layertools

Older articles describe a layertools jar mode for hand-built layered images. It was removed in Spring Boot 4.1 and replaced by the tools jar mode. Another small sign of whether what you're reading is current.

Knowing it's alive

One more starter is worth adding before you deploy anything: 

pom.xml<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
bash$ curl localhost:8080/actuator/health
{"status":"UP"}

That endpoint is what a load balancer or orchestrator polls to decide whether your instance should receive traffic — and it checks the database connection too, so it means rather more than "the process is running". Spring Boot 4.1 also expanded /actuator/info's ProcessInfo section with six new fields.

Actuator plus security

Actuator exposes operational detail. With chapter 9's config, anyRequest().authenticated() already covers it — but if you permit paths broadly, don't accidentally publish /actuator/** to the internet.

A short pre-flight list

  • ddl-auto is validate, not update, in the prod profile.
  • No credentials anywhere in src/main/resources.
  • show-sql off in production.
  • /actuator/health responds.
  • ./mvnw package is green — the tests run as part of it.

What we built

Ten chapters ago this was an empty folder. It is now an API that stores tasks in a database, validates its input, returns standards-shaped errors, requires a login, has a test suite that runs in seconds, and ships as a single file that runs anywhere with a JDK.

More usefully, the shape is the same for the next application. A resource, three layers, constructor injection, a validation boundary, a repository interface, configuration from the environment, and tests at whichever level is cheapest. Spring is enormous, but this path through it is short — and it is the same path every time.
