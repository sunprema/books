Chapter Seven

Configuration

The same JAR has to run on your laptop against H2 and in production against PostgreSQL. Nothing about that difference belongs in the code.

One file, two formats

Spring Boot reads application.properties or application.yml from src/main/resources. They are interchangeable — pick one and be consistent.

application.propertiesapplication.yml
spring.datasource.url=jdbc:h2:mem:tasks spring:
  datasource:
    url: jdbc:h2:mem:tasks

Properties files are flatter and grep better. YAML groups related keys and gets less repetitive as configuration grows. This book uses YAML.

Environment variables and relaxed binding

Environment variables can't contain dots, so Spring Boot uses relaxed binding: uppercase the property and replace each dot with an underscore.

PropertyEnvironment variable
spring.datasource.urlSPRING_DATASOURCE_URL
spring.datasource.passwordSPRING_DATASOURCE_PASSWORD
tasks.max-per-userTASKS_MAXPERUSER
 
bashSPRING_DATASOURCE_URL=jdbc:postgresql://db:5432/tasks \
SPRING_DATASOURCE_PASSWORD="$DB_PASSWORD" \
java -jar task-tracker.jar
Secrets never go in the file

application.yml is committed to git. A password in it is a password in your repository history, permanently, for everyone with read access. Credentials come from environment variables or a secret manager — no exceptions, not even "just for staging".

Profiles

A profile is a named set of overrides in application-<name>.yml. Keep shared settings in the base file and put only the differences in each profile: 

application.ymlspring:
  application:
    name: task-tracker
  datasource:
    url: jdbc:h2:mem:tasks
  jpa:
    hibernate:
      ddl-auto: update      # fine for development
    show-sql: true

tasks:
  max-per-user: 100
application-prod.ymlspring:
  jpa:
    hibernate:
      ddl-auto: validate    # never rewrite a production schema
    show-sql: false

logging:
  level:
    org.springframework.web: WARN
bashjava -jar task-tracker.jar --spring.profiles.active=prod
# or: SPRING_PROFILES_ACTIVE=prod java -jar task-tracker.jar
Profiles layer, they don't replace

application-prod.yml is applied on top of application.yml, key by key. Anything the profile doesn't mention keeps its base value — so tasks.max-per-user is still 100 in production. Expecting replacement is a reliable way to be surprised.

Note what ddl-auto: validate does above: it checks the schema matches the entities and refuses to start if not, instead of silently altering tables. That is the setting chapter 6 promised.

Typed configuration

You can read a single value with @Value: 

java@Value("${tasks.max-per-user}")
private int maxPerUser;

It works, and it scatters string keys through your codebase where nothing checks them. A typo fails at startup if you're lucky and at runtime if you're not. @ConfigurationProperties binds a whole group to a typed object instead: 

java@ConfigurationProperties(prefix = "tasks")
record TaskProperties(int maxPerUser) { }
java@SpringBootApplication
@EnableConfigurationProperties(TaskProperties.class)
public class TasksApplication { ... }
java@Service
class TaskService {

  private final TaskRepository repository;
  private final TaskProperties properties;

  TaskService(TaskRepository repository, TaskProperties properties) {
    this.repository = repository;
    this.properties = properties;
  }

  Task create(NewTask body) {
    if (repository.count() >= properties.maxPerUser()) {
      throw new TooManyTasksException();
    }
    return repository.save(new Task(body.title(), body.description()));
  }
}

Three things improve at once. Binding happens once at startup, so a bad value fails immediately. maxPerUser() is an int, checked by the compiler. And the properties arrive through the constructor like any other dependency — which means a test can pass new TaskProperties(5) without a config file.

A record works here because configuration is read-only after startup. (Note the relaxed binding again: max-per-user in YAML maps to maxPerUser in Java.)

So what did we actually gain?

One artifact that runs in any environment, secrets that live outside the repository, and settings that are typed and validated at startup rather than discovered in production. Now let's make sure the thing works before it gets there.
