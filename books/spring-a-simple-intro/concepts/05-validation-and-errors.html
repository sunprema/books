Chapter Five

Validation and Errors

Right now you can create a task with a blank title and a 40,000-character description, and a missing id returns a 500. Both are one dependency and one class away from being fixed.

The dependency

pom.xml<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-validation</artifactId>
</dependency>

This brings in Jakarta Validation — Spring Boot 4 builds on version 3.1 — which is a specification for expressing constraints as annotations, plus an implementation that enforces them.

Constraints on the input type

The constraints go on NewTask, the record clients send — not on whatever we store: 

javarecord NewTask(

    @NotBlank(message = "title must not be blank")
    @Size(max = 120, message = "title must be at most 120 characters")
    String title,

    @Size(max = 2000)
    String description) {}
AnnotationPasses when
@NotNullThe value is not null — empty string is fine
@NotBlankNot null, and contains at least one non-whitespace character
@NotEmptyNot null and length > 0 — " " passes
@Size(min, max)Length falls in range
@Min / @MaxA number is within bounds
@EmailThe string looks like an email address

For user-supplied text, @NotBlank is nearly always the one you want — @NotEmpty happily accepts a title of three spaces.

Switching it on

Annotations alone do nothing. The controller has to ask: 

java@PostMapping
ResponseEntity<Task> create(@Valid @RequestBody NewTask body) {
  // if we get here, body is valid
  ...
}
The silent failure

Forget @Valid and nothing is ever checked. There is no warning — the constraints simply sit there as documentation. If validation "isn't working", check for the missing @Valid before anything else.

With it in place, a bad request now fails before the method body runs, raising MethodArgumentNotValidException. Spring's default handling turns that into a 400 — but with a body that's shaped for a browser, not for a client that wants to know which field was wrong.

One place for every error

@RestControllerAdvice registers exception handlers that apply across every controller. This is where our 404 finally gets fixed too: 

java@RestControllerAdvice
class ApiErrors {

  @ExceptionHandler(MethodArgumentNotValidException.class)
  ProblemDetail invalid(MethodArgumentNotValidException ex) {
    ProblemDetail body = ProblemDetail.forStatusAndDetail(
        HttpStatus.BAD_REQUEST, "One or more fields are invalid.");
    body.setTitle("Validation failed");

    Map<String, String> errors = new LinkedHashMap<>();
    for (FieldError e : ex.getBindingResult().getFieldErrors()) {
      errors.put(e.getField(), e.getDefaultMessage());
    }
    body.setProperty("errors", errors);
    return body;
  }

  @ExceptionHandler(TaskNotFoundException.class)
  ProblemDetail notFound(TaskNotFoundException ex) {
    return ProblemDetail.forStatusAndDetail(
        HttpStatus.NOT_FOUND, ex.getMessage());
  }
}

The BindingResult carries one FieldError per violated constraint, which is exactly the map a client wants.

ProblemDetail

ProblemDetail is Spring's implementation of RFC 7807, the standard format for HTTP error bodies. Using it means your errors have the same shape as everyone else's: 

json{
  "type": "about:blank",
  "title": "Validation failed",
  "status": 400,
  "detail": "One or more fields are invalid.",
  "errors": {
    "title": "title must not be blank"
  }
}

setProperty adds fields beyond the standard ones, which is how the per-field errors map gets in.

Try it

bash$ curl -i -X POST localhost:8080/api/tasks \
    -H 'Content-Type: application/json' \
    -d '{"title":"   "}'

HTTP/1.1 400
Content-Type: application/problem+json

{"title":"Validation failed","status":400,
 "errors":{"title":"title must not be blank"}}

$ curl -i localhost:8080/api/tasks/999
HTTP/1.1 404
Note the content type

application/problem+json, not application/json. That's part of the RFC, and it lets a client tell an error body from a successful one without inspecting the status code twice.

Don't leak internals

One more handler is worth adding — a catch-all so an unexpected exception never reaches the client as a stack trace: 

java@ExceptionHandler(Exception.class)
ProblemDetail unexpected(Exception ex) {
  log.error("Unhandled exception", ex);   // full detail to the log
  return ProblemDetail.forStatusAndDetail(
      HttpStatus.INTERNAL_SERVER_ERROR,
      "Something went wrong.");            // nothing useful to an attacker
}

Detail goes to the log, where you can act on it. The client gets a status code and an apology. A stack trace in a response body tells a stranger your class names, library versions and often your file paths.

So what did we actually gain?

Input we can trust by the time it reaches a handler, errors in a standard format, and one class that owns the mapping from exception to response. The API is now correct. It's also still forgetting everything when you restart it.
