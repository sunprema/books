Chapter Eight

Testing the Application

Spring can start your whole application in a test. Usually it shouldn't — the interesting question is how little you can start and still learn something.

Three levels

LevelStartsSpeedUse for
UnitNothingmillisecondsBusiness rules in the service
SliceOne layer~a secondController mapping, repository queries
IntegrationEverythingsecondsOne or two end-to-end paths

Most tests should be the first kind. Reach up a level only when the thing you want to verify genuinely lives in the framework.

Unit-testing the service

This is where chapter 4's constructor injection pays off. No Spring, no context, no annotations: 

javaclass TaskServiceTest {

  private final TaskRepository repository = mock(TaskRepository.class);
  private final TaskService service = new TaskService(repository);

  @Test
  void completing_a_missing_task_is_rejected() {
    when(repository.findById(7L)).thenReturn(Optional.empty());

    assertThrows(TaskNotFoundException.class, () -> service.complete(7L));
  }

  @Test
  void completing_marks_the_task_done() {
    Task task = new Task("Write chapter 8", null);
    when(repository.findById(1L)).thenReturn(Optional.of(task));
    when(repository.save(any())).thenAnswer(i -> i.getArgument(0));

    assertTrue(service.complete(1L).isDone());
  }
}
Notice what isn't here

No @SpringBootTest, no @Autowired, no application context. TaskService is a plain Java object with one constructor parameter, so a test can build it directly. Field injection would have made this test impossible to write.

Slice-testing the controller

Controllers are mostly framework: routing, deserialization, validation, status codes. Testing those needs Spring — but only the web layer. @WebMvcTest starts exactly that: 

java@WebMvcTest(TaskController.class)
class TaskControllerTest {

  @Autowired MockMvc mvc;
  @MockitoBean TaskService service;

  @Test
  void rejects_a_blank_title() throws Exception {
    mvc.perform(post("/api/tasks")
            .contentType(MediaType.APPLICATION_JSON)
            .content("""
                {"title": "  "}"""))
       .andExpect(status().isBadRequest());
  }

  @Test
  void missing_task_is_404() throws Exception {
    when(service.byId(999L)).thenThrow(new TaskNotFoundException(999L));

    mvc.perform(get("/api/tasks/999"))
       .andExpect(status().isNotFound());
  }
}

@MockitoBean puts a Mockito mock into the context in place of the real TaskService. (If you've seen @MockBean in older code, this is its replacement.) The first test proves chapter 5's validation is actually wired; the second proves the @RestControllerAdvice maps the exception to a 404. Neither touches a database.

Slice-testing the repository

Derived query methods deserve a test, because their behavior comes from a method name: 

java@DataJpaTest
class TaskRepositoryTest {

  @Autowired TaskRepository repository;

  @Test
  void findByDoneTrue_returns_only_completed_tasks() {
    Task done = new Task("finished", null);
    done.setDone(true);
    repository.save(done);
    repository.save(new Task("still going", null));

    assertEquals(1, repository.findByDoneTrue().size());
  }
}

@DataJpaTest starts the persistence layer against an in-memory database and rolls each test back afterwards, so tests don't leak state into one another.

Integration tests

@SpringBootTest starts the whole context. Spring Boot 4 added RestTestClient: with a regular @SpringBootTest, or when @AutoConfigureMockMvc is used, you can autowire one that operates on the underlying MockMvc instance. 

java@SpringBootTest
@AutoConfigureMockMvc
class TaskApiIntegrationTest {

  @Autowired RestTestClient client;

  @Test
  void create_then_fetch() {
    client.post().uri("/api/tasks")
          .contentType(MediaType.APPLICATION_JSON)
          .bodyValue(new NewTask("Ship the book", null))
          .exchange()
          .expectStatus().isCreated();

    client.get().uri("/api/tasks")
          .exchange()
          .expectStatus().isOk();
  }
}
Use these sparingly

An integration test starts everything: context, database, security filters. It catches wiring problems the other levels can't — and if you write fifty of them, your suite takes minutes and people stop running it. A handful covering the critical paths is the right number.

Test starters in Boot 4

Boot 4's modularization gave each technology a companion test starter following the pattern spring-boot-starter-<technology>-test — so spring-boot-starter-data-jpa-test alongside spring-boot-starter-data-jpa, and likewise for validation. Projects generated by Initializr get the ones they need; you'll meet this naming when upgrading an older project whose single test starter no longer covers everything.

Running them

bash./mvnw test                              # all tests
./mvnw test -Dtest=TaskServiceTest       # one class

./gradlew test                           # Gradle equivalent

Both wrappers run the full suite as part of package too, so a failing test stops a build before it produces a JAR.

What's worth testing

  • The rules — completing a missing task, exceeding the task limit. These are unit tests and they're the ones that catch real regressions.
  • The error paths — 400 on bad input, 404 on a missing id. Easy to write, and exactly where bugs hide.
  • Derived queries — because a method name is not checked by the compiler.

Not worth testing: that save saves, or that @GetMapping maps. That's Spring's test suite, not yours.

So what did we actually gain?

A fast suite that tells you which layer broke. The service tests run without Spring at all — which was decided back in chapter 4, when we chose a constructor over a field. One thing is still missing: anyone at all can call this API.
