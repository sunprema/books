    ...classify, compensate...

Integration design review checklist

  1. Which of the four interaction styles is this, and does the runtime match?
  2. What are the four numbers: volume, peak, payload size, tightest downstream limit?
  3. What is the idempotency key, and what enforces it?
  4. Where does the correlation ID come from?
  5. Are all rejecting checks ahead of every side effect?
  6. What is in the pipeline at the final step, and would you log all of it?
  7. Pool size × node count — does it exceed a downstream limit?
  8. Sum of timeouts vs. the SLA?
  9. What is the retry unit, and is retrying it safe?
  10. Which alerts fire on absence rather than error?
  11. Is every document-type change additive?
  12. What is the rollback, and has it been executed in staging?

API design checklist

  1. Modelled on the consumer's task, not the backend's schema?
  2. Could the backend be replaced without changing the contract?
  3. Distinct status codes per error class — 400, 409, 422, 503?
  4. Idempotent submission, keyed on a business identifier?
  5. Version in the path, with a parallel-run migration plan?
  6. Rate limits: per node or global? Effective limit at current node count?
  7. Token identifies application or user — deliberately?
  8. Cross-cutting concerns in gateway policy, not in the service?
  9. Deprecation with a date and a named owner per consumer?

Production-readiness checklist

  1. Pipeline capture configured on the top-level service, with secrets dropped first and retention agreed
  2. The recoverable unit of work is a top-level service, named in the runbook by path
  3. Dead-letter destinations exist, and depth is alerted
  4. Pool utilization collected and alerted before saturation
  5. Absence alarms: partner file windows, consumer liveness, queue depth
  6. Every certificate — keystore and truststore — has an owner and a 30-day alarm
  7. One identity per integration; rotation possible without a deploy
  8. Circuit breaker on every untrusted downstream
  9. Every queue bounded, with defined behaviour at the bound
  10. Reconciliation job for every partner round trip
  11. Artifact provenance: commit, approver, tests, deploy time — from records
  12. Runbook executable by someone who did not build the system

Glossary of integration terms

At-least-once
Delivery may repeat; the consumer must be idempotent. The contract, not a defect.
Back-pressure
Signalling upstream that you cannot accept more. The alternative is an unbounded queue.
Canonical model
One shared representation all systems map to and from.
Choreography
Participants react to events with no central script.
Circuit breaker
After repeated failures, stop calling for a cooling period and fail fast.
Compensation
An action that reverses a completed step's effect.
Correlation ID
One identifier following a transaction across every system.
Dead letter
Where a message goes after exhausting retries. Alert on its depth.
Guaranteed delivery
The platform's at-least-once delivery mechanism, with its own log.
Idempotency
Repeating an operation has no additional effect.
Orchestration
One service directs the sequence.
Poison message
A message that fails deterministically and blocks the queue behind it.
Saga
Local transactions with compensations, in place of distributed commit.
Strangler pattern
Incrementally replacing a legacy system behind a facade.
Token bucket
Rate limiting that permits bursts while holding a long-run average.
Transactional outbox
Write the event in the same transaction as the state change; relay it after.
Trusted subsystem
Calling downstream as the integration's own identity rather than the end user's.
The 30-second summary

Classify the interaction style, then pick the runtime. Put the runtime where the round trips are. Validate before you cause side effects. Make everything idempotent, then retry only transient failures, bounded and jittered. Publish events after the commit, never before. Size pools to the downstream's limit divided by node count. Alert on absence. Build one artifact and promote it unchanged. And keep the pipeline clean — whatever is in it gets logged.
