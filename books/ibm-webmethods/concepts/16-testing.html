Testing integration solutions

Integration code is mostly mapping and orchestration, which is exactly the code that unit tests are worst at and production is best at breaking. The trick is knowing which of the four test layers each risk belongs to — and refusing to push a risk upward where it costs ten times as much to catch.

Four layers

What to test where
LayerScopeDownstreamsCatches
UnitOne service, one mappingNoneField-level mapping errors, rule logic
ContractOne interfaceNone — schema onlyBreaking changes to an API or document type
IntegrationOne flow, mocked edgesMocked, including failuresOrchestration, retry, compensation
End-to-endThe business processReal test systemsConfiguration and environment drift

The layers get slower and more fragile as you descend, so push every test as high as it will go. A mapping bug found by a unit test costs a minute; the same bug found by an end-to-end suite costs an afternoon of working out which of nine moving parts was wrong.

Testing mappings properly

Mappings fail in a small number of predictable ways, and testing only the sample document misses all of them. For every mapping, write these five: the happy path; every optional field absent; an empty array; a maximum-length value in every string field; and one value with characters that break naive parsers — an ampersand, a non-ASCII name, an embedded quote.

Golden files beat assertions

Rather than asserting field by field, keep an input document and its expected output as files and compare whole. The test then catches fields you did not think about — including a field that has silently started arriving as null — and a deliberate change shows up as a readable diff in review, which is exactly where you want a mapping change discussed.

Production pipelines are your best test data

Chapter 13 turned on pipeline capture so services could be resubmitted. That store is also the highest-quality corpus of test inputs you will ever have: real documents, in all their irregularity, including the ones that broke something. Sample from it, mask the personal data (chapter 14 — the masking is mandatory, and it is easier to do at extraction than to retrofit), and keep the resulting documents as fixtures.

Every production incident should end by adding its captured pipeline to the fixture set. That is how a regression suite acquires the tests that matter, rather than the tests someone imagined at design time.

Mocking, and the failures you must simulate

Mock a downstream system at its adapter boundary so the flow under test is unchanged. Then use the mock for what it is uniquely good at: producing failures you cannot ask a real system for.

  • Slow. Six seconds instead of 900 ms — the chapter 8 scenario. Does the pool saturate? Does the circuit breaker open?
  • Refused. Connection refused immediately. Does the retry back off, or hammer?
  • Half-success. The ERP creates the order, then the connection drops before the response. This is the case that finds idempotency bugs, and no real test system will produce it on demand.
  • Wrong. A 200 response with a malformed body. Does anything validate the response, or does a null propagate?
  • Duplicate. The same message delivered twice, because at-least-once means it will be.

The half-success is the test that pays for the whole mocking framework. It is the failure most likely to happen and least likely to be tested.

Contract testing

Contract tests assert the shape of an interface without running either side of it: does the current API still satisfy the schema its consumers depend on, and does the current publishable document type still satisfy its subscribers? Run them in CI on every commit. They are the cheapest possible detection for the chapter 15 failure — a required field added to a published document type — and they catch it before the artifact is even built.

Running it in the pipeline

The build server is a plain Integration Server with Deployer — no Designer, no database — so unit, contract and integration tests can run against a disposable container with mocked edges. The vendor's own DevOps libraries publish sample project layouts and Jenkins pipeline definitions that orchestrate build, deploy and test steps; the shape is standard and there is no need to invent one.

Do not put a partner in your CI pipeline

An end-to-end suite that calls a partner's real test endpoint fails for reasons you do not control: their maintenance window, their expired test certificate, their data reset. The suite goes red for a week, the team learns to ignore red, and the pipeline stops being a gate. Keep partner round-trips in a separate scheduled suite with its own alerting, and keep the CI gate hermetic.

Test data management

Two properties make a suite maintainable. It must be self-seeding — each test creates what it needs and cleans up, because a suite that depends on a hand-curated database dies the first time someone reseeds it. And it must be independent of ordering, since a test that passes only after another test ran is a test that will fail in parallel CI and be marked flaky rather than fixed.

Failure scenario

Meridian's suite is 40 end-to-end tests and nothing else. A mapping change breaks the delivery date; 31 tests go red, each with a different symptom, and half a day goes into locating the one field. Worse, the suite takes 50 minutes, so developers stop running it before pushing. The 40 tests could have been 6 end-to-end plus 34 unit tests running in nine seconds — and the mapping bug would have named the exact field in the failure message.

Design review questions

  1. What proportion of your tests are end-to-end, and which of them could be unit tests?
  2. Do your mapping tests cover absent optionals, empty arrays and awkward characters — or only the sample document?
  3. Can you simulate a half-success? What happened last time you tried?
  4. Does anything in CI fail when a published document type gains a required field?
  5. How long does the suite take, and do developers run it before pushing? The second answer follows from the first.
  6. When an incident is closed, does its payload become a fixture?
