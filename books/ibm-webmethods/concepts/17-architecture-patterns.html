Integration architecture patterns

Four patterns cover almost everything, and the interesting question is never which is best. It is which one this flow needs, and whether your platform's actual constraints allow it.

API-led

Layer the estate: system APIs expose one source of record each and change only when it does; process APIs compose them into business operations; experience APIs shape the result for one consumer. Meridian's POST /v1/orders is an experience API over an order-management process API over ERP and stock system APIs.

It buys clean reuse and clear ownership. It costs latency — three layers means three hops, and chapter 8's arithmetic applies to every one of them — and it invites layers that exist only to satisfy the diagram. If a process API only ever calls one system API and adds nothing, delete it.

Event-driven

Producers state facts; consumers subscribe. Chapter 10 built this for Meridian, and the payoff was concrete: two subscribers added months later with no change to the publisher. The constraint to know up front is platform-specific — for native pub/sub you must use Broker or Universal Messaging, since there is no native API path for foreign messaging providers in that case. If your target architecture assumes Kafka as the backbone, that assumption needs a bridge, and the bridge needs an owner.

Hub-and-spoke versus domain-aligned

The classic hub is one integration platform, one team, every flow. It gives consistency and one place to look, and it becomes a queue: every project waits for the integration team, who become the bottleneck for changes they did not ask for and cannot prioritise.

Domain-aligned distributes ownership — order management owns the order flows, finance owns the finance flows — on shared, centrally governed infrastructure. It scales with the organisation, at the cost of needing real governance (chapter 18) rather than the informal consistency a single team provides for free.

Orchestration versus choreography

Orchestration puts one service in charge of the sequence: it is visible, debuggable and easy to explain, and it couples the orchestrator to every participant. Choreography lets each participant react to events with no central script: it decouples beautifully, and no single artifact describes the business process any more.

Orchestrate what the business would draw on a whiteboard. Choreograph the reactions hanging off it.

Meridian does exactly that. The order itself — validate, price, create in the ERP — is orchestrated, because it is one business transaction with a defined outcome and someone will ask why order 4471195 was rejected. Everything downstream — CRM update, fulfilment, analytics — is choreographed off OrderStatusChanged, because each is independent and none of them changes the order's outcome.

Ownership boundaries

Draw boundaries where the business does. A boundary that cuts across a business capability produces flows that need two teams to change, and those flows are the ones that never get changed. The platform gives you the menu — API management, application and data integration, event-driven messaging, B2B/EDI and managed file transfer under one control plane — but the boundaries are an organisational decision, and the platform will faithfully implement whichever ones you draw.

Failure scenario

A team choreographs the entire order process: seven services, each reacting to the previous one's event, no orchestrator. It is elegant and it deploys independently. Then an order stalls, and answering "why" means reconstructing the sequence from seven services' logs across four runtimes — there is no artifact that says what should have happened. The team adds a "process tracker" service to record progress, which is an orchestrator with worse ergonomics and no authority.

Design review questions

  1. Which of your process APIs would survive deletion? Delete those.
  2. Is your integration team a queue? Measure the wait, not the throughput.
  3. For your main business process: which artifact describes what should happen, and could you hand it to a new joiner?
  4. Does any flow need two teams to agree before it can change?
  5. If your target architecture assumes a foreign message broker, who owns the bridge?
