API design and API management

The fastest way to publish an API is to expose the flow service directly. Do that and your internal service signature becomes a public contract, changeable only by consensus with everyone who called it. The gateway exists so that the API and the implementation can move independently.

Design for the consumer, not the backend

Meridian's ERP models an order as a header IDoc plus line segments with a plant code, a distribution channel and a division. None of that is meaningful to the customer's procurement system. If those fields appear in the public API, you have published SAP's data model under your own brand, and every future ERP change becomes a customer-facing migration.

The API should be modelled on what the consumer is trying to do: submit an order, ask about its status, cancel it. Three resources, verbs that match HTTP semantics, and a payload that is Meridian's canonical order — not the ERP's.

Status codes are part of the contract

400 means the caller must change something before retrying. 409 means a conflicting state — a duplicate PO number with different contents. 422 means well-formed but rejected by a business rule. 503 plus Retry-After means come back later, and is the honest answer when the ERP is in its batch window. A blanket 500 teaches every client to retry things that will never succeed.

What the gateway does that your service should not

API Gateway provides a policy framework that programs API behaviour and implements management functions without writing code. That sentence is a division of labour: anything that is true of every API belongs in a policy, and anything specific to orders belongs in the flow service.

Authentication and authorization

Three tiers, and most estates need all three. API keys identify an application — cheap, revocable, and not a security boundary on their own. OAuth 2.0 with scoped access tokens is the default for anything a third party calls; the scope, not the key, is what authorizes the operation. Mutual TLS is for partners with an existing certificate relationship, which is exactly the B2B population of chapter 11.

The design question that matters more than the mechanism: does the token identify the application or the user? Meridian's procurement integration is application-to-application, so a client-credentials token identifying the customer's system is right, and the customer's own user identity is carried in the payload as data. Conflating the two produces an audit trail that cannot answer either question.

Rate limiting, quotas, and the arithmetic of nodes

Rate limiting in API Gateway is the Traffic Optimization policy: it limits the number of API invocations during a specified time interval, implemented with a token bucket algorithm. Token bucket matters because it permits bursts up to the bucket size while holding the long-run average — which is what you want for a procurement system that submits fifty orders at 09:00 and nothing until noon.

The limit multiplies by your node count

If a limit is enforced per gateway node and you run four nodes behind a load balancer, a "100 per minute" policy admits up to 400 per minute. Confirm whether your limits are counted locally or in shared state before you quote a number to a customer — and before you rely on one to protect a downstream system.

Versioning and lifecycle

Version in the path (/v1/) because it is visible in every log, cache key and support ticket. Then run versions in parallel: a new major version goes live while the old one keeps serving, consumers migrate individually, and the old version is retired only when its traffic is zero and you have said so three times. Deprecation needs a date, a header on every response, and a named human at each consumer — announcements to a mailing list do not migrate anyone.

The gateway's real product is not security or throttling. It is the ability to change the implementation without asking permission.

Failure scenario

Meridian exposes submitOrder straight through, so the API's payload is the ERP's IDoc structure. Two years later the ERP is upgraded and vbeln becomes 12 characters. Every customer integration must change on the same weekend, because there is no translation layer to absorb it. The mapping that would have prevented this is about forty lines and should have been written on day one — the gateway alone would not have saved them, because the schema, not the endpoint, was the leak.

Design review questions

  1. Could you replace your backend system tomorrow without changing the API contract? If not, where does it leak?
  2. Which of your gateway policies are per-node, and what is the effective limit at your current node count?
  3. Does each error class map to a distinct status code, or does everything become 500?
  4. For your oldest API version: how much traffic does it still carry, and who owns each remaining consumer?
  5. Do your tokens identify applications or users, and does your audit trail need both?
