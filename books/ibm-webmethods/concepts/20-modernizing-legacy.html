Modernizing legacy integrations

Most webMethods work is not greenfield. It is an estate built over fifteen years by people who have left, running interfaces nobody can fully explain, which the business depends on absolutely. Modernization is the discipline of changing that without an outage.

Assess before you plan

You cannot migrate what you have not inventoried, and the inventory is always worse than the wiki says. For every interface, establish six things: who calls it and how often (from logs, never from memory); what it touches; its business criticality; whether it has a test; whether anyone alive understands it; and its actual failure rate today.

That last one reorders priorities more often than anything else. An interface failing twice a week that someone quietly re-runs by hand is a bigger problem than an ugly one that has not failed in three years — and it is usually invisible until you go looking, because the person re-running it stopped mentioning it years ago.

Sort by usage and pain, not by age

High usage and high pain: fix first. High usage, low pain: leave alone — it is working. Low usage, high pain: consider retiring rather than migrating. Low usage, low pain: leave it until it stops one of the others. "Old" is not on either axis.

The strangler pattern, concretely

Never rewrite a legacy interface in one step. Put a facade in front of the old interface, route a slice of traffic to a new implementation, compare, and grow the slice. Four properties make this work in practice, and skipping any one of them is where these programmes fail:

  • The facade goes in first, changing nothing. Deploy it, route 100% to the old path, prove it is invisible. Now you have a switch.
  • Route by a business dimension — one partner, one order type, one region. "10% of traffic randomly" makes reconciliation impossible, because you cannot tell which system should have handled a given order.
  • Run both and compare during the parallel period. This is the whole safety mechanism.
  • The switch is instant and reversible, and someone has actually pressed it back once in staging.

Wrapping SOAP and file interfaces

The temptation is a REST facade that mirrors the SOAP operation field for field, because it is fast and it works. It is also how a legacy model becomes permanent and public: you have now published the old schema under a new URL, and every future change to the legacy system is a customer-facing migration (chapter 9's failure scenario, exactly).

Map to the canonical model instead, even when the mapping is initially trivial. That translation layer is what lets the legacy system be replaced later without the API changing — which is the entire point of the exercise. The same holds for a file interface: expose the business operation, not the file's field positions.

From batch to events

The classic legacy shape is a nightly extract: twelve hours of latency, and a rerun costs a day. Moving to near-real-time events is usually worth it, but do it in the same incremental way — and expect the hard part to be semantic rather than technical.

A nightly batch is a snapshot, and a snapshot has properties an event stream does not: it is complete, consistent as of a point in time, and naturally idempotent because you reload the whole thing. An event stream is incremental and at-least-once. Consumers that quietly relied on the snapshot's completeness — "if it is not in tonight's file, it was deleted" — break in ways that take weeks to attribute. Run both for a period and reconcile.

Modernizing the platform itself

Some of this is component swaps rather than redesign. The Broker-to-Universal-Messaging path is designed for exactly that: the publish service description is similar to the old Broker publish and existing triggers continue to work, so it is an in-place migration rather than a rewrite. Alongside webMethods, IBM's acquisition included EntireX and ApplinX — the mainframe and host-application integration components — so a mainframe-facing estate has a supported path rather than a rewrite obligation.

Above that sits the strategic direction: a hybrid multi-cloud platform under a unified control plane. Treat that as a destination to move toward interface by interface, using this chapter's method, rather than as a programme with a flag day.

Migration risk is not proportional to how much you move. It is proportional to how much you move at once.

Failure scenario

A team runs a strangler migration for a supplier feed with no reconciliation, on the reasonable-sounding grounds that both paths were tested. The new path silently drops line items with a zero quantity — the legacy path had passed them through, and a downstream report counted them as cancellations. Nobody notices for six weeks, because both systems are "working". Finance finds it during quarter-end. Reconciliation during the parallel run is not overhead; it is the only thing that distinguishes a migration from a hope.

Design review questions

  1. Which of your interfaces has the highest failure rate today — measured, not remembered?
  2. Which interfaces does someone re-run by hand, and how would you find out?
  3. For your current migration: what dimension routes traffic, and can you reconcile the two paths?
  4. Does your new REST facade expose the canonical model or the legacy schema?
  5. If you moved a batch feed to events, which consumers relied on the snapshot being complete?
  6. Has anyone pressed the rollback switch, in staging, once?
