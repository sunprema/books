Core concepts and vocabulary

webMethods has its own words for things you already know, and one thing you probably do not: the pipeline. Learn the pipeline properly and eighty per cent of the confusion evaporates, because almost every mysterious bug in a flow service is a pipeline bug.

Services and flow services

A service is the unit of executable work. It has a signature — declared inputs and outputs — and it lives at a namespace path such as meridian.order.pub:submitOrder. Services can be written in Java, but the characteristic webMethods service is a flow service: a program in the flow language, assembled from steps rather than typed as text.

A flow step is the basic unit of work in the flow language, which Integration Server interprets and executes at run time. There are seven you need, and only seven.

The one everybody gets wrong

REPEAT is not a loop over data. It repeats its children on success or on failure a bounded number of times — it is the retry construct. LOOP is the iterator. Reaching for REPEAT to walk an array produces a service that either runs once or runs forever, depending on which way you set it.

The pipeline

Here is the concept with no equivalent in most languages. The pipeline is a single shared document that flows through the service. Every step reads from it and writes into it. A step's "inputs" are simply the fields it picks up out of the pipeline; its "outputs" are the fields it drops back in.

This is enormously convenient and quietly dangerous. Convenient, because wiring two services together is often literally nothing — the field the first one produced is already there for the second. Dangerous, because nothing is scoped. A field set on line 3 is still sitting in the pipeline on line 40, visible to every step in between, copied into the audit log, and held in memory for the life of the request.

Treat the pipeline as a public surface. If you would not log a field, drop it before the step that logs.

Document types, packages, adapters

An IS document type is a named structure — the platform's schema. It defines the shape of a document flowing through services, and it is what gives a mapping something to validate against. A document type can be marked publishable by setting its publishable property to true, which is what allows instances of it to be published to the messaging provider; that single boolean is the boundary between an internal structure and a contract other systems subscribe to.

A package is the unit of deployment and the unit of reuse. Integration Server looks under its packages folder for every available package; inside one, the ns folder holds the namespace tree, with a directory per folder and per service, each carrying its node definition file. Packages are how you draw ownership boundaries, and chapter 18 argues that this is the most consequential design decision in the whole estate.

An adapter is a configured connection to an external system plus generated services over it. An adapter notification is the inbound direction: the adapter detecting that something changed out there. A trigger subscribes a service to published documents. Those five nouns — service, pipeline, document type, package, adapter — cover most conversations.

Synchronous, asynchronous, and delivery

Synchronous means the caller holds a connection until the answer arrives, and therefore the caller's timeout is part of your design. Asynchronous means it does not, and therefore something else must carry the guarantee. In webMethods that something is usually guaranteed delivery, and it is logged separately — Integration Server keeps a dedicated guaranteed-delivery log alongside its server, session, error, service, security and document logs.

Idempotency, correlation, delivery — the three you must decide early
  • Correlation ID. Accept one from the caller; only generate one if there is none. A trace that begins at your edge cannot explain what happened before it.
  • Idempotency key. The customer's purchase order number is usually the natural key. Store it, check it, and make re-processing a no-op that returns the original answer.
  • Delivery guarantee. Guaranteed delivery is at-least-once. That is not a bug to work around; it is the contract. It is only safe because the consumer is idempotent — and if the consumer is not, the guarantee is actively harmful.
Failure scenario

Meridian's order service is deployed without an idempotency key. A customer's procurement system times out after 30 seconds and retries; the original call had already succeeded at 31 seconds. Two sales orders are now in the ERP for one customer PO. Nothing logged an error, because nothing was an error. The duplicate is found by the customer, at invoicing, three weeks later.

Design review questions

  1. In your busiest flow service, which pipeline fields survive to the last step, and which of them contain personal or secret data?
  2. Which of your document types are publishable, and can you name every subscriber to each?
  3. What is the natural idempotency key for your main business document — and is anything actually enforcing it?
  4. Where does your correlation ID come from: the caller, or your own edge?
