Your first integration service

We build submitOrder: an HTTP request in, a validated canonical order, a sales order in the ERP, a response out. It is about forty steps of real work and it is the skeleton every later chapter hangs something on.

What happens before your first step runs

Integration Server decodes the client request, identifies the requested service, invokes it, passes data to it in the expected format, and returns the output to the client. Your flow service is the middle of that sentence. Two consequences matter immediately: the transport has already been handled by the time you get control, and whatever you leave in the pipeline at the end is what the caller receives.

Start with the signature

Design the interface before the implementation, because the signature is the part you cannot change later without breaking someone. For Meridian's order intake:

meridian.order.pub:submitOrder — signature

Input
  order            CanonicalOrder   # document reference, not a loose string
  correlationId    String          # accepted from the caller

Output
  orderStatus      String          # ACCEPTED | REJECTED
  salesOrderNumber String          # ERP key, absent when rejected
  errors           String[]        # populated only on REJECTED
Two decisions hidden in six lines

The input is a document reference, so validation has something to check against and Designer can generate the mapping. And rejection is a normal output value, not an exception — a business rejection is a legitimate answer to a well-formed request, and modelling it as a thrown error means the caller sees a 500 for their own typo.

The guided build

Six moves, in order. The order matters: everything that can reject the request happens before anything that changes the world.

meridian.order.pub:submitOrder — flow

1 MAP     # establish the correlation id
     BRANCH on '/correlationId'
       $null: INVOKE meridian.order.util:buildCorrelationId

2 INVOKE  pub.schema:validate
     # object = /order, conformsTo = meridian.order.doc:CanonicalOrder
     BRANCH on '/isValid'
       "false": MAP -> orderStatus = "REJECTED", errors = /errors
                EXIT from '$flow' signal SUCCESS

3 INVOKE  meridian.order.impl:checkDuplicate
     # idempotency: has this customerPoNumber been seen?
     BRANCH on '/isDuplicate'
       "true":  MAP -> orderStatus = "ACCEPTED",
                       salesOrderNumber = /existingSalesOrder
                EXIT from '$flow' signal SUCCESS

4 INVOKE  meridian.order.impl:validateOrder    # business rules
     BRANCH on '/ruleFailures'
       $default: (non-empty) reject as in step 2

5 SEQUENCE (exit on: FAILURE)                 # the side effect
     INVOKE meridian.erp.adapter:createSalesOrder
     INVOKE meridian.order.impl:recordIdempotencyKey

6 MAP     # shape the reply AND drop everything else
     orderStatus      = "ACCEPTED"
     salesOrderNumber = /erpResponse/vbeln
     # drop: order, erpResponse, isValid, isDuplicate, ruleFailures

Mapping is where the bugs live

MAP looks like the boring step. It is where most defects originate, for one reason: the pipeline is permissive. Map a field name with a typo and nothing errors — the target is simply absent, the downstream system receives a null, and the order goes through with no delivery date. Three habits prevent almost all of it:

  • Validate against a document type rather than trusting the shape. pub.schema:validate against CanonicalOrder turns a silent null into a loud rejection.
  • Drop as you go. Every MAP that finishes a phase should drop the inputs that phase consumed. The pipeline at the reply step should contain the reply and nothing else.
  • Never map a field you have not seen a real example of. The ERP's vbeln is a sales order number; it is also ten characters, zero-padded, and your String will happily carry "0000123456" into a system that expected 123456.

Testing it before it exists anywhere else

Run the service in Designer with a sample pipeline. Then run it three more times: once with a required field missing, once with the same customerPoNumber twice, and once with the ERP adapter pointed at a host that refuses connections. Those three are the tests that matter, and all three should produce a defined answer rather than a stack trace reaching the caller.

Failure scenario

Step 5 succeeds in the ERP, then recordIdempotencyKey fails because the database connection pool is exhausted. The SEQUENCE exits on failure and the caller sees an error — so the customer's system retries, the duplicate check finds no key, and a second sales order is created. The lesson is uncomfortable and worth sitting with: the idempotency record must be written in the same transaction as the side effect, or the side effect must be made naturally idempotent by passing the customer PO number to the ERP as its own external reference. Chapter 8 chooses the second.

Design review questions

  1. Is every rejecting check ahead of every side effect in your flow?
  2. What is in the pipeline at your final MAP, and would you be happy to see all of it in a log?
  3. Is a business rejection modelled as an output value or as a thrown error — and which does the caller's client library do something sensible with?
  4. If the step after your side effect fails, what does a retry from the caller do?
