Flow-service design patterns

Flow has seven steps and no functions, no exceptions and no scopes. Everything structural you want — try/catch, guard clauses, layering — has to be built from SEQUENCE, BRANCH and discipline. Here is the small set of shapes that covers nearly everything.

Try/catch, built from two SEQUENCEs

This is the one idiom you cannot work without. Nest two SEQUENCE blocks inside an outer one and set their exit conditions in opposition: the first exits on FAILURE, the second on DONE. If the try block fails, control falls to the catch block; if it succeeds, the catch block is skipped.

The try/catch idiom

SEQUENCE (exit on: DONE)              # outer scope
  SEQUENCE (exit on: FAILURE)         # --- try ---
    INVOKE meridian.erp.adapter:createSalesOrder
    INVOKE meridian.order.impl:publishAccepted
    EXIT from '$parent' signal SUCCESS  # skip the catch
  SEQUENCE (exit on: DONE)            # --- catch ---
    INVOKE pub.flow:getLastError
    INVOKE meridian.order.impl:classifyFailure
    INVOKE meridian.order.impl:compensate

Two details make the difference between this working and this being a trap. First, pub.flow:getLastError must be the first step of the catch block — anything before it can overwrite the error you were about to inspect. Second, the explicit EXIT at the end of the try block is what stops a successful path from running the catch; without it you get compensation on every happy request, which is a genuinely alarming thing to discover in production.

EXIT scope is the whole game

EXIT stops execution and its scope can be the immediate parent, the closest loop, or the entire flow service. Choosing $parent when you meant $flow silently continues into steps you thought you had skipped. Read the scope on every EXIT in review; it is the flow equivalent of a missing break.

BRANCH: order is semantics

BRANCH evaluates the expression in the Label property of each child step and executes the first child whose expression evaluates to true. "First" is doing real work in that sentence: reordering the children changes behaviour. Treat a branch's child order the way you would treat the order of if/else if.

And always give it a $default. A BRANCH with no matching label and no default does nothing at all — no error, no log line, no clue. The document is simply dropped, and you find out when someone downstream asks why they got fourteen of the fifteen orders.

Three layers, and why they pay

Give every flow service exactly one of three jobs. The discipline sounds bureaucratic until the first time you need to reuse pricing logic in a batch job that has no HTTP request anywhere near it.

Service layers
LayerJobMay doMay not
InterfaceSpeak the protocolParse, shape the reply, set HTTP statusContain business rules
OrchestrationSequence the workCall services, branch, compensateCompute anything
Business / resourceDo one thingPrice, validate, call one adapterKnow about HTTP or the caller

If a service both decides what happens and computes how much, it can be reused by nothing and tested only end to end.

Designing stable interfaces

A service's signature is a contract with everyone who invokes it, and in a shared namespace you often cannot enumerate them. Three rules keep signatures survivable: take a document, not fifteen scalars, so adding a field is additive; never repurpose an existing field's meaning, even when the name still fits; and make new fields optional with a defined behaviour when absent. If you must break a contract, publish a new service beside the old one and migrate consumers — version in the namespace, not in a flag.

Anti-patterns worth naming

  • The 200-step service. If it does not fit on a screen, it cannot be reviewed, retried in parts, or reasoned about. Extract by phase.
  • Pipeline as global state. Two services communicating through a field neither one declares. It works until someone reorders steps.
  • REPEAT as a loop. Covered in chapter 3; still the most common single error.
  • Swallowed errors. A catch block that logs and continues, leaving the caller with orderStatus unset and a 200 response. Either handle it or rethrow.
  • Copy-paste reuse. A mapping duplicated in six services because extracting it felt like overhead. The sixth copy is discovered when a field changes and five of them are updated.
Failure scenario

An outer SEQUENCE is set to exit on FAILURE instead of DONE. The try block fails, the catch block runs and successfully compensates — and then the outer sequence, seeing that a child failed, propagates the failure anyway. The caller gets an error for an order that was correctly rolled back, retries it, and creates the duplicate that compensation had just cleaned up. Exit conditions are not decoration; walk them explicitly in review.

Design review questions

  1. Does every BRANCH in your codebase have a $default, and does the default do something visible?
  2. Is getLastError the first step of every catch block?
  3. Pick your three largest services. Which layer is each one in — and does any of them span two?
  4. Which mapping logic exists in more than one place, and what would it take to extract it today?
