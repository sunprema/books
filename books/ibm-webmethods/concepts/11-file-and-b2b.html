File and B2B integration

Meridian's supplier will not call an API. They will drop an EDI 855 acknowledgement on an SFTP server at 04:00, sometimes twice, occasionally half-written, and once a quarter with last week's control number. This is not a legacy edge case — it is how a large share of real commerce moves.

A file is not arrived when it appears

The single most common file-integration bug: a poller sees a filename and starts reading while the partner is still writing it. You process 60% of an acknowledgement file, mark it done, and lose the rest permanently. There are three fixes and you should insist on one of them contractually, at onboarding:

  • Write-then-rename. The partner writes ack.tmp and renames to ack.edi; rename is atomic on a POSIX filesystem, so the file only appears complete.
  • Sentinel file. The payload lands, then a zero-byte ack.done. You poll for the sentinel, never the payload.
  • Size-stable check. Weakest but sometimes the only option: read the size twice, thirty seconds apart, and act only if unchanged. It fails on a slow link with a long stall.

ActiveTransfer: the point is subtraction

ActiveTransfer is the managed file transfer component: protected internal and external transfers in a centralized system covering B2B, A2A, cloud-based and ad-hoc use. Its value is best understood as removal — it exists to eliminate transmissions scattered across dozens of separate file transfer servers, each with its own credential set, its own cron job, and no shared monitoring.

The architectural consequence is what matters: with MFT centralized, "did the file arrive?" has exactly one place to look, credentials rotate in one place, and a new partner is a configuration change rather than a new server. If your answer to "where do partner files land" names more than one system, that is the problem to fix before anything else in this chapter.

Trading Networks: identity before content

Trading Networks streamlines B2B by managing partner profiles, document types and transaction protocols. Its model is worth learning in the right order, because the order is the processing order.

A partner profile holds the descriptive information about a trading partner — name, address, contacts, external ID numbers such as DUNS or GSID, and a classification such as Customer or Supplier. A profile is required to process any transaction, because it defines the partner's identity, roles and processing rules. Identity comes first: an unrecognized sender is not a document you can process.

A TN document type is what recognizes the type of a submitted document, inbound or outbound. Trading Networks ships predefined types for the common EDI standards — EANCOM, ODETTE, TRADACOMS, UNEDIFACT, VDA, and X12 with its UCS and VICS variants — and can validate document structure for EDI, XML and flat files.

A processing rule then says what to do. Processing proceeds as rule selection based on defined criteria, then pre-processing actions defined in the TN document type and/or the rule, then the rule's own processing actions — and a processing-rule action can execute a service you write, either synchronously or asynchronously.

Onboarding a partner

The mechanical steps are quick; the agreements are what take six weeks. Capture them explicitly, because every one of these becomes an incident if left implicit: which external ID scheme identifies them (DUNS, GSID, a mutually agreed code), which transaction sets in which version, the transport and its credentials, the acknowledgement expectation (a 997 functional acknowledgement, and by when), the file naming and completeness convention from earlier in this chapter, and who to phone at 03:00.

Never onboard by copying a profile

Copying an existing partner profile and editing it is the standard shortcut and a reliable source of cross-partner leakage: external IDs and processing rules are exactly the fields that must not be shared, and they are the easiest to miss. Build from the template, not from a neighbour.

Duplicates, partials, and late arrivals

B2B reliability is mostly about three failure modes, and each has a standard defence.

The three that will happen
FailureLooks likeDefence
Duplicate fileThe same interchange control number twicePersist control numbers; treat a repeat as a no-op and alert
Partial fileTruncated final segment, or a short countAtomic arrival convention; validate the trailer's segment count
Late arrivalNothing at all, quietlyAn expectation window per partner, and an alarm on absence

Alert on the file that did not arrive. Every monitoring system watches for errors; almost none watch for silence.

Failure scenario

The supplier's system is restored from a backup and re-sends Tuesday's acknowledgement file on Thursday, with its original control numbers. Meridian has no duplicate check, so 340 order lines are acknowledged twice; the reconciliation job sees the second acknowledgement as a new confirmation and releases 340 duplicate shipments. The control number was in the file the whole time. Persisting it and rejecting a repeat is perhaps twenty lines of work, and it is the difference between a logged no-op and a warehouse incident.

Design review questions

  1. How does each inbound file signal that it is complete — and is that written into the partner agreement?
  2. Do you persist interchange control numbers, and what happens on a repeat?
  3. Which partner feeds have an expected arrival window, and which of those alarm on absence?
  4. How many places do partner files land today? What would it take to make that one?
  5. For your newest partner: was the profile built from a template or copied from another partner?
