Deployment, configuration, and environment promotion

One rule carries this chapter: the artifact that reaches production must be the same bytes that passed test, with only injected configuration differing. Everything else here is machinery for keeping that rule true.

The documented path

It is pleasantly conventional. Projects are stored in a version control system, built by webMethods Asset Build Environment, and the resulting artifacts are deployed to the target environment. The build server needs only a plain Integration Server with Deployer — no Designer, no database connection — which means it is small, disposable, and reproducible in CI.

Note what that excludes. Exporting packages from a running development server is not a build; it captures whatever happened to be on that server, including someone's half-finished edit, and it has no revision you can return to. Command Central has its place for provisioning and administration, but it is not regarded as a suitable deployment mechanism for CI/CD — it adds complexity and risk there with no offsetting benefit.

Externalizing configuration

Chapter 4 drew the line: the package's ns tree is source, and the Integration Server config folder's per-product .cnf files are environment. Promotion is where that line pays. Anything that differs between environments — hostnames, ports, pool sizes, timeouts, credential aliases, partner endpoints, feature flags — lives in a configuration repository, versioned per environment, and is injected at deploy time.

A test that catches most of it

Take the artifact built for production and deploy it to test. If it works with only test's configuration, the separation holds. If anything needs rebuilding, editing or hand-adjusting, you have environment data baked into the package — and you have just found it before an audit did.

Production—Real

Staging earns its cost only if it is genuinely production-like in the dimensions that break things: same component versions, same pool sizes, realistic data volume, and the same TLS and authentication path. A staging environment with a 5-connection pool and 200 test records proves nothing about a 20-connection pool under 12,000 orders a day — and it gives false confidence, which is worse than having no staging at all.

Rollback, and the parts that do not roll back

Redeploying the previous artifact is the easy half. The hard half is everything the deployment touched that is not code:

  • Database schema. Make every migration additive and backward-compatible for one release, so version n−1 still runs against the new schema. Then a rollback is genuinely just the artifact.
  • Published document types. An added optional field is fine; a removed field breaks consumers that already saw it, and rolling back does not un-break them.
  • Messages in flight. Messages published by the new version may be sitting in a queue when you roll back. The old consumer must tolerate them — which is chapter 7's additive-only rule, again.
  • Partner-facing changes. You cannot roll back a document you have already sent a supplier.

A deployment is reversible only if every irreversible thing it touched was made backward-compatible first.

A release checklist for integration changes

  1. Which document types changed, and is every change additive?
  2. Which downstream systems see new or different traffic, and have their owners been told?
  3. Is the schema migration backward-compatible with the current release?
  4. What is the rollback procedure, and has it been executed — not just written — in staging?
  5. What in-flight work exists at deploy time (queued messages, running guaranteed-delivery transactions, open files), and what happens to it?
  6. Which configuration values are new, and are they set in every environment including production?
  7. What is the first metric that would show this going wrong, and who is watching it for the next hour?
Failure scenario

A release adds a required field to a publishable document type. It passes test, because test's publisher and subscriber were deployed together. In production the publisher deploys first; for four minutes it emits documents the not-yet-updated subscriber rejects, and those messages exhaust their retries into the dead-letter queue. The rollback restores the publisher — and the 900 dead-lettered messages stay dead-lettered, because rollback does not replay. Additive-only is not pedantry; it is what makes the rolling window between two deploys survivable.

Design review questions

  1. Is the production artifact the same bytes that passed test? Can you prove it from the build record?
  2. Deploy the production artifact to test with test's configuration. Does anything need changing?
  3. In which dimensions does staging differ from production, and which of those matter?
  4. When did you last execute a rollback rather than document one?
  5. What happens to in-flight messages during a deploy?
