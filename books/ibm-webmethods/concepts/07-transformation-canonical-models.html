Data transformation and canonical models

Six systems, six ideas of what an order is. The canonical model is how you avoid writing thirty transformations instead of twelve — and it is also the single artifact most likely to rot into a union of everything, at which point it has made things worse.

The arithmetic

Point-to-point transformation between n formats needs up to n(n−1) mappings — six formats, thirty mappings. Route everything through one canonical model and you need 2n: six in, six out, twelve. The saving is real but it is not the main prize. The main prize is that the canonical model is where meaning is decided once: what a quantity means, which currency, whether a cancelled line is absent or present with zero quantity.

Document types are the schema

In webMethods the canonical model is expressed as IS document types. A document type defines the structure data takes as it flows through services, and setting its publishable property to true is what allows instances to be published to the messaging provider. That property is the line between "a structure my package uses" and "a contract other teams depend on" — treat flipping it to true as a governance event, not a checkbox.

meridian.order.doc:CanonicalOrder

CanonicalOrder
  header
    customerPoNumber   String    # required — the idempotency key
    customerId         String    # required — Meridian's id, not the partner's
    orderDate          String    # required — ISO 8601, always UTC
    currency           String    # required — ISO 4217, never inferred
    requestedDelivery  String    # optional — absent means "as soon as possible"
  lines[]
    lineNumber         String    # required — stable across amendments
    sku                String    # required — Meridian catalogue id
    quantity           String    # required — decimal string, never float
    unitOfMeasure      String    # required — UN/CEFACT code
    unitPrice          String    # optional — absent means "price it for me"
  source
    channel            String    # API | EDI | PORTAL
    receivedAt         String
    correlationId      String
Every "optional" is a decision you have written down

Notice that each optional field states what absence means. That is the difference between a schema and a contract. "Optional" with no stated default is how two teams end up implementing opposite behaviours from the same document type, both correctly.

The formats you will actually meet

JSON and XML are the easy half. The hard half is everything with positional meaning. Trading Networks can validate document structure for EDI, XML and flat-file formats, and it ships predefined document types for the common EDI standards — EANCOM, ODETTE, TRADACOMS, UNEDIFACT, VDA and X12 with its UCS and VICS variants. That inventory is worth knowing before someone proposes writing an X12 parser.

Carry decimals as strings

Every quantity and price in CanonicalOrder is a String, deliberately. A float round-trip through JSON turns 0.1 + 0.2 into a support ticket, and an EDI implied-decimal field (N2: 1250 means 12.50) has to be scaled at the boundary, once, where the qualifier is still in scope. Parse to a decimal type only inside the service that does arithmetic.

Versioning without breaking consumers

The rule is asymmetric and worth stating baldly: adding an optional field is safe; everything else is a new version. Making an existing field required breaks every producer that omitted it. Removing a field breaks every consumer that read it. Narrowing a value set — dropping CONTRACT from orderType — breaks a producer you may not know about.

When you do need a breaking change, run both. Publish CanonicalOrderV2 beside CanonicalOrder, have the intake service produce both for a migration window, move consumers one at a time, and delete the old one only when the subscriber list is empty and you can prove it. The cost of running two document types for a quarter is small; the cost of a coordinated flag day across six teams is not.

A canonical model that changes whenever a source system changes has become a union of every schema it was supposed to insulate you from.

Keeping it canonical

The failure mode is gradual and always looks reasonable at each step. The ERP needs a plant code, so a plant code goes into the canonical order. The CRM needs a campaign id, so that goes in too. Six months later the canonical order has forty fields, thirty of which are meaningful to exactly one system, and every one of them has to be threaded through every mapping.

Two guards. First, a field belongs in the canonical model only if at least two systems have a shared meaning for it; single-system fields belong in that system's own mapping, derived at the edge. Second, the model is owned by the domain that owns the data — order management owns CanonicalOrder — not by the integration team, who otherwise become a queue that every schema change waits in.

Failure scenario

A partner's EDI 850 carries quantity as an N0 implied-decimal element in one segment and a plain integer in another. The mapping treats both the same. For eighteen months every order is correct, because the partner only ever uses the first segment — then they upgrade their system, start populating the second, and Meridian ships 1,000 units of an instrument where 10 were ordered. The structural validator passed the document every time: both were valid integers. Only a semantic check — quantity against a plausible range for the SKU — would have caught it.

Design review questions

  1. For each field in your canonical model, which two or more systems share its meaning? Delete the ones where the answer is "one".
  2. Does every optional field document what absence means?
  3. Who owns the canonical model — a business domain, or the integration team's backlog?
  4. Where are decimals parsed, and how many times does a price change representation between the customer and the ERP?
  5. What is your migration plan for a breaking change, and have you rehearsed it once?
