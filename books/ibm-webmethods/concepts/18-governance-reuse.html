Governance, standards, and reuse

Governance written as a document decays within two releases. Governance written as a pipeline check survives, because it is the only kind that says no at the moment someone is doing the thing.

Packages are the governance unit

Chapter 4's convention becomes policy here. Name the package's root folder exactly like the package, and treat the Services and Documents folders as its public API — the resources other packages and external consumers may bind to. Everything else is private and refactorable.

That single line drawn well is worth more than any amount of naming standard. It means a team can change its internals without a cross-team negotiation, and it means the surface you must govern is small enough to actually review.

Make it a build check

A script that walks the ns trees, finds every cross-package invoke, and fails the build when the target is outside a pub folder. That is perhaps a day's work and it enforces the boundary forever — where a wiki page enforces it until the next deadline.

The "common" package trap

Every estate grows a CommonUtils that everything depends on and nobody owns. It starts as three date helpers. Two years later it holds business logic for four domains, and it cannot be changed — any change requires regression-testing every consumer, so instead people add to it, and it grows monotonically forever.

Prevention is unglamorous: give every shared package a named owning team, cap it at genuinely generic utilities with no business meaning, and version it so consumers can upgrade on their own schedule. If a "common" package contains the word "order", it is not common.

A shared component with no owner is not reuse. It is a dependency everyone has and nobody can change.

The standards worth having

Keep the list short enough that people remember it. Six is about the limit:

Six standards, and how each is enforced
StandardEnforced by
Cross-package invokes target pub onlyBuild check
Every BRANCH has a $defaultBuild check
No credentials or hostnames in packagesBuild check / secret scan
Published document types change additivelyContract test (chapter 16)
Every service documents its signatureCode review
Naming: <domain>.<entity>.<layer>:<verbNoun>Code review

Note the split: four of six are mechanical and belong in the pipeline; two need judgement and belong in review. A standard that is neither checkable nor reviewable is a preference, and calling it a standard just erodes the others.

API lifecycle governance

API Gateway's policy framework is where cross-cutting API governance is applied without code, which makes it the natural enforcement point: a standard policy set every published API inherits — authentication, threat protection, quota defaults, logging — so compliance is the default state rather than an audit finding. Around that, the lifecycle needs three things: a catalogue where an API can be found before someone rebuilds it, a review gate before first publication, and a deprecation process with dates and named owners rather than announcements.

Data ownership

Chapter 7 said the canonical model must be owned by the domain that owns the data, and it is worth repeating as governance. When the integration team owns CanonicalOrder, every schema change queues behind their backlog and the model drifts toward whatever is easiest to map. When order management owns it, the model reflects the business, and the integration team's job is to enforce the change process rather than to arbitrate meaning.

A centre of excellence that helps

The failure mode is a CoE that reviews every change, which is chapter 17's hub bottleneck wearing a governance badge. The version that works owns the platform, the pipeline checks, the templates and the shared runtime — and delegates the flows. Measure it on whether teams ship faster with it than without it. If the answer is no, it has become an approval queue, whatever the org chart says.

Failure scenario

A naming standard is published in a wiki and, for a year, followed. Then a deadline lands, an exception is granted, and the exception is never revisited. Within two releases the standard describes about half the codebase, so new joiners cannot tell which half is authoritative and copy whichever they find first. The standard is now actively harmful: it produces inconsistency with the appearance of a rule. Enforce it mechanically or retire it honestly — a half-followed standard is worse than none.

Design review questions

  1. How many of your standards are enforced by a pipeline check? The rest are preferences.
  2. Who owns your shared package, and when did they last decline a contribution?
  3. Can a developer find an existing API before building a second one?
  4. Who owns each canonical document type — a business domain, or the integration backlog?
  5. Does your CoE make teams faster, or is it an approval queue? Ask the teams, not the CoE.
