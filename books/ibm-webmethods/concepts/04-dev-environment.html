04

Setting up a productive development environment

The simplest setup that works is one shared development server everyone logs into. It works for a week. Then two developers edit the same service, one overwrites the other, and nobody can say what production is running. This chapter is about building the setup that survives contact with a second developer.

Why the shared server fails

Integration Server has a single global namespace. A service at meridian.order.pub:submitOrder exists exactly once per server. There is no branch, no working copy, no local edit — when you save in Designer, you have changed the running server for everybody connected to it. That is the bottleneck, and every good webMethods setup is a response to it.

The answer is one Integration Server per developer — local, containerized, whatever is cheap — with git as the only shared truth. Developers edit locally, commit the package sources, and a build pipeline turns those sources into deployable artifacts. The shared development server, if you keep one, becomes an integration target that is deployed to, never edited.

What lives on disk, and what belongs in git

Integration Server looks under its packages folder for all available packages, and each package has a defined internal structure. Inside a package, the ns folder holds the whole namespace you see in Designer: every folder and every service gets its own directory, each carrying its node definition file. That tree is your source code.

Configuration is a different animal. It lives under the Integration Server config folder as per-product .cnf files, and it describes this environment — which database, which host, which credential alias. Confusing the two is the single most common setup mistake.

A package layout that ages well

The convention that holds up: name the package's root folder exactly like the package, and treat the Services and Documents folders as the package's public API — the resources other packages and external consumers are allowed to bind to. Everything else is internal and may be refactored freely.

That distinction is worth being pedantic about, because it is the only thing standing between you and an estate where every service is load-bearing. Concretely, for Meridian:

Package layout

MeridianOrder/
  ns/meridian/order/
    pub/          # public: other packages may invoke these
      submitOrder
      getOrderStatus
    doc/          # public: the document types they exchange
      CanonicalOrder
      OrderStatusEvent
    # --- everything below is private ---
    impl/
      validateOrder
      priceOrder
    map/
      customerOrderToCanonical
    util/
      buildCorrelationId
The rule that pays for itself

A service outside pub may never be invoked from another package. Enforce it in code review now, and in the build pipeline later (chapter 21). Without it, the refactor you need in year two touches forty consumers you did not know existed.

Configuration, secrets and certificates

Three categories, three different homes. Environment configuration — hostnames, pool sizes, timeouts — is injected at deploy time and belongs in a config repository, versioned separately per environment. Secrets — passwords, API keys, private keys — go into a credential store or secrets manager and are referenced by alias; the alias name is the only thing that appears in a package. Certificates live in truststores and keystores, and every one of them needs an owner and an expiry alarm.

If a value differs between environments, it is configuration. If it would embarrass you in a git history, it is a secret. Never let either one into a package.

The build server

Documented and pleasantly minimal: for continuous integration, projects are stored in a version control system, built by webMethods Asset Build Environment, and the resulting artifacts are deployed. A build server needs only a plain Integration Server with Deployer — no Designer, no database connection. That means the build image is small, disposable and easy to run in CI, which is exactly what you want.

Set this up on day one, before there is anything to build. A team that adds CI in month six has to first untangle six months of hand-edits on a shared server, and that untangling is the expensive part.

Failure scenario

Two developers work on the shared dev server. One adds a field to CanonicalOrder; the other, mid-test, sees their mapping start failing with an error in a service they never touched. Half a day goes into debugging a change that was never theirs. There is no diff to look at, because there is no commit — the shared server is the working copy. This is not a discipline problem; it is an architecture problem, and the fix is one server per developer.

Design review questions

  1. Can a developer make and revert a change without affecting anyone else? If not, that is your first fix.
  2. Is the deployed artifact byte-identical across environments, with only injected configuration differing?
  3. Can you name every service outside a pub folder that is invoked from another package?
  4. Who owns each certificate in your truststore, and what alerts when one is 30 days from expiry?
  5. If your shared dev server were deleted right now, could you rebuild it from git alone?
