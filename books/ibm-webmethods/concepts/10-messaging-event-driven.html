Messaging and event-driven integration

Chapter 1 left an unsolved problem: 480 CRM notifications a minute against a 100-call budget. The answer is not a bigger budget. It is to stop calling the CRM from the order flow at all, and this chapter is the machinery for that.

Queues, topics, and when to use neither

A queue has one logical consumer: work is handed to exactly one worker, and the queue is a buffer that decouples arrival rate from processing rate. A topic has many independent subscribers, each getting its own copy, none knowing about the others. The distinction is not about technology; it is about whether adding a consumer changes anyone's behaviour.

And use neither when a caller is blocked on the answer. A synchronous request wearing a queue's clothes — publish, then poll for a reply — is a distributed system with all the latency of messaging and all the coupling of RPC.

Universal Messaging

Universal Messaging is the platform's message-oriented middleware, providing guaranteed delivery and message persistence. It is the designated successor to webMethods Broker, and the documented migration is deliberately undramatic: the publish service description is similar to the old Broker publish, and existing triggers continue to work. One thing to know before designing around a third-party broker: for native pub/sub you must use Broker or Universal Messaging — there is no native API path for foreign messaging providers in that case.

On the Integration Server side the pieces are: a publishable document type (chapter 3's boolean), a publish step, and a trigger that subscribes a service to documents of that type. Guaranteed delivery is logged in its own place — Integration Server keeps a dedicated guaranteed-delivery log, viewable in the administrator under Logs > Guaranteed Delivery.

Commands and events are not the same thing

This is the modelling decision that determines whether your architecture ages well. A command names an intended action and has exactly one rightful handler: ReserveStock. An event states something that already happened and is addressed to nobody: OrderAccepted. Commands are imperative, present tense, and coupled by design. Events are past tense, and the producer must not care who listens.

If adding a second subscriber requires the publisher to change, you published a command and called it an event.

Solving the CRM problem

Meridian's order flow publishes one event, OrderStatusChanged, and stops caring. The CRM notifier becomes a subscriber that accumulates events and pushes a batched update — 480 events a minute become well under 100 calls, and the order flow's latency no longer includes the CRM at all. Crucially, the fulfilment service and the analytics feed can subscribe later without anyone touching submitOrder.

Consumer failure, replay and dead letters

Guaranteed delivery is at-least-once. Say that out loud, because it is a contract with consequences: your subscriber will occasionally see the same event twice, and the platform is behaving correctly when it does. An idempotent consumer makes this a non-event. A consumer that increments a counter turns it into a data-quality incident.

Three mechanisms handle the rest. Retry with backoff for transient failures — bounded, because an unbounded retry on a poison message blocks everything behind it. A dead-letter destination for messages that have exhausted their retries, so the queue drains and the bad message is preserved for a human. Replay from the persistent store when a subscriber has a bug and needs to reprocess a window — which only works if the consumer is idempotent, which is the same requirement again.

Ordering is narrower than people assume

Even where a provider preserves order within a destination, that guarantee usually dissolves the moment you add a second consumer instance for throughput. If ordering matters — and for order-status transitions it does — partition by a key such as customerPoNumber so all events for one order go to one consumer, or carry a sequence number and let the consumer reject anything it has already passed.

Failure scenario

Meridian publishes OrderAccepted immediately before calling the ERP, because it reads better in the flow. The ERP call fails and the order is rejected — but the event is already out, the CRM has told the salesperson the order is confirmed, and analytics has counted revenue that will never arrive. Events describe things that have happened. Publish after the commit, never before. If you cannot publish after the commit atomically, write the event to the same database in the same transaction and have a relay publish it — the transactional outbox is the standard answer and it is worth the extra table.

Design review questions

  1. For each published message: is it a fact that happened, or an instruction? Does its name agree?
  2. What does your consumer do if it receives the same message twice? Have you tested that, or assumed it?
  3. Where do exhausted messages go, and who looks there?
  4. Is anything published before the transaction that makes it true has committed?
  5. If you needed to replay yesterday's events, could you — and what would break?
