Error handling, recovery, and resilience

Almost every bad retry policy comes from one omission: nobody classified the failure first. Retrying a validation error is pure waste; not retrying a connection reset is a lost order. The classification is the design.

Three kinds of failure

The error taxonomy that drives everything else
ClassExamplesRetry?Goes to

Business failures are not errors in the operational sense at all: the system worked perfectly and the answer is no. Model them as output values (chapter 5), route them to the requester, and keep them out of the error log — an error log full of credit-limit rejections is an error log nobody reads.

Classify once, at the boundary

Write one classifyFailure service that turns the raw error from pub.flow:getLastError into a class. Every catch block calls it, and every retry decision reads its output. Scattering the judgement across forty catch blocks guarantees forty different opinions about whether a socket timeout is retryable.

Retry, properly

Flow's built-in retry primitive is REPEAT, which executes its children one or more times and can be set to repeat on SUCCESS or on FAILURE. Repeat-on-FAILURE with a count and an interval is your retry loop. Four properties separate a retry that helps from one that causes the outage:

  • Bounded. Three attempts, not "until it works". Unbounded retry against a struggling system is how a five-minute blip becomes an hour.
  • Backed off. Exponential: 1 s, 2 s, 4 s. Immediate retries arrive while the downstream is still failing and cost you three times the load at the worst moment.
  • Jittered. Add randomness. A thousand orders that all failed at the same instant will all retry at the same instant, and the synchronized second wave is often larger than the first.
  • Conditional. Only on the transient class. This is the whole point of the taxonomy.

Idempotency is what makes retry safe

Retry is only correct if repeating the operation is harmless. Three ways to get there, in order of preference. Natural idempotency: pass the customer's PO number to the ERP as its own external reference, so a second create with the same reference returns the existing sales order rather than making another. A dedupe store: record the key before the side effect, check it on entry. Conditional update: write only if the current state matches what you expect.

Chapter 5 left a bug open — the ERP call succeeded and the idempotency record failed, so the retry duplicated the order. Natural idempotency dissolves it: with the PO number as the ERP's external reference, the retry's create is a no-op that returns the same sales order number, and the failed bookkeeping write no longer matters.

Compensation and saga thinking

Once a flow crosses two systems, atomicity is gone unless you pay for XA — and chapter 8 argued against that. The alternative is a saga: a sequence of local transactions, each with a defined compensating action, run in reverse on failure.

Meridian's order saga

forward                        compensate
1  reserve stock              →  release reservation
2  create ERP sales order     →  cancel sales order
3  publish OrderAccepted      →  publish OrderCancelled  # never "unpublish"

# fail at 3 -> run 2's compensation, then 1's, in that order

Two rules keep sagas honest. Compensations must themselves be idempotent, because the compensation can fail and be retried too. And you cannot compensate an event by deleting it — the fact was published and subscribers acted on it. You compensate a published fact with another published fact.

You cannot un-send a message. Design the reversal as a new event, or do not publish until the thing is true.

Poison messages and dead letters

A message that fails deterministically will fail forever, and while it does, it blocks everything behind it on an ordered destination. Count attempts on the message itself, and after the limit move it to a dead-letter destination with the error, the attempt count and the correlation ID attached. Then — the part teams forget — alert on the dead-letter queue's depth. A dead-letter queue nobody watches is a data-loss mechanism with extra steps.

What the platform records for you

If error logging is enabled, Integration Server always writes an error log entry when a service error occurs, and error logs contain stack trace information for all errors, including exceptions thrown by services. Separately, service audit logging can store the input pipeline — and that is what makes a later resubmit of the service possible at all. That single setting is the difference between "we lost 40 orders" and "we replayed 40 orders"; chapter 13 covers what it costs.

Failure scenario

A malformed order from a new customer integration throws on every attempt. The retry is unbounded, so the trigger reprocesses it every two seconds, forever. Each attempt writes a stack trace; over a weekend the error log fills the disk, Integration Server stops writing logs, and the genuine incident on Monday morning has no diagnostics at all. One bad message took out observability for everything else — which is why the bound, the dead-letter destination and the disk alarm are all the same control.

Design review questions

  1. Does one service classify failures, or does every catch block have its own opinion?
  2. Are your retries bounded, backed off, jittered, and conditional on the transient class? Which of the four is missing?
  3. For each retried operation: what makes it idempotent — nature, a dedupe store, or hope?
  4. Write out your longest flow's compensations. Is each one idempotent, and is the event compensated by another event?
  5. What is currently in your dead-letter destinations, and when did someone last look?
