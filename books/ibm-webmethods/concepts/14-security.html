Security for integration platforms

An integration platform is the one system that holds credentials to everything else. That makes it the highest-value target in the estate and, in most organisations, the least well-inventoried. This chapter is about the four controls that actually change the blast radius.

Transport security and the certificate you forgot

TLS everywhere is table stakes, including on the hops nobody thinks about: the JDBC connection, the SFTP transfer, the messaging link, the connection between gateway and integration runtime. "It is on the internal network" stopped being an argument some time ago, and it was never an argument for the link that carries every credential in the business.

The operational half is harder than the cryptographic half. Certificates expire, and a B2B certificate expiring at 02:00 takes a partner channel down with an error message that looks nothing like "certificate expired". Build the inventory: every certificate, its expiry, its owner by name, its renewal procedure, and an alarm at 30 days. If you do one thing from this chapter, do that — it is the highest-frequency preventable outage in enterprise integration.

Credentials and secrets

Chapter 4 put secrets in a credential store referenced by alias, with only the alias name appearing in a package. Two additional properties matter here. Rotation must be possible without a deploy — if changing a password means rebuilding an artifact, rotation will not happen, and an unrotatable credential is a permanent one. And a leaked secret must be revocable independently, which is impossible if every integration shares one account.

The shared service account problem

One svc_integration account with rights to everything is the default state of most estates, and it defeats two controls at once. The audit trail cannot attribute an action to a flow, so "who updated this order" has no answer. And revoking access for one compromised integration revokes it for all of them, which means nobody will revoke it. One identity per integration, scoped to what that integration touches.

OAuth 2.0 and token propagation

Chapter 9 chose client-credentials tokens for application-to-application traffic. The design question that follows is propagation: when the integration calls the ERP, whose identity does it use?

For Meridian, trusted subsystem is right and worth stating explicitly: orders arrive from a customer's system, not from a person, and the asynchronous paths have no user session to propagate anyway — the event that reaches the CRM two seconds later belongs to no one's token. The end user's identity travels as data in the canonical order, where it is auditable without being an authorization principal.

Least privilege, concretely

Least privilege is easy to agree with and hard to hold. Two things make it stick: grant per operation rather than per system — the order integration needs create sales order, not database write — and review grants when integrations are retired, because permissions outlive the flows that needed them and nobody removes an entitlement whose owner has left.

The integration platform holds keys to every system it touches. Its blast radius is the union of everything it can reach, and that union is almost never written down.

Payload privacy, masking, and the audit log

Chapter 13's warning becomes a compliance obligation here. Storing input pipelines in the audit log means payload contents are persisted — so audit configuration is a data-privacy decision, not only an operational one. Four rules:

  • Drop before you capture. Remove secrets and unnecessary personal data from the pipeline before the audited step, since the pipeline is captured as it stands.
  • Mask in logs. Never write a full card number, national ID or bearer token to any log — and remember an error stack trace can carry a payload fragment with it.
  • Retention shorter than the source. An audit store that keeps personal data longer than the system of record quietly breaks that system's deletion guarantees.
  • Encrypt at rest, including the audit database and the MFT landing area — where partner files sit in the clear by default.

On the enforcement side, the gateway is where these become policy rather than convention. API Gateway's role in the platform is to secure exposed APIs, applied through its policy framework rather than through code — so authentication, threat protection and payload limits are configuration you can audit centrally, not forty flow services you must read.

Failure scenario

A developer enables pipeline capture on the order service to debug a mapping and leaves it on. Six months later the audit database holds every order payload — names, addresses, contact details — for a period nobody agreed to, in a store the data-protection register does not list. Nothing was breached, and it is still a reportable finding. Diagnostic settings need the same change control as code, because they change what data you hold.

Design review questions

  1. List every certificate the platform depends on. Does each have a named owner and a 30-day alarm?
  2. Can you rotate a downstream password without a deployment?
  3. How many integrations share a service account, and what would revoking it break?
  4. Which systems can your integration runtime reach today? Is that list written down anywhere?
  5. What personal data is in your audit store, for how long, and who signed that off?
  6. Is security enforced by gateway policy, or re-implemented in each service?
