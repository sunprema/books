CI/CD and integration delivery automation

Integrations are code. The reason they are so often not treated as code is that the tooling makes editing a live server easy and committing a package tree slightly awkward — and that small asymmetry is what produces estates nobody can rebuild.

Integrations as code

Everything that defines behaviour belongs in version control: package ns trees, document types, adapter service definitions, gateway API definitions and policies, deployment descriptors, and the environment configuration for each environment (in its own repository, with secrets by reference only). If it is not in git, it cannot be reviewed, reverted, or reproduced — and the first time you need all three at once will be during an incident.

Gateway assets are the most commonly missed. The vendor's own DevOps tooling exists for exactly this: extract API Gateway assets from a local or central development environment, commit them to git, and promote them automatically to stage and production through build pipelines. Without it, the gateway becomes the one environment nobody can rebuild — which is an uncomfortable property for the component that enforces your security policies.

Branching that suits integration

Trunk-based with short-lived feature branches, for a reason specific to this platform: chapter 4 established that the Integration Server namespace is global, so long-lived branches accumulate conflicts in a namespace that has no real merge semantics. Merge daily, keep branches to a day or two, and use a feature toggle rather than a branch for anything that must be hidden.

Toggles need an expiry date

Every toggle is a branch in the code and a doubling of the paths under test. Write the removal ticket when you create the toggle, and hold the team to it. An estate with forty live toggles has a combinatorial test surface nobody is testing.

The pipeline, stage by stage

The build stage is webMethods Asset Build Environment run against a VCS checkout, and the build server needs only Integration Server plus Deployer — no Designer, no database. That is what makes an ephemeral, containerized build agent practical. The vendor's DevOps library ships a sample project layout using git with Jenkinsfile pipeline definitions orchestrating build, deploy and test; start from that shape rather than designing one.

Automated gates

This is where chapter 18's standards become real. Every mechanical standard is a gate, and a gate is a standard that cannot decay:

Every one of these gates exists because of a specific failure earlier in this book. That is the only good reason to add a gate.

Approvals, change records and auditability

Regulated environments need a change record and an approval. Neither has to be manual, and neither should be a meeting. Generate the change record from the pipeline — commit range, tickets, test results, artifact hash, target environment — and let approval be a recorded decision against that artifact. The audit trail is then better than a hand-filled form, because it is derived from what actually happened.

The property auditors are really asking about is provable provenance: for anything in production, which commit produced it, who approved it, what tests passed, and when it was deployed. If your pipeline can answer those four from records rather than recollection, most of the compliance conversation is already over.

Failure scenario

A production incident is fixed by editing the service directly on the production server at 02:00 — correctly, and the outage ends. Nobody commits the change. Three weeks later a routine deploy overwrites it with the version from git and the incident recurs, this time during business hours, and the on-call engineer is a different person with no memory of the first fix. Hot-fixing production is sometimes right; the commit is not the optional part of it. Make "commit the fix" the last step of the runbook, not an aspiration.

Design review questions

  1. Could you rebuild your entire integration estate from git alone? Including gateway policies?
  2. How long is your pipeline, and do developers wait for it or context-switch away?
  3. Which of chapter 18's standards is an automated gate, and which is still a wiki page?
  4. For a random service in production: which commit produced it, and can you show that from records?
  5. When was production last edited directly, and was the change committed afterwards?
  6. How many feature toggles are live, and how many have a removal ticket?
