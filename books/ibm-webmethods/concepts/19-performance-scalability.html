Performance, scalability, and capacity planning

An integration tier is almost never the bottleneck. It is the thing that reveals the bottleneck, usually by holding a connection open while something else thinks. Capacity planning here means finding whose limit you hit first.

Four numbers, and the ceiling they imply

Throughput, latency, concurrency and back-pressure are related by one expression you should be able to write from memory. With C concurrent slots and a hold time of t seconds, capacity is C / t per second. Everything else is a variation.

Meridian, from chapter 1: peak 8 orders/second, ERP at 20 connections and 300–900 ms, one ERP call per order. Capacity is 20 / 0.9 ≈ 22/s against a peak of 8 — a headroom factor of about 2.75. That number is the design, and it decays in exactly two ways: someone adds a second ERP call (capacity halves to 11/s), or the ERP slows under its batch window (at 6 s, capacity is 3.3/s and you are underwater).

The lever is t, not C

You cannot raise C past the downstream system's limit — a pool of 100 against an ERP accepting 20 buys errors, not throughput. So capacity work is nearly always about reducing hold time: fewer calls per transaction, a bulk interface instead of a loop, or moving work off the synchronous path entirely.

Statelessness is what makes scaling possible

Horizontal scaling works only if any node can handle any request. State in a flow service — a cached lookup, an in-memory counter, a sequence number — forces sticky sessions and turns a node failure into lost work. Keep state in the database, the messaging provider, or the request itself.

And note the constraint scaling out does not escape: adding integration nodes multiplies your demand on downstreams while their limits stay fixed. Four nodes with a 20-connection pool each is 80 connections to an ERP that accepts 20. Pool sizes must be divided across nodes, not replicated to them — this is the single most common scaling mistake in the discipline.

Where the tuning surface actually is

Adapter connection parameters are what Integration Server uses to manage connections, so pool configuration is the primary throughput control for database-bound flows. The SAP adapter is a deliberate exception worth remembering: it fully manages its own connections, pools and sessions, so tuning happens in the adapter rather than in an Integration Server pool — and wrapping it in another pool produces a system whose capacity nobody can compute.

On the messaging side, Universal Messaging provides message persistence, which means durable throughput is bounded by the persistence store as well as by the network. If your event volume is high, the disk behind the messaging provider is a capacity input, not an implementation detail.

Back-pressure, or the queue that eats memory

When arrivals exceed capacity, something must give. The good options are to reject early with 503 and Retry-After, or to buffer in a bounded, persistent queue. The bad option is the default one: an unbounded in-memory queue that grows until the runtime dies, taking every in-flight transaction with it. Bound every queue, and decide explicitly what happens when the bound is reached.

Load testing that tells you something

Three properties separate a useful load test from theatre. Use realistic payload distribution — not the average size, but the real spread, because the 1% of orders with 400 line items is what exhausts memory. Use realistic downstream behaviour, including the slow batch window. And find the knee: ramp until latency degrades, and record the arrival rate where it does. That number, not a pass/fail, is your capacity.

Load testing with one average document proves your system can process that document. It proves nothing about the day the largest customer sends their quarterly order.

Capacity planning from transaction profiles

Work forward from the business, not backward from the servers. Volume per day, shape of the peak, payload distribution, calls per transaction, downstream limits and hold times — six inputs that give you a required capacity and a headroom factor. Plan for a headroom factor of at least 2 at peak, and re-run the arithmetic whenever any of the six changes. Adding one downstream call to a flow is a capacity change, and it should be reviewed as one.

Failure scenario

Month-end doubles order volume, so the team scales from two nodes to four. Throughput does not improve — it degrades. Each node kept its 20-connection pool, so the ERP now sees 80 connection attempts against its limit of 20, rejects most of them, and the retries (chapter 12) add load on top. Scaling out made it worse, which is a genuinely disorienting thing to watch. The fix was to halve the pool per node, and it took four hours to find because nobody had written down that the ERP's limit was global.

Design review questions

  1. What is your headroom factor at peak, and when did you last compute it?
  2. Multiply every pool size by your node count. Does any product exceed a downstream limit?
  3. Which queues in your system are unbounded?
  4. What is the 99th-percentile payload size, and has anything been tested with it?
  5. Is any state held in a flow service that would prevent a node being replaced mid-request?
