Chapter Six

Better Memory Representation

Look back at the table in Chapter Two: main memory is a hundred times an L1 hit. On a modern machine most programs are not computing — they are waiting for bytes to arrive. Which means that how your data sits is often more important than what you do to it.

Smaller is faster, for a physical reason

The document's phrasing is precise, so here it is: use compact representations for data that is accessed often or that makes up a large portion of the application's memory, because a compact representation touches fewer cache lines and uses less memory-bus bandwidth.

That's the whole mechanism, and it's worth sitting with because it explains everything else in this chapter. Memory does not arrive a byte at a time. It arrives in cache lines. If the four bytes you need live in a struct of 64 bytes, you paid for 64 bytes. Halve the struct and you fit twice as many per line — the same loop now does half as many trips to memory, having changed no logic at all.

The counter-indication

Packing has a failure mode: cache-line contention. Squeeze fields that different threads write onto one line and those cores now fight over it, invalidating each other's copies. You made the struct smaller and the program slower. Compaction is for data that is read together, not for data that is written apart.

Field order, and the holes you didn't know about

Here's a thing that surprises people the first time. The compiler aligns fields, so declaration order changes sizeof. Not the semantics — just the size, silently, for free, in either direction. 

// Alternating sizes: the compiler inserts padding to keep alignment.
struct Entry {
  uint8_t  kind;      // 1 byte, then 7 bytes of padding
  uint64_t offset;    // 8
  uint8_t  flags;     // 1 byte, then 7 more bytes of padding
  uint64_t length;    // 8
};                     // 32 bytes, 14 of them nothing at all

// Same fields, grouped by alignment.
struct Entry {
  uint64_t offset;    // 8
  uint64_t length;    // 8
  uint8_t  kind;      // 1
  uint8_t  flags;     // 1, then 6 bytes of tail padding
};                     // 24 bytes

A quarter of the memory gone, and the diff is a reordering. If you have a hundred million of these, that is 800 MB you were storing for the sake of alignment rules.

Two smaller moves in the same family. Use a smaller numeric type when the values fit — uint8_t instead of int for something that never exceeds 200. And give enums an explicit underlying type, because otherwise they are int-width: 

enum class OpType { kAdd, kMul, kLoad, kStore };            // 4 bytes
enum class OpType : uint8_t { kAdd, kMul, kLoad, kStore }; // 1 byte

Hot next to hot, cold somewhere else

Size is only half of it. Neighbourhood is the other half, and there are three separate rules hiding in it.

  1. Put frequently-accessed fields together. If the common operation touches four fields, having them adjacent means one cache line served the whole operation instead of four.
  2. Separate hot read-only fields from hot mutable ones. This is the subtle one. A field that is written constantly, sharing a line with fields that are only read, drags those read-only fields out of every other core's cache on every write. Split them and the read-only line stays valid everywhere.
  3. Move cold data out of the way — to the end of the struct, behind an indirection, or into a separate parallel array. A debug string that is used once a week should not be occupying the cache line your inner loop needs.

Indices instead of pointers

On a 64-bit machine, a pointer costs 64 bits. A pointer-rich structure — a graph, a tree, a linked anything — can spend most of its memory on addresses rather than on data. The alternative is to keep the elements in an array and refer to them by index.

You get two wins at once, and the second is the bigger one:

  • The reference shrinks. If you'll never have more than four billion elements, a uint32_t index halves it. If you'll never have more than 65,536, a uint16_t quarters it.
  • The elements become contiguous. This is the real prize. Nodes reached by pointer are scattered wherever the allocator put them, so traversal is a sequence of unpredictable jumps — a cache miss each. Nodes in an array sit next to each other, so the hardware prefetcher can see you coming and the data is already there.
The through-line

Compact it, order it so the hot fields share a line, move the cold parts away, and use indices so the elements are contiguous. Four different techniques, one underlying goal: touch fewer cache lines. Every memory hint in this book is a restatement of that sentence.

One more note before the next chapter. Bit- and byte-level encodings can shrink things dramatically, and the document endorses them — with two conditions. Keep them behind a well-tested encapsulation boundary, so the cleverness is in one file rather than smeared across the codebase, and validate the win with benchmarks rather than with reasoning. A hand-packed representation that saves memory and costs more decode time than it saves is entirely possible, and you will not know which you built until you measure.
