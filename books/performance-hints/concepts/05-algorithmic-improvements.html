Chapter Five

Algorithmic Improvements

This is the chapter with the most leverage in the book, and it is also the shortest, because the advice is embarrassingly simple: before you make the loop faster, ask whether the loop should exist.

Why this beats everything else

Every other technique in this book buys you a constant factor. A better memory layout might win you 30%. Removing an allocation might win 21%. Those are real, and worth having. But turning O(N²) into O(N log N) doesn't win you a percentage — it wins you a different curve, and the gap between two curves grows without bound as your data does.

Put it in the terms of Chapter Two. At N = 1,000, an O(N²) algorithm does a million units of work and an O(N) one does a thousand. Grow to N = 1,000,000 and it's a trillion against a million. No amount of cache-friendly struct packing is going to close a factor of a million. And here is the part that stings: the quadratic version probably ran fine in your test, because your test had ten elements.

Example: detecting cycles in a graph

Here is a lovely case where the improvement isn't a cleverer algorithm but a different question. The original GraphCycles added nodes and edges one at a time and maintained a cycle-free invariant incrementally, which is genuine work on every insertion.

But often the caller has the whole graph already. So: add it all at once, in reverse post-order. Assign every node a rank during a single depth-first traversal, and then cycle detection becomes a comparison — an edge that runs from a higher rank to a lower one is, by construction, a back edge. 

bool GraphCycles::InitFrom(const util_graph::Graph& src) {
  // Assign ranks in topological order
  Rank last_rank = n;
  auto leave = [&](util_graph::Node node) {
    DCHECK(r->rank[node] == kMissingNodeRank);
    NodeInfo* nn = &r->nodes[node];
    nn->in  = kNil;
    nn->out = kNil;
    r->rank[node] = --last_rank;
  };
  util_graph::DFSAll(src, std::nullopt, leave);

  // Add edges (detect cycles as we go)
  bool have_cycle = false;
  util_graph::PerEdge(src, [&](util_graph::Edge e) {
    if (r->rank[e.src] >= r->rank[e.dst]) {
      have_cycle = true;
    } else if (!HasEdge(e.src, e.dst)) {
      EdgeListAddNode(r, &r->nodes[e.src].out, e.dst);
      EdgeListAddNode(r, &r->nodes[e.dst].in,  e.src);
    }
  });
  return !have_cycle;
}

Notice the relationship to the previous chapter. This is a bulk API, and the bulk API is what made the algorithmic improvement possible. Because the function is handed the entire graph, it can choose an order; the incremental version never had that choice. The two chapters are the same idea seen from two sides.

Example: choosing a different structure

The second family of algorithmic wins comes from swapping the data structure so the operation you do most becomes cheap.

  • An IntervalMap with O(log N) lookups was replaced by a hash table with O(1) lookups, once the code was restructured so that finding an adjacent block was a lookup rather than a traversal. The structure changed because the access pattern changed.
  • Intersecting two sorted lists cost O(N log N). Hash one side, probe it with the other: O(N). Same answer, one pass.
The asterisk on O(1)

A hash table is O(1) only if the hash function actually spreads your keys. Feed it keys that collide — a hash that ignores the varying part of a string, a pointer hash on pointers that are all 16-byte aligned — and every lookup walks a chain. You get O(N) behaviour while your complexity analysis says O(1), which is the worst possible place to be: slow and confident.

How to spot the opportunity

Algorithmic wins rarely announce themselves in a profile, because the profile shows you where the time goes, not that the work was unnecessary. A quadratic loop shows up as a perfectly ordinary hot function. So look for the shapes instead:

  • A loop inside a loop over the same collection.
  • A linear search inside anything that runs per-element.
  • Repeatedly recomputing something incrementally that could be computed once in bulk.
  • A tree or ordered structure being used when nothing ever needs the order.
  • A cost that grows visibly faster than your input does between two production days.

That last one is the honest signal. Everything else in this book you can find with a profiler. This chapter you mostly find by reading, or by watching a graph bend.
