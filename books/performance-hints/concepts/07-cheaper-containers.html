Chapter Seven

Cheaper Containers

The previous chapter was about the shape of one object. This one is about the shape of a collection of them — which is where the same cache-line argument stops being a micro-optimization and starts being worth tens of percent.

Batched storage: stop allocating per element

A node-based container — std::map, std::unordered_map, std::list — allocates a separate object for every element. Two costs follow from that, and they compound:

  • Allocator overhead per element, paid on every insert and every erase.
  • Terrible cache behaviour, because the elements end up wherever the allocator had room. Iterating a node-based map is a tour of your heap: each step is a jump the prefetcher cannot anticipate, which is a main-memory reference that Chapter Two priced at 50 ns.

The flat alternatives — std::vector, absl::flat_hash_map, absl::flat_hash_set — store many elements contiguously. One allocation covers many elements, and iteration walks straight down memory in exactly the pattern the hardware is built to accelerate.

Where a fully flat structure isn't viable, chunking gets you most of the way: partition elements into fixed-size chunks. You keep the asymptotic behaviour that made you want the structure, and you cut the cache footprint because each chunk is contiguous.

Inlined storage: the allocation that never happens

Now consider the very common case where a container holds three elements. A std::vector still heap-allocates for those three. An InlinedVector embeds space for a small number of elements directly inside the object, so a small collection costs zero allocations.

This pays best in exactly two situations, and it's worth knowing which you're in: when instances are frequently constructed as stack variables (the allocation and free were the entire cost of a short-lived object), and when very many instances exist at once (you removed one allocation each, a million times).

The counter-indication

Large sizeof(T) ruins it. Inline capacity for 4 elements of a 200-byte type makes every instance 800 bytes, whether it holds anything or not — including the ones you store a million of, and including the ones that are empty.

Flatten unnecessarily nested maps

A map of maps looks natural in the domain and is often wasteful in the machine. Every lookup is two lookups: hash or compare the outer key, land on an inner container (probably a cache miss), then hash or compare again. And every inner container carries its own bookkeeping. 

// Two levels: two lookups, and one inner map's overhead per outer key.
absl::btree_map<std::string, absl::btree_map<std::string, OpDef>> ops;

// One level, compound key: one lookup, views instead of strings,
// and a pointer instead of a stored OpDef.
absl::btree_map<std::pair<absl::string_view, absl::string_view>,
                const OpDef*> ops;

Look at how much that one line changed. The double lookup collapsed to one. The owned strings became views. The stored value became a pointer. Three separate wins from asking "does this actually need to be two structures?"

The counter-indication

If the first key is large, the nested form may win: nesting stores that key once for all its children, while flattening repeats it in every compound key. Measure with your real key sizes and your real fan-out.

Arenas

An arena allocates a big block up front and hands out pieces of it, then frees the whole block at once. Three things get cheaper: allocation becomes a pointer bump; independently-allocated items land in fewer cache lines because they are adjacent; and destruction of the individual objects goes away entirely — you drop the block.

Arenas suit complex data structures with many sub-objects — a parsed message, an expression tree, a request's whole working set. Give the arena a sensible initial size, or you will spend the win on growing it.

The counter-indication

Do not put many short-lived objects into a long-lived arena. Nothing is reclaimed until the arena dies, so a request-scoped allocation in a process-scoped arena is a leak wearing a very respectable hat.

When the map was an array all along

Here is my favourite hint in the whole document, because the fix is so much simpler than the thing it replaces. If a map's keys are small integers or enum values — or if the map only ever holds a handful of entries — a plain array or vector usually beats it outright. 

// Keys are RTP payload types: 0..127. This was never really a map.
// const gtl::flat_map<int, int> payload_type_to_clock_frequency_;
int payload_type_to_clock_frequency_[128];

Count what vanished: the hash computation, the probe sequence, the load-factor bookkeeping, the node allocations, the pointer chase. What replaced all of it is a single indexed load — and 128 ints is 512 bytes, which is a rounding error. For genuinely tiny maps the same logic applies with linear search: scanning six contiguous entries beats hashing one, because the six live in a single cache line and the hash does not.

Bit vectors instead of sets

Same idea, applied to sets. If your set's domain is small integers, a bit vector represents membership in one bit per possible element. Two hundred and fifty-six possible members fit in 32 bytes — half a cache line for the entire set.

And the set operations become single instructions on machine words: union is OR, intersection is AND. Where a hash set would iterate one side and probe the other, the bit vector does 64 elements per instruction.

Measured

Replacing dense_hash_set<ZoneId> with util::bitmap::InlinedBitVector<256> gave 26–31% improvements across benchmarks. Not the inner loop — the benchmarks. That is what changing a representation can be worth.

The document takes the trick a step further with bit matrices: tracking reachability between operands as a matrix of bits rather than as std::unordered_map<const HloInstruction*, std::unordered_set<const HloInstruction*>>. Read that type out loud and you can hear the cache misses. The bit matrix answers the same question with an indexed bit test.

Notice that every hint in this chapter is the same question asked about a different container: does the structure I reached for by habit match what this data actually is? Small dense integer keys are an array. Small-domain membership is a bit vector. Two keys are one compound key. A few elements are a flat scan. The general-purpose container is the right default precisely because it makes no assumptions — which means that when you do know something, you are paying for ignorance you no longer have.
