Chapter Four

The Shape of an Interface

An interface is a promise about what is possible. Get the shape wrong and you have promised your callers a slow program — and worse, you have made it impossible for them to fix, because the waste is on your side of the line.

Bulk APIs: cross the boundary once

Start with the simplest observation. Every call across an API boundary costs something — a call, maybe a lock, maybe a check, maybe a cache miss on the callee's state. If a caller needs a thousand things, a singular interface makes them pay that fixed cost a thousand times.

Look at what happens to the lock in a bulk delete: 

template <typename T>
absl::Status ObjectStore<T>::DeleteRefs(absl::Span<const Ref> refs) {
  util::Status result;
  absl::MutexLock l(&mu_);          // once, for the whole batch
  for (auto ref : refs) {
    result.Update(DeleteRefLocked(ref));
  }
  return result;
}

One mutex acquisition instead of N. At 15 ns per uncontended lock/unlock — and far worse under contention — a batch of a thousand just gave back fifteen microseconds and, more importantly, stopped a thousand threads from queueing at the same door.

But the amortized lock is the small win. The real win is that a bulk interface tells you something a singular one cannot: what the caller wants in total. That unlocks algorithmic improvements the one-at-a-time version has no way to reach. A LookupMany can sort the keys, or probe them in an order that plays well with the cache, or notice that they share a prefix. It can even simplify its own return type — if clients only need to know whether all the keys were found, the bulk call returns one boolean where the singular one returned a thousand results nobody examined individually.

The general principle

A singular API forces the callee to be ignorant. It can never do better than handling one request at a time, because one request at a time is all it is ever told about.

And if converting the callers is too big a job? The document's pragmatic answer: use the bulk operation internally and cache the results to serve the singular calls that follow. The caller keeps its loop; you stop paying for it.

View types: stop copying at the door

The second move is almost free and pays constantly. Prefer view types for function arguments: std::string_view, absl::Span<T>, absl::FunctionRef<R(Args...)>.

Two things happen at once. The copy disappears — you take a pointer and a length instead of duplicating the bytes. And the caller is freed: a function taking Span<const int> accepts a vector, an array, an inlined vector, a slice of any of them. A function taking const std::vector<int>& quietly demands that everyone build a vector first, and some of them will, at cost, just to call you.

Let the caller pass what it already has

Sometimes the callee recomputes something the caller was already holding. The clock is the classic case: a stats-recording function reads the wall clock, and it is being called from a loop that already knows the time. 

static void RecordRPC(const Name &name, const RPC_Stats_Measurement& m,
                      WallTime now);   // caller passes the reading it has

One parameter, and a clock read per call disappears. The pattern generalizes to anything the caller plausibly has in hand: a hash it already computed, a length it already knows, a lookup it already did. The signature is the place where you find out.

Thread-compatible, not thread-safe

The last one is the most counter-intuitive, because it sounds like an argument against safety. It isn't.

Most types should be thread-compatible — safe to use from multiple threads provided the caller synchronizes externally — rather than thread-safe, which means the type locks internally on every operation. The reason is simple arithmetic: if the type locks internally, then every caller pays for synchronization, including the overwhelming majority that use it from one thread, or that already hold a lock covering the whole operation. 

// Callers were already externally synchronized, so the lock was pure tax.
TransferPhase HitlessTransferPhase::get() const { return phase_; }

There is a genuine flip side, and the document states it: when synchronization is needed almost every time anyway, move it inside the type. Then the type owns the locking and can optimize it — a finer-grained scheme, a lock-free fast path, a sharded mutex — without a single caller changing. The question isn't "safe or fast". It's "who is in a position to know what synchronization is actually needed here", and you should put the lock where that knowledge lives.

Why this chapter comes first

Every other chapter in this book describes a change you can make later, behind your interface, without telling anyone. This one describes changes that become migrations the moment your interface has users. Get the shape right while it is still cheap.
