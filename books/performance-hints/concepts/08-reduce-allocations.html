Chapter Eight

Reduce Allocations

Allocation is the cost that hides best. It never has its own peak in a profile because it is charged to a thousand different callers — which makes it the single most likely explanation for the flat profile in Chapter Three.

One allocation, three bills

When people say "allocation is slow" they usually mean the first of these. There are three:

  1. Time inside the allocator. Finding a free block, updating bookkeeping, possibly taking a lock. The obvious one.
  2. Initialization and destruction. The object gets constructed and later destroyed, and for anything non-trivial that can dwarf the allocator time.
  3. A bigger cache footprint. Each allocation typically lands on a new cache line. Allocate a thousand small objects and you have scattered your working set across a thousand lines that used to be somebody else's.
The one people forget

The third bill is often the largest, and it is the one a microbenchmark of malloc will never show you. It is not paid at the allocation site. It is paid later, by whatever code has to walk that scattered data.

Allocations you didn't need at all

Start with the ones that produce nothing. A function returns a fresh empty object each time it is asked for an empty object. Every caller gets its own identical nothing. 

static const std::shared_ptr<DeviceInfo>& empty_device_info() {
  static std::shared_ptr<DeviceInfo>* result =
      new std::shared_ptr<DeviceInfo>(new DeviceInfo);
  return *result;
}

One shared empty instance, handed out forever. In the document's benchmark this change increased throughput by 21% — from removing an allocation whose result nobody was going to modify.

The same shape recurs: use a statically-allocated zero vector instead of allocating a vector and filling it with zeroes. Check whether the static data suffices before you reach for the heap. It's a two-line guard, and in the common case the heap never gets touched.

Size it once, not N times

A vector grown by repeated push_back reallocates as it goes, copying everything it already holds each time. If you know the final size — and you usually do — say so.

Read this one carefully

Do not use resize or reserve to grow one element at a time. Calling reserve(n+1) inside the loop can make every step reallocate and copy — the exact quadratic behaviour you were trying to avoid, now with the word "optimization" in the commit message. Reserve once, outside the loop, with the total.

Don't copy what you can move, point at, or index

Prefer moves to copies. Store pointers or indices rather than copies of objects (Chapter Six's indices, arriving from the other direction). And look hard at pipelines that pass large buffers through several layers — each layer is a chance for a copy nobody intended.

The document's example: a benchmark sending roughly 400 KB tensors over gRPC got about a 10–15% speedup from eliminating one extra copy. One. On data that was going to cross a network anyway.

Reuse the temporary

A container declared inside a loop is allocated and freed on every iteration. Hoist it out, clear it between iterations, and you allocate once for the whole loop — and after the first few iterations its capacity has settled at the size the loop actually needs, so even the clearing costs nothing. 

// Allocates (and frees) once per iteration.
for (const auto& row : rows) {
  Record record;
  Fill(&record, row);
  Emit(record);
}

// Allocates once, reused. Same output, same readability.
Record record;
for (const auto& row : rows) {
  record.Clear();
  Fill(&record, row);
  Emit(record);
}

The same idea crosses an API boundary as a scratch parameter: a function that serializes into a caller-supplied string, rather than returning a fresh one, lets the caller reuse one buffer across thousands of calls. It looks slightly less elegant in the signature and it removes thousands of allocations, which is a trade the hot path is happy to make. (Note the connection to Chapter Four: once again, the win is available only because the interface exposes it.)

Finding them

Since allocation cost doesn't concentrate into a peak, don't hunt it with a CPU profile. Use an allocation profile: it counts allocations by call site, which turns a diffuse cost into a ranked list. This is why "reduce allocation counts via allocation profiling" appeared in Chapter Three's list of moves for a flat profile — it is the instrument that makes the invisible cost visible.
