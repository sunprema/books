Chapter Nine

Avoid Unnecessary Work

The fastest code is the code that doesn't run. Every hint in this final chapter is a different way of noticing that you were about to compute something you did not need, or needed only later, or needed only once.

Fast paths for the common case

General code handles every case. Your data usually isn't every case — it's one case, overwhelmingly, with a long tail. A fast path checks for the common case cheaply and falls through to the general code otherwise. The document's examples:

  • UTF-8 scanning that handles trailing single ASCII bytes separately.
  • InlinedVector's resize, simplified for the common case.
  • Tensor shape initialization with fast paths for 1-D through 4-D.
  • A varint parser whose inlined fast path covers only the 1-byte case.
Why "only the 1-byte case"

That restraint is the real lesson. The document's reason: reducing the size of the inlined fast path reduces code size and instruction-cache pressure. A fast path that handles four cases is bigger, evicts more useful instructions, and can end up slower than the general code it replaced. Keep it small enough to stay fast.

The cheapest fast path of all is a flag that says "there is nothing to do": 

if (x.any_errors_set) {
  for (int i = 0; i < RPC::NUM_ERRORS; ++i) {
    errors[i] += x.errors[i];
  }
}

In the overwhelmingly common case where nothing went wrong, one predictable branch replaces the entire loop. And it is predictable, which — remember the quicksort arithmetic — is what makes it nearly free.

Precompute once

If a property never changes, compute it at initialization and store it. The document precomputes whether a node is an Enter or Exit node, so the hot path tests a flag instead of re-deriving the answer. The same move builds a probability lookup table once instead of recomputing values inside an inner loop.

The neighbouring hint is the classic: move loop-invariant work outside the loop. Bounds computations, length lookups, anything whose answer cannot change between iterations. Compilers do some of this; across an abstraction boundary they frequently can't, because they cannot prove the answer is stable.

Defer — and sometimes never do it

The mirror image of precomputing. If something might not be needed, don't compute it until someone asks. The numbers here are the most dramatic in the document:

Measured

Deferring GetSubSharding() calls until they were actually needed took 43 seconds of CPU time down to 2. Not a 20% improvement — a twentyfold one, from moving work behind an if that was usually false.

A second flavour: move the cost off the hot path even when it is needed. Statistics that were updated eagerly on every allocation and deallocation became computed on demand inside a Stats() call. The information is identical; it is now paid for by the rare reader instead of by the constant writer.

And a third: don't pre-build what you probably won't use. Reducing pre-allocated initial query nodes from 200 to 10 cut CPU usage by 7.5%. Someone picked 200 once, for no reason anyone remembered, and 190 objects were constructed per query forever after.

Specialize

A general library routine pays for flexibility you may not need. When the hot path uses one narrow shape of that flexibility, hand-written code can win big:

  • A custom histogram printer ran about 4× as fast as sprintf.
  • RE2 regex calls were replaced with simple prefix matching where a full regex was never needed.
  • StrCat replaced StringPrintf for formatting IP addresses.

Each of those is the same trade: give up generality you weren't using, in a place where the profile says it matters. Note the second half of that sentence — it is what separates specialization from the reinvention of a library for no reason.

Cache

If the same expensive answer is requested repeatedly, remember it. The document caches results keyed on a precomputed fingerprint, avoiding re-parsing a large serialized proto on every access. The fingerprint is what makes it safe: it is cheap to compute and tells you whether the cached answer still applies.

Making the compiler's job easier

One last section, and it comes with a warning attached. Compilers must assume the worst across abstraction boundaries — that two pointers might alias, that a called function might do anything, that a value might have changed. You often know better. But the document is explicit that this is work to do only after profiling has identified the bottleneck, because every technique here costs readability.

  1. Eliminate function calls on hot paths to avoid frame setup cost.
  2. Move slow-path code into tail-called functions, so the hot path stays small and the cold code isn't inlined into it.
  3. Copy data into local variables before heavy use. This is the subtle one: once the value is in a local, the compiler knows nothing else can change it, which lets it discard aliasing assumptions and auto-vectorize.
  4. Manually unroll very hot loops.

The document's own examples show what that looks like in practice: replacing absl::Span with raw pointers to the underlying arrays in ForEachState so the compiler can analyse the access pattern; hand-unrolling a CRC loop to process 16 bytes per iteration instead of 4; and parsing a key four characters at a time, scanning backwards for the separator rather than calling memchr.

Notice the direction of travel

Chapter Four told you to prefer absl::Span over raw pointers. This section replaces a Span with raw pointers. Both are right — the first is the default for an interface, the second is a measured exception in a proven bottleneck. If you apply this section's advice without the profile that justifies it, you have simply written worse code.

Where this leaves you

Look back at the nine chapters and notice they are one idea, applied at nine different scales. Don't cross the boundary a thousand times when once will do. Don't compute the answer with the worse curve. Don't fetch a cache line to read four bytes of it. Don't allocate what you can reuse. Don't compute what nobody asks for.

All of it is don't do unnecessary work — and the reason it takes nine chapters is that "unnecessary" is invisible until you know where to look. That is the thing worth taking away. Not the list; the habit of asking, at each of these scales, what the machine is actually being asked to do, and whether you meant to ask it.
