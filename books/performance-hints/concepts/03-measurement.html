Chapter Three

Measurement, and What a Flat Profile Means

Estimation gets you a hypothesis. Measurement is how you find out that your hypothesis was charming and wrong. You will need both, and you will need them in that order.

Reach for the profiler first

The document's first recommendation is pprof, and the reason it gives is worth repeating: it gives good high-level information and it is easy to use both locally and against code running in production. That second half is the part people skip. A profile of your benchmark tells you about your benchmark. A profile of the real system, under real traffic, with real data distributions, tells you about the thing you are actually paid to make fast.

Build for it

Build production binaries with appropriate debugging information. A profile of a stripped binary attributes time to addresses you cannot name — which is the same as having no profile, only more expensive.

Microbenchmarks, and counters

For the specific code you are improving, write a microbenchmark. It is the tight feedback loop that makes optimization tractable rather than superstitious: change, run, see the number move. Without it you are guessing twice — once about the cause and once about whether your fix helped.

And use a benchmark library that can emit hardware performance counters. Wall time tells you that something is slow. Counters tell you why: cache misses, branch mispredictions, instructions retired. A change that halves cache misses but doesn't move wall time yet is a change you should probably keep — you have removed a bottleneck that was hiding behind another one.

The trap in a CPU profile

Lock contention lowers measured CPU usage. A thread blocked on a mutex burns wall time while burning no cycles, so the profile you are staring at looks cheap and calm while your throughput is on the floor. If CPU usage is suspiciously low and latency is high, stop reading the CPU profile — you are looking at the wrong instrument.

When the profile is flat

Now the interesting case, and the one that sends most people home. You profile, and there is no hot spot. The top entry is 1.8%. The next is 1.6%. There are four hundred entries. What do you do?

What you do not do is conclude the program is optimal. A flat profile means the cost is diffuse, not that it is absent — this is exactly the state Chapter One warned about. The document lists six moves for it, and they are all variations of "stop looking for a peak and start looking for a pattern".

  1. Accumulate many 1% improvements across a subsystem. Twelve of them is the 12% that Chapter One said no other engineering discipline would call marginal.
  2. Find loops near the top of call stacks. A loop high in the stack is a place where a structural change multiplies through everything beneath it.
  3. Seek structural changes, not micro-optimizations. If the cost is everywhere, the fix is usually a different shape, not a faster instruction.
  4. Replace over-general code with specialized implementations. The general path pays for cases you do not have.
  5. Use allocation profiling to reduce allocation counts. Allocation cost hides beautifully in a flat profile, because it is spread across every caller. Chapter Eight is entirely about this.
  6. Gather hardware counters to find cache misses. A program that is uniformly memory-bound looks flat in a CPU profile and obvious in a counter.
Read the list again

Four of those six are the subjects of later chapters — specialization, allocations, cache behaviour, structure. That is not a coincidence. The rest of this book is, in a real sense, the answer to "the profile is flat, now what?"

The loop

Put the two chapters together and you have the working cycle. Estimate what it should cost. Measure what it does cost. When those two numbers disagree, the gap is your bug — and it is a much sharper question than "make it faster", because you already know what the answer should be.

Everything from here on is the catalogue: the moves that actually close that gap, ordered roughly by how much leverage they have. We start with the one that is cheapest to get right and most expensive to fix later — the shape of the interface itself.
