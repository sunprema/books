01 No hidden allocations

Why Allocators Matter in Zig

Most languages hide memory allocation behind convenient abstractions. Zig does the opposite: every single heap allocation is visible at the call site. That is not a limitation—it is the point.

The No-Hidden-Allocation Principle

Zig’s design philosophy rests on a deceptively simple rule: if a function needs heap memory, it asks for an allocator. There is no global malloc lurking behind library calls, no constructor silently newing objects into existence, no garbage collector sweeping through your address space on its own schedule.

Open any standard library function that touches the heap and you will see it spelled out in the signature. std.ArrayList takes an Allocator. std.json.parseFromSlice takes an Allocator. Even std.fmt.allocPrint—the equivalent of C’s sprintf into a heap buffer—takes an Allocator. The allocator is never smuggled in through a global variable or a thread-local default. If you can read the function signature, you know whether it allocates.

Design principle

No hidden control flow, no hidden allocations. If a Zig standard library function can allocate, you will always see an Allocator parameter in its signature. No exceptions.

This makes every allocation site greppable. You can search an entire codebase for .alloc(, .create(, or .dupe( and find every place the heap is touched. In a language with hidden allocations, that kind of audit is essentially impossible.

How Other Languages Handle Allocation

To appreciate Zig’s approach, it helps to see what the alternatives look like. Every mainstream systems language has made a different trade-off.

Allocation visibility across languages
Language How heap memory is obtained Visibility
C malloc/free calls, sometimes wrapped in macros or hidden inside library functions Partially visible—library internals are opaque
C++ new/delete, implicit copies, STL containers with default allocators, constructors Often invisible—a std::string copy allocates silently
Rust Global allocator + Box, Vec, String Types signal heap use, but the allocator itself is a hidden global
Go / Java / Python Garbage collector manages all heap memory Invisible—any object may live on the heap
Zig Explicit Allocator parameter at every call site Fully visible—if it allocates, you see it

Allocator as Dependency Injection

Passing an allocator as a parameter is a form of dependency injection. The function does not decide where memory comes from—the caller does. This has profound consequences:

  • Testing. In tests you can hand your code a testing.allocator that tracks every allocation and fails the test if anything leaks.
  • Embedded targets. On a microcontroller with no OS, you pass a fixed-buffer allocator backed by a static array. No mmap, no sbrk, no problem.
  • Performance. A hot loop can use an arena allocator that bulk-frees at the end, while the rest of the program uses a general-purpose allocator.
  • WASM. WebAssembly has no malloc by default. Zig compiles to WASM cleanly because allocators are explicit—you bring your own.

In short, the allocator-as-parameter pattern decouples what your code does from how memory is managed. Every chapter in this book builds on that insight.

Seeing It in Code

Here is a small but realistic example: a function that reads an entire file into a heap-allocated buffer. Notice how the allocator is threaded through every call that might allocate.

reading a file with an explicit allocator

const std = @import("std");

/// Reads the entire contents of `path` into a caller-owned slice.
/// The caller must free the returned slice with the same allocator.
pub fn readWholeFile(
    allocator: std.mem.Allocator,
    path: []const u8,
) ![]u8 {
    const file = try std.fs.cwd().openFile(path, .{});
    defer file.close();

    return file.readToEndAlloc(allocator, 1024 * 1024);
}

pub fn main() !void {
    var gpa = std.heap.GeneralPurposeAllocator(.{}){};
    defer _ = gpa.deinit();
    const allocator = gpa.allocator();

    const data = try readWholeFile(allocator, "config.json");
    defer allocator.free(data);

    std.debug.print("Read {d} bytes\n", .{data.len});
}

Three things to notice:

  1. readWholeFile takes an Allocator as its first parameter. Anyone reading the signature knows this function will allocate.
  2. readToEndAlloc—a standard library method—also takes an allocator. The chain of explicit allocation runs all the way down.
  3. The caller uses defer allocator.free(data) to ensure the memory is released. Allocation and deallocation are both visible, both deliberate.
Naming convention

In the standard library, functions that allocate typically have Alloc in their name (readToEndAlloc, allocPrint, dupeZ) or take an Allocator parameter. This makes allocation even more discoverable.

This is the foundation everything else in this book stands on. Allocators in Zig are not an advanced topic bolted on for power users. They are the mechanism for heap memory—simple, explicit, and composable.
