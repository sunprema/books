05 Allocate many, free once

Arena and Fixed-Buffer Allocators

Not every allocation needs its own funeral. Sometimes you allocate a hundred things during a phase of work, and when the phase is over, you tear them all down at once. That pattern is so common—and so profitable—that Zig’s standard library ships two allocators built specifically around it.

ArenaAllocator: the bulk eraser

An ArenaAllocator wraps a child allocator—any std.mem.Allocator—and uses it to grab large pages of memory behind the scenes. When you ask the arena for memory, it bump-allocates within the current page: it advances an offset pointer forward, hands you the slice, and moves on. No bookkeeping per allocation. No free-list. No headers.

The crucial trick: calling free() on an individual allocation is a no-op. The arena simply ignores it. All the memory is released in one shot when you call deinit(). This is what makes arenas fast—you pay almost nothing for each allocation, and you pay for cleanup exactly once.

The key idea

An arena turns many small allocations into a single large lifecycle. You allocate freely during a phase of work, then call deinit() and everything goes away. Individual free() calls are silently ignored—by design.

Setting up an arena

The most common pattern in real Zig code is wrapping std.heap.page_allocator:

Arena setup with defer

const std = @import("std");

pub fn processRequest(request: Request) !Response {
    var arena = std.heap.ArenaAllocator.init(std.heap.page_allocator);
    defer arena.deinit(); // everything freed here, no matter what

    const allocator = arena.allocator();

    // Allocate as many things as you need—
    // no individual free() calls required.
    const parsed = try parseHeaders(allocator, request.raw);
    const body = try decodeBody(allocator, request.payload);
    const result = try buildResponse(allocator, parsed, body);

    return result;
    // defer fires: arena.deinit() releases all pages at once
}

Notice the shape: create the arena, immediately defer its deinit(), extract the allocator() interface, and pass that interface to everything that needs memory. When the function returns—normally or via error—the defer fires and every allocation disappears. No leak possible.

How it works internally

Under the hood, the arena maintains a linked list of pages obtained from the child allocator. Each page is a contiguous block of memory. The arena keeps a pointer to the current position within the active page. When you call alloc(), it advances that pointer (aligning as needed) and returns the slice. When the current page is exhausted, it requests a new page from the child allocator and chains it onto the list.

Where arenas shine

Arenas are ideal whenever your program has phase-scoped memory—a burst of allocations that share a natural lifetime:

  • Per-request in a web server. Parse the request, build the response, send it, tear down. Every allocation lives and dies with the request.
  • Per-frame in a game. Each frame allocates scratch data—particle lists, collision results, render commands—that is discarded at the end of the frame.
  • Per-pass in a compiler. Tokenizing, parsing, and code generation each produce intermediate data that the next pass does not need.

In all three cases, the arena lets you allocate at near-zero cost during the hot path and pay for cleanup once at the boundary.

Resetting instead of destroying

Sometimes you don’t want to destroy the arena—you want to reuse it. A game loop, for example, wants to clear the scratch arena every frame without releasing and re-acquiring pages from the OS. The reset() method handles this, and it takes a mode:

Arena reset modes
ModeBehaviorUse when
.retain_capacity Keeps all pages allocated; resets the bump pointer to the start You will allocate roughly the same amount next time (game frames, request loops)
.free_all Returns every page to the child allocator Next phase may be much smaller; you want to release memory back to the system

Arena reset in a loop

var arena = std.heap.ArenaAllocator.init(std.heap.page_allocator);
defer arena.deinit();

while (game.isRunning()) {
    const allocator = arena.allocator();

    const particles = try simulateParticles(allocator);
    const collisions = try detectCollisions(allocator, particles);
    renderFrame(particles, collisions);

    // Reset for next frame; keep pages for reuse
    arena.reset(.retain_capacity);
}

FixedBufferAllocator: no heap at all

If an arena says “allocate many, free once,” a FixedBufferAllocator says “allocate from this exact slice of bytes, and nothing else.” You give it a []u8—which can be a stack-local array, a static buffer, or a slice you obtained from somewhere—and it bump-allocates within that slice. When the slice is exhausted, the next allocation returns error.OutOfMemory. That’s it. No heap involvement whatsoever.

Unlike the arena, FixedBufferAllocator does support free() in a limited way: if you free the most recently allocated block, the bump pointer rewinds so that space can be reused. This makes it behave well with standard-library containers that free and reallocate as they grow.

FixedBufferAllocator with a stack buffer

pub fn formatMessage(id: u32) ![]const u8 {
    // 4 KB on the stack—no heap, no OS calls
    var buf: [4096]u8 = undefined;
    var fba = std.heap.FixedBufferAllocator.init(&buf);
    const allocator = fba.allocator();

    var list = std.ArrayList(u8).init(allocator);
    try std.fmt.format(list.writer(), "event-{d}", .{id});

    return list.toOwnedSlice();
}
When to reach for FixedBufferAllocator

Embedded systems and kernel code where heap allocation is forbidden or unavailable. Hot paths where you know the maximum size and want zero syscall overhead. Tests that need a deterministic, bounded allocator. Any time you can answer “how much memory do I need?” with a known upper bound.

Resetting a FixedBufferAllocator

Just like the arena, a FixedBufferAllocator can be reset to reuse its buffer from the beginning:

fba.reset();  // bump pointer goes back to zero

This is useful in loops where you format or compute into a fixed buffer on each iteration.

Composition: arenas all the way down

Here is where Zig’s allocator design really pays off. Because every allocator speaks the same std.mem.Allocator interface, you can compose them. The most common composition is the one you’ve already seen:

The classic pattern

// Arena backed by the OS page allocator
var arena = std.heap.ArenaAllocator.init(std.heap.page_allocator);

But you can go further. Want an arena that is bounded—one that will never request more memory from the OS, and will return error.OutOfMemory if you exceed a fixed budget? Stack a FixedBufferAllocator underneath:

Bounded arena: ArenaAllocator over FixedBufferAllocator

// A 64 KB ceiling—the arena will bump-allocate within this,
// but can never exceed it.
var backing_buf: [64 * 1024]u8 = undefined;
var fba = std.heap.FixedBufferAllocator.init(&backing_buf);

var arena = std.heap.ArenaAllocator.init(fba.allocator());
defer arena.deinit();

const allocator = arena.allocator();

// Use 'allocator' freely. If total usage exceeds 64 KB,
// you get error.OutOfMemory instead of unbounded growth.

This is a powerful defensive pattern. In a server, it prevents a single malformed request from consuming unbounded memory. In a game, it ensures a frame’s scratch allocation stays within its budget. The arena gives you fast bump allocation; the fixed buffer gives you a hard ceiling.

Composition is the design

Zig does not give you a “bounded arena” as a special type. Instead, it gives you composable building blocks—arena, fixed buffer, page allocator, GPA—and lets you snap them together. Any allocator can wrap any other allocator. This is why the interface exists.

Common compositions

Allocator compositions you will see in real code
CompositionWhat it gives you
ArenaAllocator(page_allocator) Fast phase-scoped allocation with OS-backed pages; the most common pattern
ArenaAllocator(FixedBufferAllocator) Bounded arena; fast bump allocation with a hard memory ceiling
ArenaAllocator(GeneralPurposeAllocator) Arena with safety checks on the child; useful during development to catch bugs in page management
FixedBufferAllocator alone Zero-overhead allocation from a stack or static buffer; for embedded, kernel, or known-size work

The mental model

Think of memory allocation strategies as a spectrum:

  • At one end, general-purpose allocators (like GPA) track every allocation individually. Maximum flexibility, maximum bookkeeping.
  • At the other end, FixedBufferAllocator is nearly zero bookkeeping—just an offset into a fixed slice—but no flexibility at all.
  • ArenaAllocator sits in the sweet spot: you get the convenience of allocating many objects with different sizes and lifetimes, but the cleanup simplicity of “free everything at once.”

The art is choosing where on this spectrum each part of your program should live. A web server’s request handler? Arena. A fixed-format packet parser in an embedded device? FixedBufferAllocator. A long-lived data structure that outlives any single phase? GPA or page_allocator. The next chapter takes the idea further: you will build your own allocator from scratch.

Watch out

Arenas are not free lunch. Because individual free() is a no-op, memory usage grows monotonically within a phase. If your phase processes a million items and each allocates temporary buffers, those buffers accumulate until deinit() or reset(). If that’s a problem, break the work into sub-phases with their own arenas, or use a different allocator for the temporaries.
