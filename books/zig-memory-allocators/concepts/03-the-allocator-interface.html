Zig Memory Allocators Contents Cheatsheet
03 Two fields, four operations

The Allocator Interface

Zig does not have a global allocator hiding behind new or malloc. Instead, every function that needs heap memory receives an std.mem.Allocator — a tiny, two-field value that tells it where memory comes from and how to ask for it. That value is the entire memory-management contract, and understanding it is the key to everything that follows.

The Struct Itself

Open std.mem.Allocator in the standard library and you will find a struct with exactly two fields: 

pub const Allocator = struct {
    ptr: *anyopaque,
    vtable: *const VTable,
};

That is it. Two pointers, sixteen bytes on a 64-bit machine. The first field, ptr, is an opaque pointer to whatever state the backing allocator needs — a page-table tracker, an arena’s bump pointer, a mutex guarding a free-list. The second, vtable, points to a compile-time-known table of function pointers that implement the four fundamental operations.

Because the struct is only sixteen bytes, Zig passes it by value. You never need to worry about the allocator’s own lifetime or take a pointer to it. Copy it, store it in a field, hand it across threads — it is cheap and safe.

Key insight

An Allocator is not the allocator. It is a handle to one — a fat pointer with a vtable, much like a Rust trait object or a Go interface value. The real allocator lives behind ptr.

The VTable: Four Operations

Every allocator in Zig — whether it wraps mmap, a fixed buffer, or malloc — must provide four function pointers bundled into Allocator.VTable: 

pub const VTable = struct {
    alloc:  *const fn (ctx: *anyopaque, len: usize, log2_align: u8, ret_addr: usize) ?[*]u8,
    resize: *const fn (ctx: *anyopaque, buf: []u8,  log2_align: u8, new_len: usize, ret_addr: usize) bool,
    remap:  *const fn (ctx: *anyopaque, buf: []u8,  log2_align: u8, new_len: usize, ret_addr: usize) ?[*]u8,
    free:   *const fn (ctx: *anyopaque, buf: []u8,  log2_align: u8, ret_addr: usize) void,
};

A few things to notice. Every function receives ctx — the opaque pointer we stored in Allocator.ptr. Alignment is always expressed as log2 of the byte alignment, so an alignment of 16 is passed as 4. And there is a ret_addr parameter that carries the return address of the caller, which safety-oriented allocators use to produce helpful stack traces on double-free or leak reports.

alloc

Returns a many-item pointer (?[*]u8) to a fresh region of at least len bytes, aligned to 1 << log2_align, or null on failure. The memory is undefined — not zeroed. You will almost never call this directly; the convenience wrappers handle casting and error conversion.

resize

Attempts to grow or shrink an existing allocation in place. Returns true on success, false if the backing memory cannot be resized without moving. This is the fast path — no copy, no new pointer. If you need a guarantee of success even when moving is required, use the high-level realloc() wrapper instead.

remap

Like resize, but it may move the data to a new address. Returns the new pointer on success or null on failure. This is the operation that backs realloc().

free

Releases a previously allocated region. You must pass the exact slice and alignment that was returned by alloc or remap. Passing a different slice is undefined behavior — and in debug builds, the GeneralPurposeAllocator will catch it.

How the Pieces Fit Together

Convenience Methods

Nobody works with the vtable directly. The Allocator struct provides a suite of generic methods that handle casting, alignment, error conversion, and destruction for you. These are the ones you will use every day:

High-level allocator methods
Method Returns Purpose
create(T) !*T Allocate a single T, return a typed pointer
destroy(ptr) void Free a single-item pointer returned by create
alloc(T, n) ![]T Allocate a slice of n elements of type T
realloc(buf, n) ![]T Resize (may move); tries resize first, then remap
free(buf) void Release a slice returned by alloc or realloc
dupe(T, src) ![]T Allocate + copy a slice (like strdup but generic)
dupeZ(T, src) ![:0]T Same, but null-terminated (handy for C strings)
resize vs realloc

resize() returns a bool — it succeeds only when the backing memory can grow or shrink without moving. It is a fast, non-failing operation: no allocation, no copy. Use it when you can tolerate failure. realloc() falls back to allocating fresh memory and copying, so it always succeeds (or returns error.OutOfMemory).

Example: create and destroy

The most common single-item pattern is create/destroy. Here we heap-allocate a Node for a linked list: 

const std = @import("std");

const Node = struct {
    value: u32,
    next: ?*Node,
};

pub fn createNode(allocator: std.mem.Allocator, val: u32) !*Node {
    const node = try allocator.create(Node);
    node.* = .{ .value = val, .next = null };
    return node;
}

pub fn destroyNode(allocator: std.mem.Allocator, node: *Node) void {
    allocator.destroy(node);
}

Notice how the function accepts an Allocator by value. It does not know or care whether the caller handed it a page allocator, an arena, or a test stub. That decoupling is the whole point of the interface.

Example: alloc and free

For dynamically sized data, use alloc and free. Here we build a buffer of u8 bytes: 

pub fn readIntoBuffer(allocator: std.mem.Allocator, size: usize) ![]u8 {
    const buf = try allocator.alloc(u8, size);
    errdefer allocator.free(buf);

    // Fill the buffer with data...
    @memset(buf, 0);

    return buf;
}

pub fn main() !void {
    var gpa = std.heap.GeneralPurposeAllocator(.{}){};
    defer _ = gpa.deinit();
    const allocator = gpa.allocator();

    const data = try readIntoBuffer(allocator, 1024);
    defer allocator.free(data);

    // Use data...
}
Watch for errdefer

In readIntoBuffer, the errdefer ensures the buffer is freed if anything after the allocation returns an error. Without it, an early return would leak. Pair every alloc with either a defer free or an errdefer free, depending on who owns the memory after the function returns.

Example: dupe and dupeZ

When you need a heap copy of an existing slice, dupe saves a two-step alloc-then-copy dance: 

pub fn cloneString(allocator: std.mem.Allocator, src: []const u8) ![]u8 {
    return allocator.dupe(u8, src);
}

// For C interop, dupeZ appends a sentinel zero byte:
pub fn toCString(allocator: std.mem.Allocator, src: []const u8) ![:0]u8 {
    return allocator.dupeZ(u8, src);
}

Why This Design Works

The allocator interface achieves something subtle: it decouples allocation policy from business logic. A JSON parser can accept any allocator. In tests you hand it a testing.allocator that fails the test on leak. In production you give it an arena that frees everything in one shot when the request finishes. The parser code never changes.

Because the interface is just two pointers and four functions, implementing your own allocator is straightforward. You fill in a VTable, stash your state behind ptr, and return an Allocator. We will do exactly that in Chapter 6.

No global allocator

Unlike C, C++, Rust (with its default global allocator), or Go, Zig has no implicit allocator. If a function does not take an Allocator parameter, it does not allocate. You can read the function signature and know for certain. That explicitness is the foundation of Zig’s safety story.

You now know the complete shape of the Allocator interface: a two-field struct backed by a four-slot vtable, wrapped in a set of ergonomic generic methods.
