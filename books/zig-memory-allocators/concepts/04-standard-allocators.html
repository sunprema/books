04 The toolbox in std.heap

The Standard Allocators

You know the interface now — two fields, four operations, a handful of convenience methods. But an interface is only useful if there are good implementations behind it. The Zig standard library ships several, each tuned for a different job. This chapter opens the toolbox and examines every tool inside.

The Toolbox at a Glance

Think of std.heap as a drawer of specialized instruments. No single allocator is best for everything, but together they cover the full spectrum from “give me raw OS pages” to “fail my test if I leak a single byte.”

page_allocator

The simplest allocator in the standard library is also the lowest level. std.heap.page_allocator is a pre-built Allocator that talks directly to the operating system — mmap on Linux/macOS, VirtualAlloc on Windows. Every call to alloc reserves whole pages (typically 4 KiB each), even if you only asked for 16 bytes. 

const std = @import("std");

pub fn main() !void {
    const allocator = std.heap.page_allocator;

    // Allocates at least one full OS page (~4 KiB) even though
    // we only asked for 64 bytes.
    const buf = try allocator.alloc(u8, 64);
    defer allocator.free(buf);

    std.debug.print("got {d} bytes at {*}\n", .{ buf.len, buf.ptr });
}
When to use it

page_allocator is perfect when you need a large, long-lived buffer or when you are building a higher-level allocator on top of it (arenas, pools). It is wasteful for small, frequent allocations because every request rounds up to a full page.

GeneralPurposeAllocator

The GeneralPurposeAllocator (often abbreviated GPA, historically known as DebugAllocator) is the workhorse for development and debug builds. It is a full-featured allocator with safety instrumentation that catches the bugs that ruin your week: double-free, use-after-free, and memory leaks.

Basic Setup with Leak Checking

The canonical pattern is to create a GPA, defer its deinit(), and extract an Allocator handle. When deinit() runs, it checks for leaks: 

const std = @import("std");

pub fn main() !void {
    // Create the GPA with default safety options.
    var gpa = std.heap.GeneralPurposeAllocator(.{}){};
    defer {
        const check = gpa.deinit();
        if (check == .leak) {
            std.debug.print("Memory leak detected!\n", .{});
        }
    }

    // Obtain the Allocator interface.
    const allocator = gpa.allocator();

    // Use it like any other allocator.
    const list = try allocator.alloc(u32, 100);
    defer allocator.free(list);

    // If we forgot the defer above, deinit() would report the leak.
}

Configuration Options

The .{} in GeneralPurposeAllocator(.{}) is a configuration struct. The defaults are tuned for safety, but you can adjust them:

GPA configuration fields
Field Default Purpose
.safety true Enable safety checks (double-free, use-after-free detection)
.never_unmap false Keep freed pages mapped to catch use-after-free via segfaults
.stack_trace_frames 6 Number of stack frames captured per allocation (for leak reports)
.thread_safe true Protect internal state with a mutex for multi-threaded use 
// A GPA tuned for aggressive debugging:
var gpa = std.heap.GeneralPurposeAllocator(.{
    .safety = true,
    .never_unmap = true,       // keep pages mapped after free
    .stack_trace_frames = 12,  // deeper traces in leak reports
}){};
Key insight

The GPA’s deinit() returns .leak or .ok. In debug builds this means you get leak reports at program exit with stack traces pointing to the allocation site. This is Zig’s answer to Valgrind and AddressSanitizer, built right into the standard library.

c_allocator

When you are linking against libc — for C interop, calling into C libraries, or running on a platform where mmap is not directly available — std.heap.c_allocator wraps malloc, realloc, and free behind the standard Allocator interface. 

const std = @import("std");

pub fn main() !void {
    // Only available when linking libc (zig build with -lc).
    const allocator = std.heap.c_allocator;

    const msg = try allocator.dupeZ(u8, "Hello from malloc!");
    defer allocator.free(msg);

    // msg is a [:0]u8, safe to pass to any C function expecting
    // a null-terminated string.
    _ = std.c.printf("%s\n", msg.ptr);
}
Warning

c_allocator provides no safety checks. It does not detect leaks, double-free, or use-after-free. Use it only when you must, and prefer wrapping it with a LoggingAllocator during development to trace what it does.

testing.allocator

Every Zig test file gives you std.testing.allocator for free. It is backed by a GPA and is pre-configured to fail the test if any allocation is not freed by the time the test finishes. This is your first line of defense against leaks in library code. 

const std = @import("std");
const testing = std.testing;

test "dynamic array does not leak" {
    var list = std.ArrayList(u32).init(testing.allocator);
    defer list.deinit();

    try list.append(42);
    try testing.expectEqual(@as(u32, 42), list.items[0]);

    // If we omit the defer list.deinit(), this test FAILS.
}
Rule of thumb

If your function takes an Allocator, your test should pass it testing.allocator. This catches leaks at the unit-test level, before they reach production. It is one of the most valuable patterns in the Zig ecosystem.

LoggingAllocator

Sometimes you do not need to catch bugs — you need to see what is happening. The LoggingAllocator wraps any other allocator and logs every operation (alloc, resize, free) to the standard error stream. It is the strace for memory. 

const std = @import("std");

pub fn main() !void {
    var gpa = std.heap.GeneralPurposeAllocator(.{}){};
    defer _ = gpa.deinit();

    // Wrap the GPA in a LoggingAllocator.
    var logging = std.heap.loggingAllocator(gpa.allocator());
    const allocator = logging.allocator();

    // Every operation below is logged to stderr.
    const buf = try allocator.alloc(u8, 256);
    defer allocator.free(buf);

    // stderr output (example):
    //   alloc: 256 bytes at 0x7f...  alignment=1
    //   free:  256 bytes at 0x7f...
}

Because it satisfies the same Allocator interface, you can drop a LoggingAllocator into any code path without changing a single line of business logic. Swap it in, see the pattern of allocations, swap it out.

Side-by-Side Comparison

Standard allocators compared
Allocator Backing Safety Speed Best For
page_allocator OS pages None Slow (syscall) Large buffers, backing other allocators
GeneralPurposeAllocator OS pages Full Moderate Development, debug builds
c_allocator libc malloc None Fast C interop
testing.allocator GPA Full + test fail Moderate Unit tests
LoggingAllocator Any (wrapper) Inherited Inherited + I/O Diagnosing allocation patterns

Choosing the Right One

During development, start with the GeneralPurposeAllocator. Its safety checks will catch the mistakes you will inevitably make. In tests, always use testing.allocator — it is free and catches leaks automatically.

When you need raw performance or are building higher-level allocators, drop down to page_allocator. When you are calling into C libraries that expect malloc-compatible memory, use c_allocator. And when you cannot figure out why your program is allocating so much, wrap your allocator in a LoggingAllocator and read the output.

Key insight

These allocators compose. A LoggingAllocator can wrap a GPA. An arena (Chapter 5) can draw pages from page_allocator. A pool allocator (Chapter 6) can use a GPA as its backing store. The uniform interface makes every combination possible and every swap trivial.

You have now met every allocator that ships in std.heap. The next chapter narrows the focus to two of the most useful patterns in the toolkit: the arena allocator, which lets you allocate many things and free them all at once, and the fixed-buffer allocator, which lets you work without the heap entirely.
