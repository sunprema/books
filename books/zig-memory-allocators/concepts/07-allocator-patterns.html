07 Composition over configuration

Allocator Patterns in Practice

You know how allocators work. You have built one from scratch. Now comes the interesting part: how real Zig programs compose allocators to get clarity, performance, and safety all at once.

Allocator-Aware Containers

Every growable container in the standard library—ArrayList, HashMap, BufMap, BoundedArray—takes an Allocator in its init call. The container never decides where memory comes from. You do.

This is the same dependency-injection idea we saw in Chapter 1, scaled up to data structures. A hash map does not care whether it is backed by an arena, a general-purpose allocator, or a fixed buffer. It only calls alloc, resize, and free through the interface. That separation of concerns is what makes the patterns in this chapter possible.

arraylist with an explicit allocator

const std = @import("std");

pub fn main() !void {
    var gpa = std.heap.GeneralPurposeAllocator(.{}){};
    defer _ = gpa.deinit();
    const allocator = gpa.allocator();

    // The ArrayList does not choose its allocator — we do.
    var list = std.ArrayList(u32).init(allocator);
    defer list.deinit();

    try list.append(42);
    try list.append(99);

    for (list.items) |val| {
        std.debug.print("{d} ", .{val});
    }
}
The API design rule

If your function allocates, accept an Allocator parameter. If it does not allocate, do not accept one. This single convention makes allocation visible at every call site and lets callers choose their strategy. Never embed a hard-coded allocator inside a library.

Wrapper and Composition Allocators

Because every allocator implements the same interface, you can wrap one allocator with another. The wrapper intercepts alloc, resize, and free calls, does something useful, then forwards to the inner allocator. This is composition, not inheritance—and it is extraordinarily powerful.

The standard library ships two wrappers out of the box:

  • std.heap.LoggingAllocator—logs every alloc, resize, and free to std.log. Invaluable for understanding allocation patterns before optimizing.
  • std.testing.FailingAllocator—deliberately fails after a configurable number of allocations. Use it to stress-test error paths that are otherwise hard to exercise.

You can write your own wrappers for metrics, quotas, tracing, or memory tagging. The pattern is always the same: store a reference to the inner allocator, implement the VTable, and delegate.

wrapping with loggingallocator

const std = @import("std");

pub fn main() !void {
    var gpa = std.heap.GeneralPurposeAllocator(.{}){};
    defer _ = gpa.deinit();

    // Wrap the GPA with a logging layer.
    var logging = std.heap.loggingAllocator(gpa.allocator());
    const allocator = logging.allocator();

    // Every alloc/free through `allocator` is now logged.
    const buf = try allocator.alloc(u8, 256);
    defer allocator.free(buf);
}

Per-Subsystem Allocators

In a larger program, handing a different allocator to each subsystem gives you two powers for free:

  • Tracking. You can measure how much memory the network layer, the parser, or the renderer uses—independently.
  • Teardown. When a subsystem shuts down, you can free all of its memory at once by destroying its allocator, without hunting for individual allocations.

A common shape: give each subsystem an ArenaAllocator backed by a shared page_allocator. The subsystem allocates freely, and teardown is a single arena.deinit().

The “Temporary + Permanent” Pattern

Many real programs need two kinds of memory. Scratch memory that lives only for the duration of one request, frame, or computation—and long-lived memory that persists across the program’s lifetime.

The idiomatic solution: use an arena for scratch work and a GeneralPurposeAllocator for the permanent state. The arena is fast (bump allocation, no per-object free), and you reset or destroy it at the end of each unit of work.

per-request arena in a server loop

const std = @import("std");

pub fn main() !void {
    // Long-lived allocator for program state.
    var gpa = std.heap.GeneralPurposeAllocator(.{}){};
    defer _ = gpa.deinit();
    const perm = gpa.allocator();

    // Program-lifetime config loaded once.
    const config = try loadConfig(perm);
    _ = config;

    // Each request gets a fresh arena.
    while (true) {
        var arena = std.heap.ArenaAllocator.init(std.heap.page_allocator);
        defer arena.deinit();  // frees ALL request memory at once

        const scratch = arena.allocator();

        // All parsing, formatting, and temp buffers use `scratch`.
        try handleRequest(scratch);
    }
}
Why this works so well

Arenas make allocation nearly free (just bump a pointer) and deallocation instant (reset the pointer). You never worry about forgetting to free a temporary buffer—the arena takes care of everything when it is destroyed.

C Interop: Bridging Two Worlds

When you call C libraries from Zig, memory ownership gets interesting. If the C library allocates memory that you must free with free(), or if you must pass memory to a C function that will free it, you need to use std.heap.c_allocator. This allocator wraps libc’s malloc and free.

Never mix allocators

Memory allocated by one allocator must be freed by the same allocator. If a C library calls free(), you must have used c_allocator to allocate that memory. Mixing allocators is undefined behavior—corrupted heaps, silent data loss, crashes that only appear in production.

The rule is straightforward: use c_allocator for memory that crosses the Zig/C boundary. For everything else, use whichever Zig allocator suits the job.

Putting It All Together

These patterns are not theoretical. They are how idiomatic Zig programs are structured:

  • Containers accept allocators—they never embed one.
  • Functions that allocate declare it in their signature.
  • Wrappers add logging, metrics, or failure injection without modifying the allocator they wrap.
  • Subsystems get their own allocators for isolation and teardown.
  • Scratch work goes through arenas; long-lived state goes through a GPA or similar.
  • C interop uses c_allocator—never anything else.

Each of these is a direct consequence of the allocator interface design. Because every allocator looks the same from the outside, you can mix, layer, and swap them freely. That is composition over configuration, applied to memory management.

You now have a toolkit of patterns for structuring memory in real programs. The last question is: which allocator should I actually pick? The next chapter answers that with measurements, a decision framework, and an honest look at the trade-offs.
