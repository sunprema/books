06 From interface to implementation

Writing a Custom Allocator

You have used allocators. You have composed them. Now it is time to build one from scratch. By the end of this chapter, you will have a working bump allocator that satisfies the std.mem.Allocator interface, and a clear picture of how to extend the same technique to pool allocators, logging wrappers, and anything else you can imagine.

When you need your own

The standard library covers the common cases—general-purpose, arena, fixed-buffer. But sometimes you need something it does not offer:

  • A pool allocator for fixed-size objects (network packets, AST nodes, ECS components) where every allocation and free is O(1).
  • A logging or counting wrapper that records every allocation for profiling, without changing the underlying strategy.
  • A special-alignment allocator for SIMD data that needs 32-byte or 64-byte alignment.
  • A fail-injecting allocator for stress-testing error paths. (Zig ships std.testing.FailingAllocator for exactly this, but understanding how to build one teaches you the interface.)

The good news: the interface is small. Four functions. One struct. Let us walk through it.

The VTable, step by step

Recall from Chapter 3 that std.mem.Allocator is a thin wrapper around a pointer to a VTable. The VTable has four function pointers:

The four VTable functions
FunctionPurpose
alloc Allocate a block of n bytes with a given alignment. Return the slice, or null on failure.
resize Attempt to grow or shrink an existing allocation in place. Return true if successful, false if the allocator cannot resize without moving.
remap Attempt to remap an existing allocation to a new size, possibly moving it. May return null if not supported.
free Release a previously allocated block.

To build a custom allocator, you:

  1. Define a struct that holds your allocator’s state.
  2. Implement the four VTable functions as methods or namespace functions.
  3. Create a const vtable of type std.mem.Allocator.VTable pointing to those functions.
  4. Expose an allocator() method that returns an std.mem.Allocator using your vtable and a pointer to your state.
The key idea

A custom allocator is just a struct with state and a VTable. The VTable bridges your struct’s methods to the universal std.mem.Allocator interface. Every caller sees the same .alloc(), .free(), .create(), .destroy() API—they never know (or care) what is underneath.

Building a bump allocator

A bump allocator (also called a linear allocator) is the simplest allocator that does real work. It maintains a buffer and an offset. Each allocation advances the offset forward, aligning as needed. Freeing individual allocations is a no-op—you reset the whole thing at once, or you let it go out of scope.

This is exactly what FixedBufferAllocator does internally, but building one yourself is the best way to understand how the VTable fits together.

Step 1: the struct

Our bump allocator needs two pieces of state: the buffer it allocates from, and the current offset within that buffer.

const std = @import("std");

const BumpAllocator = struct {
    buf: []u8,
    offset: usize,

    pub fn init(buf: []u8) BumpAllocator {
        return .{
            .buf = buf,
            .offset = 0,
        };
    }

    pub fn reset(self: *BumpAllocator) void {
        self.offset = 0;
    }
};

Step 2: the alloc function

The alloc function is where the real work happens. It must align the current offset to the requested alignment, check that there is enough room, and return the slice. The ret_addr parameter captures the caller’s return address for debug stack traces—we will not use it in this simple allocator, but we must accept it.

fn bump_alloc(
    ctx: *anyopaque,
    n: usize,
    alignment: u8,
    ret_addr: usize,
) ?[*]u8 {
    _ = ret_addr;
    const self: *BumpAllocator = @ptrCast(@alignCast(ctx));
    const align = @as(usize, 1) << @intCast(alignment);

    // Align the offset forward
    const aligned_offset = std.mem.alignForward(usize, self.offset, align);

    // Check for overflow
    if (aligned_offset + n > self.buf.len) {
        return null; // out of memory
    }

    const result = self.buf[aligned_offset..][0..n];
    self.offset = aligned_offset + n;

    return result.ptr;
}
The ret_addr parameter

Every VTable function receives a ret_addr: usize. This is the return address of the caller—captured via @returnAddress()—so that debug allocators can record a stack trace of who performed each allocation. If your allocator does not need tracing, you can ignore it (assign to _). If you wrap another allocator, pass it through so the inner allocator’s traces stay accurate.

Step 3: free, resize, and remap

Our bump allocator does not support freeing individual blocks or resizing them. That is a legitimate design choice—just return the “not supported” values:

fn bump_resize(
    ctx: *anyopaque,
    buf: []u8,
    buf_align: u8,
    new_len: usize,
    ret_addr: usize,
) ?usize {
    _ = ctx; _ = buf; _ = buf_align; _ = new_len; _ = ret_addr;
    return null; // resize not supported
}

fn bump_remap(
    ctx: *anyopaque,
    buf: []u8,
    buf_align: u8,
    new_len: usize,
    ret_addr: usize,
) ?[*]u8 {
    _ = ctx; _ = buf; _ = buf_align; _ = new_len; _ = ret_addr;
    return null; // remap not supported
}

fn bump_free(
    ctx: *anyopaque,
    buf: []u8,
    buf_align: u8,
    ret_addr: usize,
) void {
    _ = ctx; _ = buf; _ = buf_align; _ = ret_addr;
    // no-op: reset the whole allocator to reclaim memory
}

Step 4: the VTable and allocator() method

Now we tie it all together. We declare a const vtable and add an allocator() method that builds the std.mem.Allocator wrapper:

const BumpAllocator = struct {
    buf: []u8,
    offset: usize,

    // ... init, reset as before ...

    const vtable: std.mem.Allocator.VTable = .{
        .alloc  = bump_alloc,
        .resize = bump_resize,
        .remap  = bump_remap,
        .free   = bump_free,
    };

    pub fn allocator(self: *BumpAllocator) std.mem.Allocator {
        return .{
            .ptr = @ptrCast(self),
            .vtable = &vtable,
        };
    }
};

And that is a complete custom allocator. You can pass bump.allocator() to any function that accepts an std.mem.Allocator—containers, parsers, serializers—and it will bump-allocate from your buffer.

Using the bump allocator

var backing: [8192]u8 = undefined;
var bump = BumpAllocator.init(&backing);
const alloc = bump.allocator();

// Use it like any allocator
const slice = try alloc.alloc(u8, 256);
_ = slice;

// When done, reset to reuse the buffer
bump.reset();

Pool allocator: the concept

A bump allocator is great when you never free individual objects. But what if you need to allocate and free many objects of the same size—say, AST nodes in a compiler, or connection structs in a server? That is the job of a pool allocator (sometimes called a slab allocator).

The idea:

  1. Pre-divide a buffer into fixed-size blocks, each large enough to hold one object.
  2. Maintain a free list—a linked list of available blocks. Initially, every block is on the free list.
  3. To allocate, pop the head of the free list. O(1).
  4. To free, push the block back onto the free list. O(1).

The trick that makes this space-efficient: store the free-list’s next pointer inside the unused block itself. A free block is not holding user data, so you can reuse its bytes for the linked-list node. No extra metadata overhead.

We will not build a full pool allocator here—the alignment and VTable plumbing follow the same pattern as the bump allocator above. The key insight is the data structure: a singly-linked free list whose nodes live inside the free blocks themselves.

Pool allocator: the free-list node trick

const FreeNode = struct {
    next: ?*FreeNode,
};

const PoolAllocator = struct {
    buf: []u8,
    block_size: usize,
    free_head: ?*FreeNode,

    pub fn init(buf: []u8, comptime block_size: usize) PoolAllocator {
        // Block must be large enough to hold a FreeNode
        comptime std.debug.assert(block_size >= @sizeOf(FreeNode));

        var self = PoolAllocator{
            .buf = buf,
            .block_size = block_size,
            .free_head = null,
        };

        // Thread all blocks onto the free list
        var offset: usize = 0;
        while (offset + block_size <= buf.len) : (offset += block_size) {
            const node: *FreeNode = @ptrCast(@alignCast(buf[offset..].ptr));
            node.next = self.free_head;
            self.free_head = node;
        }

        return self;
    }
};

Testing your allocator

Zig’s standard library includes tools purpose-built for testing allocators:

  • std.testing.allocator — a GeneralPurposeAllocator that detects leaks and double-frees. Use it as a reference: if your allocator’s behavior matches this one on the same sequence of operations, you are on solid ground.
  • std.testing.FailingAllocator — wraps any allocator and makes the n-th allocation fail. Use it to verify that code using your allocator handles error.OutOfMemory correctly.

Testing the bump allocator

const testing = @import("std").testing;

test "bump allocator basic usage" {
    var backing: [1024]u8 = undefined;
    var bump = BumpAllocator.init(&backing);
    const alloc = bump.allocator();

    // Allocate a few slices
    const a = try alloc.alloc(u8, 100);
    const b = try alloc.alloc(u32, 10);

    // Verify they don't overlap
    try testing.expect(@intFromPtr(a.ptr) + a.len <= @intFromPtr(b.ptr));

    // Verify out-of-memory when exhausted
    const too_big = alloc.alloc(u8, 2048);
    try testing.expectError(error.OutOfMemory, too_big);
}

test "bump allocator reset" {
    var backing: [256]u8 = undefined;
    var bump = BumpAllocator.init(&backing);
    const alloc = bump.allocator();

    _ = try alloc.alloc(u8, 200);
    bump.reset(); // reclaim everything

    // After reset, we can allocate again from the beginning
    const c = try alloc.alloc(u8, 200);
    try testing.expect(c.len == 200);
}
A word of caution

A custom allocator that passes its own tests is not necessarily correct. The real test is running it under code that uses it heavily—containers, parsers, concurrent tasks. Start by using std.testing.allocator (which catches leaks and misuse) as the baseline, then swap in your custom allocator and verify identical behavior.

Putting it all together

Here is the complete recipe for writing any custom allocator in Zig:

  1. Define a struct with whatever state your strategy needs (buffer + offset for bump, buffer + free list for pool, wrapped allocator + counters for logging).
  2. Implement four functions matching the VTable signatures: alloc, resize, remap, free. Functions you do not support return null (or do nothing for free).
  3. Declare a const vtable of type std.mem.Allocator.VTable pointing to your four functions.
  4. Expose allocator() returning std.mem.Allocator{ .ptr = @ptrCast(self), .vtable = &vtable }.
  5. Test with std.testing.allocator as a reference and FailingAllocator for error-path coverage.

That is the whole pattern. Every allocator in Zig’s standard library—ArenaAllocator, GeneralPurposeAllocator, FixedBufferAllocator—follows exactly these steps. The interface is small by design: four functions, one vtable, and every allocator in the ecosystem becomes interchangeable. In the next chapter, we will see how to use that interchangeability to build allocator-aware APIs, compose allocators in production, and bridge Zig allocators with C code.
