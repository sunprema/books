08 Measure, then decide

Performance and Choosing the Right Allocator

There is no “best” allocator. There is only the best allocator for your workload. This chapter gives you the numbers, the trade-offs, and a decision framework so you can choose with confidence.

Speed Varies by Orders of Magnitude

Not all allocations are equal. A call to page_allocator triggers a system call—microseconds. The GeneralPurposeAllocator manages buckets in user space—hundreds of nanoseconds. An arena just bumps a pointer—single-digit nanoseconds. A FixedBufferAllocator does the same bump with no possibility of a syscall at all.

Those differences compound. In a hot loop that allocates thousands of small objects, the choice between a GPA and an arena can be the difference between milliseconds and microseconds—a 1000x gap.

Measure first

Before you optimize, know what you are optimizing. Use LoggingAllocator or custom instrumentation to answer three questions: How many allocations? What sizes? How long does each live? The answers point directly at the right allocator.

Fragmentation: The Silent Cost

Fragmentation means your allocator has free memory it cannot use because it is broken into pieces too small for the next request. Some allocators are immune to this:

  • page_allocator—always allocates whole pages. No internal fragmentation. External fragmentation is the OS’s problem.
  • ArenaAllocator—never frees individual objects, so fragmentation does not accumulate within a phase. When you reset or destroy the arena, all memory is reclaimed cleanly.
  • Pool allocators—every slot is the same size. No fragmentation by construction.
  • GeneralPurposeAllocator—uses bucket sizes that reduce fragmentation, but in long-running programs with mixed allocation sizes, it can fragment over time.

Embedded and Kernel Targets

On a microcontroller or inside an OS kernel, you cannot call mmap. You might not even have a heap. This is where FixedBufferAllocator shines: back it with a comptime-sized static array, and you get a deterministic allocator with bounded memory use and zero syscalls.

For workloads that need many objects of the same type—network packet buffers, interrupt descriptors, timer entries—a pool allocator gives you constant-time allocation and deallocation with zero fragmentation.

Determinism matters

In safety-critical or real-time code, the worst-case allocation time matters more than the average. Fixed-buffer and pool allocators have O(1) worst-case behavior. General-purpose allocators do not.

Thread Safety

Most Zig allocators are not thread-safe by default. This is deliberate: synchronization has a cost, and you should not pay it when you do not need it.

When you do need thread safety, you have two options:

  • Wrap with ThreadSafeAllocator. This adds a mutex around the inner allocator’s operations. Simple, correct, but serializes all allocations.
  • Per-thread allocators. Give each thread its own arena or GPA. No contention, no locking, maximum throughput. This is the preferred pattern in high-performance concurrent code.

The exceptions are page_allocator and c_allocator, which delegate to the OS or libc and inherit their thread safety.

The Decision Framework

When you are staring at a new module and wondering which allocator to reach for, walk through these questions:

  1. Is this test code? Use std.testing.allocator. It catches leaks and double-frees automatically.
  2. Does the memory cross a C boundary? Use c_allocator. No exceptions.
  3. Is all memory freed at once? (A request, a parse, a frame.) Use an ArenaAllocator.
  4. Is the total memory bounded and known at compile time? Use a FixedBufferAllocator.
  5. Are you allocating many objects of the same size? Use a pool allocator.
  6. None of the above? Start with GeneralPurposeAllocator. It is safe, it detects leaks, and it is good enough for most workloads. Optimize later if measurements say you must.

The Short Version

Start with the GeneralPurposeAllocator. It catches mistakes. When your profiler tells you allocation is a bottleneck, measure your pattern (many small short-lived? same size? bounded total?) and switch to the specialized allocator that fits. Do not optimize what you have not measured.

The golden rule

Correctness first, performance second. The GPA’s safety checks have caught more bugs than arena allocation has saved cycles. Start safe, measure, then specialize.
