Zig Memory Allocators Contents Cheatsheet
02 Stack, heap, and everything between

Memory Foundations

Before we can talk about allocators in detail, we need a shared vocabulary. This chapter covers the ground rules: where memory lives, how alignment works, what happens when allocation fails, and how defer and errdefer keep cleanup correct.

Stack vs. Heap

Every running Zig program has two broad regions of memory to work with. The stack is fast, automatic, and limited in size. The heap is flexible, manually managed, and requires an allocator. Understanding the boundary between them is the first step to writing correct Zig code.

The stack

Local variables live on the stack. When a function is called, the runtime pushes a stack frame containing its locals, parameters, and a return address. When the function returns, the frame is popped and the memory is gone—instantly, with zero cost.

The trade-off is that stack memory is fixed at compile time. You cannot return a pointer to a local variable (the frame vanishes), and you cannot allocate a variable-sized array on the stack based on runtime input. Stack sizes are typically a few megabytes—enough for call chains, not for data sets.

The heap

When you need memory that outlives a function call, or whose size is only known at runtime, you reach for the heap. In Zig, that always means calling an allocator: 

// Stack allocation: size known at compile time, automatic cleanup
var buffer: [256]u8 = undefined;

// Heap allocation: size from runtime, requires an allocator
const data = try allocator.alloc(u8, runtime_size);
defer allocator.free(data);

The stack allocation is a single instruction—just a pointer adjustment. The heap allocation involves bookkeeping, possible system calls, and can fail. That cost is why Zig makes you opt into it explicitly.

Alignment

Every type has an alignment requirement—the address of a value must be evenly divisible by its alignment. This is not a Zig invention; CPUs enforce it. An unaligned load on many architectures either traps or runs slowly.

What makes Zig unusual is that alignment is a first-class part of the type system. A pointer does not just carry a type—it carries an alignment guarantee: 

// A pointer to u32 with the default alignment of 4
var p: *u32 = &value;

// A pointer to u8 with explicit 16-byte alignment (for SIMD)
var q: *align(16) u8 = @alignCast(raw_ptr);

When you ask an allocator for memory, it respects the alignment of the type you are allocating. If you request alloc(u32, 10), the returned pointer is guaranteed to be 4-byte aligned. If you request alloc(u8, n) with a custom alignment, the allocator handles that too.

Common alignments in Zig
Type Size (bytes) Alignment Typical use
u8, bool 1 1 Byte buffers, flags
u16 2 2 Unicode code units, short fields
u32, f32 4 4 Integers, floats, hash values
u64, f64, usize 8 8 Pointers (on 64-bit), sizes, timestamps
SIMD vectors 16–64 16–64 Vectorised math, crypto
anyopaque and usize

Zig uses *anyopaque where C uses void*—a type-erased pointer. The allocator interface stores its internal context this way. Sizes and counts are always usize, matching the pointer width of the target architecture.

Allocation Can Fail

In C, malloc returns NULL on failure—and most programs never check. In Zig, allocation returns an error union: ![]T. That exclamation mark is not decoration. It means the compiler will not let you ignore the failure case. 

// allocator.alloc returns Allocator.Error![]u8
// You must handle the error with try, catch, or an explicit check.

const buf = try allocator.alloc(u8, 4096);
// If alloc fails, `try` returns the error to the caller.
// If it succeeds, `buf` is a valid []u8 slice.

This is critical for the environments Zig targets. On an embedded system with 32 KB of RAM, allocation failure is not an edge case—it is Tuesday. Zig forces you to have a plan.

Out of memory is not a panic

Unlike some languages that abort on OOM, Zig allocators return error.OutOfMemory. Your code can catch it, try a smaller allocation, switch to a fallback path, or propagate the error cleanly. The choice is yours, and the compiler ensures you make one.

The defer and errdefer Pattern

Manual memory management is notoriously error-prone in C: every early return, every error branch, every goto cleanup is a chance to forget a free. Zig solves this with defer and errdefer—two keywords that schedule cleanup to run when the current scope exits.

defer: always runs

A defer statement runs its expression when execution leaves the enclosing block, regardless of whether the exit is normal or due to an error: 

pub fn processFile(allocator: std.mem.Allocator, path: []const u8) !void {
    const file = try std.fs.cwd().openFile(path, .{});
    defer file.close();  // Runs no matter how we exit

    const data = try file.reader().readAllAlloc(allocator, 1 << 20);
    defer allocator.free(data);  // Runs no matter how we exit

    try validate(data);  // If this fails, both defers still run
    try transform(data);
}

Without defer, you would need to free data and close file in every error path. With defer, you write the cleanup once, right next to the acquisition.

errdefer: runs only on error

Sometimes you allocate something that you intend to return to the caller. You do not want to free it on success—only on error. That is what errdefer is for: 

pub fn createBuffer(allocator: std.mem.Allocator, size: usize) ![]u8 {
    const buf = try allocator.alloc(u8, size);
    errdefer allocator.free(buf);  // Only if we return an error

    try initializeBuffer(buf);   // If this fails, buf is freed

    return buf;  // Success: caller now owns buf, errdefer does NOT run
}
The golden pattern

Allocate, then immediately defer or errdefer the corresponding free. Keep acquisition and release adjacent in the source code. This is the single most important idiom for correct memory management in Zig.

The combination of try, defer, and errdefer means Zig programs handle errors and clean up resources without the tangled goto chains of C or the invisible destructors of C++. The control flow is explicit, the cleanup is visible, and the compiler enforces that error unions are handled.

Putting It Together

Here is a slightly larger example that combines everything from this chapter: stack locals, heap allocation, alignment, error handling, and defer/errdefer. 

const std = @import("std");

const Header = struct {
    magic: u32,        // alignment: 4
    version: u16,      // alignment: 2
    payload_len: u32,  // alignment: 4
};

pub fn parseMessage(
    allocator: std.mem.Allocator,
    raw: []const u8,
) !struct { header: Header, payload: []u8 } {
    // Stack: header is a local, fixed-size
    const header = std.mem.bytesAsValue(
        Header,
        raw[0..@sizeOf(Header)],
    );

    // Heap: payload size is dynamic
    const payload = try allocator.alloc(u8, header.payload_len);
    errdefer allocator.free(payload);

    // Copy and validate; errdefer frees payload if this fails
    @memcpy(payload, raw[@sizeOf(Header)..][0..header.payload_len]);
    try validateChecksum(payload);

    return .{ .header = header.*, .payload = payload };
}

fn validateChecksum(data: []const u8) !void {
    _ = data;
    // ... checksum logic ...
}

The Header struct lives on the stack—its size is known at compile time. The payload is heap-allocated because its length comes from the parsed header. The errdefer ensures the payload is freed if validateChecksum fails, but on success the caller receives ownership of the memory.
