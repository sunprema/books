What Happens Inside the Box That Passes Your Message Along

Network people call this: packet processing & forwarding systems

"The router sends the packet on" hides a whole factory. Here is the factory: what it reads, how it finds the way, where packets wait, and why the hardware is shaped by a clock that never stops ticking.

Go back to the sorting room from the last sheet, but make it impossible. Letters come in on sixty-four belts. On each belt, a new letter can arrive every seven billionths of a second. A sorter has to read the address, find the right slot in a book of a million city names, write a new mark on the envelope, and drop it on one of sixty-four outgoing belts — before the next letter lands on top of it.

There is no time to think. There is no time to look in the book twice. If two letters want the same outgoing belt at once, one has to wait somewhere, and if the waiting room is full, a letter is thrown away. And if one sorter gets confused and stops, the letters behind it stop too, even the ones going somewhere else.

This sheet stays in that room the whole way through. Every trick in it — the strange memory, the many small waiting lines, the "start sending before it has all arrived," the factory you can reprogram — is a way to keep that room working at that speed.

The one-glance budget

Every box that moves packets does the same four jobs, in order. It reads the outside of the envelope to find where the useful parts are. It looks up those parts in tables. It changes the envelope (a new next-hop address, one fewer hop left to live, maybe a label pushed on). Then it puts it in line for the right way out, and a scheduler picks what leaves next. Sheet 01 called this the data plane. The control plane only writes the tables; it never touches the packets that fly by.

The hard part is not any one job. It is the clock. The smallest Ethernet packet is 64 bytes, and on the wire it also carries an 8-byte lead-in and a 12-byte quiet gap. That is 84 bytes, or 672 bits, per packet. Divide the line speed by that and you get the budget.

A lookup that needs ten trips to memory in a row cannot fit in two ticks. Everything in this sheet follows from that one line.

"Line rate" on a data sheet usually means big packets. Ask for the smallest-packet number, on all ports at once. Many boxes can't do it, and an attacker who sends tiny packets will find out for you.

Reading the envelope

A packet arrives as a long row of bits. Before any table can be checked, the box has to find where each part is. That job is called parsing. It is a small state machine: read the first wrapper (Ethernet), look at its "what's inside" field, jump to the matching next step (IPv4? IPv6? a label?), read that wrapper, and so on, until it has the fields it needs.

Here is the shape of the IPv4 wrapper the box most often cares about. The three bright fields are the ones a normal router reads or changes on every single packet.

Notice the last row. A wrapper whose length can change makes the reader's job harder, because the next wrapper starts at a different place each time. Hardware readers are built to look only so deep and only so many steps. Packets that need more — odd options, wrappers inside wrappers inside wrappers — get kicked to a slow side path run by a general processor, or dropped. That is one more reason the middle of the Internet dislikes new ideas (the "turning to bone" from Sheet 01): a new wrapper may simply be too deep for the reader.

Finding the right slot in a book of a million names

The sorter's book doesn't list every house. It lists areas, and areas sit inside other areas. One line says "anything in this country goes to belt 3." Another says "this one city goes to belt 7." A third says "this one street goes to belt 12." An address on that street matches all three. The rule is: the most exact match wins. Network people call this longest-prefix match, because the "area" is the first so-many bits of the address, and the line with the most bits wins.

How big is the book? The whole-Internet IPv4 table passed one million areas in 2025, and the count is a bit different depending on where you stand. Add IPv6 and inside-the-company routes and a big router's hardware table needs well over a million lines. There are three ways to build the lookup, and each one spends a different thing.

Way 1: walk a tree, one bit at a time

Make a tree: go left for a 0 bit, right for a 1, and remember the last area you passed. This is called a trie. It is small and easy to update, but an IPv4 address can take up to 32 steps, each one a trip to memory that has to wait for the one before. That's far too slow for a two-tick budget. Real designs read several bits per step (8 bits per step means at most 4 trips) and pack the tree so each step fits in one small, fast memory, with one memory per pipeline stage so each stage does one step.

Way 2: spend memory to save trips

A 1998 design called DIR-24-8 makes one giant list with a line for every possible first-24-bits of an address — 224 lines. Use the top 24 bits as the line number and read the answer in one trip. The rare areas longer than 24 bits point into a second, smaller list for one more trip. Most lookups take one memory read, the rest two. The price is size: the first list alone is about 32 MB. It never went into routers exactly as drawn, but the idea lives on in software forwarding (DPDK's lookup library uses a version of it).

Way 3: ask every line at once

The strangest answer is special memory that you don't read by line number at all. You hand it the address, and every line checks itself at the same moment. Each line holds a value and a "don't care" mask, so a line can say "these 24 bits must match, the last 8 can be anything." If several lines match, a small circuit at the bottom picks the first one. Put longer areas higher up and "first match" becomes "longest match," in one step. This is a TCAM ("ternary content-addressable memory": memory found by what's in it, where each bit can be 0, 1, or don't-care).

It is wonderful and it is costly. Every search charges every line, so it burns power on every packet: one model puts it near 3 millionths of a watt per bit, and an 18-megabit part running at 100–150 million searches a second is quoted at 10 watts or more, where plain fast memory of that size draws 1–2. Each bit also takes several times the chip space of a plain memory bit. And keeping the lines in length order means one new area can force many lines to shift down — slow, at the moment routes are changing fastest.

Ask everyone at once vs. walk to the answer

TCAM

One step, fixed time, handles any mask — also great for firewall-style rules with many fields. Hot, costly per bit, small, and awkward to update in order.

Tree or list in plain memory

Cheap, dense, cool. Scales to millions of lines. Needs several steps, so it needs a pipeline, and its speed depends on the shape of the table.

Big boxes use both: plain memory for the huge, simple tables (the route list), TCAM for the small, messy ones (filters, special cases). Where the line between them is drawn is a cost and power choice, not a correctness one.

Exact matches, and picking among equal roads

Not every table needs "longest." A switch's "which port has this machine's hardware address" table, or a list of known conversations keyed by the five fields (two addresses, two port numbers, protocol), needs an exact match. Those are built by hashing: mash the key into a number, use the number as the line, check the stored key to be sure. It's cheap and fits plain memory, but two keys can land on the same line, so real tables keep a few spots per line or a second hash to fall back on.

Hashing also picks roads. When a table says "four equally good ways out," the box hashes each packet's five fields and uses the result to pick one. Every packet of one conversation gets the same answer, so it stays on one road and arrives in order. This is ECMP ("equal-cost multi-path"). The catch: it spreads conversations, not bytes. Two huge transfers can hash onto the same road while the other three sit idle, and if every layer of a data center uses the same hash, the choices line up and some roads get nothing at all.

Case · 12 August 2014

"512K day": the book outgrew the shelf

Many widely used older routers split their TCAM ahead of time, and the default split held about 512,000 IPv4 routes. The Internet's table had been creeping up on that line for months, sitting around 500K. That day a burst of about 15,000 extra, more-specific routes pushed the count over. On boxes that hadn't been re-split, the routes that didn't fit fell out of the fast hardware path, and traffic slowed or broke in scattered places across the Internet. The maker had warned about it beforehand; the fix was a new split plus a reboot, which many operators hadn't scheduled.

The control plane's list of routes and the data plane's hardware table are different things with different limits. Watch the hardware one — it fails all at once, at a number, on a day someone else picks.

Getting across the room: the switch fabric

After the lookup, the letter knows its outgoing belt. Now it has to physically get there across the room. Inside the box, the thing that connects every way in to every way out is the switch fabric. Small boxes use one shared memory that every port writes into and reads from. Bigger ones use a crossbar — a grid where any input can be joined to any output for a moment — or several layers of smaller grids.

The cleanest design puts all the waiting at the outputs. But think about what that asks: if all 64 inputs send to the same output in the same tick, that output's waiting room has to accept 64 letters in one tick. Its memory must be 64 times faster than one port. At today's speeds, that memory doesn't exist. So designers move the waiting to the inputs, where each memory only has to keep up with its own port.

And that brings back the confused sorter from the opening scene. Give each input one line. The letter at the front wants belt 3, and belt 3 is busy this tick, so it waits. The letter behind it wants belt 5, which is free, but it can't go — it's stuck behind the front one. This is head-of-line blocking. A 1987 paper worked out how bad it is when every input always has something to send and the outputs are picked evenly at random: as the number of ports grows, only about 58.6% of the outputs are busy, on average. Over 40% of the box's capacity, gone, with work waiting.

The fix is to keep the waiting at the inputs but split each input's single line into one small line per output. Now a letter for belt 5 never waits behind a letter for belt 3. These are called virtual output queues. The new problem is choosing, every tick, which inputs talk to which outputs so that nobody gets two partners. A well-known answer from 1999, iSLIP, does it in a few rounds of "ask, offer, accept," with each side taking turns in a circle so nobody is starved. Under even traffic it keeps every output busy, and it was simple enough to build in hardware making about 100 million choices a second for 32 ports. Many fabrics also run their insides a little faster than the ports, so that imperfect choices still don't lose throughput.

58.6% is a number for a model: fixed-size pieces, every input full, outputs picked evenly. Real traffic is lumpier and can be better or much worse. The lesson that survives is the shape: one shared line in front of many choices wastes the choices. You'll see the same shape again in TCP (one lost packet stalls every stream behind it) and in QUIC's fix for that (Sheet 04).

How big should the waiting room be?

Even with a perfect fabric, two inputs can want one output for a while. The extra letters must wait in a buffer, or be thrown away. Too small and you drop bursts that would have fit; too big and letters sit in line so long that the sender's timers think they are lost (Sheet 05 calls this "bufferbloat").

The old rule was "hold one round trip's worth": the time for a message to go there and back, times the link speed. A 2004 paper showed that's far too much on a busy backbone. When thousands of independent conversations share a link, their speed-ups and slow-downs don't line up, and the swings cancel out. You need about the old amount divided by the square root of the number of conversations.

Worked numbers · the waiting room on a backbone link
Link speed × round trip
100 Gb/s × 100 ms = 10 Gb = 1.25 GB
Conversations on the link
n = 10,000 → √n = 100
Divided by √n
1.25 GB ÷ 100 = 12.5 MB
rule of thumb: RTT × C · many flows: RTT × C ÷ √n

That is the difference between memory you must put outside the chip, with all the speed and power that costs, and memory that can sit on the chip itself.

The √n rule needs many long, unrelated conversations. A data-center switch where forty servers all answer one request at the same instant ("incast") is the opposite case: few flows, perfectly lined up. There, shallow buffers drop the whole burst. Fifteen years after the paper, its own authors noted it had changed practice only partly — and these are the reasons.

Starting to send before it has all arrived

The careful sorter waits until the whole letter is in hand, checks the seal, then sends it on. That's store-and-forward: receive all of it, check the error code at the very end, then send. The hurried sorter reads the address on the first line and starts sending while the rest is still coming in. That's cut-through.

At 100 Gb/s and up, the gap shrinks to a fraction of a microsecond per hop. It still matters where every microsecond is money (trading, tightly coupled compute); for most traffic it is lost in the noise of queues.

Cut-through has three honest limits, and people find them annoying because the data sheet number hides them:

  • The error check is at the end of the packet, so a damaged packet is already half-sent before anyone knows. The next box catches it and drops it; the bad packet just went one hop further.
  • It only works if the way out is free right now. If the output is busy, the packet waits in a buffer like anyone else — so under load, every switch is store-and-forward.
  • It can't send from a slow port to a faster one: the outgoing side would run out of bits to send before the incoming side delivers them. Slow-to-fast always stores first.

A factory you can reprogram

For years, every one of those steps was etched into the chip. The chip knew Ethernet, IPv4, IPv6, a few kinds of labels, and nothing else. A new wrapper meant a new chip, two or three years later. These fixed-function chips are still the workhorses, and they keep doubling: in 2025 a single switch chip reached 102.4 Tb/s, enough for 512 ports at 200 Gb/s.

In 2013 a team showed you could keep that speed and still let people decide what the chip reads and does. Their design (they called it RMT, "reconfigurable match tables") has a reader you program as a state machine, then 32 identical stages. Each stage has a pool of plain memory for exact matches, a pool of TCAM for masked matches, and many small units that do the "change the envelope" work. You decide what each stage's table looks at and what its actions do. Their chip ran 960 million packets a second on a 1 GHz clock, about one packet per tick, and they estimated the freedom cost about 15% more chip space and about 12% more power than a fixed chip.

The language people write for these chips is P4. A P4 program says what the wrappers look like, how the reader walks them, which tables exist, and what each table's actions do. The rest — filling the tables — is still the control plane's job. Here is a tiny piece, the kind you'd see in a first lesson:

parser MyParser(packet_in pkt, out headers_t hdr, …) {
  state start {
    pkt.extract(hdr.ethernet);
    transition select(hdr.ethernet.etherType) {
      0x0800: parse_ipv4;
      default: accept;
    }
  }
  state parse_ipv4 { pkt.extract(hdr.ipv4); transition accept; }
}

table ipv4_lpm {
  key     = { hdr.ipv4.dstAddr : lpm; }
  actions = { forward; drop; }
  size    = 1024;
  default_action = drop();
}
  • The parser block is the reader's state machine from 2.2. Start by pulling out the Ethernet wrapper.
  • transition select looks at the "what's inside" field. 0x0800 means IPv4, so go read that; anything else, stop reading.
  • The table is one stage's lookup. Its key is the destination address, matched by lpm — longest-prefix, from 2.3.
  • actions lists what a matching line may do (send to a port, or throw away). If nothing matches, drop.

There is no loop anywhere in a P4 program's packet path, and that is on purpose. A loop could run for as many rounds as it likes, and a chip with a fixed number of stages and a fixed budget of ticks can't promise that. The language only lets you say things the line can finish in time. The architecture a program targets (v1model for the teaching software switch, PSA, or a vendor's own) says which blocks the chip has and what they're allowed to do. The current language rules are version 1.2.5, from 2024.

The same ideas moved to the network card. A SmartNIC or DPU ("data processing unit") puts a programmable packet engine and a set of ordinary processor cores on the card itself — NVIDIA's BlueField-3, for example, has Arm cores and runs at up to 400 Gb/s; AMD's Pensando cards and Intel's IPUs are the same kind of part. Cloud providers use them to run the virtual switch, the encryption and the storage traffic on the card, so the host's own processors are left entirely to the paying customer. Sheet 08 picks up that story.

Case · January 2023

The best-known programmable switch chip stops growing

The RMT ideas reached the market as the Tofino chips, later bought by Intel. Most P4 research ran on them. In January 2023 Intel said it would stop developing new Tofino chips, while still selling and supporting the existing two generations. P4 kept going on network cards, programmable logic chips and in software, and fixed-function switch chips kept doubling.

Programmability won as an idea — every serious design now has flexible readers and tables — but a separate programmable switch chip has to beat fixed chips on speed per watt per dollar, and the fixed chips don't stand still.

The four walls the hardware lives inside

Every choice on this sheet is a way around four walls. It helps to name them, because a design that seems "obviously better" is usually just leaning on a different wall.

  • Memory. Fast on-chip memory is small and spends chip space; big outside memory is slow to reach and needs many pins. Every lookup design picks a point between "one big read" and "many small reads."
  • Power. Every watt a switch chip spends becomes heat in a box packed next to other boxes, and the box can only shed so much. TCAM is the classic power-eater; the chip's input/output wiring is now another, which is why some newest chips move the light-making parts right next to the chip.
  • Time. Each stage gets a fixed number of ticks and a fixed number of trips to memory. A step that might take longer "sometimes" is not allowed, because the next packet is already there.
  • Same every time. A box that is fast on average but slow on some packets builds a line behind the slow ones. So hardware prefers fixed time for every packet over a smarter path that's usually faster — the same reason P4 has no loops.
Freedom vs. same-every-time

Let it be programmed

New wrappers, new telemetry, new tricks in software months later instead of in a new chip years later.

Etch it in

Fewer gates per job, less power, more ports per chip, and a timing promise you can test once and trust forever.

The working answer is freedom inside fixed time: you can change what a stage does, never how long it takes. That's the deal RMT and P4 offer, and it's why they can run at full speed at all.

Check yourself

Check yourself — 01 · budget

A 25 Gb/s server port receives only smallest-size Ethernet packets. How many packets per second is that, and how many nanoseconds does the box get per packet?

Each smallest packet is 672 bits on the wire (64 + 8 lead-in + 12 gap bytes). 25 × 109 ÷ 672 ≈ 37.2 million packets/s, so about 26.9 ns each. Four times the budget of a 100 Gb/s port.

Check yourself — 02 · longest match

The table holds 0.0.0.0/0 → A, 192.168.0.0/16 → B, 192.168.4.0/22 → C, 192.168.5.128/25 → D. Where do 192.168.5.200, 192.168.7.1 and 192.168.8.1 go?

192.168.5.200 → D (the /25 covers .5.128–.5.255, and it's the longest match). 192.168.7.1 → C (the /22 covers .4.0–.7.255). 192.168.8.1 → B (outside the /22, inside the /16). A only catches addresses outside 192.168.0.0/16.

Check yourself — 03 · design review

A vendor sells a top-of-rack switch as "cut-through, 300 ns port to port." Your servers connect at 25 Gb/s and the uplinks are 100 Gb/s, and the uplinks run busy at peak. When will you actually see 300 ns?

Almost never on the path that matters. Server-to-uplink is slow-to-fast, which must store first (the 100 G side would run out of bits). Uplink-to-server is fast-to-slow, which can cut through only when the server port is idle. And whenever the uplinks are busy, packets wait in buffers anyway, so queueing — not the 300 ns — sets the latency. Ask for latency under load and per speed pair.

Check yourself — 04 · waiting room

A 400 Gb/s backbone link carries about 40,000 long-running conversations, with round trips around 80 ms. How much buffer does the √n rule suggest, and what would the old rule say?

Old rule: 400 Gb/s × 0.08 s = 32 Gb = 4 GB. √40,000 = 200, so 4 GB ÷ 200 = 20 MB. The answer only holds if those conversations don't move together; if most of the traffic is a few huge synchronized transfers, plan nearer the old number or use smarter queue management (Sheet 05).

Why does a switch with one waiting line per input lose capacity even when every input has plenty to send?

Once you can see the clock ticking inside the box, every odd piece of router design — the hot memory, the many small lines, the language with no loops — turns from a mystery into the only way to sort a letter in two billionths of a second.
