File Servers

Who actually answers the thirteen messages from the last chapter: kernel devices reached through #, user-level servers built on lib9p, the /srv registry that connects a running server to a name space, and what separates a file-server interface that merely works from one that's good.

The last chapter closed with a promise: the next one is entirely about programs that answer 9P's thirteen messages. Here it is. Every Twalk, every Tread, every Twstat you've seen so far assumed a server on the other end already knew how to reply — this chapter is about what that server actually is, and it turns out to be one of exactly two things: code baked into the kernel, or an ordinary process. Both speak the identical protocol. What differs is distance.

Two places to answer from

A kernel device driver is a 9P server whose messages are dispatched as local procedure calls rather than marshaled onto a wire — no framing, no Tversion, no transport at all, just a function table the kernel calls directly. Four of the thirteen messages (Nop, Session, Flush, Error) have no subroutine equivalent inside a device driver, precisely because they exist to manage a connection, and a local procedure call has no connection to manage.

A user-level server is an ordinary process. It might be a hundred lines of C linked against lib9p, or a shell script wrapping some other program — from a client's point of view it is indistinguishable from a kernel device, because the client never sees the implementation, only the twelve requests and their replies. That indistinguishability is the entire point: chapter 1's claim that local and remote resources are reached identically rests on kernel devices and user-level servers being genuinely interchangeable at the protocol boundary, not merely similar.

The # notation: bootstrapping without a name space yet

By convention, every kernel device is eventually bound to a conventional path — #c becomes /dev, #p becomes /proc. But bind itself needs something already reachable to bind from, and at the very start of a process's life nothing is bound yet. The # notation is how a device is reached before any name space exists to reach it through: a file name beginning with # followed by one device character names the root of that driver's own tree directly, with no lookup through any directory at all. Passing such a name to a system call performs an attach straight to the corresponding driver; any characters between the device letter and the next / are passed through as the attach's aname — #I2, for instance, selects IP protocol stack instance 2.

bind -a '#t' /dev      # graft the serial-port device's root into /dev
bind '#c'    /dev      # the console device — what init does for you at boot
bind '#p'    /proc     # the process device
bind '#s'    /srv      # the srv registry itself is a device, too

You will rarely type one of these yourself. init(8) performs the conventional binds automatically at boot, via newns reading a namespace(6) description file — the mechanism chapter 2 already introduced. By the time an ordinary shell prompt appears, /dev, /proc, and /srv already exist as conventional paths; the # forms are the bootstrap underneath them, not something day-to-day programs reach for. (Typed directly to rc, # also needs quoting — it's rc's comment character.)

Two shapes of kernel device

Device drivers range from trivially flat to genuinely structured. The console device, #c, is the flat case: a one-level directory of small, independently meaningful files — cons for typed input and console output, consctl for control commands, pid/ppid/user/hostowner for identity, time/random/zero/null/reboot rounding it out — each one a plain file answering ordinary open/read/write, never a multiplexed control call. The process device, #p, is the two-level case: the top level lists one numbered directory per live process, and each pid's directory exposes ctl, status, mem, fd, ns, note, text, and more — the exact file tree that lets ps, a debugger, and process control all be plain file I/O rather than dedicated system calls, as chapter 2 already showed.

The /srv registry: how a server gets found

A user-level server has no conventional place in the tree the way a kernel device does — it's just a process holding one end of a pipe. srv, kernel device #s conventionally bound at /srv, is the bulletin board that connects the two: a process creates a file such as /srv/myserv and writes into it the decimal text of an already-open file descriptor, typically one end of a pipe to a lib9p server it just started. Any other process can then open /srv/myserv to get its own reference to that same open file — which is exactly what mount /srv/myserv /some/point does under the hood. The registry entry holds a reference to the file even while nobody has it open; removing the entry releases that reference. Writing a second number into the same server file, or reusing an existing name, is an error.

pipe(p);
fd = create("/srv/namedpipe", OWRITE, 0666);
fprint(fd, "%d", p[0]);   // post one end of the pipe under /srv
close(fd); close(p[0]);

// any other process:
mount(open("/srv/namedpipe", ORDWR), -1, "/n/x", MREPL, "");

The command-line tool srv(4) — a different thing from the srv(3) kernel device, though it's built on it — dials a remote 9P service, runs the version/attach exchange, and posts the resulting connection at /srv/name so any local process can mount it. The 9fs script wraps that plus a conventional mount onto /n/system into one command, which is the ordinary way a Plan 9 user reaches another machine's files at all.

Two things named "srv," one layered on the other srv(3) is the kernel device — the registry mechanism of posting an fd under a name. srv(4) is the command — dial, then use that mechanism to publish the result. Plenty of code posts directly to /srv without going through the command at all.

Writing one: the lib9p serving loop

A user-level server built against lib9p (#include <9p.h>) doesn't hand-roll a read loop. It fills in a Srv struct with one function pointer per 9P transaction, then calls srv(Srv*), which reads T-messages from an infd, dispatches each to the matching function, and writes the R-message to outfd. Every service function must eventually call respond(Req *r, char *error) exactly once — a nil error string means success — after which r and anything it pointed to are considered freed.

typedef struct Srv {
	Tree*	tree;              // non-nil: lib9p resolves walk/perm/dirread itself

	void	(*attach)(Req *r);
	void	(*open)(Req *r);
	void	(*create)(Req *r);
	void	(*read)(Req *r);
	void	(*write)(Req *r);
	void	(*remove)(Req *r);
	void	(*flush)(Req *r);
	void	(*stat)(Req *r);
	void	(*wstat)(Req *r);
	void	(*walk)(Req *r);   // only called when tree is nil
	…
} Srv;

int  srv(Srv *s);
void threadpostmountsrv(Srv *s, char *name, char *mtpt, int flag);
void respond(Req *r, char *error);   // error==nil means success

threadpostmountsrv is the usual way to actually launch one: it allocates a pipe, optionally posts one end at /srv/name via the registry above, forks a child that calls srv() on that end, and optionally mounts the other end at mtpt in the caller's own name space. One call does “start serving, publish it, graft it into my view” — which is why so many Plan 9 commands built this way (ramfs, cdfs, webfs) are so small.

The loop is single-threaded — by design srv's service loop does not read the next request until the current one has been answered. A service function that blocks — on real I/O, a lock, another process — stalls every other client on that connection. The intended fix isn't to make the loop concurrent; it's to hand a slow operation to a separate process and let that process call respond later. flush exists specifically so a client can cancel or hurry along a request left pending that way.

Two ways to hold the tree

lib9p offers a server two strategies for representing what it exposes, chosen by whether Srv.tree is set. With a nonzero File/Tree (built with the companion 9p-file API — alloctree, createfile, removefile, walkfile, opendirfile), lib9p resolves walk itself, checks permissions on open/create/remove/wstat, and serves directory reads — the server's own functions are only called for read/write/create/remove on actual files. That earns its keep when the hierarchy is genuinely dynamic and worth keeping in memory: ramfs, an in-memory file store, is the canonical example.

Leave tree zero and the server takes on more work — implementing walk itself (or handing it to the walkandclone helper with walk1/clone callbacks) and generating directory listings on demand via dirread9p. That's the better trade when the tree is cheap to compute and doesn't need to be remembered: cdfs listing an audio CD's tracks, or nntpfs listing newsgroups, gain nothing from maintaining a File tree that has to be kept in sync with something that already has its own source of truth — and they lose the reference-counting bookkeeping the File API imposes, which its own manual page calls, without irony, “cumbersome.”

exportfs: exporting a name space, not a file system

exportfs answers a different question than ramfs or cdfs: not “serve some data as files,” but “let a remote machine see part of my already-assembled name space.” It is itself an ordinary 9P server, but it has no File tree backing it at all — every request it receives is re-executed as an ordinary system call against the local name space it was started in, and the result relayed back over the connection. Nothing about 9P needed to change to support this; a server can always choose to answer by delegating to the local kernel instead of maintaining its own storage.

Its canonical use is the cpu(1) command. A cpu server dials back to the user's own terminal, starts exportfs there, and mounts the result on /mnt/term — so device files that only make sense on the terminal (the actual console, the actual mouse) stay reachable from processes running on the faster, remote compute server, without those processes needing to know they're remote at all. import(4) is the general-purpose command built on the same idea for any two machines, not just a cpu session.

What makes a file-server interface good

consolefs is a small, complete example worth reading closely, because it shows the design instincts rather than just stating them. It presents each configured serial console as up to three small files — console, consolectl, consolestat — instead of one file overloaded with an ioctl-style side channel. It broadcasts console output to every reader that has the file open, so a shared serial line behaves like a shared terminal rather than a single-reader stream. And it announces every open and close of a console to the other current readers as a plain bracketed text line ([+boris, vlad, barney]) — multi-reader coordination expressed as file content, not as a new system call or a lock API.

That last pattern — a plain data file paired with a same-named ctl file for commands — recurs across nearly every well-designed Plan 9 server: /net/tcp/n/{data,ctl}, /dev/{cons,consctl}, consolefs's own {console,consolectl}. It's the concrete mechanism behind chapter 1's claim that Plan 9 routes control operations themselves through ordinary file I/O: writing text to a ctl file is cat-and-echo reachable, needs no client library, and composes with every other file-oriented tool in the system for free.

The recurring shape of a good design One small, stable directory per logical resource. Control gets its own file, separate from data. A design decision shows up as a name — a numbered connection directory, a per-pid directory, a per-console directory — not as a new operation. And the tree is generated on the fly unless it's genuinely worth keeping in memory, because a generated tree needs no bookkeeping and can't drift out of sync with whatever it's a view of.

What file servers buy the rest of the book

Kernel devices and user-level servers are where the file trees actually live — the things a name space, built by bind and mount, points at. This chapter has been about the tree's source; the next one is about the operators that graft several such trees together into the single coherent view a process sees, including the one question this chapter deliberately deferred: when a union directory has several component trees bound at one point, which of them actually receives a newly created file.
