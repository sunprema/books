The 9P Protocol

The wire format underneath bind and mount: fids, qids, thirteen kinds of request answered one way each, tags that let a connection carry more than one conversation at once, and what actually changed when the protocol became 9P2000.

Chapter two ended on a promise: mount is a front door, and something is being spoken on the other side of it. That something is 9P — the one protocol chapter one told you reaches every resource in the system, local or remote, and the thing the mount device in your kernel is translating your ordinary open/read/write calls into. It is not a large protocol. Thirteen request types, a handful of framing rules, two kinds of identifier. Learn those and you can read any 9P conversation on the wire, which is the point of this chapter — the next one, on file servers, is entirely about programs that answer these messages, and it will assume you can already read them.

The shape of a message

Every 9P message, request or reply, has the same three-field head:

size[4]  type[1]  tag[2]  ...type-specific fields...

size is the length of the entire message, including these four bytes — it's the only thing that tells a reader where this message ends and the next one begins. That matters more than it looks: 9P has no delimiter, no framing byte, nothing but this count. It follows that 9P needs a transport that preserves message boundaries and delivers bytes reliably and in order, and has no mechanism of its own to recover if that transport drops or reorders anything. A pipe already has these properties; raw TCP doesn't delimit messages and UDP doesn't guarantee order, which is exactly why Plan 9 originally paired 9P with a purpose-built transport, IL, instead of just using TCP.

type is one byte naming the message — Tversion, Rattach, and so on, from a fixed enumeration. Multi-byte integers in the fields that follow are little-endian; variable-length data, including every text string, is a two-byte count n followed by n bytes of UTF-8 with no trailing NUL — and the NUL character itself is illegal anywhere in a 9P string, which is what keeps file names, user names, and error text unambiguous without needing a terminator convention at all.

Two identifiers, two different jobs

9P conversations run on two kinds of identifier that are easy to blur together the first time you meet them, because both show up in nearly every message. They answer different questions.

A fid is a 32-bit number the client picks, naming "the file I currently mean" for the rest of a conversation — not restricted to files open for I/O; a directory mid-walk or a file being stat'd is a fid too. Think of it as a handle the client hands the server on every subsequent message about that file. Because the client chooses it, and because a connection's fid space is shared by everyone using that connection, whatever multiplexes several clients onto one connection (the mount device, or a program like exportfs two chapters from now) has to make sure no two callers ever pick the same one.

A qid is the opposite direction: the server's own unforgeable identity for a file, thirteen bytes the server hands back whenever a fid comes to point at something — on auth, attach, walk, open, and create replies. It packs a one-byte type (a directory, an append-only file, and so on — the high bits of the file's mode, echoed), a four-byte version that a server typically bumps on every modification, and an eight-byte path unique across the whole served hierarchy. Two files on one server are the same file if and only if their qids match; a client can hold several different fids that all happen to resolve to one qid, and that's fine — qid identity, not fid identity, is what "the same file" means in 9P.

Tags, and why 9P isn't lockstep

The two-byte tag is chosen by the client and echoed back unchanged in the reply. Its purpose is concurrency: a client may have several T-messages outstanding on one connection at once, as long as no two of them share a tag, and a server is explicitly allowed to delay a reply and answer a later request first. That's not an edge case — it's necessary. A read on a file the kernel synthesizes from keyboard input might have nothing to return yet; a 9P server that could only ever answer requests in the order it received them would have to stall every other client behind that one pending read. Tags are what let it not do that.

There's exactly one reserved tag, NOTAG — (ushort)~0, all bits set — used only for the very first Tversion on a brand-new connection, before ordinary tag-matching rules are even in effect yet.

Don't assume in-order replies It's tempting to treat 9P like a simple call-and-response RPC and assume replies come back in the order requests went out. They don't have to. Code — or a mental model — that assumes strict FIFO ordering will misbehave against a perfectly compliant server the first time it delays one request behind another.

Thirteen requests, one shape each

Every T-message gets an R-message back whose type is exactly one greater, or the universal Rerror carrying a text ename instead — there's no per-message error type, and no Terror at all. (One message, Tflush, can never draw an Rerror; more on that below.) Walking through the set in the order a connection actually uses them:

version and auth — opening the connection

Tversion/Rversion must be the first exchange on any connection, tagged NOTAG, and the client sends no other request until the reply arrives. The client proposes msize, the largest complete message (this four-byte size field included) it will ever send or accept; the server replies with its own msize — which must be no larger than the client's — and either the client's version string, an earlier one it prefers instead, or the literal string "unknown" if it recognizes none of them. A successful exchange resets the whole connection: outstanding I/O aborts, every fid is automatically clunked. Everything between one Tversion and the next is called a session.

Authentication, if the server wants any, rides on top of the ordinary message set rather than being some separate channel. Tauth hands the server a fresh afid plus the uname/aname a following attach will use; a server that doesn't require authentication just answers Rerror, and the client sets afid to NOFID in the attach that follows. A server that does require it replies with an aqid of type QTAUTH, which the client then reads and writes with ordinary Tread/Twrite to run whatever authentication protocol the two sides agree on — 9P itself doesn't define that protocol, which is deliberate; chapter 8 is where factotum fills in what usually goes there.

attach — the fid that means "the whole tree"

Tattach is what turns a bare, version-negotiated connection into an actual client of the server: it binds a client-chosen fid to the root of the exported hierarchy, names the user (uname) and, for a server exporting more than one tree, which one (aname). It is an error if fid is already in use. Every other fid a client ever has on this connection is reached by walking, sooner or later, from this one.

size[4] Tattach tag[2] fid[4] afid[4] uname[s] aname[s]
size[4] Rattach tag[2] qid[13]

walk — descending, one message at a time (or several elements at once)

Twalk takes an existing fid and a proposed newfid, plus a list of path elements, and descends the hierarchy element by element — up to sixteen elements per message (MAXWELEM). That's a cap on one message, not on how deep a path can be; a deeper path just costs more than one Twalk. Rwalk returns one qid per successfully walked element, so a partial failure is visible directly in the count returned (fewer qids than elements requested) without disturbing the original fid or committing newfid — only a fully successful walk makes newfid live. Walking zero elements duplicates fid onto newfid, which is how a client clones a fid before doing something destructive to the copy. ".." is a legal element meaning parent directory (the root's parent is itself); "." never appears on the wire at all — it's resolved locally, before a message is even built.

size[4] Twalk  tag[2] fid[4] newfid[4] nwname[2] nwname×(wname[s])
size[4] Rwalk  tag[2] nwqid[2]  nwqid×(qid[13])

open and create — readying a fid for I/O

Topen and Tcreate both leave a fid ready for read/write and both return a qid plus an iounit — if nonzero, the largest transfer guaranteed not to be split across multiple 9P messages. open's one-byte mode packs an access type (OREAD=0, OWRITE=1, ORDWR=2, OEXEC=3) with two independent bits: OTRUNC to truncate on open, ORCLOSE to remove the file the moment this fid is later clunked. create takes a name and requested permission bits — setting DMDIR, the top bit, asks for a directory instead of a plain file — and the server masks those bits down against the containing directory's own permissions before opening the new file according to mode; asking for world-readable inside a directory that isn't doesn't make the new file world-readable.

read and write — explicit offsets, no server-side cursor

Tread/Twrite move count bytes at an explicit offset on an already-opened fid. That's a deliberate design choice, not an incidental one: 9P is offset-addressed on every call, closer to pread/pwrite than to a stream where the server remembers where you left off. (A Plan 9 seek(2) moves the client's notion of offset and generates no message at all.) Reading a directory instead returns a whole number of stat-shaped entries — the same structure a plain Tstat returns for one file — and a client must resume a directory read exactly where the previous read's byte count left off; seeking to any other directory offset is illegal.

clunk and remove — letting go of a fid

Tclunk tells the server a fid is no longer needed. On its own it never touches the file — it just retires the handle — unless that fid was opened with ORCLOSE, in which case clunking also deletes it. Either way the fid number becomes reusable immediately, and it's invalid to the client from that point even if Rclunk itself somehow comes back as an error. Tremove is exactly a clunk with a delete side effect bolted on: the server always clunks fid, whether or not the removal succeeds, and the request fails outright if the client lacks write permission in the parent directory.

stat and wstat — one structure for reading and writing attributes

Tstat/Rstat and Twstat/Rwstat move one machine-independent directory-entry structure — qid, mode, access and modify times, length, and the textual name/owner/group/last-modifier — the exact structure a directory read hands back one of per entry. A wstat is all-or-nothing: every requested change lands, or none does. A field can be left explicitly untouched — an empty string for a text field, the field's maximum integer value for a numeric one — and permission is scoped per field: renaming needs write permission in the parent, changing length needs it on the file itself, and mode/mtime/group changes are restricted to the owner or the relevant group leader. Nothing in wstat can change who owns a file.

flush and error — canceling, and the one universal failure

Tflush asks the server to abandon a still-pending request named by oldtag. The server must answer immediately with Rflush — never Rerror — and either abort the pending transaction or let it finish before flushing it. The client must wait for that Rflush before reusing oldtag, and, because the original request may already have changed server state by the time it's flushed — a Tcreate that already made a file, a Twalk that already allocated a fid — if the real reply arrives before the Rflush does, the client must honor it as having happened, not treat the flush as having erased it.

Rerror is the one reply any T-message except Tflush can draw instead of its expected answer — there's no Terror, and no per-message error variant. It carries the matching tag and a plain-text ename describing the failure, which a client may truncate if it's unreasonably long, since the string is advisory, not protocol state.

The whole set, at a glance version and auth open the connection; attach claims a root; walk navigates; open/create ready a fid for I/O; read/write move bytes at an offset; clunk/remove let go of a fid; stat/wstat inspect or change attributes; flush cancels; error reports failure. Thirteen requests, thirteen jobs, no overlap.

9P2000 versus the earlier protocol

The message set above is 9P2000's — the version string that's been the default since 2000, and the one every later description of Plan 9 (including this book) assumes. It isn't the protocol's first shape. An earlier revision kept two jobs separate that 9P2000 folds together. A session message used to do connection-opening authentication on its own, before anything else was possible on the connection; 9P2000 splits that into Tversion for negotiation and an optional, separate Tauth for authentication, so a connection that needs no authentication doesn't carry the machinery for it. And a clone message used to exist purely to copy a fid before walking into a directory with it — so the directory's own fid would survive the walk intact; 9P2000 absorbs that into Twalk itself, both by letting a zero-element walk act as a clone and by letting one Twalk carry several path elements in a single message. A clone followed by several single-step walks, in the older protocol, is one Twalk message in 9P2000.

The practical upshot: fewer message round trips for the same navigation, and a cleaner separation between "can we talk at all" (version) and "who are you" (auth), which is exactly the separation chapter 8 needs when it explains why authentication in Plan 9 is optional per server rather than baked into connecting at all.

Two dialects, two different problems

Version negotiation isn't just for picking "9P2000" versus something older — the same Tversion string can name a dialect that adds to 9P2000 rather than replacing it, and a server that doesn't recognize the extended string can legitimately answer with plain "9P2000" instead. Two such dialects matter in practice, and they solve genuinely different problems, not the same problem at two version numbers.

9P2000.u bolts Unix concepts onto the existing messages as extra fields. Base 9P names users and groups only as text; .u adds a numeric n_uname alongside the text uname on attach/auth, so a Unix-flavored server can work with numeric uid/gid directly. It adds a numeric errno hint onto Rerror next to the existing text ename, so a client that can't match the string against a table still has a numeric fallback. And it adds an extension string to the stat/wstat structure, letting device-special files, symbolic links, and hard links — concepts base 9P2000 has no notion of — be represented inside the existing stat message instead of inventing new ones.

9P2000.L takes the opposite approach, and it exists for a different consumer: Linux's own v9fs client (and things built on it, like QEMU's virtio-9p transport), which needs to answer to the Linux VFS layer, not extend Plan 9's file model. Rather than adding a few fields to the messages above, .L keeps a subset of 9P2000's core and lays a parallel set of Linux-shaped messages alongside it: Tlopen/Tlcreate (open and create using Linux's O_* flags instead of the mode byte), Tsymlink, Tmknod, Tlink, Trename/Trenameat, Treadlink, Tgetattr/Tsetattr in place of stat/wstat, Txattrwalk/Txattrcreate, Treaddir, Tfsync, and Tlock/Tgetlock for POSIX advisory locking. Errors on .L travel through Rlerror, which carries only a numeric Linux errno — no text string at all, the opposite tradeoff from .u's string-plus-hint.

.u and .L aren't the same idea twice It's easy to assume .L is just .u, later and more complete. They're not in a superset relationship: .u solves "represent Unix-only file kinds inside 9P2000's own message shapes," .L solves "answer to the Linux VFS directly," with a mostly disjoint set of new messages and a different error-reporting convention. A server speaking one doesn't thereby speak the other, and a client has to negotiate the specific string it wants.

So what did we actually gain?

Thirteen request types, a three-field message head, two identifiers that never get confused for each other once you know which direction each one points, and a tag scheme that turns "one connection" into "as many concurrent conversations as you have tags for." That's the entire protocol chapter one promised you was universal — the same thirteen messages serve a local kernel device and a file server three networks away, because nothing about them assumes locality. And it's the same thirteen messages bind and mount were quietly wrapping the whole time: mount's fd becomes a Tversion/Tattach pair before you ever see a prompt again, and every subsequent path lookup through that mount point is a Twalk you never typed. The next chapter opens the other end of the wire: what it actually takes to write something that answers these thirteen messages well — kernel devices, the lib9p serving loop, and what makes a good file-server interface in the first place.
