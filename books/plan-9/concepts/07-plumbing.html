Plumbing

Chapter 6 closed on a promise: an inter-application message bus, built, of course, as a file server. This chapter cashes it in. Everything the plumber needs already exists in this book — files as the uniform interface (ch. 1), a namespace to mount it into (ch. 2), 9P to talk to it (ch. 3), and the user-level file-server pattern itself (ch. 4). Plumbing invents no new mechanism at all; it is what falls out when you apply the existing ones to a genuinely new problem: routing messages between interactive programs.

The problem is small and familiar: a compiler prints rmstar.c:32: syntax error, and you want your editor to open rmstar.c at line 32 without retyping either. The usual answers — teach every program its own table of "what to do with this kind of text," or make the user cut, copy, and paste by hand — don't scale and don't generalize. Plan 9 centralizes the decision instead: one program, the plumber, receives messages from any application and decides, from the message's own content and a set of configurable rules, where it goes — without the sender naming a recipient and without the user carrying the data there themselves.

A router with no wires — just files

The plumber is a user-level file server, mounted by convention at /mnt/plumb. A program that wants to send a message writes it to /mnt/plumb/send; a program that wants to receive messages reads them from a port — another file under /mnt/plumb, such as /mnt/plumb/edit, which by convention is where text editors read requests to open a file. Nothing here is a socket, a signal, or a new system call. It's write and read on files that happen to be served by a program instead of a disk, exactly the pattern chapter 4 already established for every other Plan 9 service.

The message: six header lines and a blob

A plumb message is a fixed six-line textual header, one property per line in a set order, followed by a free-format data section with no terminating newline. Any header line may be blank except the last, which must be an accurate byte count of the data — only the data section is allowed to contain embedded newlines of its own.

FieldHolds
srcthe sending application's name
dsta destination port, if the sender already knows one
wdirworking directory, used to resolve a relative file name in the data
typea MIME-like tag, e.g. text — the only type currently interpreted
attrblank-separated name=value pairs, quoted as in rc(1)
ndatathe byte length of the data section that follows
datathe payload itself — a filename, a URL, arbitrary bytes

Here is a real message — it tells the editor to open /usr/rob/src/mem.c at line 27:

src   plumbtest
dst   edit
wdir  /usr/rob/src
type  text
attr  addr=27
ndata 5
data  mem.c

The C library wraps this in a struct instead of making every client parse text by hand:

typedef struct Plumbmsg  Plumbmsg;
typedef struct Plumbattr Plumbattr;

struct Plumbmsg {
	char *src;    /* source application */
	char *dst;    /* destination port */
	char *wdir;   /* working directory */
	char *type;   /* type of data, e.g. "text" */
	Plumbattr *attr;
	int  ndata;
	char *data;
};

struct Plumbattr {
	char *name;
	char *value;
	Plumbattr *next;
};

plumb(2) supplies plumbopen, plumbsend, plumbrecv, plumbpack/plumbunpack, and attribute helpers (plumblookup, plumbaddattr, plumbdelattr) so a client builds, sends, and parses messages against this struct rather than hand-rolling the wire format. From the shell, the plumb(1) command does the same job: plumb mem.c sends a message built from its arguments, with -s/-d/-t/-a/-w to set fields explicitly and -i to take the data from standard input.

Rules: patterns, then actions

The plumber's behavior comes entirely from a rules file (default $home/lib/plumbing), not from code compiled into it. The file is a sequence of blank-line-separated rule sets; each contains one or more one-line patterns followed by one or more one-line actions. Lines starting with # are comments, and an include file line splices in a shared fragment, searched first relative to the plumber's own directory and then in /sys/lib/plumb — the same library-of-rules idea a house name space (ch. 5) uses for shared bindings.

Every rule, pattern or action, has the same three-part shape: object verb [arguments]. A pattern's object names a message field (src, dst, wdir, type, data, attr) or arg, the current rule's own argument; an action's object is always the keyword plumb. Rule sets are tried top to bottom against an incoming message; the first whose patterns all succeed fires, and the rest are ignored. If none fires, the write to send fails — unless the message already names an existing dst port, in which case it's emitted there unchanged.

RuleEffect
field is argpattern — exact text match
field isdirpattern — field names an existing directory; sets $dir
field isfilepattern — field names an existing file; sets $file
data matches repattern — regex match; sets $0, $1, … to the match and submatches
attr add name=valrewrite — append an attribute (always succeeds)
attr delete namerewrite — remove an attribute if present (always succeeds)
field set valuerewrite — overwrite a field's value (always succeeds)
plumb to portaction — name the message's destination port
plumb client cmdaction — if no reader, start cmd, hold the message for it
plumb start cmdaction — if no reader, start cmd, discard the message

Rewrite rules (add, delete, set) always succeed — they aren't tests, so put them after the matching patterns in a rule set, or they'll mutate the message before it's even confirmed to be the right kind.

plumb to is the one rule evaluated out of order If an incoming message already has a dst set, a rule set only matches when its own plumb to names that same port — the sender's stated destination constrains which rule sets are even eligible, rather than being just another field the patterns happen to check.

Finding the file inside the sentence

If the user selected exactly rmstar.c, a plain data matches rule against the whole string would be enough. But usually they just point — a mouse click somewhere inside make nightmare>horse.gif — and the plumber has to figure out which substring was meant. The sending program marks this case with a click attribute: a numeric offset into the data giving the cursor position. When it's present, data matches rules stop requiring a whole-string match and instead find the longest leftmost match that touches the click position.

A rule set commonly uses two matches patterns for exactly this reason, and both must match the identical substring for the set to succeed:

data matches '[a-zA-Z0-9_\-./]+'
data matches '([a-zA-Z0-9_\-./]+)\.(jpe?g|gif|bit)'

The first, loose pattern grabs every filename-ish character around the click — it would happily match horse.gift. The second, stricter pattern demands a known image suffix; matched against horse.gift it can only match the shorter horse.gif prefix, so the two patterns disagree on where the string ends and the rule set fails — correctly refusing to treat a sentence ending in "the horse.gift" as a picture file. Once a click has been resolved to a substring this way, the plumber deletes the click attribute before the message goes out; the recipient never sees it.

Worked example: from compiler error to open editor

Put the pieces together on the motivating example. A build fails and prints rmstar.c:32: syntax error; the user points at it in a terminal window and invokes plumb. The terminal emulator sends the surrounding text as a message, with type=text and a click attribute marking the cursor.

The rule set doing this work looks close to the one in the manual for exactly this case:

# existing files, possibly tagged by an address, go to the editor
data matches '([.a-zA-Z0-9_/\-]*[a-zA-Z0-9_/\-])('$addr')?'
arg isfile $1
data set $1
attr add addr=$3
plumb to edit
plumb client window $editor

The first line's regex extracts a plausible file path (plus an optional trailing address like :32); arg isfile $1 confirms it actually exists in wdir. The rewrites that follow replace the data with the bare filename and attach the line number as an addr attribute. Finally, plumb to edit names the port, and plumb client window $editor covers the case where no editor is running yet: start one, and hand it the message once it opens edit for itself.

Starting a program versus waiting for one

If the named port already has a reader — some running program has /mnt/plumb/edit open — the message is delivered immediately and any client/start action in the rule set is simply not needed. If nothing has the port open yet, the plumber falls back to whichever of the two startup actions the rule set specifies, and the choice between them matters:

  • plumb start cmd runs cmd and discards the message — fire-and-forget, appropriate when the command is self-sufficient (it takes what it needs from its own arguments).
  • plumb client cmd runs cmd but retains the message, delivering it once that program opens the port itself — required when the program needs the message's structured fields, such as the addr attribute above, rather than just a bare filename on its command line.

Ports themselves come and go the same way file servers usually don't: the set of ports is created dynamically, one per unique destination named by a plumb to rule anywhere in the active rules. But a port, once created, is never deleted — if a later edit to the rules file removes every rule mentioning it, the port file persists; it just stops receiving anything.

The rules file is itself a live file /mnt/plumb/rules reads back the text of the currently active rule set. Appending to it — with an ordinary text editor, or echo >> — adds new rule sets immediately, no restart. Opening it with truncation clears the rules entirely. This is the same trick chapter 4's synthetic file trees use everywhere: configuration as a writable file instead of a daemon you signal or a service you restart.

Delivery is fast because it doesn't wait

If several clients have the same port open, each gets its own independent copy — the plumber fans a message out, it doesn't pick one winner. And a write to send succeeds as soon as the message is queued for its destination, not once some reader has actually consumed it, so a slow or absent recipient never blocks the sender.

Queued is not the same as delivered There is no acknowledgment of receipt — only of the write succeeding. If the intended reader exits while messages are still queued for it, those messages are simply gone, and the sender has no way to find out. The design deliberately favors not blocking the user interface over guaranteeing delivery; for a UI mechanism rather than a general reliable IPC channel, that trade has held up well in practice, but it is a real limitation, not a detail to gloss over.

Why a file server, of everything

It would be easy to read the plumber as an odd, bespoke piece of infrastructure bolted onto the system. It's closer to the opposite: nothing about it required new technology, because everything it needed — a synthetic file tree, 9P as the transport, a namespace to mount it into — already existed for other reasons. Two consequences fall out of building it that way instead of as a dedicated IPC service:

First, plumbing crosses the network for free. Because the plumber is just another Plan 9 file server, its files can be exported and mounted exactly like any other (ch. 4), so a window system and the applications it talks to can live on separate machines and still share one plumber instance, with no extra protocol. Second, its access control is the file permission system chapter 3 already gave every 9P file — no one else can open your private plumbing ports, because they're files owned like any other, not a global bus with its own separate authorization model bolted on.

The one honest limitation, documented in the plumber's own manual page as a bug rather than papered over: its name space is effectively fixed once it starts running, so rules that reference files under a service mounted after the plumber came up are hard to make work reliably. A namespace, once handed to a long-running server, isn't something that server keeps re-consulting for what's new in it.

Everything in this chapter reduces to one idea applied at a slightly larger scale than usual: a program that serves files, whose files happen to encode "what should happen to this piece of data," addressed and secured by exactly the namespace and protocol machinery already in place. File permissions are as far as that access control goes, though — the plumber trusts whatever name space and identity a process already has. The next chapter asks the question this one quietly assumes an answer to: what establishes that identity in the first place, and what happens when a namespace alone isn't enough to prove who's asking.
