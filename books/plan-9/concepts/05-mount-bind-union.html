Mount, Bind, and Union Directories

Chapter 2 introduced bind and mount and set their flag argument aside for later. This is later: MREPL/MBEFORE/MAFTER/MCREATE in full, how a union directory resolves a lookup, a read, and — the question chapter 4 deliberately deferred — a create, plus unmount and a look at the kernel structure that makes all of it work.

Two chapters back, you saw the shape of bind and mount and were told to file away that their flag argument exists. Here's the filing cabinet. Nothing new gets bolted on: the same two system calls, the same one flag, examined at the resolution this book has been building toward since chapter 1 — because it turns out that resolution is most of what makes a Plan 9 name space actually useful day to day, rather than just cleanly designed.

The four flags, precisely

Every bind and mount call ends in a flag argument, and that argument is built from exactly five bits, three of which are mutually exclusive positions and two of which are independent modifiers you OR on top:

int bind(char *name, char *old, int flag);
int mount(int fd, int afd, char *old, int flag, char *aname);

/* flag is one of: */
MREPL     // replace old outright (the default, value 0)
MBEFORE   // splice the new directory onto the FRONT of the union at old
MAFTER    // splice the new directory onto the BACK of the union at old
/* OR in: */
MCREATE   // mark this component eligible to receive a newly created file
MCACHE    // mount only: cache this mount's file contents locally

MREPL is the plain case: old is simply replaced by whatever name names, or by the tree mount just attached. If the result is a directory — which for mount is guaranteed, since a mount target must already be a directory — old becomes a union directory with exactly one member. MBEFORE and MAFTER are where "union" stops being a one-member degenerate case: both require old and the incoming directory to already be directories, and both add to whatever union is already sitting at old rather than replacing it — MBEFORE at the front, searched first; MAFTER at the back, searched last. MCREATE is orthogonal to all three positions: it says nothing about search order, only that this particular component is allowed to receive a file that doesn't exist yet anywhere in the union. MCACHE, valid on mount only, turns on local caching of that mount's file contents; without it, every read goes back to the server, and even with it on, the cache's currency is re-checked at each open, not on every read.

Flagbind/mount optionEffect on the union at old
MREPL(none)replaces old; becomes a one-member union if a directory
MBEFORE-badded to the front — searched first
MAFTER-aadded to the back — searched last
MCREATE-corthogonal: marks this member create-eligible
MCACHE-C (mount only)orthogonal: enables client-side content caching

The command-line tools use exactly this vocabulary, one option letter per bit: bind -b new old is an MBEFORE bind, bind -a -c new old is MAFTER|MCREATE, and so on. mount takes the same letters plus two more of its own — -k keypattern to constrain which factotum(4) key an authenticated mount may use, and -n to skip authentication entirely. A namespace(6) description file, the boot-time script chapter 2 walked through, uses these identical letters on its own bind and mount lines — there is no second vocabulary to learn for scripting a name space versus building one interactively.

What a union directory actually does

Stack more than one directory at a single point with MBEFORE/MAFTER and old becomes a union directory: Plan 9's own description of it is that it behaves like the concatenation of its members, in the order they were added. That single word does the work for both operations you'll actually perform on it. A lookup — opening or stat’ing a name inside the union — walks the members in order and returns the first one that has that name; the rest are never even consulted. A directory read — listing the union itself, the way ls does — concatenates each member's listing in that same order, so a name present in two members shows up twice in a plain listing even though only the first copy is ever reachable by opening it.

The canonical union: /bin

The single most-exercised union directory on any running Plan 9 system is /bin itself. It's built from /$cputype/bin — the compiled binaries for whatever architecture this machine actually is — unioned with /rc/bin, the architecture-independent shell scripts, and typically a user's own private directory besides. Because that search order is a structural property of the name space rather than a value some shell has to remember, it retires the usual solution to "where do my commands live": Plan 9's shell, rc, has no $PATH variable at all. There's nothing for it to consult; the union already is the search path, and it composes with the rest of the file model instead of standing outside it.

# architecture binaries, then rc scripts, then a private, writable directory
bind -a /386/bin  /bin      # -a = MAFTER: append at the end of the union
bind -a /rc/bin   /bin      # -a = MAFTER: append after that
bind -b -c $home/bin /bin   # -b -c = MBEFORE|MCREATE: search ME first, and
                             #   anything I *create* lands here — not in
                             #   /bin's public, read-only members

That last line is worth sitting with, because it's the pattern behind nearly every private-directory-in-a-public-union you'll see on a real system: -b puts your directory first in search order, so your own date shadows the system one if you happen to have written one; -c separately marks it as where new files should go. Neither flag implies the other — you could search your directory first without it accepting creates, or accept creates into a directory buried at the back of the union. The next section is about exactly that second question.

Who gets a newly created file

Chapter 4 closed by deferring this exact question: when a union has several members, which one receives a file that create makes with a genuinely new name? The rule Plan 9's designers settled on after several attempts is narrow and specific. By default, a member of a union accepts no new files — though create on a name that already exists in that member still succeeds normally, MCREATE governs only names that don't exist anywhere in the union yet. Binding or mounting a member with MCREATE set marks it, specifically, as eligible. When a create for a new name lands in the union, the members are tried in the union's search order, and the file is made in the first one that has create permission; if that particular create fails — no write permission, say — the whole call fails outright. It does not fall through and try the next eligible member.

That's a deliberately narrow rule, and it earns its keep on exactly the pattern from the /bin example above: put a private, writable directory anywhere in an otherwise public, read-only union, mark only it MCREATE, and every new file you create is guaranteed to land there — never accidentally written into a shared system directory you happen to have permission to search but not to add to.

MCREATE is not "this is the writable one" A union with zero MCREATE members isn't read-only for files that already exist there — ordinary open for write and create-on-an-existing-name still work through normal permission checks on whichever member the lookup finds first. MCREATE only decides where a brand-new name is allowed to be born.

Under the hood: the mount table and channel lists

The kernel's own representation of "search each member in order" is worth seeing, because it's smaller than it sounds. Every open file the kernel is tracking is a structure called a channel, and the whole name space is stored as a mount table: a list of (from, to) channel pairs. Whenever a walk successfully advances a channel to some name, the mount table is checked for a from entry matching that name; if there's a hit, the to channel is cloned and substituted for the one the walk was using — that substitution is a bind or a mount, mechanically. A union directory is nothing more exotic than what happens when that to entry is a linked list of channels instead of a single one, one link per union member in bind order. A walk that fails to find its target in the first channel simply follows the list, clones the next channel, and tries the walk again there — which is the "search order, first match" rule from a few paragraphs back, restated as what actually happens one channel at a time.

Undoing it: unmount

int unmount(char *name, char *old);

unmount reverses a bind or mount, and its two arguments give it two distinct behaviors. Pass a name — evaluated exactly as bind's name argument would be — and only the specific binding that would attach that result to old is undone; any other members of a union sitting at old are left exactly as they were. Pass zero for name, or omit it entirely at the command line, and everything currently bound or mounted at old is removed in one call — the whole union, however many members it has.

# undo just this one binding, leaving the rest of the union at /mips/lib/libc.a alone
unmount /n/dump/1992/0716/mips/lib/libc.a /mips/lib/libc.a

# undo EVERYTHING bound or mounted at this point
unmount /mips/lib/libc.a
The one-argument form is not "undo my last bind" It reads that way, but it removes every member of the union at old, not just the most recent one. If you only want to peel off what you just added, pass both arguments — the same name and old you bound or mounted with.

One more constraint, documented plainly as a note on mount(2): the call does not return until it has successfully attached to the server on the other end of fd, which means the process calling mount cannot be the same process serving that connection — posting one end for a server to answer and mounting the other end has to happen from two separate processes, or the server side has to already be running before the mount is attempted.

Same two calls, all the way down

Notice what didn't happen in this chapter: no new system call, no new file, no new protocol message. bind and mount plus one five-bit flag account for every union directory on a running system, including /bin, and every line a namespace(6) file or ns(1)'s output ever prints is one of these same two calls with one of these same four position/eligibility bits spelled out as a letter. The next chapter turns to the other half of the equation this book has been assuming so far — not what a name space is built from, but how it's inherited, copied, or started empty across rfork and process creation, and what /proc looks like from the inside of the processes it's tracking.
