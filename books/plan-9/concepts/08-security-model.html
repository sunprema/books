Security and the Capability Model

Every earlier chapter quietly assumed an answer to a question it never asked: what stops a process from binding, mounting, or reading something it shouldn't? This chapter answers it, and the answer is almost disappointingly familiar — there is no new mechanism. Plan 9 has no root, no setuid bit, and no separate permission system bolted on top of the file model. It has a namespace a process can be handed a restricted view of (ch. 2, ch. 6's RFNOMNT), ordinary file permissions on whatever that namespace exposes (ch. 3), and exactly one new component: a single agent, factotum, that holds secrets so nothing else has to.

Start with what's missing. Unix's root can do anything, and a setuid binary is a program that borrows root's power for one exec. Plan 9 has neither. A new process always runs as whoever created it — there is no bit on a binary that changes that. So how does anything ever change identity: a login shell on a shared machine, a mail server reading someone's mailbox? Through a narrow, explicit, auditable exchange: prove who you are to an agent that already knows, and the kernel hands you a one-time token for exactly that identity change. Everything in this chapter is that exchange, examined at three different distances — the agent, the wire protocol it rides on, and the kernel primitive underneath it.

There is no root — there is a host owner

Every Plan 9 machine has exactly one user id that starts out owning its local resources — the scheduler, the disks, the network interfaces. That id is called the host owner. On a single-user terminal it's simply whoever uses the machine; on a shared CPU or file server it's typically a pseudo-user with no one actually logged in as it. It is tempting to read "owns everything at boot" as "root," but the paper is explicit that the resemblance stops there: the host owner has no privileges hardcoded into the kernel. It is, in its own words, "just a regular user that happens to own the resources of the local machine." Whatever power it has is a starting allocation of ownership, not a rule the kernel enforces on its behalf.

At boot, the kernel starts one process running as the host owner: factotum. Everything else in this chapter is either factotum doing its job, or the narrow kernel support that job needs.

One agent, instead of crypto everywhere

The old design embedded authentication directly in 9P and compiled cryptographic code into every program and kernel module that needed it. That meant a protocol fix required recompiling and relinking everything that used it, and a compromised server inherited whatever privilege it needed to do its own authentication. The fix is the same move this book has made twice already — process control folded into /proc files (ch. 6), interprocess routing folded into the plumber (ch. 7) — applied to secrets: pull the sensitive logic out into one file server, and let every program that needs it be a client instead of an implementer.

factotum is a single per-user agent process that holds a copy of the user's keys and negotiates every authentication protocol on the user's behalf, conventionally mounted at /mnt/factotum. No other program contains cryptographic code at all — it asks factotum to do the negotiating and gets back only a yes/no and, if it asked, an identity. This buys four things at once: a broken protocol is fixed in one place instead of relinking every server that used it; ordinary services can run at lower, unprivileged levels because the sensitive code isn't in them; every service's keys are managed the same way; and unmodified legacy programs get single sign-on for free, because factotum — not the program — does the prompting.

FilePurpose
rpceach open is a private conversation channel; the actual authentication transactions happen here
ctlwrite key / delkey commands to add or remove keys; read it back to list current keys (public attributes only)
protoread-only list of protocols this factotum supports
confirma GUI reads this to learn when a confirm-tagged key is about to be used and needs the user's yes/no
needkeya GUI reads this to learn a requested key is missing, so it can prompt and create one via ctl
loga trace of operations, for debugging

The permissions on that file tree are the access control — nothing about the protocol adds a second check on top of them:

% cd /mnt/factotum
% ls -l
-lrw------- gre gre 0 Jan 30 22:17 confirm
--rw------- gre gre 0 Jan 30 22:17 ctl
-lr-------- gre gre 0 Jan 30 22:17 log
-lrw------- gre gre 0 Jan 30 22:17 needkey
--r--r--r-- gre gre 0 Jan 30 22:17 proto
--rw-rw-rw- gre gre 0 Jan 30 22:17 rpc

Only rpc is world-writable — anyone can ask to authenticate through it — while ctl, confirm, needkey, and log are owner-only, because they touch or reveal the keys themselves.

Keys are text, and secrets are marked, not hidden away

A key is a set of attribute=value pairs — plain UTF-8 text, not a binary blob or a certificate. That's a deliberate choice: a user can read and audit a text key the way almost nobody can read the inside of an X.509 certificate. An attribute prefixed with ! is secret — factotum never prints its value and never lets it leave its own address space, with one narrow, explicitly-flagged exception (a key with proto=pass, whose entire purpose is to hand over a plaintext password).

dom=bell-labs.com proto=p9sk1 user=gre
    !password='don''t tell'
proto=apop server=x.y.com user=gre
    !password='bite me'

A program selects a key with a query: a list of attribute=value terms (must match exactly) and/or attribute? terms (must merely exist). A key matches only if every term in the query is satisfied — e.g. proto=apop server=x.y.com user? !password? finds the second key above without the caller ever seeing what the password actually is.

Authenticating over 9P: a file, not a special message

Chapter 3 already introduced the shape of this: Tauth hands the server a fresh afid for the uname/aname a later Tattach will use, and a server that requires authentication answers with an aqid of type QTAUTH. What that chapter deferred is what happens on that fid — and the answer is the same move as everything else in this book: ordinary Tread/Twrite. 9P itself never defines the authentication protocol that runs over those reads and writes; it only provides a numbered file for two factotums to exchange opaque bytes through. That's precisely why Plan 9 has changed its authentication protocol more than once without ever touching 9P's specification.

The user-level system call fauth(int fd, char *servicename) requests this authentication file directly. Once the exchange over it succeeds, the very same file descriptor — afd — is presented to mount as proof of identity. It behaves exactly like a capability: it can be handed to another process, kept for later reuse, or closed outright to revoke it. Almost nothing calls fauth and mount directly, though; the library wraps the whole sequence in one call:

int
amount(int fd, char *mntpt, int flags, char *aname)
{
	int afd, ret;
	AuthInfo *ai;

	afd = fauth(fd, aname);
	if(afd >= 0){
		ai = auth_proxy(afd, amount_getkey, "proto=p9any role=client");
		if(ai != NULL)
			auth_freeAI(ai);
	}
	ret = mount(fd, afd, mntpt, flags, aname);
	if(afd >= 0)
		close(afd);
	return ret;
}

auth_proxy's third argument is a factotum key query, exactly like the ones two sections back — "proto=p9any role=client" asks factotum to run the negotiation metaprotocol, p9any, as the client. p9any exists because hardcoding one protocol into every service was the original design's mistake: the callee advertises the proto@domain choices its factotum holds keys for, the caller picks one, the callee confirms with a fixed-length OK, and only then does the chosen protocol (p9sk1, apop, chap, …) actually run. A network attacker positioned in the middle can narrow which choices get offered, but can't force either side onto a protocol it wasn't already willing to use.

p9sk1, briefly Plan 9's native shared-key protocol is a Kerberos-style ticket exchange with a trusted authentication server: the server issues two tickets encrypted under a fresh shared secret, one readable by the client's key and one by the server's, and each side proves it holds that secret with a nonce-based authenticator. The interesting part for this chapter isn't the cryptography — it's that a successful run hands the server exactly one more thing: a capability, which is the subject of the next section.

Local capabilities: proving it once, kernel-side

Authenticating tells a server who is asking. It doesn't, by itself, change what user id that server's process runs as — and Plan 9 has no setuid bit to fall back on for that last step. Instead there's a small kernel device, conventionally exposing /dev/caphash and /dev/capuse, that lets one trusted process empower another process to change its own identity, without ever handing out a password or a permanent credential.

A capability is a single string: old-user@new-user@random-key. The trusted process — in practice, factotum, running as host owner — hashes just the old-user@new-user part with the random key (SHA1-HMAC) and writes that 20-byte hash to caphash, a write-only file the host owner may open exactly once, right after boot. It then hands the full capability string to the process that should become new-user. That process writes the string to capuse; the kernel recomputes the same hash, checks it against the list caphash built, and on a match changes the writing process's user id. The hash is then discarded — used once, or after about a minute if never used — and none of this crosses a network: a capability minted by one kernel means nothing to any other machine's kernel.

The library wraps redemption too: auth_chuid(AuthInfo *ai, char *ns) takes the AuthInfo a successful server-role auth_proxy call returned — its cap field holds exactly this capability string — and writes it to capuse. This is the entire mechanism behind, say, a login service on a shared CPU server: it starts as the host owner, authenticates the arriving user through factotum, and only after that succeeds does auth_chuid turn it into a process running as that user. No root-owned helper, no binary flagged setuid — one kernel device, used once, by the one process allowed to use it.

Guarding the guard

Centralizing every secret in one process is only a win if that process is actually harder to compromise than the alternative of spreading them everywhere — so factotum takes two specific precautions against the one leak path this book has already built: /proc. Ordinary /proc permissions already stop a different user from reading factotum's memory through /proc/pid/mem. They do nothing, by default, against another process running as the same user — an honest mistake, or an unattended terminal, could otherwise leak keys to any of your own programs. Two control messages close that gap:

echo private >/proc/$pid/ctl   # my memory unreadable via /proc, even to my own uid
echo noswap  >/proc/$pid/ctl   # my memory pages never written to a swap device

private is inherited across fork and cleared on exec, and factotum issues both to itself at startup. Neither message is special-cased to factotum — any process guarding sensitive in-memory state can use the same two lines; the manual names a FAT-filesystem server's buffer cache as another candidate. What's left unsolved, and stated as such rather than glossed over: someone with physical access who resets the machine and reboots it with a debugger instead of a kernel can still read memory directly. No file permission reaches that.

Bootstrapping: where do factotum's own keys come from? factotum holds keys only in volatile memory, so something has to supply them at boot, before any authenticated channel exists to fetch them safely. secstore is a separate network server, used only during that bootstrap, holding each user's permanent key file encrypted under a password and protected by PAK, a password-authenticated key-exchange protocol chosen specifically because it resists offline dictionary attacks even against a passive eavesdropper. Once factotum has decrypted and loaded the key file, secstore's job is done — everything afterward runs on the keys now sitting in factotum's guarded memory.

The namespace was the access-control system all along

Pull back to the scale of the whole book. Almost every resource on Plan 9 — a device, a network connection, another process's state, a remote file tree — is reachable only through whatever is bound or mounted into a process's own namespace. That was true from chapter 1 onward, framed there as customization and transparency. It is exactly as true read as a security property: a process that never has a sensitive device or file tree bound into its namespace cannot reach it, full stop, with no separate check to bypass. Chapter 6's RFNOMNT — forbid further mounts, forbid dereferencing #-device names, inside a namespace built for something untrusted — is that idea used deliberately: the same bind/mount/rfork primitives every other chapter used for convenience, here used to construct confinement. exportfs and cpu (ch. 4) already export exactly this shape — a chosen, partial view of one machine's namespace, never the whole thing.

Ordinary file permission bits — owner, group, other, rwx — remain the other, more familiar layer, governing what's allowed once something is reachable. And 9P itself forecloses one classic escalation structurally, not by policy: chapter 3 already noted that wstat can never change a file's owner, for any caller, under any permission — there is simply no message that does it.

So what did Plan 9 actually gain by doing it this way A privileged-code footprint small enough to read in an afternoon. factotum's core is a few thousand lines — the paper's own stated goal was a trusted base "easy to verify, whether by manual or automatic means" — instead of every network-facing server separately getting cryptographic code right while running with whatever privilege that code needed. Because factotum is the only process that can ever mint a capability, every other service can run as an unprivileged pseudo-user; a compromised, buggy file server has nothing valuable to hand an attacker, because it was never holding anything valuable to begin with.

Nothing in this chapter introduced a permission system separate from the one this book started with in chapter 1: files, reached through 9P, assembled into a namespace. Authentication became a file (rpc) instead of a wire message; a capability became a file descriptor (afd) and then, once redeemed, a single kernel-verified string; even the boundary of what you're allowed to touch is drawn by which names are bound into your namespace in the first place. Plan 9's security model isn't a system bolted onto the file model — it's what the file model looks like when you ask it to hold a secret.
