Namespaces

Pillar three, taken apart. What a name space actually is, the two calls that build one, how it survives — or doesn't — a fork, and the payoff for building your system this way instead of adding a syscall per resource.

Chapter one told you every process gets its own private view of the file hierarchy. Fine — but "its own view" is doing a lot of work in that sentence. A view built how, out of what, and does it survive the next line of code you run? Those are implementation questions, and Plan 9's answers turn out to be almost embarrassingly small: two system calls, one flag argument, and a handful of bits on rfork. Everything this chapter's title promises — customization, transparency, the disappearance of whole categories of syscall — falls out of that small a mechanism.

What a name space is

A name space is a per-process attribute: a single rooted hierarchy of file names, assembled by binding and mounting service trees at chosen points in that hierarchy. That's the whole definition. The important word is per-process — there is no second, global tree sitting behind it that this is a view of. A conventional kernel keeps one mount table for the whole machine; Plan 9 keeps one name space per process (or, as we'll see in a moment, per small group of processes), full stop.

This has a consequence worth stating plainly, because it's easy to read past: the assembled result — which servers are bound where, in what order — lives entirely on the client side. A file server answering 9P requests has no idea it's mounted at /n/other for you and at /mnt/backup for someone else, or that a third process hasn't mounted it at all. The server just serves its own hierarchy; the assembly is something each client does independently, in its own kernel-resident bookkeeping. That's a deliberate departure from name-space designs (Sprite is the usual point of comparison) that keep the composed view on the server or share it across clients.

The two operators: bind and mount

If a name space is "assembled," something has to do the assembling. Two system calls do all of it:

int bind(char *name, char *old, int flag);
int mount(int fd, int afd, char *old, int flag, char *aname);

bind is the cheaper of the two, and it's worth understanding first because mount is really "bind, plus a server on the other end." bind takes something already visible somewhere in your current name space — name, a file or a directory — and makes it also visible at another point, old. No network, no server, no new connection: it's pure rearrangement of names you can already reach. And it's resolved once, at call time — name is evaluated the instant you call bind, not re-evaluated every time something later looks up old.

mount is what actually reaches outside your existing name space. fd is an open, already-connected file descriptor — a pipe or a network connection to something that speaks 9P — and after a successful mount, the entire file tree that server exports appears rooted at old. The kernel component that makes this work is called, a little confusingly, the mount device: it's the sole translator between the ordinary open/read/write/close calls your program makes and the 9P messages that actually cross fd. It does the marshaling, the buffering, the multiplexing of many callers onto one connection — it is, in fact, the only integral RPC mechanism anywhere in Plan 9. Chapter 3 opens that box up; for now, the point is narrower: mount is how a 9P connection becomes part of your name space.

Both calls take a flag that decides how the newly-visible thing joins whatever is already sitting at old: the default, MREPL, replaces it outright; MBEFORE and MAFTER instead splice the new directory onto the front or back of a union directory at old, searched in that order; MCREATE can be added to any of these to mark that element as where a later create in the union should land. That's the full vocabulary — the next chapter, Mount, Bind, and Union Directories, is entirely about what these flags buy you and how union lookup actually resolves. For this chapter, file away that the operators exist and what each one attaches; the interesting content for right now is what happens to all of this across a fork.

Inheritance: shared, copied, or empty

Here's the part that trips up people arriving from other systems. Elsewhere, fork() has one well-known meaning for whatever-you're-forking: usually a copy, sometimes copy-on-write, but a copy. Plan 9's plain fork() does something different for the name space specifically — it shares it. Parent and child end up as two processes pointing at the same name-space object, not two independent copies that happen to start out identical. Bind something in the child, and the parent sees it too, immediately, because there was never a second name space to keep in sync — there's only ever been the one.

The actual control lives in rfork's flag argument, and fork() itself is nothing more than a fixed call to it:

rfork(RFFDG|RFREND|RFPROC)    // == plain fork(): child SHARES the parent's name space
rfork(RFNAMEG |RFPROC)       // child gets a private COPY, independent from that point on
rfork(RFCNAMEG|RFPROC)       // child starts with an EMPTY name space — nothing mounted

RFNAMEG and RFCNAMEG are mutually exclusive, and between them they cover the two things "isolate the child" could mean: give it a snapshot to diverge from (RFNAMEG), or give it nothing and make it build its own from scratch by mounting something onto it (RFCNAMEG). There's a related flag, RFNOMNT, that can be set on a fresh name space to forbid any further mount calls and block dereferencing kernel-device names beginning with # inside it — a way to build a name space that, once handed to something, can't be pried open further. That's a security-relevant move on its own, and we'll come back to it once the security chapter has the rest of the vocabulary in place.

Key idea — the name-space group Because sharing really is "one object, two references" and not "two copies kept synchronized," Plan 9's own manual pages use a precise term for it: a set of processes sharing a name space this way is a name-space group. bind and mount are documented as modifying the name space of "the current process and other processes in its name space group" — which is exactly the mechanism that lets, say, two shells in the same window stay in lock-step on every rebind, with no synchronization protocol at all. There's nothing to synchronize; there's one thing.

Where a name space starts: namespace(6) and ns(1)

A process doesn't get its name space handed down from nowhere. At login, init builds the first one from a name-space description file — interpreted by the newns/addns library routines — where each line is one operation: mount, bind, import, cd, unmount, clear (equivalent to rfork(RFCNAMEG), start over empty), or . path to splice in another such file. The option letters match the shell commands you'd type by hand:

# shape of a namespace(6) description file
mount -a tcp!fileserver!564 /root
bind -a /root/386/bin /bin
bind -a /root/rc/bin  /bin
bind '#c' /dev
cd /usr/glenda

Illustrative shape only — a real description file is site- and machine-specific.

Treat that file as a bootstrap, not a policy that stays in force. Once a process is running, bind, mount, and unmount are ordinary system calls it (or anything sharing its name-space group) can call at any later moment — most of the customization this chapter is building up to happens by a running process rearranging its own already-live name space, not by re-invoking init. To actually look at what a process ended up with, there's ns: it reads /proc/pid/ns and prints back a shell script's worth of bind/mount/import lines that could, in principle, reconstruct that exact name space — the nearest thing Plan 9 has to a name-space inspector, and worth keeping in your back pocket for every example from here on.

What building it this way buys you

None of the mechanism above is interesting purely as mechanism. It earns the chapter by paying for three things that other systems solve with more moving parts.

Customization, with no new mechanism

Binaries for a given CPU architecture live in an architecture-named directory — /mips/bin, /386/bin, and so on. Every machine binds the one it actually needs to the conventional name /bin; a directory of your own private binaries is typically unioned in ahead of it with -a/-b. A shell script that runs /bin/date never has to ask what architecture it's on. Compare this to the usual solution to "where are my commands": an environment variable listing directories to search in order. Plan 9's shell, rc, doesn't have one — there's no $PATH in it at all, because the problem PATH exists to solve is solved once, structurally, by the name space, instead of per-shell-instance by a variable every script has to trust is set correctly.

Transparency, as a side effect

The window system, 8½, is not special kernel code — it's an ordinary 9P server, serving files like /dev/cons, /dev/mouse, and /dev/bitblt. Every window gets its own private copies of those names, bound into that window's own name space. A client program addressing /dev/cons has no way to ask, and no need to ask, whether that window — and therefore that file — is being served locally or by a machine three networks away; the 9P connection is already sitting in its name space before the program starts. This is the exact mechanism that lets Plan 9 run X11 as just another 8½ client, often on a big remote machine, with a measured cost of roughly 10% in graphics performance versus running on a bare local Plan 9 box — not a special remote-display protocol, just mount doing what it always does.

The special-case system calls that disappear

Process control is the sharpest example. Unix spreads it across kill, ptrace, and a pile of /proc conventions bolted on later. On Plan 9 it's plain text I/O on files under /proc/pid:

cat /proc/*/status                # a crude ps
echo stop >/proc/17/ctl           # suspend process 17 — no ptrace() anywhere
db /proc/27/text /proc/27/mem     # attach a debugger, local or (via import) remote

ps itself is close to a reformatted cat /proc/*/status; a debugger opens text and mem directly, with no ptrace-shaped call in sight. And because these are just names in a name space, they extend across a network for free: import host [remotepath] mountpoint dials a remote machine, starts a 9P server there for the requested subtree, calls mount to attach the resulting connection locally, and exits — the remote process keeps serving after import itself is gone. import lab.pc /a: /n/dos reaches a floppy drive with no local hardware for it; import helix /proc followed by db /proc/27/text /proc/27/mem is a remote debugger session, and it works cross-architecture because db reads the target's byte order from the executable header on text rather than assuming its own.

The same pattern is what the cpu command is built from: instead of moving you into a wholly distinct remote name space (the way rlogin does) or keeping one uniform name space while forcing execution to stay put (the way NFS does), cpu re-imports the pieces of your terminal's local name space that a shell actually needs — terminal-resident devices — into a new process on a fast remote CPU server, while CPU-local resources like its own file-system connection stay local. The result doesn't feel like logging into another machine. It feels like your processor got faster.

Two habits worth unlearning Coming from a fork()-means-copy background, it's easy to assume isolation is the default and sharing is the special case. For name spaces on Plan 9 it's the reverse: plain fork() shares; RFNAMEG is what you reach for to copy. And don't read a namespace(6) file as a live policy — it describes how a name space starts, not how it stays; almost everything interesting in this chapter (rebinding for debugging, import, cpu) happens by a running process editing its own name space long after boot.

So what did we actually gain?

Two system calls, evaluated eagerly, joined by one flag argument, propagated across fork according to three explicit bits. That's genuinely the entire mechanism. And yet it's enough to make a search path a structural property instead of an environment variable, make a remote window indistinguishable from a local one to the program running in it, and turn process control, remote debugging, and even "log in to a faster machine" into ordinary file operations instead of dedicated syscalls each demanding their own kernel support. The next chapter goes underneath this: bind and mount are really just convenient front doors onto 9P, the protocol that actually moves the messages once mount has grafted a connection in. Understand this chapter's two calls, and the wire format in the next one has nothing left to be mysterious about — it's just what mount was quietly speaking underneath you the whole time.
