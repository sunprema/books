The Plan 9 Model

Three ideas, stated plainly, that compose into a distributed operating system. Everything later in this book is one of these three ideas worked out in detail.

Skip the checklist reading. The interesting claim in Plan 9 isn't any one of its three design principles — it's that each one is load-bearing for the next. Take one away and the other two stop paying for themselves. So that's how we'll build the model: one piece, then the next piece bolted on, then the moment they click together.

Pillar one: resources are files

Start with the plainest of the three ideas. In Plan 9, a resource — a disk file, sure, but also a window, a network connection, a running process, the mouse, a remote machine's console — is named and reached as a file or a directory tree of files. You open it, you read and write it, you close it. That's the entire verb set.

Unix already told you files were a good idea for files. Plan 9's contribution is refusing to stop there. Where Unix reaches for a special-case system call — ioctl for device quirks, socket/connect/setsockopt for networking, a raft of /proc pseudo-files bolted on decades later for process introspection — Plan 9 asks first whether the operation can just be a file operation instead. Usually it can.

The clearest demonstration is networking, because sockets feel so load-bearing in every other system. Under Plan 9's /net, a protocol has a directory (/net/tcp); reserving a connection means reading its clone file, which hands back a connection number; that number is itself a directory with a ctl file and a data file. Dialing out is a write to ctl. Sending and receiving are writes and reads on data. No new system call, no separate namespace of file descriptors versus socket descriptors — just files.

Key idea The detail that actually matters isn't that Plan 9 has more files than Unix — it's that Plan 9 routes control operations through files too, not just data. A ctl file taking a command string, rather than a side-channel ioctl, is what makes the file interface sufficient on its own. That sufficiency is what pillar two gets to depend on.

Pillar two: one protocol reaches all of them

Here's the payoff for keeping the interface down to open/read/write/close: you only need one protocol to carry those operations over a wire. Plan 9 calls it 9P. It's a small set of request/response message pairs — walk a name, open a file, read some bytes, write some bytes, and so on — and it's what a client speaks to a server, full stop. It doesn't matter whether that server is the kernel serving a local device, or a file server across the building, or a file server across the country.

This is worth sitting with, because it's easy to read past as a throwaway detail. 9P isn't a remote-file-access protocol with a separate local fast path that happens to look similar — local devices are 9P servers, just ones the kernel happens to implement in-process for speed. A client program reading /dev/cons and a client program reading a file on a file server three hops away are, as far as the program can tell, doing the identical thing. There's exactly one client-side idea of "talk to a resource," and it's 9P.

Two more properties worth knowing before we move on, because they shape everything downstream: 9P operates on whole file systems, not isolated files — it includes the messages to walk a name down through a hierarchy, so the protocol itself understands directory structure, not just byte streams. And it works at the granularity of bytes, not fixed-size blocks, which is a real difference from block-oriented network file protocols like NFS. We'll get precise about the actual message types — Tversion, Tattach, Twalk, and the rest — in the next chapter; for now, hold onto the shape: one protocol, byte-granular, hierarchy-aware, spoken identically whether the far end is a kernel driver or a machine across a network.

Pillar three: your own private namespace

Now the piece that actually surprises people coming from Unix. In a conventional system there is one file tree, shared by every process on the machine, with maybe a chroot jail bolted on for the rare case that needs isolation. Plan 9 inverts that: every process has its own private namespace — its own view of what's mounted where — and a shared global tree isn't even on offer.

A namespace is built, not given. You start (typically) by inheriting one from your parent process, and then you bind and mount pieces of file hierarchies — served locally by the kernel or remotely by a 9P server — at whatever points in the tree you want them. Nothing about this needs a new system call for each new kind of resource: adding something to your world is a bind or a mount, using the same two operations regardless of what's on the other end.

; ns                          # list this process's namespace
bind -a /386/bin /bin
bind -a /rc/bin  /bin
bind '#c' /dev
bind '#d' /fd
mount -A /srv/boot /n/other

Illustrative shape only — the exact lines vary by machine and session. #c, #d name kernel-served device trees; /n/other is mounted from a 9P connection registered under /srv.

This is where the three pillars visibly click together. Pillar one made every resource file-shaped. Pillar two made "talk to a resource" a single uniform operation regardless of distance. Pillar three is what that uniformity buys you: because reaching a local device and reaching a remote file server go through the identical client-side call, a namespace can graft the two together with no seam. You can bind a local device tree and mount a file server three networks away into adjacent directories, and nothing about the mechanism changes at the boundary.

Local names, global conventions

If every process's namespace can be different, how does anything reliably work? The overview paper's own answer is a small piece of everyday language: compare "my house" to a house's precise postal address. The address is universal, but nobody talks that way — you say "my house," which means something different depending on who's speaking, and that's not a bug, it's how the phrase is useful at all.

/dev/cons works the same way. It always names "my terminal" — but what it actually resolves to depends on whose namespace is asking. /bin/date always names "the correct date to run," but which binary that is depends on the architecture of the machine doing the running. Plan 9 has local names governed by global conventions: a program always knows where to look, and the conventions are precisely what keep "where to look" meaningful across every machine in the installation — without ever requiring that two machines' namespaces contain the same things.

Not the same as a global namespace It's tempting to hear "consistent conventions everywhere" and round it off to "one shared file tree." Resist that. Plan 9 explicitly rejects a uniform global namespace as the model — the whole design point is that the view is local and assembled per-process, while only the path names and what-they're-for are what's held in common.

A worked example: the window system as a namespace

Plan 9's window system, 8½, is not a special kernel subsystem — it's an ordinary 9P file server, serving files like /dev/cons, /dev/mouse, and /dev/bitblt. Each window gets its own namespace, with its own private copies of those files bound in. That's the whole trick behind two things that would otherwise need separate mechanisms: first, changes you make to one window's namespace — say, substituting a file from a backup snapshot while debugging — are invisible to every other window, so experimenting is safe by construction. Second, and more strikingly, a program running in a window on a remote machine reads and writes exactly the same /dev/cons, /dev/mouse, /dev/bitblt paths as one running locally. It does not know, and has no way to ask, whether those files are local — the 9P connection back to the window is already sitting in its namespace before the program starts, doing the work pillar two promised.

That's the entire model, demonstrated in miniature: the same conventional name resolving to a different concrete resource depending purely on which namespace is doing the asking — with no code in the application aware that anything was substituted.

Why this is the right order to learn it in

One more thing worth being explicit about before we leave the model and start opening it up. Each pillar is what makes the next one cheap:

  • Files first — because every resource already looks like open/read/write/close, there is a small, fixed interface for a wire protocol to carry.
  • One protocol second — because that interface is small and uniform, 9P can be the only way to reach a resource, local or remote, with no special-casing.
  • Namespace third — because reaching anything goes through the same protocol, assembling a personal view of the system is just binding and mounting, with no kernel change required for a new kind of resource.

Everything else in this book — namespace construction in more depth, the 9P wire format itself, how to write a file server, the bind/mount/union operators, how namespaces travel across rfork, plumbing as a file server used for message-passing, and security built almost entirely out of namespace restriction — is one of these three pillars, examined closely. Keep this composition in view as we go; it's the thing that turns a checklist of features into an actual architecture.
