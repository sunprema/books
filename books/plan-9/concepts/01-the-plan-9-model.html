Part 1 — Introduction

The Plan 9 Model

Three ideas, stated precisely and then composed: resources as file hierarchies, one protocol to reach any of them, and a private namespace that assembles the ones you want into the system you see.

Open a file, and you already know how to use most of Plan 9. Not as a slogan — as a literal engineering claim. This chapter states the three ideas the rest of the book is built on, and, more importantly, shows why having all three at once is what makes the system work. Any one of them alone is a curiosity. Together they remove most of the special-case machinery an operating system usually needs.

Three ideas, one system

Plan 9's design paper states its whole architecture as three composing rules: resources are named and accessed like files in a hierarchical file system; a single protocol — 9P — is used to access those resources, local or remote, without exception; and the separate hierarchies that different servers expose are joined by the client, not the server, into one private name space. Read that a second time, because the order matters: each rule is what makes the next one possible.

Key idea

Files give you a uniform interface. 9P gives you a uniform way to reach that interface, anywhere. A namespace is just your own arrangement of the trees 9P can reach. Nothing here is a separate mechanism — it's one idea, applied three times.

Pillar one — resources are named like files

Unix already sold you on "everything is a file" for plain data. Plan 9 takes the same metaphor and refuses to make exceptions for it. A window is a file. A running process is a directory of files. A network connection is a directory of files. The mouse is a file. What you'd expect to be a special ioctl, a socket option, or a bespoke system call is instead a read or a write on an ordinary file — usually one named ctl for commands and data for the bytes that flow.

Take the network. Opening a TCP connection on most systems means a socket() call, a struct full of address-family constants, and a handful of connection-specific calls found nowhere else in the API. On Plan 9, dialing out is namespace traffic: 

# reserve a connection, get back its number
open  /net/tcp/clone            → read: "n"

# tell that connection where to go
write /net/tcp/n/ctl  "connect 192.0.2.1!80"

# then it's just bytes
write /net/tcp/n/data  ...
read  /net/tcp/n/data

Four lines, no new vocabulary. The same open/read/write/close that touches a plain text file touches a live TCP connection, because the kernel's network stack is, itself, just another file server answering under /net. This is the payoff of pillar one: once a resource is a file, every tool that already knows how to handle files — cat, a shell redirect, your own five-line program — can handle it too, with no resource-specific client code.

Pillar two — one protocol reaches all of them

A file interface is only as useful as its reach. Pillar two is what gives it reach: every one of those file trees, wherever it actually lives, is served over the same wire protocol, 9P. The kernel speaks 9P internally to serve local devices. A user-level program speaks 9P to serve a synthetic file tree of its own design. A file server on another machine, across the network, speaks the identical protocol. There is exactly one client-side mechanism for reaching any of them — walk to a file, open it, read or write it, close it — and it does not change based on where the file actually is.

That's the whole trick behind "a remote resource looks local": it isn't hidden behind a translation layer, it's reached by the same protocol a local one is. The next chapter goes through 9P's actual messages; here, the only fact that matters is that there is exactly one of them, everywhere.

Pillar three — a private namespace assembles the view

Every process has its own namespace: its own private mapping from path names to the file trees actually reachable at those paths. A namespace isn't handed down whole from the kernel — it's built, one grafted tree at a time, by binding and mounting resources into place. (Chapter 5 covers those two operators in full; here, just their effect: they graft a file tree onto a point in your namespace.) Nothing about this is global. Two processes can hold entirely different views of what /net or /bin resolves to, at the same moment, on the same machine.

A listing of a real namespace is just a log of those grafts: 

; ns
bind -a /386/bin /bin
bind -a /rc/bin  /bin
bind '#c'      /dev
bind '#d'      /fd
mount -A /srv/boot /n/other

The exact lines vary by machine and session, but the shape doesn't: kernel devices ('#c', '#d') and 9P services (/srv/boot) bound or mounted at conventional points. That "conventional" part matters. Every Plan 9 machine keeps the same path vocabulary — /net, /dev, /proc, /bin — even though what actually answers at each path can differ from process to process and machine to machine. You always know where to look. You do not get to assume what you'll find there.

/bin is the clearest everyday case: it's usually a union directory, several directories bound together at the same point and searched in order, so that the architecture-appropriate binaries win without any program having to ask which architecture it's on. The window system is the sharpest one. 8½, Plan 9's window system, is nothing but another file server: it serves files like /dev/cons, and gives every window its own private copy of that file in that window's namespace. Type into two different windows and you're writing to two different files that happen to share a name — because each window's namespace resolves /dev/cons to a different tree.

Why the three compose

So what did we actually gain by insisting on all three at once? Pillar one means there is exactly one interface shape to implement per resource: open, read, write, close. Pillar two means that interface is reachable identically whether the resource is a kernel device, a program down the hall, or a machine across the network — location stops being part of the client's job. Pillar three means "customizing the system" reduces to deciding which trees to graft where, in your own namespace, with no cooperation from anyone else's process and no new kernel code.

Put the three together and a new kind of resource — a compressed-file view, an FTP site mounted as a directory, a debugger's window into a process's memory — needs exactly one new thing: a program willing to answer 9P messages over a file tree that makes sense for that resource. No new system call, no kernel patch, no special-casing in every client that wants to use it. Chapter 4 is about writing that program. Everything from here forward is this chapter's three sentences, worked out in full.
