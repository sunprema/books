Part 2 · Mechanism

Process Namespaces

Chapter 2 introduced two of rfork's bits — RFNAMEG and RFCNAMEG — just enough to explain how a name space is inherited, and set the rest of the flag vector aside. This is the rest: RFFDG, RFENVG, RFMEM, and RFPROC's own quiet rule about when rfork forks at all — plus the process interface built out of the same file model, /proc, and why /dev/cons is not one file but as many as there are windows.

A process is not one indivisible thing on Plan 9 — it is a bundle of resources, and rfork lets you say, per resource, whether the child shares the parent's copy, gets its own, or starts clean. Name space was resource one. This chapter works through the rest of the bundle using the exact same three-way choice, then turns to how a running process is itself represented: as files, under /proc, reachable through the very name space this book has been building since chapter 1.

One call, and whether it forks at all

rfork takes one int, a bit vector, and nothing about that vector is namespace-specific — it just happens that two of its bits are the ones chapter 2 needed. The full shape:

int rfork(int flags);

RFPROC    // create a new (child) process; otherwise the CALLER's
          //   own resources are modified in place — no fork happens
RFNAMEG   // (ch. 2) child gets an independent COPY of the name space
RFCNAMEG  // (ch. 2) child starts with an EMPTY name space
RFFDG     // child gets an independent COPY of the descriptor table
RFCFDG    // child starts with an EMPTY descriptor table
RFENVG    // child gets an independent COPY of /env
RFCENVG   // child starts with an EMPTY /env
RFMEM     // child SHARES data+bss with the parent (stack is always
          //   copy-on-write regardless); valid only with RFPROC

Start with RFPROC, because it changes what every other bit means. If it's set, rfork creates a child: the parent's call returns the child's pid, the child's returns 0, exactly like fork. If RFPROC is not set, no process is created at all — the other bits instead modify the resources of the process making the call, in place. That makes rfork(RFNAMEG), with nothing else, a complete and legal statement on its own: "detach my name space from whoever I was sharing it with," no forking involved. Chapter 2's examples all paired RFNAMEG/RFCNAMEG with RFPROC because they were about what a new process inherits; a running process rewriting its own resource sharing, mid-execution, is the other half of the same mechanism.

Why one call instead of a thread API and a process API Plan 9 deliberately has a single class of process, not processes plus a separate lightweight-thread type. rfork's bit vector gives fine, independent control over which resources are shared, copied, or started clean, so the same primitive covers everything from a plain fork() to something close to a thread that shares memory but keeps its own name space. Outside the library's own fork(), it's hard to find two rfork call sites in real programs that pass the same bits — the point of the design is exactly that variety.

Shared, copied, or clean — the same choice, three times

Name space, environment, and file descriptors all follow the identical three-way shape: a plain fork() shares the resource outright, one flag splits it into an independent copy, and (for two of the three) a second flag splits it into something empty instead of a copy.

Environment variables are, unsurprisingly by now, their own file device: #e, conventionally bound to /env, one file per variable holding its value as plain text. Under a plain fork(), parent and child keep seeing exactly the same /env files — write a new value through either process and the other sees it, same as an unflagged name space. RFENVG splits that into two independent sets that started identical; RFCENVG splits into an empty set. There's no new idea here, only the same one applied to a different device.

File descriptors: the table splits, the files don't

RFFDG is easy to misread as "the child gets its own files." It doesn't — it gets its own table. After an RFFDG fork, descriptor 3 in the child still refers to the exact same open channel descriptor 3 referred to in the parent; what becomes independent is only the mapping from small integers to those channels, from that point forward. Open a new file in the child afterward and the parent's descriptor 3 is unaffected, because the tables no longer track each other — but the channel they both already had open at fork time is still one shared thing underneath, exactly as far as it was shared before.

Without RFFDG, there's only one table, referenced by both processes, and the difference is sharper than it sounds: close a descriptor in either process and it's closed for both, because there's nothing per-process to distinguish — "the parent's fd 3" and "the child's fd 3" are the same table slot. That table, shared or independently copied, stays open only until it's explicitly closed or every process still sharing it has exited.

Memory: RFMEM, and why it needs RFPROC

RFMEM is the odd one out in the list — it has no plain-copy default to contrast with, because without it the child simply gets its own copy of data and bss the way a conventional fork would. Set it, and the child instead shares those segments outright with the parent: writes either process makes are visible to the other, live. The stack is never part of that deal; it is always forked copy-on-write regardless of RFMEM, because two processes cannot sensibly share one call stack. And RFMEM only makes sense paired with RFPROC — sharing memory "with yourself" in place is not a meaningful operation, so the flag describes a property of a newly created process, not an edit to the caller.

This is Plan 9's answer to "give me a thread" rfork(RFPROC|RFMEM|RFFDG) — new process, shared memory, shared-then-independent descriptors — is about as close as the raw system call gets to spawning a thread: two schedulable processes with one address space between them. Nothing here is a distinct threading API; it's the same eight bits, chosen differently.

The process, filed under /proc

Once a process exists, Plan 9 represents it the same way it represents everything else worth naming: as files. The process device, conventionally bound as #p /proc, serves a two-level tree — a flat top level of numbered directories, one per live local process named by its pid, plus a single extra file, /proc/trace, for cross-process trace events. Each per-pid directory exposes roughly a dozen files; the ones worth knowing by name:

FileWhat it is
memthe process's virtual memory, read/write by address — writes only while Stopped
texta pseudonym for the executable it runs, for recovering its symbol table
fdcurrent directory, then one line per open descriptor: mode, type, qid, offset, name at open
nsits file name space, reconstructed as namespace(6) text (see below)
statusname, owner, state, CPU time, memory, and scheduling priority, fixed-format
ctlwrite-only control messages — stop, kill, and friends (see below)
note / notepgwrite-only, post a note to this process, or to its whole note group
waitblocks and yields records for the process's exited children

The crude version of ps chapter 2 already showed — cat /proc/*/status — is doing exactly what the real ps does, just without the reformatting. That's the whole point of representing a process as files: a debugger opens text and mem directly instead of calling a dedicated debug syscall, and because /proc is reached the same way any other directory is, import helix /proc followed by an ordinary ps or db shows or debugs helix's processes from your own machine, no remote-debugging protocol required.

The ns file: a name space, read back as text

/proc/pid/ns is the file that closes the loop this book has been building since chapter 2: a read-only textual reconstruction of that process's name space, written in the exact namespace(6) grammar that newns/addns consume to build one in the first place, with a final cd line giving the process's current directory. In principle, feeding one process's ns output back through newns rebuilds the same name space elsewhere — the closest thing Plan 9 has to a name-space inspector.

cat  /proc/17/status                  # name, state, cpu time, priority...
cat  /proc/17/ns                      # its namespace, as namespace(6) text
echo stop      >/proc/17/ctl       # suspend it — no ptrace() anywhere
echo hi        >/proc/17/note      # post a note to just this process
echo hi        >/proc/17/notepg    # post the same note to its whole note group
ns is a snapshot of names, not a live re-lookup Its contents are based on what things were called when each piece of the name space was assembled, not looked up fresh at read time. If a file that got bound in has since been renamed or moved, ns still prints the old name — the script it hands you can be stale, not a guaranteed-accurate replay.

Control and notes, as writes instead of syscalls

The ctl file replaces an entire family of process-control syscalls with one write-only file taking short text commands:

MessageEffect
stopsuspend the process into the Stopped state
startresume a Stopped process
killkill the process at its next kernel entry
close nclose file descriptor n in the process
closefilesclose every open descriptor in the process
privatemake its user memory unreadable by anyone else (inherited on fork, cleared on exec)
pri nset its base scheduling priority to n

note and notepg are the two write targets for Plan 9's signal analog. A string written to note is posted to that one process only; the identical string written to notepg is delivered to every process in the target's note group — the set of processes that, per RFNOTEG in rfork, share one — except that a process writing to its own notepg does not receive the note back itself. noteid, alongside them, is a readable and writable integer naming which note group a process currently belongs to.

/proc is a view, deliberately not a way to create one Plan 9's designers were explicit that /proc stops short of one tempting extension: something like cp /bin/date /proc/clone/mem to spawn a process by writing to a file. They rejected it — answering that write would require the server behind /proc's 9P requests to construct a new process's open files, name space, and memory image, actions that don't fall naturally out of ordinary read/write/create semantics. Process creation stays on the conventional rfork/exec path; /proc only represents and controls processes that already exist.

Per-process devices: why /dev/cons isn't one file

Nothing about the kernel special-cases /dev/cons to be "the console for whichever process opens it" — and that's exactly what makes it worth a closer look, because from a shell it certainly behaves that way. The resolution is the window system, 8½, which is itself just a user-level file server for files including /dev/cons and /dev/bitblt. Each window mounts its own private connection to 8½ into its own name space, so there isn't one /dev/cons on a running Plan 9 desktop — there are as many as there are windows, each served independently, each answering only to the process that lives in that window. A process's standard input, output, and error are simply connected to whatever /dev/cons its own name space happens to resolve that name to.

Compare that to UNIX's /dev/tty, which needs dedicated kernel code that overloads the file, on open, with whichever terminal happens to be attached to the calling process — a special case written once, in the kernel, for exactly this problem. On Plan 9 the same effect — "this conventional name means something different depending on who's asking" — is just what a per-process name space already does for every name, with no special-casing anywhere. The window system needing recursion to run inside its own window, or a client application running transparently on a machine with no graphics hardware at all, both fall out of the same fact: /dev/cons is a mount, like any other.

What inheritance still can't do

One honest limitation belongs here rather than being glossed over: Plan 9 has no operation to export a running name space as data and hand it to an unrelated process — the only way a name space travels intact is direct fork/rfork inheritance. cpu, which recreates a terminal's environment on a remote CPU server, cannot literally clone the terminal's current name space; it can only re-interpret the user's login profile and substitute a few conventional pieces, such as the binary directory for the server's own architecture. Any local, ad hoc rebinding done before running cpu simply isn't there on the other end. Everything else in this chapter — the shared/copy/clean triples, /proc, per-window devices — composes cleanly; this is the one seam the designers left, in print, as future work.

That closes out how a process and its view of the world relate. The next chapter turns to a specific, deliberately ordinary use of everything so far — an inter-application message bus, built, of course, as a file server: the plumber.
