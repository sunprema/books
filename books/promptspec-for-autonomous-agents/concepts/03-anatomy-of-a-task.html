Chapter three

Anatomy of a Task

A Task is the unit of declared work. Everything else in the language — pipelines, gates, failure policies — is about arranging tasks or about what happens when one of them doesn't go to plan. So let's take one apart. 

class DoThing(Task):
    """What this task is for. Treat as the task's core instruction."""
    some_input: str                  # bare annotations = inputs
    limit: int = Field(ge=1)         # Field bounds are part of the contract
    returns: ResultModel             # output = that Pydantic model, exactly

    tools = [Tool("gh", ops=["issue list"])]         # capability
    constraints = [ ... ]            # rules
    undo = "How to reverse this task's completed effects"
    on_uncertain = {...}             # output to return when genuinely unsure
    on_failure = "abort"

The docstring is the instruction

Start at the top, because this is the part most likely to be skimmed. In Python, a docstring is documentation. In PromptSpec it is the task's core instruction — the reference says so explicitly. It's not a comment about the task; it is the task.

That reframing changes how you write them. Compare a docstring that documents with one that instructs: 

# Documents. Tells the agent nothing it can act on.
"""Handles issue selection."""

# Instructs. Names the decision, and its priority order.
"""Resolve which issue to process: freeform run context first, else the
oldest open book-request not already in progress."""

The second one already resolves an ambiguity the first leaves open — what wins when the dispatch names a target and there's a queue. A good docstring does a lot of the work that would otherwise become a constraint.

Inputs are bare annotations

The rule is mechanical: annotated class fields are inputs, with one exception — the field named returns, which declares the output model instead. So in DoThing above, some_input and limit are inputs; returns is not.

A default value can carry a Field(...) whose bounds are part of the contract, not documentation about it. When you see limit: int = Field(ge=1), a limit of zero is not a degenerate case to handle gracefully — it is outside the declared space.

Undo: describe the state, not the call

undo declares how to reverse a task's completed effects. It only matters during an unwind, which we'll cover properly in chapter eight — but it's written here, on the task that caused the effect, because that's the only place where someone knows what the effect was.

There's a craft point here that's easy to miss. The weak version of an undo names an API call. The strong version names the state you're restoring and why it matters: 

undo = ("Remove the in-progress label and comment what went wrong on the issue, "
        "so the request returns to the queue instead of looking stuck forever")

That trailing clause — instead of looking stuck forever — is what lets an agent get the undo right when the world has drifted. If the label was already removed by someone else, an agent following "remove the label" is confused; an agent following "make sure the request is back in the queue" is not.

Design rule

Write undo as the postcondition you want, not the operation you'd type. Compensation happens in a world that has moved on since the effect.

A task that reads like one

Here is a complete, real task. Read it as six answers rather than as code: 

class MarkStarted(Task):
    """Label the issue in-progress and comment, BEFORE any generation work and
    ONLY once the run has proven it can generate."""
    issue_number: int
    returns: StartMark

    tools = [Tool("gh", ops=["issue edit", "issue comment", "label create"])]
    constraints = UNATTENDED + [ ... ]
    undo = ("Remove the in-progress label and comment what went wrong ...")
    on_failure = "abort"

Notice how much is decided. The docstring fixes the ordering (before generation, after proof). The tools list bounds the blast radius to three operations on one service. The constraints are inherited from a shared list plus local additions. The undo names the queue state. And on_failure = "abort" says that if this task fails, the run does not limp onward — it stops and unwinds.

So what did we actually gain?

A shape you can review by checklist. Six slots, and a reviewer can ask of each one: is this answered, or is it leaning on the agent to be sensible? Every slot left blank is a decision deferred to 3 a.m.

Challenges

  1. Rewrite one of your task descriptions so it resolves an ambiguity rather than naming a topic.
  2. Take a task that mutates something. Write its undo as a postcondition, then check: would it still be correct if someone else had already half-undone it?
  3. Find a task with no on_failure. Decide what should happen, and write it down.
