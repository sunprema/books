Chapter eight

Declaring Failure

We've arrived at the principle the whole language is built around: doubt and failure are declared, not improvised. And the operational half of it — apply the declared policy exactly; never substitute your own recovery.

That second clause is stricter than it sounds. It rules out the agent being clever. If a task declares that a failure aborts the run, an agent that finds an ingenious workaround has violated the spec even if the workaround succeeds — because the author decided that this failure means stop, and the author had reasons the agent can't see.

The five policies

on_failure = "abort"
Stop. Then perform the undo declarations of already-completed steps in reverse order, then report.
on_failure = {...literal...}
Return that declared default and continue. The run survives; the pipeline gets a value it can reason about.
Retry(max=N, backoff_s=S, then=...)
Up to N fresh attempts, then fall through to then.
Escalate(channel=..., timeout_s=T, then=...)
Notify the channel, wait up to T for a human, then fall through to then. The only sanctioned way to reach a person mid-run.
on_uncertain = {...}
The output to return when the agent genuinely cannot decide. Choosing it is always legitimate and never a failure.

For fan-out steps there's one more: on_item_failure, which is either "skip_and_report" — drop that item, surface it in the output, continue the batch — or "abort", which fails the whole step. The default matters. One malformed record shouldn't sink a thousand good ones, but you have to say so.

The unwind is a saga

The abort behaviour is worth recognising, because it's a well-established pattern under a different name. In distributed systems, a saga is a sequence of local transactions where each step has a paired compensating transaction; if a step fails, the compensations for the completed steps run in reverse order to bring the system back to a consistent state.

PromptSpec's undo is exactly that compensation, and on_failure = "abort" is exactly that unwind. Which means the pattern's most important caveat applies too: a compensating transaction is not a database rollback. You cannot un-charge a card by reverting a row — you issue a refund. Compensation is a new, forward-moving operation that logically cancels the earlier one.

Why reverse order

Because the effects were built up in a stack. In the diagram, GenerateBook's compensation deletes a branch; MarkStarted's puts the request back in the queue. Do those in the wrong order and you briefly advertise an unclaimed request whose branch still exists — inviting the next run to trip over exactly the debris you were cleaning up.

Notice too how the worked spec words that compensation. It doesn't say "delete the branch". It says delete it if no PR or compare URL was produced, "so a half-pushed branch with no front door does not become invisible debris the next run trips over". The condition and the reason travel with the instruction, exactly as chapter six argued.

Choosing the right policy

Here's the judgement, compressed. Ask what the failure means for the rest of the run:

Matching the policy to the failure
If the failure means…Use
The run's premise is void; continuing would compound harm"abort"
A side quest didn't work out; the main deliverable standsa literal default
Probably transient — a network blip, a rate limitRetry(...)
A human's decision genuinely changes the outcomeEscalate(...)
Nothing failed; the agent simply can't tellon_uncertain

The second row deserves an example, because it's the one that keeps routines alive. In the worked spec, the step that comments a result back onto the originating ticket declares: 

on_failure = Retry(max=3, backoff_s=30, then={"commented": False})

Three attempts, thirty seconds apart, and then a declared literal. The book was already written and the branch already pushed. Letting a failed comment abort the run — and unwind all of that — would be an absurd trade. The literal says so, in the file, permanently.

on_uncertain is not defeat

The reference goes out of its way to say that choosing it is always legitimate and never a failure. That sentence exists because an agent under pressure to produce a result will otherwise treat "I can't tell" as something to be avoided — and will guess.

Retries need idempotence

One caution that PromptSpec inherits from the wider world rather than stating itself. Retry is only safe if the operation is idempotent — if running it again has the same intended effect as running it once. Otherwise three attempts at "post a comment" is three comments, and the retry policy has become a duplication policy.

The worked spec handles this at the design level rather than with keys or tokens: its art-request step is required to be idempotent (an item that already has an open request is skipped), and its build step commits nothing until a page fully verifies. That last one is quietly excellent — it makes resumption safe by construction, so a run killed halfway can re-read its manifest and pick up at the next unbuilt page. As the spec's own constraint puts it: restart resilience is a property of the commit discipline, not of luck.

So what did we actually gain?

Failure handling that a reviewer can audit before it ever happens. Every recovery path was chosen by a person with context, at a desk, in daylight — rather than by an agent at 3 a.m. with none.

Challenges

  1. List your routine's side effects in order. For each, write the compensation as a postcondition — then check the reverse-order unwind makes sense.
  2. Find a Retry in your own automation and ask whether the operation is genuinely idempotent. Most aren't, by default.
  3. Pick your riskiest task and downgrade it from abort to a literal default — or the reverse. Whichever you chose first, argue the other side, then decide deliberately.
