Chapter four

The Output Contract

A task's returns: names a Pydantic model, and the agent must produce exactly its fields with its types. That sounds like a formality. It is actually the mechanism that makes one task's output safe to wire into another task's input — which is to say, it's what makes pipelines possible at all.

Types as a shared vocabulary

PromptSpec borrows Pydantic's BaseModel for the same reason the wider ecosystem does: it's the standard way to state the shape you expect from a model and validate what comes back. Field constraints like ge= and le= express bounds directly in the type, so the schema carries them rather than a paragraph of prose.

What PromptSpec adds is a set of reading rules, and they are stricter than "try to match the schema":

Field(ge=, le=, max_length=)
Bounds bind. They are part of the contract, not hints about typical values.
Enum["a","b"] / Literal["a","b"]
A closed set. Nothing outside the listed values is valid — not a near-synonym, not a better description of what actually happened.
x | None
Optional. The absence of a value is itself a legal answer.

The refusal to pad

Now the rule that gives this chapter its spine. The reference says the final message must end with a JSON object matching the root task's declared output — real values you produced, or a declared fallback — and then adds: never invent, coerce, or pad values to satisfy the shape.

Think about the pressure that rule is resisting. An agent that has almost-finished a task is looking at a schema with six fields and knows four of them. The shape wants filling. Filling it is easy, and the result looks like success — well-formed JSON, every field present, nothing obviously wrong. That output is worse than an error, because an error stops the pipeline and a plausible fabrication doesn't.

Closed sets are a routing decision

Here's the root task's output model from the worked spec: 

class RunReport(BaseModel):
    outcome: Enum["published_draft", "no_work", "already_in_progress",
                  "workspace_failed", "plugin_failed", "generation_failed"]
    summary: str = Field(max_length=500)
    operator_action: str = Field(max_length=300)

Six outcomes, and look at what they encode. Three are failures at distinct stages, which means "it broke" is never the answer — the report always says where. Two are clean stops that are not failures at all: no_work and already_in_progress. And one is success. Whoever consumes this report can route on the enum alone, without parsing prose.

That's why the set is closed. If the agent could add a seventh outcome when the situation felt unusual, every consumer would need a fallback branch for values it has never seen, and the enum would stop being a routing key and start being a comment.

The tempting failure

The situation genuinely doesn't match any declared member. The temptation is to pick the nearest one and explain the discrepancy in summary. Resist it: summary is bounded prose for a human, and nothing downstream reads it. Use the declared on_uncertain output instead — that's what it's for.

Bounded strings are a kindness

max_length=500 on a summary, max_length=300 on an operator action. These bounds aren't about storage. They're about the fact that the reader is a person who has just been woken up, and that a 500-character ceiling forces the writer to lead with the thing that matters.

The paired field is the interesting one. operator_action exists so the run can't merely report a symptom — it has to say what a human should change. The worked spec makes that explicit in a constraint: populate it whenever the run needed a human to change configuration, and name the file or setting, not just the symptom.

The value of a blocked run is a fix the human can apply once.

Validation as a loop, not a gate

One note on how this plays out mechanically. In the wider tooling around structured output, a validation failure is generally not the end — the standard pattern feeds the error back and retries a bounded number of times, with the failure history attached, rather than simply re-asking. Libraries such as instructor build that loop in.

PromptSpec's equivalent is declarative: bounded retries are written into the task as Retry(max=…, backoff_s=…, then=…), and the declared fallback is what the pipeline gets when the retries are spent. Same idea — the difference is that the retry policy is visible in the spec instead of buried in a client library's defaults.

So what did we actually gain?

Outputs a machine can route on and a human can act on, with a declared answer for "I don't know" so that neither reader is ever handed a confident fabrication.

Challenges

  1. Look at an enum in your own schemas. Are the clean stops distinguishable from the failures, or does one member cover both?
  2. Add a max_length to your longest free-text output field. Rewrite a real past value to fit it.
  3. For your most important task, write the on_uncertain output. If you can't, the task's success criteria are probably underspecified.
