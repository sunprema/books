Chapter one

The Unattended Problem

Let's start with an observation that sounds trivial and isn't: a prompt is written by someone who is present, and then run by an agent that is alone. Almost everything that goes wrong in autonomous execution lives in that gap.

The question that goes nowhere

When we work with an agent interactively, ambiguity is cheap. The agent hits something the prompt didn't cover — two plausible readings of "the latest release", a missing credential, a file where it expected a directory — and it asks. We answer in four seconds. Neither of us thinks of this as a feature, because it never had to be designed. It is just the room we were both standing in.

Now schedule the same prompt for 3 a.m. The agent hits the same ambiguity and asks the same question, and the question goes into a transcript that nobody will open. What happens next is the whole subject of this book. The agent either stalls — the run produces nothing and the work silently doesn't happen — or it guesses, which is worse, because a guess that happens to work is indistinguishable from a guess that happens to be catastrophic until much later.

PromptSpec's answer is blunt, and it is stated as an execution rule rather than a suggestion: never ask questions. Escalation, when it is genuinely warranted, happens only through a declared Escalate channel — a thing the spec author put there on purpose, with a timeout and a fallback, not an improvised plea into a log file.

The core move

If the agent cannot ask at runtime, then every question it might have asked has to be answered at authoring time. That is what a PromptSpec file is: the set of answers, written down in advance.

Three failure modes worth naming

The reference material for this book includes something unusually valuable: a real specification, for a headless book-generation routine, whose version history records the runs that broke it. We'll read that spec properly in chapter nine. For now it's worth naming the failure modes it documents, because they're the ones you'll meet too.

Mutating shared state before you can finish

A routine claims a work item — labels a ticket, takes a lock, posts "started" — and then dies before doing the work. Now the queue contains an item that looks claimed and isn't. The spec's rule is categorical, and it carries its reason with it: 

("Never mutate a GitHub issue — label, comment, or close — before the run "
 "has proven it can actually do the work",
 "a 'work started' comment from a run that then dies is noise the next run "
 "and the human both have to untangle", "must")

Note what that rule is really doing. It's not saying "be careful". It's imposing an ordering: prove capability first, claim second. Most of the discipline in this book is ordering discipline.

Reporting into a room with nobody in it

The same spec has a task whose entire job is to reach a human's phone, and its docstring says the quiet part out loud: "This is the run's only channel to a human; the transcript is read by nobody." A run that diagnoses a problem perfectly and writes the diagnosis only into its own log has not communicated. It has journaled.

A finding that never left the transcript did not happen.

Improvising under uncertainty

This is the subtlest one. An agent that is uncertain will still produce something, and what it produces will be shaped by whatever seems reasonable in the moment. Reasonable-in-the-moment is a fine standard when a reviewer is watching. It is a terrible standard when the output feeds another system at 3 a.m. PromptSpec's counter-principle is one line long: doubt and failure are declared, not improvised. We'll spend all of chapter eight on it.

What this costs

Let's be honest about the trade-off, because it's real. Writing a PromptSpec is more work than writing a paragraph of instructions. You have to decide, up front, things you'd rather discover later: what counts as "done", what the output looks like when the answer is "nothing to do", which tools are substitutable and which aren't, what to reverse if you abort halfway.

What you buy is that the run's behaviour stops depending on the agent's mood. Two runs of the same spec against the same world do the same thing, and — this is the part people underestimate — when a run does go wrong, the fix has somewhere to live. You don't fix it in your head, or in a Slack message to whoever is on call next. You fix it in the file, and the fix is still there next month.

So what did we actually gain?

A place to put decisions. An unattended agent has no room to ask in, so the spec becomes the room — written beforehand, read at execution time, and durable across runs in a way that a conversation never is.

Challenges

  1. Take a prompt you currently run on a schedule. List every question the agent could reasonably need to ask. That list is the spec you haven't written yet.
  2. For each item on that list, decide now what the conservative answer is. Notice how often "do nothing and report" is correct.
  3. Find one place where your routine mutates shared state. Is the mutation ordered after proof that the run can finish?
