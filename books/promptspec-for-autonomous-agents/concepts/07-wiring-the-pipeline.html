Chapter seven

Wiring the Pipeline

So far every task has stood alone. Now let's connect them. Inside an orchestrator Task, the class body is the pipeline, and the variables are the wiring — assignment by assignment, in dependency order. 

events = ScanThings(limit=limit)                       # step; kwargs bind inputs
plans  = [Triage(data=it) for it in events.items]      # fan-out: once per item
paid   = [Pay(id=p.id, plan=p.plan)                    # filtered fan-out:
          for p in plans if p.plan.tier in ["a", "b"]] #  membership only
mark   = MarkDone(n=events.count) if plans else None   # gate: skip if false
report = Digest(all_results=paid)                      # bare var = whole list

Five lines, five distinct wiring forms. Let's take them in order.

Dependency order, not source order

A step runs when everything it references has completed. That's the whole scheduling rule. Steps that don't reference each other may run in any order, or in parallel — the spec author doesn't have to say so, and shouldn't try to.

This is why the variables matter. Writing events.items in the second line is not just reading a field; it's declaring an edge. The dependency graph is inferred from the references, which means it can't drift out of sync with the code the way a hand-maintained ordering would.

Fan-out, and the filter that isn't a judgement call

A list comprehension runs a task once per item, and results collect into a list. Add an if and you filter which items proceed — but here the reference is emphatic, and for good reason: the filter is mechanical. Membership or equality against the listed literals, nothing else.

Routing, not judgment

if p.plan.tier in ["a", "b"] means exactly what it says. It is not an invitation to consider whether a particular tier-c item looks important enough to pay anyway. Apply it exactly.

That restriction is deliberate. The moment a filter admits judgement, the set of items that get processed stops being predictable from the spec, and a reviewer can no longer answer "what will this run touch?" by reading it.

Gates: a false gate is a clean stop

X(...) if cond else None runs X only when cond — a boolean field from an earlier result — is true. If the gate is false, the step is skipped, and so is everything that depends only on it.

Now the design pattern this enables, which is the most transferable idea in the chapter. Look at how the worked spec chains its gates: 

workspace = ResolveWorkspace()
plugin    = VerifyPlugin() if workspace.resolved else None
issue     = SelectIssue(...) if plugin.usable else None
mark      = MarkStarted(issue_number=issue.number) if issue.proceed else None
build     = GenerateBook(...) if mark.marked else None
art       = OpenImageRequests(...) if build.built else None
notify    = NotifyIssue(...) if build.built else None
alert     = PushAlert(workspace=workspace, plugin=plugin,
                       issue=issue, build=build)

Every step gates on the one before it reporting success. And each gate is a single boolean that the previous task computed and declared — resolved, usable, proceed, marked, built. The spec says why, in the constraint attached to one of them: "one boolean carries the whole go/no-go decision so every later step gates on it."

That's a real technique. Rather than making the orchestrator re-derive whether it's safe to continue — which would mean duplicating the previous task's logic — the task that knows collapses its own findings into one field. SelectIssue even shows its working: 

proceed = found AND (NOT already_in_progress OR redo_requested)

Skipped is not failed

This distinction is worth dwelling on because it's where a lot of home-grown automation goes wrong. The spec states it as a must: "a false gate is a clean stop, never an error."

An empty queue is not a failure. An item already claimed by another run is not a failure. Both are the system working correctly, and a routine that reports them as errors trains its operator to ignore its errors — which is the most expensive outcome available, because it disarms the alerts that do matter.

The orchestrator is the reducer

One last piece. After its steps have run, the orchestrator synthesises its own returns from whatever the steps produced. It isn't only a scheduler — it's the thing that decides what the whole run meant.

That's why gates and outcomes fit together so neatly. Each gate that closed corresponds to a member of the outcome enum from chapter four: workspace failed, plugin failed, no work, already in progress. The reduction is nearly mechanical — which is a good sign that the enum was designed around the pipeline rather than bolted on afterwards.

So what did we actually gain?

A run whose control flow is visible in eight lines. You can point at the line where a run stopped, and the boolean that stopped it was computed by the task best placed to know.

Challenges

  1. Draw your routine's gate chain. Is there a step that mutates shared state before a gate that could have stopped it?
  2. For each gate, name the single boolean and the task that computes it. If the orchestrator computes it, move that logic down.
  3. Check that your notification step is ungated. Then check that it can still say something useful when every earlier result is None.
