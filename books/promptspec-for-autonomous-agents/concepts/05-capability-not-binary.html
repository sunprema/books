Chapter five

Capability, Not Binary

A Tool declaration looks like it names a program. It doesn't — it names a capability, using its preferred mechanism as the label. That distinction is the difference between a routine that survives a changed environment and one that dies in it.

The problem, concretely

A spec declares Tool("gh", ops=["issue list", "issue view"]). The run starts, and gh is not installed. What should happen?

The naive answer is "fail" — the declared tool is missing, so the task can't run. But that's usually wrong, and it's wrong in an expensive way: the routine had the ability to list issues by another route the whole time, and it stopped anyway. The reference is direct about this. Absence of the preferred mechanism is an environment fact to route around, not a task failure.

The three conditions

Substitution isn't a free pass, though. It's permitted under exactly three conditions, and all three have teeth:

  1. Same scope, never wider. The substitute covers only the declared ops. If the spec declared issue list, the replacement may list issues — not close them, however convenient that would be.
  2. Same constraints, identically. Every rule on the task applies to the substitute exactly as it applied to the original. Swapping the mechanism doesn't reset the rules.
  3. Record it. The substitution goes into the output or the run report, so the human learns the environment drifted.

That third condition is the one people drop, and it's the one that makes the other two safe. A silent substitution works fine and teaches nobody anything; six months later the preferred mechanism has been broken for half a year and every run has been quietly papering over it.

When the mechanism is the guarantee

Sometimes a tool isn't interchangeable, and the reason is that the mechanism itself carries the guarantee. A validator, a house procedure, a signed build pipeline — these exist because of how they do the work, not merely that the work gets done. For those, Tool(..., strict=True) reverses the rule: that exact mechanism or nothing.

And the reference is unambiguous about what happens next: if a strict tool is unusable, that is a task failure, and the declared on_failure applies. No substitute is acceptable, however capable it looks. 

tools = [
    Tool("bookbank-plugin", ops=["create-book-from-issue"], strict=True),
    Tool("read", paths=["<plugin_root>/skills/**"]),
    Tool("python3", scripts=["<plugin_root>/library/validate_book.py"]),
    Tool("git", ops=["add", "commit", "push", "branch"], exclusive=True),
    Tool("gh", ops=["pr create"]),
]

Five tools, one of them strict. The distinction is the whole point of the list. gh and git are ways of reaching a service; if another route exists, fine. The plugin is not a route — it carries a structural validator, an image-slot contract and a house design that nothing else implements. Producing the same artefact by other means would skip all three and still look like a book.

A useful test

Ask: if I did this another way and the output looked identical, would anything be lost? If the answer is no, the tool is a mechanism and substitution is fine. If something invisible would be lost — a check, a convention, a signature — mark it strict.

The corollary: a script as its own specification

There's a neat extension of this rule that's worth knowing, because it turns a dead end into a path. Suppose the spec declares a script, and the script runs — but the script's own internal dependency is missing, so it can't do its job.

The reference's answer: the script then serves as the specification of the effect. Read it, reproduce its exact effect — formats, markers, idempotency — through available mechanisms at the same scope, and report the substitution.

This is more interesting than it looks. It says a script is not only an implementation; it is also the most precise available description of what the implementation was supposed to achieve. The marker format it writes, the duplicate-check it performs before creating anything — those are the contract, and they're recoverable by reading the source even when running it is impossible.

Why this rule exists

Without it, a best-effort step in an environment that can never run the script degrades into best-effort-always-fails — reporting a clean "errored, noted" every single run, forever, while nobody notices that it has never once succeeded.

The boundary that never moves

Two invariants sit underneath all of this, and they hold regardless of what's installed. Tools and capabilities not declared by the current task are out of bounds even when they're available. And substitution swaps mechanisms — it never expands capability.

Put together: a missing tool can send you looking for another way to do the declared thing. It can never send you looking for a different thing to do.

So what did we actually gain?

Robustness that doesn't cost containment. The routine rides out a changed environment, the human finds out that it drifted, and the set of things the run is permitted to touch never grows by accident.

Challenges

  1. Go through your tool declarations and mark each one mechanism or guarantee. The second group is your strict list.
  2. Pick a script your routine depends on. Could you reproduce its effect from reading it — every marker and format it writes?
  3. Where would a substitution get recorded in your current output shape? If nowhere, add the field.
