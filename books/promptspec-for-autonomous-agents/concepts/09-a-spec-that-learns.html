Chapter nine

A Spec That Learns

Everything so far has been the language. This chapter is about what happens to a specification after it meets production — and it's the part that convinced me the language is worth the trouble.

The worked example we've been quoting carries a version history in its module docstring. Not a changelog of features. A record of failures, each one traced to a specific run, each one turned into a rule. Let's read it as what it is: a postmortem that executes.

v2.0.0 — three defects from one blocked run

The first correction lists three defects "in severity order", which is already a good habit. Read them as a set, because they compound:

  1. No step gated on the capability check, so a run that could not generate anything still claimed the issue and commented on it. This is chapter seven's lesson, learned the expensive way.
  2. "Did the installer exit 0" was treated as "is the skill usable" — which it isn't, because plugins resolve at session start, so a mid-run install lands on disk and registers nothing.
  3. No step established the working directory, so repo-slug derivation and the checkout's own settings silently didn't apply.

Defect (b) is the one I'd frame and hang on a wall. The run checked something real, got a true answer, and drew a false conclusion — because the thing it measured (the installer succeeded) was not the thing it needed to know (the capability is available in this session). Every unattended routine has at least one of these, and they're invisible until the day they aren't.

A check that passes is not evidence, unless it measures the thing you actually depend on.

The fix wasn't "be more careful". It was a rule, marked must, that spells out the distinction and names the incident in its reason — so that a later editor who finds the rule fussy can see what it cost: 

("A zero exit from `claude plugin install`, and a line in "
 "`claude plugin list`, are NOT evidence the skill is usable. Usability "
 "means the skill is invocable in the session that is running now",
 "plugins resolve at session start; a mid-run install writes to disk and "
 "registers nothing. Conflating the two is what made the 2026-07-31 run "
 "report success and then fail", "must")

v2.0.1 — the missing binary

The next run met an environment without the gh CLI and stopped. The correction is chapter five in miniature: tool declarations are capabilities, not binaries, and a missing binary means "use an equivalent mechanism at the same scope and report the substitution", not "fail".

But look at what got added alongside that loosening. The same version marks the one mechanism that must never be substituted — the plugin carrying the validator and the house design — as strict=True. The author didn't just relax a rule; they relaxed it and simultaneously pinned down the exception, in the same edit. That's the shape of a good correction.

Loosen and pin, together

When a run fails because a rule was too tight, the temptation is to widen it and move on. The better edit widens the rule and names the case that must stay narrow — otherwise the next incident is the mirror image of this one.

v2.0.2 — corrections from a run that worked

Here's the entry I find most instructive. Version 2.0.2 came from "the first successful v2.0.0 run's field report". The run succeeded. It shipped. And it still produced four corrections:

  • Branch-naming authority declared. The book-branch convention is load-bearing — a downstream Action keys on it — so it must outrank the generic session-branch convention a dispatch wrapper would otherwise impose.
  • Shared-disk discipline. While the executor runs, the orchestrator performs no git operations in the same checkout: "two hands on the same git state turns delegation into corruption."
  • A declared parse for malformed input. When a structured field holds the wrong shape — prose where a list belongs — extract only explicit structure, fold the rest into notes, and record the reinterpretation.
  • Script-as-specification. The corollary we met in chapter five, written down so a best-effort step can't quietly become best-effort-always-fails.

Every one of these is friction the run's operator noticed but worked through. None of them broke anything. And each would have been re-derived — possibly differently — by the next run, because the agent that solved it doesn't carry anything forward.

That's the mechanism the whole chapter is about. An agent's judgement lasts one run. A spec lasts until someone edits it. So the question after any run isn't only "did it work?" — it's "what did this run figure out that the next one would have to figure out again?"

The rule that knows what it cost

One last constraint, because it's the most human thing in the file. The spec's alerting task requires that a notification be sent only after diagnosis has converged, that it distinguish what was verified by command from what is inferred, and that it never assert an unchecked root cause. Its reason: 

"the 2026-07-31 run pushed a confident root cause that was wrong, and the "
"correction could not reach the phone it had already misinformed"

Someone got a confident, wrong alert on their phone, and there was no way to take it back. That experience is now a permanent property of the routine. It will still be there when everyone who remembers the incident has moved on — which is precisely what an institution's memory is supposed to do, and precisely what a prose prompt cannot do.

The same task declares when to stay quiet: silent on a clean no-work run, silent on a clean success, recording a suppressed reason instead — because "a notification that was never worth reading devalues every future one". A routine that has learned when not to speak is a routine somebody trusts.

So what did we actually gain?

A place for institutional memory to accumulate. Not in a wiki nobody reads, and not in an agent's context window that evaporates at the end of the run — but in the executable artefact itself, where the next run is obliged to read it.

Where to start

You don't need to adopt the whole language on day one. If I were converting an existing routine, I'd go in this order: write the output model first, because it forces you to enumerate what "done" and "nothing to do" actually look like. Then the gate chain, because it exposes whether you mutate before you verify. Then the failure policies. The constraint lists come last and never stop growing — that's not a defect, that's the point.

And when a run surprises you, resist fixing it in your head. Open the file. Write the rule, and write down what it cost.

Challenges

  1. Find a check in your automation that measures a proxy rather than the thing you depend on. Replace it with a direct check of the capability at the moment of use.
  2. Take the last incident your team had with a scheduled job. Write the constraint tuple it should have become — rule, cost, severity.
  3. Review your most recent successful run. What did it work around that isn't written down anywhere?

That's the book. The cheatsheet has the whole language on one page for when you're writing rather than reading.
