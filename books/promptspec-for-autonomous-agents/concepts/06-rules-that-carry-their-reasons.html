Chapter six

Rules That Carry Their Reasons

Constraints in PromptSpec are tuples: the rule, the reason, and optionally a severity. The middle element is the one that makes the language work, and it's the one most likely to be filled in carelessly. 

("rule text", "why"[, "must" | "should" | "may"])

A bare string is a must. And must rules are inviolable — not "strongly preferred", not "unless there's a good reason". Inviolable.

Why write down the reason at all?

Because the agent will meet situations the author didn't imagine, and in those situations it needs to weigh things. A rule with no stated cost can't be weighed — it can only be obeyed literally or abandoned. Neither is what you want when the world has drifted slightly off-spec.

The reference puts it plainly: the why states the real cost of breaking the rule, and the agent should weigh it accordingly. So the reason isn't commentary for future maintainers. It's an operational input.

Here's the difference in practice: 

# A tautology. Tells the agent nothing when a hard case arrives.
("Do not comment on the issue early", "early comments are bad")

# A cost. The agent can now reason about a case you never wrote down.
("Never mutate a GitHub issue — label, comment, or close — before the run "
 "has proven it can actually do the work",
 "a 'work started' comment from a run that then dies is noise the next run "
 "and the human both have to untangle", "must")

Suppose the agent finds a novel mutation the rule's text doesn't quite cover — adding an assignee, say. The first version gives it nothing. The second tells it what the rule is protecting: the next run's ability to read the queue correctly. Assignees are part of that. The agent gets it right without the author having enumerated it.

Writing test

Read your why back with the rule removed. If it still tells you something about the world — what breaks, for whom, how expensive it is to clean up — it's doing its job. If it just restates the rule in different words, it's a tautology and you've written a rule that can't be weighed.

Three severities, three different jobs

Severity and what it licenses
SeverityMeaningWhen to reach for it
must Inviolable. The default for a bare string. Anything whose violation is irreversible, publicly visible, or corrupts state another run depends on.
should Strong default, weighable against a stated cost. Judgement calls with a clear right answer in the normal case — e.g. staying silent on a clean run.
may Explicitly permitted, never required. Widening the space of acceptable behaviour on purpose, so the agent doesn't treat an option as forbidden.

Notice that may exists to grant latitude, not restrict it. In a language whose baseline is "if it isn't declared you don't have it", saying "you may do X" is a real statement.

Inheritance: one-way ratchet

Rules compose down the pipeline, and the composition rule is a ratchet: a parent task's constraints bind every step inside it, and a child may add stricter rules but never weaken a parent must.

Shared lists as a policy layer

Module-level rule lists apply wherever they're referenced, which turns them into a policy layer you can name. The worked spec defines exactly one, and it's the right shape for the job: 

UNATTENDED = [
    ("Never ask questions; if anything is ambiguous, choose the conservative "
     "branch and record the ambiguity in the run report",
     "there is no human on the other end of this run"),
    ("Never mutate a GitHub issue ... before the run "
     "has proven it can actually do the work",
     "a 'work started' comment from a run that then dies is noise ...", "must"),
]

# and then, in every task:
constraints = UNATTENDED + [ ...this task's own rules... ]

Two rules, both of which are really about the same fact — nobody is watching — factored out so that no individual task can forget them. That first rule is doing double duty, incidentally: it forbids asking and tells the agent what to do instead. "Choose the conservative branch and record the ambiguity" is a complete decision procedure for every unanticipated fork in the run.

When rules collide

Two tie-breakers close the system, and they're short enough to memorise. When a rule and convenience conflict, the rule wins. When two rules conflict, the more conservative action wins.

The second one is the important one, because it means the agent never needs an authored priority ordering between every pair of rules. It has a default: do less. Take the branch with fewer irreversible effects. In an unattended run, doing less is nearly always recoverable and doing more often isn't.

Every unresolved conflict resolves toward the action that is easiest to undo.

So what did we actually gain?

Rules that survive contact with situations their author never imagined — because each one ships the cost of breaking it, and the agent can weigh a cost even when it can't match a pattern.

Challenges

  1. Apply the tautology test to every why in a spec you own. Rewrite the ones that fail.
  2. Find a rule you've marked must that is really a should. Over-marking devalues the ones that matter.
  3. Identify the rules in your spec that are really about the environment rather than the task. Factor them into a shared list and give it a name.
