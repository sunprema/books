Putting It All Together: From Files to a Running Service

Real name: "Capstone: From Repository to Running Service"

A folder of files is not yet a service

Here's the problem

Your friend has a folder. In it: a small web program that answers questions, and a little helper tool that you run from the keyboard. On your friend's laptop, both work. Now the office wants the web program running all day on a shared computer. Your friend writes a long note: "install this, then that, copy this file, start the database, remember the secret number." Two weeks later, nobody can follow the note.

You already own every tool needed to replace that note. Each earlier chapter gave you one. This chapter does not teach a new idea. It lays the tools side by side and walks one folder all the way from files to a program that runs by itself, then upgrades it, then takes the upgrade back.

Our folder is the one that has followed us through the book: a small web program written in Elixir with the Phoenix toolkit, plus a helper tool written in Rust. Call them sidekick (the web program) and sidekick-ctl (the helper).

Six pieces, one folder

Here is the whole trip as a list. Each step uses a chapter you have already read, and each gives you something you can check with your own eyes.

Steps 1 and 2: the work room, then the packages

The first page of the folder is a "flake" (chapter 13): one file that lists what the folder offers. Below is the part for the work room and the two packages. The Rust tool is the easy one. The Elixir program needs its own packaging helper, and its pieces are fetched in the way chapter 14 showed, by a hash you copy from an error message.

{
  description = "sidekick: Phoenix service + Rust helper";
  inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";

  outputs = { self, nixpkgs }:
    let
      system = "x86_64-linux";
      pkgs = nixpkgs.legacyPackages.${system};
    in {
      packages.${system} = rec {
        sidekick-ctl = pkgs.rustPlatform.buildRustPackage {
          pname = "sidekick-ctl";
          version = "0.1.0";
          src = ./ctl;
          cargoLock.lockFile = ./ctl/Cargo.lock;
          meta.mainProgram = "sidekick-ctl";
        };
        sidekick = pkgs.beamPackages.mixRelease (finalAttrs: {
          pname = "sidekick";
          version = "0.1.0";
          src = ./web;
          mixFodDeps = pkgs.beamPackages.fetchMixDeps {
            pname = "mix-deps-${finalAttrs.pname}";
            inherit (finalAttrs) src version;
            hash = pkgs.lib.fakeHash;  # build once, paste the "got:" hash
          };
        });
        default = sidekick;
      };

      devShells.${system}.default = pkgs.mkShell {
        inputsFrom = [ self.packages.${system}.sidekick-ctl ];
        packages = [ pkgs.elixir pkgs.postgresql pkgs.rust-analyzer ];
      };
    };
}

Read it slowly. The top says which big pile of recipes to use (nixpkgs) and the first build will write down exactly which version in flake.lock, so a teammate gets the same pile. Under packages sit the two programs. Under devShells sits the work room: nix develop drops you into a shell that has Elixir, a database tool and everything the Rust tool needs, and inputsFrom means you never list the Rust tool's needs twice.

Two things to know before you build

First, the flake only sees files that git knows about, so git add new files before you build. Second, the Elixir pieces are named differently in different versions of the recipe pile (you will see both mixFodDeps and mixDeps in the wild), and a Phoenix program's browser files (JavaScript and styles) are a separate step on top of this. I could not run a real Phoenix build here, so treat the Elixir half as the shape to follow and check it against the manual for the version you pinned. If the hash Nix asks for changes every time you retry, the fetching is not repeatable and the manual points you to a tool called mix2nix.

Step 3: let the folder test itself

A "check" (chapter 15) is just a small build that fails when something is wrong. Add one more output beside the others, for example the Rust tool's own tests, or a tiny script that runs the helper and compares its answer:

checks.${system}.ctl-says-hello =
  pkgs.runCommand "ctl-says-hello" {} ''
    ${self.packages.${system}.sidekick-ctl}/bin/sidekick-ctl --version > $out
  '';

Now nix flake check builds the checks and fails loudly if one does not build. Because the check uses the package, the package is built once and shared, and your computer in the office does the same work as the one on the shelf.

Step 4: say how the program should run

Nothing so far starts the web program. For that you write the form from chapter 19. This one goes a little further than the notes example: it also asks for a database, and it hands the program its secret as a file, never as text.

{ config, lib, pkgs, ... }:
let cfg = config.services.sidekick; in {
  options.services.sidekick = {
    enable = lib.mkEnableOption "the sidekick web service";
    package = lib.mkOption { type = lib.types.package; };
    port = lib.mkOption { type = lib.types.port; default = 4000; };
    secretFile = lib.mkOption {
      type = lib.types.path;
      description = "File holding the secret key; kept outside the store.";
    };
  };

  config = lib.mkIf cfg.enable {
    services.postgresql = {
      enable = true;
      ensureDatabases = [ "sidekick" ];
      ensureUsers = [ { name = "sidekick"; ensureDBOwnership = true; } ];
    };
    users.users.sidekick = { isSystemUser = true; group = "sidekick"; };
    users.groups.sidekick = { };

    systemd.services.sidekick = {
      wantedBy = [ "multi-user.target" ];
      after = [ "postgresql.service" ];
      requires = [ "postgresql.service" ];
      environment = { PORT = toString cfg.port; PHX_SERVER = "true"; };
      script = ''
        export SECRET_KEY_BASE="$(cat "$CREDENTIALS_DIRECTORY/secret")"
        ${cfg.package}/bin/migrate
        exec ${cfg.package}/bin/sidekick start
      '';
      serviceConfig = {
        User = "sidekick";
        LoadCredential = "secret:${cfg.secretFile}";
      };
    };
    networking.firewall.allowedTCPPorts = [ cfg.port ];
  };
}

Line by line, in plain words. The top half lists the boxes a computer can fill in: switch it on, which program, which door number, where the secret file is. The bottom half is only used if the switch is on. It turns on a database server and asks it to make a database and an owner called sidekick. It makes a plain user for the job to run as. It starts the web program after the database is up, reads the secret from a private spot that systemd prepares ($CREDENTIALS_DIRECTORY), runs the program's database-update command (here assumed to be a migrate script that your release provides), and then starts the server. Finally it opens the door in the wall.

I checked this form by building a computer's description with it, using a stand-in program, and reading values back: the unit waits for the database, the credential line points at the secret path, the door number is open, and the database is named. I did not boot it. Your migrate and start command names depend on how your release is set up.

Step 5: a whole pretend computer

Add the machine to the flake. This is the same trick as chapter 18: a computer is a page of settings, and that page builds.

nixosConfigurations.demo = nixpkgs.lib.nixosSystem {
  inherit system;
  modules = [
    ./module.nix
    ({ pkgs, ... }: {
      networking.hostName = "demo";
      services.sidekick = {
        enable = true;
        package = self.packages.${system}.sidekick;
        secretFile = "/run/keys/sidekick";
      };
      system.stateVersion = "25.05";
    })
  ];
};

Then build the pretend computer and start it:

nixos-rebuild build-vm --flake .#demo
./result/bin/run-demo-vm

A window opens with a new computer inside. Its disk is a file called demo.qcow2 in the folder you ran it from. That file starts empty, and that matters. The page named a secret file at /run/keys/sidekick, but nothing put it there. The web program will fail to start until you create that file inside the pretend computer. This is not a bug in your page. It is the page telling you the truth: a secret is something you bring.

Where the secret really comes from

For a throwaway demo, make the file by hand inside the VM. For a real computer, use one of the choices from chapter 19 (an encrypted file in your repository, opened by a key that lives on the machine). Either way the secret never enters the store, and never appears in the page.

What the folder cannot promise

Look back at the dotted box in the picture. Some things the folder describes completely. Others it only names.

ThingNix describes it?Who looks after it
Which version of the program runsYes, exactlythe flake and its lock file
The database program and its settingsYesthe page
That a database called sidekick existsYes (it is asked for)the page
The rows inside the databaseNoyou: backups, restores
The secret's valueNoyou: a secrets tool, or by hand
Files the program saves while runningNoyou: a state folder and its backup

This is the honest edge of the idea. A package is a pure result: same inputs, same thing. A running service is a package plus a memory. Nix is very good at the first part and politely silent about the second.

Step 6: upgrade, then take it back

Say the web program gets a new version. You change the source (or run nix flake update to pick up newer recipes), rebuild the computer, and switch. Inside the VM, or on a real machine:

nixos-rebuild switch --flake .#demo      # build the new page, make it the one in use
nixos-rebuild switch --rollback          # go back to the one before

Every switch makes a new numbered "generation" (chapter 18), and older ones stay until you clean them up. Going back means pointing at the earlier one. The old program is not rebuilt; it is still on the shelf, and the computer starts using it again. You can also pick an earlier generation from the start-up menu if the new one will not even boot.

What a rollback does not undo

It brings back the old program and settings. It does not bring back old data. Suppose the new version ran its database-update command (our unit does, every time it starts) and changed the shape of a table. The old program, now running again, may not understand that shape. So before any upgrade that changes data, take a copy, and treat "can I go back?" as two questions: can the program go back, and can the data?

Try it yourself
  1. Put the three pieces in one folder (flake.nix, module.nix, and tiny stand-in projects in web/ and ctl/), then git add everything. Run nix develop, then nix flake check.
  2. Predict first: before you build, what do you expect the first Elixir build to say about the hash? Then build and read the got: line.
  3. Build the VM, start it, and watch the web program fail for want of its secret file. Create the file inside the VM, restart the job, and see it answer on its door.
  4. Change the program's version, run switch, and list the generations. Then run switch --rollback and confirm the old version answers.
  5. Write down, in one sentence each, how you would back up the database rows, where the real secret would live, and what you would copy before an upgrade that changes data.

The folder builds the computer. You still guard what the computer remembers.

Now one folder holds your tools, your programs, your tests and your whole computer, and you can say exactly which parts it can rebuild for you and which parts are still yours to look after. Next: how to read other people's recipes and give a small fix back.
