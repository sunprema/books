Little Machines That Take Things In and Give Things Back

Real name: "Functions, Scope, and Composition"

The same settings, written again and again

Picture the Phoenix service from this book. It has a web part and an admin part. Each needs a name, a port number, and a debug switch. You write the first box of settings. Then you copy it for the second one, and change two words. Next week there is a third copy, and someone fixes a mistake in only one of them.

In a kitchen you would not rewrite the cake recipe for every cake. You would write it once, with blanks: "how many eggs, how much sugar." Then you fill in the blanks each time. In Nix the recipe with blanks is called a "function": a little machine that takes something in and gives something back.

The smallest machine

inc = x: x + 1;

Read it as: "a machine named inc. The thing that goes in is called x. What comes out is x + 1." The colon is the door between the two. To use the machine you put the thing after it with a space: inc 4 gives 5. No brackets and no commas. Brackets are only for grouping, like in school math.

Every machine in Nix has exactly one door in. If you want two things to go in, you build a machine that gives back another machine:

add = a: b: a + b;
inc = add 1;      # still waiting for b
# add 2 3  gives 5
# inc 4    gives 5

Give add only the first number and you get back a half-filled machine that waits for the second. That is why inc = add 1 works. People call this "currying", but you can just think of it as filling the blanks one at a time.

A machine that takes a box of settings

For our service, the one thing that goes in is a box of labeled slots, which you met last chapter. You can write the slot names right in the door:

{ name, port ? 4000, debug ? false, ... }:
{
  label = "${name}:${toString port}";
  inherit debug;
}

Walk through it. Between the curly brackets are the blanks. name has no backup, so whoever uses this machine must give it. port ? 4000 means "if nobody says, use 4000". debug ? false works the same way. The three dots at the end say: "if the box has more slots than I asked for, that is fine." Without the dots, an extra slot is an error. After the colon comes what the machine gives back: a new box. (toString turns the number into text so it can sit inside quote marks.)

There is one more trick. If you want the whole incoming box as well as its parts, give it a name with @, like args@{ name, ... }:. Watch out: slots that were missing and filled by a backup are not in args. Only what the caller really sent is there.

You will see this everywhere

Open almost any real Nix file and the first line is { pkgs, ... }:. It is exactly the machine above: a door that expects a box with a slot called pkgs and does not mind other slots. Who fills it in? Later chapters show a helper that looks at the names in the door and hands over the matching things.

Which sticky notes can the machine see?

Remember the sticky notes from let. A machine can read the notes that were on the desk where it was written. Not the notes on the desk where it is later used. Look:

let
  x = 1;
  f = y: x + y;
in
  let x = 100; in f 1

The answer is 2, not 101. The machine f was built next to the note x = 1, and it keeps looking at that one. The new x = 100 is a different note that f cannot see. People call this "lexical scope", which only means: where it is written decides what it can see. This is a gift. You can read a machine alone and know what it does, without checking every place that uses it.

One machine, one file

Remember that a file holds one single thing. If that thing is a machine, the file is a machine. Save the mkService text above as mkService.nix. In another file, bring it in with import:

let
  mkService = import ./mkService.nix;
in {
  services = map (name: mkService { inherit name; })
                 [ "web" "admin" ];
  worker = mkService { name = "worker"; port = 4100; };
}

import ./mkService.nix reads the file and gives back the thing inside it, here the machine. Then mkService { name = "worker"; port = 4100; } feeds it a box. You should get a label of "worker:4100". The others get port 4000, from the backup.

The word map deserves a look. map f list runs machine f on each thing in the row and gives back a row of results. Here the machine is a tiny unnamed one, name: mkService { inherit name; }. A machine that takes another machine in, or gives one back, is called "higher-order". In Nix machines are just things, like numbers and text. You can put them in boxes and pass them around.

Write the blanks once. Fill them in many times.

What to watch out for

The strict door is annoying at first. Forget one required slot, or add one the door does not allow, and Nix stops with an error about a missing or unexpected argument. That is the machine telling you the truth. Also, a machine on its own has no value to show: asking nix eval to print a function just fails. Feed it first. And there is a price for splitting everything into small files: if you chop too fine, readers must jump between ten files to learn one thing. Split when you repeat yourself, not before.

Try it yourself
  1. Save mkService.nix and a second file that imports it. Evaluate it with nix eval --file project.nix.
  2. Guess, then check: what happens if you call the machine with no name? What if you add colour = "red" to the box? Now delete the ... and try again.
  3. Add a third service whose port comes from a number in a let. Then make inc and add from above and call each one.
  4. Run the f and x example and check that you get 2.
