Learning From Others' Work and Adding Your Own

Real name: "Reading and Contributing to the Ecosystem"

A huge shelf of recipes, and you are new here

Here's the problem

You walk into a giant shared kitchen. The walls are covered with recipe cards, written by thousands of cooks over many years. You need one card that is missing. Or one card has an old number on it and needs a fresh one. You do not know where cards live, which cooks to trust, or how a new card gets onto the wall. So you stand there, holding your card, and do nothing.

That kitchen is nixpkgs, the big shared pile of package recipes you have used since chapter 10. It is also the best teacher you have. Every trick in this book is in there, used by real people for real programs. This chapter shows you how to read it, and how to hand back one small, tidy fix.

Where the cards live

Newer recipes sit in a folder called pkgs/by-name. The rule is simple: take the first two letters of the program's name, then its full name, then a file called package.nix. The recipe for hello is at pkgs/by-name/he/hello/package.nix. Other files for the same program, such as a test, sit in the same folder.

That file is a function (chapter 6). Its arguments are the things the recipe needs: lib, stdenv, fetchurl. Nixpkgs fills them in for you with callPackage (chapter 11), so nobody has to add a line to a long list. Drop the file in the right folder and the program exists. Older recipes sit in a pile sorted by topic. That pile is being retired, so new recipes go in by-name.

Finding the card for a program you already use

You do not need to dig through folders. Ask Nix where a recipe lives. Every package remembers the file and line where it was written:

$ nix-instantiate --eval -A hello.meta.position '<nixpkgs>'
"/nix/store/…-source/pkgs/by-name/he/hello/package.nix:58"

The long part in the middle is the copy of nixpkgs you are using, and the last part is the file and line. The line points at the meta block, which is a good doorway into any recipe. The website search.nixos.org does the same job in a browser, and links to the source.

Reading a card you have never seen

Open a recipe and read it in the same order each time. Do not start at the top and try to understand every word. Ask five small questions, one after another.

  1. What does it need? Look at the arguments at the top. That is the shopping list.
  2. What is the source? Find src. It is usually a fetch helper with a hash.
  3. How is it built? Look for stdenv.mkDerivation or a language helper like buildRustPackage. If you see no phases written out, the default steps from chapter 9 are doing the work.
  4. What was changed on purpose? Patches, flags, and lines that start with a comment. These are the cook's notes. Each one is a lesson.
  5. What does it promise? The meta block: who looks after it, its licence, the name of the main program.

Here is the middle of the real hello recipe, trimmed. Everything in it is something you met earlier.

stdenv.mkDerivation (finalAttrs: {
  pname = "hello";
  version = "2.12.3";

  src = fetchurl {
    url = "mirror://gnu/hello/hello-${finalAttrs.version}.tar.gz";
    hash = "sha256-DV9gFUOC/uELEUocNOeF2LH0kgc64tOm97FHaHs2aqA=";
  };

  doCheck = true;

  passthru.tests = {
    version = testers.testVersion { package = hello; };
  };
  # …
})

Walk through it. The function takes finalAttrs, which means "the finished version of this very list". That is why the web address can say finalAttrs.version: if somebody changes the version later, the address follows along, and nothing is left behind saying the old number. doCheck = true runs the program's own tests during the build. The passthru.tests part is a small test that other people can run, kept beside the recipe. This is recipe-writing as people really do it: small, and full of habits worth copying.

Copy the shape, not the baggage

When you copy a nearby recipe, you also copy its patches, its flags and its special cases. Some were needed for that program only. For every line you keep, you should be able to say why it is there. If you cannot, take it out and see if the build still works.

Adding your own card

Now the other direction. Say you want to share a tiny program called greet. Make the folder pkgs/by-name/gr/greet/ and put this inside package.nix. I built and ran this exact recipe, using a local tarball in place of a web address, and it printed its greeting.

{ lib, stdenv, fetchurl }:

stdenv.mkDerivation (finalAttrs: {
  pname = "greet";
  version = "1.0";

  src = fetchurl {
    url = "https://example.org/greet-${finalAttrs.version}.tar.gz";
    hash = lib.fakeHash;
  };

  sourceRoot = ".";
  dontBuild = true;
  installPhase = ''
    runHook preInstall
    install -Dm755 greet $out/bin/greet
    runHook postInstall
  '';

  meta = {
    description = "Prints a friendly greeting";
    homepage = "https://example.org/greet";
    license = lib.licenses.mit;
    maintainers = with lib.maintainers; [ /* your handle */ ];
    mainProgram = "greet";
  };
})

The hash = lib.fakeHash line is a trick you know from chapter 14: a hash that cannot be right, so that the first build tells you the true one. Run the build from the top of your nixpkgs copy:

$ git add pkgs/by-name/gr/greet/package.nix
$ nix-build -A greet
error: hash mismatch in fixed-output derivation '…greet-1.0.tar.gz.drv':
         specified: sha256-AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=
            got:    sha256-zLu2+/HiK0D1nQ3HyBKF5iYOeT2I+D6BrlB2tcqVSuw=

Paste the got: value in, build again, and look in ./result/bin. Run the program. A recipe that builds but whose program you never ran has not been tested.

What the meta block must hold is not optional for a new recipe: a description, a homepage, the license that matches the original program, a mainProgram when there is one main tool, and at least one person who looks after it. That person is you. Naming yourself says "I will answer when this breaks." Your own entry goes in a separate first commit named maintainers: add <handle>.

Two small traps

New files must be git added, or Nix pretends they do not exist. And the name must match the program's real name: no capital letters, hyphens kept, and an underscore in front if the name starts with a digit (0ad becomes _0ad).

Giving an old card a fresh number

Most gifts are not new recipes. They are fresh numbers. The program released version 1.1, and the card still says 1.0. You change two things: version and the hash. If you change only the first, the build stops and says the hash it expected does not match the files it got. I tried it. That message is not a punishment. It tells you the new hash, and you paste it in.

-  version = "1.0";
+  version = "1.1";
…
-    hash = "sha256-zLu2+/HiK0D1nQ3HyBKF5iYOeT2I+D6BrlB2tcqVSuw=";
+    hash = "sha256-8aZJadqMnl8hM9O5K3Fgy1NAfbF93SDMsGGFD4emBF8=";

Then read the program's own list of changes. Did it add a new thing it needs? Did it drop one? Did a patch in your recipe become pointless? A bump is a small act of reading, not just a pair of find-and-replace edits.

Helpers exist. A robot named r-ryantm opens many of these bump requests by itself. A recipe can carry a line, passthru.updateScript = nix-update-script { };, that tells the tools how to bump it. A tool called nix-update follows that line. If the program's tags look like v1.2.3, with a letter in front, the tool needs a hint, a --version-regex. Do not write a script that makes its own commits.

Test before anyone has to ask

A reviewer is a tired stranger. Make their evening easy by checking what they would check.

QuestionHow you answer it
Does it build?nix-build -A greet (add -K to keep the folder if it fails)
Does the program run?Run what is in ./result/bin
Does it build in the safe room?Leave the sandbox on. It is on by default on Linux, and the build farm uses it
Do its own tests pass?nix-build -A pkgs.greet.passthru.tests, and any related tests under nixosTests (Linux only)
Did I break a neighbour?nixpkgs-review wip builds everything that uses your change

Tick only the computers you really tried. A box ticked for a machine you never touched is a small lie, and a review is built on trust.

Sending it in

Keep one idea in each commit. For a new recipe the first line is greet: init at 1.0. For a bump it is greet: 1.0 -> 1.1, and the body links to the release notes. No full stop at the end of the first line. Squash the "oops, forgot a space" commits away.

Then pick where the change goes. Most go to master. If your change makes a great many other programs rebuild (roughly five hundred is the point to start worrying, and a thousand or more is a "mass rebuild"), it goes to staging instead, so it does not clog the line. When unsure, choose master and the reviewers will tell you.

Fill in the checklist honestly, and say in a sentence what you tried. Expect questions. Answer them calmly and push small fixes. A first request that gets three comments is a normal first request.

Knowing when to write less

The best new recipe is sometimes none. Before writing one, go down this list in order.

  1. Is it already there? Search first. Maybe under another name.
  2. Is a language helper enough? For a Rust or Elixir program, buildRustPackage or mixRelease already does the heavy lifting (chapter 14).
  3. Is a small change enough? An override or overrideAttrs in your own project (chapter 11) beats a new recipe you must keep up forever.
  4. Is this only for you? Keep it in your own project's flake. Not every card belongs on the shared wall.

One warning when you override. Changing only version in an overrideAttrs makes Nix print a warning, because the program would claim to be the new number but still build the old files. I saw that warning. Change src with it, or the number is a fib.

Inside nixpkgs itself the advice goes one step further: avoid overrideAttrs there, and give a recipe an explicit on/off switch for an optional feature instead. A switch is something others can use with a plain override.

A small shelf of your own

You can copy this layout for your own project. Keep a folder with one package.nix per program, each taking its needs as arguments, and have one file gather them with callPackage:

{ pkgs ? import <nixpkgs> {} }:
{
  sidekick-ctl = pkgs.callPackage ./pkgs/sidekick-ctl/package.nix { };
  greet        = pkgs.callPackage ./pkgs/greet/package.nix { };
}

Now your shelf and the big shelf share one habit. A person who has read nixpkgs can read yours in a minute, and a recipe that works on your shelf can be carried to the big one with almost no change.

What this does not solve

  • Reading is slow at first. Old recipes use old habits, and you will meet three ways of doing one thing.
  • A merged recipe is a promise to keep it fresh. Others will ask you to answer for it.
  • Details change: the folder rules, the checklist and the commit rules move over time. Read the files named README.md and CONTRIBUTING.md in the copy you have, not this page, when they disagree.
  • I could not open a real pull request from here, and my build tests used a tiny made-up program. The steps are checked against the official guides.
Try it: change one thing and predict
  1. Pick a program you use that is small and plain. Find its recipe with meta.position and read it with the five questions. Write one sentence for each answer.
  2. Copy the recipe, bump nothing, and build it with nix-build from a copy of nixpkgs. Now change only its version. Predict what the first line of the error will be, then check.
  3. Change version and hash to a real newer release. Build, run the program, and run nixpkgs-review wip if you can.
  4. Write the commit message, the way greet: 1.0 -> 1.1 is written, and a three-line pull request note: what changed, what you ran, what you did not run.

The big shelf is just recipes. You already read recipes.

Now the biggest pile of Nix code in the world is a place you can read, learn from, and leave a little better than you found it. That is the last chapter of the lessons; the quick-look page comes next.
