Making Your Own Computer Feel Like Home

Real name: "Managing a User Environment"

The new desk

Here's the problem

You get a new desk at a new job. You spend two days putting things back the way you like them: the lamp here, the pens there, the chair just so. A year later you get another desk, and you cannot remember half of it. Your old desk is gone, and with it, the way you had it.

Your computer is the same. Over the years you tuned your shell, your editor and your Git settings. Those settings live in small hidden files in your home folder. They are not written down as a plan anywhere. A new machine means a new two days, and you will forget things. Earlier chapters made projects repeatable. This chapter does it for you.

The idea: write your desk down, then let a helper set it up

A helper program called "Home Manager" reads a plan for your home folder and makes the folder match. It is its own project, not part of Nix itself, but it is built on the form-and-boxes machine from chapter 16. Your plan is one more filled-in form. You do not need a new operating system for this. It works on top of the Nix you already have, on Linux or a Mac.

In the plan you say things like "I want these tools" and "Git should know my name". Home Manager makes the tools appear, writes the files the tools read, and keeps every old version of your desk so you can go back.

The smallest plan

Here is a plan that does three small things: gives you two tools, turns on Git with your name, and says which Home Manager rules you started with.

{ pkgs, ... }: {
  home.username      = "ada";
  home.homeDirectory = "/home/ada";
  home.stateVersion  = "25.05";

  home.packages = [ pkgs.ripgrep pkgs.jq ];

  programs.git = {
    enable    = true;
    userName  = "Ada";
    userEmail = "ada@example.com";
  };
}

Walk through it. The first two lines say who you are and where home is. home.packages is a plain list of tools to put on your path. programs.git.enable does more than install Git: it also writes the Git settings file for you. That is the nice part about the programs boxes. One switch gives you the tool and its settings together.

The line home.stateVersion confuses almost everyone, and that is fair. It does not say which Home Manager you use. It says which release's old habits your files were first made with, so that an update never quietly moves things under you. Set it once, to the release you started on, and leave it alone. Do not raise it to "get the new version".

Names move

Home Manager's box names change from release to release. In newer ones, the Git name and email moved under programs.git.settings.user. I could not test against a live release while writing this page, so treat the names above as a shape, and look up the options for your own release.

Putting the plan to work

The plan sits in a small folder with a flake (chapter 13), so the versions are locked just like any project. Your flake gives one named setup, and you apply it with one command:

home-manager switch --flake .#ada

That word, "switch", builds the new desk and then moves you over to it. The steps are the ones you know: Nix works out the plan (evaluation), builds the files (building), and then Home Manager does one new thing, "activation": it puts links in your home folder that point at the built files. Each switch makes a numbered "generation", and the older ones stay. If the new desk is wrong, you can move back to an old one.

One thing surprises people. Those linked files are read-only, because they live in the store. If you open ~/.config/git/config and try to change it by hand, you cannot, or the next switch puts it back. Change the plan, then switch. That is the whole deal: the plan is the truth.

When your old desk is already there

Here's the problem

The helper arrives and wants to put a lamp where your own lamp already stands. A good helper does not throw your lamp away. It stops and asks.

Home Manager does exactly that. If a file it wants to manage already exists and is not one of its links, it refuses and tells you to move or remove it, or to use a backup option. Lots of people find this stop annoying on the first day, and that is fair. It is also the reason the helper is safe to try. You have two honest ways through:

  • Move your file aside yourself: rename ~/.gitconfig to ~/.gitconfig.mine, copy the settings you care about into the plan, then switch.
  • Ask for backups: home-manager switch -b backup --flake .#ada renames each blocking file to end in .backup and carries on. When Home Manager runs as part of a bigger system setup, the matching box is home-manager.backupFileExtension.

Either way, a good habit is to take over one thing at a time. Start with Git. Switch. Check it works. Then your shell. Then your editor. You do not have to burn down every file you own in one afternoon, and nothing says you must ever manage all of them.

One plan in many small files

A home plan grows. Soon it is long, and you want to find the Git part fast. This is the module system from chapter 16 doing what it does. Split the plan into small files and list them under imports:

# home.nix
{ ... }: {
  imports = [ ./git.nix ./shell.nix ./editor.nix ];
  home.username = "ada";
  home.homeDirectory = "/home/ada";
  home.stateVersion = "25.05";
}

Each small file is a module: it fills in only its own boxes. Because the boxes merge, a list of tools set in two files joins into one list. Two plain values for the same single box clash, and Nix names both files, just like in chapter 16.

Two desks that are not the same

Your laptop at home and your work machine are alike in most ways and different in a few. One has a work email. One is a Mac. You do not want two copies of the plan. You want one shared plan and a small note for each machine. Use the tools you already have:

  • Put the shared wishes in shared files, using lib.mkDefault for anything a machine might change.
  • Give each machine its own small file that sets its own values as plain notes. Plain beats mkDefault, so the machine wins and the shared file stays untouched.
  • For a piece that only makes sense on one kind of machine, wrap it in lib.mkIf pkgs.stdenv.isDarwin { ... }.
# hosts/work.nix
{ lib, ... }: {
  imports = [ ../home.nix ];
  programs.git.userEmail = "ada@work.example";
  home.packages = [ ];  # work-only tools go here
}

In the flake you name one setup per machine, such as ada@home and ada@work, and each points at its own file. Same plan underneath, small differences on top.

Yours, or the project's?

There is a trap here. Once you have a tidy home plan, it is tempting to put everything in it, even the exact compiler a project needs. Do not. Ask one question about each thing: "If a friend cloned this project, would they need it?" If yes, it belongs in the project's own dev shell (chapter 12), where the friend gets it too. If no, it is a taste of yours: your prompt, your editor colors, your Git name. That goes in the home plan.

Belongs to you (home plan)Belongs to the project (dev shell)
Shell prompt and aliasesThe compiler and its exact version
Editor look and keysBuild tools and linters the team agreed on
Git name, email, tidy habitsSettings the tests need
Handy tools you like (ripgrep)Anything a new teammate would trip on
Try it yourself
  1. Make a folder with a flake and a home.nix like the one above, using your own name. Follow the Home Manager manual for your release to wire up the flake.
  2. Before you switch, predict: which of your existing files will it refuse to touch? Check, then switch.
  3. Add one tool to home.packages, switch, and find the new generation in the list.
  4. Try to edit the generated Git file by hand. What happens? Now change the plan instead.
  5. Add a second file for a pretend second machine that changes only your email. Build both setups and compare the two files.
What this does not do

Home Manager gives you settings you can repeat. It does not hold your secrets safely: anything you write in the plan ends up in the store, which every user on the machine can read (chapter 19 comes back to this). It also does not hold your data. Your photos and your notes are not part of the plan. And it adds one more tool to learn and update, with box names that drift between releases. Many people manage a few files this way and leave the rest alone, which is a fine place to stop.

Write your desk down once. Take over one drawer at a time.

Now a new machine is an afternoon, not two days, because the way you like it is written down and checked. Next, we use the same form-filling idea for the whole computer.
