Making Real Programs People Can Use

Real name: "Packaging Real Applications"

The shopping list is somewhere else

Here's the problem

You are cooking dinner for friends from a recipe card (chapter 10). The card is short: "bread, salt, soup." But your real program is not bread. It is a long dinner, and the card says "use the cheese from the cheese list, the herbs from the herb list, and the wine from the wine list." Each list lives in a different folder, and each one names things you have never heard of.

Real programs work like that. A Rust program has a file that lists every little piece of code it borrows from other people. An Elixir program has the same kind of file, in its own style. When you build on your laptop, the tool simply goes out and fetches them. But a Nix build happens in a closed room with no door to the outside (chapter 9). Nothing can be fetched during the build. So the shopping has to be done first, with every item written down and checked, and then the shopping bag is carried into the room.

The fix: do the shopping in a separate, checked step

Nixpkgs has helpers that do this shopping for each language. Think of them as cooks who already know where each list lives. Under the hood they are still the recipe-card helper from chapter 10, with the same steps in the same order. They add two things: a way to fetch the borrowed code ahead of time, and a few extra steps that tell the language's own tools "look in this bag, not on the internet."

The Rust program

I made a tiny Rust program called greet with one borrowed piece of code, a random-number helper called fastrand. Its list is Cargo.lock, which Cargo writes for you and which you keep in git. This is the whole Nix file:

{ pkgs ? import <nixpkgs> { } }:
pkgs.rustPlatform.buildRustPackage {
  pname = "greet";
  version = "0.1.0";
  src = ./.;
  cargoLock.lockFile = ./Cargo.lock;
  meta.mainProgram = "greet";
}

Walk through it. rustPlatform.buildRustPackage is the Rust cook. pname and version are the name tag, as before. src = ./. says the code is in this folder. The new line is cargoLock.lockFile: it points the cook at the shopping list. Nix reads that list and fetches each borrowed piece by the fingerprint that Cargo already wrote down in it, so you write no hash by hand. The last line says which program inside is the main one, so nix run knows.

I ran nix-build on Nix 2.34.6 with Nixpkgs 26.11. It worked, and result/bin/greet Ada printed hello, Ada (lucky number 6). In the log I could see the steps you know from chapter 10. After the patch step came a line saying Validating consistency between Cargo.lock and the vendor dir: the cook checking the bag against the list. The build step ran Cargo with --offline, so the door really was shut. And a check step ran the program's tests, which the Rust cook does by default.

The other way: one fingerprint for the whole bag

There is a second way to say the same thing, and many packages in Nixpkgs use it: cargoHash. Instead of one fingerprint per borrowed piece, you write one for the whole bag. You do not know it yet, so you start with a pretend one, lib.fakeHash, and build once on purpose. It fails, and the failure tells you the answer:

error: hash mismatch in fixed-output derivation '…greet-0.1.0-vendor-staging.drv':
         specified: sha256-AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=
            got:    sha256-i+b/ROLku60uIwA/HBfEyMYz7WTups9Oq2SyUlfNoqY=

That is what I got. Copy the got line into cargoHash and build again. The catch is that the bag's fingerprint changes whenever the list changes, so every time you add a borrowed piece you must do the pretend-hash dance again. That is why cargoLock is nicer inside your own project, and cargoHash is common in Nixpkgs itself. If a borrowed piece comes from git instead of the usual shop, cargoLock also wants an entry for it in outputHashes, found the same way, with a pretend hash first.

The list is the boss

I added a new borrowed piece to Cargo.toml but forgot to update Cargo.lock. The build failed offline with no matching package named `itoa` found. The shut door means the list is the only truth. Keep Cargo.lock in git, and make sure it is inside the src you give Nix.

What the finished program carries

Ask for the closure of the result (chapter 4) and you get six items: the program, plus the C library glibc, two small helpers for text, and two pieces of the compiler's runtime. That is all. The borrowed Rust code, fastrand included, is melted into the program itself, so it does not travel as a separate item. A program from this cook is a single file you can copy to another Nix machine with everything it needs close behind.

Some Rust programs need a real library from outside Rust, such as OpenSSL. Then the rule from chapter 10 applies again: tools used during the build, such as pkg-config, go in nativeBuildInputs, and libraries the program links to go in buildInputs. When a build script of a borrowed piece cannot find one, the error comes from that piece, not from Nix, and it points at the same two lists.

The Elixir program

Elixir uses a different shop. Its list is mix.lock. The cook is beamPackages.mixRelease, and what it makes is called a "release": one folder holding your program, the borrowed code, and the little engine that runs it, so the target machine needs no Elixir installed. Here is the shape from the Nixpkgs manual. I did not build a whole Phoenix web program in this chapter; I checked that the helper exists in Nixpkgs 26.11 and which arguments it takes, and the rest follows the manual.

{ beamPackages, lib }:
beamPackages.mixRelease (finalAttrs: {
  pname = "your_project";
  version = "0.0.1";
  src = ./.;

  mixFodDeps = beamPackages.fetchMixDeps {
    pname = "mix-deps-${finalAttrs.pname}";
    inherit (finalAttrs) src version;
    hash = lib.fakeHash;
  };
})

Line by line: the function wants beamPackages, the whole shelf of Erlang-world things. mixRelease is the Elixir cook. Notice that you never say which Elixir to use: the shelf you pick decides it (for example beam27Packages), so the cook and the engine always match. mixFodDeps is the shopping bag. fetchMixDeps does the shopping in its own checked step and wants a fingerprint, which you find with the same pretend-hash trick as before.

There is a second way, called mix2nix. It reads mix.lock and writes out a Nix file naming every borrowed piece. Its good side: Nix knows the whole list, so changing one piece does not refetch all of them. Its bad sides: you must run it again whenever the list changes, and it cannot handle pieces fetched from git. The manual also says that if a second run of the pretend-hash dance asks for yet another hash, the shopping is not repeatable and you must switch to mix2nix.

A web program built with Phoenix has a third list: the browser files, which come from npm or yarn. The manual says to fetch these with buildNpmPackage or fetchYarnDeps, as a separate step. If your page has no styles after packaging, this is the first place to look: the mix bag does not contain the browser files.

Do not bake in the keys

A release built by Nix lands in the store, and anyone on the machine can read the store (chapter 4). So the database address and the secret key must not be written into the build. The manual says to move them into runtime.exs, which reads them when the program starts. It also says a release needs RELEASE_TMP set to a folder it may write to.

Why bother, and a work room is not a package

It is fair to grumble. Pretend hashes feel silly, the two-step shopping is more than cargo build ever asked of you, and some days a package takes an hour for one missing library. What you get back: the same bytes on your laptop, your friend's laptop, and the server, and a record of exactly which borrowed pieces went in.

Do not mix up the two things from chapters 12 and 14. A work room (chapter 12) holds tools so you can work on the code, and builds nothing. A package is a finished thing, cooked in the closed room, that must bring along what it needs. They can share the list of tools: mkShell accepts inputsFrom = [ yourPackage ], which puts everything the package needs to build into the room.

And the cooks are optional. For a small script or a project that is just a Makefile, the plain recipe-card helper from chapter 10 is simpler. Reach for the language cook when the language has a lock file that Nix can turn into many small checked fetches. If you cannot read what the helper is doing, drop down to the plain version and look.

Try it yourself
  1. Make a Rust program with cargo new --bin greet, add one dependency with cargo add, and commit Cargo.lock. Write the Nix file above and build it. Run the result.
  2. Switch from cargoLock to cargoHash = lib.fakeHash. Predict what the error will say, build, and paste the got value.
  3. Add a second dependency to Cargo.toml without updating Cargo.lock. Which phase fails, and what does the message say?
  4. Ask for the closure with nix-store -qR. Is your borrowed crate in the list? Why or why not?
  5. For an Elixir project, write the mixRelease file with fakeHash and read the first failure. Compare the two workflows: where is each hash written, and what makes you redo it?
What this does not do

Packaging builds the program. It does not run the database, make your secrets, or keep your data. A release in the store is a file, not a running service. Those parts come in later chapters, and the last one shows them kept in plain sight. Also, helper names and arguments change between Nixpkgs versions, so check the manual for yours.

Shop first with a fingerprint, then cook with the door shut.

Now a real program, with all the code it borrows, is something Nix can rebuild exactly, on any machine, any day.

Sources: the Rust build, cargoHash mismatch, out-of-sync lock and closure were run on Nix 2.34.6 with Nixpkgs 26.11pre (src-local-rust-build-nix-2.34). Helper behavior and arguments follow the Nixpkgs manual (src-nixpkgs-rust-section, src-nixpkgs-beam-section). The Elixir release example was checked only for the helper's argument names (src-local-beam-eval) and was not built.
