Reading the Words Nix Is Written In

Real name: "Learning the Nix Expression Language"

A list of orders, or a drawing of the finished thing?

Say you ask a friend to set a table. One way is to give orders: "get a plate, put it down, now get a cup." The other way is to hand over a drawing of the finished table and say, "make it look like this." Shell scripts are the orders. The words Nix is written in are the drawing.

This trips up many people, and that is fair. You know how to write orders. A file in this language does not say "do this, then do that". It holds one single thing, and the whole file is the name for that thing. The language is called "the Nix expression language", and each file you write in it is one "expression": a piece of text that stands for a value, the way "2 + 3" stands for 5.

The kinds of things you can write down

Here is a small file, top to bottom. Read it like a page, not like a recipe.

let
  name    = "hello";
  version = "2.12";
  base    = { port = 4000; debug = false; };
in {
  label    = "${name}-${version}";
  settings = base // { debug = true; };
  tools    = [ "elixir" "rustc" ] ++ [ "git" ];
  mode     = if base.port > 1024 then "user" else "admin";
  here     = ./.;
}

Words in quote marks are text. Plain digits are numbers, and true and false are yes and no. A bit of text that starts with ./ is a "path": a place on your disk, which Nix treats as a real thing and not as plain text. It needs at least one slash; without one, Nix thinks you mean a name, not a place.

Square brackets make a "list": things in a row. Look close: there are no commas. Things are split by spaces. Lots of people write a comma by habit, and it goes wrong in strange ways.

Curly brackets make an "attribute set": a box of labeled slots, each a name and a value, each ending in a semicolon. Even the last one needs its semicolon. This is the thing you will write most. Almost everything in Nix, a package, a setting, a whole machine, is a box of labeled slots.

Giving things a short name

The top of the file says let ... in. Between those two words you give short names to things, like sticky notes on a desk. After in comes the one thing the file is. The sticky notes only work inside that part. Nothing outside can see them, and you never change a note once it is stuck on. If you want a different value, you write a new note.

Below that, "${name}-${version}" mixes notes into text. Whatever is inside the ${ } is worked out and put in place, so the text becomes "hello-2.12". This is called "interpolation".

Boxes inside boxes

To read one slot, put a dot and its name after the box: base.port is 4000. If a slot may not be there, you can give a backup: base.colour or "blue". Without the backup, asking for a missing slot is an error.

To put two boxes together, use //. Slots on the right win when both have the same name. So base // { debug = true; } is a new box with the port from base and debug turned on. The old base is untouched. One catch: this only looks at the top level. If a slot holds a box, the right-hand box replaces the whole inner box, and does not mix with it.

The same if idea works here too, but it is also a piece of the drawing: if ... then ... else ... gives back a value, and so it always needs the else. There is no such thing as "do this only sometimes and give back nothing".

Not a shell script

There are no steps here, and nothing is run. Nix just works out what the one thing in the file is. The order you write the notes in does not matter. A note can use another note below it, as long as there is a way to work it out.

Watch it work out the answer

Save the file as project.nix and ask Nix what it is:

nix eval --file project.nix

You get back a box with label = "hello-2.12", mode = "user", settings with debug = true, and a list of four tools. Nix has only worked out a value. It has not built a program or touched your machine. Keep that picture: working out a value is one job, and making a thing is a different job that comes later in the book.

Two small helpers show up all over real files. rec { a = 1; b = a + 1; } lets slots in a box see each other. inherit name; inside a box is short for name = name;. Neither is needed for what you do now; you will meet them when you read other people's files.

What this does not give you

A file like this describes values. It does not by itself make a program, an environment or a machine. Those come when this language is used to describe builds, in chapters ahead. Also, the language is small on purpose, and the error messages can be harsh. A missing semicolon is the most common trouble, and a comma in a list is next.

Try it yourself
  1. Write a file that describes a small project of yours: its name, a version, a list of tools it needs, and a box of settings such as a port number.
  2. Use let so the name and version are written once, and interpolation to build one label from them.
  3. Guess first, then check: what does { a = { x = 1; }; } // { a = { y = 2; }; } give? Run it with nix eval --expr.
  4. Take out one semicolon. Read the message. Put it back.

When you write a drawing instead of a list of orders, Nix is free to work out the rest.
