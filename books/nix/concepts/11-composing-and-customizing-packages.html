Changing Someone Else's Recipe Without Ruining It

Real name: "Composing and Customizing Packages"

You like the recipe, but not one line

The big shared box has a recipe for almost everything. Now and then it is nearly right. Maybe you want one extra patch, or the same program built without one of its parts. You must not copy the whole recipe and own it forever. And you must not scribble on the shared card, because it is not yours.

The good news is that recipe cards in this box are not fixed. Each is a thing you can ask for a changed copy of. The harder part is this: when you change one card, what happens to every other card that uses it? This chapter is about that.

Cards that ask for what they need

Look at how a card in the box begins. It does not reach out and grab things. It is a function with a list of names at the front, one for each thing it needs:

{ stdenv, zlib, pkg-config }:
stdenv.mkDerivation {
  pname = "zver"; version = "0.1"; src = ./.;
  nativeBuildInputs = [ pkg-config ];
  buildInputs = [ zlib ];
}

The card says "I need a build helper, zlib and pkg-config" and does not say where they come from. Somebody has to hand them over. That job belongs to callPackage, and the idea is called "dependency injection": the card asks by name, and the caller fills the slots.

zver = pkgs.callPackage ./zver.nix { };

callPackage opens the card, reads the names in its front list, and looks for each name in the big set of all packages. The empty braces at the end are for anything you want to hand over yourself instead. I ran a tiny version of this by hand to be sure I understood it. It is only three lines: read the wanted names with builtins.functionArgs, keep those that exist in the set, add yours on top.

callWith = autoArgs: fn: args:
  let wanted = builtins.functionArgs fn;
  in fn (builtins.intersectAttrs wanted autoArgs // args);

That is the whole trick. A name with a default value, like flag ? false, is fine if the set has none. A name with no default that the set lacks is an error, which is what you want: a missing thing is loud, not quiet.

Two kinds of change: the slots and the card

There are two places you can change a finished package, and the names are easy to mix up. Use the picture: the front list of slots, and the body of the card.

override gives you the same card with different things handed to the slots. It is the right tool to swap one library for another, or turn a switch the card already offers:

zver-small = pkgs.zver.override { zlib = pkgs.zlib-ng; };

overrideAttrs gives you the same card with different settings inside the body. You write a function that gets the old settings and returns what changes. It is the right tool for a patch, a new version, or a few extra steps:

zver-patched = pkgs.zver.overrideAttrs (old: {
  patches = (old.patches or []) ++ [ ./fix-greeting.patch ];
});

Look at old.patches or []. The old card may have no patches at all, and the ++ keeps any it did have instead of throwing them away. Beginners forget this and delete the patches that were already there. If you mix the two tools up, one of two things happens: you get an error that the name is not known, or the change does nothing at all.

Either way you get a new card, and a new card means a new address on the shelf. The old package is untouched. Both can live side by side.

A set that looks at itself

Now the hard question. Say zver is used by a second card, zver-tools. You made a changed zver. Does zver-tools use yours? With the tools above, no. You made one new card on the side; the set did not notice.

To change the thing everybody uses, we need to understand how the set is built. Here is a small set, written by hand, that has the same shape as the big one:

base = self: {
  callPackage = callWith self;
  greeting = "hello";
  shout = self.callPackage ({ greeting }: { text = greeting + "!"; }) {};
  hi = self.callPackage ({ greeting, shout }: "${greeting} / ${shout.text}") {};
};

The whole set is a function of one thing, self, which is the finished set. The cards inside get their needs from that finished set. It sounds like a snake eating its tail, but Nix is lazy (chapter 7), so each name is only worked out when someone asks. We close the loop with a tiny helper, called a "fixed point": a value that, handed to the function, comes back as itself.

fix = f: let x = f x; in x;
set0 = fix base;
# set0.hi  =>  "hello / hello!"

I ran this on Nix 2.34.6 and got exactly that. Now the interesting part. Make a changed copy of base in which greeting is "howdy", but still tie the loop at the end:

ov = final: prev: { greeting = "howdy"; };
extends = overlay: base: self:
  let prev = base self; in prev // overlay self prev;
set1 = fix (extends ov base);
# set1.hi  =>  "howdy / howdy!"

Only greeting was named in the change. Yet shout and hi both came out "howdy". That is what the loop buys you: cards reach each other through the finished set, so one change flows to all who use it. A package set is exactly this, only huge.

The two names in an overlay

A change like ov above is called an "overlay": a transparent sheet you lay on top of the whole set. It is a function with two inputs, and the names matter:

  • final is the set after every sheet has been laid on. Ask it for any package and you get the version everybody will see.
  • prev is the set as it was just before your sheet. Ask it for a name and you get the old one.

When do you use which? To build on the old version of the thing you are changing, use prev. I made a second sheet that does this, adding two more marks to the old shout:

ov2 = final: prev: {
  shout = { text = prev.shout.text + "!!"; };
};
set2 = fix (extends ov2 (extends ov base));
# set2.hi  =>  "howdy / howdy!!!"

It worked: "howdy!" from the first sheet, plus two more. Had I written final.shout.text there, the new shout would ask for itself and never finish. That is the famous infinite recursion error, and it is the most common mistake with overlays. Rule of thumb: for the same name, read prev; for other names, read final so you pick up their changes.

Lots of people find final and prev maddening, and that is fair. Two names for nearly the same set is a lot to hold. The little experiment above is the best cure I know: run it, swap one name, and watch what comes out.

In the real box you hand sheets over when you load it:

pkgs = import <nixpkgs> {
  overlays = [
    (final: prev: {
      zver = prev.zver.overrideAttrs (old: {
        patches = (old.patches or []) ++ [ ./fix-greeting.patch ];
      });
    })
  ];
};

Now pkgs.zver is the patched one, and so is the zver that zver-tools receives from callPackage. The order of the list counts: a later sheet sees the earlier ones as its prev.

What I ran and what I did not

The small set, callWith, and the sheets above were run on Nix 2.34.6. The override and overrideAttrs lines on real Nixpkgs packages come from the Nixpkgs manual; the network on my test machine would not let me fetch Nixpkgs, so I did not run them. Names like zlib-ng may differ on your version.

The price of a change at the root

You saw that a change flows to everything that uses it. Think about what the shelf has to do. Every card downstream now has a different ingredient, so each has a different address, so each must be built again. Change a library at the bottom and a great many things get made again, and the ready-made copies other people built will not match yours. A small change in the wrong place can mean a very long wait.

When a sheet is too much

A sheet over the whole set is strong, and strong things have costs: it changes the set for every reader, it is harder to follow, and it can spread far. So ask first: does anything else need to see my change?

  • Only you need the changed copy, in one place? Use override or overrideAttrs in a plain let and be done.
  • It is your own program? Put it in a file and use callPackage. No sheet.
  • Other cards must use your changed version, or you want the change to hold everywhere in one project? Now a sheet is the right tool.
Try it yourself
  1. Write the zver card with the front list from this chapter. Build it with callPackage.
  2. Make a patched copy with overrideAttrs. Keep the old patches with old.patches or []. Build both and compare their addresses.
  3. Now do the same change as an overlay and load it through overlays = [ ... ].
  4. Add a second card, zver-tools, that needs zver. Which version does it get with step 2? With step 3? Why?
  5. In the overlay, replace prev.zver with final.zver. Predict the error, then run it.
  6. In the small hand-made set, change greeting in a sheet and predict hi before you run it.
What this does not do

A changed copy does not check that your change makes sense. A patch can fail to apply, or an old version of a library can break a card that wanted a new one; you learn it when you build. And overlays hide where a thing came from: when two sheets touch the same name, you must read the order to know which wins.

Change the slots with override, the card with overrideAttrs, the whole set with a sheet.

You can now change any card in the shared box without copying it, and you know when the change will reach everyone else.

Sources: the hand-made package set, callWith, extends and the overlay results were run on Nix 2.34.6 (src-local-nix-2.34-fixpoint in research.json). The override/overrideAttrs/overlays idioms follow the Nixpkgs manual's overriding chapter and were not run against live Nixpkgs.
