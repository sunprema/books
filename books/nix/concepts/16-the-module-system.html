Filling Out a Form That Builds a Whole Setup

Real name: "The Module System"

Ten people, one list

Here's the problem

You plan a big dinner. Ten friends each hand you a note. One says "I bring bread." Another says "no nuts, please." A third says "also bread, a different kind." Nobody has seen the other notes, and the notes are in ten different pockets. Someone has to put them into one plan, and say "stop" if two notes cannot both be true.

A computer setup is the same. Many files each say a little: this program is on, that port is 8080, add this tool to the list. You want one finished plan out of all of them. Packages (chapter 10) do not do this. A package is one build. An overlay (chapter 11) changes which packages exist. Neither one merges notes. The Nix tool that merges notes is called "the module system".

The idea: a form with boxes, and notes that fill them

Picture a paper form. The form has boxes: "number of loaves" takes a whole number, "flavours" takes a list of words. Making the form is one job. Filling it in is another job, done by anyone, in any file. The module system keeps these two jobs apart:

  • "Declaring an option" means drawing a box on the form, and saying what may go in it.
  • "Defining a value" means writing something in a box that already exists.

A "module" is one file that can do either job, or both: draw boxes, fill boxes, or pull in other modules. Many modules go in. One finished, checked plan comes out. The helper that does the merging is a plain function in the Nixpkgs library, lib.evalModules. It is not part of NixOS. NixOS is only a very big form that uses it (chapter 18). Here we use the machine alone, on a form small enough to hold in your head.

The smallest working form

Here is a module for a tiny bakery. It draws four boxes, and in one place it fills the last box using the other three. I ran it on Nix 2.34.6 with the Nixpkgs library.

{ lib, config, ... }:
let cfg = config.bakery; in
{
  options.bakery = {
    enable   = lib.mkEnableOption "the bakery";
    loaves   = lib.mkOption { type = lib.types.int; default = 2; };
    flavours = lib.mkOption {
      type = lib.types.listOf lib.types.str;
      default = [ ];
    };
    summary  = lib.mkOption { type = lib.types.str; readOnly = true; };
  };

  config.bakery.summary =
    if cfg.enable
    then "${toString cfg.loaves} loaves: ${lib.concatStringsSep ", " cfg.flavours}"
    else "closed";
}

Read it as a form. The file is a function. It asks for lib (the helper tools) and config (the finished plan, after all files are merged). Under options are the boxes, each with a "type": a rule for what may go in. Under config is what this file writes. Notice that cfg.enable reads from the finished plan, not just from this file. That is how a module can react to notes written in someone else's pocket.

mkEnableOption is a shortcut for a yes/no box that starts at "no". The summary box is readOnly: only the file that drew it may fill it.

Now two more files, written by people who never met

# a.nix
{ bakery.enable = true; bakery.flavours = [ "rye" ]; }

# b.nix
{ bakery.flavours = [ "seed" ]; bakery.loaves = 5; }

A file with no options and no config is allowed. Nix reads the whole thing as "these are values to fill in". To run the merge, hand all three files to evalModules and read one box from the result:

let lib = (import <nixpkgs> {}).lib; in
(lib.evalModules {
  modules = [ ./bakery.nix ./a.nix ./b.nix ];
}).config.bakery.summary

The answer was "5 loaves: seed, rye". Three things happened. The enable note came from one file, the loaves note from another, and both flavours notes were joined into one list, because a list type knows how to join. Look at the order: seed came before rye, though I listed a.nix first. Do not count on the order. If order matters to you, the option has to say so.

Leave out a.nix and b.nix, and the same module says "closed". The module did nothing until someone switched it on. This is the usual shape of a module: a switch, some settings, and work that happens only when the switch is on.

The type is a guard at the door

Types do two jobs. They check and they merge. I put bakery.loaves = "lots" in a file. Nix stopped:

error: A definition for option `bakery.loaves' is not of type `signed integer'.
Definition values:
- In `.../c.nix': "lots"

It says which box, which type, and which file wrote the wrong thing. That last part is the great gift. A typo in one of fifty files points at itself. A misspelled box does the same: I wrote bakery.loafs and got The option `bakery.loafs' does not exist with a polite Did you mean `bakery.loaves'.... A note that matches no box is never ignored.

Merging comes from the type, too. Two lists join. Two plain numbers cannot join, so I tried loaves = 3 in one file and loaves = 4 in another:

error: The option `bakery.loaves' has conflicting definition values:
- In `.../e.nix': 4
- In `.../d.nix': 3
Use `lib.mkForce value` or `lib.mkDefault value` to change the priority on any of these definitions.

Nix does not pick a winner by file order. It stops and names both files. That is the right thing for a plan built from many hands.

Some notes shout louder: priorities

Often you want a quiet suggestion that anyone can override. Think of a shared kitchen file that says "port 8080 unless told otherwise", and one machine that says "no, 9000". Notes have a "priority", a number where lower wins:

You writePriorityMeaning
lib.mkForce x50"I mean it. Beat the ordinary notes."
x (plain)100An ordinary note.
lib.mkDefault x1000"A suggestion. Anyone may beat me."
the option's own default1500What the box holds if nobody writes.

I checked it: I filled port with mkDefault 8080 in one file and plain 9000 in another. The answer was 9000, with no error. I put mkForce "forced" against a plain "plain", and forced won. Only notes of the same priority clash. This is why shared files use mkDefault, and a particular machine uses plain values: the machine always wins, and nobody edits the shared file. Use mkForce sparingly. It is how you end up fighting yourself later.

Only when the switch is on: mkIf

A note can be conditional. lib.mkIf cond value adds value only when cond is true. When it is false, it is as if the note was never written, so the box falls back to a lower priority or its default. I checked: on = lib.mkIf false true left the box at false, its default.

Why not use an ordinary if? Both are fine at a spot where you know the value. But a module usually adds whole groups of notes only when its own switch is on, and mkIf lets that choice happen at the right moment of the merge. The familiar shape, and the one you will see in nearly every service module:

config = lib.mkIf cfg.enable {
  # everything here exists only when cfg.enable is true
};

Its sibling lib.mkMerge joins several groups into one note. It will not fix a clash: I tried mkMerge [ "a" "b" ] on a string box and got the same "conflicting definition values". Strings and numbers have no way to join. Lists do.

A small surprise

I tried to fill the summary box myself, from a test file. Nix said The option `bakery.summary' is read-only, but it's set multiple times. A read-only box has exactly one writer, and it is the file that drew it. Use it for answers you work out, not settings you choose.

Where modules sit among the things you know

ThingWhat it isQuestion it answers
PackageOne build (a derivation)What is made, and how?
OverlayA function final: prev: over the package setWhich packages exist, and which are changed?
ModuleA file that declares boxes and fills them; merged with othersWhat do we want, and do all the wishes agree?
FlakeA project folder with a standard shapeHow is this project shared?

Notice what a module is not. It does not build anything by itself. It collects wishes and checks them. Something else reads the finished plan and acts on it: in NixOS, other modules read the plan and turn it into files, services and lists of packages, and those get built (chapter 18). You can use the module system with no operating system at all. Anything that needs "many sources, one checked result" can use it, and Home Manager (chapter 17) does exactly that for your personal files.

Testing a module without a whole computer

Because evalModules is just a function, you can test with it. Write a small helper that adds your module to some test notes and reads a box:

let
  lib = (import <nixpkgs> {}).lib;
  ev = mods: (lib.evalModules {
    modules = [ ./bakery.nix ] ++ mods;
  }).config.bakery;
in {
  closed = (ev [ ]).summary;
  open   = (ev [ { bakery.enable = true; } ]).summary;
}

Run it with nix-instantiate --eval --strict. I got { closed = "closed"; open = "2 loaves: "; }. The second answer shows the default of 2 loaves and an empty flavour list. Good: it shows a thing I might not want, an empty trailing space, found without building anything. This kind of test is fast because no one is baking; it checks only the plan. It cannot tell you whether a service really runs. That is a job for a real machine, which chapter 18 gives you.

One more thing about laziness (chapter 7): Nix only works out the boxes you ask for. A broken note in a box you never read can hide until someone reads it. The check in evalModules is strict about types, but it still waits to be asked.

Try it yourself
  1. Copy bakery.nix, a.nix and b.nix. Run the merge and check you get "5 loaves: seed, rye".
  2. Predict, then test: change b.nix to bakery.loaves = lib.mkDefault 9; (add lib as an argument). Which number wins, and why?
  3. Add a new box, bakery.open, of type bool. Make summary say "closed" when enable is true but open is false.
  4. Break it on purpose three ways: a wrong type, a misspelled box, two plain numbers. Before you read each error, predict which file it will name.
  5. Split your module in two files: one draws the boxes, one holds the work inside lib.mkIf cfg.enable. Join them with imports.
What this does not do

The module system checks that your wishes agree. It does not check that they are wise. A perfect-looking plan can still ask for a port nobody listens on. Big module trees are also hard to follow: when ten files fill one box, finding why it holds a value can take time (--show-trace and chapter 20 help). The error wording and the exact helper names move between versions, so read the manual for your version.

Draw the boxes once. Let everyone fill them. Let the machine say when they disagree.

You now have the part that lets many small files become one checked plan. Next, we point it at your own computer.
