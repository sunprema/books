One Work Room for Everyone on the Team

Real name: "Reproducible Development Environments"

The new friend and the missing tool

A new friend joins your team. You say, "Just get the code and run it." An hour later they write back: it will not start. Their tool for the language is too old. A helper program is not on their machine at all. Your own machine has worked for months, because over time you added a dozen small things and forgot you did.

This is a work room problem. Your room has the right tools on the right shelves, but nobody wrote down what is in it. A good team room is the same for everyone: when you walk in, the bench has what the job needs, and nothing else gets in the way.

A room you can walk into

Nix lets you write the room down in one small file. When you step into it, the tools on the list show up and your usual tools stay out of the way. Step out, and your own machine is as it was. The thing that makes the room is called "mkShell": a helper that builds a work room out of a list.

{ pkgs ? import <nixpkgs> {} }:
pkgs.mkShell {
  packages = [ pkgs.hello pkgs.jq ];
  GREETING = "hi from the shell";
  shellHook = ''
    echo "entered: $GREETING"
  '';
}

Walk through it line by line. The first two lines say: "give me the big shared box of recipes" (you met it in chapter 10). packages is the list of tools to put on the bench. GREETING is a plain note stuck on the wall; any name you write like this becomes a note the tools in the room can read. shellHook is a few lines that run once, the moment you walk in.

I ran this file on Nix 2.34.6. Stepping in with nix-shell shell.nix printed entered: hi from the shell, and then hello was on my bench, sitting in the store (chapter 4), not in any folder I had set up. Stepping out took it all away again.

Is the room really closed?

Here is a sneaky thing. When you step in the normal way, your own stuff comes along with you. I tried a test: the room listed hello, jq and cowsay, but I also asked for curl, which I never listed. It was found anyway, in a folder on my machine. So a room can seem fine while leaning on something that only your machine has. Your friend would not have it, and the room would fail for them.

The fix is to ask for a closed room with nix-shell --pure. In my test, a note I set outside (MYSECRET=abc) was visible in the normal room and gone in the closed one. Lots of people find this annoying at first, since the closed room feels bare. That is the point: if the work runs here, it runs because the file said so.

One small detail

In my test the closed room still kept HOME, so it is a tidy room and not a sealed vault. Do not count on it to keep secrets from your tools, or to stop them from reaching your home folder.

Same room as the thing you build

You often have a recipe card for your program (chapter 10) and you want a room where you can work on it. You do not have to copy the list of tools twice. Hand the card to the room with inputsFrom, and the room takes everything the card needs to be built:

pkgs.mkShell {
  inputsFrom = [ app ];
  packages = [ pkgs.cowsay ];
  MY_FLAG = "1";
}

My test card needed jq to run and hello to build. Both turned up on the bench, along with the extra cowsay I listed myself. Now the room and the thing you build cannot drift apart, because they read one list.

Same version for every person

Here is the part people miss. The line import <nixpkgs> means "use whatever box of recipes this machine happens to have." My box and your friend's box may be from different days, so hello may differ. The room is written down, but the shelf behind it is not. To make every room the same, you must pin the box to one exact day. The next chapter shows the tidy way to do that, called a lock file. For now, remember: a list of tools is only half of a promise.

A door that opens by itself

Typing the step-in command every time is boring, and you will forget. A helper named "direnv" watches which folder you are in and steps you into the room when you arrive. You put one line in a file called .envrc in the project folder:

echo 'use flake' > .envrc
direnv allow

The first line writes a note that says "this folder has a room, use it". The second says "yes, I trust this note." Without that, direnv will not run a stranger's file, which is a good rule. After that, every time you walk into the folder, the bench is ready, and your editor and terminal can see the same tools. The line use flake fits the project shape of the next chapter. There is also a version of the helper called nix-direnv that remembers the room so that walking in a second time is quick. I did not run direnv on my test machine, so take these two lines from its guides and try them yourself.

What belongs in the room and what does not

The room holds tools. It does not hold your stuff. Tools are the same for all and never change: the store keeps them, and nobody can edit them. Stuff is yours and changes all the time: the little database you test with, a pile of saved files, a note with a password in it.

So keep them apart. A start-up line can point your tools at a place for your stuff, in the project folder:

shellHook = ''
  export PGDATA="$PWD/.pgdata"
  echo "state lives in $PGDATA, not in the store"
'';

Each line: the first says "put the data folder here, inside the project"; the second tells you so. When I ran it, PGDATA pointed into my project folder. Delete the folder and the data is gone, but the room is the same. Never write a password into the room's file, either. Everything in the file can end up in the store, and anyone on the machine can read the store (more on this in a later chapter).

Our team project

For the little service this book follows, the room would list the tools for the language of the web part, the tools for the small companion tool, and the helper programs both need. The room gives you the tools. The libraries each side downloads from its own list (the lock files of that language) still come from that language's own helper. Nix gives you the work bench; the language still brings its own parts.

Try it yourself
  1. Pick a real project of yours. Write down every tool you used this week to run it.
  2. Write a shell.nix with mkShell that lists them under packages.
  3. Step in with nix-shell --pure. Run the project. Which tool did you forget? Add it and try again.
  4. Add one note on the wall, such as a port number, and print it in shellHook.
  5. Predict first: if you remove a tool from the list but it is also on your machine, will the normal room still find it? What about the closed room? Then test it.
  6. Point a data folder to a place inside the project. Is it safe to delete?
What this does not do

The room cannot make your tools the same on every day unless the box of recipes is pinned. It does not keep your data or secrets, it does not download the libraries your language needs, and a heavy start-up hook makes every step-in slow. It is a bench, not a whole workshop.

Write the room down once, and every teammate walks into the same one.

Now a new friend can join, step into one room, and start work in minutes instead of hours.

Sources: the mkShell, --pure, inputsFrom and shellHook results were run on Nix 2.34.6 with a recent Nixpkgs (src-local-mkshell-nix-2.34). The direnv lines follow the Determinate Systems nix-direnv write-up and a flakes-and-direnv guide (src-det-nix-direnv, src-devto-flakes-direnv) and were not run.
