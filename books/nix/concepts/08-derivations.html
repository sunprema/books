The Paper That Says How to Make a Thing

Real name: "Derivations: Describing a Build"

A cake and a card

Picture a card on the kitchen wall. It says: take these eggs, this flour, this much sugar, and do these steps in this order. The card is not a cake. You can read the card, copy it, pin it up in another kitchen, and not one crumb has been made. The cake only exists after someone follows the card.

Now say a friend changes one word on the card, from "two eggs" to "three eggs". Is it the same card? No. Is it the same cake? Also no. Every cake can be traced back to exactly one card, and a different card means a different cake.

Nix works like this wall. The card is called a "derivation": a written description of one build, with every ingredient, every tool and every step spelled out. Until now you have only looked at Nix words. This chapter is where Nix words finally describe something that can be made.

The smallest card you can write

Nix has one built-in helper for writing cards, derivation. You hand it a box of slots. Three slots are a must: a name, a system (the kind of computer the work happens on), and a builder (the worker program that does the steps). Here is a whole card. Save it as hello.nix:

derivation {
  name = "hello-note";
  system = builtins.currentSystem;
  builder = "/bin/sh";
  args = [ "-c" "echo \"$greeting\" > $out" ];
  greeting = "hello from a raw derivation";
}

Walk through it with a finger on the screen. The name is a label that ends up in the file's address. The system says "this computer's kind", so the card is for the machine you sit at. The builder is the worker: here it is the plain shell program that every Unix machine has. The args are what you say to the worker, in order: "run this little script". The script says: write the greeting into the file called $out.

Two things are not obvious. First, greeting is not a special word. Any extra slot you add becomes a note the worker can read, in the form of a shell variable with that same name. That is the whole way a card passes ingredients: slots become variables. Second, $out is a variable Nix fills in for you. It is the address, inside the shared shelf of built things, where your worker must put what it makes. The worker's one job is to leave something at that address.

Writing the card is not making the cake

$ nix-instantiate hello.nix
/nix/store/wfm5fxc0axvac0gxh6faib08qiqdjr0n-hello-note.drv

This is the first step, which is the "evaluation" step from last chapter. Nix worked out the card and pinned a copy to the shared shelf. The copy ends in .drv: that is the card, in a stiff and exact form. Nothing was built. Your own address will show different letters, because yours is worked out from your computer's kind and your Nix. (You may also see a warning about --add-root. It only says the card could be thrown out later by the cleaner. Ignore it for now.)

Next, ask for the cake to be made. This is the second step, the one that runs the worker:

$ nix-store --realise /nix/store/wfm5…-hello-note.drv
building '/nix/store/wfm5…-hello-note.drv'...
/nix/store/31bb…-hello-note
$ read line < /nix/store/31bb…-hello-note; echo "$line"
hello from a raw derivation

The last line of output is where the finished thing sits. It is a plain file with your greeting inside. There are now two things on the shelf: the card, and what the card made. Keep them straight, because the next chapters lean on this split. The card says how. The result is what came out.

Reading the card

The stiff card is not secret. You can ask Nix to print it:

$ nix derivation show /nix/store/wfm5…-hello-note.drv

You get a box of notes in JSON. The parts to look at, shortened: builder is /bin/sh. args are the same two strings you wrote. env lists every variable the worker will see: your greeting, plus name, system, builder, and out, which already holds the full address of the future result. inputs is two empty lists, because this card needs no other card and no files. outputs names the one result, called out.

Notice something big: the address of the result is already written on the card, before anything was made. Nix works the address out from the card itself. That is the idea from the store chapter, now visible: the address comes from the recipe, not from the cake.

Change one word

Edit the greeting in hello.nix: add an exclamation mark at the end. Run nix-instantiate hello.nix again. A new .drv name appears (in our run, c690… where there was wfm5…). Realise it and the result sits at a new address too, and holds the new greeting. The old card and the old result are still on the shelf, untouched. Nothing was overwritten, because the new card is simply a different card.

This is why Nix can say "I already made that" with confidence. Same card, same address, nothing to do. Different card, different address, so it cannot collide with anything old.

One card using another card's cake

Real work has steps that feed each other: make the dough, then bake it. In Nix, a card uses another card's result by putting it inside a string. Here the second card reads the file the first one makes:

let
  note = derivation {
    name = "note";
    system = builtins.currentSystem;
    builder = "/bin/sh";
    args = [ "-c" "echo hello > $out" ];
  };
in derivation {
  name = "shout";
  system = builtins.currentSystem;
  builder = "/bin/sh";
  args = [ "-c" "read word < ${note}; echo \"$word, world\" > $out" ];
}

The piece ${note} turns into the address of the first result. But Nix does more than paste text. It sees that the second card talks about the first, and writes that down: in nix derivation show, the inputs now list the first card. You can ask the other way too: nix-store -q --references on the second .drv prints the first .drv. When you realise the second card, Nix first makes the first result, then runs the second worker. You never wrote "do this first". You wrote what you needed and the order came out of that.

Files work the same way. Writing ${./f.txt} in a string copies that file onto the shelf and pastes its new address. Change the file's contents and the address changes, so the card changes, so the result changes.

The empty room

Try changing the second worker to use /bin/cat and /usr/bin/tr, which exist on your computer. It fails with not found and exit code 127. The worker is run in a nearly empty room: only the shell and what the card names are there. This is on purpose. If the worker could quietly grab any tool lying around on your machine, two people's builds could differ for reasons nobody wrote down. That is the whole trouble of chapter one. The cure is to name every tool on the card, as an address on the shelf. The next chapters show how people do that without writing it by hand.

What this does not fix

Writing raw cards is slow and bare. You must set the kind of computer, the worker, and every step yourself, and in an empty room you have very few tools. Almost nobody writes them this way for real work; they use helpers that fill in the plain parts. You wrote one by hand so the helpers stop being magic. Also, a worker that does not leave anything at $out fails the build, even if it ran without a complaint. And knowing a result needed another card to be made does not mean the finished result carries it around: the "shout" result is just a text file and holds no address of the "note" file, so it does not need it later. Needed-to-make and needed-to-run are two different questions.

The result is whatever the card says, and nothing else.

Try it yourself
  1. Save hello.nix, run nix-instantiate hello.nix, then nix derivation show on the path it prints. Find builder, args, env and out.
  2. Predict first: if you realise this card, what will the result file hold? Run nix-store --realise on the .drv, then read the file.
  3. Change the greeting. Before you run anything, say whether the .drv path and the result path will change. Then check. Is the first result still on the shelf?
  4. Add a second slot, name2 = "Ana";, and use $name2 in the script. Where does it show up in nix derivation show?
  5. Write the two-card example. Run nix-store -q --references on the second .drv. Then change echo hello in the first card to echo howdy and see which of the two paths change. (Both do.)
  6. Break it on purpose: make the worker call /bin/cat. Read the error, find the exit code, and explain why the tool was missing.

Once you see that every built thing came from one written card, "why did it change?" becomes "which word on the card changed?", and that you can always find out.

Sources: every example above was run with Nix 2.34.6 on x86_64-linux using nix-instantiate, nix-store --realise and nix derivation show; the JSON layout and message wording change a little between versions, and the store paths in your run will differ.
