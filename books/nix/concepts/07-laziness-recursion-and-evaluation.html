Doing Work Only When Someone Asks

Real name: "Laziness, Recursion, and Evaluation"

The error that points at a thing you never used

You write a box of settings for the Phoenix service. One slot holds a number. Another slot holds something that is broken on purpose, because you have not finished it. You ask for the number. It comes back, and all is well. The broken slot never bothers you.

Then, a week later, a friend prints the whole box. Now it stops with an angry message, and your friend asks why you broke it. You did not break it. It was broken all along. Nobody had asked for that slot until now.

Think of a kitchen that cooks a dish only when a guest orders it. The menu can list a hundred dishes, and some of them may be impossible, and the kitchen is fine until somebody orders one. Nix works like that kitchen. People call this "laziness": nothing is worked out until some other part needs the answer.

Nothing happens until you order

let x = { a = 1; b = throw "boom"; };
in x.a

The word throw means "stop and shout this message." Even so, the answer here is 1. We asked only for a, so b was never cooked. If the last line were just x, and you asked Nix to print every part, you would hear boom. Lists and machine inputs are the same. This gives 3, even with a broken thing in the middle:

builtins.length [ 1 (throw "x") 3 ]

It only counts the spots. It never opens them. And a machine that ignores its input never works out its input: (a: 5) (abort "never") gives 5.

Why does Nix work this way? Because of how big the shared package list is. It is one huge box with a slot for every program, tens of thousands of them. You ask for one. If Nix cooked them all first, you would wait a very long time for nothing. Laziness is why asking for one slot is fast.

Making something cook on purpose

Sometimes you want to find the hidden broken slots. Two helpers do it. builtins.seq a b cooks a a little, then gives back b. "A little" means just the outside layer: for a box, it looks that the box is a box, not what is inside. So builtins.seq { a = throw "shallow"; } 1 gives 1. The stronger helper, builtins.deepSeq, cooks every slot inside, and it does shout. Use these to hunt for trouble, then take them out. Your real files should not need them.

Peeking while it cooks

builtins.trace "hi" 42

This prints trace: hi on the side and gives back 42. It is a window into the kitchen: a note drops on the floor at the moment that piece is cooked. Because of laziness, if the note never shows up, that piece was never ordered. That is information too.

A box that talks about itself

Last chapter you met rec, which lets slots in a box look at each other. Now a harder game: what if two slots each wait for the other?

rec { a = b + 1; b = a + 1; }.a

Walk through it. To know a, you need b. To know b, you need a. Two friends who will each speak only after the other one does will sit in silence forever. Nix notices the circle and stops with infinite recursion encountered. Lots of people find this message maddening, and that is fair: it does not tell you who the friends are. Read the lines under it. The first line says which slot was being cooked when the circle closed.

Here is the part that surprises people. The word rec is not the villain. This is fine and gives b = 2:

rec { a = 1; b = a + 1; }

A slot may look at another slot. It may not need itself to finish. A list that tries to include itself fails the same way: let xs = [1 2 3] ++ xs; in builtins.length xs.

A circle that is allowed

Looking at yourself is fine if you only look when asked. This describes the counting numbers forever. Each card holds a number and a way to get the next card:

nat = n: { head = n; tail = nat (n + 1); };

It never ends, and it never breaks, because the next card is not made until somebody reaches for it. Take four cards with take from the exercise below and you get [ 0 1 2 3 ]. Lazy and circular go together, which is why Nix can describe whole worlds that are bigger than the computer.

Two kinds of "it did not work"

Nix does its job in two steps. First it works out what is being asked for: this is called "evaluation". Later, if anything needs making, a little builder program runs and makes it. A shout from the first step and a shout from the second step are different things, and mixing them up wastes hours.

Shouts from step one come before any building starts. They sound like: attribute 'zzz' missing, undefined variable, cannot add a string to an integer, a missing machine input, your own throw, and the circle message above. If you see one, no building happened, so do not go and read build logs. Shouts from step two come from a builder program that ran and failed. The next chapters teach that half.

Looking inside with the little test room

The best tool for all of this is the test room, called "the REPL": you type a line, it answers at once. Start it with nix repl. Here is a file to play with, saved as lazy.nix:

rec {
  a = b + 1;
  b = a + 1;
  ok = 10;
  never = throw "I was never asked";
}

In the test room, type :l lazy.nix. The room says it added four names. The file itself did not break, because loading only looks at the box; it cooks nothing. Now try them one by one. ok gives 10. never shouts your message. a shouts the circle message, and the little arrow points at b. :t ok tells you the kind of thing it is, here "an integer". :p in front of an expression prints it with everything inside cooked. :r reloads the file after you edit it. If a message is cut short with "stack trace truncated", run the same line with --show-trace and you get all of it.

A broken thing nobody orders is not yet a problem. It is a problem waiting.

What this does not fix

Laziness moves an error to the moment somebody finally asks. The place where it shouts may be far from the place where you made the mistake. Also, a quiet success tells you little: a file that loads fine may still hold slots that shout. When something looks off, ask: which slot did I just order, and what does it need? Also keep an eye out for small traps. Writing n-1 with no spaces is read as one long name, so Nix says undefined variable 'n-1'. Write n - 1.

Try it yourself
  1. Save lazy.nix. Open nix repl, load it, and order ok, never and a. Which ones shout? Which line does the arrow point at?
  2. Guess first, then check: change b = a + 1 to b = 5. Does a work now? Does the word rec matter?
  3. Wrap a line with builtins.trace "peek" ok and watch when the note appears. Then use :p { x = 1 + 1; } to see a box fully cooked.
  4. Build the endless cards: nat from above, plus take = n: l: if n == 0 then [] else [ l.head ] ++ take (n - 1) l.tail;. Ask for take 4 (nat 0). Then ask for (nat 0).tail.tail.head and predict the answer (it is 2).
  5. Run builtins.seq { a = throw "shallow"; } 1 and then the same with deepSeq. Explain the difference in your own words.

Knowing that Nix cooks only what is ordered, and that every shout comes from a specific order, turns a scary message into a short list of questions to ask.

Sources: every example above was run with Nix 2.34.6 using nix-instantiate --eval and nix repl; exact message wording and trace layout change a little between versions. The shared-package-list note comes from the DEV Community overview. The online manual could not be fetched during this build.
