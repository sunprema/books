Sharing Parts Between Many Computers

Real name: "Reusable Services and Multiple Machines"

Two computers, one pile of copied pages

Here's the problem

Your friend now has two small computers. One shows a notes web page to the whole office. The other is a quiet box on a shelf. Your friend made the second page by copying the first and deleting things. Last month they fixed a setting on one page and forgot the other. Now the two computers disagree, and nobody remembers why.

Last chapter, one page built one whole computer. This chapter is about what happens when there are many computers, and about three things a page cannot simply hold: the parts every computer shares, the secrets, and the things the computer learns while it runs.

The idea: parts you can plug in

Remember the filled-in forms from chapter 16, the ones called "modules". A form can have its own boxes, and you can write a new form for your own program. Then any computer that wants the program just ticks one box. Two kinds of form do the work here:

  • A shared form holds what every computer should do the same way.
  • A small page per computer holds only what is different about that one.

Nothing is copied. If you fix the shared form, every computer gets the fix the next time it is built.

Writing a form for your own program

Say your friend's program is a small notes server. Its form says three things: it can be switched on, it listens at some door number, and it needs a secret file. Here it is, with a plain web server standing in for the real program so the example stays small.

{ config, lib, pkgs, ... }:
let cfg = config.services.notes; in {
  options.services.notes = {
    enable = lib.mkEnableOption "the notes service";
    port = lib.mkOption {
      type = lib.types.port;
      default = 4000;
    };
    secretFile = lib.mkOption {
      type = lib.types.path;
      description = "File with the signing secret; kept outside the store.";
    };
  };

  config = lib.mkIf cfg.enable {
    systemd.services.notes = {
      wantedBy = [ "multi-user.target" ];
      after = [ "network.target" ];
      serviceConfig = {
        ExecStart = "${pkgs.python3}/bin/python3 -m http.server ${toString cfg.port}";
        DynamicUser = true;
        StateDirectory = "notes";
        LoadCredential = "secret:${cfg.secretFile}";
      };
    };
    networking.firewall.allowedTCPPorts = [ cfg.port ];
  };
}

Walk through it. The top half declares the boxes: enable, port (a type that only accepts real door numbers) and secretFile. The bottom half says what to do only if the switch is on, thanks to mkIf. It describes a background job, called a "systemd service", that starts when the computer starts and runs as a throwaway user. It also opens the chosen door in the wall.

Two lines deserve a pause, and we come back to both. StateDirectory asks for a folder where the program may keep what it learns. LoadCredential hands the program a secret file without writing the secret into the page. I checked that a computer with the switch off has no job and no open door, and a computer with it on has both.

Many computers from one folder

Now the shared form. It holds what all your friend's computers do alike: remote login on, the wall up, a time zone, and the facts every machine needs to start. Anything a computer may reasonably change is wrapped in lib.mkDefault, the "this is only my first guess" marker from chapter 16.

# common.nix
{ lib, ... }: {
  services.openssh.enable = lib.mkDefault true;
  networking.firewall.enable = true;
  time.timeZone = lib.mkDefault "UTC";
  system.stateVersion = "25.05";
  # (disk and start-up lines go per machine; stubbed here)
}

Then one flake (chapter 13) lists the computers. A tiny helper adds the shared forms in front of each computer's own lines, so you never repeat them.

{
  inputs.nixpkgs.url = "nixpkgs";
  outputs = { nixpkgs, ... }: let
    mk = mods: nixpkgs.lib.nixosSystem {
      system = "x86_64-linux";
      modules = [ ./common.nix ./notes.nix ] ++ mods;
    };
  in { nixosConfigurations = {
    web = mk [ {
      networking.hostName = "web";
      services.notes = {
        enable = true;
        port = 8080;
        secretFile = "/run/keys/notes-secret";
      };
    } ];
    box = mk [ {
      networking.hostName = "box";
      time.timeZone = "Europe/Oslo";
    } ];
  }; };
}

I read both computers back out of this and they came out as the page promised. Both have remote login. box changed its time zone to Oslo, and web kept the shared one. Only web has the notes job, and only web has door 8080 open (box has just door 22). You build one with nixos-rebuild switch --flake .#web, run on that machine, or build it elsewhere and send it over.

Rule of thumb: policy or detail?

Policy is a decision you want everywhere: the wall is up, logins use keys. Put it in the shared form, and use mkDefault only where an exception is honest. Detail is a fact about one box: its name, its disks, its role. Put it in that computer's own page. If you copy a block between two pages, it is probably policy trying to get out.

A role is just a form a computer ticks, like notes here. A computer can tick several. That is how "web server", "build machine" and "shelf box" can share parts without sharing everything.

The page everybody can read

Here's the problem

The notes server needs a secret number to sign its pages. The easy road is to type it into the page. But the page is built into the store, and chapter 4 told you the store is a public shelf.

It really is public. I wrote a tiny file with builtins.toFile and looked at it: its mode was -r--r--r--, so every person and every program on the machine can read it. A secret typed on the page, or read from a file into the page, sits there for everyone. If the store is shared with another machine's helper or pushed to a shared cache (chapter 15), it travels too.

Never inside the store

Anything the page contains ends up in the store. So the page may say where a secret file is. It must never contain the secret itself.

That is why secretFile in our form is a path to a file, and why the example gave it as a string, "/run/keys/notes-secret". (If you wrote a path right into the page, like ./secret, Nix would copy that file into the store, which is the very thing we avoid.) Who puts the file there? Not Nix's build. You have a few honest choices:

WayWhat it means
Put the file there yourselfSimple, and fine for one box. Nothing in the page records that it must exist, so write that down.
An encrypted file in the repoTools such as "agenix" and "sops-nix" keep the secret locked inside your repository. The key to unlock it lives on the machine, outside the store. When the computer turns the page on, it unlocks the file into a memory-only folder under /run, with the permissions you chose.
Hand it to the job onlyThe LoadCredential line in our form: the system copies the file to a private spot that only that one job can read.

With the last way, the program reads its secret from a file, not from a setting. That means the program itself must accept a file name. Many do; some do not, and then you wrap them in a small script that reads the file at start-up. A fair warning too: some people argue the encrypted-file tools are only as good as how carefully you share the keys, so treat that part as a choice, not a magic cure. The current option names of those tools change, so read their own pages.

What the computer learns while it runs

Our form asked for a StateDirectory. This is the folder, /var/lib/notes, where the program keeps its notes. It lives outside the store and outside every numbered generation from chapter 18. That has two consequences you should say out loud.

  • Building the page again makes the same programs, but not the same notes. The page makes the computer, not the data.
  • Going back one generation puts the old program back, and leaves today's data alone. If the new program changed the shape of the data, the old one may not understand it.

So the page should say, plainly, where each kind of data lives. A database is a good example: you tick a box such as services.postgresql.enable and the program and its settings are exactly reproducible. The rows are not. You also need a copy of them somewhere else, which means ticking a backup box, or writing a small job of your own, and pointing it at a different machine or disk.

A backup you never opened

Write the backup into the page, and then practice the other half: bring the copy back onto a fresh pretend computer and check the notes are there. Until you have done that once, you have a hope, not a backup.

What I did and did not run

I evaluated the form and the two-computer flake with a current Nixpkgs and Nix 2.34, and read the results back (names, door numbers, time zones, which computer has the job). I did not start the computers, so I have not watched the notes server answer a request or the credential arrive. The web server is a stand-in for a real program.

Try it yourself
  1. Save the three files above as notes.nix, common.nix and flake.nix in one folder, add the disk and start-up lines the shared form leaves out, and check both computers build: nix build .#nixosConfigurations.web.config.system.build.toplevel, and the same for box.
  2. Predict first, then check: if you change the shared time zone to "Europe/Paris", which computer changes?
  3. Give box the notes role on a different door number. How many lines did you add?
  4. Start web as a pretend computer (chapter 18). Put a secret file at the path the page names, and look at where the job sees its copy.
  5. Write one sentence for each computer: what data it keeps, where, and how it is backed up.

Share the rules. Keep the secrets and the memories out of the page.

Now ten computers cost you one shared page plus ten small ones, and you know exactly which parts a page can rebuild and which parts you must guard yourself. Next: what to do when something in all this will not build.
