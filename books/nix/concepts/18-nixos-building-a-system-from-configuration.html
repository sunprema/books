A Whole Computer Built From a Page of Words

Real name: "NixOS: Building a System from Configuration"

The computer nobody remembers

Here's the problem

A friend sets up a small computer to serve a web page. Over a year, they add a user here, open a door in the wall there, fix a file late at night. Then the computer breaks. Nobody, not even your friend, can say how it was put together. Building a second one just like it is a guess.

Last chapter we wrote down your home folder. This chapter writes down the whole computer: who may log in, which programs are there, which doors are open, which helpers run all day. All of it goes on one page, and the computer is built from the page.

The idea: the page is the computer

There is a computer system called "NixOS". Its trick is simple. The system is not set up by hand. It is built, the same way chapters 8 to 10 built a program, from a plan. The plan is the same kind of filled-in form you met in chapter 16. The boxes on this form are about the whole machine: its name, its users, its programs, its helpers.

The finished computer is one big thing in the store, and its address depends on every line of the page. Change one line, and you get a different big thing at a different address. The old one is still there, untouched. That one fact gives you almost everything good in this chapter.

The smallest page

Here is a page for a tiny computer. It has a name, one user, one extra tool, a remote-login helper, and one open door.

{ pkgs, ... }: {
  networking.hostName = "tiny";

  users.users.ada = {
    isNormalUser    = true;
    initialPassword = "ada";
    extraGroups     = [ "wheel" ];
  };

  environment.systemPackages = [ pkgs.ripgrep ];

  services.openssh.enable = true;
  networking.firewall.allowedTCPPorts = [ 22 ];

  system.stateVersion = "25.05";
}

Walk through it. hostName is the computer's name. The users box makes a person called ada; wheel lets her act as the boss of the machine. systemPackages is a list of tools for everybody. services.openssh.enable is the clever kind of switch: one line, and the helper program is installed, its settings file is written, and it is set to start when the computer starts. allowedTCPPorts opens one door in the wall. A real machine also needs lines about its disk and how it starts up; I left them out so the page stays small, but I checked that a page like this does build into a complete system.

The last line, stateVersion, confuses nearly everyone, and that is fair. It is not the version you run. It remembers which release's old habits your machine started with, so an update never quietly moves things under your data. Set it once. Do not raise it to "get the new version".

A plain password on a page

The password above is only for a toy machine. Whatever you write on the page ends up in the store, and anyone on the machine can read the store. Chapter 19 shows what to do about secrets.

Try it in a pretend computer first

You do not need to wipe your own computer to try this. There is a way to build the page into a pretend computer that runs inside a window on your real one, called a "virtual machine". If your own computer is not a NixOS one, the easy road is a Linux machine with Nix and the QEMU program on it. Save your page as vm.nix, and build a throwaway system around it. The usual command is nixos-rebuild build-vm, which builds a small script and leaves a link called result in your folder. Then you run:

./result/bin/run-tiny-vm

The name in the middle is your computer's name from the page. A window opens, the pretend computer starts, and you can log in as ada. Two things to know. The pretend disk is a file in your folder, named after the computer, so it keeps its own state between runs; delete that file to start fresh. And the pretend computer borrows your store read-only, so Nix commands that need to write to the store will not work inside it. For this chapter's tricks, that is fine.

What I did and did not run

I checked that a page like the one above turns into a complete system when Nix reads it (name, user, helper and open door all came out as written). I could not start a pretend computer where I wrote this, because it had no way to run one. So the exact window you see may differ from what I describe. If a command's name or flags have moved in your release, the manual for your release is the judge.

Changing the computer, and going back

Here's the problem

You change a line on the page. How does a computer that is already running become the new one, without being turned off and rebuilt?

On a real NixOS machine you use nixos-rebuild, and the word after it says how bold to be:

WordWhat happens
buildBuilds the new system. Changes nothing you can see.
testBuilds it and turns it on now, but the next restart goes back to the old one.
switchBuilds it, turns it on now, and makes it the one the computer starts with from now on.
bootBuilds it and makes it the start-up one, but does not turn it on until the next restart.

When you turn it on, called "activation", the computer points its everyday paths at the new system and starts, stops or restarts the helpers whose settings changed. Because the old system was never touched, there is little to go wrong halfway. Each switch also adds a numbered "generation" and a line in the start-up menu. If the new one is bad, you can ask for the one before:

sudo nixos-rebuild switch --rollback

Or you can restart and pick an older line from the menu, which works even when the new system will not start at all. That second road is the real safety net, so when you change something risky, such as the network, try test first: a restart puts you back.

One more surprise. Many files under /etc are now links into the store. If you edit one by hand, you cannot, or your edit vanishes at the next switch. Change the page, then switch. Lots of people find this annoying for a week and then find it a relief.

The part that belongs to this one box

Most of the page would be the same on any computer. A few facts are about this machine: which disk to use, which parts of the hardware need helper code, how it starts up. NixOS keeps those apart. A tool called nixos-generate-config looks at the machine and writes them into a file named hardware-configuration.nix. Your main page imports that file, using the imports list from chapter 16. Now the main page can be shared, and only that one small file is different on each box.

# configuration.nix
{ ... }: {
  imports = [ ./hardware-configuration.nix ];
  networking.hostName = "tiny";
  # ...the rest of the page...
}

Where the page lives

The page can sit in a flake (chapter 13), so the versions of everything are locked. The flake gives one named computer, and you build it with nixos-rebuild switch --flake .#tiny. The old style, with the page at /etc/nixos/configuration.nix and a channel, still works, but a flake gives you the same locked, shareable form you use for projects.

What a page cannot hold

Rolling back is not rolling back your data

A generation holds the system: programs, settings, helpers. It does not hold what the computer learned while running: a database's rows, uploaded files, the notes someone saved. Go back one generation, and the program may be older while the data is newer. Some programs cannot read data written by a newer version. So write down, in the page's comments at least, where the data lives and how it is backed up. The book's last project makes that explicit.

Two smaller costs. The first build can take a while and use a lot of room, since a whole computer is a lot of files; old generations stay until you clean them up (chapter 4's garbage collection). And the option names are many and change between releases, so you will spend real time reading the options list. That is the price of a machine you can rebuild from words.

Try it yourself
  1. Write the tiny page above in a file, and build and start a pretend computer from it. Log in as ada and check that rg is there.
  2. Predict first: if you add a second user to the page and build again, what will be the same, and what will be new?
  3. Add a line, such as another tool, and apply it. List the generations. How many are there now?
  4. Make a bad change on purpose, such as a mistyped option name. At which step does it fail, and does the running computer change?
  5. Go back one generation and check the tool is gone. Then make a file in the pretend computer's home folder, roll back again, and see whether the file is still there.

The computer is a thing you build, not a thing you tend.

Now a whole machine can be rebuilt from a page, tried safely in a pretend window, and undone with one command. Next: how to share parts of the page between many computers.
