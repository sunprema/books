From Paper to Thing: Every Step on the Way

Real name: "The Build Lifecycle"

Where did the time go?

You ask Nix for a thing, and a moment later a path comes back. Or an error does. Or nothing happens at all and Nix says it is done. In each case, what did Nix really do? If you cannot tell, then every error is a fog. Is the card wrong? Is the cooking wrong? Was anything cooked?

Last chapter we had a kitchen wall with cards on it. This chapter follows one card from the moment you write it to the moment a finished thing sits on the shelf. There are three steps. Each step has one job, and each step can fail in its own way.

Three steps, three jobs

Step one: work out the card. Nix reads your words and works out what the card says. This is called "evaluation": the computer reading your Nix words and finding the value they stand for. Nothing is cooked. No worker runs. A mistake here, like a missing name or a wrong kind of value, stops everything before any card exists.

Step two: pin the card to the shelf. When the value is a card, Nix writes it down in its stiff and exact form and puts it on the shared shelf as a .drv file. This is called "instantiation": making the card into a real file. Still nothing is cooked. But now the card has an address, and the address of the finished thing is already written on it.

Step three: cook. Nix looks at the card and asks one question: is there already a thing at the address on this card? If yes, it is done. If no, it runs the worker and checks that the worker left something there. This is called "realisation": turning the card into a real thing. Only this step makes a thing, and only this step needs the cooking tools.

Watch it happen

Here is the tiniest card, saved as a.nix. The worker writes one word into the file at $out.

derivation {
  name = "stamp";
  system = builtins.currentSystem;
  builder = "/bin/sh";
  args = [ "-c" "echo hi > $out" ];
}
$ nix-instantiate a.nix
/nix/store/4f5f…-stamp.drv
$ nix-store --realise /nix/store/4f5f…-stamp.drv
building '/nix/store/4f5f…-stamp.drv'...
/nix/store/a8ac…-stamp
$ nix-store --realise /nix/store/4f5f…-stamp.drv
/nix/store/a8ac…-stamp

The first line did steps one and two. The second did step three, and you can see it say building. Now look at the third command: the very same cook request. This time there is no building line. Nix looked at the shelf, found the thing already at the address on the card, and gave it back. The worker did not run again.

That is the great saving. Nix does not remember that you cooked it. It simply looks at the address, and the address is worked out from the card. Same card, same address, thing is there, done. Anyone with the same card gets the same answer, on this machine or any other.

Borrowing a finished thing

Step three has a second way to succeed. Before it cooks, Nix can ask a big shared shelf somewhere else, called a "binary cache", whether that address already has a thing on it. If so, Nix downloads it instead of cooking. The card is the same; only the way to get the thing changed. The default shared shelf is cache.nixos.org. Chapter 15 comes back to it.

Cards that need other cards

Last chapter a second card used the first card's result. Nix keeps that as a web of cards: this card needs those cards made first. In the stiff card, the list is called inputs, and you can print it with nix derivation show, or ask nix-store -q --references on the .drv.

When you ask Nix to cook one card, it walks the web from the far ends inward. Cards with nothing under them go first. A card waits until every card it needs has a thing on the shelf. Some of those may be already there, so Nix skips them. Two cards that do not need each other can be cooked at the same time. You never wrote the order down; it comes out of the web.

The empty room

Remember: the worker cooks in a nearly empty room. This room is called a "sandbox": a closed space where the worker can only touch what the card names. This is the part that makes the whole plan hold up. If the worker could reach out and grab any tool or file lying around on your computer, then the card would not tell the whole story. Two people with the same card could get different things, and neither could say why.

Here is what an unnamed tool looks like. This card asks the worker to use /bin/cat, which does exist on most computers:

derivation {
  name = "needs-cat";
  system = builtins.currentSystem;
  builder = "/bin/sh";
  args = [ "-c" "/bin/cat /etc/hostname > $out" ];
}
$ nix-store --realise $(nix-instantiate bad.nix)
building '/nix/store/n7z6…-needs-cat.drv'...
sh: /bin/cat: not found
error: Cannot build '/nix/store/n7z6…-needs-cat.drv'.
       Reason: builder failed with exit code 127.

Read this like a doctor. The words building tell you steps one and two worked: there is a card, and cooking began. not found tells you the worker looked for a tool in the empty room. Exit code 127 is the usual way a shell says "I could not find that program". The cure is not to open the room. The cure is to put the tool on the card, so that it is part of the story.

Lots of people find this part maddening at first. Something works on their machine, and Nix says it is not there. That is fair. But think about what it means: the failure is loud and early, on your desk. The other way is a quiet difference that shows up on someone else's computer next month.

One more trap

The room stops a missing tool from sneaking in, but it does not make your worker careful. A worker that says ls /usr/bin > $out; echo ok >> $out prints ls: not found, then keeps going, writes ok and finishes with no error. Nix sees a file at $out and calls it a success. The thing on the shelf is wrong, and nobody was told. Real workers stop at the first mistake. The helpers you meet next chapter do that for you.

Things that come from outside

So far a card was made only of words. But software has to come from somewhere: a file on a far-away server, a tar ball, a source tree. In an empty room with no door, how does it get in?

Nix makes one exception, and a strict one. A card may say up front: "the thing I make will have exactly this fingerprint". That kind of card is called a "fixed-output derivation". Because the fingerprint is written on the card, Nix may let this one worker open a door to the outside, since afterward it checks the fingerprint. If the bytes match, the thing goes on the shelf. If they do not, the build fails. This is how every download in Nix works.

derivation {
  name = "fixed-note";
  system = builtins.currentSystem;
  builder = "/bin/sh";
  args = [ "-c" "echo fixed > $out" ];
  outputHashMode = "flat";
  outputHash = "sha256-DDBxQY5jVuYUiYyE7QZMqV6IVRvAgRtTS98ZUuza5TQ=";
}

The two new slots say how to take the fingerprint (flat: of the one file) and what it must be. Our worker makes the file without any download, so you can see the checking part alone. Now put a wrong fingerprint in, all zeros, and cook:

error: hash mismatch in fixed-output derivation '/nix/store/0n0f…-fixed-note.drv':
         specified: sha256-AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=
            got:    sha256-DDBxQY5jVuYUiYyE7QZMqV6IVRvAgRtTS98ZUuza5TQ=

This is not a bad day, it is the normal way to learn the right fingerprint. Put in a fake one, cook, and copy the got line back in. But stop and think before you do: you are telling Nix to trust whatever came down. Look at what was fetched first.

Where it can still go wrong

Nix promises that the same card gives the same address. It does not promise the same bytes. If a worker writes the time of day into its file, or uses a random number, then two cooks of the same card give two different things, and only one of them ever sits at that address. Because Nix reuses what is on the shelf, you may not notice for a long time. The other tricks that spoil it: a worker that reads the clock, a worker that lists files in an order that changes, a fixed-output card whose far-away file was swapped for a different one with the same name (the fingerprint check is what catches this), and a tool outside the room, if you turn the sandbox off. You can test a card: nix-store --realise --check cooks it again and compares with what is on the shelf.

Work it out, pin it, cook it. Each step has one job.

Try it yourself
  1. Save a.nix. Run nix-instantiate a.nix. Is there a thing for it on the shelf yet? Check by running nix-store --realise --dry-run on the .drv, then cook it for real.
  2. Cook the same .drv a second time. Which line from the first run is missing, and why?
  3. Write the needs-cat card. Before you run it, say which step will fail. Run it and read the exit code.
  4. Fix it by changing the script so it does not use the outside tool, for example read x < /dev/null; echo hi > $out. Does the .drv path change? Does the old failed attempt leave anything on the shelf?
  5. Write the fixed-output card with a zero fingerprint. Copy the got hash in. Which of the three steps told you the right hash?

What this does not cover: how people avoid writing workers by hand, and how a build like a real C program fits in. That is the next chapter. For now, you can name the three steps and the job of each.

When something goes wrong, you no longer ask "why did Nix fail?" You ask "which of the three steps?", and that cuts the search in a third.

Sources: every command above was run with Nix 2.34.6 on x86_64-linux (recorded in research.json as src-local-nix-2.34-lifecycle); store paths and message wording differ between versions and machines.
