Letting a Machine Check Your Work, Again and Again

Real name: "Testing, CI, and Binary Caches"

Your friend's laptop does all the cooking

Here's the problem

You and three friends run a small bakery. Every morning, each of you bakes the same loaf from the same card. Three of you spend an hour on it. One friend has a tiny oven and spends four. And on Tuesday somebody sells a loaf nobody tasted first.

Your team has the same two troubles. First, who checks the work? If checking lives in one person's head, it gets skipped on a busy day. Second, who pays the waiting? Chapter 14 showed a program that takes minutes to build. Four people building it, and a robot building it on every change, adds up fast. Yet the answer was already made once, and Nix knows that exact answer by its fingerprint (chapter 4).

The fix: a taste test, a robot, and a shelf of finished loaves

Three plain ideas. One: write the taste test down as part of the project, so it can run anywhere. Two: let a robot helper run that same test on every change. This is called "CI": a computer that checks every change for you, the same way each time. Three: put finished loaves on a shelf that everyone can reach. This shelf is called a "binary cache": a place that keeps finished build results, so nobody bakes what somebody already baked.

The taste test is just another thing Nix builds

In chapter 13 a "flake" had a place called checks. Here is the surprise: a check is a build like any other. If it builds, it passes. If its builder stops with an error, it fails. There is no special test machine inside Nix. I made a tiny flake with one program and one check. The check reads what the program made and says no if it is wrong. (It uses the raw derivation from chapter 8, so you can see every part, and it needs no outside downloads.)

{
  outputs = { self }:
    let
      system = "x86_64-linux";
      mk = name: script: builtins.derivation {
        inherit name system;
        builder = "/bin/sh";
        args = [ "-c" script ];
      };
    in {
      packages.${system}.default = mk "greet" ''echo "hello" > $out'';
      checks.${system}.default = mk "greet-test" ''
        read line < ${self.packages.${system}.default}
        [ "$line" = "hello" ] || exit 1
        echo ok > $out
      '';
    };
}

Walk through it. mk is a small helper that makes a build from a name and a few lines of shell. The packages output makes a file holding the word hello. The checks output reads that same file. If the word is not hello, the shell says exit 1, which means "no". If it is right, the check writes ok to its result so there is something to keep. Because the check names the package inside it, Nix knows the package must be built first.

I ran nix flake check on Nix 2.34.6. It built both things and ended with all checks passed! Then I changed the expected word to bye and ran it again. It stopped with failed to build attribute 'checks.x86_64-linux.default' and builder failed with exit code 1. A failed taste test looks exactly like a failed build, because it is one. Run it a second time without changing anything and it answers at once: the result is already in the store, so Nix does not bake the same test twice.

A small surprise

I first wrote system = builtins.currentSystem and Nix said attribute 'currentSystem' missing. Flakes are not allowed to peek at the machine they run on, because that would make the answer depend on the machine (chapter 13). So you write the system out, once per kind of computer you support.

Give the robot the same card

The best part: the robot needs no special test script. Whatever you ran on your laptop, the robot runs. Here is the card for GitHub's robot, which is the most common one. It is the pattern from the README of install-nix-action; I did not run it here, since I have no GitHub, so check the newest version number before you copy it.

name: ci
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: cachix/install-nix-action@v31
        with:
          github_access_token: ${{ secrets.GITHUB_TOKEN }}
      - run: nix flake check -L

Line by line. The robot starts on a clean computer. checkout brings your files. The next step puts Nix on that computer. The token only helps the robot fetch things from GitHub without being told "too many questions." The last line is the one that matters: the same nix flake check you ran by hand, with -L to show the build logs when something fails. Nothing here knows about your language or tools. They all live in the flake, which is the point.

One trap: nix flake check only runs what you put in checks. If the robot only runs nix build, it builds the program and never tastes it. Another: in a git folder, Nix cannot see files that git does not know about (chapter 13). A file you forgot to git add may work on your laptop and be missing on the robot.

The shelf of finished loaves

Without a shelf, the robot starts with an empty kitchen on every run and bakes everything. With one, it asks first. You already use one: Nix comes set up to ask cache.nixos.org, the big public shelf for the official collection. I looked at a fresh install and the setting was substituters = https://cache.nixos.org/. "Substitute" is Nix's word for "take the finished loaf instead of baking it."

Why is it safe to eat a loaf somebody else baked? Because of the fingerprint in the name (chapter 4) and a signature. Each loaf on the shelf has a note, and the note carries a signature made with a secret key that only the shelf's owner holds. Your Nix keeps a list of public keys it trusts, trusted-public-keys. It takes a loaf only if the signature matches a key on that list. The setting require-sigs is on by default.

Make your own small shelf

You can try the whole idea on one computer, using a plain folder as the shelf. First make a key pair, then copy the program onto the shelf, signing it:

nix key generate-secret --key-name demo-1 > sec
nix key convert-secret-to-public < sec > pub
nix copy --to "file:///tmp/cache?secret-key=$PWD/sec" \
    $(nix build --no-link --print-out-paths)


The first line makes a secret key, the second turns it into a public one you can hand out. The third copies the finished program to the folder and signs it. In the folder I found a file nix-cache-info, a folder nar with the packed program, and one small note named after the program's fingerprint, ending in .narinfo. The note lists the path, its size, what it needs, and a Sig: line. That is the whole shelf: files in a folder. A web server in front of such a folder is a real cache.


Next I deleted the program from my own store with nix store delete, so my kitchen was empty again, and asked for it back, pointing at the shelf. Without the public key, Nix said ignoring substitute ... as it's not signed by any of the keys in 'trusted-public-keys' and baked the program itself. Then I added my public key, deleted again, and built once more. This time: copying path ... from 'file:///tmp/cache'. No baking.


nix build \
  --option substituters file:///tmp/cache \
  --option trusted-public-keys "$(cat pub) cache.nixos.org-1:6NCHdD59X431o0gWypbMrAURkbJ16ZPMQFGspcDShjY="


Easy to get wrong

The second setting replaces the old list; it does not add to it. That is why the line above repeats the cache.nixos.org key. Leave it out, and Nix stops trusting the big public shelf. Also: the public key is safe to share. The secret key is not. Keep it in your robot's secret settings, never in git.



Real shelves for a real team


A folder on one laptop helps nobody else. Teams use a hosted shelf. The common one is "Cachix", a service that keeps a shelf for you, gives you a public key, and has a ready-made step for GitHub's robot that pushes everything the robot bakes. You can also run your own over a web server or object storage. The shape is always the same: the robot, which holds the secret key, pushes signed results; the laptops, which hold only the public key, pull them. The install action lets you add a shelf's address and key through its extra_nix_config input, and Cachix has its own action for this.


A word about trust. Nix will not let any user add shelves as they please. The setting trusted-users (by default only root, which I saw on my install) lists who may. Putting a person there is close to giving them the keys to the whole kitchen, so do it for people, not for everybody. Normal people add shelves in the system's config, once, with a key.



When your oven is the wrong kind


Remember the system names from chapter 13. A check for aarch64-linux is fine to read on an x86 laptop, but it cannot be baked there: the build says the system it requires is not the current one. Two ways out. One: have the robot run on each kind of machine (a "matrix": one job per system). Two: use "remote builders", other machines Nix can send a build to over SSH. Nix reads the builders setting (mine pointed at /etc/nix/machines) and sends each job to a machine that can bake it. The results come back signed, so the builder's key must be on your trusted list, or the copy is refused. One forum report of exactly this ended in "copying fails" until the key was added.



What it costs


Lots of people find this part annoying, and that is fair: the shelf is another thing to run. Real costs:




ThingWhat you payWhat you get


Robot checksMinutes on every change, and a billNo loaf goes out untasted


Binary cacheDisk space that only grows; a key to guardFast builds for everyone


Remote buildersMachines, SSH, keys to keep workingBuilds for kinds of computers you do not own at your desk


Trusting shelvesA bad key means bad loavesSkipping hours of baking safely




So decide how long to keep old loaves, who holds the secret key, and what happens when the key leaks (you make a new one and tell every laptop). Small teams can start with just the robot and the free public shelf. Add your own shelf when waiting hurts. And remember what this does not catch: a check only tests what you wrote. Tests that need the internet or a real database do not run inside the closed room (chapter 9), so they need their own place, which chapter 21 shows.

What this does not do

A cache makes builds faster, not more correct. If your build is not repeatable (chapter 9), a shelf will happily serve the one loaf that happened to get baked. Action version numbers and Cachix plans change often; check their pages when you set them up.



Write the taste test once. Let the robot run it. Share the loaves.



Now every change gets the same careful check, and nobody on your team bakes the same loaf twice.
