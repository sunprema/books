Making Real Programs With the Shared Recipe Box

Real name: "Packaging Software with Nixpkgs"

Writing the worker by hand is a chore

Last chapter you wrote cards where you also wrote the worker: a little shell script, and a list of every tool it could touch. For a one-line card that is fine. For a real program it is not. A real program needs a compiler, a make tool, a place to unpack files, a way to copy results into the right folder, and a long list of small clean-up jobs. Writing all that for every program would be tiresome, and everyone would get it a little different.

The answer is a shared recipe box. Nix people keep one huge box of ready-made recipes, called "Nixpkgs": a big public collection of cards, plus the helpers used to write them. The most used helper is stdenv.mkDerivation. You give it a short card with only the parts that are special about your program, and it fills in the worker for you.

What the helper gives you

When you use stdenv.mkDerivation, you stop writing builder and system. The helper sets a standard worker, and that worker already has a standard toolbox in its room: a C compiler, GNU make, bash, the patch tool, and more. You write what is yours: the name, the version, where the source is, and what the program needs.

The standard worker does its job in short, named steps. Each step is called a "phase": one stage of the cooking, with its own name. You can see them go by in the build log:

Why split the work this way? So you can change one step and leave the rest alone. Need to edit the source before it is made? That is the patch step. Need to copy one extra file after install? Add a few lines to the end of the install step. You almost never replace a whole phase; you add small bits with hooks such as postInstall.

The smallest real package

Here is a tiny C program, src/hello.c, with a src/Makefile next to it. Look closely at the Makefile: it installs to /usr/local unless told otherwise.

#include <stdio.h>
int main(void) {
    printf("hello from nix\n");
    return 0;
}
PREFIX ?= /usr/local
hello: hello.c
	$(CC) -o hello hello.c
install: hello
	mkdir -p $(DESTDIR)$(PREFIX)/bin
	install -m755 hello $(DESTDIR)$(PREFIX)/bin/hello

And the card, saved as default.nix next to src/:

{ pkgs ? import <nixpkgs> {} }:
pkgs.stdenv.mkDerivation {
  pname = "hello-c";
  version = "0.1";
  src = ./src;
  makeFlags = [ "PREFIX=$(out)" ];
}

Walk through it line by line. The first line is a function that takes the recipe box (pkgs) and, if you give nothing, loads the box found on your machine. pname and version make the name. src is the source: here a folder next to the card. And makeFlags hands one setting to make, saying: install under $out, the one folder this card may fill, not under /usr/local. Without that line, the install step would try to write outside the shelf, and the shelf is read-only.

$ nix-build
Running phase: unpackPhase
unpacking source archive /nix/store/hr2v…-src
source root is src
Running phase: patchPhase
Running phase: configurePhase
no configure script, doing nothing
Running phase: buildPhase
gcc -o hello hello.c
Running phase: installPhase
install -m755 hello /nix/store/h5b9…-hello-c-0.1/bin/hello
Running phase: fixupPhase
/nix/store/h5b9…-hello-c-0.1
$ ./result/bin/hello
hello from nix

Every phase from the picture shows up. The configure step found no configure script and did nothing, which is fine. The build step ran gcc and the install step ran your Makefile's install rule. Where did gcc come from? You never named it. That is the standard toolbox at work.

Changing the source with a patch

Say you want the program to say something different, but the source belongs to somebody else. You do not edit their files. You write a small file that lists the change, called a "patch": a note that says "in this file, take out this line and put in that line". Here is one, saved as fix-greeting.patch:

--- a/hello.c
+++ b/hello.c
@@ -1,5 +1,5 @@
 #include <stdio.h>
 int main(void) {
-    printf("hello from nix\n");
+    printf("hello from a patched nix\n");
     return 0;
 }

Add one line to the card, patches = [ ./fix-greeting.patch ];. In the log, the patch step now has work to do:

Running phase: patchPhase
applying patch /nix/store/7ck8…-fix-greeting.patch
patching file hello.c

Two things to notice. The patch file itself was copied onto the shelf, so it is part of the card's story. And the thing you get now lives at a different address (xxvl… instead of h5b9…). A patch is an ingredient like any other; change it and the address changes. By default patches are applied with -p1, which means the a/ and b/ at the front of the file names are dropped. If your patch was made without them, the step will complain, and you set patchFlags.

Tools to cook with, and parts that stay inside

Now a program that needs something from outside the standard toolbox. This one prints the version of a compression library, zlib. Its C file says #include <zlib.h>, and its Makefile asks a helper tool called pkg-config where the library lives. Try it with the plain card:

$ nix-build
gcc -o z z.c $(pkg-config --cflags --libs zlib)
bash: line 1: pkg-config: command not found
z.c:2:10: fatal error: zlib.h: No such file or directory
compilation terminated.
make: *** [Makefile:3: z] Error 1
error: Cannot build '/nix/store/7v8b…-zver-0.1.drv'.
       Reason: builder failed with exit code 2.

Read it from the top, like a doctor. Nix says the build failed, but the true cause is a few lines above. Two different things are missing. One is a tool the worker runs while cooking: pkg-config. The other is a part the program is made out of: the zlib files. Nixpkgs gives each kind its own list, and this is the most important idea of the chapter.

The names are long, so here is the plain reading. nativeBuildInputs is for things that must be on the worker's path while it cooks: pkg-config, cmake, and helpers that fix up the result. buildInputs is for things that end up linked into or used by the finished program: libraries such as zlib. The Nixpkgs manual says these two tests are independent, so a thing can need to be in both. Fix one list at a time and watch the error change:

  nativeBuildInputs = [ pkgs.pkg-config ];

With only that line added, the pkg-config: command not found message goes away, but zlib.h: No such file or directory stays, because the tool is there but the library is not. Add the second list:

pkgs.stdenv.mkDerivation {
  pname = "zver"; version = "0.1"; src = ./.;
  nativeBuildInputs = [ pkgs.pkg-config ];
  buildInputs = [ pkgs.zlib ];
  makeFlags = [ "PREFIX=$(out)" ];
}
$ nix-build && ./result/bin/z
zlib 1.3.2

This is the whole method for fixing a missing dependency: read the first real error, decide if it is a missing tool or a missing part, add it to the matching list, and run again. You will meet several errors in a row. That is normal; one fix often uncovers the next. And the reason you hit them at all is the empty room from last chapter: nothing is quietly borrowed from your machine.

Why two lists at all?

Today most people build on the same kind of machine they run on, so the two lists feel like the same thing. They differ when you cook for another kind of machine, say building on a laptop for a small board. Then the tools must run on the laptop, while the parts must fit the board. Nixpkgs keeps the lists apart so that this keeps working.

Getting the source from far away

So far the source sat in a folder next to the card. Most real programs live on a web server. You already know the rule from chapter 9: a worker with the door open must say up front what fingerprint the download will have. Nixpkgs wraps that in helpers called fetchers. The simplest is fetchurl:

src = pkgs.fetchurl {
  url = "https://example.org/hello-1.0.tar.gz";
  hash = pkgs.lib.fakeHash;   # a placeholder, replaced after the first try
};

The manual's recipe for finding the real fingerprint is the one you learned before: put in a fake hash (lib.fakeHash or an empty string; not a number you invented), run the build, and copy the got line from the error into the card. Then go look at what you downloaded before you trust it, because you just told Nix to accept whatever came. When the source is a tar ball, the unpack step opens it for you and finds the folder inside.

A label on the box

A package without a label is hard to live with. Nixpkgs has a place for the label, called meta. It does not change how the thing is built, so it does not change the address; it tells people and tools what the thing is.

  meta = {
    description = "A tiny C greeter";
    license = pkgs.lib.licenses.mit;
    platforms = pkgs.lib.platforms.unix;
    mainProgram = "hello";
  };

Here description and license say what and under which terms, platforms says where it is known to work, and mainProgram names the file that nix run should start. You can read a label without building anything, because it is just a value to evaluate:

$ nix-instantiate --eval -E '(import ./default.nix {}).meta.description'
"A tiny C greeter"

Looking at what you made

Do not just trust it; look. The output is a folder with one file in it:

$ ls -R result
result:
bin
result/bin:
hello
$ nix-store -q --references result
/nix/store/h4wf…-glibc-2.44-25

The only thing the finished program points to is the C library it runs on. The compiler is not in the list, because it was only a tool for cooking. The files are read-only, and their dates say 1970; the shelf is built to keep things exactly as they were made. The last phase, "fixup", did the tidying: it trimmed the places the program searches for libraries, removed extra symbols from the file, and fixed paths at the top of any scripts.

You can also look at the card Nix made from yours. nix derivation show $(nix-instantiate default.nix) prints it. Your lists are in there as plain settings: patches, buildInputs, nativeBuildInputs, makeFlags, together with the standard worker the helper chose. Nothing is hidden; it is the same kind of card as chapter 8, only filled in for you.

What this does not do

The helper does not know what your program secretly needs. A program that loads a plug-in at run time, or runs git from a script, will build fine and fail later, because nothing told the card. It also cannot make a bad build system good: a Makefile that insists on installing to /usr/local must still be told where to go. And a src = ./. that points at a whole project folder takes in every stray file with it.

A tool you run is not a part you link. Give each its own list.

Try it yourself
  1. Make src/hello.c and src/Makefile and the first card. Build it. Which phase printed gcc? Which one made the folder in $out?
  2. Remove the makeFlags line and build again. Predict the failure first, then read it. Why does installing outside $out fail?
  3. Write the patch, add it, and rebuild. Run the program. Is the new path different from the old one? Does the old one still exist on the shelf?
  4. Change the patch so it will not apply (alter a context line). Which phase fails, and what does it say?
  5. Build the zlib example with no lists, then only pkg-config, then both. Before each run, write down which error you expect.
  6. Add meta, read meta.mainProgram without building, and run nix derivation show. Find your patches and buildInputs in the output.

What this does not cover: changing someone else's card in the box, or building the same program two ways. That is the next chapter. For now, you can take a small program from a folder to a thing on the shelf with a card of ten lines.

You no longer write the worker; you write only what is special about your program, and the shared box covers the rest.
