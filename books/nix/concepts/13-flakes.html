The Box With a Label on Every Side

Real name: "Flakes: A Standard Interface for Nix Projects"

Every project hands you a different box

You have written a recipe card for your program (chapter 10). You have a work room for your team (chapter 12). Now a friend asks: "How do I build it? Where is the room? How do I run the tests?" You say: "Open default.nix, no wait, shell.nix, and the tests are in a third file, and you need the same box of recipes I have."

Every project keeps its things in a different place, and nobody wrote down which day's box of recipes was used. It is like handing someone a box with no labels on it, and a note that says "ask me".

One file, with the same labels every time

The fix is a box where every side has a label, and the labels are the same in every project. In Nix this box is called a "flake". It is a folder with one file in it, flake.nix. The file has up to three parts: a short description, a list of inputs (the other boxes you need), and outputs (what you hand out to the world). The outputs part is a function: boxes you need go in, labeled things come out. Nothing new to learn about the language. It is the same kind of file you already know, with a set shape.

{
  description = "tiny flake, no inputs";
  outputs = { self }: {
    packages.x86_64-linux.default = derivation {
      name = "hi"; system = "x86_64-linux"; builder = "/bin/sh";
      args = [ "-c" "echo hi > $out" ];
    };
    checks.x86_64-linux.default = self.packages.x86_64-linux.default;
  };
}

Walk through it. outputs takes one thing, self, which means "this very box". It hands back a set of labels. packages is the label for "things you can build". Under it comes the kind of machine, then the name; default is the name used when you do not pick one. checks is the label for "things that must pass". Here a check just says "building the package must work", and it points at the package by saying self.packages…. The package is made with derivation from chapter 8, with no extra helpers, so nothing is hidden.

I ran this on Nix 2.34.6. nix build .#default printed a path in the store and left a result link. The .#default means "in the box in this folder, the output called default".

Reading the labels without a map

Because the labels are the same everywhere, you can ask any flake what it holds. nix flake show draws the tree. For my tiny box it printed checks and packages with x86_64-linux under each. A custom label it did not know, which I made up to test, was shown as unknown, and nix flake check warned unknown flake output. So the labels are a promise: stick to the known ones and every tool understands your box.

The well-known labels are four. packages is what nix build makes. devShells is the room you step into with nix develop (this is chapter 12's mkShell, unchanged). checks is what nix flake check builds. apps is what nix run starts, each written as { type = "app"; program = "…"; }. When you name nothing, the commands pick default.

A very common surprise

If your folder is a git repository, Nix only sees files git knows about. With a new flake.nix I got Path 'flake.nix' in the repository … is not tracked by Git, and a hint to run git add. After git add (no commit needed) it worked, with a warning that the tree was "dirty". Lots of people find this odd, and it is a little annoying. It is there so that the box is made only of files that you meant to share.

Every kind of machine gets its own shelf

Why does the label have x86_64-linux in the middle? Because a thing built for one kind of machine cannot run on another. So each label has one shelf per machine kind. A box meant for a Linux laptop and a Mac needs shelves for each, and people write a small helper to fill them all:

let
  systems = [ "x86_64-linux" "aarch64-linux" "aarch64-darwin" ];
  forAll = f: builtins.listToAttrs
    (map (s: { name = s; value = f s; }) systems);
in {
  packages = forAll (system: { default = /* … */; });
  checks   = forAll (system: { runs    = /* … */; });
}

Line by line: the first line lists the machine kinds. forAll takes a recipe that wants a machine kind, and runs it once for each, making one shelf per kind. Then each label is filled by calling forAll. When I did this, nix flake show --all-systems listed all three shelves; plain nix flake show only lists yours. When I asked for the aarch64-linux package from my x86 machine, looking at it worked but building it failed: platform mismatch, required system aarch64-linux, current system x86_64-linux. A shelf can exist without being usable from where you stand.

Asking for a label that is not there tells you where Nix looked: does not provide attribute 'packages.x86_64-linux.nope', 'legacyPackages.x86_64-linux.nope' or 'nope'. Read it as a map of the places it tried.

The label that fixes the day

Chapter 12 left a gap: <nixpkgs> meant "whatever box of recipes this machine has", so your room and your friend's room could differ. Flakes close the gap. Each input is named by an address, and the first time you use the box, Nix writes down the exact day that address pointed to, in a file called flake.lock.

{
  inputs.dep.url = "git+file:///path/to/dep";
  outputs = { self, dep }: { n = dep.lib.n; };
}

Here dep is another box on my disk, and my box asks for its lib.n. The first nix eval .#n printed Added input 'dep' and created flake.lock. The file is plain JSON and, for each input, holds the address, the exact commit (rev) and a fingerprint of the contents (narHash).

Now the part that matters. I made a new commit in dep, changing n from 1 to 2. My box still said 1. The lock held it on the old day. Only when I ran nix flake update did Nix print Updated input 'dep' with the old commit and the new one, and then the answer was 2. Updating is something you choose to do, and the change shows up as a plain edit to one file that you can look at and commit.

The rule

Commit flake.lock along with flake.nix. The lock file is what makes your friend's room the same as yours.

The real thing you will want is nixpkgs as an input. I could not reach it from where I built this chapter (the network said no), so the next box was not run here. It is the usual shape:

{
  description = "Our service";
  inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-unstable";
  outputs = { self, nixpkgs }:
    let
      system = "x86_64-linux";
      pkgs = nixpkgs.legacyPackages.${system};
    in {
      packages.${system}.default = pkgs.hello;
      devShells.${system}.default = pkgs.mkShell {
        packages = [ pkgs.hello pkgs.jq ];
      };
      checks.${system}.default = pkgs.runCommand "hello-runs" {} ''
        ${pkgs.hello}/bin/hello > $out
      '';
    };
}

The input is the shared recipe box; the lock will pin its day. legacyPackages.${system} is where that box keeps its things for each machine kind (the odd name is history). The package is just a recipe from the box. The room is the mkShell from last chapter, now with a label. The check builds a tiny thing that runs the program, and if it fails, nix flake check fails.

Under the hood: is it still the same Nix?

Yes, and this is worth holding on to. A flake does not change how things are built. Your packages are still derivations (chapter 8), still built the same way (chapter 9), still put in the store (chapter 4). What a flake adds is a fixed shape for the file and a lock for the inputs. It also makes evaluation closed: the outputs depend only on the box's own files and its locked inputs, not on a path on your machine or on your settings. If something confusing happens, you can drop down to a plain expression and look at it.

Try it yourself
  1. Take the room from chapter 12 and make a folder with flake.nix that exposes it as devShells.<system>.default. Run git init and git add flake.nix.
  2. Add your chapter 10 recipe as packages.<system>.default and a checks entry that builds it or runs it.
  3. Predict, then run: what does nix flake show print? What does nix flake check do when you break the check on purpose?
  4. Look at flake.lock. Which revision does it hold for nixpkgs? Commit it.
  5. Predict: if the shared recipe box gets a new day tomorrow, will your build change? Then run nix flake update and read the lines it prints.
  6. Ask for an output that does not exist. Which places does the error say it looked in?
What this does not do

A flake does not make things safe or secret: files in the box are copied into the store like any source. It does not remove the need for per-machine shelves. A lock holds the box still, but it cannot stop an old box from having old bugs. And flakes are still marked as an experimental feature: you turn them on with experimental-features = nix-command flakes in your settings, and details may change.

Same labels on every box, and a lock that fixes the day.

Now anyone can pick up your project, ask "what is in here?", and build, step into, or check it with one command.

Sources: the flake, lock, update, show, check, per-system and error-message results were run on Nix 2.34.6 (src-local-flakes-nix-2.34). The nixpkgs-based example follows the standard pattern (src-nix-flake-cmd, src-devto-flakes-direnv) and was not run.
