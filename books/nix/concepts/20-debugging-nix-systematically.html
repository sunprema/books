Finding What Went Wrong, Step by Step

Real name: "Debugging Nix Systematically"

Five red lights and one guess

Here's the problem

Your friend runs one command and a wall of red words comes back. They do what most of us do: change a line, run it again, change another line, run it again. After an hour the page is full of half-fixes, and the red words are different, but nobody can say if that is better.

Look at it from the side of a person who fixes bikes. They do not start by swapping parts. First they ask one question: is the problem in the chain, the tyre or the brakes? Only then do they pick up a tool. This chapter gives you that first question for Nix, plus a short list of tools for each answer.

The fix: ask "which step broke?"

Every Nix job walks through the same steps you met in chapters 7 to 9. A failure belongs to exactly one of them, and each step has its own look and its own cure.

The cheap test is to look for the line that says building '...drv'.... If it never appeared, Nix never ran any builder, so the trouble is in reading, working out, or fetching. If it appeared, the trouble is in the builder, or later.

Steps 1 and 2: the page itself

I ran every example in this chapter on Nix 2.34.6 and copied the words it gave. Start with step 1, "syntax", which just means "could Nix even read the page?" Here a semicolon is missing:

{ a = 1 b = 2; }

error: syntax error, unexpected '=', expecting ';'
       at «string»:1:11:
            1| { a = 1 b = 2; }
             |           ^

It gives a line, a column and a little arrow. The arrow often points a bit after the real mistake, because Nix only noticed when it got confused. Look at the thing just before the arrow. An unclosed list gives unexpected end of file at the very end, which means "something above was never closed."

Step 2 is "evaluation": Nix works out the page's answer. No program has run yet. These errors say what is wrong in plain words:

You wroteNix said
{ name = "x"; }.nmeattribute 'nme' missing … Did you mean name?
x + y with no yundefined variable 'y'
"a" + 1cannot coerce an integer to a string: 1
a function wanting { a, b } given only acalled without required argument 'b'
a function wanting { a } given a and ccalled with unexpected argument 'c'
rec { a = b + 1; b = a + 1; }.ainfinite recursion encountered
assert 1 == 2; 3…the condition of the assertion '(1 == 2)'

Reading the long trace

Bigger pages give a long error with lines that start with …. Think of them as a trail of footprints. Each line says "while I was doing this, I was asked to do that." The footprints lead inwards. The real reason is the error: line at the very bottom. So read the bottom line first to learn what went wrong, then climb the footprints to learn how you got there. If Nix has hidden part of the trail, add --show-trace and run it again to see all of it.

Laziness moves the red light

From chapter 7: Nix only works out what is asked for. A bad value in a set can sit there quietly until something reads it. So the line that fails may be far from the line that made the mistake. The footprints are how you walk back.

Step 3: fetching

Some pages ask for things from outside: a web address, a code repository. If that fails, the error names the fetching tool and says it could not reach the place. It also retries several times first, with longer and longer waits, which looks like a hang. Here Nix tried five times and then said:

error: … while calling the 'fetchurl' builtin
       error: unable to download 'http://localhost:1/x':
       Could not connect to server (7) …

For this step ask the plain questions. Is the network up? Is the address right? Do you need a proxy? Did the place move? Nothing in your Nix code is wrong, usually. The one fetch surprise worth knowing is a wrong stamp. A download pinned with a "hash" (a short fingerprint of the content) fails if the content differs:

error: hash mismatch in fixed-output derivation '…fixed-note.drv':
         specified: sha256-AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=
            got:    sha256-DDBxQY5jVuYUiYyE7QZMqV6IVRvAgRtTS98ZUuza5TQ=

This is also how you learn a hash: put a fake one, run, and copy the got line. But stop and ask before you copy. Is this the file you meant? If a file you trusted last week now has a different fingerprint, that is a question about the file, not about Nix.

Step 4: the builder complained

Now the "building" line has appeared, and the words that follow come from the little program doing the work, not from Nix. Here is one on purpose:

building '/nix/store/…-oops.drv'...
sh: /bin/cat: not found
error: Cannot build '/nix/store/…-oops.drv'.
       Reason: builder failed with exit code 127.
       Output paths:
         /nix/store/…-oops

Read it in three bites. The line with sh: is the builder talking: it wanted a tool and the room had none. The Reason line carries a number. 127 means "command not found", which is the classic sign of a tool the page forgot to list (chapter 9's locked room). Most other numbers just pass on whatever the failing program said, so the log must explain them. The Output paths are only where the result would have gone. Nothing is there.

Three tools help here:

  • nix log <drv> shows the saved log of a build, even after the screen has scrolled away.
  • nix-build -K keeps the failed work folder and prints keeping build directory …, so you can walk in and look at what the builder saw.
  • nix derivation show <drv> prints the builder, its arguments and its environment, so you see exactly what it was given instead of what you remember giving it.
The quiet failure

A builder that does not stop on the first bad command can finish happily with a wrong result, as chapter 9 showed. If the build "worked" but the output is empty or odd, the log is still where to look. Real package helpers stop on the first error; hand-written scripts need set -e.

Step 5: switching on

For a whole computer (chapters 18 and 19) there is a last step. The new system built fine, but turning it on can still fail: a service will not start, or a file it wants is missing. That is not a Nix evaluation error and not a build error. It is the ordinary world of the computer. So ask the ordinary questions with the ordinary tools: look at the service's status and its log (for a systemd service, systemctl status and journalctl -u), check that a secret file really exists at the path the page names, check that a door number is not already used. And remember rollback from chapter 18: the old generation is still there, so you can go back first and investigate after. I did not boot a computer for this chapter, so these commands come from the earlier chapters, not from a run here.

Make the problem small

When the cause is not clear, cut. Copy the failing part into its own small file, or into nix repl, and remove things until the red words stop. The last thing you removed is the suspect. A few handy moves:

  • :t name in the repl tells you what kind of thing a value is. Many errors are "I thought this was a list."
  • builtins.trace "here" value prints trace: here on the way past and gives back the value untouched. It only prints if that spot is really reached, which is itself useful information.
  • --strict forces everything inside the answer, so a hidden bad value shows itself.
  • builtins.tryEval asks "does this work?" without crashing.

Take out the traces when you are done. They are scaffolding, not part of the house.

"Why did I get that package?"

Sometimes nothing fails; the wrong thing just shows up: an old version, or a package with a surprise change. Two questions settle most of these.

Where did the package come from? Ask Nix to point at the file. This printed the exact file and line for hello:

nix eval nixpkgs#hello.meta.position
"/nix/store/…-source/pkgs/by-name/he/hello/package.nix:58"

If someone changed the package with an override (chapter 11), builtins.unsafeGetAttrPos "name" pkg points at where the attribute was last set, which for my test pointed into Nixpkgs' general build helper, not hello's own file. That tells you a change happened there.

Which Nixpkgs is this? Two ways of asking can reach two different copies. import <nixpkgs> {} uses whatever your search path says; nixpkgs#hello uses the flake registry; a project's flake uses the revision in its lock file. When I looked, the first two gave version strings that were not the same. So print the version (pkgs.lib.version) and the store path of the copy you are really using, before you decide the package is wrong.

A mistyped name also fails differently in each place: through a flake you get a long list of places it looked, plus a Did you mean; through import you get a short attribute 'nosuchpkg' missing.

Is it too clever?

A last habit. When a page needs three overlays, two overrides and a function that builds functions just to change one setting, stop. Ask whether the thing already has an option for it, whether one pinned input would do, or whether the plain version is shorter. Each layer you add is one more place for a footprint trail to wander through. Layers are sometimes worth it, as chapter 11 said, but the debugging cost is real, and the layer you can delete is the one you do not have to debug.

Why it is worth it

Yes, Nix errors can feel like a flood, and the longest ones have a reputation for good reason. Reading them from the bottom, one step at a time, takes some patience at first. But the method does not change from one problem to the next: find the step, read the bottom line, climb the trail, cut it small. Guessing gets slower as the page grows; the method does not.

Try it yourself

For each example, say which of the five steps it broke in before you run it. Then run it with nix-instantiate --eval -E '…' (or nix-build for the last two) and check yourself.

  1. let a = 1; in [ a b
  2. let x = 1; in x + y
  3. ({ a, b }: a) { a = 1; }
  4. let xs = [1 2 3] ++ xs; in builtins.length xs
  5. builtins.fetchurl "http://localhost:1/x"
  6. The "oops" derivation from the building step.
  7. The fixed-note derivation with an all-A hash.
Show the answers

1: step 1, reading (unexpected end of file). 2: step 2, working out (undefined variable). 3: step 2 (missing required argument). 4: step 2 (infinite recursion). 5: step 3, fetching (cannot connect). 6: step 4, building (exit code 127). 7: step 3 or 4 in spirit: the hash check happens when the fixed-output job finishes, and it is a "wrong stamp" problem, fixed by checking the file and then copying got. Notice that only 6 and 7 print a building line.

Then break something in your own project on purpose, name the step, and fix it with only the tool that step calls for.

Name the step first. The tool follows.

When the red words come, you stop guessing and start with one question, and the question already points at the next thing to try. Next: the whole book's pieces, working together.

Sources: every error message, exit code and command in this chapter was produced by running Nix 2.34.6 and a current Nixpkgs pre-release in my own test session (src-local-nix-2.34-debug, src-local-nixpkgs-26.11-debug), plus the findings of chapters 7 and 9 (src-local-nix-2.34, src-local-nix-2.34-lifecycle).
