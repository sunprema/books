Chapter 09

Security by Design

WebRTC is the rare web platform where security was not bolted on as an afterthought. From day one, the architects embedded encryption at every layer, made it mandatory rather than optional, and refused to provide an API escape hatch that could silently downgrade a session to plaintext. The result is a protocol stack where every media packet, every data channel message, and every key exchange is encrypted by default—and by requirement. Understanding why, and where the remaining attack surface lives, is essential for anyone building production real-time applications.

Key Insight

Encryption in WebRTC is not optional. There is no configuration flag, no browser setting, no SDP attribute that can disable it. Every DTLS handshake, every SRTP packet, every data channel frame is encrypted. This was a deliberate, non-negotiable design decision documented in RFC 8827. The spec authors watched what happened when protocols made encryption optional—deployments skipped it for performance, carriers stripped it for lawful intercept, and users were left unprotected. WebRTC closed that door permanently.

Secure Origins: The HTTPS Requirement

Before a single frame of video leaves a camera, the browser enforces the first security gate: secure origins. The getUserMedia(), getDisplayMedia(), and RTCPeerConnection APIs are available only on pages served over HTTPS (or localhost during development). This is not a WebRTC-specific rule—it is part of the broader Secure Contexts specification (W3C Secure Contexts)—but its impact on real-time communication is profound. An attacker who compromises a plain HTTP page could silently activate the user’s camera and microphone. The HTTPS requirement eliminates that class of attack entirely by ensuring that the page origin is authenticated via TLS before any powerful API becomes available.

In practice, this means every WebRTC deployment requires a valid TLS certificate. Self-signed certificates will trigger browser warnings and, in many cases, block API access. Services like Let’s Encrypt have made this free and automated, but it remains a hard prerequisite.

User Permissions: Explicit Consent

Even on a secure origin, the browser will not hand over camera or microphone access silently. The user must grant explicit permission through a browser-controlled prompt that your JavaScript cannot suppress, style, or auto-dismiss. This prompt is managed entirely by the browser’s permission system, not by your application code. When the user clicks “Allow,” the permission is scoped to that origin and can be revoked at any time through browser settings.

For screen sharing via getDisplayMedia(), the rules are even stricter. The browser must show a picker that lets the user choose which screen, window, or tab to share. No application can pre-select the capture target or silently begin recording the user’s display. These restrictions exist because screen sharing exposes far more information than a camera feed—passwords, private messages, financial data—all visible in a single frame.

DTLS: Encrypting the Key Exchange

DTLS (Datagram Transport Layer Security) is the UDP-adapted sibling of TLS. Where TLS secures TCP streams (your HTTPS connection, for example), DTLS secures individual datagrams—exactly what WebRTC needs for its UDP-based media transport. Every WebRTC peer connection begins with a DTLS handshake that establishes a shared secret between the two peers. This shared secret is then used to derive the encryption keys for SRTP media packets.

The DTLS handshake runs directly between the two peers, not through any intermediary server. Even if your signaling server is compromised, the attacker cannot decrypt the media because the DTLS keys are negotiated peer-to-peer. This is a critical architectural property: the signaling layer carries metadata about the session, but the encryption protects the session content independently.

SRTP: Encrypting Media in Transit

Once DTLS establishes keys, all audio and video packets are encrypted with SRTP (Secure Real-time Transport Protocol, defined in RFC 3711). SRTP encrypts the media payload of each RTP packet while leaving the header unencrypted—routers and middleboxes can still route packets without reading their content. The encryption algorithm is typically AES-128-CM (Counter Mode) with HMAC-SHA1 for authentication, though modern implementations increasingly support AES-256-GCM for both encryption and authentication in a single pass.

The combination of DTLS for key exchange and SRTP for media encryption is known as DTLS-SRTP, specified in RFC 5764. It is the only key exchange mechanism permitted for WebRTC—the older SDES (Session Description Protocol Security Descriptions) method, which embedded keys directly in the SDP, was explicitly excluded because it requires the signaling channel to be trusted. DTLS-SRTP does not.

0 Unencrypted calls possible
100% Mandatory encryption
2 Layers of encryption (DTLS + SRTP)

The DTLS-SRTP Handshake Flow

Understanding how DTLS-SRTP bootstraps a secure media channel is worth walking through step by step. The process begins during signaling, extends through the ICE connectivity check, and completes with the first encrypted media packet.

SDP Offer with DTLS Fingerprint
The offerer generates a self-signed certificate, computes its SHA-256 fingerprint, and embeds it in the SDP offer as an a=fingerprint attribute. This fingerprint is sent to the remote peer through the signaling channel.
SDP Answer with DTLS Fingerprint
The answerer generates its own self-signed certificate, computes its fingerprint, and includes it in the SDP answer. Both peers now know what certificate to expect from the other side.
ICE Connectivity Check
ICE finds a working network path between the peers using STUN binding requests. Once a candidate pair is validated, the transport is ready for the DTLS handshake.
DTLS ClientHello
The DTLS client (determined by the a=setup SDP attribute) sends a ClientHello over the validated ICE transport. The handshake negotiates cipher suites and exchanges certificates.
DTLS ServerHello + Certificate
The DTLS server responds with its certificate. Each peer verifies that the received certificate’s fingerprint matches the one declared in the SDP. A mismatch aborts the connection—this is the MITM defense.
SRTP Keys Derived
The completed DTLS handshake produces a shared master secret. Both peers use the DTLS-SRTP key export mechanism (RFC 5764) to derive symmetric encryption keys for SRTP. Encrypted media begins flowing.

Fingerprint Verification: Preventing Man-in-the-Middle Attacks

The a=fingerprint line in SDP is the linchpin of WebRTC’s MITM defense. When Peer A sends its SDP offer, it includes the SHA-256 hash of its DTLS certificate. When the DTLS handshake later occurs directly between peers, each side checks that the certificate presented during the handshake matches the fingerprint declared in the SDP. If an attacker intercepts the DTLS handshake and substitutes their own certificate, the fingerprint will not match, and the browser will refuse to complete the connection.

This mechanism works because it binds the signaling-layer identity (the fingerprint in SDP) to the transport-layer identity (the certificate in DTLS). An attacker would need to compromise both the signaling channel and the media transport simultaneously to succeed—a significantly harder attack than intercepting either one alone.

SDP fingerprint attribute
// The SHA-256 hash of the peer's DTLS certificate
a=fingerprint:sha-256 4A:1B:2C:3D:4E:5F:...
a=setup:actpass
a=rtcp-mux

Mandatory Encryption: No Opt-Out

It is worth emphasizing just how absolute this requirement is. RFC 8827 (WebRTC Security Architecture) states that implementations MUST support DTLS-SRTP and MUST NOT offer or accept unencrypted media. There is no encryption: false option in the RTCPeerConnection constructor. There is no browser flag to disable it. Even the internal Ozone/Electron-based applications that embed Chromium cannot bypass this requirement without forking the WebRTC library itself.

This design philosophy extends to data channels as well. Every SCTP data channel runs over the same DTLS transport that secures media. There is no mechanism to create an unencrypted data channel. The protocol treats encryption as a structural requirement of the connection, not a feature that can be toggled.

IP Address Leakage and mDNS Obfuscation

Warning

WebRTC can leak a user’s real IP address—including private network addresses behind a NAT—through ICE candidates. Host candidates contain the machine’s local IP (e.g., 192.168.1.42), and server-reflexive candidates reveal the public IP even when the user is behind a VPN. This is a well-documented privacy concern that has been exploited for browser fingerprinting, VPN detection, and geolocation tracking.

The ICE candidate gathering process is inherently leaky. When a browser gathers host candidates, it enumerates local network interfaces and includes their IP addresses in the candidate strings. These candidates travel through the signaling channel to the remote peer—and to anyone operating the signaling server. For users behind VPNs, this can reveal their true IP address, defeating the purpose of the VPN.

Modern browsers mitigate this with mDNS obfuscation. Instead of exposing raw IP addresses in host candidates, the browser generates a random UUID-based .local hostname (e.g., a1b2c3d4-e5f6-7890-abcd-ef1234567890.local) and uses mDNS to resolve it on the local network. The remote peer receives the .local address instead of a numeric IP. This prevents the signaling server and the remote peer from learning the user’s local network topology.

ICE candidate with mDNS obfuscation
// Before mDNS (leaks private IP)
a=candidate:1 1 udp 2122260223 192.168.1.42 54321 typ host

// After mDNS (IP address hidden)
a=candidate:1 1 udp 2122260223 a1b2c3d4-e5f6-7890-abcd-ef1234567890.local 54321 typ host

Note that mDNS obfuscation only protects host candidates. Server-reflexive candidates still reveal the user’s public IP by design—without them, connectivity through NAT would be impossible. Users who need full IP privacy must route all traffic through a TURN relay, which hides their address behind the TURN server’s IP.

ICE Consent Freshness

Establishing a connection is not enough—WebRTC must continuously verify that the remote peer still wants to receive traffic. The ICE consent freshness mechanism, defined in RFC 7675, requires each peer to send periodic STUN binding requests to the remote peer throughout the session. If a peer stops responding to these checks for 30 seconds, the browser terminates the connection.

This mechanism serves two purposes. First, it prevents a scenario where an attacker redirects traffic to a victim’s IP address after the initial handshake—the victim would not respond to consent checks, and the connection would be torn down. Second, it ensures that abandoned connections are cleaned up promptly, releasing network and system resources.

Parameter Value Purpose
Check interval Every 5 seconds Verify remote peer still consents to receive traffic
Consent timeout 30 seconds Connection terminated if no response within this window
Transaction ID Random per check Prevent replay attacks on consent responses

Screen Sharing Security Indicators

When a user shares their screen via getDisplayMedia(), browsers display persistent visual indicators that cannot be hidden or dismissed by the web application. In Chrome, this is a blue “Sharing” bar at the top of the shared window or a system notification. In Firefox, it is a pulsing tab indicator and a persistent notification. These indicators serve as an ongoing consent signal—the user can always see that sharing is active and can stop it with a single click.

Browsers also restrict what getDisplayMedia() can capture. Audio capture from screen shares is limited (some browsers only support it for tab captures, not window or screen captures). The displaySurface constraint can request a specific surface type but cannot enforce it—the user always makes the final choice. And importantly, getDisplayMedia() cannot be called without a user gesture (a click or keypress)—background tabs cannot silently begin capturing.

TURN Server Trust Considerations

When traffic flows through a TURN relay, the TURN server sees the encrypted SRTP packets but cannot decrypt them—it lacks the DTLS keys. However, the TURN server can observe metadata: which IP addresses are communicating, when, for how long, and how much bandwidth they consume. This metadata can be valuable to an adversary.

For this reason, choose your TURN provider carefully. Self-hosted TURN servers (using coturn or Pion TURN) give you full control over the relay infrastructure. Cloud-hosted TURN services (Twilio, Xirsys, Cloudflare) are convenient but mean trusting a third party with connection metadata. In highly sensitive deployments—healthcare, legal, government—self-hosted TURN behind your own network perimeter is the safer choice.

Note

TURN credentials should be short-lived. Use the time-limited credential mechanism described in RFC 8656, where the signaling server generates temporary TURN credentials (typically valid for 5–10 minutes) that are included in the iceServers configuration. This limits the window of abuse if credentials are intercepted.

Common Security Mistakes

Even though WebRTC provides strong encryption by default, developers can still introduce vulnerabilities in the layers they control. These are the mistakes that appear most frequently in production deployments.

Mistake Risk Mitigation
Signaling over plain HTTP MITM can inject rogue SDP, redirect media Always use WSS/HTTPS for signaling
No signaling authentication Anyone can join any room, eavesdrop on calls Require JWT or session tokens before room join
Long-lived TURN credentials Credential theft enables relay abuse, bandwidth theft Use time-limited credentials (5–10 min expiry)
Logging raw SDP to disk Exposes DTLS fingerprints, ICE candidates, IPs Redact sensitive fields before logging
Ignoring iceTransportPolicy Host candidates leak local IPs even when relay-only is needed Set iceTransportPolicy: "relay" for privacy-sensitive apps
Trusting SDP from untrusted sources Malformed SDP can crash parsers or trigger unexpected behavior Validate and sanitize SDP before applying
No rate limiting on signaling DoS via candidate flooding, room join spam Rate-limit signaling messages per connection 
Enforcing relay-only transport for IP privacy
const pc = new RTCPeerConnection({
  iceServers: [{
    urls: 'turn:turn.example.com:443?transport=tcp',
    username: temporaryUsername,
    credential: temporaryPassword
  }],
  // Force all traffic through TURN — no host or srflx candidates
  iceTransportPolicy: 'relay'
});

Defense in Depth: The Full Picture

WebRTC’s security model is not a single lock on the front door—it is a series of gates, each defending a different layer. Secure origins ensure the page is authentic. User permissions ensure consent is explicit. DTLS ensures keys are exchanged securely. SRTP ensures media is encrypted in transit. Fingerprint verification ensures the peer is who they claim to be. Consent freshness ensures the peer still wants to participate. And mDNS obfuscation limits the metadata leaked during connection setup.

None of these mechanisms require developer action to enable. They are all on by default, all mandatory, and all enforced by the browser. Your job as a developer is not to implement encryption—it is to avoid undermining the encryption that is already there. Secure your signaling channel. Authenticate your users. Manage your TURN credentials. And understand that the weakest link in any WebRTC deployment is almost never the protocol itself—it is the application code wrapped around it.
