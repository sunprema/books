Chapter 03

The API Surface

Before packets fly across the wire, your code has to talk to the browser. WebRTC exposes a compact set of JavaScript objects that handle everything from capturing a webcam frame to negotiating an encrypted peer-to-peer tunnel. This chapter walks through every major entry point you will reach for when building a real application — camera access, screen sharing, peer connections, data channels, and recording — with the practical detail you need to start writing code today.

Key HTTPS is mandatory. Browsers gate every media-capture API behind a secure context. That means your page must be served over https:// (or localhost during development). Without it, navigator.mediaDevices is undefined, and no permission prompt will ever appear. Set up TLS early — even a self-signed certificate on localhost saves hours of confusion.

navigator.mediaDevices.getUserMedia()

This is the front door. getUserMedia() asks the user for permission to access a camera, a microphone, or both, and returns a Promise<MediaStream> containing live tracks. The single argument is a constraints object that tells the browser exactly what you want.


const stream = await navigator.mediaDevices.getUserMedia({
  video: {
    width:       { ideal: 1280 },
    height:      { ideal: 720 },
    frameRate:   { max: 30 },
    facingMode: "user"          // front camera on mobile
  },
  audio: {
    echoCancellation: true,
    noiseSuppression: true,
    autoGainControl:  true
  }
});

document.querySelector("video").srcObject = stream;

Constraints come in three flavors: a bare true (give me anything), an exact value, or an object with ideal, min, and max hints. The browser does its best to satisfy ideals, but it will never exceed a max or drop below a min. If the hardware cannot meet a min constraint, the promise rejects with an OverconstrainedError.

Key constraints at a glance

Constraint Type Applies to Notes
width / height number | ConstraintULong video Resolution in pixels. Use ideal to let the browser pick the closest match.
frameRate number | ConstraintDouble video Frames per second. { ideal: 30, max: 60 } is a common pattern.
facingMode string video "user" (front), "environment" (rear), "left", "right".
deviceId string both Pin a specific camera or mic by its ID from enumerateDevices().
echoCancellation boolean audio Hardware or software echo cancellation. On by default in most browsers.
noiseSuppression boolean audio Removes background noise. Disable for music-capture scenarios.
autoGainControl boolean audio Normalizes mic volume automatically.
sampleRate number audio Samples per second (e.g., 48000). Browser may resample internally.

MediaStream & MediaStreamTrack

A MediaStream is a thin container. The real units of media are MediaStreamTrack objects — one per camera, mic, or screen source. Tracks carry a kind ("audio" or "video"), an id, a human-readable label, and a mutable enabled flag you can flip to mute without renegotiating the connection.


const videoTrack = stream.getVideoTracks()[0];
const audioTrack = stream.getAudioTracks()[0];

// Mute the mic (track still flows, but silence is sent)
audioTrack.enabled = false;

// Clone a track for a second destination
const clone = videoTrack.clone();

// Stop capturing entirely (releases the hardware)
videoTrack.stop();
console.log(videoTrack.readyState); // "ended"

A track moves through two states: "live" while it is actively producing media, and "ended" once stopped. Once ended, a track cannot be restarted — you must call getUserMedia() again. Cloning is useful when you need to feed the same camera into both a local preview and a peer connection, potentially with different resolution constraints applied via applyConstraints().

navigator.mediaDevices.enumerateDevices()

Before you can build a device-picker dropdown, you need the list of available hardware. enumerateDevices() returns an array of MediaDeviceInfo objects, each with a deviceId, kind, and label.


const devices = await navigator.mediaDevices.enumerateDevices();

const cameras = devices.filter(d => d.kind === "videoinput");
const mics    = devices.filter(d => d.kind === "audioinput");
const speakers = devices.filter(d => d.kind === "audiooutput");

cameras.forEach(cam => {
  console.log(cam.label, cam.deviceId);
});
Note Labels are empty until the user grants permission at least once. Call getUserMedia() first, then enumerate. This is a privacy measure — fingerprinting surfaces are reduced until the user opts in.

navigator.mediaDevices.getDisplayMedia()

Screen sharing uses a separate entry point. getDisplayMedia() triggers the browser’s native picker where the user selects a monitor, a window, or a browser tab. The returned stream contains a video track and, optionally, system audio.


const screen = await navigator.mediaDevices.getDisplayMedia({
  video: { cursor: "always" },
  audio: true   // system audio (tab audio in Chrome)
});

// Detect when the user clicks "Stop sharing"
screen.getVideoTracks()[0].addEventListener("ended", () => {
  console.log("User stopped sharing");
});

Unlike getUserMedia(), you cannot pre-select a source — the browser always shows its own picker UI. The cursor constraint controls whether the cursor is composited into the captured video. Audio capture from screen sharing is limited to Chromium-based browsers at the time of writing and applies only to tab audio, not full system audio.

RTCPeerConnection

RTCPeerConnection is the heart of the API. It manages the entire lifecycle of a peer-to-peer link: ICE candidate gathering, DTLS handshake, SRTP encryption, codec negotiation, and bandwidth estimation. You create one per remote peer.


const pc = new RTCPeerConnection({
  iceServers: [
    { urls: "stun:stun.l.google.com:19302" },
    {
      urls:       "turn:turn.example.com:3478",
      username:   "user",
      credential: "pass"
    }
  ],
  iceCandidatePoolSize: 2
});

// Add local tracks to the connection
stream.getTracks().forEach(track => {
  pc.addTrack(track, stream);
});

// Listen for remote tracks arriving
pc.addEventListener("track", (event) => {
  remoteVideo.srcObject = event.streams[0];
});

The iceServers array tells the connection where to find STUN and TURN servers for NAT traversal (covered in depth in Chapter 02). The optional iceCandidatePoolSize pre-gathers candidates before you create an offer, shaving a few hundred milliseconds off connection setup. In production, always include at least one TURN server — roughly 15% of users sit behind symmetric NATs that block direct connections entirely.

Connection lifecycle states

An RTCPeerConnection exposes two state properties that track its progress. The iceConnectionState reflects the ICE agent, while connectionState rolls up ICE, DTLS, and SCTP into a single value. Prefer connectionState when your browser support matrix allows it.

new Created, no networking yet
connecting ICE / DTLS handshake in progress
connected Media is flowing
disconnected Temporary loss, may recover
failed ICE checks exhausted
closed Connection torn down 

pc.addEventListener("connectionstatechange", () => {
  switch (pc.connectionState) {
    case "connected":
      console.log("Peer link established");
      break;
    case "disconnected":
      console.log("Connection interrupted, attempting recovery...");
      break;
    case "failed":
      console.log("Connection failed, restarting ICE");
      pc.restartIce();
      break;
    case "closed":
      console.log("Connection closed");
      break;
  }
});

The transition from disconnected to failed is not instant — the ICE agent keeps probing for several seconds (browser-dependent, typically five to thirty seconds). If the network path recovers in time, the state returns to connected without any action on your part. When it reaches failed, your best option is an ICE restart via pc.restartIce(), which triggers a new offer/answer exchange while preserving the existing media tracks.

RTCDataChannel

Not everything is audio and video. RTCDataChannel gives you a low-latency, bidirectional pipe for arbitrary data — chat messages, game state, file chunks, cursor positions. It runs over SCTP, which sits on top of the same DTLS tunnel as your media, so there is zero extra NAT traversal cost.


// Offerer creates the channel
const channel = pc.createDataChannel("chat", {
  ordered:        true,
  maxRetransmits: 3     // give up after 3 retries
});

channel.addEventListener("open", () => {
  channel.send("Hello from offerer");
});

channel.addEventListener("message", (event) => {
  console.log("Received:", event.data);
});

// Answerer listens for incoming channels
pc.addEventListener("datachannel", (event) => {
  const incoming = event.channel;
  incoming.addEventListener("message", (e) => {
    console.log("Answerer got:", e.data);
  });
});

Two reliability modes exist. Set ordered: true with maxRetransmits for TCP-like reliability with a retry cap. Or set ordered: false and maxPacketLifeTime (in milliseconds) for a UDP-like mode where stale packets are dropped. The former suits chat; the latter suits real-time game input where old positions are worthless. You can open multiple named channels on a single peer connection, each with its own reliability settings.

MediaRecorder

Sometimes you need to save what is happening, not just transmit it. MediaRecorder takes any MediaStream — from a camera, a screen share, or even a remote peer — and encodes it into a container format you can store or upload.


const chunks = [];
const recorder = new MediaRecorder(stream, {
  mimeType: "video/webm;codecs=vp9,opus"
});

recorder.addEventListener("dataavailable", (e) => {
  if (e.data.size > 0) chunks.push(e.data);
});

recorder.addEventListener("stop", () => {
  const blob = new Blob(chunks, { type: "video/webm" });
  const url  = URL.createObjectURL(blob);
  const a    = document.createElement("a");
  a.href     = url;
  a.download = "recording.webm";
  a.click();
});

recorder.start(1000); // emit a chunk every second

// Later...
recorder.stop();

The mimeType determines both the container and the codecs. Check support first with MediaRecorder.isTypeSupported(mimeType) — codec availability varies across browsers. The timeslice argument to start() controls how often dataavailable fires; smaller slices let you upload chunks progressively for live-recording scenarios, while omitting it delivers a single blob when you call stop().

Warn MediaRecorder output is not seekable by default. The WebM container written during recording lacks duration metadata until the file is finalized. If you need random-access playback, post-process the file with a tool like ffmpeg or use a library such as fix-webm-duration to patch the metadata client-side.

Putting it all together

A typical WebRTC application touches these APIs in a predictable order. First, call getUserMedia() or getDisplayMedia() to capture local media. Next, create an RTCPeerConnection, add tracks, and optionally open data channels. Then exchange offers and answers through your signaling server (Chapter 04). Once the connection enters the connected state, media flows directly between peers. If you need a recording, wrap any stream in a MediaRecorder at any point in the process.

Every object in this chapter lives in the browser — no plugins, no extensions, no native installs. That is the promise of WebRTC: a full real-time communication stack built into the platform, accessible through a handful of well-designed JavaScript interfaces. The next chapter covers the one piece the browser does not provide for you: signaling.
