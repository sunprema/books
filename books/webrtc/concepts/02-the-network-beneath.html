Chapter 02

The Network Beneath

Before you write a single line of WebRTC JavaScript, you need to understand the plumbing it runs on. The browser API is the steering wheel, but UDP datagrams, NAT boxes, and RTP packets are the engine, transmission, and road surface. Ignore them and your video call will stutter, freeze, or never connect at all. This chapter maps the terrain so you can build on solid ground.

Client–Server vs. Peer-to-Peer

Most of the web is client–server. Your browser sends an HTTP request to a server; the server sends back HTML, JSON, or a video stream. Every byte travels through a centralized machine that the service operator owns. That model works beautifully for web pages and API calls, but it introduces a mandatory detour for real-time media.

Imagine two people sitting in the same office building, each on a video call through a server hosted three thousand kilometers away. Their voice packets leave the building, cross half a continent, bounce off a data center, then travel all the way back. The round-trip adds 60–120 ms of latency that simply would not exist if the packets went directly from one laptop to the other across the office LAN.

Peer-to-peer (P2P) eliminates that detour. Once two endpoints discover each other, media flows on the shortest network path between them. The benefits are tangible:

Lower Latency

Packets take the shortest route rather than detouring through a relay server, shaving tens of milliseconds off every frame of audio and video.

Better Privacy

Media never touches a server you do not control. End-to-end encryption between peers means no intermediary can inspect the content of your conversation.

Reduced Server Cost

Bandwidth is the most expensive line item for media servers. P2P offloads that cost to the edges, where bandwidth is essentially free for the participants.

Natural Scalability

Each new peer brings its own upload capacity. For small-group calls (2–4 participants), a mesh of direct connections can handle the load without any server infrastructure.

The catch is that P2P connections are harder to establish. Both sides need to agree on addresses, punch through NATs, and negotiate codecs—problems that a centralized server handles trivially. WebRTC exists precisely to solve those problems inside the browser.

TCP vs. UDP: Choosing the Right Pipe

Every byte on the internet rides on one of two transport protocols. TCP guarantees delivery: if a packet gets lost, it retransmits it, and the receiving side waits until every byte arrives in order. UDP makes no such promise: it fires datagrams into the network and moves on. If one goes missing, nobody looks back.

For a web page, TCP is perfect. You want every byte of that HTML file, and you can afford to wait a few extra milliseconds for a retransmission. But for a live voice conversation, TCP’s reliability guarantee becomes a liability.

Characteristic TCP UDP
Delivery guarantee Ordered, reliable Best-effort, unordered
Connection setup 3-way handshake None (connectionless)
Head-of-line blocking Yes — one lost packet stalls all subsequent data No — each datagram is independent
Congestion control Built in (slow start, AIMD) None by default (app must implement)
Latency profile Variable — spikes on retransmission Consistent — no retransmission delay
Typical use HTTP, file transfer, email Voice/video, gaming, DNS

The critical concept is head-of-line blocking. When TCP detects a lost packet, it pauses delivery of everything behind it until the retransmission arrives. For a file download, that pause is invisible. For live audio, it means a 200 ms freeze while the stack waits for a packet that is already stale. By the time the retransmitted audio sample arrives, the conversation has moved on—the listener would rather hear a tiny gap than a 200 ms delay that throws off the rhythm of speech.

This is why WebRTC sends media over UDP. It accepts occasional packet loss in exchange for consistent, low latency. The application layer (codecs and jitter buffers) handles the missing data, either concealing the gap or interpolating the missing audio frame.

Note

WebRTC does use TCP as a fallback when UDP is completely blocked by a firewall. It also uses TCP for its data channel when ordered, reliable delivery is requested. But for media—voice and video—UDP is always the first choice.

Latency, Jitter, and Packet Loss

Three numbers define the quality of any real-time connection. Understanding them is the difference between debugging a choppy call in five minutes and staring at dashboards for hours.

Latency (Delay)

Latency is the time a packet takes to travel from sender to receiver, measured in milliseconds. It includes propagation delay (speed of light through fiber), processing delay (router queues, codec encoding), and transmission delay (serializing bits onto the wire). For a comfortable voice conversation, you need the one-way latency to stay under 150 ms. Go beyond 300 ms and people start talking over each other; beyond 400 ms, the call feels like a satellite phone from the 1990s.

150 ms One-way target for voice
300 ms Noticeable awkwardness begins
400 ms Round-trip ceiling (ITU-T G.114)

Jitter (Variation in Delay)

Jitter is the variation in packet arrival times. If packets arrive every 20 ms like clockwork, jitter is zero. If one arrives at 15 ms, the next at 35 ms, then 10 ms, you have high jitter. The receiver cannot play audio frames at irregular intervals without audible glitches, so it uses a jitter buffer—a small queue that absorbs variation by introducing a fixed additional delay. A larger buffer handles more jitter but adds latency. A smaller buffer keeps latency low but risks underruns when packets arrive late. Tuning this tradeoff is one of the core challenges in real-time media.

Packet Loss

On the open internet, between 0.1% and 2% of UDP packets will simply vanish. They hit a congested router, the router drops them, and nobody retransmits. Modern audio codecs like Opus can conceal up to about 5% loss before the listener notices degradation. Video is less forgiving—a single lost keyframe can corrupt every subsequent frame until the next keyframe arrives. WebRTC handles this with techniques like Forward Error Correction (FEC), negative acknowledgments (NACK), and dynamic bitrate adaptation.

Key Concept

Real-time media is a constant negotiation between latency, quality, and reliability. You cannot have all three at maximum. WebRTC’s congestion control algorithms (like Google Congestion Control, GCC) automatically adjust bitrate, resolution, and frame rate in response to changing network conditions. Understanding the underlying tradeoffs helps you configure and debug these systems.

NAT: The Invisible Wall

Network Address Translation is the reason peer-to-peer connections are hard. Nearly every device on the internet sits behind a NAT. Your laptop does not have a public IP address—it has a private address like 192.168.1.42, and your router translates that to its single public IP when packets leave your network. When the response comes back, the router maps it back to your private address.

This works seamlessly for client–server traffic because the client always initiates the connection. The router creates a mapping entry when the outbound packet leaves, and the server’s response matches that entry. But when two peers behind two different NATs want to talk to each other, neither one has a routable public address to target. Both routers are waiting for an inbound packet that matches an existing mapping—and no such mapping exists.

The NAT Problem

Two devices behind separate NATs cannot directly connect. Device A has private address 192.168.1.42 and Device B has 10.0.0.17—neither address is routable on the public internet. Even if they knew each other’s public IPs (the router’s external address), the routers would drop unsolicited inbound packets because no outbound mapping exists for them. This is why WebRTC needs STUN servers to discover public addresses and ICE to coordinate simultaneous connection attempts from both sides. When even that fails, a TURN relay server acts as a last-resort intermediary.

The Four NAT Types

Not all NATs behave the same way. The differences matter because they determine how hard (or impossible) it is to punch through.

NAT Type Mapping Rule Filtering Rule P2P Difficulty
Full Cone Same external port for all destinations Any external host can send to the mapped port Easy
Address-Restricted Cone Same external port for all destinations Only hosts the internal device has contacted can reply Moderate
Port-Restricted Cone Same external port for all destinations Only the exact host:port pair previously contacted can reply Hard
Symmetric Different external port for each destination Only the exact host:port pair previously contacted can reply Very hard — often requires TURN

Think of it like a mailroom in an office building. A full-cone NAT is a mailroom that accepts packages from anyone as long as they are addressed to the right suite number. A symmetric NAT is a mailroom that only accepts a package if it comes from the exact courier service that the suite already has an outgoing shipment with—and it assigns a different suite number for every courier. That second mailroom makes it nearly impossible for a new courier to deliver a package without prior arrangement.

Most consumer routers implement port-restricted cone or symmetric NAT. Corporate firewalls tend toward symmetric. This is why roughly 8–15% of WebRTC calls require a TURN relay to succeed—the NATs on both sides are too restrictive for direct connectivity.

Firewalls and Their Effect on P2P

Firewalls add another layer of filtering on top of NAT. A NAT translates addresses; a firewall enforces policy. Corporate firewalls often block all inbound UDP traffic by default and may restrict outbound traffic to specific ports (80 for HTTP, 443 for HTTPS). Since WebRTC media uses high-numbered UDP ports, these firewalls can silently drop every media packet.

The typical escalation path looks like this:

Try direct UDP
Peer A sends a STUN binding request directly to Peer B’s discovered public address. If both NATs cooperate, a direct UDP path is established with minimal latency.
Try STUN-assisted UDP
Both peers use a STUN server to discover their public IP and port. They exchange these via signaling and attempt simultaneous connection (“hole punching”). Works through most cone-type NATs.
Fall back to TURN relay
When NAT or firewall blocks all direct paths, both peers relay through a TURN server. Media flows peer → TURN → peer, adding latency but guaranteeing connectivity.
TURN over TCP/443
The most restrictive firewalls block all UDP. TURN can tunnel media over TCP port 443, disguising it as HTTPS traffic. This is the last resort—it works almost everywhere but adds TCP’s head-of-line blocking overhead.

WebRTC’s ICE (Interactive Connectivity Establishment) framework automates this entire escalation. It gathers candidates at every level, tests them in parallel, and picks the best working path—all before the first frame of video appears. You will build this system in detail in Chapter 04.

Media Traffic vs. Signaling Traffic

WebRTC splits communication into two fundamentally different channels, and confusing them is one of the most common mistakes newcomers make.

Media Traffic

The actual audio and video data. Encoded by codecs (Opus, VP8, H.264), packetized into RTP datagrams, and sent over UDP directly between peers. High bandwidth (hundreds of kbps to several Mbps), latency-sensitive, encrypted with SRTP. This is the data the user cares about.

Signaling Traffic

The metadata that sets up the media session: SDP offers and answers describing codec capabilities, ICE candidates listing network addresses, and session lifecycle messages (join, leave, mute). Low bandwidth (a few KB per session), not latency-critical, travels through your server. WebRTC does not define a signaling protocol—you choose your own.

Why You Need a Signaling Server

This confuses people. If WebRTC is peer-to-peer, why do you need a server at all? The answer is a bootstrapping problem: before two peers can exchange media directly, they need to exchange their connection parameters—IP candidates, supported codecs, encryption fingerprints. They have no direct channel yet, so this initial exchange must happen through a shared intermediary.

Think of it like two people who want to meet in a large city. They need to agree on a meeting point before they can walk there. The phone call where they agree on “the coffee shop on 5th and Main” is the signaling. The actual face-to-face meeting is the media session. The phone network (your signaling server) is essential for coordination but carries none of the actual conversation.

Your signaling server can be a WebSocket server, a REST API, a Firebase Realtime Database, or even a shared Google Doc with copy-paste—WebRTC genuinely does not care. It just needs the SDP offer to get from Peer A to Peer B, and the SDP answer to come back. Here is a minimal example:

// Minimal signaling with WebSocket
const ws = new WebSocket('wss://signal.example.com');

// Send our offer to the signaling server
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
ws.send(JSON.stringify({
  'type': 'offer',
  'sdp': pc.localDescription
}));

// Receive the remote answer via signaling
ws.addEventListener('message', async (event) => {
  const msg = JSON.parse(event.data);
  if (msg.type === 'answer') {
    await pc.setRemoteDescription(msg.sdp);
  }
  if (msg.type === 'candidate') {
    await pc.addIceCandidate(msg.candidate);
  }
});

RTP and RTCP: How Media Packets Work

Once the peer-to-peer path is established, media does not travel as raw audio samples or raw pixel data. It is wrapped in the Real-time Transport Protocol (RTP), defined in RFC 3550. RTP adds just enough structure to make real-time playback possible without the overhead of TCP.

Inside an RTP Packet

Every RTP packet carries a compact header followed by the encoded media payload. The header fields that matter most:

Field Size Purpose
Sequence Number 16 bits Increments by 1 per packet. The receiver detects loss and reordering by watching for gaps.
Timestamp 32 bits Encodes when the media sample was captured, using the codec’s clock rate (e.g., 48000 Hz for Opus). The jitter buffer uses this to schedule playback.
SSRC 32 bits Synchronization Source identifier. Uniquely identifies each media stream so the receiver can demultiplex audio and video arriving on the same port.
Payload Type 7 bits Identifies the codec (e.g., 111 for Opus, 96 for VP8). Mapped to specific codecs during SDP negotiation.
Marker Bit 1 bit Signals frame boundaries. For video, it marks the last packet of a frame; for audio, it can indicate the start of a talkspurt after silence.

Notice what is not in the header: there is no acknowledgment field, no retransmission request, no flow control. RTP deliberately stays lean. The feedback loop is handled by a companion protocol.

RTCP: The Feedback Channel

RTCP (RTP Control Protocol) runs alongside RTP on a separate logical channel. While RTP carries the media, RTCP carries statistics about the media. It sends periodic reports that tell each side how the other is doing:

Sender Report (SR)
The media sender transmits an SR every few seconds, containing the number of packets and bytes sent, plus NTP and RTP timestamp pairs for synchronization between audio and video streams.
Receiver Report (RR)
The receiver responds with packet loss fraction, cumulative loss count, jitter measurements, and round-trip delay estimates. These metrics drive congestion control decisions.
NACK / PLI / FIR
When the receiver detects a lost packet, it can send a Negative Acknowledgment (NACK) requesting retransmission. For video, a Picture Loss Indication (PLI) or Full Intra Request (FIR) asks the sender to emit a fresh keyframe.
REMB / TMMBR
Receiver Estimated Maximum Bitrate messages let the receiver tell the sender to slow down when bandwidth is constrained. This is how WebRTC adapts video quality in real time without buffering.

The beauty of this design is separation of concerns. RTP stays fast and stateless—it just ships media. RTCP provides the intelligence layer on top, letting both sides adapt to network conditions without adding overhead to every media packet. WebRTC bundles both onto a single UDP port using multiplexing (RFC 5761), which simplifies NAT traversal since only one port needs to be punched through.

Putting It All Together

Here is the full picture, layer by layer, of what happens when Peer A calls Peer B:

Signaling (WebSocket / HTTP)
Peer A creates an SDP offer describing its media capabilities and ICE candidates. The offer travels through your signaling server to Peer B. Peer B generates an SDP answer and sends it back. Both sides now know what codecs to use and where to send packets.
ICE Connectivity Checks
Both peers test candidate pairs—direct, STUN-reflected, and TURN-relayed—by sending STUN binding requests. The first pair that gets a response wins. The ICE agent selects the best available path.
DTLS Handshake
Once a working path exists, both peers perform a DTLS handshake over the same UDP connection. This establishes encryption keys for SRTP, ensuring that media packets are encrypted end-to-end.
Media Flow (SRTP over UDP)
Encoded audio and video frames are packetized into RTP, encrypted into SRTP, and sent as UDP datagrams directly between peers. RTCP flows alongside, providing continuous quality feedback and driving bitrate adaptation.
Key Takeaway

The network beneath WebRTC is a carefully layered stack: UDP provides the low-latency transport, RTP adds sequencing and timing for media playback, RTCP provides the feedback loop for quality adaptation, SRTP adds encryption, ICE handles NAT traversal, and your signaling server bootstraps the entire exchange. Every layer solves exactly one problem, and understanding each layer gives you the vocabulary to debug real-world issues. When a call fails, you can now ask the right question: is it a NAT problem, a codec mismatch, packet loss, or a firewall blocking UDP?
