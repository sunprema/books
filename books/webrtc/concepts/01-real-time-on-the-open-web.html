Chapter 01

Real-Time on the Open Web

For most of the web’s history, real-time communication meant installing a plugin, crossing your fingers, and hoping the other person had the same one. WebRTC changed that equation entirely: it gave every modern browser a built-in engine for sending audio, video, and arbitrary data directly between peers—no downloads, no gatekeepers, no middlemen skimming your packets. If you build things for the web, this is the most important real-time primitive you have.

The Problem WebRTC Solves

Think about what happens when you make a video call in your browser. Your camera captures frames at 30 fps, your microphone samples audio 48,000 times per second, and all of that data needs to reach another human’s screen and speakers in under half a second—ideally under 150 milliseconds. Traditional HTTP was never designed for this. It’s a request-response protocol: you ask a server for something, and the server sends it back. That round-trip model is fine for fetching a web page. It is catastrophically wrong for a live conversation.

WebRTC solves this by giving browsers the machinery to establish direct, peer-to-peer media sessions. Two browsers negotiate codecs, discover a network path through NATs and firewalls, encrypt every packet end-to-end, and begin streaming media—all without the data touching your application server. Your server helps the peers find each other (signaling), but once the call is up, it steps aside.

Key Concept

The core mental model: Two browsers agree on how to talk (codec negotiation via SDP), find a network path to each other (ICE candidate gathering through STUN/TURN), and then exchange media directly—encrypted, low-latency, peer-to-peer. Your application server is a matchmaker, not a relay.

A Brief History: From Plugins to Platform

The Plugin Era

Before 2011, real-time communication on the web required third-party browser plugins. Adobe Flash provided NetStream and RTMFP for rudimentary peer connections. Java applets could open raw sockets but demanded a JVM installation. Microsoft’s Silverlight offered its own media stack. Each plugin brought its own security surface, its own update cycle, and its own compatibility nightmares. Users had to install software before they could even start a call, and mobile browsers—where plugins were never welcome—were simply left out.

Google, GIPS, and the Open-Source Bet

In 2010, Google acquired Global IP Solutions (GIPS), a Swedish company that had spent over a decade building best-in-class voice and video codecs used by Oovoo, Yahoo Messenger, and dozens of telecom products. Instead of keeping the technology proprietary, Google open-sourced the entire codec stack—including the VP8 video codec and the iSAC/iLBC audio codecs—and proposed a new set of browser APIs to the W3C. The project was called WebRTC, short for Web Real-Time Communication.

Chrome shipped initial WebRTC support in 2012. Firefox followed the same year. By 2013, Chrome and Firefox could video-call each other without any plugin. The W3C and IETF worked in parallel—the W3C defining the JavaScript APIs, the IETF specifying the wire protocols (ICE, DTLS-SRTP, SCTP). In January 2021, WebRTC 1.0 became a full W3C Recommendation, cementing its place as a platform primitive rather than an experiment.

What WebRTC Is—and What It Is Not

A common misconception: “WebRTC is a protocol.” It is not. WebRTC is a collection of protocols, codecs, and browser APIs that work together to enable real-time communication. Under the hood, a single WebRTC session may involve:

ICE Interactive Connectivity Establishment

Discovers the best network path between peers by testing candidates—host addresses, server-reflexive (STUN), and relay (TURN)—and selecting the one with the lowest latency and highest reliability.

DTLS Datagram Transport Layer Security

Performs a handshake over UDP to establish encryption keys. Every media packet is encrypted end-to-end; no intermediary (not even your own server) can read the stream.

SRTP Secure Real-time Transport Protocol

Carries the actual audio and video frames. Uses the keys negotiated by DTLS. Provides sequencing, timestamping, and payload-type identification so the receiver can reconstruct the media timeline.

SDP Session Description Protocol

A text format for describing media capabilities—codecs, resolutions, directions, ICE credentials. Peers exchange SDP “offers” and “answers” through your signaling channel to agree on session parameters.

SCTP Stream Control Transmission Protocol

Powers RTCDataChannel. Supports reliable and unreliable delivery, message ordering, and multiple logical streams over a single association—all running on top of DTLS over UDP.

STUN / TURN NAT Traversal Servers

STUN helps a peer discover its public IP. TURN acts as a media relay when direct connectivity fails. Together they ensure that WebRTC works even behind the most restrictive corporate firewalls.

Note

WebRTC does not define a signaling protocol. How you exchange SDP offers and ICE candidates between peers is entirely up to you—WebSocket, HTTP polling, carrier pigeon. This deliberate omission gives you flexibility but also means you must build or choose a signaling layer yourself.

The Three Pillars

The browser exposes WebRTC through three JavaScript APIs. Every application you build will use at least two of them, and most will use all three.

1. MediaStream — Capture

The MediaStream API (accessed via navigator.mediaDevices.getUserMedia()) captures audio and video from the user’s camera, microphone, or screen. It returns a MediaStream object containing one or more MediaStreamTrack instances—each track representing a single audio or video source. You can display these tracks in a <video> element, process them with MediaStreamTrackProcessor, or feed them into a peer connection for transmission.

// Request camera + microphone access
const stream = await navigator.mediaDevices.getUserMedia({
  video: { width: 1280, height: 720 },
  audio: { echoCancellation: true, noiseSuppression: true }
});

// Display locally
document.querySelector('video#local').srcObject = stream;

2. RTCPeerConnection — Transport

RTCPeerConnection is the workhorse. It handles codec negotiation, ICE candidate gathering, DTLS key exchange, SRTP encryption, bandwidth estimation, packet loss recovery, and adaptive bitrate—all behind a single JavaScript object. You add tracks from a MediaStream, create an SDP offer, send it to the remote peer through your signaling channel, and apply the remote answer. Once ICE connectivity checks succeed, media flows.

const pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    { urls: 'turn:turn.example.com',
      username: 'user',
      credential: 'pass' }
  ]
});

// Add local tracks to the connection
stream.getTracks().forEach(track => pc.addTrack(track, stream));

// Create and send an offer
const offer = await pc.createOffer();
await pc.setLocalDescription(offer);
sendToRemotePeer(offer); // your signaling logic

3. RTCDataChannel — Arbitrary Data

RTCDataChannel lets you send arbitrary data—text, binary blobs, game state, file chunks—over the same peer connection that carries your media. It runs on SCTP over DTLS, giving you options for reliable or unreliable delivery, ordered or unordered messages, and configurable retransmit limits. Think of it as a WebSocket that runs peer-to-peer with no server in the middle.

const channel = pc.createDataChannel('chat', {
  ordered: true,
  maxRetransmits: 3
});

channel.addEventListener('open', () => {
  channel.send('Hello from Peer A!');
});

channel.addEventListener('message', (event) => {
  console.log('Received:', event.data);
});

The Connection Dance

Establishing a WebRTC session follows a predictable sequence. Understanding this flow is essential before you write your first line of code—every debugging session you will ever have traces back to something going wrong in one of these steps.

Peer A → Signaling Server
Peer A calls createOffer(), generating an SDP blob that lists its supported codecs, media directions, and ICE credentials. It sends this offer to the signaling server.
Signaling Server → Peer B
The signaling server relays the offer to Peer B. Peer B calls setRemoteDescription(offer) to register what Peer A supports.
Peer B → Signaling Server
Peer B calls createAnswer(), producing its own SDP with the intersection of supported codecs and parameters. It sends this answer back through signaling.
Signaling Server → Peer A
Peer A receives the answer and calls setRemoteDescription(answer). Both peers now agree on codecs and media configuration.
Peer A ⇔ Peer B
Meanwhile, both peers gather ICE candidates (host, server-reflexive via STUN, relay via TURN) and exchange them through signaling. ICE performs connectivity checks and selects the best candidate pair.
DTLS Handshake
Once ICE succeeds, a DTLS handshake runs over the selected candidate pair to establish encryption keys. SRTP keys are derived from DTLS. Media begins flowing—encrypted, peer-to-peer.

Where WebRTC Shines

WebRTC is the right tool when you need low-latency, bidirectional, real-time communication in a browser or native application. Here are the use cases where it excels:

Video Conferencing

The canonical use case. Google Meet, Jitsi, and hundreds of other platforms use WebRTC to deliver sub-second video and audio between participants. Small group calls work peer-to-peer; larger meetings use an SFU (Selective Forwarding Unit) to distribute streams efficiently.

Telehealth

HIPAA-compliant video consultations built on WebRTC’s mandatory end-to-end encryption. The browser-native approach eliminates the “please install our app” friction that patients dread. DTLS-SRTP encryption is always on—it cannot be disabled.

Live Customer Support

Embed a video or voice call directly in your web app. No app store download. No plugin. The customer clicks a button and is talking to an agent in seconds, with screen sharing via getDisplayMedia() available on demand.

Multiplayer Gaming

RTCDataChannel with unreliable, unordered delivery gives you UDP-like semantics in the browser—perfect for sending game state updates where the latest position matters more than every intermediate frame.

Peer-to-Peer File Sharing

Use RTCDataChannel in reliable mode to transfer files directly between browsers. No upload to a server, no cloud storage intermediary. Combine it with the File API and you have a zero-infrastructure file transfer tool.

IoT & Edge Computing

WebRTC is not browser-only. Native libraries (libwebrtc, Pion, GStreamer) run on embedded devices, drones, and robots. A Raspberry Pi can stream its camera feed to a browser dashboard with hardware-accelerated encoding and sub-second latency.

Where WebRTC Does Not Fit

WebRTC is optimized for low-latency, small-group, interactive communication. It is not a universal hammer. Know its limits so you reach for the right tool:

Warning

One-to-many broadcast at massive scale: A pure peer-to-peer mesh collapses at around 4–6 participants because each peer must encode and send a separate stream to every other peer. For large audiences (hundreds or thousands of viewers), you need a media server—an SFU or MCU—or a CDN-based approach like HLS/DASH. WebRTC can feed the ingest side of such a pipeline, but it is not the distribution mechanism for 100,000 concurrent viewers.

Non-real-time bulk transfer: If you need to move a 10 GB dataset between servers, use HTTP, FTP, or a purpose-built transfer protocol. RTCDataChannel is built for interactivity, not throughput. Its congestion control is tuned for fairness with media streams, not for saturating a pipe.

Server-centric architectures: If every message must be processed, stored, and authorized by your server before the other party sees it (think: a banking chat with compliance logging), the peer-to-peer model works against you. You would end up routing everything through a TURN server anyway, losing the latency and cost benefits that make WebRTC attractive. A WebSocket to your server is simpler and more appropriate.

The Landscape Today

WebRTC is supported in every major browser—Chrome, Firefox, Safari, Edge, and their mobile counterparts. The API has stabilized around the “Unified Plan” SDP format (replacing the older “Plan B” that Chrome used for years). Server-side implementations have matured: Pion (Go), mediasoup (Node.js/C++), Janus (C), and LiveKit (Go) offer production-grade SFUs. The ecosystem is rich, the standards are settled, and the community is active.

New capabilities continue to land. Insertable Streams (also called Encoded Transform) let you manipulate encoded frames in JavaScript—enabling end-to-end encryption schemes where even the SFU cannot decrypt your media. WebTransport is emerging as a complement for scenarios that need HTTP/3 semantics with low-latency data channels. And WebCodecs gives you raw access to hardware encoders and decoders, unlocking use cases like custom video processing pipelines that were previously impossible in the browser.
