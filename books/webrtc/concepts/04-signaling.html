Chapter 04

Signaling: The Out-of-Band Dance

Before two browsers can exchange a single byte of media, they need to agree on how to talk. Codec preferences, network addresses, encryption keys—all of this metadata must travel between peers through a channel that WebRTC itself refuses to define. That channel is signaling, and building it is your first real job as a WebRTC developer.

Key Insight

Signaling is often the first conceptual hurdle for newcomers. Every other real-time protocol—SIP, XMPP, RTMP—ships its own signaling mechanism baked in. WebRTC deliberately does not. This feels like a gap until you realize it is a gift: you pick the transport, the authentication model, and the message format that fits your application. A chat app can piggyback signaling on its existing WebSocket connection. A serverless demo can use Firebase. A telehealth platform can route signals through its HIPAA-compliant REST API. The freedom is intentional.

Why WebRTC Stays Silent on Signaling

The W3C and IETF made a deliberate architectural choice when they designed WebRTC: the specification defines how peers exchange media (via RTP, DTLS, SCTP) but says nothing about how they discover each other or negotiate session parameters. This is protocol agnosticism by design, documented in RFC 8825 (the WebRTC overview architecture).

The reasoning is practical. Every production application already has a server-side component—an authentication layer, a user database, a messaging bus. Mandating a new signaling protocol would force developers to run a second server stack alongside whatever they already have. Instead, the spec says: use whatever works for you, as long as two pieces of data reach the other peer—a session description and a set of ICE candidates.

What Gets Exchanged

Signaling carries two categories of data between peers. Understanding both is essential before you write a single line of server code.

Session Descriptions (SDP)

A session description is a blob of text in SDP (Session Description Protocol) format. It declares everything about what a peer wants to send and receive: codec preferences, media types (audio, video, data channels), encryption fingerprints, bandwidth limits, and extension headers. The browser generates this for you via createOffer() or createAnswer(), and you ferry it to the remote peer through your signaling channel. Chapter 05 dives deep into SDP itself—for now, treat it as an opaque string that must arrive intact.

ICE Candidates

An ICE candidate is a potential network path the peer can use to reach you. Each candidate contains an IP address, port, protocol (UDP or TCP), and a type—host (local interface), server-reflexive (public address from a STUN server), or relay (proxied through a TURN server). The browser fires onicecandidate events as it gathers these, and you send each one to the remote peer. The remote peer feeds them into addIceCandidate() so its ICE agent can test connectivity.

Session Description

Codec preferences, media lines, DTLS fingerprints, SSRC identifiers, bandwidth constraints. Generated by createOffer() or createAnswer(). Exchanged exactly once per negotiation round.

ICE Candidates

IP/port pairs with priority and type (host, srflx, relay). Fired asynchronously via onicecandidate. Multiple candidates per negotiation—typically 4–12 depending on network interfaces and STUN/TURN configuration.

The Offer/Answer Model

WebRTC borrows its negotiation model from RFC 3264, the SIP offer/answer framework. The sequence is asymmetric: one peer is the offerer (caller), the other is the answerer (callee). The offerer proposes a session configuration; the answerer responds with a compatible subset.

Offer (SDP)
Caller creates an offer via createOffer(), sets it as the local description with setLocalDescription(), then sends the SDP string to the callee through the signaling channel.
Answer (SDP)
Callee receives the offer, sets it as the remote description with setRemoteDescription(), creates an answer via createAnswer(), sets it as the local description, and sends the SDP back through the signaling channel.
ICE Candidates
As each peer gathers candidates, it sends them to the other side. Candidates can flow in both directions simultaneously, interleaved with the offer/answer exchange.
ICE Candidates
The remote peer feeds incoming candidates into addIceCandidate(). Once a working candidate pair is found, the DTLS handshake begins and media flows.

The Complete Signaling Exchange

In practice, signaling involves a relay server sitting between the two peers. Neither peer knows the other’s address—the server acts as a mailbox. Here is the full exchange with a signaling server in the middle:

Caller → Server: offer
The caller serializes its local description (the SDP offer) and sends it to the signaling server, tagged with the room or peer identifier.
Server → Callee: offer
The server forwards the offer to the callee. If the callee is not yet connected, the server may buffer the offer until it arrives.
Callee → Server: answer
The callee processes the offer, generates an answer, and sends the SDP answer back through the signaling server.
Server → Caller: answer
The server relays the answer to the caller, who sets it as the remote description. The session description exchange is now complete.
Both → Server: ICE candidates
Both peers begin sending ICE candidates as they are discovered. These flow concurrently in both directions, interleaved with the offer/answer if trickle ICE is used.
Server → Both: ICE candidates
The server relays each candidate to the opposite peer. Connectivity checks begin as candidates arrive. Once a valid pair is confirmed, the DTLS handshake starts and media can flow.

Common Signaling Transports

Because WebRTC imposes no transport requirement, the ecosystem has converged on a handful of popular options. Each has trade-offs worth understanding before you commit.

Transport Latency Complexity Best For
WebSocket Low (persistent connection) Moderate Production apps, real-time signaling
HTTP Long Polling Medium (request/response cycle) Low Environments where WebSockets are blocked
Socket.IO Low (WebSocket with fallback) Low Rapid prototyping, automatic reconnection
Firebase RTDB Low (real-time sync) Very Low Serverless demos, hackathons, MVPs
MQTT Low Moderate IoT deployments, constrained networks
gRPC Streams Low High Microservice architectures, typed contracts
Note

WebSocket is the most common transport for production WebRTC signaling. It provides full-duplex communication over a single TCP connection, which is exactly what you need for the real-time, bidirectional message flow of offer/answer/candidate exchange. The examples in this chapter use raw WebSocket, but the patterns translate directly to Socket.IO, Firebase, or any other pub/sub mechanism.

Room Concepts: Matching Peers

A signaling server needs a way to route messages between peers who want to talk. The simplest abstraction is a room—a named bucket that holds at most two participants for a 1:1 call (or N participants for a mesh conference).

The workflow is straightforward. The first peer to join a room becomes the initiator. It waits. When a second peer joins the same room, the server notifies the initiator, who then creates an offer. The room ID can be anything unique—a UUID, a human-readable slug, or a hash of two user IDs sorted alphabetically (guaranteeing the same room regardless of who joins first).

Room State Machine

A minimal room has three states: empty (no peers), waiting (one peer, the initiator), and full (two peers, negotiation in progress). When either peer disconnects, the room transitions back to waiting or empty. When both leave, the room is destroyed.

// Room state transitions
EMPTY   —[peer joins]→   WAITING
WAITING —[peer joins]→   FULL    // trigger offer creation
FULL    —[peer leaves]→  WAITING
WAITING —[peer leaves]→  EMPTY   // destroy room
FULL    —[both leave]→   EMPTY   // destroy room

A Minimal WebSocket Signaling Server

Time to build. The following Node.js server is a complete, working signaling relay. It uses the ws library (no framework overhead), implements room management, and forwards offers, answers, and ICE candidates between peers. You can run this with node server.js and connect two browser tabs to it.

const WebSocket = require('ws');
const http = require('http');

const server = http.createServer();
const wss = new WebSocket.Server({ server });

// Map of roomId -> Set of WebSocket connections
const rooms = new Map();

wss.on('connection', (ws) => {
  let currentRoom = null;

  ws.on('message', (data) => {
    let msg;
    try {
      msg = JSON.parse(data);
    } catch (e) {
      ws.send(JSON.stringify({ type: 'error', message: 'Invalid JSON' }));
      return;
    }

    switch (msg.type) {
      case 'join': {
        const roomId = msg.room;
        if (!roomId) {
          ws.send(JSON.stringify({ type: 'error', message: 'Missing room id' }));
          return;
        }

        // Create room if it doesn't exist
        if (!rooms.has(roomId)) {
          rooms.set(roomId, new Set());
        }

        const room = rooms.get(roomId);

        // Limit to 2 peers for a 1:1 call
        if (room.size >= 2) {
          ws.send(JSON.stringify({ type: 'error', message: 'Room is full' }));
          return;
        }

        currentRoom = roomId;
        room.add(ws);

        // Tell the joiner whether to create an offer
        const isInitiator = room.size === 2;
        ws.send(JSON.stringify({
          type: 'joined',
          room: roomId,
          initiator: isInitiator
        }));

        // Notify the waiting peer that someone arrived
        if (isInitiator) {
          for (const peer of room) {
            if (peer !== ws && peer.readyState === WebSocket.OPEN) {
              peer.send(JSON.stringify({ type: 'peer-joined' }));
            }
          }
        }
        break;
      }

      // Relay offer, answer, and ICE candidates to the other peer
      case 'offer':
      case 'answer':
      case 'ice-candidate': {
        if (!currentRoom || !rooms.has(currentRoom)) break;
        const room = rooms.get(currentRoom);
        for (const peer of room) {
          if (peer !== ws && peer.readyState === WebSocket.OPEN) {
            peer.send(JSON.stringify(msg));
          }
        }
        break;
      }

      default:
        ws.send(JSON.stringify({
          type: 'error',
          message: `Unknown message type: ${msg.type}`
        }));
    }
  });

  ws.on('close', () => {
    if (currentRoom && rooms.has(currentRoom)) {
      const room = rooms.get(currentRoom);
      room.delete(ws);

      // Notify remaining peer
      for (const peer of room) {
        if (peer.readyState === WebSocket.OPEN) {
          peer.send(JSON.stringify({ type: 'peer-left' }));
        }
      }

      // Clean up empty rooms
      if (room.size === 0) {
        rooms.delete(currentRoom);
      }
    }
  });
});

const PORT = process.env.PORT || 8080;
server.listen(PORT, () => {
  console.log(`Signaling server running on port ${PORT}`);
});

This server handles four message types: join (enter a room), offer (relay an SDP offer), answer (relay an SDP answer), and ice-candidate (relay an ICE candidate). Any message type other than join is simply forwarded to the other peer in the room. The server never inspects or modifies the SDP—it is a dumb relay by design.

Client-Side Signaling Integration

On the browser side, the signaling client connects to the server and wires up the message types to the appropriate RTCPeerConnection methods:

const ws = new WebSocket('ws://localhost:8080');
const pc = new RTCPeerConnection({ iceServers: [
  { urls: 'stun:stun.l.google.com:19302' }
]});

// Send ICE candidates as they are gathered
pc.onicecandidate = ({ candidate }) => {
  if (candidate) {
    ws.send(JSON.stringify({
      type: 'ice-candidate',
      candidate: candidate
    }));
  }
};

ws.onmessage = async (event) => {
  const msg = JSON.parse(event.data);

  switch (msg.type) {
    case 'peer-joined': {
      // We were waiting; now create and send an offer
      const offer = await pc.createOffer();
      await pc.setLocalDescription(offer);
      ws.send(JSON.stringify({
        type: 'offer',
        sdp: pc.localDescription
      }));
      break;
    }
    case 'offer': {
      await pc.setRemoteDescription(msg.sdp);
      const answer = await pc.createAnswer();
      await pc.setLocalDescription(answer);
      ws.send(JSON.stringify({
        type: 'answer',
        sdp: pc.localDescription
      }));
      break;
    }
    case 'answer': {
      await pc.setRemoteDescription(msg.sdp);
      break;
    }
    case 'ice-candidate': {
      await pc.addIceCandidate(msg.candidate);
      break;
    }
  }
};

// Join a room to start
ws.onopen = () => {
  ws.send(JSON.stringify({ type: 'join', room: 'my-room' }));
};

Trickle ICE vs. Vanilla ICE

There are two strategies for sending ICE candidates, and the choice affects both connection speed and signaling complexity.

Trickle ICE

Candidates are sent to the remote peer as soon as they are discovered, while gathering is still in progress. This is the default behavior in modern browsers. The advantage is speed: the remote peer can begin connectivity checks immediately, often establishing a connection before all candidates have even been gathered. The trade-off is more signaling messages—each candidate is a separate message through your server.

Vanilla ICE (Full Gathering)

All candidates are gathered before any are sent. You wait for the iceGatheringState to become "complete", then send the full SDP (which now contains all candidates as a=candidate lines) in a single message. Simpler signaling—fewer messages—but slower connection setup, because no connectivity checks can start until gathering finishes. This can add 2–5 seconds of latency.

Warning

Vanilla ICE is tempting for its simplicity, but it can cause serious delays on networks with multiple interfaces (Wi-Fi + Ethernet + VPN) or when TURN servers are slow to respond. In production, always use trickle ICE. The extra signaling messages are trivial compared to the latency savings. Vanilla ICE is acceptable only for demos or constrained environments where the signaling channel cannot handle interleaved messages.

To implement vanilla ICE, you simply wait for gathering to complete before sending the local description:

// Vanilla ICE: wait for all candidates, then send
pc.onicecandidate = ({ candidate }) => {
  if (candidate === null) {
    // Gathering complete — localDescription now has all candidates
    ws.send(JSON.stringify({
      type: 'offer',
      sdp: pc.localDescription
    }));
  }
};

The Signaling State Machine

Every RTCPeerConnection tracks a signalingState property that reflects where it is in the offer/answer negotiation. Understanding these states helps you debug failed negotiations and handle edge cases like glare (simultaneous offers).

State Meaning Transitions To
stable No offer/answer exchange in progress. This is the initial state and the state after a successful negotiation round. have-local-offer, have-remote-offer
have-local-offer A local offer has been applied via setLocalDescription(), but no answer has been received yet. stable (answer received), closed
have-remote-offer A remote offer has been applied via setRemoteDescription(), but no local answer has been created yet. stable (answer sent), closed
have-local-pranswer A provisional answer has been applied locally. Rarely used in practice. stable, closed
have-remote-pranswer A provisional answer has been received from the remote peer. Rarely used in practice. stable, closed
closed The connection has been closed. Terminal state. (none)

You can monitor state transitions with the onsignalingstatechange event handler:

pc.onsignalingstatechange = () => {
  console.log('Signaling state:', pc.signalingState);
};

Handling Glare (Simultaneous Offers)

Glare occurs when both peers create an offer at the same time—each peer is in have-local-offer when it receives the other’s offer. The perfect negotiation pattern (covered in Chapter 05) resolves this by designating one peer as “polite” (it rolls back its offer and accepts the remote one) and the other as “impolite” (it ignores the incoming offer). For now, just know that glare is a real possibility in any signaling implementation, and your code must handle it.

Error Handling: When Signaling Fails

Signaling is the most fragile part of a WebRTC connection because it depends on your server infrastructure, not on the battle-tested browser internals. Here are the failure modes you must plan for:

Server Unreachable

If the WebSocket connection drops before the offer/answer exchange completes, the peers cannot negotiate. Implement exponential backoff reconnection in your WebSocket client. Buffer unsent messages and replay them after reconnection.

Stale Offers

If the callee takes too long to respond, ICE candidates gathered by the caller may become stale (especially server-reflexive candidates whose STUN bindings expire). Set a timeout on the offer—if no answer arrives within 30 seconds, tear down the RTCPeerConnection and start fresh.

Message Ordering

WebSocket guarantees in-order delivery on a single connection, but if your signaling spans multiple hops (load balancers, message queues), messages can arrive out of order. ICE candidates arriving before the remote description is set will throw an error. Queue them and apply after setRemoteDescription() succeeds.

Malformed Messages

Always validate incoming signaling messages. A corrupted SDP string will cause setRemoteDescription() to reject with a DOMException. Wrap every signaling handler in try/catch and log failures for debugging.

A robust client-side error handling pattern looks like this:

let pendingCandidates = [];
let hasRemoteDescription = false;

async function handleSignalingMessage(msg) {
  try {
    switch (msg.type) {
      case 'offer':
        await pc.setRemoteDescription(msg.sdp);
        hasRemoteDescription = true;
        // Flush any candidates that arrived early
        for (const c of pendingCandidates) {
          await pc.addIceCandidate(c);
        }
        pendingCandidates = [];
        const answer = await pc.createAnswer();
        await pc.setLocalDescription(answer);
        ws.send(JSON.stringify({
          type: 'answer', sdp: pc.localDescription
        }));
        break;

      case 'ice-candidate':
        if (hasRemoteDescription) {
          await pc.addIceCandidate(msg.candidate);
        } else {
          // Queue until remote description is set
          pendingCandidates.push(msg.candidate);
        }
        break;
    }
  } catch (err) {
    console.error('Signaling error:', err);
  }
}
Key Takeaway

The candidate-queuing pattern above is not optional—it is essential. In trickle ICE, candidates can (and often do) arrive before the remote description. Without queuing, your connection will fail intermittently, producing the kind of bug that works on localhost and breaks in production. Always buffer early candidates.

Security Considerations

Your signaling server is a trust boundary. Everything that flows through it is unencrypted at the application layer (WebRTC encrypts the media, not the signaling). Keep these principles in mind:

  • Authenticate connections. Verify user identity before allowing a peer to join a room. A token-based approach (JWT or session cookie) is standard.
  • Validate room access. Just because a user is authenticated does not mean they should join any room. Implement authorization checks.
  • Use WSS (WebSocket Secure). Always run signaling over TLS in production. An attacker who can read signaling traffic can inject a rogue SDP offer and attempt a man-in-the-middle attack (though DTLS fingerprint verification mitigates this).
  • Rate-limit messages. A malicious client could flood the signaling server with fake candidates. Rate limiting protects both the server and the remote peer.

Putting It All Together

Signaling is the bootstrapping layer of WebRTC. It is not part of the media path—once the peer connection is established, you could shut down the signaling server and the call would continue. But without it, no connection can ever begin. Build your signaling channel to be reliable, authenticated, and fast. Keep the protocol simple: JSON messages with a type field and room-based routing. Start with the minimal server shown above, then layer on authentication, persistence, and scaling as your application demands.
