Chapter 07

Audio & Video: Capture to Render

A WebRTC call is, at its core, a media pipeline: photons hit a camera sensor, pressure waves reach a microphone, and milliseconds later those signals emerge as pixels and sound on a remote device. Between capture and render lies a chain of processing, encoding, packetization, transport, and decoding—each link precisely engineered to survive the hostile conditions of the public internet. Understanding this pipeline gives you the leverage to build calls that look sharp, sound clean, and adapt gracefully when bandwidth drops.

Media Capture: getUserMedia in Depth

Everything begins with navigator.mediaDevices.getUserMedia(). This single API call requests access to the user’s camera, microphone, or both, and returns a MediaStream containing one or more MediaStreamTrack objects. But the real power lives in the constraints object you pass to it.

Constraints are not suggestions—they are instructions to the browser’s media engine. You can specify exact values, ideal targets, and hard minimums or maximums. The browser will select the device configuration that best satisfies your constraints, or reject the promise if no configuration is possible.

getUserMedia with detailed constraints
const stream = await navigator.mediaDevices.getUserMedia({
  audio: {
    echoCancellation: { ideal: true },
    noiseSuppression: { ideal: true },
    autoGainControl: { ideal: true },
    sampleRate:        { ideal: 48000 },
    channelCount:     { ideal: 1 },
    latency:          { ideal: 0.01 }
  },
  video: {
    width:      { min: 640, ideal: 1280, max: 1920 },
    height:     { min: 480, ideal: 720,  max: 1080 },
    frameRate:  { min: 15,  ideal: 30,   max: 60 },
    facingMode: 'user'
  }
});

The constraint vocabulary is precise. An exact value is non-negotiable—the browser must match it or fail. An ideal value is a preference the browser will try to satisfy but may relax. The min and max fields define hard boundaries: the browser will never exceed them, but anything within range is acceptable. When you specify facingMode: 'user' on mobile, the browser selects the front-facing camera; 'environment' picks the rear. On desktops without multiple cameras, this constraint is quietly ignored.

Audio Processing: The Invisible Stack

Raw microphone input is rarely usable for real-time communication. Rooms echo, fans hum, and speakers feeding back into microphones create howling loops. The browser applies three critical audio processing stages before the signal ever reaches the encoder:

Echo Cancellation (AEC)

The most complex piece. AEC detects audio from the remote peer playing through the local speakers and subtracts it from the microphone signal. Without it, the remote participant hears their own voice returning with a fraction-of-a-second delay—profoundly disorienting. Modern AEC implementations use adaptive filters that model the acoustic path between speaker and microphone in real time.

Noise Suppression (NS)

Identifies and attenuates stationary background noise: air conditioning, keyboard clatter, traffic. Deep-learning models in Chrome and Firefox now handle even non-stationary noise like barking dogs or construction. The trade-off is subtle artifacts in the speaker’s voice at aggressive suppression levels.

Auto Gain Control (AGC)

Normalizes volume across speakers. A soft-spoken participant and someone shouting should both arrive at a comfortable level. AGC adjusts the microphone gain dynamically, ramping up during silence and clamping down on peaks. This prevents clipping and ensures intelligibility without manual volume adjustment.

All three are enabled by default in most browsers. You can disable them via constraints when recording music or when external audio hardware handles processing:

Disabling audio processing for music
const musicStream = await navigator.mediaDevices.getUserMedia({
  audio: {
    echoCancellation: false,
    noiseSuppression: false,
    autoGainControl:  false,
    sampleRate:       48000,
    channelCount:    2
  }
});

Video Codecs: The Compression War

Video dominates bandwidth. A raw 720p30 video stream demands roughly 660 Mbps—far beyond any residential connection. Video codecs compress that by factors of 100x to 1000x, and the choice of codec determines quality, latency, CPU cost, and compatibility. WebRTC supports four major video codecs, each with distinct characteristics.

Codec Standard Hardware Accel Compression Royalty Browser Support
VP8 RFC 6386 Limited Good Free All browsers
VP9 Pending Growing 30–50% better than VP8 Free Chrome, Firefox, Edge
H.264 ITU-T H.264 Ubiquitous Good Licensed (MPEG LA) All browsers
AV1 AOMedia Emerging 30% better than VP9 Free Chrome, partial Firefox

VP8 is the baseline. Every WebRTC implementation must support it (RFC 7742), making it the safe default. It is computationally cheap but lags behind newer codecs in compression efficiency. H.264 wins on hardware acceleration—virtually every mobile SoC and GPU has dedicated H.264 encode/decode silicon, which saves battery on phones. VP9 offers substantially better compression at higher CPU cost, making it attractive for desktop-to-desktop calls where processing power is abundant. AV1 represents the frontier: best-in-class compression, royalty-free, but encoding is still expensive and hardware support is limited to recent chipsets.

Note

You do not choose a codec in your JavaScript—codec selection happens during SDP negotiation. Each peer advertises its supported codecs in the offer/answer, and the peers converge on a mutually supported option. You can influence the priority by reordering codec entries in the SDP with RTCRtpTransceiver.setCodecPreferences(), but you cannot force a codec the remote peer does not support.

Audio Codecs: Opus Rules the Roost

While the video codec landscape is fragmented, audio in WebRTC has a clear champion.

Key Insight

Opus is the mandatory-to-implement audio codec for WebRTC (RFC 7874), and for good reason. It is a hybrid codec that seamlessly blends two compression strategies: SILK (optimized for speech at low bitrates) and CELT (optimized for music and general audio at higher bitrates). Opus adapts its bitrate from 6 kbps (narrow-band speech, barely intelligible but survivable on a 2G connection) to 510 kbps (transparent full-band stereo music). It handles sample rates from 8 kHz to 48 kHz, mono or stereo, and can switch between constant and variable bitrate mid-stream. A single codec covers conference calls, music lessons, podcasting, and accessibility narration. Opus is not just the default choice—it is, for nearly every WebRTC use case, the only choice you need.

Audio Codec Bitrate Range Latency Use Case WebRTC Status
Opus 6–510 kbps 2.5–60 ms frames Speech, music, everything Mandatory (RFC 7874)
G.711 64 kbps (fixed) Minimal PSTN interop, telephony gateways Mandatory (RFC 7874)
G.722 48–64 kbps Low Wideband telephony Optional
iLBC 13.3–15.2 kbps 25–30 ms frames Packet-loss-tolerant speech Optional

G.711 persists as a mandatory codec because it provides the bridge to traditional telephony. When a WebRTC client calls into a PSTN gateway or SIP endpoint, G.711 is the lingua franca. But for peer-to-peer browser calls, Opus is universally preferred.

The Media Pipeline: End to End

Every audio sample and video frame passes through a deterministic pipeline. Understanding each stage helps you diagnose quality problems and tune performance. The pipeline is symmetric—what the sender does to encode, the receiver undoes to decode.

Capture
Camera or microphone hardware produces raw frames or samples. The browser’s media engine reads them via platform APIs (DirectShow on Windows, AVFoundation on macOS, V4L2 on Linux) and delivers them as MediaStreamTrack objects.
Pre-Processing
Audio undergoes AEC, noise suppression, and AGC. Video may be cropped, scaled, or rotated to match the requested constraints. This stage runs in the browser’s media thread, not in JavaScript.
Encode
The processed frames are compressed by the selected codec (VP8/VP9/H.264/AV1 for video; Opus for audio). The encoder adapts its bitrate based on network feedback from the congestion controller, trading quality for reliability when bandwidth shrinks.
Packetize (RTP)
Encoded data is split into RTP packets, each with a sequence number, timestamp, and SSRC identifier. Video frames too large for a single packet are fragmented. RTCP feedback flows alongside, reporting packet loss and jitter to the sender.
Network Transit
Packets travel over the DTLS-SRTP encrypted channel established during the ICE handshake. They may traverse NATs, TURN relays, and unpredictable internet paths. Some packets arrive late; some never arrive at all.
Depacketize
The receiver’s jitter buffer reorders packets, waits for late arrivals (within bounds), and reassembles fragmented frames. Missing packets trigger NACK requests back to the sender, or FEC recovery if forward error correction is in use.
Decode
The reassembled bitstream is decompressed by the corresponding codec. Packet loss may cause visual artifacts (blocky frames, frozen regions) or audio glitches. Modern codecs include error concealment to minimize visible damage.
Render
Decoded video frames are painted to a <video> element. Decoded audio is routed to the output device via the Web Audio API or directly to the system audio stack. The pipeline ends where it began: pixels and pressure waves.

Screen Sharing: getDisplayMedia

Screen sharing uses a parallel capture API: navigator.mediaDevices.getDisplayMedia(). Unlike getUserMedia, which accesses cameras and microphones, getDisplayMedia lets the user select an entire screen, a specific application window, or a browser tab. The browser enforces a user-gesture requirement—you cannot call getDisplayMedia without a click or keyboard event triggering it.

Screen sharing with system audio
const screenStream = await navigator.mediaDevices.getDisplayMedia({
  video: {
    cursor:    'always',
    frameRate: { max: 30 }
  },
  audio: true   // capture system audio (tab audio in Chrome)
});

Screen sharing tracks behave like any other MediaStreamTrack—you can add them to an RTCPeerConnection, apply constraints, and replace them. The key difference is content type: screen content is typically high-resolution, low-motion, and text-heavy, which favors codecs and settings optimized for sharpness over temporal smoothness. Set contentHint to 'text' on the video track to guide the encoder.

Applying Constraints Mid-Call

Constraints are not locked at capture time. The applyConstraints() method on any MediaStreamTrack lets you change resolution, frame rate, or audio processing parameters while the call is live. This is essential for adaptive quality—dropping from 720p to 480p when bandwidth deteriorates, or disabling noise suppression when a user switches to music mode.

Downgrading resolution mid-call
const videoTrack = stream.getVideoTracks()[0];

// Respond to bandwidth pressure
await videoTrack.applyConstraints({
  width:     { ideal: 640 },
  height:    { ideal: 480 },
  frameRate: { max: 15 }
});

console.log('Applied:', videoTrack.getSettings());

The method returns a promise that resolves when the browser has applied the new settings (or rejects with an OverconstrainedError if the requested combination is impossible). Note that applyConstraints operates on the capture source—it changes what the camera produces, not what the encoder outputs. Encoder bitrate is controlled separately via RTCRtpSender.setParameters().

Track Manipulation: Replace, Mute, Stop

WebRTC gives you fine-grained control over individual media tracks. Three operations cover the most common scenarios:

Replacing Tracks

Switching from a camera feed to a screen share (or vice versa) without renegotiating the session is one of WebRTC’s most useful features. The RTCRtpSender.replaceTrack() method swaps the underlying media source while keeping the same RTP stream intact—no new offer/answer exchange required.

Replacing camera with screen share
const screenStream = await navigator.mediaDevices.getDisplayMedia({
  video: true
});
const screenTrack = screenStream.getVideoTracks()[0];

// Find the video sender on the peer connection
const videoSender = pc.getSenders().find(
  (s) => s.track && s.track.kind === 'video'
);

// Swap without renegotiation
await videoSender.replaceTrack(screenTrack);

// Revert when screen sharing ends
screenTrack.addEventListener('ended', async () => {
  const camStream = await navigator.mediaDevices.getUserMedia({
    video: true
  });
  await videoSender.replaceTrack(camStream.getVideoTracks()[0]);
});

Muting via track.enabled

Setting track.enabled = false mutes a track without stopping it. For video, the browser sends black frames. For audio, it sends silence. The track remains in the peer connection, the RTP stream stays active, and unmuting is instantaneous—no renegotiation, no permission prompt, no delay. This is how every “mute” button in every video conferencing app works.

Stopping Tracks

Calling track.stop() is permanent. It releases the hardware resource (camera light turns off, microphone access ends) and fires an ended event. A stopped track cannot be restarted—you must call getUserMedia again to obtain a new one. Use stop() when the user leaves a call; use enabled for momentary mute.

Warning

Never rely on track.enabled = false as a privacy guarantee. Although the browser sends silence or black frames, the track object still exists and the hardware indicator (camera LED) may remain lit in some browsers. If a user expects the camera to be truly off, call track.stop() and re-acquire when they unmute. Communicate the distinction clearly in your UI.

Canvas Capture: captureStream()

The <canvas> element’s captureStream() method generates a MediaStream from anything you can draw—WebGL scenes, 2D animations, composited video, generative art. This opens a creative pipeline: render arbitrary visuals on a canvas, capture the stream, and send it over a peer connection.

Streaming a canvas over WebRTC
const canvas = document.getElementById('render-target');
const ctx = canvas.getContext('2d');

// Draw at 30 fps
function draw() {
  ctx.fillStyle = '#0a0e1a';
  ctx.fillRect(0, 0, canvas.width, canvas.height);
  ctx.fillStyle = '#38bdf8';
  ctx.fillRect(Math.random() * canvas.width, 50, 100, 100);
  requestAnimationFrame(draw);
}
draw();

// Capture at 30 fps and add to peer connection
const canvasStream = canvas.captureStream(30);
canvasStream.getTracks().forEach(
  (track) => pc.addTrack(track, canvasStream)
);

The frame rate argument to captureStream() is a maximum—the browser will not exceed it, but may capture fewer frames if the canvas is not being updated. Passing 0 tells the browser to capture a new frame only when the canvas content changes, which is efficient for infrequent updates like whiteboard applications.

Insertable Streams: Processing in the Pipeline

The most powerful recent addition to the WebRTC media API is Insertable Streams, formally the MediaStreamTrackProcessor and MediaStreamTrackGenerator interfaces (with the Encoded Transform variant for encoded frames). These APIs let you intercept media frames at various points in the pipeline and process them in JavaScript or WebAssembly.

MediaStreamTrackProcessor consumes a MediaStreamTrack and exposes its frames as a ReadableStream. MediaStreamTrackGenerator does the reverse: it accepts a WritableStream of frames and produces a MediaStreamTrack. Between them, you can insert any transform—background blur, virtual backgrounds, frame-level encryption (end-to-end encryption for SFU architectures), watermarking, or custom video effects.

Insertable Streams: grayscale video transform
const processor = new MediaStreamTrackProcessor({
  track: videoTrack
});
const generator = new MediaStreamTrackGenerator({
  kind: 'video'
});

const transformer = new TransformStream({
  async transform(frame, controller) {
    // Read pixels, apply grayscale, write back
    const bitmap = await createImageBitmap(frame);
    const canvas = new OffscreenCanvas(
      frame.displayWidth, frame.displayHeight
    );
    const ctx = canvas.getContext('2d');
    ctx.filter = 'grayscale(100%)';
    ctx.drawImage(bitmap, 0, 0);
    frame.close();

    const newFrame = new VideoFrame(canvas, {
      timestamp: frame.timestamp
    });
    controller.enqueue(newFrame);
  }
});

processor.readable
  .pipeThrough(transformer)
  .pipeTo(generator.writable);

// Use the generator track in the peer connection
const sender = pc.getSenders().find(
  (s) => s.track?.kind === 'video'
);
await sender.replaceTrack(generator);

For encoded-frame transforms (operating on compressed data rather than raw pixels), the RTCRtpScriptTransform API lets you run a Web Worker that processes encoded frames between the encoder and packetizer (on the send side) or between the depacketizer and decoder (on the receive side). This is the foundation of end-to-end encryption in services like Google Meet and Cloudflare Calls, where the SFU can route encrypted frames without being able to read them.

Note

Insertable Streams and Encoded Transforms are still evolving. Browser support varies: Chrome has shipped both, Firefox supports Encoded Transforms, and Safari has partial support. Check window.MediaStreamTrackProcessor and RTCRtpScriptTransform before relying on them. The performance cost of per-frame JavaScript processing is non-trivial at high resolutions—offload heavy transforms to Web Workers or WebAssembly.

Putting the Pieces Together

The media pipeline in WebRTC is deep, but the API surface for controlling it is remarkably small. getUserMedia and getDisplayMedia capture. Constraints and applyConstraints shape what the camera and microphone produce. Codecs compress and decompress transparently. replaceTrack swaps sources without renegotiation. track.enabled mutes. captureStream turns any canvas into a video source. And Insertable Streams let you inject custom processing into the pipeline itself.

The most common mistake developers make is treating media as an afterthought—bolting on a getUserMedia call and hoping for the best. The reality is that media quality is the user experience. A call with perfect connectivity but bad echo cancellation is unusable. A call with beautiful video but no adaptive bitrate crumbles the moment the network dips. Master the capture-to-render pipeline, and you master the user’s perception of your application.
