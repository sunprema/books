Chapter 05

SDP & Session Negotiation

Every WebRTC connection begins with a plain-text document that looks like it was designed in 1998—because it was. The Session Description Protocol is the lingua franca that two peers use to declare what they can send, what they want to receive, and how to encrypt the whole affair. Understanding SDP is the difference between a developer who copies boilerplate and one who can diagnose a failed call by reading the wire.

Key Insight

SDP is not a negotiation protocol. It is a description format. The negotiation happens through the offer/answer model defined in RFC 3264, where one peer proposes a session configuration (the offer) and the other responds with a compatible subset (the answer). SDP is merely the envelope that carries both. This distinction matters: the format is static text, but the exchange is a stateful, ordered dance with strict rules about who speaks when.

What SDP Is

The Session Description Protocol, defined in RFC 8866 (which supersedes the original RFC 4566), is a text-based format for describing multimedia sessions. It was originally designed for multicast session announcements on the MBONE—the experimental multicast backbone of the early internet. WebRTC repurposed it because SDP already handled the hard problem of describing codecs, transport addresses, and media types in a compact, parseable format.

An SDP document is a sequence of key=value lines. There are no headers, no braces, no nesting. Each line starts with a single lowercase letter, an equals sign, and a value. Whitespace is significant. Order matters. It is brutally simple, and that simplicity is both its greatest strength and the source of most developer frustration.

Anatomy of an SDP Document

An SDP document has two sections: the session-level block (global metadata) and one or more media-level blocks (one per audio track, video track, or data channel). Here is an annotated SDP offer generated by a modern browser:

// ---- Session-level description ----
v=0                                    // Protocol version (always 0)
o=- 4618location292571 2 IN IP4 127.0.0.1  // Origin: username, session-id,
                                       //   version, network-type, addr-type, addr
s=-                                    // Session name (dash = unspecified)
t=0 0                                  // Timing: start and stop (0 0 = permanent)
a=group:BUNDLE 0 1 2                 // Multiplex all media on one transport
a=extmap-allow-mixed                  // Allow mixed RTP header extensions
a=msid-semantic: WMS stream0          // Media-stream identification

// ---- First media-level block: audio ----
m=audio 9 UDP/TLS/RTP/SAVPF 111 63 9 0 8  // Media type, port, proto, payload types
c=IN IP4 0.0.0.0                      // Connection address (placeholder; ICE decides)
a=rtcp:9 IN IP4 0.0.0.0               // RTCP address (also placeholder)
a=ice-ufrag:aR7x                     // ICE credentials (short-term)
a=ice-pwd:k9P3nR7fJ2xL5wQm8vYt       // ICE password
a=ice-options:trickle                 // Supports trickle ICE
a=fingerprint:sha-256 A1:B2:C3:...   // DTLS certificate fingerprint
a=setup:actpass                       // DTLS role: will act as client or server
a=mid:0                                // Media ID (matches BUNDLE group)
a=sendrecv                             // Direction: send AND receive
a=rtpmap:111 opus/48000/2             // Payload 111 = Opus, 48 kHz, stereo
a=fmtp:111 minptime=10;useinbandfec=1 // Opus parameters
a=rtpmap:9 G722/8000                   // Fallback codec: G.722
a=rtpmap:0 PCMU/8000                   // Fallback codec: G.711 mu-law

// ---- Second media-level block: video ----
m=video 9 UDP/TLS/RTP/SAVPF 96 97 98 99  // Video payload types
a=mid:1
a=sendrecv
a=rtpmap:96 VP8/90000                  // VP8 at 90 kHz clock rate
a=rtpmap:97 VP9/90000                  // VP9
a=rtpmap:98 H264/90000                 // H.264
a=fmtp:98 profile-level-id=42e01f     // H.264 Constrained Baseline
a=rtpmap:99 AV1/90000                  // AV1 (newer browsers)
a=rtcp-fb:96 nack                     // VP8 supports NACK for retransmission
a=rtcp-fb:96 nack pli                 // VP8 supports Picture Loss Indication
a=rtcp-fb:96 goog-remb                // VP8 supports receiver-estimated bitrate

Every line carries weight. The m= line declares a media section and lists the payload types the offerer supports, in preference order. The a=rtpmap lines map those numeric payload types to human-readable codec names. The a=fmtp lines carry codec-specific parameters. The a=fingerprint line is the DTLS certificate hash that prevents man-in-the-middle attacks. Remove any one of these, and the negotiation breaks.

Common SDP Attributes

The following table covers the attributes you will encounter most often when reading browser-generated SDP. Familiarity with these will save you hours of debugging.

Attribute Level Purpose
a=group:BUNDLE Session Multiplexes multiple media types onto a single transport (one port for audio, video, and data).
a=mid Media Media identification tag. Referenced by the BUNDLE group to associate media sections.
a=rtpmap Media Maps a payload type number to a codec name and clock rate (e.g., 111 opus/48000/2).
a=fmtp Media Format-specific parameters for a codec (e.g., H.264 profile-level-id, Opus FEC settings).
a=sendrecv Media Direction: peer will both send and receive media on this track.
a=sendonly Media Peer will send but not receive. Common for screen-sharing or broadcast scenarios.
a=recvonly Media Peer will receive but not send. Used by SFU subscribers.
a=inactive Media Track is paused. No media flows in either direction, but the media section stays in the SDP.
a=ice-ufrag / a=ice-pwd Media Short-term ICE credentials used during connectivity checks.
a=fingerprint Media DTLS certificate fingerprint for authenticating the encrypted channel.
a=setup Media DTLS handshake role: actpass (offer), active or passive (answer).
a=rtcp-fb Media RTCP feedback mechanisms: nack, pli, fir, goog-remb, transport-cc.
a=extmap Media RTP header extension mapping. Carries metadata like absolute timestamps and audio levels.
a=ssrc Media Synchronization source identifier. Associates RTP streams with labels and stream IDs.
a=candidate Media ICE candidate embedded in the SDP (used with vanilla ICE or after gathering completes).

What Offers Describe

An SDP offer is a declaration of capability. The offerer lists everything it is willing to support: every codec it can encode and decode, every RTP header extension it understands, every RTCP feedback mechanism it can process. The payload type numbers in the m= line are ordered by preference—the first codec listed is the one the offerer would most like to use.

The offer also declares the media direction for each track. The four options are sendrecv (bidirectional), sendonly (I will transmit but do not expect to receive), recvonly (I want to receive but will not transmit), and inactive (this track is on hold). Direction attributes are how you model different topologies: a broadcast sender uses sendonly, an SFU subscriber uses recvonly, and a standard video call uses sendrecv on both sides.

What Answers Describe

An SDP answer is a declaration of agreement. The answerer examines the offer and responds with a subset: a single chosen codec per media section (or sometimes a small set), a compatible direction, and its own ICE credentials and DTLS fingerprint. The answerer cannot introduce new codecs that were not in the offer. It cannot change the order of media sections. It can only accept, reject, or restrict what was proposed.

If the offerer proposed sendrecv and the answerer can only receive, the answer changes the direction to recvonly. If the offerer listed VP8, VP9, H.264, and AV1 as video codecs, the answerer picks the one it prefers (or supports) and drops the rest. This asymmetry is by design: the offerer casts a wide net, the answerer narrows the catch.

Codec Negotiation

Codec selection is the most consequential decision SDP negotiation makes. The choice affects video quality, CPU usage, bandwidth consumption, and hardware-acceleration availability. Here is what the modern landscape looks like:

Audio: Opus

Opus is the mandatory-to-implement audio codec for WebRTC (RFC 7874). It handles everything from narrowband voice at 6 kbit/s to full-band stereo music at 510 kbit/s. Every browser supports it. In practice, Opus is always the first choice; fallbacks like G.711 or G.722 exist only for interoperability with legacy telephony systems.

Video: VP8

VP8 is the mandatory-to-implement video codec. It is universally supported, well-understood, and free of patent encumbrances. It is also showing its age: compression efficiency lags behind newer codecs by 20–40% at equivalent quality. Still a safe default when you need maximum compatibility.

Video: VP9

VP9 offers substantially better compression than VP8, particularly at lower bitrates. It supports Scalable Video Coding (SVC), which SFUs use to serve different quality layers to different subscribers without transcoding. Chrome and Firefox support it well; Safari support is limited.

Video: H.264

H.264 is the most widely deployed video codec on the planet. Its key advantage in WebRTC is hardware acceleration—virtually every mobile device has an H.264 encoder and decoder baked into silicon. The trade-off is patent licensing (though browser vendors handle this). Critical for interoperability with SIP/VoIP systems.

Video: AV1

AV1 is the newest contender. It achieves 30–50% better compression than VP9 and is royalty-free. Browser support is growing: Chrome 90+, Firefox 98+, and Safari 17+ include AV1 for WebRTC. The main drawback is encode cost—AV1 encoding is CPU-intensive without hardware acceleration, which is still rolling out across device generations.

During negotiation, the offerer lists all video codecs it supports in the m=video line. The answerer selects one (or more, if the implementation supports codec switching mid-stream). If neither peer supports a common codec, the media section is rejected—the m= line in the answer will have a port of 0, indicating that media type will not flow.

The Offer/Answer Lifecycle

The JavaScript API exposes four methods that drive the SDP exchange. Understanding the exact sequence—and why the order cannot be rearranged—is essential.

1. createOffer()
The offerer’s browser inspects the RTCPeerConnection—its tracks, transceivers, data channels—and generates an SDP offer describing all available media. The offer is returned as an RTCSessionDescription object but is not yet applied.
2. setLocalDescription(offer)
The offerer applies the offer to its own connection. This transitions the signaling state to have-local-offer and triggers ICE candidate gathering. The SDP string is now ready to be sent through the signaling channel.
3. setRemoteDescription(offer)
The answerer receives the offer and applies it as the remote description. This tells the answerer’s RTCPeerConnection what the offerer wants. Signaling state moves to have-remote-offer.
4. createAnswer()
The answerer’s browser generates a compatible response: selecting codecs, confirming directions, providing its own ICE credentials and DTLS fingerprint.
5. setLocalDescription(answer)
The answerer applies its answer locally. This starts ICE gathering on the answerer’s side. The SDP answer is sent back through the signaling channel.
6. setRemoteDescription(answer)
The offerer receives and applies the answer. Both sides are now in the stable signaling state. ICE connectivity checks proceed, and once a valid pair is found, the DTLS handshake begins and media flows.
Note

Since 2019, browsers support implicit description setting. Calling setLocalDescription() with no arguments is equivalent to calling createOffer() or createAnswer() (depending on the signaling state) and then applying the result. This shorthand simplifies code but hides the two-step process. Use the explicit form when you need to inspect or log the SDP before applying it.

The Perfect Negotiation Pattern

In a naive implementation, both peers might create an offer simultaneously—a condition called glare. Each peer is in have-local-offer when it receives the other’s offer, and the setRemoteDescription() call fails because the state machine does not permit setting a remote offer on top of a local offer (in non-rollback mode). The Perfect Negotiation pattern, documented in the W3C spec, solves this by assigning asymmetric roles.

One peer is designated polite: when glare occurs, it rolls back its own offer and accepts the incoming one. The other peer is impolite: it ignores the incoming offer and waits for the polite peer to accept its offer instead. The role assignment is arbitrary—flip a coin, use alphabetical user IDs, or let the signaling server decide. What matters is that exactly one peer is polite.

// Perfect Negotiation — full implementation
// Assign roles: exactly one peer must be polite
const polite = /* true on one side, false on the other */ true;

let makingOffer = false;
let ignoreOffer = false;

// Whenever the browser decides renegotiation is needed
pc.onnegotiationneeded = async () => {
  try {
    makingOffer = true;
    await pc.setLocalDescription();   // implicit createOffer
    signaling.send({
      type: 'description',
      sdp: pc.localDescription
    });
  } catch (err) {
    console.error('Offer creation failed:', err);
  } finally {
    makingOffer = false;
  }
};

// Handle incoming signaling messages
signaling.onmessage = async ({ data: { type, sdp, candidate } }) => {
  try {
    if (type === 'description') {
      // Detect glare: we have a local offer AND an offer just arrived
      const offerCollision =
        sdp.type === 'offer' &&
        (makingOffer || pc.signalingState !== 'stable');

      ignoreOffer = !polite && offerCollision;
      if (ignoreOffer) {
        console.log('Impolite peer: ignoring colliding offer');
        return;                          // impolite peer wins
      }

      // Polite peer rolls back its own offer and accepts the remote one
      await pc.setRemoteDescription(sdp);

      if (sdp.type === 'offer') {
        await pc.setLocalDescription();  // implicit createAnswer
        signaling.send({
          type: 'description',
          sdp: pc.localDescription
        });
      }
    } else if (type === 'candidate') {
      try {
        await pc.addIceCandidate(candidate);
      } catch (err) {
        if (!ignoreOffer) throw err;    // suppress if we ignored the offer
      }
    }
  } catch (err) {
    console.error('Signaling handler error:', err);
  }
};

// ICE candidates flow normally
pc.onicecandidate = ({ candidate }) => {
  signaling.send({ type: 'candidate', candidate });
};

The elegance of this pattern is that both peers run identical code except for the value of the polite boolean. The polite peer’s setRemoteDescription() call implicitly triggers a rollback of its pending local offer (modern browsers handle this via the “implicit rollback” behavior added to the spec). The impolite peer simply returns early, secure in the knowledge that its own offer will be answered.

Key Insight

Perfect Negotiation is not optional for production applications. Any system where renegotiation can happen—adding a screen-share track, toggling video, changing codecs mid-call—is vulnerable to glare. The pattern costs you one boolean and a few extra lines of code. Skipping it costs you intermittent call failures that only surface under real-world timing conditions.

Common SDP Gotchas

SDP’s text-based simplicity invites a particular class of mistakes. These are the traps that catch even experienced developers:

  • Media section ordering. The answer must contain media sections in the same order as the offer. If the offer has m=audio then m=video, the answer must follow that order. Swapping them causes silent failures where audio routes to the video decoder.
  • Payload type collisions. Different browsers may assign different numeric payload types to the same codec. Always match codecs by the a=rtpmap name, never by payload type number alone.
  • Profile-level-id mismatches (H.264). Two peers may both support H.264 but with incompatible profiles. Constrained Baseline (42e01f) is the safe choice; High profile (640c1f) may not be available on all mobile hardware.
  • Missing BUNDLE. Without a=group:BUNDLE, the browser opens a separate transport (and port) for each media section. This multiplies ICE candidate gathering time and NAT traversal complexity.
  • DTLS role confusion. The offer must use a=setup:actpass. The answer must choose either active or passive. Getting this wrong prevents the DTLS handshake from completing, resulting in a connected ICE state but no media.
Warning

SDP munging—directly editing the SDP string before passing it to setLocalDescription() or setRemoteDescription()—is dangerous and increasingly unsupported. It was once common practice to reorder codecs, force bitrate caps, or remove unwanted media sections by splicing SDP text with string operations. This approach is fragile: a single misplaced newline or a deleted attribute can silently break encryption, disable retransmission, or cause codec negotiation to fail. Worse, browser vendors have begun tightening SDP validation, meaning munged SDP that worked in Chrome 90 may be rejected in Chrome 120. Use the Transceiver API (RTCRtpTransceiver.setCodecPreferences()) to influence codec order, RTCRtpSender.setParameters() to control bitrate, and addTransceiver() with direction options to control media flow. If you must munge SDP for a case the API does not yet cover, isolate the mutation behind a well-tested utility function, log the before-and-after SDP for debugging, and treat it as tech debt to be replaced when the standards-based API catches up.

Renegotiation

A WebRTC session is not frozen at connection time. Tracks can be added (a user turns on their camera mid-call), removed (a user mutes video), or replaced (switching from camera to screen share). Each of these changes triggers a new offer/answer round—called renegotiation—on the existing RTCPeerConnection.

The browser signals that renegotiation is needed by firing the negotiationneeded event. Your code should respond by creating a new offer and running the full lifecycle again. The Perfect Negotiation pattern handles this gracefully, because it treats every negotiationneeded event identically regardless of whether it is the first negotiation or the fifteenth.

One subtlety: renegotiation does not restart ICE. The existing ICE transport is reused unless you explicitly call restartIce(). This means renegotiation is fast—no new STUN/TURN round trips—but it also means a network change (Wi-Fi to cellular) requires a separate ICE restart, not just renegotiation.

Inspecting SDP in the Wild

When debugging a failed connection, the SDP is your primary diagnostic artifact. Chrome’s chrome://webrtc-internals page captures every SDP offer and answer in real time, along with ICE candidates, codec statistics, and bitrate graphs. Firefox offers a similar tool at about:webrtc. For programmatic inspection, attach a listener to the signaling state and log the descriptions:

// Log every SDP exchange for debugging
pc.addEventListener('signalingstatechange', () => {
  console.log('[signalingState]', pc.signalingState);
  if (pc.localDescription) {
    console.log('[localDescription]', pc.localDescription.sdp);
  }
  if (pc.remoteDescription) {
    console.log('[remoteDescription]', pc.remoteDescription.sdp);
  }
});

Read the SDP. Read it slowly. Every a= line is there for a reason, and the absence of an expected line is usually the clue that leads to the root cause.

Summary

SDP is an unglamorous format doing the most critical job in a WebRTC connection: telling both peers exactly what to expect from each other. The offer describes capability; the answer declares compatibility. Codec negotiation selects the best common ground from VP8 through AV1, Opus through G.711. The Perfect Negotiation pattern ensures glare never derails a session. And the lifecycle—createOffer, setLocalDescription, setRemoteDescription, createAnswer—is a state machine that must be followed in order, every time. Master SDP, and you master the handshake that makes real-time communication possible.
