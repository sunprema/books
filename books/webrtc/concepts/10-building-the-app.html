Chapter 10

Building a Complete App

You have the theory. You understand ICE, SDP, DTLS, and signaling as individual concepts. Now it is time to wire them together into a working product—a 1:1 video chat application you can open in two browser tabs and use to talk to yourself (the loneliest, most satisfying test in all of real-time development). This chapter is a guided build from zero to a functional app, with every line of client code shown, every error mode addressed, and every UI control explained.

Key Insight

A complete WebRTC application has three cooperating layers: a signaling server that relays offers, answers, and ICE candidates between peers; a STUN/TURN configuration that helps peers discover their public addresses and relay media when direct connections fail; and client-side JavaScript that orchestrates media capture, peer connection setup, UI controls, and error recovery. None of these layers is complex in isolation. The challenge is wiring them together correctly and handling the edge cases that emerge when real networks, real browsers, and real users get involved.

Architecture Overview

Before touching code, understand the topology. Our application consists of three pieces running across two machines (or two tabs on one machine for testing).

Component Role Technology
Signaling Server Relays SDP offers/answers and ICE candidates between peers. Manages room membership. Node.js + WebSocket (the server from Chapter 4)
STUN/TURN Servers Help peers discover their public IP (STUN) and relay media when direct paths fail (TURN). Google public STUN; self-hosted or provider TURN
Client Application Captures local media, creates RTCPeerConnection, manages UI controls, renders remote video. Vanilla JavaScript + WebRTC API

The signaling server is the one from Chapter 4—a lightweight WebSocket relay that routes JSON messages by room ID. We reuse it here without modification. The client application is where all the new work lives: it captures the camera, creates the peer connection, negotiates the session, renders remote media, and gives the user controls for mute, camera toggle, and hang-up.

Step-by-Step: Building the 1:1 Video Chat

What follows is the full construction sequence. Each step builds on the last, and by the end you will have a complete, working application. The signaling server is already in place from Chapter 4; we focus entirely on the client.

Step 1 · Connect to Signaling
Open a WebSocket to the signaling server. Join a room by name. When the server responds with joined, store whether you are the initiator. When peer-joined arrives, you know it is time to create an offer.
Step 2 · Capture Local Media
Call navigator.mediaDevices.getUserMedia() requesting audio and video. Attach the returned MediaStream to a local <video> element so the user sees their own camera feed.
Step 3 · Create RTCPeerConnection
Instantiate the peer connection with an iceServers array containing STUN (and optionally TURN) URLs. Wire up event handlers: onicecandidate, ontrack, oniceconnectionstatechange, onnegotiationneeded.
Step 4 · Add Local Tracks
Iterate over the local stream’s tracks and call pc.addTrack(track, stream) for each. This tells the peer connection what media to offer to the remote peer.
Step 5 · Offer / Answer Exchange
The initiator calls createOffer(), sets the local description, and sends the SDP through signaling. The receiver sets the remote description, calls createAnswer(), sets its local description, and sends the answer back.
Step 6 · Exchange ICE Candidates
As each peer gathers candidates, it sends them via the signaling channel. The remote peer feeds them into addIceCandidate(). Candidates that arrive before the remote description is set are queued and flushed once it is.
Step 7 · Render Remote Media
The ontrack callback fires when the remote peer’s media arrives. Attach the received stream to a remote <video> element. The call is now live.

ICE Server Configuration

The iceServers array you pass to RTCPeerConnection determines how peers discover network paths to each other. For localhost testing, you technically need nothing—both tabs share the same host candidates. For anything beyond that, you need at minimum a STUN server, and for production reliability, a TURN server.

const iceConfig = {
  iceServers: [
    // Public STUN server (free, no auth)
    { urls: 'stun:stun.l.google.com:19302' },

    // TURN server (required for symmetric NATs)
    {
      urls: 'turn:turn.example.com:3478',
      username: 'user',
      credential: 'pass'
    }
  ]
};

In the full code below, we use Google’s public STUN server for simplicity. When you deploy to production, add a TURN server—roughly 10–15% of real-world connections require relay to succeed, and that number climbs higher on mobile networks and behind corporate firewalls.

The Complete Client Code

Here is the entire client-side JavaScript for our 1:1 video chat application. This is not a sketch or a fragment—it is the full implementation, ready to drop into an HTML page with two <video> elements (#localVideo and #remoteVideo) and three buttons (#muteBtn, #camBtn, #hangupBtn). It assumes the signaling server from Chapter 4 is running on the same host.

client.js — Complete 1:1 Video Chat Client
// ── Configuration ──────────────────────────────────────────

const SIGNALING_URL = 'ws://localhost:8080';
const ROOM_ID       = 'demo-room';

const ICE_SERVERS = [
  { urls: 'stun:stun.l.google.com:19302' },
  { urls: 'stun:stun1.l.google.com:19302' }
];

// ── DOM References ─────────────────────────────────────────

const localVideo  = document.getElementById('localVideo');
const remoteVideo = document.getElementById('remoteVideo');
const muteBtn     = document.getElementById('muteBtn');
const camBtn      = document.getElementById('camBtn');
const hangupBtn   = document.getElementById('hangupBtn');

// ── State ──────────────────────────────────────────────────

let ws;                          // WebSocket to signaling server
let pc;                          // RTCPeerConnection
let localStream;                 // local MediaStream
let pendingCandidates = [];      // ICE candidates that arrive early
let hasRemoteDesc    = false;   // tracks setRemoteDescription state
let isMuted          = false;   // audio mute toggle
let isCamOff         = false;   // camera toggle

// ── 1. Get User Media ──────────────────────────────────────

async function startMedia() {
  try {
    localStream = await navigator.mediaDevices.getUserMedia({
      video: { width: { ideal: 1280 }, height: { ideal: 720 } },
      audio: true
    });
    localVideo.srcObject = localStream;
  } catch (err) {
    if (err.name === 'NotAllowedError') {
      showError('Camera/mic permission denied. Grant access and reload.');
    } else if (err.name === 'NotFoundError') {
      showError('No camera or microphone found on this device.');
    } else {
      showError(`Media error: ${err.message}`);
    }
    throw err;
  }
}

// ── 2. Create Peer Connection ──────────────────────────────

function createPeerConnection() {
  pc = new RTCPeerConnection({ iceServers: ICE_SERVERS });

  // Send ICE candidates to remote peer via signaling
  pc.onicecandidate = ({ candidate }) => {
    if (candidate) {
      send({ type: 'ice-candidate', candidate: candidate });
    }
  };

  // Render remote media when tracks arrive
  pc.ontrack = (event) => {
    if (remoteVideo.srcObject !== event.streams[0]) {
      remoteVideo.srcObject = event.streams[0];
      console.log('Remote stream attached');
    }
  };

  // Monitor connection state for disconnection / failure
  pc.oniceconnectionstatechange = () => {
    console.log('ICE connection state:', pc.iceConnectionState);

    switch (pc.iceConnectionState) {
      case 'disconnected':
        console.warn('Peer disconnected — waiting for recovery...');
        break;
      case 'failed':
        console.error('ICE failed — attempting restart');
        attemptIceRestart();
        break;
      case 'closed':
        hangUp();
        break;
    }
  };

  // Add local tracks to the connection
  for (const track of localStream.getTracks()) {
    pc.addTrack(track, localStream);
  }
}

// ── 3. Signaling via WebSocket ─────────────────────────────

function connectSignaling() {
  ws = new WebSocket(SIGNALING_URL);

  ws.onopen = () => {
    console.log('Connected to signaling server');
    send({ type: 'join', room: ROOM_ID });
  };

  ws.onmessage = async (event) => {
    const msg = JSON.parse(event.data);
    await handleSignalingMessage(msg);
  };

  ws.onclose = () => {
    console.warn('Signaling connection lost');
  };

  ws.onerror = (err) => {
    console.error('Signaling error:', err);
  };
}

function send(msg) {
  if (ws && ws.readyState === WebSocket.OPEN) {
    ws.send(JSON.stringify(msg));
  }
}

// ── 4. Handle Signaling Messages ───────────────────────────

async function handleSignalingMessage(msg) {
  try {
    switch (msg.type) {

      // Server tells us a peer arrived — we create the offer
      case 'peer-joined': {
        createPeerConnection();
        const offer = await pc.createOffer();
        await pc.setLocalDescription(offer);
        send({ type: 'offer', sdp: pc.localDescription });
        break;
      }

      // We are the second peer — set remote, create answer
      case 'joined': {
        if (msg.initiator) {
          // We are the second peer; wait for the offer
          createPeerConnection();
        }
        break;
      }

      // Incoming offer from the remote peer
      case 'offer': {
        if (!pc) createPeerConnection();
        await pc.setRemoteDescription(new RTCSessionDescription(msg.sdp));
        hasRemoteDesc = true;
        flushCandidates();

        const answer = await pc.createAnswer();
        await pc.setLocalDescription(answer);
        send({ type: 'answer', sdp: pc.localDescription });
        break;
      }

      // Incoming answer from the remote peer
      case 'answer': {
        await pc.setRemoteDescription(new RTCSessionDescription(msg.sdp));
        hasRemoteDesc = true;
        flushCandidates();
        break;
      }

      // Incoming ICE candidate
      case 'ice-candidate': {
        const candidate = new RTCIceCandidate(msg.candidate);
        if (hasRemoteDesc && pc) {
          await pc.addIceCandidate(candidate);
        } else {
          pendingCandidates.push(candidate);
        }
        break;
      }

      // Remote peer left the room
      case 'peer-left': {
        hangUp();
        console.log('Remote peer left the call');
        break;
      }
    }
  } catch (err) {
    console.error('Error handling signaling message:', err);
  }
}

// Flush candidates that arrived before the remote description
async function flushCandidates() {
  for (const c of pendingCandidates) {
    await pc.addIceCandidate(c);
  }
  pendingCandidates = [];
}

// ── 5. UI Controls ────────────────────────────────────────

muteBtn.addEventListener('click', () => {
  isMuted = !isMuted;
  localStream.getAudioTracks().forEach(t => { t.enabled = !isMuted; });
  muteBtn.textContent = isMuted ? 'Unmute' : 'Mute';
});

camBtn.addEventListener('click', () => {
  isCamOff = !isCamOff;
  localStream.getVideoTracks().forEach(t => { t.enabled = !isCamOff; });
  camBtn.textContent = isCamOff ? 'Camera On' : 'Camera Off';
});

hangupBtn.addEventListener('click', () => {
  hangUp();
  send({ type: 'leave' });
});

// ── 6. Hang Up & Cleanup ──────────────────────────────────

function hangUp() {
  if (pc) {
    pc.close();
    pc = null;
  }
  remoteVideo.srcObject = null;
  hasRemoteDesc = false;
  pendingCandidates = [];
}

// ── 7. ICE Restart (Reconnection) ─────────────────────────

async function attemptIceRestart() {
  if (!pc) return;
  try {
    const offer = await pc.createOffer({ iceRestart: true });
    await pc.setLocalDescription(offer);
    send({ type: 'offer', sdp: pc.localDescription });
    console.log('ICE restart offer sent');
  } catch (err) {
    console.error('ICE restart failed:', err);
    hangUp();
  }
}

// ── 8. Error Display Helper ───────────────────────────────

function showError(message) {
  const el = document.getElementById('errorDisplay');
  if (el) { el.textContent = message; el.hidden = false; }
  console.error(message);
}

// ── 9. Boot Sequence ──────────────────────────────────────

(async function init() {
  await startMedia();
  connectSignaling();
})();

How the Call Setup Flows

Once both peers have joined the room and the code above is running, the call setup proceeds through a precise sequence of events. The following flow shows every message and state transition, from the moment the second peer joins until media is flowing.

Peer A joins room
Peer A opens the page, captures local media, connects to the signaling server, and sends { type: "join", room: "demo-room" }. The server responds with { type: "joined", initiator: false }. Peer A waits.
Peer B joins room
Peer B opens the page in a second tab, captures media, and sends a join message. The server responds to Peer B with { type: "joined", initiator: true } and sends Peer A the peer-joined event.
Peer A → Offer
On receiving peer-joined, Peer A creates an RTCPeerConnection, adds local tracks, calls createOffer(), sets the local description, and sends the SDP offer through signaling.
Peer B → Answer
Peer B receives the offer, sets it as the remote description, creates an answer, sets the local description, and sends the SDP answer back. Both peers now have matching session descriptions.
ICE Candidates (both directions)
Both peers fire onicecandidate events as they discover host, server-reflexive, and relay candidates. Each candidate is sent via signaling to the other peer and applied with addIceCandidate().
DTLS Handshake + Media Flow
Once ICE connectivity checks succeed, the DTLS handshake establishes encryption. SRTP media begins flowing. The ontrack handler fires on both peers, and the remote video appears. The call is live.

UI Controls: Mute, Camera, Hang Up

The three UI controls in our application map directly to track manipulation on the local MediaStream. This is one of the more elegant aspects of the WebRTC API: you do not need to renegotiate the session to mute audio or disable video. You simply toggle the enabled property on the relevant track.

Control Action Effect on Remote Peer
Mute / Unmute Sets audioTrack.enabled = false Remote peer hears silence. The track remains in the session; no renegotiation required.
Camera Off / On Sets videoTrack.enabled = false Remote peer sees a black frame. The video track stays active but sends no pixel data.
Hang Up Calls pc.close() and clears remote video The peer connection is torn down. The signaling server notifies the remote peer via peer-left.

Setting track.enabled = false is distinct from calling track.stop(). The former is reversible—toggle it back to true and audio/video resumes instantly. The latter permanently ends the track, turns off the camera indicator light, and requires a new getUserMedia() call to restart. For mute and camera toggle, always use enabled.

Reconnection and ICE Restart

Network conditions change. A user walks between Wi-Fi access points. A cellular tower hands off. A brief routing disruption drops packets for two seconds. When this happens, the ICE connection state transitions from connected to disconnected. If connectivity returns quickly, the state recovers on its own. If it does not, the state eventually moves to failed.

An ICE restart is the protocol-level mechanism for recovering from failure without tearing down the entire peer connection. You create a new offer with the iceRestart flag set to true. This tells the browser to generate fresh ICE credentials and gather new candidates, while preserving the existing DTLS association and media session. The remote peer receives the new offer, creates a new answer, and both peers run a new round of connectivity checks.

ICE Restart — Triggered on Connection Failure
const offer = await pc.createOffer({ iceRestart: true });
await pc.setLocalDescription(offer);
send({ type: 'offer', sdp: pc.localDescription });

The key detail: ICE restart reuses the existing RTCPeerConnection object. You do not close and recreate it. The DTLS session, the track bindings, the data channels—everything survives. Only the ICE layer resets. This makes recovery fast and seamless when it works. When it does not (the remote peer has truly vanished), the state will fail again, and you should fall back to a full hang-up and rejoin.

Error Handling

A production WebRTC application must handle every failure mode gracefully. Errors can originate from three layers: media capture, signaling, and the peer connection itself.

Error Cause Recovery
NotAllowedError User denied camera/mic permission Show a clear message explaining how to re-grant permissions in browser settings. Cannot proceed without user action.
NotFoundError No camera or microphone available Offer audio-only or video-only fallback. Modify getUserMedia constraints to request only available devices.
NotReadableError Device in use by another application Prompt the user to close other apps using the camera. Retry after a delay.
WebSocket close/error Signaling server unreachable or crashed Implement exponential backoff reconnection. Buffer unsent messages. An existing call survives signaling loss—only new negotiations fail.
ICE state failed No viable network path between peers Attempt ICE restart. If restart fails, inform the user and offer to retry the call. Check that TURN is configured—most failures stem from missing relay servers.
setRemoteDescription rejects Malformed or incompatible SDP Log the full SDP for debugging. This usually indicates a version mismatch or corrupted signaling message. Wrap all signaling handlers in try/catch.
Warning

The most common mistakes when building your first WebRTC app: (1) Calling addIceCandidate() before setRemoteDescription()—this throws an error that kills the connection silently. Always queue early candidates. (2) Forgetting to add tracks before creating the offer—the resulting SDP will have no media lines, and the remote peer will receive nothing. (3) Not configuring TURN servers—your app works on localhost and fails for any two users behind different NATs. (4) Calling track.stop() instead of track.enabled = false for mute—this kills the track permanently and turns off the camera light, confusing users when they try to unmute.

Testing with Two Tabs

The simplest way to test a WebRTC application is to open two tabs in the same browser, both pointed at your local server. This works because each tab gets its own RTCPeerConnection, its own media stream, and its own WebSocket connection. The signaling server sees them as two independent peers.

Note

Testing in two tabs on localhost is convenient but does not exercise the full ICE stack. Both tabs share the same host candidates (same machine, same network interfaces), so ICE connectivity checks succeed trivially. You will never see server-reflexive or relay candidates in this configuration. To test STUN/TURN behavior, deploy to two different machines (or use browser flags to force relay-only mode: iceTransportPolicy: "relay" in the RTCPeerConnection configuration). For a quick smoke test, however, two tabs are invaluable—you can verify the entire offer/answer/candidate flow, see both video feeds, and test mute/unmute in under a minute.

A minimal HTML page to host the client code looks like this:

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>Video Chat</title>
  <style>
    video { width: 45%; background: #000; }
  </style>
</head>
<body>
  <video id="localVideo" autoplay muted playsinline></video>
  <video id="remoteVideo" autoplay playsinline></video>
  <div>
    <button id="muteBtn">Mute</button>
    <button id="camBtn">Camera Off</button>
    <button id="hangupBtn">Hang Up</button>
  </div>
  <p id="errorDisplay" hidden style="color:red"></p>
  <script src="client.js"></script>
</body>
</html>

Serve both the HTML page and the signaling server from the same host. Open two tabs, and you should see your own camera feed in both. Within a second or two, the remote video will appear in each tab as the peer connection completes. Open the browser console to watch ICE state transitions and signaling messages flow.

From Demo to Production

The application above is a fully working 1:1 video chat. To take it from demo to production, you would add: authentication on the signaling server (reject unauthenticated WebSocket connections), TURN server credentials fetched from your backend (never hardcode long-lived credentials in client-side code), UI feedback for connection states (a spinner during ICE negotiation, a banner when disconnected), and graceful degradation when media devices are unavailable (fall back to audio-only, or display a message explaining the problem).

But the core is here. Every production WebRTC application—from telehealth platforms to live-streaming tools to collaborative whiteboards—runs the same sequence you just built: capture media, create a peer connection, exchange offers and answers through a signaling channel, trickle ICE candidates, and render the remote stream. The protocols do the heavy lifting. Your job is to wire them together correctly and handle failure gracefully. You now know how.
