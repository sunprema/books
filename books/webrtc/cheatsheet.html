Quick Reference

The 30-Second Cheatsheet

The mental model

  • WebRTC = peer-to-peer audio, video, and data between browsers, no plugins. Three core APIs: getUserMedia, RTCPeerConnection, RTCDataChannel.
  • Signaling is the out-of-band channel (WebSocket, HTTP, carrier pigeon) used to exchange offers, answers, and ICE candidates before media can flow.
  • ICE finds a network path. STUN discovers your public IP. TURN relays when direct paths fail.
  • Media is always encrypted (DTLS-SRTP). You cannot turn encryption off.

Connection setup sequence

StepAPI / Action
1getUserMedia(constraints) → local MediaStream
2new RTCPeerConnection(config) with iceServers
3pc.addTrack(track, stream) for each local track
4Caller: pc.createOffer() → pc.setLocalDescription(offer)
5Send offer via signaling; callee: pc.setRemoteDescription(offer)
6Callee: pc.createAnswer() → pc.setLocalDescription(answer)
7Send answer via signaling; caller: pc.setRemoteDescription(answer)
8Exchange ICE candidates via onicecandidate ↔ addIceCandidate()
9Remote tracks arrive on pc.ontrack → attach to <video>

Codecs

  • Audio: Opus — adaptive 6–510 kbps, mandatory in WebRTC, handles speech and music. Typical: ~40 kbps for voice.
  • Video: VP8 (baseline, wide support) · VP9 (30–50% better compression) · H.264 (hardware acceleration, mobile friendly) · AV1 (newest, best compression, growing support).
  • Typical 720p video: ~1.5 Mbps. 1080p: ~3 Mbps.

Scaling architectures

TopologyConnectionsSweet spot
MeshN×(N−1)/2 per peer2–4 participants
SFU1 up + (N−1) down per peer5–100+ participants
MCU1 up + 1 down per peerLegacy telephony bridges
  • SFU (Selective Forwarding Unit) is the production standard. It forwards without decoding — cheap CPU, bandwidth scales linearly.
  • Popular SFUs: mediasoup, LiveKit, Janus, Jitsi Videobridge, Cloudflare Calls.

Security model

  • HTTPS required — WebRTC APIs only work on secure origins.
  • User consent — camera/mic requires explicit permission grant.
  • DTLS-SRTP — all media encrypted peer-to-peer; encryption is mandatory, not optional.
  • Fingerprints in SDP prevent MITM on the media path.
  • ICE consent — periodic checks confirm the peer is still there.
  • mDNS candidates — browsers obfuscate local IPs to prevent tracking.

Debugging toolkit

  • chrome://webrtc-internals — the single most useful tool. Shows every API call, ICE candidate, and live quality graphs.
  • pc.getStats() — programmatic access to bitrate, packet loss, jitter, round-trip time, frames per second.
  • about:webrtc in Firefox — equivalent diagnostic page.
  • Key stats to watch: packetsLost, jitter, roundTripTime, framesPerSecond, qualityLimitationReason.

Common failure patterns

  • ICE failed → symmetric NAT without TURN server, or firewall blocking UDP. Fix: add a TURN server.
  • No remote video → forgot to listen for ontrack, or didn’t attach the stream to a <video> element. Fix: check event wiring.
  • Echo → echoCancellation: true not set, or remote <audio> element not muted for local playback. Fix: set constraints and mute local playback.
  • Black video → track was stopped or enabled = false. Fix: check track state.
  • Glare (simultaneous offers) → both peers create offers at the same time. Fix: use the Perfect Negotiation pattern.
