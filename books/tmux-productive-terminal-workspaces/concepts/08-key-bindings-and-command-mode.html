Key Bindings and Command Mode

tmux ships with a full set of defaults, and the last seven chapters leaned on them without apology — they're good defaults. But every one of them is just a line in a table tmux keeps internally, put there the same way you'd put your own line: with bind-key. This chapter opens that table up. By the end, remapping the prefix, adding a binding of your own, and reading prefix : as what it actually is — a command line, not a menu — should feel like ordinary editing, not magic you're borrowing from someone else's dotfiles.

The problem: memorizing someone else's muscle memory

Chapter three's pane-navigation keys — prefix ↑ ↓ ← → — work, but they put your hand somewhere it wasn't already if you're a vim or Neovim user, where h j k l already mean exactly the same four directions. Copying a stranger's tmux.conf to fix that — and most public dotfiles remap at least the prefix and the pane-navigation keys — trades one unexamined default for another: now you're memorizing their muscle memory instead of tmux's. Neither is actually necessary. tmux's key handling is a small, fully inspectable mechanism — a handful of named tables and one command that adds lines to them — and once it's visible, writing bindings that fit your own hands is no harder than the set -g lines from the last chapter.

The idea: keys live in tables, not in one flat list

Every keystroke tmux receives is looked up in a key table — a named set of key→command mappings. A client is always in exactly one table at a time, and which table decides what a keystroke means. Four tables matter for this book:

TableActive whenExample binding
root always, before the prefix is pressed none by default — every keystroke passes straight through to the pane
prefix for one keystroke, immediately after C-b c → new-window (chapter 3)
copy-mode while a pane is in copy mode, emacs-style keys Space → begin-selection
copy-mode-vi while a pane is in copy mode, if mode-keys vi (chapter 5) v → begin-selection

That's the whole trick behind the prefix key. C-b isn't special-cased machinery — it's a binding, in the root table, whose command is switch-client -T prefix: switch this client's active table to prefix for exactly the next keystroke. Whatever key follows gets looked up in prefix instead of root, runs its command, and the client falls straight back to root afterward. There's no separate "prefix mode" state machine to learn — it's the same one-keystroke table switch you'll use yourself in a moment to build a custom sequence.

Adding and removing bindings

bind-key (short form bind) writes one line into a table: bind-key [-n] [-r] [-T table] key command. Leave -T off and it targets prefix — that's why every binding in chapter three's config was written as bind c new-window, not bind -T prefix c new-window. -n is shorthand for -T root: a binding made with -n fires with no prefix at all, which is powerful and worth exactly the caution below. unbind-key (unbind) removes one, with the same -T/-n rules.

# repeatable vim-style pane navigation (see -r below)
bind -r h select-pane -L
bind -r j select-pane -D
bind -r k select-pane -U
bind -r l select-pane -R

# split panes into wherever you already are, not the session's start directory
bind '"' split-window -v -c "#{pane_current_path}"
bind %   split-window -h -c "#{pane_current_path}"
bind c   new-window      -c "#{pane_current_path}"

# root table (-n): no prefix, be careful what you shadow
bind -n M-h previous-window
bind -n M-l next-window

The pane-navigation lines use -r, which marks a binding repeatable: after running it once, the client stays ready to accept the same table's -r bindings again without another prefix press, for as long as the repeat-time session option allows (500 milliseconds by default). Press prefix j j j and only the first j needs the prefix — the next two land inside that repeat window. It's the same mechanism chapter three's prefix 1–9 window-select keys could use but don't, because jumping to window 3 twice in a row isn't a thing you do; walking three panes over often is.

Why the split/new-window lines above matter

Without -c "#{pane_current_path}", split-window and new-window both default to the session's original starting directory — not wherever the pane you split from has since cd'd to. #{pane_current_path} is a format variable, one of the same family #S and #W belong to (chapter three); tmux expands it at the moment the binding runs, so it always resolves to the live directory of the pane you just pressed the key in, not a directory frozen in the config file. Rebinding c, ", and % this way is common enough that it's worth having in the starter config from here on.

Command mode: the prompt behind every binding

Every binding in the tables above is really just a shortcut for something typeable. prefix : runs command-prompt, which opens a one-line prompt at the bottom of the screen where any tmux command — split-window -h, rename-window logs, set -g mouse on — can be typed directly, by its full command name, with no tmux prefix and no key binding required at all. It's the same command a shell script reaches with tmux split-window -h and the same command bind-key attaches to a key; prefix : is just a live, interactive way to reach it without leaving the pane you're in, closing whatever's running there, or having pre-bound a key for that exact action.

# at prefix :, any of these run immediately, no key binding needed:
rename-window scratch
split-window -h -c "#{pane_current_path}"
set -g status-interval 2
kill-pane -t 3

That equivalence is what makes list-keys genuinely useful rather than just a reference card: it prints every current binding in exactly this command-prompt syntax. tmux list-keys -T prefix is the ground truth for what prefix followed by a given key actually does right now — on this config, after every plugin and every override has been applied — which beats trusting memory once a config file gets past a page long.

Remapping the prefix itself

C-b is not privileged — it's just the value of the prefix session option, changeable like any other. Three lines do it:

unbind C-b
set -g prefix C-a
bind-key C-a send-prefix

The third line is the one people forget, and forgetting it is the single most common prefix-remap mistake. send-prefix transmits a literal C-a keystroke into whatever's running in the active pane — without that binding, pressing the new prefix twice just re-enters the prefix table twice, and there's no way left to send bash, readline, or a nested tmux session an actual Ctrl-a. C-a specifically is the classic GNU screen prefix, which is why this exact three-line remap shows up in nearly every migration guide from screen; whatever key you pick instead, the send-prefix line is what makes it behave the same way C-b did.

Building your own key table

switch-client -T <table> — the same command the prefix key itself runs — is available to any binding, which means multi-key sequences of your own are built the identical way tmux builds its one built-in sequence. Bind a key in prefix to switch into a table you invent, then populate that table:

# prefix g, then a letter, jumps straight to a named session
bind -T prefix g switch-client -T goto-session
bind -T goto-session s switch-client -t scratch
bind -T goto-session w switch-client -t work
bind -T goto-session l switch-client -t logs

prefix g w now jumps to the work session in three keystrokes, none of them needing to be memorized as a single chord. After the second key resolves — or after it times out with no match — the client falls back to its normal table exactly as it does after any ordinary prefix binding, so goto-session never lingers and steals a later keystroke you didn't mean for it.

Key idea

There is exactly one mechanism here, used three times: switch-client -T table sets the table for the client's next keystroke. tmux's own prefix key is the first use of it. A repeatable pane-navigation binding (-r) is a convenience layered on the same repeat-time window a table switch already provides. And bind -T goto-session ... is you using it directly. Nothing about custom key tables is a separate feature from the prefix key — it's the same primitive, aimed somewhere new.

The cost of -n

A -n (root-table) binding fires with no prefix, which is exactly what makes it dangerous: it shadows that key for every program running in every pane, all the time, not just while you're mid-workflow. bind -n M-h previous-window is reasonably safe because few programs claim Alt-h; binding a bare letter or an arrow key with -n takes it away from your shell, your editor, and anything else that expected to receive it directly. Reach for -n only for keys you're confident nothing else inside tmux needs.

A realistic workflow

Building a binding set is the same reload loop chapter seven established for options, with one extra verification step: edit ~/.tmux.conf, prefix r to reload, try the new key, and if it doesn't do what you expect, tmux list-keys -T prefix (or -T root for an -n binding) to see exactly what's actually bound — not what you meant to type. A binding added twice, a typo in the table name, or a plugin that claimed the same key first are all instantly visible there, in the same syntax you'd use to fix them.

Try it
  1. Add the four repeatable h/j/k/l pane-navigation bindings from above to ~/.tmux.conf, reload with prefix r, and confirm prefix j j j walks down three panes with only one prefix press.
  2. Add the "/%/c current-path overrides. Split a pane, cd somewhere else in it, split again, and confirm the new pane opens in the directory you just moved to.
  3. Build the goto-session table from above (adjust the session names to ones you actually have running, or create a couple of test sessions first). Confirm prefix g followed by a wrong letter does nothing and falls back cleanly — no error, no stuck state.
  4. Run tmux list-keys -T prefix | grep goto-session and confirm the one line you expect (the g binding itself) shows up, while tmux list-keys -T goto-session shows the three session-jump bindings underneath it.
Common mistake

Remapping the prefix and losing the ability to send its literal key through. unbind C-b plus set -g prefix C-a, with the bind-key C-a send-prefix line left out, looks like it works — the new prefix triggers bindings fine — right up until you need to send an actual Ctrl-a to bash (jump to line start) or to a tmux session running one layer further in over SSH. Without send-prefix, that keystroke is gone; tmux swallows it every time. If a remap ever needs undoing in a hurry, tmux set -g prefix C-b from any live pane restores the default without touching the file.

Bindings decide what a keystroke does. What that keystroke's consequences look like — whether the session you just jumped to even announces itself, whether a hung build is visible before you switch to it — is a separate, still-open question. The status line chapter three's window list and chapter six's activity markers have been quietly relying on is next, and it's owed a proper look.
