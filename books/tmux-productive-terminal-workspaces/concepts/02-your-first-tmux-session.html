Installing the idea, one keystroke at a time

Your First tmux Session

Last chapter sold you the idea. This chapter you actually run it. Everything here is hands-on: by the end you'll have started a session, watched it survive something drastic happening to your terminal, and shut it down again — all on purpose, all with commands you can recall from muscle memory, not a cheat sheet.

The problem: an untouched idea is just a rumor

You now know, in the abstract, that tmux keeps a session alive on a background server while your terminal window is just a disposable client. That's a fine sentence to understand. It is a completely different thing to have typed the three or four commands enough times that your hands know them without your brain being in the loop — because the moment you actually need this (a dropped SSH link, a crashed terminal, a laptop you have to shut mid-build) is exactly the moment you don't want to be recalling syntax. This chapter's whole job is to close that gap: install tmux if it isn't already on your machine, run a session end to end, and learn to read what tmux is telling you on screen while you do it.

Installing tmux

tmux ships in the package manager of essentially every platform you'd be doing this work on, so there's rarely a reason to build it from source. Pick your line, run it, and confirm with -V:

# pick one for your platform
sudo apt install tmux        # Debian / Ubuntu
brew install tmux            # macOS (Homebrew)
sudo dnf install tmux        # Fedora
sudo pacman -S tmux          # Arch

tmux -V                       # -> tmux 3.x, confirms it's on your PATH

If your distro's package is a version or two behind upstream, don't worry about it yet — everything in this chapter has worked unchanged for years of tmux releases. We'll flag anything genuinely version-sensitive when it comes up later in the book.

The idea: a small number of commands, one rhythm

Almost everything you'll do in tmux for the rest of this book routes through a single mechanism: the prefix key. By default that's Ctrl-b. Instead of tmux grabbing every keystroke you type (which would make it impossible to use inside your shell, your editor, or anything else), it stays out of the way until you press the prefix. Only then does the next key you press get interpreted as a tmux command instead of being sent straight through to whatever's running in the pane.

Key idea

The prefix is a rhythm, not a chord. Tap Ctrl-b, let go, then tap the command key. Once that two-step motion is automatic, every tmux binding you learn later — splitting panes, searching scrollback, jumping windows — is just a different second key on the same rhythm.

With that in hand, here is the entire vocabulary this chapter needs: tmux new -s NAME creates a session and attaches to it; prefix then d detaches without touching what's running; tmux ls lists every session the server is holding; tmux attach -t NAME reattaches to a specific one. Everything else in this book builds on top of exactly these four moves.

Orienting yourself: reading the status line

The moment you're attached, tmux draws a status line along the bottom of the terminal. It looks like clutter at first; it's actually the three things you most need to know at a glance, laid out left to right.

You'll customize this heavily once we get to status lines and themes later in the book, but the default is genuinely useful as-is: the left zone names your session, the middle zone lists every window in it with the currently active one marked, and the right zone anchors you to a host and a clock — handy the instant you're juggling sessions on more than one machine.

Command What it does Reach for it when…
tmux new -s work Creates a session named work and attaches to it Starting something new
tmux new -A -s work Attaches to work if it exists, creates it if not You don't want to remember whether it already exists
prefix, then d Detaches the client; the session keeps running Stepping away, on purpose
tmux ls Lists every session on the server You forgot what you named things
tmux attach -t work Reattaches to the session named work Coming back to a known session
tmux kill-session -t work Ends the session outright, killing everything in it You're actually done with it, not just leaving
A gotcha you will hit

tmux remembers you're already inside a session via the $TMUX environment variable it sets when you attach. If you type tmux again from inside a pane that's already in a session — easy to do inside an IDE terminal or a remote shell — it refuses to quietly nest and instead prints sessions should be nested with care, unset $TMUX to force. Don't fight that message: detach first (prefix, then d) and reattach from outside, rather than forcing a session inside a session.

Hands-on: run the whole loop once

Type these in order, in a real terminal, not just as you read them. The goal isn't to memorize the syntax — it's to have your hands do this once so the next time is faster.

# create + attach a session named "work"
tmux new -s work

# inside it, look at the status line: [work] on the left
# now detach — prefix (Ctrl-b), release, then d
Ctrl-b d

# back at your normal shell, ask tmux what's running
tmux ls
# -> work: 1 windows (created ...) (attached)

# reattach, by name
tmux attach -t work

# the idempotent version you'll actually alias later:
# creates "work" if it's gone, attaches if it's already there
tmux new -A -s work

# and when you're genuinely finished with it, from outside or inside:
tmux kill-session -t work

A realistic workflow

Here's where this settles once it's a habit. You sit down in the morning and, without thinking about whether yesterday's session is still alive, you run tmux new -A -s work. If the server rebooted overnight or you closed everything cleanly, you get a fresh session. If it didn't, you're looking at exactly what you left: the same panes, the same scrollback, maybe a build still finishing. Either way it's the same one command, typed the same way, with no branch in your head for “does it already exist?” That's the payoff of the -A flag, and it's worth adopting immediately rather than treating it as an advanced trick for later.

Try it
  1. Confirm tmux is installed: tmux -V.
  2. Create two differently named sessions: tmux new -s alpha, detach (prefix d), then tmux new -s beta, detach again.
  3. Run tmux ls and confirm you see both, neither marked (attached).
  4. Reattach to alpha specifically with tmux attach -t alpha — check the status line's left zone actually says [alpha], not [beta].
  5. While still attached, type tmux (no arguments) and read the nested-session warning it gives you instead of silently doing something confusing.
  6. Detach, then run tmux kill-session -t alpha and confirm with tmux ls that only beta is left.
Common mistake

Skipping -s and losing track of what you started. Run bare tmux a few times without naming anything, and you end up with sessions called 0, 1, 2 — numbers that tell you nothing a week later. Worse, plain tmux attach with no -t doesn't ask which one you meant; it silently reattaches to whichever session was most recently used, which is rarely the one you're thinking of once more than one exists. Name every session you start (-s NAME), and always target one explicitly when reattaching (-t NAME) — it costs a few extra characters and saves you from attaching into the wrong work.

So what did we actually gain? Not a new idea — you already had that from the last chapter — but the muscle memory to act on it: install, start, detach, list, reattach, end, all without pausing to look anything up. That's the whole toolkit for one session. What you haven't done yet is put more than one thing inside a session at a time. Next chapter is exactly that: sessions, windows, and panes, and how they nest inside each other.
