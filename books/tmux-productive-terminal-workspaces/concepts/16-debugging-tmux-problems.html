Debugging tmux Problems

A binding that doesn't fire. Colors that look wrong only inside tmux. A config change that seems to do nothing. Every one of these has shown up somewhere in the last fifteen chapters as a "common mistake" callout — this chapter is the general-purpose version: a small set of commands that turn "why is this broken" into a confirmed answer, in the order that actually finds the problem fastest.

The problem: guessing instead of asking tmux directly

Every earlier chapter's mistake — a scope mismatch (chapter seven), an overridden binding (chapter eight), a forgotten reload — has the same shape: the config file says one thing, and tmux's actual running state says another, and the gap between them is invisible until you check. The instinct under pressure is to re-read the config file harder. The faster path is almost always to ask the running server what it actually thinks is true right now.

Ground truth: list-keys and show-options

Chapter eight already introduced list-keys for exactly this reason: it prints every binding in the same syntax you'd use to set it, which means it's never wrong about what a key currently does, even if three different config lines or a plugin all touched it.

tmux list-keys -T prefix    # everything prefix +  does right now
tmux list-keys -T root      # everything with no prefix (-n bindings)

The equivalent for options is show-options: -g shows the current global session-option values, and adding -w shows global window options (show-window-options -g is the same thing under its older name). This is the direct fix for chapter seven's most common mistake — a value that "looks changed" in one session but wasn't set globally — because it prints exactly what the server is running with, not what you assume your config set.

tmux show-options -g | less
tmux show-options -g -w | less
The scoping trap, restated

Running a bare set-option (no -g) inside a live session changes only that session, not the global default — the value can look correct right where you tested it and still be wrong everywhere else. And because tmux reads its config file exactly once, at server start, no edit to ~/.tmux.conf reaches an already-running server until tmux source-file <path> runs. Before doubting an option's correctness, doubt scope and reload — in that order — before anything else.

Colors that only look wrong inside tmux

default-terminal sets what $TERM becomes for new windows inside a session — and it deliberately differs from your outer terminal's own $TERM, which is the first thing worth confirming rather than assuming they should match:

echo $TERM      # outside tmux
tmux
echo $TERM      # inside tmux -- governed by default-terminal, not inherited

For truecolor specifically, terminal-overrides lets you append a capability override to a matching terminal-type pattern; the classic fix is a Tc flag on the 256-color type. tmux 3.2 and later added a purpose-built alternative, terminal-features, with an explicit RGB feature meaning the same thing more legibly:

set -g default-terminal "tmux-256color"
set -ga terminal-overrides ',xterm-256color:Tc'
# tmux >= 3.2 alternative:
set -as terminal-features ',xterm-256color:RGB'

And for a quick blunt check rather than root-causing the terminfo entry, tmux -2 forces tmux to assume 256-color support outright — useful to confirm the server isn't the problem before chasing terminal-emulator settings.

When the surface-level checks don't explain it: verbose logging

For anything the commands above don't explain, tmux -v turns on verbose logging, writing tmux-client-PID.log and tmux-server-PID.log into the current directory; -vv additionally captures everything tmux writes to the terminal in a third file. Verbose logging can also be toggled on a server that's already running, without restarting it, by sending it SIGUSR2.

tmux -v          # or: tmux -vv for terminal output too
# toggle on a server that's already running, no restart needed:
kill -SIGUSR2 <tmux-server-pid>

A hung or dead pane

respawn-pane restarts a pane's original command in place — but it refuses to touch a pane whose command is still alive, to avoid silently killing something you might not have meant to. -k overrides that: kill whatever's running first, then relaunch.

tmux respawn-pane -k -t mysession:1.0

The actual last resort

tmux kill-server terminates the server and every session it was running, immediately, with no confirmation prompt and no undo. It's a legitimate tool for a server stuck in a state nothing else fixes — but it costs everything not already checkpointed by chapter fifteen's tmux-resurrect: unsaved scrollback, in-progress shell history, any pane you hadn't gotten around to saving. Confirm resurrect (or a manual save) is current before reaching for it if there's any choice in the matter.

Try it
  1. Deliberately bind the same key twice in ~/.tmux.conf to two different commands, reload, then use list-keys -T prefix to confirm which one actually won — the later line in the file, not the first.
  2. Set an option without -g from a live pane, then check show-options -g and confirm it's unchanged — the local override is invisible to the global view.
  3. Run the echo $TERM check from above, both outside and inside tmux, and confirm they're different values.
  4. Deliberately hang a pane (run something like sleep 300 and consider it "stuck" for the exercise) and recover it with respawn-pane -k without closing the window.
Common mistake

Reaching for kill-server before trying anything smaller. A hung pane is respawn-pane -k, not a server restart. A binding that doesn't seem to work is list-keys, not deleting and re-adding lines at random. A config change that "didn't take" is show-options -g plus a reload, not editing the same line five different ways hoping one sticks. kill-server is a real last resort precisely because everything above it almost always finds the actual problem first, and does it without losing anything.
