One line at the edge of the screen, visible no matter what's running in the pane above it.

Status Lines, Themes, and Visual Context

Chapter three's window list — the numbered names you switch between with prefix 0–9 — lives in the status line. So does chapter six's activity bell, silently flipping a window's entry to a different color the moment a background build finishes. Both have been rendering from day one using tmux's stock, unstyled defaults. This chapter is where the status line stops being background furniture and becomes a surface you design: what it shows, how it's laid out, and how far to take a theme before it's shouting louder than the work happening above it.

The problem: the one place that's always visible, wasted

Every pane you've split, zoomed, or filled with a build log eventually gets covered by something else. The status line doesn't — it's the one square inch of screen tmux guarantees stays visible regardless of what's running above it. Left at defaults, that guaranteed real estate shows a session name, a pane title, and a clock: true, but not much of it is information you'd go looking for. Meanwhile the actual answers to "which host is this," "what branch am I on," and "is the build in window 3 still running" are one manual check away — a git branch, a glance at the window list, an ssh prompt you have to read closely. The status line can answer all three without being asked, continuously, for free.

The idea: three zones, one format language

The status line has three independently configured zones — a left side, a scrolling window list in the middle, and a right side — and all three are filled using the same format string language you already met in passing as #S and #W back in chapter three. status-left and status-right hold the two fixed zones directly; the middle is generated automatically, one segment per window, from window-status-format (every other window) and window-status-current-format (the one you're on).

VariableExpands to
#Ssession name
#Iwindow index
#Wwindow name
#Ppane index
#{pane_current_path}the active pane's live working directory
#{pane_current_command}the program currently running in the pane
#{?client_prefix,A,B}A while the prefix is active, otherwise B

That last row is the format language's other half: conditionals. #{?condition,true-text,false-text} renders one branch or the other depending on live state — client_prefix is true for the brief window after you press the prefix key and before the next keystroke lands, which is exactly long enough to flash a visible cue that tmux is waiting on you. Conditionals are what separate a themed status line from a static one: the same format string renders differently depending on what's actually happening, not just what session you're in.

Two length options cap how much of each zone actually renders: status-left-length (default 10 characters) and status-right-length (default 40). Content past the limit is silently truncated, not wrapped — the most common reason a carefully-written status line "doesn't show" a new segment is simply that the length budget never grew to fit it.

Coloring it: inline style blocks

Color and weight are set with #[attribute=value,...] blocks embedded directly in a format string. Everything after a #[...] block uses that styling until the next one resets it — there's no separate stylesheet, just style changes interleaved with text in the same string.

set -g status-style bg=colour234,fg=colour137

set -g status-left-length 20
set -g status-left "#[fg=green,bold]#S #[fg=white,nobold]| "

set -g window-status-current-format "#[fg=colour255,bg=colour31,bold] #I:#W#F "
set -g window-status-format         "#[fg=colour244] #I:#W#F "

status-style sets the baseline for the whole bar; each zone's own #[...] blocks override it locally, which is why the current window's format above can give itself a highlighted background without touching anything else. Distinguishing window-status-current-format from window-status-format this way — not just a different color, an actually different background block — is what makes "which window am I on" answerable at a glance instead of a squint.

Live data: shelling out for a git branch

#(shell-command) runs an arbitrary shell command and drops its output straight into the format string, re-run on the interval set by status-interval (chapter seven's starter config set this to 5 seconds). It's the mechanism behind any status segment that isn't a built-in tmux variable — battery percentage, CPU load, and, most commonly, the current git branch:

set -g status-right '#(cd #{pane_current_path} 2>/dev/null; git rev-parse --abbrev-ref HEAD 2>/dev/null) | %H:%M'

The cd #{pane_current_path} at the front is doing real work, not decoration: #(...) runs in tmux's own process, in tmux's own working directory, which has no relationship to whichever pane happens to be active. Without explicitly cd-ing into #{pane_current_path} first, a git-branch segment either shows the wrong repository's branch or silently shows nothing, depending on where the tmux server itself happened to start.

Themes: composing instead of hand-styling

Hand-writing every #[...] block works, but it's also exactly the kind of repetitive styling a plugin exists to save you from. Three worth knowing by name, each solving it differently:

PluginApproach
catppuccin/tmux pre-built segments exposed as tmux options (@catppuccin_status_<module>), composed into status-right with the #{E:...} expansion prefix
tmux-themepack whole prebuilt theme files loaded with one source-file line; individual @-prefixed options still overridable afterward
tmux-powerline segmented, arrow-divided bar in the vim-Powerline style; needs a patched Nerd Font in the terminal for its separator glyphs to render 
set -g @plugin 'tmux-plugins/tpm'
set -g @plugin 'catppuccin/tmux'
set -g @catppuccin_flavor 'mocha'

set -g status-right "#{E:@catppuccin_status_application}"
set -ag status-right "#{E:@catppuccin_status_uptime}"

run '~/.tmux/plugins/tpm/tpm'

The E: prefix matters: #{@catppuccin_status_application} would print the option's raw text, but #{E:@catppuccin_status_application} tells tmux to expand that text as a format string in its own right — which is exactly what a plugin's pre-built segment needs, since the segment's value is itself a format string, not a literal one.

Key idea

A themed status line and a hand-styled one are built from the exact same primitives — status-left/status-right, #[...] blocks, #(...) shell-outs. A plugin just pre-writes a library of segments and hands them back as options you compose, instead of you writing every #[fg=...] block from scratch. Nothing a theme plugin does is inaccessible to a status line you build yourself — it's a convenience layer over the same language, exactly like tmux-sensible was a convenience layer over chapter seven's options.

A realistic workflow: information, not decoration

The useful discipline, whether hand-styled or plugin-composed, is asking of every segment: does this answer a question I'd otherwise have to check manually? Session name and window list answer "where am I." A git-branch segment answers "what am I about to commit to." Chapter six's activity markers already answer "is something waiting for me" without a dedicated segment at all — that's the bar to hold new additions to. Color and a clean divider make the answer easy to read; they're not, on their own, a reason to add a segment.

Try it
  1. Add the status-style, status-left, and window-status-current-format/window-status-format lines above to ~/.tmux.conf and reload. Confirm the active window's entry is visually distinct from the others.
  2. Add the git-branch status-right line. From a pane inside a git repository, confirm the branch name appears; cd to a non-repository directory in that same pane and confirm the segment goes quietly blank rather than showing stale data.
  3. Add #{?client_prefix,#[reverse]PREFIX#[noreverse] ,} to the front of status-right. Press prefix and hold just long enough to see it flash, then release without completing a binding.
  4. Deliberately shrink status-right-length to something too small (try 20) and confirm the git-branch segment gets truncated — then set it back to a sane value like 60.
Common mistake

A shell-out segment that shows the wrong directory's data, or none at all. #(...) commands run in tmux's own process and working directory — not the active pane's — so a git-branch or similar segment that forgets to cd #{pane_current_path} first isn't broken, it's just answering the question for the wrong location. If a shell-out segment seems to be lying, that's the first thing to check, before suspecting the shell command itself.

Configuration and status line both live in one file, edited by hand. The next three chapters turn from that file toward the actual work tmux is for: arranging panes around a running project, keeping that arrangement alive over SSH, and building it back automatically instead of typing the same splits every morning.
