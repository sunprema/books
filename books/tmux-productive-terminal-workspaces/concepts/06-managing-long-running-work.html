The job doesn't need you to watch it. But you still need to know when it's done.

Managing Long-Running Work

You already know a tmux session survives a closed laptop lid or a dropped SSH connection — that was the whole pitch back in chapter one. What hasn't come up yet is what to do with that guarantee once you're actually relying on it: a test suite that takes twenty minutes, a deploy you kicked off and want to walk away from, a log you're tailing in a window you're not looking at right now. tmux keeps all of that alive without asking. The problem this chapter solves is the other half — knowing what happened while you weren't watching.

The problem: you've already solved "keep it running"

Before tmux, protecting a long job from a closed terminal meant backgrounding it by hand: long-build &, maybe disown on top, or nohup long-build & if you expected to log out entirely. All of that exists to survive one specific event — the shell's controlling terminal going away sends every foreground job a SIGHUP, and the job dies with it unless something insulated it first. Inside a tmux pane, that event doesn't happen. The process's parent is the tmux server, not your terminal emulator or your SSH client, so detaching — or your connection simply dropping — never sends a hangup signal in the first place. The habit isn't wrong to have from other tools; it's just solving a problem you no longer have once the job is inside a pane.

What's left is a different, quieter problem. You start a build in window 2, switch to window 1 to write code while it runs, and now you have no way of knowing — without switching back and looking — whether it's still grinding, finished cleanly a while ago, or crashed on line one. The status line is right there, always visible, and it's currently telling you nothing about any of that.

The idea: let tmux watch the window for you

tmux can flag a window in the status line based on what happens inside it, even while you're looking at a different one. Two window options drive this, and they answer two different questions. monitor-activity asks "did anything get printed at all?" — turn it on and the first new line in that window marks it, instantly. monitor-silence asks the opposite question: "has it gone quiet?" — given an interval in seconds, the window is flagged once it's produced no output for that long. For a chatty build, silence is almost always the more useful signal: a single flagged line the moment compilation starts tells you nothing you didn't already know, but a window that's stopped scrolling for thirty seconds is either finished or stuck, and either way it's worth a look.

Key idea

Both options are set with setw (short for set-window-option), scoped to whatever window you're currently attached to — not set -g, which would apply session-wide. That distinction matters more here than almost anywhere else in tmux: turn monitoring on for the one window running a build, and every other window — your editor, your shell, your log tail — stays quiet and unflagged.

Option Scope What it does
monitor-activity window, off by default Flags the window in the status line the moment it prints anything, while it isn't the one displayed.
monitor-silence <seconds> window, 0 (disabled) by default Flags the window once it's produced no output for that many seconds.
activity-action / silence-action / bell-action session, default other Which windows the flag applies to — other means "any window that isn't the one I'm currently looking at."
visual-activity / visual-silence / visual-bell session, off by default Whether the flag is just a quiet status-line mark (off) or also an on-screen message (on). 
# flag this one window when it goes quiet for 30s -- scoped to the current window
tmux setw monitor-silence 30
tmux set -g visual-activity on

# ...work elsewhere; the status line marks the window once it's silent...

tmux setw monitor-silence 0   # back off once you've reattached and dealt with it

Naming the window matters just as much as flagging it — a highlighted "2" in the status line is only useful if you remember what window 2 is. automatic-rename keeps a window's name synced to whatever's running in its active pane by default, but the moment you rename one by hand — prefix ,, from chapter three — automatic-rename switches itself off for that window permanently, until you turn it back on. That's not a bug to fight; it's exactly what you want for a job worth naming on purpose: rename the window deploy before you start, and it stays deploy in the status line long after the shell prompt has quietly returned.

When the job finishes without you: remain-on-exit

Flagging tells you a window went quiet. It doesn't protect you from the pane vanishing at the worst possible moment. By default, the instant a pane's program exits — success or failure — tmux closes that pane immediately, and if it was the last pane in the window, the window closes too. A deploy script that crashes on its final line and exits can take that error message down with it before you've read it. set -g remain-on-exit on changes that: an exited pane stays open, marked dead, showing exactly the last screen it printed and its full scrollback — prefix [ from last chapter still works on it, so you can search backward through what actually happened. respawn-pane -k restarts the same command in that same pane, same spot in the layout, once you're ready to try again.

tmux set -g remain-on-exit on
# process exits -> pane stays, shows "Pane is dead", keeps its scrollback
# prefix [ still works on a dead pane -- read exactly what it printed
tmux respawn-pane -k    # restart the same command, same pane, same layout slot

Capturing output you weren't watching

A flag in the status line and a pane that stays open both help while you're near the terminal. For anything you want on disk — a build log to attach to a bug report, a deploy transcript for the record — tmux has two different tools depending on which direction in time you need. pipe-pane connects a pane's output to an external command from that moment forward: pipe-pane -o 'cat >> ~/logs/build.log' starts appending everything the pane subsequently prints. Run the identical command again with no argument and it toggles back off. What it does not do is reach backward — anything already printed before you ran it is not in that file. For that, capture-pane takes a snapshot of what the pane already holds: -p prints to stdout, -S - means "start at the oldest line still in history," and -E - means "end at the current line" — together they dump the whole retained scrollback in one shot.

# log everything this pane prints from now on
tmux pipe-pane -o 'cat >> ~/logs/deploy.log'
# ...run the deploy...
tmux pipe-pane            # no argument, same command -> toggles logging back off

# grab what's already in the pane's scrollback, right now, in one shot
tmux capture-pane -p -S - -E - > ~/logs/deploy-snapshot.txt

A realistic workflow

A release build takes about fifteen minutes and you'd rather not sit and watch it. Before starting it: rename the window — prefix ,, type release-build — so it reads as something specific in the status line rather than a number. Turn on monitoring scoped to just this window: setw monitor-silence 45, plus set -g remain-on-exit on for the session so a crash at the very end doesn't vanish. Start the build, detach with prefix d, and go do something else in another session or window entirely. When release-build lights up in the status line, either it finished quietly forty-five seconds ago, or it's stuck — reattach and prefix [ into the pane's scrollback to find out which. If it's a pane gone dead from a nonzero exit, the last screen and full history are still sitting right there to read before you touch anything.

Try it
  1. In a session, rename the current window to watch-test (prefix ,).
  2. Turn on silence monitoring for it: tmux setw monitor-silence 15 and tmux set -g visual-activity on.
  3. Run a job that produces output, then goes quiet: for i in $(seq 1 5); do echo "step $i"; sleep 2; done; sleep 20; echo done
  4. Detach (prefix d), wait about 20–25 seconds, then run tmux ls from outside — nothing shows the flag from there, so reattach with tmux attach and look at the status line instead. It should mark watch-test once the 15-second silence window has passed.
  5. Now set tmux set -g remain-on-exit on, run echo about to fail; exit 1 in a pane, and confirm the pane stays open showing "Pane is dead" instead of closing. Run tmux respawn-pane -k to bring it back to life.
  6. Finally, try both logging tools on the same output: tmux pipe-pane -o 'cat >> /tmp/watch-test.log', print a few more lines, then compare against tmux capture-pane -p -S - -E - run in the same pane — notice the log file only has what came after you started piping, while capture-pane prints everything still in scrollback.
Common mistake

Turning monitoring on globally instead of for the one window that needs it. set -g monitor-activity on applies it to every window in the session, so an ordinary shell prompt returning in your editor window flags it exactly the same as your build finishing in the build window — the status line fills up with marks that mean nothing in particular, and the one signal you actually wanted to see gets lost in it. Scope it with a plain setw (no -g) while attached to the specific window that's running the long job, and leave every other window alone.

Between last chapter and this one, the pattern for everyday tmux use is basically complete: split and arrange panes to fit the work, reach back into scrollback for anything that's scrolled away, and let the status line tell you when a job you've stopped watching needs you again. What's still manual is everything about how tmux looks and behaves — the default prefix, the default colors, the fact that every one of these options has to be typed at a command prompt instead of just being true when you open a new session. That's what configuration is for, starting next chapter.
