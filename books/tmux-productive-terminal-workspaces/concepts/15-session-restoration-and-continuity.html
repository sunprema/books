Session Restoration and Continuity

Everything tmux knows about your sessions — every window, every pane, every running program — lives in the memory of one server process. Chapter eleven made peace with that being fragile against a dropped SSH connection, because the server itself never stopped. A reboot stops it. So does kill-server, chapter sixteen's last resort. This chapter is the one piece of session persistence that survives even that: tmux-resurrect, saving and restoring layout and running programs, and tmux-continuum, which does it automatically instead of waiting for you to remember.

The problem: in-memory state, gone at the process level

A tmux server is a normal Unix process. Reboot the machine, and every process tree it was the ancestor of — every pane, every shell, every program running in one — ends with it, the same as any other process would. Nothing about tmux's design persists that state to disk on its own; a session that took twenty minutes to arrange (chapter twelve's whole premise notwithstanding) is exactly as gone after a reboot as one built by hand, unless something explicitly wrote a snapshot somewhere durable first.

tmux-resurrect: a manual snapshot

Installed (chapter fourteen's TPM pattern), tmux-resurrect adds two bindings: prefix Ctrl-s saves the current state of every session to disk; prefix Ctrl-r restores the most recent save. A save captures sessions, windows, and panes in order; each pane's current working directory; the exact pane layout within each window, including a zoomed pane's state; which session and window were active; and, for a deliberately conservative allow-list of programs, the running program itself rather than just a bare shell.

prefix Ctrl-s   # save current tmux environment
prefix Ctrl-r   # restore last saved environment

That allow-list defaults to a short, safe set — vi, vim, nvim, emacs, man, less, more, tail, top, htop, and a couple of IRC clients. Anything else in a pane restores as a plain shell, in the right directory, but not re-launched — which is the deliberately conservative default, and worth extending explicitly rather than working around:

set -g @resurrect-processes 'ssh psql mysql sqlite3'

The syntax has two more tricks worth knowing. A leading ~ matches any process whose full command line merely contains the given text — useful for a long interpreter invocation you only care to recognize by its tail. An arrow substitutes a friendlier name on restore, and a trailing * keeps the original arguments attached to that substituted name:

set -g @resurrect-processes '"~rails server->rails server *"'
The special value :all:

set -g @resurrect-processes ':all:' restores every detected running program with no allow-list at all — and the plugin's own documentation calls this dangerous, not just permissive. tmux-resurrect has no way to know a command's context: a destructive one-off like sudo mkfs.vfat /dev/sdb re-executed against whatever disk happens to be /dev/sdb after a reboot is exactly the kind of accident this warning exists to prevent. Extend the allow-list explicitly instead.

Scrollback text itself is a separate opt-in, since it meaningfully increases save size and time: set -g @resurrect-capture-pane-contents 'on' preserves each pane's visible history alongside its layout and program.

tmux-continuum: automatic, not remembered

A manual save only protects what you remembered to save before the reboot — which, in practice, is never the reboot that actually happens (a crash, a forced update, a laptop that ran out of battery). tmux-continuum depends on tmux-resurrect and removes the "remembered" part: it saves automatically on a timer, defaulting to every 15 minutes, and can optionally restore the last save the instant the tmux server itself starts.

set -g @plugin 'tmux-plugins/tmux-resurrect'
set -g @plugin 'tmux-plugins/tmux-continuum'

set -g @continuum-save-interval '60'   # minutes; '0' disables autosave entirely
set -g @continuum-restore 'on'

Two details worth knowing before relying on it: restoration happens exclusively when the tmux server process itself starts — reloading config with source-file (chapter seven) never triggers it, only a genuinely fresh server does. And restoration is idempotent by design: it won't recreate sessions or windows that already exist, with one deliberate exception — the single default pane present the moment tmux starts specifically to perform a restore gets overwritten by the restored layout.

What doesn't come back: the boundary worth knowing

Resurrect saves and replays a command line, not a process's memory. psql mydb relaunching on restore gets you back into the right database — but any query you'd typed and not yet run, any transaction left open, is gone; the REPL is a fresh instance that happens to share the command that started the old one. An editor session restoring its file reopens the buffer, but unsaved edits, undo history, and cursor position are a separate, more involved feature some editors handle themselves (Vim's own swap/session files, for instance) — not something tmux-resurrect provides on top of a bare relaunch. Knowing that boundary in advance is what keeps a save from feeling like it "lost work" when what actually happened is exactly what the tool documents: the launcher came back, the state inside the process didn't.

Key idea

Resurrect plus continuum answers a narrower question than "did my work survive a reboot" — it answers "did my workspace survive," meaning the panes, the directories, and the command lines that were running. That's still most of what chapter twelve's setup scripts build by hand, just restored automatically instead of re-run. It is not a substitute for saving files, committing work, or trusting a REPL's in-memory state to persist — those still need their own discipline.

A realistic workflow

Set the interval loose enough not to matter (an hour is plenty for most work), turn on @continuum-restore, and otherwise forget about it — the entire point is not having to remember prefix Ctrl-s before every reboot. The one moment it's worth checking manually is right after setting it up: force a save, kill the server, start tmux fresh, and confirm the exact layout you expect comes back before trusting it unattended.

Try it
  1. Install tmux-resurrect via TPM. Build a small session with two or three panes, one running vim on a scratch file.
  2. prefix Ctrl-s to save, then tmux kill-server (chapter sixteen's last resort, used deliberately here). Start tmux again and prefix Ctrl-r to restore — confirm the panes, directories, and the running vim are all back.
  3. Add tmux-continuum with @continuum-restore 'on' and a short interval (try '1' for testing). Kill the server without saving manually this time, start tmux fresh, and confirm the layout restores on its own.
  4. Set @resurrect-processes to include a REPL you use, restart with a query typed but not run inside it, and confirm after restore that the REPL is back but the unrun query is not — the boundary from above, observed directly.
Common mistake

Toggling @continuum-restore and testing it with a config reload. prefix r (chapter seven's source-file binding) re-reads the config into the already-running server — exactly the one thing that does not trigger continuum's restore check, which only runs at server start. Testing the setting means actually killing the server (tmux kill-server) and starting fresh, not reloading config into a server that was never stopped.

A workspace surviving is one kind of resilience. The next chapter is about the more common failure mode — not a reboot, but tmux itself doing something you didn't expect, and the small set of commands that turn "why is this broken" into an answer in under a minute.
