A Personal tmux System

Nothing in this closing chapter is new. Every piece — the starter config, the bindings, the status line, the plugin list, the setup script — was built in an earlier chapter, in isolation, one idea at a time. What hasn't happened yet is putting them in the same file, in the order that makes each layer's dependency on the one below it visible, and being honest about which pieces you'd actually miss if they vanished tomorrow versus which ones were just fun to set up once.

The problem: a config that grows by accretion, not design

Left alone, a tmux.conf tends to grow the way most dotfiles do: a line added while chasing one specific annoyance, another copied from a blog post months later, a plugin added for a feature you used twice and then forgot about. Nothing in that process is wrong on its own — it's how chapters seven through seventeen were written, each chapter solving one real problem. But a config built entirely that way eventually has more lines than reasons, and the discipline chapter fourteen argued for plugins — know what every line does — quietly stops being true for a config nobody's looked at end to end in a year.

The idea: five layers, each depending on the one before it

Read start to finish, this book built a config in a specific order, and that order isn't arbitrary — each layer assumes the one before it is already solid. Reassembling it deliberately, rather than as a chronological pile, means keeping that order:

LayerWhat it isChapter
1. Fundamentalsmouse, history-limit, base-index, escape-time — scoped correctly with -g7
2. Bindingspane navigation, split-into-current-path, any prefix remap8
3. Status linewhat's genuinely worth knowing at a glance, styled last9
4. PluginsTPM plus a short, individually-understood list14
5. Per-projectsetup scripts living in each project's repo, not the dotfiles10, 12

The dependency runs downward: bindings that split into #{pane_current_path} only matter once history-limit and mouse are already sane defaults you're not fighting. A themed status line is wasted effort on top of bindings you haven't settled on yet — chapter nine's segments are cheap to restyle, chapter eight's muscle memory is not. And a plugin list (layer 4) is exactly the kind of thing that's easy to over-adopt before layers 1–3 are stable, at which point every plugin update risks fighting settings you're still actively changing by hand.

A complete starter config, assembled

Every line below was introduced somewhere in chapters seven through fourteen. This is the same config, ordered by the layers above instead of by publication order:

# ~/.tmux.conf -- assembled from this book, layer by layer

# --- layer 1: fundamentals (ch. 7) ---
set -s escape-time 10
set -g mouse on
set -g history-limit 50000
set -g base-index 1
set -g renumber-windows on
set -g focus-events on
setw -g pane-base-index 1

# --- layer 2: bindings (ch. 8) ---
bind -r h select-pane -L
bind -r j select-pane -D
bind -r k select-pane -U
bind -r l select-pane -R
bind '"' split-window -v -c "#{pane_current_path}"
bind %   split-window -h -c "#{pane_current_path}"
bind c   new-window      -c "#{pane_current_path}"
bind-key R source-file ~/.tmux.conf \; display-message "Config reloaded"

# --- layer 3: status line (ch. 9) ---
set -g status-style bg=colour234,fg=colour137
set -g status-left-length 20
set -g status-left "#[fg=green,bold]#S #[fg=white,nobold]| "
set -g status-right-length 60
set -g status-right '#(cd #{pane_current_path} 2>/dev/null; git rev-parse --abbrev-ref HEAD 2>/dev/null) | %H:%M'
set -g window-status-current-format "#[fg=colour255,bg=colour31,bold] #I:#W#F "

# --- layer 4: plugins (ch. 14, ch. 15) ---
set -g @plugin 'tmux-plugins/tpm'
set -g @plugin 'tmux-plugins/tmux-sensible'
set -g @plugin 'tmux-plugins/tmux-resurrect'
set -g @plugin 'tmux-plugins/tmux-continuum'
set -g @plugin 'tmux-plugins/tmux-yank'

set -g @continuum-save-interval '60'
set -g @continuum-restore 'on'

run '~/.tmux/plugins/tpm/tpm'   # must stay last

Layer 5 — per-project setup scripts — deliberately isn't in this file at all. It lives in each project's own repository (chapter twelve's bin/dev pattern), checked in alongside the code it sets up, so it travels with the project instead of living only on one machine's dotfiles.

Key idea

A personal system isn't more features than a stranger's dotfiles — it's the same handful of features, kept small enough that every line still has a reason you can state out loud. The test worth applying to any addition, from any chapter in this book: could you explain what this line does and why it's there, to someone reading over your shoulder, without opening the file to check? If not, it's either worth actually learning (most of this book was written to make that fast) or worth removing.

A realistic workflow: revisiting, not just building

A config built once and never revisited drifts the same way any long-lived file does — a binding for a workflow you don't use anymore, a plugin whose replacement you meant to try, an option whose default changed in a newer tmux release and quietly made your override redundant. Skimming tmux.conf top to bottom every few months, the same way chapter sixteen's list-keys and show-options -g show ground truth for a single problem, keeps the whole file honest — not by adding more, most of the time, but by noticing what's no longer earning its place.

Try it
  1. Diff your own ~/.tmux.conf against the assembled config above. For every line that differs, write one sentence — from memory, not by re-reading the relevant chapter — explaining what it does.
  2. For any line you couldn't explain, either look it up (this book's cheatsheet is the fastest path) or remove it and confirm nothing you rely on breaks.
  3. Pick one project you work in regularly and write it a bin/dev script following chapter twelve's guarded pattern, if it doesn't have one yet.
  4. Set a recurring reminder — genuinely, on a calendar — to skim your config again in three months, and see how much of it you'd still write the same way.
Common mistake

Treating "more layered" as "more productive." Every chapter in this book added a capability; none of them required using all the others. A config with just layer 1 and a couple of chapter-eight bindings, deliberately kept there, is a completely legitimate personal system — often a better one, for someone who doesn't want to think about tmux at all, than a five-layer setup maintained halfheartedly. The point of building this book's config in layers was never "reach layer five"; it was knowing which layer you're actually standing on, and why.

That's the whole arc: a terminal multiplexer, taken apart into pieces small enough to actually understand, and put back together as something that fits your own hands rather than a stranger's dotfiles. The cheatsheet that follows is the reference to keep open while that system keeps growing — every command, binding, and option from these eighteen chapters, in one place.
