Everything you typed didn't disappear — it just left the screen

Scrolling, Search, and Copy Mode

Last chapter left you with real control over a window full of panes — layouts, resizing, synchronized typing. What it didn't cover is what happens once a pane has scrolled past what's visible: the error three hundred lines up, the one stack trace frame you actually need, the command output you want in a chat message instead of a terminal. That's a different problem from arranging panes, and tmux solves it with a mode of its own.

The problem: the screen is not the output

A pane only ever renders the last however-many lines that fit in it. Run something chatty — a test suite, a build, a verbose deploy script — and the line you actually care about scrolls off the top within seconds. Your terminal emulator's own scrollbar and its native text selection, the ones you'd reach for in a plain shell, don't reliably reach that history: tmux is the thing drawing the screen, redrawing it every time a pane updates, so the buffer your terminal remembers and the buffer tmux is tracking underneath it are not the same thing. And even where dragging to select text does work, chapter four's mouse-mode note still applies: once mouse on is set, click-drag belongs to tmux, not your terminal's own triple-click-to-select-a-line habit.

None of that is a defect to work around — it's the consequence of tmux owning the screen instead of just passing text through it. Owning the screen is exactly what lets tmux offer something a plain terminal can't: a scrollback you can search, and a selection you can copy without ever touching the mouse. That's copy mode.

The idea: freeze the pane, then it's just a buffer

prefix [ enters copy mode. The pane freezes — new output still arrives underneath and gets appended to the history, but the view stops following it — a cursor appears, and everything currently on screen plus everything scrolled off it becomes one navigable, searchable buffer. How far back that buffer reaches is the history-limit option: 2000 lines per pane by default, raisable with set -g history-limit 50000. The one catch worth knowing up front: a new limit only applies to panes created after you set it — a pane that's already open keeps whatever limit was in force when it was born, until it's closed and reopened.

If all you want is to look up right now, prefix PageUp is a shortcut worth building into muscle memory: it jumps straight into copy mode already scrolled up a page, skipping the separate prefix [ step entirely.

Key idea

Copy mode isn't a scrollbar bolted onto tmux — it's a genuine mode, the same way your editor has a normal mode and an insert mode. While it's active, keystrokes are commands to copy mode, not input to the shell underneath. That's why a pane that "stopped responding" to your typing is almost always a pane still sitting in copy mode — press q and it's back.

Two key tables: pick one and mean it

Every keystroke inside copy mode is looked up in one of two key tables, chosen by the mode-keys option: emacs, the default on a fresh install, or vi, switched on with set -g mode-keys vi. This only changes copy mode — it has no effect on any binding outside it. If you live in a shell with Emacs-style readline editing, the default already matches your fingers; if you live in Vim, set it once in your config (the next chapter covers exactly where) and every binding below shifts to its vi-flavored twin.

Searching is directional and relative to the cursor, not to the top or bottom of the buffer — this trips people up more than anything else in the table. / (or Ctrl-s) searches forward, toward more recent output; ? (or Ctrl-r) searches backward, toward older output. Start a search from the bottom of a fresh scrollback and you almost always want ?.

Buffers, not just the last one

Every completed copy is stored as a tmux paste buffer, and tmux keeps more than just the latest. prefix ] pastes the most recent one into the active pane; prefix # lists every buffer currently held (list-buffers); prefix = opens an interactive picker (choose-buffer) so you can paste an older one instead of only the newest. Worth knowing before you need it — the third thing you copied twenty minutes ago isn't gone just because you copied two more things since.

# raise scrollback before creating new panes -- existing panes keep the old limit
tmux set -g history-limit 50000

# switch copy mode to vi-style navigation and selection
tmux set -g mode-keys vi

# inside a pane: prefix [ , then ? to search backward, n to repeat
# v (or Space) begins a selection, y (or Enter) copies it and exits
# prefix ] pastes the most recent buffer into whatever pane you're in now
Why scrolling over vim doesn't do what you expect

With set -g mouse on, the scroll wheel drives copy mode too — scroll up over a plain shell prompt and tmux enters copy mode automatically. Scroll up over vim, less, or htop, though, and nothing happens to tmux at all: those programs use the terminal's alternate screen and manage their own scrolling, and tmux's default mouse binding checks for that and passes the scroll straight through instead of hijacking it. Not a bug — it's the reason full-screen programs keep working normally with mouse mode on.

A realistic workflow

A test run fails two hundred lines into scrollback you can no longer see. prefix [ freezes the pane. ? then error jumps the cursor to the nearest match searching backward from wherever you were; n walks to earlier matches if the first one isn't the one you want. Once you're sitting on the right line, v begins a selection, j a few times extends it down across the stack trace, and y copies it and drops you back into a live pane. Switch to the pane running your editor or a scratch buffer, prefix ], and the trace is there — no mouse, no terminal scrollbar, no re-running the failing command just to see the error again.

Try it
  1. In a session, generate scrollback on purpose: for i in $(seq 1 400); do echo "step $i: build ok"; done; echo "step 401: ERROR missing dependency"
  2. Press prefix [ to freeze the pane, then prefix PageUp from a fresh pane afterward to compare — notice it goes straight into copy mode already scrolled up.
  3. Search backward for the failure: ? then type ERROR and press Enter. Confirm the cursor lands on line 401.
  4. Begin a selection with v (or Space in the emacs table), extend it a line or two, and copy it with y (or Enter).
  5. Move to a different pane or window and paste with prefix ]. Then run tmux set -g mode-keys vi (or unset it) and repeat the search-and-copy with the other table's keys.
Common mistake

Assuming a tmux copy reaches the system clipboard on its own. prefix ] pastes into another tmux pane instantly, which feels like "copy and paste worked" — but a stock tmux install doesn't touch the operating system clipboard at all. Pasting into a browser tab, a chat window, or any application outside tmux needs an explicit bridge configured in tmux.conf: either set -g set-clipboard on, which asks the terminal emulator to honor an OSC 52 escape sequence (works even over SSH, if the terminal supports it), or a copy-pipe-and-cancel binding that pipes the selection through a local tool — pbcopy on macOS, xclip/xsel on X11, wl-copy on Wayland. Neither is automatic, and the pipe approach only reaches as far as the machine actually running that tool.

You can now reach backward through anything a pane has ever printed, find the line that matters without reading past it, and get a copy of it wherever you need it — inside tmux for free, outside it with one line of configuration. What's still open is the other half of "everyday navigation": work that keeps running whether or not you're watching it, and what to do with a pane once the thing inside it is a long build or a tailed log rather than a scrollback you're searching through once.
