tmux for Software Projects

Nine chapters have built the vocabulary — panes, splits, copy mode, bindings, a status line that actually tells you something. This one spends it on the shape almost every software project ends up needing: an editor, something watching your code and reacting to it, and a place to poke around. Two worked stacks — Elixir/Phoenix and Rust — show what that shape looks like with real commands in it, not placeholders.

The problem: the same three panes, assembled by hand, every time

Open a project, and the first few minutes look the same regardless of language: a pane for the editor, a pane for whatever's compiling or testing in the background, a pane free for ad hoc commands. Chapter eight's -c "#{pane_current_path}" overrides mean each new split at least lands in the right directory — but the panes still have to be split, and whatever's supposed to run continuously in each one still has to be typed and started, by hand, every session. That's tolerable once. It's the kind of tedium that's worth automating the moment it happens twice, which is exactly where chapter twelve is headed. This chapter is the shape worth automating: what actually goes in each pane, and why.

The shape: editor, watcher, scratch

Three roles, three panes, one window. The editor pane runs whatever you write code in. The watcher pane runs something long-lived that reacts to every save — a test runner, a build, a dev server — so failures surface within seconds of causing them, not minutes later when you remember to check. The scratch pane is just a shell, free for the one-off command that doesn't belong permanently in either of the other two. Laying it out is exactly the split-and-populate pattern from earlier chapters, with select-layout (chapter three) giving the arrangement a consistent final shape regardless of the order the splits happened in:

tmux new-session -d -s dev -n code -c "$PWD"
tmux split-window -h -t dev:code -c "#{pane_current_path}"
tmux split-window -v -t dev:code.2 -c "#{pane_current_path}"
tmux select-layout -t dev:code main-vertical
tmux attach -t dev

Populating the watcher pane from a script is chapter eight's send-keys in its most common real use: type the long-lived command into a specific pane and submit it with C-m, the same way a human would, just without waiting on a human to do it.

tmux send-keys -t dev:code.2 'iex -S mix phx.server' C-m
A fourth shape: the same command, many panes

Not every project is one machine. setw synchronize-panes on mirrors every keystroke typed into one pane across every other pane in the window — the documented use for it is running an identical command against several hosts or shells at once, each in its own pane. Turn it back off the moment the shared command is sent; left on, the next thing you type, pane-specific or not, goes everywhere.

Worked example: Elixir and Phoenix

A generated Phoenix app splits cleanly along the same lines a watcher pane cares about: lib/<app> holds domain logic, lib/<app>_web the controllers and views, test/ mirrors lib/'s structure, and assets/ holds the front-end source Phoenix's build pipeline bundles separately. The watcher pane's job is to keep the running server and the test suite both reacting to changes anywhere in that tree.

iex -S mix phx.server starts the Phoenix server exactly the way plain mix phx.server does, but boots it attached to Elixir's interactive shell — IEx — so application functions, Ecto queries, and IEx.pry breakpoints are all reachable while the server keeps serving requests. For tests, mix test --stale re-runs only the files whose modules actually changed since the last --stale run (the very first invocation always runs the full suite, to build that tracking manifest); mix_test_watch, a small third-party dependency, goes one step further and re-runs automatically on every save, no manual re-invocation needed.

# mix.exs, dev/test only
{:mix_test_watch, "~> 1.0", only: [:dev, :test], runtime: false}

# server pane, IEx attached
iex -S mix phx.server

# watch pane, re-runs automatically on save
mix test.watch

# one-off formatting pass, rules from .formatter.exs
mix format
#!/usr/bin/env bash
SESSION=phoenix_app
tmux new-session -d -s "$SESSION" -n app -c "$PWD"
tmux split-window -h -t "$SESSION":app -c "#{pane_current_path}"
tmux split-window -v -t "$SESSION":app.2 -c "#{pane_current_path}"
tmux send-keys -t "$SESSION":app.2 'iex -S mix phx.server' C-m
tmux send-keys -t "$SESSION":app.3 'mix test.watch' C-m
tmux select-layout -t "$SESSION":app main-vertical
tmux attach -t "$SESSION"

Editor in pane 1, server-with-IEx in pane 2, tests re-running on every save in pane 3. One C-c C-c — two presses, deliberately: a single Ctrl-c inside IEx opens its BREAK menu rather than exiting — and pane 2 stops cleanly.

Worked example: Rust

Rust's watcher pane leans on cargo-watch, a separate crate (cargo install cargo-watch once, up front — it doesn't ship with rustup/cargo) that re-runs a cargo command every time a source file changes. cargo watch -x run rebuilds and re-runs on every save; cargo watch -x test does the same for the test suite; and -x chains, so cargo watch -x check -x test only bothers running the (slower) test suite once the (faster) type-check passes.

# one-time install
cargo install cargo-watch

# watch pane: rebuild and run on every save
cargo watch -x run

# or watch pane: re-run tests on every save
cargo watch -x test

# chained: only test once check passes
cargo watch -x check -x test

# ad hoc
cargo fmt
cargo doc --open
#!/usr/bin/env bash
SESSION=rust_app
tmux new-session -d -s "$SESSION" -n app -c "$PWD"
tmux split-window -h -t "$SESSION":app -c "#{pane_current_path}"
tmux split-window -v -t "$SESSION":app.2 -c "#{pane_current_path}"
tmux send-keys -t "$SESSION":app.2 'cargo watch -x run' C-m
tmux send-keys -t "$SESSION":app.3 'cargo watch -x test' C-m
tmux select-layout -t "$SESSION":app main-vertical
tmux attach -t "$SESSION"

Same shape as the Elixir script above, same three roles — only the commands populating panes 2 and 3 changed. That's the point of naming the shape explicitly: once "editor, watcher, scratch" is the mental model, adapting it to a new language is a matter of substituting the right long-lived command, not redesigning the layout from scratch.

Key idea

The Elixir and Rust scripts above differ in exactly two lines — the two send-keys calls. Everything else, the session setup, the splits, the directory inheritance, the final layout, is identical. That's not a coincidence worth ignoring: it's the shape from chapter twelve's reproducible workspaces already halfway written. A per-project setup script is this same handful of lines with the watcher command swapped in.

A realistic workflow

Morning routine, either stack: run the setup script (or, before it exists, split and populate by hand), glance at the watcher pane's most recent output before touching the editor at all — it tells you whether you're starting from a clean state or picking up a failure from yesterday — then work. The scratch pane absorbs everything that doesn't belong permanently in the watcher: a one-off git log, a database console, a quick curl against the server the watcher pane is running. Keeping those out of the watcher pane means its output stays readable as a continuous stream of build/test results, not interleaved with unrelated commands.

Try it
  1. Pick whichever stack you have installed (Elixir/Phoenix or Rust), and adapt the matching script above to a real project directory of yours.
  2. Run it. Confirm all three panes land in the project directory, and that the watcher pane's command is genuinely running (not just typed and sitting unsubmitted).
  3. Edit a source file from the editor pane and confirm the watcher pane reacts within a few seconds with no manual re-run.
  4. In the scratch pane, run tmux list-panes -t app -F '#{pane_index}: #{pane_current_command}' and confirm it names the right long-lived process for panes 2 and 3.
Common mistake

Running a scratch command in the watcher pane. It's tempting — the watcher pane is right there, already open — but typing an unrelated command into it either interrupts the running watch process (Ctrl-cing cargo watch just to run git status) or, worse, gets silently swallowed by whatever's reading stdin. The scratch pane exists specifically so this never has to happen; reaching for it out of habit is cheaper than untangling a watcher pane's output after the fact.

Both scripts above assume the project is already on the machine you're running tmux on. The next chapter drops that assumption — the same panes, the same watcher commands, but running on a remote host, kept alive across a connection that will, eventually, drop.
