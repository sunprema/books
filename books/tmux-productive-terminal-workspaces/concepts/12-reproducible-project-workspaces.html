Reproducible Project Workspaces

The Elixir and Rust scripts from chapter ten build a whole workspace in four or five commands — genuinely useful, and genuinely incomplete. Run either one a second time against a session that's already up, and tmux either errors on the duplicate session name or, worse, splits an already-populated window into a mess of extra panes. This chapter closes that gap: one guard clause that makes any setup script idempotent, plus the two dedicated tools — tmuxp and tmuxinator — that trade the script for a declarative file when a project's shape is worth writing down once and sharing.

The problem: a setup script that only works once

Chapter ten's scripts assume a clean slate — no session named phoenix_app or rust_app already running. That's true the first time. It's not true the second time you open a terminal that morning, or when a script gets triggered from a login hook, or when a teammate runs the same script against a session you already built. tmux's own error for the collision is clear enough (duplicate session: NAME), but a script that just crashes on rerun isn't actually reusable — the fix is one check, run before anything else.

The idea: check first, build only if needed

tmux has-session -t NAME exits 0 if a session by that name exists and 1 (with an error printed to stderr) if it doesn't. Redirect that stderr and branch on the exit status, and a script can tell "already running, just reattach" apart from "doesn't exist yet, build it":

#!/usr/bin/env bash
SESSION=myproject

if tmux has-session -t "$SESSION" 2>/dev/null; then
  tmux attach -t "$SESSION"
  exit 0
fi

tmux new-session -d -s "$SESSION" -n editor -c "$PWD"
tmux split-window -h -t "$SESSION":editor -c "#{pane_current_path}"
tmux split-window -v -t "$SESSION":editor.2 -c "#{pane_current_path}"
tmux send-keys -t "$SESSION":editor.2 'npm run build:watch' C-m
tmux send-keys -t "$SESSION":editor.3 'npm test -- --watch' C-m
tmux select-layout -t "$SESSION":editor main-vertical
tmux attach -t "$SESSION"

Everything below the guard is exactly chapter ten's shape — splits, a watcher command, a scratch pane, a final layout. The guard is the only new idea, and it's what turns "a script that builds my workspace" into "a script I bind to a keystroke and never think about again."

Why not just use -A?

new-session -A -s NAME (chapter three, chapter eleven) collapses the check into the create call: it attaches if NAME already exists, or creates it fresh if not. That's exactly right for attaching — but it's a silent no-op on an existing session, which means a script that still needs to run its splits and send-keys setup only on first creation can't rely on -A alone. Without the explicit has-session guard, -A would happily let the rest of the script run again anyway, re-splitting an already-configured session. Use -A for reattaching; keep has-session for deciding whether setup should run at all.

Making chapter ten's scripts idempotent

The same three-line guard drops straight into either stack-specific script from chapter ten, unchanged apart from the session name and the two send-keys lines:

#!/usr/bin/env bash
SESSION=phoenix_app

if tmux has-session -t "$SESSION" 2>/dev/null; then
  tmux attach -t "$SESSION"
  exit 0
fi

tmux new-session -d -s "$SESSION" -n app -c "$PWD"
tmux split-window -h -t "$SESSION":app -c "#{pane_current_path}"
tmux split-window -v -t "$SESSION":app.2 -c "#{pane_current_path}"
tmux send-keys -t "$SESSION":app.2 'iex -S mix phx.server' C-m
tmux send-keys -t "$SESSION":app.3 'mix test.watch' C-m
tmux select-layout -t "$SESSION":app main-vertical
tmux attach -t "$SESSION"

Save that as bin/dev (or similar) in the project root, commit it alongside the code, and "start working on this project" becomes one command for anyone who clones the repository — not a paragraph in a README describing which panes to split and what to type into each one.

When a script isn't enough: tmuxp and tmuxinator

A hand-rolled script has no dependency beyond tmux itself, and for one person on one project, that's usually the right amount of tooling. Two dedicated tools exist for when it isn't — when a workspace's shape is complex enough, or shared widely enough, that a declarative file beats an imperative script: tmuxp (Python, YAML) and tmuxinator (Ruby, YAML). Both describe a session as data — name, windows, panes, per-pane commands — and build it with one command.

# tmuxp.yaml -- equivalent to the guarded Elixir script above
session_name: phoenix_app
start_directory: ~/code/phoenix_app
windows:
  - window_name: app
    layout: main-vertical
    panes:
      - shell_command:
          - vim .
      - iex -S mix phx.server
      - mix test.watch
tmuxp load ./tmuxp.yaml
# or, from a directory that contains a recognized config file:
tmuxp load .

The YAML says the same thing the script did — three panes, two long-lived commands — but as data rather than a sequence of tmux commands. That earns its keep once a workspace spans many windows, gets shared across a whole team's dotfiles, or benefits from being templated across similar projects; for one project with one straightforward pane shape, the plain script from earlier in this chapter is honestly just as fast to write and has nothing extra to install.

Key idea

A shell script, tmuxp's YAML, and tmuxinator's YAML are three different surfaces over the identical underlying operation: new-session, some split-windows, some send-keys. Reach for the script by default — it has no extra dependency and is trivial to read a year later. Reach for tmuxp or tmuxinator when the declarative shape (many windows, shared across contributors, generated from a template) genuinely earns the extra tool.

A realistic workflow

One script per project, named consistently (bin/dev across every repository, say), committed to version control alongside the code it sets up. Cloning a new project and running its bin/dev is the whole onboarding step for "how do I start working on this" — no README section to keep in sync with reality, because the script is the reality, checked by running it.

Try it
  1. Add the has-session guard to one of chapter ten's scripts (or the generic one above) and save it as bin/dev in a project directory.
  2. Run it twice in a row. Confirm the first run builds the full workspace and the second just attaches — no duplicate panes, no error.
  3. Detach (prefix d) and run the script a third time; confirm it reattaches to the exact session you left, watcher pane still running.
  4. If you have Python or Ruby available, install tmuxp or tmuxinator and translate the same script into its YAML equivalent. Run it and compare the result to the script's.
Common mistake

Skipping the guard because "I'll remember not to run it twice." You won't — not after the tenth time you open a terminal that day, not when the script gets wired into a login hook or a teammate runs it without knowing a session's already up. The three-line has-session check costs nothing to include up front and removes an entire category of "why do I have six panes now" debugging later.

A workspace that rebuilds itself on demand is one piece of automation. The next part turns from building sessions to driving them — scripting tmux directly, curating the plugin ecosystem deliberately, and making sure a session survives not just a dropped connection but a full reboot.
