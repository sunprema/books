Scripting tmux

new-session -d, split-window, send-keys ... C-m — chapters ten and twelve already used all three from a shell script, because there was never a separate scripting API to introduce. That's the actual point worth stating plainly: every tmux command is available identically from a script, from prefix :, and from a key binding. This chapter fills in the rest of that toolkit — reading a pane's output back into a script, running conditional logic, and signaling between a driving script and a command running inside tmux — the pieces chapters ten and twelve didn't need yet.

The problem: a script that can only write, not read

Every script so far has been one-directional: type a command into a pane, never check what happened. That's fine for starting a long-lived watcher, but it falls apart the moment a script needs to know something back — did the build that just ran actually succeed, what's the current pane's live directory, is a background command finished yet. Those all have answers tmux already knows; the gap is a way for a script to ask.

Targets: naming exactly which pane

Every command that acts on a specific place takes -t session:window.pane — chapter ten's scripts already used dev:code.2 without dwelling on it. The session part matches by exact name first, then by name-prefix, then as an fnmatch(3) pattern; prefixing it with = forces an exact match only, which matters once you have both a work session and a work-2 session and don't want a loosely-matched script accidentally landing in the wrong one.

Reading a pane back: capture-pane and display-message

capture-pane -p prints a pane's contents to stdout instead of into a paste buffer — the piece that turns "type into a pane" into "pipe a pane's output into grep." By default it only grabs the currently visible screen; -S and -E set the starting and ending lines to reach into scrollback (-S -100 for the last hundred lines, -S - for the entire history), and -J joins wrapped lines back into one, useful when a long single line of output got soft-wrapped by the pane's width.

# does the visible screen mention an error?
tmux capture-pane -p -t mysession:0 | grep -i error

# the last 100 lines of scrollback, wrapped lines rejoined
tmux capture-pane -p -J -S -100 -E - -t mysession:0

display-message -p 'format' is the equivalent move for a single live value rather than a pane's full text — it prints a format string (the same #{...} language from chapter nine's status line) to stdout, expanded, so a script can capture it into a variable:

current_pane=$(tmux display-message -p '#{pane_id}')
echo "$current_pane"

Conditional and background execution

if-shell shell-command command [else-command] runs shell-command through /bin/sh and executes command on success, else-command otherwise — the mechanism for a config file that needs to branch on something the shell can test, like which OS it's running on. run-shell shell-command fires a background shell command with no pane or window created for it; without -b (backgrounded) and if the command produces output, that output briefly appears in copy mode in the target pane once it finishes.

# in tmux.conf: OS-specific clipboard setup
if-shell "uname | grep -q Darwin" "set -g default-command 'reattach-to-user-namespace -l $SHELL'"

# fire a background notification script from a binding
run-shell "~/.tmux/scripts/notify.sh"
Both of these can stall tmux

if-shell and run-shell both block tmux's command queue until the shell command finishes, unless run-shell is explicitly backgrounded with -b. A slow check placed directly in tmux.conf — a network call, a slow disk stat — visibly stalls every subsequent line of config from loading, or stalls whatever key binding triggered it. Keep shell-outs in configuration fast, or background them.

Signaling between a script and a pane: wait-for

wait-for channel, called plainly, blocks the calling client until another process runs wait-for -S channel against that same channel name — a simple rendezvous primitive for the case where a driving script needs to know a command inside a pane has actually finished, not just that it was launched:

# inside the pane, appended after the real work finishes:
tmux wait-for -S build-done

# in the driving script, blocks until the pane signals:
tmux wait-for build-done
echo "build finished"

A realistic workflow: a checked build script

Putting several of these together: open a session with panes each running a different long-lived command (the chapter ten/twelve shape), then use capture-pane to check one pane's recent output before deciding what to do next — a smoke test that confirms a server actually came up before running anything against it, without a human ever watching the pane directly.

#!/usr/bin/env bash
set -euo pipefail
SESSION=checked

tmux new-session -d -s "$SESSION" -n main
tmux split-window -h -t "$SESSION":main
tmux split-window -v -t "$SESSION":main.1
tmux select-layout -t "$SESSION":main tiled

tmux send-keys -t "$SESSION":main.0 'tail -f /var/log/syslog' C-m
tmux send-keys -t "$SESSION":main.1 'htop' C-m
tmux send-keys -t "$SESSION":main.2 'npm run dev' C-m

sleep 3
if tmux capture-pane -p -t "$SESSION":main.2 | grep -qi 'ready'; then
  echo "dev server is up"
else
  echo "dev server did not report ready in time"
fi

tmux attach -t "$SESSION"
Try it
  1. Adapt the script above to a project you have, swapping npm run dev for a real long-lived command and the grep pattern for text that command actually prints on success.
  2. Run it, and confirm the "is up" check reports correctly both when the command starts cleanly and (comment out the real command to test) when it doesn't.
  3. Add a wait-for pair: append ; tmux wait-for -S done to one pane's send-keys command, then add a bare tmux wait-for done to the script right before the final attach, and confirm the script now blocks until that pane's command actually finishes.
Common mistake

Reading a pane's output before the command has had time to produce any. send-keys returns as soon as the keystrokes are delivered, not when the program they started has produced output — a capture-pane or wait-for placed immediately after a send-keys call for a slow-starting program will see an empty or half-started pane. A short sleep, a wait-for signal from inside the pane itself, or a loop polling capture-pane for expected text are all more reliable than assuming the command has already produced its output by the next line of the script.

Scripting drives tmux from the outside. Plugins extend it from the inside — and unlike everything in this chapter, a plugin's code runs automatically, on every start, whether or not you remember what it does. That's worth being deliberate about, next.
