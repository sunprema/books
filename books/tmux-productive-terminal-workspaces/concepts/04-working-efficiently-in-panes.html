Beyond splitting: shaping the room you built

Working Efficiently in Panes

You can split a window, move focus between the pieces, and close the ones you don't need — that's the whole toolkit from the last chapter. What it doesn't cover is what happens after the third or fourth split, when the layout you hand-built no longer looks like the layout you wanted, and you're nudging borders one at a time trying to get back to something usable. This chapter is about not doing that: shaping panes on purpose, in one motion, instead of fighting them into shape one cell at a time.

The problem: hand-splitting doesn't scale past two panes

Two panes, side by side, is easy — one split key and you're done. Add a third and a fourth, though, and the arithmetic stops being obvious. Splitting a pane always divides that pane in half, so a third split rarely lands where you'd have drawn it if you were laying the window out from scratch. You end up nudging pane borders with the arrow keys, one cell at a time, trying to reverse-engineer a layout you could have just asked for. And once you have several panes running related things — three ssh sessions into three hosts, say — typing the same command into each of them separately is its own kind of tedious, and easy to get wrong on the third or fourth repetition. Both problems have the same shape: you're doing by hand, pane by pane, something tmux already knows how to do for the whole window at once.

The idea: ask for a layout, don't build one

tmux ships five built-in layouts — named arrangements it can reflow any number of panes into instantly, without you specifying a single border. even-horizontal and even-vertical spread every pane equally side by side or stacked; main-horizontal and main-vertical give one pane a big primary slot and line the rest up in a strip beside it; tiled packs every pane into as even a grid as the count allows. prefix Space cycles through all five in order — the fastest way to find one that fits — and each is also reachable directly, so you can jump straight to the one you want instead of cycling past four others to get there.

Key idea

Reach for a layout when the whole window's arrangement is wrong — prefix Space or a direct prefix Alt-N reflows every pane in one step. Reach for resize-pane only when one specific border, in an otherwise-correct layout, needs to move. Nudging borders to reinvent a layout tmux already ships is the tell that you skipped the faster option.

When you do need to resize: fine and coarse

Sometimes a layout is almost right and one border just needs to move — the editor pane wants three more columns, the log pane at the bottom is stealing too many rows. resize-pane handles that, and it's bound at two speeds so you're not stuck picking one: holding Ctrl with an arrow key moves the border one cell at a time, for a precise nudge; holding Meta (Alt, on most keyboards) with an arrow key moves it five cells, for a bigger jump. Both are repeatable — press prefix once, then keep tapping the arrow, and tmux keeps listening for a short window (the repeat-time option, half a second by default) before it goes back to expecting a fresh prefix.

Prefix, then… Command What it does
Ctrl+arrow resize-pane -{U,D,L,R} Nudges the border one cell (repeatable while held)
Meta/Alt+arrow resize-pane -{U,D,L,R} 5 Jumps the border five cells (repeatable while held)
Space next-layout Cycles to the next of the five built-in layouts
Alt-1 – Alt-5 select-layout <name> Jumps directly: even-h, even-v, main-h, main-v, tiled
Ctrl-o rotate-window Rotates every pane's content forward one position in the layout

rotate-window is the odd one out in that table, and worth a sentence: it doesn't change the layout's shape at all, it spins the panes' contents around it. If your editor ended up in the small pane and the log tail is hogging the big one, prefix Ctrl-o walks each pane's content into the next slot — often faster than swapping two panes by hand.

Typing once, running everywhere: synchronize-panes

Layouts and resizing are about how panes look. synchronize-panes is about how they behave: turned on for a window, every keystroke you type into the focused pane — not just visible characters, but backspaces and cursor moves too — gets sent to every pane in that window at once. Split a window into three panes, open an SSH connection to a different host in each, turn synchronization on, and one typed command runs identically on all three, in lockstep, as if you'd typed it three times.

# three hosts, one command each, typed once
tmux new -s fleet
Ctrl-b %
Ctrl-b %
# ssh into a different host in each of the three panes, then:
Ctrl-b :setw synchronize-panes on

sudo apt update

# turn it back off the instant the parallel part is done
Ctrl-b :setw synchronize-panes off
Turn it off the moment you're done

Synchronization is a window-wide setting, not a one-shot action — it stays on until you turn it off, and every keystroke you type after that, including ones meant for just one pane, still fans out to all of them. Typing rm -rf build/ meaning it for one host and having it land on three is exactly the failure this feature makes possible. Make turning it off a reflex, not an afterthought.

Moving a pane between windows

The last chapter covered break-pane, which pulls a pane out into a window of its own. join-pane (and its mirror, move-pane) does the reverse: it takes a pane that already exists in one window and moves it into another, joining it as a new split there. Both take a source and a target and an optional -h/-v for which way the new split should run — the same orientation flags split-window uses, with the same “names the line, not the layout” rule from the last chapter.

# move pane 1 of window 2 into window 1, as a new right-hand split
tmux join-pane -h -s fleet:2.1 -t fleet:1

Reach for it when a pane you split off in the wrong place — or a pane that used to belong somewhere else entirely — turns out to actually belong next to what you're looking at now. It's rarer than splitting or breaking out, but it's the one command that reorganizes without losing the pane's running program in the process.

If you'd rather use the mouse

Everything above has a mouse equivalent once set -g mouse on is in your config (covered properly in the configuration chapter): click a pane to focus it, drag a pane border to resize it, click a window's name in the status line to switch to it. It's a fair way to work, especially while these bindings are still new — just know that turning mouse mode on hands pane selection and drag-resize to tmux, so your terminal's own click-and-drag text selection needs a modifier key (terminal-specific) to reach it instead.

A realistic workflow

Two habits, not one, is what “working efficiently in panes” actually means day to day. First: when a window's shape is wrong, reach for prefix Space or a direct prefix Alt-N before you touch a single border — four panes almost always want tiled, and an editor-plus-helpers window almost always wants main-vertical with the editor pinned in the big slot. Second: the moment a task is genuinely parallel — the same deploy step on three servers, the same restart across two services — split once, synchronize, type it once, and switch synchronization off again before the next thing you type is meant for just one pane. Neither habit saves much on its own. Together, across a normal week, they're the difference between a session that stays tidy and one you keep silently fighting.

Try it
  1. Start a session and split it into four panes any way you like: tmux new -s lab, then prefix % and prefix " a couple of times.
  2. Press prefix Space repeatedly and watch all five layouts go by; stop on tiled and confirm every pane is an even rectangle.
  3. Jump straight to main-vertical with prefix Alt-4, then use prefix Ctrl-o twice and watch which pane's content ends up in the large slot each time.
  4. Turn synchronization on: prefix :setw synchronize-panes on. Type echo hi and confirm it appears in every pane. Turn it back off the same way, with off.
  5. From outside the session (a separate terminal, not attached), run tmux resize-pane -t lab:1.0 -R 10 and confirm pane 0 grew when you switch back to it.
Common mistake

Leaving synchronize-panes on after the parallel task is over. It's easy to turn it on for one command, get the output you wanted, and move straight on to the next thing without remembering to turn it back off — and the next thing you type goes to every pane in the window, silently. There's no confirmation prompt the way there is for closing a pane; the only signal is whatever's on your screen suddenly happening in triplicate. Build the habit of typing the off as part of the same breath as the on, not as a separate step you'll remember later.

You now have real control over the shape and behavior of a window full of panes: layouts instead of hand-splitting, precise or coarse resizing when a layout is almost right, synchronization for genuinely parallel work, and a way to relocate a pane that ended up in the wrong window entirely. What's still missing is what to do once a pane has scrolled past what's visible — how to look back at output that's gone, search through it, and pull a piece of it out to paste somewhere else. That's next.
