Remote Development with SSH

Every chapter so far assumed tmux was running on the machine in front of you. Run it on a remote host instead, over SSH, and one property changes everything else that follows: the tmux server keeps running on that remote host regardless of what your local network connection does. This chapter is about designing around that fact deliberately — one command to always land back in the same place, and the one genuine wrinkle, nested tmux, that shows up the moment you run tmux locally too.

The problem: a dropped connection used to mean lost work

SSH straight into a remote host with no tmux involved, and the shell you're working in is a child process of that one SSH connection. Close the laptop lid, lose Wi-Fi, let the VPN hiccup — the connection drops, and whatever was running in that shell dies with it: a long build, a REPL session, a `tail -f` you'd been watching. Reconnecting gets you a fresh shell in the same directory, nothing else preserved. tmux breaks that dependency entirely, but only if the session lives on the far end of the connection, not this end.

The idea: attach-or-create, one command every time

One command covers both "I've never connected today" and "I'm reconnecting after a drop":

ssh myhost -t tmux new -A -s work

The -t on the ssh side forces a pseudo-terminal — required, since tmux needs a real tty to attach to. On the tmux side, new-session -A -s work (chapter three's -A flag) attaches to a session named work if one already exists on that host, or creates it fresh if it doesn't. Same command, every single connection, whether it's the first of the day or the fifth reconnect after a flaky hotel Wi-Fi dropped you three times.

Detaching on purpose vs. the network doing it for you

tmux is a client–server program (this has been true since chapter two, just not load-bearing until now): the server is a background process on the remote host, and every terminal that attaches to it — including the one SSH just gave you — is a client the server outlives. Pressing prefix d detaches that client deliberately. The SSH connection simply dying does the exact same thing to the server's view of things: a client disappeared, the session it was attached to keeps running. Neither path kills a single process inside the session, because none of those processes are children of the SSH connection — they're children of the tmux server, which has its own life on the remote host independent of any client.

The one wrinkle: nested tmux

Run tmux locally and SSH into a session that's also inside tmux, and two servers are now stacked in the same terminal. Every shell running under tmux carries a TMUX environment variable — the server's socket path, PID, and session ID — which is how tmux itself detects it's already nested; in some cases it prints "sessions should be nested with care, unset $TMUX to force." The practical symptom is simpler than the warning sounds: your prefix key now belongs to whichever session is innermost, because that's the one actually reading your keystrokes first. Every plain prefix binding you press reaches the remote session; the local one never sees it.

# reach the OUTER (local) session's prefix by pressing the prefix twice
C-b C-b
# then whatever command you meant for the outer session, e.g.:
C-b C-b d

That works because prefix+C-b is bound, by default, to send-prefix — chapter eight's exact mechanism for sending a prefix key through literally instead of letting it get intercepted. If double-tapping feels awkward every time, the other fix is chapter eight's remap applied asymmetrically: give the local tmux a different prefix (say C-a) and leave the remote one on its default C-b, so C-a always unambiguously means "outer" and C-b always means "inner," with no double-press needed for either.

Keeping the link itself from dropping

tmux surviving a drop doesn't mean drops are free — reconnecting still takes a moment, and a NAT or load balancer with an aggressive idle timeout can close an SSH connection that's just sitting quiet while you read something in the pane. ServerAliveInterval in ~/.ssh/config sends a keepalive after N seconds of silence; set it comfortably below whatever idle timeout you're working around, not equal to or above it, or the keepalive arrives too late to matter.

Host myhost
    HostName example.com
    User dev
    ServerAliveInterval 30
    ServerAliveCountMax 3

A different problem: mosh

tmux keeps session state alive across a disconnect. It does nothing for the disconnect itself being annoying to sit through — a laptop moving from Wi-Fi to cellular still has to fully reconnect. mosh (mobile shell) solves that different, complementary problem: it uses SSH only once, for the initial handshake, then hands off to its own UDP-based protocol tied to an encryption key rather than a fixed IP or TCP connection — which is what lets it survive a laptop roaming across networks in ways a TCP-based SSH session structurally can't. The two compose directly, each covering what the other doesn't:

mosh myhost -- tmux new -A -s work

mosh keeps the link itself alive through network changes; tmux keeps the session — the running processes, the scrollback, the pane layout — alive through the client disappearing altogether. One honest caveat: mosh needs its own UDP port range reachable in addition to SSH's TCP/22, so a network that only opens 22 outbound lets the initial handshake through but the session itself hangs; it's a real deployment consideration, not just an install step.

A realistic workflow

One alias, used everywhere: alias work='ssh myhost -t tmux new -A -s work', run from a laptop, a second machine, or a phone SSH client, always landing in the same place with the same panes from chapter ten's project shape still running. A dropped connection on the train is a five-second reconnect, not a lost afternoon of build output.

Try it
  1. SSH into a remote host (or a local VM/container if that's what you have) with ssh host -t tmux new -A -s work. Start something long-lived in it — a tail -f on a log file, or a build.
  2. Close the terminal window entirely (not a graceful detach) rather than disconnecting cleanly. Reconnect with the exact same command and confirm the long-lived process is still running, undisturbed.
  3. From inside that remote session, start a local tmux on your own machine in a second terminal, if you don't already have one running, and SSH into the same remote session from a pane inside it — deliberately nesting. Practice reaching the outer session with C-b C-b.
  4. Add a ServerAliveInterval 30 line to that host's entry in ~/.ssh/config and leave the connection idle for a few minutes to confirm it doesn't silently drop.
Common mistake

Panicking when a dropped connection looks like data loss. The pane goes blank or the terminal shows a "connection closed" message, and the instinct is to assume whatever was running just died. It almost certainly didn't — the tmux server on the remote host is unaffected by a client vanishing. Reconnect with the same attach-or-create command before concluding anything was lost; the far more common actual mistake is running tmux only locally for remote work in the first place, which offers no such protection because the session dies with the SSH connection it's layered on top of.

Reattaching to the right session is only useful if the session was worth rebuilding in the first place — the next chapter turns the setup scripts from chapter ten into something that runs itself the moment a project needs a workspace, remote or local.
