Collaboration and Shared Sessions

tmux is a client–server program — chapter eleven leaned on that for surviving a dropped SSH connection, but the same architecture has a second consequence: nothing stops a second client from attaching to the same server at the same time. Two people, same panes, same keystrokes landing in the same place, live. This chapter covers doing that on purpose, two ways — native tmux sharing on a machine you both already trust, and tmate, a fork built specifically for handing a stranger a link — and the genuinely different trust model each one carries.

The problem: pairing without a dedicated tool for it

Screen-sharing software shows someone your screen. It doesn't hand them a real terminal they can type into, and setting up simultaneous SSH access for a one-off pairing session means creating an account, or sharing credentials, for something that should take thirty seconds to arrange and thirty seconds to tear back down. tmux already has the mechanism — the same server, two clients — sitting unused in every session you've ever opened.

Native sharing: the same server, a second client

Any client that attaches to the same tmux server — the default socket, or the same path given to -S socket-path — is looking at the same session, the same panes, the same running processes. By default, the socket directory tmux creates for itself must not be world readable, writable, or executable, so out of the box this only works for the same Unix user. A second real person needs either a shared login (rare, and its own security question) or an explicit, intentionally loosened socket:

# host machine
tmux -S /tmp/shared_socket new -s pair
chmod 777 /tmp/shared_socket

# the second person, same machine or same LAN with access to it
tmux -S /tmp/shared_socket attach -t pair

Once attached, there is no built-in permission tier — tmux does not distinguish "owner" from "guest." A second client that attaches normally can type into any pane exactly as the first can, because both clients are driving the same underlying processes. That's the whole feature and the whole risk in one sentence: whatever privilege level the session's shell already has — including an active sudo, if there is one — is now shared too, with no record inside tmux of which attached client typed what.

The one built-in mitigation

tmux attach -t pair -r attaches read-only: while a client is in that state, only keys bound to detach-client or switch-client do anything at all — the viewer can watch, but cannot type into or resize the session. It's the one-way pairing mode, and it only happens if the person attaching remembers the flag; there is no way to force a second client into read-only from the session's side after the fact.

tmux attach -t pair -r

attach -d is the opposite move — it detaches whichever other client is already attached before taking the session over solo, useful for reclaiming a session you meant to have to yourself, and a reminder that leaving -d off is what lets two clients stay attached simultaneously in the first place.

tmate: sharing with someone who isn't on your machine at all

Native sharing assumes the other person already has some path to your machine — same box, same LAN, an account you're willing to create. tmate, a maintained fork of tmux built specifically for instant sharing, removes that assumption entirely. Running the bare tmate command starts a session and, with zero server configuration on your end, prints ready-to-use connection strings — no shared account, no socket permissions to loosen, no inbound port to open, because the sharing works by your machine making an outbound connection to a tmate server.

tmate
# prints four connection strings:
#   ssh <token>@<region>.tmate.io          -- read-write
#   ssh ro-<token>@<region>.tmate.io       -- read-only
#   https://tmate.io/t/<token>             -- read-write, web
#   https://tmate.io/t/ro-<token>          -- read-only, web

tmate show-messages    # reprint them if the banner already scrolled away

The remote person needs nothing but an SSH client, or a browser for the web links — no account on your machine, no network path you had to open for them specifically. That's the entire appeal, and it comes from a real architectural difference, not a convenience wrapper: by default, a tmate session's traffic is relayed through tmate.io's own public servers. That's a materially different trust model from native sharing on a machine you both already have access to — a third party now sits on the connection path. tmate can be self-hosted (the open-source tmate-ssh-server, pointed at from a client's ~/.tmate.conf) to remove that relay, at the cost of running and exposing that server yourself.

Choosing between them

Native sharing wins when the other person is trusted and already reachable — same machine, same LAN, a colleague with legitimate access — because it avoids the extra network hop and, self-hosting aside, the third-party relay tmate always introduces. tmate wins when the other person is remote, unprovisioned on your machine, and you need a link working in the next thirty seconds — no user creation, no socket permissions, no firewall change required on your end.

A realistic workflow

Pairing with a teammate already on the same server: a shared socket under /tmp, torn down (rm) the moment the pairing session ends, rather than left world-writable indefinitely. Helping someone remote debug a problem on their own machine: they run tmate, paste you the read-write link, and it's over the moment they close that terminal — no cleanup on your end at all, and no standing access left behind either way.

Try it
  1. On one machine, start a shared session with an explicit socket and loosened permissions as above. From a second terminal (simulating a second person), attach to that same socket and confirm typing in one terminal appears in the other.
  2. Attach a third terminal with -r and confirm it can watch but that its keystrokes do nothing to the shared pane.
  3. If you have tmate installed, run it, copy the read-only link, and open it from a different device or browser to confirm the read-only web view works with no account.
  4. Clean up: remove the socket file you created in step 1, and confirm a new attach -S /tmp/shared_socket now fails since nothing is listening there anymore.
Common mistake

Assuming "sharing my session" means "showing my screen." It doesn't — by default it means granting full type access to whatever's running in every pane, sudo included, with no per-client permission boundary and no log of who typed what. If the goal is genuinely watch-only, the -r flag (native) or the ro- link (tmate) has to be chosen deliberately; it is never the default for a normal attach.
