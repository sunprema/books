One session, many rooms, many desks

Sessions, Windows, and Panes

You can already start a session, detach from it, and come back. That's the whole toolkit for keeping one thing alive. This chapter is about what happens the moment one thing becomes several — an editor, a test runner, a log tail, a shell for stray commands — all inside the same session, without you juggling four separate terminal windows to hold them.

The problem: one shell isn't enough, four terminals is too many

A session gets you persistence, but by itself it's still just one shell. Real work rarely fits in one shell: you want an editor open, a test suite running in the background, a log streaming somewhere you can glance at, and a spare prompt for git and one-off commands — all at once, all part of the same piece of work. You could open four separate terminal tabs for that, but then you're back to the problem from chapter one: four unrelated processes with no shared lifecycle, nothing to detach as a unit, nothing that survives together. What you actually want is a way to have several things going inside one session, organized so you can look at them one at a time or side by side, and switch between them without losing your place.

The idea: a session is a list of windows, a window is a grid of panes

tmux answers this with two more layers underneath the session you already know, and the whole hierarchy is strict: a server holds any number of sessions; a session holds one or more windows; a window holds one or more panes. A window is a single full-screen layout — think of it as one tab, occupying the whole terminal when it's the active one. A pane is a rectangle inside that layout with its own shell or program running in it. You can have several panes in one window, side by side or stacked, but you only ever see one window at a time; switching windows swaps the entire layout, while splitting panes subdivides the layout you're already looking at.

Key idea

Reach for a window when you want a whole separate full-screen context — a different concern, like “my editor” versus “my test runner” versus “a scratch shell.” Reach for a pane when you want two things visible at the same time, side by side — an editor next to the log it's writing to, a shell next to the process it's watching. Windows are for switching between; panes are for looking at together.

Naming a place: the target syntax

Because everything nests, tmux needs a way to point at one specific pane out of potentially dozens. It uses a single compact string: session:window.pane — a colon between session and window, a period between window and pane. work:1.2 means “pane 2 of window 1 in session work.” You'll type this constantly once you start scripting tmux from the outside (a later chapter), and you'll see it everywhere tmux itself prints status. For now, the one detail worth committing to memory: window and pane numbers start at 0, not 1, unless you change that later in configuration. Reach for window “the first one” and it's index 0, not 1 — a small thing that trips up almost everyone exactly once.

Prefix, then… Command What it does
c new-window Creates a new window in this session and switches to it
, rename-window Prompts for a name for the current window
n / p next-window / previous-window Steps to the next / previous window in order
0–9 select-window -t N Jumps straight to window index N
w choose-window Opens an interactive, searchable list of every window to pick from
l last-window Toggles back to whichever window you were just on
& kill-window Closes the current window (asks for confirmation)

Splitting a window into panes

Panes come from splitting a window, and this is where tmux's defaults genuinely confuse people at least once, so let's get it straight the first time. The two split keys are % and ", and they name the dividing line, not the resulting arrangement:

Once you have more than one pane, you need to move between them and occasionally get rid of one. The moves are short on purpose — you'll use them dozens of times a session:

Prefix, then… Command What it does
% split-window -h Splits with a vertical line — left / right panes
" split-window -v Splits with a horizontal line — top / bottom panes
arrow key select-pane -{U,D,L,R} Moves focus one pane over, in that direction
o select-pane -t next Cycles focus to the next pane, no direction needed
q display-panes Flashes a number over every pane; press one to jump to it
z resize-pane -Z Zooms the current pane to fill the window; press again to undo
x kill-pane Closes just this pane (asks for confirmation)
! break-pane Promotes this pane out into its own new window

Two closing rules worth knowing before you hit them by surprise: a pane closes itself, no confirmation needed, the instant the program inside it exits on its own — that's just a shell ending normally. And the nesting is real all the way down: close the last pane in a window and the window closes with it; close the last window in a session and the session itself ends.

Hands-on: build a real layout, from the outside and the inside

Everything above works two ways: typed as prefix key-combos from inside a running session, or as full tmux subcommands from an ordinary shell (useful for scripting, which comes later). Both address the same objects through the same target syntax. Try the interactive path first — it's the one you'll use ten times an hour:

# start clean
tmux new -s work

# split the window: editor on the left, a spare shell on the right
Ctrl-b %

# split that right pane again: shell on top, log tail below
Ctrl-b "

# move focus around with the arrow keys
Ctrl-b Left
Ctrl-b Down

# open a second window for the test runner — a separate concern,
# not another pane crammed into this layout
Ctrl-b c
Ctrl-b ,   # rename it: type "tests", Enter

# flip back to the editor window and back again
Ctrl-b l

Now the same operations, addressed from outside the session by name — this is the form scripts and one-liners use, so it's worth typing once even though you'll rarely need it interactively:

# add a window named "tests" to the running "work" session,
# without attaching to it
tmux new-window -t work -n tests

# split that window's active pane, left/right, from outside too
tmux split-window -h -t work:tests

# jump straight to pane 2 of window 1
tmux select-pane -t work:1.2

# ask what's actually there before you trust your mental model of it
tmux list-windows -t work
tmux list-panes -t work:1

A realistic workflow

In practice the split between windows and panes settles into a habit fast: one window per concern, panes only for things you need to see together. A typical work session ends up with an editor window (split into an editor pane and a scratch shell pane beneath it for quick git commands), a tests window running a watcher, and a logs window tailing whatever the app is writing. You flip between the three windows with prefix n / prefix p or jump straight there with a number, and inside the editor window you glance down at the scratch pane without ever leaving it. Nothing here required more than one session — the session was never the unit of “one thing,” it was always the container for everything this piece of work needs.

Don't trust the flag name from memory

split-window -h is the one bound to %, and it gives you left/right panes — “horizontal” describes the cut, not the stacking. If you ever script a split and the panes come out sideways from what you expected, this is almost always why. When in doubt, just try the prefix key and look: % for side-by-side, " for stacked.

Try it
  1. Start a fresh session: tmux new -s lab.
  2. Split it left/right with prefix %, then split the right pane top/bottom with prefix ". You should have three panes.
  3. Use the arrow keys to visit all three, then use prefix q and jump to pane 0 by pressing its number.
  4. Zoom the current pane with prefix z, confirm it fills the window, then press prefix z again to unzoom.
  5. Open a second window with prefix c and rename it side with prefix ,.
  6. From outside tmux (open a plain terminal, don't attach), run tmux list-windows -t lab and confirm you see both windows and their indexes.
  7. Back inside, toggle between the two windows with prefix l, then close the side window with prefix &.
Common mistake

Cramming everything into panes because splitting feels faster than opening a window. It's tempting to just keep hitting prefix % until you have five slivers of terminal, each too narrow to read comfortably. Panes are for things you genuinely need side-by-side right now; anything else — a different task, a different phase of the same task — belongs in its own window, where it gets the full width of your terminal and a name you can find later with prefix w. If you find yourself squinting at a sliver, that's the signal: break it out (prefix !) into its own window instead of shrinking your eyes to fit tmux's layout.

You now have the whole shape of the model: a server holding sessions, sessions holding named windows, windows holding panes you split and arrange on purpose. That's the map. What you haven't practiced yet is living in it — resizing panes without fighting the layout, cycling through built-in arrangements instead of hand-splitting every time, and keeping panes in sync when you genuinely want the same keystrokes going to several of them at once.
