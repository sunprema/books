About this book

EDI is usually taught as a file format, which is why so many EDI integrations are brittle. It is better understood as a reliability problem: documents arrive out of order, arrive twice, or fail to arrive at all, and a trading partner's implementation guide — not your architecture — decides what a valid document looks like.

We build one thing throughout: an order‑to‑cash integration that receives purchase orders and sends acknowledgments, invoices and shipment notices. Every chapter introduces a mechanism, implements a focused piece of that service, and ends with the failure modes it exists to survive.

How to read it

Chapters 1–6 are orientation: what EDI is, who the actors are, what a document looks like, and which transactions a first implementation actually needs. If you have been handed a partner's implementation guide and a deadline, start at chapter 3 and read forward.

Chapters 7–13 are the build, and they are the heart of the book. Chapters 14–16 cover delivering it to a real trading partner. The appendices are written to be returned to rather than read once.

A note on examples

Every EDI fragment in this book uses one running example — purchase order PO-88213 from ACME Retail to Widget Supply — so you can follow the same order from envelope to invoice without re-learning a new set of identifiers each chapter.
