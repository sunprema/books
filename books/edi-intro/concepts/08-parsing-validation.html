Chapter EightParsing and Validation

The parser is the easy half. The validator is where the partner relationship is actually managed — and where a bad error message costs someone a day.

Let's write the tokenizer first, because it is short and it settles chapter 3's warning about delimiters into code. Everything hinges on the ISA being exactly 106 characters wide.

def read_delimiters(raw: str):
    if not raw.startswith("ISA"):
        raise ValueError("not an X12 interchange")
    element    = raw[3]      # the char right after 'ISA'
    isa        = raw[:106]    # fixed width: exactly 106 chars
    component  = isa[104]    # ISA16
    terminator = raw[106]    # first char after the ISA segment
    repetition = isa[82]     # ISA11, in 005010 and later
    return element, component, terminator, repetition

That is the whole trick. The fixed width exists precisely so a parser can discover the punctuation before it knows the version — a small piece of 1970s design that has aged remarkably well.

Split carefully

Once you have the delimiters, do not reach for a naive split(). EDIFACT allows a release character (? by default) that escapes a delimiter inside a value, so Widget 10mm ?+ washer is one element, not two. Scan character by character honouring the release, or use a library that does.

Three layers of validation

Validation is not one pass. It is three, and they must run in this order because each assumes the previous one succeeded.

Structural checks are cheap and catch catastrophes: required segments present, loops opened and closed, element lengths and data types within their declared bounds, and — do this first of all — the trailer counts. If SE01 says nine segments and you counted seven, the file is truncated and every semantic error you are about to report is noise.

Semantic checks ask whether the values mean anything: is CA a unit of measure this partner uses, does the line total match quantity times price, is the requested delivery date in the future, does the ship-to identifier resolve to a known location.

Partner guide checks are the ones that get documents rejected in production. The guide marks optional segments required, fixes code lists to a subset, and adds rules the standard never contemplated ("REF*DP is mandatory for store-direct orders"). These are layered over the base rules, per partner, and they must be data — configuration, not branches in code — because a new partner should not require a deploy.

Error reporting that a human can act on

Chapter 5 showed how a 997 addresses a fault: group, transaction set, segment, position, element, reason. Your internal findings should carry exactly that address, because it is the only vocabulary both you and the partner share.

{
  "severity": "error",
  "interchange": "000000117",
  "group": "38",
  "transactionSet": "0001",
  "segment": "PO1",
  "segmentPosition": 12,
  "element": 3,
  "rule": "acme-retail/uom-allowed",
  "message": "unit of measure 'BX' is not in this partner's allowed list (CA, EA, PL)"
}

Compare that with "validation failed". The first can be pasted into an email to the partner's EDI coordinator and resolved in one exchange; the second starts an investigation. The rule field earns its place too — it names the specific partner rule, which tells a maintainer where to look and lets you count which rules actually fire.

Reject at the right granularity

One bad transaction set does not invalidate the interchange. The standard lets you accept a group partially, so your validator should collect findings per transaction set and let the pipeline decide the group outcome — rather than throwing on the first error and discarding nineteen good orders.

Don't trim what you can't see

Several X12 elements are fixed-width and space-padded — the ISA's sender and receiver ids most conspicuously. A blanket .strip() across every element will silently change identifiers that a partner matches on exactly. Trim where the guide says the field is variable-length, not everywhere.

So what did we actually gain?

A parser that reads its punctuation from the document, a validator layered so that the cheap checks protect the expensive ones, and findings precise enough to resolve a dispute in one message. Next: what we turn the parsed document into.
