Chapter TenGenerating Outbound EDI

Reading a document forgives sloppiness; writing one does not. Counts must be exact, control numbers must advance, and a stray asterisk in a product description will split an element in half.

Generation is the mirror of chapter 8, but with a harsher grading scheme: a parser that is slightly wrong usually still extracts something useful, whereas a generator that is slightly wrong produces a document your partner rejects in full.

Build a segment list, not a string

The first structural decision determines whether the rest is easy. Do not build the document by concatenating text. Build a list of segments, each a list of elements, and serialise once at the end. Counts then become len() instead of a running tally you have to remember to increment.

def se_count(segments):
    # SE01 counts every segment in the transaction set,
    # including the ST and the SE itself.
    return len(segments) + 1   # +1 for the SE we're about to append

That +1 is the single most common outbound bug in EDI. SE01 is inclusive of the ST and the SE, so a generator that counts "the segments I wrote" is always short by one, and the partner's validator will say so.

Control numbers

Control numbers must be assigned per partner, per direction, and must advance monotonically. Partners deduplicate on them, and some will reject a number lower than one they have already seen.

Not a timestamp, not a random number

It is tempting to derive a control number from the clock. Don't: ISA13 is nine digits, timestamps collide across a batch, and clock skew can move you backwards. Use a persisted counter per partner per direction, allocated in the same transaction that records the document you are sending — so a crash between allocation and send never reuses a number.

And because they must be persisted before the send, they are also the handle by which you find the document again: the same number you wrote into ISA13 is what the partner will quote in their 997.

Formatting values safely

Every element has a declared type and a min/max length. Three rules cover almost all of it: pad fixed-width fields to their exact width, render dates in the format the version demands (CCYYMMDD in 005010, YYMMDD in the ISA), and render money with the implied decimals the element specifies — not with a decimal point you happen to like.

Then there is the delimiter problem. A product description reading Widget 10mm * boxed will, if emitted verbatim into an asterisk-delimited document, create an element boundary where none was intended and shift every following element by one.

def escape(value, delims, release="?"):
    out = []
    for ch in value:
        if ch in delims:
            out.append(release)      # EDIFACT: escape it
        out.append(ch)
    return "".join(out)

EDIFACT gives you the release character for exactly this. X12 does not, so the honest X12 strategy is to strip or substitute delimiter characters on the way out and to reject them loudly during development — a silent substitution that changes a description is better than a corrupt document, but knowing about it is better still.

Partner output profiles

The same transaction set is emitted differently for different partners: one wants REF*DP on every line, another forbids it; one takes UP qualifiers, another only BP. So generation is parameterised by an output profile — the outbound twin of the validation profile from chapter 8, and ideally the same configuration record.

Golden-file tests

Here is the practice that keeps generation honest across refactors: for each partner and transaction set, keep a fixture — a canonical document in, a reviewed EDI file out — and assert the generated bytes match exactly.

Byte-for-byte feels brittle, and that is precisely the value. If a refactor changes a control number's padding or drops a segment, the diff shows you the character. When a change is intentional you re-bless the fixture in the same commit, which leaves a reviewable record of every outbound format change the system has ever made.

Vary only what should vary

Golden files need the non-deterministic parts pinned: inject the clock and the control-number allocator rather than reading them from the environment. A test that fails at midnight is a test people learn to ignore.

So what did we actually gain?

A generator whose counts cannot drift, whose control numbers survive a crash, and whose output changes are visible in review. Part III is done: we can receive, validate, map and emit. Part IV asks the harder question — what happens when the network, the partner, or our own service misbehaves.
