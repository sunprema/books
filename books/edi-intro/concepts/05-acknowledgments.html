Chapter FiveAcknowledgments and Error Feedback

Three different things can acknowledge an EDI document, and each proves something narrower than people assume. Getting this layer wrong is how duplicate orders are born.

There are three acknowledgment layers in an EDI exchange, and they answer three different questions. Let's separate them before we write any code.

TA1 — the envelope acknowledgment

A TA1 reports on the syntactic correctness of the interchange envelope — the ISA and IEA — and nothing else. It is the right response when the ISA is malformed, the control numbers do not pair, or the group count is wrong: at that point you cannot even reliably find the transaction sets to comment on them. TA1 is a single segment, not a transaction set, and it can travel on its own.

997 and 999 — the syntax acknowledgments

The 997 functional acknowledgment reports problems at the functional group and transaction set level. It is the traditional X12 syntax acknowledgment and the one you will meet in retail and logistics.

The 999 implementation acknowledgment does the same job and additionally reports conformance to an implementation guide rather than just the base standard. In practice it is a healthcare instrument — if you are working retail EDI you will send 997s.

A clean 997 accepting our purchase order:

ST*997*0001~
AK1*PO*38~        acknowledging group "PO", control 38
AK2*850*0001~     …and transaction set 850 / 0001 inside it
AK5*A~            A = accepted
AK9*A*1*1*1~       group accepted: included / received / accepted
SE*6*0001~

And a rejecting one. Note how precisely it addresses the fault — this is the error-reporting model your own validator should imitate:

ST*997*0002~
AK1*PO*39~
AK2*850*0007~
AK3*PO1*12**8~     segment PO1, position 12, error code 8
AK4*3*234*1~       element 3, data element 234, error code 1
AK5*R*5~           R = transaction set rejected
AK9*P*1*1*0~        P = group partially accepted
SE*8*0002~

Accept, reject, partially accept

That AK9*P is important. Acknowledgment outcomes are not binary: a functional group can be accepted, rejected, or partially accepted with specific transaction sets rejected inside it. A processor that treats a group as all-or-nothing will either discard good orders or accept bad ones, and both are worse than the partial answer the standard already gives you.

CONTRL — the EDIFACT counterpart

EDIFACT folds all of this into one message type, CONTRL. The sender requests it in the UNB segment, and it reports receipt plus syntactic and service-segment correctness. One message, three jobs — which is tidier than X12's split, at the cost of needing the request flag set correctly on the way out.

Retrying without duplicating

Here is the failure that pays for this chapter. You send an 850. No 997 comes back within the agreed window. Do you resend?

The missing acknowledgment tells you nothing about whether the partner processed the order — it may have processed it and lost the acknowledgment. So: yes, resend, but resend the identical interchange, with its original control numbers. That is what lets the partner's deduplication recognise it as the same document. If you resend with fresh control numbers you have not retried; you have placed a second order.

Acknowledge after persistence, never before

On the receiving side, generate the 997 only once the document is durably stored. A 997 sent from memory, followed by a crash, leaves the partner believing a document was accepted that you no longer have — and they will not resend it, because you told them not to.

Transport success is not acceptance

A 200 OK, a signed AS2 MDN, a successful SFTP upload: all of these prove bytes moved. None of them prove a document was understood, and none of them prove an order was accepted. Keep the transport status and the document status in separate columns — literally.

So what did we actually gain?

A retry policy that is safe by construction, and a template for error reporting: locate the fault by group, transaction set, segment, position, element and reason. We will reuse that addressing scheme in chapter 8 when we build the validator, and the resend-identical rule in chapter 12 when we make the pipeline idempotent.
