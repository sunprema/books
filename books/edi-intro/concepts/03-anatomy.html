Chapter ThreeAnatomy of an EDI Document

An EDI file looks hostile because it is optimised for 1970s bandwidth, not for your eyes. Learn the three envelopes and it becomes ordinary.

Here is our running example — purchase order PO-88213 from ACME Retail to Widget Supply — stripped to its skeleton. Read it once now; it will make more sense in ninety seconds.

ISA*00*          *00*          *ZZ*ACMEBUYER      *ZZ*WIDGETSUPPLY   *260815*1430*^*00501*000000117*0*P*:~
GS*PO*ACMEBUYER*WIDGETSUPPLY*20260815*1430*38*X*005010~
ST*850*0001~
BEG*00*SA*PO-88213**20260815~
SE*4*0001~
GE*1*38~
IEA*1*000000117~

Three envelopes, nested

X12 wraps every transmission in three envelopes, each a header/trailer pair. From outside in:

  • ISA / IEA — the interchange. One transmission, from one sender to one receiver.
  • GS / GE — the functional group. Batches documents of the same type; GS01 carries a two-letter code (PO for purchase orders, IN for invoices).
  • ST / SE — the transaction set. One business document.

Delimiters are declared, not assumed

This is the single most important mechanical fact in the chapter. An EDI file does not use fixed punctuation. The sender chooses the delimiters and declares them in the ISA, and the ISA is deliberately fixed-format: exactly 106 characters so a parser can find them at known offsets before it knows anything else about the file.

Where the delimiters live
DelimiterFound atCommon value
Data element separatorThe character right after ISA*
Component (sub-element) separatorISA16 — the last ISA element:
Repetition separatorISA11, in 005010 and later^
Segment terminatorThe character following the ISA segment~
Never hardcode delimiters

Those "common values" are conventions, not rules. A partner may legitimately send |-delimited data with a newline terminator. A parser with split('*') baked into it works beautifully until the day it is handed a file from a partner who read the spec more carefully than you did.

Control numbers

Each envelope's header and trailer are joined by a control number, and each trailer also carries a count. This pairing is what lets a receiver detect truncation and duplicates without understanding a single business field.

Header / trailer pairing
LevelNumberCount in trailer
InterchangeISA13 = IEA02IEA01 — functional groups
Functional groupGS06 = GE02GE01 — transaction sets
Transaction setST02 = SE02SE01 — segments

Hold on to these. In chapter 12 they become our idempotency key; in chapter 13 they become our correlation id. They are the only identifiers both sides of the relationship share.

The same idea in EDIFACT

EDIFACT (ISO 9735) does the same job with different names. The pairs are UNB/UNZ (interchange), UNG/UNE (functional group) and UNH/UNT (message). Instead of a fixed-width header, an optional UNA service string advice sits immediately before the UNB and declares six characters in a fixed order: component separator, element separator, decimal notation, release (escape) indicator, one reserved position, and segment terminator.

UNA:+.? '
UNB+UNOC:3+ACMEBUYER:ZZ+WIDGETSUPPLY:ZZ+260815:1430+117'
UNH+0001+ORDERS:D:96A:UN'
UNT+4+0001'
UNZ+1+117'

Note the ? in the UNA: that is the release character, EDIFACT's escape. A product description containing a + must be written ?+ or it will silently split an element in two. X12 has no equivalent, which is why X12 implementations tend to reject delimiter characters in free text rather than escape them.

So what did we actually gain?

Enough structure to write a tokenizer that is correct rather than lucky: read the delimiters from the envelope, split on them honouring any release character, pair each header with its trailer, and check the counts. That is chapter 8. First, chapter 4 fills these envelopes with the documents an order actually needs.
