Chapter SevenThe EDI Processing Pipeline

Ten stages, each with its own failure mode and its own answer to "should we retry this?". Collapse any two of them and you lose that answer.

We now have enough vocabulary to design the machine. The temptation is to write one function that takes bytes and produces an order. Resist it: the value of a pipeline is that each stage fails differently, and a stage boundary is where you get to decide whether a failure is retryable, reportable, or fatal.

The stages

1 · receive
Pull from SFTP, accept an AS2 POST, poll the VAN mailbox. Purely a transport concern.
2 · archive raw
Persist the exact bytes, before decoding, before anything. This is what makes reprocessing possible and disputes answerable.
3 · identify
Read the envelope: which partner, which standard, which version, which transaction types. This selects the rules and maps for every stage that follows.
4 · validate syntax
Delimiters, envelope pairing, control numbers, trailer counts. Failure here produces a TA1 or a rejecting 997 — never an exception log entry alone.
5 · parse
Segments into a structured representation. Mechanical, and by now unsurprising.
6 · validate business rules
Codes, combinations, totals, dates, identifiers — layered as base standard, then the partner's implementation guide.
7 · transform
Map into the canonical internal model (chapter 9).
8 · route
Publish downstream: ERP, OMS, a queue. The first stage with an external side effect.
9 · acknowledge
Emit the 997/999/CONTRL, and later the business response.
10 · archive result
Store the processing outcome beside the raw payload: status, findings, what was published.

Why the order matters

Two placements in that list are load-bearing.

Archive is stage two, not stage ten. If you archive the parsed representation instead of the raw bytes, you can no longer prove what the partner actually sent, and you can no longer reprocess a file after fixing a parser bug — the bug is already baked into what you stored. Raw first, always.

Identify is stage three, before validation. You cannot validate a document until you know whose rules apply. Partner, standard, version and transaction type are all read from the envelope, and everything downstream is parameterised by them.

Don't collapse transport into processing

The single most common structural mistake is a function that downloads a file and processes it. When it fails you cannot tell whether the network flaked or the document was malformed — so the retry policy is a guess. Separate them, and each failure carries its own obvious answer: transport failures retry, document failures do not.

Acknowledgment is a stage, not a side effect

Notice that stage 9 sits outside the success path. A document that fails syntax validation at stage 4 never reaches stage 7, but it must still reach stage 9 — that is precisely when the partner most needs to hear from you. If acknowledgment lives inside the happy path as a trailing statement, broken documents are met with silence, and silence is the hardest EDI failure to diagnose from either side.

So what did we actually gain?

A skeleton with clear seams. Each stage can be tested alone, each has one retry policy, and the two unconditional stages guarantee that nothing is ever lost silently and nothing goes unanswered. The next three chapters fill in stages 4–7: parsing and validation, the canonical model, and generating documents on the way back out.
