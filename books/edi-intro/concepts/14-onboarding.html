Chapter FourteenTrading-Partner Onboarding

Onboarding is where an EDI project actually spends its time. The engineering is a fortnight; the certification is a quarter.

A direct AS2 implementation commonly takes weeks to months, depending on infrastructure, in-house expertise and how many partners are in scope. That is not because the protocol is hard. It is because each connection is its own small project: certificates to exchange and renew, firewall rules to arrange, connection tests to schedule with someone else's technical team, and a new thing to monitor.

Which is why the first question is not technical: direct or through a network? A VAN activates a new relationship over infrastructure that already exists. A direct link is cheaper per document and more work per partner. Chapter 2 gave the economics; this is where the decision gets made, per partner, and it is fine for the answer to differ between them.

What to collect

Every onboarding gathers the same facts. Make it a form, not a conversation — the conversation loses things.

Reading an implementation guide

The guide is two hundred pages and you do not read it linearly. Read it the way you would read an API spec you have to conform to exactly:

  1. The segment tables for the transaction sets in scope — noting every place the guide marks required what the standard marks optional. This is where most rejections come from.
  2. The code lists — the guide usually restricts a standard's fifty allowed values to five.
  3. The prose sections between the tables, which is where the rules that no table can express live ("orders for stores in the 400 series must carry REF*DP").
  4. The sample documents at the back, which become your first test fixtures.

Then translate all of it into executable artifacts: the validation profile from chapter 8, the output profile from chapter 10, and the mapping rules from chapter 9. A guide read but not turned into code is a guide that will be misremembered.

Test, certify, cut over

Certification is the partner running documents through your implementation and grading the results. Two practical points.

Test with failures, not just successes. The partner's sample file is by construction the happy path. If your certification consists of processing it correctly, the first rejection you ever handle will happen in production. Send yourself a missing segment, a bad qualifier, a duplicate — appendix D has the full list.

Test and production differ in more than a URL. The interchange ids are usually different, and ISA15 carries a test/production indicator (T or P) that some partners enforce strictly. Cutting over means changing configuration, and it is worth having a checklist for it because it is done once per partner and forgotten in between.

Confine deviations to the profile

Every partner has at least one demand that fits nothing else — a date format nobody else uses, a segment required in one direction only. The pressure is always to add a small if to the shared code path. Don't. It goes in that partner's profile, even when the profile mechanism has to grow to hold it. A core mapper with eleven partner-specific branches is how an EDI codebase becomes unmaintainable, and it happens one reasonable exception at a time.

An onboarding checklist

  1. Decide transport: VAN or direct.
  2. Collect the configuration record above.
  3. Exchange certificates or keys; confirm connectivity both ways with an empty test.
  4. Read the guide; write the validation profile, mapping rules and output profile.
  5. Build fixtures from the guide's samples, plus the failure cases.
  6. Run certification; fix; re-run.
  7. Set the expected cadence and enable the silence and acknowledgment-timeout alerts.
  8. Cut over: swap ids, flip ISA15, watch the first day closely.

So what did we actually gain?

A repeatable process, and one architectural commitment worth defending in review: partner-specific behaviour lives in partner-specific configuration. Chapter 15 zooms out to the system that holds all these profiles.
