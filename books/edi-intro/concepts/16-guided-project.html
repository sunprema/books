Chapter SixteenA Guided Project: Build a Minimal EDI Service

One transaction set, one partner, one afternoon — but with the four properties that separate a parser demo from something you could actually operate.

Time to build. The scope is deliberately narrow: receive an X12 850 over SFTP or HTTP, validate it against one partner profile, map it to a canonical JSON order, persist it, and return a 997. That is it — and it is a complete, useful integration.

Define the narrow scope

  • In: 850 purchase orders from one partner, acme-retail, at 005010.
  • Out: a 997 for every interchange, accepted or rejected.
  • Store: raw payloads, normalized orders, processing status, findings.
  • Prove: idempotency, tests, logging, metrics, replay.

The whole thing, in one function

Here is the spine. Read the order of the first four steps carefully — that ordering is the lesson of Part IV, and everything else is detail.

def process(raw: bytes, partner: str) -> Result:
    archive(raw, partner)                       # 1. raw bytes first, always
    d = read_delimiters(raw.decode("latin-1"))  # 2. delimiters from the ISA
    env = parse_envelopes(raw, d)               # 3. ISA/GS/ST structure

    if seen_before(partner, env.control_numbers, sha256(raw)):
        return Result.duplicate(env)            # 4. before ANY side effect

    errors = validate(env, profile_for(partner))
    if errors:
        return Result.rejected(env, errors,
                               ack=build_997(env, errors))

    order = to_canonical(env)                   # 5. map
    publish(order)                              # 6. the only external effect
    return Result.accepted(env, ack=build_997(env, []))
The one line you cannot move

publish() must come after seen_before(). Every other statement can be reordered with only aesthetic consequences; move that one and every partner resend becomes a duplicate order in the ERP. If you take one thing from this book to your own codebase, take the position of that check.

Building it, a piece at a time

Step 1 — receive and archive

An HTTP endpoint that accepts a body, or a poller that lists an SFTP directory. Write the bytes to object storage keyed by partner and date before doing anything else, and record the reference. If the process dies on the next line, the document is safe.

Step 2 — envelopes

Chapter 8's read_delimiters, then split into segments, then walk ISA→GS→ST. Verify the pairings and the trailer counts here; a truncated file should fail now, cheaply, rather than producing forty confusing errors later.

Step 3 — the partner profile

A JSON document, not code:

{
  "partner": "acme-retail",
  "interchangeId": "ACMEBUYER", "qualifier": "ZZ",
  "version": "005010",
  "inbound": ["850"],
  "rules": {
    "requiredSegments": ["BEG", "N1", "PO1", "CTT"],
    "allowedUom": ["CA", "EA", "PL"],
    "requireDeptRef": true
  },
  "cadence": "weekdays-by-0600"
}

Step 4 — validate, and report precisely

Structural, then semantic, then the profile's rules. Collect findings per transaction set with the full address from chapter 8 — segment, position, element, rule — so a rejection can be explained without opening the raw file.

Step 5 — map and persist

Into chapter 9's canonical order, keeping sourceControl. Persist the normalized record beside the raw reference and the status.

Step 6 — acknowledge

Build the 997 from the findings: AK5*A when clean, AK5*R with AK3/AK4 detail when not, and AK9 summarising the group — including P for a partial acceptance. Send it after the document is durably stored.

Extending it

Two natural next steps, both of which reuse what you have rather than adding new machinery.

Emit an 810 invoice. This exercises chapter 10: envelope generation, the persisted control-number allocator, SE01 arithmetic, and a golden-file test. The canonical order you already store is the input.

Consume an 856. This exercises the parser against a genuinely hierarchical document — the HL loops nesting shipment, order, pack and item — and forces the canonical model to grow a shipment alongside its order. It is the honest test of whether your parse stage handles loops or merely segments.

Resist the temptation to generalise early

With one partner and one transaction set, the profile is a JSON file and the validator is a hundred lines. That is correct. The abstractions that make a multi-partner EDI platform good are discoverable only from two or three real partner guides — build those first and let the shape emerge.

So what did we actually gain?

A working service, and a demonstration that everything in Parts III and IV fits in one readable function. The appendices that follow are the reference material: the segments, the sample documents, the failure taxonomy, and the tests that prove you handled it.
