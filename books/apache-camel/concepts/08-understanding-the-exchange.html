Part III — Working with Messages · Chapter 08

08

Understanding
the Exchange

Part II ended with routes that run — a file copied, an order routed by country, the same logic spelled three different ways. What we skipped, on purpose, was what actually flows through those routes while they run. Chapter 02 gave you the one-sentence version: an Exchange is the envelope, not the letter. That sentence was enough to write a route. It is not enough to debug one. This chapter opens the envelope all the way — body, headers, properties, pattern, and the one thing Chapter 02 didn't cover at all: what happens to an Exchange the moment something goes wrong.

Four things, one Exchange

Say it precisely this time: an org.apache.camel.Exchange is not a message with a fancier name. It's a container holding four distinct things for the lifetime of one route execution, and none of the four get rebuilt mid-route — a consumer creates the Exchange once, and every processor after it reads and mutates the same instance.

If you see getIn() / getOut() in old code

Pre-3.x Camel modeled an Exchange as two separate messages — an "In" message for what arrived and an "Out" message for a step's reply. Both accessors still exist for compatibility, but both are lazy-creating: calling getOut() when no out message exists silently creates an empty one rather than returning null, which is exactly why the old idiom for "did this step actually reply?" was hasOut(), never getOut() != null — that check would always be true, because asking the question created the answer. Modern Camel collapses both slots into one current message, reached with getMessage(), which is what every example in this book uses.

The body doesn't have a type until you ask it for one

A Message's body is stored as a plain Object. It isn't "a String" or "a POJO" until some code demands it be one. Call getBody() with no arguments and you get back whatever object is sitting there, untouched. Call getBody(SomeType.class) and Camel hands the request to its type-converter registry, which searches every converter it has loaded for one that can turn the body's actual runtime type into the type you asked for — and performs that conversion right there, on the spot.

Type conversion, on demand
.process(exchange -> {
    Message msg = exchange.getMessage();
    String body = msg.getBody(String.class);       // converted on demand
    int orderTotal = msg.getHeader("OrderTotal", Integer.class);

    // exchange-scoped, not message-scoped -- survives a later split/enrich
    exchange.setProperty("originalBody", body);
});

This is convenient right up until it fails, and when it fails, it fails late. If nothing on the classpath can bridge the body's actual type to the type you asked for, that call throws NoTypeConversionAvailableException — but only at the moment the conversion is attempted. A body of the "wrong" type can ride through several processors with no complaint at all, until one of them finally asks for a type nothing can produce it from. When that exception shows up, the bug is almost never in the line that threw it.

Where the bug actually is

NoTypeConversionAvailableException tells you where the conversion was attempted, not where the wrong type was introduced. When you hit one, work backwards: what earlier step set this body to something the later step can't convert, and should that step have converted it itself, closer to the source?

Headers are case-insensitive — on purpose

Headers are message-scoped key/value metadata — a file name, an HTTP status code, a JMS correlation ID — and Chapter 02 already told you they're scoped to the current message, not the whole exchange. What it didn't tell you: Camel stores them, by default, in a case-insensitive map. header("ContentType"), header("contenttype"), and header("CONTENTTYPE") all resolve to the same entry, because the storage (a CaseInsensitiveMap, selected via the pluggable HeadersMapFactory on CamelContext) folds case before it ever compares keys. This mirrors how HTTP and mail headers are conventionally treated — genuinely convenient when you're bridging to a protocol that doesn't care about case, genuinely surprising if you were relying on OrderId and orderId being two different headers.

Properties: bookkeeping that outlives the message

Exchange properties are managed entirely off the Exchange, not the Message — setProperty(), getProperty(), getProperties(), removeProperty(), hasProperties(). Reach for one whenever a value needs to survive past a step that builds a fresh Message, which is exactly what Splitter, Multicast, and Enrich do per branch — a header set before one of those steps is not guaranteed to still be there after it; an exchange property is.

Camel writes to some properties itself, as a route runs, which means exchange properties aren't purely a developer's scratch space — a few carry framework state a route can legitimately read. The one worth knowing before the next section: Exchange.EXCEPTION_CAUGHT (the string "CamelExceptionCaught"), which holds whatever exception an onException block is currently handling.

Pattern: does this step expect a reply?

ExchangePattern answers one question about a given step: does the caller wait for a response? InOnly is one-way, fire-and-forget — publish to a queue and move on, no reply expected, none produced. InOut is request-reply — the caller blocks until a response comes back, the way an HTTP call or a bean method invocation with a return value naturally works. Every endpoint's component picks a sensible default (HTTP and bean calls default to InOut; JMS, file, and most messaging-style endpoints default to InOnly), and a route can override it explicitly wherever the default doesn't fit.

Forcing request-reply on a single step
from("jms:queue:orders.raw")
    .to(ExchangePattern.InOut, "bean:pricingService?method=quote")
    .log("Quoted price: ${body}");
The mismatch that produces no error at all

Send to a plain InOnly endpoint — a JMS producer, a file write — and then read exchange.getMessage() expecting a response, and you won't get an exception. You'll get the same message you sent, unchanged, because InOnly never produced a reply to begin with. Nothing about this fails loudly; the message is just quietly not what you assumed it was.

How an exception actually rides along

Here's the part Chapter 02 skipped entirely. When a processor — a built-in EIP or your own .process(…) lambda — throws, Camel does not let that exception propagate up the JVM call stack the way a normal Java exception would. It catches it and calls exchange.setException(cause), attaching it to the Exchange itself. exchange.isFailed() then reports true — it's really just shorthand for "is getException() non-null" — and it's Camel's error-handler machinery, the Dead Letter Channel by default, that inspects that exception and decides what happens next: retry, redirect to a dead-letter destination, or let it propagate further. Part VI covers that machinery in full; this chapter only tells you where the exception itself lives.

There's one twist worth knowing now, because it produces a genuinely confusing bug otherwise. Once an onException block (or a doTry/doCatch) has claimed an exception, exchange.getException() goes back to null for the rest of the route — the exception has been handled, not merely observed, and Camel clears the slot. The exception itself isn't gone, though; it's been relocated to that Exchange.EXCEPTION_CAUGHT property from the last section, where code downstream of the handler can still retrieve it.

Where the exception ends up after onException claims it
onException(IllegalArgumentException.class)
    .handled(true)
    .to("jms:queue:orders.rejected")
.end();

// later in the route, once IllegalArgumentException has been "handled":
// exchange.getException()                                    -> null
// exchange.getProperty(Exchange.EXCEPTION_CAUGHT, Throwable.class) -> the original exception
An Exchange isn't one thing carrying a message. It's four: a message, a property bag, a pattern, and — the instant something breaks — an exception. Every debugging session in this book is really just asking which of those four holds the answer.

So what did we actually gain?

Not new routing behavior — nothing on this page changes what a route does. What changed is what you can now read off any Exchange in a debugger or a log line: a body that's a type only once something asks, headers that fold case before they compare, properties that outlive a Splitter branch a header wouldn't, a pattern that decides whether "the response" even exists, and an exception slot that moves — predictably, once you know to look — the instant an onException block claims it. Next chapter puts processors and beans to work actually changing what's in that body, using exactly the type-conversion machinery this chapter just opened up.

Check yourself

  1. A route sets a header called OrderId in one step and reads a header called orderId two steps later, expecting them to be different values. What actually happens, and why does Chapter 02's "header vs. property" advice alone not explain it?
  2. A processor three steps into a route throws NoTypeConversionAvailableException on a getBody(Document.class) call. Why might the actual bug be nowhere near that line?
  3. Inside an onException(...).handled(true) block, a colleague writes exchange.getException() to log what went wrong and gets null every time. What should they call instead, and why does Camel clear getException() at that point in the first place?
