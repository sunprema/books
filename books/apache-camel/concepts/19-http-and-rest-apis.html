HTTP and REST APIs

Chapter 18 closed with a promise of its own: the same underlying question — how does one side know the other side is finished? — resurfacing in a new shape once the transport is HTTP instead of a filesystem. A file either exists or it doesn't; there's no ambiguity once readLock says it's safe to read. An HTTP call is messier: a request either gets a timely, well-formed answer, or it gets a slow answer, a wrong-shaped answer, an honest error, or no answer at all, and the route has to decide — explicitly — what each of those means. This chapter covers both directions Camel talks HTTP: calling out to someone else's service with camel-http, and standing up your own with the REST DSL.

Calling out: camel-http as a producer

camel-http is a producer-only component — there's no from("http://..."), only .to("http://..."). Point a route at a URL and it sends the request using Apache HttpClient 5.x under the hood (that's been true since Camel 4.13), gets back a response, and the exchange carries on with that response as its new body. The http:// or https:// scheme in the endpoint URI is Camel's own routing prefix, not literally re-sent — it's how Camel decides which component handles the call; the actual outbound scheme is whatever the URL itself says.

The plainest possible outbound call
from("direct:lookupCustomer")
    .to("http://crm.internal.example.com/api/customers/{{header.customerId}}");

That's the shape of it, but it's also the version you should never actually ship. Nothing above bounds how long the call is allowed to take, and nothing decides what "the call went badly" even means. Those two questions — timeouts and failure handling — are what the rest of this section is about.

Timeouts: three places a call can hang, three options to bound them

A hung external service doesn't fail in one place — it can fail in three, and each has its own option:

camel-http timeout options — each bounds a different way a call can hang
OptionWhat it boundsWhat it does not catch
connectTimeoutMilliseconds to establish the TCP connectionA service that accepts the connection, then goes silent
socketTimeoutMilliseconds of inactivity once connected — the gap between data chunksA service that refuses the connection outright, or is unreachable
connectionRequestTimeoutMilliseconds to wait for a free connection from the client's own poolAnything about the remote service at all — this one's about your own client being saturated

A route that sets socketTimeout alone and calls the endpoint "protected" has only covered one of those three failure modes. A service that never accepts the TCP connection in the first place — a firewall drop, a host that's down — is a connectTimeout problem, and socketTimeout never enters the picture because there was no connection for data to go quiet on.

Bounding all three failure modes explicitly
from("direct:lookupCustomer")
    .to("http://crm.internal.example.com/api/customers/{{header.customerId}}"
        + "?connectTimeout=3000&socketTimeout=5000&connectionRequestTimeout=2000");
Timeouts bound one call. They don't stop you from hammering a struggling service.

A tight socketTimeout makes each individual retry fail fast — it doesn't stop the route from immediately trying again, and again, against a downstream service that's already struggling. That's a different problem, and Camel has a different tool for it: the Circuit Breaker EIP (circuitBreaker(), backed by Resilience4j) sits in front of the call and can stop attempts entirely once a failure threshold is crossed, giving the other side room to recover. Pair it with your timeouts; it isn't a replacement for them.

throwExceptionOnFailure and HttpOperationFailedException

By default, throwExceptionOnFailure is true, and Camel treats a 3xx (redirection) or 4xx/5xx (client or server error) response as an operation failure, not just a status code to read — it raises HttpOperationFailedException instead of quietly handing the exchange a 404 body. That exception carries everything you'd otherwise have to re-derive: getStatusCode(), getStatusText(), getResponseBody(), getResponseHeaders(), getUri(), and — for redirects specifically — getRedirectLocation() and hasRedirectLocation().

Catching the exception, reading its structured fields
onException(HttpOperationFailedException.class)
    .process(exchange -> {
        HttpOperationFailedException e = exchange.getProperty(
            Exchange.EXCEPTION_CAUGHT, HttpOperationFailedException.class);
        exchange.getMessage().setHeader("FailedStatusCode", e.getStatusCode());
        exchange.getMessage().setBody(e.getResponseBody());
    })
    .to("direct:handleUpstreamFailure");

Setting throwExceptionOnFailure=false takes the opposite approach: no exception, ever, from a bad status code. The exchange just carries whatever the server actually sent, and the route reads CamelHttpResponseCode itself to decide what happened. Neither approach is more "correct" — an onException clause centralizes failure handling across a whole route, while an inline choice() on the response code keeps the success and failure paths visible side by side, right where the call happens. Pick the shape that matches how the rest of the route already handles branching.

The inline alternative: inspect the code instead of catching an exception
from("direct:lookupCustomer")
    .to("http://crm.internal.example.com/api/customers/{{header.customerId}}"
        + "?throwExceptionOnFailure=false&connectTimeout=3000&socketTimeout=5000")
    .choice()
        .when(header(Exchange.HTTP_RESPONSE_CODE).isEqualTo(200))
            .unmarshal().json(JsonLibrary.Jackson, Customer.class)
        .otherwise()
            .log("Customer lookup failed with status ${header.CamelHttpResponseCode}")
            .to("direct:customerLookupFailed")
    .end();
throwExceptionOnFailure only covers responses — not the absence of one

The default catches 3xx/4xx/5xx responses. It says nothing about a call that never gets a response at all — DNS failure, connection refused, a connectTimeout or socketTimeout expiring. Those raise a different exception entirely. An onException clause scoped only to HttpOperationFailedException silently misses that whole class of failure; catch the broader Exception (or the specific timeout exception types) alongside it if a route needs to treat "no answer" the same as "a bad answer."

One more producer option worth knowing before it costs you a debugging session: bridgeEndpoint=true. It's for building a proxy or passthrough route, and it does two things — it stops Camel from appending the incoming request's path and query string onto the outbound URI a second time, and it forces a no-op cookie store, since a bridging route is relaying someone else's session, not running its own. Skip it on a proxy route and the outbound call ends up hitting a path with the segment doubled up, which reads as a broken upstream far more readily than it reads as a missing URI option.

Building a REST API: the REST DSL is a facade, not a server

Everything so far has been the calling side. The REST DSL — rest() and restConfiguration() — is Camel's tool for the other direction: exposing your own routes as REST operations. The important thing to internalize first is that rest() itself doesn't run a web server. It's a facade for declaring operations — a verb, a path template, optional request/response types — and restConfiguration().component(...) is where you pick which actual HTTP server component serves them. platform-http is Camel 4's default binding for Spring Boot, Quarkus, and standalone Camel Main; netty-http, jetty, undertow, and servlet are the alternatives for when a specific server is already part of the deployment.

In practice you're rarely bringing your own HTTP server: platform-http plugs into whatever server the runtime already has. On Camel Quarkus, that's Quarkus's own Vert.x server via quarkus-vertx-http. On Spring Boot or a standalone Camel Main application, it's an embedded Vert.x server supplied by camel-platform-http-main. Either way, writing a rest() route doesn't mean standing up a servlet container by hand — the platform already has one running, and platform-http is what wires Camel's routes into it.

Declaring operations, delegating each one to a route
restConfiguration()
    .component("platform-http")
    .bindingMode(RestBindingMode.json)
    .apiContextPath("/api-doc")
    .apiProperty("api.title", "Order Service API")
    .apiProperty("api.version", "1.0");

rest("/orders")
    .get("/{id}").outType(Order.class)
        .to("direct:getOrder")
    .post().type(Order.class).outType(OrderConfirmation.class)
        .to("direct:createOrder");

from("direct:getOrder")
    .process(exchange -> { /* look up the order by ${header.id} */ });

Notice the shape: each rest() verb still ends in an ordinary .to("direct:..."). The REST DSL only replaces how a request enters a route — the routing, transformation, and error-handling vocabulary from every earlier chapter still applies once you're inside direct:getOrder.

bindingMode: request/response transformation, declared instead of written

Chapter 9 and Chapter 10 covered marshal()/unmarshal() and the Simple language's own conversions in general terms; bindingMode is that same Jackson-backed machinery, offered as a REST DSL convenience instead of an explicit step you write yourself. It has five values: off (the default — the route sees and returns a raw body, and marshals it manually, exactly as in every earlier chapter), auto (bind only if a data format can be inferred from the Content-Type header), json, xml, and json_xml (negotiate either, based on Accept). Set bindingMode=json and pair it with type() / outType() on a verb, as in the snippet above, and the request body is unmarshalled to that POJO before your route sees it, and the returned object is marshalled back to JSON on the way out — no explicit marshal().json(...) call needed inside direct:createOrder itself.

Two ways to bring an OpenAPI spec into the picture

A REST API and its OpenAPI (formerly Swagger) description can come into being in either order, and Camel supports both directions:

Code-first versus contract-first REST APIs in Camel
Code-firstContract-first
Source of truthYour rest() routesAn existing OpenAPI YAML/JSON file
Toolcamel-openapi-javarest-dsl-openapi
What happensThe spec is derived from your routes and served at apiContextPathThe spec is loaded at startup; Camel generates one endpoint per operation
Route wiringWhatever .to(...) you wrote per verbConvention: each operation routes to direct:<operationId>
Startup safety net—Fails to start if any operationId has no matching route, unless missingOperation allows it

Contract-first's startup validation is worth calling out on its own: if a typo lands in either the spec's operationId or the route's direct: name, the mismatch fails the whole application at boot, not at the first request that happens to hit that operation. That's a feature — a silently-missing operation is a much worse failure to discover in production — but only if you know to check the startup log rather than assume every declared operation quietly has an implementation.

There's a calling-side mirror of contract-first, too: the rest-openapi component lets a producer target an operationId from an external OpenAPI spec — .to("rest-openapi:partner-api.yaml#getUserById") — and Camel resolves the host, path, and required parameters from that document instead of you hand-assembling the URL the way the earlier camel-http examples did. The spec becomes the single source of truth for both directions: what your API accepts, and what a partner's API expects when you call it.

A file either exists to be read or it doesn't. An HTTP call can fail in a connection that never opens, a socket that goes quiet, a pool that's exhausted, a status code that means "no," or a body that means "yes" but isn't shaped the way you expected. None of those failure modes share one option or one exception type — which is exactly why camel-http gives you three separate timeouts and a structured exception instead of one blunt "it broke" flag. Naming the failure precisely is most of the work of handling it well.

So what did we actually gain?

Two components that mirror each other across the same boundary: camel-http for calling out, with connectTimeout/socketTimeout/ connectionRequestTimeout bounding the three places a call can hang and HttpOperationFailedException giving a failed response structured fields instead of a bare message; and the REST DSL for exposing your own operations, which is deliberately just a facade — restConfiguration() picks the real server (platform-http by default), and bindingMode plugs the same marshalling machinery from Chapters 9 and 10 in as a declared option instead of a written step. OpenAPI ties the two directions together, code-first or contract-first, so the shape of the API is documented in one place whichever side of the call you're building. Chapter 20 stays inside "Real Systems" but swaps the transport again — from a stateless HTTP request to a database connection that expects you to think about transactions, not just timeouts.
