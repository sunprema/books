Enterprise Integration
Patterns

Last chapter gave us five nouns and two verbs: CamelContext, Route, Endpoint, Component, Processor; consumer and producer. Useful vocabulary — but vocabulary for what, exactly? This chapter answers that. Every route you'll write in this book is an implementation of one or more patterns from a specific, twenty-year-old catalog, and Camel didn't invent a single one of them. It gave each a name you can type.

The catalog behind the code

In 2003, Gregor Hohpe and Bobby Woolf published Enterprise Integration Patterns, a catalog of 65 patterns for messaging-based integration — a shared vocabulary for problems every non-trivial integration runs into, whether or not the team building it has ever heard of the book. Underneath the other 59 sit six root patterns everything else builds on.

The six root patterns
PatternAnswersCamel's answer
Messagewhat travels between systemsthe Exchange's current Message — body + headers (Ch. 02)
Message Channelwhat it travels onan Endpoint URI — a queue, a topic, a directory
Pipes and Filtershow a message is processed in stagesa route: a chain of Processors between from and to
Message Routerwhich channel a message goes to nextchoice(), filter(), and friends

Message Endpointhow an app connects to a channela Component + Endpoint URI (Ch. 02)

Notice that we've already met three of these six without naming them as patterns — a route is Pipes and Filters, a Message is the Exchange's payload, an Endpoint is a Message Endpoint. That's not a coincidence; it's the whole reason last chapter's vocabulary felt so naturally suited to describing routing logic. The three we haven't named yet — Channel, Router, Translator — are this chapter's job.

Camel's whole trick, stated plainly

Camel doesn't invent integration patterns. It gives each named pattern in Hohpe & Woolf's catalog a DSL keyword — choice for Content-Based Router, filter for Message Filter, transform for Message Translator — so that reading a route and reading the pattern language become the same skill. Learn the book's patterns, and you can read (and design) Camel routes you've never seen before.

Channels: the pathway, not the payload

A Message Channel is the logical pipe a message travels through between a sender and a receiver. This is a small idea with a large consequence: applications never exchange messages directly with each other. They write to a channel and read from a channel — which is what actually decouples them. A sender doesn't need to know where the receiver lives, whether it's currently running, or how many receivers there even are.

Every channel is one of two base shapes. A Point-to-Point Channel guarantees exactly one receiver consumes each message — think a queue, where competing consumers race for messages but each message is claimed once. A Publish-Subscribe Channel delivers a copy of each message to every subscriber — think a topic.

Two channel shapes, and Camel's stand-ins
ChannelDeliveryCamel examples
Point-to-Pointone message, one consumerdirect:, seda:, jms:queue:
Publish-Subscribeone message, every subscriberjms:topic:, or a multicast()/recipientList() step fanning out from a point-to-point source

Camel doesn't build a new channel abstraction on top of these — it exposes whichever channel behavior the concrete component already has. A jms:queue:orders endpoint is point-to-point because JMS queues are; a jms:topic:orders endpoint is publish-subscribe because JMS topics are. When the underlying technology only offers one shape (a file directory, an HTTP endpoint), Camel's fan-out patterns — Multicast and Recipient List, later this chapter — let a route simulate publish-subscribe delivery on top of it.

Routers: choice() and filter()

A Message Router reads a message from one channel and decides, without changing its content, which output channel it should travel on next. That "without changing its content" clause is the part worth underlining — a router's job is a decision, not a rewrite. The most common router is the Content-Based Router: pick a branch by inspecting the message itself.

Content-Based Router: choice() / when() / otherwise()
from("jms:queue:orders.validated")
    .choice()
        .when(header("CamelOrderCountry").isEqualTo("US"))
            .to("jms:queue:orders.domestic")
        .when(header("CamelOrderCountry").in("CA", "MX"))
            .to("jms:queue:orders.nafta")
        .otherwise()
            .to("jms:queue:orders.international")
    .end();

Read it as if/else-if/else, because that's exactly what it is: when(…) branches are tried in order, the first true predicate wins, and otherwise() catches whatever's left. end() closes the block — easy to forget when choice() is nested inside another EIP, and forgetting it doesn't raise an obvious error; it just silently attaches your next call to the wrong scope.

A Message Filter is a router with exactly one branch and an implicit "discard" otherwise: Camel's filter() guards a portion of the route with a single predicate, and any exchange that doesn't satisfy it is simply dropped, not routed anywhere.

Message Filter: filter()
from("jms:queue:orders.validated")
    .filter(header("CamelOrderTotal").isGreaterThan(0))
    .to("jms:queue:orders.billable");

Sending one message to many: Recipient List, Multicast, Wire Tap

Three patterns answer "send this message to more than one place," and they differ in how the destinations are chosen and why you're sending. Part IV gives each its own chapter; here's the map so you recognize them on sight.

Three ways to fan a message out
PatternDestinations chosenTypical use
Recipient Listdynamically, at runtime (often a header)route to whoever's subscribed this time
Multicaststatically, fixed in the routealways notify these N fixed systems
Wire Tapone fixed secondary destinationaudit/log/debug a copy, without touching the primary flow

Recipient List (recipientList()) and Multicast (multicast()) both exist because a Publish-Subscribe Channel isn't always available on the technology you're stuck with — a plain file directory or HTTP endpoint has no notion of "every subscriber," so the route itself has to fan the message out. Both can run their destinations in parallel with .parallelProcessing() rather than one after another.

Wire Tap is the specialized case: copy a message to a secondary destination for auditing, logging, or debugging, without delaying or altering the primary route. The tap normally runs asynchronously, against a fresh copy of the exchange rather than the live one continuing downstream — a common surprise for anyone expecting the tap to finish before the main route does, or to see mutations the main route made afterward.

Wire Tap: copy without disturbing the primary flow
from("jms:queue:orders.validated")
    .wireTap("jms:queue:orders.audit-log")
    .to("jms:queue:orders.processing");

Translators: same meaning, new shape

A Message Translator changes a message's form without changing its meaning, so that two systems which disagree on data shape can still talk. Camel offers several translator shapes for the same underlying idea: transform() (an expression that replaces the body outright), .bean(…) (delegate the rewrite to a POJO method), a hand-written .process(…) lambda, and — quietly, everywhere — the type-converter registry from last chapter, which performs the smallest, most common translations (String ↔ byte[] ↔ InputStream ↔ a domain object) automatically, any time a route asks for a type it doesn't currently have.

Message Translator: transform()
from("jms:queue:orders.raw")
    .transform(simple("${bodyAs(String)}"))
    .to("jms:queue:orders.normalized");

Translators matter most when you're integrating more than two systems, which is most of the time. If every pair of systems translates directly to and from every other system's format, you're back to the point-to-point cost from Chapter 01 — just paid in translators instead of connections. The fix has a name too.

Canonical Data Model

Define one integration-owned message format — a canonical order, a canonical customer — and translate every system's data to and from that, never directly between two external formats. N systems then need N translators total, not the roughly N² a everyone-translates-to-everyone design would demand. Chapter 11 puts this into practice when we design a canonical order model for the capstone integration.

Endpoints, once more, with the pattern named

The last root pattern, Message Endpoint, asks how an application actually connects to a channel — and we answered it in Chapter 02 before we had the pattern's name: every endpoint, regardless of which of Camel's 300+ components backs it, is addressed the same way, as a URI. That uniformity is why the router, translator, and fan-out patterns above all read identically no matter which concrete technology sits at from(…) or to(…). A choice() block routing JMS messages and a choice() block routing HTTP requests are the same three lines of Camel.

Every route you write in this book is one of six patterns wearing different clothes: a channel to travel on, a router to pick a branch, a translator to reshape the payload, an endpoint to enter or leave through — strung together, Pipes-and-Filters style, into a route.

Keep the roles separate

A router decides where a message goes; a translator decides what it looks like. Mixing the two in one step — a choice() branch that also rewrites the body, say — makes both harder to test on their own and harder for the next reader to recognize which pattern they're even looking at. When a step is doing two jobs, it's usually two EIPs that want to be two steps.

So what did we actually gain?

We now have a name for almost everything a route does: the channel a message rides on, the router that picks its next channel, the translator that reshapes it along the way, the endpoint it enters and leaves through. None of this is Camel-specific — it's Hohpe and Woolf's pattern language, and Camel's entire DSL is a set of keywords for typing it out. Part II stops talking about patterns in the abstract and starts writing routes that actually run — starting with getting a Camel project set up at all.
