Files, SFTP, and Object Storage

Chapter 17 closed on a promise: from patterns for moving a message inside your own JVM to the real external systems those messages actually come from and go to. Files are the oldest of those systems — Hohpe and Woolf's own catalog names File Transfer as one of the four base integration styles, back in Chapter 1 — and they're still everywhere: a partner drops a nightly batch on an SFTP server, a nightly job writes a report to an S3 bucket, a legacy system's only integration point is a shared folder. Camel's file: component turns "watch a directory, pick up files safely, do something with each one" into a handful of URI options instead of a hand-rolled polling loop, and — this is the part worth knowing early — sftp: and the object-storage components use almost the same option set, because they're built on the same abstraction underneath.

One abstraction, three transports: GenericFile

Camel's file:, ftp:, and sftp: components all extend the same GenericFileComponent / GenericFileEndpoint base class. That's not an implementation detail — it's the reason the polling, locking, and archival options you're about to learn on file: carry over to sftp: almost unchanged. Only the connection and authentication options differ: a local directory needs a path; a remote server needs a host, a port, and credentials. Everything about how a file is safely claimed, processed, and archived is shared.

Same options, different transport — only host/auth changes
// Local directory
from("file:data/incoming?readLock=changed&delete=true")
    .to("file:data/processed");

// Same options, a remote SFTP server instead
from("sftp://partner.example.com:22/incoming?username=integ&privateKeyFile=/secrets/id_rsa&readLock=changed&delete=true")
    .to("file:data/processed");

Object storage doesn't share that exact base class — a bucket isn't a directory tree the way FTP is — but aws2-s3: was deliberately designed to feel the same way from the route's point of view: a scheduled-poll consumer, an options-driven producer, and the same instinct that "process a thing, then decide what happens to it" should be a URI option rather than code you write yourself. We'll come back to it once the file-based vocabulary is in place.

Polling a directory: delay, recursion, and filtering

A file consumer is a scheduled poll consumer under the hood, and its defaults are worth knowing precisely rather than assuming. initialDelay defaults to 1000ms before the very first poll; delay defaults to 500ms between polls after that. recursive defaults to false — a directory endpoint will not descend into subdirectories unless you say so. include and exclude take a regex tested against the filename, so a poll can consider only .*\.csv and ignore everything else sitting in the same directory. And maxMessagesPerPoll caps how many files one poll cycle will claim — useful the first time a route points at a directory with ten thousand files already sitting in it, so the route doesn't try to swallow the entire backlog in one pass.

A bounded, filtered, recursive poll
from("file:data/incoming?recursive=true&include=.*\\.csv&maxMessagesPerPoll=50&delay=30000")
    .log("Picked up ${header.CamelFileName}")
    .to("direct:processOrder");

readLock: the option that's easy to skip and expensive to skip

Here's the default that matters most in this whole chapter: readLock is none out of the box, on file:, ftp:, and sftp: alike. Nothing stops a fresh route from picking up a file that some other process is still in the middle of writing — Camel will happily hand a half-written CSV to your route, because you never told it to check. This isn't a corner case worth a footnote; it's the single most common cause of "the file consumer processed a truncated file" bug reports.

readLock strategies — how a file consumer decides a file is safe to claim
StrategyHow it decidesCaveat
none (default)Doesn't check — claims immediatelyCan read a file mid-write
markerFileCreates and holds a sibling <name>.camelLock fileNear-atomic, but not cluster-safe; not every remote server supports it
changedPolls length/mtime twice, readLockCheckInterval apart; proceeds once both matchNeeds a genuinely idle window — a slow trickle-write can never look "changed"
renameAttempts an exclusive rename as the lock test itselfRequires rename permission on the source location
fileLockA Java NIO FileLockLocal filesystems only
idempotentUses an IdempotentRepository as the lockThe one strategy that can coordinate across a cluster — if the repository backing it can

changed is the common default choice for a real filesystem or a network mount where the producer doesn't rename atomically. readLockTimeout (default 10000ms) bounds how long a file is allowed to sit waiting for its lock before that poll cycle gives up and reconsiders it later — the documented rule of thumb is to keep it at least twice readLockCheckInterval, so a changed comparison actually gets more than one window to run before timing out.

idempotent readLock is Chapter 16's Idempotent Consumer, wearing a different hat

The idempotent readLock strategy uses the same IdempotentRepository interface Chapter 16's idempotentConsumer() EIP used to filter duplicate messages. The warning from that chapter applies here without modification: an in-memory repository's history doesn't exist anywhere another route instance, or a fresh process after a restart, can see it. If more than one instance of this route might poll the same directory, the repository backing readLock=idempotent needs to be something all of them share — not the default in-memory one.

Naming a write so a reader knows it's finished

Locking solves the problem from the reader's side: keep checking until the file looks stable. tempFileName and tempPrefix solve the same problem from the writer's side instead — the producer writes under a temporary name and renames to the real name only once the write is complete. A downstream consumer watching for the final filename to simply appear is then a reliable completion signal on its own, without needing a readLock at all. This is the cleaner fix when you control both ends of a hand-off.

Write under a temp name, rename on completion
from("direct:writeReport")
    .to("file:data/outgoing?tempPrefix=.inprogress-");

// Downstream: no readLock needed — the filename itself is the signal
from("file:data/outgoing")
    .to("direct:shipReport");

doneFileName is the same idea, mirrored for a producer that can't rename atomically — a legacy job that streams a growing file, say. Instead of inspecting the data file's own stability, the consumer waits for a separate, named companion file to appear, and Camel supports two dynamic tokens for deriving that name: ${file:name} and ${file:name.noext}.

Wait for a companion .done file instead of inspecting the data file
from("file:data/incoming?doneFileName=${file:name}.done")
    .to("direct:processOrder");

On the producer side, one more option decides what happens when the target name is already taken: fileExist, with six values — Override (the default, overwrite), Append, Fail (throw), Ignore (skip the write silently), Move (move the pre-existing file aside first, per moveExisting), and TryRename (only meaningful with tempFileName — rename straight to the final name with no exists-check at all, faster on filesystems, and especially FTP servers, where a check is its own network round trip). One combination is rejected outright: fileExist=Append together with tempPrefix/tempFileName — pick one write strategy, not both.

After a successful read: delete, move, and the default you didn't ask for

What happens to a file once its exchange completes is controlled by delete, move, moveFailed, and preMove — and choosing none of them is itself a default, not an omission. If a route sets neither delete=true, move, nor noop=true, Camel's out-of-the-box behavior is to move the processed file into a hidden .camel subdirectory next to the original. The file isn't deleted — it just looks that way, until someone knows to go look in .camel.

Archive successes, quarantine failures, separately
from("file:data/incoming?move=processed/${file:name}&moveFailed=failed/${file:name}")
    .to("direct:processOrder");

SFTP: the same model, over SSH, with two defaults worth changing

An SFTP endpoint is addressed as sftp://host:port/directory?options, defaulting to port 22, and layers SSH-specific configuration on top of the same GenericFile option set covered above — the same readLock, move/delete, and doneFileName options all apply unchanged. Authentication is either username/password, or key-based via privateKeyFile / privateKeyUri (plus privateKeyPassphrase if the key needs one).

Two defaults deserve a second look before this goes anywhere near production. strictHostKeyChecking defaults to no — host-key verification is effectively disabled unless a route sets it explicitly, which is a real man-in-the-middle exposure, not a lint warning to silence. And useUserKnownHostsFile defaults to true, meaning Camel will silently read the running process's own ~/.ssh/known_hosts unless knownHostsFile (or knownHostsUri) points it at a dedicated, deployment-managed file instead.

Overriding both insecure defaults on purpose
from("sftp://partner.example.com:22/outbound?username=integ&privateKeyFile=/secrets/id_rsa"
    + "&knownHostsFile=/secrets/known_hosts&strictHostKeyChecking=yes&delay=30000")
    .to("file:data/from-partner");
"It connected fine" is not the same as "it connected to the right server"

With strictHostKeyChecking=no, a route that silently starts talking to a different host — DNS poisoning, a compromised jump box, an attacker sitting between you and the partner's server — looks exactly like a route that's working. There's no exception, no log line, nothing to notice. Setting strictHostKeyChecking=yes with an explicit, deployment-managed knownHostsFile turns a silent failure mode into a loud one: the connection simply refuses to proceed against an unrecognized or changed host key.

Large files: streamDownload, and a hang worth knowing about

By default, an SFTP (or FTP) consumer downloads a file completely to a local temp file before handing it to the route. streamDownload=true changes that: the route body becomes a live InputStream instead, so processing can start without buffering the entire object in memory or on disk first — the option to reach for once "large file" stops being hypothetical.

It comes with a documented catch worth knowing before it costs you a debugging session: combining streamDownload=true with the default stepwise=true directory navigation has a tracked hang/deadlock on files past roughly half a megabyte (CAMEL-12472, CAMEL-14506). The recorded workarounds are either disabling stepwise or pairing streamDownload with localWorkDirectory, so the "stream" is backed by a temp file instead of held open directly against the live SSH channel.

The safer pairing for a large-file SFTP pull
from("sftp://reports.example.com/exports?username=integ&password={{sftp.password}}"
    + "&streamDownload=true&stepwise=false")
    .to("file:data/large-imports");

Object storage: aws2-s3, the bucket as a directory

An aws2-s3: endpoint is addressed as aws2-s3://bucketName?options, authenticating with accessKey/secretKey/ region (or a configured default AWS credentials chain, the usual choice once you're past local testing). The consumer polls a bucket the same scheduled-poll way a file: endpoint polls a directory — but two of its defaults are the opposite of what you might expect, coming from file:.

Two aws2-s3 defaults that flip file:'s defaults
Optionaws2-s3 defaultfile: equivalent default
deleteAfterReadtruedelete defaults false (files move to .camel instead)
autoCreateBuckettrueNo equivalent — a bad file: path just fails

deleteAfterRead=true means an object is removed from the bucket as soon as its exchange commits — only on commit, not on a rollback — which is the S3 analogue of file:'s delete option, except on by default rather than opt-in. And autoCreateBucket=true means a route pointed at a misspelled or not-yet-provisioned bucket name will silently create a new, empty bucket rather than fail loudly — a configuration mistake that hides behind what looks like a working, if suspiciously empty, integration.

Read both defaults before the first deploy, not after the first incident

Set deleteAfterRead=false on purpose if a bucket is meant to be a durable archive rather than an inbox to drain, and set autoCreateBucket=false on purpose once bucket provisioning is meant to be someone else's deliberate, tracked decision — not a side effect of a route starting up with a typo in its URI.

On the producer side, streamingUploadMode=true switches to a multipart upload so a large body can be sent without knowing its total size up front, completing once batchSize or batchMessageNumber is reached — conceptually the S3 counterpart of the file producer's tempFileName pattern from earlier in this chapter, except the atomicity boundary is the multipart-complete call rather than a filesystem rename.

Streaming a large upload to S3, chapter 18's two transports end to end
from("sftp://reports.example.com/exports?username=integ&password={{sftp.password}}&streamDownload=true&stepwise=false")
    .to("aws2-s3://ingest-bucket?accessKey={{aws.key}}&secretKey={{aws.secret}}&region=US_EAST_1&streamingUploadMode=true");
Every option in this chapter answers the same underlying question in a different guise: how does one side know the other side is finished? A lock says "wait until it stops changing." A rename says "the name itself is the answer." A done-file says "I'll tell you separately." Object storage's commit-then-delete says "only count it once it's certain." Pick the mechanism the write side can actually guarantee — the read side's safety depends on it, not the other way around.

So what did we actually gain?

A vocabulary that travels: readLock, move, delete, and doneFileName mean the same thing whether the endpoint is a local directory or a partner's SFTP server, because both sit on the same GenericFile abstraction. What changes — and what deserves the most attention before a route goes anywhere near production — are the defaults: readLock=none, strictHostKeyChecking=no, and object storage's deleteAfterRead=true/autoCreateBucket=true are all defaults chosen for convenience in a quick test, not for a partner-facing production pipeline. Chapter 19 moves to the transport most integrations reach for first — HTTP and REST APIs — where the same underlying question resurfaces in a new shape: a request either gets a timely answer or it doesn't, and the route has to decide what "doesn't" means.

  2. A partner's SFTP drop connects successfully every time, with the component's defaults untouched. What two settings would you check first, and what silent risk does leaving them at their defaults create?
  3. An aws2-s3 consumer route has been running for a week against a bucket name that turns out to have a typo in it, yet nobody got an error. Which default explains that, and which one explains why the objects it "processed" can no longer be found in the bucket it meant to read from?
