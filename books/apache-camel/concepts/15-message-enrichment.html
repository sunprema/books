Message Enrichment

Chapter 14 ended on a turn: multicast and recipient lists both push one message out to more places. This chapter pushes in the other direction. An order arrives with nothing but a customer ID on it — no name, no shipping address, no loyalty tier. The route doesn't need to send that order anywhere else yet; it needs to become more complete before anything downstream can use it. Message Enrichment is Camel's answer: reach out to a second source, pull back what's missing, and fold it into the exchange you already have. Camel gives you two ways to do that reaching — enrich(), which asks a service for an answer, and pollEnrich(), which checks a place for whatever's already sitting there — and one hazard that comes with both: now your route's correctness depends on a system you don't control.

enrich(): ask a service, fold the answer in

enrich() sends the current exchange to a resource endpoint — a producer, exactly like a .to() call — and treats it as a request-reply conversation: whatever that endpoint sends back becomes a second exchange, ready to be combined with the one already in flight. It's the natural fit for anything that answers a question on demand: a customer-lookup HTTP service, a pricing bean, a database call wrapped as a Camel endpoint.

Look the customer up, keep the order flowing
from("direct:orderReceived")
    .enrich("direct:customerLookup", new CustomerEnrichmentStrategy())
.to("direct:orderValidated");

// direct:customerLookup takes the order's customerId and replies with
// a full Customer record — name, address, loyalty tier — as its body

You've already met the shape that combines the two exchanges — Chapter 13's AggregationStrategy, the same aggregate(Exchange oldExchange, Exchange newExchange) interface split() and multicast() used. enrich() hands it something simpler than either of those did: no accumulating loop, no oldExchange == null first-call case to guard against. It's called exactly once, and the two arguments are fixed by definition — oldExchange is always the original exchange, the order as it existed before enrich() ran; newExchange is always the resource exchange, the customer-lookup's reply. Your strategy's whole job is deciding what the merged result should look like:

CustomerEnrichmentStrategy.aggregate — keep the order, add the customer
public Exchange aggregate(Exchange oldExchange, Exchange newExchange) {
    Order order = oldExchange.getMessage().getBody(Order.class);
    Customer customer = newExchange.getMessage().getBody(Customer.class);
    order.setCustomer(customer);
    oldExchange.getMessage().setBody(order);
    return oldExchange;
}
No AggregationStrategy means the resource's reply replaces everything

Drop the second argument — enrich("direct:customerLookup"), nothing else — and Camel doesn't merge anything. It just uses the resource endpoint's reply body as the new outgoing body, full stop. The order you had is gone; the exchange downstream is now a bare Customer, not an order with a customer attached. It's the same shape of trap Chapter 13's split() and Chapter 14's multicast() both set with no strategy supplied — a quiet default that discards data instead of failing loudly — just aimed the other direction: there, the later results got dropped; here, the original message does.

pollEnrich(): check a place, instead of asking a service

Some enrichment sources don't answer questions — they just sit there with data waiting to be picked up. A landing directory with a reference file. A seda queue holding the latest FX rate a scheduler refreshed on its own timer. There's no request to send; there's only something to check. pollEnrich() is built for exactly that: instead of calling the resource endpoint as a producer, it reads from it as a Polling Consumer — the same take-whatever's-there action a from() performs, but invoked on demand, mid-route, once. Critically, pollEnrich() does not send the current exchange to the resource endpoint at all; it just polls whatever's already sitting there.

Attach today's FX rate, waiting at most 5 seconds for one to be ready
from("direct:paymentReceived")
    .pollEnrich("seda:latestFxRate", 5000, new FxRateEnrichmentStrategy())
.to("direct:paymentConverted");

That middle argument is pollEnrich()'s one genuinely new idea: a timeout in milliseconds, and its sign changes what it means, not just how long it waits. A negative value — -1, the default if you omit it — waits until a message is available and can block indefinitely. Zero attempts to receive immediately and returns null the instant nothing is there, no waiting at all. A positive value waits up to that many milliseconds and returns null if it times out. Camel's own documentation calls an explicit timeout "good practice" — leave it at the indefinite default and one empty resource endpoint stalls the calling thread with no way out.

A timed-out poll hands your AggregationStrategy a null newExchange

Give pollEnrich() a timeout and eventually you'll hit it — nothing was on the endpoint in time. That doesn't fail the exchange. It calls aggregate(oldExchange, newExchange) with newExchange set to null, and it's entirely your strategy's job to notice. A strategy written only for the happy path — unconditionally calling newExchange.getMessage() — throws a NullPointerException the first time the poll comes up empty. Check for null before you touch it, the same discipline Chapter 13 asked of a strategy handling its own first call.

One more difference worth holding onto: because pollEnrich() never sends the current exchange anywhere, it can't automatically know anything about it either. It can't, for instance, implicitly reuse a header your route set upstream to decide which file to read. If the resource endpoint needs to vary per message, you tell it to explicitly — both enrich() and pollEnrich() accept a dynamic URI built from an expression evaluated against the current exchange, the same trick Chapter 12's toD() used:

A per-message endpoint, computed from a header
.pollEnrich().simple("seda:${header.RateFeed}")
.enrich().simple("http:myserver/${header.orderId}/order")

Calling external services safely

Both enrich() and pollEnrich() block the calling thread on their call to the resource endpoint — that's true whether the resource replies in five milliseconds or hangs for thirty seconds. An enrichment source you don't own is now on the critical path of every exchange that needs it, and Camel gives you three separate knobs for keeping that dependency from taking your route down with it.

The first is the one you've already seen: set a real timeout. pollEnrich()'s timeout argument bounds the wait directly. enrich() has no timeout argument of its own — because it calls a producer synchronously, the bound has to come from the producer's own configuration (an HTTP component's request timeout, a JDBC pool's query timeout) or from wrapping the call, which is the second knob.

The second is aggregateOnException, an option shared by both enrich() and pollEnrich(), defaulting to false. Left at its default, a failure calling the resource endpoint skips your AggregationStrategy entirely and the exception just propagates straight to the route's error handler — your strategy never gets a say. Set it to true and a failed enrichment call routes into aggregate() instead, letting the strategy inspect the failure and decide what a degraded-but-still-moving exchange should look like, rather than losing the whole message to one bad lookup.

Protecting an HTTP enrichment call with a circuit breaker
from("direct:orderReceived")
    .circuitBreaker()
        .to("direct:customerLookup")
    .onFallback()
        .transform().constant(new Customer())
    .end()
.to("direct:orderValidated");

The third is that circuit breaker itself — .circuitBreaker(), backed by Resilience4j, wrapping the block that calls out. Tunables like failureRateThreshold, slidingWindowSize, and timeoutDuration let it notice a resource that's failing or slowing down and trip open, routing to onFallback() instead of letting every subsequent exchange queue up behind a dependency that's already in trouble. It's the same instinct as a real bulkhead: one struggling enrichment source degrades gracefully to "no customer data yet" instead of taking every route that touches it down with it.

cacheSize: the same dynamic-endpoint caution as toD() and recipientList()

A dynamic resource URI — .enrich().simple(...) — means Camel may see a genuinely different endpoint on every message. cacheSize (default 1000) bounds how many producers or consumers it keeps warm for those computed URIs. If the URIs are essentially one-off — a per-order or per-customer endpoint that's never reused — set cacheSize to a negative value to turn caching off outright, rather than let Camel hold open producers for endpoints it will never see again. If a bounded, reused set of dynamic URIs repeats across messages, the cache earns its keep as written — the same call Chapter 14 asked you to make for recipientList()'s cacheSize.

Two enrichers, one hazard

Reach for enrich() when the resource is something you ask a question — an HTTP service, a bean, a database call — and expect a reply to the exchange you sent it. Reach for pollEnrich() when the resource is a place with data already sitting in it — a file, a directory, a queue — and there's nothing to send, only something to check. Both fold their result into the exchange you already have through the same AggregationStrategy shape; both default to quietly discarding data if you don't supply one — enrich() drops the original message, pollEnrich() can hand your strategy a null reply. And both, because the call is synchronous and blocking, put an external dependency's health on your route's critical path the moment you wire one in.

Multicast and Recipient List answered "how many places should this message reach." enrich() and pollEnrich() answer the opposite question — "what does this message still need before it's complete" — using the exact same AggregationStrategy contract, aimed inward instead of outward.

So what did we actually gain?

A way to complete a message from a second source, cleanly split by how that source behaves: enrich() for a service you ask, pollEnrich() for a place you check, both handing off to the AggregationStrategy you already know from Chapter 13. And a reminder that every enrichment call is a dependency you've just taken on — aggregateOnException, a real timeout, and circuitBreaker() are the three ways to keep that dependency's bad day from becoming your route's bad day. The pattern this chapter didn't cover is what happens when the enrichment call (or anything else downstream) fails outright and the message needs to be tried again without becoming a duplicate — that's Chapter 16, Reliable Message Delivery.
