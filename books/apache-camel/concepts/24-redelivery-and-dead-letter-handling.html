Redelivery and Dead-Letter Handling

The last chapter closed with a deliberate gap: it told you how to decide, exception type by exception type, whether a failure should be swallowed, rethrown, or resumed — but it kept saying "the next chapter" every time the conversation turned to how many times to try again, how long to wait, and where a message goes once every attempt has failed. This is that chapter. The two halves fit together as one idea: onException decided whether a failure gets a second chance; everything here decides what that second chance actually looks like, and what happens when you run out of them.

The retry knob nobody turns by accident

Every onException clause and every errorHandler() carries a RedeliveryPolicy — the object that decides how many times Camel tries again and how long it waits between attempts. Its most important default is easy to miss precisely because it's quiet: maximumRedeliveries is 0 unless you say otherwise. Declare onException(SQLException.class).handled(true) with nothing else, and you get exactly one attempt — the clause changed what happens after the failure, not how many times Camel tried first. Redelivery is opt-in, on every single clause, every time.

Asking for retries, explicitly
onException(ConnectException.class, SQLException.class)
    .maximumRedeliveries(5)
    .redeliveryDelay(2000)
    .retriesExhaustedLogLevel(LoggingLevel.ERROR)
    .to("direct:deadLetter");

maximumRedeliveries(5) means what it says: up to five extra attempts after the original, six chances total for the exchange to succeed. Set it to a negative number and Camel retries forever — a real setting, occasionally the right one for a route where giving up is worse than waiting, but one that deserves a comment explaining why. redeliveryDelay is the fixed pause between attempts, in milliseconds, defaulting to 1000 (one second) if you enable redeliveries without setting it. Two log levels shape how loud each stage of this gets: retryAttemptedLogLevel (default DEBUG, often raised in production so an operator can see retries happening in real time) covers each individual attempt, and retriesExhaustedLogLevel (default ERROR) covers the one moment that actually deserves a page — the final give-up.

Backoff: spacing attempts so they don't make things worse

A fixed delay is fine for one failing exchange. It's a bad idea for a thousand of them at once. If a downstream database goes down for thirty seconds, every in-flight exchange fails at roughly the same moment and, with a flat redeliveryDelay, retries in near-lockstep — hitting the database with a synchronized burst the instant it comes back, which is a good way to knock it back down. useExponentialBackOff() is the fix: each delay becomes the previous delay times backOffMultiplier (default 2), so attempts space themselves out as the outage drags on instead of hammering at a constant rate. maximumRedeliveryDelay (default 60000ms, one minute) caps how large that growing delay is allowed to get, so exponential growth doesn't wander off into hours-long waits on a long exhaustion sequence. useCollisionAvoidance() goes one step further, adding a small random jitter to each computed delay — the difference between a thousand clients retrying at exactly second 8 and a thousand clients retrying somewhere between second 6 and second 10.

One more knob, for when neither a flat delay nor a smooth exponential curve fits: delayPattern takes a string like "5:1000;10:5000;20:20000" and reads as a table — attempts 0–4 wait 0ms, attempts 5–9 wait 1000ms, attempts 10–19 wait 5000ms, attempt 20 and beyond wait 20000ms. It's a full replacement for the delay calculation, not an addition to it: set delayPattern and redeliveryDelay, backOffMultiplier, useExponentialBackOff, and useCollisionAvoidance are all ignored. And if the delay itself — however it's computed — shouldn't block the thread that's processing the exchange, asyncDelayedRedelivery() schedules the wait on Camel's own redelivery thread pool instead of parking the calling thread for the full duration.

What "exhausted" actually means

Once maximumRedeliveries attempts have all failed, Camel stops trying and marks the exchange exhausted — recorded as exchange properties, the same way Chapter 23's Exchange.EXCEPTION_CAUGHT lives as a property rather than a field: Exchange.REDELIVERY_COUNTER for how many attempts actually ran, and Exchange.REDELIVERY_MAX_COUNTER for the configured ceiling it hit. What happens next depends entirely on which error handler is in play, which is the distinction the previous chapter drew and this one finally pays off: with the bare DefaultErrorHandler, exhaustion ends exactly like any other unhandled exception — logged, and propagated straight back to the caller. With a Dead Letter Channel configured, the exhausted exchange is redirected to a dead-letter destination instead, and — unless you explicitly set handled(false) — it's marked handled on the way out, so the original caller sees an ordinary completion, not a failure. The problem hasn't been solved. It's been redirected somewhere a human can look at it later.

onRedelivery fires before each retry, not before the first attempt

A RedeliveryPolicy can take its own onRedelivery(Processor), which runs immediately before every redelivery attempt — useful for stamping a header with the attempt count, or emitting a metric per retry:

onException(Exception.class)
    .maximumRedeliveries(3)
    .onRedelivery(exchange -> {
        int attempt = exchange.getProperty(Exchange.REDELIVERY_COUNTER, Integer.class);
        log.warn("Retry attempt {}", attempt);
    })
    .handled(true)
    .to("direct:deadLetter");

It doesn't run before the original, first attempt — only before each retry that follows a failure, which is exactly what its name promises and exactly the detail that trips people up counting attempts.

Configuring the Dead Letter Channel

There are two places to wire a dead-letter destination in, and they answer two different questions. Make it the route's error handler when you want one destination and one policy to catch anything not already claimed by a more specific onException clause:

A dead-letter destination as the route's error handler
errorHandler(deadLetterChannel("jms:queue:orders.dead")
    .useOriginalMessage()
    .maximumRedeliveries(5)
    .redeliveryDelay(5000)
    .retriesExhaustedLogLevel(LoggingLevel.ERROR));

Or pair it with a specific onException clause, the pattern Chapter 23 already used for ConnectException and SQLException: a redelivery policy followed by .to(deadLetterUri) as the clause's last step. That gives you per-exception-type destinations and policies instead of one blanket rule — a validation failure never even reaches this machinery (it's handled(true) with no redelivery, straight to a rejection queue), while a database timeout gets five retries with backoff before landing in orders.dead.

Two smaller options are worth knowing before they surprise you. useOriginalMessage() sends the exchange's original incoming body and headers to the dead-letter destination — not whatever the route had transformed the message into by the time it failed. Without it, a route that parses CSV into JSON before failing on step four sends the JSON to the dead-letter queue, which is often useless for debugging what actually arrived. And deadLetterHandleNewException, true by default, decides what happens if moving the exchange to the dead-letter destination itself throws — left true, that second exception is caught so it doesn't mask the original failure that got the exchange there in the first place.

Manual recovery and replay

A dead-letter destination that's just a log line is only half a dead letter channel. The point of routing failed exchanges somewhere durable — a JMS queue, a Kafka topic, a database table, a directory of files — is that "exhausted" doesn't have to mean "lost." A message sitting in orders.dead is one an operator can inspect, understand, and, once the actual problem is fixed, move back to the original input queue to be reprocessed from scratch. That's the entire value of choosing a durable destination over letting DefaultErrorHandler just propagate and vanish into a stack trace.

Replay is a decision, not a default

It's tempting to build a scheduled job that automatically requeues everything sitting in the dead-letter destination. Resist it. A message that failed because of a genuinely bad payload or a code defect — a real poison message — fails identically the second time, and blind auto-replay just re-poisons the queue on a loop. Replay belongs after a human (or a narrowly-scoped, well-understood automated rule) has confirmed the failure was actually transient, or that whatever caused it has actually been fixed. The dead-letter queue's job is to make that judgment call possible later, not to make it for you now.

There's a second trap waiting in replay specifically, and it connects back to Chapter 16: messaging systems deliver at-least-once, and redelivery plus dead-letter replay are two more ways the same logical message can be processed more than once — once on the original attempt (which may have partially succeeded downstream before ultimately failing), and again when it's replayed. A route that reprocesses dead-lettered messages without an idempotentConsumer() guarding the reprocessing path can double-apply an order or a payment. The fix isn't new machinery — it's the same idempotent-consumer pattern from Chapter 16, applied to the replay path as deliberately as it's applied to the original one.

A retry policy is a bet that the world gets better if you wait. A dead-letter destination is the fallback for when that bet doesn't pay off — not a trash can, but a waiting room, built so that "we tried, and it still didn't work" has somewhere durable to go besides a log line nobody reads until the customer calls.

So what did we actually gain?

The other half of the machinery Chapter 23 promised: a RedeliveryPolicy that defaults to zero retries until you ask for more, fixed or exponential delays with a cap so backoff doesn't run away, jitter for when a whole fleet of exchanges fails at once, and delayPattern for when neither fixed nor exponential fits the shape you actually need. A precise picture of exhaustion — what the redelivery counter properties record, and how the same "no more attempts" moment ends completely differently depending on whether a Dead Letter Channel is configured. Two places to wire one in, route-wide or per exception, plus useOriginalMessage() for keeping the dead-lettered payload honest. And the piece that's easy to treat as an afterthought but isn't: a dead-letter destination is only useful if something durable receives it and a human, eventually, decides whether it's safe to replay. Redelivery policy and Dead Letter Channel are both configuration — declarative, testable, inspectable. Whether that configuration actually does what you think under real failure is a different question, and it's the one the next chapter takes on directly: how do you write a test that proves a route retries the right number of times, waits the right amount, and lands in the right dead-letter queue, without waiting through real backoff delays to find out?

Check yourself

  1. A route declares onException(TimeoutException.class).handled(true).to("direct:deadLetter") with no other settings. A step throws a TimeoutException. How many total attempts does Camel make before the exchange reaches direct:deadLetter, and why?
  2. Two routes both configure maximumRedeliveries(4) with a 1000ms redeliveryDelay and useExponentialBackOff(). One also sets maximumRedeliveryDelay(3000); the other doesn't. What's the wait before the fourth (final) redelivery attempt in each case?
  3. An operator sees a dead-letter queue with two thousand messages that all failed with the same NullPointerException from a bug deployed an hour ago. The bug has just been fixed and redeployed. Is it now safe to auto-replay every message in that queue? What would you check first?
