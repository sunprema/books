Alternative Route DSLs

Chapter 06 closed on a promise: Java is this book's default, but it isn't the only way to write a Camel route, and the other options have real strengths that chapter deliberately didn't cover. You've actually already written one of them — Chapter 05's heartbeat and file-copy routes were YAML all along, before Chapter 06 rewrote them as Java. This chapter goes back to finish that thought: what YAML DSL actually looks like once routes get more interesting than from/log/to, what XML DSL is (there turn out to be two of them), and how to actually decide which one a given route, or a given team, should use.

One route, three spellings

Start from something you already know cold: Chapter 05 and 06's orders-copy route, a plain file-to-file copy with one log line. Here it is a third time, unchanged in behavior, in the two DSLs Chapter 06 didn't cover.

orders-copy.yaml — the YAML DSL, as first seen in Chapter 05
- route:
    id: orders-copy
    from:
      uri: file:data/incoming
      parameters:
        noop: true
      steps:
        - log:
            message: "Copying ${header.CamelFileName}"
        - to:
            uri: file:data/outgoing
hello.xml — the same route, in Camel 4's XML IO DSL
<routes xmlns="http://camel.apache.org/schema/xml-io">
  <route id="orders-copy">
    <from uri="file:data/incoming?noop=true"/>
    <log message="Copying ${header.CamelFileName}"/>
    <to uri="file:data/outgoing"/>
  </route>
</routes>

Same URI, same noop, same log message, same route ID. That's not a coincidence — it's the whole point. Java, YAML, and XML routes all get parsed down into the same internal route model that CamelContext actually runs. A choice() call, a choice: YAML block, and a <choice> XML element all become the identical ChoiceDefinition object underneath. The DSL changes how you write a route and what tooling you get while doing it — it changes nothing about how the route behaves once Camel starts it.

Why this matters more than it sounds like it should

Because every DSL compiles to the same model, nothing you learned in Part I is DSL-specific. The Exchange, the EIPs, the components, the URI shape — all of it is Camel's vocabulary, not Java's. What's left to learn here is genuinely just spelling, plus the practical question of which spelling fits a given project.

The YAML DSL, past the basics

Chapter 05 already showed the shape: a route is a list item under a top-level - route: key, from is a mapping with a uri and an optional parameters map, and steps is the ordered list after it, each entry a one-key map naming the EIP it represents. That shape holds for simple, linear routes. It gets more interesting the moment an EIP needs its own sub-pipeline — and choice, the Content-Based Router from Chapter 03, is exactly that kind of EIP. Here's the country-routing example from Chapter 03, reproduced in YAML:

Content-Based Router (Chapter 03), in YAML
- route:
    from:
      uri: jms:queue:orders.validated
      steps:
        - choice:
            when:
              - simple: "${header.CamelOrderCountry} == 'US'"
                steps:
                  - to:
                      uri: jms:queue:orders.domestic
            otherwise:
              steps:
                - to:
                    uri: jms:queue:orders.international

Compare that against Chapter 03's Java version and the pattern is identical, just re-expressed: choice: opens the block, when: is a list where each entry pairs a predicate (here simple:, the same expression language Chapters 05 and 06 used for ${header...} lookups) with its own nested steps: list, and otherwise: gets one too. Java's .end(), which closes a nested EIP block, has no YAML equivalent — indentation does that job instead. That's the tradeoff in one example: no method to forget, but a misplaced two spaces silently attaches a step to the wrong branch instead of failing to compile.

Indentation is the scope, not a suggestion

A to: entry indented one level too shallow under a choice: block doesn't raise an error — it just becomes a step in a different list than the one you meant. There's no compiler to catch it, and a route that "runs fine" against the wrong test case can hide this for a while. It's the single most common source of "my YAML route isn't doing what the file clearly says" bug reports.

YAML is also the newest of Camel's DSLs, and it was added for a specific reason: cloud-native and low-code workflows. Camel K's Kubernetes Integration and Pipe custom resources are written in YAML, and so is the output of most visual, drag-and-drop route editors — because a YAML document is just data. It's trivial to store in a ConfigMap, diff cleanly in a pull request, and generate programmatically from a UI, none of which is true of a compiled Java class. If a route's home is eventually a Kubernetes cluster rather than a JAR your team builds, YAML is very often already the native format for getting it there.

Two XML DSLs, not one

This is the part that trips people up: "the XML DSL" is actually two different formats that happen to share a file extension. Get them confused and schema validation fails in a way that looks nothing like the mistake you actually made.

Camel's two XML DSLs
 XML IO DSLSpring XML DSL
Root element<routes> (or a bare <route>)<camelContext> inside a Spring <beans>
Namespacecamel.apache.org/schema/xml-iocamel.apache.org/schema/spring

The XML IO DSL is Camel 4's own format, and it's the one you've technically already met: it's what camel init hello.xml from Chapter 04 scaffolds and camel run hello.xml executes, with no Spring, no camelContext, and no framework of any kind involved — just a <routes> document Camel reads directly. It's shown at the top of this chapter, and it reads almost exactly like the YAML above with angle brackets instead of indentation.

The Spring XML DSL is the older format — the one this book's brief calls out specifically because of where you'll actually meet it: not in a new project, but inside an existing Camel 2.x or 3.x application that was built before Spring Boot's auto-configuration (Chapter 04) existed, when wiring a camelContext by hand inside a Spring <beans> file was the normal way to run Camel inside Spring. Here's the same file-copy route in that shape:

The classic Spring XML shape — what a Camel 2.x/3.x Spring app's route file looks like
<beans xmlns="http://www.springframework.org/schema/beans"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="http://www.springframework.org/schema/beans
         http://www.springframework.org/schema/beans/spring-beans.xsd
         http://camel.apache.org/schema/spring
         http://camel.apache.org/schema/spring/camel-spring.xsd">
  <camelContext xmlns="http://camel.apache.org/schema/spring">
    <route id="orders-copy">
      <from uri="file:data/incoming?noop=true"/>
      <log message="Copying ${header.CamelFileName}"/>
      <to uri="file:data/outgoing"/>
    </route>
  </camelContext>
</beans>

Notice how much of that is boilerplate that has nothing to do with the route itself — the xsi:schemaLocation, the nested namespaces, the beans wrapper. That's the cost of a format built for a specific framework's XML config machinery rather than for Camel alone, and it's exactly why the newer XML IO DSL exists: same idea, no Spring tax. If you inherit an application in this shape, the pragmatic move is almost always to keep extending it in the same format — migrating a working Spring-XML route tree to YAML or Java is a real project with real risk, not a free syntax swap, and it isn't a prerequisite for adding one more route to the file.

Choosing an appropriate DSL

There's no objectively best Camel DSL, and that's not a cop-out — it follows directly from the last section. Since every DSL compiles to the same model, the question is never "which one is more powerful," it's "which one fits this route, this team, this deployment target." A few concrete pulls in each direction:

What actually pulls you toward each DSL
Reach for…when…
Javaa route needs to be generated — loops, conditionals, dependency injection (Chapter 06) — or your team already lives in JVM tooling and wants compile-time checking and real refactoring for free.
YAMLroutes are simple-to-moderate, need to be edited or generated by non-Java tooling (a low-code UI, a CI template, a Camel K Pipe), or you specifically want routes to be plain, diffable data with no compiler in the loop.
XML IOyou want an XML-shaped route with none of Spring XML's baggage — e.g. schema-validated config for a non-Java tool to write, without pulling in Spring.
Spring XMLyou're maintaining, not greenfielding — an existing Camel 2.x/3.x Spring XML application, where the pragmatic move is to keep extending it in its own format.

Tooling has narrowed the gap between these choices more than most developers expect: a community Camel Language Server and IDE plugins bring route completion, structural validation, and even a route debugger to YAML and XML routes in IntelliJ IDEA and VS Code, not just Java. What Java still gets that the others don't is that support for free, from the JVM's own compiler and refactoring tools, with no Camel-specific plugin required — a real but narrower edge than Chapter 06 might have implied on its own.

And nothing here is a one-way door for a whole project. Camel doesn't require one DSL per CamelContext — a Spring Boot application can load Java RouteBuilder routes and YAML route files side by side, which is exactly how a team migrates incrementally instead of committing to a rewrite. The DSL is a per-route-file decision, not a once-per-project one.

You don't have to pick just one

A project standardizing on Java DSL for its hand-written business routes can still load a vendor- or ops-supplied YAML route file unchanged. Both get auto-detected and started the same way Chapter 06's @Component-annotated RouteBuilder was. Mixing DSLs across files in one application is normal, not a smell.

Check yourself

  1. You paste a <camelContext>…</camelContext> block into a fresh Camel 4 XML IO file expecting it to run. Startup fails with a schema validation error. What did you actually mix up, and why does the file extension being the same for both formats make this an easy mistake?
  2. A YAML route's choice block routes every order to otherwise, even ones that should clearly match a when. There's no error anywhere. What's the first thing you'd check, given what this chapter said about how YAML represents nested scope?
  3. A teammate argues the whole team should rewrite an inherited Camel 3.x Spring-XML application into YAML "to modernize it" before adding any new routes. Using this chapter's reasoning about what a DSL choice actually costs and buys you, what would you push back on?

So what did we actually gain? Not new routing behavior — every example on this page does exactly what Chapters 04 through 06 already did. What's new is the vocabulary to read (and choose) whichever format a given Camel project happens to be written in, and the confidence that switching formats never means relearning Camel itself, only its spelling. Part III turns from how a route is written to what actually flows through it once it runs: the Exchange, in full.
