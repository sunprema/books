Working with Data Formats

Chapter 09 closed with a promise: this chapter would put JSON, XML, and CSV to work "using exactly the type-converter machinery this chapter just opened up." That's close enough to be useful and wrong enough to be worth stopping on, because the gap between "close enough" and "exact" is precisely the gap that bites people the first time they reach for convertBodyTo where they needed something else entirely. So let's be exact. Marshalling and unmarshalling use a second machine — related to type conversion, built the same way, but not the same registry, and not the same DSL entry point.

A second machine, not the one Chapter 09 promised

Chapter 09's type-converter registry answers one question: given a value of type A, can you hand me type B? getBody(Class) and convertBodyTo(Class) both ask it, and it answers from converters scanned off the classpath at startup — String to InputStream, byte[] to String, and anything else a @Converter class happens to register. It is genuinely useful for exactly this chapter's subject — but it is not what does the work when a message crosses the edge of your system as JSON, XML, or CSV. That's a second, purpose-built mechanism: the Data Format, reached through the marshal() and unmarshal() EIPs, not through getBody.

The distinction earns its keep once you say what each one is actually good at. A type converter changes one Java type into another Java type — still Java on both sides. A data format changes a Java object into an external wire representation, or back — the whole current message body, going out as bytes a JMS broker or an HTTP client can carry, or coming in as bytes that need to become an Order again before anything downstream can read a field off it. marshal(dataFormat) does the outbound half; unmarshal(dataFormat) does the inbound half. Both delegate to a pluggable DataFormat implementation — Jackson for JSON, JAXB for XML, Apache Commons CSV for CSV — the same way a converter delegates to whatever @Converter method matches.

Why convertBodyTo(String.class) won't give you JSON

It's tempting to reach for the tool you already know. But convertBodyTo only ever asks the type-converter registry, and camel-core ships no built-in converter from an arbitrary POJO to a JSON string — that conversion needs a library (Jackson) to walk the object's fields, which is exactly what a DataFormat exists to do. Reach for marshal().json() instead; it's the tool actually built for this job.

JSON with Jackson

JSON isn't wired into camel-core — it's library-pluggable. Camel supports several JSON libraries (Jackson, Gson, Johnzon, and historically XStream), selected with a JsonLibrary argument or by which JSON dataformat dependency is on the classpath. Jackson, via the camel-jackson dependency, is the one you'll reach for by default and the one this book uses.

Unmarshal in, marshal out
from("jms:queue:orders.raw")
    .unmarshal().json(JsonLibrary.Jackson, Order.class)
    .bean("orderService", "process")
    .marshal().json(JsonLibrary.Jackson)
    .to("jms:queue:orders.confirmed");

Notice the asymmetry: unmarshal needs to be told Order.class so it knows what to build; marshal doesn't — it only ever needs to know the object it already has. That's the same shape you'll see repeat across every format in this chapter.

Skipping unmarshalType doesn't fail — it just stops being what you expected

Leave the target class off .json(JsonLibrary.Jackson) and Camel doesn't complain. It hands you a java.util.Map (or a List of them, for a JSON array) instead of the Order you were picturing. The route keeps running; the failure shows up two steps later as a ClassCastException the moment something calls order.getTotal() on what is actually a Map, and the stack trace points at the wrong line.

XML with JAXB

Camel's standard XML data format is JAXB — the same annotation-driven binding used throughout the Java EE/Jakarta EE world. JaxbDataFormat is configured with a contextPath: not one class, but the package to scan for JAXB-annotated classes, so a single instance marshals and unmarshals every JAXB type in that package.

One JaxbDataFormat, one package of classes
JaxbDataFormat orderXml = new JaxbDataFormat();
orderXml.setContextPath(Order.class.getPackageName());

from("file:inbox/xml")
    .unmarshal(orderXml)
    .bean("orderService", "process")
    .marshal(orderXml)
    .to("file:outbox/xml");

Two things worth knowing before your first surprise. First: a class needs a JAXB root — either annotated @XmlRootElement or wrapped in a JAXBElement — before JAXB can marshal it, and a class that skips this doesn't fail to compile, it fails the first time a message actually reaches that marshal step. Second: JaxbDataFormat accepts an optional schema — one or more XSD locations — which turns on schema validation during both directions; without it, malformed XML unmarshals into whatever JAXB can salvage rather than failing loudly.

CSV with Apache Commons CSV

Camel's CSV data format wraps Apache Commons CSV. marshal() takes a Map (or anything convertible to one) and writes it out as a line. unmarshal() is where the defaults deserve a close look, because the out-of-the-box shape surprises almost everyone once.

CSV unmarshal, two shapes for the same file
ConfigurationResult typeReading a field
defaultList<List<String>>by position — row.get(0)
useMaps(true)List<Map<String,String>>by header name — row.get("OrderId")

By default there's no notion of column names at all — a CSV file becomes a list of lists, one inner list of raw field values per row. Set useMaps(true) and Camel treats the first row as a header line, using its values as the key for every row after it — the difference between reading a row positionally and reading it by name.

Splitting a CSV file into per-row processing
CsvDataFormat ordersCsv = new CsvDataFormat();
ordersCsv.setUseMaps(true);

from("file:inbox/csv")
    .unmarshal(ordersCsv)
    .split(body())
        .setBody(simple("${body[OrderId]} : ${body[Total]}"))
        .to("log:orders");

That's the Splitter EIP from Chapter 03's overview, put to real work: unmarshal the whole file into a list of rows, then split hands each row through the rest of the route on its own, one CSV line at a time.

One shape, everywhere you plug it in

Every example above used the short fluent form — .marshal().json(…), or a named JaxbDataFormat/CsvDataFormat instance passed straight to marshal(…)/unmarshal(…). Both are the same underlying idea Chapter 09 already showed you for converters: configure a data format once, reuse it — the instance form is just that pattern made explicit, useful the moment two routes need to agree on the exact same XML or CSV shape. And because the DSL is the DSL, the YAML form (Chapter 07) nests the same options under the same format name — marshal: / json: / library: Jackson — with nothing available in Java that YAML can't also say.

Marshalling can label its own output

Most data formats implement an optional contentTypeHeader behavior: when it's on, a successful marshal sets the message's Content-Type header to match — application/json, application/xml — so a route that marshals straight onto an HTTP or messaging endpoint doesn't need a separate setHeader step just to say what it just produced.

Marshal and unmarshal aren't a fancier type conversion. They're the point where a route stops being an internal pipeline of Java objects and becomes a citizen of the wire — something JSON, XML, or CSV, that another system entirely has to be able to read.

So what did we actually gain?

A precise fix to last chapter's teaser: marshalling and unmarshalling run on a second, purpose-built machine — the DataFormat SPI, reached through marshal()/unmarshal() — not the type-converter registry convertBodyTo reaches into. And three working formats on top of it: JSON through Jackson, with the unmarshalType that keeps you out of the generic-Map trap; XML through JAXB, with its package-scoped contextPath and its root-element requirement; CSV through Apache Commons CSV, with the default list-of-lists shape and the useMaps(true) switch that turns it into something you can read by column name. Every one of them hands you back a Java object — which raises the next question this book has been quietly setting aside: now that it's a Java object again, how much do you actually trust what's in it? That's next chapter's subject — validating the shape and content of what just arrived, and settling on one canonical model the rest of your routes can agree to trust.
