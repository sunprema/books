Reliable Message Delivery

Chapter 15 ended on an admission: every enrich() call, every outbound HTTP request, every call to a system you don't own, can fail outright — and the honest fix for a failed call is to try it again. But "try it again" has a cost nobody mentions in the happy-path tutorial. The first attempt might not have failed cleanly. It might have timed out after the downstream system already processed it, or after your own consumer already received it but crashed before acknowledging. Retry in either case and you haven't recovered from a failure — you've created a duplicate. Multiply that across a route that reads from several partitions, runs several instances in parallel, or waits on more than one slow dependency, and duplicates aren't your only new problem: messages can also arrive out of order, and a burst of retries can arrive fast enough to overwhelm whatever they're retrying into. This chapter is about the three patterns Camel gives you for exactly those three side effects — not preventing them, which you mostly can't, but surviving them.

At-least-once is the deal you actually signed

Almost nothing you integrate with promises exactly-once delivery, no matter what the marketing says. A sender that times out waiting for an acknowledgment has no way to know whether its message actually arrived — the acknowledgment could be lost just as easily as the message itself. The only safe move, and the one every real messaging system, HTTP client, and Camel redelivery policy actually makes, is to resend. That's at-least-once delivery: a message is guaranteed to arrive one or more times, never zero, and "more than one" is not a bug in the transport — it's the transport keeping its one real promise. A route built on the unspoken assumption that each message shows up exactly once will work perfectly in every demo and then quietly double-process a payment, an order, or a shipment notification the first time a network blip forces a retry.

Camel doesn't try to make the world exactly-once, because it can't — nothing downstream of an unreliable network can. Instead it gives you three EIPs that each defend against one specific consequence of at-least-once, asynchronous, parallel delivery: Idempotent Consumer catches the duplicates retries create, Resequencer restores the order that parallelism and retries scramble, and Throttler keeps a burst of retries or traffic from overwhelming whatever it's aimed at.

idempotentConsumer(): catching the duplicate before it reprocesses

The Idempotent Consumer pattern doesn't try to stop duplicates from being sent — it can't, any more than Camel can fix the network. It filters them out on arrival instead. Give it an expression that computes a unique key for each message — something the sender guarantees is stable across every copy of the same logical message, like an order ID or a message UUID — and a repository to remember which keys it's already seen. The first message with a given key goes through. Every later message with the same key is a duplicate, and Camel filters it out before your route ever touches it.

Filtering duplicate orders by OrderId
from("seda:orders")
    .idempotentConsumer(header("OrderId"), MemoryIdempotentRepository.memoryIdempotentRepository(1000))
.to("direct:processOrder");

The two arguments are the whole pattern: an Expression for the key, and an IdempotentRepository — a small SPI (org.apache.camel.spi.IdempotentRepository) that Camel ships several implementations of, covered next. Everything else about idempotentConsumer()'s behavior is controlled by three options, and their defaults are doing more work than a first read suggests.

eager, skipDuplicate, removeOnFailure — all default to true, on purpose

eager (default true) records the key before the exchange finishes processing, not after — so two copies of the same message racing each other concurrently both get caught, not just a duplicate that arrives after the first one has already completed. skipDuplicate (default true) automatically filters a detected duplicate out of the route, silently. And removeOnFailure (default true) is the one most likely to save you: if the exchange ultimately fails, Camel removes its key from the repository again, specifically so a message that failed for a real reason is still eligible to be retried — without it, one legitimate failure would look identical to a duplicate and never get a second chance.

Sometimes silently filtering a duplicate is the wrong call — you'd rather see it, log it, or route it somewhere for auditing than have it vanish with no trace. Set skipDuplicate(false) and the duplicate keeps flowing through the route instead of being dropped, with the boolean exchange property Exchange.DUPLICATE_MESSAGE set so your route can act on it explicitly:

Routing duplicates somewhere visible instead of discarding them
from("direct:orders")
    .idempotentConsumer(header("OrderId"))
        .messageIdRepository(jdbcRepo)
        .skipDuplicate(false)
    .choice()
        .when(exchangeProperty(Exchange.DUPLICATE_MESSAGE).isEqualTo(true))
            .to("direct:duplicateOrders")
        .otherwise()
            .to("direct:processOrder")
    .end();
A good idempotency key is not optional set-dressing

The whole pattern is only as correct as the key you hand it. It has to be something the sender guarantees stays identical across every copy of the same logical message — an order ID, a message UUID the producer sets once and never regenerates on retry. A key derived from arrival time, from a hash of the whole message body when the body can legitimately change between fields, or from anything the sender doesn't actually keep stable, will either let real duplicates through or, worse, flag two genuinely different messages as the same one and drop one of them for good.

Choosing a repository: memory is a single-instance answer

MemoryIdempotentRepository is the fastest option and the one every example reaches for first — a bounded, in-process map, no external dependency, no configuration. It is also the one most likely to lie to you in production. Its memory of what's been seen exists nowhere but that one JVM's heap: restart the process and the history is gone; run a second instance of the same route — which is exactly what you do to scale, or what a container orchestrator does automatically after a crash — and neither instance can see what the other has already processed. The moment more than one instance can consume the same source, or the process can restart mid-flight, you need a repository every instance shares.

The interface (add, contains, remove, plus the eager-check confirm) is the same regardless, so swapping repositories later is a configuration change, not a route rewrite.

Resequencer: putting a stream back in order

Filtering duplicates solves one side effect of retries and parallelism. Here's another: a splitter that fans work across threads, a set of retried deliveries, or messages arriving from several partitions of the same logical stream can all easily deliver message 3 before message 1. If whatever consumes them downstream cares about order — applying price updates in sequence, replaying events in the order they happened — that's a correctness bug, not a cosmetic one. The Resequencer reorders messages passing through a route back into the order the sequence expression says they belong in.

Two algorithms, chosen with .batch() or .stream() after the sequence expression — batch() is the default if you don't pick one. They make genuinely different tradeoffs, not just syntax variants of the same idea.

Batch resequencing: buffer, sort, release
from("direct:priceUpdates")
    .resequence(header("seqnum"))
        .batch()
        .batchSize(200)
        .batchTimeout(2000)
.to("direct:applyPriceUpdate");

Batch mode collects messages into a buffer, sorts the whole buffer by the sequence expression, and releases it once batchSize is reached (default 100) or batchTimeout elapses (default 1000ms), whichever comes first. It only guarantees order within one batch — a straggler that arrives after its batch has already shipped downstream is never retroactively reordered against messages that already left. A larger batchSize or batchTimeout buys a better chance of catching a late arrival before release, at the direct cost of added latency for everything waiting in that buffer.

Stream resequencing: release as soon as the next one in line shows up
from("direct:events")
    .resequence(header("seqnum"))
        .stream()
        .capacity(5000)
        .timeout(4000)
.to("direct:applyEvent");

Stream mode doesn't wait for a batch at all: it holds a rolling window of up to capacity in-flight messages and releases each one the moment it's next in the expected sequence, detecting gaps rather than sorting a fixed collection. timeout bounds how long it will hold the window open waiting for a specific gap to fill before giving up and releasing what it has anyway. rejectOld (default false) can drop any message whose sequence number is already lower than one already released — useful once you've decided a straggler that far behind is no longer worth reordering, only worth discarding.

The resequencer can't invent order it was never given

It only reorders the messages that actually reach it, using whatever sequence field you point it at. If the field is missing on some messages, isn't actually comparable, or the message that would fill a gap is never coming at all, the resequencer has nothing to correct with. Leave timeout too high (batch) or unset on a stream that can genuinely lose a message and you can end up holding every later message hostage waiting on one that will never arrive.

Throttler: protecting what's on the other end

Duplicates and disorder are about correctness. The last piece is about survival: a retried delivery, a burst of traffic, or simply more concurrency than a downstream system was built for can overwhelm it, turning "resilient" into "the thing that took the database down." Throttler caps how many messages Camel lets through to an endpoint in a given window — protecting a downstream system that can't handle unlimited load, or keeping you inside an external SLA you don't control.

At most 5 notifications per second, per tenant, without blocking the caller
from("direct:notifyCustomer")
    .throttle(5).timePeriodMillis(1000)
        .correlationExpression(header("tenantId"))
        .asyncDelayed()
.to("https://notifications.example.com/send");

throttle(n) allows at most n messages through per window; timePeriodMillis (default 1000ms) sets that window's length, so throttle(3).timePeriodMillis(10000) reads as "at most 3 messages in any 10-second span." By default the calling thread simply blocks until it's a given message's turn — fine for a low-volume route, but on a route with real concurrency it quietly turns a rate limiter into a thread-pool limiter, since every blocked thread is one not available to do other work. asyncDelayed(true) fixes that by scheduling the delayed continuation elsewhere and freeing the calling thread immediately.

correlationExpression is what turns one global budget into a per-key budget — the example above gives every tenant its own 5-per-second allowance instead of five tenants fighting over one shared quota, the same instinct as a per-tenant rate limit on any multi-tenant API. And when the right answer is a fast failure instead of a delay, rejectExecution(true) throws a ThrottlerRejectedExecutionException the instant a message is over the limit, rather than queueing it to wait its turn.

Reliable delivery was never about making a message arrive exactly once — nothing downstream of a network can promise that. It's about making at-least-once, out-of-order, bursty arrival all survivable, on purpose, instead of by accident.

So what did we actually gain?

Three EIPs, each aimed at one specific consequence of the messy, honest way distributed systems actually deliver messages: idempotentConsumer() so a retried delivery doesn't get processed twice, resequence() so parallelism and retries don't scramble an order-sensitive stream, and throttle() so a burst doesn't take down whatever it's aimed at. None of them try to fix the network — they all assume it will misbehave and give your route a way to stay correct anyway. What this chapter deliberately left out is the other half of "try it again": the retry policy itself, and where a message goes when every retry has been exhausted. That's Chapter 24, Redelivery and Dead-Letter Handling.
