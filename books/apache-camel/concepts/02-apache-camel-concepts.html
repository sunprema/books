Apache Camel
Concepts

Last chapter ended with a promise: before we write a single route, we'd learn the vocabulary. That's this chapter, and it's shorter than you might expect — Camel is built from a small set of ideas that keep recombining. Learn five nouns and two verbs well, and every route you'll ever read or write — no matter which of Camel's 300-odd components sits at either end — will already make sense.

Five words worth learning before we write anything

Here's the question to hold onto through this whole chapter: when a message moves from a file on disk to a queue on a broker, what, exactly, is doing the moving? Not "Camel," as a vague blob — five specific, small pieces, each with one job.

The building blocks, at a glance
PieceWhat it isExample
CamelContextthe runtime containerone per running application
Routethe path a message takesfrom(…).to(…)
Endpointa place a message comes from or goes tofile:incoming
Componentthe factory that builds an endpoint from a URIfile, jms, http
Processora step that acts on the message in flight.process(…), .log(…)

CamelContext is the least glamorous of the five and the one everything else answers to. It's Camel's runtime container — it wires your routes, components, and endpoints together, activates the routing rules at startup, and holds the type-converter registry every other piece quietly relies on. You'll rarely touch it directly once your project is set up (Part II shows exactly how little ceremony that takes), but every route you write lives inside one.

A Route is the thing you actually author: the path one kind of message takes, from exactly one input endpoint through zero, one, or more steps to wherever it ends up. "Read a file, then send it to a queue" is a route. So is "read a file, transform it, validate it, branch on its type, and send it to three different places" — a route can get as elaborate as the integration demands, but it always starts from a single from(…).

The endpoint is the URI

This is the part that makes Camel feel almost suspiciously simple once it clicks: every place a message can come from or go to — a directory, a queue, an HTTP URL, a database table, an S3 bucket — is addressed the same way, as a URI. Not a metaphorical URI. An actual string, in the same shape every time:

The shape every endpoint URI shares
scheme:context-path?option1=value1&option2=value2

timer:orderPoll?period=5000
file:incoming-orders?noop=true&recursive=true
jms:queue:orders.validated
https://api.example.com/orders?bridgeEndpoint=true

The scheme (timer, file, jms, https…) picks which Component handles this endpoint. A component is nothing more than an endpoint factory registered under that scheme name — hand it the rest of the URI and it hands back a concrete, configured Endpoint your route can read from or write to. That's the whole extension mechanism: every one of Camel's 300+ integrations is exactly this — a component, a scheme, a factory. The context-path is component-specific (a directory for file, a queue name for jms, a host for https), and everything after the ? configures that one endpoint instance.

Why this matters more than it looks like it should

Because every endpoint is "just a URI," the route logic you learn for one connector transfers directly to the next. Swapping file: for sftp: or kafka: is a one-line change to the URI, not a new API to learn. You are not learning "the file API," then "the JMS API," then "the S3 API." You're learning one shape, applied three hundred times.

Who talks first: producers and consumers

An endpoint sitting at the front of a route (from(…)) and one sitting at the back (to(…)) play different roles, and Camel has a name for each. A Consumer is how a route receives a message from an endpoint — it's the thing behind every from(…). A Producer is how a route sends a message to an endpoint — it's the thing behind every to(…). Same URI syntax, opposite direction of travel.

Consumers themselves come in two flavors, and the difference actually matters for how your integration behaves under load. An event-driven consumer gets pushed a message the instant one exists — a JMS listener waking up, an HTTP server accepting a request. A polling consumer goes and looks, on a schedule — the file component scanning a directory every few seconds, a database query run on a timer. Both are perfectly normal; the trap is expecting file- or database-backed routes to behave like an event listener. They don't notice new data the instant it lands — only the next time they poll.

The exchange: the envelope, not the letter

This is the distinction that trips up almost everyone reading Camel code for the first time, so let's be precise about it. An Exchange is not the message. It's the container that carries a message through one route's execution — the envelope, complete with routing metadata (exchange properties, the exchange pattern, any exception that occurred), not the letter inside it. A consumer creates exactly one Exchange per incoming payload; that same Exchange instance rides along through every processor in the route.

Older Camel material (and some still-circulating tutorials) will describe an Exchange as juggling a separate "In message" and "Out message." You can mostly forget that model — modern Camel (3.x and 4.x, which is what this book targets) simplified it: an Exchange carries a single current Message, and each step reads and replaces it in place rather than shuttling data between two slots. When your code calls exchange.getMessage(), that's the message you get — whatever the most recent step left there.

Message: body, headers — and exchange properties

Inside that envelope, the Message is the actual payload: a body (a String, a byte[], a POJO, practically any Java object — Camel's type-converter registry coerces between types on demand, so .to() and simple() expressions rarely need an explicit cast) and headers, key/value metadata scoped to that one message — a file name, an HTTP status code, a JMS correlation ID.

Camel gives you a second, easy-to-miss key/value store: exchange properties, living on the Exchange rather than the Message. The difference is scope, and it's worth internalizing now rather than debugging it later.

Header vs. exchange property
Scoped toGood for
Headerthe current messagemetadata the far side understands — an HTTP header, a JMS property, a file name
Propertythe whole exchangerouting-internal bookkeeping — an original-body backup, a correlation id used only inside the route
A header is not a promise

Some EIPs — Splitter, Multicast, Enrich, and others you'll meet in Part IV — create fresh Exchanges or Messages per branch, and headers don't always survive that the way a newcomer expects. Exchange properties, set explicitly, are the more reliable place to stash state you need later in the same route.

Processors: the verbs

Everything that actually does something to a message — log it, transform it, branch on it, enrich it — is a Processor underneath. It's a deliberately tiny Java interface: one method, process(Exchange). Every built-in EIP you'll use from Part IV onward (choice, splitter, aggregator, recipient list) is a Processor Camel ships for you; .process(…) is how you drop in your own.

A route, named end to end
from("file:incoming?noop=true")
    .routeId("orders-in")
    .log("Got file: ${header.CamelFileName}")
    .process(exchange -> {
        String body = exchange.getMessage().getBody(String.class);
        exchange.getMessage().setHeader("OrderSize", body.length());
    })
    .to("jms:queue:orders.raw");

Read that line by line and every term from this chapter shows up: file: and jms: are components; the two URIs are endpoints; from wires up a consumer, to a producer; .process(…) is a Processor acting on the current Exchange; getMessage() reaches the single current Message riding inside it. Nothing here is exotic — it's five nouns, wired together in the one shape the diagram above already showed you.

A route is a pipeline of processors between a consumer and a producer, acting on one exchange — every pattern in this book is that sentence, said a different way.

So what did we actually gain?

We still haven't written anything Camel would actually run — that's Part II's job. But we now have the vocabulary to read any Camel route on sight: an endpoint URI tells you the component and its configuration; from/to tell you the consumer and producer; the exchange is the envelope a chain of processors passes along, one current message inside it, headers and properties playing their different scopes. Next chapter puts a name to the routing patterns those processors implement — the Enterprise Integration Patterns catalog Hohpe and Woolf named, and Camel builds on.
