Deployment and Route Lifecycle

Chapter 27 ended on a promise: packaging a Camel application, running it under Spring Boot or Quarkus, and shutting it down without losing whatever message was in flight at the time. This chapter keeps that promise. But it's worth saying up front that "deployment" here isn't a single event. A route isn't just on or off — it has a lifecycle, with states in between, and every choice in this chapter (which runtime you package against, whether a broken route should take the whole application down, how long shutdown is allowed to take) is really a choice about what that lifecycle looks like in production.

Packaging: where does a route actually run

Every route in this book so far has run inside a test, or from an IDE launcher. A route's code — the RouteBuilder, the YAML, the XML — doesn't change depending on where it deploys, but what wraps around it does. Camel supports three runtime targets that share the exact same DSL: plain camel-main (a bare CamelContext booted from a main() method, no framework underneath), Spring Boot, and Quarkus. Which one you choose is a packaging and operations decision, not a routing one.

The fastest way to try a route before committing to any of the three is Camel JBang — the camel CLI you first saw in Chapter 4. camel run runs a route file directly, with no Maven project, no POM, no IDE: it resolves and downloads the Camel JARs and whatever components the route needs, and --dev adds live reload on every save. Once a prototype is ready to become a real project, camel export turns those same route files into a full Maven project scaffolded for one of the three runtimes — --runtime=spring-boot, --runtime=quarkus, or --runtime=main. Nothing about the route changes; only the project around it gets generated.

From a JBang prototype to a runtime-specific project
# iterate on a single file, no project at all
camel run OrderRoute.java --dev

# turn it into a Maven project targeting one runtime
camel export --runtime=quarkus --gav=com.example:order-integration:1.0.0

Running under Spring Boot

Add the camel-spring-boot-starter dependency and two things happen automatically: Camel auto-configures a CamelContext as a Spring bean, and it scans the application context for any RouteBuilder beans and adds their routes to it — the same auto-detection you've been relying on since Chapter 4's project setup. Packaging is Spring Boot's own concern, not Camel's: the spring-boot-maven-plugin's repackage goal, bound to Maven's package phase, nests your application's classes plus every runtime dependency inside one self-contained jar with its own launcher, so it runs with a plain java -jar.

Build once, run anywhere a JVM is available
mvn clean package
java -jar target/order-integration-1.0.0.jar

Camel Quarkus, briefly

Camel Quarkus runs the same routing engine on a different foundation, and it gives you three genuinely different ways to run an application. Dev mode (mvn quarkus:dev) live-reloads route and Java changes as you save, the fastest inner loop of the three. JVM mode — mvn package, then java -jar — is functionally close to the Spring Boot jar: an ordinary JVM process. Native mode is the one that's actually different: mvn package -Dnative ahead-of-time compiles the whole application — Camel, your routes, every dependency on the classpath — into a single platform-specific executable, using GraalVM or its Quarkus-focused downstream distribution, Mandrel.

The trade a native build makes is stark. The build itself is slower and far more resource-hungry — GraalVM has to statically analyze a closed world of every class the application could possibly reach. What you get back is a runtime that starts in milliseconds rather than seconds and sits at tens of megabytes of resident memory rather than hundreds. That's the trade that matters for a serverless-style integration, or any container platform that bills or autoscales on cold-start time and memory footprint — the two numbers a native build is built to shrink.

A native build that compiles fine can still fail on its first request

GraalVM's closed-world analysis has to see every code path statically; anything that only exists through reflection — some Camel components, some third-party libraries — needs explicit registration, or a Quarkus extension that already handles it, before native-image can include it. Skip that step and the binary builds without complaint, then throws the moment execution reaches the unregistered path in production. Test the native build itself before trusting it, not just the JVM-mode jar it was built from.

The route lifecycle: more states than "on"

A CamelContext moves through a defined sequence of operations: build, init, start, stop, and eventually shutdown, with suspend and resume as a second pair alongside start/stop. The two pairs aren't interchangeable. stop performs a full graceful shutdown — the subject of the rest of this chapter — and releases resources. suspend only pauses consumers, keeping the CamelContext itself, and every route's registered state, warm. resume is correspondingly cheaper than starting from a cold stop, because there's less to rebuild.

Individual routes carry this same distinction, independent of the whole context. Recall autoStartup="{{key}}" from Chapter 27: a route with autoStartup=false isn't skipped, it's registered like any other route, just never started automatically. It can be started later, by route ID, through Camel's RouteController — the same component responsible for starting every route automatically at boot, and the subject of the next section.

RouteController: fail fast, or supervise?

By default, Camel's RouteController is fail-fast: if any route throws while starting, CamelContext startup itself fails, and the whole application refuses to come up — one route with a database still booting or a broker not yet reachable takes down every other route with it. In a syllabus-sized application with a handful of routes that's a reasonable default. In production, with dozens of routes talking to systems you don't control the uptime of, it's often the wrong one.

The supervising route controller changes the failure mode. CamelContext starts successfully even if some routes fail, and each failed route is retried on an exponential backoff schedule in the background — independently of every other route. A transient dependency outage delays one route instead of the whole application. Since Camel 4.7, a route that exhausts its retry attempts is marked unhealthy by default, rather than silently vanishing — which is what makes a readiness probe wired to Chapter 26's health checks correctly report the application as not ready, instead of reporting healthy while quietly missing a route.

Supervising instead of fail-fast, with a bounded number of retries
camel.routecontroller.enabled = true
camel.routecontroller.backoff-delay = 5000
camel.routecontroller.backoff-max-attempts = 5
camel.routecontroller.exclude-routes = healthCheckRoute
An unbounded backoff-max-attempts can hide a route that's never coming back

Leave backoff-max-attempts unset and a permanently broken route — a typo'd hostname, a credential that was rotated everywhere except this one route's config — retries forever in the background, quietly, instead of ever surfacing as failed. Pair supervision with a bounded attempt count and the unhealthy-on-exhausted behavior from the previous paragraph, so a route that truly cannot recover eventually says so, loudly, to whatever is watching the health endpoint.

Graceful shutdown and the fate of in-flight messages

Every deployment eventually stops — a rolling update, a scale-down, a node eviction. What happens to the order that was halfway through validation when the stop signal arrives is the question this whole chapter has been building toward. Camel answers it with a pluggable ShutdownStrategy, triggered automatically when the CamelContext stops (including when Spring Boot or Quarkus itself shuts down on SIGTERM, the signal a Kubernetes eviction sends). It shuts routes down in the reverse of their start order, and in two phases: first a graceful phase, which stops each route's consumers — so no new work is accepted — while letting exchanges already in flight run to completion; then, if a configurable timeout elapses before every route has drained, a forced phase that shuts down whatever's left anyway. That timeout defaults to 45 seconds.

The timeout and its logging are configured with a small, consistent set of properties — the same names whether you're on plain camel-main, Spring Boot, or Quarkus — and the strategy is also adjustable at runtime over JMX, for the rare case where a deploy is stuck waiting and you need to intervene without a restart.

Tuning how long shutdown is allowed to take, and what gets logged
camel.main.shutdown-timeout = 60
camel.main.shutdown-suppress-logging-on-timeout = false
camel.main.log-inflight-exchanges-on-timeout = true

A single global timeout is a blunt instrument once routes have different needs — a route that other routes still send work to shouldn't shut down first, and a batch consumer mid-poll shouldn't be cut off after finishing only the message it happened to be holding. Two DSL options, set per route, refine that: shutdownRoute takes ShutdownRoute.Default (shut down as early as possible) or ShutdownRoute.Defer (delay this route to a later stage, because other routes still depend on it — typically an internal direct: endpoint other routes send to). shutdownRunningTask takes ShutdownRunningTask.CompleteCurrentTaskOnly (finish only the exchange currently being processed, then stop) or ShutdownRunningTask.CompleteAllTasks (finish every task the consumer has already accepted, not just the one in progress — the option a file or batch consumer usually wants).

A route other routes still depend on, deferred and drained fully
from("seda:orderIntake")
    .routeId("orderIntake")
    .shutdownRoute(ShutdownRoute.Defer)
    .shutdownRunningTask(ShutdownRunningTask.CompleteAllTasks)
    .to("direct:processOrder");
Defer is about dependency order, not importance

It's tempting to read ShutdownRoute.Defer as "shut this down carefully" and reach for it on every route that matters. It means something narrower: other routes still send this route work, so don't shut it down until they've finished shutting down first. A route nothing else depends on gains nothing from deferring — the ordinary reverse-start-order shutdown already handles it correctly.

A grace period shorter than the shutdown timeout defeats the timeout entirely

ShutdownStrategy only gets to run at all if the process receives SIGTERM and is given time to act on it. A container platform's hard-kill grace period — Kubernetes's terminationGracePeriodSeconds, most commonly — that's shorter than camel.main.shutdown-timeout means the orchestrator sends SIGKILL before Camel's own graceful window has elapsed, abandoning whatever was still in flight no matter how carefully the timeout was tuned. The two numbers have to agree: set the grace period comfortably longer than the shutdown timeout, not the other way around.

A route that shuts down instantly isn't fast — it's the order that never finished validating, discarded by omission instead of by decision.

So what did we actually gain?

A route's code never changes across camel-main, Spring Boot, and Quarkus — only the packaging around it does, and now you have a real basis for choosing among a plain jar, a Spring Boot fat jar, and a Quarkus JVM or native build. The route lifecycle turned out to have more shape than "running" or "not": start/stop and suspend/resume are genuinely different pairs, and a RouteController can either fail an entire application over one bad route or supervise that route back to health on its own schedule. And graceful shutdown — the reverse-order, two-phase drain governed by one timeout, refined per route with shutdownRoute/shutdownRunningTask — is what decides whether "the deployment finished" also means "no order was lost in the process." Part VII puts all of it to work on one real integration, starting from scratch with the order-processing capstone next.
