Message Splitting and Aggregation

Chapter 12 answered "given this message, where does it go?" without ever changing the message itself — choice(), filter(), and toD() all read the exchange and route it whole. Sooner or later you'll hit a message that's whole in name only: an order file with forty order lines in it, an XML batch with a hundred records, a JSON array of events that each need their own validation and their own destination. Routing the file is the wrong unit of work — you need to route the lines. This chapter covers the two EIPs built for exactly that mismatch: the Splitter, which turns one exchange into many, and the Aggregator, which turns many exchanges back into one. They're mirror images of each other, and — as you'll see partway through — Camel actually gives you two different tools that both look like "aggregation," solving two different problems. Telling them apart is most of this chapter.

split(): one exchange becomes many

split() takes one incoming exchange and an expression that says how to cut its body into parts, then sends one sub-exchange down the rest of the route per part. Each sub-exchange is a copy of the original — same headers, same properties — with the body replaced by just that one part. A route that reads a newline-delimited order file and hands each line to its own processing branch looks like this:

One sub-exchange per line of the inbound file
from("file:orders/inbound")
    .split(bodyAs(String.class).tokenize("\n"))
        .to("direct:oneOrderLine")
    .end();

The split expression can be almost anything: tokenize() for delimited text like the example above, xpath("//order") to split an XML document into a node per match, jsonpath("$.orders") to split a JSON array element by element. If the body is already a java.util.Collection, array, Iterable, or Iterator, you don't even need an expression that names a field — plain body() is enough, and Camel splits it element by element on its own.

Non-streaming by default; streaming() trades memory for an unknown total

By default split() materializes every part first — so it knows the total count up front — before processing any of them, which means the whole split result sits in memory at once. .streaming() switches to producing and processing one part at a time, without holding the rest, at the cost of never knowing the total part count in advance. For a ten-line order file the difference is invisible; for a multi-gigabyte export it's the difference between a route that runs and one that runs out of heap.

Recombining the parts, inline: split()'s own AggregationStrategy

Here's the detail that trips people up. Leave the example above exactly as written, with no second argument to split(), and ask: what does the original exchange look like once all three lines have been processed? Camel's answer, if you never say otherwise, is UseLatestAggregationStrategy — the outgoing exchange after .end() simply becomes whatever the last sub-exchange turned into. Lines one and two, and anything their processing produced, are gone. Not errored, not logged — gone, the same quiet-drop failure mode Chapter 12's choice() without otherwise() warned you about, wearing a different EIP's clothes.

If you want the pieces back — a running order total built line by line, or a list of every priced line collected into one result — give split() a second argument: an AggregationStrategy that folds each processed sub-exchange into a running result, inline, in the same block, before the split completes.

Fold each priced line back into a running order total
from("direct:orders")
    .split(body(), new MyOrderTotalsStrategy())
        .to("direct:priceOneLine")
    .end();

// MyOrderTotalsStrategy.aggregate(Exchange oldExchange, Exchange newExchange)
//   if (oldExchange == null) return newExchange;   // first line starts the running result
//   // otherwise fold newExchange's priced line into oldExchange's running total, return oldExchange

The shape — oldExchange is null on the first call, and the running result on every call after — is one you'll see again in a moment, because the standalone Aggregator EIP uses the exact same interface. But don't let that similarity blur the two together: this strategy only ever combines pieces of the one exchange that split() just cut up, in this one block, on this one route. It has no idea whether another message arrives five minutes later that should join the same group — and that's precisely the problem it can't solve.

parallelProcessing() changes how parts run, not whether the route waits

.parallelProcessing() processes sub-exchanges concurrently, but the thread that called split() still blocks at that point in the route until every part has finished — the rest of the route doesn't see the split's output early. Turn it on with a custom AggregationStrategy and that strategy's aggregate() method can now be invoked from multiple threads at once; Camel synchronizes the calls for you by default, so it's safe even if your strategy isn't written to be thread-safe — just no faster than sequential aggregation would be.

The real Aggregator EIP: correlating exchanges that arrive separately

Now the problem split()'s inline strategy can't touch: order lines that don't arrive together as one exchange at all. Picture line items streaming in one at a time from a queue, each one its own independent exchange, independently consumed, and you need to know when all the lines for order #4471 have shown up so you can release the completed order downstream. That's the Aggregator EIP — Camel's aggregate() — and it solves a genuinely different problem from the last section: correlating and combining exchanges that arrive from many separate route invocations over time, grouped by a key you compute from each one.

Group order lines by orderId; release the group once complete
from("direct:orderLines")
    .aggregate(header("orderId"), new MyOrderAggregationStrategy())
        .completionSize(header("lineCount"))
        .completionTimeout(5000)
        .to("direct:completeOrder")
    .end();

The first argument, header("orderId"), is the correlation expression: evaluated once per incoming exchange, its result is the key that decides which group an exchange joins. Every exchange whose orderId header evaluates the same joins the same running aggregate; a different orderId starts (or joins) a different group entirely. The second argument is an AggregationStrategy with the identical aggregate(Exchange oldExchange, Exchange newExchange) shape you just saw on split() — oldExchange is null for the first exchange to arrive under a given key, and the running aggregate-so-far for every exchange after that. Same interface, same null-check idiom, applied to a completely different kind of grouping.

Completion strategies: deciding when a group is "done"

A group can't stay open forever, so aggregate() needs a rule for when to release it. You can configure more than one, and whichever fires first for a given key wins:

  • completionSize(n) — complete once n exchanges have joined that key. In the example above, the size comes from a header rather than a fixed number, because different orders have different line counts.
  • completionTimeout(ms) — an inactivity timeout: it resets every time a new exchange joins that key, so it fires only once a key has gone quiet.
  • completionInterval(ms) — a fixed periodic sweep that completes whatever has accumulated so far, on a schedule independent of any single key's activity.
  • completionPredicate(...) — evaluated against the aggregated exchange after every new arrival; the group completes the moment it returns true.
completionTimeout and completionInterval answer different questions — and can't both be set

completionTimeout asks "has this particular order gone quiet?" — every new line for #4471 pushes its deadline back out. completionInterval asks "what's the state of every open order, right now, on the clock?" — it doesn't care whether a given order is still receiving lines. Camel won't let you configure both on the same aggregate(), because they're two incompatible definitions of "time's up." Either can be combined with completionSize, though — a size that completes early, and a timeout or interval that completes late orders anyway.

The example route uses completionSize and completionTimeout together deliberately: a complete order releases the instant its last line shows up, but an order that's missing a line for five seconds releases anyway — incomplete, but not stuck open forever waiting for a line that may never come.

Where an in-flight group actually lives: the AggregationRepository

Every not-yet-completed group has to be stored somewhere between the exchanges that build it — that storage is a pluggable AggregationRepository. Camel's default is a plain in-memory repository, which is fine for a single-instance route with modest group sizes, but it has an unforgiving failure mode: an in-flight group is only ever in that process's heap, so a restart at the wrong moment loses every order that hadn't yet completed, with no trace that it ever existed. A production aggregator that has to survive a restart plugs in a persistent implementation instead — Camel ships JDBC-, Infinispan-, and similarly backed repositories for exactly this.

forceCompletionOnStop closes the door on shutdown

Even with a persistent repository, a route that's stopping needs somewhere for its open groups to go. forceCompletionOnStop tells the aggregator to complete and release every in-flight group when the CamelContext stops, instead of leaving partially-built orders sitting in the repository with no consumer left running to ever finish them.

split() breaks one exchange into many; aggregate() correlates many separately-arriving exchanges back into one. They look like mirror images, and mostly are — but split() also carries its own miniature aggregation step for recombining the pieces of the message it just cut up, which is not the same machine as the standalone Aggregator EIP correlating messages that were never one exchange to begin with. Confuse the two and you'll reach for a correlation key you don't need, or miss the one you do.

So what did we actually gain?

A way to change the unit of work, in both directions. split() turns one exchange with many things in it into many exchanges, each processed on its own — with an explicit AggregationStrategy standing between "the pieces are gone the moment you don't ask for them back" and "the pieces fold into a result you actually get to use." aggregate() turns many separately-arriving exchanges into one, correlated by a key and released once a completion condition you chose actually fires. Both patterns leave the individual message untouched while they work — they change how many exchanges there are, not what's inside any one of them, the same separation of concerns Chapter 12's routing EIPs held onto. The next chapter asks a related but different question: not "how many exchanges should this become," but "how many destinations should the same message reach" — multicast and recipient lists send one exchange to several places at once, no splitting required.
