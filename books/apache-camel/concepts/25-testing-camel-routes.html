Testing Camel Routes

That's the question the last chapter closed on: how do you prove a route retries the right number of times, waits the right amount, and lands in the right dead-letter queue, without sitting through real backoff delays to find out? It's worth taking seriously, because a RouteBuilder is a configuration object, not a black box you have to run in production to trust. Camel routes turn out to be unusually testable compared to most integration code, precisely because the parts that normally make integration hard to test — real endpoints, real timing, real external systems — are exactly the parts Camel gives you a first-class way to swap out. This chapter works through four tools of increasing reach: testing a processor with no Camel context at all, mock endpoints standing in for a real destination, AdviceWith rewriting an already-built route for one test, and NotifyBuilder watching a route finish without touching it at all. By the end you'll have exactly what the last chapter promised: a test that proves a route retries three times, waits for none of it, and lands precisely where it should.

The cheapest test you can write: no Camel at all

Start with the smallest unit worth testing. Chapter 9 introduced processors as plain objects implementing process(Exchange) — and "plain object" is the operative phrase. A processor has no dependency on a running CamelContext to be exercised: build a DefaultExchange, populate its body and headers, call process(exchange) directly, and assert on what comes back. No route, no context startup, no mock endpoints, no network. This is the fastest test in the whole chapter, and the one most worth reaching for first — a validation rule or a transformation belongs here, tested in isolation, before it ever needs to prove itself inside a route.

Testing a Processor directly — no route involved
class OrderNormalizerTest {

    @Test
    void upperCasesTheCountryCode() throws Exception {
        Exchange exchange = new DefaultExchange(new DefaultCamelContext());
        exchange.getIn().setBody("order-42");
        exchange.getIn().setHeader("country", "de");

        new OrderNormalizer().process(exchange);

        assertEquals("DE", exchange.getIn().getHeader("country"));
    }
}

There's no assertion here about routing, no endpoint, nothing Camel-specific beyond the Exchange itself — which is exactly the point. This test can't tell you whether OrderNormalizer is wired into the right place in a route, only that it does what it claims to do given an exchange. That's a narrower guarantee than the tools below provide, and a much cheaper one to get.

Mock endpoints: Camel's own test double

Once a test needs to prove something about routing — that a message reaches a particular destination, in a particular shape, a particular number of times — it needs a route running, and it needs somewhere to observe what arrives. That's MockEndpoint: a test-only endpoint reached through a mock: URI, purpose-built to record what it receives and assert on it afterward. The base class for writing these tests is org.apache.camel.test.junit5.CamelTestSupport, from the camel-test-junit5 module — extend it, override createRouteBuilder() to supply the route under test, and the base class hands you a running CamelContext plus a ProducerTemplate (template) for sending test messages in.

A route test built on CamelTestSupport and a mock endpoint
class FileToJmsRouteTest extends CamelTestSupport {

    @Override
    protected RouteBuilder createRouteBuilder() {
        return new FileToJmsRoute();
    }

    @Test
    void routesEachFileAsOneMessage() throws Exception {
        MockEndpoint result = getMockEndpoint("mock:result");
        result.expectedMessageCount(1);
        result.expectedBodiesReceived("order-42");

        template.sendBodyAndHeader("direct:start", "order-42", "CamelFileName", "order-42.csv");

        result.assertIsSatisfied();
    }
}

Notice the order: expectations are set on the mock before the message is sent, and assertIsSatisfied() is called after — it's the check, not the setup. expectedMessageCount(int) fixes how many exchanges must arrive; expectedBodiesReceived(...) fixes the exact bodies, in order, and if it's set it overrides whatever count expectedMessageCount implied to match the number of bodies given. expectedHeaderReceived and expectedPropertyReceived do the same for a specific header or exchange property on every exchange the mock sees. And because assertIsSatisfied() polls rather than checks instantaneously — ten seconds by default, tunable with setResultWaitTime(millis) — a route with any asynchronous hop still has time to actually deliver before the assertion gives up on it.

Replacing external systems without touching the route

The example above only works because FileToJmsRoute already routes to mock:result — convenient when a route is written for testability from the start, useless for testing a route that really calls an HTTP API or a database. For that, CamelTestSupport can intercept endpoints without editing the route under test at all. Override isMockEndpoints() or isMockEndpointsAndSkip() with a URI pattern (or "*" for everything), and Camel inserts a mock in front of every matching endpoint before the test context even starts.

Two ways to auto-mock endpoints, and the difference that matters

Skipping a real HTTP call entirely, and scripting the mock's response
class InventoryEnrichRouteTest extends CamelTestSupport {

    @Override
    protected RouteBuilder createRouteBuilder() {
        return new InventoryEnrichRoute();
    }

    @Override
    public String isMockEndpointsAndSkip() {
        return "http:*";           // never call the real inventory API in this test
    }

    @Test
    void enrichesOrderWithInventoryStatus() throws Exception {
        MockEndpoint inventoryApi = getMockEndpoint("mock:http:inventory-api");
        inventoryApi.whenAnyExchangeReceived(exchange ->
            exchange.getMessage().setBody("{\"inStock\":true}"));

        Exchange result = template.request("direct:start",
            e -> e.getIn().setBody("{\"sku\":\"ABC-1\"}"));

        assertTrue(result.getMessage().getBody(String.class).contains("inStock"));
    }
}

whenAnyExchangeReceived(Processor) is what turns a mock from a passive recorder into a scripted stand-in: it runs on every exchange the mock receives, so it can fabricate exactly the response the real inventory API would have sent. Its sibling, whenExchangeReceived(int index, Processor), targets one specific arrival by position — the mechanism, further down, for making the first two calls fail and the third succeed.

isMockEndpoints() still calls the real thing

It's easy to reach for isMockEndpoints() when the goal is actually to avoid a real call, and be surprised when the test still hits the real endpoint. It's doing exactly what its name says — mocking, i.e. observing, not intercepting. If a test must not touch an external system, the method that matters is isMockEndpointsAndSkip().

AdviceWith: rewriting a route for one test

Auto-mocking is broad — every matching endpoint, everywhere in the route. Sometimes a test needs surgical precision instead: replace this one .to(), splice a step in before this processor, delete that onException clause entirely. AdviceWithRouteBuilder does exactly that — it rewrites an already-built route for the duration of one test, without touching the production RouteBuilder source at all. weaveByType(NodeType.class) selects nodes by their EIP type (this includes onException clauses, not just steps in the route body), weaveById(id) selects by a node's declared id, and weaveByToUri(pattern) selects .to() endpoints by URI. Each selection is then acted on with .replace(), .remove(), .before(), or .after().

Two shortcuts save a trip to weaveByToUri for the common case: adviceWith() exposes its own mockEndpoints(pattern) and mockEndpointsAndSkip(pattern), the AdviceWith-scoped equivalents of isMockEndpoints()/isMockEndpointsAndSkip() — useful when only one route in a multi-route test context needs its endpoints mocked, not every route the test loads. One setup step is easy to forget: AdviceWith needs the route not to have started yet, so CamelTestSupport's isUseAdviceWith() must return true to hold the context back from auto-starting the route on setup, leaving a window for the test to call adviceWith() before starting the context itself.

Advise a given route only once

Calling adviceWith() a second time against the same route id isn't supported, and gets especially unpredictable once an error handler is involved. A test that needs several different weavings of the same route splits them across separate test methods — each with its own freshly built context and route — rather than chaining multiple adviceWith calls against one route instance.

Proving retry behavior without waiting for it

Now the question this chapter opened with. A route configured with maximumRedeliveries(3) and exponential backoff is genuinely slow to test the naive way — a test that lets real delays run doubles as a timer, and a slow, flaky one under CI load at that. AdviceWith is the fix: weaveByType(OnExceptionDefinition.class) selects the route's onException clause and .replace() swaps in a test-only redelivery policy with the delay set to zero, or close to it. The retry mechanism under test is still the real one — the same counting, the same exhaustion logic — it just doesn't make the test sit through real-world backoff timings to prove it.

Proving three attempts, zero delay, correct dead letter
@Test
void retriesTwiceThenSucceeds() throws Exception {
    context.getRouteDefinition("orders-in").adviceWith(context, new AdviceWithRouteBuilder() {
        @Override
        public void configure() {
            weaveByType(OnExceptionDefinition.class)
                .selectFirst()
                .replace()
                .onException(ConnectException.class)
                    .maximumRedeliveries(3)
                    .redeliveryDelay(0)     // no real backoff wait in the test
                    .handled(true)
                    .to("mock:deadLetter");
        }
    });
    context.start();

    MockEndpoint downstream = getMockEndpoint("mock:downstream");
    downstream.whenExchangeReceived(0, e -> { throw new ConnectException("down"); });
    downstream.whenExchangeReceived(1, e -> { throw new ConnectException("down"); });
    downstream.expectedMessageCount(3);   // 2 failures + 1 success, all "received"

    template.sendBody("direct:start", "order-42");

    downstream.assertIsSatisfied();
}

whenExchangeReceived(0, ...) and whenExchangeReceived(1, ...) script the first two arrivals at the downstream mock to fail, so the third is the first one that actually succeeds — a precise, repeatable way to force exactly the "fails twice, then works" scenario Chapter 24's redelivery policy exists to survive. expectedMessageCount(3) on the same mock proves all three attempts were actually made, not just that the exchange eventually completed somehow.

For proving an exchange truly gave up — exhausted every redelivery and ended in failure — without adding a mock endpoint or altering the route at all, NotifyBuilder watches the CamelContext's own event notifications instead. whenDone(n) matches once n exchanges have finished, success or failure both counting as "done"; whenCompleted(n) matches only on successful completions; whenFailed(n) matches only on exchanges that ended in failure. That three-way split is what makes it the right tool for "did this really fail, in the end":

Confirming exhaustion with NotifyBuilder, no mock endpoint needed
@Test
void deadLettersAfterRedeliveriesExhausted() throws Exception {
    NotifyBuilder notify = new NotifyBuilder(context)
        .whenFailed(1)
        .create();

    template.sendBody("direct:start", "poison-payload");

    assertTrue(notify.matches(5, TimeUnit.SECONDS));
}
Four tools, four different questions
ToolQuestion it answers
Plain Processor testdoes this one piece of logic do the right thing, given an exchange?
Mock endpointdid the right message, in the right shape, reach this destination the right number of times?
AdviceWithcan I swap out one endpoint or clause in this route, for this test only, without editing production code?
NotifyBuilderdid the exchange finish — and specifically, did it finish as a success or a failure — without me altering the route at all?
Spring Boot and Quarkus add their own test layers on top

Chapter 4 covered both project styles, and testing follows the same split. On Spring Boot, camel-test-spring-junit5 adds @CamelSpringBootTest to boot the Spring context together with Camel, plus class-level @MockEndpoints/@MockEndpointsAndSkip annotations mirroring the method overrides above, and @UseAdviceWith in place of isUseAdviceWith(). On Quarkus, camel-quarkus-junit5 builds on @QuarkusTest instead of CamelTestSupport, testing routes through the same CDI-managed context the application boots — a reflection of Quarkus's build-time wiring rather than a different set of ideas.

A route that's only ever been trusted in production hasn't been tested — it's been gambled on. Mock endpoints and AdviceWith are how that same bet gets placed in a test that finishes in milliseconds, on a laptop, instead of in production traffic that finishes in an incident.

So what did we actually gain?

A layered way to test a route, cheapest tool first: a bare process(exchange) call for a processor's own logic, with no context and no network; mock endpoints and CamelTestSupport's auto-mocking for proving what a route sends where, and how many times, with real external systems swapped out via isMockEndpointsAndSkip(); AdviceWith for surgical, test-only rewrites of one endpoint or clause in an already-built route, with the hard rule that a given route gets advised exactly once; and NotifyBuilder for confirming a route finished — successfully or not — without touching it at all. Put together, they answer the question Chapter 24 left open: a test can now prove a route retries exactly as many times as configured, waits for none of it, and lands precisely where a failed exchange should. What none of this proves is what happens once the route is actually running against the real world — a downstream API that's slow instead of down, a queue backing up, a redelivery storm nobody predicted. That's a different kind of watching, done while the route is live rather than before it ships, and it's exactly what the next chapter takes on.
