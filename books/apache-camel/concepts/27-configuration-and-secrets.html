Configuration and Secrets

Chapter 26 closed on a promise: the JMS broker URL, the API key, the feature flag — the things every component in that chapter needed to actually run — have to get into a Camel application from somewhere. So far almost every example in this book has cheated a little, writing the endpoint URI as a literal string: to("sftp:orders@ftp.internal/incoming"). That's fine for a first route. It stops being fine the moment the same route needs a different host in staging than in production, or the moment that URI needs a password in it. This chapter is about the one syntax, {{key}}, that already appeared once or twice earlier without much explanation, and about who actually resolves it, in what order, and how to keep a real credential out of it entirely.

Property placeholders: the syntax you've already been using

A property placeholder is any {{key}} appearing inside a URI, a Simple expression, or almost any other string a Camel DSL accepts. Camel resolves it before the route is built, substituting whatever value key looks up to. {{key:default}} adds a fallback: if key can't be resolved anywhere, the text after the colon is used instead, so a route still starts with a sane value on a machine where the real configuration hasn't been set up. {{?key}} is different from a default — the leading ? makes the whole option optional: if key is missing, Camel leaves that option unset entirely and the endpoint falls back to its own built-in default, rather than substituting a value you chose. And prefixing a key with ! negates a boolean result — {{!integration.ftpEnabled}} resolves to the opposite of whatever integration.ftpEnabled resolves to. You'll use that last one for route toggles later in this chapter.

Three variants of the same placeholder
from("{{env:KAFKA_BROKERS:localhost:9092}}")  // explicit env lookup, with a default
    .to("sftp:orders@{{sftp.host}}/incoming?password={{sftp.password}}");

// an option Camel should leave at its own default when unset, not force to a literal
from("seda:orders?concurrentConsumers={{?orders.concurrency}}")
    .to("bean:orderService");

Placeholders nest: a resolved value can itself contain another {{...}}, and Camel resolves the reference recursively — useful for building one value out of others, like a full URL from a separately-configured host and port. That's convenient right up until a value legitimately contains literal double braces — a JSON payload template, say — at which point nested resolution turns into a bug. Turn it off for one lookup with {{myTemplate?nested=false}}, or escape the braces you mean literally with a backslash.

Who resolves {{...}}, and in what order

The {{key}} syntax is the same everywhere, but the thing actually answering it is not. Plain camel-main resolves a key through its own PropertiesComponent, checking a chain of locations you configure — typically an application.properties file — and, before that, letting OS environment variables and JVM system properties participate automatically. Two settings control that participation: camel.component.properties.environment-variable-mode and ...system-properties-mode, each one of never, fallback (checked only if the key can't be resolved anywhere else), or override (checked first, ahead of every configured location). Both default to override, and environment variable mode is checked before system property mode — so out of the box, an environment variable of the same name silently wins over a value written in a checked-in properties file, before Camel even opens the file.

Spring Boot and Quarkus don't hand {{...}} to that same chain. Spring Boot bridges it into Spring's own Environment, so it follows Spring Boot's externalized-configuration order instead — command-line arguments, then JVM system properties, then OS environment variables, then a profile-specific application-{profile}.properties (selected by spring.profiles.active), then the base application.properties. Quarkus bridges it into SmallRye Config, whose sources are ranked by a numeric ordinal, highest first: a JVM system property (ordinal 400) outranks an OS environment variable (300), which outranks application.properties (250). A profile-specific value lives in the same file with a %profile-name. prefix — %prod.camel.component.kafka.brokers=... — and the active profile defaults to prod once the application is packaged as a runnable jar.

A habit formed on one runtime can silently misfire on another

None of this matters until two same-named values disagree — a leftover ORDER_API_URL environment variable from an old deployment script, say, sitting next to a freshly-updated order.api.baseUrl in application.properties. On Camel Main, the stale environment variable wins by default. Move the exact same route to Spring Boot or Quarkus and a same-named system property would win instead, while an environment variable there still outranks the properties file — just one step lower than on Camel Main. There's no single rule that's safe to memorize across all three; when a resolved value looks wrong, check what's actually set as an env var and a system property before doubting the properties file.

Credentials and secret management

An environment variable keeps a credential out of a properties file, but it still has to get onto the host or into the container somehow — often via the same CI pipeline or orchestration manifest a wider group of people can read. Camel's vault property functions go one step further: the placeholder itself names a secret in a cloud secrets manager, and Camel fetches the value at resolution time instead of reading it from anywhere local. {{aws:secretName}} reaches AWS Secrets Manager; {{hashicorp:secret:path}} reaches HashiCorp Vault; Azure Key Vault and GCP Secret Manager have equivalent functions. Both AWS's and HashiCorp's forms support a default (:defaultValue), a specific field inside a JSON secret (#fieldName), and a specific version (@versionId) — combined, {{aws:secretName#fieldName:defaultValue@versionId}} and {{hashicorp:secret:database#username:admin@2}}.

Reaching a secrets manager instead of a local file
# HashiCorp Vault
db.username = {{hashicorp:secret:database#username:admin}}
db.password = {{hashicorp:secret:database#password}}

camel.vault.hashicorp.token = {{env:VAULT_TOKEN}}
camel.vault.hashicorp.host = vault.internal
camel.vault.hashicorp.port = 8200
camel.vault.hashicorp.scheme = https

# AWS Secrets Manager
api.key = {{aws:third-party-api#apiKey:changeit@AWSCURRENT}}

camel.vault.aws.defaultCredentialsProvider = true
camel.vault.aws.region = us-east-1

Each provider is a separate Maven dependency — camel-hashicorp-vault, camel-aws-secrets-manager, and so on — and each is configured through camel.vault.<provider>.* properties (or matching CAMEL_VAULT_<PROVIDER>_* environment variables, which is often how the vault's own connection details get in without a chicken-and-egg problem). AWS accepts either static accessKey/secretKey/region or defaultCredentialsProvider=true to use the standard AWS credential chain instead — the IAM role attached to the running instance or task, rather than a key checked in anywhere at all.

A secret fetched once at startup goes stale the moment it's rotated. AWS and Azure lean on their own change-notification events to catch that — AWS through CloudTrail/EventBridge delivering to an SQS queue (camel.vault.aws.useSqsNotification=true plus sqsQueueUrl), Azure through Event Grid. HashiCorp Vault has no equivalent native notification, so its integration instead polls the secret's metadata endpoint on an interval and compares the current_version field it reports. Either way, three things have to be true at once for a rotation to actually take effect: camel.vault.<provider>.refreshEnabled=true, ...secrets naming which secrets to watch, and — easy to miss — camel.main.context-reload-enabled=true, which is what makes Camel actually act on a detected change rather than merely notice it.

refreshEnabled without context-reload-enabled notices a rotation and does nothing about it

refreshEnabled=true turns on watching the secret — polling HashiCorp's metadata endpoint, or subscribing to AWS/Azure's change events. camel.main.context-reload-enabled=true is the separate switch that lets a detected change actually reload the CamelContext so routes pick up the new value. It's easy to configure the first and assume the job is done; without the second, a rotated database password is detected and then quietly ignored, and the route keeps authenticating with the old one until the process restarts for an unrelated reason.

Running on Kubernetes adds a fourth path that doesn't touch a cloud API at all: the camel-kubernetes component's {{secret:name/key}} and {{configmap:name/key}} functions read a Secret or ConfigMap that's been mounted into the pod as a volume, straight off local disk. That means the mount has to exist in the pod spec in the first place — there's no API-level error if it doesn't, just a placeholder that can't resolve — and that a just-rotated Secret is only as current as however quickly the kubelet has propagated the updated file into the running pod's filesystem, which is usually fast but is not instantaneous.

All of this keeps a credential out of source control and out of the route definition. It says nothing about what happens to that credential once it's sitting in a header or property at runtime — that's logMask's job, from Chapter 26. The two controls are complementary, not substitutes: a beautifully externalized db.password placeholder still ends up in a log aggregator in plain text if a downstream to("log:orders?showAll=true") prints the exchange without masking turned on.

Feature flags and route toggles

The same {{key}} mechanism that externalizes a broker URL also externalizes whether a route runs at all. Every DSL accepts a placeholder for autoStartup: .autoStartup("{{startupRouteProperty}}") in Java, autoStartup: "{{integration.ftpEnabled}}" in YAML, <route autoStartup="{{key}}"> in XML. Combined with the ! negation from earlier in this chapter, one boolean property can drive a pair of routes in opposite directions — useful for an old and a new implementation of the same intake that should never both be live at once.

One property, two routes, always exactly one active
- route:
    id: ftp-intake
    autoStartup: "{{integration.ftpEnabled}}"
    from:
      uri: sftp:orders@ftp.internal/incoming
      steps:
        - to: direct:handleOrder
- route:
    id: ftp-intake-legacy
    autoStartup: "{{!integration.ftpEnabled}}"
    from:
      uri: timer:legacyIntake?period=60000
      steps:
        - to: direct:legacyHandleOrder

A route with autoStartup=false isn't deleted or skipped — it's registered in the CamelContext like any other route, just never started automatically. That matters because it can still be started later, by name, through Camel's RouteController: a flag flip doesn't have to mean a redeploy, if the toggle is read at a moment after startup rather than baked in once as a property.

A URI string with a password typed into it isn't configuration — it's a secret wearing a route's clothes. {{key}} is what lets the same route definition mean something different in every environment it runs in, without the definition itself ever having to change.

So what did we actually gain?

One placeholder syntax, {{key}}, with a default ({{key:default}}), an optional form ({{?key}}), and a boolean negation ({{!key}}) — but resolved by a genuinely different chain depending on the runtime hosting the route, which is worth knowing before a mismatch between an environment variable and a system property surprises you in exactly the environment you can least afford it. Vault functions ({{aws:...}}, {{hashicorp:...}}, and their Azure/GCP equivalents) move a credential out of any local file entirely, with an optional refresh path so a rotation propagates without a restart — provided both refreshEnabled and context-reload-enabled are set, not just the first. Kubernetes's {{secret:...}}/{{configmap:...}} functions read straight off a mounted volume, no API call involved. And the very same mechanism that externalizes a broker URL externalizes whether a route runs at all, through autoStartup. None of this is exotic Camel machinery — it's the ordinary {{key}} syntax, aimed at three different jobs. The next chapter turns to what happens around all of this configuration once it's time to actually ship: packaging a Camel application, running it under Spring Boot or Quarkus, and shutting it down without losing whatever message was in flight at the time.
