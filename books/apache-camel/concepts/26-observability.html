Observability

Chapter 25 ended on a deliberate limit: tests prove a route retries the right number of times and lands in the right dead letter queue before it ships, but they can't tell you what a route is actually doing at two in the morning against a real, misbehaving downstream system. That's "a different kind of watching, done while the route is live" — and it has a name. Observability isn't one feature; it's four separate instruments, each answering a question the others can't: logs answer what happened to this one message, metrics answer how is the system behaving in aggregate, traces answer where did the time go across every service this message touched, and health checks answer should traffic be routed here right now. Camel has a building block for each.

Structured logging: two tools, two very different jobs

Camel gives you two ways to write a log line from a route, and confusing them is the single most common observability mistake in a Camel codebase. The Log EIP — the log() DSL step — takes a Simple-language message template and an optional level, and is the tool for steady-state production logging: you decide exactly what appears in the line.

The Log EIP: you choose what's in the line
from("direct:orders")
    .routeId("orders")
    .log(LoggingLevel.INFO, "Processing order ${header.orderId} for customer ${header.customerId}")
    .to("bean:orderService");

The log: component — a genuine endpoint, reached with to("log:orderRoute?showAll=true") — is a different tool for a different moment: showAll=true dumps the entire exchange, every header, every property, and the body, exactly as it stands at that point in the route. That's invaluable while you're building or debugging a route and want to see everything without writing a single field name. It is a poor choice to leave running in production: it's noisy by design, and without logMask also enabled, it will print whatever happens to be sitting in a header or property — including a credential, if one is.

logMask doesn't mask by default — and it isn't limited to log:

Set camel.main.logMask=true (or context.setLogMask(true) in Java) and Camel automatically redacts over five dozen well-known sensitive keywords — password, apiKey, token, secret, and more — wherever the Log EIP or the log: component would otherwise print a matching header or property value verbatim. camel.main.additionalSensitiveKeywords extends that list with names specific to your domain (ssn, cardNumber, whatever your payloads actually carry). It's off by default, which means a fresh project logging full exchanges for debugging is, by default, also logging secrets in plain text.

Correlation: naming one message across every hop it takes

A single log line is nearly useless on its own; what you actually need is every log line touched by one logical message, in order, across every route and every service it passed through. Camel's answer starts with the breadcrumbId: with useBreadcrumb enabled — the default — Camel stamps a breadcrumbId header on an exchange, falling back to the exchange's own messageId when no breadcrumb already exists on an inbound message. Because it's an ordinary header rather than internal exchange state, it survives any transport that preserves headers — HTTP, JMS, and the rest — so the same value can be grepped across every service the message visits.

Don't confuse this with Exchange.CORRELATION_ID, a separate, Camel-internal exchange property that certain EIPs set on a sub-exchange to link it back to the parent exchange it was split or copied from — the machinery behind the Splitter and Aggregator correlation you saw in Chapter 13, not something you'd grep in a log file. A route is also free to define its own application-level correlation id — an orderId or a tenantId header set once near the top of a flow and read back downstream — and that's often more useful for debugging than breadcrumbId alone, because it means something to the business, not just to Camel.

Having a correlation id in a header is only half the job; getting it into every log line without threading it through every single log() call by hand is what MDC (Mapped Diagnostic Context) is for. The legacy mechanism, camel.main.useMdcLogging=true (or context.setUseMDCLogging(true)), populates SLF4J's MDC with camel.breadcrumbId, camel.exchangeId, camel.messageId, camel.correlationId, camel.routeId, camel.stepId, camel.contextId, and camel.transactionKey for the duration of processing — a log pattern referencing %X{camel.exchangeId} ties every line for one exchange together with zero changes to any individual log() call. It's deprecated as of Camel 4.19 in favor of the newer camel-mdc component, which does the same job declaratively: camel.mdc.enabled=true plus camel.mdc.customHeaders promotes chosen exchange headers straight into MDC, instead of a processor calling org.slf4j.MDC.put directly.

Promoting an order id into every log line, the current way
camel.mdc.enabled=true
camel.mdc.customHeaders=orderId,tenantId
MDC lives on a thread, not on the exchange

SLF4J's MDC is thread-local. If a processor calls MDC.put("orderId", id) by hand, that value is only visible to log lines emitted on that same thread. Camel is deeply asynchronous — a SEDA hop, a thread pool, a redelivery on a scheduler thread — and a value set by hand does not automatically follow the exchange onto whichever thread picks it up next. It's exactly the failure mode Chapter 17's async endpoints introduce: correct on the thread you tested, silently missing on the one production actually uses. The camel-mdc component sidesteps this entirely, because the value travels with the exchange (as a header), not with a thread.

Metrics: counting and timing without touching every route

Logs answer what happened to one message; metrics answer how the whole system is behaving, in aggregate, over time. Camel's camel-micrometer component ships a MicrometerRoutePolicyFactory that instruments every route in a CamelContext with counters and timers, with no per-route code at all — register it once:

One factory, every route instrumented
@Bean
MicrometerRoutePolicyFactory micrometerRoutePolicyFactory() {
    return new MicrometerRoutePolicyFactory();
}

That single bean produces camel.exchanges.total, camel.exchanges.succeeded, camel.exchanges.failed, camel.exchanges.failures.handled, and camel.exchanges.external.redeliveries as counters, plus a camel.route.policy timer capturing exchange duration, per route, automatically. (Camel 3.21 and later use Micrometer's dotted naming convention shown here; older versions used camelCase names like CamelExchangesTotal — worth knowing if you're reading a dashboard built against an older Camel version.) It's easy to assume adding camel-micrometer-starter to a Spring Boot project is enough on its own — it isn't. Spring Boot's autoconfiguration wires Camel's metrics into whatever MeterRegistry bean is on the classpath (typically from spring-boot-starter-actuator), but the route-policy factory itself still needs the explicit bean above, or the equivalent camelContext.addRoutePolicyFactory(...) call in plain Java. Once it's registered, the counters land on the same /actuator/prometheus endpoint as the JVM and HTTP metrics — no separate registry to stand up.

The route policy factory gives you Camel's own operational numbers for free. For a business metric — orders processed, dollars refunded, files rejected — use the micrometer:counter and micrometer:timer endpoints directly inside a route:

A business-level counter and a timed block
from("direct:orders")
    .to("micrometer:timer:order.process?action=start")
    .to("bean:orderService")
    .to("micrometer:timer:order.process?action=stop")
    .to("micrometer:counter:orders.processed");

micrometer:counter increments by 1 by default, or by whatever the increment/decrement URI option (or the matching CamelMetricsCounterIncrement/CamelMetricsCounterDecrement header) says. micrometer:timer works as a pair — action=start before the block you're measuring, action=stop after it — and reports the elapsed time between the two as one named Micrometer timer, independent of whatever the automatic route-policy timer is already recording for the route as a whole.

Distributed tracing: where did the time actually go

A metric tells you the p99 latency went up. It doesn't tell you where, when the request touched Camel, a downstream REST API, a database, and a message broker along the way. That's what a trace is for: one request, one trace id, a span per hop, so a slow request shows up as one wide bar instead of four separate, disconnected numbers. Camel's camel-opentelemetry component captures a span for every message sent to or from Camel; add camel-opentelemetry-starter to a Spring Boot project and configure it through either the OpenTelemetry Java agent or Spring Boot Actuator plus micrometer-tracing-bridge-otel. Incoming trace context arrives on the standard W3C traceparent header, which shows up in a route like any other header.

camel-opentelemetry is deprecated — new work should use camel-opentelemetry2

As of Camel 4.19.0, camel-opentelemetry is deprecated in favor of camel-opentelemetry2, its replacement and the recommended choice for new tracing work. Both ship in the 4.18 LTS / 4.20 lines this book targets, so existing code on the older component keeps working — but reach for the v2 component when you're starting something new.

Tracing and MDC logging meet at exactly one point, and it's worth knowing about deliberately rather than discovering by accident: OpenTelemetry's logger auto-instrumentation adds trace_id and span_id into the very same MDC map Camel's own MDC keys populate. One log line can then be filtered by a Camel-native identifier (camel.exchangeId, camel.routeId) and a distributed trace identifier (trace_id) at the same time — the local exchange and the cross-service trace it belongs to, in one grep.

Health checks: readiness and liveness are different questions

With camel-health on the classpath, Camel automatically registers four kinds of check: a context check (is the CamelContext started), a routes check (are all discovered routes started), a consumers check (per-consumer input checks), and a registry check (any custom HealthCheck beans you've added). Producer checks are opt-in — camel.health.producersEnabled=true — and each category can be toggled independently with camel.health.routesEnabled, camel.health.consumersEnabled, and camel.health.registryEnabled.

A health check is, by default, used for both readiness and liveness — and those are genuinely different questions that deserve different answers. Readiness asks "should traffic be routed to this instance right now?" Liveness asks "is this process healthy enough to keep running, or should the platform restart it?" A custom check overrides isReadiness() and/or isLiveness() to restrict itself to one:

A downstream outage should stop traffic, not trigger a restart
public class DownstreamHealthCheck extends AbstractHealthCheck {
    public DownstreamHealthCheck() { super("custom", "downstream-order-api"); }

    @Override
    protected void doCall(HealthCheckResultBuilder builder, Map<String, Object> options) {
        if (orderApiClient.isReachable()) {
            builder.up();
        } else {
            builder.down().message("order-api unreachable");
        }
    }

    @Override
    public boolean isLiveness() { return false; } // readiness-only
}
Failing liveness for a problem you can't fix by restarting is a self-inflicted outage

If the downstream order API check above answered both readiness and liveness, a thirty-second blip in that API would make Kubernetes conclude the pod itself is unhealthy and restart it — which does nothing for an API that's down, throws away in-flight work, and adds a cold-start delay on top of the original outage. Restricting the check to readiness gets the same protective effect — the load balancer stops sending it traffic — without the process being killed for a problem that was never its own.

Spring Boot exposes the aggregated result at /actuator/health, folding Camel's checks into Spring's own health groups; Quarkus exposes the equivalent at /q/health, split into /q/health/ready and /q/health/live — the same readiness/liveness split, just at two separate URLs instead of one document.

A route that's never been watched in production is running on faith. Logs, metrics, traces, and health checks are how "it's probably fine" becomes something you can actually check — four different windows onto the same running system, each one blind to what the others see clearly.

So what did we actually gain?

A vocabulary for the four separate jobs "observability" quietly bundles together, and a Camel building block for each: the Log EIP for deliberate production log lines, and the log: component reserved for debugging, both aware of logMask; a breadcrumbId that names one message across every header-preserving hop, and MDC (now camel-mdc) to get that id, and whatever else you choose, into every log line without threading it through every call by hand; MicrometerRoutePolicyFactory for automatic per-route counters and timers, plus micrometer:counter/timer for the business metrics only your route knows about; camel-opentelemetry2 for a trace that shows where time actually went across every service a message touched; and camel-health's context/routes/consumers/registry checks, deliberately split into readiness and liveness so a downstream outage stops traffic instead of restarting a perfectly healthy process. None of this fixes anything by itself — it's how you find out something needs fixing, and where to look. The next chapter turns to a quieter but no less operational concern: how the configuration and secrets these components read — the JMS broker URL, the API key, the feature flag — get into a Camel application in the first place, safely, per environment.

  2. You enable camel.main.useMdcLogging=true and call MDC.put("tenantId", id) by hand inside a processor just before a SEDA hop. On the far side of that hop, the log lines are missing tenantId. Why, and what's the fix that doesn't involve threading the value through every downstream log() call?
