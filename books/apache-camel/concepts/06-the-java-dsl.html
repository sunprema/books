The Java DSL

Chapter 05 ended with a promise: take the two YAML routes we just got running, rewrite them as RouteBuilder classes, and explain why this book leans on Java as its default from here on. You've actually already seen the shape once — Chapter 04's OrderRoute example was a RouteBuilder all along. This chapter is where that shape stops being a thing you copied and becomes a thing you understand: what from, to, and process are actually doing, what a RouteBuilder buys you that a YAML file can't, and how direct: endpoints let you build routes out of other routes.

Same routes, real Java

A RouteBuilder is an ordinary class with one job: override configure(), and whatever routes you build inside it get registered with the CamelContext when Camel calls that method once at startup. Nothing stops you from defining more than one route in a single configure() — here are both of Chapter 05's routes, side by side, in one class:

FirstRoutes.java — heartbeat.yaml and orders-copy.yaml, as Java
@Component
public class FirstRoutes extends RouteBuilder {

    @Override
    public void configure() throws Exception {

        from("timer:heartbeat?period=5000")
            .routeId("heartbeat")
            .log("Tick ${exchangeProperty.CamelTimerCounter}");

        from("file:data/incoming?noop=true")
            .routeId("orders-copy")
            .log("Copying ${header.CamelFileName}")
            .to("file:data/outgoing");
    }
}

Read that against the YAML from Chapter 05 and there's genuinely nothing new in it — same URIs, same routeId, same log message, same noop. Only the spelling changed, exactly as promised. What is new is what that spelling is made of: @Component is what gets FirstRoutes noticed by Spring Boot's auto-configuration (skip it and the class compiles fine but Camel never starts the routes inside it — a quiet, easy mistake); configure() is a real Java method, so it can contain more than a static list of steps, which is the whole subject of this chapter.

from, to, and the shape of the chain

from(uri) is special: it's the only call that starts a route, and every route has exactly one. Everything chained after it — .routeId, .log, .to, .process — is a method on the object from handed back, which is why the whole thing reads as one fluent sentence instead of a sequence of separate statements. to(uri) is not similarly limited: a route can call .to(...) as many times as it needs, and by default each one is a sequential hop — the message goes to the first to, whatever comes back continues to the second, and so on. That's worth saying plainly because it's easy to expect multiple to calls to mean "send a copy to each" — that's a real pattern (multicast), but it isn't what plain chained to calls do; multicast gets its own .multicast() call in Part IV.

One route, however you format it

The line breaks in every example on this page are cosmetic — Java doesn't care where a statement wraps, and neither does Camel. What matters is that the whole chain, from from(...) to the trailing ;, is one Java statement building one RouteDefinition. Break it wherever it reads best; a step per line is simply the convention this book (and most Camel code you'll read) follows.

process(): when the built-in steps run out

Chapter 02 named the interface underneath every step in a route: Processor, one method, process(Exchange). .log(...) and .to(...) are Processors Camel wrote for you; .process(...) is where you write your own, and because Processor is a single-method interface, a lambda is all it takes:

A Processor as a lambda, with the full Exchange in hand
from("file:data/incoming?noop=true")
    .routeId("orders-copy")
    .process(exchange -> {
        String name = exchange.getMessage().getHeader("CamelFileName", String.class);
        if (name == null || !name.endsWith(".csv")) {
            throw new IllegalArgumentException("not a CSV file: " + name);
        }
    })
    .to("file:data/outgoing");

That's real power — the whole Exchange, body, headers, properties, and all — but it's also the option that costs the most to read later. A route that's mostly .process(exchange -> { ... }) blocks reads like a program with the plot summary removed; the intent is buried inside Java rather than visible in the chain of method names. Match the tool to the job, the same discipline Chapter 05 asked of you for logging:

Three ways to touch a message, in order of how much they cost to read
 Built-in step.bean(...).process(...)
Example.setHeader("x", simple("...")).bean(OrderValidator.class, "validate").process(exchange -> { ... })
What it seesone value, via an expression languagewhatever parameters Camel can bind for you — often just the bodythe entire Exchange
Best fora single header, body, or property changelogic that already exists as a plain, testable Java methodanything that genuinely needs headers, properties, and the body at once

Reach for .process() last, not first — it's the escape hatch for when the DSL's own vocabulary runs out, not the default way to touch a message.

direct: endpoints and building routes out of routes

Chapter 03's pattern table named direct: as Camel's point-to-point option; here's what that means in practice. direct:name is the closest thing Camel has to a plain Java method call: a producer .to("direct:name") invokes whatever route has .from("direct:name") as its consumer, synchronously, on the caller's own thread, with no queue, no serialization, and no boundary crossed — both routes have to live in the same CamelContext. That makes it the natural tool for factoring a step or two shared by more than one entry point out into their own named route, the same instinct that pulls a repeated block of code out into a method:

Two entry points, one shared validation route
from("direct:validateOrder")
    .process(exchange -> {
        String body = exchange.getMessage().getBody(String.class);
        if (body == null || body.isBlank()) {
            throw new IllegalArgumentException("empty order body");
        }
    });

from("file:data/incoming?noop=true")
    .routeId("orders-copy")
    .to("direct:validateOrder")
    .log("Copying ${header.CamelFileName}")
    .to("file:data/outgoing");
Not a queue

direct:'s synchronous, same-thread behavior is exactly what makes it feel like a method call — and exactly why it's the wrong tool the moment you want the caller to move on without waiting. A slow or blocking consumer route stalls its caller too, because there's no buffer between them. When you actually want an asynchronous hand-off, Part IV's seda: component and Wire Tap pattern are built for that; for now, treat direct: as Camel's answer to "extract a method," not "send this and forget it."

A RouteBuilder is just a class

Here's the promised answer to why this book leans on Java from here: configure() is ordinary Java, which means it has ordinary Java in it — loops, conditionals, private helper methods, constructor-injected dependencies. A YAML or XML route file is data Camel reads and interprets; a RouteBuilder is code that runs once, at startup, and produces routes. That difference stops being academic the moment you need the same route shape more than once:

Three near-identical routes, without writing any of them three times
for (String region : List.of("us", "eu", "apac")) {
    from("file:data/incoming/" + region + "?noop=true")
        .routeId("orders-copy-" + region)
        .log("Copying " + region + " order: ${header.CamelFileName}")
        .to("file:data/outgoing/" + region);
}

A declarative DSL has no equivalent move — you'd write out three routes by hand, or reach for tooling outside Camel entirely to generate the YAML. That's a genuine, structural advantage, but it's not the everyday one. The everyday advantage is duller and matters more: a typo in a URI, a misspelled method name, a missing import all fail at compile time instead of showing up as a startup error in a log line you have to go trace back to a source file. Your IDE autocompletes endpoint options because they're real method signatures, not string keys it has to guess at. Renaming a bean or a constant is a refactor the whole codebase feels, route code included, instead of a manual find-and-replace across route files that might miss one. And a breakpoint set inside a .process() lambda is a real breakpoint — you step through it, inspect the Exchange live, exactly like debugging any other Java code, because it is other Java code.

None of that makes the Java DSL strictly better — Chapter 07 takes on YAML and XML next, and both have real strengths this chapter deliberately hasn't covered. But for a book whose examples need to compile, refactor cleanly, and step through a debugger without a second toolchain, Java is the default from here on for those reasons, not out of habit.

What actually changed today

Nothing about the routes — the heartbeat and file-copy routes from Chapter 05 do exactly what they did before. What changed is the tool: configure() is a real method, so a route can be built with a loop instead of copy-pasted; .process() is the escape hatch for logic the DSL's own steps can't express; and direct: turns "call this route from that one" into one line, as long as both live in the same CamelContext.

So what did we actually gain?

The same two routes, now written in a language that can generate routes instead of only listing them, catches its own typos before you run it, and lets a debugger step inside a .process() block line by line. Nothing here required abandoning what Chapter 05 built — it's the same shape, spelled differently, with more of a real programming language available when a route needs one. Chapter 07 looks at when you'd reach for YAML or XML instead, and why "instead" is sometimes the right answer.

Check yourself

  1. A teammate writes a RouteBuilder subclass, runs the Spring Boot app, and its route never starts — no error, nothing in the logs. What's the single most likely thing missing from the class?
  2. You're deciding between .setHeader("status", simple("VALID")) and a .process(exchange -> exchange.getMessage().setHeader("status", "VALID")) lambda that does the exact same thing. Which should you write, and why?
  3. Route A calls .to("direct:enrichOrder"), but route B — the one with .from("direct:enrichOrder") — hasn't started yet when the first message arrives. What happens, and why does that happen immediately rather than the message just queuing up until route B is ready?
