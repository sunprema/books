Databases and Persistence

Chapter 19 closed on a promise: the same transport swap that turned a filesystem into an HTTP call now turns an HTTP call into a database connection. A relational database doesn't hang the way a socket does — it's usually right there, on the same network, fast — but it asks a question neither the file component nor camel-http ever had to: when more than one statement has to succeed or fail together, who is holding that guarantee? This chapter covers three ways Camel talks to a database (sql, jdbc, and jpa), how to call a stored procedure, and how transacted() answers the together-or-not-at-all question — including two threads from earlier chapters, the idempotent repository from Chapter 16 and the aggregator from Chapter 13, that turn out to be database rows underneath.

Three components, three levels of abstraction

There isn't one "database component" in Camel — there are three, and they disagree on purpose about how close to the raw SQL you want to sit:

sql, jdbc, and jpa — the same database, three different distances from raw SQL

None of the three is strictly "better" — they're answers to different questions about how much SQL you want to write and how much your route should know about rows versus objects. The rest of this chapter takes them roughly in that order: sql first, because it's the one you'll reach for most often; jdbc as the lighter alternative; jpa for when entities are already the currency of the rest of the application.

The sql component: named parameters, and where the result actually lands

A sql endpoint URI carries the SQL text directly: sql:select * from orders where id = :#id. That's immediately worth stopping on, because the URI already uses ? to separate the address from its own options — the same collision Chapter 19's REST DSL and Chapter 4's project setup never had to think about. So a literal ? placeholder in SQL text is off the table; Camel repurposes # for a positional parameter and :#name (or :#${expression}) for a named one.

Named parameters, bound straight from a header
from("direct:findCustomerOrders")
    .to("sql:select id, status, total from orders "
        + "where customer_id = :#customerId order by created_at desc"
        + "?dataSource=#myDS");

Named-parameter values are resolved in a fixed order: first a Simple expression written directly in the placeholder, then the message body if it's a java.util.Map, then message headers, then exchange variables. In the snippet above, :#customerId falls through to the header of the same name with no processor step needed to move it there first.

A select puts List<Map<String,Object>> in the body by default — one map per row, keyed by column name. Two options reshape that: outputType=SelectOne collapses a known single-row result down to one object instead of a one-element list, and outputType=StreamList streams rows one at a time rather than materializing the whole result set, the same memory concern Chapter 18 raised about large files. outputHeader redirects the result onto a header instead of overwriting the body — useful when the route is enriching a message (Chapter 15) and still needs the original body afterward.

An update, insert, or delete does not return a body

Run sql:update orders set status = 'SHIPPED' where id = :#id and the OUT body is null. The affected row count exists, but only as a header (SqlConstants.SQL_UPDATE_COUNT, i.e. CamelSqlUpdateCount) — code that expects an update to hand back rows the way a select does will find an empty body and needs to read that header instead.

One more option worth knowing before it's needed: batch=true changes what the inbound body means. Instead of one set of parameters, Camel expects an iterable of parameter-iterables — one inner list per statement execution — so a bulk insert of many rows is driven by wrapping many parameter lists into a single outer collection, not by looping .to("sql:...") once per row.

The jdbc component: lighter, producer-only, SQL in the body

jdbc makes the opposite tradeoff. Its endpoint URI names only a DataSource bean — jdbc:myDS — and the SQL text always comes from the message body, never the URI. It talks to the JDBC driver directly instead of going through Spring's JdbcTemplate, so it has no Spring dependency at all; the tradeoff is that it's producer-only (there's no from("jdbc:...") consumer) and, per its own documentation, an application that needs Spring-managed transactions around its database calls should reach for sql instead.

jdbc: SQL travels in the body, not the URI
from("direct:adHocQuery")
    .setBody(simple("select * from orders where id = ${header.orderId}"))
    .to("jdbc:myDS");

Results default to the same shape as sql — a list of maps, one per row. useHeadersAsParameters enables its own named-parameter substitution from headers, and useGetGeneratedKeys together with a CamelRetrieveGeneratedKeys header exposes auto-generated keys from an insert. Those two conveniences don't combine, though — generated-key retrieval and named-parameter binding are documented as mutually exclusive on this component, not just an uncommon pairing.

In practice, most routes in this book's style reach for sql: named parameters read better than string-concatenating a query into the body, and the polling consumer is genuinely useful. jdbc earns its place when the dependency footprint matters more than the convenience, or when a query is already dynamically built and the body is the natural place for it to live anyway.

The jpa component: entities in, entities out

jpa is the odd one out in a good way — a route using it exchanges @Entity objects, not rows. As a consumer it polls entities of a configured entityClassName and, by default (consumeDelete=true), deletes each one from the database the moment it's handed to the route. That default is worth pausing on: a route that fails downstream of consumption has already lost the record, unless consumeDelete is set to false and the route instead relies on a status column or a lock to control what gets re-polled — the same "how do I know this was really handled" question Chapter 16's idempotent consumer answers for messaging sources, now on a table you own directly.

maximumResults exists because a first poll can be a very large poll

Point a fresh jpa consumer at a table that already has a large backlog of unprocessed rows and, with no cap, the first poll tries to load the entire matching result set into memory at once. maximumResults bounds how many entities a single poll loads — set it the way Chapter 18 set bounds on file-consumer batch sizes, before the backlog is the thing that teaches you it was missing.

On the producer side, sending an entity object persists or merges it; sending a java.util.List of entities needs entityType=java.util.List so the component knows to iterate the list rather than treat it as one entity. For reads and bulk operations, three query options cover different starting points: query takes JPQL directly on the endpoint, namedQuery references a @NamedQuery already declared on the entity class, and nativeQuery runs SQL directly — but without an explicit resultClass, a native query hands back raw Object[] rows instead of typed entities, the JPA equivalent of the un-marshalled body Chapter 9 warned about.

Calling a stored procedure: sql-stored's method-signature template

Some databases put real logic behind a stored procedure rather than a table, and sql-stored is Camel's way in. Its endpoint URI is a template that reads like a Java method signature — a name, then IN/OUT/INOUT parameters, each with an SQL type and either a value expression (IN) or a result name (OUT/INOUT):

One IN, one INOUT, one OUT parameter
from("direct:runPayoutCalc")
    .to("sql-stored:CALC_PAYOUT("
        + "INTEGER ${header.accountId}, "
        + "INOUT INTEGER ${header.attempt} attemptOut, "
        + "OUT DECIMAL payoutOut)")
    .log("payout=${header.payoutOut}, attempt=${header.attemptOut}");

Every OUT and INOUT parameter names a result, and that name is where the value lands — as a message header, not the body. payoutOut above is both the SQL parameter identifier and the header key the result shows up under afterward. It's the same header-not-body habit the update-count callout raised for plain sql statements: a write-shaped operation tends to report back through headers, and a read-shaped one through the body.

transacted(): when more than one statement must succeed together

Everything so far has been one statement per call. The moment a route needs two or more database writes to succeed or fail as a unit — write an order, then write its audit trail, and never end up with one but not the other — a single call's own success isn't enough anymore. That's what transacted() is for. Placed as the first step after from(...), it marks the remainder of the route as one Spring-managed transaction: under the covers, that remainder runs inside a TransactionTemplate driven by a configured PlatformTransactionManager, and any transactional endpoint invoked from inside it — a sql or jdbc call, a JMS send under a JMS transaction manager — automatically enlists in that already-open transaction instead of opening its own.

Two writes, one unit of work
from("direct:createOrder")
    .transacted()
    .to("sql:insert into orders (id, customer_id, total) "
        + "values (:#id, :#customerId, :#total)?dataSource=#myDS")
    .to("sql:insert into order_audit (order_id, event) "
        + "values (:#id, 'CREATED')?dataSource=#myDS");

If the second insert fails, the first one rolls back too — that's the whole point of naming both statements as one transaction instead of hoping they both individually succeed. Camel also supports Spring's propagation behaviors, so a route calling into a second transacted route can choose whether that nested unit of work joins the caller's transaction (PROPAGATION_REQUIRED, the common case) or always starts a fresh one that commits or rolls back independently (PROPAGATION_REQUIRES_NEW).

transacted() only protects the calling thread

A Spring transaction context is bound to the thread that opened it. transacted() must be the first step after from(...), and every statement meant to share the transaction has to stay on that same thread to be covered by it. Route into a seda: endpoint or hand the exchange to an async listener midway through, and whatever runs on the other side executes outside the original transaction entirely — Chapter 17's SEDA queue is exactly this kind of thread boundary, and it is not transaction-aware just because the route that fed it was.

One more distinction worth naming precisely, because it collides with vocabulary from Chapters 16, 23, and 24: redelivery inside a transacted route is the backing resource's job, not Camel's. A failed insert rolls back and, depending on the resource, may be retried by the database or a JMS broker's own redelivery — not by Camel's redeliverPolicy or Dead Letter Channel. Bolting Camel-level redelivery onto a transacted route without accounting for that can mean a failure gets retried twice, by two different systems that don't know about each other, or masked entirely by whichever one gives up first.

Two threads from earlier chapters, now open on the table

Chapter 16 named JdbcMessageIdRepository in a comparison table and moved on: durable, shareable across instances, reach for it when there's already a relational database in the deployment. It's worth opening up now that the SQL underneath it is no longer a mystery. Its default table is CAMEL_MESSAGEPROCESSED(processorName, messageId, createdAt); a lookup runs SELECT COUNT(*) FROM CAMEL_MESSAGEPROCESSED WHERE processorName = ? AND messageId = ?, and a new key is recorded with a plain INSERT.

The default schema JdbcMessageIdRepository expects
CREATE TABLE CAMEL_MESSAGEPROCESSED (
    processorName VARCHAR(255),
    messageId VARCHAR(100),
    createdAt TIMESTAMP,
    PRIMARY KEY (processorName, messageId)
);

That primary key is doing real work, not just enforcing tidiness. With concurrent consumer instances, the safety of the whole idempotent-consumer pattern rests on a unique constraint over (processorName, messageId): without one, two instances can both pass the SELECT COUNT(*) check before either finishes its INSERT, and the same "new" message gets waved through twice. The guarantee comes from the constraint rejecting the second insert, not from the check that ran before it — a distinction that only becomes visible once you can see the actual statements.

The same module ships a database-backed counterpart for Chapter 13's aggregator: JdbcAggregationRepository persists in-flight aggregated exchanges to a table instead of holding them only in memory, so an aggregation in progress survives a process restart rather than losing whatever had been accumulated so far. It needs its own PlatformTransactionManager to orchestrate its writes, and, like any other transactional resource, can be given a propagation behavior when it's used inside a route that's already wrapped in transacted().

Where the connection actually comes from

None of sql, jdbc, or jpa need an explicit dataSource=#myDS option if the deployment only has one DataSource bean. Camel's #autowired property binding looks up the registry for a single bean matching the option's declared type and uses it automatically when none is configured — in a Spring Boot application, that means the framework's own auto-configured DataSource is normally picked up with zero Camel-side wiring at all.

That auto-configured DataSource has been backed by HikariCP as Spring Boot's default pool since Spring Boot 2, tunable through spring.datasource.hikari.* properties such as maximum-pool-size, connection-timeout, idle-timeout, and max-lifetime. Camel doesn't run a pool of its own on top of it — every sql, jdbc, or jpa call borrows a connection from whatever DataSource (or EntityManagerFactory) it was handed. A burst of concurrent routes competing for a pool sized for a quiet afternoon is an application-wide sizing problem, the same way Chapter 19's connectionRequestTimeout was about a client's own pool being saturated, not about the far side of the call.

A file either exists or it doesn't. An HTTP call answers or it doesn't. A database sits in between: almost always there, almost always fast, and the one transport in this book so far that lets you ask for more than "did this one thing work" — you can ask "did this whole set of things happen together, or not at all." transacted() is Camel's way of actually meaning that, instead of hoping two separate calls both quietly succeed.

So what did we actually gain?

Three components at three distances from raw SQL — sql with named parameters and a polling consumer, jdbc lighter and producer-only with SQL in the body, jpa trading rows for entities — plus sql-stored for logic that already lives behind a procedure. Underneath all four, the same two habits recur: writes report back through headers, not the body, and a DataSource is usually resolved for you rather than configured by hand. transacted() layered on top answers the question none of the earlier "Real Systems" chapters could: when more than one statement has to succeed together, a PlatformTransactionManager is what makes that true, on one thread, with redelivery left to the resource underneath rather than to Camel. And two patterns from earlier chapters turned out to be ordinary tables all along — the idempotent repository from Chapter 16 and the aggregator's durable store from Chapter 13 — which is as good a sign as any that "database" was never really a new topic in this book, just a transport this chapter finally named. Chapter 21 stays inside Real Systems once more, trading the request/response shape of HTTP and SQL for the queues and topics of a messaging system.
