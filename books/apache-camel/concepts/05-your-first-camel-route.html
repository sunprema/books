Part II — Building Your First Routes · Chapter 05

05

Your First
Camel Route

Chapter 04 got us a place to run things. Nothing has actually run yet. That changes now: we'll write the smallest route Camel can execute, watch it fire, then grow it — one small change at a time — into a route that reads a file from one directory and writes it to another. By the end, three ideas that sounded abstract in Chapter 02 — from, a route ID, and a route's lifecycle — will have shown up as things you actually typed and watched happen.

The smallest route Camel can run

Every route needs exactly one from. The simplest possible one doesn't talk to any external system at all — it's the timer component, which fires an (almost) empty message on a schedule using nothing more than java.util.Timer underneath. No file to create, no service to have running, nothing to misconfigure. That makes it the right first thing to run, even though you'll rarely ship a route that ends with one.

heartbeat.yaml
- route:
    id: heartbeat
    from:
      uri: timer:heartbeat
      parameters:
        period: 5000
      steps:
        - log:
            message: "Tick ${exchangeProperty.CamelTimerCounter}"

Scaffold and run it the same way Chapter 04 did:

Zero to a running route
$ camel run heartbeat.yaml --dev
... Started heartbeat (timer://heartbeat)
... Tick 1
... Tick 2
... Tick 3

That's a complete, running Camel route: one from, one step, one id. The id: heartbeat line is doing more work than it looks — without it, Camel would have auto-assigned this route a generic name like route1, which is fine right up until a second or third route joins the file and you're squinting at logs trying to work out which route2 is which. Name your routes. It costs one line and it's the difference between a log line you can act on and one you have to go dig for.

Properties, not headers

Each timer firing stamps three pieces of bookkeeping onto the exchange — CamelTimerName, CamelTimerFiredTime, and CamelTimerCounter (counting up from 1) — but as exchange properties, not message headers. Reach for ${exchangeProperty.CamelTimerCounter}, not ${header.CamelTimerCounter}; the latter silently resolves to nothing rather than failing loudly, which is the more annoying way to find out.

Tune the schedule through the timer's own options, all on the URI: period is the gap between firings in milliseconds (default 1000); delay is the wait before the first firing — make it negative and the first message fires immediately instead of waiting; repeatCount caps the total number of firings, so repeatCount: 1 fires exactly once and then never again; and fixedRate: true swaps Camel's default fixed-delay scheduling (wait period after the previous run finishes) for fixed-rate scheduling (fire every period on the clock, regardless of how long the last run took).

Two ways to log, and when each earns its keep

The log step above is deliberately the lightweight tool: a Simple-language string, one line of output, nothing to configure. It exists specifically so you don't need a whole endpoint just to leave a breadcrumb. But Camel also ships a full log component, reached with to("log:name?options"), that behaves like any other endpoint — and unlike the log step, it can dump the entire exchange, not just a message you wrote:

Two different tools, both called "log"
 log("...") stepto("log:name?...")
What it takesa Simple-language string you writethe exchange itself — body, headers, everything
Configurationnone — it's just a messageshowHeaders, showBody, showAll, level, multiline, groupSize…

Reach for the wrong one and you either under-log (a bare log() when you actually needed to see every header on a misbehaving exchange) or over-log (routing every exchange through a fully-configured log: endpoint just to print "step 3 done"). Match the tool to the question you're actually asking.

A route that actually moves something

A heartbeat proves the wiring works; it doesn't integrate anything. The next-smallest useful route reads a file from one directory and writes it to another — and because the file component plays both consumer and producer under the exact same file: scheme, that route is only two endpoints with a log line in between:

orders-copy.yaml
- route:
    id: orders-copy
    from:
      uri: file:data/incoming
      parameters:
        noop: true
      steps:
        - log:
            message: "Copying ${header.CamelFileName}"
        - to:
            uri: file:data/outgoing

Drop a file into data/incoming and, within a poll cycle, the same file appears in data/outgoing — same name, same content, no extra configuration required to make that happen. That's not a coincidence: when the file consumer reads a file, it stamps the original filename into a CamelFileName header on the message; the file producer, given no other instruction, writes its output using whatever is already sitting in CamelFileName. The naming rides along with the exchange for free. It's only once a message's body stops originating from a file consumer — built from scratch in a processor, say — that you need to set CamelFileName yourself.

Where did my file go?

Without noop, the file consumer's default behavior after a successful run isn't to leave the file alone or to delete it — it moves the file into a hidden .camel subdirectory inside the same folder, and the consumer always skips any filename starting with a dot (including .camel itself), so that file is never re-picked-up. The input directory looks empty; the file is one level down. noop: true is what makes a demo route safe to run over and over — the source file is genuinely untouched. delete: true is the third option, for when you want the file gone outright once it's been handled.

The Java DSL will be the working language for the rest of this book starting next chapter, but it's worth a glance now so the shape looks familiar when it arrives:

The same route, previewing the Java DSL (Chapter 06)
from("file:data/incoming?noop=true")
    .routeId("orders-copy")
    .log("Copying ${header.CamelFileName}")
    .to("file:data/outgoing");

Same route ID, same noop, same log line, same reused filename — just written as method chains against a from(...) instead of a YAML route: block. Nothing about the underlying route changed; only its spelling did.

Starting, stopping, and the difference that matters

You've already been living inside a route's lifecycle without naming it: every time camel run --dev reloaded a saved change, it wasn't restarting the whole JVM — it was using Camel's own start/stop machinery to tear down and rebuild just the route that changed. That machinery is exposed directly through the CamelContext (and, once a project is running for real, through JMX or the CLI's own management tooling), as two separate pairs of operations that are easy to reach for interchangeably and shouldn't be:

Two ways to stop a route, with different intent
OperationWhat actually happensUse it when…
stop() / start()a full, graceful shutdown — in-flight work is given time to finish, then internal state and caches are cleared; starting again rebuilds the route from scratchthe route is genuinely done, or its configuration changed
suspend() / resume()message consumption pauses, but the route's underlying services stay running wherever the component supports itthe pause is temporary — resuming is faster than a stop/start round trip

A route also doesn't have to start the instant the CamelContext does. routeId("orders-copy").autoStartup(false) in Java (autoStartup: false in YAML) defines the route but leaves it un-started until something explicitly starts it — a knob you'll reach for again in Part VI, once "when should this route be allowed to run" becomes an operational question and not just a demo convenience.

What actually changed today

Two routes, both following the same shape: one from, a named id, zero or more steps, done. The timer route proved the wiring with nothing to configure; the file route proved that two endpoints sharing one header is enough to move real data between two places. Everything from here — the Java DSL, content-based routing, splitting, enrichment — is this same shape, with more interesting steps in the middle.

So what did we actually gain?

A route that runs, and the vocabulary to talk about what it's doing while it does: an id you chose instead of one Camel guessed, a header that quietly carries a filename from one endpoint to another, and a lifecycle with two genuinely different ways to stop something. None of it required the Java DSL yet — that's next. Chapter 06 takes the YAML routes built here, rewrites them as RouteBuilder classes, and explains why this book leans on Java as its default from that point on.

Check yourself

  1. You run the file-to-file route from this chapter twice in a row against the same data/incoming directory, without noop set. What happens on the second run, and where did the first file actually go?
  2. A teammate writes log("Timer fired ${header.CamelTimerCounter} times") and it always prints an empty value. What's wrong, and what should the expression say instead?
  3. You need to pause a route for a five-minute maintenance window and bring it back up as quickly as possible afterward. Which lifecycle operation pair fits that, and why is it a better fit than the alternative?
