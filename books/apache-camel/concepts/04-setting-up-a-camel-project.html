Part II — Building Your First Routes · Chapter 04

04

Setting Up a
Camel Project

Part I gave us a vocabulary and a pattern language, but no way to run any of it. That changes here. This chapter is deliberately unglamorous — no routing decisions, no clever EIPs — because before any of that can matter you need one boring, working thing: a project Camel will actually start inside. We'll get there three different ways, from the fastest (no project file at all) to the one you'll actually ship.

Three roads in, one destination

However you arrive, a runnable Camel project resolves to the same three pieces: a build descriptor declaring Camel's dependencies and a runtime, one or more route source files, and an application.properties for configuration. What differs is how much of that you type by hand versus how much a tool generates for you.

Getting started, three ways
PathWhat you getBest for
Camel CLI (JBang)a single route file, running — no Maven project, no POM, no IDEprototyping, learning, this chapter
Maven archetypea generated Maven project skeleton, hand-typed commandstarting straight from a build file, no CLI involved
Add to existing projectone dependency (camel-spring-boot-starter) on a project you already haveCamel joining an existing Spring Boot codebase

This book leans on the first path because it gets you to a running route the fastest, and because — unlike an archetype, which is a one-shot template — the CLI has a built-in on-ramp to the other two: a single command turns whatever you've been prototyping into a full Maven project. Let's build the muscle memory.

Installing the Camel CLI

The Camel CLI runs on top of JBang, a tool for running Java without first setting up a project. Install JBang for your platform, then install Camel into it as a JBang app:

Install once
$ jbang app install camel@apache/camel
$ camel version
JBang version: 0.141.0
Camel CLI version: 4.18.0

That's the whole setup. No Maven project, no POM file, no IDE. The first time you run a route, the CLI resolves and downloads whatever Camel JARs that route needs — which does mean it wants internet access on that first run, same as any Maven or Gradle build resolving dependencies for the first time.

No JBang allowed on this machine?

A standalone Camel Launcher distribution ships the same CLI as a downloadable .zip, no JBang install required — unzip it, add its bin/ folder to your PATH, and camel works the same way from there. Same commands, same output, from here on.

From nothing to a running route

camel init scaffolds a starter route; the file extension you give it picks the DSL — nothing more to configure. Then camel run starts it.

Zero to running, three commands
$ camel init hello.yaml
$ camel run hello.yaml
... Started hello (timer://yaml)
... Hello Camel from route1
... Hello Camel from route1

Ctrl+C stops it. Swap the extension and you get the same workflow in a different DSL — camel init Hello.java for Java, camel init hello.xml for XML. We'll spend Chapter 06 on why the Java DSL is this book's default and Chapter 07 on when YAML or XML earns its keep instead; for now, notice that the CLI itself doesn't care which one you reach for.

Add --dev and the CLI watches the file: save a change, and Camel reloads the running route in place, no restart. This is the loop you'll live in for the rest of this book — edit, save, watch it reload — and it works identically across YAML, Java, and XML.

Dev mode: edit, save, watch it reload
$ camel run hello.yaml --dev

Don't have a route in mind yet? The CLI ships a catalog of ready-to-run examples, sorted by difficulty, that you can run without writing anything:

Explore before you write
$ camel run --example
$ camel run --example=timer-log --dev

Graduating: camel export

A single prototype file is exactly the right shape for learning a route, and exactly the wrong shape for deploying one. camel export is the bridge: it takes whatever route files are sitting in your working directory and generates a full Maven project around them, targeting Spring Boot, Quarkus, or standalone Camel Main.

Graduate a prototype into a deployable project
$ camel export --runtime=spring-boot --gav=com.example:order-router:1.0-SNAPSHOT
$ cd order-router
$ mvn spring-boot:run

Without --directory, the export writes into the current folder; --directory=../order-router copies it somewhere else instead. application.properties is bundled into every export automatically, and a handful of options tune the result for real project work: --parent-pom to standardize on an organization's shared parent POM, --camel-wrapper to pin the exact Camel CLI version a team uses (the same idea as the Maven Wrapper — it drops a ./camel launcher script into the project), and --resource-dirs=soap to carry whole resource folders (schemas, WSDL files) into src/main/resources once a route needs more than itself.

You can skip straight to a runtime, too

camel run hello.yaml --runtime=spring-boot (or --runtime=quarkus) runs the prototype directly against that runtime, without exporting first — useful for checking that a route behaves the same once it's inside the real target framework. Reloads still work via Spring Boot DevTools or Quarkus dev mode, with one asterisk: Java route files specifically don't hot-reload under the Spring Boot runtime the way YAML and XML do — that one needs a restart.

Starting from a Maven archetype instead

If you'd rather start from a build file with no CLI step at all, Camel ships archetypes for exactly that. Four cover the paths this book cares about:

Camel's core Maven archetypes
ArchetypeGenerates
camel-archetype-javaplain Java DSL routes on standalone Camel Main
camel-archetype-mainstandalone Camel Main, a different starting template
camel-archetype-spring-bootCamel routes wired into Spring Boot
camel-archetype-springXML DSL routes on classic Spring (legacy)
Generating a project with an archetype
mvn archetype:generate \
  -DarchetypeGroupId=org.apache.camel.archetypes \
  -DarchetypeArtifactId=camel-archetype-spring-boot \
  -DarchetypeVersion=4.18.0

There's nothing wrong with this path — it's the traditional Maven way to start any project — but notice what you lose next to camel export: you can't first prove a route out in the fast edit-save-reload loop and only then decide it's worth a Maven project. The archetype commits you to the project structure up front. We'll mostly use the CLI in this book for exactly that reason, and mention the archetype path because you'll see it in older Camel codebases and tutorials.

Adding Camel to an existing Spring Boot project

The third path skips generators entirely: if you already have a Spring Boot Maven project, Camel joins it as one dependency.

The one dependency that matters
<dependency>
    <groupId>org.apache.camel.springboot</groupId>
    <artifactId>camel-spring-boot-starter</artifactId>
    <version>4.18.0</version> <!-- match your Camel core version -->
</dependency>

camel-spring-boot-starter ships a Spring AutoConfiguration.imports file, so adding this one dependency is enough — there's no separate @EnableCamel-style annotation to remember. Camel's auto-configuration then scans the Spring application context for anything that looks like a route and starts it, at application startup, with no manual wiring:

Camel finds this bean and starts its route automatically
package com.example;

import org.apache.camel.builder.RouteBuilder;
import org.springframework.stereotype.Component;

@Component
public class OrderRoute extends RouteBuilder {

    @Override
    public void configure() throws Exception {
        from("timer:orderPoll?period=5000")
            .to("log:orders");
    }
}

Either shape works: a plain @Component-annotated class extending RouteBuilder, like above, or a @Bean-producing method inside a @Configuration class that returns a RoutesBuilder. Behind the scenes, auto-configuration builds a SpringCamelContext, registers it in the Spring context under the bean name camelContext — so it's @Autowired-able anywhere else, exactly like any other Spring bean — and starts and stops it along with the rest of the application. Route configuration (URIs, timeouts, credentials) reads from the same application.properties or application.yml file the rest of Spring Boot already uses, and those properties are available inside route code as {{placeholder}} expressions.

What a real project looks like, underneath

Whichever of these three roads you took, you land in roughly the same place. This is what camel export --runtime=spring-boot hands you — and, not coincidentally, roughly what the archetype and hand-built paths converge on too:

A generated Spring Boot project's shape
order-router/
  pom.xml                              <- Camel BOM/starter + spring-boot-starter-parent
  src/main/java/com/example/
    OrderRoute.java                    <- your RouteBuilder classes (or beans)
  src/main/resources/
    application.properties            <- runtime configuration, always included
    camel/
      hello.yaml                      <- YAML/XML route files, if that's what you prototyped

Three things, every time: a build descriptor declaring the Camel dependency (and the runtime it targets), your route source (Java, YAML, or XML, in whatever mix you chose), and an application.properties for configuration. camel export doesn't invent this shape from nothing — it's automating exactly the layout you'd assemble by hand from an archetype or from adding camel-spring-boot-starter yourself. Learn to recognize these three pieces and every Camel project you open, on GitHub or at work, stops looking unfamiliar.

Check your JDK before anything else

Camel 4.x — including the 4.18 LTS line this book targets — needs Java 17 at minimum; Camel 4.0 dropped the Java 8/11 support that Camel 3.x still carried, and 17 or 21 are the supported LTS JDKs to build and run against. A route that fails to start against an older JDK usually doesn't say "wrong Java version" — it fails with an obscure class-loading or bytecode error instead. When in doubt, java -version before camel run.

Pick a path by what you're doing right now

Exploring an idea or learning the DSL? camel init + camel run --dev, no project file in sight. Ready to ship what you built? camel export --runtime=… turns exactly that prototype into a Maven project, no rewrite. Joining Camel onto code that already exists? One dependency, camel-spring-boot-starter, and a @Component. This book uses the CLI throughout because it's the only path that lets you do all three without switching tools.

So what did we actually gain?

A working project, and — more usefully — a mental map of how Camel projects come to exist at all: CLI prototype, archetype skeleton, or a starter dropped onto something you already had, all converging on the same build-file-plus-routes-plus-properties shape. None of that involved writing an actual route yet. That's next: Chapter 05 puts a timer on one end and a log statement on the other, and walks a message through a real route for the first time.
