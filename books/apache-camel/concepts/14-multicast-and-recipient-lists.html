Multicast and Recipient Lists

Chapter 12's toD() answered "which one destination should this exchange go to, computed at runtime?" Chapter 13's split() answered "how do I turn one exchange into many, so each part gets its own trip through the route?" Neither one answers a question that comes up just as often: the same, whole exchange — not a part of it — genuinely needs to reach more than one place. An order confirmation needs to hit an audit log, a notification service, and an analytics pipeline, all three, every time. A multi-warehouse order needs to notify whichever warehouses actually stock its line items — a list that's a different length for every order. That's what this chapter covers: Multicast, for a fixed set of destinations declared right in the route, and Recipient List, for a destination set computed per message. They turn out to be close enough under the hood that the difference is really just one question — are the destinations known when you write the route, or only when a message arrives? — and everything else follows from the answer.

multicast(): a fixed fan-out, declared in the route

multicast() sends a copy of the incoming exchange to every destination chained inside its block. Each destination gets its own independent copy — same body, same headers, same properties — so nothing one branch does to its copy leaks into another's. The destinations themselves are just .to() calls, written in the route's source, identical for every message that passes through:

Every order confirmation goes to all three, every time
from("direct:orderConfirmed")
    .multicast()
        .to("jms:queue:audit.orders")
        .to("bean:notificationService?method=orderConfirmed")
        .to("kafka:analytics.order-events")
    .end();

Read that route and you've seen every destination — there's nothing to look up at runtime, nothing hiding behind a header value. That's multicast()'s whole appeal: use it when the fan-out list is a property of the integration, not of any particular message.

No AggregationStrategy means only the last reply survives

Leave multicast() exactly as written above and ask, same as Chapter 13 asked about split(): what does the exchange look like after .end()? Camel's answer, with no strategy supplied, is the same quiet drop — the outgoing exchange becomes whatever the last destination's reply turned into, and every earlier destination's result (and any exception it raised) is simply gone. It's not a coincidence that this reads like Chapter 13's warning: Camel's own documentation describes multicast as the baseline processor that both split() and recipientList() are built on — same engine, same default, same trap.

Running the fan-out in parallel, and what happens when one branch fails

If you want the fan-out's three destinations combined into one result instead of discarded down to one, give multicast() an AggregationStrategy — the exact same aggregate(Exchange oldExchange, Exchange newExchange) interface from Chapter 13, called once per destination, oldExchange null on the first call. Add .parallelProcessing() to run the destinations concurrently instead of one after another, and .timeout(ms) to bound how long the whole fan-out is allowed to take:

Same three destinations, run concurrently and folded into one result
from("direct:orderConfirmed")
    .multicast(new OrderFanOutAggregationStrategy())
        .parallelProcessing()
        .stopOnException()
        .timeout(3000)
        .to("jms:queue:audit.orders")
        .to("bean:notificationService?method=orderConfirmed")
        .to("kafka:analytics.order-events")
    .end()
    .to("direct:orderFanOutComplete");

.parallelProcessing() changes how the three destinations run, not whether the route waits for them — the calling thread still blocks at the multicast() block until all three finish, same as split()'s parallel mode in the last chapter. And with a custom strategy in play, aggregate() may now be invoked from more than one thread at once; Camel synchronizes those calls for you by default, so it's safe even if your strategy isn't written to be thread-safe on its own.

stopOnException isn't the default — a failing branch doesn't stop its siblings

Left unset, Camel keeps sending to every remaining destination even after one of them throws: the exception is recorded on that destination's own exchange, and if you've supplied an AggregationStrategy, it's up to that strategy's aggregate() method to notice newExchange.getException() and decide what to do about it. Nothing forces you to check — an aggregation strategy that only ever reads a successful body will swallow a failed branch just as quietly as the missing-strategy trap above does. stopOnException() is the other option: it aborts the whole fan-out the instant any one destination throws, and sends that exception straight to the route's error handler instead. Neither is "more correct" — a partial audit-log failure probably shouldn't block order confirmation; a partial payment fan-out probably should stop everything. Choose deliberately, per route.

recipientList(): the same fan-out, with a computed destination list

Now the case multicast() can't handle: an order that needs to notify whichever warehouses actually stock its line items — one warehouse for a small order, four for a large one, a list whose length and contents are decided per message, not per route. recipientList() is multicast() with one thing changed: instead of a chain of literal .to() calls, you give it an expression, evaluated once per exchange, whose result becomes the destination list.

Which warehouses, computed per order
from("direct:orderConfirmed")
    .recipientList(header("WarehouseTargets"))
        .ignoreInvalidEndpoints()
    .end();

// A bean upstream sets a per-order, comma-delimited header, e.g.:
// exchange.getMessage().setHeader("WarehouseTargets",
//     "jms:queue:warehouse.west,jms:queue:warehouse.east");

If the expression's result is a String, Camel splits it into individual endpoint URIs on a delimiter — a comma by default, trimming whitespace around each one — and re-configurable for values that legitimately contain commas: recipientList(header("WarehouseTargets"), ";"). If the expression already evaluates to a List or other Collection of URIs — built by a bean instead of assembled as delimited text — Camel uses it directly, no string-splitting step at all. ignoreInvalidEndpoints() is the option multicast never needed: skip a computed URI that doesn't resolve to a real endpoint, instead of failing the whole exchange over one bad entry in a list nobody wrote by hand.

Everything else about recipientList() is the option set you already know from multicast(): parallelProcessing(), stopOnException(), an AggregationStrategy, .timeout() — because underneath, it's the same fan-out engine, aimed at a list it computed instead of a list you wrote.

cacheSize: bound the producers a computed list can create

multicast()'s handful of literal .to() calls reuse the same few producers for the life of the route — nothing to bound. A recipient list can compute a genuinely different set of URIs on every message; left unbounded, Camel's ProducerCache would keep every distinct endpoint it has ever seen warm indefinitely. Set cacheSize deliberately once the possible destination space is large or unbounded — per-customer queues, for instance — the same high-cardinality caution Chapter 12 raised for toD()'s cache, applied here to a whole computed list instead of one computed destination:

from("direct:orderConfirmed")
    .recipientList(header("WarehouseTargets"), ";")
        .cacheSize(50)
    .end();

One destination, a fixed set, or a computed set — three related tools

Chapter 12's toD() and this chapter's recipientList() are easy to blur together — both compute something from an expression at runtime. The difference is cardinality: toD() computes exactly one destination per exchange; recipientList() computes zero, one, or many. Reach for toD() when a message goes to exactly one place that varies by message. Reach for recipientList() when the same message may need to reach several places at once, and which ones varies by message. And reach for plain multicast() when the "which ones" part never varies at all — when the honest answer is "always these three," writing them as literal .to() calls is more legible than routing a fixed answer through a header nobody ever changes.

multicast(), split(), and recipientList() aren't three unrelated patterns that happen to share a name — Camel documents multicast as the baseline engine the other two are built on. Same options, same AggregationStrategy contract, same default of quietly keeping only the last result if you never ask for more. What changes between them is only what gets fanned out: a fixed endpoint list, a computed endpoint list, or the parts of one exchange that was split before any of this began.

So what did we actually gain?

A way to answer "how many places should this one message reach," cleanly separated from Chapter 13's "how many messages should this become." multicast() covers the fan-out that's a property of the integration — always these destinations, written where anyone reading the route can see them. recipientList() covers the fan-out that's a property of the message — a destination list computed fresh per exchange, with ignoreInvalidEndpoints() and cacheSize as the two extra knobs that computed list needs and a fixed one never did. Both default to the same quiet, last-reply-wins trap without an explicit AggregationStrategy, and both leave stopOnException() off by default, so a partial failure keeps going unless you say otherwise. The next chapter turns the direction of these ideas around: instead of sending one message to several places, Message Enrichment pulls data in from a second place to complete the message you already have.
