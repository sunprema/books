Validation and Canonical Messages

Chapter 10 ended on a question it deliberately left open: once unmarshal has handed you back a Java object, how much do you actually trust what's in it? Not much, it turns out — and for a good reason. Marshalling and unmarshalling are forgiving by design; Chapter 10 already showed you a JSON unmarshal that quietly hands back a generic Map instead of failing, and XML that "salvages what JAXB can" from something malformed. Getting a Java object back tells you the bytes were parseable. It tells you nothing about whether they were right. This chapter closes that gap two ways: first with a set of tools for rejecting a message before it does damage, then with a design decision — the canonical model — that lets every route downstream of this one stop asking the question at all.

Two different questions, easy to run together

"Is this message valid?" is really two separate questions wearing one sentence. The first is a gate: is this thing shaped the way it claims to be, with the fields it needs, holding values that make sense? That's validation, and it's this chapter's first half. The second is a design question that has nothing to do with any one message: once something passes the gate, what shape does the rest of your system get to assume it's in? That's the canonical data model, and it's the second half. Conflate them and you get routes that re-validate a message five different ways because nobody ever wrote down what "valid" was supposed to mean — which is exactly the kind of thing this chapter exists to stop.

Three tools, escalating weight — again

If that "escalating weight" framing sounds familiar, it should — Chapter 09 organized transformation the same way, and validation splits along nearly the same lines. A predicate check is the lightest: no schema, no annotated class, just a boolean answer inline in the route. Schema validation is heavier: it checks an entire message's structure against a document written independently of any one route. Bean validation sits in between, checking constraints on a Java object you already trust the shape of. None of the three replaces the others; each one answers a question the lighter ones can't.

The lightest check: validate() and predicates

You've already met the machinery behind validate() twice. Chapter 03's filter() uses a predicate to decide whether an exchange continues; Chapter 09's Simple language builds the predicates that both steps evaluate. validate(predicate) is a third use of the same idea, with one deliberate difference from filter(): where a failed filter quietly drops the message and the route moves on as if nothing happened, a failed validate() throws a PredicateValidationException and stops the exchange right there. Filtering says "skip this one, no big deal." Validating says "this one is wrong, and something needs to know."

Two predicate checks, either one can stop the exchange
from("jms:queue:orders.raw")
    .validate(header("OrderId").isNotNull())
    .validate(simple("${body.total} > 0"))
    .to("jms:queue:orders.checked");

That's the whole tool. It's exactly as good as the predicates you write for it — which is precisely its limit. A predicate can check that one field is present, or that one number is positive. It has no way to check that an entire message is shaped the way a contract says it should be — that every field a downstream system expects is actually there, correctly typed, nested where it's supposed to be. For that, you need something that reads a whole message at once.

Schema validation: checking the wire bytes, not the object

Camel ships two components purpose-built for exactly that: the Validator component (validator:resourceUri) checks an XML body against an XSD using JAXP, and the JSON Schema Validator component (json-validator:resourceUri) checks a JSON body against a JSON Schema document — drafts v4, v6, v7, 2019-09, and 2020-12 (partial), via the NetworkNT library. Both point resourceUri at a schema file on the classpath, the filesystem, or a remote URL; both parse and cache that schema once and reuse it across every message. One difference worth knowing before you reach for either: the XML Validator can sit anywhere in a route, but json-validator is producer-only — it's always a .to(...) step, never a route's from(...).

XML: validate against an XSD before unmarshalling
from("file:inbox/xml")
    .to("validator:schemas/order.xsd")
    .unmarshal(orderXml)
    .to("bean:orderService?method=process");
JSON: same shape, a JSON Schema instead of an XSD
from("jms:queue:orders.raw")
    .to("json-validator:schemas/order-schema.json")
    .unmarshal().json(JsonLibrary.Jackson, Order.class)
    .to("jms:queue:orders.validated");

Notice where both steps sit: before unmarshal, not after. That's not a style preference — it's the whole point. Both checks run against the raw wire bytes, the String or byte array that arrived on the endpoint, exactly the thing Chapter 10's forgiving converters are willing to guess about. Validate first and a malformed message never gets the chance to become a half-trusted Order. There's also a third way to get the same schema check, one Chapter 10 already introduced without naming it as validation: JaxbDataFormat's schema option turns on XSD validation as part of the unmarshal call itself, one step instead of two, failing the exchange on invalid XML rather than letting JAXB salvage something from it.

Validate the bytes, not the object you already trust

It's tempting to unmarshal first — you already need the object anyway — and validate second. But by the time unmarshal has run, Chapter 10's forgiving converters have already made a call about what to do with anything odd: a JSON unmarshal with no unmarshalType silently becomes a Map; XML with no schema check silently becomes whatever JAXB could salvage. If validation is meant to be a gate that rejects malformed input, it has to run against the raw wire body, before or during unmarshal — not on the object that unmarshal already decided to hand you.

One more mismatch worth calling out explicitly, because it fails in a confusing way rather than a loud one: validator: expects XML and an XSD; json-validator: expects JSON and a JSON Schema document. Point either one at the other format's body and you don't get a clean "invalid message" — you get the wrong tool trying to parse bytes it was never built to read.

Bean validation: checking the object, on the other side

Schema validation guards the edge, before a message becomes Java. Once it is Java — after unmarshal, or built by hand — the Bean Validator component (bean-validator://label) is the corresponding check on the object itself: Jakarta Bean Validation annotations (@NotNull, @Size, and the rest) declared right on the class, evaluated by Hibernate Validator by default. Only the default validation group runs unless a route asks for another one with ?group=SomeGroup, which lets one class carry both an always-on baseline and a stricter set of checks only some routes opt into.

Annotations on the class, one .to() step to check them
public class Order {
    @NotNull
    private String orderId;

    @NotNull
    @Min(1)
    private BigDecimal total;
}

// route:
from("jms:queue:orders.raw")
    .unmarshal().json(JsonLibrary.Jackson, Order.class)
    .to("bean-validator://order")
    .to("jms:queue:orders.validated");
Schema and bean validation check different things

It's easy to assume that if the JSON already matched its schema, bean validation is redundant. It usually isn't. A schema checks the wire shape — is total present, and is it a number? A bean-validation constraint can encode a business rule the schema never expressed — is total at least 1? Both can be true or false independently of each other, which is exactly why they're two checks at two different points in the pipeline, not one check written twice.

What happens to a message that fails

Every validation step in this chapter does the same thing on failure: it throws, and the exchange stops right there unless something catches it. validate() throws PredicateValidationException; the schema validators throw their own validation exception on a schema mismatch. Left alone, either one crashes the route. Chapter 23 covers Camel's full exception-handling machinery, but the shape is worth previewing here, because a rejected message is the single most common reason to reach for it early:

Catch it by name, send it somewhere a human can look
onException(PredicateValidationException.class)
    .handled(true)
    .to("jms:queue:orders.rejected");

from("jms:queue:orders.raw")
    .validate(header("OrderId").isNotNull())
    .to("jms:queue:orders.checked");

A route that mixes more than one kind of validation generally needs one onException clause per exception type it wants to handle differently — a predicate failure and a schema failure aren't the same exception class, and treating them identically (or letting either one propagate unhandled) is how "we validate our orders" quietly becomes "we validate our orders, except when we don't notice we didn't."

The canonical data model: one shape, agreed on once

Validation answers "is this message admissible?" It says nothing about what shape a message should be in once it's admitted — and that turns out to matter just as much. Picture an integration that receives orders from three sources: a partner's XML feed, a web storefront's JSON, and a legacy batch job's CSV. Without a shared answer to "what does an Order look like," every route that touches an order has to know all three shapes, and every new consumer of order data has to learn them too. Hohpe and Woolf named the fix a Canonical Data Model: one integration-owned shape that every source is translated into, and every consumer reads from — never the other way around, and never source-to-source directly.

Count the translators each design needs and the payoff stops being abstract. Let every source format talk directly to every consumer that needs it and the number of translators grows with each new pairing — up to N(N−1) of them as sources and consumers both multiply, the same combinatorial growth Chapter 01 showed you for point-to-point system integration in the first place. Route everything through one canonical shape instead and it's N translators, full stop — one per source, once, no matter how many downstream routes end up reading the result. The canonical model is the point-to-point problem from Chapter 01, solved again at the level of a single message format.

Designing one isn't a Camel feature to configure — it's a modeling decision you make before you write a route. Pick field names, types, which fields are required, which units a number is in, all independent of any one source's native shape. Then the tools this book already gave you build the bridge: Chapter 09's setBody/bean/Processor and Chapter 10's marshal/unmarshal, each one a Message Translator doing exactly one format-to-canonical or canonical-to-format conversion, sitting right at the edge where a message enters or leaves your system.

A canonical model modeled on "whatever we integrated first" isn't canonical

The trap is subtle because it's easy to miss in the moment: designing the shared Order shape by copying the first partner's XML field-for-field. It looks like a canonical model — there's one shape, everything gets translated into it — but it's really that partner's format with an extra hop. The next new source still has to bend awkwardly to fit a shape that was never actually neutral, and the combinatorial cost the model was supposed to remove creeps back in, one asymmetric translator at a time.

Validation decides whether a message gets to enter your system at all. The canonical model decides what it looks like once it's in. Get both right at the edge, and every route behind that edge gets to stop asking either question.

So what did we actually gain?

A precise answer to the question Chapter 10 left hanging: trust isn't something unmarshal gives you for free, it's something you build deliberately, in layers — a predicate for a quick business rule, a schema check against the raw wire bytes for structural correctness, bean validation on the resulting object for constraints a schema can't express. And a design principle that outlasts any one route: settle on one canonical shape at the edge, translate every source into and out of it, and let every route behind that boundary work with a message it never has to re-validate. Part III closes here, with a message you can trust and a shape everything downstream agrees on. Part IV starts using that trust: Chapter 12 picks the route a validated, canonical message takes next.
