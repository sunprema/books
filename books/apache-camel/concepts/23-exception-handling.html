Exception Handling

Chapter 22 closed with routes that can reach almost anything — files, HTTP APIs, databases, queues — and a checklist for picking the right component to reach them with. None of that changes a harder fact: every one of those systems will, sooner or later, say no. A file lock will be held by another process. An API will time out. A database will refuse a connection at 2 a.m. for no reason anyone can reconcile afterward. Chapter 8 mentioned in passing that a failed exchange carries its exception around and that "Part VI covers that machinery in full" — this is that chapter, and it starts with the question every route eventually has to answer: when a step throws, what happens next, and who decided that?

The default: fail once, fail loud

Start with what happens if you configure nothing at all, because that baseline is what every onException clause in this chapter is going to override. Chapter 8 called the thing that inspects a failed exchange "the Dead Letter Channel, by default" — useful shorthand for a first look at the Exchange, worth making precise now. The component actually wired in with zero configuration is Camel's DefaultErrorHandler, and the distinction that matters is narrow but real: a Dead Letter Channel is an error handler that, on giving up, moves the failed exchange to a dead-letter destination you name. DefaultErrorHandler has no such destination. Left alone, it logs the failure and lets the exception propagate straight back to whatever called the route — the exchange simply ends there. Nothing is retried, nothing is redirected, nothing is marked "handled." The next chapter is entirely about deliberately configuring a dead-letter destination and a redelivery policy; this one is about the finer-grained tool you reach for first, on the way to that: deciding, exception type by exception type, what "handled" ought to mean.

Fail loud is a reasonable default, not an oversight

A route that silently swallowed every exception by default would hide real bugs behind a shrug. Camel's choice — propagate unless a policy says otherwise — means an unhandled exception is always visible somewhere: in a log, in a caller's stack trace, in a failed HTTP response. Everything in this chapter is about choosing, on purpose, which failures deserve a gentler ending than that.

onException: a policy per exception type

onException is how you tell a route "when this kind of thing goes wrong, do this instead of the default." It reads like a declaration, not a step in the route — you write it once, and Camel applies it wherever a matching exception surfaces:

A policy for one exception type
onException(ValidationException.class)
    .handled(true)
    .useOriginalMessage()
    .log(LoggingLevel.WARN, "Rejecting invalid order: ${exception.message}")
    .to("direct:rejectOrder");

The exception type isn't matched by a simple equality check against whatever got thrown. A processor rarely throws the exact class you declared — it throws something that wraps something that wraps the real cause, three levels deep, the way Java exceptions usually do. Camel unwraps that chain from the innermost cause outward and, at each exception along the way, looks for an exact instanceof match among your declared onException clauses; failing an exact match, it falls back to whichever clause's declared exception is the closest matching superclass. Declare both onException(IOException.class) and onException(FileNotFoundException.class), and a thrown FileNotFoundException goes to the more specific clause — not because you happened to write it first or last, but because it's the exact match.

Three settings decide what happens once a clause matches, and they're worth holding side by side, because mixing them up produces exactly the "why did the caller still see an exception" bug you'd expect:

What a matched onException clause does next
SettingThe caller sees…The route…
handled(false) — the defaultthe exception, rethrownstops; the exchange is marked failed
handled(true)a normal, non-exceptional resultstops at the onException clause; the clause's own steps become the ending
continued(true)a normal, non-exceptional resultresumes from the exact point the exception was thrown, as if it hadn't happened

There's a twist worth having ready before it surprises you: once an onException clause has claimed an exception, exchange.getException() goes back to null for the rest of the route — Chapter 8 showed you this. The exception hasn't vanished; it's living in the Exchange.EXCEPTION_CAUGHT property, which is where a clause's own steps have to look if they want to inspect what actually went wrong: exchange.getProperty(Exchange.EXCEPTION_CAUGHT, Exception.class). That's exactly what ${exception.message} resolves to inside the Simple expression in the snippet above — it's reading that same property, not the exchange's own exception slot.

One more knob, for when the exception type alone isn't specific enough: onWhen(Predicate) adds a condition on top of the type match. A clause for SQLException can fire only when the caught exception's SQL state looks transient, and leave every other SQLException to a different, less forgiving clause — two clauses for the same exception class, split by what the exchange actually looks like when it fails.

doTry, doCatch, doFinally: the local escape hatch

Sometimes a policy that spans the whole route is more machinery than the problem needs — you just want to wrap three steps the way you'd wrap them in Java, handle what goes wrong right there, and move on. Camel's DSL has exactly that, prefixed with "do" so it doesn't collide with Java's own try/catch/finally keywords:

Java's try/catch/finally, as a route segment
from("direct:start")
    .doTry()
        .process(riskyProcessor)
        .to("direct:downstream")
    .doCatch(IOException.class, TimeoutException.class)
        .to("log:catch?level=WARN")
    .doFinally()
        .to("log:finally")
    .end();

doCatch takes exception classes the same way onException does — and the same way, it accepts its own onWhen() for a conditional catch. doFinally runs whether or not anything was thrown, same as its Java namesake. And the block has to be closed with end(), or the DSL builder never knows where it stops.

doTry replaces the route's error handler, it doesn't nest inside it

This is the detail that trips people up: for the duration of a doTry block, the route's outer error handler — whatever onException policy or Dead Letter Channel would otherwise apply — is not in effect. doTry…doCatch…doFinally is its own self-contained error handler, scoped to exactly the steps inside it. An outer onException(IOException.class) will not fire for an IOException thrown inside a doTry block unless that block's own doCatch also names it. Reach for onException when a policy should apply broadly; reach for doTry when you want to handle a failure locally, in the middle of one route, without touching the policy that governs everything else.

Route-scoped and global error policies

Where you write an onException clause decides how far it reaches. Declare it at the top of a RouteBuilder's configure() method — before any from(…) — and it applies to every route that same RouteBuilder builds. That's the classic way to get one shared policy without repeating it on each route. It has a scope you should know before relying on it, though: this "global" reach is per RouteBuilder instance. Split your routes across several RouteBuilder classes in the same CamelContext, and a top-level onException in one of them does not automatically cover the others — you'd need a shared base class, or the tool built for exactly this problem: Route Configuration.

A routeConfiguration() is a named, reusable bundle of error-handling policy — onException clauses, an errorHandler(), whatever a group of routes should share — defined once and then attached to specific routes by id:

One named policy, attached to one route by id
routeConfiguration("resilient")
    .onException(Exception.class)
        .maximumRedeliveries(3)
        .handled(true);

from("direct:orders")
    .routeConfigurationId("resilient")
    .to("bean:orderService");

routeConfigurationId isn't limited to one exact name either — it accepts wildcards and regular expressions, so a single configuration can cover every route whose id matches a pattern. The practical difference from a top-of-configure() global clause: instead of one policy for everything, or a hand-copied policy per route, you get named, composable policies — a "resilient" configuration for routes that talk to flaky external systems, a "strict" one for routes where any failure should surface immediately, each attached to exactly the routes that need it.

Business exceptions versus technical exceptions

Here's a distinction that isn't a Camel API at all — it's a design habit worth building into your own exception classes before you write a single onException clause. Not every failure deserves the same response. An order with a missing customer ID is wrong, and it'll still be wrong the fifth time you retry it; an API that timed out because a network blip lasted 200 milliseconds might succeed on the very next attempt. Treating both the same way — either retrying everything, or handling nothing — wastes effort in one direction or the other.

The common answer is to make the difference visible in the type system. A business exception — your own class, something like OrderValidationException — represents an expected domain-rule failure: the input was bad, Camel didn't cause it, and redelivering won't fix it. A technical exception — ConnectException, SQLException, the HttpOperationFailedException from Chapter 19 — represents the environment misbehaving in a way that's often transient. Two onException clauses, one per category, turn that judgment call into policy instead of leaving it to whoever's on call at 2 a.m.:

Two categories of failure, two different endings
onException(OrderValidationException.class)
    .handled(true)
    .to("direct:rejectOrder");

onException(ConnectException.class, SQLException.class)
    .maximumRedeliveries(5)
    .redeliveryDelay(2000)
    .to("direct:deadLetter");

Notice what each clause is quietly saying about the failure it names. The business exception is handled(true) with no redelivery at all — retrying a validation failure just burns time arriving at the same rejection. The technical exceptions get maximumRedeliveries, because the bet there is that the environment recovers before the retries run out. That single default worth remembering from earlier in the chapter still applies: maximumRedeliveries is 0 unless you set it, on any clause, business or technical — declaring the clause is not the same as asking it to retry. The next chapter is where redeliveryDelay, backoff, and the destination named direct:deadLetter above get the depth they deserve; here, the point is just that the classification comes first, and the redelivery numbers follow from it.

A caught exception is a decision point, not just a stack trace: is this failure the kind that retrying fixes, or the kind that retrying only delays admitting? Camel gives you the mechanism — onException, doTry, route configurations. The judgment about which failures belong in which bucket is still yours to make, and making it explicit in your own exception hierarchy is what turns that judgment into something the route can act on automatically.

So what did we actually gain?

A precise picture of what "nothing configured" actually does — DefaultErrorHandler logs and propagates, with no dead-letter destination, which is the honest baseline every policy in this chapter overrides on purpose. onException for a policy scoped to an exception type, matched by walking the cause chain to the closest declared match, with handled, continued, and onWhen as the levers that decide what happens next. doTry…doCatch…doFinally for the same idea shrunk down to a few steps in the middle of a route, with its own private error handler that doesn't answer to the route's outer policy. Global, per-RouteBuilder policies for the simple case, and named Route Configurations for when different groups of routes genuinely need different rules. And a habit, not an API — splitting business exceptions from technical ones — that turns "should this retry?" from a judgment call made under pressure into a decision already written into the route. What's still missing is the machinery on the other side of that decision: how many times to actually retry, how long to wait between attempts, and where a message goes once every attempt has failed. That's the next chapter.
