Making the Order Integration Production-Ready

Chapter 29 ended with a working route and a short, honest list of what it doesn't yet handle: a malformed CSV row, a customer or inventory API that's down or slow, and a file that gets picked up twice. None of those are bugs — they're what "happy path first, harden second" leaves open on purpose. This chapter closes all three, then adds the two things a route needs before anyone should trust it unattended: tests that prove the hardening actually works, and enough observability to see it working (or failing) without reading the code again at 3 a.m.

Four layers, wrapped around the same six stages

Nothing from Chapter 29 gets rewritten. Production-readiness isn't a seventh pipeline stage — it's four concerns that wrap around the existing intake-to-publish pipeline: a duplicate check, a failure policy, a test suite that proves both, and a way to watch it all happen.

Layer 1: making reprocessing safe

Chapter 29's third open edge case was blunt: nothing in the route checks whether an orderId has already been published, so a file re-picked-up after a partial failure — the SFTP connection dropping halfway through the last run, say — republishes every order in it, duplicates included. Chapter 16 already gave you the fix in general form: the Idempotent Consumer pattern, filtering duplicates at the receiving end by checking each message's key against a repository of keys already seen. What's left is deciding exactly where that check goes and what backs it.

The key can't exist any earlier than it does. A raw CSV row-map has no orderId until OrderMapper.fromCsvRow has run and produced a real Order — so the idempotent check belongs right on the direct:toCanonicalOrder seam, immediately after the mapper bean and before anything downstream does real work on the order.

The idempotent consumer, keyed on orderId, right after the mapper produces one
@Bean
JdbcMessageIdRepository orderIdRepository(DataSource dataSource) {
    return new JdbcMessageIdRepository(dataSource, "orderIntegration");
}

from("direct:toCanonicalOrder")
    .routeId("toCanonicalOrder")
    .bean(OrderMapper.class, "fromCsvRow")
    .idempotentConsumer(simple("${body.orderId}"), orderIdRepository)
        .skipDuplicate(false)
        .choice()
            .when(exchangeProperty(Exchange.DUPLICATE_MESSAGE).isEqualTo(true))
                .log(LoggingLevel.WARN, "Duplicate order ${body.orderId} — already processed")
                .to("direct:duplicateOrders")
            .otherwise()
                .to("direct:validateOrder")
        .end()
    .end();

Two choices in that snippet are deliberate, not defaults. skipDuplicate(false) means a caught duplicate doesn't just vanish — it's routed to direct:duplicateOrders where someone can actually see it happened, the same shift from silent-drop to visible-branch Chapter 16 introduced. And the repository is JdbcMessageIdRepository, not MemoryIdempotentRepository: this route's whole reason for adding idempotency is to survive the kind of restart that would also wipe an in-memory map clean, so the history of seen order IDs has to live somewhere a fresh process can still see it — a CAMEL_MESSAGEPROCESSED table keyed on (processorName, messageId), in this case. A Kafka-backed KafkaIdempotentRepository is the equivalent choice if this integration already leans on Kafka more than a relational database.

A dead-lettered order keeps its key — on purpose, with a consequence

removeOnFailure defaults to true: when an order's exchange ends in a genuine, unhandled failure — a bad row rejected by validate(), say — its key comes back out of the repository, so a corrected resend for the same orderId isn't blocked. But that removal only fires on a truly failed exchange. An order that exhausts its redeliveries and lands on a dead letter via handled(true) is, internally, failure-handled rather than failed — so its key stays. That's correct: the idempotency check already did its job once. But it means a human replaying that dead-lettered order later has to go around the idempotent consumer (or clear that one key first) — sending it back through direct:toCanonicalOrder the normal way will have it silently treated as a duplicate of the failure that dead-lettered it.

Layer 2: an error and dead-letter policy for both remaining edge cases

Chapter 29 left two failure points genuinely undecided: a validate() rejection, and a slow or failing call to either the customer or inventory API. They're not the same kind of failure, and Chapter 23's own distinction — business exceptions versus technical ones — is exactly the tool for telling them apart.

A PredicateValidationException is a business rejection: the row is what it is, and retrying it produces the identical rejection every time, so it gets handled(true) with no redelivery at all, and a route to a rejected-orders destination for a human to look at. An HttpOperationFailedException or ConnectException from either enrich() call is different — plausibly transient, worth a few retries with backoff before giving up.

Two onException clauses, plus a route-wide Dead Letter Channel as the catch-all
onException(PredicateValidationException.class)
    .routeId("validationFailurePolicy")
    .handled(true)
    .useOriginalMessage()
    .log(LoggingLevel.WARN, "Rejecting order (validation failed): ${exception.message}")
    .to("direct:rejectedOrders");

onException(ConnectException.class, HttpOperationFailedException.class)
    .maximumRedeliveries(5)
    .redeliveryDelay(2000)
    .backOffMultiplier(2)
    .useExponentialBackOff()
    .useCollisionAvoidance()
    .maximumRedeliveryDelay(30000)
    .retriesExhaustedLogLevel(LoggingLevel.ERROR)
    .handled(true)
    .useOriginalMessage()
    .to("direct:orderDeadLetter");

errorHandler(deadLetterChannel("direct:orderDeadLetter")
    .useOriginalMessage()
    .maximumRedeliveries(2)
    .redeliveryDelay(1000));

The technical clause earns every one of its options. useExponentialBackOff() with a maximumRedeliveryDelay cap keeps a struggling customer or inventory API from being hit with the same retry cadence forever, without letting the delay grow to something absurd either. useCollisionAvoidance() adds jitter, which matters most exactly when it's needed most: if the inventory API has an outage and a hundred in-flight orders all fail their enrich() call within the same second, jitter is what keeps their hundred retries from landing back on that API in one synchronized burst the moment it starts to recover. And the route-wide deadLetterChannel(...) at the bottom isn't decorative — it's what turns "an exception neither onException clause claims" into "still lands on a durable destination" instead of "propagates back to the SFTP consumer thread and potentially aborts whatever's left of the file."

useOriginalMessage() is doing real work in both clauses, not just the route-wide one. By the time an exchange fails deep in enrichment, its body has already been reshaped away from the CSV row the partner actually sent — without it, whoever opens the dead-letter destination to debug a failure sees a half-enriched intermediate shape instead of the order as it originally arrived.

The dead-letter destination itself: durable, inspectable, counted
from("direct:orderDeadLetter")
    .routeId("orderDeadLetter")
    .marshal().json(JsonLibrary.Jackson)
    .to("micrometer:counter:orders.deadlettered")
    .to("kafka:order.integration.dlq?brokers={{kafka.brokers}}");
A dead-letter topic is a queue to inspect, not a trash can to auto-empty

Recall the redelivery chapter's warning: blind, automatic replay of an entire dead-letter destination re-poisons it — a payload-shape problem or a code defect fails identically the second time. This integration's DLQ topic exists so a human (or an automated process, once the fix is verified) can replay a specific order once its root cause is actually understood, not so the whole topic gets fed back in on a timer.

Layer 3: proving both layers actually work

Chapter 25's toolkit was built for exactly this: a duplicate check and a retry-then-dead-letter policy are both things a test should prove, not just trust. Two tests, each reusing a tool from that chapter.

Proving the idempotent consumer: a real duplicate, without a real database
class OrderIdempotencyTest extends CamelTestSupport {

    @Override
    RouteBuilder createRouteBuilder() { return new OrderIntegrationRoute(); }

    @Override
    boolean isUseAdviceWith() { return true; }

    @Test
    void secondCopyOfSameOrderIdIsFiltered() throws Exception {
        context.getRouteDefinition("toCanonicalOrder").adviceWith(context, new AdviceWithRouteBuilder() {
            @Override
            void configure() {
                weaveByType(IdempotentConsumerDefinition.class)
                    .selectFirst()
                    .replace()
                    .idempotentConsumer(simple("${body.orderId}"), MemoryIdempotentRepository.memoryIdempotentRepository(1000))
                        .skipDuplicate(false)
                        .to("mock:afterIdempotent");
            }
        });
        context.start();

        MockEndpoint afterIdempotent = getMockEndpoint("mock:afterIdempotent");
        afterIdempotent.expectedMessageCount(2);

        Order order = new Order("ORD-42", "SKU-1", 3);
        template.sendBody("direct:toCanonicalOrder", order);
        template.sendBody("direct:toCanonicalOrder", order);

        afterIdempotent.assertIsSatisfied();
        Exchange second = afterIdempotent.getExchanges().get(1);
        assertTrue(second.getProperty(Exchange.DUPLICATE_MESSAGE, Boolean.class));
    }
}

weaveByType(IdempotentConsumerDefinition.class) swaps out the durable JdbcMessageIdRepository for an in-memory one, for this test only — a unit test has no business standing up a real database, and doesn't need one to prove the filtering logic. Both sends still reach the mock because skipDuplicate(false) lets the duplicate through; the assertion checks which one got flagged, not just how many arrived.

Proving retry-then-dead-letter, without waiting through real backoff
@Test
void enrichmentFailureRetriesThenDeadLetters() throws Exception {
    context.getRouteDefinition("enrichOrder").adviceWith(context, new AdviceWithRouteBuilder() {
        @Override
        void configure() {
            weaveByType(OnExceptionDefinition.class)
                .selectFirst()
                .replace()
                .onException(ConnectException.class)
                    .maximumRedeliveries(3)
                    .redeliveryDelay(0)
                    .handled(true)
                    .to("mock:orderDeadLetter");
            weaveByToUri("http://customer-api*").replace().to("mock:customerApi");
        }
    });
    context.start();

    MockEndpoint customerApi = getMockEndpoint("mock:customerApi");
    customerApi.whenExchangeReceived(0, e -> { throw new ConnectException("down"); });
    customerApi.whenExchangeReceived(1, e -> { throw new ConnectException("down"); });

    MockEndpoint deadLetter = getMockEndpoint("mock:orderDeadLetter");
    deadLetter.expectedMessageCount(1);

    template.sendBody("direct:enrichOrder", new Order("ORD-43", "SKU-2", 1));

    deadLetter.assertIsSatisfied();
}

redeliveryDelay(0) on the test-only policy is what keeps this a fast unit test instead of a slow one: what's actually under test is that three redeliveries happen and the fourth attempt gives up, not how many real seconds a production backoff schedule would take. Real 2-second, 4-second, 8-second delays belong in production, not in a build that runs on every commit.

Layer 4: seeing it happen in production

Tests prove the hardening works once, under your control. Observability is what proves it's still working at 2 a.m., without anyone re-reading the route. Four pieces, each aimed at a different question an operator actually asks.

What each observability piece answers
QuestionAnswered by
Which stage is failing, and how often?Per-stage routeIds + MicrometerRoutePolicyFactory
How many orders actually shipped today, vs. needed a human?Inline micrometer:counter business metrics
Every log line for this one order — where are they?camel-mdc (orderId) + breadcrumbId
Should this pod stop receiving new files right now?A readiness HealthCheck on the customer/inventory APIs

The first piece is cheap and easy to miss: every code sample so far has given its from(...) block an explicit .routeId(...), and that's not incidental style. Chapter 29's version left most stages unnamed, so Camel auto-assigned generic ids — route2, route3. MicrometerRoutePolicyFactory still produces a full set of per-route counters (camel.exchanges.total, .succeeded, .failed, .failures.handled, .external.redeliveries) and a camel.route.policy duration timer either way — but a dashboard built on route4 tells an operator nothing a dashboard built on enrichOrder doesn't tell them more clearly.

Registering the metrics factory once; every named route gets counters and a timer
@Bean
MicrometerRoutePolicyFactory micrometerRoutePolicyFactory() {
    return new MicrometerRoutePolicyFactory();
}

Those automatic counters measure exchanges through a technical stage, which isn't quite the same thing as orders a business stakeholder cares about. A second, inline metric closes that gap — the dead-letter route above already pushes orders.deadlettered; the publish route gets the same treatment for the success side.

A business-level counter, not just a technical exchange count
from("direct:publishFulfillment")
    .routeId("publishFulfillment")
    .marshal().json(JsonLibrary.Jackson)
    .setHeader(KafkaConstants.KEY, simple("${body[orderId]}"))
    .to("micrometer:counter:orders.fulfilled")
    .to("kafka:order.fulfillment.events?brokers={{kafka.brokers}}");

The third piece ties every log line for one order together. breadcrumbId is already there for free — Camel stamps it on every exchange from the moment the SFTP consumer picks up the file — but it can't carry an orderId that doesn't exist until the mapper has run. camel-mdc fills that gap from toCanonicalOrder onward: the same seam where the idempotent consumer's key becomes available is also where orderId becomes worth promoting into every subsequent log line.

Promoting orderId into MDC, declaratively
camel.mdc.enabled=true
camel.mdc.customHeaders=orderId,tenantId

The fourth piece is the one easiest to get backwards: whether a customer-API or inventory-API outage should count as this integration's own liveness failure or just its readiness. It's readiness. Restarting this route's own pod does nothing to fix an outage in a system it doesn't own — all a liveness failure would accomplish is adding container churn on top of an already degraded dependency. A readiness failure, on the other hand, is exactly the right lever: it tells the orchestrator to stop sending this pod new order files until the dependency recovers on its own.

Readiness, not liveness — a downstream outage shouldn't restart a healthy pod
public class DownstreamOrderApisHealthCheck extends AbstractHealthCheck {
    public DownstreamOrderApisHealthCheck() { super("custom", "order-integration-apis"); }

    @Override
    protected void doCall(HealthCheckResultBuilder builder, Map<String, Object> options) {
        if (customerApiClient.isReachable() && inventoryApiClient.isReachable()) {
            builder.up();
        } else {
            builder.down().message("customer-api or inventory-api unreachable");
        }
    }

    @Override
    public boolean isLiveness() { return false; }
}
The route from Chapter 29 already did the interesting work. Everything in this chapter is the unglamorous other half of shipping it: deciding, on purpose, what happens when a message repeats, when a call fails, and how anyone finds out either one occurred — instead of discovering the answer the first time it happens in production.

So what did we actually gain?

Four layers, none of them new patterns — the Idempotent Consumer from Chapter 16, exception policy and Dead Letter Channel from Chapters 23 and 24, AdviceWith and MockEndpoint from Chapter 25, and camel-mdc, Micrometer, and health checks from Chapter 26, each one aimed at a specific edge case Chapter 29 left open on purpose. What's different is that none of them were optional add-ons bolted onto a finished route — the idempotent consumer had to go exactly on the seam where orderId first exists, the error policy had to distinguish a business rejection from a technical one instead of treating every exception the same, and the tests had to prove both without a real database or a real API. That's the actual difference between an integration that works and one that's production-ready: not more code, but every decision a real system forces made on purpose, before production forces it on you instead.
