Choosing Camel Components

Four chapters back we started reaching for named components without much ceremony — file, http, sql, jms, kafka — on the reasonable assumption that whatever system you needed to talk to, Camel already had something for it. That assumption held up chapter after chapter, and it wasn't luck: the catalog behind those four chapters is hundreds of components deep. This chapter finally opens that catalog up on its own terms. Not to tour more of it — you have plenty of components now — but to answer the question every one of the last four chapters quietly deferred: how do you actually read what a component offers, configure it without hardcoding your life into a URI string, and decide between two components that both, on paper, seem to do the job?

The catalog is data, not a page you skim

"The component catalog" isn't a metaphor for the documentation site — it's a real artifact, camel-catalog, shipped as its own standalone module: a JSON-schema record for every component, data format, language, and EIP in the release, generated straight from annotations in each component's Java source at build time. That's the single source of truth your tools are actually reading. Your IDE's autocomplete on a URI string, the camel-maven-plugin validating endpoint URIs at build time, JBang resolving which dependency a route needs and suggesting options in dev mode — none of them are parsing your route code and guessing. They're all querying the same catalog you could query yourself.

That catalog is large. The Camel Quarkus 3.27.x reference lists on the order of 300 components, with a handful marked deprecated and roughly sixty flagged JVM-only — meaning they run fine on the JVM but have no GraalVM native-image support, a real constraint if your deployment target is Quarkus native. The practical consequence: "search the catalog first" isn't a platitude, it's usually correct. Whatever named external system you're integrating with almost certainly already has a purpose-built component waiting, and the wrong first move is hand-rolling an HTTP or JDBC integration for something the catalog already covers by name.

Reading a URI: path options, query options, and the two-tier split

Every endpoint URI you've written since Chapter 6 has had the same shape: scheme:path?option1=value1&option2=value2. The path segment maps to what the catalog calls the component's path options — positional, context-carrying values, like the destination name in jms:queue:orders. Everything after the ? maps to parameter options, separated by &, exactly like a web URL's query string. That much you've been doing by feel. What the catalog adds is the missing layer underneath: every option belongs to one of two tiers.

Component-level options versus endpoint-level options
Component optionsEndpoint options
Set…once, per component instanceper URI, on each individual endpoint
Inherited by…every endpoint built from that componentonly that one endpoint
Typical contentscredentials, connection URLs, thread-pool sizingthe specifics of one route's use of the system
Further split by…—consumer-only, producer-only, or both
Configured via…application.properties, Component DSL, Java codeURI query string, Endpoint DSL

That third row — consumer-only, producer-only, or both — is worth stopping on, because it's a check you can do before writing a line of route code. A component's doc page tables its options in exactly these three groups. Chapter 19 mentioned in passing that camel-http is producer-only; its doc page makes that unmissable by having no consumer options table at all. Wiring a producer-only component into a from(...) is the kind of mistake that's obvious in hindsight and easy to make in the moment — reading the option tables first is cheaper than finding out at runtime.

Four ways to set the same option

Every option you've set so far has gone straight into a URI query string. That's the most direct route and often the right one, but it's not the only one, and the other three exist precisely because a URI string is a bad place to keep things like credentials or an environment-specific hostname.

Four places the same connectionFactory option could live
// 1. Directly in the URI — fine for values that never change per-environment
from("jms:queue:orders.new?connectionFactory=#jmsCF&concurrentConsumers=5")

// 2. Endpoint DSL — the same option, compiled instead of string-parsed
from(jms("queue:orders.new").connectionFactory("#jmsCF").concurrentConsumers(5))

// 3. A property placeholder, resolved from a properties file, env var, or system property
from("jms:queue:{{orders.queue.name}}?connectionFactory=#jmsCF")

// 4. Component-level, in application.properties — every jms: endpoint inherits it
// camel.component.jms.connection-factory = #jmsCF

Options (2) and (3) are really the same idea in two different places: the Endpoint DSL and Component DSL give you the identical set of options as typed, autocompleting Java method calls instead of a string you're hoping you spelled right, while a property placeholder — {{key}} — lets a value embedded anywhere in a URI string resolve from a .properties file, an OS environment variable, a JVM system property, or, under Spring Boot, application.properties/application.yml directly. Option (4) goes one step further and skips the URI entirely: camel.component.<scheme>.<option> = value in application.properties configures the component, and Spring Boot's Camel starter wires it into the component bean before any route touches it. The URI shrinks down to just what's genuinely specific to that one endpoint.

Component-level defaults, set once, instead of repeated on every URI
# application.properties
camel.component.jms.connection-factory = #jmsCF
camel.component.http.connect-timeout = 5000

# the route URI stays short: only the destination and per-endpoint overrides remain
# from("jms:queue:orders.new?concurrentConsumers=5")
The bean doesn't always need a name at all

A #jmsCF reference is an explicit lookup by name in the Camel Registry. But if you drop the # reference entirely and the option's declared Java type matches exactly one bean of that type currently registered, Camel autowires it in for you — no name needed anywhere. This only works while there's exactly one candidate: register a second ConnectionFactory bean and autowiring stops being able to guess, which is exactly when you go back to an explicit #beanId.

Two syntax traps worth knowing before you hit them

Two small parsing rules explain a disproportionate share of "why won't this URI parse" confusion. First: a value that itself contains a character the URI parser treats as a delimiter — &, =, %, or a literal # that isn't meant as a registry reference — has to be wrapped in RAW(...) so Camel takes it verbatim instead of trying to split it into more options. A password containing & is the case that bites people most often.

A password that would otherwise be misparsed as extra options
sftp:host?username=svc&password=RAW(p@ss&word!)

Second: & is XML's own reserved character, so any URI written inside the XML DSL needs every & escaped as &amp; (jms:queue:orders?requestTimeout=5000&amp;transacted=true). A route that runs unmodified in the Java or YAML DSL — where this rule doesn't apply — can silently fail to parse the moment the same URI is copied into an XML route with the escaping missed. It's not a Camel quirk so much as XML being XML; Camel just inherits it.

Choosing between components that both seem to fit

The harder question isn't syntax, it's judgment: when two or three components can all reach the same system, which one earns the route? You've already lived through this decision three times in this book without it being named. Chapter 21 put camel-jms and camel-activemq side by side: the generic, spec-level component that speaks to any compliant broker, against a thin extension pre-configured for one broker family — whose own documentation, tellingly, just points back at the JMS component for the real reference. Chapter 18 showed file, ftp, and sftp all extending the same GenericFileEndpoint base, differing only in their connection and authentication options. Chapter 20 laid out sql, jdbc, and jpa as three different abstraction levels over the same relational database — rows via Spring's JdbcTemplate, raw JDBC, or JPA entities.

The pattern across all three is the same axis, and it's the first criterion worth applying deliberately rather than by instinct: a narrower, more specific component only earns its place over the generic one underneath it when it genuinely removes configuration burden — broker-specific defaults, connection quirks, sensible presets — not merely because its name matches the vendor you happen to be integrating with. camel-activemq is worth reaching for on an ActiveMQ 5.x broker because it saves you from restating ActiveMQ's own connection defaults; it isn't worth reaching for out of habit once you're actually talking to a different broker through the generic jms component anyway.

Criteria for evaluating a connector, roughly in the order to check them
CriterionWhat to check
Direction supportDoes the component's doc page even have a consumer options table, if you need from(...)? Some components (http) are producer-only.
Generic vs. specificIs there a broader component underneath this one (jms under activemq) that does the same job with the same options, minus a vendor-specific wrapper?
Abstraction levelDo you want rows, raw JDBC, or entities (sql/jdbc/jpa)? Do you want a file's bytes or an object-storage SDK's semantics?
Maturity & supportIs it marked deprecated in the catalog for your target version? (camel-cloud was deprecated in 4.7.0.)
Runtime targetIf deploying to Quarkus native, is the component flagged JVM-only in the catalog? That's a hard blocker, not a style preference.
Configuration shapeDoes the component expose the guarantees this route actually needs — transactions, idempotency, delivery semantics — as first-class options, or would you be bolting them on yourself?
Deprecated and JVM-only are catalog facts, not opinions

Camel Quarkus tracks two flags per component beyond ordinary stable/experimental maturity: deprecated (scheduled for removal — camel-cloud is a real example, deprecated in 4.7.0) and JVM-only (works on the JVM, but has no GraalVM native-image support). Neither shows up as a compile error until you actually try to build a native image or upgrade past the deprecation window. Checking the catalog for your target Camel version and runtime before adopting a component is cheaper than discovering the incompatibility at build or deploy time.

None of this replaces reading a component's actual doc page — the catalog tells you what exists and what shape its options take, not whether it's the right tool for this particular route. But it does turn "which component should I use here?" from a guess into a short, checkable list: can it do the direction I need, is there a more generic version underneath it, what abstraction level am I actually after, and is it still on the maintained, deployable side of the catalog for where this route is going to run.

A URI string is the smallest possible surface for a decision that deserves more thought than a string affords. The catalog behind it — the option tables, the consumer/producer split, the deprecated and JVM-only flags — is where that decision actually gets made. Read the table before you write the URI, not after something breaks.

So what did we actually gain?

A way to read any component in the catalog on its own terms, not just the handful this book named directly. The catalog itself is generated metadata, not prose you have to trust blindly — the same data your IDE and build tooling already query. Every option belongs to one of two tiers, component-level or endpoint-level, and every endpoint-level option is further scoped to consumer, producer, or both, which is a five-second check that heads off the "why doesn't from(...) work with this component" mistake. The same option can move from a hardcoded URI string, to a typed DSL call, to a property placeholder, to a component-level Spring Boot setting — four points on one spectrum from "specific to this route" to "specific to this environment," and you now know which lever to reach for depending on which of those you actually mean. And the generic-versus-specific judgment call that's been implicit since Chapter 18's file family, Chapter 20's three database components, and Chapter 21's JMS-versus-ActiveMQ pairing finally has a name and a short checklist behind it, ready for Part VI's turn from choosing components to making the routes built on them fail well.

Check yourself

  2. You're evaluating a component for a route that must build to a Quarkus native image. Which two catalog flags matter most, and what does each one rule out if present?
  3. A password value containing an & is set directly as a URI query parameter with no special handling. What does Camel do with it, and what should the value have been wrapped in instead?
