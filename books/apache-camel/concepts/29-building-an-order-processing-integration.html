Building an Order Processing Integration

Twenty-eight chapters have each handed you one piece: a polling consumer, a data format, a validation step, an enricher, a router, a producer. This chapter doesn't teach a new one. It builds the thing those pieces were always for — a single, real integration that takes an order from a CSV file sitting on a partner's SFTP server all the way to a fulfillment event on a topic, stopping at every seam a production system actually has: a format it can't trust yet, data it doesn't have yet, a decision it has to make, an event someone else is waiting on. If a piece here looks unfamiliar, it isn't — it's Chapter 18, or 10, or 15, or 12, or 21, wearing an order's clothes.

The shape of this integration

Stripped of Java, the requirement from the top of this chapter reads as six stages, strictly in order: pull the file, turn its rows into orders, refuse to touch a bad one, find out what the order actually needs (a customer's address, an item's stock), decide where it ships from, and tell the rest of the system it's ready to go. Each stage is exactly one EIP or component you've already met.

Step 1: pulling order files off SFTP

A partner drops a CSV of new orders onto an SFTP server on no schedule you control. The consumer that picks it up needs Chapter 18's whole toolkit: a lock strategy that tolerates a server that doesn't write atomically, and host-key checking that isn't switched off.

Order intake — the SFTP polling consumer, reused
from("sftp://partner.example.com:22/orders/incoming"
        + "?username={{sftp.username}}&privateKeyFile={{sftp.key}}"
        + "&knownHostsFile={{sftp.knownHosts}}&strictHostKeyChecking=yes"
        + "&readLock=changed&readLockCheckInterval=2000&readLockTimeout=20000"
        + "&include=.*\\.csv&delay=30000")
    .routeId("orderIntake")
    .log("Picked up order file: ${header.CamelFileName}")
    .to("direct:parseOrders");

readLock=changed is doing real work here: a partner's export job almost never renames a file into place atomically, so Camel checks the file's size and timestamp twice, readLockCheckInterval apart, and only picks it up once both snapshots agree it's stopped growing. strictHostKeyChecking=yes plus an explicit knownHostsFile is the deliberate override of both of SFTP's insecure defaults — leaving either one off trusts whatever key the server happens to present on a given connection.

Step 2: from CSV rows to a canonical Order

A CSV row is not an order — it's a line of text with commas in it, and the very next thing every later stage needs is a real Order, addressed by field name rather than by column position. Chapter 10's CsvDataFormat with useMaps(true) gets you partway: each row unmarshals into a Map<String,String> keyed by the header row, so row.get("OrderId") replaces a fragile row.get(0). A small bean finishes the job, turning that map into the Order every later stage expects.

CsvDataFormat.useMaps(true), then a bean that builds the canonical Order
CsvDataFormat ordersCsv = new CsvDataFormat();
ordersCsv.setUseMaps(true);

from("direct:parseOrders")
    .unmarshal(ordersCsv)
    .split(body())
        .to("direct:toCanonicalOrder");

from("direct:toCanonicalOrder")
    .bean(OrderMapper.class, "fromCsvRow")
    .to("direct:validateOrder");

Notice what split(body()) is doing here: the file unmarshals into one list of row-maps, and split() hands each one down the rest of the pipeline as its own exchange. Everything from here to the Kafka publish at the end operates on one order at a time — a hundred-row file becomes a hundred independent trips through validate, enrich, and route.

Step 3: validating before anything downstream trusts it

Validation belongs here, before enrichment, not after — there's no point spending an HTTP call looking up a customer for an order whose orderId is missing. validate() is the right weight for this check: a boolean predicate over fields the mapper just set, no schema, no annotated class.

A hard gate on the fields everything downstream assumes are present
from("direct:validateOrder")
    .validate(simple("${body.orderId} != null && ${body.sku} != null && ${body.quantity} > 0"))
    .to("direct:enrichOrder");

A failing predicate throws PredicateValidationException immediately — this route doesn't yet say what happens to that exception. That's deliberate: this chapter builds the happy path end to end first, and Chapter 30 is where onException, retries, and a dead-letter destination for exactly this exception get wired in. Building it in two passes — get an order through cleanly, then harden what happens when one can't be — keeps each pass small enough to reason about.

Step 4: two enrichments, chained

A validated order still isn't a shippable one. It has a customer ID, not a shipping address or a country; a SKU, not a confirmation that the item is actually in stock. Two separate external systems answer those two separate questions, so this stage is two enrich() calls, one after the other — not one call trying to do both.

Customer lookup, then inventory lookup, on the same order
from("direct:enrichOrder")
    .enrich("http://customer-api/customers/${body.customerId}", new CustomerEnrichmentStrategy())
    .enrich("http://inventory-api/items/${body.sku}", new InventoryEnrichmentStrategy())
    .to("direct:routeOrder");

Chaining works because of what each AggregationStrategy is asked to return. oldExchange is always the order as it stood before that particular enrich() ran; newExchange is always that call's resource reply. As long as each strategy folds the reply's fields onto the order and returns oldExchange — not a fresh exchange, not newExchange — the second enrich() in the chain sees the first enrichment's result as its own starting point. Two calls compose with nothing extra wired between them.

CustomerEnrichmentStrategy — read old and new, mutate and return old
public class CustomerEnrichmentStrategy implements AggregationStrategy {
    public Exchange aggregate(Exchange oldExchange, Exchange newExchange) {
        Order order = oldExchange.getMessage().getBody(Order.class);
        Customer customer = newExchange.getMessage().getBody(Customer.class);
        order.setCustomerCountry(customer.getCountry());
        order.setShippingAddress(customer.getAddress());
        oldExchange.getMessage().setBody(order);
        return oldExchange;
    }
}
Drop the AggregationStrategy from either call and the chain breaks silently

An enrich() with no second argument doesn't merge — it replaces the whole body with the resource's reply. Omit it from the customer lookup here and the exchange going into the inventory lookup is a bare Customer, not an order; the inventory API gets called with whatever ${body.sku} evaluates to on a Customer, which is nothing. Nothing throws. The route just quietly stops being about an order midway through.

Step 5: routing domestic vs international

Only now — after enrichment, not before — does the order actually know where the customer is. That ordering matters: a choice() placed before the enrich calls would be routing on a field that hasn't been set yet. Once customerCountry is real, deriving an OrderType header and branching on it is exactly Chapter 12's pattern.

Content-based routing, keyed on a field the enrichment stage just filled in
from("direct:routeOrder")
    .setHeader("OrderType", simple("${body.customerCountry} == 'US' ? 'DOMESTIC' : 'INTERNATIONAL'"))
    .choice()
        .when(header("OrderType").isEqualTo("DOMESTIC"))
            .to("direct:domesticFulfillment")
        .when(header("OrderType").isEqualTo("INTERNATIONAL"))
            .to("direct:internationalFulfillment")
        .otherwise()
            .to("direct:manualReview")
    .end();
otherwise() is what makes this choice() safe to ship

Recall Chapter 12: a choice() with no matching when() and no otherwise() does nothing — no branch runs, no exception is thrown, the exchange falls through to whatever follows .end(). Here that would mean an order whose customerCountry came back blank, or some third value nobody planned for, is simply never fulfilled and never flagged. Routing the unmatched case to direct:manualReview instead of leaving otherwise() off turns a silent gap into a queue someone actually watches.

Step 6: publishing the fulfillment event

Domestic and international orders diverge only in where they're fulfilled from — both need the same last step, so both branches converge on one direct: endpoint rather than duplicating the publish logic. Marshalling to JSON and keying the Kafka message on orderId are both Chapter 21 moves, aimed at this order specifically.

Two branches, one publish step, keyed for per-order ordering
from("direct:domesticFulfillment")
    .setHeader("FulfillmentCenter", constant("US-EAST"))
    .to("direct:publishFulfillment");

from("direct:internationalFulfillment")
    .setHeader("FulfillmentCenter", constant("INTL-HUB"))
    .to("direct:publishFulfillment");

from("direct:publishFulfillment")
    .marshal().json(JsonLibrary.Jackson)
    .setHeader(KafkaConstants.KEY, simple("${body[orderId]}"))
    .to("kafka:order.fulfillment.events?brokers={{kafka.brokers}}");

Keying on orderId isn't cosmetic. Kafka sends every message with the same key to the same partition, and a partition is the only unit Kafka guarantees ordering within — so every event this integration ever publishes about one order lands in the order it was published, and a consumer reading that partition sees them that way too. Leave the key off and Camel's default partitioner scatters events for the same order across partitions, with no guarantee about which one a consumer reads first.

Nothing in this route is new. What's new is that a bad row, a slow API, and an unrouted order all had to be decided somewhere — and building the whole pipeline at once is what forces those decisions to actually get made, instead of staying implicit.

Edge cases this route already has to answer for

Wiring six familiar patterns together surfaces failure modes none of them show on their own:

  • A malformed CSV row. validate() catches a missing field, but a row with the wrong number of columns fails earlier, inside unmarshal() itself — before the mapper bean, and before orderId exists to log. That failure needs its own handling, not the same predicate validate() checks downstream.
  • A slow or failing enrichment call. camel-http's throwExceptionOnFailure default (true) means a 4xx or 5xx from either API raises an HttpOperationFailedException rather than quietly aggregating an error body into the order — the failure is visible, but this chapter hasn't decided yet whether it's retried, defaulted, or dead-lettered.
  • Reprocessing the same file. Nothing in this route yet checks whether an orderId has already been published. A file re-picked-up after a partial failure — the SFTP connection dropped halfway through the last run, say — republishes every order in it, duplicates included.

None of these are bugs in what's built so far — they're exactly what "happy path first, harden second" leaves open on purpose. Chapter 30 closes all three: idempotency to make reprocessing safe, an error-handling policy for the two failure points above, and the tests and observability that let you trust the answer without re-reading the route.

So what did we actually gain?

A working integration, first — SFTP intake through CSV parsing, validation, two chained enrichments, content-based routing, and a keyed Kafka publish, all six stages wired into one order's actual journey. But the bigger gain is what building it end to end revealed that no single chapter could: enrichment has to run before you can route on what it fills in, two enrich() calls only chain cleanly if every strategy returns oldExchange, and an otherwise() branch is the difference between an edge case you handle and one you never even see. Chapter 30 takes this same route and asks the harder question — not "does it work," but "does it keep working when a file repeats, an API times out, or a bad row shows up at 3 a.m."

Check yourself

  1. The choice() in Step 5 reads ${body.customerCountry}. What breaks if that choice() is moved to run before the two enrich() calls instead of after, and why doesn't Camel warn you at build time?
  2. Both enrichment strategies in Step 4 must return oldExchange, not newExchange, for the chain to work. Trace through what the second enrich() call's oldExchange would actually contain if CustomerEnrichmentStrategy returned newExchange instead.
  3. Step 6 keys the Kafka message on orderId. Suppose two different orders, published moments apart, need to be processed in the exact order they were published, regardless of which order they belong to. Does keying on orderId still deliver that guarantee? What would you key on instead, and what do you give up by doing that?
