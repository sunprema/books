Content-Based Routing

Chapter 11 ended with a promise: once a message is validated and translated into your canonical shape, every route behind that boundary gets to stop asking whether it can trust what's in the message. This chapter is where that trust starts paying off. A canonical Order now needs to go somewhere — and which somewhere depends on what's actually inside it. A domestic order and an international one need different handling. A zero-dollar test order needs to never reach fulfillment at all. Deciding a message's path by looking at the message is one of the oldest ideas in integration, and Camel gives you three increasingly specific tools for it: a branching if-else-if-else, a one-predicate gatekeeper, and a way to compute a destination that was never written down as a branch at all.

Still a Message Router, just one with content in mind

Chapter 03 introduced the Message Router as one of the EIP catalog's six root patterns: something that reads a message from a channel and decides, without changing it, which output channel it goes to. Everything in this chapter is that same idea, specialized two different ways. The Content-Based Router picks one of several named branches based on what the message contains. The Message Filter is the router's simplest possible case: it has exactly one branch, and the alternative to taking it isn't another destination — it's nowhere at all. Camel gives the first a name you'll write constantly, choice(), and the second an equally short one, filter().

choice(), when(), otherwise() — an if-else-if-else for messages

Here's the shape you'll write more than almost anything else in a Camel route. It should look familiar even before we explain it, because it's deliberately built to:

Route a canonical order by its type header
from("direct:orders")
    .choice()
        .when(header("OrderType").isEqualTo("DOMESTIC"))
            .to("direct:domesticOrders")
        .when(header("OrderType").isEqualTo("INTERNATIONAL"))
            .to("direct:internationalOrders")
        .otherwise()
            .to("direct:unroutedOrders")
    .end();

when() takes any Predicate or Expression, and just like the filter() and Simple-language predicates Chapters 03 and 09 already showed you, a bare string is parsed as Simple by default — so header("OrderType").isEqualTo("DOMESTIC") and simple("${header.OrderType} == 'DOMESTIC'") are two spellings of the same check. Camel walks the when() clauses in the order you wrote them and stops at the first one whose predicate is true. Not "whichever matches best." Not "every branch that matches." The first true predicate, full stop — exactly the semantics of a Java if / else if chain, which is precisely the mental model you should reach for.

Branch order is part of the logic, not a formatting choice

Because evaluation short-circuits at the first match, a broader predicate placed before a narrower one will quietly steal every message the narrower branch was meant to catch. If header("OrderType").isNotNull() sits above header("OrderType").isEqualTo("INTERNATIONAL"), the international branch is dead code — every order with a non-null OrderType already matched the first when(). Camel won't warn you; it will just route every message exactly the way you told it to, which isn't always the way you meant.

When nothing matches: otherwise() is optional, and that's the trap

otherwise() reads like the mandatory else at the end of the ladder, but Camel doesn't require it. Drop it, and a message that fails every when() predicate doesn't error, doesn't log, doesn't do anything you'd notice: the choice() block simply completes having run none of its branches, and the exchange falls through to whatever comes after .end() — which, if nothing else follows, means the route just ends there. Compare that to Chapter 11's validate(), which throws the instant its predicate is false. An unmatched choice() is the quiet cousin of a failed validate(): just as silent as filter() dropping a message, but far less obvious, because nothing about choice()'s name suggests it might do nothing at all.

If every message should hit some branch, say so with otherwise()

An otherwise() that routes to a dead-letter-style destination — even just a log and a holding queue — turns "we silently dropped it" into "we can see exactly which messages didn't match anything, and why." It costs one more branch to write and saves you from finding the gap in production instead of in review.

Closing the block: end() and its Java-only sibling, endChoice()

Every choice() block in the Java DSL is closed with .end(), the same terminator you'll use to close a splitter or a multicast later in this book. It exists because Java's DSL is a chain of method calls, not the naturally nested structure YAML or XML give you for free — and that has one sharp edge worth knowing about before it surprises you. If you nest another EIP that itself needs a closing call — loadBalance() is the classic example — directly inside a when() or otherwise(), a plain .end() closes the wrong scope, and the compiler loses track of which builder you're chaining onto next. Camel's answer is .endChoice(): it means specifically "pop back out to the Choice, not whatever I just nested inside it." You won't need it for the choice blocks in this chapter, but the first time a nested EIP inside a when() refuses to compile, this is why.

Filter: a Content-Based Router with exactly one branch, and no else

Sometimes you don't need to choose between destinations — you need to decide whether a message continues at all. That's filter(): one predicate, no when(), no otherwise(). A message whose predicate is true keeps going down the route past the filter. A message whose predicate is false is dropped exactly where it stands — not routed anywhere, not logged, not an error. It's the EIP catalog's Message Filter, and Hohpe and Woolf describe it as exactly this: a Message Router specialized to discard what doesn't meet a criterion, rather than routing it somewhere else.

Drop zero-and-negative-total orders before they reach fulfillment
from("direct:orders")
    .filter(simple("${header.OrderTotal} > 0"))
        .to("direct:validOrders");
// an order with OrderTotal <= 0 is dropped here; nothing after filter() runs for it
filter() drops silently; validate() throws — don't reach for the wrong one

Chapter 11's validate() and this chapter's filter() run the exact same kind of predicate, and it's an easy slip to write one where you meant the other. filter() says "skip this one, no big deal" — the right choice for messages that are legitimately not relevant to this route. validate() says "this one is wrong, and something needs to know" — the right choice for messages that should never have gotten this far. Swap them and a genuinely broken order either vanishes with no trace, or a merely irrelevant one starts triggering your exception handling.

You could write the same behavior with choice() — a single when(), an otherwise() that calls .stop(), an .end() — and it would work. But that's three DSL calls to say what filter() says in one, and the extra ceremony buys you nothing choice() wasn't built for. Reach for filter() whenever the question is genuinely "continue, or don't" with no second destination in play; reach for choice() the moment there's more than one place a matching message could go.

Dynamic routing decisions: when the destination isn't one of a few branches

Everything so far assumes the set of destinations is small and known while you're writing the route — DOMESTIC, INTERNATIONAL, otherwise. That assumption holds for a lot of routing, but not all of it. Picture routing orders to a per-region queue where "region" is one of dozens of values a config table owns, not three you'd enumerate in a when() ladder. Writing forty when() branches to cover forty regions is technically possible and a maintenance liability the moment region forty-one ships. Camel's answer is toD() — Dynamic To — which doesn't pick among branches you wrote; it computes the destination URI itself, per exchange, from an expression evaluated against the message.

The destination queue name comes from the message, not the route source
from("direct:orders")
    .toD("jms:queue:orders.${header.region}?cacheSize=20");

The expression defaults to Simple, same as everywhere else in this book, so ${header.region} is evaluated fresh for every exchange and spliced into the URI before Camel resolves it to an endpoint. Camel caches the resolved endpoint and producer per distinct URI it computes, so a region that recurs doesn't pay endpoint-resolution cost on every message — that's what cacheSize controls: how many distinct resolved destinations stay cached (0 is the default size, a negative number turns caching off entirely).

An expression with unbounded cardinality grows the cache without bound

${header.region} is safe because regions are a small, bounded set. toD("jms:queue:orders.${header.customerId}") is a different story — if customerId is effectively unlimited, every new customer mints a new cached endpoint and producer that never gets evicted at the default size. If a toD() expression's possible values aren't bounded, set cacheSize deliberately rather than trusting the default.

Don't reach for toD() reflexively, though. If your destinations really are DOMESTIC, INTERNATIONAL, and otherwise, choice() says so directly in the route and a reader can see every branch without running the code. Save toD() for the cases where writing out every branch would mean writing out a table that lives somewhere else anyway.

choice() picks among branches you already know about. filter() decides whether a message is worth routing at all. toD() computes a destination that was never a branch in the first place. Three tools, one question underneath all of them: given this message, where does it go next?

So what did we actually gain?

A vocabulary for the question every integration eventually has to answer: given this message, where does it go? choice()/when()/otherwise() for a small, known set of destinations, evaluated top to bottom with the first match winning. filter() for the narrower question of whether a message continues at all, with no second destination to name. toD() for the case where the destination itself has to be computed, because writing it out as a branch would just be copying a table you don't own. All three read the message to decide, none of them change it — routing and transformation stay separate concerns, exactly as Chapter 03's Message Router promised. The next two chapters put that same "read the message, decide what happens next" instinct to work on harder problems: Chapter 13 splits one message into many and puts the pieces back together, and Chapter 14 sends one message to more than one destination at once.

Check yourself

  1. A choice() block has .when(header("Status").isNotNull()) above .when(header("Status").isEqualTo("CANCELLED")). What happens to a cancelled order, and why does reordering the two when() clauses fix it?
  2. A route's choice() has no otherwise(). A message arrives that matches no when(). What observably happens to it, and how is that different from what filter() would do to the same message?
  3. You're deciding between choice() with ten when() branches and a single toD() call for the same routing problem. What about the destinations would make you pick one over the other, and what operational risk does the toD() choice carry that choice() doesn't?
