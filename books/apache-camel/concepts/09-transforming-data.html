Transforming Data

Last chapter opened the Exchange and showed you exactly what's inside it — body, headers, properties, pattern, exception — but it didn't change a single one of them. This chapter does. Camel gives you three ways to transform a message, and they aren't interchangeable stylistic choices: they're three different weights of tool, and picking the wrong one is how a two-line change turns into forty lines of Java nobody wants to test. We'll also come back to type conversion from Chapter 08 and finally open the box it was hiding: where those converters actually come from, and how to write your own.

Three tools, one job, escalating weight

Every transformation in a Camel route is one of three shapes. A Simple expression is the lightest: a short string evaluated inline by the DSL, no Java class of its own. A bean method is one step heavier: an ordinary Java method, already written, that Camel calls and feeds the message into. A Processor is the heaviest and most capable: a full block of Java with the entire Exchange in hand — body, headers, properties, exception, all of it. None of the three is "correct." The skill is reaching for the lightest one that actually does the job, and only climbing the stack when the job genuinely needs it.

Which tool, and why
ToolBest forUnit-testable on its own?
Simple expressiona short inline change to the current body/headernot really — it only exists inside a route
Bean methodreusable logic that doesn't need the Exchange itselfyes, as a plain Java method
Processorlogic that needs properties, the exception, or the patternyes, but the test has to build an Exchange

setBody, transform, and setHeader

The lightest tier is a DSL step evaluating an expression and writing the result somewhere specific. setBody(expression) replaces the current message's body. setHeader(name, expression) does the same for one header, leaving the body untouched. filter(predicate), which you already met in Chapter 03, is the boolean-valued cousin of the same idea: it doesn't replace anything, it decides whether the exchange continues at all.

Three declarative steps, one route
from("jms:queue:orders.raw")
    .setHeader("OrderTotal", simple("${body.total}"))
    .filter(simple("${header.OrderTotal} > 0"))
    .setBody(simple("Order ${header.OrderId} total ${header.OrderTotal}"))
    .to("jms:queue:orders.billable");

You'll also see transform(expression) in older code and in Camel's own EIP catalog, sitting right next to setBody and looking like it does the same thing — because it does. Historically the two were documented as operating on different halves of an Exchange that no longer exists in the form the docs describe.

transform() vs. setBody() — a distinction that outlived its Exchange

Back when Camel modeled an Exchange as a separate In message and Out message, transform() was documented as always writing to the Out message. Chapter 08 already told you that model is gone: modern Camel has one current message, reached through getMessage(), and both transform() and setBody() replace it the same way. In practice, reach for setBody() — it's the name people actually search for. transform() exists mainly because it's the DSL keyword named after the Message Translator pattern it implements.

One more declarative step is worth knowing for the narrowest case of all: changing the body's Java type without computing anything new. convertBodyTo(Class) hands the current body straight to the type-converter registry and writes back whatever comes out — shorter than a .process() lambda that does the exact same getBody(Class) call by hand, and more honest about what it's actually doing.

The narrow case: only the type changes
from("jms:queue:orders.raw")
    .convertBodyTo(String.class)
    .to("jms:queue:orders.text");

The Simple language, precisely

Every simple(...) string above is Camel's own expression and predicate language — the same one that's been quietly doing work since Chapter 05's log("Copying ${header.CamelFileName}"). It mixes plain literal text with ${…} markers freely: anything outside the braces is copied through unchanged, and each ${…} block is evaluated and substituted in place. That's the whole mixing rule.

Simple's built-in functions, the ones you'll reach for constantly
ExpressionReads
${body}the current message body
${header.name}a header (case-insensitive, Chapter 08)
${exchangeProperty.name}an exchange property — also ${exchangeProperty[name]}
${body.getAddress} / ${body.address}a getter on a POJO body — ${body.address.city} chains

As a predicate language — used inside filter(), choice()/when(), and anywhere else a route needs a true/false answer — Simple adds comparison and string operators: ==, >, <, >=, <=, !=, contains, in, is, range, regex, among others. The left side must be a ${…} expression; the right side can be a string literal in single quotes, a constant, null, or another ${…} expression. Camel type-converts the right side to match the left side automatically — which is why ${header.OrderTotal} > 100 just works even when a header arriving over JMS or HTTP is a String underneath.

Two ways Simple predicates fail silently

Simple requires spaces around the operator — ${header.Total}>100 doesn't parse the way it looks like it should; write ${header.Total} > 100. And an unquoted string on the right side is treated as another expression, not a literal — write 'US', not US. Neither mistake is a compile error, because Simple is only checked when the route runs, not by javac.

This is also the answer to a question Chapters 03 and 07 left open: the fluent Java builder you saw for Content-Based Router — header("CamelOrderCountry").isEqualTo("US") — and an equivalent Simple string, simple("${header.CamelOrderCountry} == 'US'"), are two spellings of the same predicate. The fluent builder is type-checked and refactorable; the Simple string is shorter, and it's the only option in the YAML and XML DSLs, which have no Java method chain to call.

Calling out to a bean

The middle tier hands a message to an ordinary Java object already sitting in Camel's registry — a Spring or Quarkus bean, or one registered by hand. .bean("pricingService", "quote") (or the endpoint form, bean:pricingService?method=quote) converts the current body to whatever type the chosen method's parameter declares, invokes it, and replaces the body with whatever the method returns. Nothing about the method itself imports Camel.

A plain Java method, called from a route
public class PricingService {
    public Quote quote(Order order) {
        return new Quote(order.getId(), order.getTotal() * 1.08);
    }
}

// route:
from("jms:queue:orders.validated")
    .bean("pricingService", "quote")
    .to("jms:queue:orders.quoted");

When you don't name a method explicitly, Camel still has to pick one, and it does so in a fixed order — worth knowing precisely, because "which method actually ran" is a surprisingly common source of confusion once a bean grows a second overload.

How Camel picks a bean method, in order
#Rule
1an explicit method name in the DSL — .bean("svc", "quote")
2a CamelBeanMethodName header set on the message
3a method the bean itself marks with Camel's @Handler annotation
4best-effort matching of the body's type against the bean's public methods

Rule 4 works right up until a second overload is added that also happens to accept a compatible type — at which point which method runs can silently change out from under you. Naming the method explicitly (rule 1) or marking it @Handler (rule 3) removes the ambiguity for good. Overloaded methods can also be disambiguated by qualifying parameter types directly in the URI — bean:foo?method=bar(String,int) — and literal parameter values can be supplied the same way for a method that doesn't need the message body at all.

A bean method's return value always wins

The bean component replaces the current body with whatever the invoked method returns — including a void method's null. A transformation method that logs something and returns nothing, called where a route still expects to read the body afterward, quietly wipes it out. If a method's job is a side effect, not a transformation, that's what a Processor or a wiretap is for — not a bean call sitting in the middle of the pipeline.

The practical case for pulling logic into a bean method instead of an inline .process() lambda is exactly this testability: a method with no Exchange in its signature can be called directly from a plain unit test, no route or mock Exchange required, and the same code is what the route calls in production.

Type conversion, revisited: writing your own

Chapter 08 showed you the consumer side of type conversion: getBody(Class) asks the type-converter registry for a converter and applies it on the spot. What it didn't show you is where those converters come from. At startup, Camel scans the classpath for META-INF/services/org/apache/camel/TypeConverterLoader files — every Camel component JAR on the classpath contributes one — and loads whatever converters they register. That's the entire reason a conversion between, say, a String and an InputStream just works with no configuration: camel-core and its components already ship the converters for it.

Writing your own is ordinary Java plus two annotations. Annotate the class @Converter, and annotate each conversion method the same way — a static method taking the from-type (and, optionally, a second Exchange parameter) and returning the to-type.

A custom type converter
@Converter
public class OrderConverters {
    @Converter
    public static Order fromJson(String json, Exchange exchange) {
        return new ObjectMapper().readValue(json, Order.class);
    }
}

Once that class is on the classpath, getBody(Order.class) can turn a JSON-string body into an Order with no route-level code change at all — the conversion becomes part of the registry, available to every route in the application, not just the one that needed it first. Adding @Converter(generateLoader = true) at the class level, together with Camel's component packaging build plugin, generates the TypeConverterLoader file at build time instead of relying on reflective scanning — faster startup, and the recommended path for new code. A separate method annotated @FallbackConverter can also be registered to run only after every regular converter has already failed to produce the requested type.

Every transformation in this book is one of three shapes underneath: an expression, a method call, or a block of Java. Knowing all three isn't the skill. Reaching for the lightest one that actually fits — and only climbing the stack when the job genuinely needs it — is.

So what did we actually gain?

A vocabulary for every transformation you'll write from here on, and a rule for choosing among them: Simple for a short inline change, a bean for reusable logic that doesn't need the Exchange, a Processor for logic that does. Plus the other half of Chapter 08's type conversion — not just how to ask for a converted type, but where the converter that answers actually came from, and how to add one of your own. Next chapter puts all of this to work on a specific, very common shape of transformation: whole message formats — JSON, XML, CSV — marshalled and unmarshalled at the edge of a route, using exactly the type-converter machinery this chapter just opened up.
