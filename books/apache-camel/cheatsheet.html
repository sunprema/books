Cheatsheet

Apache Camel is a lightweight, embeddable routing and mediation library, not a server: you write routes in a DSL that implement the Enterprise Integration Patterns catalog, and Camel runs them inside your own Spring Boot or Quarkus application. A CamelContext holds every route; a Route is one from() endpoint plus a chain of to()/EIP steps; an Exchange carries one execution's Message (body and headers) plus its own property map. Roughly 300 components share one URI model (scheme:path?option=value), so trading file: for sftp: or kafka: is a one-line change, not a rewrite. Everything below assumes the thirty-one chapters before it — this page is for looking things up, not for reading start to finish.

The route, in one shape

Every route starts here — a RouteBuilder, overriding configure()
public class HeartbeatRoute extends RouteBuilder {
    @Override
    public void configure() {
        from("timer:heartbeat?period=5000")
            .routeId("heartbeat")
            .log("Tick ${exchangeProperty.CamelTimerCounter}");
    }
}

Spring Boot auto-detects every bean that extends RouteBuilder and adds its routes to the one running CamelContext — no manual addRoutes(). Any DSL (Java, YAML, XML) compiles down to the same internal route model; the DSL only changes how a route is authored, never what it does at runtime.

CamelContext
the runtime container — wires every route, component, and endpoint together and starts them.
Component
the factory behind a URI scheme (the file component, the jms component…).
Endpoint
one concrete configured instance a component produces — file:incoming?noop=true.
Processor
the single-method interface (process(Exchange)) every DSL step compiles down to.
Exchange
the envelope for one route execution: a Message, a separate exchange-scoped property map, an ExchangePattern (InOnly/InOut), and — on failure — an exception.
direct: vs seda:
direct: is synchronous, same thread, no queue. seda: is an in-VM BlockingQueue handed to a separate consumer thread — bounded at size=1000 by default, not unbounded.

Core DSL, by task

Routing & filtering

from("direct:orders")
    .choice()
        .when(header("OrderType").isEqualTo("DOMESTIC"))
            .to("direct:domesticOrders")
        .otherwise()
            .to("direct:unroutedOrders")
    .end();

from("direct:orders")
    .filter(simple("${header.OrderTotal} > 0"))
        .to("direct:validOrders");

from("direct:orders")
    .toD("jms:queue:orders.${header.region}?cacheSize=20");

choice() is first-match-wins, top to bottom; no otherwise() means an unmatched message falls through silently — not an error. filter() drops silently on false, no "else". toD() computes the destination per exchange (Simple by default).

Splitting & aggregating

from("file:orders/inbound")
    .split(bodyAs(String.class).tokenize("\n"))
        .to("direct:oneOrderLine");

from("direct:orderLines")
    .aggregate(header("orderId"), new MyOrderAggregationStrategy())
        .completionSize(header("lineCount"))
        .completionTimeout(5000)
        .to("direct:completeOrder")
    .end();

split() defaults to non-streaming (materializes the whole list first); .streaming() processes on demand. No AggregationStrategy anywhere in this family — split, aggregate, multicast, enrich — means "keep only the last part, discard the rest," not an error. completionInterval (fixed sweep) cannot combine with completionTimeout (resets per arrival). Default AggregationRepository is in-memory and lost on restart.

Fan-out

from("direct:orderConfirmed")
    .multicast(new OrderFanOutAggregationStrategy())
        .parallelProcessing()
        .stopOnException()
        .to("jms:queue:audit.orders")
        .to("kafka:analytics.order-events")
    .end();

from("jms:queue:orders.validated")
    .wireTap("direct:auditLog")
    .to("direct:processOrder");

multicast() is a fixed destination set baked into the route; recipientList(expr[, delimiter]) computes destinations per message (default delimiter comma). Both default to calling-thread sequential; .parallelProcessing() changes how the parts run, not whether the caller waits — it still blocks until every branch finishes. stopOnException() is not the default. wireTap copies the exchange, forces InOnly, and runs async on a thread pool that falls back to CallerRuns when exhausted — under load an "async" tap quietly becomes a blocking call, and its failures are invisible to the primary route either way.

Enrichment

.enrich("direct:customerLookup", new CustomerEnrichmentStrategy());

.pollEnrich("file:inbox?fileName=data.txt", 10000, aggregationStrategy);

enrich() makes an active producer (request-reply) call; pollEnrich() pulls from a Polling Consumer. pollEnrich's timeout defaults to -1 (blocks indefinitely) — always set one explicitly. aggregateOnException defaults to false: a failed enrichment call skips the strategy entirely and just propagates the failure. In the strategy, newExchange is null on a pollEnrich timeout.

Error handling

onException(ValidationException.class)
    .handled(true)
    .log(LoggingLevel.WARN, "Rejecting: ${exception.message}")
    .to("direct:rejectOrder");

from("direct:start")
    .doTry()
        .to("direct:downstream")
    .doCatch(IOException.class)
        .to("log:catch?level=WARN")
    .doFinally()
        .to("log:finally")
    .end();

onException() matches by walking the cause chain innermost-out; the more specific declared type wins regardless of declaration order. Default handled(false) still rethrows to the caller. Read the failure via exchange.getProperty(Exchange.EXCEPTION_CAUGHT, Exception.class) — getException() is null there. doTry/doCatch/doFinally is its own private error handler for that block only; the route's outer Dead Letter Channel does not reach inside it. Attach a shared policy to many routes with routeConfiguration("id").onException(...) plus .routeConfigurationId("id") (accepts an exact id, a wildcard, or a regex, and comma-separated multiples).

Reliability

.idempotentConsumer(header("OrderId"), repository);

.resequence(header("seqnum")).batch().batchSize(200);

.throttle(5).timePeriodMillis(1000);

idempotentConsumer: eager defaults true (key added before processing completes, catches concurrent dupes); removeOnFailure defaults true, but a handled(true) dead-lettered exchange is "failure-handled," not "failed," so the key is not removed — a later replay reads as a duplicate. resequence().batch() only sorts within one batch; a straggler that arrives after its batch shipped is never retroactively reordered. throttle() blocks the calling thread unless .asyncDelayed() is set.

Data, transformation & validation

.setHeader("OrderTotal", simple("${body.total}"))
.setBody(simple("Order ${header.OrderId}"))
.bean("pricingService", "quote")
.unmarshal().json(JsonLibrary.Jackson, Order.class)
.validate(header("OrderId").isNotNull())

Simple predicate operators: == > < >= <= != contains in is range regex — spaces required around the operator, string literals need single quotes. Bean method resolution: explicit DSL name → CamelBeanMethodName header → @Handler → best-effort type match; the return value always replaces the body, even void (→ null). Leaving JSON unmarshalType unset gives a generic Map instead of failing fast — a ClassCastException surfaces downstream instead of at the unmarshal step. validate() throws on false; unlike filter(), it never drops silently.

Templates, naming & transactions

routeTemplate("partnerIntake")
    .templateParameter("remoteDir")
    .from("sftp:{{partner.host}}?fileName={{remoteDir}}/*.csv")
        .to("direct:toCanonicalOrder");

templatedRoute("partnerIntake")
    .routeId("intake-acme")
    .prefixId("acme")
    .parameter("remoteDir", "/acme/orders");

{{name}} inside a template; {{?name}} makes it optional (an unset option is omitted, not literal null). A hardcoded node id inside the template throws a duplicate-id error on the second instantiation — prefixId(...) is what avoids it. transacted() must be the first step after from() and only covers the calling thread — hopping to seda: breaks it.

Redelivery & dead letter

errorHandler(deadLetterChannel("jms:queue:orders.dead")
    .useOriginalMessage()
    .maximumRedeliveries(5)
    .useExponentialBackOff()
    .backOffMultiplier(2)
    .maximumRedeliveryDelay(30000)
    .retriesExhaustedLogLevel(LoggingLevel.ERROR));
OptionDefault
maximumRedeliveries0 — no retries unless set
redeliveryDelay1000ms, fixed
backOffMultiplier2.0, needs useExponentialBackOff(true)
maximumRedeliveryDelay60000ms cap on the backoff
retriesExhaustedLogLevel / retryAttemptedLogLevelERROR / DEBUG

Business exceptions (OrderValidationException) get handled(true), no redelivery. Technical exceptions (IOException, SQLException, ConnectException) get redelivery + backoff, then dead-letter. delayPattern replaces the whole delay calculation and isn't composable with the other backoff options. Blind auto-replay of a whole dead-letter queue re-poisons it when the failure was a payload or code defect, not a transient outage.

Gotchas

Routing & messaging

No otherwise() → unmatched message falls through, no error. split()/multicast()/recipientList()/enrich() with no strategy keeps only the last result, silently. .parallelProcessing() doesn't stop the caller from blocking until every part finishes. Wire Tap failures are invisible to the primary route. Kafka autoCommitEnable defaults true, so a mid-processing failure after commit means no redelivery. JMS with no prefix is a queue, not a topic.

Files, data & databases

File consumer's default post-processing moves a file into a hidden .camel directory, not leaving it alone or deleting it. readLock defaults to none. SFTP strictHostKeyChecking defaults to no — a real MITM exposure. aws2-s3 deleteAfterRead and autoCreateBucket are both on by default. Unset JSON unmarshalType gives a generic Map instead of failing fast. SQL row counts land on a header, body is null. jpa's consumeDelete deletes on poll, before downstream confirms success.

Errors, config & operations

onException() doesn't retry by default (maximumRedeliveries=0). doTry/doCatch/doFinally is its own private error handler — the outer Dead Letter Channel doesn't apply inside it. A handled(true) dead-lettered exchange is "failure-handled," not "failed," so an idempotent consumer's key stays and a later replay reads as a duplicate. {{?key}} falls back to the component's own default, not a value you chose. Sending SIGKILL (or too short a termination grace period) skips Camel's graceful shutdown entirely — in-flight exchanges are simply abandoned. Default fail-fast RouteController means one bad route at startup takes the whole app down; SupervisingRouteController isolates it. MemoryIdempotentRepository loses all history on restart and isn't shared across instances.

Naming, VETRO & the rest

VETRO — the shape check for one route

Validate, Enrich, Transform, Route, Operate. A route doing meaningfully more than that — real business decisions, long-lived state — has quietly stopped being an integration and started being an application that happens to live inside one. That's the moment to extract a bean, not keep growing the route.

Testing
CamelTestSupport gives a running context + template. MockEndpoint: expectedMessageCount(), expectedBodiesReceived(), assertIsSatisfied(). adviceWith(): weaveByType/weaveById/weaveByToUri + .replace()/.remove()/.before()/.after() — advise a route once per test. isMockEndpointsAndSkip() mocks and skips the real call, plain isMockEndpoints() mocks but still calls it.
Observability
Current MDC is the camel-mdc component (don't combine with the legacy useMDCLogging). breadcrumbId header is set automatically and survives HTTP/JMS transport. Micrometer counters: camel.exchanges.total/succeeded/failed, registered via MicrometerRoutePolicyFactory — not automatic from classpath presence alone. camel-health: Spring Boot → /actuator/health, Quarkus → /q/health/ready and /q/health/live — a downstream outage is a readiness failure, not a liveness one.
Config & secrets
{{key}}, {{key:default}}, {{?key}} (optional, component's own default), {{!key}} (negate). Resolution order differs by runtime: camel-main ranks system properties over env vars; Spring Boot ranks system properties above env vars too; Quarkus ranks system properties (400) > env vars (300) > application.properties (250). Vault functions: {{aws:secretName#field:default@version}} and the Hashicorp/Azure/GCP equivalents; refresh needs both refreshEnabled=true and camel.main.context-reload-enabled=true.
Route lifecycle
start()/stop() is a full graceful rebuild; suspend()/resume() pauses consumers only, keeping the context warm — faster to resume. autoStartup(false) registers a route without starting it.
Every option on this page has a default; nearly every gotcha above is what happens when nobody consciously chose one. Read the default, decide if it's yours, and be the person who wrote it down.
