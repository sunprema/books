Chapter nine

The Toolchain

Everything so far has been the language. This chapter is the other half of the system: a command-line tool called aspec that reads the same file and answers questions about it before anything runs.

That distinction is what separates AgentSpec from a prompt convention. A convention is honored by people who remember it. A spec is checked by a program, in CI, on every pull request. Here is the whole surface, and then we will walk the ones that change how you work.

No installation ceremony is required to try it — the showcase README runs it straight from the repository:

the 60-second tour

alias aspec='uvx --from git+https://github.com/sunprema/AgentSpec aspec'

aspec lint --strict depbot.aspec.py     # clean — fallbacks, rules, contracts all check
aspec plan depbot.aspec.py              # the derived schedule: gates, waves, skips
aspec diff depbot.aspec.py depbot-risky.aspec.py    # the Aha
aspec studio depbot.aspec.py            # interactive canvas + gate simulator

lint — conformance, hygiene, and type flow

aspec lint checks three different things, and it is worth separating them because they fail for different reasons.

Conformance is structural: is this a legal spec? A missing docstring, a function definition at module level, an unknown attribute on a task, an anonymous return. Rule hygiene is the layer that enforces chapter five — this is where a must-rule with no why gets flagged. And cross-task type flow checks the wiring: a step that binds a field the upstream schema does not have is caught before it is ever run.

Findings carry stable diagnostic IDs in the range AS001–AS044, which is what makes them referable — you can write "we suppress AS012 here, because…" in a comment and it will still mean something next year. The output format is the one every editor already parses: 

BookBank_routine.aspec.py:42:8: AS004 missing task docstring

Two flags matter. --json for machine consumption, and --strict, which turns warnings into failures. The exit codes distinguish all three states: 0 clean, 1 errors, 2 warnings-as-errors under --strict.

Run it strict in CI

The warning tier is where rule hygiene lives — the missing why, the exclusive tool with no undo. Those are exactly the defects that never announce themselves at runtime and only show up in the postmortem.

plan — the schedule you never wrote

Chapter seven made the point that execution order is derived from the data flow. aspec plan is where you see what was derived: the concurrent waves, the gate consequences, how a skip propagates, and — the genuinely useful one — false concurrency, where two steps look parallel but cannot actually run together.

The BookBank routine's plan is a good illustration: its wave five shows art ∥ notify running in parallel, and wave six shows a single alert step joining all six preceding steps. Neither of those facts is written anywhere in the spec. Both are consequences.

Read a plan as a review tool. If the waves surprise you, either your mental model of the routine is wrong or your binds are — and both are worth knowing before the routine runs unattended.

graph — the pipeline as a picture

aspec graph emits the pipeline as a Mermaid flowchart. Steps are rectangles, fan-outs get a distinct shape and an ×N marker, gates are dashed, and a join shows as multiple incoming edges. --out file.md writes it to a file; otherwise it goes to stdout.

The flag worth knowing is --failures, which adds a second layer: the abort, retry and escalate edges. Chapter eight's saga becomes something you can look at rather than trace by hand — and a spec whose failure graph has a path that reaches no notification is visibly wrong.

fmt — one canonical shape

aspec fmt rewrites a spec in canonical order: docstring, inputs, returns, binds, then the reserved attributes — with layout handled by ruff format --isolated. It is idempotent, so fmt(fmt(x)) == fmt(x), and --check exits 1 if a file would change without writing anything.

The obvious benefit is the usual one — no arguments about layout. The less obvious benefit is that canonical order makes the semantic diff in the next chapter far easier to read: when every spec puts its tools in the same place, a change to a tool list appears as a change to a tool list, not as a wholesale reshuffle.

run — guarded execution

aspec run executes a spec with guard rails. The dispatch context flows into the root task, outputs are validated against the declared schemas, and violations are fed back for bounded repair (--max-repairs, default 2). The run report records what actually happened — validated outputs, which fallbacks were applied, rule conflicts encountered, and any tool substitutions.

That substitution log is chapter six's third condition made real. "Record the substitution" is not an honor system; it is a field in the report.

There is also --orchestrate, which runs one guarded subagent per step. The orchestrator resolves data flow, gates, fan-out and filters, and each subagent inherits a pruned contract and deduplicated constraints — so a step is executed by an agent that has been told exactly its own job and no more. The run report then also carries skips, escalations and undo reports.

studio and lsp — the spec while you write it

aspec studio serves a localhost workbench: a wave-layered canvas of the pipeline, a task inspector, a lint overlay, and a client-side gate simulator. It re-parses on file change and keeps the last good model, so a half-typed spec does not blank the canvas.

The gate simulator is the part to try first. Toggle tests.passed on depbot and watch the pr step skip while cleanup — gated on if not tests.passed — runs instead, with notify still firing. You are reading the routine's behavior on a path that has not happened yet.

Each showcase also ships that view as a single static HTML file (depbot.html and friends), so the simulator can be opened with nothing installed at all. And aspec lsp puts the same intelligence in your editor over JSON-RPC — hover, go-to-definition, diagnostics, completions, code actions — with a VS Code extension in the repository.

So what did we actually gain?

Answers about a routine's behavior that arrive before the routine runs. A spec you can lint in CI, whose schedule you can inspect, whose failure paths you can draw, and whose untaken branches you can simulate — all from the file the model will read.
