Chapter three

Schemas: the shape of every answer

Before we build a task, we need somewhere for its answer to land. In AgentSpec that is always a named Pydantic model — never a loose dict, never "return some JSON like this". Let's see why the constraint is tighter than it first looks.

Every output is a named schema

The rule is stated without exceptions: every task output is a named schema, and anonymous returns are conformance errors. So a schema is a class, it has a name, and other tasks can refer to it by that name.

the specification's own example

class RecoveryPlan(BaseModel):
    tier: Enum["extend_trial", "partial_refund", "manual_concierge"]
    value_usd: int = Field(le=50)
    reasoning: str = Field(max_length=250)
    transaction_id: str | None = None

Four fields, and three different kinds of promise. Let's take them one at a time, because each one is doing a job you would otherwise have tried to do with English.

Closed sets

Enum[...] and Literal[...] create a closed set: any other value violates the contract. The field tier has three legal values and no fourth. There is no "other", no "partial_refund_v2", no free-text escape hatch — and crucially, no way for a model having a creative night to invent a fourth tier that the code downstream has never heard of.

This matters most for the field a routine routes on. A run's outcome is not prose; it is a key that decides who gets paged and what the next step does. Here is depbot's:

depbot.aspec.py — the terminal report

class RunReport(BaseModel):
    outcome: Enum[
        "pr_opened",
        "no_updates",
        "tests_failed",
        "update_failed",
        "scan_failed",
        "uncertain",
    ]
    stopped_at: Enum["scan", "select", "apply", "test", "publish", "complete"]
    summary: str = Field(max_length=400)
    operator_action: str = Field(max_length=200)

Read those six outcomes as a design document. no_updates and scan_failed are both "no pull request tonight" — and the routine insists on telling them apart, because one is the goal state and one is broken. uncertain is there because a run that could not decide must be able to say so without dressing up as a success.

A test for your own enums

Take any two values in the set and ask: would I want a different thing to happen? If the answer is no, you have two names for one state. If two materially different endings share a value, the enum has stopped being a routing key and become a label.

Bounds are binding

Field(le=50) on value_usd is not a hint. Field bounds — le=, ge=, max_length= — are binding at runtime. That single expression is a routine's spending ceiling, declared in the data contract rather than pleaded for in a paragraph.

This is a genuinely different way to express a limit. You could write a rule that says "never offer more than fifty dollars of value", and you probably should as well. But the rule is a constraint the model honors, while the bound is a constraint the validator enforces. Two independent mechanisms, and the expensive one — real money — gets both.

The max_length bounds do quieter work. A summary capped at 400 characters cannot quietly become a three-page transcript that nobody reads. An operator_action capped at 200 has to name a fix rather than narrate the run.

The refusal to pad

Now the part that makes typed output actually trustworthy. The execution contract says the agent finishes on the contract: the final message ends with a JSON object matching the root task's returns — real values, or a declared fallback. And then, emphatically: never invent, coerce, or pad values to satisfy the shape.

A schema that gets filled in by guesswork is worse than no schema. It produces well-formed answers that are not true.

This is why the fallback machinery in chapter eight exists. Without a declared way to say "I could not get this", the pressure of a required field is enormous — the shape demands a value, and the easiest value to produce is a plausible one. AgentSpec's answer is to make the honest option always available and always legitimate. Notice how depbot's scan declares both:

two different empty answers

on_uncertain = {"ok": True,  "found": False, "count": 0, "candidates": []}
on_failure   = {"ok": False, "found": False, "count": 0, "candidates": []}

Identical except for one boolean. "I looked and there was nothing" and "I could not look" produce the same empty list and a different ok — and downstream, one is a clean finish and the other is a failure worth waking someone for.

What the runtime does when the shape is wrong

Guarded execution closes the loop. aspec run validates outputs against the declared schemas and feeds violations back to the model for bounded repair — bounded because the budget is a flag, --max-repairs, defaulting to two attempts.

Bounded is the operative word. An unbounded repair loop is a machine for converting a model's uncertainty into a confident-looking lie: try again, try again, until something validates. Two attempts is enough to fix a genuine formatting slip and not enough to grind out a fabrication.

So what did we actually gain?

A place for every answer to land, with the illegal answers ruled out by construction rather than by instruction — and an honest way to return nothing, which is what keeps the shape from manufacturing content to fill itself.
