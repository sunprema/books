Chapter one

The Unattended Contract

Let's start with the situation the whole language is built for, because if you have not been in it, none of the design decisions will look necessary. It is 3 a.m. A routine you wrote fires on a schedule. It hits something you did not anticipate. There is nobody to ask.

What happens next is the entire subject of this book. A capable model, given a prompt that does not cover the case in front of it, will do the most reasonable thing it can think of. That is usually a feature. In an unattended run it is the failure mode, because "the most reasonable thing it can think of" is not written down anywhere, was not reviewed by anyone, and will be slightly different tomorrow night.

AgentSpec is a declarative specification language for exactly this setting — autonomous AI routines — paired with a static analysis toolchain that reads the same files. Its premise is short enough to state in one line: the routine's judgment lives in the model, but the routine's boundaries live in a file, and that file is reviewable, checkable and versioned like any other piece of code.

Where AgentSpec is meant to run

The specification is explicit about its own scope. AgentSpec exists for routines that run unattended: nightly jobs, webhook handlers, queue workers — anywhere no human is present to answer a question, catch a mistake, or improvise a recovery. That last phrase is the important one. Improvisation is not a bug in a model; it is what a model is for. The problem is that an unattended run has no way to tell you it improvised, and no way for you to say no.

The argument in one sentence

In an unattended setting the specification is the only place human judgment lives, so it must be reviewable like code, checkable like code, and versioned like code.

Notice what that sentence rules out. It rules out judgment that lives in a README nobody reads at 3 a.m. It rules out judgment that lives in the head of the engineer who wrote the routine and has since changed teams. And it rules out judgment that lives in the model's general good sense, which is real but is not yours, and which you cannot diff.

Five principles, and why each one is there

The specification opens with five design principles. They are worth reading slowly, because every construct in the rest of the book is a consequence of one of them.

If it declares, it's allowed; if it computes, it's forbidden
The spec carries structure and constraints; all reasoning happens in the model. Anything a mechanical harness would have to evaluate — beyond membership and boolean checks — does not belong in the file.
Ghost Python
Every construct is standard Python or Pydantic that models, developers and tooling already understand. AgentSpec adds semantics, not syntax.
Rationale is first-class
Rules carry their why. Models follow constraints better when the cost of breaking them is stated, and reviewers approve intent rather than wording. Conformance tooling warns on any must-rule without one.
Doubt and failure are declared, not improvised
Every task states what to do when uncertain and what to do when it fails — including how to reverse what it already did.
Features are earned
A construct enters the language only after real specs have failed twice without it.

That last principle is unusual enough to dwell on. Most languages grow by anticipation: someone imagines a need and adds a feature. AgentSpec grows by postmortem. The two-failure rule means that every construct you are about to learn is a scar. When we get to derivations in chapter seven, the honest description of them is not "a routing primitive" but "the thing that had to exist after two specs routed themselves into the wrong answer."

A prompt that works because you are watching is not a routine. It is a demo with a person standing behind it.

What this is not

It would be easy to mistake AgentSpec for a prompt-formatting convention — a tidy way to lay out instructions. That reading misses half the system. The other half is a command-line toolchain, aspec, that parses the same file and answers questions about it before anything runs: does this spec conform, what order will its steps take, what does its pipeline look like as a diagram, and — the one that changes how teams work — what did this pull request just give the routine permission to do?

We will get there in chapters nine and ten. For now, hold onto the shape of the claim: a spec is a file a human reviews, a model executes, and a linter checks, and all three are looking at the same bytes.

The stakes are not hypothetical

The repository ships three showcase routines, and it is worth noticing what they are. depbot updates a dependency and opens a pull request. oncall-triage decides whether to wake a human at 4 a.m. cost-janitor deletes things to save money. None of these is a toy, and each one is dangerous in a different direction: depbot could ship a breaking change, oncall-triage could stay silent through an outage, and cost-janitor could delete something you needed.

We will use depbot as this book's worked example throughout. It is small enough to hold in your head and real enough that its constraints have all been paid for. By chapter ten you will be able to read its permission diff and see, in four lines, why the language exists.

So what did we actually gain?

Nothing yet — we have only named the problem. But naming it precisely is what makes the next nine chapters feel inevitable rather than decorative. Every construct answers the question: what would you want written down, if you knew you would not be there?
