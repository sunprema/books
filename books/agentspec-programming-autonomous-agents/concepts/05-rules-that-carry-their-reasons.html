Chapter five

Rules That Carry Their Reasons

A constraint in AgentSpec is not a sentence in a paragraph. It is a declared object with an identity, a severity, a rationale and a provenance. Let's build one and see what each field buys.

the shape of a rule

Rule("id", "rule text", why="...", severity="...", since="...")

Two required fields, three optional ones. The two required are the obvious pair — an identifier and the rule itself. The three optional ones are where the language's opinions live.

The id: a rule you can name

Ids are lowercase kebab-case and unique within a task's constraints. They exist so a rule can be referred to — discussed in review, reported in a run summary, and, most importantly, tracked across versions by the semantic diff.

That last use is the one that repays the ceremony. A rule with a stable id can be followed through a file's history: this is the same rule, and here is what happened to it. A rule identified only by its wording disappears the moment someone rephrases it, and reappears looking like a new rule nobody has to justify.

The why: rationale is first-class

why= states the cost of breaking the rule. This is one of the five design principles, and the specification gives two distinct reasons for it: models follow constraints better when the cost of breaking them is stated, and reviewers approve intent rather than wording. The conformance tooling backs this up — it warns on any must-rule that carries no rationale.

Here is a rule from depbot's shared doctrine, set out in full:

one-update-per-run must · since v1.1.0

Update exactly ONE dependency per run, even when many are outdated.

the 2026-07-12 run bundled 14 bumps into one unreviewable PR; one small diff per night keeps review honest and blast radius tiny.

Read the rule text alone and it sounds arbitrary — inefficient, even. Why would a bot leave thirteen updates on the table? Read the why and the rule becomes obviously correct, and, more to the point, becomes correct in cases the text does not cover. A model that knows the reason is "keep the diff reviewable" will not go looking for a loophole, because it understands what the loophole would cost.

A rule without its reason survives review by wording. A rule with its reason survives contact with a case nobody anticipated.

Notice too that this why is a dated postmortem. It is not abstract principle; it is "on this night, this happened." We will come back to that in chapter eleven — it is how a spec accumulates.

Severity, and what happens when rules collide

severity= takes one of three values: "must" (the default), "should", or "may". The semantics are ordered and stated:

  • must rules are inviolable.
  • should rules yield to conflicting musts.
  • When two rules conflict, the more conservative action wins.

That third clause is the interesting one, because it settles the case the first two do not: two musts that genuinely pull in opposite directions. The language does not pretend this never happens. It declares a tie-break, and the tie-break is the direction that does less. An unattended routine that is confused should shrink, not improvise.

Defaulting to must is also a deliberate choice. In a file about boundaries, the unmarked case is the strict one; softening a constraint takes a keystroke you have to justify.

The since: provenance

since= records where a rule came from — a version number, or an incident reference like "v2.0.3(6)". It answers the question that kills good rules over time: is this still necessary? A rule stamped with the run that caused it can be evaluated on evidence. A rule with no provenance eventually gets deleted by someone who cannot see what it is protecting.

Doctrine: rules that travel

Rules are ordinary Python objects in ordinary lists, which means they compose with +. That is how a routine carries operational doctrine into every task:

depbot.aspec.py — module-level doctrine

DOCTRINE = [
    Rule(
        "one-update-per-run",
        "Update exactly ONE dependency per run, even when many are outdated",
        why="the 2026-07-12 run bundled 14 bumps into one unreviewable PR; "
        "one small diff per night keeps review honest and blast radius tiny",
        severity="must",
        since="v1.1.0",
    ),
    Rule(
        "no-undeclared-software",
        "Never install, fetch, or enable software that no task declares",
        why="a dependency bot that widens its own toolbox is the incident",
        severity="must",
    ),
]

And then every task opts in by construction: 

constraints = DOCTRINE + [
    Rule(
        "safest-first",
        "Prefer patch over minor over major; among equals, prefer the "
        "most widely depended-upon package",
        why="the smallest semantic step has the smallest review cost",
        severity="must",
    ),
]

Two properties follow, and they are the reason to bother. First, inheritance is visible: the doctrine is a named list, in the file, and you can see which tasks take it. Second, the composition only goes one way — a parent task's constraints bind every child step, and a child may add stricter rules but may never weaken a parent must.

The line to remember

Downgrading a rule from must to should is a one-word edit and a capability change. In chapter ten we will watch a tool notice exactly that and flag it as widening — which is the payoff for every field on this page.

So what did we actually gain?

Constraints that a model can weigh (because they carry their cost), that a reviewer can approve on intent, that a diff can follow across versions (because they have ids), and that a maintainer can safely re-examine years later (because they carry their origin).
