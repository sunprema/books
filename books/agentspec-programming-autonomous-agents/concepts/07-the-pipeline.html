Chapter seven

The Pipeline and Its Derivations

We have tasks. Now we compose them — and the composition uses no new syntax at all. Inside an orchestrator task, ordinary class-body assignments are the pipeline, and the variable names are the wiring.

the specification's §7 example

class Routine(Task):
    events  = ScanThings(limit=limit)
    plans   = [Triage(data=it) for it in events.items]
    paid    = [Pay(id=p.id, plan=p.plan)
               for p in plans if p.plan.tier in ["a", "b"]]
    mark    = MarkDone(n=events.count) if events.found else None
    report  = Digest(financials=paid, all_plans=plans.plan)

Five lines, five constructs. Let's walk them.

The four forms

Step
var = TaskClass(param=...). The variable holds that step's result; var.field reads a field of it.
Fan-out
A list comprehension runs the task once per item. The results collect into a list, so plans.plan is a list of plans.
Filtered fan-out
A comprehension if selects which items get processed — and it may only test literal membership or equality. It is routing, not judgment.
Gate
X(...) if cond else None runs the step only when cond is true. A false gate is a clean skip, never an error, and it propagates to steps that depend only on it.

That restriction on filters deserves a moment. Why not allow a richer expression? Because the moment a filter can express a judgment, two things break: a reviewer can no longer tell by reading which items will be processed, and the toolchain can no longer say it either. Keeping filters mechanical is what keeps the pipeline analysable. Judgment belongs inside a task, where it has a docstring, rules and an eval.

Order is derived, not written

Nowhere in that class did anyone write a sequence. Order falls out of the references: a step runs when everything it references has completed, and steps with no mutual references may run in any order or in parallel.

This is worth pausing on, because it means the schedule is a consequence of the data flow rather than a second thing to keep in sync with it. aspec plan reads the binds and derives the execution waves — showing concurrency, gate consequences and skip propagation, and flagging false concurrency where two steps look parallel but cannot be.

  1. scannothing to wait for
  2. pickgated on scan.found
  3. applygated on pick.selected
  4. testsgated on apply.applied
  5. pr ∥ cleanupmutually exclusive gates — never both
  6. notifyjoins every path

That is depbot's shape. Notice wave five: pr runs if tests.passed and cleanup runs if not tests.passed. They sit in the same wave because nothing orders them — and the plan can prove they never overlap, because their gates are negations of each other.

A false gate is not a failure

This is the single most common misunderstanding when people first read an AgentSpec pipeline, so let's be blunt about it. When scan.found is false, pick does not run. Nothing has gone wrong. The repository was up to date; that is the goal state. depbot says so in a rule:

gates-are-clean-stops must

Every step is gated on the one before it reporting success; a false gate is a clean stop, never an error.

an up-to-date repo and a failed scan must end differently in the report, but neither is a crash.

Derivations: routing you can read

Now the construct that earns its place most clearly. At the end of a run you have a pile of step results and you need one answer: what happened? Doing that reasoning in prose invites two parts of the routine to reach two different conclusions from the same state. A derivation makes it mechanical — a first-match-wins dict from condition to literal outcome:

depbot.aspec.py — the routing derivation

route = {
    not scan.ok:        {"outcome": "scan_failed",   "stopped_at": "scan"},
    not scan.found:     {"outcome": "no_updates",    "stopped_at": "complete"},
    not pick.selected:  {"outcome": "no_updates",    "stopped_at": "select"},
    not apply.applied:  {"outcome": "update_failed", "stopped_at": "apply"},
    not tests.passed:   {"outcome": "tests_failed",  "stopped_at": "test"},
    not pr.opened:      {"outcome": "update_failed", "stopped_at": "publish"},
    True:               {"outcome": "pr_opened",     "stopped_at": "complete"},
}
notify = Notify(outcome=route.outcome, pr=pr, tests=tests)

Read top to bottom; the first true row wins; the True key is the fallthrough. It is a decision table, and it is data — which means the toolchain can render it, simulate it, and diff it.

The last line is the reason derivations were added rather than left as a reduction step. notify needs the outcome, but the outcome is not produced until the orchestrator reduces — a value that does not exist yet cannot be piped into a step. The derivation lifts the routing decision up to where both the step and the reducer can read it, from one declared table. Two consumers, one source of truth.

oncall-triage uses the same construct for something with sharper stakes:

oncall-triage — severity, mechanically

triage = {
    not facts.actionable: {"severity": "none", "page": False},
    not diag.collected:  {"severity": "sev2", "page": True},   # blindness pages
    facts.customer_facing and facts.env == "prod":
                          {"severity": "sev1", "page": True},
    hypo.confidence == "low": {"severity": "sev2", "page": True},
    True:                 {"severity": "sev3", "page": False},
}

Look at row two. If diagnostics could not be collected, severity floors at sev2 and somebody gets paged — blindness pages. A model reasoning freely at 4 a.m. can talk itself down from an alert it cannot substantiate; a table cannot. The showcase says exactly this: the lookup exists so the routine cannot talk itself down under fatigue.

Put the judgment in the model. Put the routing in a table. Confusing the two is how a routine ends up with an opinion about whether to page you.

The orchestrator is its own reducer

After its steps run, the orchestrator synthesizes its own returns. With a derivation in place, that reduction becomes almost clerical — and depbot makes the split explicit:

reduce-from-route must

Copy route.outcome and route.stopped_at verbatim into RunReport, then author summary and operator_action.

routing is declared and mechanical; only the prose is judgment.

That is the whole design philosophy in one rule. The machine-readable fields are copied from a table. The human-readable fields are written by the model, which is the only participant capable of writing them.

So what did we actually gain?

A pipeline whose order nobody had to write, whose skips are ordinary outcomes rather than errors, and whose routing decisions are a table two different consumers can read the same way.
