Chapter eleven

From Dev Mode to Unattended

We began with a routine at 3 a.m. that has nobody to ask. This last chapter is about how a spec gets to the point where it does not need to — and it turns out that "how" is a loop you can run on purpose.

Letting the routine ask, on purpose

aspec run --dev turns on a clarification harness. When a task reaches a declared doubt point, the run pauses and asks you. You answer; the answer is recorded and fed back into the task's execution. Decline, and the spec's declared fallback applies as written.

The constraint on where questions may arise is the interesting part. A question may only surface where the spec declared a doubt point — an on_uncertain or an Escalate. Tasks without one have asserted "I never doubt here."

Reading that backwards

Every task you wrote without an on_uncertain is a claim about the world. Dev mode is where that claim gets tested — not by argument, but by the routine either needing to ask or not.

Each exchange becomes a Clarification object, captured in RunResult.clarifications, so a dev run is auditable afterwards. And one line governs how much authority your answers carry: clarification is not authorization — answers resolve questions; they never override must-rules. You can tell a paused routine which of two reasonable things to do. You cannot tell it to do the thing the spec forbids.

The gap report

When the run finishes, the tool prints a count: 

N clarifications — each is a candidate rule.

That framing is the whole method. Every question the routine had to ask is a place the spec was incomplete. The developer's job is not to keep answering; it is to edit the file so the question cannot arise again — which means writing a rule, with a why that records what actually happened and a since that dates it.

The readiness signal

So when is a routine ready to run with nobody watching? The answer is refreshingly unglamorous: when the gap count trends to zero across representative dev runs. No clarifications needed means nothing was left for a human to supply.

There is one more claim underneath this, and it is what makes the signal trustworthy: the routine's semantics ARE its unattended semantics; dev mode is the development harness where gaps surface cheaply. Dev mode does not make the routine behave differently. It makes the same routine pause instead of falling back — so what you observe in development is what will happen at 3 a.m., minus the pausing.

A file that accumulates

Deployment is not the end of the loop; it is where the loop gets its best material. The specification is direct about this: the spec file is where operational lessons accumulate. After a run that surprises you, the friction moves out of the agent's head and into the file — a new rule with the incident as its why and its since=, a schema field for what the run learned and dropped, a gate for the path nobody had modeled.

And one line that is easy to skim past and worth stopping on:

A success that required improvisation is also an incident — the expensive kind.

A run that worked because the model quietly did something the spec never granted did not prove the spec is fine. It proved the spec has a hole that happened to be filled well this time. That is the most dangerous kind of green run, because nothing about it asks for your attention.

The module docstring as an incident log

Chapter two mentioned that the module docstring conventionally carries revision history. Now we can read one properly. Here is depbot's, in full:

depbot.aspec.py — the history

v1.0.0 — initial routine.
v1.1.0 — the run of 2026-07-12 updated 14 dependencies in one PR; the diff
was unreviewable and shipped a breaking minor. One update per run, always.
v1.2.0 — a flaky test failed a clean update; the branch was left behind and
confused the next run. Tests get one declared retry; a failed run now
cleans its own branch.
v1.3.0 — routing moved into the `route` derivation (AgentSpec 2.2); the
notify step consumes route.outcome and fires on every terminal path.

Every entry names a night and what it cost, and every entry has a counterpart somewhere in the file. v1.1.0 is the one-update-per-run rule you met in chapter five, carrying that same date in its why. v1.2.0 is the Retry and the CleanupBranch step from chapter eight. v1.3.0 is the route derivation from chapter seven.

This is what "features are earned" looks like from the inside. Read the history and then read the spec, and the spec stops looking like a configuration file. It looks like an argument, where every clause was paid for by a specific night that went wrong.

What to do on Monday

If you have a routine already running on a prompt, you do not need to rewrite it to start. Write down its output shape as a schema; you will find at least one state it currently cannot express. Write down its tool surface as an enumerated list; you will find at least one operation you never meant to grant. Then run aspec lint --strict and let the warnings tell you which of your must-rules never explained themselves.

After that, the loop does the work. Run it in dev mode. Watch what it asks. Graduate each question into a rule that carries the reason. When it stops asking, it is ready — and when it surprises you anyway, the surprise has somewhere to go.

So what did we actually gain?

A way to become ready that is a measurement rather than a feeling, and a file that gets stronger every time it is wrong. The routine's judgment stays in the model, where it belongs. Its boundaries live in a file you can lint, diff, simulate and argue with — which is the only place they were ever safe.
