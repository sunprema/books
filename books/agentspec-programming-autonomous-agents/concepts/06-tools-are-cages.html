Chapter six

Tools Are Cages

A Tool declaration does two things at once. It grants a capability, and — because the grant is enumerated — it denies everything else. The second half is the reason the construct exists.

the five declaration forms, §6

tools = [
    Tool("gh", ops=["issue list", "pr create"]),
    Tool("python3", scripts=["lib/validate.py"]),
    Tool("read", paths=["<root>/skills/**"]),
    Tool("git", ops=["add", "commit", "push"], exclusive=True),
    Tool("house-plugin", ops=["build"], strict=True),
]

Three ways to narrow a surface — ops for permitted operations, scripts for approved script surfaces, paths for read-accessible locations — and two flags that change the rules of engagement. Let's take the narrowing first, because it is where the security story lives.

The permission that is written as an absence

Here is depbot's entire authority over GitHub: 

tools = [Tool("gh", ops=["pr create"])]        # no merge op. Ever.

One operation. The routine can open a pull request and can do nothing else with gh — it cannot merge, cannot approve, cannot enable auto-merge, not because it has been told not to but because the words are not in the list. Its authority ends at the proposal.

And then the spec says it a second time, as a rule:

never-merge must

Never merge, approve, or enable auto-merge on any PR — this routine's authority ends at the proposal.

merge is the human's act; a bot that can merge its own proposals is a supply-chain incident waiting for a flaky test.

Belt and braces, and deliberately so. The tool surface is the mechanism; the rule is the intent. A future editor who adds "pr merge" to the ops list has to walk past a must-rule that explains, in one clause, what they are about to buy. Two independent statements of the same boundary make it much harder to erode by accident.

The oncall-triage showcase applies the same technique in the other direction: it is a first responder that observes, hypothesizes and pages, and its tool surface performs no state modification at all. Being read-only is not a promise in its prompt — it is the absence of a verb.

Two flags

exclusive=True
Marks a resource that concurrent steps must not hold at the same time. git is the canonical case — two steps sharing one working tree will happily corrupt each other's index. Declaring exclusivity lets the planner prove that two steps cannot race.
strict=True
Reverses substitution. That exact mechanism, or the task fails. Strict tools exist where the mechanism itself carries the guarantees — a validator, a signed pipeline, a house build system whose behavior is the contract.

Capability, not binary

Now the subtle part, and the one that trips people up. A Tool names a capability by its preferred mechanism. If that mechanism is unavailable — the binary is missing, the endpoint is down — an equivalent may substitute, under three conditions:

  1. it covers only the declared ops, never a wider scope;
  2. every constraint on the task applies to it identically;
  3. the substitution is recorded, so the human learns the environment drifted.

So a task declaring Tool("gh", ops=["issue list"]) on a box with no gh binary may reach the same capability another way — an API call that lists issues, and nothing else. Absence of the preferred mechanism is an environment fact to route around, not a task failure. Unless the tool is strict: an unusable strict tool is a task failure, and the declared failure branch applies.

Script as specification

There is a neat corollary for declared scripts. Suppose a task declares Tool("python3", scripts=["lib/validate.py"]) and that script's own internal dependency is missing. The script then serves as the specification of the effect: read it, reproduce its exact effect via available mechanisms at the same scope, and record the substitution.

"At the same scope" is carrying the weight. A script that appends one marker-guarded block to one file describes a small, idempotent effect — and reproducing it by hand means reproducing the guards too, not just the copy.

Declare the whole procedure

One last requirement, and it is the one most often violated in practice: the tool list must cover the whole procedure the task mandates. That includes the degradation branches — the paths taken when an optional piece is missing.

Where the gap gets filled

A task whose instruction demands more than its tool list grants does not stop. It improvises, at 3 a.m., with nobody to check the improvisation. Under-declaring a tool list does not make a routine safer; it makes the widening invisible instead of reviewable.

This has a counter-intuitive consequence worth stating outright: a degraded path often needs a larger tool list than the happy path. When a strict plugin does the work, it does everything internally and the task needs only the one declaration. When that plugin is unavailable and the model performs the same procedure by hand, it now needs every verb the plugin used. Writing the fallback's tool list as a subset of the happy path's is how a routine ends up standing at a step it has been instructed to perform and has not been permitted to.

So what did we actually gain?

A permission model that is readable at a glance and reviewable as a diff. The most important thing a tool list says is what is not in it — and unlike a promise in a prompt, an absent operation stays absent when the model is tired, wrong, or being talked into something.
