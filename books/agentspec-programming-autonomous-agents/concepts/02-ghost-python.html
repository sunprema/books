Chapter two

Ghost Python

Here is the sentence that reorganizes everything: an AgentSpec file is valid Python that is never executed as code. Read it twice. The file imports, declares classes, and type-annotates fields — and no interpreter ever runs a line of it.

So what happens to it? A model reads it and executes it directly. The specification puts this plainly: the model is the runtime. There is no compiler, no rendering step, and no framework between the file a human reviews and the file an agent runs — they are the same bytes.

That identity is the point. Most agent frameworks have a gap: you write configuration, something transforms it into a prompt, and the thing the model actually sees is a derived artifact nobody reviewed. Every bug in that transformation is invisible in review. AgentSpec closes the gap by refusing to have a transformation at all.

Why Python, if it never runs?

Because everyone already reads it. That is the whole of the ghost Python principle: every construct is standard Python or Pydantic that models, developers and tooling already understand. AgentSpec adds semantics, not syntax. Your editor highlights it. Your reviewer's eye parses it. The model has seen a million files shaped like it. And a linter can walk it with the standard library's own AST module.

The files carry a distinct extension — .aspec.py — so tooling can find them and so nobody mistakes one for a module to import. Here is the header of the depbot showcase, which is a real spec:

depbot.aspec.py — the top of the file

"""
depbot — nightly dependency updater. Runs unattended in a repo checkout:
picks ONE outdated dependency, updates it on a branch, runs the tests, and
opens a draft PR. It can propose; it can never merge — that is the point,
and it is visible in the tool declarations below.
"""

from pydantic import BaseModel, Field
from agentspec import Task, Tool, Enum, Retry, Rule

Two imports. pydantic gives you the data contracts; agentspec gives you the five nouns the language is made of. That is the entire vocabulary you need to start, and we will meet each one in turn.

What the file may contain

The specification is strict about module level, and the strictness is what makes static analysis possible. Exactly four things are allowed:

  1. A docstring — conventionally carrying the routine's revision history and postmortems. We will return to this in chapter eleven; it turns out to be the most interesting part of a mature spec.
  2. Imports from agentspec, pydantic, typing, and other .aspec.py files.
  3. Constants holding literals or rule lists.
  4. Class definitions — the schemas and the tasks.

And what is forbidden: functions, loops, I/O, and arbitrary expressions anywhere in the file. Not discouraged — conformance errors. The linter will tell you.

The rule behind the rule

If it declares, it's allowed; if it computes, it's forbidden. A helper function in a spec file is a small piece of logic that escaped review by looking like plumbing. If you feel the need to write one, the thing you are computing is either a constant (declare it) or a judgment (give it to the model, under a rule).

Parse, never import

Here is where the "never executed" discipline pays a second dividend, and it is a security dividend. All of AgentSpec's static analysis happens at parse time via AST inspection: specs are never imported or executed. So running aspec lint on a spec that arrived in a pull request from someone you do not know cannot run their code, because nothing in the pipeline ever calls import.

Compare that with the usual configuration-as-Python arrangement, where loading the config is executing it. The whole toolchain — lint, plan, graph, diff, format — reads a syntax tree and never a stack frame.

The world outside the file

A routine does need some ambient facts — what time it is, where it is running. AgentSpec grants exactly five, in a closed env namespace:

The whole environment
NameWhat it holds
env.nowan ISO timestamp
env.cwdthe working directory
env.userthe invoking user
env.platformthe platform
env.run_idthis run's identifier

Nothing else exists. Anything else a task needs is an input — which means it appears in the task's signature, where a reviewer can see it and the toolchain can type-check the step that supplies it. A closed namespace is a small design decision with a large effect: there is no ambient channel through which a dependency can sneak into a routine unannounced.

So what did we actually gain?

A file with no execution semantics of its own. That sounds like a limitation and behaves like a guarantee: what you read is what runs, an untrusted spec is safe to analyse, and every dependency the routine has is visible in a signature rather than hidden in an import.
