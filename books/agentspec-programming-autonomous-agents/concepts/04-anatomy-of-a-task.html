Chapter four

Anatomy of a Task

A task is the unit of declared work: one instruction, its inputs, its output contract, the tools it may reach for, the rules it must honor, and what it does when things go sideways. It is a Python class, and every part of it is in a fixed place.

the canonical skeleton, §4

class TriageTicket(Task):
    """One-paragraph intent. This is the task's core instruction."""
    ticket: TicketData                    # bare annotations = inputs
    returns: Verdict                      # output contract, a named schema

    tools = [ ... ]                       # see §6
    constraints = [ ... ]                 # see §5
    undo = "How to reverse this task's completed effects"
    on_uncertain = { ...literal output... }
    on_item_failure = "skip_and_report"   # for fan-out; see §8
    on_failure = "abort"                  # see §8
    meta = {"version": "1.0.0"}           # free-form; version lives here

The docstring is the instruction

Not documentation. Not a comment for your colleagues. The docstring is required, and it is the task's core instruction — the prompt, if you like, except that it sits where a Python reader already expects to find the statement of purpose.

This placement does something subtle to how people write. Compare these two, both from depbot:

two docstrings, two jobs

class ScanDeps(Task):
    """List outdated dependencies from the manifest, mechanically — no
    judgment here, just an accurate inventory."""

class SelectUpdate(Task):
    """Pick the single safest update from the candidates. This is the
    routine's one judgment call — it is pinned by evals."""

Each one says what kind of work it is. The first disclaims judgment entirely; the second announces itself as the routine's one real decision and names how it is held to account. A reader who knows nothing else about depbot now knows where to look when its choices go wrong.

Inputs and the output contract

Inputs are the annotated class fields other than returns. That is the whole rule. A bare annotation declares an input; the name returns is reserved and names the output schema.

There is no separate parameter list to keep in sync, and no way to consume a value the signature does not mention — which is exactly what makes the toolchain able to check type flow across steps. When we wire tasks together in chapter seven, the wiring is only these names.

Reserved attributes, and nothing else

Seven names are reserved: tools, constraints, undo, on_uncertain, on_failure, on_item_failure and meta. Unknown attributes are errors.

With one exception, and it is a big one: in an orchestrator — a task whose job is to run other tasks — non-reserved assignments are the pipeline. That is how the same class syntax serves both "do a thing" and "coordinate the things", and it is why chapter seven can teach the pipeline without introducing a new construct.

meta is the free-form corner, and by convention it is where a spec's version lives: 

meta = {"version": "1.3.0", "dispatch": "cron nightly"}

Small, but it is the hook the semantic diff and the incident history hang on. A spec that cannot say which version it is cannot tell you which version misbehaved.

Which task starts?

A spec file holds several tasks. The root task is the one no other task references — unless the dispatch context names one explicitly. Its inputs come from the dispatch context, and unnamed freeform text flows into the input whose name fits, conventionally freeform_context.

That convention is doing more work than it looks. A webhook payload, a cron trigger, a human typing a sentence — all of them arrive as text with no schema. Giving that text a declared landing place means a task can be written to treat it with suspicion, which is precisely what a good selection task does. We will see one in chapter ten that verifies by command anything the freeform context claims, rather than believing it.

Sizing a task

Nothing in the language tells you how big a task should be, so here is a practical grain, drawn from how the showcases are cut: one task per judgment. depbot could easily have folded selection into scanning — list what is outdated and pick one, same step. It does not, and the docstrings tell you why: the scan is mechanical, the pick is the judgment, and a judgment you have separated is a judgment you can pin with an eval.

The cost of merging steps

A task that both gathers and decides cannot be tested on its decision without also standing up its gathering. Worse, its failure modes blur: was the answer wrong because the inventory was incomplete, or because the choice was bad? Two tasks, two fallbacks, two answers.

There is a second, quieter reason. Every task declares its own tools, so the seam between two tasks is also a seam between two permission sets. ScanDeps can read the manifest; it cannot touch git. Splitting the work split the authority, and that is the subject of chapter six.

So what did we actually gain?

A unit of work whose instruction, contract, permissions and failure behavior all sit in one class, in fixed places. You can review a task without reading the rest of the file — and the linter can check it the same way.
