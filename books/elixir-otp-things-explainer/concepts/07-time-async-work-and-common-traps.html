Errands, Timers, and Ways to Trip Yourself Up

Here's the problem

Say posting a message should also send a slow outside notification — an email, a push alert. If RoomServer does that itself, inside handle_cast, then while it's waiting on that slow errand, it can't read any other note in its mailbox. The whole room freezes for everyone, just because one message triggered a slow side-errand.

The rule

Remember: a worker reads its mailbox one note at a time, strictly in order. Anything slow done inside that reading — a network call, a big computation — blocks every other note behind it, no matter how unrelated. The fix isn't "make the worker faster." It's "don't make the worker do the slow part at all."

A Task is a worker hired for one short, independent errand, and then it's done — it doesn't sit around holding long-term memory like a GenServer does. Run it under a Task.Supervisor and, if that one errand blows up, only the errand fails — the room worker that asked for it keeps going, untouched.

# fire-and-forget: we don't care about the result
Task.Supervisor.start_child(MyApp.TaskSupervisor, fn ->
  Notifier.send_email(user, message)
end)

The room worker hands off the slow errand and immediately goes back to reading its next note — the errand runs on its own desk, watched by the task supervisor instead of the room's own supervisor.

A second useful trick: notes from the future

Process.send_after/3 is exactly send, except the note doesn't land in the mailbox until a delay has passed. It's the one primitive underneath every "clean up this room after five minutes of silence" or "retry this in a few seconds" behavior.

Traps worth naming, plainly
  • A growing mailbox is a warning, not a quirk. If notes keep arriving faster than a worker reads them, its mailbox just keeps growing — that's a sign something should be offloaded (to a Task) or slowed down at the source, not ignored.
  • A GenServer's memory is not a database. It lives only as long as that one worker does, and — as chapter 4 keeps insisting — a crash wipes it clean. Anything that must survive a crash belongs somewhere durable.
  • Not everything needs to be a worker. A plain function that just computes an answer and returns it doesn't need a desk, a mailbox, or a supervisor watching it. Reach for a process only when there's a real reason — something needs to own state, run independently, or be allowed to fail in isolation.
The moment a note's answer requires waiting on something slow, hand the waiting to a Task and let the worker get back to its mailbox.
