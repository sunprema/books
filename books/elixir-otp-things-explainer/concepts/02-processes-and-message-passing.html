Little Workers That Talk By Passing Notes

Here's the problem

You want a little worker sitting at its own desk, keeping count of something — say, how many people have joined a room. Other parts of the program need to bump that count, and sometimes ask what it currently is. How do you even get a worker like that to exist?

The rule

spawn hires a worker. You hand it a little job description — a function — and it starts a brand-new desk, running that function, right away. You don't wait around for it to finish; you're handed a claim ticket for that desk (a PID, short for process identifier) and you go on with your own work.

Now: getting a note to it

You've hired the worker. It's sitting at its desk. How do you actually tell it to bump the count?

The rule

send slides a note onto that worker's desk — its mailbox — and then walks away immediately. It never waits to see if the note gets read. The worker, whenever it's ready, uses receive to look through its mailbox for a note matching a shape it knows how to handle, reads that one, and does whatever it says.

Notes land in the mailbox in the order they were sent — first sent, first in line. But it's still entirely up to the worker's own code which one it deals with, and when. Nobody can walk over and grab a note out of another worker's mailbox.

defmodule Counter do
  def start(initial) do
    spawn(fn -> loop(initial) end)
  end

  defp loop(count) do
    receive do
      {:bump, amount} -> loop(count + amount)
      {:get, caller} ->
        send(caller, {:count, count})
        loop(count)
    end
  end
end

Walking through it, line by line: start hires a worker running loop, starting the count at initial. loop waits at receive for one of two kinds of notes: a :bump note, which just calls loop again with the new total (the worker's "memory" is really just the argument it passes to its own next round); or a :get note, which slides a reply note back to whoever asked, then loops with the count unchanged.

Worth knowing

Writing that loop function by hand works, but notice everything you'd have to rebuild yourself for a real worker: matching a reply to the right request, giving up after a timeout, handling a crash cleanly, reloading code without losing the worker's memory. Every hand-rolled worker ends up reinventing the same handful of things — which is exactly the itch that the next chapter's tool, GenServer, scratches.

A worker owns its own memory and only ever talks by sliding notes — it never lets anyone else reach in and touch what it's holding.
