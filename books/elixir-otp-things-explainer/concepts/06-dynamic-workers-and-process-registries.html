Elixir calls this: DynamicSupervisor, Registry

Workers You Hire on the Spot

Here's the problem

Every supervisor list we've written so far names its workers up front: "watch the lobby room." But real rooms get created whenever someone types a new room name — "acme", "widgets-co", a thousand others we can't possibly list in advance. We need a supervisor that can be told, while the app is already running, "hire one more, right now, for this new id."

The rule

A DynamicSupervisor is a supervisor with an empty starting list — you tell it what to watch as you go, calling DynamicSupervisor.start_child/2 whenever a new one needs hiring. Same watch-and-restart behavior as before, just with hires happening on the fly instead of all at boot.

Hiring on the spot creates a second problem: how does anyone else find the worker for "room acme" later, without keeping a claim ticket (a PID) passed around by hand everywhere it's needed? A claim ticket also goes stale the moment a worker crashes and gets replaced — the new worker gets a brand new one.

The rule

A Registry is a lookup desk: it maps a plain name you choose ("room acme") to whichever worker currently holds that name — automatically forgetting a crashed worker and picking up its replacement the moment one re-registers under the same name. A worker can register itself the instant it's hired by starting with a special kind of name — {:via, Registry, {registry_name, key}} — instead of a fixed atom name.

# started once, at boot, under the top supervisor
children = [
  {Registry, keys: :unique, name: MyApp.RoomRegistry},
  {DynamicSupervisor, strategy: :one_for_one, name: MyApp.RoomSupervisor}
]

keys: :unique means each name can point to exactly one worker at a time — the right choice for room ids, where "room acme" should never mean two different workers at once.

Putting it together: "find it, or hire it"

Now we can write the exact operation the capstone project needs — look a room up, and only hire a new one if it doesn't exist yet:

def get_or_start(room_id) do
  case Registry.lookup(MyApp.RoomRegistry, room_id) do
    [{pid, _}] ->
      {:ok, pid}

    [] ->
      spec = {RoomServer, name: {:via, Registry, {MyApp.RoomRegistry, room_id}}}
      DynamicSupervisor.start_child(MyApp.RoomSupervisor, spec)
  end
end

If the lookup finds someone already at that desk, we're done. If not, we hire a fresh RoomServer, telling it to register itself under that same room id the moment it starts — so the very next lookup for "room acme" finds it.

Worth knowing — the race hiding in "get or start"

Two requests for a brand-new room id, arriving at almost the same moment, can both see an empty lookup and both try to hire a worker. Because the Registry key is unique, only the first hire actually succeeds — the second gets told {:error, {:already_started, pid}} instead of quietly creating a second worker for the same room. A caller that expects this and falls back to using that pid handles the race correctly; a caller that ignores it and crashes on the unexpected error does not.

A DynamicSupervisor hires whatever wasn't known in advance; a Registry is how anyone finds what got hired, by name, without ever passing a claim ticket around by hand.
