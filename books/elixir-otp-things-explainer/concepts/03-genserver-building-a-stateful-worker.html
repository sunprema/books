Elixir calls this: GenServer

A Worker With a Job Description

Here's the problem

Every hand-rolled worker from the last chapter ends up with the same shape: hire it, give it a starting memory, loop forever matching notes, sometimes send a reply. Writing that loop by hand for every single kind of worker in a real app — a room, a user session, a job queue — means writing the same plumbing over and over, and getting little details (a slow reply, a forgotten reply, a crash mid-note) wrong slightly differently each time.

The rule

GenServer is a ready-made job description you fill in. You still write the interesting parts — what this worker's memory looks like, what it does with each kind of note — but the hiring, the note-matching loop, the reply-tracking, and the "what if it crashes mid-note" handling are all handled for you, the same reliable way, every time.

You fill in three kinds of blanks: init/1 (what memory does a freshly hired worker start with?), handle_call/3 (a note that expects a reply, and won't move on until it gets one), and handle_cast/2 (a note that doesn't expect any reply at all — fire and forget). A fourth blank, handle_info/2, catches anything else that lands in the mailbox that wasn't sent through the normal call/cast door — a timer going off, for instance.

Say two different callers slide the worker a note at once. Which one wins? Neither has to — the worker still reads its mailbox one note at a time, same as before. Sliding a note that expects a reply (call) makes the caller stop and wait until that particular reply comes back; sliding a note with no reply expected (cast) lets the caller walk away immediately, the same way send always did.

Building the room worker

Let's give the running project its first real worker: RoomServer, one per chat room, holding that room's messages.

defmodule RoomServer do
  use GenServer

  # --- the part other code calls ---
  def start_link(room_id) do
    GenServer.start_link(__MODULE__, room_id, name: room_id)
  end

  def post(room_id, user, message) do
    GenServer.cast(room_id, {:post, user, message})
  end

  def messages(room_id) do
    GenServer.call(room_id, :messages)
  end

  # --- the part GenServer calls for us ---
  @impl true
  def init(room_id), do: {:ok, %{room_id: room_id, messages: []}}

  @impl true
  def handle_cast({:post, user, message}, state) do
    {:noreply, %{state | messages: [{user, message} | state.messages]}}
  end

  @impl true
  def handle_call(:messages, _from, state) do
    {:reply, Enum.reverse(state.messages), state}
  end
end

Walking through it: start_link hires the worker and gives it a name so callers don't have to remember a raw claim ticket. post and messages are the whole public face of the room — nobody outside this file needs to know that posting is a fire-and-forget note and reading is a wait-for-reply note. init/1 sets the starting memory: an empty list of messages. handle_cast answers a :post note by tucking the message onto the front of the list and saying "no reply needed." handle_call answers a :messages note by sending back the list, put in the right order, and keeping the memory exactly as it was.

Worth knowing

A GenServer isn't really "an object with methods," even though RoomServer.post/3 and RoomServer.messages/2 look a little like methods from the outside. It's one single worker, at one desk, whose entire job is owning this one room's memory and nothing else. Nobody else's code ever reaches in and edits state directly — the only door in is a note.

A GenServer is the same hire-loop-note pattern from the last chapter, just with the repetitive parts written once, correctly, so you only ever fill in "what does this worker actually do."
