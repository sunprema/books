Proving It Falls Down the Right Way

Here's the problem

We've built a room worker, taught it to crash cleanly, and taught a supervisor to hire a replacement. How do we actually check any of that works — including the crash-and-recover part — instead of just believing it does?

The rule

start_supervised!/1 hires a worker for exactly one test, under the test framework's own supervisor, and guarantees it's cleared away the moment that test ends — so tests never leave stray workers running behind them.

test "posting adds a message" do
  room = start_supervised!({RoomServer, :test_room})
  RoomServer.post(room, "sundar", "hi")
  assert [{"sundar", "hi"}] = RoomServer.messages(room)
end

That checks the ordinary, working path. But this book's whole point is that OTP correctness includes the falling-down path too — so let's actually test a crash and a restart, not just assume the earlier chapters were right.

Watching for a message instead of guessing a delay

A tempting but flaky way to test "did it restart yet?" is sprinkling in Process.sleep/1 and hoping enough time passed. Don't — a slow test machine breaks that silently. Instead, wait for an actual, observable signal.

test "a crashed room comes back under the same name" do
  {:ok, sup} = DynamicSupervisor.start_link(strategy: :one_for_one)
  {:ok, room} = DynamicSupervisor.start_child(sup, {RoomServer, :acme})
  ref = Process.monitor(room)

  GenServer.cast(room, :crash)
  assert_receive {:DOWN, ^ref, :process, ^room, _reason}

  # give the supervisor a beat to react, then check a fresh one exists
  assert_receive {:room_ready, _new_pid}, 1000
end

Walking through it: Process.monitor/1 asks to be told, with a real message, the moment the room worker exits — that's the signal assert_receive waits on, not a guessed delay. (A worker that announces its own readiness — sending {:room_ready, self()} from init/1 — gives the test a second real signal for "the replacement is actually up," rather than testing the crash but not the recovery.)

Worth knowing

Treating "it recovers from a crash" as a test worth writing, not an edge case to skip, is the difference between believing your supervision tree works and actually knowing it does.

Before calling any OTP piece "done," ask

  • What state does this process own?
  • Can that state be reconstructed after a crash?
  • Who supervises this process?
  • What should happen if it repeatedly fails?
  • Does this really need a GenServer, or would a Task — or a plain function — do?
  • How will I test and observe its failure, not just its happy path?
The finished project is small on purpose: a registry, a room supervisor that hires on demand, and rooms that crash cleanly and come back — proof that a handful of plain ideas, put together, really do add up to "doesn't fall over."
