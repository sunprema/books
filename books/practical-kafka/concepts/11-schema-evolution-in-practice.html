Chapter 11

Schema Evolution in Practice

Compatibility modes are not a quality ranking. They are a statement about who upgrades first, and choosing one is choosing a deployment order.

The six modes

The registry enforces one compatibility level per subject. Read each definition twice — the direction is easy to invert in your head.

Compatibility levels and what each permits
LevelGuaranteesChecked against
BACKWARD
default		 A consumer using the new schema can read data written with the latest registered schema Latest version
BACKWARD_TRANSITIVE …can read data written with all previously registered schemas Every version
FORWARD A consumer using the latest registered schema can read data written with the new schema Latest version
FORWARD_TRANSITIVE Consumers on any registered schema can read data written with the new schema Every version
FULL Both backward and forward compatible Latest version
FULL_TRANSITIVE Both, against every version Every version
NONE No checking at all —

The difference transitive makes is precisely this: the new version is verified against all previous versions, not only the immediately preceding one. Without it, a sequence of individually-compatible changes can leave you unable to read your oldest data — each step was legal, the composition is not.

Why BACKWARD is the default

Because it lets you rewind a consumer to the beginning of a topic. If a new consumer schema can read everything already written, replay works. That is the property most event platforms need most often, which is why the tool picks it for you.

Compatibility is a deployment order

This is the framing that makes the modes memorable.

If you control the consumers and they can be upgraded ahead of the producers, BACKWARD is comfortable. If your producers are upgraded first — a common situation when the producing team owns the deployment pipeline and consumers are external — FORWARD is what you need. If you cannot guarantee either order, FULL is the honest answer, and it is correspondingly restrictive.

Adding a field

The bread-and-butter change, and it works because of the resolution rule from Chapter 3: a field present in the reader but absent in the writer takes the reader's default.

Safe: add with a default

{ "name": "promotionCode",
  "type": ["null", "string"],
  "default": null }        // reader supplies null for old records

Without the default, a new consumer meeting an old record has nothing to put in the field, and resolution signals an error. That is why "add a field with a default" is the canonical safe change and "add a required field" is not.

Defaults are a migration tool, not a business rule

A default answers "what should a reader use when this data predates the field?" It does not mean "the business value is null." If the real answer is "we do not know," make that representable — a nullable field whose null means unknown — rather than defaulting to a value that will be mistaken for a fact.

Deleting a field

Riskier, and the risk runs the other way. Deleting a field is safe for backward compatibility only if old readers can cope — which means the field must have had a default in the readers' schema. If consumers declared it required, removing it breaks them.

In practice the sequence is: stop populating the field meaningfully, wait until no consumer reads it (which requires knowing who your consumers are — Chapter 13), then remove it. The waiting is the hard part and it is organisational, not technical.

Never reuse a name

Deleting status and later adding a new status with a different meaning passes every compatibility check and is a silent data corruption. A replaying consumer will read old values as though they meant the new thing. Compatibility checking validates structure; it has no idea what your fields mean.

Renaming with aliases

Avro fields are matched by name, so a rename looks like "delete one field, add another" — which loses the data. Aliases fix this: a reader's field can declare the previous names it accepts, and resolution will match data written under the old name.

Reader-side alias

{ "name": "customerId",
  "type": "string",
  "aliases": ["custId"] }     // reads data written as custId

Note that the alias lives on the reader's schema. It is a statement about what this consumer will accept, which means a rename still requires every consumer to adopt the alias. Aliases make renames possible; they do not make them free.

Type changes

Avro permits certain primitive promotions — reading an int as a long, for example — because the wider type can represent every value of the narrower one. What is technically valid and what is operationally wise are different questions.

A promotion in the safe direction is fine. Going the other way is not, and neither is changing a decimal's precision or scale (Chapter 3: both must match). The rule of thumb: if the change could lose information for any value that has ever been written, it is not a type change you can make in place. It is a new field, or a new topic (Chapter 12).

Enums and unions

From Chapter 3: if the writer's symbol is absent from the reader's enum and the reader has a declared default, that default is used; otherwise an error is signalled. So:

  • Declare an enum default from day one. Something explicitly meaning "a value this reader does not recognise" — UNKNOWN — not a real business value. Without it, adding a symbol is a breaking change that detonates on the first record carrying it.
  • Adding a symbol is then safe for existing readers, who will see UNKNOWN.
  • Removing a symbol is not safe, because retained records still carry it — the same "the past does not change" problem as field deletion.
  • Adding a branch to a union is a forward-compatibility break: old readers have no matching branch and resolution errors. Adding to a union is really the same class of change as adding an enum symbol, without the default to save you.

If a field's value set is genuinely open-ended, a string with documented values is often more honest than an enum. Enums are for closed sets. "Closed" means you are prepared to make a schema change to extend it.

So what did we actually gain?

A vocabulary for schema review that is about consequences rather than taste. "This adds a required field, so under BACKWARD it will be rejected, and if we relax the policy our replay breaks" is a reviewable statement. "I don't like this" is not.

But some changes are simply not evolutions. The next chapter is about recognising those early, before you have contorted a schema to avoid admitting it.
