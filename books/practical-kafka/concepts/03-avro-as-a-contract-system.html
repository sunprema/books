Chapter 03

Avro as a Serialization and Contract System

Avro's central move is to let the reader and the writer hold different schemas, and to define precisely how the two are reconciled. Everything useful about Avro follows from that.

Two schemas, not one

When Avro reads data it uses two schemas: the writer's schema, which was used to produce the bytes, and the reader's schema, which describes what the reading application wants. Resolution reconciles them field by field.

This is the whole game. A consumer deployed six months ago reads a record written this morning by a producer that has since added two fields. The consumer does not fail; resolution drops the fields it does not know about. A consumer deployed this morning reads a record from last year; resolution fills the missing field from the reader's declared default. Both of those work because the rules are specified, not because everyone redeployed in lockstep.

The shape of a schema

An Avro schema is JSON. The building blocks are primitives (null, boolean, int, long, float, double, bytes, string) and complex types: record, enum, array, map, union, and fixed. Records, enums and fixed are named types — they have a name and a namespace, which together form the fullname. Hold on to that; Chapter 4 shows how the fullname can become the registry subject, which makes naming an operational decision rather than a stylistic one.

OrderPlaced.avsc

{
  "type": "record",
  "name": "OrderPlaced",
  "namespace": "com.acme.orders.v1",
  "doc": "A customer order was accepted. Emitted once per order, never amended.",
  "fields": [
    { "name": "orderId",
      "type": { "type": "string", "logicalType": "uuid" } },
    { "name": "occurredAt",
      "type": { "type": "long", "logicalType": "timestamp-micros" } },
    { "name": "total",
      "type": { "type": "bytes", "logicalType": "decimal",
                "precision": 12, "scale": 2 } },
    { "name": "couponCode",
      "type": ["null", "string"], "default": null }
  ]
}

Note the doc field. It is part of the schema, travels with it into the registry, and is therefore the one piece of documentation that cannot drift away from the contract. Use it for semantics — "amounts are in the order's currency, excluding tax" — not for restating the field name.

Why the payload carries no schema

Avro's binary encoding writes no field names and no type tags. The payload is positional: to read it at all you must already know the writer's schema. A three-field record is just three values laid end to end.

This is why Avro records are so much smaller than JSON, and it is also why Avro on Kafka needs the Schema Registry. Avro files (the object container format) embed the full schema in the file header, which is fine when you write a million records into one file — but a Kafka record is one record, and embedding a schema per record would be absurd. The registry exists to solve exactly that: it lets the record carry a small schema reference instead of a schema. Chapter 4 is that mechanism.

Key idea

Avro embeds schema information conceptually — the reader always obtains the writer's schema — without embedding the schema itself in every Kafka message. Where that schema comes from is the registry's job, not Avro's.

The resolution rules worth memorising

You do not need the whole specification, but four rules explain most real-world behaviour:

  • Records match by field name. A field in the writer but not the reader is ignored. A field in the reader but not the writer uses the reader's default — and if there is no default, it is an error.
  • Arrays and maps resolve recursively: the algorithm is applied to the item schemas and the value schemas respectively.
  • Unions resolve to the first branch in the reader's union that matches the writer's selected schema; if none match, an error is signalled. When the reader's schema is a union and the writer's is not, the same rule applies — first matching branch wins.
  • Enums: if the writer's symbol is not present in the reader's enum and the reader has a declared default, that default is used; otherwise an error is signalled.

That last one is a small rule with large consequences. An enum without a default is a field that will break the day someone adds a symbol — and it will break at the consumer, in production, on the first record carrying the new value, which is the worst possible time and place.

Logical types

Logical types annotate a primitive with meaning: a long that is a timestamp-micros, a string that is a uuid, bytes that are a decimal. Readers that understand the annotation give you a proper type; readers that do not still get valid data.

Decimal is the one to be careful with. Precision and scale are declared in the schema, and for resolution purposes two decimal schemas match only if their scale and precision match. Scale must be zero or a positive integer no greater than the precision. Practically: you are choosing your money precision permanently, at design time. Changing scale later is a type change, not an additive one.

Avro fits event streams well because its evolution model was designed for exactly this problem, and because the size advantage compounds across billions of records. Protobuf's tag-number identity is arguably more robust to renames; JSON Schema is the right answer when human inspectability matters more than bytes, or when your consumers are outside your organisation. Pick one per platform and stop relitigating it.

Modelling traps

The three that keep recurring

Nullable field ordering. Write ["null","string"] with "default": null — the default must match the first branch of the union. ["string","null"] with a null default is invalid, and the error message will not be kind.

Ambiguous unions. A union of several record types means a reader must inspect the value to know what it got. It resolves, but your consumer code becomes a type switch that grows forever. Prefer one record with a discriminator, or separate topics.

Doubles for money. Use a decimal logical type with declared precision and scale. This is not pedantry; floating point rounding in a financial event stream is a defect that surfaces in reconciliation months later.

So what did we actually gain?

A precise idea of what "compatible" can mean. Avro does not promise that any two schemas work together; it defines an algorithm and tells you when that algorithm errors. Compatibility policy — the subject of Chapter 11 — is just a set of constraints chosen to guarantee the algorithm never errors in a particular direction.
