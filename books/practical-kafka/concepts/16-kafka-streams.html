Chapter 16

Kafka Streams and Stream Processing

Kafka Streams is a library that turns the hard parts of Chapter 15 — state, restoration, exactly-once — into configuration. In exchange it creates topics on your behalf, and you should know which ones.

Topologies

A Streams application is a topology: a graph of processing nodes. Source nodes read from topics, processor nodes transform, sink nodes write back to topics. State stores hang off processors that need memory.

It is a library, not a cluster. Your application is a normal process that you deploy normally; scaling means running more instances, which join a consumer group and divide the partitions between them exactly as in Chapter 7. There is no separate scheduler to operate, which is the main reason to prefer it over a heavier processing framework when your input and output are both Kafka.

Streams and tables

The core abstraction. A KStream is a sequence of independent facts: every record is a new event. A KTable is a changelog: every record is an update to the value for its key, and only the latest matters.

This is Chapter 9's distinction, lifted into the programming model — a KTable is what a compacted topic looks like from inside an application. And the two convert: aggregating a stream produces a table; reading a table's changes produces a stream.

The topics Streams creates for you

This is the part that surprises operators, so it belongs early rather than in a footnote.

Changelog topics. Every state store gets one automatically, logging updates so the store can be rebuilt elsewhere. They are compacted, which is exactly right: restoring only needs the latest value per key. This is what makes a Streams instance's state survive the loss of the machine holding it — a new instance replays the changelog and continues.

Repartition topics. Any operation that changes the key — a groupBy, or a join on a different field — inserts one, so that records sharing the new key land in the same partition. Without it, aggregation would be wrong: the same key's records would be spread across instances that cannot see each other.

Capacity planning

A Streams application with three re-keying steps and four state stores is running seven extra topics. Count them when sizing your cluster (Chapter 21) — teams are routinely surprised by where their partition count and disk went.

Stateless and stateful operations

Stateless — filter, map, flatMap, branch. One record in, zero or more out, no memory. Cheap, and freely reordered by the optimiser. Note that map may change the key and therefore trigger a repartition; mapValues promises it will not, so prefer it when you are only touching the value.

Stateful — aggregate, count, reduce, joins, windowing, deduplication. These need a state store, and therefore a changelog, and therefore a restoration time when an instance starts. A large store means a slow startup — which is the practical reason to keep state stores as small as the problem allows.

Joins

Which join you get depends on what you are joining, and the semantics differ substantially:

  • KStream-KStream — must be windowed. Two streams of events only join if they arrive close enough in time, because otherwise the state would grow forever.
  • KStream-KTable — an enrichment lookup. Each event is joined against the table's current value for its key. Not windowed, and the workhorse of most pipelines: enrich an order event with the customer's current tier.
  • KTable-KTable — a non-windowed inner equi-join on primary key, where the join attribute is thisKTable.key == otherKTable.key. The result is an ever-updating KTable representing the current result of the join.

All of them require co-partitioning: both sides must have the same number of partitions and the same keying strategy, or matching records land on different instances and simply never meet. Streams will insert a repartition to fix this when it can, and fail at startup when it cannot.

Event time, and the grace period

Records arrive out of order — a mobile client was offline, a partition was slow, a producer retried. So Streams distinguishes event time (when the fact happened, from the record) from processing time (when you saw it). Windowing uses event time, which is the only choice that gives reproducible results on replay.

The grace period controls how long a window waits for out-of-order records. If a record arrives after the window's end plus the grace period — that is, record.ts > window-end + grace — it is discarded and not processed into that window.

The trade-off, stated plainly

A longer grace period means more complete results and later results, and more state held open. A shorter one means faster answers that may be wrong. There is no setting that gives both — decide which failure the business prefers, and monitor how many records you are dropping so the decision stays informed.

Exactly-once in Streams

This is where the transactions of Chapter 8 become practical. Streams implements consume-transform-produce with transactional offset commits internally; you turn it on with a configuration setting rather than writing the loop.

The improved implementation, exactly-once v2, arrived in the 2.6.0 release and requires broker 2.5.0 or newer. It is materially more efficient than the original implementation, which used one producer per input partition.

The same boundary from Chapter 8 still applies, and it is worth repeating because the configuration flag makes it easy to forget: this guarantees exactly-once within Kafka. A Streams application that calls an external API in a processor is back to at-least-once for that call, flag or no flag.

Interactive queries

State stores can be queried directly from the application that owns them. That turns a Streams app into a low-latency read model: the aggregate is already computed and held locally, so a lookup is a local read rather than a database query.

The catch is that state is partitioned across instances, so a query may need routing to whichever instance owns the key. Streams tells you which one that is; you still have to do the routing, and handle the window during a rebalance when the answer is "nobody, briefly."

When not to use it

Streams is the right tool when input and output are both Kafka and the logic is genuinely streaming. It is the wrong tool when you are really doing an ETL job into a warehouse (use Connect, Chapter 17), when the transformation is a single stateless map that a plain consumer would do in twenty lines, or when you need to join against a large external dataset that does not belong in a state store.

So what did we actually gain?

State management, restoration, and exactly-once as library features rather than application code — at the price of hidden topics, restoration times, and co-partitioning constraints that are invisible until they are not.
