Chapter 14

Publishing Reliable Domain Events

You need to change a row and publish an event, atomically, without a distributed transaction. There is a standard answer, and the naive approach fails in a way that is very hard to see in testing.

The dual-write problem

Your service accepts an order. It must write the order to its database and publish OrderPlaced to Kafka. Two systems, two writes, no shared transaction.

Database first, then publish: a crash between them leaves an order that exists but that no downstream system will ever hear about. No error is raised anywhere. The bug surfaces days later as "some orders never got fulfilled."

Publish first, then commit: a rollback leaves an event announcing something that did not happen. Downstream consumers act on it — charge a card, reserve stock — for an order your database has no record of.

Wrapping the send inside the database transaction does not help either: Kafka does not participate in it, so the record is published the moment it is sent regardless of what the database does afterwards. It also means a slow broker holds a database transaction open, which is its own kind of outage.

Why not two-phase commit?

Because it is not available here in any practical form, and because even where XA exists it trades a rare inconsistency for a common availability problem: a coordinator failure can leave locks held until a human intervenes. The industry moved to the outbox pattern for good reasons.

The transactional outbox

The insight is to make it one write. Write the event to an outbox table in the same local database transaction as the business change. The transaction is atomic by construction — one database, one commit. Then a separate relay reads the outbox and publishes to Kafka.

The relay is at-least-once, which is fine — consumers are idempotent anyway (Chapter 15), and the event id from Chapter 1 is the deduplication key. What the relay can never do is publish an event whose business change was rolled back, because the outbox row rolled back with it.

A workable outbox table

CREATE TABLE outbox (
  id             uuid        PRIMARY KEY,
  aggregate_type text        NOT NULL,  -- routes to a topic
  aggregate_id   text        NOT NULL,  -- becomes the Kafka KEY
  event_type     text        NOT NULL,
  payload        jsonb       NOT NULL,
  occurred_at    timestamptz NOT NULL,
  trace_context  text
);

aggregate_id earns its place: it becomes the Kafka message key, which means all events for one aggregate land in one partition and stay ordered (Chapter 2). Getting this wrong — keying by the event id instead — destroys per-aggregate ordering silently, and the symptom is a consumer occasionally seeing OrderShipped before OrderPlaced.

Two ways to run the relay

Polling. A background job selects unpublished rows, publishes them, marks them done. Simple, easy to reason about, no extra infrastructure. It adds polling latency and load on the database, and you own the "mark as published" logic and its own dual-write problem in miniature (publish, then mark — so a crash between them republishes; that is fine, consumers are idempotent).

Change data capture. A CDC connector tails the database's replication log and emits a Kafka record per outbox row. No polling, no query load, low latency. Debezium is the common choice: it runs as a Kafka Connect connector and captures changes from PostgreSQL logical replication, the MySQL binlog, and others.

Debezium ships an outbox.event.router Single Message Transform for exactly this pattern. It post-processes the raw CDC events, routes them to the right topic based on the aggregate type, and uses the aggregate id as the message key — which is what preserves per-aggregate ordering. That is the pattern's ordering guarantee made mechanical.

CDC without an outbox — and why it is different

You can also point CDC straight at your business tables and skip the outbox. It is less work, and it publishes a fundamentally different thing.

Table-level CDC publishes row changes, so "status went from PENDING to CANCELLED" reaches consumers without the reason. Was it cancelled by the customer, by fraud review, or by a timeout? The table does not know, so neither do your consumers — and this is exactly the table-shaped-event problem from Chapter 10, arriving through the back door.

Use table CDC where you cannot change the application — legacy systems, packaged software, a database you inherited. Use the outbox everywhere you own the code. The outbox is CDC plus the freedom to design your own contract.

Per-aggregate sequencing

Kafka gives you ordering within a partition. Keying by aggregate id gives you ordering per aggregate. That is usually enough — but consumers cannot tell the difference between "these arrived in order" and "these are all the events there were."

For anything where a gap matters, carry an explicit sequence number per aggregate in the event. A consumer that sees sequence 7 after 5 knows something is missing and can react, rather than silently applying an incomplete history. It costs one field and turns a class of invisible bug into a detectable one.

Reconciliation

Even a correct outbox benefits from an audit. A periodic job that compares business-table counts against published-event counts for a window will catch a relay that has been silently stuck for six hours, a connector that lost its replication slot, or a topic whose ACLs changed under you.

Publish that comparison as a metric. "Outbox rows unpublished older than five minutes" is one of the highest-value alerts in an event-driven system, because it fires before anyone downstream notices anything is wrong.

So what did we actually gain?

A publication path where the failure mode is a duplicate rather than a lie, and where the event's shape is still yours to design. Every downstream chapter assumes this: consumers are built for at-least-once because the reliable publication patterns are at-least-once.
