Chapter 23

Case Study: Order-to-Cash Platform

One system, built with everything in this book. We will make the decisions in order and name the chapter each one comes from.

Step 1 — Draw the domain boundaries

Six domains, each owning its data and its events: ordering, payment, inventory, fulfillment, notifications, analytics.

The first four publish facts. Notifications and analytics are pure consumers — they publish nothing anyone else depends on, which makes them safe places to iterate quickly. That asymmetry is worth noticing early: the teams that publish contracts carry a governance burden the consuming teams do not.

Step 2 — Topics, keys, and ordering scope

Naming follows Chapter 13's convention; keys follow Chapter 2's rule that the key is the ordering promise.

The topic layout, and what each key promises
TopicKeyPolicyOrdering promise
orders.order.eventsorderIddelete, 30dOne order's lifecycle is ordered
payments.payment.eventsorderIddelete, 90dOne order's payments are ordered
inventory.reservation.eventsskudelete, 30dOne SKU's movements are ordered
fulfillment.shipment.eventsorderIddelete, 90dOne order's shipments are ordered
orders.order.stateorderIdcompactCurrent state of every order

Two decisions in that table deserve their reasoning stated.

Payments are keyed by orderId, not paymentId. We want authorization, capture and refund for one order to arrive in order, and paymentId would scatter them across partitions. This is Chapter 5's point about ordering scope beating distribution: it is a slightly worse key for load balancing and the right key for correctness.

Inventory is keyed by sku. Stock movements for one SKU must be ordered against each other — an order's events are not the relevant sequence here. Different aggregate, different key, and that is fine: not every topic in a system shares an ordering scope.

Because one order's lifecycle spans several event types on orders.order.events, this topic uses TopicRecordNameStrategy (Chapter 4) — heterogeneous events, each evolving independently, ordering preserved by the shared key.

Step 3 — The schemas

A shared envelope (Chapter 10), referenced by every event schema via a schema reference (Chapter 4):

com.acme.common.EventEnvelope

{ "eventId":       uuid,
  "occurredAt":    timestamp-micros,
  "correlationId": uuid,
  "causationId":   ["null", uuid],
  "actor":         string,
  "tenantId":      string,
  "sequence":      long }   // per-aggregate, for gap detection (Ch 14)

com.acme.orders.v1.OrderPlaced

{ "envelope":  EventEnvelope,
  "orderId":   uuid,
  "customerId":uuid,          // an id, not a name — Ch 10, Ch 22
  "currency":  string,
  "total":     decimal(12,4),  // scale 4: permanent, so be generous
  "lines":     array<OrderLine>,
  "channel":   enum{WEB,MOBILE,STORE,UNKNOWN} default UNKNOWN }

Three deliberate choices in ten lines

decimal(12,4) — scale is permanent (Chapter 3), so we take four now rather than discover we needed it. customerId, not customer name — minimisation makes Chapter 22's erasure problem largely disappear. An enum default of UNKNOWN — so adding a channel later is additive rather than an outage (Chapter 11).

Compatibility tiers per Chapter 13: payments run FULL_TRANSITIVE (money, and external auditors), orders and inventory run BACKWARD_TRANSITIVE, analytics topics run BACKWARD.

Step 4 — Publishing reliably

The ordering service writes the order row and an outbox row in one local transaction; Debezium's outbox.event.router relays it, keyed by aggregate_id so per-order ordering survives (Chapter 14). Producers run the durability profile from Chapters 5 and 6: acks=all, idempotence on, RF 3, minISR 2, unclean leader election disabled.

Payment is the interesting case, because the side effect is a card authorization at an external provider — outside any Kafka transaction (Chapter 8). So the payment service passes the orderId as the provider's idempotency key, and publishes PaymentAuthorized from its own outbox after the provider confirms. A duplicate consumption of the command re-sends the same idempotency key and the provider deduplicates. Exactly-once where it counts, built from at-least-once parts.

Step 5 — Consumers

Every consumer follows Chapter 15: bounded in-line retries for transient failures, retry topics for anything slower, dead-letter with full context headers for the permanent cases, and an idempotency strategy chosen per consumer.

  • Fulfillment — conditional writes. "Set status to PACKED where status is PAID." A duplicate updates zero rows, which is correct.
  • Notifications — a processed-event store keyed by eventId, written in the same transaction as the send record. This is the consumer that must never be replayed carelessly, so it is deliberately separate from the projection consumers.
  • Analytics — a Connect sink to the warehouse (Chapter 17), with errors.tolerance=all and a configured dead-letter topic.

Step 6 — Deriving order state

A Kafka Streams job (Chapter 16) aggregates the order lifecycle into orders.order.state, a compacted topic holding the current status of every order. Because both inputs are keyed by orderId they are co-partitioned, so no repartition topic is needed — a design choice, not luck.

The compacted state topic serves the operational dashboard directly: a new dashboard instance reads from offset zero and has every order's current status without a database query. This is Chapter 9's bootstrap property doing real work.

Step 7 — Evolving the schema, six months in

Marketing wants promotion details on OrderPlaced. Walk the ladder from Chapter 12:

It is additive, it changes no existing field's meaning, and it can carry a default. Rung 1 — evolve the schema. Add promotion as ["null", "Promotion"] with "default": null. Under BACKWARD_TRANSITIVE the CI check (Chapter 13) passes, the producer deploys, and no consumer does anything at all. Consumers that do not know the field ignore it; consumers that want it upgrade when convenient.

Compare with the change that is not rung 1: splitting total into subtotal and tax and removing total. That deletes a required field. Under our policy it is rejected — correctly. The honest options are to add the new fields while keeping total populated, deprecate it, and remove it only when the consumer inventory shows nobody reads it.

Step 8 — A new consumer, two years later

A fraud team wants to build a model on historical order behaviour. They create a new consumer group, set auto.offset.reset=earliest, and replay everything retained.

Nothing else notices. Offsets are per group (Chapter 2), so no existing consumer is affected. BACKWARD_TRANSITIVE guarantees their new schema reads every historical version. They get 90 days from payments and 30 from orders — and the fact that those numbers are lower than they hoped is a retention decision (Chapter 21) that someone made deliberately, not an accident.

This is the payoff for everything in Parts I–III. A team you had never met built on a two-year-old contract with no coordination, no migration, and no meeting. That is what the discipline buys.

So what did we actually gain?

A system where the common changes are free and the expensive ones are visible. Adding a field, adding a consumer, replaying history: routine. Changing an ordering scope or deleting a required field: a project, correctly, because that is what those things are.
