Chapter 22

Data Lifecycle and Compliance

An append-only log and a right to erasure are in genuine tension. Pretending otherwise — usually by assuming compaction is a delete button — is how teams end up with an obligation they cannot meet.

The core problem

Kafka's value comes from immutability. Records are appended, never modified; consumers replay history; the log is the record of what happened. Regulations frequently require that specific data about a specific person be deleted on request, within a deadline.

You cannot delete one record from the middle of a Kafka partition. There is no API for it, and the architecture is built around there not being one. So the question is not "how do I delete a record" but "how do I design so that I never need to."

Why compaction is not the answer

The intuitive move is: compacted topic, write a tombstone, the record disappears. Chapter 9 explained why this does not hold up as a compliance mechanism. Restated in compliance terms:

  • Compaction only touches closed segments. Data in the active segment is not cleaned at all, and there is no bound on when the segment rolls on a low-traffic topic.
  • Cleaning is threshold-driven. min.cleanable.dirty.ratio means a partition may sit uncleaned indefinitely if it is not dirty enough.
  • Timing is non-deterministic. Compaction does not guarantee one record per key at any moment; several versions and a tombstone can coexist.
  • It only removes superseded values for the same key. If personal data appears in the value of an event keyed by order id, no tombstone for that person exists to write.

State this plainly to your compliance team

Compaction is a storage optimisation with no deletion deadline. It cannot be relied on to remove an individual record by a specific date. If you have told an auditor otherwise, correct it before it is tested.

Four strategies that do work

1. Do not publish it. The cheapest erasure is data you never wrote. Publish a customer id, and let consumers that genuinely need the name look it up from a system that supports deletion. Chapter 10's data minimisation, restated as a compliance control. This handles more cases than teams expect once they audit what consumers actually use.

2. Tokenise at the source. The event carries a token; the mapping from token to personal data lives in a system that supports deletion. Erasure means deleting the mapping. The events remain, intact and replayable, and are now permanently meaningless with respect to that person.

3. Crypto-shredding. Encrypt sensitive fields with a per-subject key (Chapter 19). Erasure means destroying the key. The ciphertext remains in the log and is unrecoverable. This is the strongest option when the data genuinely must travel in the event, and it is more operationally demanding: you now run a key management system whose availability gates consumption, and whose key destruction must be as auditable as the deletion it implements.

4. Short retention on sensitive topics. If personal data must be in the payload and encryption is impractical, bound its lifetime. A 30-day retention means the erasure deadline is met by the passage of time — provided your deadline is longer than your retention, which is a calculation worth doing explicitly rather than assuming.

Topic isolation for regulated data

Because the topic is the unit of authorization (Chapter 19), regulated data on its own topic is the only isolation that is actually enforceable. It also makes every other control tractable: retention can be set for that topic alone, ACLs are narrow enough to serve as an access record, and a compliance audit has a bounded surface to examine rather than "somewhere in these 400 topics."

The design pattern: publish the non-sensitive event broadly, and the sensitive fields to a separate restricted topic keyed the same way. Consumers that need both join them; most consumers need only the first, and never receive the sensitive data at all.

The obligation propagates

This is the part that turns a deletion request into a project. Every consumer that read the data may have copied it — into a warehouse, a search index, a cache, a materialized view, a partner system. Deleting from Kafka, even if you could, does not delete any of those.

Which means erasure needs a propagation mechanism, and it is a design decision, not an operational one:

  • Publish erasure as an event. A SubjectErased event that every consumer handles, deleting its own copy. Auditable, and it puts the obligation where the data actually is.
  • Maintain a consumer inventory (Chapter 13) so you can answer "who has this data" at all. Without it, erasure is guesswork.
  • Make erasure handling a condition of consuming a regulated topic. Grant the ACL to consumers that implement the handler.

Replay, lineage, and legal hold

Three lifecycle interactions that catch people out:

Replay can resurrect deleted data. If you erased a downstream copy but the source event still carries the data, replaying it restores what you deleted. This is why erasure must happen at the source — key destruction, token deletion — rather than only downstream.

Lineage is a real requirement and Kafka gives you an unusually good starting point: the event log is lineage, provided events carry causation ids (Chapter 1). "Why does this record say this?" is answerable by replaying the chain.

Legal hold conflicts with retention. A hold requires preserving data that your retention policy is about to delete. Kafka has no per-record hold mechanism, so in practice this means copying the relevant data to a held store — which is another copy, with its own obligations. Plan the mechanism before you are served with a hold.

A regulated-topic checklist

  • Is the sensitive data necessary in the event, or can consumers look it up?
  • Is it on its own topic, with narrow ACLs?
  • Is the erasure mechanism decided — tokenisation, crypto-shredding, or retention?
  • Is retention shorter than the erasure deadline?
  • Is there an inventory of consumers, and does each handle erasure?
  • Is there an erasure event, and is handling it a condition of access?
  • Does replay re-expose anything that was erased?
  • Is the classification recorded in the schema (Chapter 10)?
  • Is there a legal-hold procedure that does not depend on Kafka retention?

So what did we actually gain?

An honest position. Kafka cannot delete individual records, and no configuration changes that. What you can do is design so the log never holds anything that must be individually deleted — through minimisation, tokenisation, or encryption — and make erasure a first-class event that propagates to everyone who copied the data.
