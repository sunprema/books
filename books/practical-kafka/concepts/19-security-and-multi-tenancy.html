Security and Multi-Tenant Boundaries

The topic is the unit of authorization. That single fact determines how you isolate tenants, protect sensitive data, and separate environments — and it has to be designed in, not added later.

Authentication, then authorization

Two separate steps that get conflated constantly. The flow is: the client authenticates (via SASL, mTLS, or another mechanism), the principal identity is extracted, the client attempts an operation on a resource, the authorizer queries stored ACLs for a matching rule, and if an Allow rule exists the operation proceeds — otherwise it is denied.

Deny-by-default is the important property. An operation with no matching rule fails, which means every permission your applications need must be explicitly granted. That is more work at setup and it is what makes the model worth anything.

TLS, SASL, and the naming confusion

This trips up nearly everyone once, so it is worth being explicit. SASL/PLAIN is an authentication mechanism — username and password. SASL_PLAINTEXT and SASL_SSL are security protocols — indicating whether the connection is encrypted with TLS.

The trap is SASL_PLAINTEXT with SASL/PLAIN: it looks internally consistent and it sends your credentials over the network in clear text. Always pair SASL with TLS (SASL_SSL), and prefer SASL/SCRAM or SASL/GSSAPI over SASL/PLAIN in production.

ACLs: the resources that matter

An ACL binds a principal to an operation on a resource. The resources are topics, consumer groups, the cluster itself, and transactional ids. Getting the set right the first time saves a genuinely tedious debugging session:

The classic first-deploy failure

Consumers need permissions on both the topic and the consumer group. Granting topic Read and stopping there produces an authorization error that names the group, not the topic, and teams spend an afternoon re-checking topic ACLs.

Prefixed ACLs are what make this manageable at scale: grant a team's principal rights on orders.* rather than on forty individual topics. It pairs directly with the naming convention from Chapter 13 — a naming scheme that maps prefixes to teams is also an authorization scheme.

Registry authorization is separate

Worth repeating from Chapter 13 because it is so easy to miss: broker ACLs and Schema Registry permissions are different systems. A principal denied Write on a topic can still, if the registry is open, register an incompatible schema version on that topic's subject and break every consumer.

Secure both, with the same ownership model, and keep the ability to lower a compatibility level restricted to the platform team. Lowering the policy is the privileged operation.

Multi-tenancy: three models

Because the topic is the unit of authorization, tenant isolation is a topic-layout question.

Shared topic with a tenant field is cheapest and scales to many tenants, but the boundary is enforced by application code. One filtering bug leaks tenant data, and no broker-level control can prevent it. Acceptable for internal tenancy; rarely acceptable for external customers.

Topic per tenant makes the boundary real: an ACL per topic, enforced by the broker. It multiplies your topic and partition count, which is a genuine constraint at hundreds of tenants (Chapter 21). This is the right default for external multi-tenancy at moderate scale.

Cluster per tenant is complete isolation including the blast radius of an operational mistake. Expensive; reserved for regulatory requirements or a small number of very large tenants.

Sensitive data

Chapter 10 covered the schema-design moves. The operational layer adds:

  • Topic isolation for sensitive fields. Since the topic is the authorization unit, sensitive data on its own topic is the only isolation that is actually enforceable. A "restricted" field on a widely-readable topic is readable by everyone with topic access.
  • Encryption at rest protects the disks, not your consumers — every authorized consumer still reads plaintext. It addresses a different threat model than access control, and neither substitutes for the other.
  • Field-level encryption does address consumer-level access: the value is encrypted in the payload, and only key-holding consumers can read it. It also makes crypto-shredding possible — destroy the key and the data is unrecoverable, which is the closest thing to per-record deletion an immutable log offers (Chapter 22).
  • Tokenisation at the source, so the event never carries the sensitive value at all. The cheapest option when consumers only need to correlate, not to read.

Audit logging

Authorization decisions — especially denials — should be logged and monitored. A spike in denials usually means a misconfigured deployment, and occasionally means something worse. Either way it is information you want before someone opens a ticket.

Note the asymmetry that makes Kafka auditing hard: consumption is not individually logged the way a database query is. You can see which groups have committed offsets, but not every read. If your compliance regime requires proof of who accessed what, that has to be designed in — typically by restricting access narrowly enough that the ACL set is the audit record.

Environment isolation

Separate clusters per environment. Not separate topic prefixes on one cluster — separate clusters.

The reasoning is failure isolation rather than access control: a load test in staging should not be able to starve production of broker resources, and a misconfigured consumer group name should not be able to read production data at all. Prefix separation makes both of those one typo away.

So what did we actually gain?

A security model that follows from one structural fact: the topic is the unit of authorization. Tenancy, sensitive data isolation and environment separation are all consequences of that, which is why they are topic-layout decisions made at design time rather than security controls bolted on afterwards.
