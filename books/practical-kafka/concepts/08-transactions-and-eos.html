Chapter 08

Transactions and Exactly-Once Semantics

Kafka's exactly-once is real, precise, and much narrower than the phrase suggests. It covers Kafka. It does not cover your database, and it never will.

What EOS actually is

Exactly-once semantics in Kafka is three mechanisms working together:

  • The idempotent producer — sequence-number deduplication, so a retry does not create a duplicate (Chapter 5).
  • The transactional producer — atomic writes spanning multiple partitions, via a two-phase commit coordinated by the broker.
  • read_committed consumers — consumers that refuse to see records belonging to transactions that have not committed.

Idempotence alone gets you "no duplicates from retries on one partition." Transactions get you "these writes across these partitions all happen, or none do." The isolation level is what makes the second one observable.

read_committed and the last stable offset

Here is the mechanism people miss. A read_committed consumer receives records in offset order as usual, but only those with an offset below the last stable offset (LSO) — the lowest offset of any open pending transaction. So it only ever sees records from transactions that have already been committed or aborted.

This has a direct operational consequence: long-running transactions block read_committed consumers at the LSO and increase the chance of hitting the transaction timeout. A transaction that stays open for thirty seconds adds thirty seconds of latency for every downstream consumer on that partition, no matter how fast they are.

Keep transactions short. If your transaction spans an external call, you have designed a system where a slow third party stalls your consumers.

Consume-transform-produce

The pattern transactions were built for: read from input topics, compute, write to output topics, and commit the input offsets — all atomically. The crucial detail is that the offset commit is part of the transaction. The producer sends the offsets to the transaction, not the consumer.

The shape of the loop

producer.initTransactions();

while (running) {
  records = consumer.poll(timeout);
  if (records.isEmpty()) continue;

  producer.beginTransaction();
  try {
    for (record : records)
      producer.send(transform(record));

    // offsets committed inside the transaction, by the PRODUCER
    producer.sendOffsetsToTransaction(offsetsOf(records), consumer.groupMetadata());
    producer.commitTransaction();
  } catch (Exception e) {
    producer.abortTransaction();   // outputs never become visible
  }
}

Required

Set enable.auto.commit=false on the consumer. With transactional offset commits, auto-commit double-commits and destroys the atomicity you just paid for.

Where it stops

Two boundaries, and both are absolute:

Transactions are supported only within a single Kafka cluster. A transaction cannot span two clusters. Cross-cluster replication is at-least-once, so mirrored topics carry duplicates.

Side effects outside Kafka are not covered. If your processing writes to a database, sends an email, or calls a payment API, those are not in the transaction and cannot be rolled back by abortTransaction(). Kafka commits atomically; your database does not know the transaction exists.

The sentence to remember

Kafka's exactly-once means exactly-once processing of Kafka records into Kafka records. The moment a side effect leaves Kafka, you are back to at-least-once and you need idempotency — a deduplication key, an upsert, or a processed-event store.

What to use instead, when the side effect is real

Three patterns cover essentially every case where EOS does not reach:

  • The outbox pattern — for writing to a database and publishing. Write the event to an outbox table in the same local database transaction as the business change, then relay it to Kafka. One atomic write, one asynchronous relay. Chapter 14.
  • Idempotent consumers — for consuming into a database. Make the write itself repeatable: upsert by a natural key, or record processed event ids and skip ones you have seen. Chapter 15.
  • Deduplication keys on external calls — for third-party APIs. Most payment and messaging providers accept an idempotency key precisely because this problem is universal.

Should you turn it on?

Transactions cost throughput and latency, and they add a failure mode (the stalled LSO) that is genuinely awkward to debug. They are clearly worth it for Kafka-to-Kafka stream processing where correctness of aggregates matters — Kafka Streams makes this a single configuration setting (Chapter 16), which is where most teams should meet transactions.

Hand-rolling transactions in an application that ends up calling a database anyway is usually the wrong trade: you pay the cost and still need idempotency for the part that mattered. Ask first where the side effects are. If any of them leave Kafka, design for idempotency and consider whether transactions are buying you anything at all.

So what did we actually gain?

A sharp boundary. Inside Kafka, atomicity is available and cheap to describe. Outside it, you own the problem — and knowing which side of that line each of your side effects sits on is what stops a team from enabling EOS and assuming the duplicate-payment bug is now impossible.
