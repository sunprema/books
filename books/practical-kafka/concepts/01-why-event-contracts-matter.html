Practical Kafka Part I · The Event Contract Mindset

Chapter 01

Why Event Contracts Matter

An event is not a message you send. It is an interface you publish, to an audience you cannot enumerate, for a duration you do not control.

"We'll clean up that field later" is the most expensive sentence in event-driven architecture.

The question this chapter answers

Why do teams who are perfectly competent at REST APIs — who version them, document them, deprecate them politely — produce Kafka topics that become unmaintainable in eighteen months?

Because a REST API looks like an interface. You can see the consumers in your access logs. You can put a /v2 in the path. When you break it, someone's pager goes off within the minute, and you find out.

A Kafka topic looks like a pipe. You write to it; something reads from it. Nothing about the API surface tells you that a data science team started reading it last quarter, that a compliance archive has retained every record you have ever written, or that a consumer you have never met will replay your topic from offset zero next March. So the interface gets designed with the care you would give a log line.

The "event is forever" mindset

Here is the property that makes events different. Retained records can be read by consumers written long after the producer — so an event's shape is a published API rather than an implementation detail. Deleting a field does not just affect the consumers running today; it affects every consumer that will ever replay the retained history.

This is not hypothetical caution. It is baked into how the tooling behaves. The Schema Registry's default compatibility mode is BACKWARD, and it is the default for a specific reason: it lets you rewind a consumer to the beginning of a topic and still read the oldest records with your newest schema. The tool's default assumes you will replay history. Design as though you will.

Five things people call "events"

Before you can design a contract you have to know what kind of thing you are publishing. These get conflated constantly, and the conflation is what produces topics nobody can evolve.

What are you actually publishing?
KindMeansAudienceTense
CommandDo thisExactly one ownerImperative
Event (fact)This happenedAnyonePast
NotificationSomething happened, go lookAnyonePast, thin
State snapshotThis is how it is nowAnyonePresent
Document / viewHere is a projectionNamed consumersPresent

The distinction that matters most is command versus fact. A command has one legitimate recipient and can be rejected — which means it can also be versioned by agreement between two parties. A fact has no recipient in particular and cannot be rejected, because it already happened. You cannot negotiate a version change with an audience you cannot name. That asymmetry is the entire reason facts need stricter contract discipline than commands do.

Key idea

Publish facts in the past tense, named for the business event (OrderPlaced), not the mechanism (OrderTableUpdated) and not the intent (PlaceOrder). If the name would still make sense to someone reading it in three years with no access to your codebase, it is probably a fact.

Ownership: who may publish, who owns the schema

Every topic needs one team that owns its schema, and that ownership needs to be enforceable rather than documented. In practice this means three separate decisions, and teams routinely make only the first:

  1. Who may write to the topic? An ACL question (Chapter 19).
  2. Who may register or evolve the schema? A registry authorization question (Chapter 13). These are not the same permission, and a team that can evolve a schema can break every consumer without ever touching the broker.
  3. Who decides the compatibility policy? A governance question. The policy is what determines whether decision 2 is dangerous.

This is why schema registry governance is API governance, not tooling. The registry is where you encode "this team may not break that team," and if you leave it open to every producer, you have written the policy in a wiki instead of in the system.

What every event carries

Independently of the domain payload, an event needs identity and provenance. Design this once, apply it everywhere — the consistency is worth more than the per-topic optimisation.

  • Event id — unique per emission. This is the deduplication key consumers need, because at-least-once delivery is the practical default (Chapter 8).
  • Occurred-at — when the fact happened in the business, which is not when the record was written. Event-time versus processing-time (Chapter 16) starts here.
  • Correlation id — ties everything caused by one originating request together.
  • Causation id — the id of the specific event or command that directly caused this one. Correlation gives you the trace; causation gives you the edge.
  • Actor and tenant — who did it, and on whose behalf. Retrofitting tenancy into an event stream is miserable; the field is cheap now.
  • Trace context — carried in Kafka record headers, not the payload, so it can be propagated without touching the schema.

Trap

Do not model event identity as "the aggregate id plus a timestamp." Two events can share both. Use a real unique id, and let the aggregate id do its own job — partition key, and therefore ordering scope.

So what did we actually gain?

Nothing yet, mechanically. But we have set up the question the rest of the book answers: if an event is a long-lived interface to an unknown audience, then every subsequent decision — how many partitions, which key, what retention, which compatibility mode, whether to add a field or a topic — is a decision about that interface, not about throughput.

The next chapter looks at Kafka's data model with exactly that lens. Not "what is a partition," but "what does choosing a partition key promise to a consumer you have not met."
