Chapter 09

Storage, Retention, and Compaction

Compaction is not deletion, is not immediate, and does not guarantee one record per key. Three facts that together explain a great many production surprises.

Segments: how a partition is stored

A partition is not one enormous file. It is a sequence of segments, each a log file with accompanying index files. Exactly one segment is active — the one currently being appended to. When it reaches a size or age limit, it is closed and a new active segment is rolled.

This structure explains almost every retention behaviour that looks wrong at first. Deletion works on whole segments, not individual records; compaction works only on closed segments. So the newest data is never cleaned, and "retention is 1 hour" does not mean a record is gone 60 minutes after it was written — it means the segment containing it becomes eligible for deletion once its records are all older than that, and the segment must have been closed first.

Retention by deletion

The default policy. retention.ms and retention.bytes set how long, or how much, to keep; whichever limit is hit first triggers deletion of the oldest segments. Setting either to -1 means unlimited.

The design question is not "how long do we keep data" but "how far back must a consumer be able to start?" Retention is your replay window, and it is bounded by three separate requirements that rarely agree:

  • Recovery — a consumer that has been broken over a long weekend must still be able to catch up rather than skip.
  • Bootstrap — a brand-new consumer that needs history to build its initial state (Chapter 24).
  • Compliance — a maximum, not a minimum. Sometimes the binding constraint is how long you are allowed to keep data (Chapter 22).

Compaction: a changelog, not a history

With cleanup.policy=compact, the log cleaner retains at least the latest value for each key and discards older records for that key. The topic stops being "everything that happened" and becomes "the current value of every key" — a changelog.

This is what makes a compacted topic a bootstrap mechanism. A new consumer reads from offset zero and ends up with current state for every key, without needing a separate snapshot API. It is how Kafka Streams state stores are backed up (Chapter 16), and it is the right shape for customer profiles, account state, feature flags, and reference data.

Tombstones

Deletion under compaction is expressed as a record with a null value — a tombstone. It says "this key no longer exists." The tombstone is retained for delete.retention.ms and is then removed along with the key's older values.

The retention window for tombstones exists for a specific reason: a consumer must have a chance to see the deletion. If tombstones were removed instantly, a consumer that was offline during the delete would rebuild its state from the compacted log, never see the tombstone, and keep the deleted key forever. The window is how long you are guaranteeing a rebuild will still observe deletions.

Consequence

A consumer offline for longer than delete.retention.ms cannot safely rebuild state incrementally — it may resurrect deleted keys. Either keep the window comfortably longer than your worst realistic outage, or rebuild from scratch after a long absence.

Compaction is best-effort and asynchronous

This is the part that catches people, so it is worth stating flatly: compaction does not guarantee there is only one record with a given key at any moment. There may be several, including a tombstone, because cleaning timing is non-deterministic.

Two mechanisms drive the timing. min.cleanable.dirty.ratio — 0.5 by default — means a partition's log must be at least half "dirty" before the cleaner bothers with it. And only closed segments are eligible, so segment.ms governs how quickly records become candidates at all. A low-traffic compacted topic may go a long time with duplicates sitting in it, entirely correctly.

Practical rule: consumers of compacted topics must still be idempotent and must handle seeing the same key more than once. Compaction is a storage optimisation; it is not a uniqueness guarantee, and code that assumes otherwise will work in testing and fail under replay.

compact,delete — both at once

The two policies can be combined. With cleanup.policy=compact,delete you keep the latest value per key and time-expire older, fully-cleaned segments. This is the answer for a changelog that must not grow without bound — for example, state for entities that eventually go dormant, where you want current values but not a permanent record of every key that ever existed.

Designing a compacted topic

Three rules, learned the hard way:

  1. The key must be the entity identity, exactly. Compaction deduplicates by key, so the key defines what "the same thing" means. Getting this wrong is unrecoverable without a full republish.
  2. Never use a null key. A record with a null key on a compacted topic has no identity to compact against and is rejected outright.
  3. The value must be a complete snapshot, not a delta. A consumer that reads only the latest record for a key must have the whole current state. Deltas break the moment compaction removes the intermediate records they depend on — and it will.

So what did we actually gain?

The right mental model for two very different topic shapes, and — importantly for Chapter 22 — the knowledge that neither one is a deletion mechanism. Compaction removes superseded values on its own schedule. If a regulation requires that a specific record be gone by a specific date, compaction is not the tool, and believing it is has produced some genuinely uncomfortable audit conversations.

That closes Part II. We now have enough mechanism to return to contracts and be precise about what "compatible" must mean.
