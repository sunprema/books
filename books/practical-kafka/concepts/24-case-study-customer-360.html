Chapter 24

Case Study: Customer 360 and Data Platform

A different shape from Chapter 23: state rather than events, sources you do not control, and a PII problem that has to be solved at design time.

The problem

Build a unified customer view from six systems — CRM, billing, support, web analytics, the loyalty programme, and a marketing platform. Feed a warehouse, a search index, and back into the CRM. Three of the six are packaged software nobody can modify.

The distinction that shapes everything: this is a state problem, not an event problem. Nobody wants "the customer's address changed" so much as "what is the customer's address." That points at compacted topics (Chapter 9) from the start.

Getting data out of systems you do not own

Chapter 14 preferred the outbox pattern — but it requires changing the application. For the three packaged systems that is not available, so table-level CDC is the honest answer, with its costs acknowledged rather than ignored.

Contain the CDC topics

CDC topics publish table shapes, so they are coupled to a schema the CRM vendor changes at their convenience (Chapter 17). Treat them as internal to the data platform team — an internal.cdc.* prefix, not consumed by anyone outside. The platform team transforms them into real domain contracts. Skipping that step exports the vendor's schema to the whole company.

Compacted state topics

The curated layer is a set of compacted topics keyed by canonical entity id:

  • customer.profile.state — identity, contact preferences, status
  • customer.account.state — billing account, plan, standing
  • customer.consent.state — marketing permissions, per channel
  • customer.pii.state — restricted, name and contact details

Chapter 9's three rules apply throughout: the key is the canonical customer id exactly, never null, and each value is a complete snapshot rather than a delta. A consumer reading only the latest record for a key must have the whole current state, because compaction will remove the intermediate records a delta depends on.

The PII split

Note that fourth topic. Because the topic is the unit of authorization (Chapter 19), splitting personal data onto its own restricted topic is the only isolation that actually holds.

Both topics are keyed by customer id, so a consumer with both grants can join them. Personal fields on the restricted topic are encrypted per customer (Chapter 22), which makes erasure a key destruction rather than an impossible delete. The warehouse and search sinks read only the non-restricted topics, so the obligation never propagates to them.

Identity resolution

The genuinely hard part, and it is a data problem rather than a Kafka problem. Six systems have six identifiers for the same person, and none is authoritative.

The workable structure is a separate compacted topic, customer.identity.map, keyed by source-system identifier with the canonical id as the value. Enrichment jobs consume it as a KTable and use it to translate incoming records onto the canonical key.

Keep resolution logic out of the enrichment jobs and in a dedicated service that publishes to the map. Matching rules change constantly — new heuristics, manual merges, corrections — and you want those changes in one place with its own history, not spread across every pipeline that happens to need a customer id.

Enrichment with Streams

A Kafka Streams job (Chapter 16) builds the curated state from the raw sources. Two design notes that matter:

Re-keying costs a repartition topic. Incoming CDC records are keyed by the source system's primary key, and the curated topics are keyed by canonical customer id. That re-key inserts a repartition topic per source (Chapter 16) — six extra topics, sized like the sources themselves. Count them in capacity planning (Chapter 21).

KTable-KTable joins for state. Joining profile state with account state is a non-windowed inner equi-join on the primary key, producing an ever-updating KTable. That is the right operation here — no windowing, because state has no notion of "recently."

Sinks

All four sinks are Connect (Chapter 17), each with errors.tolerance=all and its own dead-letter topic:

  • Warehouse — the analytical copy. Reads curated non-PII topics only.
  • Lakehouse — raw and curated, for data science.
  • Search — a subset for customer lookup in support tooling.
  • CRM — enriched attributes written back. The loop-risk sink.

The feedback loop

The CRM is both a source (via CDC) and a sink. Writing an enriched attribute back produces a CDC event, which re-enters the pipeline, which may write again. Mark platform-originated writes so the CDC source filters them out — an SMT is exactly the right tool — and verify it, because this loop is silent until it is a storage incident.

Where Avro compatibility stops helping

The honest limitation of this whole book's approach, and it shows up most sharply here.

Avro guarantees a consumer can still read the data. It says nothing about whether the data still means the same thing. If the CRM team redefines "active customer" from "logged in within 90 days" to "purchased within 12 months," every schema check passes. The field is the same type with the same name. Every downstream metric changes, and nothing in the tooling notices.

Structural compatibility is automatable; semantic compatibility is not. The controls are human — the doc field carrying the definition (Chapter 10), review by someone who understands the domain (Chapter 13), and treating a semantic change as a new field or a new event rather than a redefinition (Chapter 12).

So what did we actually gain?

A platform where new consumers bootstrap from compacted topics without touching source systems, where personal data is isolated behind an enforceable boundary, and where the sources you cannot change are contained rather than exported.

And a clear statement of what the machinery does not cover. Which is a good place to be standing when the next chapter goes wrong.
