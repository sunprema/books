Chapter 17

Kafka Connect and Data Integration

Connect is the answer to "we need to move this data and the logic is trivial." Its main risk is being used where the logic is not trivial.

Source and sink

Connect is a framework for running connectors as configuration rather than code. A source connector pulls data into Kafka; a sink connector pushes it out. You POST a JSON configuration to the Connect REST API and the cluster runs it, restarts it, distributes it, and tracks its offsets.

The value is not that it is impossible to write a consumer that writes to Elasticsearch. It is that you would write the same consumer forty times — with forty different approaches to offset management, error handling, restart behaviour and schema conversion. Connect makes that one well-tested implementation with a configuration file.

Tasks and parallelism

A connector is split into tasks, and tasks are the unit of parallelism, distributed across the workers in a Connect cluster. tasks.max caps how many.

How that maps to real parallelism depends on the direction:

  • Sink connectors are a consumer group. Tasks divide the topic's partitions, so the usual ceiling applies — more tasks than partitions leaves tasks idle (Chapter 2).
  • Source connectors split by whatever the source offers: tables, files, shards. A JDBC source with three tables cannot use more than three tasks no matter what you configure.

Sizing note

Setting tasks.max high does not create parallelism the source or the topic cannot supply. Check the actual split before assuming a throughput problem is a scaling problem.

Converters: where the schema lives

Connect separates the connector (which knows about Postgres, or S3) from the converter (which knows about serialization). The connector produces a Connect-internal record with a schema; the converter turns it into bytes.

This is where the Schema Registry enters. Configuring the Avro converter means source connectors register schemas derived from the source's structure — a Postgres table becomes an Avro record with fields matching the columns — and sink connectors resolve schemas on the way out.

Notice what that implies, and it is Chapter 10's warning arriving through a configuration file: a source connector's schema is your source system's schema. Point Connect at a table and the table's shape becomes a published contract, with its column names, its nullability, and its next migration.

This is exactly why Chapter 14 recommends the outbox: an outbox table is a schema you designed for publication, so CDC over it publishes a contract rather than an implementation.

Single Message Transforms

SMTs are small transformations applied per record inside the pipeline: rename a field, mask a value, route to a topic based on content, extract a field as the message key. Debezium's outbox.event.router from Chapter 14 is one.

They operate on one record at a time. That is what makes them cheap, and it is also the hard boundary: an SMT cannot join, cannot aggregate, cannot look anything up, and cannot see the record before or after. No amount of chaining changes that.

Choosing where the transformation goes
TransformationRight tool
Rename or drop a fieldSMT

Route by a field's valueSMT
Set the key from a fieldSMT

Anything needing prior recordsKafka Streams

When you find yourself chaining six SMTs to reshape a record, you have written a stream processor in configuration syntax, without tests, in a place where a failure stops the connector. Move it.

Error handling — the setting that matters

By default, if Connect hits a serialization error the connector task stops. That is deliberately safe: an invalid message will not be silently processed. It is also a full pipeline halt until someone intervenes.

Setting errors.tolerance=all makes Connect skip records that fail in supported stages — converters and SMTs — rather than failing the task immediately. Combine it with a dead-letter queue, which in Connect is a configured Kafka topic that failed records are routed to.

Sink connector — error handling that does not lose data

"errors.tolerance": "all",
"errors.deadletterqueue.topic.name": "dlq.orders.es-sink",
"errors.deadletterqueue.context.headers.enable": true,
"errors.deadletterqueue.topic.replication.factor": 3,
"errors.log.enable": true,
"errors.log.include.messages": false

The dangerous half-configuration

errors.tolerance=all with no dead-letter queue configured silently discards records. The pipeline looks healthy, throughput looks normal, and data is quietly gone. Always set both together — and note context.headers.enable, which is what records why each record failed.

Note also that error tolerance covers converters and SMTs — the stages Connect controls. It does not turn a failing target system into a success: if Elasticsearch is down, the task fails, and that is correct.

Where Connect stops

A reasonable decision rule:

  • Use Connect when the movement is the point and the transformation is per-record and simple. Database to Kafka, Kafka to warehouse, Kafka to search index, Kafka to object storage.
  • Write an application when there is business logic, external calls, non-trivial error semantics, or anything you would want to unit test.

The line is usually clear at the start of a project and gets crossed gradually, one SMT at a time. It is worth revisiting a connector's configuration occasionally and asking whether it has quietly become an application.

Operating it

Two things that matter more than they look:

A connector's status is not a task's status. A connector can report RUNNING while individual tasks have failed. Monitor task state, not connector state — this is the single most common Connect monitoring gap, and it presents as "the connector is running but no data is moving."

Source offsets live in Kafka, in an internal topic. That is what makes a source connector resumable, and it means restoring a Connect cluster without those internal topics will re-read the source from the beginning. Include them in whatever you consider a backup.

So what did we actually gain?

A way to integrate the systems around Kafka without an application per integration — and a clear boundary for when that stops being the right shape. Reusable integration infrastructure at the edges, custom services where the logic actually lives.
