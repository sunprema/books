The 30-second summary

If you remember six things

1. Ordering is per partition, and the key chooses the partition — so the key is your ordering promise.
2. acks=all + RF 3 + min.insync.replicas=2, or you do not have durability.
3. At-least-once is the default; every consumer with a side effect needs idempotency.
4. Add fields with defaults; never reuse a deleted field name.
5. Exactly-once means Kafka-to-Kafka only.
6. Compaction is not deletion and has no deadline.

Topic-design checklist

  • Name — follows the convention; the prefix maps to a team
  • Owner — one team, recorded, with registry permissions to match
  • Key — states the ordering scope you are promising
  • Partitions — measured, not guessed; good divisors; room to grow
  • Retention — derived from recovery, bootstrap and compliance needs
  • Cleanup policy — delete for history, compact for state
  • Classification — does it carry personal or regulated data?
  • ACLs — producers, consumers (topic and group), monitoring
  • Schema subject — naming strategy chosen deliberately
  • Compatibility tier — matched to criticality and replay needs
  • SLAs — availability, and consumer time-behind targets

Event-schema checklist

  • Identifiers — opaque and stable; not database surrogate keys
  • Event id — unique per emission, usable as a dedup key
  • Timestamps — occurredAt distinct from recordedAt; micros not millis
  • Correlation and causation ids present
  • Tenant and actor present, if they could ever matter
  • Sequence number per aggregate, if gaps must be detectable
  • Semantic documentation in doc: units, inclusivity, what absent means
  • Defaults on every optional field; null first in the union
  • Enum defaults declared, so symbols can be added later
  • Decimals with generous scale and a currency alongside
  • PII classified, minimised, and ideally on a separate topic
  • Evolution plan — what is likely to change, and how it will

Consumer reliability checklist

  • Idempotency — natural, conditional write, or a processed-event store
  • Failure classification — transient vs permanent, retried differently
  • Retries — fast in-line only; slow retries via retry topics
  • Dead-letter topic — with context headers, monitored, with a replay tool
  • Offset commits — manual, after processing
  • Observability — lag per partition, processing latency, rebalance rate
  • Replay safety — what happens on a reset to earliest?
  • Side-effect isolation — replayable and non-replayable in separate consumers
  • Backpressure — bounded in-flight work; no unbounded internal queue
  • Poison-pill alert — lag climbing while throughput is zero

Glossary

ISR
In-sync replicas — the replicas currently caught up with the leader. acks=all and min.insync.replicas are both stated over this set, and it shrinks and grows at runtime.
High water mark
The offset up to which all in-sync replicas have replicated. Consumers cannot read past it, so unreplicated data is never observable.
LEO
Log end offset — the offset of the next record to be appended to a replica's log. The leader's LEO is ahead of the high water mark whenever replication is in flight.
LSO
Last stable offset — the lowest offset of any open pending transaction. A read_committed consumer reads only below it, which is why a long transaction stalls readers.
Compaction
A cleanup policy retaining at least the latest value per key. Works only on closed segments, is threshold-driven, and guarantees nothing about timing.
Tombstone
A record with a null value on a compacted topic, marking a key deleted. Retained for delete.retention.ms so offline consumers can still observe the deletion.
Rebalance
Redistribution of partitions among a consumer group's members. Usually triggered by processing exceeding max.poll.interval.ms, not by real failure.
Consumer lag
Latest produced offset minus the group's last committed offset. Alert on time-behind, diagnose with record count.
Schema subject
The registry's unit of versioning and compatibility policy. How subjects are named (topic, record fullname, or both) sets the blast radius of a schema change.
Writer / reader schema
The schema used to write the bytes, and the one the reader wants. Avro resolution reconciles them; compatibility policy constrains the pair so resolution cannot fail.
Transactional offset commit
Committing consumer offsets as part of a producer transaction, so output records and input progress become atomic. Requires enable.auto.commit=false.
Share group
KIP-932's queue-like cooperative consumption — several consumers reading one partition with per-record acknowledgement. Removes the partition-count ceiling; gives up per-partition ordering.
Repartition topic
An internal topic Kafka Streams inserts when an operation changes the key, so records sharing the new key reach the same instance.
Changelog topic
A compacted internal topic backing a Kafka Streams state store, allowing state to be restored on another instance.
