Part II · The core design philosophies

Correctness, Extensibility, and Open Interfaces

Designing around invariants, stable cores, and open protocols

The philosophies so far have been about what to build. This one is about what to promise — because a product that lasts decades is mostly a set of promises, and the design question is which promises you can afford to keep forever.

Start from an invariant you can say out loud

An invariant is a property your system guarantees in every state it can reach. The useful ones fit in one sentence. Git’s: an object’s name is the hash of its content. Kafka’s: within a partition, records are totally ordered and an offset identifies exactly one record. SQLite’s: a transaction commits atomically, and the file format stays readable forever. Sentences this short do enormous work, because every feature discussion can be tested against them cheaply: does this proposal preserve the sentence, or break it? A design team with a crisp invariant has a shared “no” machine. A team without one re-litigates correctness feature by feature, and loses by erosion.

Watch Git’s sentence cash out. Because names are content hashes, verifying one tip hash verifies an entire history — every commit, every tree, every byte — no matter which mirror, transport, or stranger’s laptop delivered it. Trust in the hosting becomes unnecessary because integrity rides in the data. One invariant, chosen in week one by a man famous for trusting nobody, and twenty years of hosting providers have been unable to corrupt a repository without detection.

The end-to-end argument: put guarantees where they’re real

Where should a guarantee live? The classic answer is Saltzer, Reed, and Clark’s 1984 paper “End-to-End Arguments in System Design,” and it’s the rare academic principle that reads like hard-won operational advice. If a function can only be implemented completely and correctly with the knowledge of the application at the endpoints, then building it into the lower layer cannot, by itself, deliver the guarantee — at best it’s a performance optimization. Their example: careful file transfer. The network can checksum packets all it likes, but only the endpoints can verify the file arrived intact, because corruption can happen before and after the network ever sees a byte.

Git’s integrity design is the end-to-end argument executed perfectly: the verification travels with the content, so every intermediary becomes untrusted plumbing. And the argument generalizes into a daily design heuristic: for each guarantee you’re about to promise, ask which layer can actually keep it? Guarantees stationed at the wrong layer are the most expensive kind of decoration.

Stable core, open edge

Invariants give you the second structural move of this philosophy: split the system into a small core that embodies the invariants and changes glacially, and an edge where variety and churn are welcome. Git calls the layers plumbing and porcelain — the object model froze in 2005 while the UI above it was rebuilt repeatedly. SQLite’s frozen file format is the core; the library around it evolves continuously. Kafka’s partition-ordering contract is the core; brokers, storage engines, and whole reimplementations churn around it.

And the edge can open all the way: publish the contract and let strangers implement it. That’s when an interface stops being your API and becomes infrastructure. Kafka’s wire protocol is now a de facto standard — Redpanda, WarpStream, and others reimplement it from scratch, inheriting a decade of client libraries by speaking it (Redpanda documents compatibility with Apache Kafka 0.11 onward, exceptions listed). Note the mechanism that makes a protocol able to live that long: Kafka clients begin every connection by asking the broker which API versions it speaks. Explicit versioning, negotiated up front — evolution designed in, not bolted on.

A product is temporary; a protocol with independent implementations is permanent.

The tax on openness: Hyrum’s Law

Opening the edge has a price, and it has a name. Hyrum’s Law: with a sufficient number of users, it does not matter what you promise in the contract — all observable behaviors of your system will be depended on by somebody. Your accidental ordering, your timing, your quirky error message: load-bearing, all of it, the moment enough strangers build on you. The lesson isn’t “don’t open up.” It’s that everything observable is de facto interface, so shrink what’s observable: tight contracts, deliberate noise where you want freedom (randomized iteration orders are a vaccine against Hyrum), and the humility to know the ecosystem now co-owns your roadmap.

Correctness is earned, not declared

Finally, the unglamorous leg holding up the other two. Promises this strong must be kept, mechanically, forever — and the case study is SQLite, which backs its invariants with one of the most extreme test regimes in software: millions of test cases, 100% branch coverage of the core, simulated crashes and I/O failures, each release tested more thoroughly than most products are in their lifetime. That discipline is why a library embedded in two billion devices can promise its file format forever. There’s a quiet inversion here worth savoring, because it closes a loop from chapter 4: “worse is better” wins the adoption game, but the systems that become civilization’s load-bearing walls tend to be the ones that then paid the “right thing” bill in full — on the invariants, where it counts, and nowhere else.

Key idea

The order of operations is the philosophy: choose invariants you can state in a sentence → station them at the layer that can actually keep them → freeze the smallest core that embodies them → open everything else → and spend your testing budget exactly where the promises are.

So what did we actually gain? The fourth philosophy: products endure by promising little, crisply, at the right layer — and opening the rest. Part II’s survey is complete. Part III turns all four lenses toward the blank page: finding the problem worth this kind of design.
