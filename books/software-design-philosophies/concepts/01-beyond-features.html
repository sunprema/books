Introduction

Beyond Features

What actually made Git, Kafka, DuckDB, and SQLite win

Here’s a question worth sitting with before we write a line of design doc: why do some software products not just succeed, but become the obvious way to do something — so obvious that we forget there was ever another way?

Nobody chooses Git because of a feature comparison chart. Nobody picks SQLite after a bake-off of administration consoles — it doesn’t have one, and that’s the point. These products won something deeper than a feature war. They changed what their users think the problem is. Before Git, version control meant asking a server for permission to see your own history. After Git, history is a graph you hold in your hands. Before Kafka, data in motion was something you routed and lost; after Kafka, it’s something you keep. That shift — from solving a problem to reframing it — is what this book is about.

Meet the cast

We’ll keep coming back to the same five systems, because they’re the clearest specimens we have, and because you almost certainly use all of them — sometimes without knowing it:

  • Unix — the 1970s operating system whose design maxims (“make each program do one thing well”) still govern how we compose tools half a century later.
  • Git (2005) — born in roughly a week of furious work. Linus Torvalds’ first commit calls it, with a grin, “the information manager from hell” — and contains almost no features at all. Just a data model and seven small programs.
  • SQLite (2000) — a complete SQL database in a library, no server, no configuration. By its own count the most widely deployed database engine in the world: it’s in every phone in your house.
  • Kafka (2011) — LinkedIn’s answer to drowning in point-to-point data pipelines. Its heart is one structure: the append-only log.
  • DuckDB (2019) — “SQLite for analytics.” Its launch paper opens not with features but with a gap in the map: people clearly want in-process databases, and nobody had built one for analytical work.

We explain success backwards

When a product wins, we tell its story as a checklist: Git was fast, Git was distributed, Git had cheap branches. All true — and all consequences, not causes. Git’s speed, distribution, and cheap branching each fall out of one decision underneath: store immutable snapshots, name them by the hash of their content. The features are the shadow the design casts. Study the shadow and you’ll learn to imitate shadows.

This backwards habit matters for builders, because it suggests the wrong recipe. If you believe features cause success, the way to build the next Git is to accumulate features. The record says otherwise: the initial Git commit had no branches, no remotes, no status, not even a commit command you’d recognize — and yet it already contained the entire product, the way an acorn contains an oak. What it had was a data model worth growing.

A great product is a position in an argument about what the problem really is.

So what’s a “design philosophy”?

Not a mission statement, and not taste. A design philosophy, as we’ll use the term, is a small set of load-bearing commitments that decide the hard calls before they arrive. SQLite’s documentation does something most products would never dare: it lists, prominently, the situations where you should not use SQLite — many concurrent writers, client/server access over a network. That page is a philosophy made visible. The commitment (“we compete with fopen(), not with Postgres”) tells the maintainers which features to refuse, and refusing features is the hardest and most valuable thing a philosophy does.

Key idea

You can tell a real design philosophy from a slogan by one test: does it ever say no to a reasonable request? A philosophy that permits everything decides nothing.

There’s a second, stranger property: a good philosophy often ships less than its competitors and wins anyway. Richard Gabriel noticed this back in 1989 and gave it a deliberately uncomfortable name — “worse is better.” Unix and C, he argued, spread like viruses precisely because they kept their implementations simple and let completeness suffer. The polished, complete, “right thing” systems of the day were still being perfected while Unix was already everywhere. We’ll return to this tension; it’s one of the live wires of the whole subject.

The plan for this book

We’ll work the way a good builder works: understand the machine before redesigning it.

  • Part I (chapters 2–3) builds our two analytical lenses: the mental model a product imposes, and the primitive it’s built around.
  • Part II (chapters 4–7) surveys four recurring philosophies — simplicity & composition, embedded-first, log-centric time, and invariant-driven openness — each grounded in our case studies, each with its honest failure modes.
  • Part III (chapters 8–9) turns the lenses around: how to find the hidden problem in your own domain, and how to get from a philosophy to a product someone adopts.
  • Chapter 10 closes the loop: principles as tools for reasoning, not rules to obey.

One warning before we start. None of these philosophies is correct. They conflict with each other on purpose — embedded-first argues with distributed systems, omission argues with completeness — and every great product we’ll study is a particular, opinionated resolution of those conflicts. The goal is not to hand you the right answers. It’s to make the arguments explicit enough that you can run them yourself, on your own problem.

So what did we actually gain? A working definition — a design philosophy is the set of commitments that decides what a product refuses to do — and a cast of five systems to test it against. Next: the first lens, mental models.
