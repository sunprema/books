Part II · The core design philosophies

Embedded First, Distributed When Necessary

SQLite and DuckDB — the philosophy of deleting the server

Our second philosophy asks a question most architectures never pause on: does this capability need to be somewhere else? Every “somewhere else” in a design — another process, another machine, another team’s cluster — is a tax collected forever. Embedded-first design starts from zero infrastructure and makes distribution justify itself.

Name the tax first

Let’s itemize what a client/server boundary actually costs, because almost none of it shows up in benchmarks. You pay in configuration: something must be installed, addressed, and credentialed. In operations: the server is now a thing that can be down, so someone owns it, patches it, and wakes up for it. In latency shape: every interaction crosses a socket, so chatty access patterns are punished and you contort your code into batches. And in failure modes: the network’s partial failures seep into what used to be a function call. None of these costs buys your user anything. They are pure overhead — unless, of course, the boundary is doing a job.

SQLite: the database as a file

SQLite’s self-description is a string of refusals: self-contained, serverless, zero-configuration. The whole database — tables, indices, triggers, views — is one ordinary disk file, read and written directly by a library linked into your program. There is no process to start, no port, no user accounts, no “setup.” And its documentation draws the philosophy’s boundary with a candor worth studying: SQLite doesn’t compete with client/server databases, it says — it competes with fopen(). The same page lists exactly when you should use something else: many concurrent writers, clients arriving over a network, data larger than one disk.

Holding the problem at “a file” is what made SQLite the most widely deployed database engine on Earth — in every Android and iOS device, every major browser, countless appliances. Not because it beat the servers at their game, but because it noticed how much of the world never needed the server game at all. An application file format, an on-device store, a cache: these wanted a smarter file, and a smarter file is what they got.

DuckDB: the same move, replayed for analytics

What makes this a philosophy rather than one product’s trick is that the move replays. DuckDB’s SIGMOD 2019 paper opens with the gap: SQLite’s ubiquity proves the demand for in-process data management, yet nothing like it existed for analytical workloads. The analyst’s center of gravity is a Python or R process; the data is a pile of files; so put a columnar, vectorized OLAP engine in the process. Twenty years of warehouse architecture — deleted, for the workloads that fit. The engine is different everywhere it should be (columns, not rows; vectors, not tuples) and identical where it counts: it’s a library.

The empirical leg: most data is small

The philosophy got a provocative empirical defense in 2023 from Jordan Tigani — a founding engineer of Google BigQuery, which gives the argument its bite — in an essay titled “Big Data is Dead.” His claim, from years of watching real customer workloads: most organizations’ analytical data is far smaller than the big-data era assumed, most queries touch mostly recent data, and a single modern machine is absurdly capable — so the distributed warehouse is, for the typical workload, machinery without a mission. Full disclosure belongs in the same breath: Tigani was selling the alternative (his company, MotherDuck, builds on DuckDB), the percentages are internal estimates rather than independent measurements, and the company itself has since softened the framing. Treat it as strong testimony from a credible witness, not a theorem.

Key idea

The philosophy’s ordering matters more than either endpoint: start embedded, and let measured need — not anticipated scale — argue you across each boundary. The failure mode it prevents is paying the distributed tax on day one for scale that never arrives.

The cheapest infrastructure to operate is the infrastructure that doesn’t exist.

The honest boundary

Where does embedded-first genuinely end? At shared mutable state with many concurrent writers — the one job a library-plus-file cannot do, because coordinating writers scattered across machines is precisely what a server is. SQLite says this about itself, plainly. Note the asymmetry, though: sharing reads stopped requiring a server years ago (ship the file; put Parquet on object storage and point DuckDB at it), and single-writer-many-readers patterns stretch surprisingly far. The honest boundary is narrower than the industry’s habits assume — but it exists, and pretending otherwise is how embedded-first curdles into dogma.

There’s also a quieter cost inside the boundary: an embedded engine ships inside someone else’s process, so your bug is their crash, your upgrade rides their release train, and your testing burden is brutal — a theme we’ll meet again in chapter 7 when we look at how SQLite earns the right to be trusted in two billion pockets.

So what did we actually gain? A philosophy with a direction of travel: itemize the boundary tax, start at zero infrastructure, and cross each boundary only on measured evidence — plus the honest limit (many concurrent writers) where the server earns its keep. Next: a philosophy about time itself.

Sources: sqlite.org, “About SQLite” and “Appropriate Uses For SQLite”; Raasveldt & Mühleisen, “DuckDB: An Embeddable Analytical Database” (SIGMOD 2019); J. Tigani, “Big Data is Dead” (MotherDuck, 2023).
