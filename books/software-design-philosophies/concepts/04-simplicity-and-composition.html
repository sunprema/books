Part II · The core design philosophies

Simplicity and Composition

The Unix philosophy — small tools, clear interfaces, deliberate omission

The first great design philosophy in our survey is also the oldest, and it fits on an index card. It was written down in 1978, in the Bell System Technical Journal’s special issue on Unix, by Doug McIlroy — the man who invented the pipe.

The index card

McIlroy’s maxims, lightly compressed: make each program do one thing well; to do a new job, build afresh rather than complicate an old program with new “features”; expect the output of every program to become the input to another, so write programs that handle text streams, and don’t clutter output with extraneous information. (The slogan everyone quotes — “write programs that do one thing and do it well” — is McIlroy’s own later summary, polished by retelling; the 1978 text is plainer and more practical.)

Notice this is not one principle but two, locked together. Simplicity: each tool does one job. Composition: tools connect, so the jobs add up. Neither works alone. A thousand small tools that can’t connect is a junk drawer; a composition system with bloated parts is a monolith with pipes drawn on it. The genius of the design is the shared carrier that locks them together: everything speaks text streams over file descriptors. The interface so universal nobody has to negotiate it.

Deliberate omission is the active ingredient

It’s tempting to read “do one thing well” as modesty. It’s the opposite — it’s refusal, practiced as a discipline. grep declines to sort; sort declines to filter; both decline to understand your file format. Every refusal keeps a tool’s interface small enough that the carrier stays sufficient. The moment one tool grows a private binary format or a “convenient” built-in version of its neighbor’s job, it opts out of the ecosystem and starts the slide toward monolith.

We’ve seen this philosophy restated twice already in this book, by designers who’d recognize each other instantly. SQLite’s “we compete with fopen()” is deliberate omission — a database refusing to be a server. And Hickey’s “Simple Made Easy” is the index card generalized: compose simple (un-braided) parts, rather than taking pride in your ability to manage complected ones. Simplicity, in both tellings, is not a beginner’s virtue. It is, in Hickey’s phrase, serious work.

Why the modest version won

Here’s the uncomfortable history. In 1989, Richard Gabriel — a Lisp designer, from the losing side — set out to explain why elegant, complete systems like Common Lisp kept losing to Unix and C. His essay, “The Rise of ‘Worse is Better’,” contrasts two schools. The MIT “right thing” school ranks interface simplicity, correctness, and completeness first. The “New Jersey” school (Bell Labs is in New Jersey) ranks implementation simplicity first — and will sacrifice completeness, even a little correctness at the edges, to keep it. Gabriel’s deliberately scandalous conclusion: the New Jersey approach wins. Simple implementations are easy to port, easy to ship, easy to fix in the field — they spread like viruses, and by the time the right thing is finished, the worse thing is everywhere and improving.

Key idea

Simplicity is not only an aesthetic — it’s a distribution strategy. A design simple enough to implement everywhere gets implemented everywhere. We’ll lean on this hard in chapter 9.

Each tool’s refusal is what keeps the whole system able to say yes.

When simplicity becomes a limitation

A philosophy you can’t criticize is a religion, so let’s be adults about the costs. The Unix carrier is untyped text, which means every consumer re-parses what its producer just serialized — and every pipeline silently depends on whitespace conventions, locale behavior, and column orders that nothing checks. The system pushed its complexity outward, onto ten thousand fragile awk incantations. (Half a century on, PowerShell’s typed objects and the --json flags sprouting on modern CLIs are direct admissions of this bill coming due.)

Second cost: some problems refuse to decompose along pipe lines. A transaction, a GUI, a distributed consensus round — these need shared state or rich bidirectional contracts, and chaining small tools gives you neither. And third: “build afresh” erodes. Tools accrete flags (count ls’s sometime), because in the real world shipping a flag is cheaper than shipping a new tool. Deliberate omission, it turns out, requires a maintainer willing to keep refusing — the philosophy lives in people, not in the architecture.

So the mature reading of the index card is conditional: where a domain has a natural carrier and jobs that chain, small-and-composable beats integrated — and where it doesn’t, forcing the pattern just relocates the complexity to the joints. Judging which situation you’re in is the actual skill, and it’s the reason this chapter is lens-work, not law.

So what did we actually gain? The first core philosophy, as two locked principles — one job per part, one carrier for all parts — powered by refusal, and a clear view of its bill: untyped joints, undecomposable problems, and the erosion of “no.” Next: a philosophy about where code should live.

Sources: M. D. McIlroy et al., Bell System Technical Journal 57:6 (1978), foreword maxims; P. Salus, A Quarter-Century of Unix (1994); R. Gabriel, “The Rise of ‘Worse is Better’” (1989); R. Hickey, “Simple Made Easy” (2011); sqlite.org, “Appropriate Uses For SQLite”.
