04

Structured concurrency and scoped values

Chapter 3 ended with a fan-out that worked and two holes it could not close: a failed call did not stop its siblings, and nothing bounded the request as a whole. This chapter closes both. One of the two features doing that is final on Java 25. The other is not, and this chapter will not let you forget it.

Read this before you write any of it

Scoped values are final on Java 25 (JEP 506). Use them freely.

Structured concurrency is still preview on Java 25 (JEP 505, the fifth preview). It needs --enable-preview at compile time and at run time, it is not covered by any compatibility guarantee, and its API has changed in every LTS-adjacent release it has appeared in — including once more after Java 25. Every StructuredTaskScope snippet in this chapter carries that label.

By the end of this chapter you will be able to
  • express a fan-out as a single unit of work with one deadline and one failure policy;
  • choose the right Joiner for "all must succeed" versus "first one wins";
  • carry request, tenant and trace context to every subtask without a parameter or a ThreadLocal;
  • state exactly what adopting the preview API costs you, and decide whether to pay it.

The fan-out that will not stop

Here is Chapter 3's aggregator again, and here is what it does when things go wrong.

Works; leaks
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    var catalog = exec.submit(() -> catalogClient.find(sku));
    var price   = exec.submit(() -> pricingClient.find(sku));
    var stock   = exec.submit(() -> inventoryClient.find(sku));

    return new Product(catalog.get(), price.get(), stock.get());
}
Make a Prediction

The catalog service returns a 500 after 10 milliseconds. Pricing and inventory are healthy but slow — 30 seconds each today, because a downstream cache is cold. The user has already been shown an error.

What are pricing and inventory doing at second 25?

Answer Still running. catalog.get() threw, the return never happened, and close() is now waiting for the other two to finish before it will let the method exit. Your request thread is stuck for thirty seconds serving a response nobody will see, and the two connections are held that whole time. Under load, this is how a single sick dependency takes out a healthy service.

Both defects have the same root cause: the three tasks are related in your head and unrelated to the runtime. Nothing ties their lifetimes together, so nothing can cancel them together or time them out together.

Your Brain on structured concurrency

You already trust this idea everywhere except concurrency. A method call cannot outlive its caller. A try block cannot leave a file open past its closing brace. Control flow in sequential Java is a tree, and the shape of the tree is the shape of the code.

Then you call submit() and the tree becomes a pile. The task's lifetime is now unrelated to the block that started it — it can outlive the method, the request, the exception handler.

Structured concurrency puts the tasks back in the tree. A scope is a block; subtasks forked inside it cannot outlive it, in the same unremarkable way a local variable cannot. Once that is true, "cancel the siblings" and "one deadline for the whole thing" stop being features you implement and start being properties of the block.

A scope is a block

Same aggregation, as one unit of workPreview on 25:

PREVIEW on Java 25 — compile and run with --enable-preview
import java.util.concurrent.StructuredTaskScope;
import java.util.concurrent.StructuredTaskScope.Joiner;
import java.util.concurrent.StructuredTaskScope.Subtask;

Product lookup(String sku) throws Exception {
    try (var scope = StructuredTaskScope.open(
             Joiner.<Object>awaitAllSuccessfulOrThrow(),
             cf -> cf.withName("product-lookup")
                     .withTimeout(Duration.ofSeconds(2)))) {

        Subtask<CatalogEntry> catalog = scope.fork(() -> catalogClient.find(sku));
        Subtask<Price>        price   = scope.fork(() -> pricingClient.find(sku));
        Subtask<Stock>        stock   = scope.fork(() -> inventoryClient.find(sku));

        scope.join();                       // one wait; throws if any subtask failed

        return new Product(catalog.get(), price.get(), stock.get());
    }   // close() cannot be reached with a subtask still running
}

Replay the failure. Catalog fails at 10ms; join() immediately cancels the scope, which interrupts pricing and inventory, and throws. Total elapsed: about 10 milliseconds, with nothing left running. And if all three are merely slow, the two-second timeout cancels the scope for you.

The shape is always the same three beats: fork everything, join once, then read results. Subtask.get() is only legal after join(), and only on a subtask that succeeded — call it early and you get IllegalStateException rather than a race.

Joiners: the policy, named

The first argument to open is a Joiner, and it encodes what "done" means for this scope. Picking it is the whole design decision.

Joiners on JDK 25 (preview API)
JoinerFinishes whenUse for
allSuccessfulOrThrow()all succeed — cancels and throws on the first failurea fan-out where every part is required
anySuccessfulResultOrThrow()the first success — throws only if all failracing replicas or mirrors
awaitAllSuccessfulOrThrow()all succeed; join() returns null, results read per subtasksubtasks with differing result types

When every subtask has the same result type, allSuccessfulOrThrow() is the tidier choice, because join() hands you the results directly:

PREVIEW on Java 25 — racing several quote providers
try (var scope = StructuredTaskScope.open(Joiner.<Quote>allSuccessfulOrThrow())) {
    for (String carrier : carriers) scope.fork(() -> quoteFrom(carrier, request));

    return scope.join()              // Stream<Subtask<Quote>> on JDK 25
                .map(Subtask::get)
                .toList();
}
This exact line changes in JDK 26

On JDK 25, join() with allSuccessfulOrThrow() returns a Stream<Subtask<T>>. JEP 525 — structured concurrency's sixth preview, in JDK 26 — changes it to return a materialized List<T> in fork order, so the .map(Subtask::get) disappears.

That is a small change and a good one. It is also the fourth API revision in a row, and the reason this book will not tell you the API has settled. If you adopt structured concurrency now, adopt it behind a thin interface of your own, so the migration is one class rather than every service.

Scoped values: context without a parameter

Now the other half, and the reassuring half: scoped values are final on Java 25Final Java 25. No flag, no caveat.

The problem they solve is old. A request has a trace id and a tenant. Twelve methods down the call stack, something needs the trace id. Your options used to be threading a parameter through all twelve signatures, or a ThreadLocal — which is mutable from anywhere, easy to leak on a pooled thread, and multiplies badly across a million virtual threads.

Final on Java 25 — no --enable-preview
public static final ScopedValue<RequestContext> CONTEXT = ScopedValue.newInstance();

void handle(HttpExchange exchange) {
    var ctx = new RequestContext(traceIdOf(exchange), tenantOf(exchange));

    ScopedValue.where(CONTEXT, ctx).run(() -> route(exchange));
}   // binding is gone the moment run() returns — guaranteed, even on exception

void audit(String action) {                     // twelve frames deeper
    log.info("[{}] {}", CONTEXT.get().traceId(), action);
}

Three properties make this better than a ThreadLocal, and they all come from the same design choice — the binding is one-way and bounded:

ThreadLocal versus ScopedValue
ThreadLocalScopedValue
Mutationset() from anywherenone — bind at the scope, read below it

Leaks on a pooled threadyes, classicallynot expressible

That last row is the payoff of pairing the two features. A subtask forked inside a StructuredTaskScope inherits the scope owner's scoped-value bindings, so the trace id reaches the catalog call, the pricing call and the inventory call without appearing in a single signature.

A ThreadLocal is a variable that happens to be per-thread. A scoped value is a parameter that happens not to be written down.

What Could Go Wrong?

You ship the preview API without deciding who owns it. --enable-preview is not a compiler flag you set once — it must be on for compilation and for every JVM that runs the artifact, and class files compiled with preview features are rejected by a different JDK version outright. That is a deployment-wide decision, not a per-module one.

You call Subtask.get() before join(), or on a subtask that failed. Both throw IllegalStateException. Fork, join, then read — in that order, always.

You read a scoped value outside its extent. get() throws NoSuchElementException. If the value is genuinely optional, use isBound() or orElse(fallback) — and note that in the finalized Java 25 API, orElse no longer accepts null.

You try to mutate a scoped value. There is no set(). To change the value for part of the call tree, nest another where(...).run(...); the inner binding shadows the outer one and unwinds at the inner block's end.

You wrap a scope in a catch that swallows. Cancellation reaches subtasks as an interrupt. Code that catches InterruptedException and continues will defeat the timeout you just added.

Code Surgery

A team migrating off ThreadLocal wrote this. It compiles. It is wrong in two ways.

static final ScopedValue<String> TENANT = ScopedValue.newInstance();

void handle(Request r) {
    ScopedValue.where(TENANT, r.tenant()).run(() -> {
        executor.submit(() -> reindex(r));      // (1)
    });
}

void reindex(Request r) {
    String t = TENANT.orElse(null);             // (2)
    index.write(t, r);
}

(1) The task is submitted to an unrelated executor, so it runs on a thread outside the binding's extent — and run() returns as soon as submit() does, unbinding the value while reindex is still queued. TENANT will not be bound when the task actually runs. Scoped values are inherited by subtasks forked in a StructuredTaskScope, not by anything handed to an arbitrary executor.

(2) orElse(null) is not permitted in the finalized Java 25 API. It was also hiding the bug in (1): a null tenant silently indexed into the wrong place instead of failing loudly.

The repair: fork inside a scope so the binding is inherited and the work cannot outlive the request, and let get() throw if the value is genuinely required:

// PREVIEW on Java 25
ScopedValue.where(TENANT, r.tenant()).run(() -> {
    try (var scope = StructuredTaskScope.open(Joiner.<Void>awaitAllSuccessfulOrThrow())) {
        scope.fork(() -> { reindex(r); return null; });
        scope.join();
    } catch (Exception e) { throw new RuntimeException(e); }
});

If the reindex genuinely should outlive the request, then it is not request-scoped work and the tenant belongs in its payload — pass it as a parameter, honestly.

Under the Hood

A scope owns its subtasks: fork refuses from any thread other than the owner, and close is what enforces the structural rule. Because close cannot return while a subtask runs, "leaked subtask" is not a state the API can be talked into.

Cancellation is cooperative and rides on interruption. When the joiner decides the scope is finished — a required subtask failed, the timeout fired — the remaining subtasks are interrupted. A subtask blocked in a JDK blocking call notices immediately; a subtask spinning on a CPU loop that never checks its interrupt status will not. Structured concurrency gives you the mechanism, not immunity from ignoring it.

Scoped-value bindings are held on the thread as a small immutable stack of bindings rather than a mutable map, which is why binding is cheap, reads are fast, and a subtask can inherit the whole set by sharing it rather than copying. Immutability is not a style preference here — it is what makes the sharing safe.

Both features were designed alongside virtual threads and assume them. On platform threads they work, but the economics that motivate them — a thread per task, a million of them — do not apply.

  2. Rewrite it with StructuredTaskScope and awaitAllSuccessfulOrThrow(). Compile and run with --enable-preview --release 25. Time it again. (Fifty milliseconds.)
  3. Add withTimeout(Duration.ofSeconds(1)) and remove the failing task. Confirm the scope gives up at one second rather than five.
  4. Bind a ScopedValue outside the scope and read it inside each subtask. Confirm it is visible. Then move one task to a separate executor and confirm it is not — the failure mode from Code Surgery, reproduced deliberately.
Chapter project — part 4 of 7

Two changes to the aggregator, and one decision.

Add the context (final API, safe to ship): a ScopedValue<RequestContext> bound once in the HTTP handler, read by the logging and metrics code, never passed as a parameter.

Add the scope (preview API): replace the three submit calls with three fork calls inside a StructuredTaskScope carrying a 2-second timeout, so a failed catalog call cancels pricing and inventory.

The decision is the real exercise. Write down, in two sentences you would be willing to show a tech lead, whether your team should run --enable-preview in production for this. There is no correct answer — there is only a decision made deliberately or by accident. If the answer is no, keep the executor version from Chapter 3 and add a plain per-call timeout; you will lose sibling cancellation and get it back on the release that finalizes the API.

Fast Recap
  1. A StructuredTaskScope makes concurrent tasks a block: fork everything, join() once, then read results.
  2. The Joiner is the failure policy — allSuccessfulOrThrow, anySuccessfulResultOrThrow, awaitAll, allUntil.
  3. withTimeout applies one deadline to the whole scope; failure or timeout cancels the surviving subtasks by interrupt.
  4. Structured concurrency is preview on Java 25 (JEP 505) and changes again in JDK 26 (JEP 525) — wrap it behind your own interface if you adopt it.
  5. Scoped values are final on Java 25 (JEP 506): bind with where(...).run(...), read with get(), never mutate, and orElse(null) is not allowed.
  6. Subtasks forked in a scope inherit scoped-value bindings; tasks handed to an unrelated executor do not.
