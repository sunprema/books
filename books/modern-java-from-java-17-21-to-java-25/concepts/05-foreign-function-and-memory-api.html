Foreign Function & Memory API

Calling C from Java used to mean JNI: a header generator, a C shim, a native build in your pipeline, and a class of bug where the JVM does not throw an exception because the JVM is no longer running. The FFM API replaces all of that with ordinary Java — and, more importantly, turns the worst failure mode into a stack trace.

By the end of this chapter you will be able to
  • call a C function from plain Java with no native build step;
  • allocate and free off-heap memory deterministically with an Arena;
  • explain why use-after-free is an exception here and undefined behaviour in JNI;
  • decide when not to reach for this API — which is most of the time.

The old bargain

Suppose you need one function from a C library. With JNI, "one function" costs you: a native method declaration, a generated header, a C file implementing it, a compiler and toolchain per target platform, a shared library shipped alongside your jar, and System.loadLibrary at the right moment. Every one of those is a place for the build to break on somebody else's machine.

And then there is the memory. JNI hands you raw pointers. So did sun.misc.Unsafe, which is how half the ecosystem did off-heap work for a decade.

Make a Prediction

You allocate an off-heap buffer, free it, and then — through a stale reference you forgot about — read from it. What does the JVM do?

Answer With Unsafe or a raw JNI pointer: whatever the operating system feels like. Usually you read someone else's data and carry on with a wrong answer. Occasionally you get a hard crash — a hs_err_pid file, no stack trace, no exception, the whole process gone. Debugging that is archaeology.

With the FFM API: IllegalStateException, with a stack trace pointing at the line that read too late. This is the feature. The convenience is nice; the safety is why it exists.

Your Brain on the FFM API

Two ideas, and everything else is detail.

A MemorySegment is a pointer that knows its own bounds and its own lifetime. A C pointer is just a number, so the language cannot tell a valid read from a wild one. A segment carries its size and a reference to the scope that owns it, so every access can be checked — spatially (am I inside the segment?) and temporally (is it still alive?).

An Arena is who decides when the memory dies. Not the garbage collector, not a finalizer — an object with a close(). Which means try-with-resources is your free(), and the compiler helps you place it.

Calling C, in full

Here is the whole thing — the canonical strlen callFinal Java 22. No C file, no header generator, no build plugin.

Complete and runnable — java --enable-native-access=ALL-UNNAMED Strlen.java
import java.lang.foreign.*;
import java.lang.invoke.MethodHandle;

public class Strlen {
    public static void main(String[] args) throws Throwable {

        Linker linker = Linker.nativeLinker();          // the platform ABI

        MethodHandle strlen = linker.downcallHandle(
            linker.defaultLookup().find("strlen").orElseThrow(),
            FunctionDescriptor.of(ValueLayout.JAVA_LONG,     // size_t return
                                  ValueLayout.ADDRESS));      // const char*

        try (Arena arena = Arena.ofConfined()) {
            MemorySegment cString = arena.allocateFrom("modern java");
            long len = (long) strlen.invokeExact(cString);
            System.out.println(len);      // 11
        }   // memory freed here, deterministically
    }
}

Read it as four moves. Get the linker for this platform's calling convention. Look up the symbol — defaultLookup() covers the libraries the JVM already has open, libc among them. Describe the C signature with ValueLayout constants. Then call it like any MethodHandle.

allocateFrom(String) is doing the fiddly part: copying the Java string into off-heap memory as a NUL-terminated UTF-8 sequence, which is what a char* means to C.

Arenas: choosing a lifetime

Every segment belongs to an arena, and the arena decides when the memory goes away. There are four, and picking the right one is most of the safety story.

The four arenas

Reach for ofConfined() unless you have a specific reason not to. It is the cheapest to check — no cross-thread coordination — and it is the one that makes the mistake in the prediction box impossible to miss:

The error you want
MemorySegment escaped;
try (Arena arena = Arena.ofConfined()) {
    escaped = arena.allocate(ValueLayout.JAVA_INT);
    escaped.set(ValueLayout.JAVA_INT, 0, 42);
}

escaped.get(ValueLayout.JAVA_INT, 0);
// IllegalStateException: Already closed

Access a confined segment from the wrong thread and you get WrongThreadException instead. Read past its end and you get IndexOutOfBoundsException. Three whole categories of native memory bug, converted into ordinary Java exceptions with ordinary stack traces.

The FFM API did not make native code safe. It made your side of the boundary safe, which is the half you were going to get wrong.

Two flags and a warning

Calling native code is a restricted operation: it can violate the JVM's own invariants, so the runtime wants it declared. Modules permitted to do it are named with --enable-native-access; unnamed code on the classpath uses ALL-UNNAMED.

Run it like this
java --enable-native-access=ALL-UNNAMED -jar app.jar
java --enable-native-access=com.example.imaging -m com.example.app/...

Leave it off today and you get a warning. JEP 472 is the standing plan to make it an error in a future release, so treat the warning as a deprecation notice with your name on it and pass the flag now.

This is the pinning exception from Chapter 3

A virtual thread executing a native frame — which is exactly what an FFM downcall is — cannot unmount from its carrier. That did not change in JEP 491, and it will not.

A quick strlen is irrelevant. A native call that blocks for 200ms, invoked from ten thousand virtual threads, will pin every carrier you have and stall the scheduler. If you must do slow native work under virtual threads, bound it with a semaphore sized well below the carrier count — the same technique as the connection pool, for the same reason.

What Could Go Wrong?

invokeExact is fussier than it looks. It is signature-polymorphic: the static types at the call site must match the FunctionDescriptor exactly. The cast in (long) strlen.invokeExact(seg) is not decoration — it is part of the signature. Drop it, or assign to an int, and you get WrongMethodTypeException at runtime. Use invoke (no Exact) if you want asymmetric conversions, and pay a little performance for it.

You describe the C signature wrong. Nothing checks your FunctionDescriptor against the real function — there is no header being read. Get size_t wrong and you will corrupt a return value silently. This is where jextract earns its keep.

You use ofShared() because it seemed easier. Shared arenas need cross-thread coordination to close safely, which is slower, and they let a segment escape to a thread you did not think about. Confined by default.

You reach for FFM at all. The most common mistake. A pure-Java library, however unfashionable, has no ABI, no platform matrix, and no way to take the process down. FFM is for when there is genuinely no Java implementation — a vendor SDK, a hardware interface, a codec nobody has ported.

Code Surgery

This wrapper compiles and passes its unit test. It fails in production under load.

private static final Arena ARENA = Arena.ofConfined();      // (1)
private static final MethodHandle HASH = lookupHash();

public long hash(String input) throws Throwable {
    MemorySegment seg = ARENA.allocateFrom(input);          // (2)
    return (long) HASH.invokeExact(seg);
}

(1) A confined arena is confined to the thread that created it — here, whichever thread first loaded the class. Every other thread calling hash gets WrongThreadException. The unit test passed because it was single-threaded.

(2) Worse: the arena is never closed, so every call leaks. This is a native memory leak, so it will not appear in a heap dump and your GC graphs will look fine right up until the container is OOM-killed.

The repair is to scope the arena to the call, which is what arenas are for:

public long hash(String input) throws Throwable {
    try (Arena arena = Arena.ofConfined()) {
        MemorySegment seg = arena.allocateFrom(input);
        return (long) HASH.invokeExact(seg);
    }
}

The MethodHandle is fine as a static — it holds no memory and is thread-safe. It is the arena that must be per-call. The general rule: a MethodHandle is a constant, an Arena is a resource.

Under the Hood

For structured data there is a second layer this chapter has skipped. A MemoryLayout describes a C struct — MemoryLayout.structLayout(JAVA_INT.withName("x"), JAVA_INT.withName("y")) — and from it you derive a VarHandle that reads or writes one named field at the right offset, with the right alignment, on the right platform. Hand-computing offsets is exactly the sort of thing that works on your laptop and not on the ARM box.

Calls go both ways. A downcall is Java calling C, as above. An upcall goes the other way: linker.upcallStub(...) turns a Java MethodHandle into a function pointer C can invoke, which is how you supply a callback to a native library.

jextract reads a C header and generates the whole binding layer — descriptors, layouts, var handles, the lot. It is part of Project Panama but is not shipped in the JDK; you download it separately. For anything larger than a handful of functions, use it rather than hand-writing descriptors.

Performance, roughly: a simple downcall is in the same range as a JNI call, sometimes better, because the linker can specialize the call site and there is no JNI environment marshalling. This is not a reason to switch, but it removes the last argument for staying.

Try This Now15 minutes
  1. Run the Strlen example above with java --enable-native-access=ALL-UNNAMED Strlen.java. It should print 11 with no build step at all.
  2. Remove the flag. Read the warning — that is what JEP 472 plans to turn into an error.
  3. Change (long) to (int). Observe WrongMethodTypeException, and note that it names both signatures.
  4. Move escaped.get(...) outside the try block, as in the earlier snippet, and confirm you get IllegalStateException. Take a second to appreciate that on the old API this same mistake had no stack trace.
  5. Try getpid (no arguments, returns int) on your own. It is a two-line change and it proves you have the pattern.
Chapter project — part 5 of 7

Here is an honest answer: your aggregator should not use this API. It calls three HTTP services. There is no native library in that picture, and adding one would be the mistake the last bullet of What Could Go Wrong? warns about.

So this chapter's contribution to the capstone is a decision rule, written into the project's notes rather than its code:

Reach for FFM when there is no pure-Java implementation and the native one is not optional — a vendor SDK, a hardware interface, a codec. Not for speed, not for novelty. When we do, the arena is per-call, the handle is static, --enable-native-access is in the launch script, and any call that can block is bounded by a semaphore because it pins a carrier.

If you want the exercise anyway, add a /health/host endpoint that returns the machine's hostname via a gethostname downcall — a genuine use of a C function with an out-parameter, and small enough to throw away. Then notice that InetAddress.getLocalHost() already did it, and delete your version. That is the lesson.

Fast Recap
  1. The FFM API is final since Java 22 and lives in java.lang.foreign — no JNI shim, no native build.
  2. Linker.nativeLinker() + SymbolLookup + FunctionDescriptor gives you a MethodHandle for a C function.
  3. An Arena owns memory lifetime; ofConfined() with try-with-resources is the default, and frees deterministically.
  4. Use-after-free is IllegalStateException, wrong thread is WrongThreadException, overrun is IndexOutOfBoundsException. That is the point of the API.
  5. Pass --enable-native-access; today it silences a warning, later it will be required.
  6. An FFM downcall is a native frame, so it pins a virtual thread — bound slow native calls explicitly.
  7. The handle is a constant; the arena is a resource. Never the other way round.
