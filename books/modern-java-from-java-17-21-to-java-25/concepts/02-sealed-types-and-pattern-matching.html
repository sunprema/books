Sealed types and pattern matching

Records let you say what a value is. Sealed types let you say what a value can be — the whole set, closed, no additions. Put the two together with pattern matching and you get something Java has never had before: a domain model where forgetting a case is a compile error.

By the end of this chapter you will be able to
  • model a closed set of outcomes with a sealed interface and record subtypes;
  • write an exhaustive switch that needs no default branch;
  • deconstruct records inside a switch with record patterns, including nested ones;
  • explain why adding a default throws away the feature's main benefit.

The chain that lies to you

Every codebase has one of these. A payment can be a card, a bank transfer, or cash, and somewhere there is a method that has to tell them apart.

The shape you have today
String describe(Payment p) {
    if (p instanceof Card c)          return "card " + c.last4();
    if (p instanceof BankTransfer b)  return "transfer from " + b.iban();
    if (p instanceof Cash)           return "cash";
    throw new IllegalStateException("unknown payment: " + p);   // the lie
}

That last line is a lie in two directions. It claims the situation is impossible, and it defers finding out to runtime — in production, in the one code path nobody tested, six months after someone added GiftCard.

Make a Prediction

A colleague adds a fourth payment type, GiftCard, and wires it through the parser. They do not touch describe. The project compiles. Tests pass, because no test constructs a GiftCard yet.

Now suppose Payment had been declared sealed and describe had been a pattern switch with no default. What happens instead?

Answer The project does not compile. The compiler reports that the switch does not cover GiftCard, pointing at the exact method, before the code is committed. That single behavioural difference is the whole reason to seal a hierarchy.

Closing the set

A sealed typeFinal Java 17 names the types allowed to extend or implement it. Everything else is rejected at compile time.

Payment.java — three permitted subtypes, no more
public sealed interface Payment
        permits Card, BankTransfer, Cash {}

public record Card(String last4, int expiryYear) implements Payment {}
public record BankTransfer(String iban)         implements Payment {}
public record Cash()                             implements Payment {}

Three rules govern this, and they exist to keep the set genuinely closed:

  • Every permitted subtype must itself be final, sealed, or explicitly non-sealed. There is no silent third option — if you want to reopen a branch of the hierarchy, you must write non-sealed and mean it.
  • Permitted subtypes must live in the same module as the sealed type (or, outside a module, the same package). Nobody can extend your closed set from their jar.
  • The permits clause may be omitted when all the subtypes are in the same source file — convenient for a small result type, and it keeps the whole domain visible at once.

Records as the permitted subtypes is the common shape, and not by accident: records give you transparent components, sealing gives you a closed set, and the next section is what happens when the compiler knows both.

Pattern matching, and the guarantee

Pattern matching for switchFinal Java 21 lets a case label be a type pattern instead of a constant. Record patternsFinal Java 21 go further and destructure the record in the label itself.

The same method, Java 21 and later
String describe(Payment p) {
    return switch (p) {
        case Card(String last4, int year) when year < 2026 -> "expired card " + last4;
        case Card(String last4, int ignored)               -> "card " + last4;
        case BankTransfer(String iban)                     -> "transfer from " + iban;
        case Cash c                                        -> "cash";
    };
}

Read what is not there. No default. No throw new IllegalStateException. No cast, and no call to last4() — the component is bound by the pattern. The switch is a switch expression, so every arm produces a value and the compiler checks that every arm does.

The guard, introduced by the contextual keyword when, is what lets two arms share a type and differ on a condition. Order matters: guarded arms go first, because the unguarded Card arm would otherwise match everything.

Nesting, and why it pays off

Record patterns nest. This is where the syntax stops being a nicety and starts removing real code — reaching three levels into a structure and checking a condition, in one label:

One label, three levels deep
record Line(Product product, int qty) {}
record Product(CatalogEntry catalog, Price price, Stock stock) {}

boolean isFreeGift(Line line) {
    return switch (line) {
        case Line(Product(var catalog, Price(var sku, var ccy, long minor), var stock), int qty)
             when minor == 0 && qty > 0 -> true;
        default -> false;
    };
}

Note that this switch does have a default, and correctly so: Line is not a sealed hierarchy, it is a single record, and the question being asked is a boolean test rather than a dispatch over a closed set. The rule is not "never write default". It is "never write default over a sealed hierarchy you want the compiler to police".

var is allowed in patterns, and it is worth using for components you are only passing through. The binding names are what the next reader will use to understand the label, so name the ones that matter and var the ones that do not.

What Could Go Wrong?

You add default "just to be safe". This is the mistake that costs the most. A default over a sealed hierarchy makes every switch trivially exhaustive, so the compiler stops checking, and the feature you sealed the type for is gone. If you genuinely need a fallback, prefer a case for the type you mean.

Dominance errors surprise you. Putting a broader pattern before a narrower one is a compile error, not a dead branch — the opposite of an if/else chain, where the same mistake silently wins. This is good news; it just reads as a strange error the first time.

null throws. A pattern switch throws NullPointerException on a null selector unless you write an explicit case null ->. This is deliberate — it preserves what switch always did — but it means "the switch is exhaustive" does not mean "the switch handles null". Handle it in one place:

case null      -> "no payment";
case Cash c    -> "cash";

You seal across a module boundary. Permitted subtypes must be in the same module. Discovering this after splitting a monolith is an unpleasant afternoon; plan the sealed hierarchy and the module boundary together.

Code Surgery

Here is a switch that compiles, runs, and is quietly broken. Find the defect before reading on.

BigDecimal fee(Payment p) {
    return switch (p) {
        case Card c         -> new BigDecimal("0.029");
        case BankTransfer b -> BigDecimal.ZERO;
        default            -> BigDecimal.ZERO;
    };
}

The defect: default covers Cash today, which is correct today. Add GiftCard with a 1.5% fee and this method silently charges zero — a revenue bug that no test will catch, because the test suite has no GiftCard case either. The compiler could have told you. You asked it not to.

The repair is to spell out the last case, so the switch is exhaustive by coverage rather than by fallback:

        case Cash c         -> BigDecimal.ZERO;

Now adding GiftCard fails the build here, and in every other switch over Payment in the codebase. That list of failures is a migration checklist you did not have to write.

Under the Hood

Sealing is recorded in the class file as a PermittedSubclasses attribute, so it is enforced by the JVM at class load, not only by javac. A subclass smuggled in by bytecode manipulation fails to load.

A pattern switch compiles to an invokedynamic call against java.lang.runtime.SwitchBootstraps.typeSwitch, which resolves the selector to a case index. Dispatch is therefore closer to a table lookup than to a chain of instanceof checks — you are not paying for the readability.

There is one runtime hole worth knowing about. If a sealed hierarchy is recompiled with a new subtype but a dependent class is not recompiled, the old exhaustive switch can face a value it has no case for. Rather than fall through, it throws MatchException. You should never see it in a clean build; seeing it means a stale artifact is on the classpath.

Preview note: primitive types in patterns, instanceof and switch — matching on int, long and friends the way you match on reference types — is still a preview feature on Java 25Preview on 25. It is genuinely useful and genuinely not final; do not put it in production code yet.

Try This Now15 minutes
  1. Find an enum in your codebase that is always used with a switch and always needs extra data per constant — the classic type + nullable fields smell.
  2. Rewrite it as a sealed interface with one record per constant, each carrying exactly the fields that constant needs.
  3. Convert the switches. Delete every default and every null check that only existed because a field was optional-per-type.
  4. Count the fields that became non-nullable. That number is what the enum was costing you.
Chapter project — part 2 of 7

Give the aggregator a result type. Every downstream call in Chapter 7 will return one of exactly three outcomes, and the sealed declaration is what will force the HTTP layer to handle all three:

public sealed interface Result<T> permits Ok, NotFound, Failed {}

public record Ok<T>(T value)           implements Result<T> {}
public record NotFound<T>(String sku)   implements Result<T> {}
public record Failed<T>(String reason) implements Result<T> {}

Then write the renderer, exhaustively and with no default:

String render(Result<Product> r) {
    return switch (r) {
        case Ok(Product p)        -> p.catalog().sku() + " ok";
        case NotFound(String sku) -> "no such product: " + sku;
        case Failed(String why)   -> "lookup failed: " + why;
    };
}

Now try adding a fourth outcome — Degraded, say — and watch the build tell you every place that has to change. That is the feature.

Fast Recap
  1. sealed + permits closes a hierarchy; each permitted subtype must be final, sealed, or non-sealed, and must live in the same module.
  2. A pattern switch over a sealed type is exhaustive without a default, and stops compiling when a subtype is added.
  3. Record patterns bind components in the label and nest arbitrarily deep; var is allowed for the ones you do not care about.
  4. Guards use the contextual keyword when, and guarded arms must precede the unguarded arm of the same type.
  5. Adding default to a sealed switch silently disables exhaustiveness checking — this is the one mistake to police in review.
  6. null throws unless you write case null.
  7. Primitive patterns are still preview on Java 25.
