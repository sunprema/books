Virtual threads

For twenty years the rule was: threads are expensive, so pool them, so never block one. Every reactive framework, every CompletableFuture chain, every callback pyramid in your codebase is downstream of that one constraint. Virtual threads remove the constraint. What they do not remove is your habits.

By the end of this chapter you will be able to
  • run blocking I/O on a virtual thread per task, and explain why that scales;
  • say what happens to a carrier thread when a virtual thread blocks;
  • identify what still pins a virtual thread on Java 25 — and what stopped pinning in Java 24;
  • replace the accidental back-pressure a thread pool was giving you with something deliberate.

A pool of 200, and a call that takes a second

Your service calls a payment provider. The call takes about a second, most of which is the network being the network. You run it on a fixed pool of 200 platform threads, because 200 felt like a reasonable number in 2019 and nobody has revisited it.

Make a Prediction

Traffic spikes to 2,000 concurrent requests, each needing one of those one-second calls. Nothing is CPU-bound; the machine is idle. How long does the 2,000th request wait before its call even starts?

Answer About nine seconds. The pool runs 200 at a time, so the queue drains in ten waves of roughly a second each, and the last request sits through nine of them. Your CPU graph is flat the whole time. You were not out of capacity — you were out of threads, which is a different and entirely artificial thing to run out of.

The classic fixes both cost you something real. Raise the pool to 2,000 and you buy 2,000 OS threads, each with a stack reservation measured in megabytes and a scheduler that now has 2,000 things to consider. Go reactive and you keep the small pool but rewrite the code into a form where a stack trace no longer tells you what happened.

Your Brain on virtual threads

The mental model that unlocks this: a thread is a stack, and a stack does not need an OS thread to exist — only to run.

A platform thread is a thin wrapper over an OS thread: the stack lives in OS-reserved memory, and it is bound to that OS thread for its whole life, awake or asleep. A virtual thread's stack lives on the Java heap. It borrows an OS thread — its carrier — only while it is actually executing. The instant it blocks on I/O, the JDK copies the stack out, hands the carrier to somebody else, and puts your thread aside until the bytes arrive.

So "blocking" stops meaning "occupying a scarce OS resource for a second" and starts meaning "sitting on the heap, costing a few hundred bytes". That is the entire feature. Everything else follows.

The API is deliberately boring

Virtual threadsFinal Java 21 are java.lang.Thread instances. Not a new type, not a wrapper — the same class, with a different implementation behind it. Debuggers, thread dumps, stack traces and try/catch all keep working, which is the point: the feature exists so that ordinary blocking code scales, not so that you rewrite it.

One virtual thread per task
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<String>> futures = urls.stream()
        .map(url -> executor.submit(() -> fetch(url)))   // plain blocking call
        .toList();

    for (var f : futures) System.out.println(f.get());
}   // close() waits for every task — the executor is AutoCloseable

Or, without an executor at all:

Thread.ofVirtual()
Thread t = Thread.ofVirtual().name("fetch-1").start(() -> fetch(url));
t.join();

Run the earlier scenario on this and the 2,000th request starts immediately, alongside the other 1,999. There is no queue, because there is nothing scarce to queue for.

Stop pooling. Start bounding.

The first instinct on meeting virtual threads is to put them in a pool, because that is what you do with threads. Do not. A pool exists to amortize an expensive creation and to cap a scarce resource. Virtual threads are cheap to create, and they are not the scarce resource.

But read that second half carefully, because it contains a trap. Your thread pool was capping something. Maybe deliberately, more likely by accident: a pool of 200 meant at most 200 concurrent database calls, which happened to sit nicely under a connection pool of 250. Swap in virtual threads and that ceiling evaporates. Now 5,000 requests arrive at a connection pool of 250 simultaneously, and instead of a queue you get 4,750 threads racing for connections, timing out, retrying.

Virtual threads do not remove your bottleneck. They remove the queue that was politely hiding it.

The fix is to bound the scarce thing explicitly, where it actually is:

A semaphore says what you mean; a thread pool only implied it
private final Semaphore dbPermits = new Semaphore(20);   // match the connection pool

Order load(long id) throws InterruptedException {
    dbPermits.acquire();
    try { return repository.find(id); }
    finally { dbPermits.release(); }
}

Ten thousand virtual threads may call load. Twenty are inside the repository at any moment; the rest are parked on the semaphore, costing heap and nothing else. The limit is now written down, next to the resource it protects, in a number you can explain.

Pinning: what changed, and what did not

A virtual thread is pinned when it cannot unmount from its carrier. While pinned, a blocking call holds an OS thread exactly like the old model — and if enough carriers are pinned at once, the scheduler starves.

This is where most of the advice on the internet is out of date, so be precise about versions:

Pinning by JDK version
CauseJava 21–23Java 24–25
Blocking inside synchronizedpinsdoes not pin (JEP 491)
Blocking inside a native frame (JNI, FFM downcall)pinspins
Blocking in a class initializerpinspins
ReentrantLockdoes not pindoes not pin

JEP 491, delivered in JDK 24, changed the JVM so that a monitor is associated with the virtual thread rather than with its carrier. A virtual thread can now block inside a synchronized block and still unmount. The practical consequence is large and underappreciated: you no longer need to rewrite synchronized as ReentrantLock to be virtual-thread friendly — and neither do the libraries you depend on, most of which were never going to.

Pinning has not vanished. A virtual thread executing a native frame cannot unmount, which is why Chapter 5's foreign-function calls come with a warning attached. The way to find remaining pinning is not to reason about it but to measure it: JFR emits a jdk.VirtualThreadPinned event whenever a virtual thread parks while pinned. Chapter 6 shows how to read the recording.

What Could Go Wrong?

You expect CPU-bound work to get faster. It will not. The carrier pool is a ForkJoinPool sized to the CPU count, so ten thousand virtual threads doing arithmetic contend for the same cores as ten platform threads would. Virtual threads are for tasks that wait.

You keep the pool "just in case". Executors.newFixedThreadPool(200) full of virtual threads is the worst of both: you pay for the abstraction and keep the queue.

ThreadLocal quietly becomes expensive. It still works, but a per-thread copy times a million threads is a real number, and thread-local state cannot be handed to a subtask in any disciplined way. Chapter 4 is the answer.

You act on stale advice. "Avoid synchronized with virtual threads" was correct in 2023 and is obsolete from Java 24. "Avoid long native calls" was correct then and still is. Check the version stamp on any virtual-thread advice you read.

Code Surgery

This migration was done on a Friday. Spot the two problems.

// was: Executors.newFixedThreadPool(64)
private final ExecutorService pool =
        Executors.newFixedThreadPool(64, Thread.ofVirtual().factory());

List<Row> loadAll(List<Long> ids) {
    return ids.stream()
        .map(id -> pool.submit(() -> jdbc.findRow(id)))
        .toList()
        .stream().map(Future::join)
        .toList();
}

Problem one: a fixed pool of 64 virtual threads. The virtual-thread factory is being used to build exactly the queue virtual threads exist to remove. Replace it with Executors.newVirtualThreadPerTaskExecutor().

Problem two: once you do, nothing bounds the JDBC calls. Sixty-four was accidentally protecting a connection pool. Add the semaphore — sized to the connection pool, not guessed — around jdbc.findRow.

Fixing only the first problem is worse than fixing neither: you would remove the cap and keep no replacement. That is how a "performance improvement" becomes an incident.

Under the Hood

The default scheduler is a ForkJoinPool in FIFO mode, with parallelism defaulting to the number of available processors. Carriers are its worker threads. There is no fairness guarantee and no priority; a virtual thread runs until it blocks, yields, or finishes.

Mounting and unmounting are implemented with continuations: when a virtual thread blocks, the JVM copies its stack frames from the carrier's stack into a chunk on the Java heap, and copies them back on resume. This is why the cost of a virtual thread scales with its stack depth rather than being a fixed megabyte reservation — and why deep recursion on a virtual thread is more expensive than you might guess.

The JDK's own blocking points — sockets, files on most platforms, Thread.sleep, BlockingQueue, ReentrantLock, and since Java 24 monitors — were retrofitted to unmount. Anything that blocks outside the JDK's knowledge, notably native code, cannot be.

Try This Now15 minutes
  1. Write a task that sleeps one second and prints its thread name. Run 10,000 of them on newFixedThreadPool(200). Time it.
  2. Change one line to newVirtualThreadPerTaskExecutor(). Time it again.
  3. Take a thread dump during each run (jcmd <pid> Thread.print). Note that the virtual-thread run has a handful of carriers and your tasks are elsewhere entirely — use jcmd <pid> Thread.dump_to_file to see them.
  4. Now put a synchronized block around the sleep. On Java 21 the run collapses back toward the pooled timing; on Java 24+ it does not. If you have both JDKs available, this is the most convincing five minutes in the chapter.
Chapter project — part 3 of 7

Your aggregator makes three downstream calls per request: catalog, pricing, inventory. Right now, imagine them sequential — 90ms + 40ms + 60ms = 190ms per request, all of it waiting.

Fan them out on virtual threads:

try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    var catalog = exec.submit(() -> catalogClient.find(sku));
    var price   = exec.submit(() -> pricingClient.find(sku));
    var stock   = exec.submit(() -> inventoryClient.find(sku));

    return new Product(catalog.get(), price.get(), stock.get());
}

190ms becomes about 90ms, and it took no reactive rewrite. Keep this version — and keep a note of what it still cannot do: if catalog fails immediately, pricing and inventory keep running to completion anyway, and there is no deadline covering the request as a whole. Chapter 4 fixes exactly those two holes.

Fast Recap
  1. A virtual thread is a real Thread whose stack lives on the heap and which borrows an OS carrier only while running.
  2. Blocking is cheap now. One virtual thread per task; Executors.newVirtualThreadPerTaskExecutor().
  3. Never pool virtual threads — but do replace the cap your old pool was accidentally providing, with a Semaphore on the scarce resource.
  4. From Java 24 (JEP 491), synchronized no longer pins. Native frames and class initializers still do.
  5. CPU-bound work does not speed up; the carrier pool is still sized to the CPU count.
  6. Find real pinning with JFR's jdk.VirtualThreadPinned, not by reasoning.

Next: you can now start a thousand threads without thinking. Chapter 4 is about the discipline that makes that safe — giving concurrent work a lifetime, a deadline, and a context, with structured concurrency and scoped values.
