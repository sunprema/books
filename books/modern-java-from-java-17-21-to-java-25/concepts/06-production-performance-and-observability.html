Production performance and observability

Five chapters of new features and not a single measurement. That is the normal way upgrades go wrong: a team adopts virtual threads, latency improves for unrelated reasons, everyone learns the wrong lesson. This chapter is the corrective — how to see what your service is really doing, and which Java 25 knobs are worth turning.

By the end of this chapter you will be able to
  • take a JFR recording in production and know which events answer which question;
  • find virtual-thread pinning with evidence rather than reasoning;
  • use the Java 25 AOT cache to cut startup and warm-up, in two commands;
  • say what compact object headers cost and whether they are on by default (they are not);
  • write a microbenchmark that measures the thing you meant.

"It got slower after the upgrade"

A service moves to Java 25 and virtual threads. P99 latency goes up. Someone opens a profiler, sees a lot of time in the HTTP client, and concludes the client is the problem.

Make a Prediction

The profiler is a sampling profiler measuring wall-clock time. The service does three downstream HTTP calls per request, each about 90ms of waiting. Where will most of the samples land, and what does that tell you about CPU cost?

Answer Almost all of them land in the HTTP client, because that is where the threads are — parked, doing nothing. It tells you nothing at all about CPU cost. Wall-clock profiles of an I/O-bound service mostly rediscover that it is I/O-bound. To find where the CPU actually goes you need samples attributed to CPU time, which is precisely what JDK 25 added.

JFR is already in there

JDK Flight Recorder is built into the JVM and designed to be left on in production. It is not a profiler you attach during an incident; it is a flight recorder, which is a different thing and a better one.

Two ways in
# From launch, dumping on exit
java -XX:StartFlightRecording=settings=profile,filename=app.jfr,dumponexit=true -jar app.jar

# Or attach to something already running and unhappy
jcmd <pid> JFR.start name=live settings=profile
jcmd <pid> JFR.dump  name=live filename=live.jfr

Two built-in settings profiles: default, cheap enough to run permanently, and profile, more detail and still modest. Open the file in JDK Mission Control, or query it from the command line with jfr summary and jfr print.

What Java 25 added to JFR

Three JEPs landed together, and they are more useful as a group than the release notes suggest.

JEP 509 — CPU-time profilingExperimental · Linux is the answer to the prediction box. The new jdk.CPUTimeSample event uses the Linux SIGPROF timer, so samples are attributed to CPU time rather than wall-clock time, and native frames — including the FFM downcalls from Chapter 5 — appear in the profile instead of vanishing into a black box. Two caveats you must carry: it is experimental, and it is Linux-only. Your container is probably Linux; your laptop may not be.

JEP 518 — cooperative sampling is the least visible and arguably the most valuable. JFR now walks thread stacks at safepoints rather than interrupting threads at arbitrary points, which makes sampling safe under ZGC and lets stack walking scale concurrently. You do not turn it on; it just stops being a source of instability. It also adds a SafepointLatency event, which is how you find out that a thread took 40ms to reach a safepoint — a latency source most teams have never once looked at.

JEP 520 — method timing and tracing is the one you will reach for during an incident. Two events, jdk.MethodTiming (invocation counts and execution times) and jdk.MethodTrace (individual invocations with stack traces), implemented by bytecode instrumentation and selected by configuration. You can time a specific method in a running JVM without editing, rebuilding or redeploying it.

Startup and warm-up: the AOT cache

A JVM starts slow twice. First it loads and links thousands of classes; then it runs everything interpreted until the JIT has watched long enough to compile. On a short-lived job or a scale-to-zero service, you may pay both costs and never reach steady state.

JDK 24 introduced the AOT cache (JEP 483): do a training run, record the loaded-and-linked classes, reuse them on subsequent starts. JDK 25 made it usable in two commands (JEP 514) instead of three:

Java 25 — the whole workflow
# 1. Training run: exercise a realistic path, then let it exit
java -XX:AOTCacheOutput=app.aot -jar app.jar

# 2. Every run after that
java -XX:AOTCache=app.aot -jar app.jar

JDK 25 also added AOT method profiling (JEP 515): the cache now carries execution profiles for hot methods, so the JIT can start emitting optimized code at startup instead of re-learning what it learned yesterday. That targets warm-up, not just startup — the second of the two slow phases.

Two practical notes. The training run must exercise a path resembling production; training on --version caches nothing useful. And the cache is tied to the JDK build and the application — regenerate it in CI as a build artifact, do not hand-copy it between environments.

Compact object headers

Every object on a 64-bit JVM carries a header. Traditionally 12 bytes. Compact object headers shrink it to 8.

Four bytes sounds trivial until you multiply. A heap full of small objects — and a heap full of records is exactly that — can lose a meaningful fraction of its footprint to headers alone. Less footprint also means better cache behaviour and less GC work, so the effect is usually larger than the arithmetic suggests.

Get the status right — this is widely misreported

Compact object headers were experimental in JDK 24 (JEP 450) and became a product feature in JDK 25 (JEP 519). Product feature means the experimental-flag requirement is gone.

It does not mean on by default. On Java 25 you must still opt in:

java -XX:+UseCompactObjectHeaders -jar app.jar

A separate proposal, JEP 534, would enable it by default in a later release. Until then, a blog post telling you Java 25 shrinks your heap automatically is wrong, and you will not see the benefit without the flag.

It is a genuinely easy win to evaluate: turn it on in a load test, compare heap-after-GC and allocation rate, keep it if the numbers move. Which brings us to the part of the chapter that matters more than any flag.

Measure, and measure the right thing

Every flag in this chapter is worth exactly as much as your ability to tell whether it helped.

Timing a loop with System.nanoTime does not survive contact with the JVM. The JIT will constant-fold a computation whose result you ignore, eliminate the loop entirely, and swap implementations halfway through your measurement. JMH exists to control for exactly these effects: warm-up iterations, separate forked JVMs, and a Blackhole to consume results the compiler would otherwise delete.

A benchmark that measures what it claims to
@State(Scope.Benchmark)
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 5, time = 1)
@Fork(2)
public class ParseBenchmark {

    private String input;

    @Setup public void setup() { input = "2026-08-16T12:00:00Z"; }

    @Benchmark
    public Instant parse() {
        return Instant.parse(input);      // returned, so JMH consumes it
    }
}

Returning the result is not a style choice — it is how JMH knows the value is used. A void benchmark needs a Blackhole parameter instead. And note what this benchmark does not do: it does not tell you whether your service is faster. JMH answers "which of these two implementations of one method is quicker". Service-level questions belong to a load test and a JFR recording.

What Could Go Wrong?

You enable jdk.VirtualThreadStart and End in production. They are off by default for a reason. A million virtual threads means two million events, and your recording becomes a very expensive way to fill a disk.

You profile with a wall-clock profiler and tune what it shows you. On an I/O-bound service it will point at the I/O. Use CPU-time sampling when the question is CPU — on Linux, with the experimental caveat understood.

You benchmark on a laptop with a browser open. Thermal throttling and background load will move your numbers more than the change you are testing. Benchmark where you deploy.

You turn on three flags at once. AOT cache, compact headers and a GC change together, and now you cannot attribute the result to anything. One at a time, with a measurement between.

You believe compact object headers are on by default in Java 25. They are not. Check with -XX:+PrintFlagsFinal -version | grep UseCompactObjectHeaders rather than trusting a changelog summary.

Code Surgery

This benchmark "proves" that string concatenation is free.

long start = System.nanoTime();
for (int i = 0; i < 1_000_000; i++) {
    String s = "order-" + i;         // never used
}
System.out.println((System.nanoTime() - start) / 1_000_000 + "ms");

Three defects, any one of which invalidates it. s is never used, so the JIT is entitled to delete the whole loop body — you may be timing an empty loop. There is no warm-up, so the early iterations run interpreted and the later ones compiled, and you are averaging two different programs. And it runs in a JVM that has already been doing other things, so the profile of every call site involved is polluted.

The repair is not to patch this loop but to stop hand-rolling it:

@Benchmark
public String concat(Blackhole bh) {
    String s = "order-" + counter++;
    bh.consume(s);
    return s;
}

If a JMH dependency is genuinely not worth it for the question you have, that is a fine answer — but then do not report a number. Report that you did not measure.

Under the Hood

JFR events are emitted into per-thread buffers, flushed to a global buffer, then to disk. That design is why the overhead is a few percent rather than the tenfold cost of an instrumenting profiler: the hot path is a buffer write, not a call into an agent.

The safepoint bias that JEP 518 addresses is a decades-old problem in JVM sampling. Traditional async samplers interrupt a thread wherever it happens to be, but walking a stack safely at an arbitrary instruction is genuinely hard; the classic compromise walks only at safepoints, which biases samples toward safepoint-adjacent code. JEP 518's cooperative approach keeps the safety and reduces the bias — and, incidentally, is what makes sampling trustworthy under ZGC.

Compact object headers work by folding the class pointer into the mark word, so a 96-bit header becomes 64. That interacts with locking and hashing, which is why it spent a release as experimental and why JEP 534 exists as a separate step: the JEP is finished, the confidence to default it on is a different question.

The AOT cache is Project Leyden's first shipping increment. Reading it as "Java is getting an AOT compiler" is a misreading — it caches class loading, linking and now profiles, while leaving the JIT in charge of code generation. You keep peak throughput, which is the thing native-image trades away.

Try This Now20 minutes
  1. Run any service you have with -XX:StartFlightRecording=settings=profile,filename=app.jfr,dumponexit=true. Put some load through it. Exit.
  2. jfr summary app.jfr — read the event counts. This is the cheapest orientation you will ever get on an unfamiliar service.
  3. jfr print --events jdk.VirtualThreadPinned app.jfr. If your service uses virtual threads and this is empty, you have evidence, not a hope.
  4. Take a training run with -XX:AOTCacheOutput=app.aot, then time ten starts with and without -XX:AOTCache=app.aot. Report the median, not the best.
  5. Run once with -XX:+UseCompactObjectHeaders under the same load and compare heap-after-GC. Change one thing at a time.
Chapter project — part 6 of 7

Give the aggregator a way to answer questions about itself. Three things, none of which touch application code:

  1. Add -XX:StartFlightRecording=settings=profile,filename=/var/log/agg.jfr,dumponexit=true to the launch command.
  2. Configure jdk.MethodTiming for the aggregation method, so you can see its distribution without instrumenting it by hand.
  3. Write down, before you measure, what you expect: three concurrent 90ms calls should give roughly 90–100ms per request, near-zero CPU per request, and no jdk.VirtualThreadPinned events.

Step 3 is the discipline that makes the rest worth doing. A measurement you did not predict is a number; a measurement that contradicts a written prediction is a finding.

Fast Recap
  1. JFR is in the JVM, cheap enough for production: -XX:StartFlightRecording or jcmd <pid> JFR.start.
  2. jdk.VirtualThreadPinned is how you find real pinning; the start/end events stay off in production.
  3. JDK 25 JFR: CPU-time profiling (JEP 509, experimental, Linux-only), cooperative sampling (JEP 518), method timing and tracing (JEP 520, no code change).
  4. AOT cache in two commands: -XX:AOTCacheOutput=app.aot once, then -XX:AOTCache=app.aot. JEP 515 adds method profiles, which helps warm-up.
  5. Compact object headers are a product feature in Java 25 but still opt-in: -XX:+UseCompactObjectHeaders.
  6. Use JMH for method-level questions and a load test plus JFR for service-level ones. Never a hand-rolled nanoTime loop.
  7. Change one thing at a time, and predict before you measure.
