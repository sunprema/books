Capstone: modernize a small service

One service, about a hundred lines, written the way everyone wrote them in 2021. Six changes, in an order that lets you measure each one. At the end you will have a Java 25 service and — more useful — a defensible account of which change bought what.

By the end of this chapter you will be able to
  • sequence a modernization so that each step is independently reversible;
  • convert an exception-and-null API surface into a sealed result type;
  • replace a thread pool with virtual threads without losing back-pressure;
  • state which parts of your Java 25 service are preview code and who owns that decision.

The service, as it is

GET /product/{sku}. Three downstream calls — catalog, pricing, inventory — merged into one response. Roughly 90ms, 40ms and 60ms respectively, essentially all of it network wait.

ProductService.java — Java 17, and every line of it is normal
public class ProductService {

    private final ExecutorService pool = Executors.newFixedThreadPool(64);

    // returns null when not found; throws when anything else goes wrong
    public ProductDto lookup(String sku, String traceId) throws Exception {
        Future<CatalogDto> c = pool.submit(() -> catalog.find(sku, traceId));
        Future<PriceDto>   p = pool.submit(() -> pricing.find(sku, traceId));
        Future<StockDto>   s = pool.submit(() -> inventory.find(sku, traceId));

        CatalogDto cd = c.get();
        if (cd == null) return null;

        return new ProductDto(cd, p.get(), s.get());
    }
}

Four things are wrong with it, and none of them are bugs today.

  • The DTOs are hand-written classes with hand-maintained equals, hashCode and toString.
  • The outcomes are encoded as null for "not found" and an exception for everything else. Nothing in the signature says so; a comment does.
  • The pool of 64 caps concurrency at a number nobody can justify, and it is the only thing protecting the downstream connection pools.
  • traceId is threaded through every method that might want to log.
Make a Prediction

You have an afternoon. You convert the DTOs to records, swap the pool for virtual threads, introduce a sealed Result, and move traceId to a scoped value — all in one commit. Load test shows P99 up 40%.

Which change caused it?

Answer You cannot tell, and that is the entire lesson of this chapter. The likely culprit is the virtual-thread swap removing the cap of 64 in front of a connection pool — but "likely" is not "measured", and to find out you now have to unpick a commit that touched every file. Sequence the changes and each one gets its own verdict.

The order, and why it is that order

Six steps, each independently reversible

Steps 1 and 2 are pure refactors of shape — land them first, precisely because they are boring and they make everything after them easier to read. Step 3 is the one that can take the service down, so it goes alone, behind a flag, with the semaphore in the same commit. Steps 4 and 6 are safe. Step 5 is the one requiring a policy decision, so it goes last, when everything else is already stable.

Steps 1 and 2: shape

The records are Chapter 1's project. The sealed result type is Chapter 2's. Together they change what the signature promises:

The signature now says what the comment used to
public record CatalogEntry(String sku, String name, String category) { /* validates sku */ }
public record Price(String sku, String currency, long minorUnits)  { /* validates sku */ }
public record Stock(String sku, int onHand, boolean backorderable) { /* validates sku */ }
public record Product(CatalogEntry catalog, Price price, Stock stock) {}

public sealed interface Result<T> permits Ok, NotFound, Failed {}
public record Ok<T>(T value)            implements Result<T> {}
public record NotFound<T>(String sku)    implements Result<T> {}
public record Failed<T>(String reason)  implements Result<T> {}

// no comment needed: the type is the documentation
Result<Product> lookup(String sku);

And the HTTP layer becomes an exhaustive switch, with no default and no null check:

HTTP mapping, checked by the compiler
HttpResponse toResponse(Result<Product> result) {
    return switch (result) {
        case Ok(Product p)        -> HttpResponse.json(200, p);
        case NotFound(String sku) -> HttpResponse.problem(404, "unknown sku " + sku);
        case Failed(String why)   -> HttpResponse.problem(502, why);
    };
}

Add a Degraded outcome next quarter and this method stops compiling, along with every other place that maps a Result. That failing build is a to-do list you did not have to write.

Step 3: the dangerous one

This is the change that makes the service faster and the change most likely to cause an incident, and those are the same change. Ship the semaphore in the same commit as the executor swap — not the next one.

Virtual threads with the cap made explicit
private final Semaphore downstream = new Semaphore(64);   // was the pool size; now it is a stated limit

private <T> T call(Callable<T> c) throws Exception {
    downstream.acquire();
    try { return c.call(); }
    finally { downstream.release(); }
}

public Result<Product> lookup(String sku) {
    try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
        var c = exec.submit(() -> call(() -> catalog.find(sku)));
        var p = exec.submit(() -> call(() -> pricing.find(sku)));
        var s = exec.submit(() -> call(() -> inventory.find(sku)));

        return new Ok<>(new Product(c.get(), p.get(), s.get()));
    } catch (Exception e) {
        return new Failed<>(e.getMessage());
    }
}

Note the semaphore is 64, not "unbounded because virtual threads are cheap". You did not learn that 64 was correct — but it was the number in production yesterday, so it is the number that keeps this step a single-variable experiment. Tune it afterwards, deliberately, with the downstream pool in view.

Keeping the old limit is not timidity. It is the only way the load test tells you anything.

Steps 4 and 5: context, then structure

The traceId parameter goes to a scoped value — final API, no flag:

Bound once, at the edge
public static final ScopedValue<RequestContext> CONTEXT = ScopedValue.newInstance();

void handle(HttpExchange x) {
    var ctx = new RequestContext(traceIdOf(x), tenantOf(x));
    ScopedValue.where(CONTEXT, ctx)
               .run(() -> respond(x, toResponse(products.lookup(skuOf(x)))));
}

Then the structural step. This is the one carrying the preview label, and the one that finally closes the hole Chapter 4 opened:

PREVIEW on Java 25 (JEP 505) — --enable-preview required
public Result<Product> lookup(String sku) {
    try (var scope = StructuredTaskScope.open(
             Joiner.<Object>awaitAllSuccessfulOrThrow(),
             cf -> cf.withName("product-lookup")
                     .withTimeout(Duration.ofMillis(500)))) {

        var c = scope.fork(() -> call(() -> catalog.find(sku)));
        var p = scope.fork(() -> call(() -> pricing.find(sku)));
        var s = scope.fork(() -> call(() -> inventory.find(sku)));

        scope.join();
        return new Ok<>(new Product(c.get(), p.get(), s.get()));

    } catch (NoSuchElementException e) {
        return new NotFound<>(sku);
    } catch (Exception e) {
        return new Failed<>(e.getMessage());
    }
}

Three things changed and all three matter. A failure in any call now cancels the other two immediately, instead of leaving them to run out the clock. The 500ms timeout covers the request as a whole rather than each call separately. And the scoped context binds through to every subtask, because subtasks forked in a scope inherit it.

What Could Go Wrong?

You do it in one commit. The prediction box. Six changes, one number, no attribution.

You drop the semaphore in step 3 because virtual threads are cheap. They are; the downstream connection pool is not.

You catch Exception around the scope and swallow the interrupt. Cancellation arrives as an interrupt; code that catches and continues defeats the timeout you just added.

You ship --enable-preview without telling anyone. It has to be on for compilation and for every JVM that runs the artifact, and preview class files are rejected outright by a different JDK version. That is an operational decision with your ops team's name on it, not a build tweak.

You convert an entity to a record. Product is a value. A Customer row with an id is not — component-wise equality on an entity is a bug waiting for a HashSet.

Code Surgery

A team followed this chapter and produced the following. It passes review at a glance.

try (var scope = StructuredTaskScope.open(Joiner.<Object>awaitAllSuccessfulOrThrow())) {
    var c = scope.fork(() -> catalog.find(sku));
    CatalogEntry entry = c.get();                    // (1)

    var p = scope.fork(() -> pricing.find(entry));
    scope.join();
    return new Ok<>(merge(entry, p.get()));
} catch (InterruptedException e) {
    return new Failed<>("interrupted");        // (2)
}

(1) get() before join() throws IllegalStateException. The intent — "fetch the catalog entry, then use it to price" — is genuinely sequential, and a scope is the wrong tool for it. Either call catalog directly and then open a scope for the parallel part, or nest a second scope. Do not try to interleave fork and get.

(2) Catching InterruptedException without restoring the interrupt status leaves the thread's flag cleared, so an outer scope's cancellation is silently absorbed. If you catch it and do not rethrow, call Thread.currentThread().interrupt() before returning.

The repair: separate the sequential dependency from the parallel fan-out, and re-arm the interrupt.

CatalogEntry entry = catalog.find(sku);          // sequential: just call it

try (var scope = StructuredTaskScope.open(Joiner.<Object>awaitAllSuccessfulOrThrow())) {
    var p = scope.fork(() -> pricing.find(entry));
    var s = scope.fork(() -> inventory.find(entry));
    scope.join();
    return new Ok<>(merge(entry, p.get(), s.get()));
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return new Failed<>("interrupted");
}
Under the Hood

Worth noticing what this modernization did not require. No reactive types. No new framework. No callback rewrite. The final lookup reads top to bottom, throws where it fails, and produces a stack trace that names the line — the whole reason to prefer blocking code, now that blocking is cheap.

The two most durable changes are also the least glamorous. The sealed Result means the compiler enumerates your failure modes, forever. The records mean the model cannot drift out of sync with its own equality. Both survive the next JDK, the next framework, and the API churn in Chapter 4 — which is why they are steps 1 and 2 rather than an afterthought.

And keep this in proportion: the service went from about 190ms to about 90ms because three calls now overlap. That is Chapter 3's arithmetic, not magic, and you could have had it with a thread pool. What the rest of the chapters bought is that the fast version is also the one that cancels cleanly, times out as a unit, carries its trace context, and tells you when it is lying to you.

  2. Apply steps 1–3. Measure again. You should see roughly 190ms → 90ms.
  3. Make the catalog stub throw after 10ms and the other two sleep for 30 seconds. Measure how long lookup takes to return. (Thirty seconds.)
  4. Apply step 5. Measure the same failure. (Ten milliseconds.)
  5. Delete the semaphore and run 5,000 concurrent requests against a stub that permits only 20 concurrent calls. Watch what "removing back-pressure" actually looks like, in a place where nobody gets paged.
Chapter project — part 7 of 7: what you are holding

A working service, and a one-page migration note you can hand to the next team. The note should say, for each of the six steps: what changed, what you measured, and what you decided. Two entries matter more than the rest.

  • Step 3 — the concurrency limit is now 64 in a semaphore rather than implied by a pool. Whoever tunes it next needs to know it was chosen to keep one experiment clean, not because it is right.
  • Step 5 — whether you shipped preview code, and who agreed. If you did, note that JDK 26 changes allSuccessfulOrThrow to return a List, and that the wrapper interface is where that change lands.

That note is the actual deliverable. The code will be edited by someone who was not here; the reasoning is what they cannot reconstruct.

Fast Recap
  1. Sequence the changes. Shape first (records, sealed results), concurrency second, structure and observability last.
  2. A sealed Result turns a comment about null and exceptions into something the compiler enforces at every call site.
  3. Swap the pool and add the semaphore in the same commit, keeping the old number, so the load test measures one variable.
  4. Scoped values remove the traceId parameter; a structured scope adds sibling cancellation and one deadline — the second is still preview.
  5. Predict, then measure with JFR. A measurement without a prediction is a number.
  6. The lasting wins are the boring ones: correct equality, and failure modes the compiler enumerates.
