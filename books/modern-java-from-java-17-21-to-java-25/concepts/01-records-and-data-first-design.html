Records and data-first design

Open any Java service written before 2021 and count the lines that carry data versus the lines that carry ceremony about data. The ratio is embarrassing. Records fix that, and they do it in a way that changes more than line count — they make "this type is just its components" a thing the compiler knows.

By the end of this chapter you will be able to
  • replace a hand-written DTO or value object with a record, and say precisely what you gained;
  • validate and normalize arguments in a compact constructor;
  • decide, for a given type, whether a record is the right shape or the wrong one;
  • spot the shallow-immutability trap before it ships.

The forty lines nobody reads

Here is a type that holds two things. It is, by volume, mostly not about holding two things.

The Java 8 shape — abbreviated, and that is the point
public final class Money {
    private final String currency;
    private final long minorUnits;

    public Money(String currency, long minorUnits) {
        this.currency = currency;
        this.minorUnits = minorUnits;
    }

    public String getCurrency() { return currency; }
    public long getMinorUnits() { return minorUnits; }

    // equals: 11 lines. hashCode: 3. toString: 5.
    // All three generated by the IDE, all three now your problem forever.
}

That last comment is the real cost. The generated methods are not free — they are a standing obligation. Add a third component next sprint and you must remember to touch all three, and nothing in the language will remind you. Everyone has met the bug where equals knows about a field that hashCode does not.

Make a Prediction

Someone adds a String description field to the class above, updates the constructor and the getter, and forgets equals and hashCode. Two Money objects differ only in description. What happens when you put both in a HashSet?

Answer The set holds one. Both objects hash the same and compare equal, so the second is silently discarded — no exception, no warning, just a missing element somewhere downstream. This class of bug is why records exist.

The record version is one line, and it has no such obligation.

The same type, Java 16 and later
public record Money(String currency, long minorUnits) {}
Your Brain on records

Do not think "shorthand for a class with getters". Think: the components are the state, and I am telling the compiler so.

An ordinary class hides its representation on purpose — that is encapsulation, and it lets you change the internals later. A record does the opposite deliberately: it declares that this type is nothing but these components, in this order, and hands you every consequence of that declaration for free. You are trading the freedom to change the representation for the guarantee that everything derived from it stays correct.

That trade is exactly right for a DTO, an API model, an event, a map key, a coordinate, a result. It is exactly wrong for a type whose internals you expect to rework.

What the compiler actually gives you

A record declaration is a transparent carrier for immutable dataFinal Java 16. From the header alone, the compiler derives:

Two details catch people out. First, the accessor is named currency(), not getCurrency() — records do not follow the JavaBeans convention. Second, the record class is implicitly final and implicitly extends java.lang.Record, so it cannot extend anything else. It can implement interfaces, which is what Chapter 2 is built on.

What you may still add: static fields and methods, instance methods, nested types, and extra constructors — provided every extra constructor eventually delegates to the canonical one. What you may not add is an instance field. The components are the state; there is no room for a second copy of it.

The compact constructor

A record that accepts any garbage you hand it is not a value object, it is a tuple. The compact constructor is where a record earns the word "value": it declares no parameter list, its body runs before the fields are assigned, and the parameters are ordinary variables you may reassign.

Validate, then normalize — in that order
public record Money(String currency, long minorUnits) {

    public Money {                              // no parameter list: that is the "compact" part
        if (currency == null || currency.length() != 3)
            throw new IllegalArgumentException("ISO-4217 code required: " + currency);

        currency = currency.toUpperCase(Locale.ROOT);   // reassign: this is what gets stored
    }
}

Assigning to the parameter is the idiom, and it reads oddly the first time. There is no this.currency = ... because you are not writing the assignment — you are amending the value the compiler is about to assign. Trying to write this.currency = currency in a compact constructor is a compile error.

A record without a compact constructor is a tuple with a nice toString. A record with one is a type that cannot exist in an invalid state.

That last row is underused. A record may be declared inside a method, which turns the usual "I need a pair here but a class feels heavy" moment into a non-decision:

A local record: visible to nothing outside this method
List<Order> topByValue(List<Order> orders, int n) {
    record Scored(Order order, long total) {}

    return orders.stream()
        .map(o -> new Scored(o, o.total()))
        .sorted(Comparator.comparingLong(Scored::total).reversed())
        .limit(n)
        .map(Scored::order)
        .toList();
}
What Could Go Wrong?

You assume a record is deeply immutable. It is not. A record guarantees that the component reference cannot be reassigned. If the component is an array or a mutable list, the referent is still wide open:

record Tags(List<String> values) {}

List<String> mine = new ArrayList<>(List.of("a"));
Tags t = new Tags(mine);
mine.add("b");                // t.values() now has two elements

Your framework wants getX(). Older serialization and mapping libraries look for JavaBeans accessors and find nothing. Jackson has supported records natively for years, but an in-house mapper written in 2015 will not. Check before you migrate a whole DTO package.

You reach for a record because it is short. Brevity is the least interesting thing records give you. If the type has identity — a User row, an Account — component-wise equality is actively wrong, and short is no consolation.

Code Surgery

Fix the Tags record above. One line, in the compact constructor:

record Tags(List<String> values) {
    Tags {
        values = List.copyOf(values);
    }
}

List.copyOf is doing three jobs: it copies, so later mutation of the caller's list cannot reach you; it returns an unmodifiable list, so t.values().add(..) throws instead of succeeding; and it rejects null elements. Note the accessor still hands out the internal list — that is fine now, because the list it hands out cannot be modified.

For an array component there is no copyOf that returns something unmodifiable. Either clone in the constructor and in the accessor, or — better — do not use an array component.

Under the Hood

A record compiles to a final class extending java.lang.Record, plus a Record attribute in the class file listing the components and their types. That attribute is what reflection reads through Class.getRecordComponents(), and it is how a serialization library discovers the canonical constructor without guessing.

equals, hashCode and toString are not emitted as ordinary bytecode. They are invokedynamic call sites bootstrapped by java.lang.runtime.ObjectMethods, which builds the implementation from the component list at first call. Practical consequence: the semantics are guaranteed to stay consistent with the components, because there is no per-method code to fall out of date.

Records are also serialization-friendly in a way ordinary classes are not: deserialization goes through the canonical constructor, so your compact-constructor validation runs on the way in. A hand-written class deserialized by the default mechanism bypasses its constructor entirely — a long-standing way to conjure invalid objects.

Try This Now10 minutes
  1. Pick the smallest DTO in a project you actually work on. Convert it to a record.
  2. Delete its equals, hashCode and toString. Run the tests.
  3. Now add a compact constructor that rejects the one input your team has an open bug about — the empty string, the negative quantity, the null id.
  4. Run the tests again. If something failed, you have just found code that was constructing an invalid object and getting away with it.

Step 4 is the point of the exercise. The conversion is trivial; the validation is what changes your Tuesday.

Fast Recap
  1. A record declares that a type is its components — the compiler then derives fields, accessors, the canonical constructor, equals, hashCode and toString.
  2. Accessors are currency(), not getCurrency(). Records are final and cannot extend a class, but can implement interfaces.
  3. The compact constructor is where you validate and normalize; assign to the parameter, not to this.
  4. Records are shallowly immutable. A mutable component needs a defensive copy.
  5. Use a record when component-wise equality is the truth; use a class when the type has identity or a representation you want to keep private.
  6. Local records make a throwaway tuple free.

Next: records give you the shapes. What they do not give you is a way to say "a payment is a card, a transfer, or cash — and nothing else". That is Chapter 2, where sealed types close the set and pattern matching makes the compiler check that you handled all of it.
