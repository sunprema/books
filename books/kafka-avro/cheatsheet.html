Cheatsheet

Vocabulary

TermMeaning
BrokerA Kafka server; a cluster is a set of brokers
TopicA named, ordered, durable log of records
PartitionA topic's parallel, independently-ordered sub-log
OffsetA record's sequential position within its partition
Consumer groupConsumers sharing a group.id, splitting partitions between them
Leader / replicaThe broker serving a partition's reads/writes / its fault-tolerance copies

Ordering guarantee

Per partition only. Use a partition key (usually an entity id) for anything that needs relative ordering.

Minimal Avro record schema

{
  "type": "record",
  "name": "MyEvent",
  "namespace": "com.example",
  "fields": [
    { "name": "id",   "type": "string" },
    { "name": "note", "type": ["null", "string"], "default": null }
  ]
}

Optional field = union with null listed first. Give every field you might later add or drop a default.

Compatibility modes

ModeGuarantee
BACKWARD (default)New schema reads data written with the previous schema
FORWARDPrevious schema reads data written with the new schema
FULLBoth directions hold
*_TRANSITIVESame check, against every prior version — not just the last one

Message on the wire (Kafka + Schema Registry)

[ schema id ][ Avro-binary payload ]

Producer registers/looks up the schema once, caches the id. Consumer resolves the id to a schema via the registry, then decodes.

Pitfalls, collected

MistakeWhy it bites
No default on a fieldBlocks safe schema evolution under any compatibility mode
Renaming instead of adding + aliasesReads as drop-one/add-one to the compatibility checker; usually fails
Producer/consumer on different registriesSchema ids are only meaningful within the registry that issued them
No partition keyLoses relative ordering between causally related events
Assuming topic-wide orderingKafka only orders within a single partition
Sending the full schema on every messageThe exact overhead a Schema Registry exists to remove
