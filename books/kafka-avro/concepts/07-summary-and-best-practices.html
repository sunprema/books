7. Summary and Best Practices

Zoom back out. Three pieces, three jobs, and none of them substitutes for the other two:

Kafka moves events from producers to consumers reliably, in order within a partition, at whatever scale you need. Avro gives each event a compact, explicit, typed shape instead of an unenforced JSON convention. The Schema Registry is what lets every producer and consumer agree on that shape without re-sending it on every single message — and, more importantly, catches an incompatible change before it ships.

Best practices worth carrying forward

Version schemas like code A schema change is an API change for every consumer of that topic. Review it, and know which compatibility mode you're relying on before you make it.
Choose your compatibility mode deliberately BACKWARD if you need to replay history through new consumers (the common case, and the default). FORWARD if old consumers must survive a producer upgrade without being redeployed first. FULL when both directions genuinely matter — it's the strictest, so expect it to reject more changes.
Test compatibility before production, not in it Register schema changes against a staging registry (or the registry's compatibility-check endpoint) in CI. Finding out a schema is incompatible from a producer's failed registration call in prod is the expensive way to learn it.

Self-check

1. A consumer group rewinds to the start of a topic and must read every historical record with today's schema. Which compatibility mode is this relying on?

BACKWARD — the new (current) schema must be able to read data written by every previous schema it's reading. It's also the registry's default for exactly this reason.

2. Why can't a consumer decode a raw Avro-binary message with no schema at all, the way it could with JSON?

Avro's binary encoding carries no field names or type tags — values are positioned purely by the schema's field order. Without the exact writer schema, there's nothing in the bytes themselves to say where one field ends and the next begins.

3. You need to add a required field to an event that's read under BACKWARD compatibility. What's the safe way to do it?

Give the field a default value. Without one, the new schema can't produce a value for records written before the field existed, so the registry rejects the registration outright rather than let a consumer hit the gap at runtime.
