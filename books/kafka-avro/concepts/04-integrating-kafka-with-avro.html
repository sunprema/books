4. Integrating Kafka with Avro

Put the last two chapters together and the appeal is obvious: Kafka moves bytes reliably at scale; Avro makes those bytes compact and typed instead of an unenforced JSON blob. Smaller messages, a real contract on the wire. What's not to like?

The problem Avro alone doesn't solve

Remember from the last chapter: Avro binary is not self-describing. A consumer needs the exact writer schema to decode a message. So — where does that schema come from?

The naive answer is: attach it. Put the full Avro schema in the message alongside the data. It works, technically. It's also wasteful in a way that gets worse the longer you ignore it: for a small event, the schema JSON can easily be larger than the data it describes, and you're now paying that cost on every single message, forever, even though the schema itself almost never changes between one message and the next.

The fix is the same trick you'd reach for anywhere else in software: indirection. Store each schema exactly once, somewhere central, and give it a small ID. Messages carry only the ID. Anyone who needs the actual schema — mainly, a consumer decoding a message — looks it up by that ID, once, and caches it.

What this buys you A message stays small (an ID plus the Avro-binary payload), and every producer and consumer is checking against the same registered schema — which is also the hook that makes schema evolution something you can enforce, not just hope people remember.

That central store is the Schema Registry, and it's the piece that turns "Kafka plus Avro" from two good ideas glued together into an actual, checked data contract. That's the whole next chapter.
