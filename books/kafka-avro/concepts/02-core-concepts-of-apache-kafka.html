2. Core Concepts of Apache Kafka

Let's build Kafka's vocabulary the way you'd build any new API's mental model: from the outside in. Three roles, one durable structure, and a rule about ordering you'll want to remember before it surprises you.

Producers, brokers, consumers

Producers publish records. Brokers are the servers that store those records durably and serve them back out — a Kafka cluster is just a set of brokers cooperating. Consumers subscribe and read, typically as part of a consumer group, which is what lets a group of processes split the work of reading a topic instead of each one reading everything.

Topics and partitions

A topic is an ordered, durable log of records — think of it as roughly analogous to a table, or a named category of event ("orders", "payments"). A topic is split into partitions so Kafka can parallelize both storage and throughput across brokers: each partition is its own append-only log, and different partitions can live on different brokers.

The rule that matters most Kafka guarantees ordering within a single partition. It makes no ordering guarantee across partitions of the same topic.

This is why a producer usually sends records with a key — Kafka routes records with the same key to the same partition, so "all events for order #4471, in order" is a guarantee you get almost for free, as long as order-id is your key. Two different orders can and will interleave across partitions; that's fine, because nothing ordered them relative to each other in the first place.

Pitfall Assuming a topic is globally ordered because "it's a log." It's a log per partition. Events with a causal relationship need to land on the same partition — which means the same key — or that relationship isn't preserved.

Leaders, replicas, and the message lifecycle

Each partition has one broker acting as its leader, handling every read and write for that partition; other brokers hold replicas for fault tolerance, ready to take over if the leader goes away. A record's path is simple once you see it this way: a producer sends to the partition's current leader, the leader appends it to the log and assigns it the next offset (just a sequential position number), and a consumer reads forward from whatever offset it last processed.

Consumer groups and offsets

Within a consumer group, Kafka assigns each partition to exactly one consumer instance at a time — that's the whole parallelism story: more partitions, more consumers in the group, more throughput, up to one consumer per partition. Two different groups reading the same topic don't interfere with each other at all; each group tracks its own offset per partition, and that offset bookkeeping is itself stored durably as records in an internal Kafka topic, replicated like everything else.

Pitfall Forgetting offsets are per group.id. Point a second consumer at the same topic with a new group id, and it starts from scratch — it isn't "joining" the first consumer, it's an entirely independent reader.

That's the whole skeleton: producers write to partition leaders, brokers durably store and replicate, consumer groups split the reading work, and ordering is a per-partition promise, not a topic-wide one. Everything Kafka does at scale is this skeleton, repeated across many topics and many brokers. Now let's give the records themselves a real shape — that's where Avro comes in.
