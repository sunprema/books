6. A Basic Implementation Guide

Theory's done. Let's wire an actual producer and consumer through Avro and a Schema Registry, in pseudo-code close enough to a real client library that translating it is mechanical. Two pieces of infrastructure need to be running first: a Kafka broker, and a Schema Registry, both reachable at addresses your code will point at.

The schema

We'll reuse the UserRegistered event from chapter 3, trimmed to three fields:

{
  "type": "record",
  "name": "UserRegistered",
  "namespace": "com.example.events",
  "fields": [
    { "name": "userId", "type": "string" },
    { "name": "email",  "type": "string" },
    { "name": "plan",   "type": "string", "default": "free" }
  ]
}

The producer

The only thing that changes from a plain Kafka producer is the value serializer: instead of a raw string or byte-array serializer, you configure the Avro serializer, pointed at the registry's URL. It handles registering-or-looking-up the schema and prefixing the payload with the schema ID for you.

# Producer (pseudo-code, Confluent-style Avro serializer)
value_serializer = AvroSerializer(schema_registry_client, user_registered_schema)
producer = Producer({"bootstrap.servers": "localhost:9092"})

event = {"userId": "u-42", "email": "ada@example.com", "plan": "pro"}
producer.produce(
    topic="user-registered",
    key=event["userId"],
    value=value_serializer(event, SerializationContext("user-registered", MessageField.VALUE)),
)
producer.flush()

Notice the key: event["userId"]. Per chapter 2, that's what keeps every event for a given user in the same partition, in order — worth doing even in a first prototype, because retrofitting a partition key later means every consumer's ordering assumptions can silently shift.

The consumer

# Consumer (pseudo-code, Confluent-style Avro deserializer)
value_deserializer = AvroDeserializer(schema_registry_client)
consumer = Consumer({
    "bootstrap.servers": "localhost:9092",
    "group.id": "user-registered-watchers",
    "auto.offset.reset": "earliest",
})
consumer.subscribe(["user-registered"])

while True:
    msg = consumer.poll(1.0)
    if msg is None:
        continue
    event = value_deserializer(msg.value(), SerializationContext("user-registered", MessageField.VALUE))
    handle(event)

The deserializer never sees user_registered_schema as a hardcoded value — it pulls the schema ID off the front of the message and asks the registry for the matching schema. Change the producer's schema next month, in a backward-compatible way, and this consumer keeps working unmodified.

Pitfall Pointing the producer and consumer at different Schema Registry instances (easy to do by accident across environments). Schema IDs are only meaningful within the registry that issued them — a consumer looking up "schema 7" in the wrong registry gets the wrong schema, or none at all.
Pitfall Starting the consumer after the producer and being confused when nothing shows up. By default a fresh consumer group only sees records produced after it starts; auto.offset.reset: "earliest" (as above) is what lets a new group read from the beginning of the topic instead.

That's the whole loop: a schema, a producer that registers it once and reuses the ID, and a consumer that resolves any ID it sees back to the exact schema it needs. Everything from chapters 2 through 5 is in these two snippets — you just can't see the registry calls, because the serializer and deserializer are making them for you.
