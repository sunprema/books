5. The Schema Registry

A Schema Registry is a small, central service with one job: store every version of every schema your topics use, hand back a compact ID for each one, and — this is the part that earns its keep — refuse a new schema version if it breaks the compatibility rule you've configured for that topic.

The workflow, end to end

Walking it through: the producer's Avro serializer registers (or looks up, if it's already registered) the schema with the registry and gets back a schema ID. It caches that mapping locally, so this round-trip only happens again if the schema actually changes — not on every message. It writes the ID plus the Avro-binary payload to Kafka.

The consumer's Avro deserializer reads the ID straight out of the message, fetches (and caches) the matching schema from the registry, and uses that exact schema to decode the bytes. Crucially, the consumer never needs to know the writer's schema ahead of time — it asks the registry, every time it sees a new ID.

Compatibility modes — the part that actually prevents incidents

Registering a schema isn't a rubber stamp. Each subject (roughly, each topic) has a configured compatibility mode, and the registry checks every new schema version against it before accepting the registration.

ModeWhat it guarantees
BACKWARD (default)Consumers on the new schema can read data written with the previous schema.
FORWARDConsumers on the previous schema can read data written with the new schema.
FULLBoth directions hold at once — the strictest single-version check.
*_TRANSITIVE variantsSame checks, but against every prior version, not just the immediately preceding one.

BACKWARD is the default for a good reason: it's what lets you rewind a consumer group to the beginning of a topic and still read every historical record correctly with today's schema. If your consumers are the thing that gets upgraded first (the common case), BACKWARD is usually what you want.

Pitfall Adding a required field with no default. Under BACKWARD compatibility, a schema reading old data has no value to put in that field for records written before the field existed — so the registry rejects the registration outright, rather than let a consumer discover the gap at runtime.
Pitfall Renaming a field instead of adding a new one (with an aliases entry pointing at the old name). To the compatibility checker, a rename looks like dropping one field and adding an unrelated one — and that usually fails the check for the same reason a required field with no default does.

This is the payoff of the whole chapter: a schema change is no longer "hope everyone downstream noticed the Slack message." It's a registration call that either succeeds — because it's provably compatible — or fails loudly, before a single bad message reaches a consumer.
