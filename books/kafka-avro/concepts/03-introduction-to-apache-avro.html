3. Introduction to Apache Avro

Kafka doesn't care what's inside a record — to a broker, a message is just bytes with a key and a value, both opaque. So the shape of your data is entirely up to you. You could send JSON. Plenty of systems do. So why reach for something else?

Serialization, quickly

Serialization is converting an in-memory value into a byte stream you can send over a network or write to disk; deserialization reverses it. JSON is a serialization format that happens to also be human-readable text — which is convenient for debugging and expensive for everything else: every field name gets repeated in every single message, and there's no enforced structure, so "the schema" lives only in whatever code happens to read the JSON.

What Avro buys you

Apache Avro takes the opposite bet: define the schema once, separately from the data, and let every message skip repeating it. Avro schemas are themselves written as JSON — you're not learning a new syntax, just a new vocabulary of keywords.

{
  "type": "record",
  "name": "UserRegistered",
  "namespace": "com.example.events",
  "fields": [
    { "name": "userId",     "type": "string" },
    { "name": "email",      "type": "string" },
    { "name": "plan",       "type": "string", "default": "free" },
    { "name": "referredBy", "type": ["null", "string"], "default": null }
  ]
}

A record schema needs a name and a fields array; namespace keeps names from colliding across a large codebase, the way a package name does. Each field has a name, a type, and — this matters a lot in the next chapter — an optional default.

Notice referredBy: an optional field is a union with null, written ["null", "string"]. The convention is to list null first, because a field's default value must match the type of the union's first branch — so "default": null only type-checks when null comes first.

Binary vs. JSON encoding

Avro actually defines two wire encodings. The JSON one is verbose and meant for debugging. The one that matters in production — and the one Kafka clients use by default — is the binary encoding, and it's compact for a specific reason: it writes no field names and no type tags at all. Just the raw values, in exactly the order the schema declares.

That's the trade you're making: Avro binary is smaller and faster to parse, but it's not self-describing. Hand someone a raw Avro-binary blob with no schema and they cannot decode it — there's nothing in the bytes to tell them where one field ends and the next begins. JSON never has this problem; it pays for that safety with every field name, every time.

Pitfall Forgetting a default on a field you'll ever want to add or remove later. Without one, evolving the schema breaks compatibility outright — which is exactly what the Schema Registry chapter checks for you before it happens in production.

So Avro alone solves "what shape is this data" — but it doesn't yet solve "how does a consumer know which schema a given binary blob was written with." That's the missing piece, and it's what the next two chapters build.
