Media Ingestion and
Lakehouse Architecture

Two rules organise this chapter, and everything else follows from them. Objects go in object storage; the stream carries the pointer. And the raw layer is immutable, because the ability to reprocess is the only thing that lets you fix a mistake made two months ago.

Separate the bytes from the metadata

The temptation is to put an image in the event so that consumers get everything at once. Resist it: a megabyte payload wrecks a broker's batching, inflates retention costs by orders of magnitude, and means every consumer pays to move data most of them do not want.

Instead the media object is uploaded directly to object storage, and the event carries a reference plus the metadata needed to decide whether to fetch it. Consumers that only need to count detections never touch a byte of imagery.

The upload sequence
1. agent requests an upload URL      // scoped, expiring, per-object
2. agent uploads, resumable multipart // survives a link drop mid-part
3. storage confirms; agent computes content hash
4. agent publishes media.stored.v1 with ref + hash + size
5. indexer verifies hash, records lineage, makes it searchable

Step two matters more than it looks on a rail asset. A resumable multipart upload survives a link that drops halfway through a 600 MB file, which on a moving vehicle is the normal case, not the exception. A non-resumable upload restarts from zero and may never complete at all.

And step three gives deduplication for free. Content hashing means an object uploaded twice — after an ambiguous failure, say — resolves to one stored object, and it doubles as integrity verification: the hash the agent computed must match what storage holds.

Object layout

Layout is close to permanent, because rewriting a petabyte to change a prefix is not a maintenance task. Put the coarse partition dimensions first, and never use a purely random prefix — it defeats every prefix-scoped lifecycle rule and access policy you will later want.

A layout that survives
media/
  raw/
    dt=2026-08-16/           # time first: lifecycle rules key on it
      asset=inspection-car-03/
        run=0447/
          frame-0009412.webp
  derived/
    thumbs/dt=2026-08-16/...
    clips/dt=2026-08-16/...

Separating raw/ from derived/ means a lifecycle policy can expire thumbnails aggressively while raw evidence sits under a seven-year retention rule — and it makes it obvious which prefix is safe to regenerate.

Bronze, Silver, Gold

The medallion architecture layers lakehouse data as Bronze for raw ingestion, Silver for cleaned and conformed data, and Gold for business-ready aggregates; the term was popularized by Databricks around 2019–2020.1 The same layering can be implemented on Apache Iceberg, Delta Lake, or Apache Hudi and queried with Trino, Spark, or Flink, without a proprietary runtime.1,2

Map it concretely for this platform. Bronze: raw telemetry exactly as received, media object references, and the source metadata — append-only, partitioned by ingest date. Silver: normalised, unit-converted, deduplicated on event_id, enriched with asset and location, and with quality flags applied. Gold: per-asset daily health, defect density by track segment, plan-versus-actual, and the feature tables the models consume.

Never edit Bronze

The moment raw is mutable, reprocessing stops reproducing history and every lineage claim becomes unverifiable — which in a regulated domain is the difference between evidence and assertion. Corrections are new rows in Silver, or a new Silver computed from an unchanged Bronze. If a bad batch landed in Bronze, quarantine the partition; do not rewrite it.

Why a table format, not just files

Lakehouse table formats supply ACID transactions, schema evolution, and time travel, which is what makes a raw layer safely reprocessable.2 Without them, a concurrent write during a long-running query gives you a partially-written table and no way to tell.

Iceberg's partition evolution is worth calling out for this workload specifically: changing the partitioning scheme without rewriting the underlying data,2 plus hidden partitioning so queries need not name partition columns. You will get partitioning wrong initially, because the query patterns do not exist until there are queries.

Partitioning for time and space

Telemetry is queried two ways — "this asset over this period" and "this stretch of track over this period" — and one partitioning scheme cannot serve both well.

Partition by date first, since almost every query is time-bounded and lifecycle policies key on it. Then cluster within the partition on the secondary dimension: asset for telemetry tables, track segment for inspection tables. Silver tables are commonly partitioned by business keys or dates, with clustering techniques such as Z-ordering used to improve read performance for common access patterns.1

The anti-pattern to avoid: partitioning spatial data by ingest date alone, so every geographic query scans the whole table. If "show me all findings on main-2 between mileposts 180 and 190" is a common question — and on this platform it is the most common question — the layout has to anticipate it.

Retention is where the money is. Storage costs are decided by policy, not by ingest rate, and a policy nobody wrote is the most expensive kind.

Retention classes and tiering

Chapter 2 estimated petabytes. Whether that is affordable is entirely a question of lifecycle policy, and the policy should be written as a table that an auditor and a finance team can both read.

The fourth row does most of the saving, and it is the one that needs a conscious decision: unflagged imagery is the overwhelming majority of the volume, and keeping it long is the difference between an affordable platform and an unaffordable one. Balance that against Chapter 14's point that you need some negatives to measure recall — hence a sampled subset promoted to the longer retention class.

Lineage and reproducibility

Record, for every derived table: the source tables and the exact snapshot version read, the transformation code version, the run timestamp, and the row counts in and out. With that, "why does this number differ from last week's report?" has an answer, and a regulator's request to reproduce a figure is a job rather than an incident.

Design review questions

  1. Cost your retention table for a three-year fleet plan. Which single row dominates, and what would halving it cost you analytically?
  2. Can you reproduce last quarter's defect-density report exactly? Try it. Note every input you could not pin.
  3. Take your commonest spatial query. Does your partitioning serve it, or does it scan?
