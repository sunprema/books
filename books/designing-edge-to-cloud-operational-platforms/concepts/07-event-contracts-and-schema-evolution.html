Event Contracts and
Schema Evolution

An event that ten teams consume is an API, and it will outlive the service that emits it. In a fleet with twenty-year assets it will also outlive several generations of that service. This chapter is about designing events that can change without a coordinated deployment — because in a fleet you cannot have one.

An event is a published interface

The failure to avoid is the event that mirrors an internal database row. It looks free — the data is right there — and it silently couples every consumer to one service's storage decisions. Renaming a column then becomes a fleet-wide migration.

Design the event for the consumer instead. It should describe something that happened in the world, be self-describing enough to interpret without calling back, and carry its own identity and time.

Topic taxonomy

Name topics so that a person can infer the contents and a machine can route on the prefix. The shape we use throughout: family.stage.major-version.

The topic set for the rail platform
telemetry.raw.v1          # as received: envelope + opaque payload
telemetry.normalized.v1   # validated, unit-converted, typed
asset.position.v1         # derived, keyed by asset, compacted
inspection.detected.v1    # vision detections as events
maintenance.alert.v1      # operator-facing, safety-adjacent
schedule.plan.updated.v1  # optimizer output, versioned plans

The raw/normalized split earns its keep. telemetry.raw is the audit record and the replay source — it is never edited, and it is what lets you re-derive everything downstream when you find a bug in normalisation two months later. telemetry.normalized is what almost every consumer actually reads.

Choosing a serialisation format

There is no universally right answer, but there is a right answer per link, and the constraints differ sharply between the metered radio link and the cloud-internal one.

For this platform: Protobuf on the device link, where every byte is metered and the schema is compiled into firmware anyway; Avro or Protobuf on internal topics, where a registry is available; and JSON at the edges that humans and partner systems touch. Converting once at the gateway is a good trade.

Compatibility, and which direction you need

This is where teams get confused, so let's be concrete about the two directions and which one a fleet actually forces on you.

Backward compatible
A new reader can read old data. You need this to replay history and to deploy a consumer before its producers upgrade.
Forward compatible
An old reader can read new data. You need this whenever producers upgrade first — which, with devices in the field, is always.
Full
Both. The only safe default for a topic consumed by systems you do not deploy.

The fleet consequence is stark: you will have devices on last year's firmware for a long time, and consumers that must handle both. So the rules are the conservative ones — add optional fields, never reuse or renumber a field, never change a field's meaning, and never make an existing optional field required.

A new topic version is a consumer migration

Bumping v1 to v2 is not a schema change, it is a project: dual-publish, migrate consumers one at a time, verify, then retire. Reserve it for genuinely breaking changes. Everything else should be a compatible evolution inside the schema, which costs nobody anything.

The schema registry as a gate

A registry is only worth having if it can say no. Its real job is to reject an incompatible schema at CI time, when the change is cheap, rather than at 2 a.m. when a consumer starts throwing deserialization errors.

  1. Schemas live in version control, reviewed like code.
  2. CI registers them against the registry's compatibility rule and fails the build on violation.
  3. Producers reference schemas by id; the id travels in the envelope.
  4. Consumers resolve the id, cache aggressively, and treat an unknown id as a quarantine case — not a crash.

That last point matters more than it looks. An unknown schema id is exactly the situation a fleet produces when a device runs ahead of a consumer. Quarantining is graceful; crashing takes down a consumer group and stops the traffic behind it.

Contracts continue into the lake

The contract does not stop at the stream. Lakehouse table formats provide schema evolution as a first-class capability, which is what lets a long-lived data contract change without rewriting history.1 Apache Iceberg additionally supports partition evolution — changing the partitioning scheme without rewriting the underlying data — and hidden partitioning, so queries need not name partition columns.1

Partition evolution is not a footnote for a telemetry platform. You will get the partitioning wrong at first, because you cannot know the query patterns before there are queries. Being able to change it without a petabyte-scale rewrite is the difference between a correction and a project.

Governance in the envelope

Some fields are sensitive: crew identifiers, precise positions that reveal individual movement, imagery containing people. Handle it in the contract rather than in each consumer, by classifying at the field level in the schema itself.

Field-level classification, carried by the schema
message CrewAssignment {
  string assignment_id = 1;
  string crew_id       = 2 [(classification) = "pii"];
  string asset_id      = 3;
  int64  starts_at     = 4;
}

With the classification in the schema, masking, retention, and export rules can be enforced by tooling that reads the registry — one implementation, applied everywhere — instead of by twelve consumers each remembering to do the right thing.

Design the event for the consumer you have not met yet. In a twenty-year fleet, that is most of them.

Data-quality contracts

A schema says an event is well-formed. It does not say it is plausible. Publish a quality contract alongside it — expected value ranges, expected arrival rate per asset, the freshness target, and how a consumer should treat a suspect quality flag — and monitor against it. Violations are usually a sensor fault or a firmware regression, both of which are fleet-health signals worth catching early.

Design review questions

  1. Take your busiest event type. Could a consumer written today read an event produced by firmware from three years ago? Try it against real archived bytes, not against a schema diff.
  2. Which of your topics is really a database table with a topic name in front of it?
  3. What does your consumer do with an unrecognised schema id right now? If the answer is "throws", you have a fleet-wide outage waiting for a firmware rollout.
