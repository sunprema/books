Secure Fleet and
Device Management

This is the control plane. It is low-volume, high-consequence software: a bad firmware rollout can strand a fleet, and a mishandled certificate expiry can silence it. The organising insight is that every operation here is a staged, reversible, evidence-producing change — which is a very different shape from the data plane we just built.

The identity hierarchy

A single device id is not enough, because enrollment, authorisation, revocation, and audit each need a different level of the tree. Model all six levels from the start; retrofitting them is painful.

Identity levels and what each one is for
organisation   // tenancy, data residency, contractual boundary
 └ fleet       // policy scope: config, firmware channel, rollout cohort
    └ asset    // what operations names — "loco-4471"
       └ device       // the physical box; replaceable without changing asset
          └ module    // a card or subsystem within the box
             └ sensor // the individual signal source

The asset/device split is the one that pays for itself. A telemetry control unit fails and is swapped; the asset is unchanged, its history must remain continuous, and the new device needs its own credentials and its own audit trail. Systems that conflate the two either lose history at every hardware swap or reuse credentials across physical boxes.

Enrollment and mutual TLS

Production IoT fleets authenticate devices with mutual TLS using X.509 client certificates, so that device and server each establish trust in the other.1 The device proves possession of a private key that ideally never leaves its secure element; the server proves it is the real endpoint, which matters because a device in a rail yard is physically reachable by people you did not vet.

Enrollment is the delicate part, because it is where a device with no credentials acquires some. The three usual approaches, in decreasing order of comfort: a certificate injected during manufacture into a secure element; a claim certificate exchanged for an operational one on first connect; or manual provisioning by a technician. Whichever you pick, record who provisioned what and when — that record is the thing an auditor asks for.

Rotation is a feature you build before you need it

Devices and clients must support rotation and replacement of certificates so operation continues smoothly as certificates approach expiry; periodic rotation of the device certificate and private key is a documented security best practice.2 Build the rotation path on day one and exercise it quarterly. A fleet that discovers its rotation code is broken in the month before expiry has a very bad quarter.

Design rotation to overlap: the device obtains and validates a new credential while the old one is still valid, switches, confirms, and only then reports the old one retired. Never a flag day, and never a window where the device holds nothing usable.

Firmware rollout: canaries and commit windows

A dual-bank (A/B) update scheme keeps an active and a backup firmware slot, downloads the new image into the inactive slot, and switches the bootloader only after validation.3 The mechanism that makes this genuinely safe is the commit window: the newly booted image must signal health before the boot is committed, and the bootloader reverts to the previous slot if it does not.3

That is the whole trick. Rollback is not an operator action taken after a bad night; it is the bootloader's default when the new image fails to prove itself. On a mobile asset that is the difference between a software problem and a recovery truck.

Rollout practice mirrors the same caution: start with a canary cohort of a handful of devices chosen to be geographically and hardware-diverse, soak for a day or two, and promote to progressively larger cohorts only if health gates pass.3 Diversity in the canary matters more than size — ten identical units in one depot will not surface the fault that only appears on the older hardware revision in cold weather.

Configuration and feature flags

Configuration follows the same discipline as firmware, one notch lighter. Version it, scope it to a level of the identity hierarchy, roll it out in cohorts, and — critically — have the device report the configuration version it is actually running in every telemetry envelope. That is what the cfg field in Chapter 4 was for.

Without it you will eventually have a fleet where a third of the devices are on a configuration nobody remembers deploying, and no way to prove which third.

Digital twins: desired versus reported

A device shadow is a cloud-side representation of a device's reported and desired state that lets applications interact with the device while it is disconnected.4 It is the mechanism that makes the control plane usable at all in an intermittently connected fleet: an operator sets desired state now, and the device reconciles when it next appears.

Two properties keep it honest. Reported state must carry a timestamp, so a consumer can see that this "current" state is nine hours old. And desired state should carry an expiry, so an instruction that was reasonable this morning does not execute on a vehicle that reconnects next week.

Desired state without an expiry is an instruction that will eventually be obeyed at the worst possible moment.

Command and control

Commands are the only inbound traffic that changes device behaviour, so they get the strictest handling in the platform: signed individually, scoped to one device, given an expiry, given a unique id so execution is idempotent, and acknowledged in three stages — received, executed, result — matching the acknowledgement discipline from Chapter 5.

And bounded in blast radius. A command channel that can address the whole fleet in one call is a single mistake away from a fleet-wide incident; require an explicit cohort, a rate limit, and a second approver for anything above a threshold.

The safety boundary

Nothing on this command channel may alter safety-critical behaviour. Configuration, telemetry rates, diagnostic modes, software versions — yes. Anything that a safety case depends on is owned by the systems and procedures certified for it, and is not reachable from a cloud control plane. Where the two must interact, the interaction is an advisory input to a system that makes its own decision.

Threat modelling a physically exposed device

Assume the attacker has the device in hand, because eventually someone will. That changes which mitigations are real.

Key extraction
Keys in a secure element, non-exportable. A key in a file on the filesystem is a key you have published.
Firmware tampering
Secure boot with signature verification at each stage; an unsigned image simply does not run.
Impersonation
Per-device credentials only. A shared fleet secret means one compromised unit compromises the fleet.
Replay
Command ids and expiries; a captured command is useless after its window.
Decommissioning
Revocation that works while the device is still physically installed — the common case, and the one most designs forget.

Exercise

  1. Write the certificate rotation sequence as a state machine, including the case where the device loses power mid-rotation. Which state is unrecoverable, and how do you avoid entering it?
  2. Your canary cohort is ten devices. Choose them for a 4,000-vehicle fleet and justify each choice by the failure it could surface.
  3. An operator sets desired state on 300 disconnected vehicles, then realises it was wrong. What is your undo, and how long is the window?
