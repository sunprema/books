Rebalancing, Ordering,
and Correct Processing

The backbone is sound; now the consumers have to be. This is where most real telemetry bugs live — not in the broker, but in a consumer that took too long, got evicted, restarted, and reprocessed an hour of events into a database that was not ready for it.

Why rebalances happen

A consumer group rebalances whenever its membership or its topic metadata changes: a consumer joins, leaves, crashes, is judged dead for missing heartbeats, or partitions are added. The first four are routine. The third and fourth are the ones you cause accidentally.

Under the original eager protocol, a rebalance revokes every assignment across the group and reassigns from scratch — a stop-the-world pause during which nobody consumes. The incremental cooperative protocol, introduced in Kafka 2.4, avoids revoking partitions a consumer will keep owning after the rebalance, which cuts that migration cost sharply.1 It was aimed particularly at heavy stateful consumers such as Kafka Streams applications, where losing a partition means rebuilding local state.1

Two further pieces of the puzzle are worth knowing. Static membership gives a consumer a group.instance.id that persists across restarts, so the coordinator can reapply the same assignment and skip the rebalance entirely during planned restarts or brief outages.2 And KIP-848 defines a next-generation protocol that moves assignment computation to the group coordinator on the broker.3

Writing a rebalance-safe consumer

The rule is short: never do long work inside the poll loop. A consumer that spends ninety seconds calling an external service will miss its heartbeat deadline, be evicted, and trigger exactly the rebalance the work was trying to survive — and then the next consumer will do the same work and be evicted the same way.

The shape that survives
while running {
    let batch = consumer.poll(Duration::from_millis(500));

    // bounded: sized so worst-case latency stays under max.poll.interval.ms
    for msg in batch.iter().take(MAX_PER_POLL) {
        handle_idempotently(msg)?;   // keyed on event_id
    }

    // commit AFTER effects are durable, never before
    consumer.commit(batch.offsets())?;
}

Two details carry the weight. MAX_PER_POLL is sized so the worst-case batch finishes inside max.poll.interval.ms — measure it, do not guess. And the commit happens strictly after the effects are durable: committing first converts a crash into silent data loss, which is far worse than the duplicate you get from committing last.

Also implement the partition-revoked callback. On revocation, flush in-flight work and commit what is genuinely complete; on assignment, load whatever per-partition state you need. Skipping this is how a cooperative rebalance still loses work.

The poison-pill problem

One message cannot be processed — a schema the consumer does not know, a payload that fails a downstream constraint. If the consumer retries it forever, every well-formed message behind it on that partition waits too. One bad event has stopped a locomotive's entire telemetry stream.

The fix is a bounded retry ladder, then get it out of the way:

  1. Retry in-process a few times, with backoff, for transient faults.
  2. Then publish to a delayed retry topic — a separate topic, so the main partition advances.
  3. After a bounded number of ladder steps, publish to a dead-letter topic with the original bytes, the failure reason, and the correlation id.
  4. Alert on dead-letter arrival rate, and provide a replay path.

Note that this deliberately sacrifices ordering for the failed message. That is the right trade: the alternative is sacrificing liveness for every other message on the partition.

The dual-write problem and the outbox

Here is a bug that looks like correct code. A service updates its database and then publishes an event. There is no transaction spanning both, so a failure between them leaves the two inconsistent — the database says the work order exists, the stream never said so.4

The transactional outbox resolves it by writing the event payload into an outbox table inside the same local transaction as the business data, with a separate relay process reading that table and forwarding to the broker.4,5 One transaction, one atomic outcome.

The outbox does not eliminate duplicates — it moves the problem to a place you can solve. Because a relay can republish after a crash, consumers must be idempotent, typically by tracking the ids of messages already processed.5,4 That consumer-side table is the inbox, and the two patterns are meant to be used together.

The inbox: dedup and effect in one transaction
BEGIN;
  INSERT INTO inbox (event_id, consumer, seen_at)
  VALUES (:event_id, 'workorder-svc', now())
  ON CONFLICT DO NOTHING;
  -- 0 rows means we have seen it: skip the effect, commit, move on

  INSERT INTO work_order (...) VALUES (...);
COMMIT;

Bound the inbox. Retaining every id forever is neither necessary nor affordable; retain for the longest replay window you actually support, and say what that window is. An unbounded dedup table is a slow-motion outage.

Exactly-once is not a setting you enable. It is idempotent effects keyed on a stable identity, plus a dedup window you can defend.

Per-asset ordering with cross-asset parallelism

Keying by asset_id gives per-asset ordering, and then a multithreaded consumer can throw it away in a line of code — by handing a partition's messages to a thread pool. If you need concurrency inside a consumer, shard the work by key and keep one worker per key, never a shared pool over one partition.

And be honest about what ordering you actually need. "Events for one asset, in order" is usually sufficient and cheap. "All events across the fleet, in order" is neither, and nobody has ever genuinely needed it.

Testing the claim

A correctness claim you have not tested against the failure is a hope. Build these three tests before you need them:

  • Duplicate injection — replay a known batch twice and assert the effects are identical, not merely "no errors".
  • Kill during processing — SIGKILL a consumer between effect and commit, restart, and assert exactly one effect.
  • Rebalance under load — add and remove consumers during sustained traffic; assert no gaps in per-asset sequence.

Design review questions

  1. What is your max.poll.interval.ms, and what is your measured worst-case batch time? If you do not know the second number, you are relying on luck.
  2. Does any consumer commit before its effect is durable? Find it.
  3. How long is your dedup window, and which replay scenario justifies that length?
