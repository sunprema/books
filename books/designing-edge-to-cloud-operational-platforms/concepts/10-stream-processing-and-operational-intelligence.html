Stream Processing and
Operational Intelligence

Raw telemetry is not operational intelligence. Turning one into the other means windows, joins, and state — and in a fleet with hours-long disconnections, it means confronting the hardest question in the book: when is a window actually finished?

Choosing a processor

The choice matters less than teams expect, and the deciding factor is usually operational rather than technical.

Where each option fits
OptionStrengthCost

A defensible split for this platform: plain consumers on the hot path where the logic is per-event and latency is the whole point, and a real stream processor for the warm path where windows, joins, and event-time correctness are the whole point. Resist the urge to run everything through one engine.

Watermarks, and what a fleet does to them

Watermarks track the progress of event time through a stream and are what let a processor decide a window is complete despite out-of-order arrival.1 A bounded-out-of-orderness strategy encodes the maximum lateness you expect, after which an element is treated as late.1

Now the operational reality. Your expected lateness is not a property of the network jitter — it is a property of the fleet's disconnection profile. A locomotive that spent three hours in a valley will deliver three-hour-old events, correctly, with good timestamps. If your watermark strategy assumes seconds, every one of those events is "late".

Set lateness from the fleet, not the median

A vehicle out of coverage for an hour is not late data — it is a replay. Sizing allowed lateness from the median delay guarantees that every genuine disconnection produces a flood of side-output records that nobody has designed a home for.

Allowed lateness changes a window's termination condition: state is retained past the watermark for a configured duration so late events can update an already-emitted result, and anything later is routed to a side output.2 That gives you three tiers, and you should use all three deliberately.

Within the watermark
Normal path. The window fires once, complete.
Within allowed lateness
The window re-fires with a correction. Downstream must accept a restatement — design for it explicitly.
Beyond allowed lateness
Side output. Route to the reconciliation path, which reprocesses on the cold path rather than trying to patch the live aggregate.

That third tier is the one to design rather than discover. Send it to a topic, count it, alert on its rate, and reconcile in batch. A side output nobody consumes is silent data loss wearing a respectable name.

State, checkpoints, and recovery

Stateful processing is what makes stream processing worth the trouble — per-asset running aggregates, geofence membership, pattern detection across a sequence of events. Checkpointing periodically persists that state so a job can recover from failure while preserving exactly-once application state.2

The failure mode to plan for is state growth. Keyed state for retired assets never goes away on its own, so the backend grows monotonically and every restore gets slower — until one day a recovery takes longer than your RTO. Set a TTL on keyed state, size it from the longest credible disconnection, and monitor state size as a first-class metric alongside lag.

Joins that do not call services

Enrichment wants reference data: which asset is this device on, which route is it assigned, what is the sensor's calibration. The tempting implementation is an RPC per event. Do not: it couples stream throughput to a service's latency and its availability, and it makes replay impossible because the service's state has moved on.

Publish reference data as a compacted topic and do a stream-to-table join instead. The processor holds a local materialised view, the join is a local lookup, and a replay resolves against the reference state as it is — or, if you version reference data, as it was.

Anomaly detection and alert hygiene

Detection is the easy half. Alert hygiene is what determines whether anyone acts on the output, and it is mostly about suppression.

  • Deduplicate on a stable alert key — asset, kind, and a coarse time bucket — so one condition raises one alert.
  • Debounce: require a condition to hold for N samples or T seconds. A single spike is usually a sensor, not a fault.
  • Suppress dependents: if the whole telemetry unit is offline, do not raise forty individual sensor alarms.
  • Escalate on age, not on repetition — an unacknowledged alert should get louder, not more numerous.
  • Rate-limit per asset, with an explicit "N further alerts suppressed" record so the suppression is visible.

The reconnect case deserves its own rule. When a fleet comes back after an outage, hours of buffered telemetry arrive at once and naive detection will raise thousands of alerts for conditions that have already passed. Alerts derived from historical events should be raised as findings on the warm path — recorded, reviewable, not paging — while only current conditions page anyone.

An alert that fires for a condition which has already ended is not an alert. It is a history lesson with a siren attached.

Serving live state

Applications need current state — where is every asset, what is each one's health. Two viable shapes: query the processor's own state store directly, or materialise into a store built for the read pattern. The second is usually right, because operations dashboards have query patterns that a stream processor's state store was not designed for.

Whichever you choose, one requirement is non-negotiable: the response carries its own freshness. Every read returns the event-time watermark behind it, and the UI shows it. That single discipline converts "the system was lying to me" into "the system told me it was four minutes behind", which is the difference between an incident and an inconvenience.

Exercise

  1. Measure your fleet's actual event-time lateness distribution over a week. Set allowed lateness from the p99, then decide what happens to the remaining 1%.
  2. Replay a day of raw telemetry through your warm path. Does it produce the same aggregates? If not, you have a hidden processing-time dependency — find it.
  3. Simulate 4,000 vehicles reconnecting with two hours of backlog. Count the alerts. Then design the suppression that makes that number sensible.
