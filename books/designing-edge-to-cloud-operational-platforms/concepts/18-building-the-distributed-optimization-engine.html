Part VI — Distributed Scheduling and Optimization · Chapter 18

Building the Distributed
Optimization Engine

The model is settled; now it has to run — repeatedly, under deadline, on a cluster, without becoming a source of operational risk in its own right. The organising principle is that an optimization run is a pure function of a pinned snapshot. Everything in this chapter follows from taking that seriously.

Pin the inputs

The tempting design lets solver workers read live operational state directly. It is wrong twice over: runs become non-reproducible because the state moves underneath them, and planning latency becomes coupled to operational load.

Instead, a run begins by materialising an immutable snapshot — asset positions and availability, crew rosters, committed maintenance windows, network model version, the current plan — written once, identified, and never modified. Workers read only from it.

The job descriptor is the whole reproducibility story
{
  "job_id":        "opt-2026-08-16-1140-a3f",
  "snapshot_id":   "snap-2026-08-16T11:38:02Z",
  "snapshot_age_s": 118,
  "horizon":       { "from": "2026-08-16T12:00Z", "to": "2026-08-17T00:00Z" },
  "scope":         { "division": "west" },
  "weights_ver":   "policy-2026-07",
  "constraints_ver": "rules-4.1.0",
  "solver":        { "name": "cbc", "version": "2.10.11", "seed": 42 },
  "deadline_s":    240
}

Reproducibility requires pinning the input snapshot, the model and constraint versions, and the solver version together, since any of them changes the result. That is why all four appear in the descriptor, along with the random seed — many solvers use randomised heuristics, and an unpinned seed alone will make two runs disagree and cost you a day of investigation.

Isolation and admission

Optimization is bursty and resource-hungry, and it must not be able to hurt the operational path. Run it in its own cluster or node pool, with its own quota. Chapter 11's dependency rule applies with full force: the operational services must not synchronously depend on the optimizer, so a solver stampede degrades planning and nothing else.

Admission control matters too. Jobs arrive from schedules, from material events, and from planners exploring what-ifs. Give each source a quota, so an enthusiastic scenario exploration cannot starve the scheduled replan that operations depends on.

Worker pools and partitioning

Two shapes of parallelism, and they suit different problems. Map-reduce style works when partitions are genuinely independent — scenario evaluation, or corridors with fixed boundary commitments. Coordinated search is needed when partitions must agree on shared resources, and it costs you a communication protocol between workers plus a convergence criterion.

Start with the first. Fix boundary commitments from the previous plan, solve corridors independently, then reconcile: if a boundary commitment could not be met, either renegotiate it in a second round or accept the penalty and record it. Two rounds of independent solving usually beat one round of coordinated search, and it is dramatically simpler to operate.

Deadlines, checkpoints, preemption

Optimization has no natural stopping point — it has an anytime quality curve. So give every job a hard deadline and require the solver to surrender its best feasible solution when the deadline arrives. A good plan now beats a better plan after the window it applied to has passed.

Checkpoint long runs. Checkpointing is what makes distributed work restartable rather than restart-from-zero — the same property stream processors get from periodic state snapshots. Persist the incumbent solution and search state periodically so a lost worker resumes rather than restarts.

And if you preempt a job for a higher-priority one, checkpoint it first. Preempting without checkpointing converts priority scheduling into wasted compute, and it will happen precisely during a disruption when both jobs mattered.

Validate before publishing

Never publish a solver's output unchecked. The assumption that a solver cannot violate its own hard constraints is wrong often enough to be dangerous: model bugs, numerical tolerance, and a mis-encoded constraint all produce confidently infeasible plans.

Run an independent validator — deliberately written separately from the model, ideally by someone else — that re-checks every hard constraint against the plan. If validation fails, the plan is discarded, the previous plan stands, and an alert fires. This is cheap, it is fast, and it is the difference between a bad plan reaching a dispatcher and not.

The validator is not the model

If the validator reuses the model's constraint code, it will agree with the model's bugs. Write it independently, against the specification rather than the implementation. The redundancy is the point.

Publishing plans as versioned events

A validated plan is published as an immutable event carrying its full provenance — the job descriptor from the start of this chapter, the objective breakdown, the boundary commitments, and the diff against the plan it supersedes.

The diff is what makes the plan usable by humans. A dispatcher does not want to read a fresh 400-movement schedule; they want to know what changed and why. "Movement 4471-E delayed 12 min to resolve a block conflict at MP 186" is reviewable. A new complete plan is not.

Approval, override, rollback

Plans above a change threshold should require human approval; below it, auto-apply with notification. Set the threshold from the operational consequence of the change, not from its size in rows.

Overrides are first-class, not exceptions. A dispatcher who changes one movement is recording an operational constraint the model did not know about — capture it as a pinned commitment that the next run must respect, and capture the reason. Overrides that recur are the model's best bug report.

And rollback is trivial by construction: plans are immutable and versioned, so reverting is republishing the previous version. That is the payoff for refusing to overwrite plans in place.

Every override is a constraint the model did not know about. Treat the pattern as a specification, not as user error.

Exercise

  1. Run the same job descriptor twice. Do you get an identical plan? If not, find the unpinned input — it is usually a seed, a clock, or a live read.
  2. Write the independent validator for your three most important hard constraints. Then deliberately break the model and confirm the validator catches it.
  3. Analyse a month of dispatcher overrides. Which recur? Each recurring one is a missing constraint.
