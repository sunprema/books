16

Spatial Data and
Inspection Workflows

A latitude and longitude is not an address a maintenance crew can be dispatched to. Rail operations reasons in track segments and mileposts, and the translation between the two is a real subsystem with real failure modes. This chapter builds it, then builds the defect lifecycle on top.

Linear referencing

Linear referencing identifies positions along a linear feature by a relative measure — typically distance from a known origin — rather than by explicit x,y coordinates.1,2 In railways, mileposts are the most commonly used referent, and obstructions, signals and assets are logged against track-based measures.1 The system has an axis along which measures are taken, which may be a track segment or a whole line.2

The data-modelling payoff is substantial. Storing one version of the linear geometry and referencing data to it as event tables — rather than segmenting the geometry per attribute — means attribute updates edit compact event tables instead of many small line features, and queries typically run faster.1,3 In GIS platforms this is realized as m-aware route feature classes plus event layers holding the tabular data.3

Turning GPS into a track position

Map-matching a GPS fix to a track position is the awkward part, and it is awkward for a reason worth understanding: parallel tracks in a corridor can be four metres apart, well inside GPS error. Position alone cannot tell you which track a vehicle is on.

So use more than position. Heading disambiguates direction of travel; recent history constrains which track is reachable; the movement authority or scheduled route, if available, is strong evidence; and wayside detector passes give occasional exact fixes to snap to. Then — this is the important part — emit a confidence with the match, and let consumers decide what a low-confidence position is worth.

A resolved position, with its uncertainty
{
  "asset_id":    "loco-4471",
  "event_time":  "2026-08-16T09:14:22.418Z",
  "raw":         { "lat": 41.8213, "lon": -87.6412, "hdop": 1.4 },
  "matched": {
    "track_id":    "main-2",
    "milepost":    184.372,
    "direction":   "increasing",
    "confidence":  0.94,
    "network_ver": "2026-Q2"      // which survey this measure refers to
  }
}

Keep the raw fix alongside the match. When the network model is re-surveyed, or the matcher is improved, you can re-derive every historical position — and you will want to, because early matching is always the worst matching.

A measure is meaningless without a network version

Mileposts are not uniformly spaced — historical realignments leave long and short miles — and they are periodically re-surveyed. Milepost 184.372 under the 2026-Q2 network is not necessarily the same physical place as under the 2019 network. Version the network model and stamp every measure with the version it was computed against, or your historical defect locations will drift silently.

Spatial indexing that fits the question

Two query shapes dominate, and they want different indexes. "Everything on this track between these mileposts" is a one-dimensional range query on (track_id, milepost) — an ordinary B-tree, fast and boring, and it covers most operational queries. "Everything within 500 metres of this point" is genuinely two-dimensional and wants a geospatial index on the raw coordinates.

Keep both. The linear index serves operations; the geospatial index serves analysis and the map view. Trying to serve operations from the geospatial index is the common mistake, and it makes the most frequent query in the system the slowest.

The inspection finding

A finding is the durable operational object — distinct from a detection, which is one model's opinion about one frame. Several detections of the same physical defect across several passes should converge on one finding, and that correlation is the interesting logic.

Correlate on location within a tolerance, defect class, and a time window; the tolerance has to account for the position confidence above. Then the finding accumulates evidence over time: each pass adds a detection, and a defect seen on four consecutive runs is a far stronger signal than one seen once — both for prioritisation and for suppressing false positives.

The defect lifecycle

Two transitions carry the design. Closure is on verification, not on repair: a repair that did not fix the problem must not close a finding, and the verification pass — usually the next inspection run over that segment — is what confirms it. Closing on repair loses exactly the evidence that repairs work.

And the rejection path feeds back. A reviewer rejecting a detection is producing a labelled negative, which Chapter 14 needs. Capture the reason — wrong class, wrong location, shadow, water on the rail — because "rejected" alone teaches the model nothing.

A finding closes when a later pass confirms the defect is gone. Anything earlier is a claim about a repair, not evidence of one.

Training data from production

Every adjudication is a label, and the lifecycle above generates them continuously. Two cautions keep the resulting dataset honest.

First, the reviewed population is biased — it is dominated by what the current model flagged. Training only on it teaches the next model to agree with the last one. The random negative sample from Chapter 14 is the corrective, and it has to be genuinely random.

Second, split by geography and time, not randomly. Frames from the same run are highly correlated, so a random split puts near-duplicates in train and test and produces an evaluation score that is simply wrong. Hold out whole runs, or whole corridors.

Exercise

  1. Design the correlation rule that merges detections across passes into one finding. What tolerance, and how does it change with position confidence?
  2. The network is re-surveyed and mileposts shift by up to 30 m. Write the migration for 400,000 open and historical findings.
  3. Measure the time from detection to verification for last quarter's findings. The distribution's tail is usually the real story.
