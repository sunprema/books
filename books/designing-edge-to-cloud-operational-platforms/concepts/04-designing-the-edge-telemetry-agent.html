Designing the
Edge Telemetry Agent

The agent is the piece of software that runs on the vehicle, and it is the most constrained thing you will write: limited CPU, a disk that has to survive vibration, a clock you cannot trust, and no operator. It is also the piece that determines whether the rest of the platform ever sees the truth. Let's build it a responsibility at a time.

Seven jobs, in dependency order

An agent that tries to be clever fails in the field. An agent that does these seven things well is boring and survives, and the order matters because each one depends on the one before it.

  1. Protocol adaptation — speak J1939, Modbus, or whatever the equipment offers, and translate it into one internal shape.
  2. Validation — range checks, unit checks, plausibility. A sensor reporting −400 °C is a fault report, not a reading.
  3. Local enrichment — attach identity, sequence, firmware and configuration version. Only from state the agent already holds.
  4. Durable buffering — write to disk before acknowledging anything upstream of it.
  5. Batching and compression — because the link is metered.
  6. Local rule evaluation — the small set of conditions that must be detected without the cloud.
  7. Secure command receipt — verify, execute, acknowledge, and be able to say which of those three it got to.

Job three has a trap in it. "Enrichment" tempts you to look up something in the cloud — the asset's current assignment, say. Don't. The moment enrichment needs a network round trip, the offline path depends on the online path, and the agent stops being able to do its job in the exact conditions it exists for.

The edge data model

Here is the envelope we will carry for the rest of the book. Every field in it exists because leaving it out costs you something downstream.

The telemetry envelope
{
  "event_id":   "01J8Z3K2QF7M9YB0H4V2N6TA5C",  // ULID: unique + sortable
  "device_id":  "loco-4471-tcu",               // the box
  "asset_id":   "loco-4471",                   // the thing operations cares about
  "sensor_id":  "traction.motor.2.temp_c",
  "seq":        918342,                       // per-device, monotonic, gap-detecting
  "event_time": "2026-08-16T09:14:22.418Z",
  "ingest_time": null,                        // stamped by the cloud, never here
  "value":      104.5,
  "quality":    "good",                      // good | suspect | substituted | bad
  "fw":         "3.11.2",
  "cfg":        "cfg-2026-07-01",
  "clock_src":  "gps"                        // gps | ntp | rtc | unsynced
}

Three of those deserve defending. seq is what lets the cloud detect a gap without comparing timestamps — a missing range of sequence numbers is unambiguous evidence of loss, where a time gap could just be a quiet sensor. quality means a suspect reading can flow through the pipeline and be excluded by consumers, rather than being silently dropped at the edge where nobody can audit the decision.

And clock_src is the one people leave out and regret. Vehicles lose GPS lock in tunnels and depots; an unqualified device timestamp silently corrupts every event-time window downstream. Recording how the time was obtained lets a stream processor treat unsynced events differently — usually by falling back to ingest time and marking the result.

Never trust the device clock, but do record it

The instinct to "fix" a bad timestamp at the edge is wrong: it destroys the evidence. Send what the device believed, plus how confident it was. Correction is a cloud-side decision made with more context than the agent has.

Durable buffering: the write-ahead log

The pattern the industry has converged on for intermittently connected assets is local persistence plus store-and-forward at the edge, with a durable cloud buffer isolating producers from slower downstream consumers.1 In practice, edge gateways implement this as a page-based on-disk buffer: messages are queued to disk when the connection fails and published once it is restored.2

The detail that makes it correct is acknowledgement tracking. A buffer page is recycled only after every message on it has been acknowledged, which requires per-message delivery confirmation rather than a fire-and-forget send.3 Get this wrong and the buffer will happily reuse a page whose contents never landed.

Disk exhaustion is a policy, not an error

Eventually the buffer fills. A locomotive out of coverage for three days will exhaust any disk you can afford to fit. What happens next must be a decision you made at design time, because the default — drop the oldest — discards exactly the alert you needed while preserving a week of routine diagnostics.

Retention classes and their eviction behaviour
ClassExampleWhen the disk fills
CriticalFault alert, safety-adjacent eventNever evicted; evict others first
High-valuePosition, traction healthDownsample in place
RoutineDiagnostic countersAggregate to min/max/mean per window
BulkWaveform captures, mediaEvicted first, and a marker kept

Two refinements make this humane. First, downsample rather than delete where you can — a minute-resolution summary of an hour costs almost nothing and preserves the shape. Second, leave a marker: an explicit "N events of class X evicted between T1 and T2" record, so the cloud can tell the difference between a quiet sensor and a full disk. And raise a local alarm; disk exhaustion is a fleet-health signal that should reach operations before it reaches the data.

Choosing a runtime

The constraints are a fixed memory ceiling, multi-year uptime, and no operator to restart anything. That points at a small set of choices, and the tradeoff is real rather than a matter of taste.

Rust
No GC pauses, predictable footprint, strong story for the I/O and framing code. The default choice for a constrained gateway.
Go
Faster to write, good concurrency, GC pauses that are acceptable unless you are near a hard latency bound. A reasonable fleet default.
Elixir / BEAM
Supervision trees and hot upgrades are genuinely valuable on a box you cannot reach; the cost is a heavier runtime than the smallest devices allow. Strong for gateways, weak for microcontrollers.
C / C++
Sometimes the only option the hardware vendor supports. Budget for the memory-safety work you are taking on.
The agent's job is not to be smart. It is to never lose an event it accepted, and to be honest about the ones it could not keep.

Exercise

  1. Size the agent's disk for your worst credible outage at your event rate. Now halve it and write the eviction policy that makes that survivable.
  2. Implement gap detection from seq alone. What does your detector do when a device is reflashed and its sequence resets?
  3. Trace one event from sensor to durable ack and mark every point where it could be lost without anyone noticing. Each mark is a required metric.
