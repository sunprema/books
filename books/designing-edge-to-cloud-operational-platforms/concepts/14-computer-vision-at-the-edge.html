Computer Vision
at the Edge

Vision breaks the telemetry mould in three ways: the data is thousands of times larger, the processing is expensive enough that where you run it is an architectural decision, and the output is a probabilistic claim about the world. That third one is the deep difference, and it changes what the platform must carry.

Why it needs its own pipeline

A telemetry event is a few hundred bytes and is either right or wrong. A 4K inspection frame is megabytes, and a detection on it is "82% confident there is a rail surface defect here". You cannot alert on that the way you alert on a temperature threshold, and you cannot ship every frame the way you ship every reading.

~2 MB
Inspection car, 8 h at 10 fps

Detections from that run
~3 MB

Look at the last two rows. The findings from a full inspection run fit comfortably in the event stream; the imagery does not, by five orders of magnitude. That ratio is the whole architecture: run inference where the pixels are, ship the findings, and upload only the evidence that matters.

Edge or cloud inference

The established shape for industrial defect detection is: models trained in the cloud, optimized for the edge hardware, deployed through a managed rollout mechanism, and monitored for drift with results synchronized back to the cloud.1 Inference inputs and outputs are captured at the edge and synchronized to the cloud for human review and retraining.1

The tradeoff, honestly stated
Edge inferenceCloud inference
BandwidthFindings onlyEvery frame uploaded
LatencyMillisecondsLink-bound; often hours
Model updateFleet rollout, stagedInstant, central
Compute costHardware per vehicleElastic, metered
ReprocessingOnly what was uploadedEverything, any time

The last row is the one that decides most real designs. If you only kept the frames the model flagged, you can never re-run an improved model over what the old one missed — and "what the old model missed" is precisely the population you care about. The usual resolution is a hybrid: edge inference for the operational path, plus a sampled and event-triggered upload that preserves enough raw material to retrain and re-evaluate.

Adaptive upload

Design the upload policy explicitly, in priority order, and make it configuration rather than code — you will tune it for years.

  1. Every detection above the review threshold, with a short clip either side for context.
  2. Everything near the decision boundary — the uncertain band is where the model learns most.
  3. A random sample of confidently-negative frames, which is the only way to estimate false negatives at all.
  4. Anything a human flagged from the cab.
  5. Bulk raw, depot links only, retained briefly.

Item three is routinely omitted and it is the one that makes your metrics honest. Without a sample of what the model said "nothing here" about, you can measure precision but never recall, and a model that quietly stopped detecting a defect class looks perfect.

Detections as events

A detection joins the same stream as everything else, and carries what a reviewer and a future auditor will need.

inspection.detected.v1
{
  "event_id":      "01J8ZB4M0K2R7T9V3XW6QH8N2D",
  "asset_id":      "inspection-car-03",
  "event_time":    "2026-08-16T11:02:44.120Z",
  "defect_class":  "rail_surface_spalling",
  "confidence":    0.82,
  "bbox":          [0.41, 0.55, 0.09, 0.07],   // normalised
  "position": {
    "track_id":    "main-2",
    "milepost":    184.372,             // see chapter 16
    "network_ver": "2026-Q2"
  },
  "media_ref":     "s3://insp/2026/08/16/car03/frame-0009412.webp",
  "model":         { "name": "railsurf", "version": "4.2.1" },
  "review":        { "status": "pending" }
}

Two fields carry disproportionate weight. media_ref is a pointer, never the bytes — media lives in object storage and the stream carries the reference, for the reasons Chapter 15 goes into. And model.version is non-negotiable: without it, a regression cannot be attributed or bounded, and "which findings came from the bad model" is unanswerable at exactly the moment it is asked.

A confidence score is not a probability

0.82 does not mean "82% of such detections are real" unless the model has been calibrated to say so. Setting a review threshold on the assumption that it does is how teams end up with a review queue whose true positive rate is nothing like what they planned. Calibrate against reviewed outcomes, and re-calibrate after every model change.

Drift, and why it is not a software fault

Vision systems degrade in production from physical and environmental causes — dirty lenses, shifting lighting, changes to the inspected subject — which appear as data drift rather than as software faults.2 Nothing crashed; the model is simply no longer looking at the world it was trained on.

Drift is detected by comparing production input distributions against a training reference using statistical measures, with low-confidence predictions routed to human review while precision, recall and F1 are tracked operationally.2,3 And mature edge-ML operations track model version per device centrally and can roll back on measured degradation within minutes.3

The review queue is a product

Production failures — false positives corrected by operators, false negatives found downstream, edge cases flagged for review — are the most valuable training data the system produces.2 That only holds if the review tool captures them as structured labels.

So build the queue as a first-class surface: prioritised by confidence band and consequence, showing the reviewer enough context to judge (the frame, its neighbours, the location, the asset's history), and capturing a verdict that is specific — confirmed, rejected, wrong class, wrong location — rather than a thumbs-down. A rejected detection with a reason is a label; a rejected detection without one is a lost opportunity.

Track queue depth and time-to-review as operational SLIs. A review queue that grows without bound is a detector that has effectively been turned off, and it will be discovered as such at the worst time.

The safety boundary

A detection is a finding that prioritises human inspection. It is not a determination that track is unsafe, and it must never be the sole basis for a decision with safety consequence. Equally, the absence of detections is not evidence of absence of defects — which is why the false-negative sampling above is a design requirement rather than an ML nicety.

Exercise

  1. Compute your bandwidth budget for a full inspection run under each of the five upload priorities. Where does the budget actually run out?
  2. Design the rollback: a model ships, and six hours later its false positive rate has tripled. How do you detect it, how fast can you revert the fleet, and what happens to the findings it already emitted?
  3. Estimate your recall. If you cannot, add the negative sampling that would let you.
