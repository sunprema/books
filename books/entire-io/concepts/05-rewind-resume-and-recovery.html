05 When the agent goes sideways

Rewind, Resume, and Recovery

AI agents are powerful, but they are not infallible. They go down rabbit holes. They misinterpret a prompt. They produce code that compiles but solves the wrong problem. They refactor three files when you asked them to fix one. You have seen this happen — and the instinct is to hit Ctrl-Z, close the session, start over. But "start over" means losing all the context the agent built up: the files it read, the approaches it explored, the constraints it discovered. Entire gives you a better option: rewind to a known-good checkpoint and try again, with the full context of what went wrong still available.

Why Rewind Matters

Let us draw a simple scenario on the whiteboard. You start a session, ask the agent to refactor an authentication module, and checkpoint after it finishes the first step successfully. Then you ask it to continue with step two. The agent takes a wrong turn — it decides to replace the entire auth library instead of refactoring the existing code. By the time you notice, it has modified eight files, introduced a new dependency, and broken three tests.

Without checkpoints, your options are grim. You can try to manually undo the changes. You can git stash or git reset --hard to throw away the code changes. But even if you recover the files, you have lost the session context. The agent no longer knows what it already tried, what constraints it discovered, or what the original plan was. You are starting from zero.

With Entire, you rewind to the last good checkpoint. The code goes back. The context goes back. You are standing at the exact moment before things went wrong, with the full conversation history still available, and you can re-prompt the agent with better instructions.

Key idea

Rewinding code without rewinding context is useless. If you restore the files but lose the conversation, the agent starts from zero and is likely to make the same mistake again. Entire rewinds both, together.

The Rewind Operation

Conceptually, a rewind does three things:

1. Restores the code state. The working tree is returned to the exact state it was in at the target checkpoint. Files that were added after the checkpoint are removed. Files that were modified are restored. Files that were deleted are brought back. This is similar to git reset, but scoped to the checkpoint rather than to an arbitrary commit.

2. Restores the session context. The agent's conversation history is rolled back to the point of the checkpoint. The prompts, reasoning, and tool calls that happened after the checkpoint are preserved in the session log (so you can review what went wrong), but the active context is reset to the checkpoint state.

3. Preserves the record. The work that happened after the checkpoint is not deleted. It remains in the session history as a branch of exploration that was abandoned. You can review it later to understand what went wrong, or even cherry-pick specific insights from it.

The curved arrow in the diagram is the rewind. You are jumping back in both timelines simultaneously. The red nodes (CP3, CP4) are not erased — they are retained as a record of the abandoned path. But the active working state snaps back to CP2, and you can continue from there with a fresh prompt.

The Resume Operation

Rewind is about going back. Resume is about picking up where you left off. These are different operations that solve different problems.

Here is the resume scenario: you have been working with an agent for forty-five minutes. It has read dozens of files, built up a deep understanding of your codebase, and is halfway through a complex refactoring. Then your laptop runs out of battery. Or you need to switch to a meeting. Or your terminal crashes. The session ends.

Without Entire, that is forty-five minutes of context gone. You can start a new session with the same agent, but it will not remember anything from the previous session. It will need to re-read files, re-discover constraints, and re-build the mental model it already had. You are paying the context-building cost a second time.

With Entire, you resume the session. The agent picks up from the last checkpoint, with the full conversation history available. It knows what it already read, what it already tried, and what the plan was. The interruption costs you the time between the last checkpoint and the interruption — not the entire session.

In practice

Regular checkpointing is insurance against interruption. If you checkpoint every time the agent completes a meaningful unit of work, the worst case on resume is re-doing the last unit. If you never checkpoint, resume has nothing to work with.

Recovery Patterns

Rewind and resume are the primitives. The interesting part is the patterns they enable. Let me walk through the three most common recovery scenarios.

Pattern 1: The broken build

The agent produces code that does not compile, does not pass tests, or breaks existing functionality. You have tried asking it to fix the issue, but it is making things worse with each attempt — a familiar downward spiral.

The recovery: Rewind to the last checkpoint where tests were passing. You now have working code and the context of everything that was tried. You can re-prompt with more specific instructions: "Refactor only the handler function, do not change the middleware, and run the tests after each change."

Pattern 2: The wrong path

The agent understood your prompt but chose the wrong approach. It decided to rewrite a module from scratch when you wanted incremental changes. It introduced a new framework when you wanted to use the existing one. The code might even work, but it is not what you wanted.

The recovery: Rewind to before the wrong approach started. Review the agent's reasoning in the abandoned checkpoints to understand why it chose that path. Then re-prompt with explicit constraints: "Use the existing Express middleware. Do not introduce new dependencies."

Pattern 3: The interrupted session

The session ended unexpectedly — crash, timeout, network loss, or simply running out of time. The work was halfway done. Some files have changes that depend on other files that have not been updated yet.

The recovery: Resume from the last checkpoint. The agent gets the full context back and can continue the work. If the partial changes are in a bad state, rewind to the previous checkpoint first, then resume from clean state.

Recovery patterns at a glance
Scenario Symptom Operation Key benefit
Broken build Tests fail, agent spiraling Rewind to last green checkpoint Working code + context of failures
Wrong path Code works but wrong approach Rewind to pre-divergence checkpoint Can re-prompt with constraints
Interrupted session Session ended mid-work Resume from last checkpoint Context preserved, minimal re-work
Exploratory dead end Agent explored, found nothing useful Rewind, keep findings in log Negative results documented

Comparison with Git Recovery Tools

Git already has recovery mechanisms. It is worth understanding how checkpoints differ from them and why the distinction matters for agent-driven work.

git reset --hard restores your working tree to a previous commit. It is effective for code recovery, but it knows nothing about agent context. After a hard reset, you have the old files but the agent starts from scratch. The reset is code-only — the conversation, the reasoning, the tool calls are all gone.

git revert creates a new commit that undoes a previous commit. It preserves history, which is good, but it operates at the commit level, not the intent level. If the agent made five commits during a wrong-turn exploration, you need to revert each one or use a range revert. And again, no context is restored.

git stash saves uncommitted changes for later. It is useful for human workflows but irrelevant for agent recovery — agents typically commit their work, and the problem is usually committed code, not uncommitted changes.

Git recovery tools restore code state. Entire's rewind restores code state and reasoning state, together. That is the difference between starting over and continuing intelligently. Why checkpoints beat git reset for agent work

The fundamental gap is that git's recovery tools only operate on one of the two timelines. They can rewind the code, but they cannot rewind the context. Entire's rewind operates on both simultaneously, which is why it is a better fit for agent-driven development.

The Checkpoint Discipline

Recovery only works if you have checkpoints to recover to. This raises a practical question: when should you checkpoint?

The answer is straightforward: checkpoint after every meaningful unit of progress. "Meaningful" here means a state you might want to return to. Think of it like saving a game: you save before the boss fight, not after you have already lost half your health.

Good checkpoint moments include: after the agent completes a subtask successfully, before asking the agent to do something risky or experimental, when the tests are all passing and the code is in a clean state, and at natural transition points in the work (research done, moving to implementation).

Bad checkpoint moments: mid-refactoring when files are in an inconsistent state, after the agent has produced code you have not reviewed, during a debugging spiral where nothing is working.

Trap

Do not confuse frequent checkpointing with frequent committing. A checkpoint captures the full state: code, context, conversation. A commit captures only a file diff. You might make ten commits between two checkpoints, or one commit per checkpoint. The cadences are independent.

The Deeper Insight

Step back from the mechanics for a moment and consider what rewind and resume represent. They are an acknowledgment that agent-driven development is inherently non-linear. Agents explore. They try things. Some of those things do not work. That is not a bug in the agent — it is the nature of the work.

Traditional development tools assume a mostly linear workflow: write, commit, push. Yes, you branch and merge, but the expectation is forward progress. Agent-driven development is more like a search algorithm: explore a direction, evaluate the result, backtrack if necessary, try a different direction. Checkpoints are the nodes in that search tree. Rewind is backtracking. Resume is re-entering the search from a saved state.

Once you see it this way, the checkpoint is not just a safety net — it is a fundamental part of the workflow. You checkpoint not because something might go wrong, but because exploration is the process, and you need waypoints to navigate by.

Key idea

Agent-driven development is a search process, not a linear march. Checkpoints are the nodes. Rewind is backtracking. Resume is re-entering the search. Together, they make non-linear exploration safe and efficient.

In the next chapter, we will extend this model beyond a single agent. When multiple agents work together — one researching, one implementing, one testing — the checkpoint becomes something even more powerful: a handoff document that transfers not just code but understanding.
