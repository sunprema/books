08 What to capture, what to forget

Privacy, Redaction, and Trust

Durable context is valuable precisely because it captures what happens during a coding session — the prompts, the reasoning, the tool calls. But "what happens during a coding session" can include API keys pasted into prompts, customer names in debug output, internal URLs in stack traces, and proprietary logic discussed in plain text. The same richness that makes session context useful for review makes it dangerous if stored carelessly.

This chapter is about the tension between capturing enough context to be useful and capturing so much that you create a liability. There is no universal answer. But there is a framework for thinking about it, and that framework starts with understanding what actually ends up in a session transcript.

What lives inside a session

When an agent works on your codebase, the session transcript records everything that flows through the conversation. Let me draw the data categories on the whiteboard:

The first category — prompts, reasoning, tool calls — is almost always safe to store. This is the core value of Entire: capturing the "why" and "how" behind code changes. The second category depends on your organization's security posture. The third needs redaction. The fourth should never enter a session transcript in the first place.

Trap

Developers routinely paste secrets into agent prompts. "Here is the API key, now call this endpoint and debug the response." That key is now part of the session transcript. If the session is checkpointed to a shared branch, the key is in your Git history forever — even if you delete the branch later. Git does not forget.

How secrets enter sessions

Secrets rarely arrive through a single obvious channel. They leak in through multiple paths:

  • Direct prompt injection: Developer pastes a key into the conversation — "Use this token: sk-abc123..."
  • Environment variable exposure: Agent reads .env files or runs commands that print environment variables
  • Debug output: Agent runs a failing API call, and the error response includes the auth header
  • Log file contents: Agent reads log files that contain request bodies with credentials
  • Stack traces: Error traces that include connection strings or configuration values
  • Copy-paste from dashboards: Developer shares a screenshot or text from an admin console

Each of these is a vector for sensitive data entering the checkpoint branch. And the challenge is that most of them happen incidentally — the developer is focused on solving a problem, not on what data might end up in the transcript.

The data handling matrix

Here is a practical framework for classifying data in sessions and deciding how to handle each category:

Data category Example Risk level Handling
Prompts and instructions "Refactor the auth module to use JWT" Low Capture as-is
Agent reasoning "I will check if the middleware handles expired tokens" Low Capture as-is
Tool call metadata Read file: src/auth/middleware.ts Low Capture as-is
Source code fragments Function bodies, class definitions Medium Capture; restrict branch access
Internal URLs https://api.internal.company.com/v2/users Medium Capture or redact; depends on repo visibility
API keys and tokens sk-proj-abc123..., ghp_xxxx Critical Redact before checkpoint
Database credentials postgres://user:pass@host/db Critical Redact before checkpoint
Customer PII Names, emails, phone numbers in debug output Critical Redact before checkpoint
Production secrets Encryption keys, master passwords Severe Never include in session; rotate immediately if exposed

Redaction: stripping before storing

Redaction is the process of removing or replacing sensitive data from a session transcript before it is committed to the checkpoint branch. The goal is to preserve the structure and reasoning of the session while eliminating the specific values that pose a risk.

A well-redacted session still tells you: "The developer asked the agent to debug an API authentication failure. The agent read the middleware, found a token validation bug, and fixed it." What it does not tell you is the specific API key, the specific customer whose request failed, or the specific internal endpoint URL.

Key idea

The goal of redaction is to preserve intent while removing identity. The reasoning is valuable. The specific credentials are not. A redacted transcript should still tell you why a decision was made without telling you who it was about or what keys were used.

Common redaction patterns include:

  • Replacing API keys with [REDACTED_API_KEY]
  • Replacing email addresses with [REDACTED_EMAIL]
  • Replacing connection strings with [REDACTED_CONNECTION_STRING]
  • Replacing JWT tokens with [REDACTED_TOKEN]
  • Replacing IP addresses with [REDACTED_IP]
In practice

Entire performs automatic secret detection during checkpointing. It also integrates with OpenAI's Privacy Filter (OPF) — a 1.5-billion-parameter model for PII detection — applied at pre-push time. Commits on the checkpoint branch that pass through OPF receive an Entire-OPF-Applied: true trailer, so you can verify redaction was applied. For organizations that need stronger isolation, Entire also supports routing checkpoint data to a separate private repository via its checkpoint remote configuration.

Public vs. private repos: different risk profiles

The risk calculus changes dramatically based on repository visibility:

Factor Private repo Public repo
Who can see the checkpoint branch Team members with repo access Anyone on the internet
Source code in transcripts Low risk — already visible to team Medium risk — reveals implementation details
Internal URLs Acceptable with team trust Must redact — exposes internal infrastructure
API keys Must redact Must redact — immediate compromise risk
Architecture discussions Low risk — shared context Medium risk — reveals system design to competitors
Recommended approach Capture broadly, redact secrets Capture selectively, redact aggressively

For open-source projects, the checkpoint branch is as public as any other branch. Every session transcript, every prompt, every piece of reasoning is world-readable. This means redaction is not optional — it is a hard requirement. For private repos, the risk is lower but not zero; anyone with repo access sees everything, and access can change over time.

What teams should think about before adopting

Before turning on session capture across a team, have an explicit conversation about these topics:

  1. Data classification. What data do your developers routinely interact with during coding sessions? If they are debugging production issues, customer data will appear in transcripts. If they are building new features, it probably will not.
  2. Retention policy. How long should session data persist? The checkpoint branch is a Git branch — it lives forever unless explicitly pruned. Decide whether you need session data from six months ago or whether it should be garbage-collected.
  3. Access control. Who should be able to read session transcripts? In most teams, this aligns with repo access. But some organizations may want finer-grained control — allowing code access but restricting session access.
  4. Compliance requirements. If you operate in a regulated industry (healthcare, finance, government), storing agent transcripts may create audit obligations you did not have before. Conversely, it may satisfy audit requirements that were previously unmet.
  5. Developer consent. Developers should understand that their prompts and conversations with agents will be stored and potentially reviewed. This is not surveillance — it is transparency — but the distinction matters, and people should opt in knowingly.
Trust is not a boolean. It is a spectrum, and the right position on that spectrum depends on who can see the data and what the consequences of exposure are. The Whiteboard Architect

What should NEVER be captured

Some data should never enter a session transcript under any circumstances, regardless of redaction capabilities:

  • Production database contents. If you are debugging a query, use synthetic data. Do not paste real customer records into an agent prompt.
  • Encryption keys and master secrets. These are not just "credentials" — they are the keys to the kingdom. If exposed, the blast radius is total.
  • Regulated data. HIPAA-protected health information, PCI cardholder data, GDPR personal data — these have legal requirements that casual Git storage cannot satisfy.
  • Access to production infrastructure. SSH keys, cloud console credentials, VPN configurations. These should never be in a developer's prompt in the first place.
In practice

The best defense against sensitive data in sessions is not redaction after the fact — it is developer discipline before the fact. Teams that adopt Entire should establish clear guidelines: never paste production credentials into agent prompts, use environment variables instead of inline secrets, and sanitize debug output before sharing it with an agent. Redaction is a safety net, not a strategy.

The trust equation

Adopting durable context requires trust at multiple levels: trust that the tooling will handle data responsibly, trust that teammates will not abuse access to session transcripts, and trust that the organization will not use session data for surveillance. This trust is earned, not assumed.

Start with the low-risk data. Capture prompts, tool calls, and reasoning. Leave aggressive capture for later, after the team has built comfort with the workflow and established norms around what belongs in a session and what does not. The goal is a culture where durable context is seen as a shared asset — a team resource that makes everyone's work better — not as a surveillance mechanism that records every keystroke.

Privacy and utility are not enemies. They are design constraints. And like all design constraints, they produce better outcomes when you take them seriously from the start.
