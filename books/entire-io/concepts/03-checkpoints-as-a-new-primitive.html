03 The unit of agent traceability

Checkpoints as a New Primitive

You already know three primitives for recording the state of a software project: the commit, the log entry, and the snapshot. Each one captures something real, and each one is missing something important. A checkpoint is a fourth primitive — one designed for a world where agents, not just humans, produce code. This chapter explains what makes it different, what it contains, and why it is the minimum viable unit of agent accountability.

A checkpoint is not a commit

A git commit records a file-system state: here is what every tracked file looked like at this moment, here is who made the change, here is a one-line summary. It is the foundational primitive of version control, and it is very good at what it does. But a commit is deliberately content-addressed — it cares about the bytes in the files, not about the process that put them there. Two completely different development processes that produce the same file tree will produce the same tree hash. The commit cannot tell them apart, and that is by design.

A checkpoint captures the process, not just the product. It records the conversation state at a specific moment — the prompts that were given, the reasoning the agent produced, the tool calls it made, and the code state at that point. Two different processes that produce the same code will produce two different checkpoints, because the checkpoints carry the reasoning that led to the code, and the reasoning was different.

This is the key distinction. A commit answers: "What does the code look like right now?" A checkpoint answers: "What does the code look like right now, and how did it get here?"

A checkpoint is not a log entry

Log entries are everywhere in software systems. Application logs, audit logs, event streams — all append-only records of things that happened. They share two properties that make them useful for debugging and compliance: they are ordered, and they are immutable. But they have a property that limits their value for understanding agent work: they are unlinked.

A log entry says: "At 14:23:07, the agent called the file-read tool on src/parser.rs." That is a fact, and it might be useful. But it does not tell you which commit that read contributed to, which checkpoint it belongs to, which session it was part of, or what the agent did with the information it read. To reconstruct the story, you have to manually correlate timestamps across multiple log streams and hope the clocks agree.

A checkpoint, by contrast, is linked by construction. It knows which session it belongs to. It knows which commits it produced. It contains the tool calls and the reasoning that connected them. You do not have to reconstruct the story; the story is the checkpoint.

A checkpoint is not a snapshot

Snapshots are familiar from filesystems, virtual machines, and databases. They capture the full state of a system at a point in time, and you can restore to that state later. In that sense, checkpoints share the "returnable state" property with snapshots. But a snapshot is context-free — it tells you what the state was, not why the state was that way.

A VM snapshot lets you roll back to "the machine as it was at 3pm on Tuesday." A checkpoint lets you roll back to "the session at the point where the agent had just finished the refactor and was about to start the migration, with the full conversation history intact so you (or a new agent) can continue from exactly that context." The difference is the difference between restoring bytes and restoring understanding.

The anatomy of a checkpoint

Draw a checkpoint as a box with four compartments. Each compartment holds a different kind of state, and all four together make the checkpoint a self-contained unit of agent accountability.

1. Conversation state. The full history of prompts and responses between the developer and the agent, from the beginning of the session up to this checkpoint. This includes the developer's instructions, the agent's reasoning, any clarifications or corrections, and the agent's internal chain of thought where available. This is the "why" — the reasoning record.

2. File state. A reference to the state of the working tree at the moment of the checkpoint. This is typically a commit hash, but it may also include uncommitted changes if the checkpoint is taken mid-work. This is the "what" — the code as it existed at this point.

3. Tool-call history. The ordered list of tool invocations the agent made: file reads, file writes, searches, test runs, type checks, and any other tool the agent called. Each entry includes the tool name, the input, and the output. This is the "how" — the investigative and constructive process.

4. Commit linkage. Explicit references to the git commits that were produced during or up to this checkpoint. These references are what let you navigate from the checkpoint to the diffs and vice versa. This is the "bridge" — the connection between the reasoning record and the code record.

Commit vs. checkpoint vs. log entry

The three primitives are not competing. They serve different purposes and operate at different levels of the stack. The following table makes the distinctions concrete.

Key idea

A commit is the minimum viable unit of code accountability: it tells you what changed and who changed it. A checkpoint is the minimum viable unit of agent accountability: it tells you what changed, who directed the change, what the agent was thinking, what it tried, and how it arrived at the result.

Three capabilities checkpoints enable

A checkpoint is not just a record. Because it captures both code state and conversation state, and because it is linked to the git history, it enables three capabilities that none of the other primitives can provide on their own.

Traceability

Traceability is the ability to trace any line of code back to the reasoning that wrote it. Start with git blame — it tells you which commit last touched a line. Follow the commit to its linked checkpoint. The checkpoint shows you the conversation: the prompt that initiated the change, the agent's reasoning about how to implement it, the tool calls it made to understand the existing code, and the constraints the developer set. You have gone from a line of code to a full account of why it exists.

This is the capability that matters most for debugging. When you find a bug in agent-generated code, traceability tells you whether the agent was given bad instructions, whether it misunderstood good instructions, whether it tried the right approach and hit a limitation, or whether it simply made an error. Each of those diagnoses leads to a different fix.

Review

Review is the ability to inspect the decision path, not just the result. When a pull request arrives with agent-generated code, a reviewer can look at the diffs and assess whether the code is correct, well-structured, and tested. But they cannot assess whether the approach is right without knowing what alternatives were considered and why they were rejected.

Checkpoints make this possible. A reviewer can open the session, read the conversation, see that the agent tried approach A and it failed for a specific reason, then tried approach B and it worked. The reviewer now knows that approach A was already explored, why it was abandoned, and why approach B was chosen. This is the kind of review that catches design mistakes, not just syntax errors.

Reviewing a diff without the reasoning is like reviewing a proof without the lemmas. You can check the conclusion, but you cannot assess the argument. The review gap

Recovery

Recovery is the ability to roll back to a known-good state when an agent goes sideways. This is not the same as git reset. Resetting to a previous commit gives you the old code, but it does not give you the old conversation context. If you want to continue from a known-good point in the session — "go back to where you were after the refactor but before you started the migration" — you need to restore both the code state and the conversation state. That is exactly what a checkpoint provides.

Recovery is particularly valuable in long sessions where the agent has built up significant context about the codebase. If the agent goes wrong at minute thirty of a forty-minute session, you do not want to start over from scratch and lose the thirty minutes of context-building that went well. You want to rewind to the last good checkpoint and continue from there, with all the accumulated understanding intact.

In practice

Think of recovery checkpoints the way a rock climber thinks about protection points. You place them at intervals, and when you fall, you fall to the last one — not to the ground. The cost of placing them is low. The cost of not having them, when you need them, is starting the whole pitch over.

How checkpoints fit into a session

Picture a timeline. The session starts on the left. As the agent works, checkpoints appear at intervals — after significant milestones, after commits, or when the developer explicitly saves one. Each checkpoint captures everything up to that point. The session ends on the right, and the final checkpoint captures the complete state.

Notice the dashed arc in the diagram. It shows that CP 2 is a rewind target — if the agent's work between CP 3 and CP 4 had gone wrong, you could rewind to CP 2 and try a different approach, with the full conversation context from that point intact. The checkpoints are not just records; they are decision points you can return to.

The minimum viable unit

Why call it a "primitive"? Because it is the smallest unit that is sufficient for agent accountability. A commit alone is not enough — it lacks reasoning. A log entry alone is not enough — it lacks linkage. A transcript alone is not enough — it lacks code state. A snapshot alone is not enough — it lacks context.

A checkpoint combines all four: reasoning (conversation state), code (file state), process (tool-call history), and linkage (commit references). Take away any one of those, and you lose a capability. Remove reasoning, and you cannot trace intent. Remove code state, and you cannot restore. Remove tool-call history, and you cannot understand the process. Remove linkage, and you cannot navigate between code and context.

The checkpoint is the minimum viable unit because it is the smallest thing that carries all four. Everything Entire does — traceability, review, recovery, multi-agent handoffs, search — is built on top of checkpoints. They are the atoms of the system.

Trap

Do not confuse "checkpoint" with "auto-save." An auto-save captures bytes at an interval. A checkpoint captures understanding at a meaningful moment. The difference is intent: checkpoints are placed where they matter, not where a timer fires. An auto-save every sixty seconds gives you sixty snapshots of files. A checkpoint after each milestone gives you four or five snapshots of decisions.

What to take away

  • A checkpoint is a new primitive, distinct from commits (which lack reasoning), log entries (which lack linkage), and snapshots (which lack context).
  • A checkpoint captures four things: conversation state (why), file state (what), tool-call history (how), and commit linkage (the bridge between code and context).
  • Checkpoints enable three capabilities: traceability (trace any line back to the reasoning that wrote it), review (inspect the decision path, not just the diff), and recovery (rewind to a known-good state with full context).
  • The checkpoint is the minimum viable unit of agent accountability. Remove any of its four components and you lose a capability.
  • Chapter 4 explores how session history and git history work together — two parallel records, connected by commit linkage, giving you the complete picture of what changed and why.
