04 Two histories, one repository

Sessions, Commits, and History

Every repository already has a history. You know it well: a chain of commits, each recording a diff, a message, a timestamp, and a parent pointer. That history tells you what changed. But if an AI agent produced those commits, there is a second history running in parallel — one that records how and why the changes were made. Entire gives you both, in the same repo, linked together so you can jump between them. This chapter is about understanding that dual-timeline architecture and why it matters more than you might expect.

The Two Histories

Think about what a git commit actually captures. It stores a tree of file contents, a diff from its parent, a one-line message someone typed (or an agent generated), and some metadata — author, date, hash. That is genuinely useful. But it is also genuinely incomplete.

When a human writes code, the reasoning lives in their head. You might recover fragments of it from PR descriptions, Slack threads, or design docs. When an AI agent writes code, the reasoning is explicit — it exists as a conversation transcript, a chain of tool calls, a sequence of prompts and responses. The problem is that this explicit reasoning is trapped in the agent session, and the session is ephemeral. Close the terminal, and it evaporates.

Entire introduces a second history — session history — that captures exactly what the commit log leaves out: the prompts you gave, the reasoning the agent followed, the approaches it tried and abandoned, the tool calls it made, and the decisions it reached. Session history and git history are complementary views of the same work.

What each history captures
Dimension Git history Session history
Files changed Full diff, line-by-line Referenced indirectly via commits
Commit message One line (sometimes a paragraph) Full conversation that led to the commit
Intent / motivation Rarely captured Recorded as the original prompt
Reasoning chain Not captured Full agent reasoning, step by step
Failed approaches Not captured (unless committed separately) Recorded as part of the conversation
Tool calls Not captured Every file read, search, edit, command
Temporal order Commit timestamps (sometimes rebased) Exact chronological sequence
Searchability git log --grep, git blame entire session list, checkpoint metadata

Neither history is sufficient on its own. Git history without session context is a series of diffs with no explanation. Session history without git linkage is a transcript with no anchor to the actual code. You need both, and you need them connected.

Key idea

Git history answers "what changed?" Session history answers "why did it change, what was tried, and what was the reasoning?" Entire links them so you can navigate freely between the two.

The Checkpoint Branch

Here is the design question: where do you store session metadata? You have a few options, and each has tradeoffs.

You could store it in a database — a SaaS backend, a local SQLite file, or some cloud service. That works, but now your context lives in a completely different system from your code. It does not travel with the repo when you clone, fork, or transfer ownership. It requires a separate backup strategy, a separate access control model, a separate search tool. It introduces a dependency on infrastructure that might not exist in six months.

You could store it alongside your code in the working branch — just drop JSON files into a .entire/ directory. That is simple, but it pollutes your working tree. Every git status shows metadata files. Every PR includes session artifacts alongside code changes. Your CI pipeline sees files it does not care about.

Entire takes a third path: the checkpoint branch. Session metadata is stored on a separate git branch — typically entire/checkpoints — that lives in the same repository but never merges into your working branches. It is there when you need it, invisible when you do not.

The checkpoint branch is metadata that travels with the code, without getting in the way of the code. The design principle behind Entire's storage model

This is a deliberate architectural choice, and it gives you several properties for free:

Distributed by default. When someone clones the repo, the checkpoint branch comes with it. When you push to a remote, the metadata goes too. No separate sync step, no separate credentials, no separate service to maintain.

Versioned. Git already knows how to version data. The checkpoint branch gets the same history, the same integrity guarantees, the same immutable content-addressed storage as your code.

Searchable with standard tools. You can git log entire/checkpoints to browse session metadata. You can grep it. You can diff it. You can use any git-aware tool you already know.

Access-controlled by the repo. Whoever has access to the repo has access to the context. No separate permission model to maintain.

Clean separation. Your feature branches, your main branch, your CI — none of them see the checkpoint data unless they explicitly look at the checkpoint branch. No noise in your working tree.

In practice

The checkpoint branch is an orphan branch — it has no common ancestor with your main branch. This is the same technique GitHub Pages uses with gh-pages branches. It shares the repository but has a completely independent history.

The Dual Timeline

Picture your repository as having two parallel timelines. On top, the familiar git commit chain: each node is a commit, connected to its parent, recording file changes. Below, the session timeline: each node is a checkpoint, recording the state of the conversation and reasoning at that moment. Between them, links connect checkpoints to the commits they produced.

The dashed lines in the diagram are the key. They represent the commit linkage — the connection between a checkpoint and the git commits it produced. A single checkpoint might generate one commit or several. And from the other direction, every commit that was made during a tracked session can be traced back to the checkpoint that produced it.

Navigating Between the Two

The real power of dual history is not just having both records — it is being able to move between them. Entire supports two directions of navigation:

From a commit, find the session

You are reading git log and you see a commit that puzzles you. The diff is clear enough — a function was refactored, a dependency was swapped out — but the commit message just says "refactor: update handler logic." Why was this change made? What prompted it? Was there a reason the agent chose this approach over another?

With Entire, you can trace from that commit back to the checkpoint that produced it. The checkpoint gives you the full conversation: the prompt that kicked it off, the agent's reasoning about the problem, the alternatives it considered, the tool calls it made to explore the codebase, and the chain of decisions that led to the final diff. The commit is the what. The checkpoint is the why.

From a checkpoint, find the commits

You are reviewing a session and you want to see exactly what code changes resulted from a particular piece of work. The checkpoint records which commits it produced, so you can jump directly to the diffs. This is especially useful when a session spans multiple checkpoints — you can see which checkpoint produced which commits, giving you a fine-grained map of intent to outcome.

Trap

Do not confuse the checkpoint branch with a feature branch. The checkpoint branch is metadata storage, not a code branch. You never merge it, never rebase it, never check it out to write code. It is infrastructure, like .git/ itself, but visible and searchable.

Why Git, Not a Database?

A reasonable question: why store session metadata in git at all? Why not a purpose-built database, a JSON API, a file on S3?

The answer comes down to where code already lives. Git is the system of record for source code. Every developer has it installed. Every team has a workflow built around it. Every CI/CD pipeline starts with a git clone. By storing context in git, Entire avoids introducing a new dependency, a new point of failure, a new thing to back up and secure.

But there is a deeper reason. Git is content-addressed. Every object — every blob, tree, commit — is identified by the SHA hash of its content. This means that the link between a checkpoint and a commit is not a fragile foreign key in a database. It is a cryptographic reference to an immutable object. The link cannot become stale, cannot point to something that has been modified, cannot be silently corrupted by a database migration.

And git is distributed. When you push your repo to a remote, the checkpoint branch goes with it. When a teammate clones, they get the full context. When you fork, the history follows. There is no "sync step" where metadata might be lost or out of date.

The Separation Principle

There is one more design decision worth drawing on the whiteboard: why keep the two histories separate at all? Why not embed session metadata directly into commit messages, or attach it as git notes?

The answer is about granularity and lifecycle. A checkpoint and a commit do not have a one-to-one relationship. One checkpoint might produce three commits. A session might span ten checkpoints across two hours of work. The checkpoint captures the unit of intent — "add authentication to this API" — while the commits capture the units of code change that fulfilled that intent.

Jamming session data into commit messages would bloat the git log. Using git notes would create a fragile coupling that breaks on rebase. The checkpoint branch keeps them separate but linked: parallel timelines in the same repository, connected by commit references that survive rebases, cherry-picks, and merges.

Separate but linked. Two timelines that tell one story. The architecture of dual history

What This Changes

Once you have both histories, several things that were previously difficult become straightforward:

Code review gets context. Instead of reviewing a PR as a set of file diffs, you can see the conversation that produced those diffs. You can understand not just what the agent did, but what it was asked to do and why it made specific choices.

Debugging gets archaeology. When you find a bug in a line of code, git blame tells you which commit introduced it. From the commit, Entire tells you which session produced it, what the prompt was, and what constraints the agent was working under. That context often tells you whether the bug is a misunderstanding of requirements or a genuine implementation error.

Onboarding gets depth. A new team member looking at unfamiliar code can trace from any commit to the reasoning behind it. Instead of asking "why is this done this way?" in Slack and hoping someone remembers, they can read the original session and understand the decision in its original context.

Knowledge survives. When the person who wrote the code leaves the team — or when the agent session that produced it closes — the reasoning does not vanish. It is in the repo, versioned and searchable, for as long as the repo exists.

Key idea

The checkpoint branch is the connective tissue between intent and outcome. It gives you a way to answer "why was this code written this way?" months or years after the fact, without relying on anyone's memory.

The Mental Model, Completed

If you have been following the progression of this book, you now have the full picture. Chapter 2 introduced the mental model: sessions, checkpoints, commit linkage. Chapter 3 explored checkpoints as a primitive. This chapter connected the two histories and showed where the metadata actually lives.

The architecture is deliberately minimal: two branches in one repo, linked by commit hashes. No external services, no proprietary storage, no new tools to learn beyond the Entire CLI itself. Everything is built on top of git because git is already the universal substrate of software development.

In the next chapter, we will put this architecture to work. When an agent goes sideways — and they do — you need to rewind to a known-good state and try again. That operation only makes sense if you can restore both the code and the context. Which is exactly what the dual-timeline architecture gives you.
