06 Context that transfers

Multi-Agent and Handoff Workflows

So far, we have talked about a single agent working inside a single session. That is the simplest case, and it is where most developers start. But the direction of the industry is clear: teams are beginning to use multiple agents, each with a different specialty, working on different aspects of the same codebase. One agent researches and prototypes. Another implements. A third writes tests. A fourth handles deployment configuration. The question is not whether multi-agent workflows will become normal — it is how you keep those agents from duplicating each other's work, contradicting each other's decisions, and operating in the dark about what has already been tried.

The Handoff Problem

Let me draw the problem on the whiteboard. You have Agent A — a research agent. You ask it to explore different authentication strategies for your API. It reads your codebase, investigates three libraries, benchmarks two of them, identifies edge cases around token expiry, and recommends a specific approach. It writes a summary in a markdown file and produces a proof-of-concept in a branch. Good work. Session ends.

Now you bring in Agent B — an implementation agent. You want it to take the research and build the production auth system. But Agent B knows nothing about what Agent A did. It can see the proof-of-concept code, sure — that is in the branch. It can read the markdown summary. But it does not know:

— Why Agent A rejected the other two libraries (was it performance? API design? licensing?). — What edge cases Agent A discovered during exploration. — What constraints Agent A identified in the existing codebase. — What approaches were tried and abandoned, and why.

Without that context, Agent B is operating with partial information. It might re-investigate the same libraries. It might choose an approach that Agent A already proved does not work. It might violate a constraint that Agent A discovered but did not document in the summary. The handoff is lossy.

A handoff without context is not a handoff. It is a cold start wearing a handoff's clothes. The multi-agent context problem

The Checkpoint as Handoff Document

This is where Entire changes the equation. When Agent A checkpoints its work, it captures not just the code state but the full reasoning trail: every prompt, every tool call, every file it read, every decision it made, every approach it tried and abandoned. The checkpoint is not a summary written after the fact — it is the actual record of the work, complete and unedited.

When Agent B starts, it can load Agent A's checkpoint as its starting context. Now it knows everything Agent A knew. It knows why library X was rejected (performance under concurrent connections was 3x worse). It knows about the edge case with token refresh during WebSocket upgrades. It knows that the existing user model has a quirk in how it handles nullable email fields. Agent B picks up where Agent A left off, with full context, not from zero.

Key idea

A checkpoint carries not just code state but the reasoning, constraints, and decisions that led to it. This makes it a complete handoff document — one that an agent can consume directly, not just a human-readable summary.

The difference is significant. A human-written handoff document is a lossy compression of the original work. The author decides what to include and what to omit, and they inevitably leave out details that turn out to matter later. A checkpoint is lossless. It contains the full transcript, the full tool-call history, the full reasoning chain. The receiving agent can search it, reference it, and build on it.

Handoff Patterns

Not every multi-agent workflow looks the same. Let me walk through the patterns that emerge in practice, because each has different characteristics and different requirements for context transfer.

Sequential handoff

The simplest pattern: Agent A finishes its work, checkpoints, and Agent B picks up from that checkpoint. This is the pipeline model — research flows into implementation, implementation flows into testing, testing flows into review. Each agent inherits the full context of the previous stage.

Sequential handoffs work well when the work has natural phases and each phase requires a different kind of expertise. A research agent might be configured with broad web search and documentation access. An implementation agent might have deeper access to the codebase and build tools. A testing agent might have access to CI pipelines and test runners. Each agent is optimized for its phase, and the checkpoint ensures continuity between phases.

Parallel agents, shared context

A more complex pattern: multiple agents work on different features or components simultaneously. Agent A handles the backend auth module. Agent B handles the frontend login flow. Agent C handles the database migrations. They are working in parallel, but their work will eventually need to fit together.

Checkpoints help here because each agent can review the others' checkpointed sessions to understand decisions that affect their own work. When Agent B needs to know how the auth tokens are structured, it can look at Agent A's checkpoint rather than reading half-finished code and guessing. When Agent C needs to know what fields the frontend expects, it can look at Agent B's checkpoint for the data contract.

Specialist agents

Some workflows use specialist agents for cross-cutting concerns. A security agent reviews code for vulnerabilities. A performance agent profiles and optimizes. A documentation agent generates API docs. These specialists do not build features — they analyze and improve what other agents built.

For specialist agents, the checkpoint is an intake document. The security agent loads the implementation agent's checkpoint and understands not just the code but the constraints the implementation agent was working under. "We chose this library because it handles PKCE natively" is context that changes how a security review should proceed.

What Transfers in a Handoff

A checkpoint-based handoff transfers more than you might expect. Let me enumerate what the receiving agent gets access to, because this is where the value becomes concrete.

The code state. Obviously — the exact file tree at the moment of the checkpoint. This is the same as what a git branch would give you.

The original prompt. What the previous agent was asked to do. This is the intent — the "why" behind the code. The receiving agent can read this and understand the goal without anyone having to re-explain it.

The reasoning chain. How the previous agent arrived at its decisions. Which files did it read? What patterns did it identify? What constraints did it discover? This is the knowledge that is hardest to transfer in human teams — the "I tried X and it did not work because of Y" insights that usually live only in someone's head.

The tool-call history. Every file the previous agent read, every search it ran, every command it executed. This tells the receiving agent not just what the previous agent decided but how it investigated the problem. If Agent A searched for "authentication" and found a legacy auth module that everyone forgot about, Agent B knows that module exists.

The negative results. What was tried and abandoned. This is arguably the most valuable part of the handoff. If Agent A spent twenty minutes exploring a library and determined it was unsuitable, that information saves Agent B twenty minutes of repeating the same exploration. Negative results are almost never documented in traditional development. With checkpoints, they are captured automatically.

Trap

Do not assume the receiving agent will read the entire checkpoint transcript end-to-end. Checkpoints can be large. Effective handoffs work best when checkpoints are taken at meaningful boundaries with clear intent, so the receiving agent can orient quickly.

Agents as Team Members

Here is the bigger picture. Think about how a well-run human team works. When an engineer finishes a piece of work and hands it off to another, they do not just push code and walk away. They write a PR description. They leave comments in the code. They have a brief conversation explaining the tricky parts. They update the relevant design doc. They transfer context.

Good engineers leave documentation behind. They write code that is readable. They leave breadcrumbs for the next person. The reason this matters is that software development is fundamentally collaborative and sequential — someone else will always work on your code after you, whether that is a teammate, a future you, or an agent.

Now apply this to agents. An agent that checkpoints its work is an agent that leaves documentation behind. Not documentation it was explicitly asked to write, but documentation that is a natural byproduct of the checkpoint process. The conversation is the documentation. The tool-call history is the audit trail. The reasoning is the design rationale.

This reframes the multi-agent problem. It is not about building elaborate agent-to-agent communication protocols. It is about making each agent a good team member who leaves their work in a state that the next person (or agent) can pick up without a cold start.

The Coordination Question

A natural concern with multi-agent workflows is coordination. If Agent A and Agent B are both modifying the same codebase, how do you prevent conflicts? How do you ensure consistency?

Entire does not try to solve this at the orchestration level. It is not a task scheduler or a workflow engine. What it provides is the substrate for coordination: shared, searchable context that every agent can access. The actual coordination — deciding which agent works on what, in what order, with what constraints — is up to you and your workflow tooling.

But the substrate matters more than you might think. Most coordination failures are not scheduling failures — they are information failures. Agent B did not know about Agent A's constraint. Agent C did not know that Agent A had already tried and rejected an approach. The checkpoint branch makes that information available. Whether agents read it proactively or are directed to it by a human, the information is there.

In practice

Start with sequential handoffs. They are the simplest to reason about and the easiest to debug when something goes wrong. Move to parallel patterns only when you have confidence in your checkpoint discipline and your agents are working on genuinely independent components.

Context Windows and Handoff Boundaries

There is a practical constraint that makes multi-agent handoffs not just a nice-to-have but sometimes a necessity: the context window. Every language model has a finite context window — a limit on how much text it can process at once. Long sessions can approach or exceed that limit, causing the agent to lose track of earlier parts of the conversation.

Checkpoints provide a natural solution. Instead of one agent working in a single marathon session that pushes the context window to its limit, you can break the work into phases, checkpoint between them, and have a fresh agent pick up each phase with a clean context window loaded with the relevant checkpoint data. The checkpoint acts as a compressed, structured summary of the previous work — smaller than the raw transcript but carrying the essential state.

This is one of those cases where a constraint (finite context windows) and a feature (multi-agent handoffs) reinforce each other. The same mechanism that enables handoffs also solves the context-window problem. You are not choosing between a long session and a multi-agent workflow — you are choosing between a long session that degrades in quality as it goes, and a series of focused sessions connected by high-quality checkpoints.

Looking Ahead

Multi-agent workflows are where Entire's architecture pays its biggest dividends. A single agent working alone benefits from checkpoints for recovery and traceability. But multiple agents working together benefit from checkpoints as a communication channel — a structured, searchable, complete record of work that transfers context without loss.

The vision is not that every developer will orchestrate a fleet of agents. It is that the infrastructure for context transfer will be in place when the workflows evolve. Whether you are using one agent or ten, checkpointing your sessions means the work is durable, traceable, and transferable. The context survives the session, the agent, and the workflow.

In the next chapter, we will look at how this captured context changes one of the most important activities in software development: code review. When you can review not just the diff but the reasoning that produced it, review becomes a fundamentally different — and more effective — activity.

Key idea

Multi-agent handoffs are context transfers. Checkpoints make those transfers lossless. The result is agents that build on each other's work instead of repeating it, and a development process where knowledge accumulates instead of evaporating.
