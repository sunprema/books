07 The decision path, not just the result

Reviews with Intent, Not Just Diffs

A pull request lands in your inbox. Forty-seven files changed. The diff is clean: consistent naming, solid test coverage, no obvious bugs. You approve it. Three weeks later, a production incident traces back to an assumption buried in that PR — an assumption the diff never surfaced because the diff only shows what, never why.

This is the shape of a problem that has plagued code review for decades, and agent-generated code makes it dramatically worse. When a human writes code, the reviewer can at least infer intent from commit messages, PR descriptions, and the shared context of working on the same team. When an AI agent writes code, even that thin layer of implicit context disappears. The code appears fully formed, with no visible trail of reasoning.

The answer without the question

Imagine a math exam where you can only see the final answers, not the working. A student writes "42." Is that correct? You cannot tell without knowing the question. Was the question "What is 6 times 7?" or "What is the airspeed velocity of an unladen swallow?" The answer looks the same either way.

Reviewing agent-generated code without context is exactly this. You see the output — a refactored module, a new API endpoint, a migration script — but you do not see:

  • The prompt that initiated the work
  • The constraints the developer specified (or forgot to specify)
  • The alternatives the agent considered and rejected
  • The tool calls the agent made to understand the codebase
  • The assumptions the agent operated under
  • The failure modes it encountered and worked around

Without this, a reviewer is pattern-matching on syntax and structure. They can catch style issues, obvious logic errors, and missing edge cases — but they cannot catch misaligned intent. And misaligned intent is where the most dangerous bugs live.

When Entire checkpoints a session, it captures all four layers. The checkpoint includes the transcript — the full conversation between developer and agent — which contains the prompt (Layer 4), any constraints the developer specified (Layer 3), the agent's reasoning and tool calls (Layer 2), and links to the commits that form the diff (Layer 1).

Traditional review vs. context-aware review

Here is what changes when reviewers have access to session context:

Review dimension Traditional (diff only) Context-aware (with Entire)
Understanding intent Inferred from PR description and commit messages Read the original prompt and conversation
Evaluating trade-offs Guess why one approach was chosen over another See which alternatives the agent explored and why they were rejected
Checking assumptions Hope the code speaks for itself Inspect what the agent read and what it assumed about the codebase
Validating scope Compare diff against PR description Compare diff against original prompt constraints
Spotting hallucination Requires deep domain knowledge Cross-reference tool calls with actual file contents
Review speed Proportional to diff size Proportional to intent complexity, often faster for large diffs
Confidence in approval Medium — pattern-matching on output High — validated against full decision chain
Key idea

Context-aware review does not replace reading the diff. It supplements it. You still look at the code, but now you can verify that the code matches the intent — and that the intent matches the actual need.

The intent gap in agent-generated code

Agent-generated code has a unique problem: it can be locally correct but globally wrong. An agent given the prompt "add caching to the user lookup" will produce code that caches user lookups. The code will be clean. The tests will pass. But maybe the real problem was that the database query was missing an index, and caching was a workaround for a deeper issue. Or maybe the caching invalidation strategy conflicts with an eventual-consistency model used elsewhere in the system.

A reviewer who sees only the diff sees caching code. It looks fine. A reviewer who sees the session transcript sees:

  1. The developer prompted "user lookup is slow, add caching"
  2. The agent read the query and noted the missing index but was not asked to fix it
  3. The agent chose an LRU cache with a 5-minute TTL
  4. The agent did not check whether other services write to the users table

Now the reviewer has something to work with. They can say: "Why not add the index instead? And if caching, have you checked the write path?" The review becomes a conversation about architecture, not just syntax.

What tool calls reveal

One of the most underappreciated aspects of session transcripts is the tool call trace. When an agent works on a codebase, it reads files, searches for patterns, runs tests. The sequence of tool calls tells you what the agent actually looked at — and, critically, what it did not.

Trap

An agent that never reads the test file before writing new tests is likely generating tests from its training data, not from the actual codebase conventions. The tool call trace makes this visible. Without it, the tests might look plausible but follow completely wrong patterns.

Consider a typical agent session. The tool calls might look like: 

1. Read src/models/user.ts
2. Search for "UserService" across codebase
3. Read src/services/user-service.ts
4. Read src/services/cache-service.ts
5. Run existing tests
6. Write src/services/user-service.ts (modified)
7. Write src/services/__tests__/user-service.test.ts
8. Run tests (pass)

This is a reasonable sequence. But compare it to one where the agent skips step 4 — never reading the existing cache service — and invents its own caching mechanism. Or one where it skips step 5, writing tests without running the existing suite first. The tool call trace makes these gaps legible to the reviewer.

Reviewing constraints, not just code

When a developer instructs an agent, they often specify constraints: "do not modify the public API," "keep backward compatibility," "use the existing error handling pattern." These constraints shape every line of the generated code, but they are invisible in the diff.

With checkpointed context, a reviewer can verify that constraints were actually followed. More importantly, they can spot when constraints were missing — when the developer forgot to specify something critical, and the agent filled the gap with its own assumptions.

In practice

Teams that review session transcripts often develop a habit of scanning the opening prompt first. If the prompt is vague — "fix the auth bug" — they know to scrutinize the code more carefully. If the prompt is specific — "the JWT refresh token endpoint returns 401 when the access token is expired but the refresh token is valid; fix the token validation order in middleware/auth.ts without changing the response format" — they can focus their review on whether that specific problem was solved correctly.

The review as a feedback loop

There is a second-order benefit here that is easy to miss. When developers know their prompts and session transcripts will be reviewed alongside their code, the quality of their prompts improves. They start specifying constraints more carefully. They start thinking about what a reviewer will need to see. The review process creates a feedback loop that improves the input, not just the output.

This is the same dynamic that made pull requests transformative in the first place. Before pull requests, developers committed directly to trunk. The social pressure of review — knowing someone would read your code — improved code quality even before the review happened. The same thing happens with session transcripts. Knowing someone will read your prompt makes you write better prompts.

The review is not just a gate. It is a mirror. It reflects the quality of the question, not just the answer. The Whiteboard Architect

Catching bugs that look correct in isolation

The hardest bugs to catch in review are the ones where every line of code is correct in isolation but the composition is wrong. A function that returns the right type. A conditional that checks the right field. An API call with the right parameters. Each piece is fine. But the overall flow has a subtle ordering issue, or a race condition, or an assumption about state that does not hold.

These are precisely the bugs that intent-based review catches. When you can see the agent's reasoning — "I am assuming this function is called only after authentication middleware runs" — you can verify that assumption against reality. When you can see the prompt — "handle the case where the user is not logged in" — you can check whether that case is actually covered, not just whether the code compiles.

Intent transforms review from "does this code look right?" to "does this code do what we actually need?" Those are fundamentally different questions, and only the second one prevents production incidents.

Building a context-aware review practice

You do not need to read every line of every transcript. That defeats the purpose. A practical approach:

  1. Start with the prompt. Read what the developer asked for. This sets your expectations for what the diff should contain.
  2. Skim the tool calls. Check that the agent read the right files and ran the right tests. Look for gaps.
  3. Read the diff with intent in mind. Now you know what the code is trying to do. Does it do that? Does it do only that?
  4. Check for constraint violations. If the developer specified constraints, verify they were respected.
  5. Flag missing constraints. If the prompt was too vague, comment on the prompt quality, not just the code.

This is not slower than traditional review. For large, agent-generated PRs, it is often faster — because the transcript gives you a map of the territory before you start reading the code.

Key idea

Reviewing with intent is not about adding more work. It is about shifting the work from "figure out what this code is doing" to "verify this code does what it should." The first is detective work. The second is validation. Validation is faster and more reliable.

From gatekeeping to collaboration

The traditional code review has an adversarial undercurrent: the reviewer is looking for things wrong with the code. Context-aware review shifts this toward collaboration. The reviewer is no longer just a gatekeeper — they are a co-pilot, helping ensure that the developer's intent was faithfully translated into code by the agent.

This matters especially in teams where agent usage is growing. As more code is agent-generated, the reviewer's role evolves from "check the code" to "check the intent-to-code pipeline." That evolution requires visibility into the pipeline itself — and that is exactly what checkpointed sessions provide.

The diff shows you the destination. The session shows you the journey. Good review requires both.
