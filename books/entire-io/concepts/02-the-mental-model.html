02 Sessions, checkpoints, and the checkpoint branch

The Mental Model

Entire has four concepts. Not five, not "it depends" — four. Learn them as a stack, each one building on the one below it, and you will have the complete mental model for everything the tool does. Draw four boxes on the whiteboard. Label them session, checkpoint, commit linkage, and checkpoint branch. This chapter fills in each box.

Sessions: the unit of agent work

A session is a recorded unit of work between a developer and an AI coding agent. It starts when the agent begins working on a task and ends when the task is finished, abandoned, or paused. During that window, the session captures the full conversation: every prompt the developer sent, every response the agent produced, every tool call it made, every file it read or wrote, every error it encountered, and every decision it explained.

Think of a session the way you think of a feature branch. A feature branch scopes a set of file changes to a single piece of work. A session scopes a set of decisions and reasoning to a single piece of work. The feature branch tells you what changed. The session tells you how and why it changed. They are two views of the same work, recorded in two different structures, both living in git.

A session is not a transcript in the sense of a raw log file. It is structured data: each exchange between developer and agent is a distinct record with a timestamp, a role (human or agent), and typed content (text, tool call, tool result, file edit). This structure is what makes sessions searchable and navigable rather than just readable.

Key idea

A session is not a log. It is a structured, time-ordered record of collaboration between a human and an agent, captured with enough fidelity that you can reconstruct not just what happened, but why each decision was made.

Checkpoints: save points within a session

A checkpoint is a save point within a session. If a session is the full recording of a piece of work, a checkpoint is a bookmark — a specific moment you can name, return to, and use as a reference point.

What does a checkpoint capture? Two things, simultaneously. First, the conversation state: the full history of prompts, responses, tool calls, and reasoning up to that point. Second, the code state: a snapshot of the working tree and the git commits that have been made. A checkpoint is a point in time where you know both what the code looks like and what the agent was thinking when it got there.

You can create checkpoints manually — "save this state, I want to be able to come back here" — or Entire can create them automatically at significant moments: after a commit, after a test run passes, or at regular intervals. The key property is that a checkpoint is a returnable state. It is not just a record of the past; it is a point you can rewind to if the agent goes sideways later in the session.

Picture a long session where the agent makes good progress for twenty minutes, then takes a wrong turn and spends fifteen minutes making things worse. Without checkpoints, you are stuck with the final state: you can undo the commits, but you cannot recover the agent's context from the point before it went wrong. With checkpoints, you can rewind to the last good state — both the code and the conversation — and continue from there.

A checkpoint is the moment where you know both what the code looks like and what the agent was thinking. You can go back to either one. The dual-state property

Commit linkage: connecting code to intent

The third concept is commit linkage, and it is the one that makes the whole system useful rather than merely interesting. Each checkpoint is linked to the git commits it produced. Not "associated with" in some loose metadata sense — linked, with explicit references that you can follow in either direction.

Start from a commit. The commit's metadata includes a reference to the checkpoint that created it. Follow that reference, and you arrive at the checkpoint: the conversation state at the moment of the commit, the tool calls that led to it, the reasoning the agent gave for the change. You have gone from "what changed" to "why it changed" in one hop.

Now go the other direction. Start from a session. Look at its checkpoints. Each checkpoint lists the commits it produced. You can see the code diffs alongside the conversation that generated them. This is the view a reviewer wants: not just the diff, but the diff with the reasoning attached.

Commit linkage is what distinguishes Entire from a session recorder. A session recorder gives you a transcript. Entire gives you a transcript that is wired into your git history, so you can navigate between code and intent without switching tools.

The checkpoint branch: metadata that stays out of your way

The fourth concept answers a practical question: where does all this metadata actually live? If sessions and checkpoints are stored in the repository, do they clutter the working branch? Do they show up in git status? Do they conflict with merges?

The answer is the checkpoint branch. Entire stores all session metadata on a separate git branch — specifically, entire/checkpoints/v1. This branch is part of the same repository, pushed and pulled with the same remotes, searchable with standard git tools. But it never intersects with your working branches. It is a parallel track of metadata that lives alongside your code history without touching it. The link from commits back to checkpoints is a git trailer — Entire-Checkpoint: <id> — added automatically via a PrepareCommitMsg hook.

This design choice matters for three reasons.

First, cleanliness. Your working branch — main, feature/auth, whatever you are on — contains only source code and the files your project actually needs. No .entire/ directory, no metadata files, no JSON blobs mixed in with your src/ folder. When you run git log on your working branch, you see code commits. The session metadata is elsewhere.

Second, compatibility. Because the metadata is on a separate branch, it does not participate in merges, rebases, or cherry-picks on your working branches. You will never have a merge conflict in a session file. CI pipelines that check out your working branch do not see the metadata. Tools that scan your repository do not trip over unfamiliar files. Entire adds metadata to your repo without changing the experience of working in it.

Third, searchability. Because the metadata is in git, you can search it with git. You can git log entire/checkpoints to see the history of session recordings. You can grep through checkpoint data. You can use any tool that reads git to read session metadata. There is no separate database, no proprietary format, no API to query. It is files in a branch.

In practice

The checkpoint branch is pushed to your remote like any other branch. When a teammate clones the repo, they get the session history along with the code history. When they fetch, they get new sessions. The metadata travels with the code because it is part of the repository — just on a different branch.

The four concepts together

Now step back and look at all four boxes on the whiteboard. A session records a unit of agent work. Within the session, checkpoints mark save points that capture both code state and conversation state. Commit linkage connects each checkpoint to the git commits it produced, so you can navigate from code to intent and back. And the checkpoint branch stores all of this metadata in the same repository, on a separate branch that stays out of your way.

Notice what this gives you. From any commit on your working branch, you can follow the linkage to the checkpoint that created it, and from there to the full session. From any session on the checkpoint branch, you can follow the linkage to the commits it produced. The two branches — working and checkpoint — are separate in structure but connected in meaning. They are two views of the same work.

This is not just logging

It is tempting to look at this and think: "So it is a structured log." It is not, and the distinction matters. A log is append-only, unlinked, and passive. You write to it and maybe read from it later. Entire's model is different in three ways.

First, it is linked. Every checkpoint has explicit references to the commits it produced. Every commit can be traced back to its checkpoint. This is not "grep through a log file and hope you find the right entry." It is a navigable graph with typed edges.

Second, it is structured. Sessions and checkpoints are not free-text dumps. They have schema: a session has an ID, a start time, an end time, a list of checkpoints. A checkpoint has a conversation state, a list of linked commits, a snapshot reference. You can query this data, filter it, and build tools on top of it.

Third, it is git-native. The metadata lives in git, not in a database, not in a cloud service, not in a local cache that gets wiped. It is versioned, distributed, and durable in exactly the same way your code is. When you push, the metadata pushes. When a teammate pulls, they get the metadata. When you back up the repo, you back up the sessions.

Trap

Do not confuse the checkpoint branch with an orphan branch used for documentation or GitHub Pages. Those are unrelated histories that happen to share a remote. The checkpoint branch is a parallel metadata track whose content is meaningfully linked to commits on the working branches. It is not documentation about your code; it is the reasoning record of your code.

An analogy: the lab notebook

If you have worked in a research lab, you know the lab notebook. The published paper shows the final result: the method, the data, the conclusion. The lab notebook shows everything else: the hypotheses that did not pan out, the calibration that took three tries, the note that says "talked to Dr. Kim, she suggested trying lower temperature." The paper is the commit. The lab notebook is the session.

In science, lab notebooks are not optional. They are required for reproducibility, intellectual property, and regulatory compliance. No one argues that publishing papers is enough. The reasoning record is separately maintained because it serves different purposes than the result record.

Software engineering is arriving at the same realization, driven by the same forces. When an agent writes code, the "result" (the diff) is insufficient for understanding, review, and accountability. You need the "notebook" (the session) too. Entire is the tool that maintains it.

The published paper is the commit. The lab notebook is the session. Science does not treat them as interchangeable, and neither should engineering. The lab notebook analogy

What to take away

  • Four concepts, stacked: sessions record the full unit of agent work. Checkpoints are save points within a session that capture both code and conversation state. Commit linkage connects each checkpoint to the git commits it produced. The checkpoint branch stores all metadata on a separate branch in the same repository.
  • Sessions are structured data, not raw logs. Each exchange has a timestamp, a role, and typed content.
  • Commit linkage is bidirectional: from a commit you can reach the session, and from a session you can reach the commits.
  • The checkpoint branch keeps metadata out of the working branch: no clutter, no merge conflicts, no impact on CI. But it is still in git, so it is searchable, versioned, and distributed.
  • This is not logging. It is a linked, structured, git-native reasoning record.
  • Chapter 3 goes deeper into checkpoints — what makes them different from commits, log entries, or snapshots, and why they are the core primitive of agent traceability.
