06 From paper to production

Building and Using OAuth Systems

Everything so far has been about how OAuth behaves. This chapter is about what you type, in what order, and what you will be staring at when it does not work. The build order matters more than the theory, because almost every OAuth outage I have watched came from a step someone skipped rather than a concept someone misunderstood.

Building a client, in order

Do these in sequence. The order is not aesthetic — each step produces the input the next one needs, and the steps people reorder are exactly the ones that produce the errors nobody can diagnose later.

  1. Fetch the metadata document before writing any code. When you meet an unfamiliar provider, /.well-known/openid-configuration or the RFC 8414 document at /.well-known/oauth-authorization-server returns the live endpoint URLs and the advertised capabilities. These are two distinct endpoints and may return different documents on the same host. Whichever you use, the issuer in the response must be identical to the issuer identifier you derived the URL from; if it is not, discard the document.
  2. Register, and record three strings exactly. The client_id, the client secret if you are a confidential client, and the redirect URI — character for character. RFC 9700 requires authorization servers to compare redirect URIs by exact string matching, with a narrow carve-out for loopback URIs whose port varies at runtime. A trailing slash is a different URI.
  3. Generate the verifier and challenge. A code_verifier is 43 to 128 characters from the unreserved set, and RFC 7636 asks for a minimum of 256 bits of entropy — base64url-encoding 32 random octets gives you a compliant 43-character string. Then code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier))). Hash the ASCII bytes of the verifier string, not the random octets you generated it from.
  4. Generate a one-time state bound to the user-agent session. RFC 9700 asks for one-time-use CSRF tokens securely bound to the user agent. A random value that is reusable, or that lives in a global map with no session binding, protects nothing.
  5. Build the authorization URL. Parameters go in the query component in application/x-www-form-urlencoded form: response_type=code, client_id, redirect_uri, scope, state, code_challenge, code_challenge_method=S256.
  6. Write the redirect handler so it validates before it touches the code. Compare state against the value bound to this session and burn it. Where the server offers RFC 9207's iss parameter, form-urldecode it and compare it by simple string comparison to the issuer you sent the request to, rejecting on mismatch. Only then read code.
  7. POST to the token endpoint over TLS. RFC 6749 requires TLS on both the authorization and token endpoints. Send grant_type=authorization_code, code, client_id, code_verifier, and the same redirect_uri you used in the authorization request — it is repeated here for verification, not decoration.
  8. Store what came back according to client type. A confidential web application keeps credentials and tokens on the server, where the resource owner cannot reach them. A browser application should not hold them in JavaScript at all; the Backend-For-Frontend pattern routes resource requests through a backend so tokens never enter the page.
  9. Attach the token as a header. Authorization: Bearer …, never a query parameter — RFC 9700 states clients MUST NOT pass access tokens in a URI query parameter, because they leak into logs, history and Referer.
  10. Handle 401 by refreshing once, then re-authorizing. One refresh attempt, and if that fails, start a fresh authorization request. A retry loop against a dead grant just generates noise in someone's audit log.
  11. Persist the rotated refresh token on every refresh. Public clients' refresh tokens must be sender-constrained or rotated, so assume the response carries a new one and that the old one is dead the moment you receive it.

Three of those get skipped, reliably. Step one: people copy endpoint URLs out of a blog post and never discover that the provider moved them or that the tenant they were pointed at has a different issuer. Step six: the redirect handler reads code first and validates state in a branch that a refactor eventually deletes. Step eleven: the client writes the new access token and quietly drops the rotated refresh token, which works perfectly until the access token expires and the client presents a credential the server has already retired. That last one is the classic "it broke overnight and nothing changed" ticket.

Key idea

Validation happens before use. state and iss are checked before the authorization code is read; aud and the signature are checked before a token's claims are trusted. Any code path that reverses that order is the bug.

Discovery — the first thing to run against an unfamiliar provider

curl -s https://accounts.example.com/.well-known/openid-configuration \
  | jq '{issuer, authorization_endpoint, token_endpoint, userinfo_endpoint, jwks_uri}'

Deriving the S256 challenge from the shell

code_verifier=$(openssl rand -base64 96 | tr -d '\n=+/' | cut -c1-64)
code_challenge=$(printf '%s' "$code_verifier" \
  | openssl dgst -binary -sha256 \
  | openssl base64 | tr '+/' '-_' | tr -d '=')

What an authorization server is actually made of

If you are considering writing one, it helps to see the shape of the state it must keep. The endpoints are the easy part: an authorization endpoint, a token endpoint, and then whichever of the optional ones you commit to — introspection (RFC 7662), revocation (RFC 7009), device authorization (RFC 8628), a jwks_uri and a metadata document. The stores behind them are where the work lives.

clients + registered redirect URIs
Identity and credentials per client, plus the URI set the server compares against by exact string match. This table is the whole defence against code exfiltration.
authorization codes
Single-use, short-lived — RFC 6749 recommends a maximum lifetime of ten minutes — with the code_challenge and code_challenge_method bound to each code at issue time, because that binding is what the token endpoint compares against.
replay detection on codes
If a code is presented twice the server must deny the request and should revoke all tokens previously issued from it. That means codes cannot simply be deleted on use; the server has to remember it saw them.
grants
The durable record of what this user allowed this client to do, and at what scope. This is what a revocation UI operates on, and what an audit log has to be able to reconstruct.
refresh token families
Rotation is a detection mechanism, not a prevention one, and detection needs lineage: presentation of a rotated-out token is evidence of theft and should kill the whole family.
signing keys
Published through jwks_uri over https so resource servers can validate JWT access tokens. Keys must roll without breaking tokens already in flight, which means overlapping validity and a publication schedule.

Read that list again and notice how little of it is protocol. The message formats are a weekend. Consent UX that users understand, key rotation that does not cause an outage, revocation that actually revokes, and audit logging that survives a compliance review — that is the product. The protocol is the small part.

In the spec

RFC 9126 defines the pushed authorization request endpoint: the client pushes its authorization parameters to the server over a back channel and receives a request_uri to reference at the authorization endpoint. If you are building a server, it is the available option for keeping request parameters off the front channel entirely.

Testing an integration

Start at discovery, always. The metadata document tells you the endpoints, the issuer, and what the server claims to support, which is a faster way to find out that a provider does not offer the device grant than reading its marketing pages. Then get a real authorization response onto your laptop: a loopback redirect URI, http://127.0.0.1:{port}/{path} for IPv4 or http://[::1]:{port}/{path} for IPv6, is the spec-sanctioned way to do it, and RFC 8252 requires the authorization server to allow any port to be specified at request time. Do not hardcode the port. Bind to an ephemeral one and put it in the request.

From there, the token endpoint response is your primary debugging artifact. It is a JSON object, its error member is the server's machine-readable diagnosis, and everything else you might do — adding logging, bisecting parameters, asking the provider's support desk — is downstream of reading it properly. Where the provider issues JWT access tokens under the RFC 9068 profile, you can base64url-decode the header and claims and look at iss, aud, exp and scope directly; that is a decode, not a validation, and it works because base64url is not encryption. For opaque tokens, RFC 7662 introspection is the server-side answer: the response's active member is the authoritative liveness signal, and the optional scope and client_id members tell you what the token actually carries rather than what you hoped it carried.

Introspection — ask the server what the token really is

POST /introspect HTTP/1.1
Host: server.example.com
Authorization: Basic czZCaGRSa3F0MzpnWDFmQmF0M2JW
Content-Type: application/x-www-form-urlencoded

token=mF_9.B5f-4.1JqM

One more path worth wiring in: RFC 9728 lets a resource server answer a 401 with a challenge carrying a resource_metadata URL, which turns "this API rejected me" into a discoverable route to that resource's requirements. If you follow it, check that the resource value in the returned metadata is identical to the URL you used to reach the resource server — the spec requires it, and it is the check that stops a metadata document from redirecting you somewhere it should not.

A 401 that tells you where to look next

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token",
  resource_metadata="https://api.example.com/.well-known/oauth-protected-resource"

Reading the errors

This is the table I would put on the wall. The codes are terse by design, and the gap between what a code literally means and what actually caused it is where the debugging time goes.

Token and authorization endpoint errors, and what they really mean
ErrorLiteral meaningWhat actually causes itWhere to look
invalid_request Missing a required parameter, an invalid parameter value, a parameter sent more than once, or otherwise malformed. A duplicated parameter from a URL builder; a missing code_challenge where the server requires PKCE; wrong content type on the token POST. The exact bytes of the request you sent, not the ones your library logged.
invalid_client Client authentication failed. Wrong client_id/secret pair; the right secret for the wrong environment; the wrong client authentication method (header vs. form body). The 401 response — if you authenticated via the Authorization header, RFC 6749 requires a matching WWW-Authenticate header back.
invalid_grant The grant or refresh token is invalid, expired, revoked, does not match the redirect URI used in the authorization request, or was issued to another client. A code redeemed twice; a PKCE verifier mismatch; a rotated-out refresh token. Server-side logs. See below — this one cannot be resolved from the client.
unauthorized_client This authenticated client is not authorized to use this grant type. Client credentials or device grant not enabled on the registration; a grant type the server supports but this client is not approved for; a confidential-only grant attempted by a public client. The client registration, and grant_types_supported in the metadata document.
invalid_scope The requested scope is invalid, unknown, malformed, or exceeds the scope granted by the resource owner. A typo or wrong delimiter in the scope string; a scope not enabled for this client; a refresh request asking for more scope than was originally granted. The provider's scope list, and the scope value in the original token response.
unsupported_grant_type The authorization server does not support this grant type. A grant type URN mistyped or not URL-encoded; the password grant, which is a flat MUST NOT under RFC 9700; a device grant on a provider that has none. grant_types_supported in the metadata document.
redirect_uri_mismatch Not an RFC 6749 registered error code — a provider-specific string, often surfaced as an invalid_request variant. A trailing slash; http vs. https or a differing port; the wrong environment's callback registered. A rendered error page in the browser, not a redirect. The server must not redirect to an unverified URI, so nothing reaches your handler.

Give invalid_grant its own respect. It is the most overloaded code in the specification: an expired authorization code, a replayed authorization code, a PKCE verifier that does not transform to the stored challenge, a refresh token that has been rotated out or revoked, and a redirect URI that does not match the one used in the authorization request all arrive at your client as the same six words. That overloading is deliberate — the server declines to tell an unauthenticated caller which of those it was — and it means invalid_grant cannot be diagnosed from the client side alone. When you get it, stop guessing and go and read the authorization server's logs, or ask someone who can. If you own the server, the single highest-value thing you can do for your own future debugging is log which of those five branches fired.

Trap

error_description is explicitly for humans. Branching client logic on its text works right up until the provider rewords a string, and then it fails in production with no code change on your side. Switch on error; log error_description.

In the spec

RFC 6749 requires the authorization server not to automatically redirect the user agent when the redirect URI is missing, invalid, or mismatched. That single rule is why redirect URI failures show up as an error page rather than as an error= parameter on your callback.

Build or buy

Buy. For most teams, most of the time, the recommendation is not close, and I will name the axes so you can check whether you are the exception.

The first axis is who your users are. If they are your own employees, you already have an identity provider and the question is integration, not construction. If they are consumers, you are signing up for password reset, account recovery, session management and abuse handling, none of which is OAuth and all of which you will build anyway. If they are machines — a client credentials grant scoped to one audience, no user, no consent — that is genuinely the small case, and a narrowly scoped token issuer is defensible.

The second is federation. The moment you must accept identities from providers you do not run, you inherit their key rotation schedules, their metadata quirks, and mix-up attack surface, plus the discipline of checking every iss against the server you actually addressed. Bought products have already absorbed that.

The third is the standing cost of key rotation and revocation, which is where home-grown servers go to die. Rotation is not a feature you ship once; it is a recurring operation that must not invalidate tokens in flight. Revocation is only meaningful if it propagates to resource servers, which means either short token lifetimes or an introspection call on the hot path — a real latency and availability decision, not a checkbox.

The fourth is regulatory scope. If your sector requires evidence of who authorized what and when, the audit trail is a first-class deliverable with retention and integrity requirements, and it is far cheaper to buy something whose logs an auditor already recognises.

Build when the authorization server is your product, when data residency or air-gap constraints genuinely rule out every hosted option, or when the machine-to-machine case above is the entire requirement and will stay that way. Everything in between — "we only need a small one", "our needs are unusual" — is the failure mode. What starts as a token issuer becomes a consent UI, then a revocation console, then an on-call rotation. Buy the server; spend your engineering on the resource servers, where validating iss, aud and exp correctly is work only you can do.

The artifact you will spend the most time reading

{
  "error": "invalid_grant",
  "error_description": "Authorization code expired or already redeemed"
}

What to take away

  • Discovery first, always: the metadata document gives you live endpoints and a verifiable issuer, and it must byte-match the identifier you derived the URL from.
  • The redirect handler validates state and, where offered, iss before it reads the code. Reversing that order is the bug.
  • Persist the rotated refresh token on every single refresh, or you will lock yourself out on the next call.
  • invalid_grant covers expired codes, replayed codes, PKCE mismatch, rotated-out refresh tokens and redirect URI mismatch — it is not diagnosable from the client alone.
  • Switch on error, never on error_description; redirect_uri_mismatch is not an RFC 6749 code and arrives as a page, not a redirect.
  • Buy the authorization server unless it is your product. The protocol is the small part; consent, key rotation, revocation and audit logging are the system.
