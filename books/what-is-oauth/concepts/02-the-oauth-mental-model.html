02 The redirect dance

The OAuth Mental Model

Chapter 1 established the four roles. Now we wire them together. Everything that follows in this book — PKCE, refresh rotation, sender-constrained tokens, the device grant — is a variation on one skeleton: a redirect out, a redirect back carrying a claim ticket, and a server-to-server exchange that turns the ticket into a token. Draw that skeleton once, properly, and the rest of OAuth stops being a pile of parameters and starts being a system you can reason about.

The shape of the thing

Start at the whiteboard with the simplest thing that could work. A user is sitting in front of your app. Your app wants to read their calendar, which lives behind somebody else's API. The app needs something it can put on an HTTP request that the API will accept. That something is an access token, and the entire protocol exists to answer one question: how does the app get one without ever holding the user's password?

The answer is to route the human through a third party. The app stops being the thing that asks for credentials and becomes the thing that asks for a grant. It hands the user to the authorization server, the authorization server does the sensitive part, and the app gets back a receipt it can redeem. Two endpoints carry the whole conversation. The authorization endpoint is where the user's browser goes; the client signals which grant it wants with the response_type parameter, whose value is code for an authorization code. The token endpoint is where the client goes, on its own, to exchange that grant for a token. Every grant type except the implicit grant uses the token endpoint; implicit is the odd one out that issues a token straight from the authorization endpoint, and chapter 4 explains why that was a mistake.

Commit that picture to memory. Four lifelines, seven arrows, one colour change in the middle. If you can redraw it on a napkin you can debug almost any OAuth failure, because every failure is an arrow that did not arrive or arrived carrying the wrong thing.

Why a redirect instead of a password field

Here is the pressure that forces the design. The naive version has the app render its own login form for the calendar service, collect the username and password, and use them against the API. It works on day one and it is indefensible by day two. The app now holds a credential that unlocks everything, forever, for every user who ever connected. Its logs, its crash dumps, its backups, its junior engineer's laptop are all inside the blast radius of the calendar service's account system. There is no way to grant less, and no way to revoke without a password reset.

The fix is to move the credential entry out of the app's failure domain entirely. RFC 6749 is explicit about the preference: using the authorization server as an intermediary to obtain the authorization grant — rather than having the client collect the resource owner's credentials — is the preferred method. Read that as an architectural instruction, not a style note. The password is typed into a page served by the authorization server, over that server's own TLS connection, in the user's own browser. The client is not in the request path. It cannot see the form, cannot log the POST, cannot be compromised into replaying it later. The credential never enters the client's address space, so no bug in the client can leak it.

The redirect is not a user-experience decision. It is a boundary that keeps the user's password inside the one system that is already allowed to see it. The rule of thumb

There is a second dividend, and it is the one users actually notice. Because the authorization server owns the page, it can render a consent screen: it authenticates the resource owner, shows them which application is asking and for what, and obtains an explicit authorization before anything is issued. A scope is the mechanism for limiting an application's access to a user's account — requested by the client, granted by the resource owner. That screen is where the granting happens. An app that asks for calendar.read gets a token that says calendar.read, and the user saw it say so. You cannot build that with a password; a password has exactly one scope, which is everything.

Key idea

The client is issued a different set of credentials from the resource owner, and uses an access token rather than the owner's credentials to reach protected resources. Every other property of OAuth — scoping, expiry, revocation, consent — follows from that one substitution.

Two channels, and why the code takes the slow one

Now apply pressure again. We have moved the user to the authorization server. The authorization server needs to get something back to the client, and the only wire it has to the client is the user's browser. So look hard at that wire.

The front channel is the browser. Anything sent on it travels as a URL: it appears in the address bar, in browser history, in the Referer header of any subsequent request, in proxy and web-server access logs, in the shoulder-surfer's field of view. RFC 9700 names the Referer header explicitly as a leakage channel that can disclose the authorization request or response URI. The front channel is not private and cannot be made private; it is a public bus that happens to run past the right building.

The back channel is a direct HTTP request from the client's server to the authorization server's token endpoint. No browser, no address bar, no history, no Referer. The authorization server is required to demand TLS on both the authorization endpoint and the token endpoint, and on the back channel that TLS session is the entire audience. A confidential client can also authenticate itself here, which the front channel gives it no way to do.

Front channel vs back channel
AxisFront channelBack channel
CarrierThe user's browser, as a URLServer-to-server HTTP over TLS
Who can see itHistory, logs, Referer, the screenThe two endpoints
Client authenticationNot possiblePossible and expected for confidential clients
Safe to carryA single-use, short-lived codeAccess and refresh tokens
If the message leaksSurvivable — the code alone is not enoughA token leak is a full compromise

That table is the argument in full. You must send something on the front channel, so send the thing that is cheapest to lose. The redirect carries an authorization code: a claim ticket, useless on its own, redeemable exactly once, at a different endpoint, by a party that can prove it is the client. The token comes back on the back channel where nobody is watching. This is also the reason RFC 9700 tells clients to use response_type=code rather than any response type that puts an access token in the authorization response — the code response reduces attack surface because access tokens are never exposed in URLs, and it lets the authorization server detect replay attempts.

In the spec

RFC 6749 RECOMMENDS a maximum authorization code lifetime of 10 minutes, and says the client MUST NOT use the authorization code more than once. If a code is used more than once, the authorization server MUST deny the request and SHOULD revoke, where possible, all tokens previously issued from that code.

Read that revocation clause carefully, because it is the part that makes the design work rather than merely sound nice. A second redemption of a code is evidence: either an attacker got the code, or the legitimate client did, but the server cannot tell which. So it assumes theft and burns everything descended from that code. Single-use is not hygiene, it is a tripwire.

Trap

Do not put the token exchange behind a generic HTTP retry-with-backoff wrapper. A transient network error after the server has already redeemed the code will make your retry replay it, and the response is invalid_grant — plus, per the rule above, the tokens you successfully obtained on the first attempt may be revoked underneath you. Retry the whole authorization, not the exchange.

The exchange on the wire

Four messages. The client builds the authorization request by adding parameters to the query component of the authorization endpoint URI in application/x-www-form-urlencoded format, then sends the browser there.

1 · Authorization request (front channel)

GET /authorize?response_type=code
    &client_id=s6BhdRkqt3
    &redirect_uri=https%3A%2F%2Fclient.example.org%2Fcb
    &scope=calendar.read
    &state=xyz HTTP/1.1
Host: server.example.com
# line-wrapped here for reading; on the wire it is one URL
Authorization request parameters
ParameterStatusWhat it does
response_typeREQUIREDWhich grant you want. MUST be code for the authorization code grant.
client_idREQUIREDIdentifies the application asking. Public, not a secret.
redirect_uriOPTIONALWhere to send the browser back to. Send it, and send the same value again at the token endpoint.
scopeOPTIONALThe access being requested, and what the consent screen will describe.
stateRECOMMENDEDOpaque client value the server echoes back on the redirect.

The user logs in and consents. The authorization server then bounces the browser back to the registered redirect URI with two things attached — and note what is not attached.

2 · Authorization response (front channel)

HTTP/1.1 302 Found
Location: https://client.example.org/cb?code=SplxlOBeZQQYbYS6WxSbIA&state=xyz

A code and the state you sent. No token. That URL will sit in the user's history and quite possibly in a load balancer log, and it does not matter much, because within ten minutes at the outside the code is dead and it can only be spent once anyway. Now the client leaves the browser behind and goes direct.

3 · Token request (back channel)

POST /token HTTP/1.1
Host: server.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=SplxlOBeZQQYbYS6WxSbIA&redirect_uri=https%3A%2F%2Fclient.example.org%2Fcb&client_id=s6BhdRkqt3

The redirect_uri appears twice in the flow on purpose: the client includes the redirection URI used to obtain the code so the server can verify it matches. It is a binding check, not a routing instruction — nothing is redirected here. Get it wrong and the token endpoint answers invalid_grant, not invalid_request, which is why a stray trailing slash can cost you an afternoon.

4 · Token response (back channel)

{
  "access_token": "2YotnFZFEjr1zCsicMWpAA",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "tGzv3JOkF0XG5Qx2TlKWIA",
  "scope": "calendar.read"
}

If the request is valid and authorized, the server issues an access token and an optional refresh token. At model level, three things matter here and chapter 3 does the anatomy. The access token is a string denoting a specific scope, lifetime and other access attributes — the thing you actually put on API calls. The refresh token is a credential used to obtain access tokens: a new one when the current token expires or becomes invalid, or additional tokens with identical or narrower scope. Whether the client must authenticate to use it depends on the client type and on authorization server policy. And scope in the response is the server telling you what you actually got, which is not always what you asked for.

Notice the division of labour that falls out. The refresh token lives only on the back channel and only in the client's server-side storage. The access token is short-lived and goes out to resource servers. Two credentials, two lifetimes, two exposure profiles — that separation is why a leaked access token is an incident with an expiry date rather than a permanent one.

state: recommended by the spec, mandatory in practice

One parameter deserves its own section because the spec understates it. state is an opaque value the client uses to maintain state between the request and the callback, which the authorization server includes when it redirects the user-agent back. RFC 6749 marks it RECOMMENDED. Treat that as a historical artifact and write your code as if it said MUST.

The reason is the failure mode it closes. Your redirect endpoint is a public URL that accepts a code parameter and turns it into a linked account. Without state, anything that can make a user's browser issue a GET to that URL — an image tag on a forum, a link in an email — can complete a flow the user never started, silently attaching an attacker's account to your user's session. With state, the client generates an unguessable one-time value, stores it bound to the user's session, and on the callback checks that the returned value is the one it stored. A callback that does not carry your value did not come from your request, and you drop it before you ever call the token endpoint.

Trap

The base specification only RECOMMENDS state, so a conformant server will happily run a flow without it and nothing in your integration tests will go red. There is no error code for "you forgot your CSRF defence". Chapter 5 covers what a good state value looks like — one-time-use and bound to the user agent — and the narrow conditions under which PKCE can stand in for it.

The trade-off, stated plainly

OAuth's redirect dance costs you real things: two extra round trips, a browser you do not control in the middle of your critical path, a callback endpoint to secure, and a class of bugs that only reproduce in a real browser. Measured on latency and implementation complexity, handing the app a password wins outright. Measured on blast radius, revocability, and least privilege, it is not close. You are trading a few hundred milliseconds and a state machine for the ability to say "this app can read one calendar, until Tuesday, and the user can cut it off from their account settings without changing anything else". Take that trade every time.

What the skeleton still does not give you is proof that the party redeeming the code is the party that requested it. For a confidential client, client authentication at the token endpoint covers that. For a public client — a mobile app, a single-page app — there is no secret to authenticate with, and the code can be intercepted on its way back. That gap is exactly what PKCE closes, and it is where chapter 4 picks up.

What to take away

  • Two endpoints, two channels. The authorization endpoint talks to the browser; the token endpoint talks to your server. Which channel a message rides determines what it is safe to put on it.
  • Credentials are typed into the authorization server's page, in the user's browser. Using the authorization server as an intermediary is the spec's preferred method, and the client never sees the password.
  • The redirect carries a code, not a token. The code is single-use with a RECOMMENDED 10-minute maximum lifetime; reuse means the server MUST deny and SHOULD revoke everything issued from it.
  • Send redirect_uri in both requests, identically. A mismatch surfaces as invalid_grant.
  • Access token for calling APIs, refresh token for getting more access tokens, scope for bounding both. Chapter 3 opens them up.
  • state is RECOMMENDED in RFC 6749 and mandatory in any code you would defend in review.
