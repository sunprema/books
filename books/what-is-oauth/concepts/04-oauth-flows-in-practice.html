04 Pick the right dance

OAuth 2.0 Flows in Practice

RFC 6749 defines four grant types — authorization code, implicit, resource owner password credentials, and client credentials — plus a mechanism for defining more. That reads like a menu. It is not. It is a record of pressure being applied to one design until it broke in four different places. Start from the simplest system that works, apply the pressure yourself, and the zoo turns into a short decision procedure.

Start with the flow that already works

Chapter 2 walked the authorization code flow: the client sends the user to the authorization endpoint with response_type=code, the server redirects back with a code, and the client trades that code at the token endpoint for an access token. Nothing about that is provisional. It is the default, and for every client type discussed in this chapter the answer starts from it. The reason is structural rather than aesthetic. The redirect carries a code, not a token, so anything that observes the redirect — browser history, a proxy log, a Referer header — sees a value that is single-use, short-lived (a maximum lifetime of ten minutes is recommended), and useless without a second request to the token endpoint. That second request is a back channel the client controls, which gives the server a second place to check things.

The original design assumed the client could authenticate on that second request. A web application running on a server is a confidential client: the client secret and the issued tokens live on the server and are never exposed to the resource owner. The code alone is worth nothing to a thief, because redeeming it also requires the secret. Under that assumption the flow is complete and the rest of this chapter would be unnecessary.

Pressure one: the client cannot keep a secret

Now the client is a mobile app. You ship it to a hundred thousand phones, and whatever secret you compile into it is a secret that a hundred thousand people can extract. It is a public client — it authenticates with nothing but its client_id, which is not a credential, it is a name. The token endpoint can no longer ask "are you really this client?" and so the entire security of the exchange rests on one assumption: that nobody but the real client sees the authorization code.

That assumption does not hold on a phone. RFC 8252 gives native apps three ways to receive the redirect, and the common one — a private-use URI scheme such as com.example.app:/oauth — is explicitly weak, because multiple apps can register the same scheme and it is indeterminate which one the operating system hands the redirect to. A malicious app that registers your scheme receives your authorization code. It has your client_id, because that is public. It has the code. It has everything the token endpoint asks for. This is the authorization code interception attack, and it is the specific hole PKCE was built to close.

Proof Key for Code Exchange fixes the shape of the problem rather than the symptom. If the client cannot prove its identity with a long-lived secret, let it prove continuity with a fresh one: generate a random value per authorization request, send only a hash of it up the front channel, and present the original at the token endpoint. The server binds the hash to the code at issuance and checks it at redemption. An attacker who intercepts the code never saw the original value and cannot produce it. Beyond interception, this same binding is what prevents authorization code injection and gives the flow CSRF protection.

Key idea

PKCE does not make the authorization code harder to steal. It makes a stolen code unredeemable, because the token endpoint now demands a value that only ever existed inside the real client.

The derivation, exactly

The client generates a code_verifier. Its grammar is 43*128unreserved, where unreserved = ALPHA / DIGIT / "-" / "." / "_" / "~" — between 43 and 128 characters, drawn from that set and nothing else. It must be cryptographically random with enough entropy that guessing is impractical; the specification recommends a minimum of 256 bits. Those two constraints meet neatly: base64url-encoding a 32-octet random sequence produces a 43-octet URL-safe string, which is both the shortest legal verifier and a full 256 bits of entropy. That is why nearly every correct implementation you will read looks the same.

The S256 transformation

code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))

Deriving verifier and challenge in Python

import os, hashlib, base64

verifier = base64.urlsafe_b64encode(os.urandom(32)).rstrip(b'=').decode('ascii')
challenge = base64.urlsafe_b64encode(
    hashlib.sha256(verifier.encode('ascii')).digest()
).rstrip(b'=').decode('ascii')

Read the second statement again, because the whole extension turns on it. The hash input is verifier.encode('ascii') — the ASCII bytes of the verifier string. It is not os.urandom(32), the raw octets the string was derived from. Both are 32-ish bytes of random-looking material, both produce a plausible-looking challenge, and only one of them interoperates. This is the single most common PKCE bug, and it is miserable to diagnose because the failure appears at the token endpoint, in the other party's code, as a generic invalid_grant.

Trap

Hash the ASCII bytes of the verifier string, never the random octets you generated it from. Two related traps sit beside it: strip the = padding from base64url output and translate +// to -/_, or the server rejects the challenge; and derive the verifier from 32 random octets, not 32 random characters, which yields materially less than the recommended 256 bits.

RFC 7636 ships a test vector in Appendix B precisely so you can settle this in thirty seconds rather than in a support ticket. Feed the verifier below into your implementation. If you do not get the challenge below, you are hashing the wrong thing.

RFC 7636 Appendix B test vector

code_verifier  = dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
code_challenge = E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM

S256 against plain, and what the server owes you

There are two challenge methods. With plain, code_challenge = code_verifier — the secret travels up the front channel in the clear, so anything that could intercept the code could also have read the challenge on the way past. With S256 the challenge is the hash, and an eavesdropper who observes or intercepts it gains nothing, because the challenge cannot be used without the verifier. Servers that support PKCE at all are required to support S256. There is no trade-off here worth deliberating: use S256, and treat a server that quietly accepts plain as offering no protection.

The server has two obligations, one at each endpoint. When it issues the authorization code it MUST associate the code_challenge and code_challenge_method values with that code — the binding is state on the server, not something carried in the code by convention. At the token endpoint it transforms the received code_verifier according to the method it recorded and compares the result against the stored challenge; if the values are not equal the request must be rejected. And if the server requires PKCE but the client omits code_challenge, the authorization endpoint must return an authorization error response with error set to invalid_request, explaining that a challenge is required. A server that ignores a missing challenge has an extension it does not enforce, which is worse than none because it reads as protection in a review.

Authorization code + PKCE token request

POST /token HTTP/1.1
Host: server.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=SplxlOBeZQQYbYS6WxSbIA&redirect_uri=https%3A%2F%2Fclient.example.org%2Fcb&client_id=s6BhdRkqt3&code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
PKCE ensures that an attacker cannot redeem a stolen authorization code without knowledge of the code verifier. RFC 9700, in one line

The current security best practice has moved past treating this as an option. RFC 9700 states that authorization servers MUST support PKCE and that public clients MUST use it to prevent injection of authorization codes into the authorization response. For confidential clients RFC 9700 makes it RECOMMENDED rather than required; OAuth 2.1 is the document that folds it into the base authorization code grant for everyone. Either way, the engineering answer is the same and it is not a judgement call: turn it on everywhere. It costs one hash.

Pressure two: there is no user

Now remove the human. A nightly reporting job needs to read from an internal API. There is no resource owner sitting at a browser to consent, no redirect to come back to, and no session to maintain. Every mechanism in the authorization code flow exists to route a decision through a person, and there is no person. Running the flow anyway — with a service account, a headless browser and a scraped consent screen — is a well-known way to build something that breaks at three in the morning.

The client credentials grant is the honest version. The client authenticates as itself directly at the token endpoint and receives a token. It applies when the authorization scope is limited to protected resources under the control of the client, or to resources previously arranged with the authorization server — that is, when the client is acting on its own behalf rather than on anyone's. Two things follow. There is no refresh token to manage, because re-authenticating is exactly as cheap as refreshing. And the client is confidential by definition: if it cannot hold a credential, this grant has nothing to stand on.

Client credentials request

POST /token HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Authorization: Basic czZCaGRSa3F0Mzo3RmpmcDBaQnIxS3REUmJuZlZkbUl3

grant_type=client_credentials&scope=reports.read

Pressure three: there is no keyboard

Now put the client on a television. There is a user, and they can consent, but the device has a ten-foot display and a four-way remote. Typing a password into it is hostile; typing it into an on-screen keyboard in front of a room of people is worse. The input constraint, not the security model, is what breaks here — so the device authorization grant of RFC 8628 moves the browser part of the flow onto a second device the user already has in their pocket.

The device asks the device authorization endpoint (advertised in authorization server metadata as device_authorization_endpoint) for a session, and gets back six fields. device_code is the device's own handle, kept internally. user_code is the short string the device puts on screen. verification_uri is where the user goes to enter it — GitHub, for instance, uses https://github.com/login/device. verification_uri_complete is the same URI with the user code already embedded, designed for non-textual transmission such as a QR code, which removes the typing entirely. expires_in bounds the session, and interval is the minimum number of seconds the client should wait between polls — if the server omits it, clients MUST default to 5 seconds. Defaulting to zero because the field was absent is how a device gets rate-limited on its first boot.

Meanwhile the device polls the token endpoint with the grant type URN urn:ietf:params:oauth:grant-type:device_code, form-encoded like any other token request.

Device grant poll request

POST /token HTTP/1.1
Content-Type: application/x-www-form-urlencoded

grant_type=urn%3Aietf%3Aparams%3Aoauth%3Agrant-type%3Adevice_code&device_code=GmRhmhcxhwAzkoEqiMEg_DnyEysNkuNhszIySk9eS&client_id=1406020730

The usual answer, for a while

{"error": "authorization_pending"}

The poll loop has four terminal-or-not outcomes, and the most common implementation mistake is treating the first two as failures. They are flow control.

Device grant poll responses
ResponseMeaningWhat the client does
authorization_pendingThe authorization request is still pending.Keep polling; wait at least interval seconds, or 5 if none was given.
slow_downA variant of pending: you are polling too fast.Keep polling, but increase the interval by 5 seconds for this and all subsequent requests.
expired_tokenThe device_code expired; the session has concluded.Stop. Start a new device authorization request.
access_deniedThe authorization request was denied.Stop. Tell the user.
Trap

The slow_down increase is permanent, not a one-request penalty. A client that backs off by five seconds and then resets to its original interval on the next successful-ish poll will keep tripping the same limit and can be cut off entirely.

The user code deserves more design attention than it usually gets, because a human retypes it under mild social pressure. Because it is typed by hand, shorter codes are preferred for usability, and its entropy is typically lower than the device code's — which is exactly why the server should rate-limit attempts against it. On the input side, if the code set is only A-Z, uppercase the user's input before comparison, and strip characters outside the chosen set so that spaces and stray dashes do not cause failures. These are small mercies that remove most of the support load from the flow.

The two flows to stop reaching for

The implicit grant returned an access token directly from the authorization endpoint, in the URL fragment, skipping the token endpoint entirely. It existed because browsers once could not make the cross-origin token request. They can now, and what remains is a design that puts a bearer token in a URL, where it is vulnerable to leakage and to replay. The resource owner password credentials grant had the client collect the user's actual username and password. It existed for migration, and it inverts the premise of the entire framework: using the authorization server as the intermediary, rather than having the client handle the user's credentials, is the preferred method and always was.

In the spec

RFC 9700 states that clients SHOULD NOT use the implicit grant or any other response type issuing access tokens in the authorization response, and SHOULD use the response type code instead, which lets the authorization server detect replay attempts and keeps access tokens out of URLs. Of the password grant it is blunter: it MUST NOT be used. OAuth 2.1 omits both grants from the specification altogether.

Note the register. "Discouraged" and "legacy but allowed" are not what these documents say, and the difference matters when you are the one arguing against a vendor SDK in a design review. Cite the normative words.

The decision guide

Here is the whole chapter compressed. Find your client type, take the flow, and move on. The third column is the question that actually decides it — if you find yourself debating, that is the question you are debating.

Client type to flow
ClientUse thisThe deciding question
Server-side web appAuthorization code with PKCE, authenticating as a confidential clientCan the client hold a secret the browser never sees? Yes — so authenticate, and add PKCE anyway.
Browser SPAAuthorization code with PKCE, preferably behind a Backend-For-FrontendCan tokens be kept out of JavaScript? A BFF is the pattern that says yes.
Mobile / native appAuthorization code with PKCE, in the system browser or an in-app browser tabCould another installed app claim your redirect? With private-use URI schemes, yes — so PKCE is not optional.
CLI / desktop toolAuthorization code with PKCE on a loopback redirect, http://127.0.0.1:{port}/{path}Can this machine open a browser and listen on an ephemeral port? If yes, no special flow is needed.
TV, console, smart deviceDevice authorization grant (RFC 8628)Can the user comfortably type into this device? If no, move the browser to their phone.
Backend service, no userClient credentialsIs there a resource owner to ask? If no, stop pretending there is one.

Two entries in that table are the same flow wearing different clothes, and that is the point. Web app, SPA, mobile, CLI — all authorization code with PKCE. What changes is the redirect mechanism and whether the client can additionally authenticate. The device grant is a genuinely different flow because a genuinely different constraint produced it, and client credentials is different because it deletes the user rather than routing around them. Everything else is one flow with the interception hole patched. If a provider offers you a fifth option that is not on this list, the burden is on that option to explain which constraint it exists to relieve.

What to take away

  • Authorization code with PKCE is the default for every client that has a user. The differences between web, SPA, mobile and CLI are redirect mechanics, not different flows.
  • code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier))), always S256. Hash the ASCII bytes of the verifier string; check yourself against the Appendix B vector before you ship.
  • A 43-character verifier from 32 random octets satisfies both the 43*128unreserved grammar and the 256-bit entropy recommendation.
  • The server's job is two-sided: bind challenge and method to the code at issuance, recompute and compare at the token endpoint.
  • Client credentials when there is no user; device grant when there is a user but no usable keyboard, with authorization_pending and slow_down handled as flow control rather than errors.
  • Implicit is SHOULD NOT and password is MUST NOT under RFC 9700, and OAuth 2.1 omits both. Use the normative words, not "discouraged".
