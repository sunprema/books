03 What you are actually holding

Tokens Up Close

An access token is a string. RFC 6749 defines it as a string denoting a specific scope, lifetime, and other access attributes, and that sparse definition is the entire contract. Everything else — whether the string is a random handle or a signed document, whether the resource server can read it, how fast a revocation actually takes effect — is a design decision somebody made. This chapter is about making it on purpose.

Bearer means what it says

RFC 6750 says clients SHOULD make authenticated requests with a bearer token using the Authorization request header field with the Bearer HTTP authorization scheme. The name is the specification. A bearer token authorizes whoever bears it. The resource server never asks who is calling; it asks whether the string it was handed is good. There is no client key in the request, nothing for the caller to sign, nothing to prove. That is the simplest thing that works, and it works remarkably well: the resource server holds no per-client state, needs no handshake and no certificate store, and any HTTP client written in the last thirty years can call it.

The cost is that the whole security model collapses into a single requirement — keep the string secret — and three consequences follow from that. Keep it off the wire in the clear, which is why TLS is not a deployment preference. Keep it out of URLs: a token in a query parameter is copied into access logs, Referer headers and browser history, three systems whose retention policy you do not control and none of which will ever tell you it happened. And keep the lifetime short, because the blast radius of a stolen bearer token is time-remaining multiplied by everything the scope allows, and expiry is the only one of those two factors you can shrink for free.

The grammar is worth pinning down, because it is what your storage and transport layers have to survive. RFC 6750 defines credentials = "Bearer" 1*SP b64token, where b64token is one or more of ALPHA, DIGIT, -, ., _, ~, +, /, followed by any number of = characters. Note what is absent: no spaces, no colons, no braces. A token is a single header-safe blob — and the dots you see inside a JWT are legal members of that set, which is exactly why JWTs slot into the bearer scheme without needing a new header.

Calling a protected resource

GET /calendar/v3/events HTTP/1.1
Host: api.example.com
Authorization: Bearer mF_9.B5f-4.1JqM
Trap

Passing the access token as a URI query parameter leaks it into server logs, Referer headers and browser history. The header form above is the one clients are told to use; a query parameter is a durable copy of a live credential in three places you will never fully clean.

Two shapes of token

Every access token you will meet is one of two shapes, and choosing between them is a systems decision, not a matter of taste. An opaque token is a handle. The string carries no information at all; it is a lookup key into the authorization server's storage. Nothing but the authorization server can say what it means, which means the truth about that token exists in exactly one place, with exactly one copy, and changes to it are instantly and universally visible.

A JWT access token is a self-describing signed document. RFC 9068 defines the profile that makes this interoperable across vendors: the media type application/at+jwt, and a typ header value that SHOULD be at+jwt. JWT access tokens MUST be signed; any signing algorithm may be used, but asymmetric cryptography is RECOMMENDED because it simplifies acquiring validation information for resource servers. That last clause is the architectural point. With an asymmetric signature the resource server needs only a public key it can fetch over HTTPS — not a shared secret that has to be distributed to, and rotated across, every resource server in the estate.

So the two shapes differ on where the truth lives, and everything else falls out of that. Put the truth at the authorization server and every validation is a network call, but a revocation lands immediately. Copy the truth into the token and validation is local arithmetic, but the copy in the attacker's hands stays true until it expires.

Opaque versus JWT, on the axes that matter

What I would pick

For a high-volume API — every request from every client carrying a token — take short-lived JWTs validated locally, and reserve introspection for the handful of high-value operations where a stale answer is unacceptable: money movement, permission changes, destructive deletes. When instant revocation matters more than the extra hop — an admin console, an internal tool, anything where "log out everywhere" must mean now — use opaque tokens and pay the network call.

An opaque token asks the authorization server what is true. A JWT tells you what was true when it was signed. The trade-off in one line

How a resource server validates a token

Local validation is a fixed sequence, and every step in it is normative. The resource server MUST validate the signature of all incoming JWT access tokens using the algorithm specified in the alg header parameter, against a key retrieved from the authorization server's jwks_uri. Then three checks on the payload: the authorization server's issuer identifier MUST exactly match the iss claim; aud MUST contain a resource indicator value corresponding to an identifier the resource server expects for itself, and the token MUST be rejected if it does not; and the current time MUST be before the time represented by exp. Only after all four pass does sub mean anything.

iss
Checked against the authorization server's issuer identifier — an exact match, not a prefix or a host comparison.
aud
Checked against an identifier this resource server expects for itself. No match, no service.
exp
Checked against the current time, which must be earlier. This is the only bound on a leaked token you validate offline.
sub
Where a resource owner is involved, their subject identifier; where none is — the client credentials grant — an identifier for the client application itself.

Of those four, aud is the one teams skip, because a token that verifies and has not expired feels valid. It is not. Verifying the signature proves only that your authorization server minted the token; it says nothing about who the token was minted for. Without the audience check, any service that trusts the same issuer will accept a token issued for any other service that trusts the same issuer — so a token your low-value analytics API legitimately receives can be lifted and replayed against your billing API. Every resource server behind one authorization server is then a single failure domain, and the weakest one sets the level for all of them.

In the spec

RFC 9068 makes this non-negotiable: the resource server MUST validate that aud contains a resource indicator value corresponding to an identifier it expects for itself, and MUST reject the token if it does not.

Trap

Reading alg out of the token and doing whatever it says is not signature validation — it is asking the attacker which lock to use. Pin the algorithms you accept, and never accept none. And remember the other direction: a JWT is readable by anyone holding it, so never put anything in one that the client should not see.

The other path is RFC 7662 introspection. The introspection endpoint takes a parameter representing an OAuth 2.0 token and returns a JSON document describing the meta information surrounding it, including whether the token is currently active. In that response, active is the only REQUIRED member: a boolean indicator of whether the presented token is currently active. A true value generally indicates that the token was issued by this authorization server, has not been revoked by the resource owner, and is within its validity window — three questions answered by one field, from the authoritative store. scope (a space-separated string) and client_id are OPTIONAL extras.

Introspection request

POST /introspect HTTP/1.1
Content-Type: application/x-www-form-urlencoded

token=mF_9.B5f-4.1JqM&token_type_hint=access_token

Introspection response

{
  "active": true,
  "scope": "calendar.read",
  "client_id": "s6BhdRkqt3",
  "exp": 1782000000
}

Read active and nothing else to decide. It is tempting to ignore it and recompute a verdict from the exp in the response, since that field is right there — but every optional member is decoration around the one answer the endpoint is required to give. Reconstructing the decision yourself reintroduces the staleness you paid a network hop to avoid.

What the resource server says when it says no

Two failures, two status codes, and clients depend on the distinction. The invalid_token error code indicates the access token provided is expired, revoked, malformed, or invalid for other reasons, and the resource server SHOULD respond with 401. The insufficient_scope error code indicates the request requires higher privileges than the token provides; the resource server SHOULD respond with 403 and MAY include the scope attribute naming the scope necessary to access the resource. All challenges defined by RFC 6750 MUST use the auth-scheme value Bearer in the WWW-Authenticate header field.

The reason to be precise is that the two codes trigger different client behaviour. A 401 with invalid_token means refresh and retry — the credential is stale but the grant may be fine. A 403 with insufficient_scope means stop and send the user back through authorization for more scope; retrying with a fresh token will fail identically forever. Collapse both into 401 and you have built a refresh loop that can never succeed, which is a support ticket that arrives as "the integration hangs".

Expired or revoked token

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="example",
                  error="invalid_token",
                  error_description="The access token expired"

Valid token, wrong scope

HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer realm="example",
                  error="insufficient_scope",
                  scope="calendar.write"

There is a third case, and it is the one that gets implemented wrong most often. If the request lacks any authentication information at all, the resource server SHOULD NOT include an error code or other error information in the response. Nothing has failed yet — the caller simply has not tried. The correct answer is a bare Bearer challenge that advertises the scheme and says nothing more. The available error codes, for completeness, are invalid_request, invalid_token and insufficient_scope; the challenge attributes are realm, scope, error, error_description and error_uri. That is the entire vocabulary.

Expiry, refresh, revocation, audience

Expiry is the default eviction mechanism and it costs nothing to run. Refresh tokens are the counterweight: credentials used to obtain a new access token when the current one becomes invalid or expires, or to obtain additional access tokens with identical or narrower scope. The resulting shape is the one you want — a long-lived grant held at the authorization server, where it can be inspected and withdrawn, and a short-lived token at the resource server, where it cannot.

RFC 7009 adds the endpoint that closes the loop: it lets a client notify the authorization server that a previously obtained refresh or access token is no longer needed. The request is form-encoded with a REQUIRED token parameter and an OPTIONAL token_type_hint, for which the specification defines two values, access_token and refresh_token. Notice which failure domain revocation actually reaches. Revoke an opaque token and the next introspection returns active: false. Revoke a JWT you validate offline and the authorization server's records change instantly while the resource servers keep honouring the copy in circulation until exp. Revocation is a promise about the authorization server, not about every process holding a cached public key.

Revocation request

POST /revoke HTTP/1.1
Content-Type: application/x-www-form-urlencoded

token=45ghiukldjahdnhzdauz&token_type_hint=refresh_token

The audience check earlier only works if somebody set the audience, and RFC 8707 is how the client says what it wants. The resource parameter value identifies a resource the client is requesting access to and can carry the location of a protected resource, typically as an https URL or a more abstract identifier. It MUST be an absolute URI, MUST NOT include a fragment component, and SHOULD NOT include a query component. Used on an access token request at the token endpoint, for all grant types, it indicates the target service where the client intends to use the token. An authorization server MAY require clients to specify the resources they intend to access and MAY fail requests that omit the parameter with an invalid_target error — and on a multi-API estate, requiring it is the right default, because it turns audience restriction from a convention into something the server enforces.

Discovery: where the resource server gets its facts

Local validation needs two inputs the resource server cannot invent: the signing keys and the expected issuer. RFC 8414 publishes both. Authorization server metadata lives at a .well-known location derived from the issuer identifier, and the default well-known URI string /.well-known/oauth-authorization-server is the right choice for general-purpose OAuth authorization servers. In that document, issuer is REQUIRED and is an https URL with no query or fragment components; authorization_endpoint is REQUIRED unless no grant types using it are supported, and response_types_supported is REQUIRED. The jwks_uri references the document containing the signing keys used to validate the authorization server's signatures, and that URL MUST use the https scheme. RFC 9068 points straight at this: authorization servers SHOULD advertise their signing keys via jwks_uri and the expected iss value via issuer.

One rule anchors the whole chain. The returned issuer value MUST be identical to the issuer identifier into which the well-known URI string was inserted, and if they are not identical the data in the response MUST NOT be used. Skip that comparison and a redirect or a hijacked host can hand you a metadata document pointing jwks_uri at keys an attacker controls — at which point every signature you check will pass. It is one string comparison guarding every downstream verification you will ever do.

The construction rule surprises people. If the issuer identifier contains a path component, any terminating / is removed and /.well-known/ is inserted between the host component and the path component — the suffix goes before the path, not after it. Most implementers guess the opposite, append the well-known path to the issuer URL, and get a 404 they then work around by hardcoding an endpoint.

Metadata request, with and without a path component

# issuer https://example.com
GET /.well-known/oauth-authorization-server HTTP/1.1
Host: example.com

# issuer https://example.com/issuer1
GET /.well-known/oauth-authorization-server/issuer1 HTTP/1.1
Host: example.com
Trap

/.well-known/oauth-authorization-server and /.well-known/openid-configuration are distinct endpoints and may return different documents on the same host. Fetching the one you did not mean is a debugging session that starts with a missing metadata field. The OpenID Connect side is chapter 7.

What to take away

  • Bearer means possession is authorization. TLS, no tokens in URLs, and short lifetimes are not hardening — they are the security model.
  • Opaque or JWT is a choice about where the truth lives. Opaque buys instant revocation for a network hop per request; JWT buys offline validation and independence from the authorization server for a revocation delay bounded by exp.
  • Local validation is four mandatory checks: signature via alg and the JWKS, then iss, aud, exp. Dropping aud makes every resource server behind one issuer a single failure domain.
  • With introspection, active is the answer. It is the only REQUIRED member of the response, and it is authoritative.
  • invalid_token is 401, insufficient_scope is 403, and a request with no authentication information at all gets a bare challenge with no error code.
  • Fetch discovery metadata, compare the returned issuer to the one you derived the URL from, and reject the document on mismatch. Remember the well-known suffix goes before the path.
