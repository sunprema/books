05 Where it actually breaks

Security, Pitfalls, and Best Practices

Every chapter so far described the protocol working. This one describes it under attack. The useful way to hold this material is not as a list of rules but as a set of failure domains: for each control, know what an attacker walks away with when that control fails, and know which other control is still standing behind it. A single mitigation that carries an entire flow is a design smell.

The document that changed the defaults

RFC 9700, "Best Current Practice for OAuth 2.0 Security", was published in January 2025 as BCP 240. It is the published successor to the long-running draft-ietf-oauth-security-topics series, which many teams cited for years while it was still a draft. If your internal standards document points at a security-topics draft revision, that pointer is now stale.

The important structural fact is that RFC 9700 updates RFC 6749, RFC 6750, and RFC 6819 — it does not obsolete them. It extends their threat model and deprecates modes of operation deemed less secure or insecure. Practically: RFC 6749 still defines what the parameters are and what the endpoints do; RFC 9700 redefines what a correct implementation of RFC 6749 looks like in 2025. You need both open. Reading 6749 alone will lead you to build something that was compliant in 2012 and is not defensible now.

In the spec

RFC 9700 says public clients MUST use PKCE to prevent authorization code injection and misuse of authorization codes, and that for confidential clients use of PKCE is RECOMMENDED. Authorization servers MUST support it. The blanket "PKCE for every client, always" mandate is OAuth 2.1's, not RFC 9700's — quote the right document when you are writing a policy someone has to comply with.

Redirect URI validation is the whole boundary

RFC 9700 requires that authorization servers use exact string matching when comparing a client's redirection URI against the pre-registered ones. Exact means the whole URI, not just the origin — not the host, not the host plus a path prefix. Wildcard paths, wildcard subdomains, and tolerated extra query parameters all reopen the same hole: they let an attacker name a redirect target that the authorization server accepts but that the client's own infrastructure will forward somewhere else.

That "somewhere else" is the open redirector. RFC 9700 states that clients and authorization servers MUST NOT expose open redirectors — URLs that forward the browser to an arbitrary URI taken from a query parameter — precisely because they enable exfiltration of codes and access tokens. The point that gets missed in reviews: the open redirector does not have to live on an OAuth endpoint. Any forwarding endpoint anywhere on the client's registered domain is enough, because the authorization server's exact match already succeeded before the forward happens. The audit scope is the whole site — marketing landing pages, legacy /out?url= handlers, login-return helpers — not the four routes your OAuth library owns.

Native apps get one narrow carve-out from exact matching. RFC 8252 loopback redirects use a port chosen at runtime, so the authorization server must accept any port for those. Hardcoding a fixed port in a desktop client is the pitfall on the other side of that rule: the port will eventually be taken, and the flow will fail on a user's machine you cannot reach.

Loopback redirect forms (RFC 8252)

http://127.0.0.1:{port}/{path}   IPv4
http://[::1]:{port}/{path}       IPv6

Failure domain: if exact matching is broken or an open redirector exists, the attacker receives authorization codes minted for real users. What is still standing is PKCE — the code is inert without the code_verifier, which never left the legitimate client. That is exactly why PKCE is a MUST for public clients rather than a nice-to-have. Redirect validation and PKCE are two independent layers over the same asset, and you should assume you will one day need the second one.

CSRF at the redirection endpoint

RFC 9700 requires clients to prevent CSRF against the redirection endpoint: requests that arrive at your redirect URI carrying a code but that did not originate at the authorization server. The concrete harm is account grafting — the attacker gets their own authorization code delivered into the victim's browser session, and the victim's account at your client ends up linked to the attacker's resources.

The stated countermeasure is a one-time-use CSRF token carried in state and securely bound to the user agent. Both halves are load-bearing. A 256-bit random state that your server accepts twice, or that is not tied to the browser session that started the flow, is decoration; it looks like entropy and provides no CSRF protection at all.

Trap

Randomness is not the property that matters here. Single use and binding to the user agent are. Storing state in a shared cache keyed only by its own value, and deleting it "eventually", fails both tests while passing every code review that only greps for secrets.token_urlsafe.

RFC 9700 does permit a client to rely on PKCE's CSRF protection instead of state — but only once the client has confirmed that the authorization server supports PKCE. Confirmed, not assumed: against a server that silently ignores code_challenge, dropping state removes your only CSRF control. In OpenID Connect flows the nonce parameter also provides CSRF protection. What nonce does not do is protect a public client's authorization codes, because an attacker holding a stolen code can call the token endpoint directly and never touch the ID token. PKCE is the defence for that; nonce is not a substitute.

Mix-up attacks

A mix-up attack arises when a client talks to two or more authorization servers and at least one of them is attacker-controlled. The attacker tricks the client into sending a code or token issued by the honest server to the compromised one. If your client only ever talks to a single authorization server, this class does not apply to you — which is worth saying out loud, because it is the cheapest way to know whether the countermeasure is on your critical path or not. The moment you add a second identity provider, or ship multi-tenant "bring your own IdP", it moves onto that path.

The countermeasure is RFC 9207, which defines the iss authorization response parameter carrying the authorization server's issuer identifier explicitly. A supporting client extracts iss from the authorization response, form-urldecodes it, and compares it by simple string comparison to the issuer identifier of the server it actually sent the request to — rejecting the response on mismatch.

Authorization response with the issuer identifier

HTTP/1.1 302 Found
Location: https://client.example.org/cb?code=SplxlOBeZQQYbYS6WxSbIA
   &state=af0ifjsldkj
   &iss=https%3A%2F%2Fserver.example.com
Trap

Receiving iss is not the defence. Comparing it against the issuer you started the flow with, and rejecting on mismatch, is the defence. A client that logs iss, or stores it, or trusts it as the issuer instead of checking it against its own record, has added a field and no security.

Leakage: where secrets fall out of the flow

RFC 9700 states that clients MUST NOT pass access tokens in a URI query parameter in the manner described in Section 2.3 of RFC 6750. Query strings are copied into server logs, proxy logs, browser history, and analytics pipelines, none of which are designed to hold credentials. The Authorization header is the only carriage you should be building on.

The Referer header is the second channel, and it is subtler because nobody writes the leak deliberately. RFC 9700 identifies it as a way the authorization request or response URI can be disclosed — from the authorization server's own pages or from the client's. That is why the RFC advises the authorization endpoint and the page rendered from the authorization response SHOULD NOT include third-party resources or links to external sites. A tag manager on your OAuth callback page is a code exfiltration channel with a vendor invoice attached.

Third is clickjacking of the consent screen: a malicious site loads the target authorization page in a transparent iframe positioned over decoy buttons, so the user grants consent while believing they clicked something else. The consent screen is a UI security control, and like any UI control it is only as good as the guarantee that the user sees what they are approving.

Replay, and the honest limits of rotation

Authorization codes are single use by construction. RFC 6749 says the client MUST NOT use a code more than once, recommends a maximum lifetime of ten minutes, and requires the authorization server to deny a reused code and SHOULD revoke, where possible, all tokens previously issued from it. That last clause is the interesting one: reuse is treated as evidence of compromise, not as a client bug to be forgiven. Build your retry logic accordingly — a naive retry loop around the token request will burn the grant.

Refresh tokens are the long-lived asset, so RFC 9700 requires that refresh tokens for public clients MUST either be sender-constrained or use refresh token rotation. Section 4.14.2 presents rotation as a detection and correction mechanism for refresh token theft, not a prevention mechanism. Nothing about rotation stops a stolen token from being redeemed once. What rotation buys you is that the legitimate client and the thief now hold divergent state, and one of them will present a rotated-out token.

Rotation without reuse detection is bookkeeping, not security. RFC 9700 §4.14.2, read honestly

Refresh request

POST /token HTTP/1.1
Host: server.example.com
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&refresh_token=tGzv3JOkF0XG5Qx2TlKWIA&scope=read

Response — the refresh token must be a new one

{
  "access_token": "2YotnFZFEjr1zCsicMWpAA",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "XkP2rQ9vLb7ZmT4dHs1Nuw"   // not tGzv3JOk...
}

Then the part that is easy to skip: presentation of tGzv3JOkF0XG5Qx2TlKWIA after this response is evidence of theft, and the server must treat it that way — revoke the whole grant, not just reject the request. A deployment that rotates and then quietly issues a fresh token to whoever shows up with a stale one has implemented the ceremony and none of the mechanism.

Where tokens live, by client type

A confidential client running on a web server is the easy case, and it is easy for a structural reason: the client credentials and the issued tokens are stored on the server and are never exposed to the user agent. There is no browser storage question because there is nothing in the browser to store.

Native and mobile apps are governed by RFC 8252 (BCP 212), which requires that authorization requests be made through an external user-agent — normally the system browser — and not an embedded one. The reason is definitional: an embedded user-agent is hosted by the requesting app and shares its security domain, so the app can read cookie storage and inspect or modify page content. A webview turns "the user types their password into their identity provider" into "the user types their password into your app". The in-app browser tab is the endorsed middle ground: it renders inside your app but retains the browser's full security properties and authentication state. RFC 8252 defines three redirect mechanisms — private-use URI scheme, claimed https scheme, and loopback interface. Private-use schemes are the weak one, because multiple installed apps can register the same scheme and it is indeterminate which receives the code; PKCE is what keeps that survivable.

Browser apps are the hard case, and the reference is "OAuth 2.0 for Browser-Based Applications", an IETF Internet-Draft with intended status Best Current Practice — as of this writing, revision -27, and not yet an RFC. It presents three architectural patterns in decreasing order of security: Backend-For-Frontend, Token-Mediating Backend, and Browser-Based OAuth Client. In the BFF pattern the browser app delegates all OAuth responsibilities to a backend and routes every resource request through it, so tokens never reach JavaScript at all.

Trap

Short access token lifetimes and refresh token rotation are ineffective against an active XSS attacker. Script running in your page simply starts its own flow and obtains a fresh, independent set of tokens. Rotation shortens the life of what was stolen; it does nothing about the attacker's ability to steal again. Treat in-page token custody as an architecture decision, not a storage decision.

Sender-constrained tokens

A bearer token is worth whatever it costs to steal it; sender-constraining changes that economics by making possession insufficient. RFC 9449 defines DPoP, an application-layer mechanism that binds access and refresh tokens to a client-held public key proven on every request, independently of the client authentication method. RFC 8705 defines mutual-TLS client authentication and certificate-bound access tokens, binding a token to the client's X.509 certificate — carried as the x5t#S256 confirmation method inside cnf — so the protected resource can verify the presenter is the client the token was issued to.

Key idea

The selection rule is deployment-shaped, not security-shaped. mTLS suits server-to-server and regulated back-end deployments that already run a PKI. DPoP suits public clients, browser apps, and mobile apps that cannot present a client certificate — RFC 9449 names the dynamically downloaded single-page application explicitly. Choose on whether you can issue and rotate certificates, because both mechanisms defeat plain token theft.

DPoP's honest limit in the browser: it does not stop an attacker who is present at the moment of token issuance, because that attacker can bind fresh tokens to their own key pair. DPoP raises the cost of exfiltrating a token to somewhere else; it does not evict an attacker who is already executing in your page. That is a different failure domain, and the answer to it is the BFF, not a signing key.

Scope, audience, and keeping parameters off the front channel

Scope is the mechanism for limiting an application's access to a user's account — requested by the client, granted by the resource owner. Least privilege here is not a slogan; it is the thing that bounds the blast radius of every failure above. When redirect validation fails and PKCE saves you, the scope on the token is what would have been lost.

Coarse scopes also quietly break audience restriction. RFC 8707 resource indicators let a client name the resource it intends to use the token at, and say the authorization server SHOULD audience-restrict issued access tokens to those resources, expressed as the aud claim in a JWT or in the introspection response. RFC 9068 goes further and requires every individual scope string in a JWT access token's scope claim to have meaning for the resources named in aud. Without resource indicators, a token minted for one API is replayable at every other API that trusts the same issuer — you have an authorization boundary on paper and a shared bearer credential in practice.

If you want to shrink the front channel entirely, RFC 9126 defines pushed authorization requests: the client pushes the authorization request parameters to the authorization server over a back channel and receives a request_uri to reference them at the authorization endpoint. Nothing sensitive travels in the browser's address bar, so the Referer and history channels have nothing to leak. It costs one extra round trip and requires server support; where you have both, it is the cheapest structural reduction of attack surface on this list.

What to take away

Audit against this list. Every item is a yes or no, and a "mostly" is a no.

  • Your policy document cites RFC 9700 (BCP 240, January 2025), not a security-topics draft revision — and quotes MUST/RECOMMENDED at the strength the RFC uses.
  • The authorization server compares the full redirect URI by exact string match, with a loopback-port exception only for native apps.
  • Someone has audited the client's entire domain for open redirectors, not just its OAuth routes.
  • Public clients use PKCE. If any client drops state, it did so after confirming the AS actually supports PKCE.
  • state is one-time-use and bound to the user agent session — not merely random.
  • If the client talks to more than one authorization server, it compares iss against the expected issuer and rejects on mismatch.
  • No access token appears in a URI query parameter, and the authorization and redirect pages carry no third-party resources or external links.
  • Refresh token rotation is paired with reuse detection that revokes the grant; code reuse revokes the tokens issued from that code.
  • Native apps use the system browser or an in-app browser tab; no embedded webview anywhere in the authorization path.
  • Browser apps have chosen a pattern deliberately — BFF where possible — and nobody is claiming short token lifetimes as an XSS defence.
  • Sender-constraining is chosen on deployment: mTLS where PKI exists, DPoP where certificates are impossible.
  • Scopes are narrow enough that aud means something, and resource indicators are used where more than one resource server trusts the issuer.
