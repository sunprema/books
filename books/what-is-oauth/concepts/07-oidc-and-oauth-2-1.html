07 The layer above, the version ahead

OpenID Connect and the Road to OAuth 2.1

Chapter 1 drew a line between two questions and promised to come back to the second one. This chapter pays that off. First: OpenID Connect, the identity layer that sits on top of OAuth 2.0 and gives a client something it can actually verify about who signed in. Second: OAuth 2.1, which is not a new protocol but a consolidation of the one you already know — and, as of today, still a draft.

OAuth answers one question; OIDC answers the other

Stand at the whiteboard and draw two boxes. The left box is the question OAuth 2.0 was designed to answer: may this client do this thing, on this resource, on whose behalf? Everything in the first six chapters serves that box — scopes, consent, the authorization code, the access token presented to an API. The right box is a different question: who is the end user sitting behind this client, and did they just authenticate? OAuth 2.0 alone does not answer it. It conveys authorization. It has no artifact that says, in a form the client can check, that a human proved who they were at a particular moment.

OpenID Connect 1.0 fills the right box. It is a simple identity layer built on top of OAuth 2.0, and the word layer is doing real work: OIDC lets a Relying Party — the OIDC name for the client — verify an end user's identity by relying on an authentication performed by an OpenID Provider, and its authentication flows are defined in terms of OAuth 2.0 authorization flows. It is not a competing protocol, not a fork, and not a replacement. It is the same redirect, the same code, the same token endpoint, with one extra scope value, one extra request parameter, and one extra token in the response.

That framing matters because the shortcut is genuinely tempting. You already have an access token in hand at the end of chapter 4. It came back from a provider you trust, over TLS, after the user visibly clicked "allow". Why not call that a login? Because of what the artifact is and who it is addressed to. Weigh it on three axes. Verifiability: only the ID Token carries a verifiable authentication event, and only when its signature, iss, aud, exp and nonce are all validated; an access token, opaque or not, carries no such assertion for the client. Addressing: the access token is addressed to a resource server, not to you. Cost: adding openid to a scope list and validating a JWT is a morning of work, not a quarter. The recommendation is not close. Use OIDC rather than inferring identity from an access token.

Key idea

OIDC adds one new token type to OAuth 2.0 — the id_token — and defines its authentication flows in terms of OAuth's authorization flows. Learning OIDC after OAuth is learning a delta, not a second protocol.

The ID Token: a statement about an authentication event

The id_token is a JSON Web Token carrying claims about the authentication of the end user, plus whatever other claims the Relying Party asked for. Two of those claims are what scope it to a single client: aud, the audience, and nonce, a value you generate and send in the authorization request and get back unmodified inside the token. The nonce associates a client session with an ID Token and mitigates replay; OIDC requires it to have enough entropy that it cannot be guessed. Between them, aud and nonce answer "was this token minted for me?" and "was it minted for this sign-in attempt of mine?"

OIDC authentication request (line-wrapped)

GET /authorize?response_type=code&client_id=s6BhdRkqt3
    &redirect_uri=https%3A%2F%2Fclient.example.org%2Fcb
    &scope=openid%20profile&state=af0ifjsldkj
    &nonce=n-0S6_WzA2Mj
    &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
    &code_challenge_method=S256 HTTP/1.1
Host: server.example.com

Read that request next to the one in chapter 4 and the delta is two parameters. Everything else — the code response type, state, the PKCE challenge — is the authorization code flow you already build. The code comes back to the redirect URI, you exchange it at the token endpoint with your verifier, and the token response now carries an id_token beside the access token.

Decoded ID Token payload

{
  "iss": "https://server.example.com",
  "sub": "248289761001",
  "aud": "s6BhdRkqt3",
  "exp": 1311281970,
  "iat": 1311280970,
  "nonce": "n-0S6_WzA2Mj",
  "at_hash": "77QmUPtjPfzWtF2AnpK9RQ"
}

Receiving that is not the same as accepting it. The client is the validating party here — not the API, not a gateway — and the checks are the whole point of the token. Reject the ID Token if aud does not list this client as a valid audience, and reject it too if it contains additional audiences the client does not trust. Check iss: it is a case-sensitive https URL with a scheme, host, and optional port and path, and no query or fragment component, so string comparison is the correct comparison. Check that the current time is before exp. Check that nonce is the one you generated for this session. Skipping any of these turns a signed assertion back into an unverified blob of JSON.

The last claim in that payload is the seam between the two boxes. at_hash is the base64url encoding of the left-most half of the hash of the ASCII access_token value, using the hash algorithm implied by the ID Token's JOSE alg header. It binds the identity assertion to the specific access token delivered alongside it, so a client that checks it can tell that the two artifacts arrived as a matched pair rather than being stitched together by something in the middle.

In the spec

OpenID Connect Core 1.0: the exp claim marks the time on or after which the ID Token MUST NOT be accepted, and the current time MUST be before it. The client MUST reject a token that does not list it as a valid audience, or that carries additional audiences it does not trust.

The openid scope is the switch

There is no separate OIDC endpoint to call and no separate protocol to negotiate. The openid scope value is what turns an OAuth 2.0 authorization request into an OpenID Connect authentication request. Include it and you are asking for an authentication event; leave it out and you have made a plain authorization request, and a plain authorization request gets a plain OAuth response.

Trap

"The provider isn't returning an ID token." Nine times in ten the scope list says profile email and not openid profile email. Nothing is broken; you asked an authorization question and got an authorization answer. Check the outgoing scope parameter before you open a support ticket.

UserInfo, discovery, and the exact-match rule

The ID Token tells you an authentication happened and who it was about. For claims beyond that, OIDC defines the UserInfo endpoint, and its design is a small lesson in layering: UserInfo is an ordinary OAuth 2.0 protected resource. You present an access token; it returns claims about the authenticated end user. Its URL MUST use the https scheme. Nothing about calling it is special — it is chapter 3's resource-server story with a well-known response shape, which is exactly why it does not need new machinery.

Discovery follows the same instinct. A provider supporting OIDC Discovery MUST publish a JSON document at the Issuer concatenated with /.well-known/openid-configuration, served as 200 OK with content type application/json. Note the shape of that URL: the well-known path is suffixed to the issuer rather than pinned at the host root, specifically so a single host can serve multiple issuers in multi-tenant hosting.

Check the issuer before you trust anything else

curl -s https://accounts.example.com/.well-known/openid-configuration | jq .issuer

That one-liner is the check worth building into your integration tests. To prevent impersonation, a Relying Party MUST ensure that the Issuer URL used for the configuration request exactly matches the issuer claim in the returned metadata, and that both exactly match the iss claim in ID Tokens from that provider. Three strings, one comparison, no normalization games. If they diverge, you are pointing at something that is not the issuer it claims to be.

Chapter 3 covered the parallel arrangement on the plain-OAuth side: RFC 8414 authorization server metadata, the same idea in a different document, discovered separately. Two metadata documents that look alike is a mild annoyance rather than a design flaw — they were standardized by different bodies for different layers. What matters operationally is knowing which one your library is fetching, because a provider can publish one, the other, or both.

Two mirror-image category errors

Almost every identity bug I have seen in an OAuth codebase is one of two mistakes, and they are reflections of each other. The first is using an access token as proof of authentication: the client receives a token, treats its arrival as a successful login, and creates a session. The second is sending an ID Token to an API as if it were an access token: the API accepts a JWT, sees a signature it can verify, and authorizes the call. Both fail for the same underlying reason — the artifact was addressed to somebody else.

OAuth 2.1: consolidation, not reinvention

Now the version ahead, and a point of accuracy first, because this is where write-ups go wrong. As of 2026-07-27, OAuth 2.1 is still an Internet-Draft and has not been published as an RFC. The current revision is draft-ietf-oauth-v2-1-15, issued around 2 March 2026, with an expiry of 3 September 2026 and an intended status of Standards Track. Cite it as a draft. Design to it, argue for it in review, ship it — but do not tell a colleague or an auditor that it is a standard, because it is not one yet.

What it is, is a consolidation. OAuth 2.1 folds the widely adopted OAuth 2.0 extensions and the Best Current Practice guidance into a single simplified core document rather than inventing new protocol, and it is scoped to replace and obsolete RFC 6749 (the core framework) and RFC 6750 (bearer token usage) once published. That is the whole strategic idea: one document a newcomer can read end to end, in which the safe path is the only path described.

Look down that middle column and the honest reaction should be a shrug. If you followed chapters 4 and 5 — authorization code with PKCE everywhere, no implicit, no password grant, exact redirect URI registration, tokens in headers rather than URLs — you have already been writing OAuth 2.1. That is by design. The draft is not asking the ecosystem to migrate; it is asking the specification to catch up with what careful implementers already do. The practical consequence for a team is smaller than the version number suggests: mostly it removes the argument, because "the core spec still permits it" stops being a defence of the implicit grant.

Where this is heading

Three threads are worth watching, and it is worth being precise about which are settled. The first is token exchange. RFC 8693 — a published RFC — defines OAuth 2.0 Token Exchange as an HTTP and JSON based security token service, using the grant type urn:ietf:params:oauth:grant-type:token-exchange. Its most useful contribution is conceptual: it distinguishes impersonation, where the acting party becomes indistinguishable from the subject, from delegation, where the acting party keeps its own identity while acting on the subject's behalf. Once a request crosses three services, that distinction is the thing your audit log lives or dies on.

The second is crossing trust boundaries. draft-ietf-oauth-identity-chaining, "OAuth Identity and Authorization Chaining Across Domains", defines a mechanism to preserve identity and authorization information across trust domains. As of today it is at revision 12, Standards Track, and not yet an RFC. Alongside it, RFC 9728 — published — defines OAuth 2.0 Protected Resource Metadata, a metadata format a client or authorization server can use to learn how to interact with a protected resource, including the scopes it supports and how to present a token to it. That is the missing third document next to the two discovery formats above: metadata for the resource, not just for the issuer.

The third is authorization for AI agents, which is where these pieces are being assembled first. The Model Context Protocol's authorization specification builds its model on OAuth 2.1, with a protected MCP server acting as an OAuth 2.1 resource server. It adopts RFC 9728, requiring MCP servers to publish protected resource metadata at /.well-known/oauth-protected-resource. It requires clients to implement PKCE and to verify PKCE support before proceeding, using the S256 code challenge method whenever technically capable, and to implement RFC 8707 resource indicators in both the authorization request and the token request. Read that list against this book's table of contents: it is chapters 3, 4 and 5, made mandatory.

Named anti-patterns

MCP requires servers to validate that presented tokens were issued specifically for them — that is the specification's defence against token passthrough, where a server forwards a client's token upstream or accepts one minted for somebody else. Its security considerations also describe confused-deputy attacks on proxy servers that use a static client ID with dynamic client registration and skip per-client consent before forwarding authorization requests.

Notice that none of that is new protocol. The agent story is being built out of audience-restricted tokens, resource indicators, PKCE and explicit consent — the same four ideas this book has been circling since chapter 2. The interesting problems are moving up the stack, into who is permitted to act for whom across how many hops, but the primitives underneath are the ones you now know.

What to take away

  • OIDC is a layer, not a rival: its authentication flows are defined in terms of OAuth's authorization flows, and the openid scope is the switch that turns one into the other.
  • The client validates the ID Token — signature, iss, aud, exp, nonce — or it has validated nothing. at_hash binds it to the access token it arrived with.
  • Never read identity out of an access token, and never send an ID Token to an API. Each artifact is addressed to exactly one party.
  • OAuth 2.1 is a consolidation of 2.0 plus its extensions and BCP guidance, currently draft-ietf-oauth-v2-1-15 and not an RFC. Follow chapters 4 and 5 and you are already compliant with it.
  • Closing note: if you re-read only three things from this book, make them the four roles and the redirect in chapter 2, the authorization code flow with PKCE in chapter 4, and the security practices in chapter 5. Everything here — token exchange, identity chaining, agent authorization — is a rearrangement of those three.
