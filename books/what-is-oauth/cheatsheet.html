Cheatsheet

The 30-second version, then the parameters, the errors, and the decisions. Print it, pin it, stop re-reading RFC 6749 at 2am.

The 30-second summary

An app sends you to the authorization server in your own browser. You log in there — never in the app — and approve a specific scope. The server redirects you back to the app with a short-lived, single-use code. The app trades that code for an access token over a direct back-channel call, then sends the token to the API as Authorization: Bearer …. The app never sees your password, and the grant can be revoked without changing it.

Parameters, by request

Authorization request → GET /authorize

response_type
REQUIRED. code.
client_id
REQUIRED.
redirect_uri
OPTIONAL in the spec; in practice always send it, and it must match a pre-registered value by exact string comparison.
scope
OPTIONAL. Space-separated. Least privilege.
state
RECOMMENDED by RFC 6749; treat as mandatory. One-time use, bound to the user-agent session.
code_challenge / code_challenge_method
PKCE. S256, never plain.
nonce
OpenID Connect only, alongside the openid scope.
resource
RFC 8707. Absolute URI, no fragment. Audience-restricts the token.

Token request → POST /token

grant_type
authorization_code · refresh_token · client_credentials · urn:ietf:params:oauth:grant-type:device_code
code
Single use. RFC 6749 RECOMMENDS a maximum lifetime of 10 minutes.
redirect_uri
Repeat it if it was in the authorization request — it is verified.
code_verifier
43–128 unreserved characters. The server recomputes the challenge from it.
client_id / client authentication
Confidential clients MUST authenticate.

Response: access_token, token_type, plus expires_in, refresh_token, scope where issued.

PKCE in one line

code_challenge = BASE64URL-ENCODE(SHA256(ASCII(code_verifier)))

32 random octets, base64url-encoded, gives a 43-character verifier (≥256 bits of entropy, as RFC 7636 recommends). Hash the ASCII bytes of the verifier string — not the octets you built it from. Strip = padding; map + → - and / → _.

RFC 7636 Appendix B — check your implementation against this

code_verifier  dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
code_challenge E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM

Security checklist

Before you ship (RFC 9700, BCP 240)

  • Redirect URIs compared by exact string matching — whole URI, not just origin. Loopback ports are the one carve-out.
  • PKCE: MUST for public clients, RECOMMENDED for confidential ones. OAuth 2.1 requires it for everyone.
  • state: one-time use, bound to the user agent. Only substitute PKCE for it once you have confirmed the AS supports PKCE.
  • Talking to more than one AS? Check iss (RFC 9207) and reject on mismatch. Parsing it and ignoring it is not a defence.
  • No access tokens in query strings. No open redirectors anywhere on your domain.
  • No third-party scripts or external links on the authorization or redirect landing page — Referer leaks.
  • Public-client refresh tokens: sender-constrained or rotated — and rotation only counts if reuse is detected and the family revoked.
  • Resource servers: validate signature, iss, exp, and aud. Pin the accepted alg.
  • Native apps: system browser, never an embedded webview (RFC 8252).
  • SPAs: prefer a Backend-For-Frontend. Short lifetimes and rotation do not stop an active XSS attacker.

Discovery & the two well-knowns

Start every integration here

Ask the provider what its endpoints are

curl -s https://accounts.example.com/.well-known/openid-configuration \
  | jq '{issuer, authorization_endpoint, token_endpoint, jwks_uri}'
  • /.well-known/oauth-authorization-server — RFC 8414, plain OAuth.
  • /.well-known/openid-configuration — OpenID Connect. Different document, same host.
  • /.well-known/oauth-protected-resource — RFC 9728, the resource server's own metadata.
  • The returned issuer MUST byte-match the URL you derived it from. If not, discard it.
  • Issuer has a path? The suffix goes before it: /.well-known/oauth-authorization-server/issuer1.
