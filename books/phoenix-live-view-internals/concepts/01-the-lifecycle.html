01 Where a LiveView actually lives

The Lifecycle: From HTTP to Living Process

Let's start with a question that trips up almost everyone new to LiveView: when you visit a LiveView page, is your browser talking to a controller, or to a websocket? The honest answer is both, in sequence — and the gap between those two answers is where most of LiveView's internals live. We're going to build the mental model one request at a time, the same way we'd trace a request through any system we didn't write: by watching what actually happens.

Two renders, one module

A LiveView module gets rendered twice for a single page visit, by two completely different transport mechanisms, and it doesn't know the difference unless it asks.

The first render happens the moment the browser makes its initial GET request. Phoenix's router dispatches it like any other HTTP request, through the ordinary plug pipeline — session, CSRF token, authentication plugs, all of it. At the end of that pipeline sits your LiveView, and Phoenix calls mount/3, then handle_params/3, then render/1, and ships the resulting HTML back as a perfectly normal HTTP response. At this point there is no persistent process, no websocket, nothing stateful at all. It's a request that started and finished, the same as any Phoenix controller action.

The second render happens moments later, once the page's JavaScript (LiveSocket) opens a websocket connection back to the server. Now Phoenix spawns a dedicated process for this specific browser tab, and that process runs mount/3 and handle_params/3 again — this time with a socket that is connected. It renders once more, diffs that render against what the disconnected render already put on the page, and sends only the differences down the wire. From this point on, the process stays alive for as long as the tab stays open, holding your application state in memory between one user interaction and the next.

Key idea

mount/3 runs twice on a fresh page load: once disconnected (HTTP, no process), once connected (websocket, a live process). Both runs execute the same code. Phoenix.LiveView.connected?/1 is how a mount tells them apart — true only on the second pass.

That distinction matters in practice more than it sounds like it should. Imagine subscribing to a PubSub topic in mount/3 so the LiveView gets live updates. Do that unconditionally, and the disconnected render subscribes too — a process that is about to die anyway, having never been meant to receive messages at all. The idiom is to gate anything with a side effect behind connected?/1:

lib/my_app_web/live/dashboard_live.ex

def mount(_params, _session, socket) do
  if connected?(socket) do
    Phoenix.PubSub.subscribe(MyApp.PubSub, "dashboard:updates")
  end

  {:ok, assign(socket, :count, MyApp.Metrics.current_count())}
end

Notice that the data fetch — current_count/0 — runs on both passes. That's deliberate: the disconnected render is what search engines and slow connections actually see, so it should show real content, not a blank shell waiting for JavaScript. Only subscriptions, timers, and anything else that would leak or duplicate belong behind the guard.

A LiveView is a process, not a template

Here's the reframe that makes the rest of this book click: stop thinking of a LiveView as a template that happens to update itself, and start thinking of it as a BEAM process that happens to render HTML. Once the websocket connects, your LiveView module is running inside a process that behaves like a GenServer — it has its own mailbox, its own isolated heap, and its own supervised lifecycle, riding on top of a Phoenix Channel for the actual wire-transport.

This is not an implementation detail you can safely ignore. It's the reason LiveView gets fault isolation for free: if one visitor's LiveView process crashes — a bad pattern match, an unhandled exit from a linked task — it takes down exactly one browser tab's worth of state. Every other connected user's process keeps running, untouched, because the BEAM's whole design point is that a crashing process cannot corrupt another process's memory. Compare that to a thread-per-request model backed by shared application state, where the blast radius of "something went wrong" is much harder to draw a boundary around.

Crashes and dropped connections

Because the connected LiveView is just a process, "the connection dropped" and "the process crashed" resolve to the same recovery path: the client-side LiveSocket notices the channel is gone, shows a (configurable) disconnected indicator, and attempts to reconnect. When it succeeds, the browser doesn't resume the old process — that process, and whatever was in its memory, is gone for good. Instead the whole handshake happens again from the top: mount/3, then handle_params/3, exactly as if the visitor had loaded the page for the first time.

In practice

This is why LiveView state should be treated as a cache of a durable source of truth, not the source of truth itself. If a counter only lives in socket.assigns and the process restarts, the counter resets. Fine for UI state like "which tab is open"; not fine for anything a user would be upset to lose — that belongs in the database, and mount/3 should reload it, not reinvent it.

That reconnection path is also a quiet security feature, which Chapter 10 leans on directly: because every reconnect re-runs mount/3's authorization checks from scratch, there is no window where a process keeps running with permissions the current session no longer has, as long as those checks read live data (the current user, their current role) instead of a value captured once and never revisited.

What we actually gained

So what did splitting the lifecycle into "stateless render, then live process" actually buy us? Three things worth naming explicitly, because the rest of this book assumes them:

  • A working page with no JavaScript. The disconnected render is real HTML, so the first paint is fast and crawlable, and a visitor on a flaky connection still sees content.
  • Per-visitor fault isolation. Each connected tab is its own supervised process; one crash affects one visitor.
  • A recovery model that's also a security model. A dropped connection doesn't leave a zombie process behind — it forces a full re-mount, re-running whatever authorization logic mount/3 contains.

Chapter 2 zooms into that first pass in detail — what the router actually wires up, and the precise contract of mount/3, handle_params/3, and render/1 as a trio.
