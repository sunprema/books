05 Three ways in, three ways out

Client Events, Server Messages, and Navigation

A LiveView process, like any BEAM process, spends most of its life waiting for a message and reacting to it. What makes it feel alive is that those messages come from two very different directions — a click in the browser, or a broadcast from some other part of your system — and LiveView gives each direction its own callback so the two never get confused with each other.

handle_event/3 — the client asking for something

Bindings like phx-click, phx-submit, and phx-change turn a DOM interaction into a message sent over the websocket, which arrives as a call to handle_event(event_name, payload, socket): 

<button phx-click="increment" phx-value-amount="5">+5</button>
def handle_event("increment", %{"amount" => amount}, socket) do
  {:noreply, update(socket, :count, &(&1 + String.to_integer(amount)))}
end

That payload map — here, %{"amount" => "5"} — is built entirely on the client from phx-value-* attributes and form input values. Chapter 10 spells out the consequence directly: nothing stops a browser's dev tools from sending handle_event("increment", %{"amount" => "999999999"}, socket) instead of clicking the button at all. The payload is exactly as trustworthy as any other client-submitted form field, no more.

handle_info/2 — a message from somewhere else in the BEAM

handle_info(message, socket) is the ordinary GenServer callback for "a message landed in my mailbox that didn't come through handle_call or handle_cast." For a LiveView, the most common source is a PubSub broadcast the process subscribed to back in mount/3 — Chapter 8 builds a whole feature around exactly this pattern — but it's just as much at home receiving a message from Process.send_after/3 for a recurring tick, or from a linked Task completing (though for that specific case, prefer the purpose-built start_async/3 from Chapter 6, which handles crashes more gracefully than a hand-rolled task and a raw handle_info/2). 

def handle_info({:metric_updated, value}, socket) do
  {:noreply, assign(socket, :current_value, value)}
end

handle_cast/2 exists too, for the rarer case of another process calling GenServer.cast/2 directly against the LiveView's pid — useful if some other part of your supervision tree already holds that pid and wants to push to it without going through PubSub at all.

Key idea

handle_event/3 answers "what did the person looking at this page just do." handle_info/2 answers "what happened somewhere else in the system that this page cares about." Keeping that distinction sharp is what makes a LiveView's message handlers readable at a glance months later.

Three ways to move, three different guarantees

LiveView has three distinct navigation functions, and reaching for the wrong one is a common source of "why did my socket reconnect when I didn't expect it to."

Navigation functions and what they actually do
FunctionProcessRe-runsUse for
push_patch(socket, to:) Same process, same mount handle_params/3 only Changing the URL within one LiveView — a tab, a filter, a page number
push_navigate(socket, to:) New process, same live_session mount/3 and handle_params/3 Moving to a different LiveView without a full page reload
redirect(socket, to:) Full page reload Everything, from an HTTP request Crossing a live_session boundary, or after a plain (non-live) action

push_patch/2 is the cheapest of the three by a wide margin — it never leaves the current process, so nothing in socket.assigns is lost, and the only work is a fresh handle_params/3 call plus a render. That makes it the right choice for anything that's really "the same page, different view of it": paginating a table, switching tabs, expanding a filter. push_navigate/2 spawns a genuinely new process, which is why it re-runs mount/3 — it's a fresh start, just one that skips the websocket teardown/rebuild that a full redirect/2 would cost.

push_event/3 — talking to client-side JavaScript

Everything so far has been server state driving server-rendered markup. push_event(socket, event, payload) is the escape hatch for when the server needs to trigger client-only behavior that has no markup representation — playing a sound, focusing an element, kicking off a CSS animation the diff wouldn't otherwise produce. It dispatches a "phx:" <> event browser event that a JS hook's handleEvent callback picks up — Chapter 9 covers hooks properly when uploads give us a concrete reason to write one.

What we actually gained

  • handle_event/3 handles what the client did; handle_info/2 handles what some other process reported — kept apart, a handler's origin is obvious from its name.
  • Event payloads are exactly as trustworthy as any other client input — validate them the same way you'd validate a form.
  • Reach for the cheapest navigation function that does the job: push_patch for same-view URL changes, push_navigate for a new LiveView without a full reload, redirect only when you must leave the socket behind.
  • Chapter 6 covers what happens when a handler needs to do real work — a slow API call, a report to generate — without blocking the process from answering anything else in the meantime.
