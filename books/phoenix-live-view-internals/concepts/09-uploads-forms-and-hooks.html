09 Where the server meets the browser directly

Uploads, Forms, and Browser Integration

Most of what we've built so far treats the browser as a rendering target for server-computed HTML. File uploads break that model on purpose: the file's bytes never touch the server as a normal handle_event/3 payload, because a multi-megabyte upload doesn't belong crammed into a websocket text frame the way a click payload does. LiveView solves this with a dedicated channel for binary data, wired through the same declarative style as everything else.

allow_upload/3 — declaring the contract up front

def mount(_params, _session, socket) do
  {:ok,
   socket
   |> assign(:uploaded_files, [])
   |> allow_upload(:avatar, accept: ~w(.jpg .jpeg .png), max_entries: 1, max_file_size: 5_000_000)}
end

allow_upload/3 registers an upload configuration — accepted extensions, how many files, a size ceiling — under a name (:avatar) that the template and later callbacks refer back to. That configuration populates @uploads.avatar, which a <.live_file_input> component renders as a file picker wired up with the right accept and multiple attributes automatically: 

<.form for={@form} phx-change="validate" phx-submit="save">
  <.live_file_input upload={@uploads.avatar} />
  <button type="submit">Upload</button>
</.form>

Both phx-change and phx-submit matter here, and for different reasons than an ordinary form. phx-change fires as the visitor selects a file — before any bytes are uploaded — triggering an automatic "validate" event that lets @uploads.avatar.entries report client-side validation errors (wrong extension, too large) immediately, with progress and error state managed for you. phx-submit is what actually starts the upload and, once every entry finishes, calls your "save" handler.

consume_uploaded_entries/3 — the one moment files exist

def handle_event("save", _params, socket) do
  paths =
    consume_uploaded_entries(socket, :avatar, fn %{path: path}, _entry ->
      dest = Path.join("priv/static/uploads", Path.basename(path))
      File.cp!(path, dest)
      {:ok, "/uploads/" <> Path.basename(dest)}
    end)

  {:noreply, update(socket, :uploaded_files, &(&1 ++ paths))}
end

consume_uploaded_entries/3 is deliberately the only place the uploaded file's temporary path is available — it hands your function a temp path per entry, and once the function returns, LiveView cleans that temp file up. This forces "do something durable with the file" (copy it to permanent storage, hand it to an upload service) to happen in one clear place, rather than leaving temp files hanging around for a later callback to maybe get to.

Trap, and Chapter 10's rule showing up again

Client-reported file metadata — the declared content type, the declared size before the bytes arrive — is exactly as untrustworthy as any other client input. LiveView enforces max_file_size as chunks actually arrive over the wire, not by trusting whatever the browser claims up front, which is why the check can't be bypassed by a doctored request. Whatever you do with the consumed file afterward — especially if you inspect its declared content type to decide how to handle it — deserves the same "never trust it, verify server-side" treatment.

Client hooks: when the browser needs to do something LiveView can't express

Uploads are a natural moment to reach for a JS client hook — Chapter 5 mentioned push_event/3 as the escape hatch for server-to-client instructions with no markup diff; hooks are the receiving end of that escape hatch, plus a way to go the other direction. A hook attaches to an element via phx-hook (which requires that element carry a unique DOM id) and implements a small set of lifecycle callbacks: 

// assets/js/hooks.js
const Hooks = {};

Hooks.DropZone = {
  mounted() {
    this.el.addEventListener("drop", (e) => {
      e.preventDefault();
      this.pushEvent("file_dropped", { count: e.dataTransfer.files.length });
    });
  },
  destroyed() { /* clean up anything mounted() started */ }
};

export default Hooks;
Client hook lifecycle callbacks
CallbackFires when
mountedThe element joins the DOM and its LiveView has finished mounting
beforeUpdateJust before the server patches this element — must stay synchronous
updatedJust after the server patches this element
destroyedThe element is removed — by a parent patch, or the LiveView unmounting
disconnectedThe parent LiveView's socket disconnects
reconnectedThe parent LiveView's socket reconnects (Chapter 1's recovery path)

Inside those callbacks, this.pushEvent(event, payload, callback) sends a message to the LiveView — landing in handle_event/3 exactly like a phx-click would — and this.handleEvent(event, callback) is the receiving end of a server-side push_event/3. Together they form a full round trip: server pushes an instruction the DOM alone can't express (play this sound, focus this element, initialize a third-party JS widget), and the hook can push back whatever that interaction produces.

Key idea

Reach for a hook only when something needs a real browser API a phx-* binding doesn't cover — drag-and-drop, clipboard access, a charting library, focus management. If a phx-click or phx-change binding already expresses what you need, a hook is solving a problem you don't have.

What we actually gained

  • allow_upload/3 declares the contract; phx-change validates as files are picked; phx-submit uploads and triggers your save handler.
  • consume_uploaded_entries/3 is the one place a temp file path is available — move it to durable storage there, or lose it.
  • Client-declared file metadata is untrusted input, same as any form field; LiveView enforces size limits from the actual bytes received, not the client's claims.
  • JS hooks bridge server state and browser-only APIs through pushEvent/handleEvent, reached for only when a phx-* binding genuinely can't express the need.
  • Chapter 10 closes the loop on every "untrusted input" aside threaded through this book, and adds the piece none of the earlier chapters covered: what a dropped connection means for the authorization checks Chapter 1 promised would re-run.
