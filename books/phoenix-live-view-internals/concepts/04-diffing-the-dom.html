04 Why LiveView feels reactive without a client framework

The Static/Dynamic Split and the Diff Engine

Here's the trick question: LiveView re-renders the whole template on every assign change — so why doesn't a chat app with a thousand messages on screen re-send a thousand messages' worth of HTML every time someone hits "send"? The answer is a compile-time transformation that happens to every HEEx template, and once we've seen it, "diffing" stops being magic and starts being a straightforward data structure.

What the compiler actually does

Take a template with one interpolation: 

<h1>{expand_title(@title)}</h1>

The HEEx compiler doesn't treat that as one string to regenerate on every render. It splits it into two separate parts at compile time: the static part — <h1> and </h1>, markup that can never change no matter what @title is — and the dynamic part — the result of calling expand_title(@title), the only piece that could possibly differ between renders.

On the very first render, both parts go to the client, because the client has nothing to compare against yet. On every render after that, LiveView checks whether @title changed. If it didn't, the dynamic part isn't even recomputed — not just "not sent," but never evaluated at all, because render/1 was never asked to run that branch of the template. If it did change, only the new dynamic value goes over the wire; the static markup, already sitting in the browser's DOM from the first render, is never resent.

Key idea

A LiveView diff is not "compute the new HTML, compute the old HTML, find the difference." It's "know in advance which parts of the template are static, and only ever compute or send the dynamic parts that changed." The diffing happens before render, not after.

Field-level tracking

This granularity goes deeper than "which template expression changed." LiveView tracks changes down to individual fields of a struct or map that's being read through @. If @user.name changes but @user.id doesn't, a template section that only reads @user.id is untouched — even though @user itself, as a whole value, is technically a new term. That's the payoff of reassigning through assign/3 that Chapter 3 flagged: the tracker needs the full old and new values to compute this field-level diff, and it only sees them when the reassignment goes through the sanctioned path.

What silently defeats change tracking

Because the optimization depends on the compiler being able to isolate a dynamic expression at compile time, anything that hides the real dependency from that expression breaks it. Three patterns do this routinely, and all three are things a Rails or Django habit will reach for without thinking twice:

1. Doing real work inside the template. 

## defeats tracking — runs on every render, changed or not
<p>Users online: {Accounts.count_online_users()}</p>

The compiler sees a function call with no assign dependency it can track, so it has no signal telling it "this hasn't changed, skip it." It re-evaluates count_online_users/0 — a database query — on every single render, whether or not the online count actually moved. The fix is to compute it in a callback and assign the result, so change tracking has an assign to key off: 

## in handle_info, on a timer or a presence_diff message
assign(socket, :online_count, Accounts.count_online_users())

2. Local variables computed in the template. 

## defeats tracking — `total` isn't a tracked assign
<% total = @subtotal + @tax %>
<p>Total: {total}</p>

A <% … %> local binding looks harmless, but it obscures which assigns the value actually depends on. Move the computation into a plain function and call it with the assigns it needs — {total(@subtotal, @tax)} — and the compiler can once again see through to @subtotal and @tax directly.

3. Generic map-mutation functions. Building an updated map with Map.put(socket.assigns, :count, n) instead of assign(socket, :count, n) updates the value, but skips the bookkeeping assign/3 does to mark :count as changed. The template will eventually show the right value on some future render that touches it for other reasons, but the specific optimization — "only send what changed, right when it changed" — is gone for that assignment.

Seeing it for real

In practice

Open your browser's network tab, filter to WS (websocket), and click something that changes one small piece of a busy page. A well-tracked template sends a frame with just that one changed value — a few dozen bytes. A frame that's suspiciously large for a small visible change is a sign some part of the template just lost its tracking, and is worth reaching for Phoenix.LiveView.Utils-adjacent debug helpers or simply re-reading the template for one of the three patterns above.

What we actually gained

  • HEEx compiles templates into static and dynamic parts at compile time — the diff strategy exists before a single render runs.
  • An unchanged assign means the dynamic expression that reads it is skipped entirely, not just "not sent" — it's not even recomputed.
  • Change tracking sees through @user.name to the field level, but only for values reassigned through assign/3.
  • Function calls in the template, local <% %> bindings, and generic map mutation all defeat it — compute in a callback, assign the result, read the assign in the template.
  • Chapter 5 is where those assigns start changing in response to something other than a page load: client events and server messages.
