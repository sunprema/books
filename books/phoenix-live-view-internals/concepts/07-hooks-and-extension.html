07 Cross-cutting behavior, without copy-paste

Hooks, on_mount, and Extension Points

Every LiveView we've written so far has kept its callbacks to itself. But real applications have a handful of things that dozens of LiveViews all need — "check the user is logged in," "log every event for telemetry," "close a menu when the URL changes." Copy-pasting that logic into every mount/3 is exactly the kind of repetition Elixir gives us tools to avoid, and LiveView's answer is a pair of server-side hook mechanisms, distinct from the client-side JS hooks Chapter 9 covers.

on_mount/1 — running before mount, everywhere

on_mount/1 lets a module inject logic that runs before a LiveView's own mount/3, wired up either per-LiveView or, more usefully, once for an entire live_session in the router:

lib/my_app_web/live/auth_hooks.ex

defmodule MyAppWeb.AuthHooks do
  import Phoenix.LiveView

  def on_mount(:require_authenticated, _params, session, socket) do
    case Accounts.get_user_by_session(session) do
      nil -> {:halt, redirect(socket, to: "/login")}
      user -> {:cont, assign(socket, :current_user, user)}
    end
  end
end
# router.ex
live_session :authenticated, on_mount: [{MyAppWeb.AuthHooks, :require_authenticated}] do
  live "/dashboard", DashboardLive
  live "/settings", SettingsLive
end

The return contract — {:cont, socket} to keep going, {:halt, socket} to stop — is the same shape every hook mechanism in this chapter uses, and it's worth internalizing once: cont means "this LiveView's own mount/3 should still run," halt means "don't even bother, I've already redirected/rejected." Authentication is the canonical use, but the same mechanism is just as at home assigning a shared value every LiveView in a session wants — feature flags, the current locale, an analytics session id.

attach_hook/4 — intercepting a LiveView's own callbacks

Where on_mount/1 only runs once, at the very start, attach_hook/4 can intercept every subsequent call to handle_params/3, handle_event/3, handle_info/2, handle_async/3, or the render-adjacent after_render stage — called inside mount/3 (or later), and typically for something narrower and more local than a whole authentication scheme: 

def mount(_params, _session, socket) do
  {:ok,
   attach_hook(socket, :close_menu_on_nav, :handle_params, fn _params, _uri, socket ->
     {:cont, assign(socket, :menu_open?, false)}
   end)}
end

That hook fires on every handle_params/3 call for this one LiveView — closing a nav menu on every URL change — without the LiveView's own handle_params/3 clause needing to know the menu exists at all. A hook attached to :handle_event can also {:halt, reply, socket}, short-circuiting before the LiveView's own handle_event/3 clauses ever see the event — the shape a request-logging or rate-limiting hook would use.

Key idea

on_mount/1 is for "run this once, before everything else, for every LiveView that opts in" — wired in the router. attach_hook/4 is for "intercept this specific callback, on this specific LiveView, every time it fires" — wired inside the LiveView itself.

Hooks versus LiveComponents

It's tempting to reach for a Phoenix.LiveComponent any time markup gets reused, but a LiveComponent is solving a different problem than a hook is. A LiveComponent bundles state and event handling into a reusable, stateful unit — its own mount/1, update/2, render/1, and handle_event/3 — but it does not get its own process. It runs inside the parent LiveView's process, sharing memory with it; only the assigns are scoped separately.

Four ways to reuse behavior, and what each one actually gives you
MechanismHas state?Own process?Reach for it when…
Function component No No Reusing markup with no event handling of its own — the default choice
LiveComponent Yes No (parent's process) The reused piece needs its own handle_event/3 and internal state
attach_hook/4 Reads/writes host socket No Intercepting one callback on one LiveView, without owning any markup
on_mount/1 Reads/writes host socket No The same setup logic needs to run for every LiveView in a session

The official guidance is blunt about the first row: prefer a function component whenever it's enough, precisely because it's the simplest abstraction with the smallest surface area. Reach for a LiveComponent specifically when a piece of UI needs to encapsulate both its own event handling and its own state — a self-contained autocomplete widget with its own open/closed state and its own keystroke handling is a good fit; a card that just displays a passed-in struct is not, and should stay a function component.

Trap

Because a LiveComponent shares its parent's process, a bug inside one doesn't get the fault isolation Chapter 1 described for a LiveView itself — an unhandled crash in a LiveComponent takes down the whole parent LiveView's process, menu bar and all. That's one more reason to reach for the plainest mechanism that solves the problem: less code running inside the one process means less that can bring the whole page down with it.

What we actually gained

  • on_mount/1 centralizes once-per-connection setup — authentication first among equals — across every LiveView that opts in via live_session.
  • attach_hook/4 intercepts a specific callback on a specific LiveView, useful for behavior that's local rather than application-wide.
  • Both share the same {:cont, socket} / {:halt, socket} contract — learn it once.
  • A LiveComponent is for state and event handling that deserves its own encapsulated unit; it still runs inside the parent's process, so it doesn't buy the fault isolation a separate LiveView would.
  • Chapter 8 turns from single-process concerns to multi-process ones: how LiveViews talk to each other, and to the rest of your application, via PubSub and streams.
