06 Keeping the process responsive

Async Work: Tasks, Results, and Failure

A LiveView process handles one message at a time — that's just what a GenServer-shaped mailbox means. So what happens if handle_event/3 needs to call a slow external API? If it does that inline, the process can't respond to anything else — not a click, not a PubSub message — until that call returns. LiveView's async primitives exist to get real work off the main process without giving up the safety of "one process holds the state."

The problem with a naive Task.async

You could, of course, just spawn a raw Task and send yourself a message when it's done — and in fact that's close to what LiveView does under the hood. But hand-rolling it means hand-rolling the failure cases too: what happens if the task crashes? If the LiveView navigates away before the task finishes? If two clicks fire the same fetch before the first one lands? start_async/3 and assign_async/3 exist because those questions have the same right answer often enough to bake it in once.

assign_async/3 — the common case

For the shape "run this function, and I want the result in an assign when it's done, with loading/error states handled for me," assign_async/3 is the direct tool: 

def mount(%{"id" => id}, _session, socket) do
  {:ok,
   assign_async(socket, :report, fn ->
     {:ok, %{report: Reports.generate_slowly(id)}}
   end)}
end

The function runs in a linked task, only once the socket is connected — recall Chapter 1's disconnected/connected split; an async fetch during the disconnected render would just be wasted work for a process about to die. socket.assigns.report becomes a Phoenix.LiveView.AsyncResult struct that starts in a loading state and updates itself once the task resolves: 

<.async_result :let={report} assign={@report}>
  <:loading>Generating your report…</:loading>
  <:failed :let={_reason}>Something went wrong. Try again.</:failed>
  {report.title}
</.async_result>

The function you hand to assign_async/3 must return {:ok, assigns_map} or {:error, reason} — that's the whole contract, and the loading/success/failure branches in the template above map onto it directly, with no manual state juggling in your callbacks at all.

start_async/3 and handle_async/3 — when you want more control

Sometimes the result doesn't map cleanly onto "assign one thing when it's ready" — maybe it should trigger a flash message, or update two unrelated assigns, or kick off a second async task. That's what start_async/3 plus a handle_async/3 callback buys: the same crash-safe, connected-only, linked-task machinery, but you write the completion logic yourself instead of it being implied by the assign shape. 

def handle_event("generate", _params, socket) do
  {:noreply, start_async(socket, :report_gen, fn -> Reports.generate_slowly(socket.assigns.id) end)}
end

def handle_async(:report_gen, {:ok, report}, socket) do
  {:noreply, socket |> assign(:report, report) |> put_flash(:info, "Report ready")}
end

def handle_async(:report_gen, {:exit, reason}, socket) do
  {:noreply, put_flash(socket, :error, "Generation failed: #{inspect(reason)}")}
end

Notice the two handle_async/3 clauses: the task either finished with {:ok, result}, or it exited — crashed, timed out, whatever — and arrives as {:exit, reason}. Handling both explicitly is the whole point of reaching for this over a bare Task: there is no code path where a failed task silently vanishes and leaves the UI stuck on "loading" forever.

Key idea

assign_async/3 is start_async/3 + handle_async/3 with the completion logic pre-written for the single-assign case. Reach for the lower-level pair only when a result needs to do more than fill in one assign.

The pitfall: copying the whole socket into a task

Both functions run their closure in a separate process, which means whatever the closure captures gets copied across process boundaries — and it is easy to accidentally capture socket itself instead of just the field the task needs: 

## copies the ENTIRE socket — every assign, every internal field —
## into the task's process just to read one field out of it
start_async(socket, :fetch, fn -> Api.fetch(socket.assigns.user_id) end)

## copies exactly what's needed
user_id = socket.assigns.user_id
start_async(socket, :fetch, fn -> Api.fetch(user_id) end)

For a socket with a handful of small assigns this is a rounding error. For one holding a large dataset, a big embedded struct, or anything with a nested LiveComponent tree, the copy is real work and real memory — bind the specific values you need to local variables before the closure, the same discipline as passing arguments to any other spawned process.

Cancellation and process linking

Because the async task is linked to the LiveView process, the relationship holds in both directions: if the LiveView process dies (a crash, or simply navigating away), the linked task is torn down with it — no orphaned work still running against a page nobody's looking at. Going the other way, cancel_async/3 lets a handler explicitly kill an in-flight task — the natural response to, say, a user typing a new search query before the previous search's results have come back.

What we actually gained

  • Async primitives keep the LiveView process free to answer other messages while real work happens on a linked task elsewhere.
  • assign_async/3 for the common "fill one assign, get loading/failed states for free" case; start_async/3 + handle_async/3 when completion needs to do more.
  • Both handle task failure as a first-class outcome — there's no silent "stuck loading forever" path.
  • Capture only what a task's closure needs, not the whole socket, to avoid copying more than necessary across the process boundary.
  • Chapter 7 turns to a different extension point — hooks and on_mount — for behavior that needs to run across many LiveViews, not just inside one.
