10 The rule that was underneath every chapter so far

Security, Authorization, and Reconnection

Look back over this book and a pattern repeats: Chapter 2's path params, Chapter 5's event payloads, Chapter 9's upload metadata — every one of them got a callout warning that the value in question came from the client and couldn't be trusted at face value. That wasn't nine separate warnings. It's one rule, stated once properly here: anything that crosses from the browser to the server is untrusted, full stop, and LiveView's persistent connection changes exactly nothing about that.

Two authentication checkpoints for one connection

Recall Chapter 1's two-render lifecycle: a LiveView starts as a plain HTTP request, then upgrades to a websocket. Both of those legs need session validation, and they need it independently — the plug pipeline validates the session for the disconnected HTTP render, and mount/3 validates it again for the connected websocket render. Skipping the second because "the plug pipeline already checked" misses that the websocket handshake is a genuinely separate connection, subject to its own hijacking and replay concerns; LiveView doesn't inherit trust from the HTTP leg automatically.

In practice this means authentication (who is this?) happens the same way it would for a regular controller — session tokens, checked by plugs shared with the rest of the app — while authorization (is this specific user allowed to do this specific thing?) shows up at three separate points inside the LiveView itself, and needs checking at all three:

Where authorization belongs, and what each checkpoint answers
CheckpointQuestion it answers
mount/3Is this user allowed to open this page at all?
handle_params/3Is this user allowed to navigate to this specific URL/params — e.g., someone else's record id?
handle_event/3Is this user allowed to perform this specific action — e.g., delete this post?
 
def handle_event("delete_post", %{"id" => id}, socket) do
  post = Blog.get_post!(id)

  if Blog.can_delete?(socket.assigns.current_user, post) do
    Blog.delete_post!(post)
    {:noreply, put_flash(socket, :info, "Post deleted")}
  else
    {:noreply, put_flash(socket, :error, "Not allowed")}
  end
end

Notice that the check passes socket.assigns.current_user — something the server put there itself, back in mount/3, from a validated session — never anything read out of the event payload. The id came from the client and is only trustworthy as "a string the client sent"; the user making the request is only trustworthy because it was resolved server-side and never re-derived from anything the client claims about itself.

Key idea

A disabled button, a hidden menu item, a client-side route guard — none of these are authorization. They're UI polish that a legitimate user experiences as guidance and an attacker simply ignores, by hand-crafting a handle_event payload the real UI would never send. The only checks that count are the ones running in your Elixir code, against server-held data.

Disconnecting a live session on logout

A LiveView's persistent connection creates a wrinkle a stateless controller never had to think about: a visitor can log out in one browser tab while an already-connected LiveView process, in another tab, keeps right on running with the old session's assigns still resident in memory — nothing about closing an HTTP session automatically tears down a live process that was already spawned from it. Phoenix's answer is live_socket_id: a per-session identifier your logout flow can broadcast a disconnect against, forcing every LiveView tied to that session to drop and reconnect — which, per Chapter 1, means running mount/3's authorization checks again from a clean slate. 

## on login, tag the session so it can be targeted later
conn
|> put_session(:live_socket_id, "users_socket:#{user.id}")

## on logout, force every LiveView tied to that id to disconnect
MyAppWeb.Endpoint.broadcast("users_socket:#{user.id}", "disconnect", %{})

Without this, "log out" only ever meant "the next plain HTTP request will be treated as logged out" — an already-open LiveView tab would keep displaying (and acting on) data as the old user until the visitor manually reloaded it.

Reconnection, revisited

This closes a loop Chapter 1 opened but didn't fully justify. Every reconnect — whether from a network blip, a crash, or the forced disconnect above — re-runs mount/3 and handle_params/3 from scratch, against a fresh session lookup. There is no code path where a LiveView process keeps running indefinitely on a permission decision made once, minutes or hours earlier, and never revisited. As long as your authorization checks read live data — the current user record, its current role — rather than a value captured once at mount and trusted forever after, every reconnect is a fresh chance for those checks to catch a permission that has since changed.

In practice

Test this directly: open a page that depends on a role, then revoke that role from another session while the tab stays open. Nothing changes immediately — the process is still running with whatever it assigned at mount. Force a reconnect (toggle the network tab's offline switch off and on, or kill and restart the app in dev) and watch mount/3's authorization check catch it. That gap between "permission revoked" and "next reconnect" is the honest security boundary a long-lived connection buys you — know its size for your application, and use live_socket_id broadcasts for the cases where it needs to be zero.

What we actually gained — and what this book was really about

  • Authentication and authorization are separate concerns: sessions are validated on both the HTTP and websocket legs; authorization is checked independently at mount/3, handle_params/3, and every handle_event/3.
  • Nothing from the client — params, event payloads, upload metadata — is trustworthy until server code says so, no matter how the UI constrained what a well-behaved client would send.
  • live_socket_id broadcasts close the gap between "session ended" and "the already-open tab notices."
  • Every reconnect is a full re-mount, which means it's also a full re-check of whatever mount/3 validates — as long as those checks read current, not cached, permission data.

Ten chapters ago we asked whether a LiveView page was a controller or a websocket. The answer we've built since is more precise than "both": a LiveView is a supervised BEAM process that happens to speak HTML on one connection and receive typed messages on another — one process, one mailbox, one set of assigns, reacting the same way whether the message came from a click, a broadcast, an async task, or a fresh reconnect. Once that model is load-bearing in your head, the rest of the API — every function this book named — reads less like a framework's magic and more like the obvious tool for the job it names.
