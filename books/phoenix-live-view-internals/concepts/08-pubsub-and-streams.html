08 One process's news is another's handle_info

PubSub, Streams, and Cross-Process Updates

Chapter 1 leaned hard on isolation: one LiveView process per connected browser tab, crash-isolated from every other. Taken alone, that sounds like it should make a live-updating dashboard impossible — if every visitor's process is sealed off from every other, how does one person's action show up on another person's screen? The answer is a broadcast mechanism that doesn't break the isolation, it just gives every interested process the same message at the same time.

Phoenix.PubSub: a topic, a broadcast, a mailbox

Phoenix.PubSub is a topic-based publish/subscribe system built into every Phoenix app. A process subscribes to a topic string; any process (LiveView or otherwise) that broadcasts to that topic gets the message delivered to every subscriber's mailbox — which, for a LiveView, means it shows up in handle_info/2, exactly as Chapter 5 described. 

## subscribe once connected (Chapter 1's connected?/1 guard matters here too)
def mount(_params, _session, socket) do
  if connected?(socket), do: Phoenix.PubSub.subscribe(MyApp.PubSub, "orders:new")
  {:ok, assign(socket, :orders, Orders.recent())}
end

## broadcast from anywhere — a context function, a background job, another LiveView
def create_order(attrs) do
  {:ok, order} = Orders.insert(attrs)
  Phoenix.PubSub.broadcast(MyApp.PubSub, "orders:new", {:order_created, order})
  {:ok, order}
end

## every subscribed LiveView receives this
def handle_info({:order_created, order}, socket) do
  {:noreply, stream_insert(socket, :orders, order, at: 0)}
end

Notice what didn't happen: the code that creates an order has no idea how many LiveViews are watching, or whether any are. It broadcasts once to a topic; PubSub fans that single message out to every current subscriber's mailbox. Add a hundred more people watching the same dashboard, and the broadcasting code doesn't change at all — only the number of processes receiving the fan-out grows.

Key idea

PubSub doesn't compromise per-process isolation — it's built on top of it. Every subscriber gets its own copy of the message and reacts on its own terms, in its own process, at its own pace. A slow or crashed subscriber never blocks the broadcaster or any other subscriber.

Streams: collections the server doesn't hold

That last example used stream_insert/4 rather than assign/3, and this is where Chapter 3's "temporary assigns aren't always enough" gets resolved. A live order dashboard that stays open for hours can receive thousands of :order_created broadcasts. Even with temporary assigns resetting after each render, every one of those broadcasts still goes through a full assign-and-diff cycle keyed to a growing (or, if you cap it, awkwardly truncated) list.

stream(socket, :orders, initial_orders) takes a different approach entirely: the server tells the client to render an initial set of items, each with a stable DOM id, and never holds the full collection in socket.assigns again. From then on, stream_insert/4, stream_delete/3, and stream_delete_by_dom_id/3 send small, targeted instructions — "insert this one item at this position," "remove the item with this id" — and the browser's DOM becomes the authoritative record of what's currently shown. The server's job shrinks to "tell the client what changed," never "remember the whole list so I can re-render it." 

<ul id="orders" phx-update="stream">
  <li :for={{dom_id, order} <- @streams.orders} id={dom_id}>
    {order.customer_name} — {order.total}
  </li>
</ul>

That phx-update="stream" attribute is what tells the client-side runtime to manage this container's children by DOM id rather than by re-rendering the whole list on every patch — the client-side half of the same "the collection lives in the DOM, not the process" contract.

Trap

Because a stream isn't held server-side, you can't read socket.assigns.streams.orders back out as a list to, say, count how many orders are showing or search through them in a later callback — that data simply isn't there anymore after the initial render. If a LiveView needs to both stream a collection for display and reason about its contents elsewhere, keep a separate, smaller assign for whatever summary you actually need (a count, a total) rather than trying to derive it from the stream.

What we actually gained

  • PubSub fans one broadcast out to every subscribed process's own mailbox, arriving as an ordinary handle_info/2 — it doesn't reach into any process's state directly.
  • Subscriber isolation from Chapter 1 holds: a slow or crashed subscriber never blocks the broadcast or any other subscriber.
  • Streams move a collection's authoritative copy out of socket.assigns and into the client DOM, keyed by stable id — the right tool once temporary assigns' per-render reset isn't enough on its own.
  • Chapter 9 turns to input flowing the other way — forms and file uploads — and the client-side JS hooks that bridge server state to browser-only APIs.
