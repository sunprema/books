02 The backbone trio

Router, Mount, and the Initial Render

Every LiveView page, no matter how simple or elaborate, is assembled by exactly three callbacks running in a fixed order: mount/3, then handle_params/3, then render/1. Get comfortable with what each one is for — not just what it does — and a surprising amount of "why doesn't my LiveView update" confusion evaporates on its own.

Wiring it up in the router

A LiveView enters the picture through the router, with live/3 standing in for get/3:

lib/my_app_web/router.ex

scope "/", MyAppWeb do
  pipe_through :browser

  live "/dashboard", DashboardLive, :index
  live "/posts/:id/edit", PostLive, :edit
end

That :index / :edit atom is the live action. It's how one LiveView module serves several related routes — a list view and an edit view for the same resource, say — without duplicating mount/3. The live action shows up as socket.assigns.live_action, and handle_params/3 is exactly where you branch on it.

Routes that should share one persistent connection — so navigating between them feels instant instead of re-running the whole HTTP+websocket handshake — are grouped under live_session. We'll lean on this again in Chapter 5, when push_navigate/2 needs somewhere to navigate to without tearing the socket down.

mount/3 — wiring up assigns, nothing else

mount(params, session, socket) is called once per render pass (recall Chapter 1: that's twice on a fresh load, once on every reconnect). Its job is narrow on purpose: put the socket into a valid initial state by assigning whatever the page needs, and return {:ok, socket} or {:ok, socket, opts}. 

def mount(%{"id" => post_id}, _session, socket) do
  post = Blog.get_post!(post_id)

  {:ok,
   socket
   |> assign(:post, post)
   |> assign(:page_title, post.title)}
end

params here are the path params — %{"id" => "42"} for /posts/42/edit. session is the plug session, the same one a controller would see, which is how a LiveView learns who's logged in. Both are untrusted client-adjacent data in the sense Chapter 10 covers in depth — a path param is a string an attacker can set to anything the route pattern allows.

The options tuple is worth knowing even though most mounts don't need it. {:ok, socket, temporary_assigns: [comments: []]} tells LiveView to reset :comments to [] after every render instead of keeping the last-rendered value resident in the process — Chapter 3 explains exactly why that matters for memory. {:ok, socket, layout: {MyAppWeb.Layouts, :minimal}} overrides the root layout for just this LiveView.

Trap

Don't reach for URL query params inside mount/3. They aren't passed to it — only path params and the session are. Query params, and every later change to the URL from push_patch/2, arrive through handle_params/3 instead. A common bug is expecting ?tab=settings to show up in mount/3's first argument; it never will.

handle_params/3 — the URL is the source of truth

handle_params(params, uri, socket) runs immediately after mount/3 on every render pass, and then again on its own every time the URL changes via push_patch/2 or a <.link patch={…}> the visitor clicks. This is the callback that reads query params, and it's where a guided-mode-style page decides which tab, filter, or step to show based on the URL rather than on hidden internal state. 

def handle_params(params, _uri, socket) do
  tab = Map.get(params, "tab", "overview")
  {:noreply, assign(socket, :active_tab, tab)}
end

The reason this split exists — rather than folding params handling into mount/3 — is that mount/3 only runs when the process is born, but a URL can change many times over that process's life as the visitor clicks around inside your app. Treating the URL as the single source of truth for "what should this page currently show" is also what makes the browser's back button work correctly for free: navigating back changes the URL, which re-invokes handle_params/3, which re-derives the right assigns.

render/1 — a pure function of assigns

render(assigns) is called after every assign change, and its contract is the simplest of the three: given the current assigns, return a Phoenix.LiveView.Rendered struct — almost always by writing a ~H​"""…""" HEEx template, either inline or loaded automatically from a colocated .html.heex file. 

def render(assigns) do
  ~H"""
  <h1>{@post.title}</h1>
  <p>{@post.body}</p>
  """
end

Treat render/1 as a pure function: same assigns in, same markup out, no side effects, no database calls. The moment a call like Repo.all(Comment) shows up inside a template, LiveView's change tracking — the whole reason renders are cheap — stops working for that section, because it can no longer tell whether the section's output actually changed without running the query every time. Chapter 4 shows exactly why.

Key idea

Divide responsibility by when it needs to run: mount/3 for once-per-connection setup, handle_params/3 for anything driven by the URL, render/1 for turning the current assigns into markup and nothing more.

What we actually gained

Splitting "set up state," "react to the URL," and "draw the page" into three callbacks with three distinct contracts means each one stays small enough to reason about on its own. A bug where the wrong tab shows up after a back-button press is a handle_params/3 bug; a bug where a brand-new visitor sees stale data is a mount/3 bug; a bug where the markup itself is wrong for the assigns it was given is a render/1 bug. That's a much smaller search space than "somewhere in this 200-line module."

  • mount/3 assigns the initial state; runs once per process birth (and once, disconnected, before that).
  • handle_params/3 is the URL's handler; it owns query params and re-runs on every in-session navigation.
  • render/1 stays pure — assigns in, HEEx out, no queries, no side effects.
  • Chapter 3 picks up right where assign/3 left off: what actually lives in socket.assigns, and how LiveView decides what to re-render when one value changes.
