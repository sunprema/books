03 The one piece of mutable state you're allowed

Socket Assigns and State Transitions

Everything a LiveView knows about the current page lives in one place: socket.assigns, an ordinary Elixir map living in the process's heap. There's no client-side state store, no separate cache layer — assigns are the state, and the moment they change, LiveView goes and figures out what the browser needs to know about it. Let's build up exactly how that works, because "assigns change → page updates" is doing more work than it looks like.

assign/3 and the render loop it drives

assign(socket, :count, 5) (or the pipeable assign(socket, count: 5) for several keys at once) does two things: it puts :count into socket.assigns, and it marks that key as changed for this render cycle. After every callback that returns an updated socket — handle_event/3, handle_info/2, whatever — LiveView calls render/1 again, but the changed-keys tracking is what lets it skip re-computing anything that only depended on assigns that didn't change. We'll follow that tracking all the way to the wire in Chapter 4; for now, the mental model to hold is simpler: assigning is the only way anything on the page updates. There's no two-way data binding, no client store to mutate directly — every visible change traces back to some callback calling assign/3. 

def handle_event("increment", _params, socket) do
  {:noreply, update(socket, :count, &(&1 + 1))}
end

update/3 is just assign/3 with the new value derived from the old one — convenient for counters, toggles, and anything that's naturally "the next state given the current state."

Reassigning, not mutating, nested data

Because assigns are an ordinary immutable map, "updating" a field inside a nested struct means building a new struct and reassigning it whole, exactly like anywhere else in Elixir: 

def handle_event("toggle_published", _params, socket) do
  post = %{socket.assigns.post | published: !socket.assigns.post.published}
  {:noreply, assign(socket, :post, post)}
end

This matters for change tracking, which we're building toward in Chapter 4: LiveView can track changes at the level of individual struct/map fields (so a template that only reads @post.title won't re-render when @post.published flips), but only when you reassign through assign/3. Reach for Map.put/3 or Kernel.put_in/3 on the assigns map directly, bypassing assign/3, and that tracking has nothing to hook into.

Temporary assigns: state that resets itself

Every assign, by default, stays resident in the process for as long as the process lives — which is exactly what you want for @current_user, but a genuine liability for something like a chat log that only ever grows. A LiveView that assigns the full message history on every new message keeps that entire history alive in memory for the lifetime of the connection, even though the client only ever needed to see the diff.

Temporary assigns solve this by telling LiveView "reset this key back to a default value immediately after each render" — declared once, in mount/3's options: 

def mount(_params, _session, socket) do
  {:ok, assign(socket, :messages, []), temporary_assigns: [messages: []]}
end

def handle_info({:new_message, msg}, socket) do
  {:noreply, assign(socket, :messages, [msg])}
end

Read that handle_info/2 carefully: it assigns [msg], a list of one message, not the whole history appended. The template renders that one new message, LiveView diffs it against the last render and patches the client-side DOM (which still has every earlier message sitting in it from previous patches), and then — because :messages is temporary — LiveView resets socket.assigns.messages back to [] before the next render. The server never holds the full log at once; the browser's DOM does.

Key idea

Temporary assigns don't change what gets sent to the browser on any given render — they change what the process keeps holding afterward. Use them for anything append-only and unbounded: chat messages, activity feeds, log tails.

When even that isn't enough: a preview of streams

Temporary assigns solve unbounded growth, but they still round-trip every appended item through the full assign-and-diff machinery, and they don't help when you need to reorder, delete, or bulk-reset a large collection efficiently. That's what stream/4 is for — a purpose-built mechanism for large collections that we'll cover properly in Chapter 8, once PubSub gives us a reason to be pushing collection updates from other processes in the first place.

Choosing a state strategy

Three ways to hold changing state in a LiveView
StrategyServer keepsBest for
Plain assign/3 The full current value, always Small, bounded state — a form, a selected tab, a counter
Temporary assigns Only the latest delta, reset after render Append-only, unbounded lists — chat, activity feeds
Streams (Ch. 8) Nothing — the client owns the collection by DOM id Large or frequently reordered/mutated collections

What we actually gained

  • Assigns are the only mutable state a LiveView has, and assign/3 is the only sanctioned way to change them.
  • Reassign nested data as new values, not in-place mutations — both idiomatic Elixir and required for change tracking to see the field that actually changed.
  • Temporary assigns trade "the process remembers everything" for "the process remembers only the latest render," which is exactly the trade unbounded, append-only state wants.
  • Chapter 4 follows one assign/3 call all the way to the bytes sent over the websocket, and explains precisely why some code defeats that optimization.
