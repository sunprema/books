The Whole Notebook, Compressed

Ten chapters boil down to one habit: hand every source of nondeterminism to a seed, run the same real logic through as many hostile timelines as you can stand, and make an oracle — never a crash — the thing that decides pass or fail. Everything below is a distillation of chapters 1–10, nothing new. Pin this page; it's the one you'll actually reach for at 2am.

The formula

ch. 2, 4, 6, 7, 10

seed + config + workload + fault schedule → one deterministic execution → oracle renders pass or fail. Same seed, same code, same build environment → byte-identical run, every time.

Determinism contract checklist

ch. 2 · miss one row and replay quietly stops being true

Leaks inReplaced with
Wall clockVirtual clock, advances only when the simulation says so
TimersScheduled against the same virtual clock, not a real one
Random numbersA PRNG seeded from one recorded number
Scheduling orderSingle-threaded, cooperative order the seed controls
Network deliverySimulated network; every drop/delay/reorder a seeded coin flip
Disk persistenceSimulated disk; fails exactly when the seed says to
Process identityPinned down, or kept out of decisions entirely
External APIsA stub/model driven by the same seed as everything else
Watch out Determinism isn't a spectrum. Hand seven of the eight leaks to the seed and leave one to real hardware, and the instant the two runs diverge you can no longer tell replay from coincidence.

Fault taxonomy

ch. 7

CategoryConcrete faults
NetworkPartition (symmetric & asymmetric), loss, latency, duplication, reordering, throttling
NodeGraceful shutdown, ungraceful crash, hang (running but unresponsive)
ClockJitter/skew, discontinuous jumps, DST transitions, leap seconds
Thread pausingStall one thread a seed-chosen interval — perturbs interleaving, not a dependency
CPU modulationChange simulated clock speed & relative op cost, cluster-wide

First three simulate a dependency misbehaving; the last two perturb timing itself — that's what finds races the first three structurally can't.

Storage lieWhat actually happens
fsync() successA failed writeback's pages can be dropped, not retried — a later success proves nothing
rename() atomicityAtomic-on-crash is file-system-specific, not POSIX
Write orderingDifferent files' writes can reach disk out of program order
"Disk unavailable"Full, torn, corrupted, slow are four faults, four code paths

Blind spot to model deliberately: DNS, config, and dependency faults — some of the worst real outages live exactly there, not in network/disk/clock.

Oracle types

ch. 6

Watch out "It didn't crash" is one of the weakest oracles available — most correctness bugs (a lost write, a duplicate ID) leave no crash, no stack trace, no log line unless something was specifically watching.
TechniqueNeedsMisses
Local assertionAn invariant you thought to writeAnything you didn't think of
History / linearizability checkA recorded log with real-time boundsCost, at scale, without a graph-based checker
Reference model / shadowAn independently-trusted simpler modelBugs the model shares with the real system
Metamorphic relationA known relation between transformed runsOnly as strong as the relation picked
Liveness watchdogFaults actually healed, plus a bound for "eventually"Whether the result was correct, only that one arrived

Safety: bad thing never happens, refutable by one finite prefix (a lost write, a graph cycle). Liveness: good thing eventually happens — every real checker substitutes a concrete bound for "eventually," which is a design choice, not a formality.

Debugging workflow: failing seed → shrunk regression test

ch. 5, 8, 10

  1. Run the swarm — same test, hundreds of seeds.
  2. One seed fails; the panic prints its own seed. That number is the whole find.
  3. Persist the bundle: seed + config + workload + fault schedule + trace, plus the exact commit and build environment.
  4. Shrink the choice sequence, not the derived trace — bisect, replaying every candidate through the real generator so it's always a legal execution.
  5. Replay the shrunk seed once more, before touching code — confirms it's the bug you think it is.
  6. Fix it. Replay the same seed — should now pass.
  7. Rerun the full swarm, fresh seeds — a fix for one timeline can miss a neighboring variant.
  8. Pin it: write the shrunk scenario as a checked-in, hand-authored test. A seed's reproducibility expires the moment code upstream shifts — the test is what stays fixed.
the two commands 
$ MADSIM_TEST_NUM=100 cargo test --release my_test
# swarm: same test, 100 different seeds

$ MADSIM_TEST_SEED=1629626496 cargo test my_test
# replay: one seed, identical failure every time
CadenceJob

What DST does not catch

ch. 9

TechniqueCatches something the others miss
DST (this book)Concurrency/correctness bugs, exactly replayable — not real performance
Real-cluster performance testingActual throughput/latency under real contention
Hardware fault testing (Jepsen-style)Real clock skew, real kernel/NIC/disk faults
Production observability / chaos-in-prodUnknown-unknowns no model anticipated
Formal methods (TLA+)Exhaustive correctness before a line of code exists — not implementation bugs
Watch out A clean DST run is not proof of production-readiness. The simulator models the abstraction it was given — not real performance, not third-party black boxes, not a specific kernel's actual fsync semantics. Run DST alongside these other techniques, not instead of them.
