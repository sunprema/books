Chapter 08 · Part IV — Living With It

Debugging & Developer Workflow

Here's the thing nobody tells you when they hand you a working deterministic simulator: replay was never the hard part. Replay is a solved problem the moment you've done the work of chapters 2 through 4 — hand the same seed to the same code and you get the same run, full stop. The hard part starts after that: you're staring at a run that fails in the same exact way, on demand, as many times as you like, and you still have to figure out why. A perfectly replayable crime scene is not a solved crime. This chapter is about the tools that turn "I can make it happen again" into "I know what happened and I can prove it" — and, just as important, into a form of the bug that never has to be found again.

The failure artifact: what you actually have to keep

When a simulation run fails, the temptation is to grab whatever's on screen — a stack trace, an assertion message, the last few log lines — and call it a bug report. Don't. None of that is the artifact. The artifact is the whole bundle that made the run reproducible in the first place: the seed, the configuration it drew (topology, replication, storage engine — see chapter 5's swarm dials), the workload, the fault schedule, the full event trace, any logs, and the assertion/invariant history up to the moment things went wrong. A log line tells you what happened once. The bundle is what lets you make it happen again, on your own machine, right now.1

TigerBeetle's VOPR ties this bundle to exactly two numbers: the random seed, and the Git commit the simulation ran against. Find a bug, and you get both back plus a precise trace of how to reproduce it locally — zig build vopr -- <seed> against that same commit reruns the identical failure.2 The commit matters as much as the seed, because — as chapter 2 warned — a change anywhere upstream of the failure can shift where later draws from the PRNG stream land, and a seed replayed against different code can walk an entirely different, innocent path.

FoundationDB's correctness service, Joshua, reruns one specific failing test by setting the JOSHUA_SEED environment variable to the recorded value.3 In practice the reproducibility contract turns out to have a third ingredient beyond seed and commit: the exact build environment. A binary compiled against libstdc++ instead of libc++, or built inside a different container image than the one the original failure ran in, isn't guaranteed to reproduce bit-for-bit — subtle differences in floating-point behavior, hashing, or memory layout can desync the replay before it ever reaches the bug.3

Watch out "Same seed" quietly means "same seed, same commit, same build." Chapter 2 already taught you the first two. The third is easy to forget until a bug reproduces on the CI runner and refuses to reproduce on your laptop, and the actual difference turns out to be a compiler flag, not the bug.

Determinism-preserving observability: logging without moving the schedule

Chapter 1 opened with a warning about Heisenbugs: attach a debugger or sprinkle in some logging, and a real concurrency bug can vanish, because the instrumentation itself perturbs the OS thread scheduler's timing just enough to dodge the race. It would be reasonable to assume the same curse applies inside a simulator. It doesn't — and the reason why is worth sitting with, because it's the cleanest payoff this whole book has to offer.

A deterministic simulator's schedule isn't a function of OS timing at all. It's a function of the seeded PRNG stream, full stop (chapter 2). An observability call that only reads state and writes it out — without drawing from that PRNG stream, without blocking on real I/O, without reading the real wall clock — cannot perturb the schedule, for the simple reason that it was never part of what the schedule depends on in the first place. You can watch the crime scene as closely as you like without smudging it, as long as your flashlight doesn't touch anything the schedule is actually made of.

FoundationDB builds exactly this guarantee into its own tooling. tr.debugTransaction() combined with debugRandom() turns on detailed tracing for one specific transaction inside a simulation run without changing the deterministic randomness stream that produced the original failure — the trace is read off the run, never fed back into it. Separately, fdbserver --print-sim-time surfaces the simulated clock, not the wall clock, when a run appears to hang — because inside a discrete-event simulation, the simulated clock is the only one whose value means anything at all.4

// unsafe: reads the real wall clock and the host RNG -- both are outside
// the seed's control, so this desyncs the very run you're trying to debug
function logUnsafe(msg):
  print(real_gettimeofday(), msg, host_random())

// safe: reads only the simulated clock and writes text out -- consumes
// no entropy, blocks on nothing, so the schedule that follows is untouched
function logSafe(sim, msg):
  print(sim.clock.now(), msg)   // sim.clock is the same virtual clock
                                    // every other decision in the run uses
Key idea The instrument only becomes a Heisenbug again if it reaches around the injected clock/RNG/scheduler the same way any other leak would (chapter 2's leak pitfall, come back to bite you) — a logging helper that quietly calls a real timestamp function, or that happens to draw from the same RNG the simulation itself uses and shifts every later value downstream. Determinism-preserving observability isn't a special trick. It's just chapter 2's determinism contract, applied to your own debug code with the same discipline you'd apply to the system under test.

Time travel, checkpoints, and causal slicing: reading less of the trace

A failing run can carry thousands of events. Reading them start to finish is the slowest possible way to find a bug, and it's also unnecessary, for a reason specific to how these simulators are built: everything runs single-threaded, in one process, with all state sitting in memory. That makes a full checkpoint at any event boundary just a snapshot — cheap enough to take often. A general record-and-replay debugger on a real multi-threaded program can only ever step forward from the start. A deterministic simulator lets you seek to any event index in an already-recorded failure and resume from there, or re-diverge from there with a different decision — genuine time travel, made practical by the same single-threaded discipline that makes replay possible at all.5

The other way to read less of the trace is to not read the causally irrelevant parts of it in the first place. Academic causal slicing and dynamic-slicing techniques for concurrent and message-passing programs reconstruct only the events that are actually connected to the failure — by data dependency, control dependency, or (for a distributed system) causal message ordering — and discard the rest.6 Most of a long trace, it turns out, has nothing to do with any one bug; slicing is what tells you which handful of events do.

Antithesis's causality analysis feature automates the same question a different way: starting from one observed bug timeline, it rewinds to a series of earlier moments and, from each one, re-explores forward multiple times with different fuzzer decisions, tracking what fraction of those re-explorations still hit the same bug. Plotted as bug-probability over time, a sharp jump at a given moment identifies the event that causally mattered — the tool is finding the cause by search, not asking a human to eyeball a thousand-event trace and guess which one counted.7 It's the same distinction chapter 6 drew between a symptom and an oracle, aimed inward at the debugging process itself: "this crashed" is a symptom; "this specific earlier event is what made the crash likely" is a diagnosis.

Binary search through execution: minimizing the failure

Chapter 5 introduced shrinking as a way to hand off a smaller, cleaner bug before you ever look at it. The same idea, run interactively, is one of the single best debugging techniques for a long DST trace. Andreas Zeller and Ralf Hildebrandt's delta debugging algorithm, ddmin, automates exactly the "binary search through execution" intuition: split a failing case into halves, test each half (and its complement) against the failure, keep whichever half still fails, and recurse — converging on a case where removing any single remaining element makes the failure vanish. Their original evaluation minimized a Mozilla crash from 95 recorded user actions down to 3, and 896 lines of failure-inducing HTML down to a single line, fully automatically.8

Applied to a DST failure, the object you bisect should be the seed's underlying choice sequence — the stream of scheduling, fault, and workload decisions the PRNG actually produced — not the derived event trace directly. That's chapter 5's "integrated shrinking" principle again, generalized from an automated pre-commit pass into your own interactive debugging loop: every bisection candidate is replayed through the same generator and simulator, so it's guaranteed to be a legal execution, never an impossible trace stitched together by hand.9 A run that takes thousands of events to fail typically isolates its minimal cause in on the order of log₂n replays — not a linear read of the whole thing.

// bisect the SEED'S CHOICE SEQUENCE, not the derived trace -- every
// candidate is replayed through the real generator, so it's always legal
function bisect(choices, reproduces):
  while len(choices) > 1:
    mid = len(choices) / 2
    left, right = choices[:mid], choices[mid:]
    if reproduces(replay(left)):  choices = left
    elif reproduces(replay(right)): choices = right
    else: return choices          // both halves needed -- this IS the minimal cause
  return choices                  // ~log2(n) replays, not a linear trace read

From minimized failure to permanent regression

A minimized reproducer isn't just faster to read — it's less likely to get accidentally fixed. A small, causally-tight failure gives an unrelated later change less surrounding code to coincidentally touch; a sprawling 10,000-event trace gives it plenty. That's the same discipline chapter 5 introduced for handing off a clean bug report, now doing double duty as a debugging aid, not just a courtesy to whoever reads it next.10

But a minimized seed is still only conditionally reproducible — conditional on the exact code, and now you know, conditional on the exact build. The standard practice across every DST-using team this book has drawn from is the same: treat a freshly minimized failure as raw material, not as the permanent artifact. Convert the minimized fault schedule and workload shape into a concrete, hand-written regression scenario that gets checked in and runs on every future build — rather than trusting the original seed number to keep finding the bug as the codebase moves on underneath it.11

If your only record of a fixed bug is the seed that found it, do you actually have a regression test?

Not really — not a durable one. A routine refactor upstream, months later, can shift where later PRNG draws land in the stream and quietly walk that seed past the state where the bug used to live. No test fails, because the "test" was never pinned to the scenario; it was only ever pinned to a number. Turning the seed into a named, hand-written scenario is what makes the fix stay fixed.

CI strategy: three cadences, three jobs

Zoom out from any one debugging session and the question becomes: when does all of this actually run? Every real DST program this book has drawn from answers with the same shape — not one testing cadence, but (at least) three, each doing a job the others structurally cannot.

CadenceJobConcrete example
Per-PR smoke DSTFast, gates every merge RisingWave: 16 seeds in parallel per test, full PR suite inside ∼20 minutes, leaning on simulated time running 4–5× faster than real time
Nightly / continuous seed farmDeep, runs in the background FoundationDB's Joshua runs ensembles around the clock — every code probe (BUGGIFY site) is expected to be hit at least once per night; TigerBeetle's CFO runs a dedicated fleet continuously, published to a public devhub, with a fuzz label to steer extra attention at one PR
Pre-release burstDeepest, occasional TigerBeetle's fuzzing fleet runs 24/7 on ∼1024 dedicated cores at ∼700× simulated-time acceleration — on the order of two millennia of cluster faults-and-recoveries explored every single day

The three cadences trade off exactly what you'd expect: the per-PR tier is fast and necessarily shallow, because a developer is sitting there waiting on it. The continuous tier is deep but has latency — a bug it finds may already be a day old by the time anyone sees it. The pre-release burst is the deepest of all, at the cost of only running occasionally. Run only one of the three and you get a specific, predictable failure mode: per-PR-only means the search is structurally too shallow to find most of what DST exists for; nightly-only means real bugs sit undetected in the mainline for a day or more; skipping the pre-release burst forgoes the single deepest pass right when it matters most, immediately before shipping.12,13

Key idea Notice what all three tiers share: every one of them still ends at a seed, a commit, and (per the section above) a build environment — the same three-part bundle a single developer needs to reproduce one failure locally. A fleet of a thousand cores and a laptop replaying one seed are running the exact same machinery. Scale changes how much of the state space you search, not what a failure, once found, is made of.

Failure triage, in practice, is mostly a visibility problem: TigerBeetle's public devhub dashboard and PR-level fuzz labels exist specifically so a found failure has somewhere obvious to land, and a developer can point the fleet at their own change on demand rather than waiting for the next scheduled sweep to (maybe) stumble onto it.
