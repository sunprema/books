Chapter 10 · Part V — Capstone

Hands-On Capstone

Nine chapters of this notebook have been circling the same claim from different angles: control every source of nondeterminism, and a run stops being a sighting and becomes a recipe. It's time to stop taking that on faith and go build the thing. This chapter walks you through a small, complete project — a tiny replicated key-value store, wrapped in your own deterministic simulator — from the four ports, through a planted bug, to a permanent regression test. Nothing here is hypothetical scaffolding; every technique is the same one chapters 2 through 8 already gave you a name for. The only thing new is that this time, you're the one turning the crank.

What you're building

Pick one of three small, well-understood systems — a replicated key-value store, a job queue, or a payment ledger — and build a toy version with real replication logic, wrapped in a simulator you write yourself. This chapter walks the key-value store, because its correctness properties are exactly the ones chapter 6 already gave you vocabulary for: no committed write is ever lost, every client sees one consistent view of the keyspace, and once faults stop, the cluster eventually elects a leader and starts serving requests again — safety and liveness, both, on a system small enough to fit in one sitting.1 If you'd rather build the job queue or the ledger, every step below still applies almost word for word — only the workload and the oracle's specific invariant change.

Keep the scope honest: three nodes, one leader, followers that replicate the leader's writes, and a client that issues PUT/GET operations. That's small enough to hold in your head, and — this is the part that matters — small enough that when the simulator finds a bug, you'll be able to actually see why, instead of drowning in a real system's incidental complexity. This is deliberately the same move chapter 3 described for FoundationDB and TigerBeetle, just aimed at a toy instead of a production database: keep the application logic real, and simulate only the environment around it.

Key idea The point of this capstone isn't the key-value store. Nobody needs another toy KV store. The point is the simulator wrapped around it, and the muscle memory of watching a seed turn a "why did this fail once in CI" shrug into a three-line, permanently reproducible bug report.

The four ports, one more time

Chapter 3 named the seam: your store's logic should depend on interfaces for Clock, Network, Storage, and Random — never on a concrete std::time::Instant::now(), a raw socket, a file handle, or the OS's random-number generator directly. In Rust, that's naturally four traits, with two implementations of each: a real adapter for production, and a seeded, simulated adapter for tests.

trait Clock {
    fn now(&self) -> Instant;
    async fn sleep(&self, d: Duration);
}

trait Network {
    async fn send(&self, to: NodeId, msg: Msg) -> Result<()>;
    async fn recv(&self) -> Msg;
}

trait Storage {
    async fn append(&mut self, entry: LogEntry) -> Result<()>;
    async fn read(&self, idx: u64) -> Option<LogEntry>;
}

trait Random {
    fn next_u64(&mut self) -> u64;
}

// production: RealClock, TcpNetwork, DiskStorage, OsRandom
// simulation:  SimClock,  SimNetwork(seed), SimStorage(seed), SeededRandom(seed)
// your store's own logic imports only the four traits above — never a concrete type

You don't have to write those simulated adapters from nothing, either. MadSim — a real, publicly available Rust crate — is an async runtime that mirrors Tokio's own API surface closely enough that application code written against it runs unmodified against either the real Tokio runtime in production or MadSim's seeded, simulated time/network/task scheduler in tests, borrowing the same simulation-first idea straight from FoundationDB.2 And you don't have to imagine what "a Raft-replicated key-value store on MadSim" looks like finished, either: MadRaft is a public teaching lab — derived from MIT's 6.824 Raft and KV-store assignments — that builds exactly this capstone's project on top of MadSim, specifically to teach deterministic simulation testing hands-on.3 Read its source once you've built your own version; seeing a second, independent implementation of the same idea is one of the fastest ways to notice what you got right.

Building it in Elixir instead The BEAM gives you something Rust doesn't: every process is already an isolated, message-passing state machine, and supervision trees already give you crash/restart for free. What it doesn't hand you off-the-shelf is a MadSim-style deterministic scheduler — you'd need to control message delivery order and the virtual clock yourself, the same simulation-first discipline as the Rust version, just applied at the process-mailbox boundary instead of an async-trait boundary. Treat it as the harder, more educational path: you'll come away understanding exactly which part of "deterministic" a language runtime gives you for free, and which part is always on you.

The loop this whole book has been building toward

Every chapter so far has been one piece of a single pipeline. This capstone is where you finally assemble all of it and watch the pieces hand off to each other for real.

The workload and the reference oracle

Structure your workload the way chapter 5 described FoundationDB doing it — three phases, SETUP / EXECUTION / CHECK — and write the CHECK phase before you write anything fancier than a single-node store. The oracle is a plain, single-threaded reference map: apply every client operation to it in the order the client issued them, then compare the reference map's final state against whatever the real replicated cluster ends up holding. That's a shadow-implementation oracle, the same style TigerBeetle's VOPR uses to check every state transition against a trusted model as it happens.4

struct ReplicationWorkload { reference: BTreeMap<Key, Value> }

impl Workload for ReplicationWorkload {
    fn setup(&mut self, cluster: &mut Cluster, rng: &mut dyn Random) {
        cluster.elect_initial_leader();
    }

    async fn execution(&mut self, cluster: &mut Cluster, rng: &mut dyn Random) {
        for _ in 0..rng.next_u64() % 500 {
            let (k, v) = (random_key(rng), random_value(rng));
            if let Ok(()) = cluster.put(k, v).await {
                self.reference.insert(k, v); // only record what was actually ACKED
            }
        }
    }

    fn check(&self, cluster: &Cluster) {
        for (k, expected) in &self.reference {
            assert_eq!(cluster.get(*k), Some(*expected),
                "lost a write the client was told succeeded"); // the oracle, ch.6
        }
    }
}

Notice what that CHECK is and isn't. It isn't "the process didn't crash" — chapter 6 already warned you that's one of the weakest oracles available, because most correctness bugs in a distributed system don't crash anything.5 It's a direct, specific safety property: every write the client was told succeeded is still there. That's the one property this capstone is built to violate on purpose.

Planting a bug on purpose

Here's the deliberate mistake: make the leader acknowledge the client's write as soon as it appends the entry to its own log, without waiting for a majority of followers to append it too. It looks fine in every quiet run — the followers usually catch up within microseconds, long before anything else happens. It is also a textbook example of exactly the class of bug Jepsen-style fault injection has found in real systems again and again: a configuration that acknowledges a write the cluster hasn't actually made durable yet.6 The bug needs three things to line up before it shows itself, and none of them are rare in isolation — which is precisely why nobody would find this by hand.

Find it: run the swarm

You will almost never find this bug by running the test once. You find it the way chapter 5 described FoundationDB doing it, and the way MadRaft's own tooling makes a one-line habit: run the same test under hundreds of different seeds and let each one draw its own random timing, its own random crash point, its own random partition schedule.7

# the same test, 100 different seeds, one command
$ MADSIM_TEST_NUM=100 cargo test --release replicate_under_partition

# a failing run prints its own bug report -- nothing to write down by hand
thread '...' panicked at 'lost a write the client was told succeeded'
MADSIM_TEST_SEED=1629626496

That single environment variable is the entire find. One seed, out of the hundred you ran, happened to draw the exact combination of timings that exposes the early-ack bug — and the moment it printed, the sighting stopped being a one-off and became a number you can hand to anyone, including your future self.

Shrink it

Seed 1629626496 reproduces the bug, but the run behind it might carry hundreds of client operations and dozens of scheduling decisions — almost all of them irrelevant. Don't read that trace top to bottom. Bisect it, the same integrated-shrinking idea chapter 5 introduced and chapter 8 turned into a developer habit: shrink the seed's own underlying choice sequence — fewer operations, an earlier crash, a shorter fault schedule — and replay each candidate through the real generator, so every candidate you try is guaranteed to still be a legal execution, never a hand-edited trace that couldn't actually have happened.8

// shrink the CHOICE SEQUENCE, not the derived trace -- every candidate
// replays through the real generator, so it's always a legal execution
function shrink(choices, still_fails):
  best = choices
  for candidate in smaller_variants(best):
    if still_fails(replay(candidate)):
      best = candidate  // keep shrinking from here
  return best  // converges to: 1 write, 1 crash, 1 partition, 1 stale election

Done well, this converges to almost exactly the four-event timeline the diagram above already drew: one write, one early ack, one crash, one stale election. That minimal trace is not just easier to read — it is the bug, stripped of everything that was never a cause.

Replay it, fix it, and make it stay fixed

Before touching a line of the fix, replay the shrunk seed once more and watch it fail the identical way — this is the cheapest confidence check available to you, and it's worth doing on principle: it confirms the bug you're about to fix is the bug you actually found, not a different one that happens to trip the same assertion.

$ MADSIM_TEST_SEED=1629626496 cargo test replicate_under_partition
# same panic, same line, every time -- that's the whole point

The fix is exactly what the bug's shape suggests: don't ack the client until a majority of the cluster has durably appended the entry, not just the leader. Rerun the shrunk seed once more; it should now pass, because a stale follower missing that write can no longer win an election without first catching up. Then run the full swarm again — hundreds of fresh seeds, not just the one you already know about — because a fix aimed at one seed's exact timeline can still leave a neighboring variant of the same bug undiscovered.

Now do the one step it's easiest to skip: pin the scenario. Per chapters 2 and 8, a seed's reproducibility is a property of the seed and the exact code it ran against — a routine, unrelated change upstream can silently shift where later random draws land in the stream and walk right past the bug without ever reproducing it again.9 So don't rely on the seed alone. Write the shrunk scenario down as a small, explicit, hand-authored test — "leader acks before majority, then crashes, then a stale follower is elected" — that runs on every future change, independent of whether MADSIM_TEST_SEED=1629626496 still finds it. The seed got you here. The checked-in test is what keeps this exact bug from ever shipping again.

If you'd skipped the oracle and just watched for crashes, would you have ever found this bug?

No. The planted bug never crashes anything — the leader dies cleanly, the cluster elects a new leader cleanly, and the store keeps serving requests the whole time. Every symptom you'd normally watch for stays green. The only thing that ever notices is a reference model that remembers what the client was actually promised, and checks it. That's the whole lesson of chapter 6, arriving here as something you watched happen to your own code instead of something you read about someone else's.

Try this
  1. Build it. Pick Rust with MadSim (or hand-roll your own four adapters), or take the harder, more educational Elixir path from this chapter's sidebar. Get the honest version working first — majority-ack, no planted bug — before you break anything on purpose.
  2. Plant a second bug of a completely different shape: a liveness bug instead of a safety one, like chapter 6's stuck-view-change livelock, where the cluster never crashes and never loses data — it just quietly stops making progress forever. Notice that your safety oracle from this chapter cannot catch it; you'll need a bound-on-"eventually" liveness check instead.
  3. Swap the target: rebuild this same pipeline around a job queue (invariant: no job is ever executed twice, or ever silently dropped) or a payment ledger (invariant: the sum of balances is conserved across every transfer, even mid-fault). Keep the four ports, the SETUP/EXECUTION/ CHECK workload shape, and the find-shrink-replay-fix-pin loop identical — only the oracle's specific assertion should change.
