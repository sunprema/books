Chapter 07 · Part III — Exploring & Judging

Fault Models

Two chapters ago we built a machine that can inject almost anything — drop a packet, tear a write, skip a clock forward, starve a thread. That's a toolbox, not a plan. "Inject faults" is not a fault model any more than "use tools" is a blueprint. A fault model is the deliberate, written-down answer to a much narrower question: which faults, in which combinations, does this system actually need to survive — and which ones would just be you wasting a seed farm on a scenario that could never happen? Get the model too narrow and your simulator finds nothing your unit tests wouldn't have. Get it too wide and it finds nothing useful, because "the disk returns the wrong answer and also claims success and also this violates causality" isn't a bug report, it's a system that couldn't exist. This chapter is about drawing that line correctly.

Not all failures are created equal: Cristian's hierarchy

Start with the oldest, cleanest idea in this space. Flaviu Cristian's 1991 taxonomy of distributed-system failures orders them by how constrained the broken component's misbehavior is allowed to be.1 At the mild end: a crash (or "fail-stop") failure — the component just halts, cleanly, and does nothing else wrong. One notch up: an omission failure — it's still behaving correctly when it behaves at all, but it silently skips some steps or drops some messages. Another notch: a timing failure — every answer it gives is correct, just late. And at the far end, the failure class with essentially no constraints at all: arbitrary, or Byzantine, failure — the component can send wrong data, contradict itself to different observers, or actively lie. Each class sits strictly inside the next: anything a crash failure can do, an omission failure can also do, and so on up the chain.

Why does an old taxonomy from a systems-theory paper matter to a chapter about picking which faults to inject? Because it hands you the one honest yardstick for the question this whole chapter keeps circling: is this fault realistic, or is it excessive? A fault is realistic exactly when it stays inside the failure class the system under test actually claims to tolerate. Push past that boundary and you haven't found a new bug — you've re-derived a limitation the system's own designers already knew about and accepted. We'll come back to this as the organizing principle for the whole chapter; first, the taxonomy needs one more split that Cristian's paper treats almost in passing, but that matters enormously for how you build a simulator.

Crash-stop versus crash-recovery: does the process come back?

Inside the "component halts" family sit two models that look almost identical on paper and are worlds apart in practice. Under crash-stop, a process that fails is gone for good — it never resumes, the cluster just has to route around a permanently missing member. Under crash-recovery, a process may crash and later restart, rejoining the computation by reconstructing whatever it can from stable storage.2 An algorithm proven safe under crash-stop assumptions can be unsafe under crash-recovery, because a process that comes back can replay a stale in-flight action or wake up staring at a log that was only half-written when the lights went out — states the crash-stop model never had to account for, because in that model, once you're gone, you simply don't get a vote anymore.

Here's the part that's easy to miss when you're building the fault injector rather than reading about it in a paper: this distinction decides which of your own code paths ever get run at all. A harness that only ever kills a node once and leaves it dead is testing crash-stop, full stop — membership shrinks, quorums recompute, and that's the entire story. It is structurally incapable of ever running your write-ahead-log replay, your snapshot-recovery routine, or your rejoin-after-restart protocol, because none of that code executes unless something actually comes back. Only a crash-recovery fault — kill the process, wait a seeded interval, restart it, force it to rejoin — ever exercises that machinery. If your fault model never reboots a node, an entire, often safety-critical subsystem of your codebase is running at 0% coverage no matter how many seeds you burn.

// crash-stop: gone for good, no recovery path is ever exercised
function crashStop(node):
  node.kill()
  cluster.remove(node)               // membership just shrinks

// crash-recovery: the only kind of fault that runs recovery code at all
function crashRecover(node, rng):
  node.kill()
  simulated_sleep(rng.next_offset())   // down for a seeded interval
  node.restart_from(node.stable_storage)     // WAL replay / snapshot load
  cluster.rejoin(node)
Key idea A fault model that only ever asks "can it survive losing a node?" is answering a crash-stop question. The much harder, much more valuable question — "can it survive losing a node and then getting it back?" — is a crash-recovery question, and it's the one that finds the WAL-replay bug, the double-recovery bug, and the split-brain-on-rejoin bug. If your fault model never reboots anything, you've only ever asked the easy half of the question.

A table worth having: five categories of injectable fault

With that framing in hand, here's the survey. Antithesis, whose entire product is built around injecting faults into an unmodified guest OS at the hypervisor boundary, organizes what it injects into five named categories — and having a fixed vocabulary for "the kinds of things that can go wrong" turns out to be one of the more useful artifacts a DST program can adopt wholesale.3

CategoryWhat it perturbsConcrete faults
NetworkMessage delivery between nodes Partition (symmetric & asymmetric), packet loss, latency, duplication, reordering, bandwidth throttling
NodeWhether a process is running at all Graceful shutdown, ungraceful crash/termination, hang (running but unresponsive)
ClockWhat time the system thinks it is Jitter/skew, discontinuous jumps forward or back, DST transitions, leap seconds
Thread pausingThe order concurrent work interleaves in Stall one thread for a seed-chosen interval, letting others race ahead of it
CPU modulationRelative timing of low-level operations, cluster-wide Change simulated clock speed and the relative cost of different operations

Notice the last two rows are a different kind of fault from the first three. Network, node, and clock faults simulate an external dependency misbehaving — something the code, in principle, could check for and handle. Thread pausing and CPU modulation don't touch any dependency at all; they perturb timing itself, cluster-wide, without changing one line of the guest's code.3 That's precisely what lets them find bugs the first three categories structurally cannot: an interleaving- dependent race that has nothing to do with the network, the disk, or the clock being wrong — only with two threads racing each other in an order nobody happened to test.

Storage semantics: the disk lies more often than you'd like

The network-and-node half of the table gets most of the attention because partitions are dramatic and easy to picture. The storage half is quieter and, in practice, meaner — because the contract a disk actually offers is narrower than the one most application code assumes, and the gap between the two is exactly where "durability lies" live.

Take the single most-assumed guarantee in all of durable storage: fsync() returned success, therefore my data is safe. The contract most engineers carry around in their heads is "everything written since the last successful call is now durable." That is not the contract Linux actually implements. On a writeback error, the kernel is permitted to drop the offending dirty pages from the page cache rather than keep retrying them — which means a second fsync() call can return success without ever having flushed the bytes that failed the first one.4 PostgreSQL assumed the stronger, wrong contract for essentially its entire history. The bug — now known as "fsyncgate" — was reported to the project's mailing list in 2018, after two decades in production; because the write-then-fsync pattern is close to universal, the same trap sat underneath most other databases built on buffered I/O too.4,5

Watch out The fix PostgreSQL shipped was not "retry more cleverly." It was to PANIC the entire process the instant fsync() reports an error — treat the OS's own report of a write failure as unrecoverable, crash on purpose, and force a full write-ahead-log replay on restart, rather than keep running against a page cache that might now silently disagree with what's actually on disk.5 That is the correct general response to a durability lie once you know the interface's contract is narrower than you assumed: treat the lie as a crash, and let crash-recovery do its job.

The lie isn't limited to error handling, either. Pillai et al.'s 2014 study tested the "persistence properties" applications quietly depend on — is rename() atomic on crash? can writes to two different files be reordered? does a file's data reach disk before its metadata does? — across six popular Linux file systems, all of which nominally implement the same POSIX interface. The properties varied widely.6 An application's crash-consistency protocol tested against only one file system can be silently unsafe on another. Which is the concrete design implication for your simulator: a storage fault model that only ever corrupts or removes data blocks is missing half the picture. It also needs to reorder and partially apply metadata updates — the exact class of fault that decides whether rename() looks atomic after a crash.

One more storage fault deserves its own line item rather than folding into "disk unavailable": running out of space. The standard deterministic technique is to intercept the write call itself and have it return ENOSPC on demand — no need to actually fill a real disk, the injection is exact and instantaneous.7 It earns a separate slot because it's usually mishandled differently than a dead disk: every other operation on that disk keeps succeeding, only the one write that would exceed capacity fails, which is a narrower, easier-to-miss condition for a storage layer to get right than "the disk is entirely gone."

Clocks, DNS, configuration, and dependencies: the fault model's blind spot

Clock faults belong squarely in the taxonomy table above — skew, discontinuous jumps, DST transitions, leap seconds, all straightforward to reason about once you know to inject them. What's easy to leave out entirely, because it doesn't fit neatly next to "network" or "disk," is the fault category that some of the worst real production incidents actually come from: DNS, configuration, and dependency failures.

A concrete, recent example. The October 2025 AWS US-EAST-1 outage was not a network partition or a disk failure at all — it was a latent race condition inside DynamoDB's own DNS-management automation. Two independent "DNS Enactor" processes updated the same service's records concurrently; a stale plan overwrote a newer one, and cleanup automation then deleted it, wiping the DNS records for a core internal endpoint outright. Because dozens of other AWS services — EC2, IAM, Lambda among them — resolve that endpoint internally, the fault cascaded to more than 140 downstream services.8 No node crashed. No packet was dropped on any link that mattered. The system simply forgot, for a while, where one of its own most-depended-on components lived — and a fault model built only around network partitions, node crashes, and disk corruption has no vocabulary for that at all.

This is the same shape of problem the "gray failure" idea from the very first chapter warned about: a partial failure with differential observability, where some part of the system sees things as healthy while another part experiences them as broken.9 A stale DNS entry, a config push that only breaks one code path, a dependency returning plausible-but-wrong data instead of erroring cleanly — these don't look like an "up" or "down" fault to a health check built around binary liveness. If your fault model can only express "the dependency is reachable" or "the dependency is gone," it will systematically miss the failure mode that's arguably the most dangerous one in production: the dependency that's technically there, technically responding, and quietly wrong.

Fault realism: staying adversarial without becoming absurd

Which brings the chapter back to the question it opened with. A simulator that can inject anything will, left unguided, waste most of its search budget on combinations that could never occur — and worse, on combinations that don't even test anything real. Two disciplines keep a fault model adversarial without letting it drift into absurdity.

The first is Cristian's hierarchy again, now doing real work: stay inside the failure class the system claims to tolerate. If a system is documented as crash-fault-tolerant, injecting arbitrary data corruption or forged messages — Byzantine failures — doesn't surface a bug. It reconfirms, expensively, something the system's own designers already told you: it wasn't built to survive that. A fault model earns its adversarial power by pushing right up against the edge of what the system claims, not by leaping to a strictly harder class it was never designed for.1

The second discipline is about correlation, not severity. FoundationDB's simulator deliberately injects failures at machine, rack, and whole-datacenter granularity within the same run, so a single simulation can plausibly reproduce a correlated multi-machine outage — a rack losing power, a top-of-rack switch failing — rather than only ever killing one independently chosen node at a time.10,11 Real outages cluster: shared power, shared network gear, one bad deploy landing on every replica simultaneously. A fault model that only ever samples independent single-node faults is under-exploring precisely the correlated scenarios that cause the worst real incidents — while a fault model that goes to the opposite extreme, hitting every category in the table at maximum severity, simultaneously, every run, isn't more adversarial for it. It's mostly just sampling states no real system would ever land in, at the expense of seeds that could have found something true.

Key idea Recall buggification from the workloads chapter: FoundationDB restricts its rarest injected outcomes to results the code is already contractually obligated to handle — a documented possible error return, a legal-but-unusual delay — rather than inventing a fault outside the system's own contract.10 That's the same discipline this chapter has been building toward, generalized across every category in the table: a network fault should look like something a real network can produce; a storage fault, something a real disk can return; a clock fault, something a real NTP daemon or DST transition can cause. A fault that violates the platform's own documented contract outright — a write acknowledged and then never durable with no crash anywhere in between — doesn't test your system. It tests a system that couldn't exist.

Put the two disciplines together and "fault realism" stops being a vague aesthetic judgment and becomes a checklist you can actually apply to a fault before you wire it in: Is this within the failure class the system claims to tolerate? Could it plausibly co-occur with the other faults active in this run, the way real failures correlate in production? Answer yes to both, and you have adversarial power worth spending seeds on. Answer no to either, and you've built a very expensive way to rediscover something you already knew.

If your simulator has never rebooted a node, what exactly has it been testing?

Crash-stop behavior, and only crash-stop behavior — membership shrinking, quorums recomputing, nothing more. Every line of recovery code you've written — WAL replay, snapshot loading, rejoin protocols — has been sitting at zero coverage the entire time, no matter how many seeds ran overnight, because none of it can execute unless something actually comes back. It's worth checking, right now, whether your own fault model has quietly been asking only the easy half of this chapter's central question.
