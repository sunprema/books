Chapter 03 · Part II — Building It

Architectures for DST

Chapter 2 was the contract: hand every leak — the clock, the RNG, the scheduler, the network, the disk — to the seed, or the replay guarantee quietly stops being true. Fine. But a contract is just words until somebody signs the plumbing. Where, physically, in a real codebase, does "hand it to the seed" actually happen? It turns out there are only two honest answers, and they disagree about almost everything except the goal.

One answer says: teach the application the trick. Rewrite it so every place it reaches for the clock, the RNG, the network, the disk, it reaches through a door you built — and put a simulator behind that door instead of the real world. The other says: don't touch the application at all. Build a sandbox so convincing that an ordinary, unmodified program can't tell it isn't running on real hardware — and control the sandbox's clock, RNG, and scheduler instead. Call the first simulation-first and the second virtualization-first. This chapter is about the trade-off between them, and about how you'd design a system, from day one, to make the first option even possible.

Simulation-first: teach the application one trick

Here's the trick, and it's worth being precise about it, because it's easy to mishear this as "mock everything." That is not the idea. The idea is to run as much real, unmodified application logic as possible, and replace the environment only at a small number of well-defined boundaries. FoundationDB's core logic depends on two abstract interfaces — INetwork for networking and IAsyncFile for disk — instead of calling the OS directly. In production those interfaces resolve to Net2, built on Boost.ASIO, talking to a real kernel. In simulation the very same interfaces resolve to Sim2/SimFile, where every decision — does this read succeed, how long does it take, does this connection just die — is a seeded dice roll. The database code in between never finds out which side of the door it's talking to.1,3

That swap is only cheap because of a second, deeper choice: FoundationDB's core is written in Flow, an actor-based extension to C++11. An ACTOR function wait()s on a future without blocking anything else — it compiles down to a cooperative state machine, not an OS thread. The same Flow source compiles to the real production binary, and, linked against the simulator instead, becomes the single-threaded process that runs against simulated network and disk. Production logic and simulated logic are not two implementations that might drift apart — they are one file.2,1

FoundationDB is not alone in this shape — it just got there first and loudest. TigerBeetle's entire I/O layer sits behind one abstract interface, implemented in production with io_uring on Linux (or kqueue on macOS) and swapped for an in-memory deterministic implementation inside its simulator, "the VOPR." TigerBeetle keeps that layer single-threaded and in userspace by design — the project's own reasoning is that this is simultaneously the simplest implementation and the one that makes determinism possible at all.4,5 And madsim brings the same idea to async Rust: it ships simulated drop-in replacements for common runtime and networking crates, modeled on Tokio's own API surface, so application code written against those APIs runs unmodified against either the real Tokio runtime in production or madsim's simulated time, network, and task scheduler in tests — every simulated random choice pulled from one global seeded generator.6

Key idea Simulation-first is not "replace the system under test with a fake." It is the opposite: run the real system, unmodified, and replace only the small set of doors it uses to touch the outside world. The bigger those doors, the more of your actual bugs the simulator can find.

Virtualization-first: don't touch the application at all

Simulation-first has one real cost: somebody has to build (or already have built) that whole ports-and-adapters skeleton, in a language whose concurrency model even makes single-threaded determinism possible. Most existing systems don't have that skeleton, and rewriting one to get it is not a testing add-on — it's a rearchitecture. Antithesis exists because of that gap, and it takes the structurally opposite bet: instead of asking the application to expose doors, run the entire unmodified system — arbitrary containers, in any language — inside a custom deterministic hypervisor, built by heavily modifying FreeBSD's bhyve.7,8

The hypervisor hides every real source of entropy from the guest. It substitutes a fake clock and a fake random-number generator for the ones the guest OS would normally hand out, and it separately controls the guest's own thread scheduler — which doubles as a fault-injection mechanism for free, since deliberately starving or reordering a thread is just a scheduling decision made one layer down. The mechanism that makes this deterministic-and-controllable at the hardware boundary is the x86 VMCALL instruction — a roll-your-own hypercall facility that lets the hypervisor intercept and answer the guest's system calls at the VM boundary, rather than inside the application at all.7

One more deliberate trade shows up here that's easy to miss: each guest instance runs on a single pinned physical core. That sounds like giving up performance for nothing, until you notice these are test instances, not production replicas — a single-core run costs nothing that matters to a test. Antithesis recovers throughput a completely different way: run enormous numbers of independent single-core instances in parallel across a fleet, each one exploring a different region of the state space, instead of trying to make any one run faster.7,9 Simulation-first buys its speed by decoupling simulated time from the wristwatch inside one process (recall Chapter 2's 10-to-1 ratio); virtualization-first buys it by fanning out across many processes instead.

Watch out "No code changes required" does not mean "no engineering cost." Someone still has to build the deterministic hypervisor — Antithesis's own account of doing it treats this as a genuinely hard systems problem, not a weekend project.7 The cost didn't disappear; it moved from every adopting team's codebase into one team's hypervisor.

A middle path: intercept the syscalls, touch nothing else

There's a third point on this spectrum, sitting between "rewrite the application" and "virtualize the whole machine": intercept system calls on an otherwise unmodified binary. Meta's Hermit sandboxes ordinary Linux x86_64 programs and intercepts the syscalls they make — in some cases replacing the kernel's answer outright, in others forwarding the call to the real kernel and then sanitizing what comes back — to make time, thread interleaving, and randomness deterministic without either rewriting the application's source or virtualizing an entire guest OS.10 It gives up some of a full hypervisor's fidelity (it's still running on the host kernel, not a fully isolated guest) in exchange for a much lighter footprint than standing up bhyve.

Choosing one: the actual trade-offs

None of these three is strictly better — each one is a different answer to "who pays, and in what currency."

Hermit sits between the middle two rows: lighter than a full hypervisor, but — like virtualization-first — requires no source rewrite, at the cost of running on the host kernel rather than a fully isolated guest.10

Designing a system so simulation-first is even an option

If you're building new, or can afford to rearchitect, simulation-first is the cheaper, higher-fidelity option in the long run — but only if the codebase is shaped correctly from the start. The shape has a name, and it predates DST by decades: hexagonal architecture, or "ports and adapters," as Alistair Cockburn originally defined it. The core logic depends only on a named port — an interface expressing a purposeful conversation, like "a clock" or "a network" — never on any specific technology behind it. One or more adapters plug into each port for a specific implementation.11

Dependency injection is the wiring discipline that makes this actually swappable: adapters are connected to ports from outside the core — typically once, at process startup — so the core never constructs or reaches for a concrete implementation itself. That single property is exactly what a simulation-first DST harness depends on: swap a real adapter for a simulated one without touching a single line of the core logic under test.1,6

// the core never imports a concrete Clock, RNG, Network, or Storage —
// only the port (interface) each one is defined by
interface Clock   { now() -> Time }
interface Random  { next() -> f64 }
interface Network { send(peer, msg); recv() -> Msg }
interface Storage { write(key, val); read(key) -> val }

// two adapters per port, wired in at startup, never inside the core
production := App(RealClock(), OsRandom(),        TcpNetwork(),     DiskStorage())
simulation := App(SimClock(),  SeededRandom(seed), SimNetwork(seed), SimStorage(seed))

Two more habits fall directly out of the same discipline. First: explicit clocks and RNGs, passed in as arguments or constructor parameters, never grabbed ambiently from a global — "what time is it" and "give me a random number" have to be questions the core asks its Clock and Random ports, never questions it answers by calling a language runtime's built-ins directly. Second: no hidden global state — no singleton holding a real socket, no static timer thread started at import time, no background goroutine touching the OS clock on its own schedule. Every one of those is a door that bypasses the ports entirely, and Chapter 2 already named what happens next: the determinism contract has an eighth-leak problem, and hidden global state is where the ninth one hides.

Watch out One raw socket call, one direct os.random(), one background timer thread reached for out of convenience instead of through a port — and the whole system's determinism leaks through that one spot, silently, the same way one uncontrolled clock read broke replay in Chapter 2. Architecture doesn't prevent this by being clever; it prevents it by making the direct path harder to reach for than the port.

But if virtualization-first needs no code changes, why would anyone choose simulation-first?

Because "no code changes" isn't the same as "no cost" — it's a different bill, sent to a different address. Building your own deterministic hypervisor (or adopting one) is a serious systems undertaking, and even once it exists, coarser control at the syscall/VM boundary makes it harder to name an internal, application-specific fault precisely — you can starve a thread or drop a packet, but you can't as easily say "fail exactly this write, inside exactly this transaction." Simulation-first pays its cost earlier, in architecture, and gets that precision back: the fault injection happens at the exact port the application's own logic calls, so you can name faults in the application's own vocabulary. Neither bill is smaller — they're just due at different times, to different teams, for a different kind of precision.
