Chapter 04 · Part II — Building It

Building the Simulator

Chapter 3 drew the box labeled simulation and left it deliberately closed — a set of ports on one side, seeded adapters on the other, and a promise that whatever ran inside was deterministic. Fair enough for an architecture chapter. But "deterministic" isn't a property you get by wishing for it; it's a property of a specific, buildable machine. Open the box. Inside is almost always the same three moving parts: a queue that holds the future, a way of running many things at once without needing the operating system's help, and a family of small, honest lies about the network, the disk, the machine, and the clock. Build those three things well and the promise from Chapter 3 — replay this seed, get this exact run, forever — just falls out of the mechanism. Build them carelessly and the promise quietly stops being true, usually with no error message to tell you so.

The engine room: one queue, sorted by time

Start with the simplest possible question: how does a simulator know what happens next? Not "next" in wall-clock time — there is no wall clock in here — but next in the story the simulation is telling. The answer, in essentially every deterministic simulator anyone has built, is a discrete-event scheduler: a priority queue of pending events, each stamped with a timestamp, always sorted so the earliest is on top. The loop is almost embarrassingly small. Pop the earliest event. Set the clock to its timestamp — jump, don't count up to it. Run whatever handler is attached to that event. That handler does its work and, as a side effect, schedules zero or more new events further out on the timeline. Repeat.1

Notice what just happened to "time." It stopped being a thing the host machine's wristwatch tells you and became a position in a queue. If nothing is scheduled for the next four simulated hours, the simulator doesn't sit there for four hours, or even four milliseconds — it sets the clock to the next timestamp and keeps going. This is the mechanism behind FoundationDB's roughly 10-to-1 ratio of simulated time to real time, and it's also why a 30-second timeout, inside a simulation, costs the scheduler nothing but a single queue pop: the clock simply jumps ahead 30 seconds and whatever was waiting on it fires right on schedule.1,9

There's a second queue hiding in that description, and it matters just as much as the first. Real distributed systems run many logical processes at once — nodes, connections, background tasks — and a simulator has to decide, on every step, which one goes next. Simulators like madsim (and RisingWave, which is built on it) keep a ready-queue of every runnable task and deliberately drain it in a near-random order — closer to "first-in-random-out" than strict FIFO — rather than always resuming things in the order they became ready. That's not an implementation accident; it's the whole point. A simulator that always resumes actor A before actor B will never, ever find the bug that only happens when B gets there first. Seed-shuffling the ready-queue is what turns "one deterministic run" into "many different deterministic runs, each one still perfectly replayable."6

// two queues working together, per the diagram above
ready = seeded_shuffle(runnable_coroutines)   // order drawn from the seed
for task in ready:
  task.resume()                 // runs only until its next await/wait()
  // resuming may push new network/disk/timer events below

loop:
  event = event_queue.pop_min() // earliest timestamp wins, always
  clock = event.timestamp       // jump, never sleep
  effects = handlers[event.kind](state, event)
  for e in effects: event_queue.push(e)
Key idea The scheduler doesn't know anything about networks, disks, or crashes. It knows exactly one thing: pop the earliest timestamp, run its handler, repeat. Every fault type in the rest of this chapter is just a different kind of event a handler decides to schedule.

Actors, state machines, and why none of this needs a real thread

The engine room raises an obvious question: if there's no real OS thread scheduler in here, what is being "resumed" and "suspended" every time the loop turns? The answer is something you've probably already used without thinking about it this way: an async function. When a language compiles an async/await function — or, equivalently, one of FoundationDB's Flow ACTOR functions — it doesn't produce a normal subroutine. It produces a small object, a state machine, that holds the function's local variables plus a marker for exactly where it's paused. Calling it again doesn't start over; it resumes from that marker. Suspension only ever happens at an explicit point the code names — await, or Flow's wait() — never in the middle of an ordinary statement the way a real OS could interrupt a thread at any instruction at all.11,2

That one property — suspend only where you say so — is the whole trick. Because the simulator itself is the thing deciding which suspended coroutine to resume next (by draining its seeded ready-queue), and because a coroutine can only ever be resumed at one of its own named suspension points, the entire interleaving of dozens of concurrent "actors" — each one usually standing in for one simulated node, connection, or background task — becomes a pure function of the seed. There's no real thread scheduler left anywhere in the loop that could inject a timing decision the seed didn't make.2,1

But if the network, the disk, and the clock in this whole chapter are all fake, how is any of this telling us something true?

Because "fake" is doing very specific, narrow work here. The environment is substituted — the actual bytes on the wire, the actual sectors on a platter, the actual reading of a hardware clock. The application code running on top of it is not. An actor in this simulation is the same compiled code, making the same decisions, holding the same state, that would run in production — it just can't tell that the "network" answering its wait() is a scheduled event instead of a NIC. And every one of the "lies" the rest of this chapter builds — a dropped packet, a torn write, a node that pauses for half a second — is a thing a real machine can genuinely do. The simulator's job isn't to invent physically impossible behavior; it's to make the rare-but-real behaviors happen on command, and often, so the one line of code that mishandles them doesn't have to wait for a data center to get unlucky first.

Simulating the network: delay, loss, duplication, reordering, partitions

A simulated network is, underneath, almost insultingly simple: a connection is two in-memory buffers instead of a socket, and every decision about what happens to a packet is a scheduled event or a boolean check, driven by the same seeded PRNG as everything else. FoundationDB's simulator (Sim2) hands out Sim2Conn objects in place of real sockets; when a packet is "sent," the simulator schedules its delivery as a future event, with the delay drawn straight from the seed — that's latency, handled. Reordering and duplication are just what happens naturally when independent packets on the same or different connections get independently-random delays: two packets sent in order can easily be scheduled to arrive out of order, and nothing has to specially code that in.3

Partitions and packet loss work the same way, one level up: before delivering a packet, a connection consults a shared "clogging" table for the link between its two endpoints, and simply refuses delivery if that link is currently clogged. A network partition, at this level, is nothing more exotic than a boolean flipping to true for a while.3 TigerBeetle's VOPR does the equivalent job in its own vocabulary — it drops packets, reorders them, and partitions the network, all tuned by the same per-run seed that also drives its storage faults.4

// FDB Sim2, paraphrased: a "connection" is two buffers plus one check
function deliver(conn, packet):
  if clogging.disconnected(conn.from, conn.to):
    return                       // dropped — this IS a partition, here
  delay = rng.next_delay()       // seeded latency
  schedule_at(clock + delay, () => conn.to.inbox.push(packet))

One distinction is worth being precise about, because it's the difference between a fault model that finds real bugs and one that only finds toy ones: a symmetric partition (the link is down, in both directions, full stop) is not the same fault as an asymmetric one, where a node can send but not receive, or vice versa. Real networks do this — a firewall rule, a one-way routing failure, a NIC that can transmit but whose receive queue is stuck. And asymmetric partitions can reach failure modes a symmetric-only model never will.

Watch out If your fault model can only sever a link both ways at once, you are testing a real but narrower slice of what networks actually do. Give your simulator the ability to clog one direction of a link independently of the other — it's a small change to the "clogging" check above, and it's the difference between finding a livelock and never being able to.

Simulating the disk: more than just "unavailable"

It's tempting to model a disk fault the same crude way people first model a network fault — up or down — but a real disk fails in more specific, more interesting ways than that, and a simulator that only knows "unavailable" will never exercise the code paths written for the others.

Simulated disk faultWhat it mimics
Partial / torn writePower is lost mid-flush; only some of the bytes or sectors in a write actually land on the platter before the disk cache empties.12,3
Corruption of durable dataBit rot, a firmware bug, or a misdirected write silently changes bytes that were already successfully written and acknowledged.4
Added latencyA busy, throttled, or degraded drive taking far longer than usual to service an operation.
Disk full (ENOSPC)The write call is intercepted and made to return an out-of-space error on demand — no need to actually fill a real disk to test how the caller handles it.12

FoundationDB deliberately reaches for the first row on this table specifically because it mirrors real hardware: the corruption it injects on a simulated crash targets unsynchronized writes, the ones a real disk's cache hadn't finished flushing yet — exactly the data a real machine loses when the power drops mid-write.3 TigerBeetle's VOPR took a similar path from a different starting point: it originally only produced torn writes indirectly, as a side effect of simulating a crash mid-operation, and was later extended to inject read and write corruption directly on the storage path — independent of any crash — at seed-controlled probabilities, which is a strictly larger fault surface than "crashes sometimes tear a write."4

Notice, too, that FoundationDB doesn't stop at one disk on one machine. The same run can inject fail-stop failures and reboots at the level of a single machine, a whole rack, or an entire simulated data center, layered together with the network faults from the previous section — so one simulated run can plausibly reproduce a correlated, multi-machine outage, not just one node quietly dropping out while everything else hums along.3,13

Key idea "The disk failed" isn't one fault — it's a family of them, and each member of the family exercises different code. A durability bug and a corruption bug and an out-of-space bug are three different bugs; a simulator that only knows how to make the disk vanish will only ever find one kind.

Process and node lifecycle: crash, pause, reboot, slow, reconfigure

Everything above happens to data in flight or at rest. This section is about what happens to the process itself. A crash-stop fault is the blunt one — a node simply disappears, mid-operation, with whatever was in memory gone and whatever was on simulated disk exposed to exactly the partial-write faults from the section above. A reboot is the more interesting cousin: the process comes back, and now has to recover from whatever state its disk was actually left in — which is precisely why the disk-corruption faults need to be wired to the crash faults, not treated as unrelated dials.

Two subtler lifecycle faults deserve equal billing, because they don't crash anything at all — they just make a process behave strangely while it keeps running. Antithesis's taxonomy names both: thread pausing simulates one individual thread unexpectedly taking a long time, by pausing it for a short, seed-chosen span, so that threads interleave differently on every run without any code changing at all. CPU modulation goes a layer deeper still — it changes the simulated processor's effective clock speed, and the relative cost of different low-level operations, which perturbs the order concurrent work completes in without touching a single line of the guest's source.7,8 Both are, in the end, just more finely-grained versions of the same idea from the engine room: perturb which event lands first, seeded and on purpose, instead of hoping a real machine happens to schedule things unluckily.

Configuration change is the lifecycle fault that's easiest to forget precisely because it isn't dramatic — a node's tuning parameters, feature flags, or cluster membership changing while the system is running. It matters for the same reason everything else in this chapter matters: production configuration changes happen concurrently with real traffic and real faults, and a simulator that only ever changes configuration between clean, quiescent runs will never exercise the code path that has to handle a config flip landing mid-request.

Time semantics: timers, deadlines, leases, and clocks that jump

Come back to the engine room one more time. A lease expiring in ten seconds, a request's deadline, a heartbeat timeout — none of these are special to the scheduler. They're just another entry in the same timestamp-ordered queue as a network delivery or a disk write completing. That's not a simplification for this book; it's the actual mechanism. Because a lease's expiry is data in the same queue as everything else, the simulator can jump straight to the instant it fires, inject a fault exactly at that boundary — a lease renewal that lands one tick too late — or place two competing deadlines in a dead heat and see which one the real code resolves first.1,9

Clock skew is a related but distinct fault from clock jumps. A shared "virtual time" for the whole simulated system (Antithesis's approach) means a clock-skip fault moves every node's view of time together, which is the right model for testing "what happens when the whole system's clock suddenly jumps forward" — a leap second, a bad NTP sync, a VM pause on the host. Testing skew — one node's clock running fast or slow relative to the others — needs the simulator to give each simulated node its own, independently-adjustable clock instead of one shared one; both are real hardware behaviors, and they exercise different assumptions in your code.7

One last, very practical question, since this chapter has been about building the thing: where does the interception actually happen in real code? Two answers show up in the wild. Some runtimes go beneath the application's own async layer entirely — one documented approach for async Rust overrides the libc symbols a runtime ultimately calls through, getrandom/ getentropy for randomness and clock_gettime for time — so determinism is enforced below the application, not just at its ports. Others build it into the runtime itself: Tokio exposes a first-class "paused" clock mode where simulated time only advances on an explicit sleep() call, so code that asks tokio::time::Instant for the time — rather than the OS's std::time::Instant — automatically observes the controlled clock, no port required.10
