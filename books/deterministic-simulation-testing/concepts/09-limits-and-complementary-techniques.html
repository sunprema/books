Chapter 09 · Part IV — Living With It

Limits & Complementary Techniques

Every tool this book has built so far does one job: take the terrifying combinatorics of a distributed system's failure modes and shrink them down to something one person can explore on a laptop, on demand, forever. That's a genuine superpower, and by now you should believe it. But a simulator that faithfully catches everything you thought to put inside it will just as faithfully stay silent about everything you didn't — and silence looks exactly like safety until the day it isn't. This chapter draws that boundary honestly: what a deterministic simulator structurally cannot tell you, no matter how well you build it, and what you still have to run — alongside it, not instead of it — before you get to believe the system is actually safe.

The boundary the simulator can't see past

Go back to chapter 3's central move: you take the real application, and at a handful of well-chosen seams — the clock, the RNG, the network, the disk — you swap the real thing for a seeded stand-in. Everything on the near side of those seams is real code, exercised for real, and simulation's authority over it is total. Everything on the far side — the actual kernel, the actual disk firmware, the actual network card, a third-party service you only ever reach through an adapter — was never run at all. It was replaced. A simulator cannot find a bug in something it never executed, and that's not a flaw to fix; it's the definition of the technique.

FoundationDB's own documentation says this plainly, and it's worth taking at face value from the project that has leaned on simulation harder than almost anyone: simulation is not able to reliably detect performance issues, such as an imperfect load-balancing algorithm, and it is unable to test third-party libraries or dependencies — or even first-party code that wasn't written against Flow, the actor framework simulation is tightly integrated with.1 Notice the shape of that admission: it isn't "simulation has a bug." It's "simulation, working exactly as designed, has a boundary" — and FoundationDB's response wasn't to widen the boundary until it disappeared. It was to minimize how much of the system lives outside it, by avoiding external dependencies wherever it reasonably could.1

The performance blind spot deserves its own moment, because the mechanism is almost elegant. A discrete-event simulator (chapter 4) advances its clock by jumping straight to the next scheduled event whenever nothing is happening — that's exactly what lets a night of simulation explore vastly more of the state space than the same wall-clock hours would allow in the real world. But that trick has a cost: the simulator's notion of "elapsed time" was never built to be a faithful stand-in for real latency or real throughput under real contention. The very feature that makes simulation fast at finding correctness bugs is the same feature that makes it unreliable for judging whether the system is fast enough.1,2 A clean simulated run is evidence about correctness. It is not evidence about performance, and treating it as such is a category error, not an optimistic rounding.

Watch out "We didn't simulate it" and "we tested it and it was fine" are not the same sentence, even when they're said in the same breath. A third-party payment API, a managed message queue, a cloud provider's load balancer — anything reached only through an adapter is, by construction, outside what your seeds have ever exercised.

The simulation gap, and why fidelity isn't free

Robotics and autonomous-vehicle testing have a name for this that's worth borrowing: the reality gap, or sim-to-real gap — the mismatch between what a simulator's physics and sensor models predict and what the real hardware actually does. The same structural idea applies here, and this book will call it the simulation gap: your simulated network, disk, and scheduler are chosen abstractions with a cost model that approximates reality, and the simulation gap is exactly the set of real-world behaviors that abstraction was never built to reproduce.3 A higher-fidelity simulator narrows that gap, but fidelity is never free — every extra behavior you model is more implementation to write, more surface to keep correct, and more assumptions about the real world baked into code that itself needs to be right.

Chapter 7 told the story of "fsyncgate" — the Linux kernel behavior where a failed fsync() can silently mark the affected dirty pages clean, so a later retry reports success without the original write ever having been made durable — and of Pillai et al.'s 2014 study, which found hundreds of crash-vulnerabilities by testing how real filesystems actually behave against the POSIX contract applications assumed.4 Notice where that knowledge came from: nobody simulated their way to the discovery that fsync() lies. Someone had to run real code against a real kernel and watch it lie. A simulated disk can faithfully replay a lie once a human has told it the lie exists; it cannot discover a lie it was never told about. The fault menu chapter 7 built is only as good as the real-world observation that populated it — and that observation has to come from outside the simulator, every time.

Real hardware exposes fault classes a simulated or even containerized environment can't produce at all, for a mundane reason: some faults need a real thing to fail. Jepsen's own tooling documentation notes that containers — LXC and Docker alike — can't change their system clock, so testing anything that depends on clock skew requires running nodes as separate physical machines or full VMs instead.5 The fault doesn't merely go untested in a container; it structurally cannot exist there, because there's no real clock underneath to desynchronize. The same logic reaches all the way down: real disk controllers, real NICs, real CPUs under real thermal and power constraints can all fail in ways nobody wrote into any fault model, because nobody has observed them yet.

Key idea A simulator can only inject the faults someone already knew to describe to it. Discovering new fault classes is not a simulation problem at all — it's an observation problem, and it only gets solved by pointing something at the real world: real hardware, a real kernel, real production traffic.

A map of complementary techniques

None of this is an argument against simulation — chapters 1 through 8 made the case for why it earns its place. It's an argument for a map: five techniques, each covering ground the others structurally can't, deliberately overlapping at the edges rather than pretending any one of them is sufficient alone.

TechniqueStructurally catchesStructurally misses
Deterministic simulation (this book) Concurrency/correctness bugs across a huge simulated state space, exactly replayable Real performance, third-party black boxes, real hardware/OS behavior nobody told it about
Real-cluster performance testing Actual throughput, latency under real contention, real load-balancing behavior The deep, rare interleavings and fault combinations DST explores by the thousand
Hardware fault testing (Jepsen-style nemeses) Real clock skew, real kernel/NIC/disk faults, faults that need real hardware to exist at all DST's state-space breadth; slow and comparatively expensive per run
Production observability & chaos-in-prod The actual live system under actual live traffic; unknown-unknowns no model anticipated A controlled, minimized, replayable trace — a production failure is often gone the moment it's over
Formal methods (TLA+ and similar) Exhaustive correctness over an abstracted model, before a line of implementation exists Implementation bugs — a correct spec can still have an incorrect implementation — and any performance signal at all

Datadog's engineering team ran exactly this pipeline end to end while validating Courier, their message-queuing service, and the story is the cleanest illustration this chapter has of the techniques actually meeting in the middle. A TLA+ model of the protocol let their checker explore 5,515,710 distinct reachable states without finding a violation of a "no lost messages" property — but staying tractable meant abstracting away real implementation details, including the specific concurrency-control mechanism the real storage layer used underneath.6 A lightweight discrete-event simulation then predicted realistic performance under node-failure scenarios — something the formal model had no way to surface, since it doesn't reason about performance at all — and revealed an oscillating-throughput pattern caused by CPU load redistributing across surviving nodes. Finally, chaos testing against the real, running implementation confirmed that production behavior actually matched what the simulation had predicted.6 Three techniques, three different questions: formal modeling asked "can this go wrong at all?", simulation asked "how much would it cost if it did?", and chaos testing asked "does the real system actually behave the way both models assumed?" Drop any one of the three and that particular question goes back to being unanswered, not answered by whichever technique remains.

Cost, ROI, and an incremental roadmap for an existing service

Everything in this book reads more naturally as a green-field design decision than a retrofit, and that's not an accident of presentation — retrofitting DST onto a system that already ships is genuinely harder than designing for it from day one. Every hidden source of nondeterminism has to be found and routed through a seed-controlled seam, and missing even one — a stray real-time call, an unseeded library RNG buried three dependencies down — can quietly undermine determinism for the whole system, not just the code path that used it.7 Tools that simulate at the hypervisor or OS boundary instead of the source level (chapter 3's deterministic-hypervisor architecture) sidestep that retrofit entirely, at the cost of a coarser, black-box fault surface — the same trade-off chapter 3 drew between simulation-first and virtualization-first, now viewed specifically through an adoption-cost lens rather than a fidelity one.

The payoff, when it lands, can be substantial: WarpStream has reported simulating roughly 280 logical hours of their system's behavior within about 6 hours of real wall-clock time using a deterministic hypervisor.8 Treat that as illustrative of the throughput advantage simulated, accelerated time gives state-space exploration — not as a universal constant. It's one workload, on one team's infrastructure, at one point in that tool's development; your own ratio will depend entirely on how much of your system's real time is spent waiting versus computing.

Concretely: pick the subsystem whose bugs are most expensive — the one handling money, consensus, or data you can't afford to lose — and wrap only that one behind a port/adapter boundary with an explicit injected clock and RNG (chapter 3). Seed a small generative workload against it and write exactly one safety oracle worth trusting (chapters 5 and 6) before adding anything fancier. Add a small, realistic fault menu grounded in faults you already know are real (chapter 7), and wire the whole thing into CI as a fast smoke tier (chapter 8) so it earns its keep on every merge. Only then widen the simulated surface module by module — the same incremental, boundary-by-boundary substitution the "strangler fig" pattern uses for legacy-system migrations generally, aimed here at simulation coverage instead of a rewrite9 — while layering the other four techniques from this chapter's map back in around the growing simulated core: real-cluster performance testing before a launch, hardware fault testing for anything that touches real disks or real clocks, a formal spec for the one invariant you'd be most embarrassed to get wrong, and production observability running underneath all of it, permanently, as the ground-truth check that nothing above was fooling itself.

If a system passes a thousand nights of DST and has never once been exercised in production or on real hardware, do you actually know it's safe?

No — not fully, and not for a subtle reason. It's the plain one this chapter opened with: a thousand simulated nights only ever tell you about the thousand nights' worth of world the simulator was built to model. Real hardware, a real kernel, real third-party dependencies, and real production traffic patterns are, by construction, outside that model. A clean DST run is strong evidence about correctness inside the boundary. It is silent — not reassuring, silent — about everything outside it.

Try this
  1. Think of a real production incident you know of that was caused by real hardware, OS, or third-party behavior — not a race condition or a scheduling bug. Would a deterministic simulator, however well built, have had any realistic chance of finding it before it happened? Write down exactly why or why not, in terms of which side of the simulation boundary the cause lived on.
  2. Take a system you actually work on and fill in this chapter's five-row technique map for it: for each of DST, real-cluster performance testing, hardware fault testing, production observability, and formal methods, name one concrete bug class from that system each technique would catch, and one it would structurally miss.
  3. Sketch a one-page incremental adoption roadmap for a real, already-shipping service: name the first subsystem you'd wrap behind a port/adapter boundary, the first oracle you'd write for it, and which one of this chapter's four complementary techniques you'd layer in second — and defend why that one, and not one of the other three, earns the second slot.
