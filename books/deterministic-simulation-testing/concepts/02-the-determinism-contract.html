Chapter 02 · Part I — The Problem & The Idea

The Determinism Contract

Last chapter ended on a promise: one seed, one hostile timeline, one exact replay. It's a beautiful promise. It is also, if you look at it sideways, a slightly absurd one — because your program is running on a real machine, with a real clock ticking, a real kernel handing out CPU time however it feels like, and a real network dropping packets on its own schedule. None of that is under your control. So how can replaying "the same seed" possibly replay the same run?

The honest answer is: it can't, unless you make it a rule. Not a suggestion, not a best-effort — a contract. Every single thing your program's behavior could depend on, other than its own logic, has to be handed to the simulator and driven from the seed. Miss one, and the promise from Chapter 01 quietly stops being true — not with an error, just with a replay that drifts a little more each time, until one day it doesn't reach the bug at all.

Eight leaks, one contract

Think about everything an ordinary running program reaches out and touches that isn't its own code. The wall clock. A timer. The OS's random-number generator. Whichever thread the scheduler decides to run next. Whether a network packet arrives now, later, twice, or never. Whether a disk write actually landed or just looked like it did. The program's own process ID. A response from some other service across the internet. Every one of those is a door through which the outside world's chaos walks straight into your program's decisions — and a test that doesn't control every door isn't testing your logic, it's testing today's weather.1,4

Notice the shape: none of these become absent. They become owned. The clock still ticks, the coin still flips, the packet still drops — the only thing that changes is who's holding the dial.

Scheduling: the sneakiest leak

Of the eight, scheduling is the one people forget, because it doesn't look like an input. You didn't hand your program a "scheduling order" — the OS just decided one, silently, based on things like how many other processes happen to be running on the machine right now. Two runs of the exact same binary, same inputs, same everything, can still interleave two threads in a different order, purely because the kernel felt like it. That's a whole extra source of randomness you never asked for and can't see.1

FoundationDB's answer is to not use real OS threads for its core logic at all. Its actor language, Flow, compiles ordinary-looking C++ functions into cooperative state machines: an actor wait()s on a future without blocking anything else, and control only ever passes at those explicit hand-off points. Run that under the simulator and there's exactly one thread, making decisions in an order the seed picks — the same production code, but now the "who runs next" question has an owner instead of a kernel rolling dice.2

Key idea You can't make a scheduler deterministic by asking it nicely. You make it deterministic by not using a real one — swap the OS's opaque, load-dependent scheduler for a single-threaded, cooperative one where "what runs next" is a question with a seed-derived answer, not a kernel-derived one.

Randomness doesn't disappear — it gets a name

Here's a place people trip on the word "deterministic": they hear it and picture a simulation with all the randomness switched off. That's backwards. A simulation that never explores anything unexpected is useless — the entire value of DST is running through a huge variety of hostile schedules, fault combinations, and inputs. The trick isn't removing randomness. It's seeded pseudo-randomness: every "random" decision, in every subsystem, is drawn from one PRNG that was itself started from one recorded number. Randomness and reproducibility were never actually in tension — they only look that way if you've never separated "unpredictable to a human reading the code" from "unpredictable given the seed".

FoundationDB leans on this as hard as it can: every simulation run randomizes the cluster size and configuration, the workload it throws at the database, which fault-injection parameters are active, and which rare-but-legal "buggification" points get triggered — cluster size, workload, and faults, all pulled from the same seeded stream.6 Nothing about that is timid. It's maximally random, on purpose — it's just random from a starting point you wrote down.

// one seed, every "random" decision in the run
rng = PRNG(seed)
clock.set(rng.next_offset())   // virtual wall clock, not gettimeofday()
scheduler.order(rng)           // which actor/event runs next
network.decide(rng)            // delay, drop, duplicate, reorder this packet?
disk.decide(rng)               // latency, partial write, corruption this op?

Logical time, virtual time, and the discrete-event jump

If the clock is simulated, what does "time" even mean inside the simulation? Not what your wristwatch means by it. A deterministic simulator is almost always a discrete-event simulation: instead of a clock ticking forward in small, even steps, a scheduler keeps a queue of pending events sorted by timestamp, and time advances in jumps — straight to whichever event is earliest. If nothing is scheduled for the next four hours of simulated time, the simulator doesn't wait four hours, or even four milliseconds. It just sets the clock to the next timestamp and keeps going. Time, here, is a property of the program's own logical schedule, not of the wall clock the host machine happens to be running on.

loop:
  event = queue.pop_min()      // earliest timestamp, not "soonest wall-clock"
  clock = event.timestamp      // jump the logical clock forward, no sleeping
  effects = handlers[event.kind](state, event)
  for e in effects: queue.push(e)   // scheduled relative to `clock`

This isn't a new trick invented for databases. Distributed systems solved a cousin of this problem back in 1978: Leslie Lamport's logical clocks give every event a counter, incremented locally and carried on outgoing messages, satisfying one rule — the clock condition — if event a causally happens-before event b, then C(a) < C(b).8 A discrete-event scheduler is doing the same underlying move: replace "when did this really happen, on someone's wristwatch" with "what order does the program say this happened in" — because the second question is the only one a replay can actually answer.

Key idea Virtual time isn't just a determinism trick — it's a speed trick. FoundationDB runs its simulations at roughly a 10-to-1 ratio of real to simulated time;1 TigerBeetle's simulator farm accelerates simulated time by roughly 700×, turning a few seconds of wall-clock CPU time into tens of minutes of exercised behavior.3 Decoupling the clock from the wristwatch is what makes exploring thousands of hostile timelines a nightly job instead of a decade-long one.

What has to survive a run — and the seed's expiration date

A seed alone replays a schedule. To turn a simulated failure into something a human can actually debug, you generally persist more than that: the seed, the configuration, the workload, and the fault schedule that produced the run, plus — for the debugging step itself — the resulting event trace or log. Some simulators go further and check state snapshots directly: TigerBeetle's replicas are designed to write byte-for-byte identical data files once caught up, and its storage checkers verify exactly that across simulated runs, so "did every replica actually converge" is something the simulation can assert on, not just hope for.3

But the contract has a quiet asterisk: replay is a guarantee about the seed and the code, not the seed alone. Change the code upstream of a failure — add one new random draw, reorder two existing ones — and every later value the PRNG stream produces shifts. Same seed, different universe. That's why TigerBeetle ties reproducibility to the seed plus the exact Git commit: replaying an old seed against a new commit isn't guaranteed to reach the same state at all.3

replay — the seed's expiration date 
$ dst replay --seed 0x9f2a --commit 4a1c9de
> identical trace, identical failure

$ git checkout main && dst replay --seed 0x9f2a --commit 4a1c9de
> commit mismatch (HEAD is 7e2a01f) — replay not guaranteed
> re-running anyway... trace diverges at event 41
> recommendation: pin this scenario as a regression test, not a seed

So the practical move, once a seed finds something real, is to stop depending on the seed continuing to find it. Convert the failing scenario into a concrete, permanent regression test — the seed got you there once; the test is what keeps you there.7 That's the same idea Chapter 01 closed on, sharpened: a replayable failure is only durable for as long as you treat it as perishable and pin it down before the code moves on without it.

Watch out A seed that reproduced a bug yesterday is not a permanent asset. It's a lead. Convert it into a test before the next commit quietly revokes it.

But why does partial control equal no control?

Suppose you hand seven of the eight leaks to the seed and leave the disk's latency to real hardware, because "it's probably fine." Now run the same seed twice. Seven sources produce identical decisions both times — and the eighth, real disk latency, doesn't. The moment those two runs diverge, which one is the "true" replay? You can't tell anymore, because you no longer know whether a difference in outcome came from the bug you're chasing or from the one dial you left to chance. That's the whole reason this has to be a contract and not a best-effort policy: determinism isn't a spectrum you can be mostly on. The instant one source of entropy sneaks back in uncontrolled, you've lost the ability to tell replay from coincidence — and you can't get that ability back by controlling more of the other seven harder.

Try this
  1. Your team's simulator seeds its RNG correctly, but one code path calls a hardware timestamp counter directly to log a "high-resolution" duration. What does this break, and why might it take weeks to notice?
  2. A teammate says "our replay is broken — same seed, different trace" right after merging a refactor that added a new random UUID generation earlier in the request path. Explain what happened to the PRNG stream, in one sentence.
  3. Why does a discrete-event scheduler jumping the clock forward in uneven leaps, instead of advancing it in small fixed steps, make simulated runs both faster and more accurate to what actually happens in production?
