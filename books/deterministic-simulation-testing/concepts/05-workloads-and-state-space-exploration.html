Chapter 05 · Part III — Exploring & Judging

Workloads & State-Space Exploration

Chapter 4 finished the machine. There's a queue sorted by time, a pack of actors that suspend and resume on command, and a network, a disk, and a clock that all lie to the application in small, controllable, physically-plausible ways. Turn it on right now and… nothing happens. A discrete-event simulator with nothing scheduled is just an expensive way to idle. Something has to walk in and do things — issue transfers, write records, kill a node, delay a packet — and that something is the workload. This chapter is about the two questions that follow from having a machine that can run any hostile timeline: what do we make it do, and out of the practically infinite number of hostile timelines available, which ones are actually worth the CPU?

Two ways to fill the machine: generated versus hand-authored

The most direct way to exercise a simulator is to write down, by hand, the exact sequence of operations you're worried about — upgrade the cluster while a transaction is in flight, kill the leader one tick after it accepts a write, that kind of thing. Call this a hand-authored scenario. It's precise, it's readable, and it's how you encode "we already know this matters." But it only ever tests what you already thought to write down. The other way is to describe the shape of a workload — "pick two random accounts and transfer a random amount between them, ten thousand times" — and let a pseudo-random generator, seeded like everything else in this book, fill in the details differently on every run. Call this a generative (or property-based) workload. FoundationDB structures both the same way: a Workload is a small class with a SETUP phase that loads initial data, an EXECUTION phase that issues load, and a CHECK phase that verifies an invariant and reports metrics — and a simulation run boots the cluster, runs every workload's SETUP one after another, then lets every workload's EXECUTION run concurrently, so several generative workloads collide in time exactly the way independent real clients would.1,2

// modeled on FoundationDB's SETUP / EXECUTION / CHECK workload phases
class TransferWorkload(Workload):
  def setup(self, cluster, rng):
    self.accounts = cluster.create_accounts(rng.randint(10, 1000))

  def execution(self, cluster, rng):
    // generative: a different, but seed-reproducible, sequence every run
    for _ in range(rng.randint(100, 10000)):
      src, dst = rng.sample(self.accounts, 2)
      cluster.transfer(src, dst, rng.randint(1, 100))

  def check(self, cluster):
    assert cluster.total_balance() == self.initial_total  // the oracle

Don't hear this as "generative workloads win." A hand-authored scenario is how you pin down a specific regression forever — the exact sequence that broke last Tuesday, replayed on every CI run until the heat death of the repository. A generative workload is how you find next Tuesday's bug, the one nobody has written down yet because nobody has thought of it yet. You want both, for the same reason a physicist wants both a specific experiment designed to test one hypothesis and a particle accelerator that just smashes things together and sees what falls out.

One seed, four dials

Here's the idea this whole book keeps coming back to, now made completely literal. Everything that makes one simulation run different from the next — which workload runs, what data it touches, which faults fire and when, what the cluster even looks like — is a decision made by pulling numbers out of one pseudo-random generator, seeded by one integer. The workload's own choices (which accounts, which amounts, how many operations) are not exempt from this; they're drawn from the very same seed as the network delay and the disk corruption from the last chapter. That's the whole trick behind "replay this exact run": there was never anything to remember except one number.

The space is too big to walk

Now the uncomfortable arithmetic. Every one of those dials is really several independent choices, and independent choices multiply, not add. Suppose your simulator can pick from 3 cluster topologies, 3 replication modes, 4 storage engines, a workload with just 5 meaningfully-different shapes, and a fault schedule with a modest 10 interesting places to inject something — each with, say, 4 fault types worth trying. That's already 3 × 3 × 4 × 5 × 10 × 4 = a few thousand combinations, before you've touched the actual scheduling question of which order dozens of concurrent actors interleave in, which is its own combinatorial factor on top. This is the same "state explosion problem" that has limited exhaustive model checkers since the 1980s: the reachable state space of a system with several concurrent processes grows exponentially in the number of processes, and no realistic amount of CPU time walks it in full.5 A DST harness is not exempt from this arithmetic just because it calls its states "simulation runs" instead of "model-checker states."

So the honest goal was never "cover the state space." It's "sample the state space in a way that's biased toward the parts likely to contain a bug, without giving up the ability to replay whatever you find." Everything from here to the end of the chapter is a technique for doing exactly that.

Sampling on purpose: coverage, novelty, and buggification

Pure uniform randomness is a start, but it wastes most of its budget re-visiting the common case. Two complementary fixes show up across the field. The first is coverage-guided steering: instead of resampling blindly, watch which lines of code (or, for a whole distributed system, which combinations of scheduling decisions, network events, and injected faults) a run actually touched, and bias the next run toward territory the search hasn't reached yet. Antithesis frames its own version of this as applying fuzzing's central trick — observe coverage, steer toward the unexplored — to an entire cluster of real processes at once, by mutating scheduling and fault decisions rather than input bytes; the vendor's own framing is that this turns an otherwise-exponential search into something closer to polynomial.6,7

The second fix is more surgical, and it's FoundationDB's contribution to the vocabulary: buggification. A developer marks one specific line as "an interesting place to misbehave" with a macro called BUGGIFY: "this commit could plausibly fail here 1% of the time," or "this call could plausibly take ten seconds instead of ten milliseconds." Two things make this more than a fancy if (random() < p). First, which BUGGIFY call sites are even active is itself decided once per simulation run, drawn from that run's seed — so a given run either explores that corner or it doesn't, deterministically, and a different seed makes the opposite choice. Second, the outcome being selected is always something the system's contract already allows — a spurious-but-legal error a client is supposed to retry, a slow response within an already-documented timeout — not a violation of the contract itself. The point isn't to break the rules; it's to make the code hit the rare-but-legal corners of its own rules on command instead of waiting years for production to get unlucky.1

// BUGGIFY-style: whether this call site is even "live" this run
// is itself decided once, from the run's seed -- not re-rolled per call
if buggify_enabled("slow_commit", seed, p=0.01):
  def maybe_delay(rng):
    if rng.random() < 0.01:
      simulated_sleep(10.0)  // rare, legal, seed-reproducible
Key idea A 1-in-100 probability does not mean "unlikely to matter." Run a hundred thousand seeds overnight — a continuous seed farm, like the fleet of machines TigerBeetle's VOPR runs around the clock, does exactly this9,10 — and the 1-in-100 corner fires roughly a thousand times. The probability controls how often one run visits the corner; the seed count controls how often it gets visited at all. Low per-run probability and high overall coverage are not in tension — that's the entire reason cheap, fast simulated time (Chapter 4) matters as much as it does.

Swarm testing: vary the whole cluster, not just the operations

There's a subtlety in random testing that's easy to miss: giving every run access to every feature isn't obviously the best way to find bugs, and it can actively be the worst way. Groce et al.'s 2012 swarm testing paper found that deliberately omitting a random subset of available features from each individual test — rather than letting every test draw from the full set — measurably increases both coverage and fault-finding: in one week-long experiment against a collection of C compilers, swarm testing found 42% more distinct crashing bugs than the same random tester's heavily hand-tuned default configuration. The mechanism is intuitive once you see it: some features actively mask or crowd out the behavior that triggers a different bug — a pop call can prevent a stack's overflow-detection logic from ever firing, purely by keeping the stack short.4

Applied to a whole DST harness, "swarm" stops meaning just "which operations this test calls" and starts meaning "which slice of the entire system this run even is." FoundationDB's SimulatedCluster does exactly this at cluster scope: each run draws its own random topology (1–5 datacenters, 1–10+ machines each), its own storage engine (memory / ssd / redwood), and its own replication mode (single / double / triple) from the seed — so no two runs, even back to back, are exploring quite the same corner of the system.3 Generalize that pattern and you get the swarm-testing menu for a DST harness:

Shrinking: from a monster seed to a one-line bug report

A seed that took ten million events and forty simulated minutes to fail is a terrible thing to hand to a teammate. Somewhere in those ten million events, usually, is a handful that actually matter, buried in a mountain that doesn't. Shrinking is the automated process of finding that handful. Classic property-based testing (QuickCheck's original approach) does this structurally: once a failing input is found, try smaller variants — shorter lists, smaller numbers via something close to binary search, dropped substructures — re-running the property on each candidate and keeping whatever smaller variant still fails, converging on a local minimum.8

But a DST run isn't really a data structure you can chop pieces out of and hope for the best — it's a causal sequence, where event 900 might only exist because event 12 happened first. Delete event 12 by itself and you don't get a smaller version of the same bug; you get a run that was never reachable at all. This is exactly the problem an alternative shrinking strategy — used by Python's Hypothesis, Haskell's falsify, Racket's RackCheck — sidesteps, and it happens to be the natural fit for DST specifically: instead of shrinking the generated structure, shrink the underlying sequence of random choices that produced it, then replay the same generator on the shortened sequence. Because a DST run's entire execution is already "generated" from one seed's stream of scheduling and fault decisions, minimizing a failing run is naturally this kind of choice-sequence shrinking: trim the seed's decision stream — fewer faults, an earlier-firing timeout, a shorter schedule — and replay through the same deterministic machine to confirm the bug survives. Every candidate, by construction, is still a legal execution, because it was produced by the same generator that produced the original.8

// shrink the seed's choice sequence, not a serialized fault list --
// every candidate replays through the same generator, so it's always legal
function shrink(choices, still_fails):
  best = choices
  for candidate in delta_debug_candidates(best):
    if still_fails(replay(candidate)):
      best = candidate   // keep shrinking from here
  return best

How do you know the shrunk-down run is really the same bug, and not some other, unrelated failure?

You don't, automatically — that's why the loop replays every candidate and checks it still trips the same oracle failure, not just "some" failure, before accepting it as smaller. This is also precisely why choice-sequence shrinking earns its keep over blind structural deletion: because every candidate is a real replay of a real (shorter) seed through the real deterministic machine, "does it still fail the same way" is a question the simulator can just answer, cheaply, the same way it answers it for any other seed. The manual fallback, when you don't have an automated shrinker at all, is the same intuition by hand — if a bug needs a list of 500 items, try 5, then 2, then 1, and see how far the failure follows you down.11

Watch out A minimized seed is a debugging aid, not automatically a good regression test. The whole point of Chapter 1's promise is that the original failing seed, unmodified, becomes a permanent, replayable CI case — keep it. The shrunk version is what a human reads to understand the bug; don't let "we minimized it" quietly become "we only kept the minimized one."

  1. A teammate proposes running every generative workload with every feature flag enabled on every seed, reasoning "more coverage per run is strictly better." Using the stack-overflow example from the swarm testing section, explain in your own words why that reasoning can be wrong.
  2. Sketch, in words, why a BUGGIFY-style fault (fires with probability p, decided once per run from the seed) is easier to reason about than a fault that re-rolls its own dice on every single call site invocation within one run. What would the re-rolling version make harder to replay?
  3. You have a failing seed that took 40 minutes and touched three simulated datacenters.
