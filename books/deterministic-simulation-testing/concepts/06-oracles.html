Chapter 06 · Part III — Exploring & Judging

Oracles: Deciding Whether a Run Is Correct

Last chapter we built something that can, on command, generate an almost unlimited supply of hostile timelines — different topologies, different workloads, different faults landing at different simulated instants, all of it reproducible from one seed. Turn that machine loose overnight and it will hand you back ten million completed runs by morning. Now ask the question we've been quietly dodging: ten million runs of what, exactly? Nothing about "the simulation finished" or "the process didn't crash" tells you whether any of those ten million runs was correct. Something has to look at what happened and render a verdict. That something is called an oracle, and this chapter is entirely about how you build one you can trust.

A crash is a symptom. It is not a verdict.

In software testing generally, this is an old and famous headache called the oracle problem: given a test case, how do you decide, mechanically, whether the output was correct? For a calculator, easy — check 2+2 against 4. For a distributed key-value store running ten thousand concurrent transfers under packet loss and disk corruption, "the expected output" isn't a number you can write down in advance. Nobody hand-computes what a correct execution trace should look like.1 So DST harnesses default to the cheapest oracle available — did the process crash, did it hang, did anything throw — and that default is dangerously weak, in both directions.

A crash is a signal, but notice what produced it: some assertion, somewhere, already knew what "bad" looked like and caught it. The crash is the symptom an oracle already built into the code produced; it was never the oracle itself. Flip it around and the real danger shows up: a run that neither crashes nor hangs is not proof of anything, unless something was actively watching for the specific bad outcome you're trying to provoke. Most of the correctness bugs that matter in a distributed system — a write silently vanishing, an ID reused, two replicas quietly disagreeing — do not crash anything. They just produce a wrong answer that looks, to an unwatched process, exactly like a right one. "It didn't crash" is the weakest oracle on the table, and it's also the one every naive test suite ships with by default.

The cheapest oracle: local assertions and runtime invariants

The most direct oracle you can write is one that runs continuously, inside the code, checking something that must always hold: a balance that must never go negative, a data structure that must never contain a cycle, a counter that must never decrease. FoundationDB leans on exactly this — most of its synthetic workloads carry built-in assertions verifying invariants that only correct transaction atomicity and isolation can maintain, and the workload's CHECK phase, run at the end of a simulated run, is where these get walked and verified.1,2 The version below is modeled on that pattern: a workload that maintains a linked chain of records and, in CHECK, walks the whole chain looking for exactly the kind of corruption a broken isolation guarantee would produce.

class ChainIntegrityWorkload(Workload):
  def check(self, cluster):
    // a local, always-on invariant check -- an assertion, not a search
    node = cluster.get(self.head_key)
    seen = set()
    while node is not None:
      assert node.key not in seen, "cycle detected -- isolation was violated"
      seen.add(node.key)
      node = cluster.get(node.next_key) if node.next_key else None
    assert len(seen) == self.expected_length, "chain is broken or truncated"

The appeal of a local assertion is that it catches corruption at the point it happens, or close to it, instead of forcing you to reconstruct what went wrong from a downstream symptom three thousand events later. The limit is right there in the name: it's local. An assertion only catches what you thought, in advance, to write down as "this must always be true." It has nothing to say about a whole class of bugs that only show up when you look at the entire history of what a distributed system did — which is the next, much harder, oracle.

End-to-end safety: does the whole history make sense?

Lamport's classic split gives every correctness property one of two shapes.3 A safety property says something bad never happens — no lost committed write, no double-spend, no two clients handed the same "unique" ID, no response delivered out of the order it was promised. A safety violation is provable from a finite prefix of the run: the instant the second client gets the same ID, safety is already broken, full stop, no matter what happens afterward. That's what makes safety properties checkable at all: you're always looking for one bad thing that either did or didn't occur in a fixed, already-recorded history.

The richest and hardest safety property most systems care about is linearizability: that the whole messy, concurrent history of operations against the system — overlapping in real time, arriving out of order, some of them left dangling by a crashed client — looks, to every observer, exactly as if each operation took effect atomically at some single instant between when it was invoked and when its response came back. Checking that isn't a lookup; it's a search. A history-checking tool takes the recorded log of every operation's start time, end time, and observed result, and asks: does there exist at least one legal sequential order — one operation at a time, consistent with everyone's real-time bounds — that reproduces every single observed result? Jepsen's Knossos checker does exactly this against a single-threaded reference model.4,5

function is_linearizable(history, model):
  // history: {op, start_time, end_time, invoked_args, observed_result}[]
  for order in real_time_consistent_permutations(history):
    state = model.initial()
    for op in order:
      (state, expected) = model.apply(state, op.invoked_args)
      if expected != op.observed_result:
        break  // this order doesn't work, try the next one
    else:
      return PASS(witness=order)
  return FAIL("no legal order reproduces every observed result")

That brute-force search does not scale: Knossos-style checkers commonly time out or run out of memory once a history passes a few hundred operations, because the number of real-time-consistent orderings to search grows combinatorially with history length — the same state-explosion arithmetic from the last chapter, here applied to orderings instead of schedules. That's what motivated Elle (Kingsbury & Alvaro, 2021): instead of searching for an order, Elle infers a dependency graph among the client-observed transactions and looks for a cycle in it — a cycle is a proof that no legal order can exist, found by graph traversal instead of permutation search. Elle checks histories of hundreds of thousands of transactions in tens of seconds, three or four orders of magnitude past what a search-based checker reaches.6

Safety propertyWhat "bad" looks like
No lost committed writesA write the system acknowledged is later simply gone.
No double-spend / uniquenessTwo clients are handed the same "exclusive" ID, balance, or lock.
OrderingA response arrives implying an order the real-time record can't support.
Linearizability / serializabilityNo single legal sequential order explains every observed result.

Liveness and recovery: the other half of correctness

Everything so far checks that nothing bad happened. It says nothing about whether anything good ever happens again. A cluster that partitions itself in half and then simply freezes, forever, refusing every request — but never corrupting a single record — passes every safety check in the previous section with flying colors. It is also completely useless, and DST needs an oracle for that failure mode too.

Key idea Lamport's other half of the split: a liveness property asserts that something good eventually happens — the system converges, recovers, serves the next request. Unlike a safety violation, a liveness violation can never be proven from a finite prefix: there is, formally, always more time left for the good thing to still occur. Which means an implementable liveness oracle can't wait for "eventually" — it has to pick a concrete bound and call the run stuck if the good thing hasn't happened by then.3 That bound is an engineering decision with a real trade-off, not a technicality: too short, and correct-but-slow recovery reads as a false bug; too long, and a genuine stall burns CPU for hours before anyone notices.

Two independent systems converge on the same shape of answer. FoundationDB checks recoverability by returning its simulated hardware environment — after injecting whatever failures were needed to break availability — to a state where recovery should be possible, then verifying the cluster actually gets there.1 TigerBeetle's VOPR simulator runs two explicit modes: a safety mode that fuzzes faults continuously and checks invariants as it goes, and, once a run's safety-mode timeout expires without the cluster answering every outstanding client request, a liveness mode that first heals every non-correlated fault — clears partitions, lets the cluster settle — and only then checks whether it actually recovers. Healing before checking is what separates "stuck because of a genuinely unrecoverable fault, like a permanent partition with no reachable majority" from a real liveness bug in the recovery path itself.7

A concrete bug that shape of check was built to catch: a replica broadcasts a view-change message and, hearing back from no one, keeps re-triggering further view changes on its own — a livelock where the cluster never settles back into normal operation and never processes another transaction. No safety property is ever violated; nothing bad happens. The system just quietly stops doing anything good, forever, and only a liveness watchdog notices.7

Watch out A cluster correctly refusing to make progress during a fault it genuinely cannot survive — a true network split with no majority on either side — is not a liveness bug. A liveness oracle that checks for recovery before the faults causing the stall are actually healed will flood you with false positives. Heal first, then start the clock.

When there's no simple invariant: reference models and metamorphic checks

Sometimes the correct answer genuinely can't be written as one assertion or one safety property — the logic under test is itself the specification, and there's no independent formula to check it against. Two more techniques cover that gap.

A reference model (or shadow implementation) is a second, deliberately simpler and independently-trusted model of what the system is allowed to do, run alongside the real one and checked against it continuously rather than only at the end. TigerBeetle's VOPR runs a StateChecker that hooks into every simulated replica and checks each state transition against a reference model the instant it happens, using cryptographic hash chaining to prove causality between transitions — a divergence is caught at the transition that caused it, not discovered later as a downstream symptom.8 This is the same idea as the workload CHECK phase from earlier in the chapter, generalized: instead of one hand-written invariant, an entire independent model of correct behavior runs the whole time.

Metamorphic testing sidesteps the oracle problem differently, for cases where you don't know either the "true" model or a clean invariant, but you do know how the output should relate to a transformed version of the input. The textbook example: you may not know the exact numeric output of sin(x), but you know it must equal sin(π − x) for any x — if it doesn't, the implementation is wrong, and you never had to know the "correct" value of either call.9 The DST analog: take a run that reached some final state, replay the same committed operations through a different valid fault schedule or interleaving, and check the two runs land on the same final application state — neither run's intermediate trace has to be independently "known correct" for the comparison itself to be a real oracle.

One vendor has turned this whole chapter into an SDK surface. Antithesis exposes two kinds of test properties: an Always property, which must hold every time the assertion executes anywhere across the run — the SDK form of the local invariant from the first section — and a Sometimes property, which only needs to be observed true at least once across the entire session. Sometimes properties aren't really correctness oracles by themselves; they're coverage oracles, confirming a rare fault combination or code path was actually exercised at all during a run, since a check that never fires can't meaningfully be said to have passed.10

If a run never crashes and never trips an assertion, have you verified anything — or only failed to look?

Only the second, unless one of the oracles in this chapter was actually watching for the specific bad thing you care about. This is worth sitting with, because it's the same trap in a new outfit every time: "we ran it and nothing broke" is a description of your test suite's blind spots, not evidence of correctness, right up until you can name the safety property, the liveness bound, or the reference model that was actually checking. An oracle that isn't specific to a claim isn't an oracle for that claim.
