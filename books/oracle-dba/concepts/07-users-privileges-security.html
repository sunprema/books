Part II — Build and Administer the Environment

Who Gets Which Keys

Real name: Users, Privileges, and Security

The order shop needs a program that reads and writes orders. It does not need a key to every door in the house. This chapter is about giving each person and each program the keys for their job, and no more, and being able to prove which keys they hold.

The problem

A program fails with a “not allowed” message. It is late. Someone hands it the master key “just for tonight.” Nobody takes it back. A year later a bug in that program wipes a table, or a stolen password opens the whole house. The error went away, and the risk stayed.

The question for this chapter: how do you give the access that is needed without giving access that nobody controls?

The parts: who, what, how

A person or program that can sign in is a “user”. Each user owns a set of things, such as tables, called a “schema”. A user may own nothing at all. A bundle of keys with a name is a “role”: hand out the bundle, not each key. A card of house rules for a user, such as how many wrong tries lock the door and how often a password must change, is a “profile”.

Keys come in two kinds. A key for an action anywhere in the house, such as CREATE TABLE, is a “system privilege.” A key for one thing, such as reading orders.order_lines, is an “object privilege.” Watch for any key with ANY in its name. SELECT ANY TABLE reads every table in every home you can reach, including other people’s.

Master keys, cut into smaller keys

Long ago there was one master key, “SYSDBA”, and whoever held it could do anything. Newer houses cut it into smaller keys, each for one job: SYSOPER to start and stop the house, SYSBACKUP to make and use backups, SYSDG for the copy-keeping team (Data Guard), and SYSKM for the people who hold the secret-code keys. The backup person does not need to read the orders. The key person does not need to restart the house. That is called “separation of duties”: no one person holds every key.

These keys are checked a different way from normal ones: by a password file, or by the person’s group on the machine, so they work even when the house is closed. V$PWFILE_USERS lists who holds them. Look at it. It is usually a short list, and it should stay short.

House rules on passwords

A profile can lock a door after too many wrong tries (FAILED_LOGIN_ATTEMPTS), set how long it stays locked (PASSWORD_LOCK_TIME), force a change after a time (PASSWORD_LIFE_TIME), and name a checker that turns away weak passwords (PASSWORD_VERIFY_FUNCTION). The house ships some checkers, such as ORA12C_VERIFY_FUNCTION. Everyone starts on the DEFAULT profile, so read what it says before you trust it.

Programs are not people. A program that changes its password every 180 days will, one night, be refused (ORA-28001, the password has expired) with nobody awake to change it. Give program accounts their own profile: lock after wrong tries, but do not let the password quietly run out. Rotate the secret on a day you chose, with both sides ready.

CREATE PROFILE svc_app LIMIT
  FAILED_LOGIN_ATTEMPTS 5
  PASSWORD_LOCK_TIME    1/24
  PASSWORD_LIFE_TIME    UNLIMITED
  SESSIONS_PER_USER     40;

Five wrong tries lock the account for one hour (1/24 of a day). The password does not run out by itself, and one login cannot open more than 40 sessions, which also guards the connection limit from Chapter 5.

The program gets only what it needs

The best plan uses two accounts for one app. The first, the “owner,” holds the tables and is used only when you change the shape of things. The second, the “login,” is what the program uses every day. It can sign in, and it can touch the few tables it needs, through a role. It cannot drop a table, because it does not own one.

CREATE ROLE orders_rw;
GRANT SELECT, INSERT, UPDATE ON orders.order_lines TO orders_rw;
CREATE USER orders_app IDENTIFIED BY "<from-the-secret-store>"
  PROFILE svc_app;
GRANT CREATE SESSION, orders_rw TO orders_app;

Line 1 makes the bundle. Line 2 puts three keys in it, only on one table. Lines 3 and 4 make the login and give it the right to sign in plus the bundle. Note what is missing: no DELETE, no ANY, no DBA. If the program later needs delete, add that one key, and write down why.

Key idea

Keys that come through a role do not work inside stored code that runs with its owner’s rights (“definer’s rights”). If that code needs a table, grant that table to its owner directly. Also, watch PUBLIC: anything given to it is given to everyone.

Where the secret goes

A password typed in a script or on a command line can be seen by others on the machine in the list of running jobs, and it stays in shell history. Better: use the machine’s own sign-in for admin jobs, or a “wallet” (a locked file made for stored sign-ins) that lets a script connect by an alias, or ask a person at the keyboard. Never put a secret in a file that is checked into the shared code store.

Who did what: the log

Keys are only half the job. You also need a record of use. The house has one place for this, “unified auditing.” You write a rule that names what to record, turn it on, and read the record from UNIFIED_AUDIT_TRAIL. In a new 19c house, some rules are already on, including one for failed sign-ins. Some things, such as use of the master key, are always recorded and cannot be turned off.

CREATE AUDIT POLICY orders_ddl_pol
  ACTIONS CREATE TABLE, DROP TABLE, ALTER TABLE;
AUDIT POLICY orders_ddl_pol;

SELECT event_timestamp, dbusername, action_name, object_name
  FROM unified_audit_trail
 ORDER BY event_timestamp DESC FETCH FIRST 20 ROWS ONLY;

Make the rule, switch it on, then read the last 20 records: when, who, what, and which thing. The record is kept in the helper shelf SYSAUX unless you move it, and it grows. Give it its own shelf and a clean-up plan (DBMS_AUDIT_MGMT), or Chapter 6 will find you at two in the morning. Standard auditing needs no extra license; the fine-grained kind needs Enterprise Edition.

Locking the data itself

A thief who takes a disk, or a copy of a backup, does not need a password. “Transparent Data Encryption” scrambles data in the files so a stolen file is noise. The key to unscramble is kept in a locked file called a “keystore,” away from the data. Open it with ADMINISTER KEY MANAGEMENT; check it with V$ENCRYPTION_WALLET. An “auto-login” keystore opens by itself after a restart, which is handy, but then whoever can read that file can open the data.

Two cautions. This protects files and backups, not what a signed-in person with SELECT can read. And if you lose the keystore, the data and its backups cannot be read by anyone. Save the keystore somewhere else, and test that you can open it. (Network scrambling is in Chapter 5.)

Many homes, many key rings

From Chapter 3: a “common” user lives in the root and may hold keys in every home; its name starts with C##. A “local” user lives in one home only. A key given inside one home works only there. Given from the root with CONTAINER=ALL, it works in all of them, so use that rarely. Each home keeps its own users, roles and profiles. Before any security check, say which home you are standing in.

Lab: two accounts, then prove what they can do

Use the lab house, Oracle 19c, with the home orders. The goal: make one admin account and one app account, and show what each can and cannot do.

Step 1: Look first. In the home, run SELECT username, account_status, profile FROM dba_users WHERE oracle_maintained='N'; Write down who is there. Then look at V$PWFILE_USERS from the root.

Step 2: Make the app side. Create the profile, role and login from the code above. Make the owner orders hold the table order_lines.

Step 3: Make the admin side. Create a local admin orders_dba with a role of only the keys needed for its job (for instance create session, create user, and alter user), not DBA. Give it its own profile.

Step 4: Prove it. Sign in as orders_app. Try an insert (should work), then DROP TABLE orders.order_lines and SELECT * FROM dba_users (both should fail). Write the exact messages. Then list its keys: SELECT privilege FROM dba_sys_privs WHERE grantee='ORDERS_APP' and SELECT granted_role FROM dba_role_privs WHERE grantee='ORDERS_APP'. Run SELECT * FROM session_privs as the app to see what it really holds right now, including keys that arrive through roles.

Step 5: Watch it. Turn on the audit rule. Try six wrong passwords for orders_app and see the lock. Read the failed sign-ins in UNIFIED_AUDIT_TRAIL. Unlock with ALTER USER orders_app ACCOUNT UNLOCK.

Step 6: Clean up. Drop the lab users and the profile, and confirm with the first query that they are gone.

A misleading sign

At night the app starts to fail with a “not allowed” error on one table. The tired DBA runs GRANT DBA TO orders_app and the error goes away. The shop opens. Everyone sleeps.

What really happened: a new stored procedure was added, runs with its owner’s rights, and the owner never got the key to the table it reads. The app’s own keys were never the problem. Now the app can drop every table, read every home it can reach, and make new users.

Evidence: the error text names the table; the audit record shows who failed and on what. Safe fix: grant that one object privilege to the procedure’s owner. Check: rerun the failed call as the app, then list the app’s keys. Undo: REVOKE DBA FROM orders_app at once, and look in the audit record for anything it did while it held the key. Write down the cause so the next change comes with its grants.

Checklist for production

  • Every program has its own login, never the owner and never shared between programs.
  • Logins hold roles with named keys; no DBA, no ANY keys without a written reason.
  • Admin keys are split (SYSBACKUP, SYSDG, SYSKM) and V$PWFILE_USERS is short and reviewed.
  • Program profiles lock after wrong tries; rotation is planned, not by surprise.
  • Oracle-made accounts are locked or have new passwords; unused accounts are removed.
  • No secret in scripts, command lines, or the shared code store.
  • Audit rules are on, the trail has its own shelf and a purge plan, and someone reads it.
  • The encryption keystore is saved apart from the data, and an open test is done.
  • For each home, you know which common users hold keys there.

Give each one the key for the job, keep a record of who used it, and a bad night stays a bad night, not a bad year.
