Part III — Protect Data and Recover from Failure

Putting Things Back After a Bad Day

Real name: Recovery, Flashback, and Failure Scenarios

Chapter 8 gave the order shop copies it can trust. Now a bad day comes, and the copies are not the hard part. The hard part is the question: what exactly is broken, and what is the smallest thing I can put back?

The problem

Picture a toy shop with a big ledger, a drawer of photos of the ledger, and a diary of every change. A bad day can mean very different things. The lights go out for a second. One page is torn. The whole ledger is eaten by a flood. Or the worst one: nothing is broken at all, but someone wrote the wrong numbers on a thousand lines at nine in the morning.

A beginner reaches for the biggest tool every time: bring everything back from the photos. That works, but it throws away every good order taken since. A good keeper of the ledger asks two things first. What state must come back? And which road keeps the most good work?

Before you touch anything

Every road below can make things worse if you start in a hurry. Do these first, each time:

  • Stop the damage. If a bad job is still running, stop it. If people are still adding orders on top of wrong rows, that makes the mess bigger.
  • Write down the time and the clock number. The house has a counter that goes up with every commit, the “SCN” from Chapter 2. Run SELECT current_scn FROM v$database; and write it with the wall-clock time.
  • Read the alert log (Chapter 10 goes deeper). It tells you what the house itself thinks went wrong.
  • Do not delete anything — no old diary files, no “tidy up”. You may need all of it.

Four roads, from small to big

Think of a ladder of tools. Start at the top rung that fits, and go down only when you must.

Lights out; house stopped hardJust start it. The house repairs itself.A short wait
A file is lost or has bad cardsBring back that file, then replay the diaryOnly that file is shut for a while

Road 1: the lights go out

If the machine dies or the house is stopped with SHUTDOWN ABORT, some finished work may exist only in the diary, and some unfinished work may have landed in the ledger. You do not fix this. At the next start, the house reads the diary forward, puts back every finished change, and then undoes every unfinished one using the old versions from Chapter 2. This is “instance recovery” (Chapter 1 showed why it works). It needs no copies and no archived diary files.

Your job is to start the house, wait, and read the alert log to see that it finished. Starting may take longer if lots of work was in flight. If it cannot repair itself, something below it is broken, and you are on Road 2.

Road 2: a file is lost or torn

A shelf of the ledger (one data file) is gone, or a few cards on it are bad. With the diary kept (Chapter 8), bring the file back from the copy and replay the diary on top, so it catches up to now. Nothing is lost. The other shelves can stay open if the damaged shelf is not the system one.

-- RMAN, connected to the house (or to the root of a house with homes)
SQL 'ALTER DATABASE DATAFILE 7 OFFLINE';
RESTORE DATAFILE 7;
RECOVER DATAFILE 7;
SQL 'ALTER DATABASE DATAFILE 7 ONLINE';

Line by line: close the damaged shelf so nobody reads it; bring back its copy; replay the diary on it; open it again. Find the number with SELECT file#, name FROM v$datafile; and check what is wrong with SELECT * FROM v$recover_file;.

For a few torn cards, you need not bring back the whole shelf. SELECT * FROM v$database_block_corruption; lists them, and RECOVER CORRUPTION LIST; repairs just those cards from the copy and the diary, with the shelf still open. Ask why the cards tore — a bad disk or bad memory will tear more.

Road 2b: the map is lost

The control file is the house’s map (Chapter 1). The house keeps more than one copy of it. If one copy is lost and another is fine, stop the house, copy the good one over the lost one’s name, and start again. If all copies are lost, this is why Chapter 8 told you to turn on autobackup:

STARTUP NOMOUNT;
RESTORE CONTROLFILE FROM AUTOBACKUP;
ALTER DATABASE MOUNT;
RECOVER DATABASE;
ALTER DATABASE OPEN RESETLOGS;

Line by line: start only enough to run the helper; fetch the newest saved map; mount it; replay the diary because the saved map is older than the files; open with a fresh diary start. If the helper cannot find the autobackup, you need to tell it where to look, or give it the house’s long number (the “DBID”). Write that number in your runbook today.

Road 3: nothing is broken, but the numbers are wrong

Here is the worst kind of bad day. At 09:40 a release script ran UPDATE orders SET status = 'CANCELLED' with no filter. The files are fine. The house did exactly what it was told. A copy from last night would bring back the old numbers, but also lose everything done since.

The house already keeps old versions of rows (the undo from Chapter 2) so readers see a steady picture. “Flashback” uses them as a time machine. Start with the gentlest one, which only reads:

SELECT order_id, status
  FROM orders
  AS OF TIMESTAMP SYSTIMESTAMP - INTERVAL '30' MINUTE
 WHERE order_id = 4101;

This asks, “show me this table as it looked thirty minutes ago.” Nothing changes. If the answer looks right, you know the old numbers still exist, and you can pick how to put them back: copy the good rows into the table, or rewind the whole table:

ALTER TABLE orders ENABLE ROW MOVEMENT;
FLASHBACK TABLE orders
  TO TIMESTAMP SYSTIMESTAMP - INTERVAL '30' MINUTE;

Line 1 lets the house move rows around while it rewinds; line 2 puts the table back to how it was. Two warnings. Rewinding the whole table also undoes good changes made since, so you may prefer copying only the wrong rows. And a table that someone dropped is a different case: the house first moves it to a “recycle bin” and FLASHBACK TABLE orders TO BEFORE DROP; brings it back, if it was not purged and space was not tight. Its indexes come back with strange names; rename them.

Key idea

Row flashback works only while the old versions are still kept. The setting UNDO_RETENTION is a wish, not a promise: if the old-version room is small, the house may reuse it sooner. Only a room set to “guarantee” keeps them for sure, at the cost that busy writers can then fail for lack of space. When the old versions are gone you get the same error from Chapter 2, ORA-01555, and you must go down the ladder.

Road 3b: rewind the whole house

Sometimes the wrong change is everywhere — a bad release touched ten tables and a dozen shelves. Then you can use “Flashback Database”. It is a fast way to rewind the whole ledger to an earlier moment, using a second kind of small diary called “flashback logs” kept in the recovery area. You must have switched it on before the bad day:

ALTER DATABASE FLASHBACK ON;
SELECT oldest_flashback_scn, oldest_flashback_time
  FROM v$flashback_database_log;

The first line turns it on (the house must be keeping archived diary files, and have a recovery area). The second shows how far back you can really go right now. The target DB_FLASHBACK_RETENTION_TARGET says how far you want to go, in minutes, but it is a goal, not a promise. If the recovery area gets crowded with copies and diary files, the house may throw away the oldest flashback logs.

The strongest use is before a risky change. Make a marker the house will not let go of:

CREATE RESTORE POINT before_release
  GUARANTEE FLASHBACK DATABASE;

A “guaranteed restore point” keeps every flashback log from now until you drop it. That is the promise. The price is room: the logs pile up, and a forgotten one will fill the recovery area and freeze the shop (Chapter 8). Drop it the day the release is judged good: DROP RESTORE POINT before_release;.

To rewind, you stop the shop, close the doors, and go back. Look before you commit to it:

SHUTDOWN IMMEDIATE;
STARTUP MOUNT;
FLASHBACK DATABASE TO RESTORE POINT before_release;
ALTER DATABASE OPEN READ ONLY;
-- look: are the old numbers right? If not, flash back again, to a different point.
SHUTDOWN IMMEDIATE;
STARTUP MOUNT;
ALTER DATABASE OPEN RESETLOGS;

Opening read-only first is the safety catch: you can still change your mind. Opening with RESETLOGS is the point of no return — it starts a new run of the diary, and everything after the target is gone for good. Flashback Database cannot help with a lost or torn file or a lost map; it rewinds changes, and it does not replace the copies.

Road 4: go back to a chosen moment, from the copies

When old versions and flashback logs are gone, use the copies from Chapter 8. This is “point-in-time recovery”: bring back every file from a copy made before the mistake, then replay the diary, but stop just before 09:40.

STARTUP MOUNT;
RUN {
  SET UNTIL TIME "TO_DATE('2026-10-12 09:39:00','YYYY-MM-DD HH24:MI:SS')";
  RESTORE DATABASE;
  RECOVER DATABASE;
}
ALTER DATABASE OPEN RESETLOGS;

Line by line: start only enough to work; say where to stop; bring back all files; replay the diary up to the stop; open with a fresh diary run. Use the clock number you wrote down (SET UNTIL SCN) when you have it — it is exact where a clock time is fuzzy. The price: everything after the stop is gone, in every table, including orders taken legitimately at 09:50. Right after opening, take a new full copy: the old copies are from before the new run of the diary.

Three ways to keep the good work

Because the big road costs so much, there are three ways to bring back only what you need.

  • One table, from the copies. RMAN’s RECOVER TABLE builds a small throw-away house on the side, brings the table back to a time you choose, and loads it into your house (or into a file) while the shop stays open.
  • A whole second house. DUPLICATE builds a copy of the house, as of a past moment, on another machine. You look at it, pull out the rows you need, and put them into the real one. This is also the best way to practice (see the lab).
  • One home inside the house. From Chapter 3: if the shop has separate homes, you can put just orders_pdb back to a moment while the others keep working.
-- connected to the root
RUN {
  ALTER PLUGGABLE DATABASE orders_pdb CLOSE;
  SET UNTIL TIME "TO_DATE('2026-10-12 09:39:00','YYYY-MM-DD HH24:MI:SS')";
  RESTORE PLUGGABLE DATABASE orders_pdb;
  RECOVER PLUGGABLE DATABASE orders_pdb;
  ALTER PLUGGABLE DATABASE orders_pdb OPEN RESETLOGS;
}

The same road as before, narrowed to one home. The other homes never close. Read the Oracle guide for the exact limits on flashing back a single home; they depend on the release.

Lab: break the lab house three ways, and write down each choice

Use the lab house from Chapter 8 (19c, diary kept, autobackup on, a fresh level 0 and some level 1 copies). For each break, fill in a small card before you act: What I saw. What state I need back. The road I chose and why. How I checked. How I would undo it.

Break 1: lights out. Run a batch of inserts, leave some uncommitted, then SHUTDOWN ABORT. Start, watch the alert log, and count the rows. Your card should say: no copies used.

Break 2: a lost file. Stop the house, delete one non-system data file from the operating system, and start. It mounts but refuses to open. Use v$recover_file, then the four lines of Road 2. Check the file is online and the last order is still there.

Break 3: the wrong update. Make a guaranteed restore point, note the SCN, run the filter-less update on orders, commit, and let a few good orders go in after it. Now solve it twice: first with flashback query and a copy-the-good-rows fix, then, on a second pass from a fresh restore point, with Flashback Database. Compare what each one lost.

Last: the map. On the separate test machine only, delete every control file and bring them back using Road 2b. Time each break and write the minutes beside your goal from Chapter 8.

A misleading sign

After the wrong update, the keeper tries FLASHBACK TABLE orders TO TIMESTAMP ... and gets an error saying the snapshot is too old — it is ORA-01555 again. A teammate says, “So the data is gone; restore from last night.” It is not gone. The old versions for that table are gone, because a heavy overnight job reused the room. The flashback logs are a different store.

Evidence: v$flashback_database_log shows the oldest point is still before 09:40; the guaranteed restore point is listed in v$restore_point. Safe fix: flash back the whole database to the restore point, opened read-only first; if too much good work would go, instead DUPLICATE a second house to that point and carry the rows over. Check: the order counts match the pre-release note, and the app can write again. Undo: before RESETLOGS you can still flash back again to another time; after it, you cannot. So decide with a written target, not a guess.

Checklist for production

  • You have a written decision ladder (the table above, with your own names and numbers), reachable when the network is down.
  • Stop the damage, then record time and SCN, before any recovery step.
  • You know the DBID, the backup locations and how the autobackup is found, and they are written outside the database.
  • Flashback Database is on where the owner wants it, and v$flashback_database_log is checked, not assumed.
  • A guaranteed restore point is made before every risky release and dropped the day after it is judged good.
  • Undo is sized for the oldest row flashback you promise; the promise is written down.
  • You rehearse restore of a file, of the map, of one table, and of a point in time, and write down the minutes.
  • After OPEN RESETLOGS, a new full copy is taken before the day ends.
  • The recovery area has room for flashback logs and copies, and is watched.

When you know which road keeps the most good work, a bad day becomes a small repair and not a lost week.
