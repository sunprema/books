Part IV — Observe, Diagnose, and Improve

Jobs That Run Themselves Safely

Real name: Workload Management and Automation

Chapter 11 fixed one slow question. But the house has hundreds of chores that must happen every day, at night, while shoppers are still buying. How do you make those chores happen on time, leave a clear written trail, and never make a bad day worse?

The problem

The shop clears old orders every night at two. For a year, one tired person ran it by hand. Then they went on holiday, and a helper ran it twice, halfway through, by mistake. Half the old orders were gone, half were not, and nobody could say which. The next night the chore ran again at the same time as the yearly counting job, and the order screen crawled. Lots of people find chores like this boring, and that is fair. It is also why they go wrong: boring jobs get rushed.

Sharing the house fairly

Think of one kitchen and many cooks. When there is plenty of room, nobody minds. When the kitchen is full, the loud cook can push out the quiet one. The house has a part that hands out turns, called “Resource Manager”. You sort workers into groups (“consumer groups”: shop buyers, report readers, night chores) and write a plan saying how big a share of the cooking power each group gets when there is not enough to go round. When there is enough, the plan stays out of the way.

The house comes with a ready-made group for its own chores, and two ready-made time slots at night called “maintenance windows” where those chores run. A window can switch on a plan when it opens. That is a promise: during the window, the chores get a small, fixed share and the shoppers keep the rest. If you see sessions waiting on resmgr:cpu quantum, the plan is telling them to wait for their turn. That is the plan working, not the house breaking.

The clock that starts the chores

Chores are started by the house’s own clock, the “Scheduler” (the DBMS_SCHEDULER package). It keeps a written list of chores, when each should run, who owns it, and what happened last time. Compared with an old-style timer on the server, it knows about the house: it can write down every try, stop and restart with the database, and tie a chore to a group so the plan above applies.

BEGIN
  DBMS_SCHEDULER.CREATE_JOB(
    job_name        => 'OPS.PURGE_OLD_ORDERS_JOB',
    job_type        => 'STORED_PROCEDURE',
    job_action      => 'OPS.PURGE_OLD_ORDERS',
    repeat_interval => 'FREQ=DAILY;BYHOUR=2;BYMINUTE=0',
    enabled         => TRUE,
    comments        => 'Nightly purge, safe to rerun');
END;
/

Line by line: give the chore a name and an owner; say it is a stored piece of house code; name that code; say “every day at two in the morning”; turn it on; leave a note for the next person. Afterwards, the trail is in dba_scheduler_job_run_details: one line per try with the result (status), the error number, when it really started, and how long it took.

Five rules for a chore you can trust

RulePlain pictureHow it looks in practice
Check beforeLook in the fridge before cookingIs the disk space there? Is this the right house (PDB)? Is another run still going?
Safe to repeat (“idempotent”)Sweeping a clean floor harms nothingDelete rows by a date line, in small batches; a second run finds nothing left to do.
Say it out loudA chore chart with ticks and timesWrite a time-stamped line at start, each step, and end.
Fail loudlyA bell, not a whisperStop at the first error, return a non-zero exit number, tell a person.
Check afterLook at the floor when doneCount what is left; compare to what you expected.
A quiet trap

A chore that catches every error and carries on will show “SUCCEEDED” in the history even when it did nothing. Let the error go up, or log it and raise it again.

A chore written as a script

#!/bin/bash
set -euo pipefail
LOG=/var/log/dba/purge_$(date +%Y%m%d_%H%M%S).log
exec >>"$LOG" 2>&1
echo "$(date -Is) start"
if ! sqlplus -L -s /@ORDERS_OPS @precheck.sql; then
  echo "$(date -Is) precheck failed"; exit 2
fi
sqlplus -L -s /@ORDERS_OPS @purge.sql || { echo "purge failed"; exit 3; }
sqlplus -L -s /@ORDERS_OPS @postcheck.sql || { echo "postcheck failed"; exit 4; }
echo "$(date -Is) done"

Walk through it: stop at the first thing that goes wrong; write everything to a dated log; run a check file, then the work file, then a check file again; each failure has its own exit number so whoever reads the result knows which step broke. In the SQL files, start with WHENEVER SQLERROR EXIT FAILURE so SQL*Plus cannot carry on after an error. The login is /@ORDERS_OPS: the secret lives in a locked store (a wallet), not in the script and not on the command line, where anyone running ps could read it.

Who does the chore, and with what key

Give the chore the smallest key that opens only its own door (Chapter 7). A purge needs to delete from one shelf, not to own the house. For chores that run outside the database, on the server itself, the Scheduler wants a “credential”: a stored name and secret for an operating-system user, made with DBMS_CREDENTIAL.CREATE_CREDENTIAL and attached to the job. The job owner needs the right to use it, and the user behind it should be a plain, limited one, not the account that owns the database files. In a container database, a job lives in the pluggable database where you made it (Chapter 3), so check where you are before you create or run anything.

Where a person must say yes

Some chores are safe to run alone: gathering notes, checking space, sending a report. Some are not: deleting data, changing settings, ending sessions. A safe line is simple. Chores that only read or only touch their own scratch work run alone. Chores that remove or change real data run in two steps: the chore makes a list of what it would do (a “dry run”) and stops; a person looks, approves, and only then does the second step run. Put a limit inside the chore too: it refuses to remove more than a set number of rows, so a wrong date line cannot empty the shelf.

The shop’s night purge

You rebuild the chore. Before: it checks free scratch room and that it is in the orders house. It builds a list: orders closed more than 400 days ago, and refuses to go on if the list is longer than 200 thousand. After the nod, it removes 5 thousand at a time, saving after each batch and writing a line to the log. If it stops half way, the next night it just finds fewer old orders and carries on. At the end, it counts what remains over the date line and expects zero. It runs in a group with a small share of power, inside the night window.

The trap: the chore says it worked

A few weeks later the history shows green ticks every night, yet the orders shelf keeps growing. Why? A change to the status words meant the list was empty every night, so the chore did nothing, correctly and quietly. Green does not mean useful. The check-after step is what catches this: it expected that nothing old remained, and it also should expect that, on a normal night, something was removed. Count work done, and tell a person when the count is strangely small as well as strangely large.

Lab: build a chore with a bell and a safe rerun

  1. Make a log table and an old-orders table with 100 thousand rows; 30 thousand are older than 400 days.
  2. Write a procedure that does the precheck, makes the list, refuses over a limit, deletes in batches of 5 thousand, commits each batch, and logs start, each batch and end into the log table.
  3. Add a postcheck that raises an error if any old rows remain. Do not catch errors silently.
  4. Create a Scheduler job for it with CREATE_JOB. Run it once with RUN_JOB. Read dba_scheduler_job_run_details.
  5. Kill it half way (stop the job), then run it again. Show that the final result is the same and nothing was removed twice.
  6. Force a failure (lower the limit below the list size). Show the error in the job history, the log table and the exit status of a wrapper script.
  7. Bonus: put the job in a job class tied to a consumer group, and watch the group’s share in v$rsrc_consumer_group while a busy test runs.

Checklist for production

  • Every routine chore is in the Scheduler (or one clear tool), with an owner and a note.
  • Prechecks before, postchecks after; failure stops the chore and rings a bell.
  • Safe to run twice; work done in small saved batches with a limit.
  • Log lines with times, kept somewhere a person will look; check run history, not only a green tick.
  • No secrets in scripts, command lines or job text; use a wallet or credential.
  • Smallest key for the job; check which pluggable database it runs in.
  • Chores that remove or change data need a dry run and a human yes.
  • Heavy chores sit in a group and a window with a plan; test with the shop busy.

When every chore checks first, can be repeated, and leaves a trail, the night shift stops being a worry and becomes something you can read in the morning.
