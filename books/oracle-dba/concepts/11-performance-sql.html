Part IV — Observe, Diagnose, and Improve

Why One Question Takes So Long

Real name: Performance Diagnosis and SQL Execution

Chapter 10 ended with one statement eating most of the time since the new release. Now you stand in front of it. Which part of its work costs the time, and what is the smallest change that fixes the cause?

The problem

The shop’s order screen asks one thing: “show me this buyer’s open orders.” Last month it took a blink. Now it takes eleven seconds. Someone says “add an index.” Someone else says “give it more memory.” Each guess is a change, and each change has a price. Lots of people find it hard to stay calm and measure while the screen is slow, and that is fair. It is still the only way to fix the cause and not just the feeling.

The route the house picks

Before the house answers a question, a part called the “optimizer” picks a route: which shelves to visit, in what order, and how to put the results together. The written route is the “execution plan”. The picking is done with guesses about how many rows each step will find. Good guesses, good route. Bad guesses, a long walk.

There are two very different papers. One is the route the house would take (EXPLAIN PLAN): an estimate, made without running anything. The other is the route the house did take, with real counts written beside the guesses. Only the second can catch a wrong guess. Never settle an argument with the first.

See what really happened

SELECT /*+ gather_plan_statistics */ COUNT(*)
  FROM orders
 WHERE status = 'OPEN' AND customer_id = :cid;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY_CURSOR(NULL, NULL, 'ALLSTATS LAST'));

Line by line: run the question with a small note asking the house to count real rows as it goes; then, straight after, in the same session, ask for the route of the last run. The paper has columns E-Rows (the guess), A-Rows (what was found), Starts (how many times the step ran) and A-Time (time spent). Look for the first step where guess and found are far apart.

Why guesses go wrong: the notes

The house guesses from notes it keeps about each table and column: how many rows, how many different values, which are common. These are the “optimizer statistics”. If the notes are old (the table grew from 5 thousand to 5 million rows), or if one value is far more common than the rest, the guess is wrong. Fresh notes come from EXEC DBMS_STATS.GATHER_TABLE_STATS(USER,'ORDERS', cascade=>TRUE);, not the old ANALYZE. The house also refreshes notes by itself in a nightly job (Chapter 12), but a big load in the afternoon can beat it.

Careful

New notes change routes for many questions at once, not just yours. On a busy day, try it on a copy first, or keep the old notes so you can put them back (DBMS_STATS.RESTORE_TABLE_STATS).

Ways to reach rows, ways to put them together

ChoicePlain pictureGood when
Read the whole shelf (“full scan”)Walk every pageYou need a big share of the rows. Not always bad.
Use an index (“range scan”)Use the back-of-book list, then jumpYou need a small share of the rows.
One at a time (“nested loops”)For each row here, look up one thereFew rows on one side, fast lookup on the other.
Pile and match (“hash join”)Sort both piles by buyer, then matchLarge piles; needs memory.

No choice is the winner every time. Whether a shelf walk or a list jump is cheaper depends on how many rows you need. That is why the guess matters so much.

Asking the same question a thousand ways

Each time the house sees a new question it has not seen, it picks a route from scratch. This is a “hard parse”, and it is costly and takes a shared lock on common memory (Chapter 1). If the shop writes ... WHERE customer_id = 7001, then ... = 7002, then ... = 7003, each looks like a new question. If the shop writes ... = :cid and passes the number separately (a “bind variable”), the house reuses the route: a “soft parse”. Symptoms of the first way: many nearly equal lines in v$sql, a busy shared memory area, and CPU spent on routes, not rows.

If the shop code cannot be fixed, a setting (CURSOR_SHARING=FORCE) makes the house swap the numbers for binds itself. It is a patch: Oracle’s own advice is to test it, because one route may then be used for values that need different routes. The house has a partial cure for that too, called “adaptive cursor sharing”, which keeps more than one route for a bind question when the values call for it (see is_bind_aware in v$sql).

Indexes cost on the way in

An index is a second list that must be kept up to date. Every new order, every change to an indexed value, every removal updates each index too. So each extra index makes reading some questions quicker and writing every row slower, and adds diary (redo) and old-page (undo) work. For a shop that takes thousands of orders a minute, six indexes on the orders shelf is a real cost. Add one when a measured, important question needs it, and check that the writes did not get worse.

Not enough working room

Sorting and matching need a table to work on, and the house gives each job a slice of private memory (the PGA, Chapter 1). If the piles do not fit, the job spills to scratch space on disk (temp, Chapter 6) and runs several times slower. In the plan this shows as a TempSpc column, and ORA-01652 if scratch runs out. The cure is often a smaller pile (a better filter or join order), not simply more memory.

Trace: one session’s whole day, written down

EXEC DBMS_MONITOR.SESSION_TRACE_ENABLE(
       session_id => :sid, serial_num => :serial,
       waits => TRUE, binds => FALSE);
-- let the slow screen run, then:
EXEC DBMS_MONITOR.SESSION_TRACE_DISABLE(:sid, :serial);
# on the server:  tkprof orcl_ora_4242.trc out.txt sys=no sort=exeela

Line by line: start writing down everything that one session does, including what it waits for; stop; then turn the trace file (found in the ADR trace folder, Chapter 10) into a readable report, longest statements first. The report shows, per statement, how many parses, runs and fetches, the CPU and elapsed time, the rows, and the waits. When 90% of elapsed time is one wait, you have your answer.

Photos of a whole hour: AWR, ASH and the helpers

For a problem across the whole house, not one session, the house keeps hourly snapshots (“AWR”) and per-second samples (“ASH”, Chapter 10). From these you can print a report for a bad hour, or compare it to a good one. Advisors read them and make suggestions. Treat suggestions as ideas to check against the plan, not orders.

A rule about money, again

AWR, ASH and ADDM need the paid Diagnostics Pack on Enterprise Edition. The SQL Tuning Advisor and SQL Access Advisor need the Tuning Pack. A setting, CONTROL_MANAGEMENT_PACK_ACCESS, switches them off, but it does not erase past use. Without the packs, use the free views, SQL trace and TKPROF, and Statspack. Check your licence before you run a report.

The shop’s eleven seconds

You find the statement from Chapter 10 in v$sql: the same sql_id with a huge number of reads per run. You run it with real counts. Step one guessed 5 rows and found 48,000. The notes on the orders shelf say 5 thousand rows; the table has grown by a load last week. The house chose “one at a time” matching, so step two ran 48,000 times.

Fix, one thing: new notes on the orders shelf (kept old ones for rollback). The route changes to pile-and-match. It now takes 0.4 seconds. Nobody added an index; nobody bought memory.

The trap: the second run is always faster

After the fix you run it again and it takes 0.1 seconds, and a colleague says “wow.” But the first run also warmed the desk: pages are now in memory, so the second run needs no walk to the shelf. A fair test compares like with like: same amount of data, run several times, and look at numbers that do not depend on luck, such as the count of pages read (buffer_gets, the Buffers column of the plan) beside the time. Write down before and after. If the only change you can show is a faster second run, you have shown nothing yet.

Lab: slow, find, fix, measure

  1. Make an orders table with 50 thousand rows where 95% have status='CLOSED', and an index on status. Gather stats.
  2. Run a question for status='OPEN' with the plan note. Save the plan, A-Rows, Buffers and time.
  3. Load 500 thousand more rows without gathering stats. Run again. Find the first step where E-Rows and A-Rows differ most.
  4. Gather stats on the table. Run again. Save the new plan and numbers.
  5. Run each version three times. Report buffer gets and elapsed time as before and after, and say what you changed (one thing).
  6. Bonus: run the same question with literals 200 times, then with a bind 200 times; compare parse_calls and the number of lines in v$sql.

Checklist for production

  • Judge by the plan of what really ran, with guessed and found counts side by side; not by EXPLAIN PLAN alone.
  • Find the first step where the guess is far off; look at stats, skew and filters there.
  • Keep the old stats before gathering new ones, and test on a copy when the table is important.
  • Use bind variables in the application; treat CURSOR_SHARING=FORCE as a tested patch.
  • Add an index only for a measured need, and check the cost to writes.
  • Watch for spills to scratch space before buying memory.
  • Use trace and TKPROF for one session, AWR/ASH reports for the whole house, only if licensed.
  • Change one thing; measure before and after with repeatable numbers; beware the warm second run.

When you find where the time goes before you pick a fix, a slow question stops being a mystery and becomes one small, checkable change.
