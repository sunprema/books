Part II — Build and Administer the Environment

Building a Place Someone Else Can Copy

Real name: Provisioning, Configuration, and Database Lifecycle

You built the order shop’s house last month. Today you are sick, and a friend must build the same house for the testers. Can they? This chapter is about making a house that a friend can build again from your notes, and run without guessing.

The problem

Picture a cake made once, by feel: a bit of this, a hand of that. It was great. Nobody can make it again. A database built by clicking through screens and changing settings late at night is that cake. It runs, but only you know why.

The fix has three parts: a fixed place for the program, a written recipe for building, and a saved list of every setting so you can see when something has moved.

Part one: where things live, and who owns them

The program files sit in a folder called the “Oracle home.” The name of the house you run is kept in a shell word, ORACLE_SID (the instance name); the folder is kept in ORACLE_HOME. Two homes, say one before a patch and one after, can sit side by side. Each house is tied to the home that made it, so when you later patch (Chapter 13) you choose which home each house lives in.

On a Linux machine, one computer user, usually oracle, owns the program and the files. A few groups decide who may do house-wide jobs, such as oinstall and dba. The computer also has to give that user enough room: many open files, many processes, and enough shared memory. On Oracle Linux and its cousins, a ready-made package named oracle-database-preinstall-19c sets the user, the groups, the limits and the kernel settings for you. If you do it by hand, write every value down. Guides often show something like 65,536 open files and 16,384 processes as the top limit for the user, but read your own version’s manual and do not copy a number you cannot explain.

export ORACLE_BASE=/u01/app/oracle
export ORACLE_HOME=$ORACLE_BASE/product/19.0.0/dbhome_1
export ORACLE_SID=ORCL
export PATH=$ORACLE_HOME/bin:$PATH
id oracle          # which groups?
ulimit -n -u       # open files, processes, as this user

Lines 1–4 say where the program is and which house you mean. The last two ask the computer who the user is and what it is allowed to open. Put the first four lines in one small file that every DBA loads. A cron job does not load your login settings, so a job that works by hand and fails on a timer often has a different home or name.

Part two: the recipe for building

The tool that makes a new house is the “DBCA” (the database configuration assistant). It has a picture screen and a quiet mode that takes its answers from the command line or a file. Use the quiet mode: a recipe you can run twice beats a screen you clicked through once.

dbca -silent -createDatabase \
  -templateName General_Purpose.dbc \
  -gdbname ORCL -sid ORCL \
  -characterSet AL32UTF8 \
  -createAsContainerDatabase true \
  -numberOfPDBs 1 -pdbName orders

Walk through it: use the plain template; name the house and its instance; use the text rule that holds almost every language; make a house with homes (Chapter 3), with one home called orders. The secret words (the passwords for the strongest users) are asked for, or come in a protected file, and are never written in the recipe or typed where they show in the process list. Check the exact flags for your version with dbca -help; the flags change over time.

Some things you cannot change cheaply afterward: the text rule (“character set”), the block size, and whether you built a house with homes. Choose them on purpose, and write the choice in the notes. For a lab, make a fast house with small memory. For the real one, size it from the work it will do.

Part three: settings, and where they are kept

A house has hundreds of settings, called “initialization parameters.” They are read when the house starts. They live in a file in one of two shapes. The old shape is a text file, the “PFILE”: you can read it and edit it. The better shape is a machine-written file, the “SPFILE”: the house itself can write to it while running, so a change survives a restart. Do not edit the SPFILE with a text tool. To read it, make a text copy; to go the other way, make a machine copy from the text.

CREATE PFILE='/stage/init_before.ora' FROM SPFILE;
CREATE SPFILE FROM PFILE='/stage/init_edited.ora';

First line: write a readable copy of the settings; keep it as your before-picture. Second line: build the machine file from a text file you edited. Use this second one when a bad setting stops the house from starting at all.

Changing a setting: now, later, or both?

This is the part that bites. When you change a setting on a running house, you say how long the change should last with SCOPE.

You sayWhat happensDanger
SCOPE=MEMORYChanges the running house now. Gone after restart.The fix quietly vanishes at the next restart.
SCOPE=SPFILEWritten to the file. Takes effect at next start.Nothing changes today. Some settings can only be changed this way.
SCOPE=BOTHBoth. This is the default when the house runs from an SPFILE.Not every setting allows a change while running.

Say the scope every time, even when it is the default; the next reader then knows you meant it. Compare what is running with what is saved:

ALTER SYSTEM SET open_cursors = 500 SCOPE=BOTH;
SELECT p.name, p.value running, s.value saved
  FROM v$parameter p JOIN v$spparameter s ON s.name = p.name
 WHERE p.name = 'open_cursors';

The first line sets it now and keeps it. The query puts the running value beside the saved one. If they differ, someone changed only one side. A setting that cannot change while running (the house says so in the column issys_modifiable of v$parameter) refuses with an error unless you say SCOPE=SPFILE, and then needs a restart. In a house with homes, a setting can be set for one home only if its ispdb_modifiable column says yes.

Starting and stopping, one stop at a time

Starting is four stops, as in the figure. Normally you say STARTUP and go all the way. But some jobs need an early stop: at the first stop (NOMOUNT) you can rebuild the control map; at the second (MOUNT) you can move files and switch the diary mode (Chapter 8).

STARTUP NOMOUNT;
ALTER DATABASE MOUNT;
ALTER DATABASE OPEN;

Stopping has four speeds. NORMAL waits for every visitor to leave, maybe forever. TRANSACTIONAL waits for every open piece of work to finish. IMMEDIATE undoes unfinished work, sends visitors out, and stops cleanly; this is the one you will use. ABORT pulls the plug: no tidying, and the next start must repair the house from the diary (Chapter 1). ABORT is a last tool, not a faster one, and it is the right one when IMMEDIATE hangs.

Part four: the baseline, and drift

When the house is built and healthy, write down what it looks like. This is the “baseline.” Later, when somebody says “it was fine last week,” you can look. If today differs from the baseline in a way nobody wrote down, that is “drift.” Most drift is not evil; it is a quick fix at night that nobody noted.

A good baseline is small enough to keep and complete enough to rebuild from:

  • The version and patch level of the program, and the home path.
  • The recipe you used to build (the quiet DBCA call, or the response file), without secrets.
  • A readable copy of every setting that is not the default.
  • Names and sizes of files; the text rule; the block size; the diary mode; the homes and their open state.
  • The computer side: user, groups, limits, kernel settings, mount points.
-- every setting someone changed from the default
SELECT name, value, issys_modifiable
  FROM v$system_parameter
 WHERE isdefault = 'FALSE' ORDER BY name;
SELECT banner_full FROM v$version;
SELECT log_mode, cdb FROM v$database;

Spool these into text files, and put the text files, the recipe, and the environment file into version control with your other notes. Run the same set again each month and compare with a plain diff. The diff is your drift alarm, and it costs nothing.

Lab: build a house and write its baseline

You need a Linux lab machine with the 19c program already unpacked in its home (installing the program is out of scope here). Use a small memory target.

Step 1: Make the ground ready. As the program’s owner, load the environment file from the code above. Run id and ulimit -n -u; write the output in your notes file.

Step 2: Build. Run the quiet DBCA recipe with a home called orders. When it asks for passwords, type them at the prompt. Afterward run sqlplus / as sysdba and SELECT name, open_mode FROM v$database;.

Step 3: Take the before-picture. Run CREATE PFILE='/stage/baseline.ora' FROM SPFILE; and spool the three baseline queries into /stage/baseline.txt.

Step 4: Try each scope. Set open_cursors to 400 with SCOPE=MEMORY. Restart with SHUTDOWN IMMEDIATE and STARTUP. Look at the value: it is back to the old one. Now set it with SCOPE=BOTH, restart, and see it stay. Then try a static one such as processes with the default scope and read the error; set it with SCOPE=SPFILE and see that the running value waits for the restart.

Step 5: Walk the stops. SHUTDOWN IMMEDIATE, then STARTUP NOMOUNT; run SELECT status FROM v$instance;. Then mount, check again, open, check again. Write what each answer was.

Step 6: Find the drift. Make one unwritten change (ALTER SYSTEM SET cursor_sharing=FORCE SCOPE=BOTH;). Spool a new baseline and diff it against the first. The change appears. Put it back and diff again: empty. Finally, ask a friend to rebuild from your notes alone; where they get stuck is what the notes lack.

A misleading sign

Last week the order app was slow, and a DBA raised the work-area size to fix it. It worked. This Monday, after a power cut and a restart, the app is slow again, and the DBA is sure the house is “broken.” The fix was SCOPE=MEMORY. The restart put back the old value.

Evidence: the query that puts v$parameter beside v$spparameter, and the alert log, which records parameter changes and the settings used at start. Safe fix: set the value again with SCOPE=BOTH, then add a line to the notes. Check: restart the lab twin and see the value stay. Undo: set the old value back, or start from the before-picture PFILE.

A second trap: someone edited init.ora by hand to fix a setting, and nothing changed. The house reads the SPFILE if there is one; the text file was ignored. Ask the house which it used: SHOW PARAMETER spfile is empty when a PFILE started it.

Checklist for production

  • One environment file for ORACLE_HOME, ORACLE_SID, PATH, loaded by humans and by timers alike.
  • The build is a script or a response file in version control, with no secrets inside.
  • Text rule, block size, and house-with-homes choice are written down before the build.
  • The house runs from an SPFILE; a readable copy of it is saved after every planned change.
  • Every ALTER SYSTEM says its SCOPE and is noted with who, when and why.
  • A monthly baseline run is compared with the last one; each difference has a reason.
  • Stop with IMMEDIATE; ABORT only when it is truly stuck, and say so in the notes.
  • Someone other than the builder has rebuilt the lab house from the notes.

When your house is built from a recipe and every setting is written down, anyone can make it again, and no one has to guess why it works.
