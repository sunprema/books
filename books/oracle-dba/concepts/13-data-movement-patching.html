Part V — Change and Availability

Moving House Without Losing Anything

Real name: Data Movement, Patching, Upgrades, and Migration

Chapter 12 made the daily chores safe. Now the big change: the shop needs a newer house, or a copy of its shelves in a test room. How do you change things and still know, at every step, how to get back?

The problem

The shop is moving its orders to a newer house over one weekend. On Friday night someone sends the shelves across, the new house starts, and shoppers come in. On Monday a helper notices that a few thousand orders have no prices, and nobody kept the old house as it was. The move “worked” and the shop still lost a week. The trouble was not the move. It was that nobody had practised it, written down what “right” looks like, or kept a road back.

Three kinds of moving

Before you pick a tool, ask what you are moving. There are three jobs, and they get mixed up all the time.

JobPlain pictureUsual tool
Move the things on the shelvesCarry boxes of goods to another room“Data Pump” export and import
Copy the whole roomPhotograph and rebuild the room as it isBackup restore, duplicate, or a pluggable-database clone (Chapter 3)
Change the house itselfFit new walls and wiringPatch the program files; upgrade to a new release

Carrying boxes: Data Pump

The house has its own box-carrier, called “Data Pump” (the tools expdp and impdp). It works inside the house, not on your laptop: it reads and writes files in a folder the database knows by a name, called a “directory object”, and keeps a small table of notes about the job in the owner’s space. That is why a job can be stopped and picked up again.

Two traps hide in a plain export. First, a busy shop keeps changing while you carry, so the boxes may not match each other. Ask for a fixed moment with flashback_scn (or flashback_time) and every box is from that same instant. Second, the new room may have different names. remap_schema=SHOP:SHOP_TEST and remap_tablespace rename the owner and the shelf area on the way in.

# carry out, all boxes from one moment
expdp system@ORDERS_PDB schemas=SHOP directory=DP_DIR \
  dumpfile=shop_%U.dmp logfile=shop_exp.log \
  parallel=4 flashback_scn=<scn>

# carry in, under a new owner name
impdp system@TESTPDB schemas=SHOP remap_schema=SHOP:SHOP_TEST \
  directory=DP_DIR dumpfile=shop_%U.dmp logfile=shop_imp.log

Line by line: take the shop’s shelves; use the named folder; write several files (the %U becomes 01, 02, and so on); use four helpers at once; freeze the view at one moment. Then bring them in under a new owner name. In real life the secret login lives in a wallet, as in Chapter 12, not on the line. There is also a way with no files at all: network_link pulls straight across a link between two houses. It is handy when there is no room for files, but it needs the right keys on both sides, so check that with the people who guard them (Chapter 7).

Changing the house itself

Two different changes get called “patching” and “upgrading”. A small fix, called a “release update”, swaps program files inside a house of the same release. A big step, an “upgrade”, moves the shelves and records to a newer release. Both have a part that touches the program files and a part that touches the records inside the database. If you do only the first part, the house looks fixed from outside and is not.

For a release update the usual path is: check that the patch tool is new enough, take a backup, stop the database and its listener, apply the patch to the program files, start again, then run datapatch -verbose to update the records inside, then recompile code that went stale (utlrp.sql). To check, compare two lists: opatch lspatches (what the files say) and dba_registry_sqlpatch (what the database says). They should agree. The write-ups behind these steps are community ones, so read the patch’s own readme before you start; it can add steps.

Stepping up to a new release

For an upgrade, the house comes with a helper called “AutoUpgrade”. You write a short file naming the old home, the new home and the database, and then run it in modes, one after another: analyze reads the old house and lists what would go wrong; fixups repairs what it can; deploy does the whole move. Run analyze first and often. It costs nothing and it tells you the bad news early.

global.autoupg_log_dir=/u01/au/logs
upg1.source_home=/u01/app/oracle/product/19.0.0/dbhome_1
upg1.target_home=/u01/app/oracle/product/19.0.0/dbhome_2
upg1.sid=ORDERS
upg1.restoration=yes

# then, in turn:
java -jar autoupgrade.jar -config orders.cfg -mode analyze
java -jar autoupgrade.jar -config orders.cfg -mode deploy

The last setting is the road back. With restoration=yes the helper puts down a marker in time (a “guaranteed restore point”) before it starts, and for that it needs room in the recovery area. Set it to no for a database that does not keep old change records, or for the cheaper edition, and then you must take the backup and do the restore by hand. The option -restore_on_fail lets it go back by itself, but only when the main part or a whole single database fails; trouble in one pluggable home is not counted as a reason to undo everything.

A marker is not a backup

A restore point lives in the same recovery area as your other files. Take a real backup first and prove you can restore it (Chapter 8). The marker only makes the way back quicker.

The shop’s weekend move

The shop copies the busy house into a test room, with Data Pump and a fixed moment, then runs the whole move there. This is the rehearsal. It finds two problems: a stale list of old words the new house does not know, and a chore from Chapter 12 that points at the old house’s name. Both are fixed in writing. The second rehearsal runs from the written steps with nobody improvising, and takes four hours, not the nine the first one took.

The trap: it finished, so it must be fine

At the real move everything finishes without an error, but the next morning the order screen shows empty prices. The import log, read slowly, shows a few lines saying some records were skipped because a related shelf did not exist yet. Nobody read the log because the job’s last line said it finished. “Finished” and “correct” are different words.

The fix is a list of checks written before the move, run on both sides and compared: how many rows on each shelf; how many broken pieces of code; how many things disabled; a sum of the money column; the name of every chore and whether it is on. Then a real shopper test: place one order, read it back.

The road back

A road back is only real if you have walked it. Write down, for every step, the point after which you can no longer go back (after the shop takes new orders in the new house, the old house is behind by those orders). Pick a time before that point where one person says go or stop, with the numbers from the checks in front of them. Keep the old house untouched until the new one has been fine for as long as you promised.

Lab: rehearse a move with a way back

  1. Pick the shop schema in a test house. Write the checks first: row counts, invalid code, sum of totals, chore list. Save the numbers.
  2. Export with a fixed moment (flashback_scn), import under a new owner with remap_schema, and read the whole import log. Rerun the checks and compare.
  3. In a lab copy of the house, run AutoUpgrade in analyze mode and read every line of its report.
  4. Apply one release update to a spare home, run datapatch -verbose, then compare opatch lspatches with dba_registry_sqlpatch.
  5. Write the steps as a runbook with times, a go or stop point, and the way back. Walk the way back once for real (restore the backup or flash back to the marker) and write down how long it took.

Checklist for production

  • Say whether the job is moving things, copying a room, or changing the house.
  • A rehearsal on real-sized data, run from the written steps, until it is dull.
  • Export from a fixed moment; read the import log to the end.
  • Checks written before, run on both sides, numbers compared.
  • Patch both halves; compare the file list and the database list.
  • Run AutoUpgrade analyze early and again right before; know what the restore point needs.
  • A tested backup, plus a marker if you can have one.
  • A go or stop time, and a named person who decides.
  • Check licence and edition rules for any option you lean on.

A move you have practised, measured and can undo is not a leap. It is a walk you have already taken once.
