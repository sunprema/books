Part V — Change and Availability

When the Main Machine Goes Dark

Real name: High Availability and Disaster Recovery

Chapter 13 changed the house on purpose. This chapter is about the day the house changes without asking: the power goes, the floor floods, or a worker pulls the wrong plug. Which of those can the shop live through, and what do the shoppers see while it happens?

The problem

The shop keeps all its orders in one room. One night a pipe bursts in that building. The room is gone, the backup tapes are in a box in the same building, and the shop is shut for days. Another night, only one worker falls ill, and the shop carries on fine. The same word, “down”, hid two very different troubles. Before you buy anything, you have to say which troubles you plan to live through.

Ask first: what can break, and how big is it?

Each thing that can break has a size. A worker, a machine, a shelf of disks, a whole building, a whole town. Two numbers go with the plan: how long the shop may be shut (“recovery time”), and how many of the last orders it may lose (“recovery point”). Write both down, with the boss’s name beside them. Everything after this is a way to buy those two numbers.

A second building that copies every note

Picture a second shop in another town. Every time the main shop writes a line in its order book, a runner carries that line over, and the second shop writes it too. That is “Data Guard”. The main one is the “primary”; the copy is the “standby”. The runner carries the change notes from Chapter 1 (the “redo”), the second shop keeps them in its own small notebook (the “standby redo log”), and a second helper “applies” them to the copy shelves.

How long does the main shop wait for the runner?

This is the big choice, called the “protection mode”. It is a choice between speed and safety, and each answer has a price.

ModeThe shop…If the copy shop is out of reach
Maximum performance (the default)Says “done” at once; the runner follows behind (async)Carries on. The last few orders may exist only here
Maximum availabilityWaits until the copy has written the note down (sync)Carries on, for a while without protection
Maximum protectionWaits, alwaysStops taking orders rather than risk a loss

So a failure with the first mode can lose the last few orders, and the shop has to say how many it can stand to lose. The last mode loses none but can shut the main shop over a bad road. Most shops choose the middle one when the copy is close, and the first when the copy is far away and the road is slow. If you want to climb from the first to the last, you step through the middle one.

Check the price list

The plain copy is part of the big edition. Reading from the copy while it is being updated is a separate paid extra (“Active Data Guard”). The cheaper edition has no Data Guard at all. Since release 19c it has no RAC either, only a start-over-on-another-machine helper. Check your own licence before you design around it.

Is the copy really a copy?

The most common sad story: a copy that has not kept up for weeks, and nobody looked. A green “all good” light is not proof. On the copy, read the two lags from v$dataguard_stats, and ask the helper tool, called the “broker”, whether a move would work right now.

-- on the copy: how late is it?
SELECT name, value, time_computed
  FROM v$dataguard_stats
 WHERE name IN ('transport lag', 'apply lag');

# in the broker's tool
DGMGRL> VALIDATE DATABASE 'ORDERS_STBY';

Line by line: ask the copy for its two delays and when they were last worked out; then ask the broker if this copy is ready to take over. Zero is healthy. If the copy is down, the numbers can read as unknown or stale, so read the time beside them too.

Two ways to swap places

A “switchover” is a planned swap: the main shop finishes its notes, the copy takes the lead, and the old main becomes the copy. Nothing is lost, and you can swap back. A “failover” is what you do when the main shop is gone: the copy takes the lead with whatever notes arrived, and the old main shop cannot just rejoin. Use the planned swap for chores like Chapter 13’s patching and for drills. Keep the other for the bad night.

DGMGRL> SWITCHOVER TO 'ORDERS_STBY';   # planned, no loss
DGMGRL> FAILOVER TO 'ORDERS_STBY';     # main is gone
DGMGRL> REINSTATE DATABASE 'ORDERS_OLD'; # bring old main back as a copy

The third line works only if the old main shop had its rewind switch on (“Flashback Database”, Chapter 9) before it failed: the tool rewinds it to the moment the copy took over, then it follows as a copy. Without that switch you rebuild it from scratch. Before any failover, make sure the old main shop is truly off. Two shops both writing orders is worse than none.

An automatic version exists, “fast-start failover”. A small watcher process, the “observer”, lives on a third machine and starts the swap by itself when the main shop vanishes. It is fast, and it is also a machine that can be wrong, so decide on purpose whether you want a person in that loop.

Two clerks, one set of shelves

“RAC” is a different idea. Two or more clerks (instances, on separate machines) work at the same shelves. If one clerk falls ill, the other keeps serving, and shoppers may only see a short pause. It is a fine answer for a sick machine or a day of patching, one clerk at a time. But look at the picture: there is one set of shelves. If the shelf room floods, both clerks lose everything together. RAC makes the shop harder to knock over by one worker; it does not make a second building. Many shops use both: clerks to cover machines, a copy shop to cover the building.

What do the shoppers see?

The data can be perfectly safe on the copy while the shoppers still see errors. Why? Their door key points at the old building. Three habits fix most of it. First, the app should ask for a named front door (a “service”, Chapter 5), never the default one and never one machine’s name. Second, make that service “role-based”, so it opens only on whichever shop is currently the lead; after a swap it opens on the new lead by itself. Third, tell the app to wait and try again, since the swap takes a little time.

orders_ha =
 (DESCRIPTION =
  (CONNECT_TIMEOUT=10)(RETRY_COUNT=30)(RETRY_DELAY=2)
  (ADDRESS_LIST =
   (ADDRESS=(PROTOCOL=TCP)(HOST=siteA)(PORT=1521))
   (ADDRESS=(PROTOCOL=TCP)(HOST=siteB)(PORT=1521)))
  (CONNECT_DATA=(SERVICE_NAME=orders_rw)))

Walk through it: list both buildings; ask for the front door that only the lead opens; try again thirty-one times, two seconds apart, which is about a minute. Oracle’s own rule of thumb is that retries times delay should be longer than the longest swap you expect. Orders that were half-way when the swap hit are another matter: newer drivers can replay some of that work (“Application Continuity”, 19c and later), but not every kind, so test your own order flow rather than trust the brochure.

The shop’s drill

The shop picks maximum availability, because the buildings are close. Its written numbers: shut for no more than fifteen minutes, lose no orders. Every quarter it runs the planned swap in daylight with someone timing it. The first drill takes forty minutes. The order screen keeps showing the old building’s name, because one chore script (Chapter 12) had it written in. The fix goes into the runbook. The next drill takes eleven minutes.

The trap: the copy faithfully copied the mistake

On a Tuesday a helper runs a clean-up and deletes the wrong shelf of orders. A moment later the copy shop has deleted it too, because that is its job. Having two buildings did nothing here. The way out is the rewind and backup tools of Chapters 8 and 9, and sometimes a copy told to wait an hour before writing, so there is time to catch such a mistake. Staying up and being able to go back are different gifts; you need both.

Lab: swap places and watch the shoppers

  1. Write your two numbers (shut-time and lost-orders) and the mode that buys them.
  2. On the copy, read both lags. Run VALIDATE DATABASE and read every line, not just the last.
  3. Start a steady stream of test orders from a small program that uses the orders_ha style address. Note the count.
  4. Run a planned SWITCHOVER. Time how long orders fail or wait. Check no order was lost and none doubled.
  5. Swap back. Then, in a throwaway lab only, stop the lead hard, run FAILOVER, and REINSTATE the old one. Note whether the rewind switch was on.
  6. Fix what the drill found (names written in scripts, too-short retry time) and run it again.

Checklist for production

  • Two numbers, shut-time and lost-orders, written and agreed.
  • List what each design survives: worker, shelves, building, bad change.
  • Protection mode matched to distance and to the lost-orders number.
  • Both lags watched and alerted on; VALIDATE before every planned move.
  • Rewind switch on, so an old main shop can be reinstated.
  • Apps use a named, role-based front door and a retry time longer than a swap.
  • Backups and rewind kept, since a copy repeats mistakes.
  • A swap drill each quarter, timed, with the runbook fixed after.
  • Licence and edition checked for Data Guard, the read-only copy, and RAC.

When you know which troubles you can live through, and have rehearsed the swap, the dark night becomes a short, dull task.
