Part II — Build and Administer the Environment

Where All the Room Goes

Real name: Storage, Tablespaces, and Space Management

At two in the morning the order shop stops taking orders. The message says a thing “cannot grow.” Is the shelf full, the room full, or the whole building full? This chapter teaches you to see the layers, so you can tell which one ran out.

The problem

Picture a store room. It has shelves. The shelves hold boxes. The boxes hold small cards. When someone says “we are out of room,” they might mean the box is full, the shelf is full, or the street outside will not let you build a bigger room. Each one needs a different fix. If you fix the wrong one, nothing changes and the shop stays shut.

Lots of people find this maddening, and that is fair, because the house shows only one sad message for many causes. The way out is to know the layers by heart.

The layers, small to big

The smallest piece is a “block”: one card, usually 8 thousand bytes. A run of blocks side by side is an “extent”: a box of cards. All the boxes that belong to one table or one index are a “segment”: one drawer of the store. Drawers live on a shelf called a “tablespace”. A shelf is built from one or more “datafiles”: real files on a real disk.

Today, shelves keep their own list of free boxes inside their own files (a “locally managed” shelf), so finding room is fast. This is the normal way for new shelves in 19c.

The shelves every house has

The house makes some shelves for itself. SYSTEM holds the house’s own notebook (the “data dictionary”). SYSAUX holds helper things, such as the history the house keeps about itself. Keep your own data off both. A shelf for the shop’s data should be made on purpose, and you should name a default shelf so new users do not drop their things into the wrong one.

Two shelves are special. The “undo tablespace” holds the old copies from Chapter 2. The “temporary tablespace” is a table in the hall where a big sort or join spreads papers when they do not fit in memory. Nothing there needs to be kept: when the job ends, the papers are not needed, and the files can be made again.

Small files or one big file

A shelf can be built from many “smallfile” datafiles, each one capped at about 4 million blocks (about 32 GB when a block is 8 KB). Or it can be one “bigfile” datafile that can hold about 4 billion blocks (about 32 TB). One big file means fewer things to name and watch. But one very big file is slow to copy or restore as one piece, so choose with your backup plan in mind (Chapter 8).

Each file may be set to grow by itself, “autoextend”, in steps (NEXT) up to a ceiling (MAXSIZE). This is kind, until it hides a problem: the file grows quietly until the street is full. Set MAXSIZE on purpose, never leave it to chance.

Ask each layer, in order

The first trap: the plain “free space” list can say a shelf is 95 parts full, and the shelf may still have a lot of room, because the files can still grow. The reverse is worse: a shelf may look half empty and the street behind it may be nearly full. A number that includes the growth room is in dba_tablespace_usage_metrics.

SELECT tablespace_name,
       ROUND(used_percent,1) used_pct,
       ROUND(tablespace_size*8192/1024/1024/1024,1) max_gb
  FROM dba_tablespace_usage_metrics
 ORDER BY used_percent DESC;

This lists each shelf, how full it is measured against the biggest it could ever get, and that biggest size. (The 8192 is the card size; change it if yours differs.) Then look at the files of the worst shelf:

SELECT file_name, ROUND(bytes/1048576) mb, autoextensible,
       ROUND(maxbytes/1048576) max_mb
  FROM dba_data_files WHERE tablespace_name = 'ORDERS_DATA';

Line by line: the file name, its size now, whether it may grow by itself, and its ceiling. If a file is at its ceiling, the fix is on the file. If not, look at the street: the free space on the disk, or in the ASM disk group (a set of disks Oracle manages as one pool, where “full” means the pool, not a folder).

The hall table that never looks empty

After a big sort ends, the hall table does not go back to the store. The papers are picked up, but the table stays the same size, kept ready for the next job. So the temporary shelf can look full all day when nothing is wrong. When it truly runs out, a job fails with ORA-01652. First ask who is using it now:

SELECT s.sid, s.username, u.segtype,
       ROUND(u.blocks*8192/1048576) mb, u.sql_id
  FROM v$tempseg_usage u
  JOIN v$session s ON s.saddr = u.session_addr
 ORDER BY u.blocks DESC;

Who, what kind of paper, how many megabytes, and which statement. If the top row is one job that spreads out far more than it should, the job is the thing to fix. If the table is big only because of old work, tell the house to give back what it can: ALTER TABLESPACE temp SHRINK SPACE KEEP 2G;

Throwing things out does not free the room

You delete 80 percent of the old order lines. The drawer is mostly empty, but the shelf is not any freer, and the file has not shrunk. The drawer remembers how far it once stretched (its “high water mark”), and the file still has to hold that stretch. Room comes back only if you ask for it.

Three common ways, from gentle to strong. Shrink the drawer from the inside while people use it (needs a shelf of the normal kind and permission to move rows). Move it to a fresh drawer, which is faster but blocks users for a while and ruins the lists that point at it until they are rebuilt. Empty it with TRUNCATE, only if all of it can go. After the drawer shrinks, the file can be cut down, but only to the last used box: if any drawer sits near the end of the file, the cut fails (ORA-03297).

ALTER TABLE orders.order_lines ENABLE ROW MOVEMENT;
ALTER TABLE orders.order_lines SHRINK SPACE CASCADE;
ALTER DATABASE DATAFILE '/u01/oradata/ORCL/orders01.dbf' RESIZE 20G;

Line 1: allow the house to slide rows. Line 2: pack the drawer and its lists, and give the end back. Line 3: cut the file to 20 GB. If it fails, something still sits past that point. Do not guess; ask where the last drawer is.

Warning

Packing a drawer writes a lot of redo and undo. If the place that keeps old redo (the archive area) is nearly full, a clean-up can start a second fire. Check that room first.

One more hiding place: when you drop a table, the house may only put it in a bin (the “recycle bin”), and its room stays used. DROP TABLE ... PURGE or PURGE TABLESPACE really frees it, and you cannot get it back after.

Each home has its own shelves

From Chapter 3: each home inside the house has its own shelves and files. When you ask about room, first say which home you are standing in. DBA_ views show only the home you are in; the CDB_ ones, asked from the root, show all. A home can be given a cap on its total room, so one home cannot eat the street.

Lab: the shop stops at two in the morning

Use the lab house, Oracle 19c, with a home called orders. The goal: make the shelf run out, read the signs, and try three ways to fix it.

Step 1: Make a small shelf. In the home: CREATE TABLESPACE lab_data DATAFILE SIZE 50M AUTOEXTEND ON NEXT 10M MAXSIZE 200M; and a table lab_big in it, with a user whose default shelf is lab_data.

Step 2: Fill it. Insert rows in a loop until the job stops with ORA-01653. Write down the exact words of the message: it names the table and the shelf.

Step 3: Ask each layer. Run the two queries above. Is the file at MAXSIZE? Is the disk full? Which layer is the answer?

Step 4: Compare three fixes. (a) Raise the ceiling: ALTER DATABASE DATAFILE ... AUTOEXTEND ON MAXSIZE 400M. Quick, but you only moved the wall. (b) Add a second file to the shelf. Same, and the file may be on a different disk. (c) Delete old rows and shrink. Slowest, but it brings back room that was already yours. Write down the cost and risk of each: time, redo made, who is locked out, and whether it can be undone.

Step 5: Prove it. Re-run the insert, then re-run the usage query. Finally, drop the lab shelf with DROP TABLESPACE lab_data INCLUDING CONTENTS AND DATAFILES; and check that the file is gone from the disk.

A misleading sign

The alert says the shelf ORDERS_DATA is 92 percent full, and the night DBA adds 100 GB. The shop still stops. Why? The alert came from a plain free-space list, but the file was already at its ceiling of 32 GB in a smallfile shelf, and the new space was added to the wrong place: a different shelf with a similar name.

Evidence: the ORA-01653 message names the shelf, dba_data_files shows which file is at its ceiling, and the disk check shows the street still has room. Safe fix: add a file to the named shelf, or raise MAXSIZE on the file that is full. Check: rerun the failed job and the usage query. Undo: a file added to a shelf can be dropped only if it is empty, so prefer raising the ceiling when you may need to take it back. Whatever you pick, write down the cause, so the alert looks at the ceiling next time and not the plain free list.

Checklist for production

  • Shop data lives on its own shelves, not in SYSTEM or SYSAUX; a default shelf is set on purpose.
  • Every autoextend file has a MAXSIZE that was chosen, not left open.
  • Alerts read dba_tablespace_usage_metrics and the disk or ASM pool, not the plain free list.
  • Temp and undo shelves are sized for the worst job, and you know who the biggest user is.
  • Growth is recorded weekly (segment sizes per shelf), so you can say how many days are left.
  • Shrinks and moves are done with free room in the archive area and a written undo step.
  • For each home, you know its shelves and its cap.
  • The runbook says in order: which layer, which view, which fix.

When you can name the layer that ran out, a night call becomes one quick look and one right fix, not a guess.
