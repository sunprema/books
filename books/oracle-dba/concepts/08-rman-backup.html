Part III — Protect Data and Recover from Failure

Making Copies You Can Trust

Real name: Backup Engineering with RMAN

The disk that holds the order shop’s data dies on a Tuesday. Someone says, “We have copies, right?” This chapter is about how to answer yes and be right: which bad days your copies can fix, and how you know before the bad day comes.

The problem

Think of a shop that keeps its big ledger in one room. You make a photo of every page each Sunday and put the photos in a drawer in the same room. Then the room floods. The ledger and the photos are both gone. Or the photos are fine, but you never looked at them, and half the pages are blank.

Two questions matter. How much work can the shop lose? (Call that the “recovery point”: how far back in time you may fall.) And how long can the shop stay shut? (The “recovery time”.) Ask the shop’s owner, not the computer. “Lose at most five minutes, shut for at most one hour” is a very different job from “lose a day, shut for a day.”

Keep the diary, not only the photos

A photo of the ledger shows Sunday night. The shop kept taking orders all week. To get back to Tuesday at noon, you need the photo and the diary of every change made after it. The diary is the old redo from Chapter 1. By default the house writes the diary in a small ring of notebooks and writes over the oldest ones. That is fine for a crash, and fatal for a flood.

The fix is to tell the house to keep each full notebook as a file before it writes over it. This is “ARCHIVELOG mode”; the kept files are “archived redo logs”. Without it, you can only go back to the exact time of a copy made with the shop closed. With it, you can copy while the shop is open, and go back to nearly any moment after the copy.

-- as SYSDBA, in the lab house
SELECT log_mode FROM v$database;
SHUTDOWN IMMEDIATE;
STARTUP MOUNT;
ALTER DATABASE ARCHIVELOG;
ALTER DATABASE OPEN;

Line by line: check the mode now; stop the house; start it only far enough to read the control file; switch on diary-keeping; open the shop. This needs a short stop, so plan it.

The helper that knows how to copy

You could copy files with a plain copy command. But an open file changes while you copy it, so the copy can be torn. Oracle ships a helper called “RMAN” (the recovery manager). It reads the files the right way, checks every card as it goes, writes down in the house’s notebook what it saved and where, and later knows what to bring back. Use it, and give it the narrow key from Chapter 7: rman target / as SYSBACKUP, not the master key.

Two kinds of copies, and three ways to do less work

A “backup set” is a packed box in RMAN’s own shape: only cards that hold something, and it may be squeezed smaller. An “image copy” is a plain, whole copy of a file. A box must be unpacked before use. An image copy can be pointed at right away, which makes it fast when time is short, but it is big.

Copying everything every night is slow. So you copy everything once a week (a “level 0”), and each night copy only the cards that changed (a “level 1”). A differential level 1 takes what changed since the last copy of any kind. A cumulative level 1 takes what changed since the last level 0: bigger, but fewer pieces to bring back. To find changed cards fast, the house can keep a list of them (“block change tracking”); that is an Enterprise Edition feature, so check your edition.

Write the plan into the house

RMAN keeps settings. Set them on purpose, once:

CONFIGURE RETENTION POLICY TO RECOVERY WINDOW OF 7 DAYS;
CONFIGURE CONTROLFILE AUTOBACKUP ON;
CONFIGURE BACKUP OPTIMIZATION ON;
CONFIGURE DEVICE TYPE DISK PARALLELISM 2;

Line 1: keep enough copies and diary to reach any moment in the last seven days. Line 2: after each copy, also save the control file and the settings file, and name them so they can be found with nothing else in hand. Line 3: skip files that are already saved and have not changed. Line 4: use two helpers at once.

Line 2 is the one people forget. The control file is the house’s map of where everything is. If the map and the machine are both lost, and no one saved the map under a known name, you have boxes and no way to start. Autobackup is off unless you turn it on.

Key idea

“Retention” does not delete anything. It only decides which copies count as “obsolete”. You then delete them (DELETE OBSOLETE), or the recovery area does when it needs room. The default, if you set nothing, is to keep one copy of each file — which may not reach back as far as you think.

A week, as scripts

-- Sunday
BACKUP INCREMENTAL LEVEL 0 DATABASE TAG 'weekly0';
BACKUP ARCHIVELOG ALL NOT BACKED UP 1 TIMES;

-- Monday to Saturday
BACKUP INCREMENTAL LEVEL 1 DATABASE TAG 'daily1';
BACKUP ARCHIVELOG ALL NOT BACKED UP 1 TIMES;

-- every night, after
CROSSCHECK BACKUP;
DELETE NOPROMPT OBSOLETE;

The diary files are copied once, then not again. The crosscheck asks, “is every file the notebook lists really still there?” Anything missing becomes “expired” in the notebook, so you learn about the gap now. Delete diary files only through RMAN. If someone removes them by hand, RMAN still thinks they exist, and you find out on the bad day.

Where the copies live

Ask of each bad day: does a copy survive it? A file lost: the copy next to it is fine. A disk lost: copies on the same disk are gone. A machine or room lost: only copies somewhere else survive. So keep the first copy near, for speed, in the “fast recovery area”, and a second copy far away. When the near area fills up, the house cannot keep new diary files and the shop can freeze (ORA-19809 and friends), so watch v$recovery_area_usage. For a bigfile shelf (Chapter 6), remember one huge file is one huge piece to bring back.

If you have homes inside the house

From Chapter 3: connected to the root, BACKUP DATABASE copies the whole house and every home. BACKUP PLUGGABLE DATABASE orders copies one home, and one home can be brought back without stopping the others.

Prove it, in three steps of growing strength

A copy nobody has tried is a hope. There are three ways to check, and each is stronger than the one before.

  • Read the files. BACKUP VALIDATE CHECK LOGICAL DATABASE; reads every card in the live files and reports the broken ones. It writes nothing. It checks the shop, not the copies.
  • Read the copies. RESTORE DATABASE VALIDATE; reads the boxes it would use and checks they can be unpacked. It does not bring anything back.
  • Bring it back, somewhere else. Restore onto another machine, open it, and ask the shop’s own questions: are the last orders there? This is the only proof that covers the whole chain, from the map to the diary.

Also ask the house to list what has no safe copy: REPORT NEED BACKUP; and REPORT UNRECOVERABLE;. And have it tell you how each night went:

SELECT status, input_type,
       ROUND(elapsed_seconds/60) mins,
       TO_CHAR(start_time,'YYYY-MM-DD HH24:MI') started
  FROM v$rman_backup_job_details
 ORDER BY start_time DESC
 FETCH FIRST 10 ROWS ONLY;

Each row is one night: did it work, what did it copy, how long, and when. Run the scripts from a scheduler that stops and shouts when RMAN ends with an error code, not one that only checks the script started. A slow rise in minutes is a warning too.

Lab: make a plan, then break the shop on purpose

Use the lab house, Oracle 19c. The goal: build the weekly plan, then prove it by bringing the shop back on a second machine or a second folder.

Step 1: Write the goal. On paper: at most 15 minutes lost, back in 2 hours. Say which bad days it must survive.

Step 2: Switch on the diary. Use the lines above, then check log_mode says ARCHIVELOG.

Step 3: Configure and copy. Use the four settings, run the level 0, add some orders, run a level 1, add more orders, and switch the diary file so the last changes are kept: ALTER SYSTEM ARCHIVE LOG CURRENT; then back up the archived logs.

Step 4: Check the three ways. Run the read-the-files and read-the-copies checks. Run REPORT NEED BACKUP; and read the answer.

Step 5: Prove it. On the second place, with the same settings file and the copies, start the house in the lightest state, restore the settings file and the map from the autobackup, then restore and recover the data, and open it. Count the orders. Write down the minutes it took, and compare with your goal of 2 hours.

A misleading sign

Every morning the report says COMPLETED, in green. The disk fails. The restore stops: the diary files from Wednesday on are missing. The night job copied the data, and a tidy-up script run by hand had removed the old diary files from the disk, so the nightly diary copy found nothing to copy and said nothing.

Evidence: LIST BACKUP OF ARCHIVELOG ALL shows a gap in the numbers; CROSSCHECK ARCHIVELOG ALL marks files expired; the alert log shows the sequence skip. Safe fix: take a new level 1 at once, so the gap no longer matters for new days, and move the tidy-up into RMAN: DELETE ARCHIVELOG ALL BACKED UP 2 TIMES TO DEVICE TYPE DISK; (or set the archived log deletion policy). Check: the sequence numbers are whole from the last level 0 to now, and a fresh read-the-copies check passes. Undo: there is no undo for lost diary files; that is why you find out before the bad day, and why a restore on a second machine goes on the calendar.

Checklist for production

  • The owner has written the recovery point and recovery time, and the plan is built from them.
  • The database is in ARCHIVELOG mode, and archived logs go to RMAN-managed storage with a deletion policy.
  • Autobackup of the control file and settings file is ON, and you know where it lands.
  • A retention policy is chosen on purpose, and obsolete copies are removed through RMAN.
  • One copy is fast and near; one copy survives the loss of the machine and the room.
  • The recovery area is watched; a full one stops the shop.
  • Jobs are run by a scheduler that alarms on a failed exit code and on a growing run time.
  • Reads of the files and the copies run on a schedule, and a real restore on a second machine runs on the calendar, with its time written down.
  • Backup jobs use the narrow backup key, and no password is left in a script.
  • Your edition supports what the plan uses (for example block change tracking).

When you have tried your copies, a lost disk is a bad hour with a known end, not a bad week with no end.
